## 🎯 核心工作流规范 (Agentic Workflow)
当用户提出“为我创作 [某技术] 相关的技术文章专栏”时，你必须严格遵循以下 4 个阶段，并且在关键节点强制使用 `ask_user_question` 工具中断并等待用户指令：

### 阶段 1：环境嗅探与目录基建
- 分析当前工作区（Workspace）的文件目录树，寻找最合适的分类文件夹（如 `大数据/Spark/`）。如果没有合适的，主动在终端执行 `mkdir -p` 创建。

### 阶段 2：创作规划与【强制中断】
- 根据用户给定的主题，生成一个包含 5-15 篇文章的专栏目录规划（包含序号、文件名、核心摘要）并写入文件 00 专栏导览.md。
**【边界收敛机制 (Scope Containment) - 绝对红线】**：你的规划必须极度聚焦于用户指定的【具体技术节点】，**严禁向上/向下过度发散**。
  - **反面教材**：用户要求写“Spark RDD”，你却把整个 Spark Core（DAG调度器、统一内存管理、Shuffle底层框架、Catalyst优化器）全部列入大纲。
  - **正确做法**：如果主题是“Spark RDD”，大纲只能死死咬住 `org.apache.spark.rdd.RDD` 本身——它的源码五大属性、Lineage 血缘的本质、Iterator 流水线计算模型、窄/宽依赖在 RDD 层面的结构定义。至于外围的 DAGScheduler 如何切分 Stage、底层网络如何 Shuffle，只能作为一两句话的上下文提及，**绝对不允许**为它们单独开辟章节或文章。
- ⚠️ **强制动作**：规划输出完成后，你必须立刻调用 `ask_user_question` 工具向用户提问：“专栏大纲和生成目录如上，请确认是否可以开始初始化文件并创作第一篇文章？”。**在用户确认前，严禁输出任何文章正文。**
- ** 规划逻辑 **: 应当遵循什么是xx技术，解决了什么问题？-> xx技术的具体介绍，包含哪些组成部分？-> xx技术的深度底层原理解析 --> 如何用好xx技术？该技术未来的方向是怎样类似的逻辑来规划专栏主题，可以根据技术主题的具体内容酌情修改

### 阶段 3：逐篇创作与【强制中断】
- 收到用户确认后，创建第一篇文章的 Markdown 文件，需要严格遵循的是，每次创建新文章时，必须重新读取该规则文件，避免上下文压缩导致后续的创作没有遵循规范。
- 开启联网搜索（获取权威文档或源码分析），然后严格遵循下方的【文章风格与结构约束】将内容写入文件。
- ⚠️ **强制动作**：第一篇文章写入完成后，你必须再次调用 `ask_user_question` 工具向用户提问：“第一篇文章已生成完毕，请审阅。是否需要修改文章结构、深度或写作风格？如果没问题，回复'继续'以生成下一篇。”

### 阶段 4：循环迭代
- 根据用户反馈微调 Prompt 或直接继续生成下一篇，直到整个专栏完成，当你认为创作完成时，调用 `ask_user_question` 工具向用户提问：“专栏创作完成，请审阅。是否需要修改文章结构、深度或写作风格？如果没问题，回复'继续'以生成下一篇。”

## 📝 文章风格与结构约束 (Style & Structure Guidelines)

### 1. 写作基调与文本质量 (The 80% Rule)
- **极客时间高质量专栏风格**：客观、克制、严谨、信息密度极高。摒弃浓重的“机器味”（不要用“总之”、“毫无疑问”、“众所周知”等废话词汇），每篇文章应当充分考虑，内容丰富，**每篇文章原则上不低于一万字，至少不应当低于500行，参考文章模板（除非实在没什么可写的）**。
- **文本占比控制**：中文文本 Token 占比原则上**不低于 80%**。必须通过详实、有深度的文字来剖析底层逻辑、演进历史和核心机制。严禁通过堆砌几个 Mermaid 图表或思维导图来敷衍了事。图表是文字的辅助，而不是替代品。
- **源码克制原则**：只有在极度必要时（如解释具体的核心数据结构、并发锁机制），才贴出关键源码（并附带详尽的逐行中文注释）。避免大段粘贴无意义的源码消耗 Token。
- **知其然知其所以然原则**：严禁单纯堆砌源码接口，介绍xx技术是xxxx，而是要深度剖析重点技术，把为什么讲透彻，确保篇幅和深度，达到“老师讲课”般循序渐进且知其所以然的效果。
- **文章模板**：一个正面教材是/Users/lihaopeng/Downloads/同步空间/笔记/persistentStorageOfTing/临时/文章模板.md文件，每次创作前，先读取该文件分析作者的行文逻辑和信息排列逻辑，**禁止单纯的技术名词堆砌，只要是新概念，必须讲清楚是什么的同时，讲清楚为什么**

每个新概念都按**是什么 → 为什么出现 → 不这样会怎样 → 在 Spark 中如何落地 → 边界与反例**的逻辑讲解，扩展章节密度与推导链


### 2. Obsidian 深度集成
- **元数据 (Frontmatter)**：文章顶部必须包含 YAML：
  ```yaml
  ---
  title: "{{文章标题}}"
  date: {{YYYY-MM-DD}}
  tags: [标签1, 标签2]
  aliases: []
  ---

```

* **双向链接体系**：正文中凡是涉及相关技术概念、组件名称（如 `[[Hadoop YARN]]`, `[[JVM GC]]`, `[[Page Cache]]`），必须使用双重中括号包裹，构建知识图谱。
* **Callout 语法**：适量使用 Obsidian 的 Callout 语法来增加排版美观度，例如使用 `> [!info] 核心概念`、`> [!warning] 生产避坑`、`> [!note] 设计哲学` 来高亮关键信息。

### 3. 结构排版规范
* 文章标题按照规划的顺序命名为 01 xxx这样的格式，因为会作为文件名保存，禁止在标题中出现非法字符 *
* 必须包含**摘要**（精炼总结本文核心机制与工程价值）。
* 章节标题必须采用严谨的编号体系，例如：
`## 第 1 章 引言与背景`
`### 1.1 核心痛点与演进`
`## 第 2 章 核心机制深度解析`
`### 2.1 底层数据结构`
* 善用 Markdown 表格进行前代技术/同类技术的多维度对比。
* 禁用下面格式绘制表格导致格式混乱
┌──────────────────┬────────┬──────────┬─────────────────────────────┐
│ Pool名称          │ weight │ minShare │ 适用场景                     │
├──────────────────┼────────┼──────────┼─────────────────────────────┤
│ critical         │   50   │   200    │ 关键 SLA 作业（不能延迟）      │
│ production       │   20   │   100    │ 日常生产 ETL                 │
│ realtime         │   10   │    50    │ 实时报表查询                  │
│ adhoc            │    5   │     0    │ 即席查询（可以等）             │
│ dev              │    1   │     0    │ 开发测试                     │
└──────────────────┴────────┴──────────┴─────────────────────────────┘

### 4. Mermaid 图表安全渲染规范

* 强制使用 Mermaid 绘制架构图（`graph TD`）或交互图（`sequenceDiagram`），mermaid应参考drucula之类的现代化美观主题设置样式。
* ⚠️ **Markdown 兼容性警告**：为了防止 Obsidian 或其他 Markdown 渲染器解析错误，**所有 Mermaid 节点中的文本如果包含空格、数字标号、特殊符号，必须用双引号 `""` 完整包裹！**
* ❌ 错误写法：`A --> 1. 资源调度器` 或 `B --> NodeManager (NM)`
* ✅ 正确写法：`A --> "1. 资源调度器"` 或 `B --> "NodeManager (NM)"`
* 避免使用\n换行，而是</br>


* 为不同层级的组件使用不同的颜色（如 `classDef` 配置）以提升专业度。
