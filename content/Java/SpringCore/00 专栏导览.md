# Spring Core 源码机制专栏导览

## 这一列怎么读

Spring 的坑大多不在"不会用"，而在"不知道它在哪一刻做了什么"——为什么构造器里用 `@Autowired` 是 NPE、为什么 `@Transactional` 加在 `private` 上不生效、为什么 `@Async` 遇到循环依赖直接报错、为什么有些 Bean 会跳过一次 AOP。这些问题的答案都在容器的时序里。

十个位置按"容器的启动顺序"排：模块与 `refresh()` 骨架（01）→ 取 Bean 的路径（02）→ Bean 定义从哪来（03）→ 一个 Bean 的完整生命周期（04）→ 注入与循环依赖（05）→ AOP 织入（06）→ 事务（07）→ 事件（08）→ 表达式与属性（09）→ 九个扩展点收口（10）。

每一篇都尽量落到源码级：方法名、调用链、`ThreadLocal` 在哪、哪个回调在第几步。

## 与另外两列的边界

| 专栏 | 写什么 |

| `Java/OOP设计模式/09` | 模式视角：框架为什么必须这么用（`FactoryBean`、AOP 代理选择、`@Transactional` 失效五因、事件与事务的顺序） |

三列之间互不重复：涉及另两列已写过的点，本列只给一句结论 + 双链。

**技术版本**：Spring Framework 6.x / Boot 3.x。`javax.*` 已全部迁到 `jakarta.*`；`@Configuration` 的 `proxyBeanMethods` 在 Framework 6.2 的 javadoc 里**默认仍是 `true`**——默认关闭的是 Boot 的 `@AutoConfiguration`（它自带 `proxyBeanMethods = false`），这两件事容易混。

## 一条排查顺序

遇到"Bean 不对劲"时，按这个顺序定位：

| 现象 | 先去哪篇 | 看什么 |
| :--- | :--- | :--- |
| 构造器里拿不到注入的字段 | 04 | 构造器执行时 `populateBean` 还没跑 |
| `@Transactional` 不生效 | 06 / 07 | 是否走了代理、`rollbackOn` 的默认值、是否自调用 |
| 循环依赖启动失败 | 05 | 是否构造器注入、是否 `@Async`（它的后处理器不重写 `getEarlyBeanReference`） |
| 事件没触发 | 08 | `@EventListener` 的注册晚于早期事件、`fallbackExecution` 默认 false |
| 自定义 `BeanPostProcessor` 注入了业务 Bean | 10 | 会触发 `is not eligible for getting processed by all BeanPostProcessors` |
| `@Value` 拿到的是字面量 | 09 | `${}` 在定义阶段替换、`#{}` 在 `getBean` 阶段求值 |
