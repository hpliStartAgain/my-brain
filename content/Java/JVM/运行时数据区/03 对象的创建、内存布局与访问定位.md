# 03 对象的创建、内存布局与访问定位

> [!abstract] 摘要
> 当 Java 代码执行一条 `new Object()` 时，JVM 内部究竟发生了什么？一个 Java 对象在内存中是如何排列其字节的？`obj.field` 这样一次字段访问，底层经历了怎样的指针追踪？本文逐层回答这三个问题，并把每个机制的"为什么"讲到源码与位布局级别。**对象创建**：`new` 指令触发的五步流程——类加载检查、内存分配（指针碰撞/空闲列表 + TLAB 无锁分配及其慢路径处理）、零值初始化、设置对象头、执行 `<init>`；同时补充逃逸分析与标量替换如何让部分对象根本不经过这条流程。**对象内存布局**：逐位解析对象头（Mark Word 在不同 JDK 版本下的位布局演进、偏向锁的兴衰、HashCode 的惰性计算）与 Klass Pointer（及其独立的压缩机制——Compressed Class Space），实例数据的字段重排序，以及 **CompressedOops** 如何用 4 字节表示 32GB 堆内的任意对象引用，包括零基压缩、位移压缩与堆基址加法三种编解码路径。**对象访问定位**：HotSpot 选择直接指针而非句柄池背后的工程权衡，并与 IBM OpenJ9 的句柄方案做对比。这些知识是理解 [[volatile与内置锁/04 synchronized 的锁升级——偏向锁、轻量级锁与重量级锁]] 中 Mark Word 位变化、[[对象生命周期与GC/04 垃圾回收基础——可达性分析、安全点与安全区域]] 中 GC Roots 遍历与对象移动、[[执行引擎/12 JIT 编译与逃逸分析——从解释执行到本地代码]] 中标量替换的物理基础，以及生产中 `jol`（Java Object Layout）工具输出的理论支撑。

## 第 1 章 从 new 到对象可用的五步流程

### 1.1 第一步：类加载检查

当 JVM 遇到一条 `new` 字节码指令时，它首先检查这条指令的参数（一个常量池中的符号引用，指向目标类）能否在常量池中定位到对应的类，并检查这个类是否已经被加载、解析和初始化过。

如果没有，则必须先触发该类的**类加载过程**（见 [[类加载器/10 类加载机制——双亲委派模型与打破它的场景]]）。类加载完成后，JVM 才知道这个类的内存布局，知道需要为对象分配多少字节的内存空间。

**为什么必须先做这一步**：对象的内存分配是一个纯粹的"按大小切一块内存"的机械操作，它的前提是"大小"这个数字必须提前确定。如果类还没有被解析，JVM 根本不知道这个类有多少个字段、每个字段占多少字节、需不需要继承父类的字段——分配内存这件事无从谈起。类加载检查因此成为整条流程里唯一一个可能涉及"重量级"操作（磁盘 I/O、字节码解析、符号引用解析）的步骤，其余四步都是纯内存操作。

**一个容易被忽视的细节**：对象大小在类加载的**准备阶段**就已经完全确定，并不是在创建对象时动态计算的。JVM 在准备阶段会根据类的字段描述符，按 [[02 运行时数据区——堆、栈、方法区的内存布局]] 中描述的方法区元数据规则，计算出该类实例需要的确切字节数（包括对齐填充），并保存在类的元数据（`InstanceKlass`）中的一个字段 `_size_helper` 里。后续每次 `new` 这个类时，直接读取这个预计算好的大小分配内存，不需要重新遍历字段列表——这是"分配对象为什么这么快"的第一个原因：**耗时的计算工作被提前到了类加载阶段，创建对象时只剩下查表和搬指针**。

> [!note] 不这样会怎样
> 如果 JVM 选择在每次 `new` 时都重新计算对象大小（遍历字段描述符、计算对齐），对象分配这个高频操作就会附带一次并不算轻量的元数据遍历。对于一个每秒创建数百万临时对象的高吞吐服务，这个开销会被无限放大。提前计算并缓存，是"一次计算、无数次复用"的典型工程权衡。

### 1.2 第二步：分配内存

类加载检查通过后，JVM 为新生对象**在 Java 堆中分配内存**。所需内存大小在类加载时已经确定，分配过程本质上是从堆中划出一块对应大小的区域。

分配内存有两种策略，选择哪种取决于堆中内存是否规整（是否带有碎片）：

**策略 1：指针碰撞（Bump-the-Pointer）**

前提：堆内存是规整的——所有已用内存在左边，所有空闲内存在右边，中间有一个指针作为分界点。

分配方式：将指针向空闲方向移动对象大小的距离。简单、快速、无碎片。

适用收集器：Serial、ParNew（都使用带压缩的复制/整理算法，堆总是规整的）

**策略 2：空闲列表（Free List）**

前提：堆内存不规整，已用和空闲内存相互交错，JVM 维护一张记录空闲内存块的列表。

分配方式：从空闲列表中找到一块足够大的区域分配，并更新列表。

适用收集器：CMS（使用标记-清除算法，不压缩，堆会产生碎片）

**为什么会有两种策略并存**：分配策略本质上是收集器算法的副产物。指针碰撞要求堆规整，这是"标记-复制"和"标记-整理"算法的天然结果（复制/整理之后必然规整）；空闲列表则是"标记-清除"算法不做移动、必然留下碎片的必然结果。分配器没有独立的设计空间——它只能适配收集器留下的堆形态。这也是为什么 G1、ZGC 这类基于 Region 的收集器在 Region 内部依然可以使用指针碰撞（因为 Region 内部的分配总是从局部规整区域中进行）。

**并发安全的分配**：

多线程同时分配对象时，指针碰撞的"移动指针"操作不是原子的，需要同步。如果不做任何同步处理，两个线程可能同时读到同一个分配指针的旧值，各自认为自己"抢到"了同一块内存，随后各自把对象写进去——这是一次真实的内存踩踏（对象越界重叠），后果是数据错乱甚至 JVM 崩溃。JVM 有两种处理方式：

1. **CAS + 失败重试**：用 CAS 原子地更新分配指针，失败则重试。简单，但高并发下竞争激烈——每个线程分配对象都要跟其他所有线程抢同一把"堆分配锁"（即那个全局分配指针），线程数越多，CAS 失败重试的次数越多，分配吞吐量反而随线程数增加而下降。

2. **TLAB（Thread-Local Allocation Buffer）**：每个线程预先在 Eden 区申请一块私有缓冲区，线程在自己的 TLAB 中分配时完全无需同步。只有 TLAB 用完需要申请新 TLAB 时才需要同步。这是 HotSpot 的默认策略（`-XX:+UseTLAB`，默认开启）。

#### 1.2.1 TLAB 为什么能做到"无锁"

TLAB 的本质是**把"多线程争用一个全局分配指针"的问题，转化为"多线程各自拥有一个私有分配指针"的问题**。全局层面仍然有一个 Eden 区的分配指针需要同步，但同步的频率从"每次 `new` 对象"骤降为"每次 TLAB 用尽需要重新申请一块"——如果每个 TLAB 默认能容纳成百上千个中小对象，同步频率就降低了两到三个数量级。这正是并发系统里常见的"批量化换锁频率"的思路，和数据库连接池、内存池的设计哲学一脉相承。

线程拿到 TLAB 之后，在 TLAB 内部分配对象仍然是最朴素的指针碰撞——只是这次碰撞的指针是线程私有的，不需要 CAS，一条简单的加法指令就能完成。这也解释了"HotSpot 里对象分配是所有操作中最快的路径之一"这个说法的物理基础：绝大多数分配请求最终落地为几条机器指令（比较剩余空间、移动指针、返回地址），没有系统调用、没有锁、没有原子操作。

#### 1.2.2 TLAB 的大小与动态调整

TLAB 不是固定大小的。HotSpot 默认开启自适应调整（`-XX:+ResizeTLAB`），JVM 会根据每个线程近期的对象分配速率动态调整分配给它的 TLAB 大小：分配频繁、TLAB 经常很快用尽的线程会获得更大的 TLAB；分配稀疏的线程分到的 TLAB 会缩小，避免浪费 Eden 空间。也可以用 `-XX:TLABSize` 显式指定初始大小（不设置则由 JVM 按线程数量和 Eden 大小估算一个初始值）。

**TLAB 分配失败之后走哪条路——这才是真正考验设计的地方**：当一个对象请求的大小超过当前 TLAB 剩余空间时，JVM 面临三种选择，具体走哪一条由分配请求的大小与 TLAB 剩余空间、TLAB 总大小的比例共同决定（由 `-XX:TLABRefillWasteFraction` 这个"浪费容忍度"参数控制，它定义了一个阈值——TLAB 剩余空间与 TLAB 总容量的比值如果小于这个阈值，剩余空间会被当作"可接受的浪费"直接丢弃）：

1. **丢弃当前 TLAB 的剩余空间，重新申请一块新 TLAB**：如果剩余空间很小（低于浪费容忍阈值），继续在原 TLAB 里挤根本挤不出下一个对象的空间，索性放弃这点残余空间（计入"TLAB 浪费"统计），从 Eden 区重新申请一块完整大小的新 TLAB，再在新 TLAB 里分配对象。这一步涉及一次 CAS（争用 Eden 区的全局分配指针），但发生频率远低于每次对象分配。

2. **直接在 Eden 区分配，不经过 TLAB（Direct Allocation in Eden）**：如果这个对象本身就很大（相对 TLAB 容量而言），即使换一块新 TLAB 也难以容纳，或者换新 TLAB 划不来（会造成更大浪费），JVM 会跳过 TLAB，直接对 Eden 区的全局分配指针做一次 CAS 分配。这条路径退化为"CAS + 失败重试"策略，但只针对个别大对象，不影响 TLAB 给其余小对象带来的整体收益。

3. **Eden 区本身空间不足，触发 Minor GC**：如果连 Eden 区都腾不出这么大一块连续空间，说明 Eden 已经"满"了，JVM 会触发一次 Minor GC 回收 Eden 中的垃圾对象，GC 结束后再重新尝试分配。若对象过大以至于连整个新生代都无法容纳（超过某个阈值，不同收集器判断逻辑不同——例如 G1 会把超过 Region 一半大小的对象当作"巨型对象 Humongous Object"特殊处理，直接分配在老年代对应的连续 Region 中），则可能直接在老年代分配，绕开新生代的分配路径。

> [!info] 核心概念：分配路径是分层降级的
> TLAB 分配 → TLAB 换新 → Eden 直接分配 → 触发 GC → 老年代兜底，这是一条典型的"先走最快路径，逐级降级到更通用但更慢的路径"的设计。绝大多数对象（占比通常在 99% 以上）在第一层就完成分配，只有少数偏大或偏"不合时宜"（正好撞上 TLAB 边界）的对象才会走到后面几层。理解这条降级链，是理解 JVM 分配吞吐量为什么在正常情况下几乎不随对象大小敏感的关键——因为绝大多数请求根本没有走到需要真正同步的那一层。

**零 TLAB 化的场景**：如果显式关闭 TLAB（`-XX:-UseTLAB`），所有分配都会退化为对 Eden 全局分配指针的 CAS 竞争，在高并发场景下会显著拖慢分配速度，这也是为什么该参数几乎不会在生产环境中被关闭——它是压测时用来验证"TLAB 到底带来多大收益"的对照实验参数，而不是生产调优选项。

> [!warning] 生产避坑：TLAB 相关的常见误区
> 1. 认为调大 `-Xmn`（新生代大小）就能线性提升 TLAB 效率——实际上 TLAB 大小是自适应的，单纯增大新生代只是让更多线程能同时拿到足够大的 TLAB，并不会改变单个 TLAB 内分配的原理。
> 2. 混淆"对象分配在 TLAB 里"与"对象在 TLAB 生命周期内"——TLAB 只是一段被预先占用的 Eden 内存区间，对象一旦分配完成，它的存活周期与 GC 分代规则完全无关，TLAB 只是"分配时"的加速手段，不影响对象后续的晋升与回收逻辑。
> 3. 排查"为什么明明堆够用还频繁 Minor GC"时，容易忽略 TLAB 换新失败或大对象绕过 TLAB 直接吃掉 Eden 剩余空间的情况，可以通过 `-Xlog:gc+tlab=trace`（JDK 9+ 统一日志）观察 TLAB 的申请、浪费和换新频率。

### 1.3 第三步：零值初始化

内存分配完成后，JVM 将分配的内存空间（不包括对象头）**全部初始化为零值**：`int` → 0，`boolean` → false，`Object` → null，`long` → 0L……

这一步保证了 Java 对象在程序员显式赋值之前，其字段就已经有了确定的初始值，不会出现 C 语言那样的"未初始化变量包含随机值"的问题。这就是为什么你可以在 Java 中直接调用 `new int[100]`，得到的数组元素保证全是 0。

**为什么一定要做零值初始化，而不是"谁用谁负责初始化"**：如果 JVM 不保证零值，未初始化的内存区域会残留上一次使用者留下的脏数据（这块物理内存之前很可能被其他已经被回收的对象占用过）。这不仅是一个"代码不优雅"的问题，更是一个**安全问题**——脏数据可能意外暴露之前对象的内容（例如一个刚被回收的密码字段的残留字节），或者导致程序在字段被赋值之前就读取到一个语义上不可能出现的值（比如一个从未被设置过的对象引用字段读出一个非 null 的野指针），从而引发极难复现的偶发性 Bug 甚至内存安全漏洞。Java 选择在语言规范层面把这个不确定性彻底消除掉，代价是每次分配都多一步清零操作。

**这一步在 TLAB 场景下几乎免费**：因为 TLAB 内存本身在被线程首次申请时，通常已经被 JVM 批量清零过（`-XX:+ZeroTLAB` 控制是否在申请 TLAB 时立即清零，或者延后到实际分配对象时按需清零）。对单个对象而言，清零的开销和对象大小成正比，但由于现代 CPU 对连续内存写入有很好的向量化和缓存预取支持，这部分开销通常远小于人们的直觉。

**零值初始化与局部变量的区别**：局部变量（存储在虚拟机栈中）不会自动零值初始化，使用前必须显式赋值。编译器（`javac`）会在编译期通过数据流分析强制检查局部变量是否被初始化，未初始化就使用会导致编译错误 `"variable might not have been initialized"`。而实例字段（存储在堆中）受零值初始化保护，不需要显式初始化就可以使用。

> [!note] 不这样会怎样
> 局部变量之所以不需要零值初始化，是因为它由编译器静态检查兜底——编译期就能保证不存在"读到未初始化局部变量"的路径，运行时清零的成本可以省掉。而实例字段的初始化路径太多（反射、序列化反序列化、`Unsafe.allocateInstance` 绕过构造方法等），编译期无法穷尽所有场景，因此必须依靠运行时清零这个"兜底保证"。这是一个典型的"编译期能保证就不做运行时开销，编译期保证不了就必须运行时兜底"的设计取舍。

### 1.4 第四步：设置对象头

零值初始化完成后，JVM 需要填写**对象头（Object Header）** 中的元数据：

- 将对象的类型信息（指向 `Klass` 的指针，即 Klass Pointer）写入对象头
- 根据当前 JVM 的状态设置 **Mark Word**（哈希码、GC 分代年龄、锁状态标志）

对象头的结构是本文第 2 章的核心内容，后面详细展开。

### 1.5 第五步：执行 `<init>` 方法

以上步骤完成后，从 JVM 的角度看，一个对象已经"存在"了（内存分配好了，对象头也填写完毕）。但从程序员的角度看，对象还没有按照程序员的意图完成初始化。

最后一步，JVM 执行对象的 **`<init>` 方法**（由 `javac` 将构造方法、实例变量初始化语句和实例初始化块合并生成），按照程序员编写的逻辑设置实例字段的值、调用父类构造方法等。

执行完 `<init>` 之后，一个真正意义上"可以使用"的对象才产生。

> [!note] 设计哲学
> 将"对象创建"分为"JVM 层面的内存分配和对象头初始化"与"程序层面的 `<init>` 初始化"两个阶段，是 JVM 设计精巧之处。前者是纯机械的内存操作，速度极快（TLAB 场景下只需要移动一个指针）；后者才是真正执行用户代码，时间取决于构造方法的复杂度。这个分层也使得 JVM 可以在分配完内存后立即设置对象头（如锁状态、GC 信息），而不需要等待 `<init>` 完成。
>
> 这个分层还带来一个反直觉但真实存在的现象：一个尚未执行完 `<init>` 的对象，理论上已经可以被其他线程通过"逸出的 `this` 引用"访问到——如果构造方法内部把 `this` 传给了另一个线程（例如注册监听器、启动子线程），那个线程看到的对象字段可能仍是零值。这正是"构造函数中不要让 `this` 逸出"这条编码规范背后的内存模型原因。

### 1.6 逃逸分析：并非所有对象都会走完这五步

上面五步描述的是"对象在堆上分配"的标准路径。但现代 HotSpot 的即时编译器（JIT）在满足条件时，可以让部分对象**完全绕开堆分配**。

**逃逸分析（Escape Analysis）** 判断一个对象的生命周期是否"逃逸"出了创建它的方法或线程。如果一个对象不会被返回、不会被赋给堆上的字段、不会被传递给无法分析的方法、也不会被其他线程共享，JIT 就可以对它做**标量替换（Scalar Replacement）**——把这个对象拆解成几个局部变量，完全不创建对象实例，也就没有第 1.1~1.5 节描述的任何一步会发生。

```java
void processRequest() {
    Point p = new Point(3, 4);           // p 不逃逸：局部变量，未被返回、未被赋给字段
    double dist = Math.sqrt(p.x * p.x + p.y * p.y);
}
// 经标量替换后，Point 对象完全消失，p.x、p.y 变成两个普通的局部整型变量
```

这解释了一个常见的困惑：为什么大量创建短命小对象（`Point`、临时的 `Optional`、`StringBuilder`）在实测中不一定带来预期中的 GC 压力——如果这些对象不逃逸且所在方法足够小到能被内联，JIT 根本不会走到本章描述的堆分配路径。逃逸分析和标量替换的完整机制，详见 [[执行引擎/12 JIT 编译与逃逸分析——从解释执行到本地代码]]。

> [!warning] 生产避坑
> 逃逸分析依赖内联，而内联对方法体大小、调用点是否单态（monomorphic）有严格限制。不要把"逃逸分析能省去分配"当作可以无限制创建局部对象的免死金牌——一旦对象被传给一个无法内联的调用（例如一个多态严重、经常触发去优化的方法），标量替换就会失效，对象老老实实走完五步流程进入堆。生产环境应通过 `-XX:+PrintEscapeAnalysis -XX:+PrintEliminateAllocations`（Debug 版 JVM）或 JFR 的分配采样来验证假设，而不是凭直觉判断。

## 第 2 章 对象的内存布局

### 2.1 三个组成部分

一个 Java 对象在堆内存中，由三个部分依次排列：

```
对象内存布局（64 位 JVM，开启 CompressedOops）：

┌─────────────────────────────────────────────────────────────┐
│                       对象头（Header）                        │
│  ┌────────────────────────────────────────────────────────┐  │
│  │             Mark Word（8 字节，64 位）                   │  │
│  ├────────────────────────────────────────────────────────┤  │
│  │         Klass Pointer（4 字节，开启压缩指针后）           │  │
│  └────────────────────────────────────────────────────────┘  │
├─────────────────────────────────────────────────────────────┤
│                    实例数据（Instance Data）                   │
│  按字段类型紧密排列（可能有字段重排序优化）                      │
├─────────────────────────────────────────────────────────────┤
│                    对齐填充（Padding）                         │
│  将对象总大小补齐为 8 字节的整数倍（0~7 字节）                  │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 Mark Word——对象头的核心

**Mark Word** 是对象头中信息密度最高的部分，只有 8 字节（64 位 JVM），却要承载多种状态下的不同信息，做到这一点靠的是**多路复用（Multiplexing）**——根据最低几位的**标志位（tag bits）**，整个 Mark Word 有完全不同的解释方式。

**为什么要做多路复用，而不是给每种状态单独留一块空间**：如果给"HashCode""GC 年龄""锁信息""GC 标记"每种用途都单独分配固定空间，对象头会膨胀到远超 8 字节——而对象头是每一个对象都必须携带的固定开销，哪怕只增加 4 个字节，在一个持有几千万对象的堆里也会累积成上百 MB 的额外占用。HotSpot 的设计者观察到一个关键事实：**这几种信息在时间维度上几乎互斥**——一个对象在同一时刻只可能处于一种锁状态，锁信息和 HashCode 也很少同时需要（详见下文），于是选择用最低几位区分当前"该怎么解释剩下的位"，把 8 字节压榨到极限。这是空间换算法复杂度的典型取舍：读写 Mark Word 时永远要先判断标志位再解释剩余内容，增加了少量分支判断的 CPU 开销，换来的是每个对象节省数字节的空间。

**64 位 JVM 中 Mark Word 的位布局**（bit 0 为最低位）：

| 锁状态 | bit 0~1（lock） | bit 2（biased_lock） | Mark Word 剩余内容 |
| :--- | :--- | :--- | :--- |
| **无锁 / 从未加锁（Normal）** | `01` | `0` | 对象 HashCode（31 位）+ 1 位未用 + GC 年龄（4 位） |
| **可偏向但未加锁（Biasable）** | `01` | `1` | 全 0（线程 ID 为空）+ Epoch（2 位）+ 1 位未用 + GC 年龄（4 位） |
| **偏向锁（Biased）** | `01` | `1` | 持有偏向的线程 ID（54 位）+ Epoch（2 位）+ 1 位未用 + GC 年龄（4 位） |
| **轻量级锁（Lightweight）** | `00` | — | 指向线程栈中 Lock Record 的指针（62 位） |
| **重量级锁（Heavyweight）** | `10` | — | 指向 Monitor 对象的指针（62 位） |
| **GC 标记（Marked for GC）** | `11` | — | GC 内部使用，语义随收集器实现变化 |

> [!info] 核心概念：Mark Word 的多路复用
> 一个 Java 对象从无锁 → 偏向锁 → 轻量级锁 → 重量级锁的整个加锁升级过程，本质上就是 Mark Word 内容的变化过程——升级本身不需要挪动对象、不需要重新分配内存，只是原地重写这 8 个字节。[[volatile与内置锁/04 synchronized 的锁升级——偏向锁、轻量级锁与重量级锁]] 中对此有详细剖析。GC 年龄（4 位，最大值 15，对应 `-XX:MaxTenuringThreshold=15`）也编码在 Mark Word 中——这就是为什么 `MaxTenuringThreshold` 的上限是 15，因为 4 位最多表示 0~15，这是位布局对 JVM 参数取值范围的硬约束，不是人为规定的"经验值上限"。

**偏向锁的历史转折**：偏向锁在设计之初假设"锁大概率只被一个线程使用"，通过在 Mark Word 里直接记录线程 ID 省去 CAS 操作。但从 JDK 15 起（JEP 374），HotSpot 默认**关闭**了偏向锁（仍可通过 `-XX:+UseBiasedLocking` 显式开启），原因是现代应用框架（尤其是使用大量线程池、协程式调度的框架）中"锁长期被同一线程独占"的假设越来越不成立，偏向锁的撤销成本（下文详述）在这些场景下反而成为负担；同时轻量级锁路径本身已经过持续优化，收益差距缩小。这是一个"曾经普适的优化，随着典型工作负载变化而被重新评估"的真实案例——理解 Mark Word 的位布局演进，本身就是理解 JVM 优化策略如何随时代变化的一个窗口。

**HashCode 的惰性计算**：

`Object.hashCode()` 返回的身份哈希码（Identity HashCode，与 `equals` 无关的那个基于对象创建时刻的随机数或地址相关信息计算的哈希码）**只在第一次调用 `hashCode()` 时才计算，计算后存入 Mark Word**（无锁状态下的 31 位 HashCode 字段）。

这带来一个有趣的约束：当对象处于**偏向锁状态时**，Mark Word 中没有空间存放 HashCode（偏向锁占用了大部分位用于线程 ID）。如果对一个已偏向的对象调用 `hashCode()`，JVM 必须**撤销偏向锁**（revoke biased lock），将其降为无锁或直接升级为轻量级/重量级锁状态，才能在 Mark Word 中存入 HashCode。撤销偏向锁不是一个廉价操作——它可能需要暂停持有偏向的线程（安全点相关机制，详见 [[对象生命周期与GC/04 垃圾回收基础——可达性分析、安全点与安全区域]]）来确认该线程当前是否真的在使用这个锁。这就是为什么大量调用 `hashCode()` 的对象（如作为 `HashMap` 的 key）不适合使用偏向锁——偏向锁的撤销开销会超过它带来的收益，这也是 JDK 15 默认关闭偏向锁的现实依据之一。

**GC 年龄的极限**：

对象每在 Survivor 区经历一次 Minor GC，Mark Word 中的 GC 年龄字段（4 位）加 1。年龄达到 `-XX:MaxTenuringThreshold`（默认 15，也是最大值，因为 4 位只能表示 0~15）时，对象晋升到老年代。如果想将 `MaxTenuringThreshold` 设置为 16，JVM 会报参数不合法——这正是 Mark Word 的位布局决定的，不是配置文件里可以随意突破的软限制。

> [!warning] 生产避坑
> 排查"为什么对象总是提前晋升老年代"时，容易只关注 `-XX:MaxTenuringThreshold` 的配置值，却忽略了 HotSpot 的**动态年龄判定**机制——即使 `MaxTenuringThreshold` 设置为 15，只要 Survivor 区中某个年龄段的对象总大小超过 Survivor 空间的一半（`-XX:TargetSurvivorRatio` 相关逻辑），JVM 会直接把该年龄及以上的对象提前晋升，不会等到年龄真正达到 15。这个机制同样是通过读取和重写 Mark Word 中的年龄字段实现的，与本节讨论的位布局是同一套物理机制的两种应用场景。

### 2.3 Klass Pointer——类型信息的入口

**Klass Pointer** 是对象头的第二部分，它是一个指向 JVM 内部 `Klass` 对象（C++ 实现的类元数据结构，存储在 [[02 运行时数据区——堆、栈、方法区的内存布局]] 所述的 Metaspace 中）的指针，代表"这个对象是哪个类的实例"。

`Klass` 及其子类（`InstanceKlass` 代表普通类，`ArrayKlass` 及其子类代表数组类型）本身不是 Java 对象，而是 JVM 内部的 C++ 结构，是"类"这个概念在运行期的物理化身。通过 Klass Pointer，JVM 可以：

- 知道对象的类型（用于 `instanceof` 判断、多态分派）
- 找到对象所有字段的布局信息（用于 GC 扫描对象中的引用字段——GC 遍历一个对象时，正是靠 Klass 元数据里记录的"哪些偏移量是引用类型"才知道该往哪里递归标记）
- 找到对象的虚方法表（vtable，用于虚方法调用分派）

在 64 位 JVM 中，如果不进行压缩，一个 Klass Pointer 需要 8 字节。开启**压缩类指针（CompressedClassPointers）** 后，Klass Pointer 只需要 4 字节。

> [!warning] 容易混淆的两个开关
> `-XX:+UseCompressedOops` 和 `-XX:+UseCompressedClassPointers` 是**两个独立的开关**，分别压缩堆里对象引用（heap oop）和对象头里的 Klass Pointer，很多资料把它们混为一谈。二者默认都在满足条件（64 位、堆或类空间足够小）时自动开启，但控制的内存区域完全不同——前者作用于堆，后者作用于下文的 Compressed Class Space。关闭 `UseCompressedOops` 并不会自动关闭 `UseCompressedClassPointers`，反之亦然（虽然实际上 HotSpot 在 `UseCompressedOops` 关闭时通常也会关闭类指针压缩，因为二者共享一部分基础设施，但这是实现细节而非规范要求）。

**Klass Pointer 的压缩靠的是另一块独立内存区域**——**压缩类空间（Compressed Class Space）**。这是 Metaspace 内部专门划出的一块连续区域（默认容量由 `-XX:CompressedClassSpaceSize` 控制），所有 `InstanceKlass` 元数据都集中分配在这块连续区域内。因为区域连续且有固定基址，JVM 可以像压缩堆引用一样，把指向这块区域内的 8 字节地址压缩成一个相对基址的 4 字节偏移量。这与 CompressedOops 压缩堆引用的原理是同一套思路的两次独立应用，但物理上是两套完全独立的地址空间、两套独立的基址和位移参数，互不影响。

### 2.4 CompressedOops——用 4 字节寻址 32GB

**什么是 CompressedOops（压缩普通对象指针）？**

在 64 位 JVM 中，所有对象引用（Ordinary Object Pointer，OOP）原本是 64 位（8 字节）的指针。如果堆中有 10 万个对象，每个对象平均有 5 个引用字段，那么仅引用字段就占用约 10万 × 5 × 8 = 4MB。相比之下，32 位 JVM 中相同场景只占用 2MB。

64 位的引用带来了大量额外的内存开销，同时降低了 CPU 缓存利用率（缓存行中能存储的引用数量减少了一半，意味着同样大小的缓存能容纳的对象图深度减半，间接引用带来的缓存未命中概率上升）。这不是一个理论问题——在 JDK 6 刚普及 64 位部署时，社区实测发现同一个 Java 应用从 32 位迁移到 64 位后，内存占用普遍上涨 30%~50%，GC 停顿时间也随之增加，直接原因就是所有引用字段翻倍。这正是"不这样会怎样"的真实历史答案：CompressedOops 不是锦上添花的优化，而是 64 位 JVM 能被大规模生产采用的前提条件之一。

**CompressedOops 的解决思路**：

Java 对象在堆中的内存地址是 **8 字节对齐**的（对象大小必须是 8 的倍数，见 2.6 节）。这意味着堆中任意对象的起始地址的低 3 位（bit 0~2）永远是 0。

既然低 3 位永远是 0，为什么要存储它们？可以把这 3 位"借"出来——将 32 位的压缩指针（称为 narrow OOP）左移 3 位，就得到真实的 64 位地址：

```
真实地址（64 位）= 压缩指针（32 位）<< 3 + 堆基址（heap base）

理论寻址范围：2^32 × 8 = 32GB
```

**编解码不是只有一种算法，而是三种，取决于堆的实际布局**：

| 编码模式 | 触发条件 | 解码公式 | 说明 |
| :--- | :--- | :--- | :--- |
| **Unscaled（不移位）** | 堆整体位于地址空间前 4GB 以内 | `真实地址 = narrow oop` | 堆足够小，32 位本身就能直接表示地址，连移位都省了 |
| **Zero-based（零基移位）** | 堆位于地址空间前 32GB 以内，且 JVM 成功将堆基址预留在低地址（base = 0） | `真实地址 = narrow oop << 3` | 只需移位，不需要加基址，比一般情况少一次加法运算 |
| **Heap-based（基址移位）** | 堆基址不为 0（操作系统或其他原因导致堆没有分配在低地址） | `真实地址 = (narrow oop << 3) + heap_base` | 通用情况，多一次寄存器加法 |

这张表揭示了一个容易被忽略的事实：**CompressedOops 的性能收益不仅来自"节省内存"，还取决于 JVM 能不能把堆预留在低地址**——如果操作系统的地址空间布局随机化（ASLR）或者其他限制导致堆基址不为 0，每次指针解引用都要多做一次加法。HotSpot 启动时会主动尝试把堆预留在有利的低地址区间，以争取落入 Unscaled 或 Zero-based 这两种更快的模式，这也是为什么同一段 Java 代码在不同操作系统、不同启动参数下，指针解引用的微观性能可能存在细微差异。

用 32 位（4 字节）的压缩指针，就能寻址 32GB 以内的整个堆。当堆大小 ≤ 32GB 时（`-Xmx` ≤ 32g），JVM 默认开启 CompressedOops（`-XX:+UseCompressedOops`）；超过 32GB 则自动关闭，改用 8 字节原始指针。

**为什么上限恰好是 32GB，而不是 4GB（32 位指针本来能表示的范围）**：如果不利用"低 3 位永远是 0"这个对齐特性，32 位裸指针只能表示 4GB 地址空间。左移 3 位相当于把可表示的地址范围放大了 8 倍（`2^3`），代价是牺牲了寻址粒度——不能表示任意字节地址，只能表示 8 字节对齐的地址。这个代价对 Java 对象来说是免费的，因为 Java 对象本来就必须 8 字节对齐（详见 2.6 节），压缩指针不需要表示"对象内部某个字节"的地址，只需要表示"某个对象的起始地址"，而起始地址天然满足 8 字节对齐——这是一次"利用已有约束换取额外收益"的精妙设计，而不是巧合。

**CompressedOops 的工程意义**：

1. **内存节省**：64 位 JVM 开启压缩指针后，引用字段内存开销与 32 位 JVM 相同（均为 4 字节），配合 64 位的大堆，兼顾了内存效率与寻址能力。

2. **缓存友好**：同样大小的对象，压缩指针版本能在 CPU 缓存行中存下更多引用字段，缓存命中率更高。一个典型的例子是链表和树这类"指针密集"的数据结构，压缩指针能让同一个缓存行容纳两倍数量的节点指针，遍历时缓存未命中率显著下降。

3. **为什么 32GB 是"悬崖"**：很多公司将 JVM 堆大小上限设为 31GB 或 30GB，就是为了保持在 32GB 以内，确保 CompressedOops 持续生效。一旦堆超过 32GB，压缩指针关闭，所有引用字段从 4 字节变 8 字节，内存占用可能反而比 30GB 堆更大（对象数量不变但每个对象更大），这是反直觉的性能"悬崖"。

> [!warning] 生产避坑
> 一个常见的误解：把堆从 30GB 增大到 34GB，以为能缓解内存压力。实际上，一旦超过 32GB，CompressedOops 关闭，所有对象的引用字段内存占用翻倍，导致有效载荷（业务数据）占比下降，GC 压力反而可能上升。正确做法：要么保持 ≤ 32GB，要么直接部署多个 JVM 实例（每个实例 ≤ 32GB），水平扩展。判断当前 JVM 是否处于 CompressedOops 生效状态，可以用 `java -Xmx32g -XX:+PrintFlagsFinal -version | grep UseCompressedOops` 直接查看该布尔标志的最终取值，而不是仅凭堆大小配置去猜测。

### 2.5 实例数据——字段的紧凑排列

实例数据区存储对象真正的有效数据——类定义的所有实例字段（不包括 static 字段，static 字段存在方法区）。

**字段排列顺序与重排序优化**：

JVM 不保证字段在内存中的顺序与源码中声明的顺序相同。HotSpot 默认按照**字段类型大小进行排序**（从大到小）以减少内存对齐损耗：

```
默认字段排列顺序（HotSpot）：
long / double（8 字节）
int / float（4 字节）
char / short（2 字节）
byte / boolean（1 字节）
Object 引用（CompressedOops：4 字节；原始：8 字节）
```

**为什么要重排序，而不是按声明顺序原样排列**：如果严格按照声明顺序排列字段，很容易在两个不同大小的字段之间产生"对齐空洞"——例如一个 `boolean` 后面紧跟一个 `long`，`long` 要求 8 字节对齐，编译器/JVM 就必须在 `boolean` 后面填 7 个字节的空洞才能让 `long` 落在对齐边界上。如果类里有多个这样"大小交错"的字段，空洞会累积成相当可观的浪费。按大小从大到小排列，能让大字段先"吃满"对齐边界，小字段自然地填进后面产生的缝隙里，整体空洞最小化。这是一个典型的"贪心装箱"问题的简化解，JVM 没有做全局最优装箱（那样开销太高），而是用一个简单的排序规则拿到足够好的效果。

父类的字段在子类字段之前。父类字段末尾可能有空洞（为了对齐），子类字段可能"插入"父类的空洞中（由 `-XX:+CompactFields` 控制，JDK 8+ 默认开启）。

> [!note] 不这样会怎样
> 如果关闭 `CompactFields`（或者在不支持该优化的旧版本 JVM 上），子类字段永远从父类字段结束的下一个对齐边界开始排列，父类留下的空洞永远不会被填充，继承层次越深，累积的浪费空间越多。对于字段稀疏、继承层次深的领域模型（DDD 中常见的多层继承实体），这个差异在大规模对象场景下会直接反映在堆内存占用上。

**用 JOL 工具查看真实布局**：

```java
// 使用 Java Object Layout (JOL) 工具分析对象布局
// 依赖：org.openjdk.jol:jol-core

public class LayoutExample {
    boolean flag;   // 1 byte
    int value;      // 4 bytes
    long bigValue;  // 8 bytes
    String str;     // 4 bytes（CompressedOops）

    public static void main(String[] args) {
        System.out.println(ClassLayout.parseClass(LayoutExample.class).toPrintable());
    }
}
```

典型输出（64 位 JVM，开启 CompressedOops，JDK 17）：
```
LayoutExample object internals:
OFFSET  SIZE   TYPE DESCRIPTION
     0     4        (object header: mark)    ← Mark Word 低 4 字节
     4     4        (object header: mark)    ← Mark Word 高 4 字节
     8     4        (object header: class)   ← Klass Pointer（4 字节，压缩）
    12     4    int value                    ← int 字段（4 字节，排在 long 前，因为有空位）
    16     8   long bigValue                 ← long 字段（8 字节，8 字节对齐）
    24     4 String str                      ← 引用字段（4 字节，压缩）
    28     1 boolean flag                    ← boolean 字段（1 字节）
    29     3        (alignment/padding gap)  ← 对齐填充（3 字节，使总大小=32，是8的倍数）
Instance size: 32 bytes
```

注意：虽然源码中 `boolean flag` 先声明，但 JVM 将 `int value` 排到 `flag` 前面（字段重排序），充分利用了 Klass Pointer 后面的 4 字节空隙（否则需要 4 字节填充）。这正是上一小节讲的"贪心装箱"规则的真实产出——`int value` 恰好能填满对象头之后的空隙，避免了额外的对齐填充字节。

### 2.6 对齐填充——整理内存的"垫片"

Java 对象的大小**必须是 8 字节的整数倍**。这是 CompressedOops 能够工作的前提（低 3 位为 0 才能"免费"存储，见 2.4 节），同时也有利于 CPU 缓存行对齐（64 字节缓存行恰好能容纳整数个对象，减少一个对象跨两个缓存行导致的"伪共享"式额外开销）。

当对象头 + 实例数据的总字节数不是 8 的整数倍时，JVM 在末尾填充若干字节（0~7 字节）的**对齐填充（Padding）**，使总大小达到 8 的整数倍。对齐填充没有任何实际意义，纯粹是为了满足内存对齐要求。

**最小对象的大小**：

一个完全没有实例字段的 `Object` 对象（`new Object()`）在 64 位 JVM + 压缩指针下的大小是：

```
Mark Word（8 字节）+ Klass Pointer（4 字节）= 12 字节
→ 补齐至 8 的倍数 = 16 字节（填充 4 字节）
```

所以 `new Object()` 在 HotSpot JVM 中占用 **16 字节**，不是直觉上以为的 0 字节或 8 字节。

> [!info] 核心概念：对齐填充与 CompressedOops 是同一套约束的两个表现
> 8 字节对齐这条规则同时服务于两个目的——它是 CompressedOops 得以把地址左移 3 位的前提，也是这里对齐填充存在的原因。二者不是两个独立的设计决定，而是"对象必须 8 字节对齐"这一条底层约束在不同场景下的两次体现。理解了这一点，就不会奇怪为什么关闭 CompressedOops（比如堆超过 32GB）之后，对象仍然要求 8 字节对齐——对齐要求本身独立于压缩指针是否启用，只是压缩指针恰好利用了这个既有约束。

## 第 3 章 数组的内存布局

数组的内存布局与普通对象略有不同：在对象头之后、实例数据之前，有一个额外的 **Array Length** 字段（4 字节），记录数组的长度：

```
数组对象内存布局：
┌─────────────────────────────────────────────────────────┐
│  Mark Word（8 字节）                                     │
├─────────────────────────────────────────────────────────┤
│  Klass Pointer（4 字节，压缩）                           │
├─────────────────────────────────────────────────────────┤
│  Array Length（4 字节）                                  │
├─────────────────────────────────────────────────────────┤
│  数组元素 [0]  [1]  [2]  ...  [n-1]                     │
│  （每个元素按其类型占相应字节数，int[] 每个 4 字节）        │
└─────────────────────────────────────────────────────────┘
```

**为什么数组需要单独存一个 Array Length 字段，而普通对象不需要**：普通对象的字段数量和布局在类加载时就已经固定死了（见 1.1 节），运行期不需要再查询"这个对象有多少个字段"——直接靠 Klass 元数据里记录的固定偏移量访问即可。但数组的长度是运行期才确定的（`new int[n]` 的 `n` 是一个变量），同一个 `int[]` 类型的不同实例可以有不同长度。JVM 必须把这个"实例特有"的长度信息存在实例本身而不是类型元数据里，这正是数组类型 `ArrayKlass` 与普通类型 `InstanceKlass` 在实例布局上分道扬镖的根本原因——数组访问越界检查（`ArrayIndexOutOfBoundsException`）也正是靠这个 Array Length 字段实现的，每次数组元素访问，JVM 都会拿下标和这个字段比较。

`new int[100]` 在 64 位 JVM（CompressedOops）下的大小：
- 对象头：8（Mark Word）+ 4（Klass）+ 4（Array Length）= 16 字节
- 数组元素：100 × 4（int）= 400 字节
- 总计：416 字节（恰好是 8 的倍数，无需填充）

对于引用类型数组（如 `Object[100]`），每个元素占用一个压缩指针的大小（开启 CompressedOops 时为 4 字节），这也是"存放大量对象引用时优先用数组而不是链式结构"在内存紧凑性上更占优的直接原因——数组没有链表节点那样额外的对象头开销，元素之间是完全连续、紧密排列的。

## 第 4 章 对象的访问定位

### 4.1 为什么需要"定位"

Java 程序通过栈上的**引用（reference）** 来操作堆上的对象。但 JVM 规范只规定了引用是一个指向对象的类型，并没有规定引用的具体结构——是直接存放对象的堆地址，还是存放指向"对象描述信息"的某种间接引用？

这个规范上的留白不是疏忽，而是有意为之：不同厂商的 JVM 实现可以根据自己的 GC 策略、平台特性选择最合适的引用表示方式。这就引出了两种主流实现方式：**句柄方式**和**直接指针方式**。

### 4.2 句柄方式（Handle Pool）

**工作原理**：JVM 在堆中划出一块区域作为**句柄池（Handle Pool）**，每个对象对应池中的一个句柄。句柄中包含两个指针：
- 指向对象实例数据的指针（对象在堆 Eden/Old 区的地址）
- 指向对象类型数据的指针（Klass Pointer，指向方法区/Metaspace 的类元数据）

栈上的 reference 存储的是句柄池中对应句柄的地址，而不是对象的直接地址。

```
栈 reference → 句柄池[i] ──┬── → 实例数据（堆）
                           └── → 类型数据（方法区）
```

**优点**：当 GC 移动对象（压缩整理后对象地址变化）时，只需更新句柄池中的实例数据指针，所有持有该对象 reference 的栈帧、其他对象，都不需要更新——它们存储的是句柄地址，句柄地址没变。这在 GC 需要频繁移动对象的场景下（例如复制算法、分代收集）是一个显著的简化：需要更新的指针数量从"堆中所有指向该对象的引用"降低为"这个对象唯一的一条句柄记录"。

**缺点**：每次对象访问（字段读取、方法调用）需要两次内存间接寻址（reference → 句柄 → 对象），相比直接指针多一次指针追踪，性能较低。句柄池本身也需要额外的内存空间，且句柄池自身的管理（分配、回收、扩容）也是一份额外的簿记成本。

### 4.3 直接指针方式（Direct Pointer）

**工作原理**：栈上的 reference 直接存储对象在堆中的地址（直接指针）。对象头中的 Klass Pointer 存储类型信息指针。

```
栈 reference ──────────→ 实例数据（堆）
                         对象头中有 Klass Pointer → 类型数据（方法区）
```

**优点**：字段访问只需一次内存间接寻址（reference → 对象），速度快。不需要额外的句柄池空间。

**缺点**：GC 移动对象时，必须更新所有指向该对象的引用（栈上、其他对象的引用字段），扫描更新代价高（但实际上 GC 本来就需要遍历所有引用以判断可达性，顺手更新引用值并无额外的"发现"成本，只是多了一次写操作）。

### 4.4 HotSpot 的选择——直接指针

**HotSpot VM 选择了直接指针方式**。理由很简单：**对象访问是程序中最频繁的操作之一**（方法调用、字段读写），每次访问节省一次指针解引用的收益非常显著，远大于 GC 时更新指针的代价（GC 本来就要遍历所有引用）。

这也解释了为什么 HotSpot 的对象头需要包含 Klass Pointer——因为没有了句柄池，类型信息只能存在对象头中，这是 4.2 节和 4.3 节两种方案在对象头设计上的连带差异：选择直接指针，意味着"类型信息去哪里找"这个问题必须由对象自己回答，句柄方式则可以把这个责任转移给句柄池。

**并非所有 JVM 实现都做了同样的选择**。IBM 的 OpenJ9（前身是 IBM J9）历史上就采用过间接的对象访问方案，其设计目标之一是更好地支持某些嵌入式和大内存场景下 GC 压缩的效率。两种设计并没有绝对的"对"与"错"，只是针对不同的典型工作负载（是"对象访问频率"更关键，还是"GC 移动对象的频率和代价"更关键）做出的不同取舍。

| 维度 | 句柄方式 | 直接指针方式（HotSpot） |
| :--- | :--- | :--- |
| 字段访问的间接寻址次数 | 2 次 | 1 次 |
| GC 移动对象时需更新的引用数量 | 1 条（句柄本身） | 所有指向该对象的引用 |
| 额外内存开销 | 句柄池 | 无（但对象头需含类型指针） |
| 更适合的场景 | GC 移动频繁、对象访问相对不那么密集 | 对象访问远比 GC 移动频繁（典型 Java 应用负载） |

> [!note] 设计哲学
> 句柄方式是"稳定性优先"的设计（GC 更新代价低），直接指针是"性能优先"的设计（访问代价低）。HotSpot 选择直接指针，是对"对象访问频率远高于 GC 频率"这一事实的理性回应——一个典型 Java 应用每秒执行的字段访问和方法调用数以亿计，而 GC 引发的对象移动事件即便在高分配速率下也只是"偶发"事件，二者数量级相差巨大，性能优化理应向高频路径倾斜。

## 第 5 章 生产实践：用 JOL 验证与常见误区

### 5.1 用 JOL 观察真实布局与锁状态迁移

Java Object Layout（JOL）是 OpenJDK 官方提供的对象布局分析工具，直接读取 JVM 运行时的真实内存布局，而不是依据理论推导——这一点很重要，因为不同 JDK 版本、不同参数组合下的实际布局可能与手工推算存在细微差异（例如某些 JVM 内部实现细节的调整），JOL 是消除这种不确定性的权威工具。

```xml
<!-- Maven 依赖 -->
<dependency>
    <groupId>org.openjdk.jol</groupId>
    <artifactId>jol-core</artifactId>
    <version>0.17</version>
</dependency>
```

```java
import org.openjdk.jol.info.ClassLayout;
import org.openjdk.jol.vm.VM;

public class JolDemo {
    static class Demo {
        int a;
        long b;
        boolean c;
    }

    public static void main(String[] args) {
        // 查看 JVM 信息（包括指针大小、CompressedOops 是否生效）
        System.out.println(VM.current().details());

        // 未加锁时的对象布局
        Demo obj = new Demo();
        System.out.println(ClassLayout.parseInstance(obj).toPrintable());

        // 加锁后 Mark Word 的变化
        synchronized (obj) {
            System.out.println("Locked: " + ClassLayout.parseInstance(obj).toPrintable());
        }
    }
}
```

通过对比加锁前后的输出，可以直接看到 Mark Word 低几位标志位从"无锁/可偏向"状态迁移到"轻量级锁"或"偏向锁"状态时，那 8 个字节内容的具体变化——这是验证第 2.2 节位布局理论最直接的方式，比对着文字描述在脑中推演更可靠。

### 5.2 常见误区清单

> [!warning] 生产避坑：本文涉及机制的高频误用场景
> 1. **把"对象大小 = 字段大小之和"当作估算依据**：忽略了对象头（通常 12~16 字节）和对齐填充，在评估大批量小对象的内存占用（例如缓存里存放几千万个小 POJO）时会严重低估真实内存开销。正确做法是用 JOL 实测 `Instance size`，再乘以数量。
> 2. **认为关闭 CompressedOops 一定能提升性能**：多数场景下关闭压缩指针只会让内存占用上升、缓存命中率下降，几乎没有正向收益，只有在极端场景（比如需要访问超过 32GB 的单一连续对象图且移位计算本身成为瓶颈，这种场景极为罕见）才可能考虑关闭。
> 3. **对锁频繁竞争的对象上追求"看起来更快"的偏向锁**：偏向锁只在真正意义上"几乎不存在竞争"的场景下有收益，一旦存在竞争，偏向锁撤销的开销比直接使用轻量级/重量级锁更高。JDK 15 之后默认关闭偏向锁正是社区对这一现实的回应。
> 4. **混淆 TLAB 与对象存活周期**：TLAB 只影响分配速度，不影响对象在 Eden/Survivor/老年代之间的迁移与晋升逻辑，二者是完全独立的两套机制，排查 GC 问题时不要把分配路径的问题和晋升路径的问题混为一谈。

## 第 6 章 总结

一个 Java 对象的完整生命周期，从内存视角看是：

**创建**：类加载检查（确定对象大小，提前计算好，避免每次分配都重新计算）→ 堆内存分配（指针碰撞/空闲列表，通过 TLAB 把"全局竞争"转化为"线程私有分配"以消除大部分同步开销，TLAB 用尽后按"换新 TLAB → 直接在 Eden 分配 → 触发 GC → 老年代兜底"的降级链处理）→ 零值初始化（保证字段在被显式赋值前具有确定的、安全的初始值）→ 设置对象头（Mark Word + Klass Pointer）→ 执行 `<init>`。逃逸分析和标量替换可以让部分不逃逸的对象完全绕开这条路径。

**内存布局**：对象头（Mark Word 8 字节 + Klass Pointer 4/8 字节）+ 实例数据（字段按大小从大到小重排序，减少对齐空洞）+ 对齐填充（补齐至 8 的整数倍）。Mark Word 通过最低几位标志位实现多路复用，同时承载 HashCode、GC 年龄、锁状态等多种信息，其位布局直接决定了 `MaxTenuringThreshold` 的取值上限，也决定了 HashCode 计算与偏向锁之间的互斥关系。

**CompressedOops**：将 32 位压缩指针左移 3 位寻址真实地址（视堆基址情况，实际有 Unscaled、Zero-based、Heap-based 三种编解码路径），以 32GB 为上限，在堆 ≤ 32GB 时自动启用，大幅降低 64 位 JVM 的引用字段内存开销；Klass Pointer 的压缩则依赖另一套独立的 Compressed Class Space 机制，二者原理相通但物理上完全独立。

**访问定位**：HotSpot 选择直接指针方案，reference 直接指向对象实例数据，对象头中的 Klass Pointer 再指向类型元数据，一次间接寻址完成对象访问，性能最优——这是"对象访问频率远高于 GC 移动频率"这一现实工作负载特征驱动的工程决策，而不是唯一正确的答案，OpenJ9 等其他实现的句柄方案在不同权衡下同样合理。

下一篇 [[对象生命周期与GC/04 垃圾回收基础——可达性分析、安全点与安全区域]] 将从对象的"出生"转向"死亡"——GC 如何判断对象是否已死，安全点与安全区域如何让 JVM 在不破坏一致性的前提下发起 GC，届时会再次用到本文讲解的对象头结构（GC 标记状态正是复用了 Mark Word 的标志位）与直接指针带来的"移动即更新"的代价模型。
