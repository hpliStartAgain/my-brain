# 05 垃圾回收算法——标记清除、复制、标记整理与分代假说

**摘要：**

上一篇解决了"哪些对象是垃圾"，本篇解决"如何回收这些垃圾"。现代 GC 的所有算法，都是在三种基础算法——**标记-清除（Mark-Sweep）**、**复制（Copying）**、**标记-整理（Mark-Compact）**——的基础上演化而来的。三种算法各有侧重：标记-清除简单但产生碎片，复制高效但浪费空间，标记-整理不碎片化但移动成本高。没有完美的算法，只有针对特定场景的最优权衡。正是这种权衡，催生了**分代收集（Generational Collection）** 的设计——将堆分为新生代和老年代，针对不同年龄段对象的生命周期特征，分别选用最合适的算法。分代收集的理论根基是三条统计意义上的假说：弱分代假说、强分代假说，以及经常被忽略却同样关键的**跨代引用假说**。本文不仅还原三种算法的算法细节与工程取舍（Cheney 扫描算法、分配担保、双指针/表格整理算法的实现差异），还深入剖析了分代 GC 的内在矛盾：跨代引用如何打破分代 GC"只扫本代"的完美假设，以及**记忆集（Remembered Set）** 和**卡表（Card Table）** 如何以写屏障为代价、用空间换时间的方式解决这个矛盾。文末进一步梳理了 Minor GC / Major GC / Full GC 的触发条件与生产排障案例，并对卡表记忆集与 G1 未来将采用的 Region 级 RSet + SATB 方案做了铺垫性对比，为后续章节做准备。

## 第 1 章 三种基础算法：没有完美，只有权衡

### 1.1 垃圾回收的两个阶段

无论哪种 GC 算法，都包含两个核心阶段：
1. **标记（Mark）**：通过可达性分析，找出所有存活的对象（或反过来找出所有垃圾对象）
2. **回收（Sweep/Copy/Compact）**：处理已标记的垃圾，让内存可以被重新使用

三种基础算法在"回收"阶段的处理方式不同，由此带来了各自的优缺点。

值得强调的是，**"标记"阶段的算法几乎是通用的**——不管后续用哪种回收策略，都要先完成一次可达性分析（参见 [[对象生命周期与GC/04 垃圾回收基础——可达性分析、安全点与安全区域]]）。三种基础算法的真正差异，全部体现在标记完成之后，"如何处理内存"这一步上。这意味着理解 GC 算法的关键不是记住三个名字，而是理解"回收"这一步在**是否移动对象**这个维度上做出的不同选择——一旦想清楚这一点，标记-清除、复制、标记-整理之间的所有优缺点都可以被推导出来，而不需要死记硬背。

### 1.2 一个统一的评价框架：四个维度

在分别展开三种算法之前，先建立一套通用的评价坐标系，后面的对比才有共同的度量单位。评价一种 GC 回收策略，通常从以下四个维度衡量：

| 评价维度 | 含义 | 关注点 |
| :--- | :--- | :--- |
| **吞吐量（Throughput）** | 应用程序运行时间占总时间（应用时间 + GC 时间）的比例 | GC 算法本身做的"有效功"占比越高越好 |
| **延迟/停顿（Latency）** | 单次 GC 造成的 STW 时长，以及停顿的可预测性 | 尾延迟敏感的在线服务最关心这一项 |
| **空间利用率（Footprint）** | 堆内存中，有多大比例可以真正用来存放存活对象 | 直接决定同样堆大小下能撑住多少业务数据 |
| **实现/移动复杂度（Complexity）** | 是否需要移动对象、更新引用、维护额外元数据 | 决定了算法能否与并发/增量执行结合 |

没有任何一种算法能在四个维度上同时做到最优——这正是"没有完美算法，只有场景化权衡"的具体含义。标记-清除牺牲空间利用率（碎片）换取了零移动开销；复制算法牺牲 50% 空间换取了近乎最快的分配速度和最低的标记开销；标记-整理牺牲了移动成本换取了空间利用率和无碎片。带着这套框架去看后面每一节的"优势"和"代价"，会发现它们其实都是同一张权衡表在不同轴上的投影。

## 第 2 章 标记-清除算法（Mark-Sweep）

### 2.1 什么是标记-清除

**标记-清除（Mark-Sweep）** 是最早、最基础的垃圾回收算法，1960 年由 John McCarthy 在 Lisp 语言实现中提出——这也是"GC"这个概念在计算机历史上第一次真正落地。

**两个步骤**：
1. **标记阶段（Mark）**：从 GC Roots 出发，通过可达性分析遍历所有可达对象，将其标记为"存活"
2. **清除阶段（Sweep）**：遍历整个堆，将所有未被标记的对象（垃圾）的内存空间**释放（清除）回空闲列表**

```
标记前（M=存活/标记，□=垃圾）：
┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
│M │□ │M │M │□ │□ │M │□ │M │□ │
└──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘

清除后（F=空闲）：
┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
│M │F │M │M │F │F │M │F │M │F │
└──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘
  ↑碎片化：空闲空间不连续，大对象无法分配
```

### 2.2 标记信息存在哪里：从对象头到位图

一个容易被忽略的实现细节是："标记"这个动作本身要有地方存放结果。最直观的做法是在对象头（Mark Word）里预留一个标记位，但这样做有一个副作用——每标记一个对象，就要写一次这个对象所在的那块内存，如果对象分散在堆的各处，这种写操作对 CPU 缓存极不友好（大量的 Cache Miss）。

HotSpot 实际采用的是**位图标记（Bitmap Marking）**：额外维护一块与堆内存平行的位图区域，每个字（或每个可能的对象起始地址）在位图中对应一个比特位，标记时只需要翻转对应比特位，而不需要触碰对象本身的内存。这样一来：
- 标记阶段对堆对象是**只读**的，不会因为写操作污染 CPU 缓存或触发写屏障；
- 清除阶段只需要顺序扫描位图，找到连续的"未标记"区间，再统一处理，天然对缓存友好（顺序访问）；
- 位图本身很小（1 bit 对应 1 个字，通常是堆大小的 1/64 左右），额外内存开销可以接受。

这也是为什么现代收集器（包括 G1、Shenandoah 的并发标记阶段）普遍采用位图而不是对象头标记位来记录"标记状态"——不移动对象的算法里，"标记"本身的实现方式也是有讲究的。

### 2.3 优势：简单，低对象移动开销

标记-清除的最大优势是**不移动对象**——存活对象在回收后仍留在原位置，只是垃圾对象的内存被标记为"可用"。

不移动对象意味着：
- 不需要更新所有指向这些对象的引用（更新引用是一个代价高昂的操作）
- 存活对象的处理速度快（只需标记，不需复制）
- 由于对象地址不变，栈上的局部变量、JIT 编译后内联的直接地址引用都不需要修正，这对并发/增量式回收极其友好——CMS 之所以能做到"标记阶段可以和用户线程并发执行"，一个重要前提正是它选择了不移动对象的标记-清除算法。如果标记的同时对象还在被移动，并发的复杂度会指数级上升。

### 2.4 空闲空间如何管理：空闲列表与分配代价

清除之后留下的空闲内存块，需要某种数据结构去追踪，最常见的是**空闲列表（Free List）**：用双向链表把所有空闲块串起来，每个节点记录起始地址和大小。分配对象时，收集器需要在空闲列表里寻找一块足够大的空闲区域，常见策略有：

- **首次适配（First-Fit）**：从链表头开始，找到第一个足够大的块就用，实现简单但容易在链表前部留下越来越多的小碎片；
- **最佳适配（Best-Fit）**：遍历整个链表，找到最接近所需大小的块，减少浪费但遍历成本更高；
- **分离空闲列表（Segregated Free List）**：按对象大小分桶维护多条空闲列表，分配时直接定位到对应大小的桶，是空闲列表管理里综合表现较好的方案。

无论哪种策略，空闲列表分配都比复制/整理算法之后的"指针碰撞（Bump-the-Pointer）"慢——指针碰撞只是一次比较和一次加法，而空闲列表分配涉及链表遍历、可能的块分裂（分配后剩余部分重新入链）。这正是标记-清除"不移动对象"这一优点带来的直接代价：**存活对象不用挪，但分配变慢了**，天下没有免费的午餐。

> [!note] 设计哲学：TLAB 与空闲列表分配的取舍无关
> 需要澄清一个常见误解：TLAB（Thread-Local Allocation Buffer，参见 [[运行时数据区/02 运行时数据区——堆、栈、方法区的内存布局]]）解决的是"多线程并发分配时的同步竞争"问题，与堆内是空闲列表分配还是指针碰撞分配是两个独立维度。即便在使用空闲列表的分代（如 CMS 管理的老年代），JVM 依然可以在为 TLAB 申请大块内存这一层面减少全局锁竞争；只是 TLAB 内部小对象分配的"指针碰撞"速度优势，仍然只在新生代复制算法下才能真正兑现到最细粒度。

### 2.5 致命缺陷：内存碎片化

标记-清除的致命问题是**内存碎片化（Fragmentation）**：

回收后，空闲的内存块散布在堆的各个位置，不连续。当需要分配一个大对象时，即使堆的空闲空间总量足够，也可能因为没有连续的足够大的空闲块而触发 Full GC 甚至 OOM。

**碎片化导致的连锁问题**：
- 必须使用"空闲列表"来追踪散碎的空闲空间，分配速度比"指针碰撞"慢
- 随着时间推移，碎片越来越多，大对象分配越来越困难
- 最终只能通过 Full GC 进行内存整理，引入长时间 STW 停顿

碎片化还分为两类，容易被混为一谈：**外部碎片（External Fragmentation）** 指空闲空间总量够、但分散在多处无法满足单次大块分配的需求（标记-清除的典型问题）；**内部碎片（Internal Fragmentation）** 指分配器为了对齐或分桶而多划出的、永远无法被利用的浪费空间（比如按 8 字节对齐产生的填充位，参见 [[运行时数据区/03 对象的创建、内存布局与访问定位]]）。标记-清除主要受外部碎片困扰，这也是为什么它天然需要一个"整理"的补救手段（见第 4 章标记-整理）。

**CMS 就是标记-清除算法**（并发版本），因此 CMS 也长期受碎片化问题困扰，最终在 JDK 9 被标记为废弃（Deprecated），在 JDK 14 中被彻底移除。

### 2.6 CMS 碎片化问题的生产表现：从"Concurrent Mode Failure"到 Full GC

标记-清除的碎片问题不是纯理论层面的缺陷，在 CMS 的生产实践中有非常具体的表现形式，值得展开说一下，因为这直接解释了 CMS 为什么会被废弃：

CMS 老年代长期使用标记-清除，不做整理，碎片持续累积。当碎片积累到"总空闲空间够，但没有一块连续区域能容纳当前要晋升/分配的对象"时，会触发两类典型故障：

- **Promotion Failed（晋升失败）**：Minor GC 过程中，Survivor 区的对象要晋升到老年代，却因为老年代碎片化找不到连续空间容纳，晋升失败。此时 JVM 别无选择，只能退化为一次**Serial Old 的标记-整理式 Full GC**来腾出连续空间——而 Serial Old 是单线程、完全 STW 的，停顿时间可能高达数秒。
- **Concurrent Mode Failure（并发模式失败）**：CMS 的并发标记/清除阶段本身也需要分配内存（用户线程仍在运行，仍在创建新对象）；如果在并发回收还没跑完之前，老年代已经被填满，CMS 就无法继续并发工作，只能"退化"为 Serial Old 做一次完整的 Full GC。

这两种故障的本质都是同一个根因：**标记-清除不整理内存，长期运行后碎片必然积累到某个临界点，用一次代价高昂的 Full GC 兜底**。这也是为什么 G1（参见 [[对象生命周期与GC/07 G1 收集器——Region 化内存与混合回收]]）在设计上选择了 Region 化 + 复制式整理，从根本上避免了 CMS 这种"平时很快、偶尔暴击"的不可预测性。

## 第 3 章 复制算法（Copying）

### 3.1 复制算法的思想来源

复制算法（Copying Collection）由 Cheney 在 1970 年提出，核心思想是：**把内存分成两个等大的半空间（From space 和 To space），每次只使用 From space；GC 时将 From space 中的存活对象全部复制到 To space，然后直接清空整个 From space；最后交换 From 和 To 的角色**。

```
GC 前（From 使用中，To 空闲）：
From: │A│B│.│C│.│.│D│.│E│  （A/C/D/E 存活，B 是垃圾，. 是碎片）
To:   │.│.│.│.│.│.│.│.│.│  （空闲）

GC 后（存活对象复制到 To，From 清空）：
From: │.│.│.│.│.│.│.│.│.│  （整个清空，可以直接重用）
To:   │A│C│D│E│.│.│.│.│.│  （连续排列，无碎片）
↑ From 和 To 角色互换，下次 GC 方向反过来
```

### 3.2 Cheney 算法：如何在不用递归的前提下完成一次完整复制

复制算法说起来只有一句话——"把存活对象搬到另一半空间"——但真正的工程难点在于：**存活对象之间彼此引用，复制一个对象时，它内部的引用字段也指向别的对象，怎么保证不重复复制、不遗漏、还不用递归（避免栈溢出）？**

Cheney 在 1970 年给出的答案是用两个指针做一次**广度优先扫描（BFS）**，而不是自然想到的深度优先递归：

- **scan 指针**：指向 To space 中"已经复制过来、但内部引用字段还没有被处理"的对象；
- **free 指针**：指向 To space 中下一个可用于存放新复制对象的位置（本质就是复制算法的"指针碰撞"分配指针）。

算法流程大致是：先把 GC Roots 直接引用的对象复制到 To space（free 指针随之前移），然后 scan 指针从 To space 起始处开始向前推进——每处理一个对象，就检查它的引用字段：如果引用指向的对象还在 From space（尚未被复制），就把它复制到 free 指针位置（free 前移），并在原对象（From space 中）的对象头写入一个**转发指针（Forwarding Pointer）**，指向它在 To space 的新地址；如果引用指向的对象已经有转发指针（说明已经复制过），直接把引用改写为转发指针记录的新地址即可。scan 指针追上 free 指针时，说明所有可达对象都已经处理完毕，复制结束。

这个"两根指针一路向前扫，永不回头"的过程，天然是迭代式的，不需要显式的调用栈或者递归，也不需要额外的标记结构去记录"这个对象是否已经访问过"——转发指针本身既是复制结果的记录，也充当了"已访问"的标记。这是复制算法在工程实现上远比听起来更精巧的地方，也是它能做到"标记"和"复制"合并为一次遍历（而不是先标记再复制两次遍历）的关键。

### 3.3 优势

**无碎片化**：存活对象被紧密地排列在 To space 的开头，内存是连续的，可以用最快的"指针碰撞"方式分配新对象。

**GC 速度快**：只需处理存活对象（复制），不需要遍历整个堆中的垃圾对象。如果存活对象很少（比如新生代 GC 时大多数对象已死），复制的工作量极小，GC 速度极快。

**自动整理**：每次 GC 后，对象紧密排列，顺带完成了内存整理，不需要像标记-整理那样再单独执行一次移动扫描。

### 3.4 代价：空间利用率减半，且不适合高存活率场景

复制算法的代价也很明显：

**空间利用率只有 50%**：始终有一半内存（To space）是空闲的，作为复制目标缓冲区，被"浪费"掉。如果将整个 8GB 堆用于复制算法，有效可用空间只有 4GB。

**存活率越高，代价越大**：复制算法的工作量与存活对象数量成正比。如果 90% 的对象都存活（老年代的典型情况），需要复制 90% 的数据，效率极低。

因此，**复制算法最适合存活率极低的场景**——恰好与新生代的特征完美匹配（弱分代假说：绝大多数对象朝生暮死）。这也是 Java 新生代使用 Eden + S0 + S1 的复制收集方案的根本原因。

### 3.5 新生代的 Eden + Survivor 改良

直接将堆分成两个等大的半空间，50% 浪费太多。HotSpot 对复制算法做了改良：

将新生代分为 **Eden（80%）+ S0（10%）+ S1（10%）**，比例由 `-XX:SurvivorRatio=8` 控制。

每次 Minor GC：
- 存活对象从 Eden + 当前 From Survivor 复制到空的 To Survivor
- Eden 和 From 全部清空
- From 和 To 角色互换

浪费的空间只有 **10%（一个 Survivor 区）**，远比 50% 高效。但有一个前提：存活对象的总大小必须不超过 To Survivor 的容量。如果超过了（某次 GC 存活率特别高），溢出的对象直接晋升到老年代（**分配担保，Allocation Guarantee**）。

### 3.6 对象年龄与晋升：分配担保的具体判定流程

"复制到 Survivor"这句话背后还隐藏着一套完整的年龄判定机制，它决定了对象到底应该继续留在新生代，还是提前"毕业"进入老年代：

**对象年龄计数**：每个对象的 Mark Word 中有一个专门的字段记录"年龄"（Age），初始为 0；每经历一次 Minor GC 依然存活，年龄加 1。年龄字段只有 4 bit，最大值 15，这也是为什么 `-XX:MaxTenuringThreshold` 的默认上限是 15——超过这个阈值，无条件晋升老年代，符合强分代假说"越老越难死，不如提前放进老年代"的判断。

**动态对象年龄判定（Dynamic Age Determination）**：单纯按固定阈值晋升并不智能——如果某一批对象在某次 GC 中大量存活，即使年龄还没到阈值，也应该提前晋升，否则会把 Survivor 区挤爆。HotSpot 的实际策略是：把 Survivor 区中所有对象按年龄从小到大排序，累加各年龄段对象的总大小，一旦累加值超过 Survivor 区容量的一半，就将该年龄及以上的所有对象都晋升到老年代——不必等到 `MaxTenuringThreshold`。这是一种自适应机制，让"晋升时机"跟随实际存活率动态调整，而不是死守一个固定参数。

**分配担保的判定顺序**：当一次 Minor GC 发现存活对象的总大小超过 To Survivor 的容量时，会触发晋升，但晋升的前提是老年代要有足够空间接纳。JVM 在每次 Minor GC 之前，会先检查老年代的连续可用空间是否大于新生代所有对象的总大小（这是最保守的估算）；如果不满足，则进一步检查 `-XX:+HandlePromotionFailure`（JDK 6 之后默认开启）配置下，是否允许根据"之前每次晋升的平均大小"进行担保——如果历史平均值仍大于老年代剩余空间，说明这次 Minor GC 很可能导致晋升失败，JVM 会提前改为直接执行一次 Full GC，而不是先尝试 Minor GC 再半路失败。这正是第 2.6 节提到的 Promotion Failed 场景在参数层面的对应关系。

**大对象的直接晋升**：如果一个对象的大小超过 `-XX:PretenureSizeThreshold` 设定的阈值，会跳过新生代，直接在老年代分配（大对象晋升，Direct Allocation in Old Gen）。这是因为大对象如果先放进新生代，复制它的成本很高（违背了复制算法"只适合小对象、低存活率"的前提），且容易导致 Eden 空间提前耗尽触发频繁 Minor GC。这也是本专栏 [[运行时数据区/03 对象的创建、内存布局与访问定位]] 中提到的对象分配路径的一个分支。

**PLAB——老年代晋升的专属缓冲**：与新生代内部依靠 TLAB 减少多线程分配竞争类似，多个 GC 工作线程并行地把对象晋升到老年代时，也需要避免频繁竞争老年代的分配指针/空闲列表锁。HotSpot 为并行 GC（如 Parallel Scavenge、G1）的每个 GC 线程提供了**PLAB（Promotion Local Allocation Buffer，晋升本地分配缓冲）**——原理与 TLAB 完全一致，只是服务对象换成了"GC 线程晋升对象到老年代"这一场景，而不是"用户线程创建新对象"。

> [!warning] 生产避坑：Survivor 区过小导致的"未熟晋升"
> 如果业务代码中存在大量生命周期略长于一次 Minor GC、但远未达到真正长期存活的对象（比如处理一个较长的请求批次），且 Survivor 区容量设置偏小（`-XX:SurvivorRatio` 设置过大），这些对象会被动态年龄判定提前晋升到老年代——这种现象称为**"未熟晋升"（Premature Promotion）**。未熟晋升的对象很快在老年代变成垃圾，却只能等 Major/Full GC 才能被清理，变相拖慢了老年代 GC 的频率和效率。排查思路是通过 GC 日志（`-Xlog:gc+age=trace`，JDK 9+）观察 Survivor 区各年龄段对象的分布，如果发现低年龄段对象占比异常低（说明它们都被提前晋升走了），就应该考虑调大 `-Xmn` 或调整 `SurvivorRatio`。

## 第 4 章 标记-整理算法（Mark-Compact）

### 4.1 什么是标记-整理

**标记-整理（Mark-Compact）** 是为了解决标记-清除的碎片问题，同时避免复制算法的空间浪费而设计的。

**两个步骤**：
1. **标记阶段（Mark）**：与标记-清除相同，标记所有存活对象
2. **整理阶段（Compact）**：将所有存活对象**向内存的一端移动**，紧密排列；移动完成后，端边界之外的所有内存直接清空（更新为空闲状态）

```
整理前：
┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
│A │□ │B │C │□ │□ │D │□ │E │□ │
└──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘

整理后（所有存活对象向左移动，连续排列）：
┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
│A │B │C │D │E │F │F │F │F │F │
└──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘
                  ↑ 空闲空间：连续大块
```

### 4.2 优势：无碎片 + 空间利用率 100%

标记-整理完美解决了标记-清除的碎片问题，同时不像复制算法那样浪费一半空间：
- **无碎片**：存活对象连续排列，大对象可以正常分配
- **100% 空间利用率**：不需要保留一半空间作为复制目标
- **分配速度快**：整理后可以用指针碰撞分配，速度与复制算法相同

### 4.3 代价：移动对象的高昂成本

标记-整理的问题在于**移动对象的成本极高**：

**更新所有引用**：对象移动后，所有指向它的引用（其他对象的字段、栈上的变量、JNI 全局引用等）都必须更新为新地址。这需要遍历整个堆，工作量巨大。

**STW 时间长**：整理阶段必须在 STW 下进行（否则用户线程可能正在使用旧地址的对象，移动后立即崩溃）。移动大量存活对象（尤其是老年代，存活对象很多）时，STW 时间显著增加。

**CPU 缓存效应**：移动对象会使 CPU 缓存中的数据失效（对象在新位置，缓存中是旧位置的数据），导致后续访问的缓存命中率短暂下降。

因此，标记-整理更适合**老年代**——老年代虽然存活率高（移动对象多），但 GC 频率远低于新生代，整体代价是可以接受的。

### 4.4 移动对象的三种经典实现：双指针、表格法与 Lisp2

"把存活对象移到一端"这句话背后，同样存在着多种工程实现，彼此在遍历次数、额外空间开销上有取舍，值得展开：

**双指针算法（Two-Finger Algorithm）**：用两个指针分别从堆的头部和尾部向中间扫描，头指针找空洞（垃圾对象占用的位置），尾指针找存活对象，找到一对后把尾部的存活对象搬到头部的空洞里，两指针继续向中间靠拢，直到相遇。这种算法的问题是要求堆中所有对象大小相同（否则空洞和待搬移对象大小不匹配，需要额外处理），实用场景有限。

**表格算法（Table-Based Algorithm，也称 Lisp2 算法）**：先完整扫描一次堆，为每个即将移动的存活对象计算出它的目标地址，并把"旧地址 → 新地址"的映射记录下来（可以借用对象头暂存，也可以用独立的转移表）；再做第二次扫描，这次真正搬移对象内容，并同步更新所有引用字段——通过查表把旧地址替换为新地址。这种做法需要**至少两次完整堆扫描**（一次计算地址、一次搬移+修正引用），但对对象大小没有限制，是通用性最好的整理算法，也是 HotSpot Serial Old 收集器（老年代整理阶段）实现思路的原型。

**滑动整理（Sliding Compaction）**：在表格算法基础上进一步要求"移动后对象的相对顺序与移动前保持一致"（即所有对象整体向一端滑动，不打乱原有次序），这样可以避免对象在移动过程中相互覆盖，且有利于保持某些依赖对象分配顺序的局部性优化。HotSpot 的标记-整理实现总体上采用的正是滑动整理的思路。

值得注意的是，不管哪种实现，标记-整理都需要**至少一次额外的"计算新地址+修正引用"遍历**，这正是它移动成本高于复制算法的根本原因——复制算法通过转发指针把"标记、复制、修正引用"三件事在一次 Cheney 式扫描里就干完了，而标记-整理天然需要先算好全局的目标布局，再统一搬移，遍历次数更多。

### 4.5 三种算法的横向对比

| 维度 | 标记-清除 | 复制 | 标记-整理 |
| :--- | :--- | :--- | :--- |
| **是否移动对象** | 否 | 是 | 是 |
| **内存碎片** | 有（严重）| 无 | 无 |
| **空间利用率** | 100% | 50% | 100% |
| **GC 速度（高存活率）** | 慢（需遍历垃圾）| 慢（需复制大量对象）| 慢（需移动大量对象）|
| **GC 速度（低存活率）** | 中 | 快（复制量少）| 中 |
| **分配速度** | 慢（空闲列表）| 快（指针碰撞）| 快（指针碰撞）|
| **遍历堆的次数（一次 GC）** | 1 次（标记+清除可合并）| 1 次（Cheney 扫描合并标记与复制）| 至少 2 次（计算地址 + 搬移修正）|
| **是否适合并发执行** | 相对容易（不移动对象）| 困难（并发时对象地址在变化）| 最困难（移动+修正引用量最大）|
| **最适合** | 老年代（并发版）| 新生代（低存活率）| 老年代（低频率 GC）|

## 第 5 章 分代收集假说——算法选择的理论基础

### 5.1 分代假说的三个核心命题

现代 GC 都遵循**分代收集（Generational Collection）** 理论，其理论基础是三个基于大量程序统计数据的假说——前两个广为人知，第三个则常常被忽略，但恰恰是第 6 章"跨代引用"问题能被高效解决的理论前提。

**弱分代假说（Weak Generational Hypothesis）**：绝大多数对象的生命周期极短，在创建后不久就会变成垃圾。统计数据显示，典型的 Java 程序中，超过 90%（有些场景更高）的对象在创建后第一次 GC 之前就已经死亡。

**强分代假说（Strong Generational Hypothesis）**：经历过越多次 GC 仍然存活的对象，未来继续存活的概率越高。换句话说，"越老越难死"——存活了 100 次 GC 的对象，很可能会继续存活很长时间。

**跨代引用假说（Intergenerational Reference Hypothesis）**：跨代引用相对于同代引用来说仅占极少数——也就是说，老年代对象引用新生代对象的情况客观存在，但数量远小于"同一代内部对象互相引用"的数量。这个假说不直接决定"该用哪种算法"，而是决定了第 6 章要讲的记忆集/卡表方案是否"划算"：如果跨代引用很多，用一个轻量级结构去记录它们就没有意义（记录成本接近于全扫描）；正因为跨代引用是少数，用卡表这种粗粒度、低开销的结构去追踪它们，才能在绝大多数场景下把 Minor GC 的工作量牢牢限制在新生代内部。

### 5.2 假说的实验依据与边界

这些假说并不是凭空的经验之谈，而是来自对大量真实程序堆行为的统计观测——最早的系统性论证来自 David Ungar 1984 年关于"Generation Scavenging"的论文，他对 Smalltalk-80 程序的堆分配做了跟踪统计，发现绝大多数新分配对象存活时间极短，这直接启发了后续几乎所有主流语言运行时（Java、.NET CLR、V8 等）的分代设计。此后针对 Java 程序的大量堆行为分析（包括 Sun/Oracle 官方的 GC 调优文档）反复验证了同样的规律，才使得分代收集成为几乎所有生产级 GC 的标准范式，而不是某一家的特例设计。

但假说终究是"统计意义上"的，不是物理定律，一旦应用的对象分配模式偏离典型模式，假说就会失效或者效果打折：

**缓存密集型应用**：如果应用大量使用长期存活的缓存结构（连接池、Guava Cache、本地二级缓存等），大量对象一开出生就注定长期存活，弱分代假说在这部分对象上完全不成立——它们会迅速晋升到老年代，且在老年代长期占用空间，直到缓存失效或应用重启。这类应用的老年代 GC 压力会显著高于典型 Web 应用，是本文末尾思考题探讨的场景。

**批处理/大数据类应用**：一次性加载大批量数据进行计算（如内存排序、批量聚合），这些对象的生命周期往往与"一批任务"的边界对齐，可能远超一次 Minor GC 的周期，但又不是真正永久存活——它们会先被误判为"老对象"晋升，计算完成后又集中死亡，造成老年代出现大范围的短暂性垃圾潮汐，这与"强分代假说"隐含的"越老越难死"假设也是相悖的。

**弱分代假说与强分代假说本身也存在张力**：弱分代假说说大多数对象死得快，强分代假说说熬过 GC 的对象死得慢——两者合起来描述的其实是一个双峰分布：一部分对象"朝生夕灭"，另一部分对象"活得很久"，中间地带（活过几次 GC 但又没活很久）的对象比例较小。这也是为什么"晋升阈值"（`MaxTenuringThreshold`）只需要一个不太大的数字（默认参考值通常在 15 以内）就能有效地把两类对象分开，而不需要精细调参——大多数场景下，对象的存活时间分布确实呈现出比较清晰的双峰特征。理解这一点，才能明白为什么分代假说在工程上"够用"，而不需要更复杂的统计模型。

### 5.3 从假说到工程设计

这两个假说直接推导出了分代 GC 的设计决策：

**基于弱分代假说**：将大多数新创建的对象集中在**新生代（Young Generation）**。由于新生代中绝大多数对象很快死亡，GC 后存活的对象极少，特别适合**复制算法**——复制量少，速度快，且可以高频率执行（因为每次停顿时间短）。

**基于强分代假说**：将经历多次 GC 仍存活的"老"对象晋升到**老年代（Old Generation）**。老年代中存活对象多、GC 频率低，**标记-整理或标记-清除**更合适（复制算法在高存活率时代价过高）。

**基于跨代引用假说**：不需要为了追踪少数跨代引用而牺牲分代 GC 本身的效率，用一套轻量级的辅助结构（记忆集/卡表，详见第 6 章）以极低的额外成本换取正确性。

**分代 GC 的核心收益**：通过将不同生命周期的对象隔离到不同区域，每次 GC 只需要扫描其中一个区域，大幅降低了单次 GC 的工作量，提高了整体吞吐量。

### 5.4 Minor GC、Major GC 与 Full GC 的触发条件详解

**Minor GC**（也称 Young GC）：**只回收新生代**（Eden + Survivor）。执行时间：通常几毫秒到几十毫秒（新生代小，存活率低，复制快）。频率：高（可能每隔几秒就触发一次）。

| 触发时机 | 具体条件 | 备注 |
| :--- | :--- | :--- |
| Eden 区分配失败 | 新对象申请空间时，Eden 剩余空间不足 | 最常见、最普遍的触发方式 |
| 大对象分配前的预判 | JVM 预估即将到来的大对象分配可能导致空间不足 | 与老年代空间检查联动 |
| 显式触发 | 部分诊断工具或压测场景手动触发 | 生产环境极少见 |

**Major GC**（也称 Old GC）：**只回收老年代**。并非所有收集器都有单独的 Major GC 概念——CMS 有独立的老年代并发收集周期；G1 在 Mixed GC 阶段也可以只回收部分老年代 Region（这也是 G1 与传统"整代扫描"式 Major GC 的重要区别之一，后续 [[对象生命周期与GC/07 G1 收集器——Region 化内存与混合回收]] 会展开）。

| 收集器 | Major GC 的具体形态 | 触发方式 |
| :--- | :--- | :--- |
| CMS | 独立的并发标记-清除周期 | 老年代占用达到 `-XX:CMSInitiatingOccupancyFraction` 阈值 |
| Parallel Old | 与 Full GC 基本等价（整代标记-整理） | 老年代空间不足 |
| G1 | Mixed GC，只回收部分高价值 Region | Young GC 后老年代占用超过 `-XX:InitiatingHeapOccupancyPercent` |

**Full GC**：**回收整个堆（新生代 + 老年代）以及方法区（元空间）**。通常是因为：
- 老年代空间不足，无法为晋升对象分配内存
- 系统显式调用 `System.gc()`（虽然只是建议，JVM 可能执行 Full GC）
- 元空间（方法区）空间不足
- 大对象直接分配失败
- CMS 出现 Promotion Failed 或 Concurrent Mode Failure（见第 2.6 节），退化为 Serial Old 式 Full GC
- 通过 `-XX:+ScavengeBeforeFullGC` 触发的、Full GC 之前先做一次 Minor GC 的联动场景

Full GC 是代价最高的 GC：涉及整个堆，STW 时间最长（可能数秒），是生产系统性能问题的主要来源之一。**优化 GC，本质上是减少 Full GC 的频率和持续时间**。

> [!warning] 生产避坑
> `System.gc()` 是一个陷阱：它触发的 Full GC 往往在业务低峰期没有问题，但在高并发时调用（比如代码中判断内存不足时手动触发）会造成严重的性能抖动。JVM 参数 `-XX:+DisableExplicitGC` 可以让 JVM 忽略 `System.gc()` 的调用（但要注意，这会影响 NIO 堆外内存的回收，需要 `-XX:+ExplicitGCInvokesConcurrent` 配合）。

### 5.5 一个生产排障案例：元空间引起的周期性 Full GC

分享一个在实践中很常见、但根因容易被误判的排障案例：某服务上线后监控显示每隔几小时出现一次持续数秒的 Full GC，业务侧感知为周期性的接口超时抖动。排查过程中第一反应通常是怀疑老年代对象晋升过快，但通过 GC 日志（`-Xlog:gc*:file=gc.log:time,uptime,level,tags`）比对发现，老年代占用率在 Full GC 前后几乎没有变化，反而是**元空间（Metaspace）** 占用持续上升，逼近 `-XX:MaxMetaspaceSize`（若未设置则受本机可用内存限制），触发条件正是"元空间空间不足"。

进一步排查代码发现，该服务使用了某个动态代理/字节码生成框架，且在业务逻辑中存在不当的重复类生成（每次请求都动态生成一个新类，而不是复用已生成的类）——每个动态生成的类都会占用一份独立的元空间元数据，且这些类几乎永不回收（类需要其加载器不可达才能被回收，而动态生成的类通常绑定在长期存活的类加载器上）。修复方式是缓存并复用动态生成的类，而不是每次重新生成。这个案例说明：**Full GC 的触发原因不止是堆空间不足，元空间耗尽同样会导致 Full GC，且往往需要结合类加载相关的知识（而非单纯的对象生命周期）才能定位根因**。这也提示排障时不能想当然地只看老年代占用曲线，还要把元空间、直接内存等一并纳入观察范围。

## 第 6 章 分代 GC 的内在矛盾——跨代引用

### 6.1 跨代引用的问题

分代 GC 的假设是：每次 Minor GC 只扫描新生代，不扫描老年代，从而减少工作量。但这个假设有一个隐患：**老年代的对象可能持有对新生代对象的引用**（跨代引用）。

```java
// 经典的跨代引用场景：
// 老年代中的缓存对象，其值字段引用着新生代中的新创建对象
class Cache {               // Cache 是老年代对象（存活时间长）
    Object value = new Object();  // value 指向的 Object 是新生代对象（刚创建）
}
```

如果 Minor GC 只扫描新生代的 GC Roots，会遗漏老年代中 `Cache.value` 这条引用——从 Minor GC 的视角看，新生代中的 `value` 对象似乎没有任何引用（新生代内部没有指向它的引用），就会被错误地回收！但实际上它通过老年代的 `Cache` 对象是可达的，不应该被回收。

如果把老年代对象全部加入 GC Roots 集合，相当于每次 Minor GC 都要扫描整个老年代——这完全破坏了分代 GC 的收益，退化为全堆扫描。

### 6.2 记忆集（Remembered Set）——解决跨代引用的数据结构

**记忆集（Remembered Set，RSet）** 是分代 GC 为解决跨代引用问题而引入的数据结构。它的核心思想：**不需要扫描整个老年代来找跨代引用，只需要记录"哪些老年代对象持有对新生代对象的引用"**，Minor GC 时只扫描这些特定的老年代对象。

更准确地说，记忆集记录的是**"跨代引用的来源位置"**（谁引用了新生代对象），使这些位置可以作为 GC Roots 的补充。这也正是第 5.1 节"跨代引用假说"发挥作用的地方——记忆集之所以能做到"轻量"，前提就是跨代引用相对稀少，值得单独记账。

记忆集在实现上可以选择不同的记录精度，精度越高定位越准，但维护成本也越高：

| 记录精度 | 记录内容 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- |
| 字长精度（Word-Precise） | 精确到每一个存在跨代引用的字（引用字段） | 扫描时完全不浪费 | 记录数据量最大 |
| 对象精度（Object-Precise） | 精确到每一个包含跨代引用字段的对象 | 兼顾精度与开销 | 仍需在对象内部定位具体字段 |
| 卡精度（Card-Precise） | 精确到一块固定大小的内存区域（卡页） | 记录数据量小，维护开销低 | 需要重新扫描整个卡页内的所有对象 |

HotSpot 选择的是**卡精度**，即卡表（Card Table）——这是三种精度里工程上性价比最高的一种：记录成本足够低（只是一个字节数组），代价是命中一个"脏卡"后需要扫描该卡页内全部对象（而不是精确到某个字段），但因为卡页本身很小（512 字节），这个代价可以接受。

### 6.3 卡表（Card Table）——记忆集的高效实现

记忆集是概念，**卡表（Card Table）** 是 HotSpot 最常用的记忆集实现：

**基本思想**：将老年代的内存划分为一系列**固定大小的卡页（Card Page，512 字节）**，用一个字节数组（卡表）来标记每个卡页的状态：
- `0`：干净，该卡页中没有跨代引用
- `1`（脏，Dirty）：该卡页中**可能存在**跨代引用

```
老年代内存（假设共 4MB）：
│ 卡页0  │ 卡页1  │ 卡页2  │ 卡页3  │ ... │（每页 512 字节）
│  512B  │  512B  │  512B  │  512B  │

卡表（每个元素对应一个卡页）：
│  0  │  1  │  0  │  1  │ ...│
  ↑         ↑
干净        脏：该区域内有对象引用了新生代中的对象
```

注意这里的"可能存在"两个字非常关键：卡表只是粗粒度地记录"这块区域曾经被写过、可能引入了跨代引用"，并不保证这块区域内一定有跨代引用，也不精确标记具体是哪个字段——真正确认引用关系，仍需要 Minor GC 时把脏卡页内的所有对象都当作潜在的 GC Roots 来源，重新扫描一遍它们的引用字段。这正是"空间换时间"里"时间"没有完全省掉、只是被大幅压缩的地方。

**卡表存放在哪里**：卡表本身不与堆内对象混放，而是作为 JVM 内部的一块独立元数据区域单独管理，与堆内存按固定比例（1:512）对应。此外，为了在卡页内快速找到"对象的起始地址"（脏卡内扫描时需要按对象边界解析内容，而不是随意从字节流中间开始读），老年代还配合维护了一个**块偏移表（BOT，Block Offset Table）**，记录每个卡页内最后一个对象的起始偏移，避免每次都要从整个老年代的起始处开始逐个对象向后遍历定位。

**Minor GC 时**：只扫描卡表中标记为"脏"的卡页（而不是整个老年代），找出其中指向新生代的引用，将其作为额外的 GC Roots 加入到扫描集合中。

**写屏障（Write Barrier）维护卡表**：每次一个老年代对象的引用字段发生写入时（`oldObj.field = youngObj`），JVM 需要将对应的卡页标记为"脏"。这通过**写屏障（Write Barrier）** 实现——JIT 编译器在每条对象引用写入指令之后插入额外代码，检查并更新卡表。

```java
// 原始代码：
cache.value = newObj;

// JIT 编译后插入写屏障（伪代码，post-write barrier）：
cache.value = newObj;
// ↓ 写屏障（额外插入的代码）
int cardIndex = (int) ((address_of_cache) >> 9);  // 512 = 2^9
cardTable[cardIndex] = 1;  // 标记该卡页为"脏"
```

这类插入在赋值语句**之后**的写屏障称为**post-write barrier**，是卡表维护采用的形式；与之相对的是**pre-write barrier**（插入在赋值**之前**，用于捕获"即将被覆盖掉的旧引用"，这是 SATB 方案的核心手段，见第 7 章）。两者插入的位置不同，服务的目的也不同——卡表关心"新写入了什么引用"，SATB 关心"删除了什么引用"。

写屏障有一定的运行时开销（每次引用赋值都需要额外操作），但相比每次 Minor GC 都全扫老年代的代价，这个开销是微不足道的。在真实的字节码/机器码层面，这段逻辑通常是几条简单的移位、比较和条件写指令，且现代 CPU 分支预测对这种"大概率不需要真正写入"的逻辑（同一个卡页短时间内被多次标记脏，重复写入是无意义的，可以用一次判断跳过）优化得相当好，实测中写屏障带来的吞吐量损耗通常在个位数百分比以内。

### 6.4 卡表扫描的性能开销分析：为什么老年代越大，问题越明显

卡表把"扫描整个老年代找跨代引用"压缩成了"扫描卡表 + 扫描脏卡页"，但这不意味着这个开销可以完全忽略，尤其是当老年代持续增大时：

**卡表本身的扫描成本**：即便老年代里绝大多数卡页都是干净的，遍历整张卡表（哪怕只是为了判断哪些是脏的）仍然是一个与老年代大小线性相关的操作——老年代按 1:512 的比例对应卡表大小，1GB 老年代对应 2MB 卡表。虽然 2MB 相对内存扫描而言不算大，但当老年代扩大到几十 GB（大内存服务器的常态配置），卡表本身也会扩大到数十 MB，纯粹遍历这个字节数组去找"1"的过程，也会成为 Minor GC 停顿时间中不可忽视的一部分。

**脏卡页内部扫描的放大效应**：一个卡页 512 字节，通常能容纳数个到十几个中小对象。一旦某个卡页被标记为脏，即使这个卡页里只有一个对象产生了一条跨代引用，Minor GC 也要把整个卡页内的所有对象都重新扫描一遍——如果老年代里存在一些"引用字段更新非常频繁"的热点对象（比如某个全局状态容器持续被更新），它所在的卡页会长期处于脏状态，每次 Minor GC 都要重复扫描，形成局部的扫描热点。

**这正是传统全局卡表方案的天花板**：卡表是"老年代整体"共享的一张表，无法区分"这块脏卡页里的跨代引用，到底指向新生代的哪个具体位置"，也无法把扫描工作按照堆的物理分区做更细粒度的并行化——所有 GC 线程要扫描脏卡页，本质上都是在争抢同一份全局元数据。当堆本身变得很大、且被后续要讲的 Region 化收集器管理时，这种"全局单一卡表"的设计就会成为瓶颈。

> [!note] 设计哲学：预告——G1 为什么不满足于卡表
> G1（参见 [[对象生命周期与GC/07 G1 收集器——Region 化内存与混合回收]]）把堆划分为大量独立的 Region，每个 Region 单独维护自己的记忆集（RSet），只记录"谁引用了我这个 Region"，而不是维护一张覆盖全堆的卡表；同时 G1 在并发标记阶段采用 SATB（原始快照，见第 7 章）而不是仅依赖卡表的"post-write barrier 标脏"机制去处理并发写入带来的一致性问题。这样一来，回收某个 Region 时只需要查询它自己的 RSet，而不必扫描一张随堆增大而线性增大的全局卡表，从根本上把记忆集的扫描开销和堆大小解耦，代价是每个 Region 都要维护一份独立的、结构更复杂的 RSet（本身也要占用额外内存和维护成本）。这里只做原理性的铺垫对比，具体的 RSet 实现细节和 SATB 在 G1 中的完整工作流程，留给后续 G1 专题文章展开。

### 6.5 精确卡表 vs 粗粒度卡表

卡页大小是精度与性能的权衡：
- **卡页过小**（如 64B）：精度高，脏卡页少，扫描工作量小；但卡表本身占用内存多，写屏障执行频率高
- **卡页过大**（如 4KB）：卡表小，写屏障不频繁；但一个卡页包含很多对象，"脏"卡页中需要扫描的范围大，效率降低

HotSpot 选择 **512 字节**为卡页大小，是经验上的折中选择。

### 6.6 记忆集在不同收集器中的实现对比（预告性总览）

为了让本章的知识在后续文章中能够顺利承接，这里用一张表提前总览各主要收集器对"跨代/跨区引用"问题的处理方式差异，细节留给对应的专题文章：

| 收集器 | 记忆集/引用追踪方案 | 处理并发写入的一致性手段 |
| :--- | :--- | :--- |
| Serial / Parallel | 全局卡表（老年代覆盖） | STW 下运行，天然无并发写入问题 |
| CMS | 全局卡表（沿用传统方案） | 并发标记阶段配合增量更新写屏障 |
| G1 | 每个 Region 独立 RSet | 并发标记阶段使用 SATB |
| ZGC / Shenandoah | 不依赖传统卡表，转而使用染色指针 / 转发表等机制 | 读屏障 / 并发转移，机制与卡表完全不同 |

这张表的核心信息是：卡表 + 写屏障是分代 GC 时代（Serial/Parallel/CMS）解决跨代引用的通用方案，而进入 Region 化和低延迟 GC 时代（G1/ZGC/Shenandoah）之后，"如何追踪跨区/跨代引用"这个问题被重新设计了更精细的方案，本篇讲的卡表机制是理解后续所有方案的基础，但不是它们的终点。

## 第 7 章 并发 GC 的额外挑战——写屏障的扩展应用

### 7.1 并发标记的漏标问题

前面在 [[对象生命周期与GC/04 垃圾回收基础——可达性分析、安全点与安全区域]] 中提到，三色标记在并发执行时，用户线程可能修改引用关系，导致**漏标（floating garbage 的反面——本该存活的对象被标为垃圾）**。

具体地，同时满足以下两个条件时，会发生对象丢失：
1. 赋值器（应用线程）向**黑色对象**（已完成扫描的）插入了一条指向白色对象的新引用
2. 赋值器删除了所有从**灰色对象**（待扫描的）出发、到达该白色对象的路径

此时白色对象通过黑色对象可达，但 GC 不会再扫描黑色对象，最终白色对象会被误回收。

### 7.2 写屏障的两种解决方案

解决漏标问题，需要通过写屏障拦截引用关系的变化，有两种理论：

**增量更新（Incremental Update）**：当黑色对象被赋予新的白色引用时，通过写屏障将该黑色对象重新置为灰色（加回工作队列），等待重新扫描。这是一种**post-write barrier**——拦截的是"新写入了什么"。**CMS 使用此方案（维护黑变灰的更新集合，并发标记结束后重新扫描）**。增量更新的直觉很朴素：既然黑色对象又多了一条新引用，说明它没有真正"扫描完"，那就重新把它降级为灰色，反正重新扫一次代价不大。

**原始快照（SATB，Snapshot At The Beginning）**：在并发标记开始时，记录引用关系的"快照"——当灰色对象删除到白色对象的引用时，通过写屏障记录被删除的这条引用，确保被删除引用的白色对象在本次 GC 中不会被回收（将其置为灰色）。这是一种**pre-write barrier**——拦截的是"即将删除什么"，需要在赋值发生之前先记下旧值。**G1 和 ZGC 使用此方案**。SATB 的直觉是：只要保证"标记开始那一刻"可达的对象都不会被漏标，之后即使引用关系变了，也不影响本轮回收的正确性——它维护的是一个逻辑上的堆快照，而不是实时追踪堆的最新状态。

两种方案在效果上都能保证不漏标，但代价模型不同：增量更新会让原本已经"扫描完"的黑色对象重新变成待扫描状态，增加的是本轮标记的工作量，但不会产生本该消亡却被保留的对象；SATB 则相反——它会把原本已经不可达的对象（灰色对象删除了到它的引用，本该变成垃圾）强行保留到本轮回收结束之后，这部分对象被称为**浮动垃圾（Floating Garbage）**，SATB 天生比增量更新更容易产生浮动垃圾，好处是不需要把已经扫描完的黑色对象打回灰色重新扫描一次，标记阶段的过程更简单、更容易做增量式推进。

### 7.3 写屏障的性能账本：不同方案的开销对比

到这里，本文一共出现了三种性质不同的写屏障用途，容易混淆，做一次总结性归纳：

| 写屏障用途 | 插入位置 | 拦截目标 | 采用者 | 典型代价 |
| :--- | :--- | :--- | :--- | :--- |
| 卡表脏位标记 | post-write barrier | 新写入的跨代引用 | Serial/Parallel/CMS/G1 老年代维护 | 极低，一次移位+条件写 |
| 增量更新 | post-write barrier | 黑色对象新增的引用 | CMS 并发标记 | 中等，可能扩大重新扫描范围 |
| SATB pre-barrier | pre-write barrier | 被删除的旧引用 | G1、ZGC | 中等，产生浮动垃圾，需下轮清理 |

这张表说明一个容易被忽视的事实：**"写屏障"不是一个单一机制，而是一整类"在引用赋值前后插入额外逻辑"的技术手段，具体拦截什么、什么时候拦截，完全取决于收集器要解决的问题**。跨代引用问题用的是卡表式 post-barrier；并发标记漏标问题用的是增量更新或 SATB 式 pre-barrier；这几种写屏障在支持并发标记的收集器（比如 G1）中是同时存在、各自服务不同目的的，不能把它们混为一谈。

这是 GC 算法设计中最精妙也最复杂的部分，后续专门讲解 CMS 和 G1 的章节会深入展开这两种写屏障各自完整的并发标记流程与终止条件判断。

## 第 8 章 总结

三种基础算法的本质是在**碎片化、空间利用率、移动成本**三个维度上的权衡，这一权衡可以用第 1.2 节建立的四维评价框架统一解释：标记-清除牺牲空间利用率与分配速度换取零移动开销，天然适合与并发标记结合；复制算法牺牲 50% 空间利用率换取近乎最优的分配速度和标记效率，代价随存活率上升而急剧增加；标记-整理牺牲移动成本换取空间利用率和无碎片特性，代价随存活对象数量线性增长。三种算法各自的实现细节——空闲列表管理、Cheney 扫描算法与转发指针、双指针/表格式整理——决定了它们各自能否被并发化、增量化，这是理解后续所有收集器演进的地基。

**标记-清除**：不移动、有碎片、100% 空间利用率，适合老年代（并发版：CMS，代价是长期运行后碎片积累引发不可预测的 Promotion Failed / Concurrent Mode Failure）

**复制**：移动对象、无碎片、50%（工程上优化到约 10%）空间利用率，适合新生代（存活率低时效率极高，配合动态对象年龄判定和分配担保处理边界情况）

**标记-整理**：移动对象、无碎片、100% 空间利用率，适合老年代（低频率 Full GC 时可以接受移动代价）

**分代假说**把这三种算法组合成了分代 GC 的经典形态——新生代用复制、老年代用标记-整理或标记-清除——是目前绝大多数生产 JVM 的基础。三个假说（弱分代、强分代、跨代引用）分别解释了"为什么要分代""对象该在什么时机晋升"以及"为什么记忆集这种轻量级结构是可行的"，三者合在一起构成了分代收集完整的理论支撑，同时也划定了它的适用边界——缓存密集型、批处理类应用会显著削弱假说的有效性，需要更精细的调优甚至不同的收集器策略。

**跨代引用**是分代 GC 的内在矛盾，**记忆集/卡表 + 写屏障**用精巧的空间换时间策略解决了这个矛盾，使 Minor GC 在不全扫老年代的前提下仍然保持正确性；但全局卡表方案本身也有随堆增大而放大的扫描开销，这正是后续 Region 化收集器要进一步解决的问题。并发标记场景下，写屏障还承担着防止漏标的额外职责，增量更新与 SATB 是两种代价模型不同、但同样有效的解决方案，理解它们的差异是读懂 CMS 与 G1/ZGC 并发标记算法的前提。

> [!note] 思考题
> 1. 分代假说（Generational Hypothesis）认为'大多数对象朝生夕灭'。但在缓存密集型应用（如 Redis 客户端的连接池、Guava Cache）中，大量对象存活时间很长。分代假说在这种场景下是否仍然成立？如果 Old Gen 中存活对象占比极高（>90%），标记-整理算法的效率会如何变化？
> 2. 复制算法（Copying）将存活对象从 From 区复制到 To 区，然后清空 From 区。它的优点是没有碎片，但代价是浪费一半内存空间。HotSpot 的 Young Gen 使用 Eden + 两个 Survivor 的比例（默认 8:1:1），只浪费 10% 空间。如果某次 Minor GC 时 Survivor 区放不下所有存活对象，会发生什么？这些对象去了哪里？
> 3. 标记-清除（Mark-Sweep）算法产生内存碎片，标记-整理（Mark-Compact）需要移动对象（修改引用）。CMS 收集器在老年代使用标记-清除，碎片积累到无法分配大对象时会触发一次 Full GC（Serial Old 的标记-整理）。G1 通过 Region 化设计解决了这个问题——G1 是如何做到'只整理部分 Region 而非整个堆'的？
> 4. 卡表的粒度是 512 字节，一个卡页内可能包含多个对象。如果卡页内只有一个字段发生了跨代引用写入，Minor GC 仍然需要重新扫描整个卡页内的所有对象。假设老年代对象平均大小是 32 字节，粗略估算一个脏卡页平均会带来多少倍于"精确记录"的额外扫描开销？这个开销与卡页大小之间是什么关系？
