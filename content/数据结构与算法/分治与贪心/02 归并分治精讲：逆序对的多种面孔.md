# 归并分治精讲：逆序对的多种面孔

**摘要：**

归并排序的"合并"阶段不只是在排序——它还可以在两个有序段合并时，同步统计"跨越两段的配对数量"。这是一类极重要的算法模式，能将看似需要 $O(n^2)$ 暴力枚举的统计问题降到 $O(n \log n)$。本文通过三道由易到难的 LeetCode 题目，深度剖析这一模式：LeetCode 315（统计后面更小的元素数目）、LeetCode 493（翻转对），以及 LeetCode 327（区间和的个数）。每道题不只给答案，而是推导为什么归并能解决这个问题，以及为什么暴力或其他方式不够好。

---

## 第 1 章 归并合并阶段的隐藏能力

### 1.1 回顾：归并排序的合并阶段

在标准归并排序中，合并阶段的逻辑如下：

```
左段 L = [1, 3, 5]
右段 R = [2, 4, 6]

合并过程：
i=0, j=0: L[0]=1 < R[0]=2, 取 1
i=1, j=0: L[1]=3 > R[0]=2, 取 2
i=1, j=1: L[1]=3 < R[1]=4, 取 3
...
```

这个过程里，**每次从右段取元素时（即 `L[i] > R[j]`），说明右段的当前元素比左段的 `L[i], L[i+1], ..., L[m]` 都小**（因为左段有序，`L[i]` 已经是左段中最小的未处理元素）。换句话说，**从右段取 `R[j]` 的那一刻，`R[j]` 和左段剩余所有元素都构成了"右小于左"的配对**。

这个观察是后续所有"归并统计"问题的核心：**利用归并过程中两段的有序性，在 $O(1)$ 的代价内统计出跨越左右两段的所有配对数量。**

### 1.2 逆序对的原始形式

**逆序对**（Inversion）的定义：在数组中，如果 $i < j$ 且 $a[i] > a[j]$，则 $(i, j)$ 是一个逆序对。

逆序对的数量衡量了数组"有多乱"：完全有序时逆序对为 0，完全逆序（降序排列）时逆序对为 $\binom{n}{2} = \frac{n(n-1)}{2}$，这是最大值。

**暴力解法**：枚举所有 $(i, j)$ 对，$O(n^2)$。对于 $n = 10^5$，暴力需要 $10^{10}$ 次操作，远超时间限制。

**归并分治解法**：在归并排序的合并阶段，当从右段取元素 $R[j]$ 时，左段剩余元素 $L[i], L[i+1], ..., L[m-1]$ 共 $m - i$ 个都与 $R[j]$ 构成逆序对（左段下标 < 右段下标，且值更大）。累加所有合并步骤中的统计，即得总逆序对数量。

**复杂度**：归并排序本身 $O(n \log n)$，统计操作只在合并步骤中进行，每次 $O(1)$，总计 $O(n \log n)$，整体 $O(n \log n)$。

## 第 2 章 LeetCode 315：统计后面更小的元素数目

### 2.1 题目

**LeetCode 315 - Count of Smaller Numbers After Self**（困难）

给你一个整数数组 `nums`，按要求返回一个新数组 `counts`。数组 `counts` 有该性质：`counts[i]` 的值是 `nums[i]` 右侧且比 `nums[i]` 小的元素的数量。

```
输入: nums = [5, 2, 6, 1]
输出: [2, 1, 1, 0]
解释:
  5 右边比 5 小的元素有：2, 1 → counts[0] = 2
  2 右边比 2 小的元素有：1   → counts[1] = 1
  6 右边比 6 小的元素有：1   → counts[2] = 1
  1 右边没有更小的元素      → counts[3] = 0
```

### 2.2 为什么这是"逆序对"的变形

将问题等价转化：对每个 `nums[i]`，统计满足 `i < j` 且 `nums[i] > nums[j]` 的 `j` 的数量。这正是以 `nums[i]` 为左端点的逆序对数量。

与原始逆序对问题的区别在于：原始问题只要总数，这道题**要求每个元素各自的逆序对数量**（per-element count）。

### 2.3 核心难点：元素在归并中会被移动

在归并排序过程中，元素会不断地被搬移，原始的下标关系会被打乱。如果我们只是统计某段中的总逆序对数量（原始问题），不需要关心哪个元素贡献了多少。但这道题要求 per-element 的统计，所以我们必须**追踪每个元素的原始下标**。

**解决方案**：不直接排序 `nums`，而是排序一个存储 `(值, 原始下标)` 的配对数组。合并时，当从右段取元素 `R[j]` 时，左段剩余元素 `L[i], ..., L[m-1]` 的**原始下标对应的 `counts`** 各自加 1。

但"各自加 1"看起来需要 $O(m - i)$ 的时间，这会让总复杂度退化到 $O(n^2)$。

**更聪明的做法**：不在合并时逐个更新，而是记录"合并过程中，右段某个元素 $R[j]$ 在某一步从右段取出时，左段还剩多少个元素"——这个数字就是 $R[j]$ 对应的原始下标应该累加的值。

但等等，问题是**左段的元素 `L[i]`** 被取出时，它不知道右段之后还有多少个元素会"排在它前面"。

**换个视角**：统计的是"每个 `L[i]` 对应的逆序对"。当 `R[j]` 从右段取出时（即 `R[j] < L[i]`），这意味着 `R[j]` 最终会排在 `L[i]` 的前面，但 `R[j]` 的原始下标比 `L[i]` 大——所以 `(L[i].index, R[j].index)` 是一个逆序对，`counts[L[i].index]++`。

但用 `counts[L[i].index]++`，每次只增加当前左段指针 `L[i]` 的计数，而不是左段所有剩余元素的计数——**这是错误的**，因为 `L[i+1], ..., L[m-1]` 也与 `R[j]` 形成逆序对，它们也需要加 1。

**正确做法 1（懒惰统计）**：换个统计方向——不在合并时更新 left-side 元素的 counts，而是**统计每个右段元素在多少次合并中"插队"到了左段元素前面**。

具体地，维护一个计数器 `rightCount`，记录到目前为止从右段取了多少个元素。每次从左段取元素 `L[i]` 时，`counts[L[i].index] += rightCount`（表示右段已经有 `rightCount` 个元素排在了 `L[i]` 的前面，而它们的原始下标都比 `L[i]` 大，所以都是 `L[i]` 的逆序对）。

```go
// 合并过程（简化版）：left/right 是两个有序的 (值, 原始下标) 数组，counts 是结果数组
func mergeCounts(left, right [][2]int, counts []int) {
	merged := make([][2]int, 0, len(left)+len(right))
	i, j := 0, 0
	rightCount := 0 // 到目前为止从 right 取了多少个元素

	for i < len(left) && j < len(right) {
		if left[i][0] <= right[j][0] {
			// 从左段取元素：右段已有 rightCount 个元素（原始下标更大、值更小）排在它前面
			counts[left[i][1]] += rightCount
			merged = append(merged, left[i])
			i++
		} else {
			// 从右段取元素：记录右段已取出的数量
			rightCount++
			merged = append(merged, right[j])
			j++
		}
	}
	// 处理左段剩余元素：右段已全部取完，rightCount 不再增加
	for i < len(left) {
		counts[left[i][1]] += rightCount
		merged = append(merged, left[i])
		i++
	}
	for j < len(right) {
		merged = append(merged, right[j])
		j++
	}
}
```

### 2.4 完整实现

```go
// countSmaller LeetCode 315：归并分治统计每个元素右侧更小元素的个数
// 时间复杂度：O(n log n)，空间复杂度：O(n)
func countSmaller(nums []int) []int {
	n := len(nums)
	counts := make([]int, n)
	pairs := make([][2]int, n) // pairs[i] = (值, 原始下标)
	for i, v := range nums {
		pairs[i] = [2]int{v, i}
	}

	var mergeSort func(arr [][2]int, left, right int)
	mergeSort = func(arr [][2]int, left, right int) {
		if left >= right {
			return
		}
		mid := left + (right-left)/2
		mergeSort(arr, left, mid)
		mergeSort(arr, mid+1, right)

		// 合并阶段统计逆序对
		temp := make([][2]int, 0, right-left+1)
		i, j := left, mid+1
		rightCount := 0 // 到目前为止从右段 [mid+1, right] 取出的元素数量
		for i <= mid && j <= right {
			if arr[i][0] <= arr[j][0] {
				// 从左段取：当前元素在原始数组中的位置 arr[i][1]，
				// 已有 rightCount 个右段元素（原始下标更大、值更小）排在它前面
				counts[arr[i][1]] += rightCount
				temp = append(temp, arr[i])
				i++
			} else {
				rightCount++
				temp = append(temp, arr[j])
				j++
			}
		}
		// 左段剩余：右段已全部排完，rightCount 固定
		for i <= mid {
			counts[arr[i][1]] += rightCount
			temp = append(temp, arr[i])
			i++
		}
		for j <= right {
			temp = append(temp, arr[j])
			j++
		}
		copy(arr[left:right+1], temp)
	}

	mergeSort(pairs, 0, n-1)
	return counts
}
```

**复杂度分析**：
- 时间：$O(n \log n)$，与归并排序相同，统计操作不增加渐近复杂度
- 空间：$O(n)$，临时数组

### 2.5 正确性验证

以 `nums = [5, 2, 6, 1]` 为例：

初始 `pairs = [(5,0), (2,1), (6,2), (1,3)]`

**第一轮归并**（left: `[(5,0), (2,1)]`，合并为有序段）：
- `i=0, j=1`：`(5,0)` vs `(2,1)`，取 `(2,1)`，`rightCount=1`
- `i=0`，左段剩余：`counts[0] += 1 = 1`，取 `(5,0)`
- 合并结果：`[(2,1), (5,0)]`

**第一轮归并**（right: `[(6,2), (1,3)]`）：
- `i=0, j=1`：`(6,2)` vs `(1,3)`，取 `(1,3)`，`rightCount=1`
- `i=0`，左段剩余：`counts[2] += 1 = 1`，取 `(6,2)`
- 合并结果：`[(1,3), (6,2)]`

**第二轮归并**（`[(2,1),(5,0)]` 和 `[(1,3),(6,2)]`）：
- `(2,1)` vs `(1,3)`：取 `(1,3)`，`rightCount=1`
- `(2,1)` vs `(6,2)`：取 `(2,1)`，`counts[1] += 1 = 1`
- `(5,0)` vs `(6,2)`：取 `(5,0)`，`counts[0] += 1 = 2`
- 右段剩余 `(6,2)`，`counts[2]` 不再增加
- 合并结果：`[(1,3),(2,1),(5,0),(6,2)]`

最终 `counts = [2, 1, 1, 0]`，与期望一致。

## 第 3 章 LeetCode 493：翻转对

### 3.1 题目

**LeetCode 493 - Reverse Pairs**（困难）

给定一个数组 `nums`，如果 `i < j` 且 `nums[i] > 2 * nums[j]`，则称 `(i, j)` 为一个**翻转对**。返回数组中所有翻转对的数量。

```
输入: nums = [1, 3, 2, 3, 1]
输出: 2
解释: (1, 4) 和 (3, 4) 是翻转对
     nums[1]=3 > 2*nums[4]=2
     nums[3]=3 > 2*nums[4]=2

输入: nums = [2, 4, 3, 5, 1]
输出: 3
```

### 3.2 与 LeetCode 315 的关键区别

LeetCode 315 的条件是 `nums[i] > nums[j]`，而 LeetCode 493 的条件是 `nums[i] > 2 * nums[j]`。这个区别看似微小，实则导致了**完全不同的归并统计策略**。

在 315 中，我们的统计和合并是**同步进行**的：在合并 `L` 和 `R` 的同时，每次从 `R[j]` 取元素时，`rightCount` 累加到左段剩余元素的 counts 中。这之所以可行，是因为"从 `R[j]` 取出"这个事件，**等价于** `R[j] < L[i]`（合并的判断条件），也就是满足翻转对条件的判断。

但对于 493，条件是 `L[i] > 2 * R[j]`。这与合并操作的判断 `L[i] <= R[j]`（用于决定从哪边取）**不同步**。换句话说，**满足翻转对条件的配对**，不一定是在归并的某一步"恰好被检测到"的。

> [!warning] 关键认知：统计与合并要分离
> 对于条件形如 `f(L[i]) > g(R[j])` 的归并统计，当 `f` 和 `g` 与合并的大小比较不完全相同时，需要将**统计阶段**和**合并阶段**分开：
>
> 1. **统计阶段**：在合并之前，用双指针在有序的 `L` 和 `R` 上扫描，统计满足条件的跨段配对数量（此时 `L` 和 `R` 都已经是有序的，可以用单调性加速）
> 2. **合并阶段**：正常归并排序，将 `L` 和 `R` 合并为有序段

### 3.3 双指针统计翻转对

在合并 `L` 和 `R` 之前，`L` 和 `R` 都已经是有序的（递归排好了）。现在要统计满足 `L[i] > 2 * R[j]` 的配对数量。

对固定的 `j`，满足条件的 `i` 是 `L` 中所有值大于 `2 * R[j]` 的元素。由于 `L` 有序，这些元素是 `L` 的某个后缀 `L[k..m-1]`（其中 `k` 是第一个满足 `L[k] > 2 * R[j]` 的位置）。

关键观察：随着 `j` 增大，`R[j]` 增大，`2 * R[j]` 增大，满足条件的 `k` 只会增大（不会减小）。因此可以用**双指针**：

```
j 从 0 到 n-1 遍历右段
k 从 0 开始，对每个 j 向右移动直到 L[k] <= 2*R[j]
配对数量 += m - k   （L[k..m-1] 中所有元素都满足条件）
```

整体统计复杂度：$O(m + n)$，与合并本身的复杂度相同。

### 3.4 完整实现

```go
// reversePairs LeetCode 493：归并分治统计翻转对（i < j 且 nums[i] > 2*nums[j]）
// 时间复杂度：O(n log n)，空间复杂度：O(n)
func reversePairs(nums []int) int {
	var mergeSort func(nums []int, left, right int) int
	mergeSort = func(nums []int, left, right int) int {
		if left >= right {
			return 0
		}
		mid := left + (right-left)/2

		// 递归排序左右两段，并统计各段内部的翻转对
		count := mergeSort(nums, left, mid) + mergeSort(nums, mid+1, right)

		// 跨段统计：此时 nums[left..mid] 与 nums[mid+1..right] 均已有序，双指针 k 单调右移
		k := mid + 1
		for i := left; i <= mid; i++ {
			// 用 int64 防止 2*nums[k] 溢出
			for k <= right && int64(nums[i]) > 2*int64(nums[k]) {
				k++
			}
			// [mid+1, k-1] 范围内的元素都满足 nums[j]*2 < nums[i]
			count += k - (mid + 1)
		}

		// 标准归并合并
		temp := make([]int, 0, right-left+1)
		i, j := left, mid+1
		for i <= mid && j <= right {
			if nums[i] <= nums[j] {
				temp = append(temp, nums[i])
				i++
			} else {
				temp = append(temp, nums[j])
				j++
			}
		}
		temp = append(temp, nums[i:mid+1]...)
		temp = append(temp, nums[j:right+1]...)
		copy(nums[left:right+1], temp)
		return count
	}

	return mergeSort(nums, 0, len(nums)-1)
}
```

> [!warning] 生产避坑：整数溢出
> `2 * nums[j]` 在 `nums[j]` 接近 `Integer.MAX_VALUE / 2` 时会溢出。必须将比较表达式改为 `(long) nums[i] > 2L * nums[j]`，或者将整个数组提前转为 `long[]`。这是面试中容易被扣分的细节。

### 3.5 为什么双指针的 k 不需要重置

这是最容易让人困惑的地方。循环中 `k` 从 `mid+1` 开始，然后随着 `i` 的增大，`k` 只会增大（不会减小），这看起来好像 `k` 没有随 `i` 重置？

**这是正确的**。原因是：当 `i` 从 `i` 增大到 `i+1` 时，`nums[i+1] <= nums[i]`（因为左段 `[left, mid]` 已有序，但我们是从小到大遍历，所以 `nums[i+1] >= nums[i]`，即左段值递增）。

等等，左段是从小到大有序的，所以 `nums[i+1] >= nums[i]`，这意味着 `nums[i+1] > 2 * nums[k]` 的条件比 `nums[i] > 2 * nums[k]` **更难满足**（左边更大了，但右边 `2*nums[k]` 没变）……

**等等，这里要重新想**：随着 `i` 增大，`nums[i]` 增大（因为左段有序，我们从 `left` 到 `mid` 遍历），所以 `nums[i] > 2 * nums[k]` 的条件**更容易满足**（左边更大），`k` 应该继续右移或保持不动，但不会左移。

因此 `k` 单调递增，每次内层 `while` 循环总共最多移动 $O(n)$ 步，整体 `countCross` 的时间复杂度是 $O(m + n)$。

## 第 4 章 LeetCode 327：区间和的个数

### 4.1 题目

**LeetCode 327 - Count of Range Sum**（困难）

给你一个整数数组 `nums` 以及两个整数 `lower` 和 `upper`，求数组中值位于范围 `[lower, upper]`（含两端点）之内的**区间和的个数**。

区间和 `S(i, j)` 表示在 `nums[i]` 到 `nums[j]` 的元素总和（$i \leq j$）。

```
输入: nums = [-2, 5, -1], lower = -2, upper = 2
输出: 3
解释: 满足条件的三个区间是：[0,0]、[2,2]、[0,2]
     S(0,0) = -2 ∈ [-2, 2]
     S(2,2) = -1 ∈ [-2, 2]
     S(0,2) = 2 ∈ [-2, 2]
```

### 4.2 前缀和转化：将问题变为"有序段上的配对统计"

**核心转化**：区间和 $S(i, j) = \text{prefix}[j+1] - \text{prefix}[i]$，其中 $\text{prefix}[k] = \sum_{t=0}^{k-1} \text{nums}[t]$（前缀和数组，`prefix[0] = 0`）。

条件 $\text{lower} \leq S(i, j) \leq \text{upper}$ 等价于：

$$\text{lower} \leq \text{prefix}[j+1] - \text{prefix}[i] \leq \text{upper}$$

即：

$$\text{prefix}[j+1] - \text{upper} \leq \text{prefix}[i] \leq \text{prefix}[j+1] - \text{lower}$$

现在问题变成：在前缀和数组中，统计满足 $i < j+1$ 且 $\text{prefix}[j+1] - \text{upper} \leq \text{prefix}[i] \leq \text{prefix}[j+1] - \text{lower}$ 的配对 $(i, j+1)$ 数量。

**这正是一个"两个有序段上的配对计数"问题**：在归并排序前缀和数组的过程中，当合并 `L = prefix[left..mid]` 和 `R = prefix[mid+1..right]` 时，对每个 `R[j]`，统计 `L` 中满足区间条件的元素数量。

### 4.3 双指针统计区间配对

对固定的 `R[j] = prefix[j']`（`j'` 是某个 `j+1`），满足条件的 `L[i]` 需要满足：

$$R[j] - \text{upper} \leq L[i] \leq R[j] - \text{lower}$$

由于 `L` 有序，满足条件的 `L[i]` 是某个连续段 `[lo, hi)`，可以用双指针维护：

```go
// 跨段统计：[lo, hi) 是满足条件的左端点区间，随 prefix[j] 增大单调右移
lo, hi := left, left
for j := mid + 1; j <= right; j++ {
	for lo <= mid && prefix[lo] < prefix[j]-int64(upper) {
		lo++
	}
	for hi <= mid && prefix[hi] <= prefix[j]-int64(lower) {
		hi++
	}
	count += hi - lo
}
```

**注意**：`lo` 和 `hi` 不需要重置，因为随着 `prefix[j]` 增大（`R` 有序），下界 `prefix[j] - upper` 和上界 `prefix[j] - lower` 也单调递增，满足条件的 `lo` 和 `hi` 只会向右移动。

### 4.4 完整实现

```go
// countRangeSum LeetCode 327：前缀和 + 归并分治统计区间和落在 [lower, upper] 的子数组个数
// 时间复杂度：O(n log n)，空间复杂度：O(n)
func countRangeSum(nums []int, lower int, upper int) int {
	n := len(nums)
	// 前缀和用 int64 防止溢出（nums[i] 可达 10^4，n 可达 10^4，总和可达 10^8）
	prefix := make([]int64, n+1)
	for i, v := range nums {
		prefix[i+1] = prefix[i] + int64(v)
	}

	var mergeSort func(prefix []int64, left, right int) int
	mergeSort = func(prefix []int64, left, right int) int {
		if left >= right {
			return 0
		}
		mid := left + (right-left)/2

		// 递归处理左右两段
		count := mergeSort(prefix, left, mid) + mergeSort(prefix, mid+1, right)

		// 跨段统计：此时 prefix[left..mid] 与 prefix[mid+1..right] 均已有序
		lo, hi := left, left
		for j := mid + 1; j <= right; j++ {
			// 找到 [lo, hi) 使得 prefix[lo..hi-1] 均落在 [prefix[j]-upper, prefix[j]-lower]
			for lo <= mid && prefix[lo] < prefix[j]-int64(upper) {
				lo++
			}
			for hi <= mid && prefix[hi] <= prefix[j]-int64(lower) {
				hi++
			}
			count += hi - lo
		}

		// 标准归并合并
		temp := make([]int64, 0, right-left+1)
		i, j := left, mid+1
		for i <= mid && j <= right {
			if prefix[i] <= prefix[j] {
				temp = append(temp, prefix[i])
				i++
			} else {
				temp = append(temp, prefix[j])
				j++
			}
		}
		temp = append(temp, prefix[i:mid+1]...)
		temp = append(temp, prefix[j:right+1]...)
		copy(prefix[left:right+1], temp)
		return count
	}

	return mergeSort(prefix, 0, n)
}
```

### 4.5 复杂度分析与正确性

**时间复杂度**：归并排序 $O(n \log n)$，统计阶段每层 $O(n)$，整体 $O(n \log n)$。

**空间复杂度**：$O(n)$，临时数组。

**正确性关键**：为什么在归并排序前缀和数组是正确的？

关键在于，统计 `count` 的阶段是在**合并之前**执行的，此时 `prefix[left..mid]` 和 `prefix[mid+1..right]` 虽然已经被重新排序（它们各自是有序的），但它们的原始含义（前缀和的值）没有改变。我们统计的是"来自左段（原始下标 $\leq$ mid）的前缀和" 和 "来自右段（原始下标 $>$ mid）的前缀和"满足条件的配对，这恰好对应原始问题中 $i \leq j$ 的区间和（因为 $\text{prefix}[j+1] - \text{prefix}[i]$ 中，`j+1` 在右段，`i` 在左段，所以 `i < j+1`）。

> [!note] 设计哲学：前缀和 + 归并分治的通用性
> "前缀和 + 归并分治"是一类通用的模式，凡是需要统计"子数组的某种聚合统计量满足条件的个数"，都可以考虑：
> 1. 将区间聚合统计量转化为"两个前缀统计量之差"
> 2. 对前缀统计量数组进行归并分治
> 3. 在合并阶段统计跨段配对数量

## 第 5 章 三题横向对比与模式总结

### 5.1 三道题的统一视角

| 特征 | LeetCode 315 | LeetCode 493 | LeetCode 327 |
|------|-------------|-------------|-------------|
| 条件 | $L[i] > R[j]$ | $L[i] > 2 \cdot R[j]$ | $R[j] - \text{upper} \leq L[i] \leq R[j] - \text{lower}$ |
| 条件与合并大小比较关系 | **等价**（从右段取元素时成立） | **不等价** | **不等价** |
| 统计策略 | 统计和合并**同步** | 先统计，再合并（`countCross` 分离） | 先统计，再合并（双指针范围查询） |
| 统计时需要 per-element 结果 | 是（315 要每个元素各自的数量） | 否（493 只要总数） | 否（327 只要总数） |
| 处理原始下标的方式 | 存储 `(值, 下标)` 配对，用 `rightCount` 记录 | 不需要追踪原始下标 | 不需要追踪原始下标 |
| 时间复杂度 | $O(n \log n)$ | $O(n \log n)$ | $O(n \log n)$ |

### 5.2 归并分治统计的通用模板

```go
// 归并分治统计的通用模板（Go 泛型版）
func mergeSortCount[T any](arr []T, left, right int,
	countCross func(arr []T, left, mid, right int) int,
	less func(a, b T) bool) int {
	if left >= right {
		return 0
	}
	mid := left + (right-left)/2

	// 步骤 1：递归处理左右两段，统计各段内部的配对数
	count := mergeSortCount(arr, left, mid, countCross, less) +
		mergeSortCount(arr, mid+1, right, countCross, less)

	// 步骤 2：在合并之前统计跨越两段的配对数（此时两段均已有序，可利用有序性加速）
	count += countCross(arr, left, mid, right)

	// 步骤 3：将两段合并为有序段（标准归并）
	temp := make([]T, 0, right-left+1)
	i, j := left, mid+1
	for i <= mid && j <= right {
		if less(arr[i], arr[j]) {
			temp = append(temp, arr[i])
			i++
		} else {
			temp = append(temp, arr[j])
			j++
		}
	}
	temp = append(temp, arr[i:mid+1]...)
	temp = append(temp, arr[j:right+1]...)
	copy(arr[left:right+1], temp)
	return count
}
```

### 5.3 什么情况下统计可以与合并同步

**同步条件**：当"满足统计条件"和"合并时从右段取元素"是等价的事件。

具体来说，如果统计的条件是 `L[i] > R[j]`（普通逆序对），那么：
- 合并时从右段取 `R[j]`，等价于 `L[i] > R[j]`（当前左段头部比右段头部大）
- 此时左段的 `L[i], L[i+1], ..., L[m-1]` 都比 `R[j]` 大，逆序对数量是 `m - i`（或用 `rightCount` 统计）

**不同步条件**：当统计条件是 `L[i] > 2 * R[j]`（493）或范围查询（327），条件与合并判断不等价，必须将统计阶段独立出来。

## 第 7 章 树状数组求逆序对与离散化的工程实战

### 7.1 为什么树状数组是逆序对的另一把快刀

在第 2 章中，我们用**归并分治**在 $O(n \log n)$ 时间内统计了逆序对。其实还有一条完全不同的路线——**树状数组（Binary Indexed Tree，Fenwick Tree）**：
- 从右往左倒序扫描数组，对每个元素 `nums[i]`，先查询树状数组中**值域在 `[1, nums[i] - 1]` 区间内已经出现过多少个元素**（即它右边比它小的元素个数），累加进答案；再把 `nums[i]` 插入树状数组；
- 单次查询与更新均为 $O(\log V)$（$V$ 为值域），总时间 $O(n \log V)$；
- 与归并分治相比，树状数组写法更短、且天然支持**流式增量**（元素逐个到达时实时统计），但需要值域离散化。

### 7.2 离散化：当值域高达 $10^9$ 时的必修课

树状数组要求下标落在 `[1, V]` 的连续值域内。当元素值域高达 $10^9$ 而元素个数 $n \le 10^5$ 时，直接开 `10^9` 的数组会爆内存。**离散化（Coordinate Compression）**三步走：
1. 把所有元素收集进切片并**排序去重**（`slices.Sort` + `slices.Compact`）；
2. 用**二分查找 `sort.SearchInts`** 把每个原始值映射为它在去重序列中的排名（`1-indexed`）；
3. 在排名值域 `[1, len(unique)]` 上建树状数组。

```go
package main

import (
	"slices"
	"sort"
)

// countSmallerTree LeetCode 315 树状数组解法：离散化 + 从右往左查询值域前缀和
// 时间复杂度：O(n log n)，空间复杂度：O(n)
func countSmallerTree(nums []int) []int {
	n := len(nums)
	// 1. 离散化：排序去重
	sorted := slices.Clone(nums)
	slices.Sort(sorted)
	unique := slices.Compact(sorted)
	m := len(unique)

	// 2. 树状数组（1-indexed）
	tree := make([]int, m+1)
	update := func(i int) {
		for ; i <= m; i += i & (-i) {
			tree[i]++
		}
	}
	query := func(i int) int {
		s := 0
		for ; i > 0; i -= i & (-i) {
			s += tree[i]
		}
		return s
	}

	res := make([]int, n)
	// 3. 从右往左倒序扫描：先查比 nums[i] 小的已出现元素个数，再插入 nums[i]
	for i := n - 1; i >= 0; i-- {
		rank := sort.SearchInts(unique, nums[i]) + 1 // 1-indexed 排名
		res[i] = query(rank - 1)
		update(rank)
	}
	return res
}
```

### 7.3 三条路线的横向对比与选型指南

| 路线 | 时间复杂度 | 空间复杂度 | 是否支持流式增量 | 实现难度 |
|------|------------|------------|------------------|----------|
| 归并分治（第 2 章） | $O(n \log n)$ | $O(n)$ | 否（需一次性拿到全数组） | 中（合并阶段双指针） |
| 树状数组 + 离散化 | $O(n \log n)$ | $O(n)$ | **是**（逐元素实时统计） | 低（模板固定） |
| 线段树 + 区间合并 | $O(n \log n)$ | $O(n)$ | 是 | 高（需手写区间树） |

在面试中，建议**先写归并分治**（考察对分治合并阶段的理解，是本专栏的主线），再主动补充"树状数组 + 离散化"作为流式场景的替代方案——两条路线的对照恰好呼应了第 01 篇"分治 vs 数据结构加速"的辩证关系。

### 7.4 延伸实战：区间和的个数（LC 327）的树状数组解法

在第 4 章我们用归并分治解决了 **LeetCode 327：区间和的个数**。它同样可以转化为树状数组问题：
- 构造前缀和数组 $P[0 \dots n]$，问题变为统计满足 $P[l] \in [P[r] - upper, P[r] - lower]$ 的历史左端点个数；
- 把所有 $P[i]$、$P[i] - lower$、$P[i] - upper$ 三类值合并离散化，从左往右扫描：对每个 $r$，先查询值域 $[P[r] - upper, P[r] - lower]$ 内已出现的前缀和个数累加进答案，再把 $P[r]$ 插入树状数组，总时间 $O(n \log n)$。


### 7.5 延伸实战：区间和的个数（LC 327）的树状数组完整实现

在第 7.4 节我们给出了 LC 327 树状数组解法的思路，下面补齐完整实现：

```go
package main

import (
	"slices"
	"sort"
)

// countRangeSumBIT LeetCode 327 树状数组解法：前缀和 + 三类值合并离散化 + 值域区间计数
// 时间复杂度：O(n log n)，空间复杂度：O(n)
func countRangeSumBIT(nums []int, lower int, upper int) int {
	n := len(nums)
	prefix := make([]int64, n+1)
	for i, v := range nums {
		prefix[i+1] = prefix[i] + int64(v)
	}

	// 1. 收集三类值：P[i]、P[i] - lower、P[i] - upper，统一离散化
	all := make([]int64, 0, 3*(n+1))
	all = append(all, prefix...)
	for i := 0; i <= n; i++ {
		all = append(all, prefix[i]-int64(lower), prefix[i]-int64(upper))
	}
	slices.Sort(all)
	all = slices.Compact(all)
	m := len(all)

	rank := func(v int64) int {
		return sort.Search(len(all), func(i int) bool { return all[i] >= v }) + 1
	}

	// 2. 树状数组（1-indexed）
	tree := make([]int, m+1)
	update := func(i int) {
		for ; i <= m; i += i & (-i) {
			tree[i]++
		}
	}
	query := func(i int) int {
		s := 0
		for ; i > 0; i -= i & (-i) {
			s += tree[i]
		}
		return s
	}

	total := 0
	update(rank(prefix[0])) // 先插入空前缀 P[0] = 0
	for r := 1; r <= n; r++ {
		// 统计历史前缀和落在 [P[r] - upper, P[r] - lower] 内的个数
		lo, hi := rank(prefix[r]-int64(upper)), rank(prefix[r]-int64(lower))
		total += query(hi) - query(lo-1)
		update(rank(prefix[r]))
	}
	return total
}
```

请留意第 22–27 行的**三类值合并离散化**：因为查询区间端点 $P[r] - upper$ 与 $P[r] - lower$ 本身可能不在前缀和数组中出现过，必须把它们与 $P[i]$ 一起收集、排序、去重后再建树状数组，否则 `rank` 二分查找会漏掉边界值。这一细节是所有"值域区间计数"类树状数组题的通用保命符。

| 归并分治（第 4 章） | $O(n \log n)$ | $O(n)$ | 中（跨区双指针窗口） | 面试主线，考察分治合并 |

### 7.7 延伸实战：计算右侧小于当前元素的个数（LC 315）的树状数组完整实现

在第 7.1–7.2 节我们给出了树状数组 + 离散化的完整实现。这里再补充一个工程细节：当数组中存在**大量重复元素**时，离散化的排名必须使用 `sort.SearchInts`（lowerBound 语义）而非 `sort.SearchInts + 1` 的误用——因为 `SearchInts` 返回的是第一个等于该值的位置，天然把相同值归入同一排名桶，保证"严格小于"的查询语义（查询 `rank - 1` 即严格小于当前值的所有已出现元素）。

若把排名误算为 `SearchInts(unique, v) + 1` 之后又查询 `rank - 1`，当 `v` 是最小值时会查询排名 `0`，树状数组返回 `0`，恰好正确；但当存在重复值时，`SearchInts` 返回的是该值**第一次出现**的排名，相同值共享同一排名，因此"严格小于"的统计依然精确。这一细节在 LC 315 的重复元素用例（如 `[5, 2, 6, 1]` 与 `[2, 2, 2]`）上是隐含的正确性保障，值得在面试中主动点出。

### 7.8 三题的统一视角与工程映射

| 题目 | 统计量定义 | 跨段双指针窗口 | 归并时机 | 工程身影 |
|------|------------|----------------|----------|----------|
| LC 315 | 右侧更小元素个数 | `rightCount` 累加 | 合并中同步 | 数据库索引选择度估算 |
| LC 493 | 翻转对 `nums[i] > 2*nums[j]` | `[mid+1, k)` 单调右移 | 合并前独立统计 | 金融风险敞口配对 |
| LC 327 | 区间和落在 `[lower, upper]` | `[lo, hi)` 双游标单调右移 | 合并前独立统计 | 信号处理滑窗能量统计 |

三题的共同骨架是：**归并排序把无序序列的二维偏序问题，在每一层分治的交界处还原为"两个有序数组之间的单调双指针统计"**。当统计条件可以写成关于有序值的单调区间时，跨段统计就能在 $O(m)$ 内完成；否则（如 LC 493 的 `2*nums[j]` 非线性条件）需要在合并前单独跑一遍双指针，但依然保持 $O(n \log n)$ 总复杂度。


### 7.9 逆序对统计的工程映射与复杂度终检

逆序对统计在生产系统中的身影远比想象中广泛：数据库查询优化器用逆序对估算索引的选择度（一个键值序列的逆序对密度直接反映该索引对排序查询的收益）；量化金融用翻转对统计资产收益序列中的"大幅回撤配对"密度；信号处理用区间和统计（LC 327）计算滑窗能量落在阈值带内的样本数。三条路线的终检对照如下：归并分治是面试主线（考察合并阶段的双指针理解），树状数组 + 离散化是流式增量场景的替代（逐元素实时统计），平衡树是动态插入删除场景的兜底。三者时间复杂度同为 $O(n \log n)$，选型依据完全取决于**数据是静态一次性、流式增量还是动态可变**。

### 7.10 逆序对统计的复杂度终检与变体扩展

三条路线（归并分治、树状数组 + 离散化、平衡树）的时间复杂度同为 $O(n \log n)$，但常数与适用场景各异：归并分治的合并阶段双指针缓存友好、无哈希开销，是静态一次性统计的首选；树状数组 + 离散化的更新与查询各需 $O(\log V)$，胜在代码模板固定且支持流式增量；平衡树在 Go 中无内置实现，仅在需要动态插入删除时兜底。变体方面，若把统计条件从"严格小于"改为"小于等于"（非严格逆序对），归并合并的比较从 `<=` 改为 `<` 即可；若要求统计**逆序对的价值总和**（如 LC 1560 变体），则在合并时把 `rightCount` 替换为右侧已取出元素的**权值前缀和**，框架完全不变。

### 7.11 逆序对统计的面试表达与终检口诀

在面试中阐述归并分治统计时，推荐的四段式表达是：第一段定性（"这是逆序对统计问题，暴力 $O(n^2)$，我计划用归并分治降到 $O(n \log n)$"）；第二段点明合并阶段的隐藏能力（"两个有序半区之间的偏序统计，可以用单调双指针在 $O(m)$ 内完成"）；第三段说明统计时机（"统计可以在合并前独立进行，也可以在合并中同步进行，取决于统计条件是否与合并比较条件同构"）；第四段主动补充替代方案（"若数据是流式的，可用树状数组 + 离散化逐元素实时统计"）。终检口诀：**统计条件与合并条件同构则合并中同步统计，不同构则合并前独立统计；数据流式则换树状数组**。

### 7.12 逆序对统计的终检口诀

归并分治统计的终检口诀有三条：其一，统计条件与合并比较条件同构时（如 LC 315 的"值更小"），可在合并中同步统计；不同构时（如 LC 493 的"两倍关系"、LC 327 的"区间和"），需在合并前独立跑双指针，但复杂度不变。其二，跨段双指针的单调右移依赖左右半区各自有序，因此统计必须在递归排序之后、合并之前进行。其三，数据流式到达时切换树状数组 + 离散化，逐元素实时统计。三条口诀与三条路线的对照表共同构成了逆序对家族的完整作战地图。
## 小结

1. **归并的"合并"阶段是统计跨段配对的黄金时机**：此时左右两段分别有序，可以用双指针在 $O(m+n)$ 时间内完成原本需要 $O(mn)$ 的配对统计。

2. **区分"同步统计"和"分离统计"**：统计条件与归并方向一致时（如 $L[i] > R[j]$），可以同步进行；条件更复杂时（如范围查询），先统计再合并。

3. **整数溢出是这类题的常见陷阱**：LeetCode 493 中需要用 `(long) nums[i] > 2L * nums[j]`，LeetCode 327 中需要将前缀和数组定义为 `long[]`。

4. **追踪原始下标需要存储 `(值, 下标)` 配对**：LeetCode 315 需要 per-element 的结果，因此在排序过程中必须携带原始下标信息。

5. **前缀和将区间聚合问题转化为前缀差问题**：LeetCode 327 的核心转化，将"区间和 ∈ [lower, upper]"变为"两个前缀和的差 ∈ [lower, upper]"，从而适配归并分治框架。
