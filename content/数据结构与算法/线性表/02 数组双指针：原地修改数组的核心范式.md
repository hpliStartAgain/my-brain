# 数组双指针：原地修改数组的核心范式

**摘要：**

"原地修改数组"是面试中出现频率极高的一类题型，它要求在不另开空间的前提下，对数组做过滤、去重或删除。这类题看似简单，却最能拉开差距——因为它考的从来不是"会不会写双指针"，而是**能不能从约束出发，把双指针的必然性推导出来，并用一个清晰的循环不变量把边界条件钉死**。本文以 LeetCode 26、80、27 三道经典题为切入点，先讲清楚"为什么不能另开数组"这一铁约束如何逼出双指针，再逐题推导解法、用 Go 语言完整实现，最后把三道题泛化成"保留 k 次"的通用模板，并给出同向与对撞两种双指针的取舍标准。读完本篇，你将获得一个能覆盖大量数组变体题的核心范式，以及一套判断"该用哪种双指针"的思维方法。

---

## 第 1 章 从约束出发：为什么不能另开数组

### 1.1 题目约束的本质

先看 LeetCode 26 的要求：

> 给你一个**升序排列**的数组 `nums`，请你**原地**删除重复出现的元素，使每个元素**只出现一次**，返回删除后数组的新长度。**不要使用额外的数组空间**，你必须在**原地**修改输入数组并在使用 $O(1)$ 额外空间的条件下来完成。

真正决定解题方向的，是"不要使用额外的数组空间"与"$O(1)$ 额外空间"这两句话。面对这道题，很多人的第一反应是：开一个新数组 `result`，遍历 `nums`，把不重复的元素依次塞进去，最后再把 `result` 复制回 `nums`。这个思路逻辑清晰、实现简单，本身没有任何错误——但题目明确禁止了它，因为它需要 $O(n)$ 的额外空间。

于是我们被逼进一个很窄的角落：**在原数组这一块固定内存上动刀，而在这块内存上，我们能做的只有两件事——读取某个位置的值，以及覆写某个位置的值**。没有第三件事。既然不能开辟新空间，那"结果"就只能寄存在原数组里；既然结果要寄存在原数组里，那就必须让原数组同时扮演两个角色：一部分位置存放已经整理好的结果，另一部分位置充当尚未处理的原料。

### 1.2 双指针的必然性

把上一步的结论再往前推一格：既然原数组要同时扮演"结果区"和"原料区"，那就必须有一条**边界**把两者分开；而这条边界会随着处理进度不断前移，所以它不能是一个固定下标，必须是一个**会移动的变量**。一个变量负责标记"结果区到哪儿了"，这还不够——我们还需要另一个变量去"读"原料区的每一个元素。两个变量，一个管写、一个管读，这就是双指针的由来。

**请注意这里的推导链条：不是"老师说要双指针所以用双指针"，而是"不能另开空间 → 原数组要兼任结果区与原料区 → 需要一条移动的边界 → 需要读与写两个角色 → 双指针"**。把这条链走通，双指针就不再是一个需要记忆的套路，而是一个被约束逼出来的必然选择。

用一个生活场景来类比：你是一个邮差，手里有一摞信件（原数组），其中有些是重复的。任务是把不重复的信件整理好、叠放在桌子的左侧（原数组前段），且不允许另找一张桌子。你于是需要两只手——**左手（慢指针 `slow`）维护"已整理好区域"的边界，指向下一个可以安全放信的位置；右手（快指针 `fast`）逐一检查每封信，判断它是否值得被放到左侧**。两只手各司其职，通过移动速度的差异完成原地筛选。这就是双指针最直观的样子。

### 1.3 不变量：双指针的地基

优秀的双指针代码背后，一定站着一个**循环不变量（Loop Invariant）**——即在每次循环迭代结束后都恒成立的一个性质。对这类"原地过滤"的双指针而言，不变量是：

> **`nums[0..slow-1]` 区间内的元素，始终是已经处理完毕、满足保留条件的最终结果。**

这句话看着朴素，却是整段代码的定海神针。它同时回答了两个问题：慢指针 `slow` 当前指的位置意味着什么（下一个可写位置），以及判断"新元素是否该保留"时该和谁比较（结果区的最后一个元素，即 `nums[slow-1]`）。**初学者在双指针上栽的跟头，几乎都能追溯到没有把不变量说清楚**——一旦说清楚了，边界条件便不再是靠直觉猜，而是靠逻辑推。

## 第 2 章 LeetCode 26：删除有序数组中的重复项

### 2.1 题目

**LeetCode 26 - Remove Duplicates from Sorted Array**（简单）

给你一个升序排列的数组 `nums`，请原地删除重复出现的元素，使每个元素只出现一次，返回删除后数组的新长度。元素的相对顺序应当保持一致。

```text
输入: nums = [1,1,2]
输出: 2, nums = [1,2,_]

输入: nums = [0,0,1,1,1,2,2,3,3,4]
输出: 5, nums = [0,1,2,3,4,_,_,_,_,_]
```

### 2.2 思路推导：有序性给了我们什么

**关键前提是"数组已升序排列"。** 这个前提的分量，怎么强调都不过分——正因为有序，所有相同的元素必然紧挨在一起，于是判断一个元素是否"重复"，只需要和它前面那个元素比较，而不必回头全局搜索。换句话说，**有序性把"判重"从一次全局查找，降维成了一次相邻比较**。

现在把双指针框架套上去，并明确不变量：

- **初始状态**：`slow = 1`。为什么是 1 而不是 0？因为第一个元素永远不可能重复，它天然属于结果区，直接保留即可。此时 `nums[0..0]` 已是结果，慢指针指向下一个可写位置 `1`。`fast` 同样从 1 开始。
- **循环体逻辑**：拿 `nums[fast]` 与**结果区的最后一个元素** `nums[slow-1]` 比较。若相等，说明是重复值，`fast` 独自前进；若不等，说明是新值，把它写到 `slow` 处，`slow` 与 `fast` 一起前进。

这里有一个初学者最容易混淆的细节：**为什么是跟 `nums[slow-1]` 比，而不是跟 `nums[slow]` 比？** 因为 `slow` 指向的是"下一个可写位置"，它此刻存放的内容还是尚未处理的旧数据，没有意义；只有 `slow-1` 才是"结果区里最后一个被确认保留的元素"。这个区别，正是从不变量里自然生长出来的——当你清楚 `nums[0..slow-1]` 是结果区，就不会再去比较 `nums[slow]`。

**手动模拟** `[0,0,1,1,1,2,2,3,3,4]`：

```text
初始:  [0, 0, 1, 1, 1, 2, 2, 3, 3, 4]
        ↑slow=1 ↑fast=1

step1: nums[1]=0 == nums[slow-1=0]=0 → 重复，fast++（slow 不动）
step2: nums[2]=1 != nums[0]=0       → 新值，nums[1]=1, slow=2, fast=3
       [0, 1, 1, 1, 1, 2, 2, 3, 3, 4]
           ↑slow=2    ↑fast=3
step3: nums[3]=1 == nums[1]=1       → 重复，fast++
...
最终:  [0, 1, 2, 3, 4, 2, 2, 3, 3, 4]
                        ↑slow=5
返回: slow = 5
```

前 `slow` 个元素就是去重后的结果，后面的残留数据不必清理，题目也不要求清理。

### 2.3 Go 实现

```go
// removeDuplicates 原地删除有序数组中的重复项，返回去重后的长度。
func removeDuplicates(nums []int) int {
    if len(nums) == 0 {
        return 0
    }
    // slow 指向下一个可写位置；nums[0..slow-1] 始终是已去重的结果区。
    slow := 1
    for fast := 1; fast < len(nums); fast++ {
        // 与结果区最后一个元素比较：不相等才说明是新值。
        if nums[fast] != nums[slow-1] {
            nums[slow] = nums[fast]
            slow++
        }
        // 相等则跳过，fast 由循环自增，slow 原地不动。
    }
    return slow
}
```

**复杂度分析**：时间 $O(n)$，`fast` 从头扫到尾，每个元素至多被访问两次（一次读、一次可能的写）；空间 $O(1)$，只用了两个整型变量，满足题目要求。

### 2.4 边界条件

- **空数组**：`len(nums) == 0` 需特判。若不特判，`slow` 初值为 1，循环不执行，返回 1——但空数组的正确结果应当是 0。
- **单元素数组**：`slow = 1`，循环不执行，返回 1，正确。
- **全部相同**，如 `[1,1,1]`：`slow` 始终停在 1，`fast` 走到底，最终返回 1，正确。

> [!note] 一个常见的错误初值
> 有人把 `slow` 设成 0，再用 `nums[++slow] = nums[fast]` 这种"先加后写"的写法。代码或许能跑对，但"`slow` 究竟指向结果区边界还是已写入的最后一个位置"这两套语义会在脑子里打架，一旦题目变复杂，bug 就来了。**笔者的建议是：永远采用"`slow` 指向下一个可写位置"这一套语义，并在注释里把不变量写清楚**。语义统一，胜过一时的代码精简。

## 第 3 章 LeetCode 80：删除有序数组中的重复项 II

### 3.1 题目

**LeetCode 80 - Remove Duplicates from Sorted Array II**（中等）

与第 26 题几乎相同，唯一区别是：每个元素最多保留**两次**（而非一次）。

```text
输入: nums = [1,1,1,2,2,3]
输出: 5, nums = [1,1,2,2,3,_]

输入: nums = [0,0,1,1,1,1,2,3,3]
输出: 7, nums = [0,0,1,1,2,3,3,_,_]
```

### 3.2 从第 26 题泛化：保留 k 次的通用规律

这道题是第 26 题的自然延伸，设计得极为优雅，值得细细体会。

回顾第 26 题的判重逻辑：每个元素最多保留 1 次，所以拿 `nums[fast]` 与结果区的**倒数第 1 个**元素 `nums[slow-1]` 比较。那么第 80 题要求最多保留 2 次，顺理成章地，应当拿 `nums[fast]` 与结果区的**倒数第 2 个**元素 `nums[slow-2]` 比较。

规律于是浮出水面：**若要每个元素最多保留 $k$ 次，就比较 `nums[fast]` 与 `nums[slow-k]`。**

为什么这个规律成立？让我们把它证明清楚。假设 `nums[fast] == nums[slow-k]`。由于数组有序、相同元素连续，若结果区倒数第 $k$ 个元素都等于当前值，那么倒数第 $k-1$、$k-2$、……、第 1 个元素必然也全都等于当前值——也就是说，结果区末尾已经有连续 $k$ 个元素等于 `nums[fast]` 了。此时若再把 `nums[fast]` 收进来，这个值就会出现 $k+1$ 次，超出限制，故应跳过。反之，若 `nums[fast] != nums[slow-k]`，说明结果区末尾连续等于当前值的元素不足 $k$ 个，还可以再收一个，于是放入。

**这就是所谓"泛化"的威力：同一个框架，只改变一个参数 $k$，就解决了一整类"最多保留 k 次"的题目**。面试中若能主动把第 26 题归约到第 80 题、再给出通用模板，往往能让面试官眼前一亮——因为它展示的是"看穿题目共性"的能力，而非"多背了一道题"。

### 3.3 Go 实现

```go
// removeDuplicatesK 原地去重，每个元素最多保留 k 次，返回新长度。
func removeDuplicatesK(nums []int, k int) int {
    if len(nums) <= k {
        return len(nums) // 元素不足 k 个，无需删除
    }
    // 前 k 个元素直接保留，slow 从 k 开始。
    slow := k
    for fast := k; fast < len(nums); fast++ {
        // 与结果区倒数第 k 个元素比较：不等才说明该值出现次数还没满 k。
        if nums[fast] != nums[slow-k] {
            nums[slow] = nums[fast]
            slow++
        }
    }
    return slow
}
```

第 80 题就是 `k = 2` 的特化调用：`return removeDuplicatesK(nums, 2)`。

**手动验证** `[1,1,1,2,2,3]`（$k=2$）：

```text
初始: slow=2, fast=2
      [1, 1, 1, 2, 2, 3]
          ↑slow    ↑fast

step1: nums[2]=1 == nums[slow-2=0]=1 → 已满 2 次，跳过，fast=3
step2: nums[3]=2 != nums[0]=1       → nums[2]=2, slow=3, fast=4
       [1, 1, 2, 2, 2, 3]
             ↑slow=3   ↑fast=4
step3: nums[4]=2 != nums[1]=1       → nums[3]=2, slow=4, fast=5
       [1, 1, 2, 2, 2, 3]
                ↑slow=4   ↑fast=5
step4: nums[5]=3 != nums[2]=2       → nums[4]=3, slow=5
       [1, 1, 2, 2, 3, 3]
                   ↑slow=5

返回: 5，结果 [1,1,2,2,3] ✓
```

### 3.4 一个易被忽略的细节：为什么是 `slow-k` 而不是 `fast-k`

有人会问：既然 `nums[fast]` 要和"结果区倒数第 k 个"比，那结果区倒数第 k 个的下标，究竟是 `slow-k` 还是 `fast-k`？答案是 `slow-k`，因为结果区的长度由 `slow` 决定，而与扫描位置 `fast` 无关。当 `fast` 已经远走在前面、`slow` 落在后面时，`fast-k` 指向的是原料区里的旧数据，只有 `slow-k` 才指向结果区。**这个区别再次印证了不变量的价值——只要牢记"`nums[0..slow-1]` 是结果区"，下标该怎么写便不言自明。**

## 第 4 章 LeetCode 27：移除元素

### 4.1 题目

**LeetCode 27 - Remove Element**（简单）

给你一个数组 `nums` 和一个值 `val`，原地移除所有数值等于 `val` 的元素，返回移除后数组的新长度。不要使用额外的数组空间，必须仅使用 $O(1)$ 额外空间并原地修改输入数组。元素的顺序可以改变。

```text
输入: nums = [3,2,2,3], val = 3
输出: 2, nums = [2,2,_,_]

输入: nums = [0,1,2,2,3,0,4,2], val = 2
输出: 5, nums = [0,1,4,0,3,_,_,_]
```

请注意，和第 26 题不同，这里的数组**不一定有序**，可以是任意顺序。

### 4.2 方法一：同向双指针

最直接的思路与第 26 题一脉相承：`slow` 指向可写位置，`fast` 扫描每个元素，遇到不等于 `val` 的就写入 `slow`。不变量是"`nums[0..slow-1]` 里保存的都是不等于 `val` 的元素"。

```go
func removeElement(nums []int, val int) int {
    slow := 0
    for fast := 0; fast < len(nums); fast++ {
        if nums[fast] != val {
            nums[slow] = nums[fast]
            slow++
        }
    }
    return slow
}
```

时间 $O(n)$，空间 $O(1)$。这个方法**保留了元素的原始相对顺序**，这一点在某些题目里是硬性要求。但本题题目说了"顺序可以改变"，这就暗示着存在一个更省力的方案。

### 4.3 方法二：对撞双指针

方法一有一个不为人知的浪费：即使 `val` 只出现一次，我们仍然会把其余所有元素都"复制"一遍——`nums[slow] = nums[fast]` 会执行 $n-1$ 次。而题目允许改变顺序，这扇门一旦打开，就有了更聪明的走法：用一个左指针 `left` 从头扫，一旦发现 `nums[left] == val`，就用**末尾元素** `nums[right]` 覆盖它，然后右指针左缩。

```go
func removeElementCollide(nums []int, val int) int {
    left, right := 0, len(nums)-1
    for left <= right {
        if nums[left] == val {
            // 用末尾元素覆盖当前 val，右边界左缩。
            nums[left] = nums[right]
            right--
            // 注意：这里不能 left++，因为覆盖过来的元素可能也等于 val，
            // 必须在下一轮重新检查当前 left 位置。
        } else {
            left++
        }
    }
    return left // left 即为有效元素个数
}
```

**手动模拟** `[3,2,2,3], val=3`：

```text
left=0, right=3: nums[0]=3 == val → nums[0]=nums[3]=3, right=2
left=0, right=2: nums[0]=3 == val → nums[0]=nums[2]=2, right=1
                 [2,2,2,3]
left=0, right=1: nums[0]=2 != val → left=1
left=1, right=1: nums[1]=2 != val → left=2
left=2 > right=1 → 退出
返回: 2，有效区 [2,2] ✓
```

**对撞双指针的优势**：当 `val` 出现次数很少时，只需要少量覆盖操作。设数组长 $n$、只有 $k$ 个 `val`，那么对撞方案只需 $k$ 次覆盖，而同向方案需要 $n-k$ 次复制。当 $k \ll n$ 时，对撞方案的实际写入次数少得多。**注意这里说的是"实际写入次数"，而非渐进复杂度——两者都是 $O(n)$，差别在常数因子上。**

> [!info] 何时选同向，何时选对撞
> - **同向双指针**：需要保留元素的原始相对顺序时（如 LeetCode 26、80），或判断逻辑依赖已处理区域的状态时。
> - **对撞双指针**：允许改变顺序，且希望减少实际内存写操作次数时（如本题方法二）；另一个典型场景是有序数组的两数之和（从两端夹逼）。
>
> 判断标准其实就一句话：**题目是否把"顺序"当作一种需要维护的信息**。需要，就同向；不需要，就可以考虑对撞。

### 4.4 对撞双指针的自我覆盖：一个值得说清的细节

在 `left == right` 且 `nums[left] == val` 时，代码会执行 `nums[left] = nums[right]`——这是自己给自己赋值，看似多余，实则无害（结果仍是 `val`）。紧接着 `right--`，于是 `right < left`，循环退出，返回 `left`。此时 `nums[left]` 这个位置在内存上仍留着 `val`，但它已经落在返回长度之外，逻辑上被"排除"了。**这个细节说明：题目要求的"移除"是逻辑上的移除——只要返回的长度不包含它即可，不要求真的把内存清零**。理解这一点，就不会在这个边界上纠结。

## 第 5 章 范式的提炼：读写分离与漏斗

### 5.1 一句话概括双指针的本质

回顾三道题，同向双指针的核心逻辑可以用一句话说尽：

> **慢指针（写）只在"值得保留"时才推进，快指针（读）每轮都推进。两者的速度差，形成了一个筛选漏斗——通过条件的元素被慢指针收入囊中，不通过的被快指针直接越过。**

这句话之所以有用，是因为它把"写"和"读"两件事彻底解耦了。解耦之后，无论题目是去重、删除、还是把偶数挪到前面，你要改的都只是"判断是否保留"这一个条件，框架本身纹丝不动。

### 5.2 有序 vs 无序，决定了判重方式

三道题的判重逻辑，恰好构成一组对照：

| 题目 | 数组状态 | 判重方式 | 为什么可以这样判重 |
|------|---------|----------|-------------------|
| LeetCode 26（最多 1 次） | 有序 | 与 `nums[slow-1]` 比较 | 有序保证相同元素相邻，只需比前一个 |
| LeetCode 80（最多 2 次） | 有序 | 与 `nums[slow-2]` 比较 | 同上，泛化到 k 次 |
| LeetCode 27（移除指定值） | 无序 | 直接与 `val` 比较 | 判断条件是绝对值，不依赖相邻关系 |

这张表隐含了一个重要推论：**如果第 26 题的数组是无序的，同向双指针就不够用了**——因为无序数组里相同的元素可能天各一方，靠"和相邻元素比较"无法判重，必须借助哈希表记录"某个值是否出现过"，空间代价从 $O(1)$ 升到 $O(n)$。**有序性，是很多线性扫描算法得以成立的前提**。面试中一看到"升序数组""已排序"这类字眼，就该条件反射般意识到：它为你打开了一批高效算法的门。

### 5.3 与排序的结合

有时原数组无序，但题目允许先排序再处理。排序的代价是 $O(n \log n)$，但如果排序之后能用 $O(n)$ 的双指针收尾，总复杂度仍是 $O(n \log n)$，通常远好于 $O(n^2)$ 的暴力枚举。这正是第 05 篇 [[05 多指针夹逼：3Sum、3Sum Closest、4Sum 系列]] 的核心策略：先排序，再双指针夹逼。**把"排序"看作一次性的投资，用它换取后续线性扫描的便利，是算法设计里反复出现的思路。**

### 5.4 这类题的面试应答流程

遇到数组的"原地过滤/修改"类题目，建议按以下步骤组织思路：

1. **确认空间约束**：是否允许额外空间。允许，用新数组最省事；不允许，走双指针路线。
2. **确认顺序约束**：是否必须保持相对顺序。不必，则可考虑对撞双指针以减少写操作。
3. **明确不变量**：动笔前先在心里说清"任意时刻，`nums[0..slow-1]` 保存的是什么"。
4. **检查边界**：空数组、单元素、全部是目标值、全部不是目标值。

**这四步里，第三步是分水岭。** 绝大多数人的 bug 不在算法思路上，而在"写着写着忘了 `slow` 到底指向哪里"。

## 第 6 章 代码模板与常见陷阱

### 6.1 三个可复用的模板

**模板一：同向双指针（保留非 val 元素，维持顺序）**

```go
slow := 0
for fast := 0; fast < len(nums); fast++ {
    if 符合保留条件(nums[fast]) {
        nums[slow] = nums[fast]
        slow++
    }
}
return slow
```

**模板二：有序数组去重（最多保留 k 次）**

```go
if len(nums) <= k {
    return len(nums)
}
slow := k
for fast := k; fast < len(nums); fast++ {
    if nums[fast] != nums[slow-k] {
        nums[slow] = nums[fast]
        slow++
    }
}
return slow
```

**模板三：对撞双指针（允许改变顺序，用末尾覆盖）**

```go
left, right := 0, len(nums)-1
for left <= right {
    if nums[left] == val {
        nums[left] = nums[right]
        right-- // 不 left++，需重新检查当前位置
    } else {
        left++
    }
}
return left
```

### 6.2 常见陷阱

**陷阱一：`slow` 的语义不统一。** 前文已述，务必固定为"指向下一个可写位置"。

**陷阱二：对撞双指针忘记重新检查。** 用末尾元素覆盖后如果立刻 `left++`，就会漏掉"覆盖过来的元素本身也等于 `val`"的情况。**正确做法是覆盖后不动 `left`，让下一轮循环重新判断当前位置。**

**陷阱三：Go 里 `range` 无法充当写指针。** `for _, v := range nums` 拿不到下标，也就无法执行 `nums[slow] = v` 这类写入。双指针题必须用下标索引遍历。

```go
// 错误：拿不到下标，无法做原地写回
for _, v := range nums {
    // 不知道 v 在哪儿，nums[slow] = v 无从谈起
}
```

**陷阱四：空数组的特判。** 模板二里 `len(nums) <= k` 的分支，既处理了空数组，也处理了"元素本就不足 k 个、无需删除"的情况，一举两得。

## 第 7 章 双指针家族：同向、对撞与窗口的谱系

本文反复出现"双指针"这个词，但它其实是一个**家族**，成员之间的差别不小。把家族成员摆到一起，有助于在遇到新题时迅速判断该请出哪一位。

### 7.1 三个成员

**同向双指针**（本文主角）：两个指针同方向移动，一快一慢，靠"速度差"完成原地筛选。典型场景是原地过滤、去重——慢指针划定结果区，快指针扫描原料区。

**对撞双指针**：两个指针相向而行，从两端向中间收缩，靠"有序性"保证每一步都能排除一整行或一整列。典型场景是有序数组的两数之和、本文的 Remove Element 方法二。

**滑动窗口**：两个指针同向移动，但语义是"窗口的左右边界"，靠"窗口内统计量的单调性"维护合法性。它其实是同向双指针的一种特化——只不过两个指针的间距（窗口大小）有了明确的含义。

### 7.2 三者的共同前提：单调性

三个成员之所以都能把 $O(n^2)$ 降到 $O(n)$，靠的是同一个前提——**单调性**：指针朝某个方向移动时，问题的某种性质单调地改善或恶化，从而保证"另一个指针不必回退"。

- 同向双指针的单调性来自"已处理区域的判定条件只依赖相邻元素"（有序数组才有）；
- 对撞双指针的单调性来自数组的全局有序；
- 滑动窗口的单调性来自"窗口内统计量相对于边界单调"（如全为正数时，扩窗只会让和增大）。

**一旦这个前提不成立，双指针就会失效。** 例如在含负数的数组上求"和大于等于 target 的最短子数组"，滑动窗口的单调性被破坏（缩窗后和可能反而增大），必须改用前缀和。**"这题能不能用双指针"，等价于"这题有没有可利用的单调性"。**

### 7.3 选型速查

| 题型特征 | 该请出哪一位 |
|---------|-------------|
| 原地过滤/去重，保持顺序 | 同向双指针 |
| 原地删除，允许改变顺序 | 对撞双指针（减少写次数） |
| 有序数组找一对元素满足条件 | 对撞双指针 |
| 连续子数组满足某种约束 | 滑动窗口 |
| 数组含负数、子数组求和 | 前缀和（双指针失效） |

**这张表的价值，是让你在面对新题时先做一次"归类"，再动手。** 本专栏后续的第 05 篇（多指针夹逼）会把对撞双指针用到 $k$ 数之和上；同目录的滑动窗口专栏则会把窗口这一支线展开。**但它们的内核，都是本文反复强调的那条主线——利用单调性，把重复的枚举省掉。**

## 小结

本篇从一个铁约束出发——不能另开空间——一步步逼出了双指针：原数组必须兼任结果区与原料区，于是需要一条会移动的边界；这条边界加上一个扫描游标，便是慢指针与快指针。**双指针不是背下来的套路，而是约束推导出的必然**。

三道题串起来看，真正的收获有三条。其一，**不变量是双指针的地基**，"`nums[0..slow-1]` 是结果区"这一句话，决定了判重该和谁比、下标该怎么写。其二，**"最多保留 k 次"是一个可泛化的框架**，参数 $k$ 一变，一整类题目迎刃而解，这种"看穿共性"的能力比多背几道题更有价值。其三，**同向与对撞的选择，取决于题目是否把顺序当作需要维护的信息**——需要则同向，不需要则对撞以减少写操作。

在认知层面，这三道题还给了一个更普遍的提醒：**约束不是障碍，而是解题方向的指南针**。题目越是把条件收紧（原地、$O(1)$ 空间、保持顺序），可行解的空间就越窄，推导的路径反而越清晰。学会读约束、从约束反推解法，是比记住任何模板都更持久的本事。

下一篇 [[03 数组二分搜索变体：旋转数组与中位数]] 将进入二分搜索的深水区。二分查找的"找某个值"人人都会，但"在旋转有序数组里搜索"和"求两个有序数组的中位数"是面试的高频难点。我们会从二分的核心思想——每次排除一半搜索空间——出发，建立应对所有二分变体题的通用不变量框架。
