# 链表基础与哑节点技巧：Remove Duplicates、Partition List

**摘要：**

从本篇起，专栏跨出数组，进入链表世界。链表题的核心挑战与数组题截然不同：它考的从来不是时间复杂度的优化，而是**指针操作的正确性**与**边界条件的处理**——每一步都不能错，错一步就是空指针异常或断链。本文作为链表专题的入门，引入两件基础工具：**哑节点（Dummy Node）**与**双指针追踪（prev + curr）**，并通过三道典型题落地：LeetCode 83（有序链表去重，每个值保留一次）、LeetCode 82（有序链表去重，重复值全部删除）、LeetCode 86（链表分区）。三题的难度递进关系很讲究——83 不需要哑节点，82 必须用哑节点，86 则要同时维护两条链表并处理"末节点置空"这一隐蔽陷阱。本文用 Go 语言完整实现，并在每一步交代"为什么这么写"，为后续的快慢指针、链表反转打下基础。

## 第 1 章 链表的内存模型与操作要点

### 1.1 链表节点的定义

用 Go 定义 LeetCode 的标准单链表节点，只有两行：

```go
type ListNode struct {
    Val  int
    Next *ListNode
}
```

链表是由节点串成的**动态数据结构**，每个节点存一个值和一个指向后继的引用。与数组相比，它的特性可以用一张表对照：

| 特性 | 数组 | 链表 |
|------|------|------|
| 内存布局 | 连续 | 不连续（散落在堆上） |
| 随机访问 | $O(1)$ | $O(n)$ |
| 头部插入/删除 | $O(n)$（需移位） | $O(1)$ |
| 中间插入/删除（已知前驱） | $O(n)$（需移位） | $O(1)$ |
| 缓存友好性 | 好 | 差（指针跳跃） |

**这张表在后面的每一道题里都会被用到**——链表题之所以偏爱"改引用"而非"搬数据"，正是因为它的中间插入删除是 $O(1)$ 的。

### 1.2 链表操作的三个核心注意点

**注意点一，操作顺序。** 修改指针时，顺序至关重要。以删除节点 B（链为 `A → B → C`）为例，正确写法是 `A.Next = C`，让 B 自然被"遗弃"（Go 的垃圾回收器会回收它）；不需要额外写 `B.Next = nil`。但如果是要**反转**一段链表，顺序就更讲究了——必须先保存后继、再改写当前节点的 `Next`，否则后继节点就永久丢失（第 12 篇会专门讲）。

**注意点二，空指针检查。** 每次访问 `node.Next` 或 `node.Val` 之前，都要确保 `node != nil`。链表题里的空指针异常，十有八九来自遗漏了这一步。

**注意点三，头节点的特殊性。** 许多操作（删除、分区）都可能改动头节点。处理"头节点也要被删"有两条路：**方式 A** 单独特判头节点（繁琐、易错）；**方式 B** 引入哑节点统一处理（推荐）。下面就来认识这件工具。

### 1.3 哑节点：用一个"永远存在的前驱"抹平边界

**哑节点（Dummy Node，也叫哨兵节点）**是一个人为创建的虚拟头节点，安放在真实头节点之前：

```go
dummy := &ListNode{Next: head} // Val 无所谓，只为占位
```

它的作用，用一句话概括就是：**让所有节点（包括原来的头节点）都有一个前驱。** 有了前驱，"删除头节点"与"删除中间节点"的代码就完全一致了——都是 `prev.Next = prev.Next.Next`，不再需要任何 `if head == nil` 的特判。

**使用惯例**：操作全部经由 `dummy` 或 `dummy.Next` 进行，最后返回 `dummy.Next`（它才是操作之后真正的头节点，可能已不是原来的 `head`）。

> [!note] 哑节点的本质：把"特例"变成"通例"
> 哑节点的价值，不在于它多存了一个节点，而在于它**改变了问题的边界结构**。原本"头节点没有前驱"是一个需要单独讨论的特例；加上哑节点后，头节点也有了前驱，特例就消失了，全流程被统一成一种情形。**这种"用一个哨兵抹平边界"的手法，在链表、数组、乃至更复杂的数据结构里反复出现**——它是一种通用的工程智慧：与其为边界写一堆分支，不如改变结构让边界不再特殊。

## 第 2 章 LeetCode 83：删除排序链表中的重复元素（保留一次）

### 2.1 题目

**LeetCode 83 - Remove Duplicates from Sorted List**（简单）

给定一个已排序的链表的头节点 `head`，删除所有重复的元素，使每个元素只出现一次。返回已排序的链表。

```text
输入: head = [1,1,2]      →  输出: [1,2]
输入: head = [1,1,2,3,3]  →  输出: [1,2,3]
```

### 2.2 分析：为什么这题不需要哑节点

链表已排序，所有相同的值必然连续出现，于是判重只需比较"当前节点与它的后继"。

**核心策略**：用一个指针 `curr` 遍历链表。当 `curr.Val == curr.Next.Val` 时，跳过 `curr.Next`（令 `curr.Next = curr.Next.Next`）；否则把 `curr` 前移到下一个节点。

**为什么这题不需要哑节点？** 因为我们**保留每个值的第一次出现**，而头节点作为第一个节点，一定会被保留、绝不会被删除。既然头节点不会消失，就不存在"返回的头节点改变"这一问题，也就用不着哑节点。**"是否需要哑节点"的判断标准，其实就一句话：返回的头节点会不会变？会，就需要；不会，就不必。** 这一点在第 82、86 题里会体现得更清楚。

```go
func deleteDuplicates(head *ListNode) *ListNode {
    curr := head
    for curr != nil && curr.Next != nil {
        if curr.Val == curr.Next.Val {
            curr.Next = curr.Next.Next // 跳过重复节点，curr 不移动
        } else {
            curr = curr.Next
        }
    }
    return head
}
```

**注意 `curr` 在跳过重复后不移动这个细节**：因为跳过一个节点后，`curr.Next` 变成了一个新节点，它可能与 `curr` 又相同（连续多个重复），所以必须在原地再检查一次。**只有当 `curr.Val != curr.Next.Val` 时，才安全地把 `curr` 前移。** 这与第 02 篇对撞双指针里"覆盖后不能立刻 `left++`"是同一种边界意识。

**手动验证** `[1,1,2,3,3]`：

```text
curr=1: curr.Val==curr.Next.Val(1) → 跳过: 1→2→3→3
curr=1: curr.Val!=curr.Next.Val(2) → curr=2
curr=2: curr.Val!=curr.Next.Val(3) → curr=3
curr=3: curr.Val==curr.Next.Val(3) → 跳过: 1→2→3→nil
curr=3: curr.Next==nil → 退出
返回 [1,2,3] ✓
```

**复杂度**：时间 $O(n)$，空间 $O(1)$。

## 第 3 章 LeetCode 82：删除排序链表中的重复元素 II（全部删除）

### 3.1 题目

**LeetCode 82 - Remove Duplicates from Sorted List II**（中等）

给定一个已排序的链表的头节点 `head`，删除原始链表中所有含重复数字的节点，只保留没有重复出现的数字。返回已排序的链表。

```text
输入: head = [1,2,3,3,4,4,5]  →  输出: [1,2,5]
输入: head = [1,1,1,2,3]      →  输出: [2,3]
```

### 3.2 为什么这道题必须用哑节点

第 82 题与第 83 题的唯一区别是：**重复的节点要全部删除，而不是保留一个。**

这个区别带来的后果是决定性的。考虑 `[1,1,1,2,3]`：值为 1 的节点全部要删，**头节点本身也要消失**，返回的头节点不再是原来的 `head`。这就正好踩中了前文那条判断标准——返回的头节点会变，所以**必须用哑节点统一处理**。

```go
func deleteDuplicatesAll(head *ListNode) *ListNode {
    dummy := &ListNode{Next: head}
    prev := dummy // prev 指向最后一个"确认保留"的节点

    curr := head
    for curr != nil {
        // 检测 curr 是否为重复节点的起点
        if curr.Next != nil && curr.Val == curr.Next.Val {
            dupVal := curr.Val
            // 跳过所有值等于 dupVal 的节点
            for curr != nil && curr.Val == dupVal {
                curr = curr.Next
            }
            prev.Next = curr // 把整段重复节点一次性切除
        } else {
            // curr 是唯一值，保留，prev 前移
            prev = curr
            curr = curr.Next
        }
    }
    return dummy.Next
}
```

### 3.3 双指针的角色分工

这道题用了两个指针，分工需要说清：

- `prev`：指向**最后一个确认保留的节点**（初始为哑节点），它负责"接线"；
- `curr`：向前探测，负责"发现重复段"。

当 `curr` 和 `curr.Next` 值相同，说明 `curr` 是一段重复节点的起点：用 `dupVal` 记下这个值，然后让 `curr` 一路跳过所有等于 `dupVal` 的节点；跳出内层循环后，`curr` 停在第一个不等于 `dupVal` 的节点上，此时令 `prev.Next = curr`，**就把整段重复节点一次性切除了**——注意是"整段"，而不是逐个删除，这正是"全部删除"语义的体现。

反之，若 `curr` 是唯一值，就让 `prev` 前移到 `curr`（把它标记为"确认保留"），再让 `curr` 前移。

**手动验证** `[1,1,1,2,3]`：

```text
初始: dummy(-1) → 1 → 1 → 1 → 2 → 3
prev=dummy, curr=1

curr=1: curr.Next(1).Val == curr.Val(1) → dupVal=1
  内层循环: curr 跳过所有 1，停在 2
  prev.Next = 2 → dummy → 2 → 3
curr=2: curr.Next(3).Val != curr.Val(2) → prev=2, curr=3
curr=3: curr.Next==nil → prev=3, curr=nil
返回 dummy.Next = 2 → 3 ✓
```

**复杂度**：时间 $O(n)$，空间 $O(1)$。

> [!warning] 生产避坑：内层循环的终止条件
> 内层"跳过所有 `dupVal`"的循环，条件必须写成 `curr != nil && curr.Val == dupVal`——**`curr != nil` 这个检查绝不能省**。若省略它，当重复段一直延伸到链表末尾时（如 `[1,1,1]`），`curr` 会一路走到 `nil`，再访问 `curr.Val` 就会 panic。链表题里"遍历到末尾"的边界，永远要用 `curr != nil` 兜住。

## 第 4 章 LeetCode 86：分隔链表

### 4.1 题目

**LeetCode 86 - Partition List**（中等）

给你一个链表的头节点 `head` 和一个特定值 `x`，对链表进行分隔，使得所有**小于** `x` 的节点都出现在**大于或等于** `x` 的节点之前。你应当**保留**两个分区中每个节点的初始相对顺序。

```text
输入: head = [1,4,3,2,5,2], x = 3  →  输出: [1,2,2,4,3,5]
输入: head = [2,1], x = 2          →  输出: [1,2]
```

### 4.2 双哑节点：分开维护两条链

**关键约束是"必须保留原始相对顺序"**，所以不能简单地交换节点的值，只能重新组织引用。

**解法**：创建两条独立的链表——`smallList` 收集所有 `< x` 的节点，`largeList` 收集所有 `>= x` 的节点。遍历完原链表后，把 `smallList` 的尾部接到 `largeList` 的头部，再把 `largeList` 的尾部置空（断开可能残留的多余连接）。

```go
func partition(head *ListNode, x int) *ListNode {
    smallDummy := &ListNode{} // 小链表的哑节点
    largeDummy := &ListNode{} // 大链表的哑节点

    small, large := smallDummy, largeDummy // 两条链各自的当前尾部
    for curr := head; curr != nil; curr = curr.Next {
        if curr.Val < x {
            small.Next = curr
            small = small.Next
        } else {
            large.Next = curr
            large = large.Next
        }
    }

    large.Next = nil            // 关键：大链表末尾置空，防止成环
    small.Next = largeDummy.Next // 小链表尾部接上大链表头部
    return smallDummy.Next
}
```

### 4.3 为什么必须写 `large.Next = nil`

这是一个极易遗漏、又极其致命的细节。回看原链表 `[1,4,3,2,5,2]`：最后一个节点 `2` 的 `Next` 原本指向 `nil`，但倒数第二个 `5` 的 `Next` 原本指向那个 `2`。分区时，`2` 被收进了 `smallList`，而 `5` 被收进了 `largeList`。**如果不把 `large` 的尾部 `Next` 置空，那么 `5.Next` 仍然指着 `2`——而这个 `2` 此刻正位于 `smallList` 之中**，于是两条链之间多出一条回边，链表结构被破坏，甚至形成环。

```go
large.Next = nil // 断开大链表末尾指向旧结构的残留连接
```

**这一行在面试中经常被遗漏。** 记住它的理由很简单：**当一条链的尾部曾经指向另一个节点、而这个节点后来被挪去了别处时，这个尾部引用就成了悬空的残留，必须显式断开。** 从 `smallDummy` 和 `largeDummy` 出发，两个哑节点在这里又各司其职了一次——它们分别充当了两条新链的"永远存在的前驱"。

**手动验证** `[1,4,3,2,5,2], x=3`：

```text
curr=1(<3):  small 链: dummy→1
curr=4(>=3): large 链: dummy→4
curr=3(>=3): large 链: dummy→4→3
curr=2(<3):  small 链: dummy→1→2
curr=5(>=3): large 链: dummy→4→3→5
curr=2(<3):  small 链: dummy→1→2→2

拼接:
  large.Next = nil  → 4→3→5→nil
  small.Next = 4    → 1→2→2→4→3→5
返回 smallDummy.Next → [1,2,2,4,3,5] ✓
```

**复杂度**：时间 $O(n)$（一遍扫描），空间 $O(1)$（只用了常数个指针）。

## 第 5 章 链表操作的通用思维框架

### 5.1 画图优先

链表操作在脑子里抽象推导极易出错，**动手画图永远是第一步**：用方框表示节点，箭头表示 `Next`，在图上标出每一步操作后指针的变化。面试时对面试官说一句"我先画个图梳理一下"，不是浪费时间，而是展示扎实的工程习惯——**因为链表题的错误几乎全都藏在那些"箭头指向哪里"的细节里，而画图是暴露这些细节最有效的方式。**

### 5.2 哑节点的使用准则

把三道题的经验归纳成一条准则：

**必须用哑节点的情形：**
- 可能删除头节点（LeetCode 82、19、203）；
- 返回的头节点可能改变（LeetCode 21 合并链表、LeetCode 86）；
- 需要维护多条链表并在最后拼接（LeetCode 86、143）。

**不必用哑节点的情形：**
- 头节点一定被保留（LeetCode 83 保留每个值一次）；
- 只是遍历、不删除（求长度、找节点等）。

**判断的口诀只有一句：返回的头节点会不会变？**

### 5.3 常见边界条件清单

每写完一道链表题，把下面这些边界过一遍：

| 边界条件 | 说明 |
|---------|------|
| `head == nil` | 空链表，函数是否直接返回 |
| 只有一个节点 | `head.Next == nil`，循环是否执行、返回值是否正确 |
| 要操作的是头节点 | 是否用哑节点统一处理 |
| 链表末尾节点 | `curr.Next == nil` 时，别再访问 `curr.Next.Val` |
| 操作后末节点的 `Next` | 是否需要置 `nil`（防止残留连接成环） |

**这份清单里的最后一条，正是第 86 题的 `large.Next = nil`。** 它提醒我们：链表题的边界，不只是"两端"，还包括"操作完成后那些被改动的引用是否干净"。

### 5.4 三道题的模式对比

| 题目 | 需要哑节点 | 核心操作 | 难点 |
|------|-----------|---------|------|
| LeetCode 83（保留一次） | 不需要 | `curr.Next = curr.Next.Next` | 无 |
| LeetCode 82（全部删除） | **必须** | `prev.Next = curr`（跳过整段） | 内层循环的终止条件 |
| LeetCode 86（分区） | **两个哑节点** | 分拆再合并 | `large.Next = nil` 防成环 |

**三题的递进关系很值得玩味**：83 教你"如何遍历与跳过"，82 教你"如何用哑节点统一头节点边界"，86 教你"如何用多个哑节点维护多条链"。它们共同构成链表操作的基础设施，后面所有链表题都会用到这套工具。

## 第 6 章 延伸：三道同源的链表基础题

前面的三道题已经立起了哑节点与双指针两件工具。为了让这套工具更扎实，这里再补三道同源的题——它们用到的技巧与前面完全一致，正好可以用来检验"是否真的把工具握在了手里"。

### 6.1 LeetCode 203：移除链表元素

**题目**：给你一个链表的头节点 `head` 和一个整数 `val`，删除链表中所有满足 `Node.Val == val` 的节点，返回新的头节点。

这道题与第 82 题的差别在于：**82 题删的是"出现重复的值"，203 题删的是"等于某个指定值的节点"**。判定条件变了，但"头节点可能被删"这一结构性困难没变——所以它同样**必须用哑节点**。

```go
func removeElements(head *ListNode, val int) *ListNode {
    dummy := &ListNode{Next: head}
    prev := dummy
    for curr := head; curr != nil; curr = curr.Next {
        if curr.Val == val {
            prev.Next = curr.Next // 跳过 curr，prev 不动
        } else {
            prev = curr // curr 保留，prev 前移
        }
    }
    return dummy.Next
}
```

**注意这里与第 83 题的一个关键区别**：83 题用单指针 `curr` 就能跳过重复节点（因为跳过之后 `curr` 不移动、下一轮继续检查新的 `curr.Next`）；而 203 题用 `prev` + `curr` 双指针，是因为"要删的节点可能在任意位置"，需要一个"确认保留的最后一个节点"来接线。**什么时候用单指针、什么时候用双指针，取决于"被跳过的节点是否总是当前节点的后继"**——83 题是（重复值必然相邻），203 题不是。

### 6.2 LeetCode 21：合并两个有序链表

**题目**：将两个升序链表合并为一个新的升序链表并返回。

这道题与第 86 题的分区思路一脉相承——**都是"分拆再合并"，只是这里的"分拆"依据不是某个阈值，而是两个链表各自的顺序**。它同样用哑节点作为新链表的起点：

```go
func mergeTwoLists(list1, list2 *ListNode) *ListNode {
    dummy := &ListNode{}
    curr := dummy
    for list1 != nil && list2 != nil {
        if list1.Val <= list2.Val {
            curr.Next = list1
            list1 = list1.Next
        } else {
            curr.Next = list2
            list2 = list2.Next
        }
        curr = curr.Next
    }
    // 接上剩余的、非空的那条链
    if list1 != nil {
        curr.Next = list1
    } else {
        curr.Next = list2
    }
    return dummy.Next
}
```

**最后"接上剩余链"那一步是本题的点睛之笔**：当一条链先走完时，另一条链剩下的部分**本身就已有序、且整体不小于已合并部分**，于是直接整条接上即可，无需逐个比较。**这个"剩余部分直接接上"的简化，正是利用了两条链各自有序这一前提**——若两条链无序，就必须逐个归并到底。

### 6.3 LeetCode 234：回文链表

**题目**：判断一个链表是否为回文链表。

这道题把前面几篇的工具**串了起来**：先用快慢指针找中点（第 11 篇的预告），再反转后半段（第 12 篇的预告），最后逐个比较前后两半。它是一道很好的"综合体检题"。

```go
func isPalindrome(head *ListNode) bool {
    // 第一步：快慢指针找中点
    slow, fast := head, head
    for fast != nil && fast.Next != nil {
        slow = slow.Next
        fast = fast.Next.Next
    }
    // 第二步：反转后半段（slow 之后的部分）
    var prev *ListNode
    for slow != nil {
        next := slow.Next
        slow.Next = prev
        prev, slow = slow, next
    }
    // 第三步：前后两半逐个比较
    left, right := head, prev
    for right != nil { // 以较短的后半段为边界
        if left.Val != right.Val {
            return false
        }
        left, right = left.Next, right.Next
    }
    return true
}
```

**循环边界再次体现为"以较短的一段为准"**：反转后的后半段不会比前半段长，因此用 `right != nil` 作为比较的终止条件最稳妥。这与第 13 篇重排链表的"交叉合并"用的是同一条原则——**凡是处理"一长一短两段"的链表题，循环上界都应取较短的那一段。**

### 6.4 小结：工具的真正掌握

把这三道延伸题与前面三题并排看，会发现一件有意思的事：**它们并没有引入任何新工具，用的还是哑节点、双指针、反转、合并这几件旧家伙。** 之所以还能称作"新题"，只是因为约束或载体换了个样子。

这正是笔者把这三题放在这里的原因——**检验"是否真正掌握一件工具"的标准，不是能不能复述它的代码，而是遇到一个换了皮的场景时，能不能一眼认出"这里该用它"**。当你看到"头节点可能被删"就条件反射地想到哑节点，看到"一长一短两段"就想到"以短的为准"，这套工具才算真正长在了手上。

## 第 7 章 从链表到工程：这些技巧在真实系统里的影子

面试题里的链表操作看似"学术"，但本章要讲的这几件工具——哑节点、分拆合并、双向链表——在真实系统里都有对应的身影。理解这一点，有助于回答面试官那句常见的追问："这些东西工作中用得到吗？"

### 7.1 哑节点：链表实现的通用防护栏

几乎所有严肃的链表库，都会在链表头部放一个"哨兵"或"虚拟头"。原因与面试题里如出一辙：**它让插入、删除、遍历这些操作不再需要区分"操作的是不是第一个节点"。** 一个带哨兵的循环链表，插入与删除的代码可以短到只有两行，而且天然支持"空链表"这一情形——因为哨兵节点自己构成了一个最小的环。

反过来说，那些不带哨兵、处处 `if (head == nil)` 的实现，往往就是 bug 的高发区。**哑节点在面试里是一个小技巧，在工程里却是一种"用结构消除分支"的设计习惯**——这与第 01 篇提到的"让基础设施替应用隐藏复杂性"是同一类思想。

### 7.2 分拆再合并：从链表分区到归并排序

第 86 题的"分拆两条链再拼接"，本质上就是归并排序在链表上的雏形。归并排序对链表特别友好——因为它的核心操作是"把两条有序链合并成一条"，而链表合并**不需要额外的 $O(n)$ 空间**（数组归并需要），只需重新串接指针。

这也是为什么工业界的链表排序（如 Linux 内核、JDK 的 `LinkedList` 排序）几乎都选用归并排序而非快速排序：**归并能在链表上做到稳定且 $O(1)$ 额外空间，而快排的分区操作对链表并不自然**。第 86 题里那句 `large.Next = nil`，在真实的归并实现里对应的就是"合并前先断开两条链"这一必要步骤——**一处被面试题简化了、却在工程里必须严谨处理的细节。**

### 7.3 双向链表：一切"有序容器"的地基

第 86 题只需单链表，但一旦需求变成"能在 $O(1)$ 时间内删除任意一个已知节点"，单链表就力不从心了——因为它拿不到前驱。这时双向链表就登场了。Linux 内核的链表、Redis 的列表与 LRU、Java 的 `LinkedHashMap`，底层都依赖双向链表。

**这解释了一个常见的面试追问**："为什么 LRU 缓存要用双向链表而不是单链表？"标准答案不是"双向链表更高级"，而是"**删除任意节点必须是 $O(1)$，而单链表删一个节点必须先 $O(n)$ 找到前驱**"——一句朴素的时间复杂度分析，正是这道题的全部要害。第 13 篇会把这套逻辑完整展开。

### 7.4 认知落点：技巧的背后是约束

把本章的三段影子放在一起看，会发现它们都在回应同一件事：**工程里的链表实现之所以长成那个样子，全都是被"边界处理""额外空间""操作代价"这些约束逼出来的。** 哑节点是为了消除边界分支，归并是为了省下 $O(n)$ 空间，双向链表是为了让删除够快——没有一处是为了"好看"。

这恰恰呼应了本专栏反复强调的那条主线：**约束是解题方向的指南针**。面试题是约束的浓缩，工程实现是约束的展开；看懂了约束如何塑造解法，你就同时看懂了两者。

## 第 9 章 面试表达：如何把一道链表题讲清楚

链表题"做出来"和"讲清楚"是两回事。面试官看的往往不只是最终代码，而是你**在不确定时如何思考**。本章给出一套可复用的表达模板。

### 9.1 五步表达法

**第一步，复述题意并点出关键约束。** "这题要删除有序链表中重复的节点，且重复的要全部删掉——所以头节点可能被删，我打算用哑节点统一处理。" **这一句就向面试官展示了你已经识别出本题的核心难点。**

**第二步，画出初始状态。** 在纸上画几个方框和箭头，标出 `prev`、`curr` 的位置。**链表题的思考离不开图，主动画图本身就是加分项。**

**第三步，讲清指针的角色分工。** "`prev` 指向最后一个确认保留的节点，`curr` 向前探测。当 `curr` 与 `curr.Next` 相同时，说明进入了一段重复，我用内层循环跳过整段，再让 `prev.Next` 指向跳过的落点。"

**第四步，说清边界。** "内层循环必须带 `curr != nil`，否则重复段延伸到末尾时会 panic；头节点可能被删，所以返回 `dummy.Next`。"

**第五步，分析复杂度并检查边界清单。** "时间 $O(n)$、空间 $O(1)$。我再检查一下空链表、单节点、全同元素这三种情况……"

### 9.2 为什么要"讲"而不只是"写"

**面试官无法读你的心，只能听你的话。** 一段正确的代码，若你说不清它的不变量与边界，面试官就无法确认你是"想清楚了"还是"碰巧写对了"。反之，即便代码略有瑕疵，只要你能清晰说明思路、并主动指出"这里我可能要考虑某个边界"，往往也能获得不错的评价。

**这就是"表达"在算法面试里的真实分量**——它不是包装，而是把你的思考过程外化，让面试官有机会与你协作。**一道链表题，讲得清楚比写得快更重要。**

### 9.3 一个常被忽视的收尾

讲完解法后，主动补一句"**如果链表是双向的，这题会简单一些，因为删除节点不需要先找前驱**"或"**如果要保留头节点，就不需要哑节点了**"，这类"举一反三"的补充，能显著提升印象分——**它说明你不是在背一道题，而是真的理解了这类题的边界在哪里。**

## 小结

本篇作为链表专题的开篇，把"指针操作的正确性"这一主线立了起来。LeetCode 83 用最朴素的单指针遍历，示范了"跳过重复但不前移"的边界处理；LeetCode 82 引入哑节点，把"头节点可能被删"这一特例统一成了通例，并用 `prev + curr` 双指针完成"整段切除"；LeetCode 86 则同时维护两条链表，暴露了 `large.Next = nil` 这个隐蔽却致命的残留连接陷阱。

三道题合起来，给出两条可迁移的经验。其一，**哑节点是链表题的通用解药**，其判断标准可以浓缩成一句"返回的头节点会不会变"——会变就用，不会变就不必。其二，**链表题的难点几乎全在边界**：末尾节点的访问、整段删除的终止条件、操作完成后的残留引用，这些都不是算法层面的难题，而是"每一步都不能错"的精细功夫。**链表题考的不是智商，而是严谨——这恰恰是它作为面试筛子的价值所在。**

下一篇 [[11 链表快慢指针：环检测、倒数节点与链表旋转]] 将引入链表题最经典的技巧——**快慢指针**（Floyd 判圈算法）。两个速度不同的指针在链表上"赛跑"，能解决环路检测、找环入口、删除倒数第 N 个节点、旋转链表等一系列问题，其中的数学推导尤为精彩。
