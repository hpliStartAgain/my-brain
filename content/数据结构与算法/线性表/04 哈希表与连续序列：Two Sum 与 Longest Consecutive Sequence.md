# 哈希表与连续序列：Two Sum 与 Longest Consecutive Sequence

**摘要：**

哈希表（Hash Table）是线性表题目里最常用的"外挂"——它不改变数组本身，却能把"查找"这一动作的代价从线性压到常数。本文以两道题为主轴：LeetCode 1（Two Sum）是面试界的"Hello World"，几乎人人会写，但真正理解它"单遍边存边查"为什么就足够、以及它与有序数组双指针的取舍关系的人并不多；LeetCode 128（Longest Consecutive Sequence）则是一道反直觉题，直觉告诉你"连续序列非排序不可"，但哈希表能在 $O(n)$ 时间内解决，其中的关键是一句"只从连续段的起点出发扩展"的过滤条件。本文不止步于给出代码，而是逐层追问：哈希表的 $O(1)$ 究竟买的是什么、代价是什么；单遍遍历为什么不会漏掉答案；以及一个看似 $O(n^2)$ 的双层循环，凭什么能被证明是 $O(n)$。读完本篇，你将掌握"以空间换时间"这一策略的完整判断依据，而不只是两道题的答案。

## 第 1 章 哈希表：$O(1)$ 查询买的是什么，代价又是什么

### 1.1 数组的软肋：知道值，却找不到位置

在已有数组、链表这些结构的前提下，哈希表究竟补上了哪块短板？

数组的随机访问是 $O(1)$，但这份便利有一个苛刻的前提——**你必须知道下标**。可现实中更常见的需求恰恰相反：你手里只有一个**值**，想知道它是否存在、出现在哪里。数组对此无能为力，只能从头到尾线性扫描，代价 $O(n)$。链表更糟，连按下标定位都做不到。

哈希表（Hash Map / Hash Set）要解决的，正是这个问题：**给定一个任意的键（Key），在 $O(1)$ 期望时间内判断它是否存在，或取出它对应的值。** 这个能力在算法题里无处不在。以 Two Sum 为例，问题的核心动作是"对于每个 `nums[i]`，判断 `target - nums[i]` 是否出现过"——一次典型的"按值查找"。若每次查找都要线性扫描，整个算法就退化成 $O(n^2)$；一旦把查找降到 $O(1)$，整体也就降到了 $O(n)$。**哈希表在 Two Sum 里的角色，不是存数据，而是把"查找"这个动作变廉价。**

### 1.2 哈希表的原理与它的真实复杂度

哈希表的做法是：用一个**哈希函数**把键映射到数组的某个下标，

$$\text{index} = \text{hash}(\text{key}) \bmod \text{capacity}$$

理想情况下，不同的键映射到不同的下标，查找便退化为"算一次哈希、读一次数组"，是货真价实的 $O(1)$。但理想归理想，实际中不同键难免撞到同一个下标，这就是**哈希冲突**。工程上的解法无非两类：链表法（每个槽位挂一条链表，冲突的元素接在后面）与开放寻址法（冲突时按某种规则探测下一个空槽）。以 Go 为例，运行时的 `map` 采用桶（bucket）加溢出链的设计，当单个桶内元素过多时查找会变慢，因此运行时会通过扩容维持负载因子在低位。

> [!info] 哈希表的 $O(1)$ 是期望值，不是最坏值
> 说"哈希表查询是 $O(1)$"，严格来说指的是**期望复杂度**，其成立依赖哈希函数能把键均匀打散。倘若哈希函数设计得极差，所有键都映射到同一个槽，查找就退化成 $O(n)$。因此哈希表的安全感，一半来自结构，另一半来自哈希函数的质量。此外，哈希表还有**扩容**机制：负载因子超过阈值时申请更大的表并重新散列，这次操作是 $O(n)$ 的，但均摊到每次插入仍是 $O(1)$——与动态数组扩容是同一套均摊分析的道理。

### 1.3 代价：天下没有免费的 $O(1)$

哈希表不是免费的午餐。它换来 $O(1)$ 查询的代价，是**额外的 $O(n)$ 空间**，以及哈希计算、冲突处理带来的常数开销。这正是"以空间换时间"最纯粹的体现。

这条代价有一个很实用的推论：**面试里一旦面试官追问"能否用 $O(1)$ 额外空间实现"，几乎就等于在暗示"不许用哈希表"，你得换一条路**——要么直接在原数组上原地操作，要么先排序再借助有序性。**哈希表能出现在解法里，本身就意味着你默认接受了 $O(n)$ 的空间账单**，写代码前先想清楚这笔账能不能付，比写完之后被追问要主动得多。

## 第 2 章 LeetCode 1：两数之和

### 2.1 题目

**LeetCode 1 - Two Sum**（简单）

给定一个整数数组 `nums` 和一个目标值 `target`，找出和为 `target` 的两个整数，返回它们的**数组下标**。假设每种输入只对应一个答案，且同一元素不能使用两次。

```text
输入: nums = [2,7,11,15], target = 9  →  输出: [0,1]
输入: nums = [3,2,4], target = 6      →  输出: [1,2]
输入: nums = [3,3], target = 6        →  输出: [0,1]
```

### 2.2 从暴力到优化的推导

**暴力解法**是两层循环，枚举所有下标对 $(i, j)$，检查 `nums[i] + nums[j] == target`。时间 $O(n^2)$，$n = 10^4$ 时就是 $10^8$ 次比较，必然超时。

优化的切口在哪里？请把暴力解法重新表述一遍：对每个 `nums[i]`，我们其实在问一个**查找问题**——"数组里有没有另一个元素等于 `target - nums[i]`"。暴力的慢，不在于枚举本身，而在于**每一次这样的查找都用了一次线性扫描**。于是优化方向不言自明：把这 N 次查找，从 $O(n)$ 各自为战，换成 $O(1)$。

- 用**线性扫描**查找：每次 $O(n)$，总体 $O(n^2)$——和暴力没有区别；
- 用**哈希表**查找：每次 $O(1)$，总体 $O(n)$——这就是优化方向。

### 2.3 单遍哈希：边存边查

一个常见的写法是"先把所有元素存进哈希表，再逐个查补数"。但更优雅、也更不易出错的，是**单遍哈希**：遍历到 `nums[i]` 时，先查哈希表里有没有 `target - nums[i]`（即"我需要的另一半"是否已出现过），有就直接返回；没有，再把 `nums[i]` 连同下标存入，供后面的元素来查。

```go
func twoSum(nums []int, target int) []int {
    // key 为数组中的值，value 为该值出现的下标
    seen := make(map[int]int, len(nums))
    for i, v := range nums {
        complement := target - v // 需要的另一半
        if j, ok := seen[complement]; ok {
            return []int{j, i} // 找到，返回两个下标
        }
        seen[v] = i // 没找到，登记当前元素，供后续查找
    }
    return nil // 题目保证有解，逻辑上不可达
}
```

### 2.4 为什么单遍就够了——一个不容含糊的证明

初次见到单遍写法的人，常有一个疑问：遍历到靠前的元素时，它"需要的另一半"可能还在数组后方、尚未被存入哈希表，这样岂不是会漏掉答案？

**不会，而且可以严格证明。** 设答案是一对下标 $(i, j)$ 且 $i < j$。当遍历指针走到 $j$ 时，`i` 必然已经被存入哈希表——因为 $i < j$，`i` 更早被访问，其元素在那一轮就已登记。于是走到 $j$ 时查询 `target - nums[j]`，恰好命中 `nums[i]`，答案在这一刻被捕获。反过来，走到 $i$ 时 `j` 还没被访问，哈希表里自然没有 `nums[j]`，这一轮查不到——但这无关紧要，因为我们在这一轮把 `nums[i]` 登记了进去，等于给未来的 `j` 留好了线索。

**这段证明的价值在于，它把"单遍就够"从一个需要记忆的技巧，变成了一条可以推导的结论。** 面试中若被追问"为什么不用两遍"，这段论证就是最好的回答。

### 2.5 重复元素与"同一元素不能用两次"

考虑 `nums = [3, 3]`、`target = 6`：

- `i = 0`：补数为 3，哈希表为空，未命中，登记 `{3: 0}`；
- `i = 1`：补数为 3，命中，返回下标 `[0, 1]`。

单遍写法的"先查后存"顺序，天然规避了"用同一个元素两次"的风险：在第 0 轮查的时候，哈希表里还没有 `3`，不可能查到"自己"；到第 1 轮查到的 `3`，其下标是 0，与当前的 1 不同，是货真价实的两个不同位置。**顺序，在这里不是随意的，而是正确性的一部分。**

> [!warning] 生产避坑：两遍哈希必须校验下标不同
> 若改用"先全部存入、再逐个查"的两遍写法，就必须显式检查"查到的下标是否等于当前下标"，否则当 `2 * nums[i] == target` 时，会用一个元素配对自己，得出错误答案。单遍写法把这一检查内化进了顺序里，因而更推荐。**能靠顺序规避的边界，就不要留给条件判断。**

### 2.6 如果数组有序：双指针更省空间

若题目改为"数组已升序、返回 1-based 下标"（LeetCode 167），则对撞双指针能在 $O(n)$ 时间、$O(1)$ 空间内解决：

```go
func twoSumSorted(nums []int, target int) []int {
    left, right := 0, len(nums)-1
    for left < right {
        sum := nums[left] + nums[right]
        switch {
        case sum == target:
            return []int{left + 1, right + 1}
        case sum < target:
            left++ // 和偏小，右移左指针以增大和
        default:
            right-- // 和偏大，左移右指针以减小和
        }
    }
    return nil
}
```

**为什么对撞双指针在有序数组上一定正确？** 因为它依赖有序性提供的**单调性**：当 `sum < target` 时，我们需要的是一对更大的数；由于数组升序，右移左指针必然让和增大，而左移右指针只会让和更小——所以此时"右指针不该动"是可以证明的，而不是猜的。每一步的调整都是确定性的，既不重复也不遗漏。

**这道题完整地展示了"算法选择取决于约束"这一命题**：

| 输入条件 | 推荐方案 | 时间 | 空间 |
|----------|----------|------|------|
| 无序数组，返回原下标 | 哈希表 | $O(n)$ | $O(n)$ |
| 有序数组，返回下标 | 对撞双指针 | $O(n)$ | $O(1)$ |
| 无序数组，要求 $O(1)$ 空间 | 先排序再双指针 | $O(n \log n)$ | $O(1)$（但丢失原下标） |

请特别注意最后一行：先排序虽然能换来 $O(1)$ 额外空间，却把原始下标信息打乱了，因此它**不适合"要求返回原下标"的 Two Sum**，只适合"返回值或存在性"的变体。**约束不是孤立的——空间约束会牵动下标的可用性，进而决定方案是否可行**，这就是为什么"看题先看约束"永远排在"想解法"之前。

## 第 3 章 LeetCode 128：最长连续序列

### 3.1 题目

**LeetCode 128 - Longest Consecutive Sequence**（中等）

给定一个未排序的整数数组 `nums`，找出数字连续的最长序列的长度（不要求序列元素在原数组中相邻）。要求实现时间复杂度为 $O(n)$ 的算法。

```text
输入: nums = [100,4,200,1,3,2]      →  输出: 4（最长连续序列 [1,2,3,4]）
输入: nums = [0,3,7,2,5,8,1,4,6,9]  →  输出: 10（全部数字连成一段）
```

### 3.2 直觉陷阱：为什么"排序"看起来是唯一的路

第一直觉几乎必然是：排个序，再线性扫描一遍找最长的连续段。

```go
// 排序方案：逻辑正确，但复杂度为 O(n log n)
sort.Ints(nums)
maxLen, curLen := 1, 1
for i := 1; i < len(nums); i++ {
    if nums[i] == nums[i-1]+1 {
        curLen++
    } else if nums[i] != nums[i-1] { // 跳过重复元素
        curLen = 1
    }
    if curLen > maxLen {
        maxLen = curLen
    }
}
```

这段代码完全正确，但它败在复杂度上：排序本身是 $O(n \log n)$，达不到题目要求的 $O(n)$。**题目为什么要卡这个复杂度？因为它在逼你跳出"排序"这个默认选项，去直面问题的本质困难。**

本质困难是什么？数组无序，你手里拿着一个数 `n`，却不知道它的前驱 `n-1` 和后继 `n+1` 在哪儿。排序之所以有效，是因为它**一次性建立了这种"相邻关系"**，代价是 $O(n \log n)$。那么有没有办法，不排序也能随时判断"某个数在不在数组里"？有的——这正是哈希表登场的时机。**用哈希表把"查询某数是否存在"的代价降到 $O(1)$，就相当于在 $O(n)$ 的预算内"模拟"出了排序后遍历的效果。**

### 3.3 核心洞察：只从连续段的起点出发

把元素全部放进哈希集合后，一个自然的想法是：对每个元素，都试着向两边扩展，数出它所在的连续段长度。但这样做会有一个致命问题——**同一个连续段会被反复扩展**。`[1,2,3,4]` 这段，从 1 扩展一遍、从 2 扩展一遍、从 3 扩展一遍、从 4 扩展一遍，白白做了四倍的工作，最坏情况退化成 $O(n^2)$。

破局的关键，是一个极其简洁的过滤条件：**一个数 `n` 是它所在连续段的起点，当且仅当 `n - 1` 不在集合中。** 如果 `n - 1` 存在，那么 `n` 绝不是起点，它只是某个更长序列的中间或末尾——于是我们**只从起点出发向右扩展**，段内的其他元素都因为"不是起点"而被直接跳过，不再重复劳动。

```text
nums = [100, 4, 200, 1, 3, 2]
集合 = {100, 4, 200, 1, 3, 2}

逐个检查是否为起点（即 n-1 是否不在集合）：
- 100: 99 不在 → 起点，向右扩：101 不在，长度 = 1
- 4:   3  在   → 不是起点，跳过
- 200: 199不在 → 起点，向右扩：201 不在，长度 = 1
- 1:   0  不在 → 起点，向右扩：2在→3在→4在→5不在，长度 = 4
- 3:   2  在   → 不是起点，跳过
- 2:   1  在   → 不是起点，跳过

最长长度 = 4
```

### 3.4 Go 实现

```go
func longestConsecutive(nums []int) int {
    if len(nums) == 0 {
        return 0
    }
    // 用集合存储全部元素，把"某数是否存在"降到 O(1) 期望时间
    numSet := make(map[int]struct{}, len(nums))
    for _, v := range nums {
        numSet[v] = struct{}{}
    }

    maxLen := 0
    for v := range numSet { // 遍历集合而非原数组，天然去重
        // 只从起点开始扩展：v-1 不存在，v 才是某段的起点
        if _, ok := numSet[v-1]; ok {
            continue
        }
        cur, length := v, 1
        for {
            if _, ok := numSet[cur+1]; !ok {
                break
            }
            cur++
            length++
        }
        if length > maxLen {
            maxLen = length
        }
    }
    return maxLen
}
```

### 3.5 为什么它真的是 $O(n)$——均摊分析的又一次现身

这道题最容易引起疑惑之处在于：外层 `for` 循环是 $O(n)$，内层那个 `for` 扩展循环看起来也可能执行很多次，直觉上像是 $O(n^2)$，怎么就被称作 $O(n)$ 了？

答案仍要回到那个"起点过滤"条件上。**内层循环的每一次推进，都对应着访问一个"某段起点之后"的元素；而每个元素最多被内层循环访问一次。** 理由是这样的：内层扩展只从起点出发，而每个连续段有且仅有一个起点，段内其余元素都因"`n-1` 在集合中"而在 `continue` 处被跳过，绝不会驱动另一次扩展。于是，把外层循环的总轮次 $n$ 与内层循环的总推进次数（同样是 $n$）相加，总操作数是 $O(n)$。

**这种"外层 $n$ 次、内层累计 $n$ 次"的分析方式，正是均摊分析（Amortized Analysis）的典型形态**——与第 01 篇里动态数组扩容的分析如出一辙。它提醒我们一件事：**看到嵌套循环就断言 $O(n^2)$ 是危险的；真正决定复杂度的，是每个元素在全部循环中被访问的"总次数"，而不是循环的层数。**

> [!note] 设计哲学：在入口处过滤，避免重复劳动
> 这道题的精髓，全在"只从起点出发"这一句过滤条件上。它用一次 $O(1)$ 的前置检查（`n-1` 是否存在），把一个潜在的 $O(n^2)$ 过程压成了 $O(n)$。这种"在入口处拦截，而不是在过程中去重"的思路，在算法里反复出现：与其在扩展时费力判断"这段我是不是算过了"，不如在源头上只让该干活的那一个元素干活。**约束施加得越早，省下的重复工作就越多。**

### 3.6 另一种视角：并查集

Longest Consecutive Sequence 也可以用**并查集（Union-Find）**求解：初始时每个元素自成一个集合，随后对每个元素 `n`，若 `n+1` 存在，就把 `n` 与 `n+1` 所在集合合并；最终取最大的那个集合。并查集在路径压缩后，单次操作均摊接近 $O(1)$，整体也是 $O(n)$。

两种方案复杂度相当，取舍在于代码量：**哈希表方案只需一个集合加一段扩展逻辑，清晰得多；并查集方案则多出一整套父指针数组、查找与合并函数。** 面试中优先给出哈希表方案，若面试官追问"还有别的思路吗"，再补充并查集，往往能体现视野的宽度。

## 第 4 章 哈希表在线性表题中的通用模式

### 4.1 四类典型场景

哈希表在数组、字符串题里的用法，基本可以归入下面四类。识别出题目属于哪一类，解法方向就定了大半：

| 场景 | 哈希表的作用 | 典型题目 |
|------|-------------|----------|
| 查找补集 | 存已见元素，$O(1)$ 查"需要的另一半"是否存在 | Two Sum（LC 1）、3Sum（LC 15） |
| 判断存在性 | 快速判断某值是否在集合中，避免线性扫描 | Longest Consecutive Sequence（LC 128） |
| 统计频次 | 统计每个元素出现次数，为后续判断提供依据 | 字母异位词（LC 242）、Single Number II（LC 137） |
| 记录位置 | 存元素首次出现的下标，用于计算长度 | 无重复字符的最长子串（LC 3） |

### 4.2 HashSet 还是 HashMap

面试中该用集合还是映射，判断标准其实只有一条：**题目是否需要返回下标或附加信息**。

- **集合（HashSet）**：只存值，回答"某值是否存在"，最省空间——用于 Longest Consecutive Sequence；
- **映射（HashMap，key 为值、value 为下标）**：既存值又存下标，回答"某值在哪"——用于 Two Sum。

**当题目只要"存在性"，用集合即可，不必多此一举地存下标**；反之，若题目要求返回下标，映射就是必需的。选错了不会错，但会显得对问题的理解不够精准。

### 4.3 三个常见陷阱

**陷阱一：对同一元素查了两次。** 两遍哈希的写法必须校验下标不同（前文已述）。单遍写法靠"先查后存"的顺序天然规避。

**陷阱二：重复键覆盖。** `seen[v] = i` 在数组有重复元素时，会用靠后的下标覆盖靠前的。对 Two Sum 而言题目保证唯一解，通常无碍；但若场景要求记录**所有**出现位置，就得分用 `map[int][]int`。

**陷阱三：遍历集合还是遍历原数组。** Longest Consecutive Sequence 里，遍历集合而非原数组，能天然去重，逻辑也更干净。**这类"数据该以什么形态被遍历"的选择，看似细节，实则直接影响代码的清晰度与正确性。**

## 第 5 章 习题扩展与权衡曲线

### 5.1 LeetCode 454：四数相加 II

四个数组 `A、B、C、D`，统计满足 `A[i]+B[j]+C[k]+D[l] = 0` 的四元组个数。

**思路是 Two Sum 的直接推广**：把 `A[i]+B[j]` 的全部可能值存入一个映射并计数（时间 $O(n^2)$），再遍历 `C[k]+D[l]` 的全部可能，查映射中 `-(C[k]+D[l])` 的计数并累加。总时间 $O(n^2)$，空间 $O(n^2)$。**这道题说明：哈希表的"补集查找"模式并不局限于二元，任意维度的问题都能通过"两两打包"降维到它。**

### 5.2 LeetCode 242：有效的字母异位词

判断两个字符串是否互为字母异位词（字母相同、顺序不同）。用映射统计 `s` 中各字符频次（`+1`），再用 `t` 抵消（`-1`），最后检查是否全部归零。若字符集固定为小写字母，可用长度 26 的数组替代映射，空间更省、常数更小。**当键的取值范围有限且已知时，数组往往比哈希表更快——这是"用更专的结构换更小的常数"的又一个小权衡。**

### 5.3 时间与空间的权衡曲线

这两道题共同印证了一条普遍规律：**降低时间复杂度，通常要付出空间代价。** 把本篇的方案整理成一张取舍表：

| 方案 | 时间 | 空间 | 适用场景 |
|------|------|------|----------|
| Two Sum 暴力 | $O(n^2)$ | $O(1)$ | 内存极度受限 |
| Two Sum 哈希 | $O(n)$ | $O(n)$ | 常规场景 |
| LCS 排序 | $O(n \log n)$ | $O(1)$（原地排序） | 对空间敏感 |
| LCS 哈希 | $O(n)$ | $O(n)$ | 对时间敏感 |

**在真实工程中，内存通常比 CPU 时间廉价，用 $O(n)$ 空间换取从 $O(n \log n)$ 到 $O(n)$ 的时间改善，是极为常见的优化手段。** 但在面试的特定语境下，"能否 $O(1)$ 空间"是一个独立的考点，因此不能一概而论——**权衡的依据永远是具体的约束，而非某条放之四海而皆准的教条。**

## 第 6 章 哈希表的工程细节：扩容、负载因子与最坏情况

前面把哈希表当作一个"查询 $O(1)$"的黑盒来用。但对面试官而言，"你知不知道黑盒里发生了什么"往往是一个区分度的考点。本章补上几处关键细节。

### 6.1 负载因子与扩容

哈希表不可能把桶填满——如果装得太满，冲突会急剧增多，查询退化。于是它维护一个**负载因子（load factor）**：已存元素数 ÷ 桶数量。当负载因子超过阈值（Go 的 `map` 大约是 6.5，Java 的 `HashMap` 默认是 0.75），就触发**扩容**：申请一个约两倍大的新桶数组，把旧元素重新散列过去。

**扩容本身是 $O(n)$ 的**，与动态数组的扩容如出一辙。但同样地，均摊到每次插入仍是 $O(1)$——**这就是为什么说哈希表的 $O(1)$ 是"均摊"的**。面试中若被问"哈希表插入的最坏复杂度"，严谨的答案是"单次可能 $O(n)$（扩容），均摊 $O(1)$"。

### 6.2 最坏情况：当哈希函数失效

哈希表的 $O(1)$ 依赖一个隐含前提——**哈希函数能把键均匀打散**。若所有键都映射到同一个桶，查找就退化成 $O(n)$。这不是理论上的杞人忧天：如果输入的键恰好与哈希函数"犯冲"（比如某些实现下大量字符串的哈希值取模后相同），退化就会真实发生。

正因如此，现代哈希表实现会做一些防护：Go 的 `map` 用随机化的哈希种子抵御"哈希碰撞攻击"；Java 的 `HashMap` 在单个桶内元素过多时把链表转成红黑树，把最坏查询从 $O(n)$ 降到 $O(\log n)$。**这些设计的共同点，是"不让最坏情况太坏"——用一点额外成本，换取一个更可预测的性能下界。**

### 6.3 对面试的三点启示

**启示一，别说"哈希表查询是 $O(1)$"就完事**，补一句"期望/均摊 $O(1)$，最坏 $O(n)$"，能显著提升答案的严谨度。

**启示二，键的选取会影响性能。** 用整数作键通常比用长字符串快（哈希计算更便宜）；若键的范围有限且已知，直接用数组下标（如第 07 篇数独的位掩码、字符计数的 `int[26]`）往往比哈希表更快、更省。

**启示三，"哈希表 vs 排序"是两条不同的加速路径。** 哈希表用 $O(n)$ 空间把查找降到期望 $O(1)$，适合"一次建表、多次查询"；排序用 $O(n \log n)$ 时间把数据变有序，适合"后续要做范围查询、找相邻、去重"等操作。**选哪条路，取决于后续要做什么，而不取决于哪条路听起来更快。**

> [!info] 一个实用的替代
> 当键的取值范围有限（如小写字母、0-255 的字节、0-9 的数字），**数组常常是比哈希表更好的"映射"**：`int[26]` 之于小写字母、`int[256]` 之于字节，它们的"哈希函数"就是下标本身，没有冲突、没有扩容、常数极小。**在算法题里，能开数组就别开哈希表**——这是第 02、07、09 篇反复出现的同一建议。

## 小结

本篇的两道题，共同讲述了一个关于"查找"的故事。Two Sum 揭示了哈希表最核心的价值：**它不改变数据，只把"按值查找"这一动作从线性降到常数**，于是原本 $O(n^2)$ 的枚举，得以在一遍线性扫描里完成。而单遍哈希之所以成立，靠的是一条可证明的性质——答案对 $(i, j)$ 中靠后的那个下标被访问时，靠前的那个必已入表。Longest Consecutive Sequence 则把哈希表用于"判断存在性"，再用一句"只从起点扩展"的过滤条件，把看似 $O(n^2)$ 的扩展压回 $O(n)$，其背后是均摊分析。

两道题串起来，能提炼出三点可迁移的经验。其一，**哈希表的本质是"空间换时间的查找加速器"，判断该不该用它，只需问一句"这题的核心动作是不是按值查找"**。其二，**约束会连锁传导**——空间约束会牵动下标可用性，进而决定方案可行与否，因此看题必须先看约束。其三，**看到嵌套循环不要急着下 $O(n^2)$ 的结论**，真正决定复杂度的是每个元素被访问的总次数，这既是均摊分析的精髓，也是很多人高估难度的根源。

在认知层面，本篇还留下一个更普遍的问题：哈希表把查找变得廉价，这份廉价究竟从何而来？答案是它**预先支付了一笔空间与哈希计算的成本**，把未来的查找成本摊薄了。现实中的缓存、索引、预处理，莫不如此——**所有"查询变快"的背后，都藏着一笔早已付出的代价**，理解了这一点，也就理解了性能优化里最常见的那类权衡。

下一篇 [[05 多指针夹逼：3Sum、3Sum Closest、4Sum 系列]] 将进入"多数之和"专题。这类题是 Two Sum 的自然延伸，核心策略是"排序 + 降维"：把 k 数之和逐步归约为 Two Sum，最终落到双指针或哈希上。真正的难点，是如何在去重的同时不漏掉任何一组解。
