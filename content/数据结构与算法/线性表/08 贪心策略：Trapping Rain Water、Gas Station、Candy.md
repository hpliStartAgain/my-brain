# 贪心策略：Trapping Rain Water、Gas Station、Candy

**摘要：**

贪心算法（Greedy Algorithm）是四套基础算法思想里最"反直觉"的一套：它每一步只顾眼前，从不回头，却时常能得出全局最优解。正因为它时常成立、又时常不成立，贪心题真正考验的从来不是"怎么贪"，而是"**凭什么能贪**"——也就是那个必须被证明的"贪心选择性质"。本文以三道经典题为载体，把这条主线讲透。接雨水（LeetCode 42）是面试高频硬题，有动态规划、双指针、单调栈三种 $O(n)$ 解法，其中双指针用一句"哪侧更矮、哪侧的瓶颈就已确定"的推理把空间压到 $O(1)$；加油站（LeetCode 134）的贪心正确性证明堪称理解贪心的绝佳案例——"从当前起点到失败点之间的任意点都不可行"这一论断，必须靠反证才能立住；分发糖果（LeetCode 135）则展示了"两遍扫描 + 取最大值"这一处理双向约束的通用手法。本文用 Go 语言完整实现，并在每一题后交代它的贪心为何成立，力求让你既会写、也敢证明。

## 第 1 章 贪心算法的本质与适用条件

### 1.1 贪心是什么，它为什么可能正确

贪心的定义简单到近乎朴素：**在每一步决策中，选择当前看起来最优的选项，不回头，不修改已经做出的决定。**

直觉上，这像是一种"短视"策略——只顾眼前得失，不计长远后果。那么它凭什么有时能得到全局最优？关键在一个性质上，称为**贪心选择性质（Greedy Choice Property）**：局部的最优选择，能够推导出全局最优解。与之配套的，还有**最优子结构**——原问题的最优解，包含子问题的最优解。

**贪心算法的真正难点，因此不在"如何贪"，而在"能不能贪"。** 一道题如果具有贪心选择性质，代码往往短得出奇；若不具有，你却硬套贪心，就会得到一个"能跑但错"的解。这也解释了为什么贪心题在面试里格外有价值：它考的是**判断力与证明能力**，而非模板记忆。

### 1.2 贪心与动态规划的边界

贪心和动态规划（Dynamic Programming）都面向"最优化"问题，却是两种截然不同的思路。它们的区别可以用一句话概括：**贪心"只顾一条路走到底"，动态规划"把所有可能性都记下来，再从中挑最好的"。**

| 特性 | 贪心 | 动态规划 |
|------|------|---------|
| 决策方式 | 每步做当前最优决策，不回头 | 记录所有子问题的解，反复利用 |
| 子问题重叠 | 不需要 | 需要（这正是 DP 的价值来源） |
| 时间复杂度 | 通常 $O(n)$ 或 $O(n \log n)$ | 通常 $O(n^2)$ 或更高 |
| 难点 | 证明贪心选择性质 | 找出状态转移方程 |
| 适用条件 | 最优子结构 + 贪心选择性质 | 最优子结构（不必有贪心性质） |

**这张表最值得记住的一行是"难点"。** 动态规划的难，在于"想不出转移方程"；贪心的难，在于"证不出它为什么对"。前者是构造性的困难，后者是论证性的困难。**面试中如果一道题你能写出贪心解，却说不清它为何正确，往往比写不出更危险——因为面试官一句"为什么这样贪不会漏掉最优解"，就足以让你哑口。**

## 第 2 章 LeetCode 42：接雨水

### 2.1 题目

**LeetCode 42 - Trapping Rain Water**（困难）

给定 `n` 个非负整数表示宽度为 1 的柱子高度图，计算下雨之后这些柱子能接住多少雨水。

```text
输入: height = [0,1,0,2,1,0,1,3,2,1,2,1]
输出: 6
```

柱子之间的凹槽可以蓄水，求总蓄水量。

### 2.2 核心观察：每个位置的存水量由"两侧最高柱"决定

这道题的一切推导，都从下面这条观察出发：

> 位置 $i$ 能存下的水量，等于 $\min(\text{左侧最高柱},\ \text{右侧最高柱}) - \text{height}[i]$（若该值为负，说明此处不存水，按 0 计）。

为什么是"两侧最高柱的较小者"？因为水往低处流——一个位置的水位，只会被**两侧更矮的那道"墙"**拦住，超出的部分会从矮的那一侧溢出去。**把两侧最高柱想象成围住这段地形的两道堤坝，水位自然由较矮的那道堤坝决定。** 这条观察是把三维的"积水"问题降维成一维"逐格计算"的钥匙。

### 2.3 方法一：动态规划预处理（$O(n)$ 时间，$O(n)$ 空间）

有了核心观察，最直接的实现就是：先用两个数组，分别预计算出每个位置"左侧最高柱"与"右侧最高柱"，再逐格套公式。

```go
func trapDP(height []int) int {
    n := len(height)
    if n == 0 {
        return 0
    }
    leftMax := make([]int, n)
    rightMax := make([]int, n)

    // 从左到右，求每个位置（含自身）左侧的最高柱
    leftMax[0] = height[0]
    for i := 1; i < n; i++ {
        leftMax[i] = max(leftMax[i-1], height[i])
    }
    // 从右到左，求每个位置（含自身）右侧的最高柱
    rightMax[n-1] = height[n-1]
    for i := n - 2; i >= 0; i-- {
        rightMax[i] = max(rightMax[i+1], height[i])
    }

    total := 0
    for i := 0; i < n; i++ {
        total += min(leftMax[i], rightMax[i]) - height[i]
    }
    return total
}
```

时间 $O(n)$，空间 $O(n)$。**这是思路最清晰、最容易讲清楚的方案**，面试时先抛出它，既展示了正确的推导，也为后面的空间优化留了台阶。

### 2.4 方法二：双指针（$O(n)$ 时间，$O(1)$ 空间）

方法一用了 $O(n)$ 的预处理数组。能否只用常数空间？可以，但需要一句关键的推理。

用两个指针 `left`、`right` 从两端向中间靠拢，各自维护"到目前为止左/右两侧的最高柱" `leftMax`、`rightMax`。**关键推理是这样的**：当 `height[left] < height[right]` 时，对于 `left` 这个位置——

- 它左侧的最高柱，已经确切等于 `leftMax`（左边扫过了）；
- 它右侧的最高柱，**至少**有 `height[right]` 那么高（右边还没扫完，但 `height[right]` 本身就是一道已知的墙）。

于是 $\min(\text{左侧最高},\ \text{右侧最高})$ 中的"右侧最高"至少是 `height[right]`，而它比 `height[left]` 大——**这意味着"两侧最高柱中的较小者"必定来自左侧，即 `leftMax`**，与右侧尚未探明的部分无关。既然 `left` 位置的存水量此刻已经可以完全确定（就是 `leftMax - height[left]`），那就放心处理它、并把 `left` 右移。

这正是贪心"能贪"的地方：**不是猜的，而是"更矮的那一侧，其瓶颈已经确定"这一推理给了我们确定性。** 反之，当 `height[left] >= height[right]` 时，右侧的瓶颈已经确定，处理 `right` 并左移。

```go
func trapTwoPointers(height []int) int {
    left, right := 0, len(height)-1
    leftMax, rightMax := 0, 0
    total := 0

    for left < right {
        if height[left] < height[right] {
            // 左侧更矮，左侧成为瓶颈，left 位置的存水量已确定
            if height[left] >= leftMax {
                leftMax = height[left]
            } else {
                total += leftMax - height[left]
            }
            left++
        } else {
            // 右侧更矮（或相等），右侧成为瓶颈
            if height[right] >= rightMax {
                rightMax = height[right]
            } else {
                total += rightMax - height[right]
            }
            right--
        }
    }
    return total
}
```

**手动验证** `[0,1,0,2,1,0,1,3,2,1,2,1]`：

```text
left=0(h=0), right=11(h=1): h[left]<h[right] → leftMax=0, total+=0-0=0, left++
left=1(h=1), right=11(h=1): h[left]>=h[right] → rightMax=1, right--
left=1(h=1), right=10(h=2): h[left]<h[right] → leftMax=1, left++
left=2(h=0), right=10(h=2): h[left]<h[right] → total+=1-0=1, left++
...
（继续推进，最终 total=6）
```

### 2.5 方法三：单调栈（$O(n)$ 时间，$O(n)$ 空间）

第三种思路截然不同：它**按"横向的层"累加存水**，而不是逐格计算。维护一个"高度单调不增"的栈（存下标），当遇到比栈顶更高的柱子时，说明栈顶那个位置找到了"槽的右壁"，于是弹出它、计算这一层的存水量。

```go
func trapStack(height []int) int {
    stack := []int{} // 存下标，对应高度单调不增
    total := 0
    for i := 0; i < len(height); i++ {
        for len(stack) > 0 && height[i] > height[stack[len(stack)-1]] {
            mid := stack[len(stack)-1]
            stack = stack[:len(stack)-1] // 弹出凹槽底部
            if len(stack) == 0 {
                break
            }
            left := stack[len(stack)-1]
            width := i - left - 1
            h := min(height[i], height[left]) - height[mid]
            total += width * h
        }
        stack = append(stack, i)
    }
    return total
}
```

**三种方法的取舍：**

| 方法 | 时间 | 空间 | 特点 |
|------|------|------|------|
| 动态规划预处理 | $O(n)$ | $O(n)$ | 最直观，思路清晰 |
| 双指针 | $O(n)$ | $O(1)$ | 空间最优，需要"瓶颈侧"的推理 |
| 单调栈 | $O(n)$ | $O(n)$ | 按横向层累加，是理解单调栈的好例子 |

> [!info] 面试时该讲哪一种
> 建议的顺序是：**先讲动态规划方案**（展示清晰的推导），**再给出双指针优化**（展示空间优化能力）。单调栈方案作为"还有一种完全不同的视角"备用——它虽然也是 $O(n)$，但空间并不更优，且思路与前者差异较大，除非面试官特意问起单调栈，否则不必主动展开。**展示"能优化"比展示"知道很多解法"更重要。**

## 第 3 章 LeetCode 134：加油站

### 3.1 题目

**LeetCode 134 - Gas Station**（中等）

一条环路上有 `n` 个加油站，第 `i` 站有汽油 `gas[i]` 升。油箱容量无限。从第 `i` 站开往第 `i+1` 站需耗油 `cost[i]` 升。你从某一站出发、初始油箱为空，若能绕环路行驶一周，返回出发站编号，否则返回 -1。若存在解，**保证唯一**。

```text
输入: gas = [1,2,3,4,5], cost = [3,4,5,1,2]  →  输出: 3
输入: gas = [2,3,4], cost = [3,4,3]          →  输出: -1
```

### 3.2 两条基础观察

**观察一，总量决定可行性。** 若 $\sum \text{gas}[i] < \sum \text{cost}[i]$，油的总供给不够总消耗，无论从哪里出发都跑不完全程，直接返回 -1。

**观察二，总量够则必有解。** 令 `diff[i] = gas[i] - cost[i]` 表示在第 `i` 站净获得的油量。若 $\sum \text{diff}[i] \ge 0$，则必然存在某个合法起点——这一点后面会由贪心过程顺带证明。

### 3.3 贪心的关键论断与它的证明

从位置 0 开始模拟，维护当前油量 `tank`。一旦某一刻 `tank < 0`，说明从当前起点出发，到这里就"跑不动了"。此时贪心地**把起点更新为下一站 `i+1`，并把 `tank` 清零**，继续模拟。

这个贪心之所以成立，全靠下面这条论断：

> **若从起点 `start` 出发、走到位置 $i$ 时油量变负，那么从 `start` 到 $i$ 之间（含 `start`）的任意一个位置 $k$ 出发，同样不可行。**

**证明（反证）**：从 `start` 出发，走到 $k$ 时油量必然 $\ge 0$（否则更早就该换起点了，不会走到 $i$ 才失败）。而从 $k$ 出发，相比从 `start` 出发，少了 `start` 到 $k$ 这一段积累的净油量——也就是说，从 $k$ 出发到达 $i$ 时的油量，只会比从 `start` 出发时更少。既然从 `start` 出发到 $i$ 已经是负数，从 $k$ 出发只会更负。故 $k$ 也不可行。

**这条论断的威力在于，它把"排除一个起点"升级成了"排除一整段起点"**——一次失败，就安全地跳过了 `start` 到 $i$ 的所有候选，这正是贪心能把复杂度压到 $O(n)$ 的根据。

```go
func canCompleteCircuit(gas, cost []int) int {
    totalGas, tank, start := 0, 0, 0
    for i := 0; i < len(gas); i++ {
        diff := gas[i] - cost[i]
        totalGas += diff
        tank += diff
        if tank < 0 {
            // 从 start 出发到不了 i+1，区间 [start, i] 全部排除
            start = i + 1
            tank = 0
        }
    }
    if totalGas < 0 {
        return -1
    }
    return start
}
```

### 3.4 为什么只走一圈就够

这道题最令人不安的地方是：模拟时我们只从 `start` 走到了末尾，并没有真的绕回 `start` 前面那些站，凭什么断定绕完一圈也不会失败？

**关键在"总量足够"这一前提。** 设找到的起点为 `start`。模拟过程保证了从 `start` 到 `n-1` 这段后半程油量始终 $\ge 0$；而由于总量 $\sum \text{diff} \ge 0$，走完后半程后油箱里积累了非负的油量。当汽车绕回前半段 `[0, start-1]` 时，它带着这笔"盈余"出发——**前半段本身可能在起点处失败过（所以 `start` 才会被推到这里），但那是在"空油箱"假设下的失败；如今带着后半程攒下的盈余进入，处境只会更好。**

用一个更直观的比喻：把累计净油量画成一条随位置起伏的折线（$y$ 轴是累计油量，$x$ 轴是位置）。**贪心选出的 `start`，正是这条折线的全局最低点的下一个位置。** 从全局最低点之后出发，折线只会向上或持平，走完一圈自然不会再跌到负数。**"从最低点出发"这一几何直觉，比逐字推导更能让人一眼看穿贪心的合理性。**

## 第 4 章 LeetCode 135：分发糖果

### 4.1 题目

**LeetCode 135 - Candy**（困难）

`n` 个孩子站成一排，`ratings[i]` 是第 `i` 个孩子的评分。分发糖果需满足：每个孩子至少 1 块；**相邻孩子中评分更高者，获得的糖果更多**。求最少需要准备的糖果总数。

```text
输入: ratings = [1,0,2]  →  输出: 5（分配 [2,1,2]）
输入: ratings = [1,2,2]  →  输出: 4（分配 [1,2,1]）
```

### 4.2 双向约束与"两遍扫描"的思路

这道题的约束来自**两个方向**，且彼此独立：

- 左约束：若 `ratings[i] > ratings[i-1]`，则 `candy[i] > candy[i-1]`；
- 右约束：若 `ratings[i] > ratings[i+1]`，则 `candy[i] > candy[i+1]`。

难点在于，一个位置可能同时受两侧约束（如 `[1,2,1]` 中的中间峰顶，必须比左右都多）。**一次从左到右的扫描只能照顾左约束，一次从右到左的扫描只能照顾右约束——于是自然的想法是：分别扫两遍，每一遍专门处理一个方向的约束，最后取两者中较大的那个值。**

**第一遍，从左到右**，处理左约束：初始化每人 1 块，若 `ratings[i] > ratings[i-1]`，则 `candy[i] = candy[i-1] + 1`。

**第二遍，从右到左**，处理右约束：若 `ratings[i] > ratings[i+1]`，则 `candy[i] = max(candy[i], candy[i+1] + 1)`。

```go
func candy(ratings []int) int {
    n := len(ratings)
    candies := make([]int, n)
    for i := range candies {
        candies[i] = 1 // 每人至少 1 块
    }

    // 第一遍：从左到右，满足左约束
    for i := 1; i < n; i++ {
        if ratings[i] > ratings[i-1] {
            candies[i] = candies[i-1] + 1
        }
    }

    // 第二遍：从右到左，满足右约束，取 max 以不破坏左约束
    for i := n - 2; i >= 0; i-- {
        if ratings[i] > ratings[i+1] {
            candies[i] = max(candies[i], candies[i+1]+1)
        }
    }

    total := 0
    for _, c := range candies {
        total += c
    }
    return total
}
```

**手动演算** `[1,0,2]`：

```text
第一遍（左约束）：[1, 1, 2]
第二遍（右约束）：
  i=1: ratings[1]=0 < ratings[2]=2，不更新
  i=0: ratings[0]=1 > ratings[1]=0，candies[0] = max(1, 1+1) = 2
结果：[2,1,2]，总和 = 5 ✓
```

### 4.3 为什么第二遍必须用 `max` 而不是直接赋值

这是本题最容易出错、也最能体现"双向约束"精髓的一处细节。**若第二遍直接赋值 `candies[i] = candies[i+1] + 1`，就会把第一遍建立的左约束结果覆盖掉。** 以 `ratings = [1,2,3,2,1]` 为例：

```text
第一遍后：      [1, 2, 3, 1, 1]（峰顶 candies[2]=3 满足左约束）
若直接赋值：i=2 时 candies[2] = candies[3]+1 = 2，覆盖了 3
             变成 [1,2,2,2,1]
             但 ratings[2]=3 > ratings[1]=2，却 candies[2]=2 == candies[1]=2，左约束被破坏
用 max：      candies[2] = max(3, 2) = 3，两个约束同时满足 ✓
```

**`max` 的作用，是在"满足新约束"的同时"不破坏旧约束"。** 每一个位置要同时满足两侧约束，而它最终应取的糖果数，就是两个方向各自要求的最大值。**这正是"分别处理、再取最大"这套手法的核心——独立约束之间没有耦合，可以用两遍独立的扫描各自求下界，最后取并。**

### 4.4 贪心正确性说明

两遍贪心的正确性，可以逐条说清：

- **第一遍是对的**：它按左约束求出了每个位置的"左向最小值"——若 `ratings[i] > ratings[i-1]`，则至少要比左邻多 1；否则 1 已是最小。
- **第二遍是对的**：它在右约束下把每个位置抬到"右向最小值"，并用 `max` 保留了左向的下界，因此结果同时满足两个方向，且每一步都不多给。
- **全局最优**：两遍之后，每个位置的值都是"满足全部约束前提下的最小可能值"，逐项最小，总和自然最小。

**这里出现了一个值得注意的现象**：分发糖果看似是一道"两遍贪心"的题，但它的正确性其实并不依赖某种玄妙的"贪心选择性质"，而依赖一个更朴素的事实——**两个方向的约束彼此独立，可以对它们分别求下界再取并。** 换句话说，它是"分而治之"而非"真正的贪心"。**辨清这一点很重要：不要把所有"一次线性扫描得出最优"的解法都笼统归为贪心，它们背后的正确性依据可能完全不同。**

## 第 5 章 贪心正确性的证明方法

三道题各用了不同的论证方式，值得把它们抽象成可复用的套路：

**套路一，反证排除一整段（加油站）。** 先假设"最优起点"落在某个区间内，再证明该区间内任一点都不可能，从而把候选集一次性砍掉一大截。**这是贪心能"一步排除多个候选"的典型论证。**

**套路二，瓶颈确定即安全处理（接雨水双指针）。** 当"更矮的一侧"决定了当前位置的答案，且这一决定与尚未处理的部分无关时，就可以放心地定下这个位置。**这是"局部可确定"型贪心的论证。**

**套路三，独立约束分别求下界（分发糖果）。** 当约束来自多个互不耦合的方向时，分别处理、再取并，即可同时满足。**这其实是"分治"思想的一种变体。**

**三套套路共同的落脚点，是"证明每一步的局部决策不会损害全局最优"。** 面试中答贪心题，请务必把这句话讲出来，并配上一段具体的论证——**只会写代码不会证明，是贪心题里最常见的失分点。**

## 第 6 章 延伸：贪心家族的三道同源题

三道主线题展示了贪心的三种形态。再补三道题，它们用的都是同一套"局部最优推出全局最优"的思路，可以进一步巩固对贪心的判断力。

### 6.1 跳跃游戏（LeetCode 55）：维护可达区间

**题目**：给定非负整数数组 `nums`，你最初位于第一个下标。每个元素代表在该位置可以跳跃的最大长度。判断能否到达最后一个下标。

这道题的贪心视角非常干净：**不要纠结"具体跳到哪一步"，只需维护"当前能到达的最远下标"**，一路更新下去；若最远下标能覆盖到终点，就成功。

```go
func canJump(nums []int) bool {
    farthest := 0 // 当前能到达的最远下标
    for i := 0; i < len(nums); i++ {
        if i > farthest {
            return false // 当前位置已不可达，说明卡住了
        }
        if i+nums[i] > farthest {
            farthest = i + nums[i]
        }
        if farthest >= len(nums)-1 {
            return true
        }
    }
    return true
}
```

**为什么这样贪心是对的？** 因为我们维护的 `farthest` 是"在已走过的所有位置中，能到达的最远处"，它是一个**单调不减的上界**。只要当前位置 `i` 不超过这个上界，它就一定可达；反之，一旦 `i > farthest`，说明中间出现了一段无法跨越的"真空地带"，任何走法都到不了这里，自然也就到不了终点。**这里没有"选择哪一步"的纠结，只有"可达范围"的维护——很多贪心题的关键，正是找到一个这样单调推进的不变量。**

### 6.2 买卖股票的最佳时机（LeetCode 121）：一次遍历求最大差值

**题目**：给定数组 `prices`，第 `i` 个元素是某股票第 `i` 天的价格。你只能选择某一天买入、并在未来某一天卖出，求最大利润。

直觉上要枚举所有"买入-卖出"对（$O(n^2)$），但贪心能把它降到 $O(n)$：**遍历过程中，始终维护"到目前为止的最低价格"，并用"当前价格 − 最低价格"更新最大利润。**

```go
func maxProfit(prices []int) int {
    minPrice := math.MaxInt32
    maxProfit := 0
    for _, p := range prices {
        if p < minPrice {
            minPrice = p // 更新历史最低价
        } else if p-minPrice > maxProfit {
            maxProfit = p - minPrice // 更新最大利润
        }
    }
    return maxProfit
}
```

**贪心成立的依据是"最优卖出日一定对应某个最优买入日"**：对于每一个"卖出日"，为了让利润最大，买入日必然是它之前价格最低的那一天。于是只需一次遍历，边记录最低价、边计算"若今天卖出能赚多少"。**这道题与接雨水的双指针异曲同工——都是"在扫描中维护一个历史最值，用它来即时确定当前位置的答案"。**

### 6.3 柠檬水找零（LeetCode 860）：面额优先级的贪心

**题目**：顾客排队买柠檬水，每杯 5 元。顾客可能付 5、10、20 元，你需要正确找零。判断能否给每位顾客都正确找零。

这道题的贪心策略是**"找零时优先使用大面额"**：收到 20 元时，优先用一张 10 元加一张 5 元找零，而不是三张 5 元。原因很直接——**10 元只能用于给 20 元找零，而 5 元更灵活（既能给 10 元找、也能给 20 元找）**，所以应当尽量把灵活性低的 10 元先用出去。

```go
func lemonadeChange(bills []int) bool {
    five, ten := 0, 0
    for _, b := range bills {
        switch b {
        case 5:
            five++
        case 10:
            if five == 0 {
                return false
            }
            five--
            ten++
        case 20:
            if ten > 0 && five > 0 {
                ten--
                five--
            } else if five >= 3 {
                five -= 3
            } else {
                return false
            }
        }
    }
    return true
}
```

**这道题的贪心依据，是"资源的灵活性排序"**：5 元比 10 元更通用，所以优先消耗 10 元。**当贪心涉及"多种资源的选择顺序"时，判断标准往往是"哪种资源更稀缺/更不通用，就先消耗它"**——这是一个可以迁移到很多调度类问题的经验。

### 6.4 三道延伸题给我们的

三道题分别代表了贪心的三种"可证明性来源"：跳跃游戏靠**单调不变量**（可达范围只增不减），买卖股票靠**历史最值**（最优卖出对应最优买入），柠檬水找零靠**资源灵活性排序**。它们与主线三题一起，构成了一张贪心的"证据类型"图谱。

**判断一道题能不能贪心，本质上就是在寻找这样一份证据。** 找到了，贪心就是对的；找不到，就该老老实实回去用动态规划。**贪心与动态规划的分界线，从来不是"题目难度"，而是"能否给出这份证据"。**

## 第 7 章 常见误区与自测方法

### 7.1 四个高频误区

**误区一：把"局部最优"当成"全局最优"，却不加证明。** 这是贪心题最根本的错误。**凡是写下贪心解，心里必须同时装着一句"它为什么对"；装不下这句，就别用贪心。**

**误区二：接雨水双指针里，误判"哪侧是瓶颈"。** 代码比较的是 `height[left]` 与 `height[right]`，而非 `leftMax` 与 `rightMax`。**"更矮的柱子那一侧成为瓶颈"依赖的是柱子高度，而不是累计最高柱**——这一处极易混淆。

**误区三：加油站忘记先判断总量。** 若总量不足，无论起点在哪都无解；代码必须在返回前检查 `totalGas >= 0`，否则可能返回一个非法起点。

**误区四：分发糖果第二遍直接赋值而非取 `max`。** 这会覆盖第一遍建立的左约束结果（详见第 4 章）。

### 7.2 一套自测用例

| 用例 | 检验什么 |
|------|---------|
| `height = [3,2,1]` / `[1,2,3]` | 接雨水的单调边界（不存水） |
| `gas = cost`（总量为 0） | 加油站的临界可行性 |
| `ratings = [1,2,3,2,1]` | 分发糖果的"峰顶双向约束" |
| 全相等数组 | 三题的退化情形 |

**尤其值得反复验证的是"单调数组"与"全相等数组"**：它们分别是贪心策略的"最简"与"最极端"两种边界，很多错误写法在这两类输入下会原形毕露。

### 7.3 留一道自测题

接雨水的双指针方案里，若把比较条件 `height[left] < height[right]` 改成 `leftMax < rightMax`，结果还对吗？请动手验证。

**这道题的答案（不对）并不重要，重要的是验证的过程**——它会逼你把"哪一侧是瓶颈"这一推理再想一遍，从而确认自己理解的到底是"柱子高度决定瓶颈"还是"累计最高柱决定瓶颈"。**"改一个条件、看是否仍然正确"，是检验"是否真正理解了不变量"的最好方式**——比反复读一遍代码有效得多。

## 小结

本篇用三道题把贪心的三种典型形态铺展开来。接雨水从一条"水位由两侧较矮的墙决定"的观察出发，衍生出动态规划、双指针、单调栈三种 $O(n)$ 解法，其中双指针靠"更矮的一侧瓶颈已定"这一推理，把空间压到 $O(1)$；加油站用一句可反证的论断——"从起点到失败点之间的任意位置都不可行"——把一次失败升级为排除一整段，从而一遍扫描即得答案；分发糖果则用"两遍扫描、各管一侧、最后取最大"处理双向约束，其正确性依据其实是独立约束的可分解性。

贯穿三题的认知只有一条：**贪心不是"图省事"，而是"有资格图省事"。** 它的每一步之所以敢不回头，是因为背后都站着一条能证明的论断——要么是"其余候选已被排除"，要么是"局部答案已确定"，要么是"约束彼此独立"。**判断一道题能不能贪心，本质上就是去寻找这样一条论断；找到了，贪心成立；找不到，就该退回去用动态规划。** 这也是为什么贪心题往往代码极短、思考极长——短的是结果，长的是那条看不见的证明。

下一篇 [[09 动态规划与位运算：Climbing Stairs、Plus One、Single Number 系列]] 将进入动态规划与位运算的交叉地带。爬楼梯是动态规划的入门经典，但"状态"二字究竟意味着什么，很多人并未真正想清；Plus One 是大数加法的模拟，细节决定成败；Single Number 系列则把异或运算的特性用到了极致。
