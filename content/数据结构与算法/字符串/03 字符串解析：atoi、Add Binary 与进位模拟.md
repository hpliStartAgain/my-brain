# 字符串解析：atoi、Add Binary 与进位模拟

**摘要：**

本篇讲两道类型互补的字符串解析题：LeetCode 8（String to Integer / atoi）与 67（Add Binary）。**atoi 是"从字符串解析出数值"**——它的难点不在算法，而在前导空格、符号位、溢出这些边界状态，**有限状态机（DFA）**是应对"逐字符处理"的最优建模工具；**Add Binary 是"把数值结果写回字符串"**——核心是进位模拟，与链表版的"两数相加"异曲同工。两道题合起来，构建了"字符串 → 数值"与"数值 → 字符串"两个互补的模式。本文用 Go 语言实现，并逐层追问：为什么 atoi 要用状态机、溢出为什么要"边累积边截断"、以及"大数加法"为什么能用同一套模板覆盖二进制、十进制乃至链表。掌握这套模板，你就掌握了"在字符串上做数值运算"的全部套路。

## 第 1 章 LeetCode 8：字符串转整数（atoi）

### 1.1 题目

**LeetCode 8 - String to Integer (atoi)**（中等）

实现 `myAtoi(s)`，把字符串转成 32 位有符号整数（类似 C 的 `atoi`）。规则：跳过前导空格；可选一个 `+`/`-` 符号；读取连续数字；遇到非数字或结束即停；溢出时返回 `INT_MAX` 或 `INT_MIN`。

```text
输入: "42"              → 42
输入: "   -42"          → -42（跳过前导空格，读符号）
输入: "4193 with words" → 4193（遇非数字停止）
输入: "words and 987"   → 0（首个非空格字符不是数字或符号）
输入: "-91283472332"    → -2147483648（溢出，返回 MIN）
```

### 1.2 为什么这道题难

**不是算法难，是细节难。** 需要正确处理：

- **前导空格**（可以有多个）；
- **符号位**（`+`/`-`，只能有一个，且必须在数字前）；
- **数字读取**（连续多位，直到非数字字符）；
- **非法字符**（首个有效字符不是数字或符号 → 返回 0）；
- **整数溢出**（32 位边界，且必须**边累积边判断**）。

**若用一堆 `if-else` 处理，代码容易出错且难以验证覆盖了所有情况。** 有限状态机是更系统的建模方法。

### 1.3 有限状态机建模

**有限状态机（DFA）**由四要素构成：状态集合、输入字母表、转移函数、初始/终止状态。为 atoi 建模：

**输入分类**：`space`（空格）、`sign`（`+`/`-`）、`digit`（`0-9`）、`other`（其他）。

**状态**：`START`（初始）、`SIGNED`（已读符号）、`IN_NUMBER`（正在读数字）、`END`（终止）。

**转移表**：

| 当前状态 | space | sign | digit | other |
|---------|-------|------|-------|-------|
| START | START | SIGNED | IN_NUMBER | END |
| SIGNED | END | END | IN_NUMBER | END |
| IN_NUMBER | END | END | IN_NUMBER | END |
| END | END | END | END | END |

**这张表本身就是"文档"**——它穷举了所有状态与输入的组合，**不会遗漏边界**。这正是 DFA 的核心价值。

### 1.4 Go 实现（不建表，直写状态逻辑）

```go
func myAtoi(s string) int {
    i, n := 0, len(s)
    // 1. 跳过前导空格
    for i < n && s[i] == ' ' {
        i++
    }
    // 2. 读符号
    sign := 1
    if i < n && (s[i] == '+' || s[i] == '-') {
        if s[i] == '-' {
            sign = -1
        }
        i++
    }
    // 3. 读数字（边累积边截断）
    result := 0
    for i < n && s[i] >= '0' && s[i] <= '9' {
        d := int(s[i] - '0')
        // 溢出预判：若累积后会超过 INT_MAX，直接返回边界
        if result > (math.MaxInt32-d)/10 {
            if sign == 1 {
                return math.MaxInt32
            }
            return math.MinInt32
        }
        result = result*10 + d
        i++
    }
    return sign * result
}
```

**注意 `i < n` 这一保护**——它让"字符串提前结束"的情形自然成立（不进入循环即可），无需特判。**这与状态机里"END 状态吞掉一切"是同一效果，只是用循环条件表达了。**

### 1.5 溢出：为什么必须"边累积边截断"

**错误做法**是"先累积、最后再截断"——**因为累积本身可能溢出**。例如 `"99999999999999999999999999999999"`（32 个 9），若用 `int` 累积，中途就会溢出，得到错误结果。

**正确做法**是**在每次累积前预判**：

```go
if result > (math.MaxInt32-d)/10 {
    // 累积后必然溢出，直接返回边界
}
```

**这个不等式的含义是**："若 `result * 10 + d > INT_MAX`，则溢出"。把它变形为"先除后比"，就避开了"乘法本身溢出"的风险。**"用除法预判乘法溢出"是一个值得记住的技巧。**

> [!warning] 生产避坑：溢出预判要"先除后比"
> 判断 `a * b > LIMIT` 时，若直接算 `a * b`，可能先溢出。**正确写法是 `a > LIMIT / b`**（注意整除的边界）。**凡是"可能溢出的比较"，都要改写成"除法形式"。** 这在 atoi、二分中点、大数运算里反复出现。

### 1.6 手动验证

`s = "   -42"`：

```text
跳过 3 个空格 → i=3
读到 '-' → sign=-1, i=4
读到 '4' → result=4
读到 '2' → result=42
结束 → 返回 -1 * 42 = -42 ✓
```

`s = "words and 987"`：

```text
i=0 不是空格，也不是符号，也不是数字 → 循环不执行 → result=0
返回 0 ✓
```

## 第 2 章 LeetCode 67：二进制求和

### 2.1 题目

**LeetCode 67 - Add Binary**（简单）

给你两个二进制字符串 `a`、`b`，以二进制字符串形式返回它们的和。

```text
输入: a = "11", b = "1"      →  "100"（3 + 1 = 4）
输入: a = "1010", b = "1011" →  "10101"（10 + 11 = 21）
```

### 2.2 解法：从低位到高位模拟

二进制加法规则与十进制同理，只是进位阈值从 10 变成 2：

```go
func addBinary(a, b string) string {
    i, j, carry := len(a)-1, len(b)-1, 0
    var sb []byte

    for i >= 0 || j >= 0 || carry > 0 {
        sum := carry
        if i >= 0 {
            sum += int(a[i] - '0')
            i--
        }
        if j >= 0 {
            sum += int(b[j] - '0')
            j--
        }
        sb = append(sb, byte('0'+sum%2)) // 当前位
        carry = sum / 2                  // 进位
    }
    // 反转（因为是从低位往高位追加的）
    for l, r := 0, len(sb)-1; l < r; l, r = l+1, r-1 {
        sb[l], sb[r] = sb[r], sb[l]
    }
    return string(sb)
}
```

**循环条件 `i >= 0 || j >= 0 || carry > 0` 是灵魂**：前两项处理"两串长度不同"，最后一项处理"最高位仍有进位"。**三者缺一不可**——这与链表版"两数相加"、线性表专栏第 09 篇"Plus One"的循环条件是同一套。

### 2.3 手动验证

`a = "1010", b = "1011"`：

```text
i=3,j=3: sum=0+0+1=1 → 写 '1', carry=0
i=2,j=2: sum=1+1+0=2 → 写 '0', carry=1
i=1,j=1: sum=0+0+1=1 → 写 '1', carry=0
i=0,j=0: sum=1+1+0=2 → 写 '0', carry=1
i=-1,j=-1: carry=1 → sum=1 → 写 '1', carry=0

sb = "10101"，反转后仍是 "10101" ✓（21）
```

**复杂度**：时间 $O(\max(m,n))$，空间 $O(\max(m,n))$（结果串）。

### 2.4 与链表两数相加的对比

**Add Binary 与链表版"两数相加"（线性表专栏第 13 篇）是同一类问题的两种形式**：

| 特性 | LC 67（字符串） | LC 2（链表） |
|------|----------------|-------------|
| 数字存储 | 字符串（高位在前） | 链表（低位在头） |
| 遍历方向 | 从右到左（`i--`） | 从头到尾（已是低位优先） |
| 进制 | 二进制 | 十进制 |
| 结果写入 | 字节切片 + 反转 | 新链表节点 |

**通用模板（大数加法，任意进制）**：

```text
从低位开始逐位相加（字符串需从右往左）
sum = a[i] + b[j] + carry
当前位 = sum % base
进位    = sum / base
循环直到两数处理完 且 进位为 0
```

**这个模板适用于**：二进制加法（base=2）、十进制加法（base=10）、十六进制加法、链表两数相加。**一旦掌握它，所有"大数运算"都成了"改一个 base"。**

> [!info] 一个模板，覆盖"所有大数运算"
> "逐位相加 + 进位"这一模板，是"字符串上做数值运算"的核心。**它的普适性来自"进制只是 base 的不同"**——二进制、十进制、十六进制，代码只差一个常量。**理解了这一点，你面对任何"大数加法/乘法"的题，都能先问一句"base 是多少、进位怎么算"。**

## 第 3 章 有限状态机（DFA）的通用价值

### 3.1 什么时候用 DFA

**DFA 特别适合"按字符逐个处理、有明确阶段转换"的字符串问题**：

| 问题 | 状态示例 |
|------|---------|
| atoi（LC 8） | 前导空格 → 符号 → 数字 → 终止 |
| Valid Number（LC 65） | 整数部分 → 小数点 → 小数部分 → 指数 |
| URL 解析 | 协议 → 主机 → 路径 → 参数 |
| 词法分析 | 关键字识别、注释跳过 |

**DFA 的三大优势**：其一，**穷举所有状态**，不会遗漏边界；其二，**代码结构清晰**，转移表就是文档；其三，**易于扩展**，加规则只需改表。

### 3.2 通用 DFA 框架

```go
state := INITIAL_STATE
for i := 0; i < len(s); i++ {
    charType := classify(s[i])       // 字符分类
    state = transition[state][charType] // 查表转移
    if state == SOME_STATE {
        // 执行副作用
    }
    if state == DEAD_STATE {
        break // 提前终止
    }
}
return isAcceptState(state)
```

**这个框架在第 07 篇的 Valid Number（LC 65）里也会用到**——届时状态更多，但骨架完全一致。**"状态多"不是问题，因为转移表会把它管理得井井有条。**

### 3.3 为什么 DFA 比 `if-else` 好

**`if-else` 的写法，本质上是"把状态转移隐含在控制流里"**——一旦状态多、转移复杂，控制流就会变成"套娃"，难以验证、难以扩展。**而 DFA 把"状态"和"转移"显式地分离出来**：状态是一个变量，转移是一张表。**这让你能"一眼看全所有情形"，从而确信没有遗漏。**

**这与工程里"把配置与逻辑分离"是同一种思想**——**显式的数据结构（表）比隐式的控制流（嵌套 if）更易维护。**

## 第 4 章 字符解析的工程细节

### 4.1 四个常见陷阱

**陷阱一，前导/尾随空格。** 大多数解析题需处理前导空格；**注意题目可能只把 `' '` 当空格，而不含 `\t`、`\n`**（`strings.TrimSpace` 会去掉更多字符）。

**陷阱二，多余符号。** `"++1"`、`"+-1"`、`"1+2"` 等——**DFA 只在 `START` 状态接受符号**，就能自然处理这些情形。

**陷阱三，整数溢出。** 永远"边累积边检测"（见 1.5 节）。

**陷阱四，前导零。** atoi 无需特殊处理（`"0032"` 自然得到 `32`）。

### 4.2 `c - '0'`：字符到数字的转换

**这是字符串数字解析里最常用的技巧**：

```go
c := byte('7')
digit := int(c - '0') // 55 - 48 = 7
```

`'0'` 的 ASCII 是 48，`'9'` 是 57——**利用 ASCII 连续性，`c - '0'` 直接得到数字值**，无需查表。

类似地：`c - 'a'` 把 `a-z` 映射到 `0-25`；`c - 'A'` 把 `A-Z` 映射到 `0-25`。**这些技巧在哈希计数、Trie 树、位掩码等场景里大量使用**（回顾二叉树专栏第 07 篇数独的 `board[i][j] - '1'`）。

> [!note] ASCII 连续性：一个廉价而强大的假设
> `c - '0'`、`c - 'a'` 这类写法，依赖"数字/字母在 ASCII 表里连续"这一假设。**它在 ASCII 下成立，但在 EBCDIC 等非 ASCII 编码下不成立。** 现代环境几乎都是 ASCII/Unicode，所以可以放心使用——**但要知道这个技巧的"前提"是什么。**

## 第 5 章 延伸：更多字符串解析与进位模拟题

### 5.1 字符串相加（LeetCode 415）

**题目**：给定两个字符串形式的非负整数，计算它们的和（十进制），不能使用大数库。

**它就是"Add Binary"的十进制版**——把 base 从 2 改成 10：

```go
func addStrings(num1, num2 string) string {
    i, j, carry := len(num1)-1, len(num2)-1, 0
    var sb []byte
    for i >= 0 || j >= 0 || carry > 0 {
        sum := carry
        if i >= 0 {
            sum += int(num1[i] - '0')
            i--
        }
        if j >= 0 {
            sum += int(num2[j] - '0')
            j--
        }
        sb = append(sb, byte('0'+sum%10))
        carry = sum / 10
    }
    for l, r := 0, len(sb)-1; l < r; l, r = l+1, r-1 {
        sb[l], sb[r] = sb[r], sb[l]
    }
    return string(sb)
}
```

**这道题与 Add Binary 的代码几乎一模一样**——只有 `%2`/`/2` 换成了 `%10`/`/10`。**这正是"大数加法模板"的普适性：base 是唯一的变量。**

### 5.2 字符串相乘（LeetCode 43）

**题目**：给定两个字符串形式的非负整数，计算它们的乘积。

**乘法比加法复杂**：加法是"逐位相加 + 进位"，乘法则是"逐位相乘 + 错位相加 + 进位"。**核心是"结果数组"**：`m` 位数乘 `n` 位数，结果最多 `m+n` 位；把每个 `num1[i] * num2[j]` 的贡献累加到结果数组的 `i+j+1` 位，最后统一处理进位。

```go
func multiply(num1, num2 string) string {
    if num1 == "0" || num2 == "0" {
        return "0"
    }
    m, n := len(num1), len(num2)
    res := make([]int, m+n) // 结果最多 m+n 位

    for i := m - 1; i >= 0; i-- {
        for j := n - 1; j >= 0; j-- {
            mul := int(num1[i]-'0') * int(num2[j]-'0')
            res[i+j+1] += mul // 累加到对应位
        }
    }
    // 统一处理进位
    for i := len(res) - 1; i > 0; i-- {
        res[i-1] += res[i] / 10
        res[i] %= 10
    }
    // 去掉前导 0
    start := 0
    for start < len(res) && res[start] == 0 {
        start++
    }
    var sb []byte
    for i := start; i < len(res); i++ {
        sb = append(sb, byte('0'+res[i]))
    }
    return string(sb)
}
```

**"先累加、最后统一进位"是乘法模拟的关键**——它避免了"每次乘法都处理进位"的复杂性。**这与加法"边加边进位"不同，是因为乘法会有"多个贡献落到同一位"的情况。**

### 5.3 数组形式的整数加法（LeetCode 989）

**题目**：给定一个整数数组（表示一个大数的各位）和一个整数 `k`，返回它们相加后的数组形式。

**它是"加法模板"的另一个载体**——一个操作数是数组、一个是整数：

```go
func addToArrayForm(num []int, k int) []int {
    var res []int
    i := len(num) - 1
    for i >= 0 || k > 0 {
        if i >= 0 {
            k += num[i] // 把数组位加到 k 上
            i--
        }
        res = append(res, k%10)
        k /= 10
    }
    // 反转
    for l, r := 0, len(res)-1; l < r; l, r = l+1, r-1 {
        res[l], res[r] = res[r], res[l]
    }
    return res
}
```

**这里把 `k` 本身当作"进位 + 加数"复用**——每次 `k += num[i]`，再取末位、右移。**这是一个"用一个变量同时承载加数与进位"的巧思**，代码极简。

### 5.4 整数转英文（LeetCode 273）

**题目**：把非负整数转换为英文表示（如 `123` → `"One Hundred Twenty Three"`）。

**这是"解析"的逆操作——"数值 → 文字"**，属于"字符串生成"而非"字符串解析"。**它的核心是"按三位一组分组"**（因为英文数字的规则以千为界：thousand、million、billion），再对每组三位数用统一的规则生成。

**这道题展示了"字符串生成"类问题的套路**：**先把大问题按规则切成小单元，再对每个单元应用固定模板。** 这与"解析"的"逐字符状态转移"是相反的思路——**一个是从结构到文字，一个是从文字到结构。**

### 5.5 三道延伸题的共性

415、43、989 三道题，都在用"大数运算模板"：**逐位处理 + 进位**。区别只在"进制"（2/10）、"操作"（加/乘）、"载体"（字符串/数组/链表）。**它们与主线题（Add Binary）合起来，构成了"字符串上做数值运算"的完整图谱**——**一旦掌握了模板，剩下的只是"改一个参数"。**

## 第 7 章 DFA 的实现细节与工程实践

### 7.1 DFA 的三种实现方式

**其一，转移表（二维数组）**——最直观，适合状态多的情况（如第 07 篇 Valid Number）。**缺点是需要预先分配 `状态数 × 输入类型数` 的空间。**

**其二，`switch` 分支**——适合状态少的情况。**它把"转移"写成代码，省去了表格。**

**其三，显式状态变量 + `if` 链**——最"朴素"，适合状态极少的情况（如 atoi 的 4 个状态）。

**三者等价，取舍在"状态数"与"可读性"**：状态多选表格（一眼看全）、状态少选 `switch`（代码紧凑）。**不要为了"统一"而硬套表格**——过度设计同样是错。

### 7.2 "边读边算"vs"先收集再处理"

**字符串解析有两种风格**：

- **流式（边读边算）**：读到数字就累积、读到符号就更新状态——**空间 $O(1)$**，适合"只需一个结果"的场景（atoi）；
- **先收集再处理**：先把字符串按分隔符切成 token，再逐个处理——**代码更清晰，但需要 $O(n)$ 空间**。

**本专栏的 atoi、Add Binary 都是流式**——因为它们只需"一个结果"。**而像"解析 CSV 成表"这类需要保留所有字段的场景，就得"先收集再处理"。** 取舍在"是否需要保留中间结果"。

### 7.3 一个常被忽视的点：输入的长度上限

**DFA 的实现，要确认"状态数是否有限"**。**若规则本身允许"无限状态"（如"任意深度的括号嵌套"），纯 DFA 就不够用**——需要"下推自动机（带栈）"。

**例如"验证括号匹配"就需要栈**（栈与队列专栏第 01 篇）——因为它要记住"嵌套深度"，而 DFA 没有记忆。**"DFA 能处理'有限状态'的规则，栈/下推自动机能处理'无限状态'的规则"**——这是形式语言理论的一条基本结论，也是"什么时候该用栈"的理论依据。

> [!info] 从"字符串解析"到"形式语言"
> 字符串解析的底层理论，是"形式语言与自动机"——**正则语言用 DFA，上下文无关语言用下推自动机（栈）**。理解了这一点，你就明白"为什么括号匹配必须用栈"（因为它不是正则语言）、"为什么 atoi 能用 DFA"（因为它是正则语言）。**这层理论背景，能让你的"工具选择"从'凭经验'上升到'有依据'。**

## 第 9 章 大数运算的完整图谱与工程应用

### 9.1 大数运算的完整图谱

**"大数运算"是一族操作**——加、减、乘、除、比较，都能在字符串/数组上模拟：

| 运算 | 核心技巧 | 复杂度 |
|------|---------|--------|
| 加法 | 逐位相加 + 进位 | $O(n)$ |
| 减法 | 逐位相减 + 借位（需处理负数/大小） | $O(n)$ |
| 乘法 | 逐位相乘 + 错位累加 + 统一进位 | $O(n^2)$ |
| 除法 | 长除法（试商） | $O(n^2)$ |
| 比较 | 先比长度、再逐位比 | $O(n)$ |

**它们共享"逐位处理"这一骨架**——只是"进位/借位/累加"的规则不同。**理解了加法，其他都只是"改规则"。**

### 9.2 乘法为什么是 $O(n^2)$

**大数乘法的 $O(n^2)$ 来自"每一位都要与另一数的每一位相乘"**——这是"竖式乘法"的固有代价。**若追求更快，可用 Karatsuba 算法（$O(n^{1.585})$）或 FFT（$O(n \log n)$）**，但实现复杂，工程里通常用库。

**"从 $O(n^2)$ 到 $O(n \log n)$"是乘法算法的一条演进线**——它说明"即使是基础运算，也有优化的空间"。**但面试里，能手写 $O(n^2)$ 的竖式乘法就够了。**

### 9.3 大数运算在工程里的位置

**大数运算不是"算法题专属"，它在工程里无处不在**：

- **密码学**：RSA 加密用的是"几百位的大数幂运算与取模"；
- **金融**：货币计算需要"精确到分"，不能用浮点（浮点有精度误差）；
- **科学计算**：高精度常数（如 π 的百万位）；
- **编程语言**：Java 的 `BigInteger`、Python 的任意精度整数、Go 的 `math/big`。

**这些场景的共同需求，是"精确的、任意位数的数值运算"**——**而"字符串/数组模拟"正是它的基础实现方式。**

### 9.4 一个值得记住的对照

**"用字符串做数值运算"与"用浮点数做数值运算"是一对**：

| 维度 | 字符串/大数 | 浮点数 |
|------|-----------|--------|
| 精度 | 精确（任意位） | 有限（约 15-17 位有效数字） |
| 速度 | 慢（逐位） | 快（硬件指令） |
| 适用 | 金融、密码学 | 科学计算、图形 |

**"金融不能用浮点"是一条工程铁律**——因为 `0.1 + 0.2 != 0.3`（浮点精度问题），而金额必须精确。**这就是为什么"大数运算"在工程里如此重要**——**它不是"炫技"，而是"某些领域正确性的刚需"。**

> [!info] 从"一道题"到"一个领域"
> 字符串大数运算，看起来是"模拟题"，实则是"高精度计算"这一领域的基础。**金融、密码学、科学计算都依赖它**——**而这些领域对"精确性"的要求，是浮点数无法满足的。** 理解了这一点，你就明白为什么"大数加法"这类题值得反复练——**它训练的是"精确计算"这一工程刚需。**

## 第 11 章 解析类问题的完整图谱

### 11.1 解析问题的两大方向

**"字符串解析"其实有两大方向**：

- **"字符串 → 值"**：atoi、Valid Number、罗马转整数——**从文本提取语义**；
- **"值 → 字符串"**：整数转罗马、整数转英文、大数运算结果——**把语义编码成文本**。

**它们是一对逆操作**（第 05 篇"重建 vs 序列化"同理）。**本专栏的题，两个方向都有。**

### 11.2 解析问题的完整地图

| 问题 | 方向 | 核心方法 |
|------|------|---------|
| atoi（LC 8） | 串 → 值 | 状态机 |
| Valid Number（LC 65） | 串 → 值（验证） | 状态机 |
| 罗马转整数（LC 13） | 串 → 值 | 映射 + 减法 |
| 整数转罗马（LC 12） | 值 → 串 | 贪心枚举 |
| 大数加法（LC 67、415） | 值 → 串 | 进位模拟 |
| 验证 IP（LC 468） | 串 → 值（验证） | 分段 |
| 表达式求值（LC 224、150） | 串 → 值 | 栈 + 优先级 |

**这张地图的"共同骨架"，是"逐单元处理"**——**单元可以是"字符"（状态机）、"段"（IP）、"符号"（罗马）、"位"（大数）。** **识别"单元是什么"，是解析题的第一步。**

### 11.3 一个统一的解题框架

**解析类问题的通用框架**：

1. **确定"单元"**：字符？段？位？符号？
2. **确定"单元的规则"**：每个单元如何解释？
3. **确定"单元之间的关系"**：是独立（IP 各段）、还是有序（罗马的减法）？
4. **选择处理方式**：独立 → 分段；有序且规则复杂 → 状态机；有序且规则简单 → 逐单元处理。

**这四步，几乎能覆盖所有解析题**——**"单元 + 规则 + 关系 + 方式"，是解析题的四要素。**

> [!info] 解析题的四要素
> 任何解析题，都可以用"**单元、规则、关系、方式**"四要素来分析。**单元是"最小处理粒度"，规则是"单元如何解释"，关系是"单元间是否独立"，方式是"用什么结构处理"。** 把这四要素想清楚，解析题的解法就自然浮现了。**这是一个可以套用到任何解析问题的分析框架。**

### 11.4 与工程的联系

**解析类问题在工程里无处不在**：

- **配置文件解析**（YAML/TOML/INI）；
- **协议解析**（HTTP/TCP/JSON）；
- **日志解析**（提取字段）；
- **SQL/表达式解析**（编译器的前端）。

**它们共享"逐单元处理"这一骨架**——**本专栏的题，是这些工程场景的"最小模型"。** 理解了它们，你面对任何"解析"任务，都有了"从单元入手"的起点。

## 第 12 章 常见误区与自测方法

### 5.1 四个高频误区

**误区一：atoi 溢出"先累积后截断"。** 会中途溢出。

**误区二：atoi 忘了"非法首字符返回 0"。** 如 `"words"` 应返回 0。

**误区三：Add Binary 循环条件漏掉 `carry > 0`。** 最高位进位会丢。

**误区四：Add Binary 忘记反转。** 逐位追加是从低位到高位，结果需反转。

### 5.2 一套自测用例

| 用例 | 检验什么 |
|------|---------|
| `""`、`" "` | 空/全空格 |
| `"+-1"`、`"++1"` | 多余符号 |
| `"2147483648"` | 正溢出（应返回 INT_MAX） |
| `"-2147483649"` | 负溢出（应返回 INT_MIN） |
| `a="0", b="0"` | Add Binary 全零 |
| `a="111", b="1"` | 连续进位 |

**其中 `"2147483648"` 与 `"-2147483649"` 最值得测**——它们是溢出边界（恰好越过 INT_MAX/MIN 一格），最能暴露"溢出预判"的 off-by-one。

## 第 13 章 一句话带走

**如果只能从本篇带走两句话：**

**其一，"解析的本质，是把规则显式化"**——DFA 把"状态转移"从隐式控制流里解放出来，变成可核对的表；**规则越复杂，越该"显式化"（用表而非 `if` 链）。**

**其二，"大数运算的本质，是'逐位处理 + 进位'"**——二进制、十进制、任意进制、链表、数组，都只是"改一个 base 或载体"。**掌握了这个模板，所有大数运算都成了"填空"。**

**而这两条背后，是一个共同的工程思想：把"重复的模式"抽象出来，让代码"改一个参数就能复用"。** DFA 的转移表、大数运算的 base——**它们都是"用抽象消除重复"。**

> [!note] 一个可复用的判断
> 遇到"解析/大数运算"题，**先问两句**：规则复杂吗（该不该用状态机）？是"逐位运算"吗（该不该用进位模板）？**这两问，能定下解析题与大数题的骨架。**

## 第 14 章 复杂度速查与选型

| 题目 | 时间 | 空间 | 手写要求 |
|------|------|------|---------|
| LC 8 atoi | $O(n)$ | $O(1)$ | **必须能手写**（含溢出处理） |
| LC 67 Add Binary | $O(\max(m,n))$ | $O(\max(m,n))$ | **必须能手写** |
| LC 415 Add Strings | $O(\max(m,n))$ | $O(\max(m,n))$ | **必须能手写** |
| LC 43 Multiply Strings | $O(mn)$ | $O(m+n)$ | 能手写更佳 |

**"大数加法模板"是必须熟练的**——它覆盖 LC 67、415、2、989 等多道题。**乘法（LC 43）稍难，但"先累加、后统一进位"的思路值得掌握。**

**这个模板的价值，是"一次掌握、多题通用"**——**二进制、十进制、链表、数组，都只是"改 base 或载体"。**

> [!note] 一个总体判断
> 遇到"大数运算"题，**先问"是加法还是乘法"**——加法用"逐位相加 + 进位"（$O(n)$），乘法用"逐位相乘 + 错位累加"（$O(n^2)$）。**而"字符串解析"题，先问"规则复不复杂"（决定用不用状态机）。**

## 小结

本篇用两道题覆盖了字符串解析的两个方向。atoi（"字符串 → 数值"）的难点全在边界，DFA 是系统化的建模工具；Add Binary（"数值 → 字符串"）的核心是进位模拟，其模板可覆盖任意进制与任意载体（字符串/链表）。两者的共同经验是：**"逐位处理 + 边界周全"**。

贯穿全篇的核心认知有两条。其一，**DFA 把"状态转移"从隐式的控制流里解放出来，变成显式的表**——这让"覆盖所有情形"从"凭经验"变成"可核对"。其二，**"大数加法"是一个可复用的模板**，base 是唯一的变量。**把这两条握住，你面对任何字符串解析或大数运算题，都有了系统化的起点。**

下一篇 [[04 最长回文子串：中心扩展与 Manacher 算法]] 将深入回文子串的搜索。LeetCode 5 是一道频率极高的中等题：中心扩展法 $O(n^2)$、空间 $O(1)$ 足以通过；而 Manacher 算法通过"镜像利用"把时间降到 $O(n)$，是字符串领域最优雅的线性优化案例之一。

**再补充一段落点。** atoi 与 Add Binary 看似无关，实则共享一个主题——**"字符串与数值之间的转换"**。atoi 是"串 → 值"，Add Binary 是"值 → 串"；而它们各自的难点（状态机、进位），都指向同一个工程思想：**"把'转换规则'显式化"**。atoi 用状态表显式化"字符如何影响状态"，Add Binary 用"进位变量"显式化"位与位的关系"。**理解了"显式化"这一思想，你面对任何"转换"任务，都会先问"规则如何表达成结构"。**

**再看一个更深的落点。** 大数运算在工程里不是"炫技"，而是"某些领域的刚需"——**金融不能用浮点（精度问题）、密码学需要几百位的大数（RSA）。** 而"字符串模拟大数"正是这些场景的基础实现。**理解了这一点，你就明白为什么"大数加法"这类题值得反复练**——它训练的是"精确计算"这一工程刚需，而非一道孤立的模拟题。**从"一道题"看到"一个领域的刚需"，是算法学习"由浅入深"的标志。**

**最后再强调一点"练习方法"。** atoi 的"溢出预判"要练到"不假思索写出 `result > (INT_MAX-d)/10`"；Add Binary 的"循环三条件"要练到"闭着眼写出 `i>=0 || j>=0 || carry>0`"。**这两处，是"大数/解析"类题的高频考点，也是"差一位就错"的地方。**

**最后，留一道值得回味的思考题。** 若把 Add Binary 改成"支持负数的二进制加减"，难点在哪？**答案是"符号与借位"**——负数需要"补码表示"或"先判大小再决定加减"，比单纯加法复杂得多。**这个思考题说明："加法"之所以简单，是因为它不需要处理"符号与大小"；一旦引入减法，规则就复杂了。** 这也解释了为什么"减法"比"加法"难写——**它多了"判断大小、决定借位"这一步。**
