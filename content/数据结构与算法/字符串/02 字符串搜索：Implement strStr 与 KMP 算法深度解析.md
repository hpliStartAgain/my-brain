# 字符串搜索：Implement strStr 与 KMP 算法深度解析

**摘要：**

LeetCode 28（Implement strStr）是字符串搜索的入门题：在文本串 `haystack` 中找到模式串 `needle` 第一次出现的位置。朴素算法的时间复杂度是 $O(mn)$，在最坏情况下（如 `haystack = "aaaa...ab"`、`needle = "aaaab"`）性能极差。KMP 算法（Knuth-Morris-Pratt）通过预处理模式串的**最长相等前后缀（LPS）信息**，把"失配时该回退到哪"精确算了出来，从而把总复杂度降到 $O(m+n)$。理解 KMP 的 `next` 数组，是区分"刷过题"与"真正掌握算法"的分水岭。本文从朴素匹配的浪费出发，逐步推导 KMP 的核心直觉、`next` 数组的定义与构建、以及完整的匹配过程，并用 Go 语言实现；随后讨论两种流行的 `next` 定义、KMP 的线性复杂度证明、以及它在"最短重复单元"（459）上的应用。全文逐层追问：为什么失配时不必从头再来、`next` 数组本身为什么也是"自我匹配"、以及工程里为什么仍常用朴素算法。

## 第 1 章 朴素字符串匹配

### 1.1 题目

**LeetCode 28 - Find the Index of the First Occurrence in a String**（中等）

给你两个字符串 `haystack` 和 `needle`，在 `haystack` 中找出 `needle` 第一个匹配项的下标（从 0 开始）；若不存在则返回 -1。

```text
输入: haystack = "sadbutsad", needle = "sad"  →  输出: 0
输入: haystack = "leetcode", needle = "leeto" →  输出: -1
```

### 1.2 朴素匹配

**思路**：对 `haystack` 中每个可能的起始位置 `i`，检查从 `i` 开始的子串是否等于 `needle`。

```go
func strStrNaive(haystack, needle string) int {
    n, m := len(haystack), len(needle)
    if m == 0 {
        return 0 // 空 needle 约定返回 0
    }
    for i := 0; i <= n-m; i++ { // 上界是 n-m，不是 n
        j := 0
        for j < m && haystack[i+j] == needle[j] {
            j++
        }
        if j == m {
            return i // 完全匹配
        }
    }
    return -1
}
```

**复杂度**：时间 $O(mn)$，空间 $O(1)$。**注意循环上界是 `n-m`**——因为起始位置 `i` 最多到 `n-m`，否则 `i+j` 会越界。

### 1.3 朴素匹配的浪费

考虑这个场景：

```text
haystack = "aaaaaaaaaaab"（11 个 a + 1 个 b）
needle   = "aaaab"（4 个 a + 1 个 b）
```

每次从位置 `i` 开始，`needle` 前 4 个字符 `aaaa` 都能匹配，直到第 5 个字符 `b` 与 `a` 不匹配，于是 `i++`、从头再来。**每次都比 5 次，总计约 $11 \times 5 = 55$ 次。**

**浪费在哪里？** 每次失配后 `i` 只移动一步，但我们已经知道 `needle[0..3]` 全是 `a`，而 `haystack[i+1..i+3]` 也全是 `a`（刚比过）——**没必要从头再比。** KMP 的核心思想，正是"**利用已知的匹配信息，跳过不可能成功的对齐位置**"。

> [!info] 朴素算法的"信息浪费"
> 朴素算法的问题，不是"比得多"，而是"**比过的信息被浪费了**"。它每次失配后都把"已匹配的长度"归零，仿佛什么都没学到。**KMP 的全部价值，就是把这份"已匹配的信息"利用起来。** 这与第 01 篇"双指针能提前返回"、第 03 篇"用哈希表缓存查找结果"是同一种精神：**不要重复做已经做过的事。**

## 第 2 章 KMP 的核心直觉

### 2.1 失配时，不从头再来

当模式串在位置 `j` 失配时，朴素算法把文本指针回退、模式指针从 0 重新开始。**KMP 的核心观察是：模式串已匹配的前缀里，含有"自相似"信息。**

具体说：如果已匹配的前缀 `needle[0..j-1]` 有一个"既是前缀又是后缀"的子串，那么就可以**直接利用这个重叠**，把模式指针回退到这个重叠的末尾，而不是从 0 开始。

### 2.2 一个具体例子

```text
needle = "ABCABD"

haystack: ... A B C A B E ...
needle:       A B C A B D
                        ↑
            在这里失配（'E' != 'D'）
```

失配时，已匹配 `needle[0..4] = "ABCAB"`。朴素算法会让模式串整体右移一位、重新匹配。**但注意：`"ABCAB"` 的前缀 `"AB"` 与后缀 `"AB"` 相同（长度为 2 的最长相等前后缀）。**

这意味着——**当前 haystack 中已匹配的末尾 `"AB"`，与 `needle` 的开头 `"AB"` 相同。** 于是不必从头匹配，直接把模式指针跳到位置 2（`"AB"` 之后）继续：

```text
haystack: ... A B C A B E ...
needle:           A B C A B D
                    ↑
            从这里继续（j=2）
```

**这就是 KMP 的精髓**：`next[j]` 存的是 `needle[0..j-1]` 的最长相等前后缀长度，失配时把 `j` 回退到 `next[j]`，而不是 0。

### 2.3 `next` 数组（前缀函数）的定义

**定义**：`next[j]` = `needle[0..j-1]` 的**最长相等真前后缀**的长度。"真"意味着不包括字符串自身。

以 `needle = "ABCABD"` 为例：

| j | `needle[0..j-1]` | 相等前后缀 | `next[j]` |
|---|------------------|-----------|-----------|
| 0 | `""` | 无 | 0 |
| 1 | `"A"` | 无 | 0 |
| 2 | `"AB"` | 无 | 0 |
| 3 | `"ABC"` | 无 | 0 |
| 4 | `"ABCA"` | `"A"`（长度 1） | 1 |
| 5 | `"ABCAB"` | `"A"`、`"AB"`（最长 `"AB"`，长度 2） | 2 |
| 6 | `"ABCABD"` | 无 | 0 |

于是 `next = [0, 0, 0, 0, 1, 2, 0]`。

> [!note] "真前后缀"为什么要加"真"字
> "真前后缀"指"**不含字符串自身**的前后缀"。若不排除自身，那么任何字符串的"最长相等前后缀"都是它自己（长度 = 全长），`next` 就失去了意义。**加"真"字，是为了排除这个平凡解。** 这也是 `next[0] = 0`（单字符没有真前后缀）的原因。

## 第 3 章 `next` 数组的构建

### 3.1 关键推导：构建 `next` 也是"自我匹配"

**构建 `next` 数组本身，就是一个"模式串与自身匹配"的问题。**

设已知 `next[j] = k`（即 `needle[0..j-1]` 的最长相等前后缀长度为 `k`），现在要求 `next[j+1]`：

- **情况一**：若 `needle[j] == needle[k]`，则 `needle[0..j]` 的最长相等前后缀长度为 `k+1`，即 `next[j+1] = k+1`；
- **情况二**：若 `needle[j] != needle[k]`，则需**缩短前后缀**——看 `needle[0..k-1]` 的最长相等前后缀（即 `next[k-1]`），令 `k = next[k-1]` 继续尝试，直到 `k == 0` 或找到匹配。

**注意"情况二"的回退方式，与匹配过程的回退方式完全一致**——这正是"构建 `next` 也是 KMP"的体现。

### 3.2 Go 实现

```go
// buildNext 构建前缀函数：next[j] = needle[0..j] 的最长相等真前后缀长度
func buildNext(needle string) []int {
    m := len(needle)
    next := make([]int, m)
    k := 0 // k 是当前已匹配的前缀长度
    for j := 1; j < m; j++ {
        // 失配时，利用已有的 next 信息回退
        for k > 0 && needle[j] != needle[k] {
            k = next[k-1]
        }
        if needle[j] == needle[k] {
            k++ // 匹配成功，k 前进
        }
        next[j] = k
    }
    return next
}
```

**逐步演示** `needle = "ABCABD"`：

```text
j=0: next[0]=0（初始化）
j=1: k=0, needle[1]='B' != needle[0]='A' → k=0；next[1]=0
j=2: k=0, 'C' != 'A' → k=0；next[2]=0
j=3: k=0, 'A' == 'A' → k=1；next[3]=1
j=4: k=1, 'B' == needle[1]='B' → k=2；next[4]=2
j=5: k=2, 'D' != needle[2]='C' → 回退 k=next[1]=0
     k=0, 'D' != 'A' → k=0；next[5]=0

next = [0, 0, 0, 1, 2, 0] ✓
```

**注意 j=5 时的回退**：`k` 从 2 退到 `next[1]=0`——**这就是"缩短前后缀、再试"的过程**，与匹配时的回退同构。

### 3.3 完整 KMP 匹配

```go
func strStr(haystack, needle string) int {
    n, m := len(haystack), len(needle)
    if m == 0 {
        return 0
    }
    next := buildNext(needle)
    j := 0 // 模式串已匹配的长度

    for i := 0; i < n; i++ {
        // 失配时，利用 next 数组回退
        for j > 0 && haystack[i] != needle[j] {
            j = next[j-1]
        }
        if haystack[i] == needle[j] {
            j++
        }
        if j == m {
            return i - m + 1 // 匹配成功，返回起始位置
        }
    }
    return -1
}
```

**注意 `j = next[j-1]` 而不是 `j = next[j]`**：因为当前位置 `j` 已失配，我们要用的是"已成功匹配的 `needle[0..j-1]`"的前后缀信息，即 `next[j-1]`。**这是 KMP 里最容易写错的一处下标。**

**复杂度**：预处理 $O(m)$，匹配 $O(n)$，**总计 $O(m+n)$**，空间 $O(m)$。

## 第 4 章 正确性与复杂度

### 4.1 为什么 KMP 是线性的

**关键观察**：`j` 的**增加**由 `i` 的推进驱动（`i` 每次 `+1`，`j` 至多 `+1`）；而 `j` 的**减少**（`j = next[j-1]`）每次至少减少 1。**总增加量 $\le n$，总减少量 $\leq$ 总增加量 $\le n$**，所以整个匹配的比较次数 $\le 2n = O(n)$。

**构建 `next` 时同理**：`k` 的总增加量 $\le m$，总减少量 $\le m$，故 $O(m)$。

**KMP 总复杂度 $O(m+n)$，空间 $O(m)$。**

**这种"某个量只增不减、增减总量有界"的分析方式，就是摊还分析**——与第 01 篇双指针、栈与队列专栏单调栈的分析同源。**凡是"指针只朝一个方向净移动"的算法，都能用这套论证证明线性复杂度。**

### 4.2 与朴素算法的对比

| 场景 | 朴素算法 | KMP |
|------|---------|-----|
| 最好情况 | $O(n)$ | $O(n+m)$ |
| 最坏情况 | $O(mn)$ | $O(n+m)$ |
| 平均情况 | 通常接近 $O(n)$ | $O(n+m)$ |

**在真实工程里，朴素匹配由于"缓存友好 + 代码简单"，性能往往并不差**；但对"大量重复字符"的输入（如 DNA 序列、二进制串），KMP 的优势才明显。

### 4.3 工程里为什么仍用朴素算法

**很多语言的标准库 `indexOf`/`find` 用的其实是朴素算法（配合启发式跳跃）**，而非 KMP。原因有三：其一，朴素算法在随机字符串上性能已接近 $O(n)$（失配很快）；其二，代码简单，JIT/编译器能高度优化；其三，KMP 的 $O(m)$ 额外空间在频繁调用时有开销。

**这提醒我们：算法在工程中的应用，不只看理论复杂度。** 与线性表专栏第 04 篇"哈希表的 $O(1)$ 是期望值"、第 01 篇"理论复杂度与实际性能之间的缝"是同一主题。

> [!info] 理论复杂度 vs 工程选择
> KMP 的理论复杂度优于朴素算法，但工程里常用朴素算法——**这不是"工程界不懂算法"，而是"工程界的优化目标是综合的"**（代码简单、缓存友好、无额外空间）。**理解这一点，你就能明白为什么"最优算法"与"最常用算法"常常不是同一个**——这正是本专栏反复强调的"没有银弹，因地制宜"。

## 第 5 章 `next` 的两种定义与 KMP 变种

### 5.1 两种流行的 `next` 定义

网上有两种流行的 `next` 定义，常导致混乱：

- **定义 A（本文使用）**：`next[j]` = `needle[0..j]` 的最长相等真前后缀长度。`"ABCABD"` → `[0, 0, 0, 1, 2, 0]`；
- **定义 B**：`next[j]` = 失配时应跳转的位置（相当于定义 A 左移一位，起始为 -1）。`"ABCABD"` → `[-1, 0, 0, 0, 1, 2]`。

**两种定义本质相同，代码细节略有差异。** 理解了一种，换成另一种只需微调下标。**面试里若面试官用的是另一种，先确认"你说的 `next[j]` 是哪个定义"，再写代码**——**避免"定义不一致"导致的沟通错误。**

### 5.2 最短重复单元（LeetCode 459）

**题目**：判断一个字符串是否能由它的某个子串重复多次构成。

**巧用 `next` 数组的性质**：若 `s` 由长度为 `d` 的子串重复构成，则 `next[n-1] = n - d`，且 `n % d == 0`。

```go
func repeatedSubstringPattern(s string) bool {
    n := len(s)
    next := buildNext(s)
    longest := next[n-1]  // 最长相等前后缀长度
    d := n - longest      // 最短重复单元长度
    return d < n && n%d == 0 // d < n 排除整体；n % d == 0 确认能整除
}
```

**为什么这个性质成立？** 若 `s = d 重复 k 次`，则它的最长相等前后缀就是"去掉第一个重复单元"——长度为 `n - d`。**反推之，`d = n - next[n-1]` 就是最短重复单元。** 而 `n % d == 0` 保证"能整除、确实是重复构成"。

**这道题是 KMP 的"副产品应用"**——它不需要真正做匹配，只用 `next` 数组的最后一个值。**它展示了 `next` 数组除了"加速匹配"，还携带了"字符串自相似结构"的信息。**

### 5.3 更多字符串匹配算法

| 算法 | 时间 | 空间 | 特点 |
|------|------|------|------|
| 朴素 | $O(mn)$ | $O(1)$ | 简单、缓存友好 |
| KMP | $O(m+n)$ | $O(m)$ | 无哈希冲突、稳定 |
| Rabin-Karp | $O(m+n)$ 期望 | $O(1)$ | 基于哈希、适合多模式 |
| Boyer-Moore | $O(n/m)$ 最好 | $O(m)$ | 从右往左比、跳跃大 |
| Z 算法 | $O(m+n)$ | $O(m)$ | 与 KMP 等价、更直观 |

**这些算法各有取舍**：KMP 适合"单模式、要求稳定"；Rabin-Karp 适合"多模式"；Boyer-Moore 适合"字母表大、模式长"（跳跃远）；Z 算法与 KMP 等价但更直观。**工程里选哪个，取决于"模式数量、字母表大小、是否需要稳定"**。

## 第 6 章 面试应对策略

### 6.1 strStr 的标准回答路径

1. **给出朴素解法**（2 分钟内）：双层循环，说明 $O(mn)$；
2. **分析缺陷**：举出"大量重复字符"的最坏场景；
3. **引入 KMP**：说明核心思想（利用已匹配的前后缀信息避免回退）；
4. **解释 `next` 数组**：能从头推导出构建逻辑；
5. **给出完整代码**：分开 `buildNext` 与匹配函数；
6. **分析复杂度**：$O(m+n)$ 时间、$O(m)$ 空间。

### 6.2 面试官最常追问的三个问题

**追问一："为什么用 `while` 而不是 `if`？"** 答：单次回退后，新的 `j` 对应的字符可能仍不匹配，需要继续回退，直到匹配或 `j == 0`。

**追问二："为什么是 `next[j-1]` 而不是 `next[j]`？"** 答：当前位置 `j` 已失配，要用的是"已成功匹配的 `needle[0..j-1]`"的前后缀信息，即 `next[j-1]`。

**追问三："KMP 与 Rabin-Karp 有何区别？"** 答：KMP 基于字符比较、通过前缀函数跳过无效对齐；Rabin-Karp 基于哈希、先比哈希再验证。**Rabin-Karp 适合多模式搜索，KMP 无哈希冲突风险。**

### 6.3 一个表达上的建议

**讲 KMP 时，务必先讲"为什么需要它"（朴素算法的浪费），再讲"它怎么做到"（前后缀重叠）。** 很多人一上来就讲 `next` 数组的定义，听众却不知道"为什么要有这个东西"。**先说清"问题"，再说"方案"，是讲清任何算法的通用顺序**——这与本专栏"先讲为什么、再讲怎么做"的取向一致。

> [!note] KMP 是"分水岭"题
> 面试里，KMP 常被用来区分"背了答案"与"真正理解"。**区别在于：能否讲清"为什么失配时不必从头再来"，以及能否从头推导出 `next` 的构建逻辑。** 死记代码的人，往往答不出"为什么是 `next[j-1]`"这类追问。**所以学 KMP 时，重点不是背代码，而是理解"前后缀重叠"这一核心直觉。**

## 第 7 章 字符串匹配的算法家族

KMP 不是唯一的字符串匹配算法。本章把主要的几种摆在一起，帮你在"该选哪个"时有判断依据。

### 7.1 Z 算法：与 KMP 等价的另一种视角

**Z 算法**（也称扩展 KMP）定义 `z[i]` 为"字符串 `s` 与它的后缀 `s[i..]` 的最长公共前缀长度"。**它的核心思想与 KMP 完全一致——利用已算出的 `z` 值、跳过重复比较**，因此也是 $O(n)$。

**把模式串与文本串用特殊字符拼接**（如 `p + "#" + s`），再求 Z 数组，就能在 $O(m+n)$ 内找到所有匹配位置。**Z 算法与 KMP 等价，但"Z 数组"的语义（后缀与前缀的公共长度）比 `next` 数组更直观**——这也是很多人觉得 Z 算法"更好懂"的原因。

**两者的关系，恰如"同一件事的两种语言"**——理解了 KMP 的"前后缀复用"，Z 算法就是它的"换个说法"。

### 7.2 Rabin-Karp：基于哈希的匹配

**Rabin-Karp 用哈希代替逐字符比较**：为模式串算一个哈希值，再滑动窗口计算文本中每个长度 `m` 的子串的哈希值，**哈希相等时再逐字符验证**（因为哈希可能冲突）。

**它的关键技巧是"滚动哈希"**——滑动窗口移动一格时，用"去掉左端字符、加上右端字符"的方式 $O(1)$ 更新哈希，而无需重算整个窗口：

$$\text{hash}_{i+1} = (\text{hash}_i - s[i] \cdot b^{m-1}) \cdot b + s[i+m]$$

**Rabin-Karp 的优势是"多模式匹配"**——若要在一段文本里同时找多个模式串，可以先把所有模式的哈希放进集合，再滑动窗口查集合。**而 KMP 一次只能处理一个模式。**

### 7.3 Boyer-Moore：从右往左比、跳得远

**Boyer-Moore 从右往左比较**，并利用"坏字符规则"与"好后缀规则"在失配时**跳过尽可能多的位置**。**它的最好情况是 $O(n/m)$**（模式越长、字母表越大，跳得越远），因此在实际文本搜索（如编辑器查找）中常被采用。

**它为什么能"跳"？** 因为若某个字符在模式中根本没出现，那么整个模式可以直接跳到该字符之后。**"字母表越大、模式越长，这种跳跃越有效"**——这也是它适合"自然语言文本"的原因。

### 7.4 Aho-Corasick：多模式匹配的王者

**Aho-Corasick（AC 自动机）**是"多模式匹配"的经典算法——它把"KMP 的思想"与"Trie"结合，**在一趟扫描中找出所有模式的出现位置**，时间 $O(n + \sum m_i + \text{匹配数})$。**它是"敏感词过滤""入侵检测"等场景的标准工具。**

**AC 自动机的本质是"Trie + 失配指针"**——Trie 负责"多模式的共享前缀"，失配指针（相当于 KMP 的 `next`）负责"失配时跳到哪个状态"。**理解了 KMP，AC 自动机就只是"把 KMP 搬到 Trie 上"。**

### 7.5 五种算法的对照

| 算法 | 时间 | 空间 | 适合场景 |
|------|------|------|---------|
| 朴素 | $O(mn)$ | $O(1)$ | 短模式、缓存友好 |
| KMP | $O(m+n)$ | $O(m)$ | 单模式、稳定 |
| Z 算法 | $O(m+n)$ | $O(m)$ | 单模式、更直观 |
| Rabin-Karp | $O(m+n)$ 期望 | $O(1)$ | 多模式（哈希集合） |
| Boyer-Moore | $O(n/m)$ 最好 | $O(m)$ | 长模式、大字母表 |
| AC 自动机 | $O(n + \sum m_i)$ | $O(\sum m_i)$ | **多模式** |

**这张表的落点是"需求决定算法"**：单模式求稳定选 KMP；多模式选 AC 自动机或 Rabin-Karp；实际文本搜索选 Boyer-Moore。**没有"最好的匹配算法"，只有"最适合当前需求的"。**

> [!info] 从"一个算法"到"一个家族"
> 学字符串匹配，最容易的误区是"只记 KMP"。**但真正有用的是"知道有哪几种、各自适合什么"**——因为面试官可能问"还有别的算法吗"，实际工程里也可能需要"多模式匹配"（KMP 就不适用）。**把"算法家族"而非"单个算法"装进脑子里，是进阶的标志。**

## 第 9 章 KMP 的实现细节与调试

### 9.1 三处最容易写错的地方

**其一，`buildNext` 里的回退用 `next[k-1]` 而非 `next[k]`。** 因为 `k` 是"当前已匹配的前缀长度"，回退时要看"长度 `k` 的前缀的最长相等前后缀"，即 `next[k-1]`。

**其二，匹配时用 `next[j-1]` 而非 `next[j]`。** 因为 `j` 已失配，要用的是"已成功匹配的 `needle[0..j-1]`"的信息。

**其三，初始化 `next[0] = 0`。** 单字符没有真前后缀。

**这三处都是"下标差一位"的错误**——KMP 的 bug 几乎全在这里。

### 9.2 如何验证 KMP 写对了

**用"自匹配"用例**：`needle = "aabaabaaa"` 这类"自身含重复前后缀"的串，最能暴露 `next` 数组的错误。

**手算 `next` 数组**：对一个小串（如 `"aabaa"`），手算 `next = [0,1,0,1,2]`，再对照代码输出。

**跑"最坏情况"**：`haystack = "aaaa...ab"`、`needle = "aaaab"`——这是 KMP 相对朴素算法优势最大的场景。

### 9.3 一个"从暴力到 KMP"的表达模板

面试中，建议按这条链讲 KMP：

1. **暴力是 $O(mn)$**，瓶颈在"每次失配都从头再来"；
2. **观察**：已匹配的前缀里含"前后缀重叠"信息；
3. **利用**：失配时跳到"重叠的末尾"，而非 0；
4. **`next` 数组**存"最长相等前后缀长度"；
5. **`next` 本身也是自我匹配**，用同样的回退逻辑构建；
6. **复杂度**：$j$ 的总增/减有界，故 $O(m+n)$。

**这条链的价值，是它展示了"从问题到解法"的完整推导**——而非"直接给出 `next` 数组的定义"。

> [!info] KMP 的"下标细节"为什么难
> KMP 的算法思想其实很清晰（复用前后缀信息），**难的是"下标"**——`next[k-1]`、`next[j-1]`、`next[i-2]` 这些偏移，一旦差一位就全错。**这正是"字符串算法"的普遍特点：思想不难，细节磨人。** 应对办法是"先手算小例子、再写代码"，以及"想清楚每个变量的语义（是'长度'还是'位置'）"。

## 第 11 章 字符串搜索的工程实践

### 11.1 真实工具用什么算法

**`grep`、`ripgrep`、编辑器的查找，底层用的是什么？** 答案往往出乎意料——**它们多用"Boyer-Moore 的变体"或"SIMD 加速的朴素算法"，而非 KMP。**

- **ripgrep** 用"Boyer-Moore + SIMD"（一次比较多个字符），速度极快；
- **GNU grep** 用"Boyer-Moore-Horspool"；
- **Python 的 `str.find`** 用"Two-Way 算法"（KMP 与 BM 的结合）。

**为什么不用 KMP？** 因为 **KMP 的"逐字符比较"难以利用现代 CPU 的 SIMD 指令**，而 Boyer-Moore 的"跳跃"与 SIMD 的"并行比较"更契合。**这是"算法选择要考虑硬件"的典型例子。**

### 11.2 SIMD：现代字符串搜索的加速器

**SIMD（单指令多数据）**允许一条指令处理多个字符——**这对"字符串搜索"是天然的加速**。例如"一次比较 16 个字符是否等于目标"，能大幅提升"逐字符匹配"的速度。

**ripgrep 的核心竞争力，正是"SIMD + Boyer-Moore"**——它能在海量文本上做到"接近内存带宽"的搜索速度。**这提醒我们：算法的"理论复杂度"之外，"能否利用硬件特性"同样是工程性能的关键。**

### 11.3 大小写敏感与 Unicode

**真实搜索还要处理"大小写敏感"与"Unicode"**：

- **大小写不敏感**：需先归一化（如统一转小写），或对字符做"大小写折叠"；
- **Unicode**：同一个字符可能有多种表示（第 06 篇的归一化），需先标准化。

**这些"预处理"，往往比"搜索算法本身"更影响正确性**——**因为"看起来相同的文本"，在字节层面可能不同。**

### 11.4 从"算法"到"工程"

**字符串搜索的工程实践，与"课本算法"有明显差距**：

| 维度 | 课本 | 工程 |
|------|------|------|
| 算法 | KMP（最优复杂度） | Boyer-Moore / SIMD |
| 优化目标 | 最坏复杂度 | 实际吞吐 |
| 处理对象 | 单模式 | 多模式 / 正则 |
| 关键细节 | 前缀函数 | 硬件特性 / Unicode |

**这个差距的核心，是"工程优化目标是综合的"**——不只看复杂度，还看"硬件利用、实际数据分布、正确性细节"。**这与本专栏反复出现的"理论复杂度不等于工程选择"（第 02 篇 4.3 节）一脉相承。**

> [!info] 从"会算法"到"懂工程"
> 知道 KMP，只说明"会一个算法"；**知道"工程里为什么不用 KMP"，才说明"懂工程"。** 两者之间的差距，是"理论"与"实践"的差距——**而弥补这个差距，靠的是"知道真实系统怎么选、为什么这么选"。** 本专栏每篇留一节讲工程，正是为了帮你跨过这道坎。

## 第 12 章 常见误区与自测方法

### 7.1 四个高频误区

**误区一：朴素匹配的循环上界写成 `n`。** 应为 `n-m`，否则 `i+j` 越界。

**误区二：`next` 数组构建时忘了 `while` 回退。** 只写 `if` 会导致某些输入的 `next` 值错误。

**误区三：匹配时用 `j = next[j]` 而非 `next[j-1]`。** 下标差一位，结果全错。

**误区四：混淆 `next` 的两种定义。** 面试前先与面试官确认定义。

### 7.2 一套自测用例

| 用例 | 检验什么 |
|------|---------|
| `needle = ""` | 空模式串约定 |
| `haystack = "a", needle = "a"` | 单字符匹配 |
| `haystack = "aaaab", needle = "aab"` | 部分匹配后失配 |
| `haystack = "aaaa...ab", needle = "aaaab"` | 最坏情况 |
| `needle` 长于 `haystack` | 越界保护 |

**其中"最坏情况"（大量重复字符）最值得测**——它是 KMP 相对朴素算法优势最大的场景，也是朴素算法容易超时的场景。

## 第 13 章 一句话带走

**如果只能从本篇带走一句话，那就是：**"字符串匹配的本质，是'不要浪费已经比较过的信息'——KMP 的全部价值，就是把朴素算法丢掉的那份信息利用起来。"**

朴素算法每次失配都把"已匹配长度"归零，仿佛什么都没学到；**KMP 把这份信息存进 `next` 数组，失配时直接跳到"重叠的末尾"。** 而 `next` 数组本身，也是"用同样的回退逻辑构建"的——**"构建 `next` 就是 KMP 自己"**，这是 KMP 最优雅的地方。

**更进一步，这份"复用信息"的思想，可以迁移到一切"重复计算"的场景**：缓存、预处理、索引、记忆化搜索。**看到"同一个计算被反复做"，就该问一句"能不能把它存下来"。**

**而 KMP 的另一层启示，是"理论最优 ≠ 工程最优"**——KMP 复杂度更优，但工程里常用朴素算法（简单、缓存友好）。**记住这一点，你就不会陷入"唯复杂度论"的误区。**

## 第 14 章 一个可复用的判断

遇到"字符串匹配/查找"题，**先问三句**：

1. **是单模式还是多模式？** 单模式选 KMP/Z 算法，多模式选 AC 自动机/Rabin-Karp；
2. **是"最坏复杂度敏感"还是"实际吞吐敏感"？** 前者选 KMP，后者选 Boyer-Moore/SIMD；
3. **模式是否固定？** 固定且要多次匹配，可预建自动机；不固定则朴素或 KMP。

**这三问，能定下"用什么匹配算法"。** 而它们的共同依据，是本篇反复强调的——**"需求决定算法"**。

## 第 15 章 复杂度速查

| 算法 | 时间 | 空间 | 手写要求 |
|------|------|------|---------|
| 朴素 | $O(mn)$ | $O(1)$ | 必须能写 |
| KMP | $O(m+n)$ | $O(m)$ | **必须能手写** |
| Rabin-Karp | $O(m+n)$ 期望 | $O(1)$ | 能讲原理即可 |
| Boyer-Moore | $O(n/m)$ 最好 | $O(m)$ | 能讲原理即可 |
| AC 自动机 | $O(n+\sum m_i)$ | $O(\sum m_i)$ | 能讲原理即可 |

**"必须能手写"的只有 KMP**——**其余算法"能讲原理即可"。** 这个分层，能帮你合理分配精力。

## 小结

本篇从朴素匹配的"信息浪费"出发，推导出 KMP 的核心——**利用已匹配前缀的"最长相等前后缀"，让失配时不必从头再来**。`next` 数组的定义与构建、匹配过程的回退、以及"为什么是 `next[j-1]`"这些细节，都围绕这一直觉展开。复杂度证明用的是摊还分析（`j` 的总增/减有界），延伸的 459 题则展示了 `next` 数组携带的"自相似结构"信息。

贯穿全篇的核心认知有两条。其一，**算法优化的本质，常常是"不要浪费已经得到的信息"**——朴素算法把"已匹配长度"归零，KMP 把它利用起来。其二，**理论复杂度不等于工程选择**——KMP 更优，但工程里朴素算法因其简单、缓存友好而常用。**把这两条握住，你面对任何字符串匹配或"信息复用"类问题，都会先问"我浪费了什么信息"。**

下一篇 [[03 字符串解析：atoi、Add Binary 与进位模拟]] 进入字符串解析领域。atoi 是考察状态机设计的经典题，需处理前导空格、符号位、溢出等多个边界；Add Binary 是二进制加法的字符串模拟，与链表的两数相加异曲同工。

**再补充一段落点。** KMP 是"字符串算法"里最值得精读的一道——**它不仅教了一个算法，更教了一种思想（复用已比较的信息）和一种态度（理论最优 ≠ 工程最优）。** 当你把"复用信息"这一思想迁移到缓存、索引、记忆化搜索，把"工程取舍"这一态度迁移到技术选型，**KMP 的价值就远远超出了一道题。** 这正是本专栏想传达的——**学算法，学的是思想，而非代码。**
