# 字符串模拟：Valid Number、整数与罗马互转

**摘要：**

本篇覆盖三道字符串模拟题：LeetCode 65（Valid Number）、12（Integer to Roman）、13（Roman to Integer）。**Valid Number 是字符串解析题里公认最复杂的一道**——它要处理整数、浮点数、科学计数法的所有合法与非法格式，**有限状态机（DFA）是最优雅的解法**；整数与罗马互转则属于规则明确的模拟题，贪心与哈希映射即可解决。三道题放在一起，恰好展示了字符串解析的两个极端：**规则复杂的状态机解析**，与**规则简单的直接枚举**。本文用 Go 语言实现三道题，并逐层追问：为什么旗标法"能工作但难扩展"、DFA 的转移表为什么是"可核对的文档"、以及罗马数字的贪心为什么成立。掌握本篇，你就掌握了"用状态机驯服复杂规则"这一核心能力。

## 第 1 章 LeetCode 65：Valid Number

### 1.1 题目

**LeetCode 65 - Valid Number**（困难）

判断一个字符串是否是"有效数字"。有效数字可分成：一个**小数**或**整数**，可选地后跟 `e`/`E` 和一个**整数**。

- **小数**：可选符号 + （数字后跟点 / 数字后跟点再跟数字 / 点后跟数字）；
- **整数**：可选符号 + 数字。

```text
有效: "2", ".1", "2.", "2.0", "+.8", "2e10", "2E+10", "-2.3e4"
无效: ".", "+", "e", "1e", "1e2e3", ".e1", "--6", "+-3"
```

> [!warning] 这道题的难点不在算法，而在"把规则读准"
> LeetCode 65 的测试用例极其严格。**题目描述本身就是规则，必须逐字阅读。** 例如 `"1."` 是有效的（"数字后跟点"这一格式），而 `"."` 无效（没有任何数字）。**建议动笔前先把所有合法/非法格式列一遍。**

### 1.2 解法一：旗标法

用四个旗标追踪状态：是否出现过数字、是否出现过点、是否出现过 `e`、`e` 之后是否出现过数字：

```go
func isNumber(s string) bool {
    s = strings.TrimSpace(s)
    numSeen, dotSeen, eSeen := false, false, false
    numAfterE := true // e 之后必须有数字

    for i := 0; i < len(s); i++ {
        c := s[i]
        switch {
        case c >= '0' && c <= '9':
            numSeen = true
            numAfterE = true
        case c == '+' || c == '-':
            // 符号只能在开头或 e/E 之后
            if i != 0 && s[i-1] != 'e' && s[i-1] != 'E' {
                return false
            }
        case c == '.':
            // 点不能出现两次，也不能在 e 之后
            if dotSeen || eSeen {
                return false
            }
            dotSeen = true
        case c == 'e' || c == 'E':
            // e 不能出现两次，且 e 之前必须有数字
            if eSeen || !numSeen {
                return false
            }
            eSeen = true
            numAfterE = false // e 之后还没有数字
        default:
            return false // 非法字符
        }
    }
    return numSeen && numAfterE
}
```

**验证关键边界**：

| 输入 | 结果 | 原因 |
|------|------|------|
| `"."` | false | `numSeen=false` |
| `"1."` | true | 有数字、有点、无 e |
| `".1"` | true | 点后有数字 |
| `"1e"` | false | `numAfterE=false` |
| `"1e+2"` | true | `+` 在 `e` 后合法 |
| `"++1"` | false | 第二个 `+` 前不是 `e` |

### 1.3 解法二：有限状态机（DFA）

**旗标法能工作，但当规则更复杂时（如解析 JSON、SQL）就难以维护。** DFA 是字符串解析的通用解法。

**状态定义**（0-8）：0=初始、1=读入符号、2=读入整数部分数字、3=读入小数点（前有数字）、4=读入小数点（前无数字）、5=读入小数部分数字、6=读入 `e`、7=读入 `e` 后的符号、8=读入指数部分数字。

**接受状态**（合法终止）：2、3、5、8。

**转移表**（行是状态，列是字符类型：数字 / 符号 / 点 / e）：

| 状态 | 数字 | 符号 | 点 | e |
|------|------|------|-----|---|
| 0 | 2 | 1 | 4 | -1 |
| 1 | 2 | -1 | 4 | -1 |
| 2 | 2 | -1 | 3 | 6 |
| 3 | 5 | -1 | -1 | 6 |
| 4 | 5 | -1 | -1 | -1 |
| 5 | 5 | -1 | -1 | 6 |
| 6 | 8 | 7 | -1 | -1 |
| 7 | 8 | -1 | -1 | -1 |
| 8 | 8 | -1 | -1 | -1 |

（`-1` 表示非法转移）

```go
func isNumberDFA(s string) bool {
    transition := [][]int{
        {2, 1, 4, -1}, // 状态 0
        {2, -1, 4, -1}, // 状态 1
        {2, -1, 3, 6}, // 状态 2
        {5, -1, -1, 6}, // 状态 3
        {5, -1, -1, -1}, // 状态 4
        {5, -1, -1, 6}, // 状态 5
        {8, 7, -1, -1}, // 状态 6
        {8, -1, -1, -1}, // 状态 7
        {8, -1, -1, -1}, // 状态 8
    }
    accept := []bool{false, false, true, true, false, true, false, false, true}

    state := 0
    for i := 0; i < len(s); i++ {
        c := s[i]
        var typ int
        switch {
        case c >= '0' && c <= '9':
            typ = 0
        case c == '+' || c == '-':
            typ = 1
        case c == '.':
            typ = 2
        case c == 'e' || c == 'E':
            typ = 3
        default:
            return false // 非法字符
        }
        state = transition[state][typ]
        if state == -1 {
            return false
        }
    }
    return accept[state]
}
```

**DFA 的优势**：即使规则变化（如支持 `i` 表示虚数），**只需修改状态表，不必重写逻辑**。**这正是"显式数据结构优于隐式控制流"的体现**——转移表本身就是一份可核对的文档。

> [!info] 为什么 DFA 是"解析器的工程范式"
> Java 编译器的词法分析、JSON 解析器、正则引擎，底层都是 DFA（或其变体）。**它们之所以用 DFA，是因为"规则可能变化、需要可维护、需要可证明覆盖所有情形"。** 第 03 篇的 atoi 用了简化版 DFA；本篇的 Valid Number 是它的完整版。**理解了 DFA，你就理解了"如何用一张表，驯服任意复杂的字符规则"。**

## 第 2 章 LeetCode 12：整数转罗马数字

### 2.1 题目与规则

**LeetCode 12 - Integer to Roman**（中等）

把整数转为罗马数字（输入在 1-3999 之间）。罗马数字有 7 个基础符号（I=1、V=5、X=10、L=50、C=100、D=500、M=1000），另有 6 个减法组合（IV=4、IX=9、XL=40、XC=90、CD=400、CM=900）。

```text
3 → "III"；4 → "IV"；58 → "LVIII"；1994 → "MCMXCIV"
```

### 2.2 贪心解法

**把所有面值（含减法组合）从大到小排列，每次尽量用最大面值：**

```go
func intToRoman(num int) string {
    values := []int{1000, 900, 500, 400, 100, 90, 50, 40, 10, 9, 5, 4, 1}
    symbols := []string{"M", "CM", "D", "CD", "C", "XC", "L", "XL", "X", "IX", "V", "IV", "I"}

    var sb strings.Builder
    for i, v := range values {
        for num >= v {
            sb.WriteString(symbols[i])
            num -= v
        }
    }
    return sb.String()
}
```

**手动验证** `num = 1994`：

```text
1994 >= 1000 → "M"，剩 994
994 >= 900  → "CM"，剩 94
94 >= 90    → "XC"，剩 4
4 >= 4      → "IV"，剩 0
结果："MCMXCIV" ✓
```

**复杂度**：时间 $O(1)$（输入上限 3999，循环次数有界）、空间 $O(1)$。

> [!note] 贪心为什么成立
> 贪心在这里成立，因为**面值系统是"完备的"**：无论从哪个大面值开始，剩余部分都能用更小的面值精确表示，**不存在"选了大面值导致后续无法凑整"的情况**。这与"美元系统的硬币找零"能用贪心是同一原因。**而如果面值系统不完备（如面值 1、3、4），贪心就可能失败**——所以"贪心能否用"取决于面值系统的性质。

## 第 3 章 LeetCode 13：罗马数字转整数

### 3.1 题目与核心规则

**LeetCode 13 - Roman to Integer**（简单）

把罗马数字转为整数。

**核心规则**：罗马数字是加法系统，但有 6 个减法例外。**识别减法的规则是：若当前字符的值小于下一个字符的值，则减去当前字符的值**（而非加）。

```text
"IV"：I(1) < V(5) → -1 + 5 = 4
"IX"：I(1) < X(10) → -1 + 10 = 9
"XC"：X(10) < C(100) → -10 + 100 = 90
```

### 3.2 Go 实现

```go
func romanToInt(s string) int {
    value := map[byte]int{'I': 1, 'V': 5, 'X': 10, 'L': 50, 'C': 100, 'D': 500, 'M': 1000}
    result := 0
    for i := 0; i < len(s); i++ {
        cur := value[s[i]]
        if i+1 < len(s) && cur < value[s[i+1]] {
            result -= cur // 减法情况
        } else {
            result += cur // 加法情况
        }
    }
    return result
}
```

**手动验证** `"MCMXCIV"`：

```text
i=0: 'M'=1000, next='C'=100 → 1000>100 → +1000 = 1000
i=1: 'C'=100, next='M'=1000 → 100<1000 → -100 = 900
i=2: 'M'=1000, next='X'=10 → +1000 = 1900
i=3: 'X'=10, next='C'=100 → -10 = 1890
i=4: 'C'=100, next='I'=1 → +100 = 1990
i=5: 'I'=1, next='V'=5 → -1 = 1989
i=6: 'V'=5, next=0 → +5 = 1994 ✓
```

**复杂度**：时间 $O(n)$、空间 $O(1)$（映射表只有 7 个固定条目）。

### 3.3 优化：用数组/switch 代替 map

只有 7 种字符，可以用 `switch` 或数组替代 `map`，减少哈希开销：

```go
func valueOf(c byte) int {
    switch c {
    case 'I': return 1
    case 'V': return 5
    case 'X': return 10
    case 'L': return 50
    case 'C': return 100
    case 'D': return 500
    case 'M': return 1000
    }
    return 0
}
```

**"映射表很小且固定"时，数组/switch 比哈希表更快**——这与第 06 篇"字符频率用 `[26]int` 而非 map"是同一优化。

## 第 4 章 三道题对比与面试要点

### 4.1 难度梯度

| 题目 | 难度 | 核心技术 | 面试频率 |
|------|------|---------|---------|
| LC 13（罗马→整数） | 简单 | 哈希映射 + 减法判断 | 高 |
| LC 12（整数→罗马） | 中等 | 贪心 + 面值枚举 | 高 |
| LC 65（有效数字） | 困难 | 旗标法 / DFA | 中 |

### 4.2 Valid Number 的面试策略

LeetCode 65 在面试中较少考原题，但"字符串合法性验证"这一思路很常见（如验证 IP、邮箱）。面试时：

1. **先问清规则**：完整描述你对"合法数字"的理解，与面试官对齐（`"1."` 到底算不算合法？）；
2. **旗标法作为第一版**：先写出可工作的版本；
3. **DFA 作为进阶**：说明"如果规则更复杂，我会用状态机，可扩展性更强"。

### 4.3 罗马数字题的常见错误

**常见错误是"没有处理最后一个字符"**（`i+1` 越界）：

```go
// 错误：循环上界写成 n-1，漏掉最后一个字符
for i := 0; i < n-1; i++ { /* ... */ }

// 正确：在循环内用条件判断处理越界
if i+1 < len(s) && cur < value[s[i+1]] { /* ... */ }
```

> [!warning] 面试中的陷阱
> 罗马数字题看起来简单，但面试官常会要求你**不看映射表、只用 `switch` 实现**——考察你是否真的记住了 7 个符号。**建议面试前背熟：`I=1, V=5, X=10, L=50, C=100, D=500, M=1000`。**

## 第 5 章 延伸：DFA 在工程中的更多应用

Valid Number 用 DFA 处理"数字格式"，但 DFA 的用武之地远不止于此。本章看几个真实场景。

### 5.1 词法分析：编译器的第一步

**编译器的第一步是"词法分析"（Lexing）**——把源码切成一个个 token（关键字、标识符、数字、运算符）。**这本质上就是一个 DFA**：状态机读入字符流，根据当前状态与字符，决定"继续读"还是"输出一个 token"。

**例如识别标识符**：遇到字母进入"标识符状态"，继续读字母数字，遇到非字母数字则输出。**这正是 DFA 的运作方式。**

**工程上，词法分析器常用"正则表达式 → NFA → DFA"的工具链自动生成**（如 `lex`、`flex`）。**你写的正则规则，最终被编译成一张 DFA 转移表**——与 Valid Number 的转移表是同一回事。

### 5.2 JSON 解析：DFA 的另一个舞台

**JSON 解析器也是 DFA**——它读入字符流，根据当前状态（在对象里？在数组里？在字符串里？）决定如何解析。**"字符串里遇到转义符怎么办""数字的边界在哪"，都是状态转移要处理的问题。**

**理解了 Valid Number 的 DFA，你就理解了 JSON 解析器的骨架**——只是 JSON 的状态更多、规则更复杂。**"状态多"不是障碍，因为转移表会把它管理好。**

### 5.3 协议解析：状态机的经典应用

**网络协议（如 HTTP、TCP）的解析，本质是状态机**：

- HTTP 请求解析：请求行 → 请求头 → 空行 → 请求体；
- TCP 状态机：CLOSED → LISTEN → SYN_RCVD → ESTABLISHED → ……

**这些"状态"与"转移"，与 Valid Number 的 9 个状态是同一种建模方式。** **协议之所以"复杂"，往往不是因为逻辑难，而是因为状态多——而 DFA 正是驯服"多状态"的工具。**

### 5.4 一个可复用的 DFA 设计方法

从 Valid Number 到词法分析，DFA 的设计可以总结成一套方法：

1. **列出所有状态**：每个状态代表"读到某类字符后所处的阶段"；
2. **列出所有输入类型**：把字符按"对状态的影响"分类（如数字/符号/点/e）；
3. **画转移表**：对每个（状态，输入）组合，确定"下一个状态"或"非法"；
4. **标记接受状态**：哪些状态是"合法的终止状态"；
5. **实现**：用一个循环 + 一张表。

**这套方法的价值，是它把"复杂规则"变成"可核对的表格"**——**表格的每一格都可以单独检查，而嵌套的 `if-else` 无法。** 这就是 DFA 相比 `if-else` 的根本优势。

> [!info] 从"处理字符串"到"设计状态机"
> 很多人把字符串解析当成"写一堆 `if`"，结果越写越乱。**而 DFA 提供了一种"先设计、再实现"的方法**——先在纸上把状态和转移理清，再照着表格写代码。**这种"先设计状态、再实现"的习惯，是工程化的解析器与"能跑的代码"之间的分野。** 它也是本专栏反复强调的"先把问题结构理清、再动手"的一个具体体现。

### 5.5 罗马数字：另一种"规则表示"

**与 DFA 相反，罗马数字题的规则是"简单且静态"的**——7 个符号、6 个减法组合，一共 13 条规则，**直接枚举即可，无需状态机**。

**这个对比很有启发性**：

| 问题 | 规则复杂度 | 推荐表示 |
|------|-----------|---------|
| Valid Number | 高（9 状态 × 4 输入） | DFA 转移表 |
| 词法分析 | 高 | DFA / 自动生成 |
| 罗马数字 | 低（13 条静态规则） | 直接枚举 |

**"规则越复杂、越动态，越需要状态机；规则越简单、越静态，越适合直接枚举。"** 这条判断，能帮你在"该不该上状态机"时做决定——**不是所有字符串解析都要状态机，过度设计同样有害。**

> [!note] 工具要与问题匹配
> 状态机是强大的工具，但**"杀鸡用牛刀"同样是错误**。罗马数字题若硬套 DFA，反而更繁琐。**判断"该用什么工具"的能力，与"会用工具"同样重要**——这与本专栏反复出现的"没有银弹，因地制宜"一脉相承。

## 第 6 章 有限状态机的形式化与验证

### 6.1 DFA 的形式定义

**有限状态机（DFA）可以用五元组形式化**：$(Q, \Sigma, \delta, q_0, F)$——状态集合 $Q$、输入字母表 $\Sigma$、转移函数 $\delta: Q \times \Sigma \to Q$、初始状态 $q_0$、接受状态集合 $F$。

**Valid Number 的 DFA 就是这套形式的一个实例**：$Q$ 是 9 个状态、$\Sigma$ 是 4 类字符、$\delta$ 是转移表、$q_0$ 是状态 0、$F = \{2,3,5,8\}$。

**这个形式化定义的价值，是它让"字符串验证"变成了"状态转移"这一可分析的对象**——你可以用形式化的方法证明"某个 DFA 接受的语言是什么"。

### 6.2 如何验证 DFA 的完备性

**DFA 的常见 bug 是"漏掉某个（状态，输入）组合"**——即转移表里有"未定义"的格子。**验证方法是"穷举所有组合"**：

1. 列出所有状态 × 所有输入类型；
2. 逐个填转移；
3. **检查有没有遗漏**——任何遗漏都可能导致"意外接受"或"意外拒绝"。

**这正是 DFA 相比 `if-else` 的优势**——**表格的每一格都是显式的，遗漏一眼可见；而 `if-else` 的遗漏藏在控制流里，难以发现。**

### 6.3 从"能跑"到"可证明"

**DFA 的更高价值，是"可证明"**——你可以形式化地证明"这个状态机接受的语言，恰好是所有合法数字"。**而 `if-else` 的代码，只能靠"测试覆盖"来近似保证。**

**这就是为什么"解析器"这类需要高可靠性的组件，几乎都用形式化的状态机**（而非手写 `if-else`）——**因为"可证明正确"比"测试通过"更强。**

> [!info] 形式化：从"工程"到"科学"
> 字符串解析的底层是形式语言理论。**用 DFA/正则/NFA 这些形式化工具，你能"证明"解析器的正确性，而不仅是"测试通过"。** 这提示我们：**当一个问题的规则复杂到"靠测试难以覆盖"时，形式化往往是唯一的出路。** 编译器、协议解析器、安全校验器都遵循这条路径——**它们不满足于"能跑"，而追求"可证明"。**

## 第 8 章 罗马数字的历史与数制转换的通用思路

### 8.1 罗马数字为什么"反直觉"

**罗马数字是一套"非位值制"的数制**——它的值由"符号相加/相减"得到，而非"位值 × 权重"。**这与我们熟悉的十进制（位值制）根本不同**，也解释了它为什么"反直觉"：

- **没有"零"**：罗马数字没有表示 0 的符号（因为它不需要占位）；
- **没有"进位"**：加法是"符号拼接"，不是"逢十进一"；
- **减法规则**：`IV`、`IX` 等 6 个例外，是为了"避免连写四个相同符号"（如 `IIII` → `IV`）。

**理解了"罗马数字不是位值制"，你就明白为什么它"看着简单、写着别扭"**——**因为我们的思维被十进制"训练"过了。**

### 8.2 数制转换的通用思路

**"整数转罗马"用的是"贪心 + 面值枚举"，而"整数转二进制/十六进制"用的是"取模 + 除基"**——**它们看起来不同，但本质都是"用一组'面值'去逼近目标值"**：

- 罗马数字：面值是 `[1000, 900, ..., 1]`（含减法组合）；
- 二进制：面值是 `[2^k, ..., 2, 1]`；
- 十进制：面值是 `[10^k, ..., 10, 1]`。

**"用面值逼近"是数制转换的统一思路**——**罗马数字的"面值"不规整（含 900、400 等），所以要用"贪心 + 枚举"；而二进制的"面值"规整（全是 2 的幂），所以"取模除基"就够了。**

**换句话说：罗马数字题之所以"要枚举面值"，是因为它的"面值系统不规则"**——**理解了这一点，你就明白为什么它不能像二进制那样"取模除基"。**

### 8.3 一个可迁移的观察

**"面值系统是否规整，决定了转换方法"**——这条观察可以迁移到很多"转换"类问题：

| 转换 | 面值系统 | 方法 |
|------|---------|------|
| 整数 → 二进制 | 规整（2 的幂） | 取模除基 |
| 整数 → 罗马 | 不规整（含减法） | 贪心枚举 |
| 整数 → 英文 | 不规整（三位一组） | 分组模板 |

**它们共同说明：转换方法的"复杂度"，取决于"目标系统是否规整"。** **规整的用公式（取模），不规整的用枚举（贪心）。**

> [!info] "规整 vs 不规整"：一个被忽视的维度
> 很多人以为"数制转换"是一件事，其实**"目标系统是否规整"决定了方法**。**规整的（二进制、十进制）用"取模除基"，不规整的（罗马、英文）用"贪心枚举 + 模板"。** 这个维度，能帮你在遇到新的"转换"问题时，快速判断"该用公式还是枚举"。

## 第 10 章 字符串验证的更多工程场景

### 10.1 验证 IP 地址（LeetCode 468）

**题目**：验证一个字符串是否是有效的 IPv4 或 IPv6 地址。

**IPv4**：四段十进制数，每段 0-255，无前导零；**IPv6**：八段十六进制数，每段 1-4 位。

```go
func validIPAddress(queryIP string) string {
    if isIPv4(queryIP) {
        return "IPv4"
    }
    if isIPv6(queryIP) {
        return "IPv6"
    }
    return "Neither"
}

func isIPv4(s string) bool {
    parts := strings.Split(s, ".")
    if len(parts) != 4 {
        return false
    }
    for _, p := range parts {
        if len(p) == 0 || len(p) > 3 {
            return false
        }
        if len(p) > 1 && p[0] == '0' { // 无前导零
            return false
        }
        n := 0
        for i := 0; i < len(p); i++ {
            if p[i] < '0' || p[i] > '9' {
                return false
            }
            n = n*10 + int(p[i]-'0')
        }
        if n > 255 {
            return false
        }
    }
    return true
}
```

**这道题是"分段 + 逐段验证"的典型**——**先按分隔符切分，再对每段做范围与格式检查。** 它与 Valid Number 是同一类"格式验证"，但"分段处理"代替了"状态机"——**因为 IPv4 的规则"每段独立"，无需状态机。**

### 10.2 验证邮箱：为什么"别用正则"

**"验证邮箱"是一个著名的话题**——**用正则验证邮箱"几乎不可能完全正确"**（RFC 5322 允许极其复杂的格式）。**工程界的共识是**：

- **简单校验**：只检查"有 `@`、有点、长度合理"，足够过滤明显错误；
- **终极校验**：**发一封确认邮件**——这才是唯一可靠的方式。

**"别用正则验证邮箱"是一个重要的工程经验**——**它说明"有些规则复杂到不值得用程序精确验证"，而"用别的手段（发邮件）更可靠"。** 这与 Valid Number"规则复杂但值得精确验证"形成对照——**是否值得精确验证，取决于"错误的代价"。**

### 10.3 比较版本号（LeetCode 165）

**题目**：比较两个版本号 `version1`、`version2`（如 `"1.01"`、`"1.001"`），返回 -1/0/1。

**核心是"按点切分、逐段比较"**——**注意前导零要忽略（`"1.01"` 等于 `"1.1"`）：**

```go
func compareVersion(version1, version2 string) int {
    v1 := strings.Split(version1, ".")
    v2 := strings.Split(version2, ".")
    for i := 0; i < len(v1) || i < len(v2); i++ {
        n1, n2 := 0, 0
        if i < len(v1) {
            n1, _ = strconv.Atoi(v1[i]) // Atoi 自动忽略前导零
        }
        if i < len(v2) {
            n2, _ = strconv.Atoi(v2[i])
        }
        if n1 < n2 {
            return -1
        }
        if n1 > n2 {
            return 1
        }
    }
    return 0
}
```

**"用 `Atoi` 自动忽略前导零"是一个巧思**——**它避免了"手动去前导零"的繁琐。** 这类"用库函数简化逻辑"的技巧，在字符串题里很常见。

### 10.4 三道验证题的共性

468、165 加上 Valid Number，都是"格式验证/比较"：

| 题目 | 规则特点 | 方法 |
|------|---------|------|
| LC 65 Valid Number | 规则复杂、状态多 | 状态机 |
| LC 468 验证 IP | 每段独立 | 分段 + 逐段验证 |
| LC 165 版本号比较 | 分段比较 | 切分 + 逐段比较 |

**它们共同说明："字符串验证"的方法，取决于"规则的形态"**——**规则复杂且相互关联 → 状态机；规则按段独立 → 分段处理。** **"先看规则的形态，再选方法"，是处理验证题的第一步。**

> [!info] 验证题的"方法选择"
> 字符串验证题不是"一律用状态机"——**IP 验证用"分段"更简单，版本号比较用"切分"更直接。** **"规则按段独立"时，分段处理比状态机更清晰。** 这又一次印证了"工具要与问题匹配"——**过度设计（硬套状态机）与设计不足（漏掉边界）同样是错。**

## 第 11 章 常见误区与自测方法

### 5.1 四个高频误区

**误区一，LC 65 的 `numAfterE` 初始值写成 `false`。** 应为 `true`（"还没有 e"意味着"e 之后无需数字"）。

**误区二，LC 65 允许点出现在 `e` 之后。** 如 `"1e2.3"` 应无效。

**误区三，LC 12 漏掉减法组合。** 面值表必须包含 `900, 400, 90, 40, 9, 4`。

**误区四，LC 13 漏处理最后一个字符。** 循环上界与越界判断都要小心。

### 5.2 一套自测用例

| 用例 | 检验什么 |
|------|---------|
| `"."` / `"1."` / `".1"` | 点的各种位置 |
| `"1e"` / `"1e2"` / `"e1"` | `e` 的各种位置 |
| `"1e2.3"` | 点不能在 `e` 后 |
| `4` / `9` / `40` / `900` | 减法组合 |
| `"III"` / `"IV"` / `"MCMXCIV"` | 罗马互转往返 |

**其中 `"1e2.3"` 最值得测**——它专治"点出现在 `e` 之后"这一陷阱。

## 第 12 章 一句话带走

**如果只能从本篇带走一句话，那就是：**"规则越复杂，越该用状态机；规则越简单，越可直接枚举。"

- **Valid Number**：规则复杂（9 状态 × 4 输入）→ 状态机；
- **罗马数字**：规则简单（13 条静态规则）→ 直接枚举。

**这条判断，能帮你在"该不该上状态机"时做决定**——**状态机是强大的工具，但"杀鸡用牛刀"同样是错。** 判断"该用什么工具"的能力，与"会用工具"同样重要。

**而状态机的另一层价值，是"可证明"**——它的转移表让"覆盖所有情形"从"凭经验"变成"可核对"，甚至能形式化证明。**这是为什么高可靠性组件（编译器、协议解析器）偏爱状态机。**

**最后，罗马数字的贪心启示是："贪心能否用，取决于问题结构"**（面值系统是否完备）。**理解这一点，你就不会盲目套用贪心。**

> [!note] 一个可复用的判断
> 遇到字符串解析/验证题，**先问两句**：规则有多复杂？状态多不多？**状态多（>5）就用转移表，状态少就用 `switch`，规则简单就直接枚举。** 这两问，能定下"用什么结构"。

## 第 13 章 复杂度速查与选型

| 题目 | 时间 | 空间 | 手写要求 |
|------|------|------|---------|
| LC 65 Valid Number | $O(n)$ | $O(1)$ | 旗标法必须能手写；DFA 能讲原理 |
| LC 12 整数转罗马 | $O(1)$（上限 3999） | $O(1)$ | **必须能手写** |
| LC 13 罗马转整数 | $O(n)$ | $O(1)$ | **必须能手写** |

**"必须能手写"的是罗马互转**（简单且高频）；**Valid Number 的旗标法必须能写、DFA 能讲清即可**——因为 Valid Number 在面试中"较少考原题"，但"字符串验证"的思路很常见。

**这个"手写要求"的分层，能帮你合理分配备考精力**——**把时间花在"必须能手写"的题上。**

> [!note] 一个总体判断
> 遇到"字符串验证"题，**先问"规则复不复杂"**——复杂（如 Valid Number）用状态机，简单（如 IP）用分段。**而"罗马数字"这类"规则简单的模拟题"，直接枚举即可。**

## 小结

本篇用三道题，覆盖了字符串模拟的两个极端。Valid Number（LC 65）展示了**"规则复杂时，用 DFA 把规则显式化"**——转移表既是实现，也是文档；整数与罗马互转（LC 12/13）则展示了**"规则简单时，贪心与映射即可"**。两者的对比说明：**规则越复杂，越需要"结构化的表示"（状态表）；规则越简单，越可以直接枚举。**

贯穿全篇的核心认知有两条。其一，**DFA 是"驯服复杂字符规则"的通用范式**——它把"状态转移"从隐式控制流里解放出来，变成可核对的表。其二，**"贪心能否用"取决于问题结构**（如罗马面值系统是否完备），而非贪心本身。**把这两条握住，你面对任何字符串模拟/验证题，都会先问"规则有多复杂、该用什么结构表示"。**

下一篇 [[08 路径规范化与边界处理：Simplify Path 与 Length of Last Word]] 是字符串专栏的收尾篇，收录两道工程气息浓厚的题：LeetCode 71（Simplify Path）用栈处理路径分量，是文件系统路径规范化的精简版；LeetCode 58（Length of Last Word）考察从右往左扫描的边界处理。

**再补充一段落点。** 本篇两道题代表了字符串解析的两个极端：Valid Number 是"规则复杂到必须用状态机"，罗马数字是"规则简单到直接枚举"。**它们共同说明一件事：工具要与问题匹配。** 状态机强大，但对简单规则是"杀鸡用牛刀"；枚举简单，但对复杂规则会"越写越乱"。**能判断"该用什么工具"，比"会用工具"更需要经验**——而这份经验，来自对"规则复杂度"的敏感。

**再看一个更深的落点。** Valid Number 的 DFA 与"编译器的词法分析"是同一件事——**你写的正则规则，最终被编译成一张 DFA 转移表。** 而"字符串验证"在工程里对应"配置校验、输入校验、协议解析"。**理解了这层对应，你就把"一道困难题"上升成了"一类工程组件"。** 这正是本专栏每篇留一节讲工程的原因——**让你看到"题目背后更大的世界"。**

**最后再强调一点"练习方法"。** 罗马数字题要在"不看映射表"的情况下写出来——**把 `I=1, V=5, X=10, L=50, C=100, D=500, M=1000` 背到条件反射。** 而 Valid Number 要练到"能默写转移表"——**因为它是"DFA 建模"的最佳练习素材。** 这两道题的练习价值，远超它们的"难度"。

**最后，留一道值得回味的思考题。** 若把 Valid Number 的规则改成"支持千分位逗号"（如 `"1,000"`），状态机要怎么改？**答案是加几个状态**——"读到逗号后必须跟三位数字"。**这个思考题说明：状态机的好处正是"加规则只需加状态"，而不必重写逻辑。** 这正是 DFA 相比 `if-else` 的"可扩展性"优势——**规则会变，而状态表只需"加几行"。** 这也是为什么"可扩展的解析器"都用状态机——**因为真实世界的规则总是在变，而状态表让"应对变化"变得便宜。** 理解了这一点，你就明白为什么"解析器"这一工程组件，几乎都用状态机而非 `if-else`——**它把"应对未来变化"的成本，压到了最低。** 这也是本篇把 Valid Number 与罗马数字放在一起的原因——**它们分别代表"该用状态机"与"不该用状态机"两种情形，对照着看，判断力就出来了。** 而这份判断力，正是"工具选择"的核心。
