# 栈的设计题：最小栈与用队列模拟栈

**摘要：**

本篇进入栈的"设计类"题目——它们不要求你解决某个具体计算，而是要求你**在既有数据结构的约束下，额外撑起一项新能力**。LeetCode 155（Min Stack，最小栈）要求在普通栈之上支持 $O(1)$ 的 `getMin()`，核心思路是用一个辅助栈同步追踪每个状态下的最小值，这是"以空间换时间"的经典设计；LeetCode 225（用队列实现栈）则要求用 FIFO 的队列模拟 LIFO 的栈，它逼你直面两种结构的本质差异，并给出三种代价各异的方案。两道题看似简单，却是**系统设计思维的微缩版**——"辅助结构同步追踪派生信息"这一模式，在数据库索引、Redis 的 Sorted Set、优先队列的惰性删除里反复出现。本文用 Go 语言完整实现，并逐层追问：为什么全局最小值变量不够用、辅助栈里到底存了什么、`<=` 与 `<` 之差为何致命、以及"用队列模拟栈"的三种方案该如何取舍。

---

## 第 1 章 设计题：从"能跑"到"够快"

### 1.1 设计题与算法题的分野

算法题问的是"怎么算"，设计题问的是"怎么撑"。以最小栈为例，它不要求你做任何计算，只要求你实现四个操作，并保证 `getMin()` 是 $O(1)$。**换句话说，设计题的核心不是算法，而是数据结构的选择与组合。**

这带来一个思维上的转向：算法题从"约束"出发推导解法，设计题则从"每个操作的目标复杂度"出发，为它们匹配（或组合）能同时满足的数据结构。**这两条路径的分叉，值得在动笔前先分清。**

### 1.2 设计题的四步推导

无论是本专栏的栈设计题，还是第 13 篇的 LRU 缓存，都可以用同一套四步来推：

1. **列出每个操作的目标复杂度**。最小栈要求 `push`、`pop`、`top`、`getMin` 都是 $O(1)$。
2. **为每个操作匹配结构**。`push/pop/top` 用栈天然满足；难点全在 `getMin`。
3. **验证结构能否同时支撑所有操作**。这一步是核心——它往往会把单一结构逼向"组合体"。
4. **处理边界**。空栈操作、相等元素的处理、辅助结构的同步。

**第 3 步之所以关键，是因为它揭示了设计题的一般形态：单一结构通常不够用，答案往往是一个"主结构 + 辅助结构"的组合。** 本篇的两道题，正是这一形态的最小样本。

## 第 2 章 LeetCode 155：最小栈

### 2.1 题目

**LeetCode 155 - Min Stack**（中等）

设计一个支持 `push`、`pop`、`top` 和 `getMin` 操作的栈，其中 `getMin` 必须在 $O(1)$ 时间内运行。

```text
MinStack s = new MinStack()
s.push(-2); s.push(0); s.push(-3)
s.getMin()  // 返回 -3
s.pop()
s.top()     // 返回 0
s.getMin()  // 返回 -2
```

### 2.2 朴素思路为何行不通

最直接的想法是维护一个全局的 `minValue` 变量：每次 `push` 时更新它。但这在 `pop` 时会立刻撞墙——

```go
// 有缺陷的实现
type BadMinStack struct {
    data []int
    min  int
}

func (s *BadMinStack) Push(val int) {
    s.data = append(s.data, val)
    if val < s.min {
        s.min = val
    }
}

func (s *BadMinStack) Pop() {
    v := s.data[len(s.data)-1]
    s.data = s.data[:len(s.data)-1]
    if v == s.min {
        // 最小值被弹出了，新的最小值是多少？无从得知
    }
}
```

**问题的症结在于：最小值是一个"随栈状态变化而变化"的量，而全局变量只保留了"当前"这一个快照。** 一旦最小值被弹出，我们没有任何线索恢复"上一个状态的最小值"——除非重新扫描整个栈，代价 $O(n)$。

**这里的教训具有普遍性：当某个查询结果依赖于"历史状态"时，只存当前值是不够的，必须把历史也存下来。** 这正是辅助栈的由来。

### 2.3 核心设计：辅助栈记录"每个状态的最小值"

解法是引入一个辅助栈 `mins`，与主栈 `data` 同步：**`mins` 的第 $i$ 个元素，记录的是"当主栈恰好有 $i$ 个元素时，这 $i$ 个元素的最小值"。** 于是 `mins` 的栈顶，永远等于"当前主栈所有元素的最小值"。

```go
type MinStack struct {
    data []int // 主栈：存所有元素
    mins []int // 辅助栈：mins[i] = 主栈前 i+1 个元素的最小值
}

func Constructor() MinStack { return MinStack{} }

func (s *MinStack) Push(val int) {
    s.data = append(s.data, val)
    if len(s.mins) == 0 || val <= s.mins[len(s.mins)-1] {
        s.mins = append(s.mins, val)
    }
}

func (s *MinStack) Pop() {
    v := s.data[len(s.data)-1]
    s.data = s.data[:len(s.data)-1]
    if v == s.mins[len(s.mins)-1] {
        s.mins = s.mins[:len(s.mins)-1]
    }
}

func (s *MinStack) Top() int    { return s.data[len(s.data)-1] }
func (s *MinStack) GetMin() int { return s.mins[len(s.mins)-1] }
```

**关键直觉**：主栈每 `pop` 一次，辅助栈也"退回到上一个状态"，于是辅助栈顶永远对应着当前主栈的最小值。**它把"最小值的完整历史"存了下来——这正是全局变量做不到的事。**

**示例**（`push(-2), push(0), push(-3), pop(), getMin()`）：

```text
push(-2): data=[-2]        mins=[-2]
push(0):  data=[-2, 0]     mins=[-2]        （0 不比 -2 小，不压辅助栈）
push(-3): data=[-2, 0, -3] mins=[-2, -3]
getMin() → mins 栈顶 = -3 ✓
pop():    data=[-2, 0]     mins=[-2]        （弹出的 -3 等于辅助栈顶，同步弹出）
top()    → data 栈顶 = 0 ✓
getMin() → mins 栈顶 = -2 ✓
```

**复杂度**：所有操作时间 $O(1)$；空间最坏 $O(n)$（单调递减时辅助栈与主栈等长），最好 $O(1)$（单调递增时辅助栈只留一个元素）。

### 2.4 一个致命的等号陷阱

上面的代码里，压辅助栈的条件写的是 `val <= mins[top]`，用的是 `<=` 而不是 `<`。**这一个等号之差，决定了代码正确与否。**

考虑 `push(3), push(3), pop()` 的操作序列：

```text
若用 <：
  push(3): 3 < 空 → 压辅助栈，mins=[3]
  push(3): 3 < 3 为假 → 不压，mins=[3]
  pop():   弹出 3，3 == mins 栈顶 3 → 辅助栈也弹出，mins=[]
  此时主栈还剩一个 3，但 getMin() 访问 mins 栈顶会越界 → 错误

若用 <=：
  push(3): 压，mins=[3]
  push(3): 3 <= 3 为真 → 也压，mins=[3, 3]
  pop():   弹出 3，同步弹出，mins=[3]
  主栈还剩一个 3，getMin() 返回 3 → 正确 ✓
```

**根因在于"多个相等的元素"与"辅助栈的同步"之间的耦合**：每个被压入主栈的最小值元素，都必须在辅助栈里留下一个"可对应的副本"，否则弹出时辅助栈会比主栈先空。**用 `<=`，保证了"有几个最小值元素，辅助栈就有几个副本"。**

> [!warning] 生产避坑：辅助结构与主结构的"数量对齐"
> 最小栈的等号陷阱，本质是"辅助结构与主结构的元素数量没对齐"——辅助栈提前空了。**凡是"主结构 + 辅助结构同步"的设计，都要反复确认：主结构每减少一个元素，辅助结构是否也恰好减少一个？两者会不会先于对方变空？** 这类"对齐"问题在 LRU（哈希表与链表的同步）、并查集（父指针与秩的同步）里同样致命。

### 2.5 另一种设计：辅助栈与主栈等长

还有更简单的写法——**辅助栈永远与主栈等长**，每次 `push` 都往辅助栈压"当前最小值"，每次 `pop` 都弹一次：

```go
func (s *MinStack) Push(val int) {
    s.data = append(s.data, val)
    if len(s.mins) == 0 {
        s.mins = append(s.mins, val)
    } else {
        m := s.mins[len(s.mins)-1]
        if val < m {
            m = val
        }
        s.mins = append(s.mins, m)
    }
}
func (s *MinStack) Pop() {
    s.data = s.data[:len(s.data)-1]
    s.mins = s.mins[:len(s.mins)-1] // 无条件同步弹出
}
```

**这种写法没有等号陷阱**（因为每次无条件同步），但辅助栈恒为 $O(n)$ 空间。**两种写法是"空间"与"简单"之间的一次典型权衡**：前者省空间但需小心等号，后者费空间却不易出错。**面试中，笔者更推荐前者并主动说明 `<=` 的理由——因为能讲清这个等号，恰恰证明你理解了同步的本质。**

## 第 3 章 LeetCode 225：用队列实现栈

### 3.1 题目

**LeetCode 225 - Implement Stack using Queues**（简单）

仅使用两个队列实现一个 LIFO 栈，支持 `push`、`pop`、`top`、`empty`。只能使用队列的标准操作（入队、出队、取队头、大小、判空）。

```text
MyStack s = new MyStack()
s.push(1); s.push(2)
s.top()   // 返回 2
s.pop()   // 返回 2
s.empty() // 返回 false
```

### 3.2 矛盾的核心：只允许访问"另一头"

**栈是 LIFO，队列是 FIFO**，这是两种结构的根本差异。若用队列存 `[1, 2, 3]`，它自然的出队顺序是 `1 → 2 → 3`；而栈需要的出栈顺序是 `3 → 2 → 1`。

**矛盾的核心在于：我们需要访问队列的"尾部"（最后加入的元素），但队列只允许访问"头部"。** 既然结构本身不给这个能力，那就只能**用"搬移"来人工制造它**——把想要的那个元素，通过搬移"挪"到队头。这就是下面三种方案共同的思路来源。

### 3.3 方案一：push 时搬移（push $O(n)$，pop $O(1)$）

让主队列 `q1` 始终按"栈顶在前"的顺序存储。每次 `push` 时，先把新元素放入空队列 `q2`，再把 `q1` 的所有元素依次移入 `q2`（此时新元素自然排在最前），最后交换 `q1`、`q2`。

```go
type MyStack struct {
    q1 []int // 主队列：栈顶在头部
    q2 []int // 辅助队列
}

func (s *MyStack) Push(x int) {
    s.q2 = append(s.q2, x) // 新元素先进 q2
    for len(s.q1) > 0 {    // q1 全部搬到 q2（排在 x 后面）
        s.q2 = append(s.q2, s.q1[0])
        s.q1 = s.q1[1:]
    }
    s.q1, s.q2 = s.q2, s.q1 // 交换：q1 成为主队列
}

func (s *MyStack) Pop() int {
    v := s.q1[0]
    s.q1 = s.q1[1:]
    return v
}

func (s *MyStack) Top() int    { return s.q1[0] }
func (s *MyStack) Empty() bool { return len(s.q1) == 0 }
```

**手动演示**：

```text
push(1): q2=[1]，q1 空 → 交换 → q1=[1]
push(2): q2=[2]，q1=[1] 搬入 → q2=[2,1] → 交换 → q1=[2,1]
push(3): q2=[3]，q1=[2,1] 搬入 → q2=[3,2,1] → 交换 → q1=[3,2,1]
pop()  → q1 出队 = 3，q1=[2,1] ✓
```

**代价**：`push` 是 $O(n)$（每次要搬移已有全部元素），`pop/top` 是 $O(1)$。**适合"push 少、pop 多"的场景。**

### 3.4 方案二：pop 时搬移（push $O(1)$，pop $O(n)$）

反过来：`push` 直接入队（$O(1)$），`pop` 时把 `q1` 中除最后一个元素外的全部搬到 `q2`，剩下的那个就是栈顶；取出后再把 `q2` 搬回 `q1`（或交换两者）。

```go
func (s *MyStack) Push(x int) { s.q1 = append(s.q1, x) } // O(1)

func (s *MyStack) Pop() int {
    for len(s.q1) > 1 { // 除最后一个，全部搬到 q2
        s.q2 = append(s.q2, s.q1[0])
        s.q1 = s.q1[1:]
    }
    v := s.q1[0]
    s.q1 = s.q1[:0]
    s.q1, s.q2 = s.q2, s.q1 // 交换回来
    return v
}
```

**代价**：`push` 是 $O(1)$，`pop/top` 是 $O(n)$。**适合"push 多、pop 少"的场景。**

### 3.5 方案三：单队列实现（进阶）

其实一个队列就够了——`push` 后，把队列里"新元素之前的所有元素"循环地出队再入队，使新元素旋转到队头。

```go
type MyStack struct{ q []int }

func (s *MyStack) Push(x int) {
    s.q = append(s.q, x)
    // 把 x 之前的元素全部旋转到 x 后面，使 x 到达队头
    for i := 0; i < len(s.q)-1; i++ {
        s.q = append(s.q, s.q[0])
        s.q = s.q[1:]
    }
}
func (s *MyStack) Pop() int    { v := s.q[0]; s.q = s.q[1:]; return v }
func (s *MyStack) Top() int    { return s.q[0] }
func (s *MyStack) Empty() bool { return len(s.q) == 0 }
```

**直观理解**：每次 `push` 后做一次"循环旋转"，把新元素转到队头。于是队列内部始终维持"最新入的在最前"的顺序，出队即等同于出栈。**代价仍是 `push` $O(n)$、其余 $O(1)$，但只需一个队列——这是"用一个更巧的操作，省掉一个结构"的典型。**

### 3.6 三种方案的取舍

| 方案 | push | pop | top | 队列数 | 适用场景 |
|------|------|-----|-----|--------|---------|
| 方案一（push 搬移） | $O(n)$ | $O(1)$ | $O(1)$ | 2 | push 少 |
| 方案二（pop 搬移） | $O(1)$ | $O(n)$ | $O(n)$ | 2 | pop 少 |
| 方案三（单队列） | $O(n)$ | $O(1)$ | $O(1)$ | 1 | 同方案一，更省结构 |

**面试中，建议先把"push 昂贵"与"pop 昂贵"两种方案都讲出来，再说明取舍依据**——这展示的是"根据访问模式选型"的意识，比只给一个方案更能打动面试官。**注意这里没有"最优方案"：三者的总代价相当，区别只在"把昂贵的那一步放在哪个操作上"，而这取决于真实的访问模式。**

## 第 4 章 设计题的思维方法

### 4.1 "辅助结构同步追踪派生信息"模式

最小栈的设计思想——**主结构负责存储，辅助结构同步追踪某种派生信息**——在工程中极为常见：

- **数据库索引**：主表不动，通过维护独立的 B+ Tree 索引来支持 $O(\log n)$ 查询；
- **Redis 的 Sorted Set**：同时维护哈希表（$O(1)$ 按成员查分数）与跳表（$O(\log n)$ 按分数范围查询），以双倍空间支持两种查询模式；
- **优先队列 + 惰性删除**：无法从堆中直接删除任意元素时，维护一个"待删除集合"，在弹出时跳过。

**这个模式的设计原则有三条：**

1. **同步更新**：每次主结构变化后，辅助结构也随之更新；
2. **记录派生信息**：辅助结构存的是"由主结构派生出来的信息"（最小值、前缀和、累计计数、下标映射）；
3. **读查辅助、写更两者**：读操作只查辅助结构（$O(1)$），写操作同时维护两者。

**最小栈是这三条原则最简洁的样本**：辅助栈同步更新、存的是"派生出的最小值"、`getMin` 只查辅助栈。**理解了这三条，你就能把"最小栈"的思路迁移到"最大栈""最小队列""带最值的滑动窗口"等一系列变体上。**

### 4.2 栈与队列互转的复杂度对照

| 操作 | 栈模拟队列（LeetCode 232） | 队列模拟栈（LeetCode 225） |
|------|--------------------------|--------------------------|
| push | $O(1)$ 摊还 | $O(n)$（方案一） |
| pop | $O(1)$ 摊还 | $O(1)$（方案一） |

**一个耐人寻味的对比**：用栈模拟队列能做到"摊还 $O(1)$"（见第 03 篇的推导），而用队列模拟栈的两种方案都有一端是 $O(n)$。**为什么不对称？** 因为"双栈模拟队列"能把昂贵操作摊还掉（每个元素最多进出两次），而"队列模拟栈"的搬移无法摊还（每次都要搬动几乎全部元素）。**这个不对称本身，就说明了栈与队列并非"完全对称"的两种结构。**

> [!note] 设计题的面试评分维度
> 这类题的评分，不只看"能否写出"，还看：
> 1. **需求澄清**：先问清"哪些操作必须 $O(1)$、哪些可以 $O(n)$"，再给出对应权衡；
> 2. **多方案对比**：能给出"push 昂贵"与"pop 昂贵"两种方案并说明适用场景；
> 3. **边界与细节**：空结构操作、相等元素的处理（如最小栈的等号）。
>
> **这三条里，第 1 条最容易被忽视，却最能体现工程素养**——因为在真实工程里，"哪个操作更频繁"往往决定了整个设计。

## 第 5 章 延伸：设计题的更多面孔

### 5.1 最大栈（LeetCode 716）：最小栈的镜像

**题目**：设计一个支持 `push`、`pop`、`top`、`peekMax`、`popMax` 的栈。

它与最小栈的差别在于多了一个 `popMax()`——**要删除最大值所在的元素**，而最大值可能藏在栈的中间。这比最小栈难得多，因为它要求"删除任意位置的最大值元素"。

一种可行的思路是**用有序结构（如平衡树）维护元素的顺序，同时记录每个元素的位置**；另一种思路是"主栈 + 辅助栈 + 惰性删除"。**这道题之所以更难，是因为它把"查询最值"升级成了"删除最值"——查询可以只读辅助结构，删除却必须改动主结构。** 这个区别，是设计题里一条清晰的难度分水岭。

### 5.2 带 min 的队列：单调队列的雏形

若把最小栈的"辅助栈"思路，换成"维护一个单调递增的辅助队列"，就能得到"$O(1)$ 查询队列最小值"的结构——这正是第 06 篇**单调队列**的雏形。

**换句话说，单调队列就是"最小栈"思想从栈迁移到队列的结果。** 只不过队列两端都能进出，维护单调性的难度更高（需要用双端队列）。**这也再次印证了那条主线：设计题的核心动作，是"为一个新能力匹配合适的辅助结构"，而结构怎么选，取决于主结构的形态。**

### 5.3 设计题与算法题的交汇

本专栏的 LRU 缓存（线性表专栏第 13 篇）、最小栈、单调队列，表面分属不同主题，内核却一致——**都是"在基础结构上叠加一项新能力，并让所有操作维持在可接受的复杂度内"。** 区别只在叠加的能力是什么：LRU 叠加"按访问顺序淘汰"，最小栈叠加"$O(1)$ 查最小值"，单调队列叠加"$O(1)$ 查窗口最值"。

**把这类题归拢成一种"设计模式"，你在遇到新设计题时，就能先问："我要叠加的是什么能力？该用什么辅助结构追踪它？"** 这比逐题记忆有效得多。

## 第 6 章 常见误区与自测方法

### 6.1 四个高频误区

**误区一：最小栈用全局 `minValue` 变量。** 最小值被弹出后无法恢复，必须用辅助栈保存"最小值的完整历史"。

**误区二：压辅助栈的条件用 `<` 而非 `<=`。** 遇到重复的最小值时，辅助栈会提前变空（详见 2.4 节）。

**误区三：用队列模拟栈时，忘记"交换"两个队列。** 方案一、二都依赖"主队列始终是 `q1`"，若不交换，后续操作就会读到辅助队列。

**误区四：`pop` 与 `top` 混淆。** `top` 只读取不移除，`pop` 读取并移除——栈设计题里两者都要实现，不能混用。

### 6.2 一套自测用例

| 用例 | 检验什么 |
|------|---------|
| `push(3), push(3), pop(), getMin()` | 最小栈的等号陷阱 |
| 单调递增入栈 | 辅助栈空间最优（只留一个元素） |
| 空栈后 `empty()` | 空结构边界 |
| `push(1), push(2), top(), pop(), empty()` | 队列模拟栈的操作顺序 |

**其中"重复最小值"用例是必测项**——它是 `<=` 与 `<` 的唯一分野，且只在重复元素出现时才暴露。

## 第 7 章 延伸：增量操作栈与设计题的通用心法

### 7.1 支持增量操作的栈（LeetCode 1381）

**题目**：设计一个支持 `push`、`pop` 与 `increment(k, val)` 的栈。`increment(k, val)` 表示"把栈底开始的 `k` 个元素都加上 `val`"。

**朴素思路**：`increment` 直接遍历栈底 `k` 个元素逐个加——但每次操作是 $O(k)$，若反复调用，总代价可能退化。

**优化思路**：用一个"**懒惰增量**"数组 `add`——不立刻修改元素值，而是把"待加的增量"记在 `add[i]` 上，等到该元素被弹出时才真正结算。具体地，`increment(k, val)` 只需在 `add[min(k, size) - 1]` 上累加 `val`（$O(1)$）；`pop()` 时，把当前栈顶元素的增量"向下传递"给下一个元素，再返回 `值 + 该增量`：

```go
type CustomStack struct {
    data []int
    add  []int // add[i]：当前下标 i 及以下所有元素待加的增量
    cap  int
}

func (s *CustomStack) Push(x int) {
    if len(s.data) == s.cap {
        return // 已满，拒绝
    }
    s.data = append(s.data, x)
    s.add = append(s.add, 0)
}

func (s *CustomStack) Pop() int {
    if len(s.data) == 0 {
        return -1
    }
    i := len(s.data) - 1
    v := s.data[i] + s.add[i] // 结算当前元素的增量
    if i > 0 {
        s.add[i-1] += s.add[i] // 把增量传递给下一个
    }
    s.data = s.data[:i]
    s.add = s.add[:i]
    return v
}

func (s *CustomStack) Increment(k, val int) {
    if len(s.data) == 0 {
        return
    }
    i := min(k, len(s.data)) - 1 // 影响栈底 k 个元素，增量记在"第 k 个"上
    s.add[i] += val
}
```

**这道题的精髓，与最小栈如出一辙——都是"不立刻做，而是记下来，等需要时再结算"。** 区别在于：最小栈的辅助结构记录的是"最小值"，这里记录的是"待加的增量"。**"懒惰"是设计题里一条极常用的思路**（第 03 篇双栈队列的"懒惰搬移"、第 06 篇单调队列的"懒惰删除"也都是它）——**把昂贵的操作推迟到真正必要时才做，是设计题里最有效的省力手段之一。**

### 7.2 设计题的通用心法

把本篇与延伸题的经验归拢，可以得到一套设计题的通用心法：

**心法一，先问"哪个操作必须快"。** 设计题从不要求"所有操作都最优"，而是要求"给定的约束下最优"。先厘清哪些操作有复杂度要求，才能决定把代价放在哪里。

**心法二，单一结构往往不够，答案是"组合体"。** 最小栈 = 主栈 + 辅助栈；增量栈 = 数据栈 + 增量数组；LRU = 哈希表 + 双向链表。**设计题的核心动作，是"为一个新能力匹配合适的辅助结构"。**

**心法三，优先考虑"懒惰"。** 能不立刻做的，就记下来待会儿做。懒惰搬移、懒惰删除、懒惰增量——它们把"频繁的小代价"合并成了"偶发的大代价"，从而在摊还意义下更优。

**心法四，反复确认"对齐"。** 主结构与辅助结构必须同步增减，且不能有一方先空（如最小栈的等号陷阱、LRU 里哈希表与链表必须成对更新）。

> [!note] 四道设计题的统一视角
> 最小栈、增量栈、LRU 缓存（线性表专栏第 13 篇）、单调队列（第 06 篇），表面分属不同主题，内核却一致——**都是"在基础结构上叠加一项新能力，并让所有操作维持在可接受的复杂度内"**。它们的差异，只在"叠加的能力是什么"与"用什么辅助结构追踪它"。**把这类题归拢成一种设计模式，你面对新的设计题时，就有了一个固定的思考起点。**

## 第 8 章 设计题的面试表达与延伸

### 8.1 如何讲清一道设计题

设计题的面试评分，与算法题略有不同——**它更看重"你是否能在需求尚不明确时主动澄清"**。建议的表达顺序是：

1. **先澄清约束**："请问这几个操作里，哪些必须有复杂度要求？比如 `getMin` 是否必须 $O(1)$？"——**主动问清约束，是设计题的第一步，也最能体现工程素养。**
2. **列出朴素方案及其缺陷**："用全局 `min` 变量看似可行，但 `pop` 掉最小值后无法恢复，除非重新扫描。"
3. **给出辅助结构方案**："所以我用一个辅助栈同步保存每个状态的最小值。"
4. **分析代价**："所有操作 $O(1)$，空间最坏 $O(n)$。"
5. **主动指出边界**："这里要用 `<=` 而不是 `<`，否则遇到重复最小值会出错。"

**第 1 步与第 5 步，是设计题区别于算法题的地方**——前者体现"需求意识"，后者体现"边界意识"。

### 8.2 从栈设计到系统设计

最小栈与用队列模拟栈，看起来是"小题目"，但它们的内核——**为一项新能力匹配一个辅助结构**——恰恰是系统设计面试的核心动作。以经典的"设计一个限流器"为例：它的需求是"$O(1)$ 判断某请求是否放行"，辅助结构则可能是"滑动窗口计数器""令牌桶"或"漏桶"——**这与最小栈"为 `getMin` 匹配辅助栈"是同一套思路，只是辅助结构更复杂。**

**换句话说，设计题的"小"，只在它的辅助结构简单；而它的"思维模式"，与系统设计完全同构。** 理解了这一点，你就不会把这两道题当成孤立的技巧，而会把它看作"设计思维"的一次最小演练。

### 8.3 一个值得回味的对照

最小栈与用队列模拟栈，恰好代表了设计题的两个方向：

| 题目 | 设计方向 | 核心动作 |
|------|---------|---------|
| 最小栈 | **增加能力**（在栈上叠加 `getMin`） | 加一个辅助结构追踪派生信息 |
| 用队列模拟栈 | **转换能力**（用 A 结构实现 B 结构） | 用搬移人工制造缺失的能力 |

**"增加能力"靠辅助结构，"转换能力"靠搬移操作**——这两条路，几乎覆盖了所有设计题的解法方向。**当你在面试中拿到一道设计题，先判断它属于哪一类，思路就会清晰很多。**

## 小结

本篇以两道设计题，立起了"主结构 + 辅助结构"这一设计模式。最小栈的难点在于"最小值随栈状态变化"——全局变量只留当前快照，无法回溯历史，于是引入辅助栈保存最小值的完整轨迹；而那个 `<=` 的等号，则是"辅助结构与主结构数量对齐"这一隐性要求的直接体现。用队列模拟栈的三种方案，则从不同角度展示了"用搬移人工制造能力"的思路，并给出"按访问模式选型"的取舍依据。

两道题合起来，给出两条可迁移的经验。其一，**设计题的答案通常是"组合体"**——单一结构往往不够，需要一个辅助结构同步追踪派生信息；其二，**"哪个操作更频繁"决定了把昂贵代价放在哪一端**——这与"没有银弹、因地制宜"的架构观一脉相承。**设计题考的，正是这种"为需求匹配结构、为模式匹配代价"的判断力。**

### 一句话带走

如果只能带走一句话，那就是：**"设计题没有标准答案，只有'匹配约束'的答案。"** 最小栈用"辅助栈"、用队列模拟栈用"搬移"，选择哪条路，取决于"哪个操作更频繁、哪个约束更紧"。**这与架构设计的核心命题一脉相承——没有银弹，只有权衡。** 把设计题当作"架构权衡"的最小演练，你的收获会远超几道题的解法。

下一篇 [[03 队列基础：用栈实现队列与循环队列设计]] 将覆盖队列的对称设计题：LeetCode 232（用栈实现队列）与本篇的 LeetCode 225 形成镜像，并通过摊还分析解释为什么"双栈队列"的摊还时间是 $O(1)$；LeetCode 622（循环队列）则考察用定长数组实现队列时的下标取模技巧，是理解环形缓冲区（Ring Buffer）的绝佳入口。

> [!note] 辅助结构的空间代价，未必是"浪费"
> 最小栈的辅助栈最坏是 $O(n)$，看起来是"双倍空间"。但请想一想：**若不用辅助栈，`getMin` 就必须 $O(n)$ 扫描；用辅助栈，空间 $O(n)$ 换来时间 $O(1)$。** 这笔账在"查询频繁"时是稳赚的。**设计题里几乎每一处"多花空间"，都要用"少花时间"来还——而是否值得，取决于真实场景里"查询多不多"。** 这也是为什么设计题的第一步永远是"澄清哪个操作更频繁"。
