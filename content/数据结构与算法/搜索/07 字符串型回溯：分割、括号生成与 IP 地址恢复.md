# 字符串型回溯：分割、括号生成与 IP 地址恢复

**摘要：**

字符串上的回溯，有一个与"组合/排列"不同的特征——**它的"选择"往往是"切分"或"添加"，而"约束"来自字符串本身的语义**。本文用三道经典题展开：LeetCode 131（分割回文串）讲**分割问题的"指针模型"**，LeetCode 22（括号生成）讲**"合法性前向剪枝"**（用计数保证任意前缀的括号合法），LeetCode 93（复原 IP 地址）讲**"分段约束"**（每段 0-255、无前导零）。三题的共同点是：**回溯的骨架不变，变的是"选择列表"与"合法性判定"。** 全文用 Go 语言实现，并逐层追问：分割问题为什么用"起点指针"、括号生成为什么能"边生成边判断合法性"、以及 IP 恢复的"段数"如何约束搜索。

## 第 1 章 分割问题：指针模型

### 1.1 分割问题的通用形态

**"分割"类问题（如分割回文串、复原 IP、单词拆分）有统一的形态**：

- **状态**：当前分割到了哪个位置（一个"起点指针" `start`）；
- **选择**：从 `start` 开始，切出长度为 1、2、3……的一段；
- **约束**：切出的这段必须满足某种合法性（是回文、是合法 IP 段、在字典中）。

**"起点指针 `start`"是分割问题的标志**——**它把"切分字符串"转化为"从某个位置切一段、递归处理剩余"。**

```go
var dfs func(start int)
dfs = func(start int) {
    if start == len(s) { // 切完了
        记录结果
        return
    }
    for end := start + 1; end <= len(s); end++ {
        segment := s[start:end]
        if !合法(segment) {
            continue // 不合法，跳过
        }
        path = append(path, segment)
        dfs(end) // 从 end 继续
        path = path[:len(path)-1]
    }
}
```

**这个"起点指针 + 枚举终点"的模型，覆盖了所有分割问题。**

## 第 2 章 LeetCode 131：分割回文串

### 2.1 题目

**LeetCode 131 - Palindrome Partitioning**（中等）

给你一个字符串 `s`，请将 `s` 分割成一些子串，使每个子串都是回文串。返回 `s` 所有可能的分割方案。

```text
输入: s = "aab"
输出: [["a","a","b"],["aa","b"]]
```

### 2.2 Go 实现

```go
func partition(s string) [][]string {
    var res [][]string
    var path []string

    var dfs func(start int)
    dfs = func(start int) {
        if start == len(s) {
            tmp := make([]string, len(path))
            copy(tmp, path)
            res = append(res, tmp)
            return
        }
        for end := start + 1; end <= len(s); end++ {
            if !isPalindrome(s, start, end-1) {
                continue // 不是回文，跳过
            }
            path = append(path, s[start:end])
            dfs(end)
            path = path[:len(path)-1]
        }
    }
    dfs(0)
    return res
}

func isPalindrome(s string, l, r int) bool {
    for l < r {
        if s[l] != s[r] {
            return false
        }
        l++
        r--
    }
    return true
}
```

**复杂度**：最坏 $O(n \cdot 2^n)$（每个位置可选"切"或"不切"），是"输出敏感"的。

### 2.3 优化：预处理回文表

**`isPalindrome` 每次 $O(k)$ 判断，可以预处理成 `isPal[i][j]` 表**（$O(n^2)$ 预处理、$O(1)$ 查询）：

```go
// 预处理：isPal[i][j] = s[i..j] 是否回文
isPal := make([][]bool, n)
for i := range isPal {
    isPal[i] = make([]bool, n)
}
for i := n - 1; i >= 0; i-- {
    for j := i; j < n; j++ {
        if s[i] == s[j] && (j-i < 2 || isPal[i+1][j-1]) {
            isPal[i][j] = true
        }
    }
}
```

**这与字符串专栏第 04 篇"回文 DP"完全一致**——**"预处理 + 查询"是"反复判断某性质"的通用优化。**

## 第 3 章 LeetCode 22：括号生成

### 3.1 题目

**LeetCode 22 - Generate Parentheses**（中等）

数字 `n` 代表生成括号的对数，设计函数生成所有可能且有效的括号组合。

```text
输入: n = 3
输出: ["((()))","(()())","(())()","()(())","()()()"]
```

### 3.2 关键：合法性前向剪枝

**这道题的精妙，在于"合法性判定"可以在"生成过程中"完成**——**只需维护两个计数**：

- `open`：已用的左括号数；
- `close`：已用的右括号数。

**合法性约束**：

- **左括号数不超过 `n`**（`open < n` 才能加左括号）；
- **右括号数不超过左括号数**（`close < open` 才能加右括号）——**这保证"任意前缀里，右括号不超过左括号"，即"前缀合法"。**

```go
func generateParenthesis(n int) []string {
    var res []string
    var cur []byte

    var dfs func(open, close int)
    dfs = func(open, close int) {
        if len(cur) == 2*n { // 生成完毕
            res = append(res, string(cur))
            return
        }
        if open < n { // 可以加左括号
            cur = append(cur, '(')
            dfs(open+1, close)
            cur = cur[:len(cur)-1]
        }
        if close < open { // 可以加右括号
            cur = append(cur, ')')
            dfs(open, close+1)
            cur = cur[:len(cur)-1]
        }
    }
    dfs(0, 0)
    return res
}
```

**"前向剪枝"是本题的核心**——**它不生成"非法前缀"，从而避免"生成完再过滤"。** **这把搜索空间从"所有 $2^{2n}$ 种括号串"缩小到了"合法的 Catalan 数种"。**

**`close < open` 这条约束，是"任意前缀合法"的精确表达**——**它保证了"不会出现"右括号多于左括号"的非法前缀"。**

> [!info] 前向剪枝：把"过滤"提前到"生成"
> 朴素做法是"生成所有括号串、再过滤合法的"（$O(2^{2n})$）。**而"前向剪枝"在生成时就保证合法，把搜索空间直接缩小到合法解的数量。** **这是剪枝的最高境界——不是"生成后剪掉"，而是"根本不生成非法的"。** 理解了这一点，你就明白为什么"括号生成"的解法如此优雅。

## 第 4 章 LeetCode 93：复原 IP 地址

### 4.1 题目

**LeetCode 93 - Restore IP Addresses**（中等）

给定一个只包含数字的字符串 `s`，复原它并返回所有可能的有效 IP 地址格式。有效 IP 地址由四个 0-255 的整数组成，以 `.` 分隔。

```text
输入: s = "25525511135"
输出: ["255.255.11.135","255.255.111.35"]
```

### 4.2 思路：分割 + 段数约束

**它就是"分割问题"**——只是多了两个约束：

- **只能切成 4 段**；
- **每段是 0-255 的整数、且无前导零**（`"01"` 不合法，但 `"0"` 合法）。

```go
func restoreIpAddresses(s string) []string {
    var res []string
    var path []string

    var dfs func(start int)
    dfs = func(start int) {
        // 剪枝：段数过多，或剩余字符无法填满/超出
        if len(path) == 4 {
            if start == len(s) {
                res = append(res, strings.Join(path, "."))
            }
            return
        }
        // 剪枝：剩余字符数必须在 [4-len(path), 3*(4-len(path))] 之间
        remainSegs := 4 - len(path)
        if len(s)-start < remainSegs || len(s)-start > 3*remainSegs {
            return
        }
        for end := start + 1; end <= start+3 && end <= len(s); end++ {
            seg := s[start:end]
            if !validSeg(seg) {
                continue
            }
            path = append(path, seg)
            dfs(end)
            path = path[:len(path)-1]
        }
    }
    dfs(0)
    return res
}

func validSeg(seg string) bool {
    if len(seg) > 1 && seg[0] == '0' {
        return false // 前导零
    }
    n := 0
    for i := 0; i < len(seg); i++ {
        n = n*10 + int(seg[i]-'0')
    }
    return n <= 255
}
```

**两处剪枝是本题的精髓**：

- **段数剪枝**：`len(path) == 4` 时不再递归；
- **长度剪枝**：剩余字符数必须在 `[剩余段数, 3×剩余段数]` 之间——**每段 1-3 位，所以"剩余字符太多或太少"都能提前排除。**

**"长度剪枝"是本题最有效的优化**——**它避免了大量"切到后面才发现长度不对"的无效搜索。**

### 4.3 三道题的对照

| 题目 | 选择 | 合法性 | 剪枝 |
|------|------|--------|------|
| LC 131 分割回文串 | 切一段 | 是回文 | 预处理回文表 |
| LC 22 括号生成 | 加 `(` 或 `)` | 前缀合法（计数） | **前向剪枝** |
| LC 93 IP 恢复 | 切 1-3 位 | 0-255、无前导零 | **段数 + 长度剪枝** |

**它们共同说明：字符串型回溯的差异，在"选择列表"与"合法性判定"**——**骨架不变，变的是"切什么"与"什么算合法"。**

## 第 5 章 常见误区与自测方法

### 5.1 四个高频误区

**误区一，分割问题忘了"起点指针 `start`"。** 无法表达"从哪继续切"。

**误区二，括号生成忘了 `close < open` 约束。** 会生成非法括号串。

**误区三，IP 恢复忘了"无前导零"。** `"01"` 会被误判为合法。

**误区四，IP 恢复忘了"段数/长度剪枝"。** 效率低下。

### 5.2 一套自测用例

| 用例 | 检验什么 |
|------|---------|
| `s=""` | 空串 |
| `s="a"` | 单字符 |
| `n=0`（LC 22） | 空结果 |
| `s="0000"`（LC 93） | 全零 |
| `s="111111111111111"`（超长） | 长度剪枝 |

**其中 `"0000"` 最值得测**——它检验"前导零"与"0 合法"的边界（正确答案是 `"0.0.0.0"`）。

## 第 6 章 字符串回溯的更多变体与工程应用

### 6.1 单词拆分（LeetCode 139 / 140）

**题目（139）**：判断字符串 `s` 能否被拆分成字典中的单词。
**题目（140）**：返回所有可能的拆分方案。

**139 是"判断可行性"**——**用"回溯 + 记忆化"（或 DP）**；**140 是"枚举所有方案"**——**用回溯**。

```go
// 140：枚举所有拆分方案
func wordBreak(s string, wordDict []string) []string {
    wordSet := map[string]bool{}
    for _, w := range wordDict {
        wordSet[w] = true
    }
    var res []string
    var path []string
    var dfs func(start int)
    dfs = func(start int) {
        if start == len(s) {
            res = append(res, strings.Join(path, " "))
            return
        }
        for end := start + 1; end <= len(s); end++ {
            seg := s[start:end]
            if wordSet[seg] {
                path = append(path, seg)
                dfs(end)
                path = path[:len(path)-1]
            }
        }
    }
    dfs(0)
    return res
}
```

**139 与 140 的对比，再次说明"求存在用搜索/DP、求全部用回溯"**——**139 用记忆化（因为有重叠子问题），140 用回溯（因为要枚举所有）。**

### 6.2 电话号码的字母组合（LeetCode 17）

**题目**：给定数字串 `"23"`，返回它可能表示的所有字母组合（2→abc、3→def）。

**它就是"组合型回溯"**——**每一层选择"当前数字对应的某个字母"**：

```go
func letterCombinations(digits string) []string {
    if digits == "" {
        return nil
    }
    phone := []string{"", "", "abc", "def", "ghi", "jkl", "mno", "pqrs", "tuv", "wxyz"}
    var res []string
    var path []byte
    var dfs func(idx int)
    dfs = func(idx int) {
        if idx == len(digits) {
            res = append(res, string(path))
            return
        }
        for _, c := range phone[digits[idx]-'0'] {
            path = append(path, byte(c))
            dfs(idx + 1)
            path = path[:len(path)-1]
        }
    }
    dfs(0)
    return res
}
```

**注意"选择列表"是"当前数字对应的字母"**——**这是"组合型回溯"在字符串上的实例。** 它的"层数"由数字串长度决定，"每层的选择"由数字决定。

### 6.3 字母大小写全排列（LeetCode 784）

**题目**：给定字符串，返回所有"字母大小写变换"后的字符串。

**它就是"子集型回溯"**——**每个字母"选大写或小写"**：

```go
func letterCasePermutation(s string) []string {
    var res []string
    b := []byte(s)
    var dfs func(i int)
    dfs = func(i int) {
        if i == len(b) {
            res = append(res, string(b))
            return
        }
        if isLetter(b[i]) {
            b[i] = toLower(b[i])
            dfs(i + 1)
            b[i] = toUpper(b[i])
            dfs(i + 1)
        } else {
            dfs(i + 1)
        }
    }
    dfs(0)
    return res
}
```

**注意这里"做选择"与"撤销"是"就地修改 + 恢复"**——**它展示了"回溯"在字符串上的另一种写法（原地修改字符数组）。**

### 6.4 三道变体的共性

17、784 加上主线的 131、22、93，构成"字符串回溯家族"：

| 题目 | 题型 | 选择 |
|------|------|------|
| LC 131 分割回文串 | 分割 | 切一段（是回文） |
| LC 22 括号生成 | 生成 | 加 `(` 或 `)` |
| LC 93 IP 恢复 | 分割 | 切 1-3 位 |
| LC 17 电话号码 | 组合 | 选一个字母 |
| LC 784 大小写全排列 | 子集 | 大写或小写 |

**它们说明：字符串回溯的"选择"可以是"切分""添加""替换"**——**骨架不变，变的只是"选择是什么"。**

> [!info] 字符串回溯的"选择"很灵活
> 字符串回溯的"选择"非常灵活——**可以是"切一段"（分割）、"加一个字符"（生成）、"选一个字母"（组合）、"改大小写"（子集）。** **但无论选择是什么，骨架都是"做选择、递归、撤销"。** 理解了这一点，你就不会被"选择的花样"迷惑——**抓住骨架，题目就成了填空。**

### 6.5 一个可复用的判断

**遇到"字符串枚举/分割/生成"类问题，按这个顺序问**：

1. **选择是什么？** 切分、添加、还是替换；
2. **合法性如何判定？** 是回文、在字典中、还是前缀合法；
3. **能否前向剪枝？** 如括号生成的计数约束、IP 的长度约束；
4. **有无重叠子问题？** 若有（如单词拆分），考虑记忆化。

**这四问，能定下字符串回溯题的方案。**

## 第 7 章 字符串回溯的面试追问与复杂度速查

### 7.1 五个高频追问

**追问一："分割问题为什么用'起点指针 `start`'？"** 答：**因为它把"切分字符串"转化为"从某位置切一段、递归处理剩余"**——`start` 就是"剩余部分的起点"。

**追问二："括号生成的 `close < open` 为什么等价于'任意前缀合法'？"** 答：**因为"任意前缀里右括号不超过左括号"正是"合法括号串"的定义**——`close < open` 恰好保证了这一点。

**追问三："'前向剪枝'与'生成后过滤'差多少？"** 答：**生成后过滤要枚举 $2^{2n}$ 种括号串；前向剪枝只枚举合法的 Catalan 数种。** 差距是指数级的。

**追问四："IP 恢复的'长度剪枝'为什么有效？"** 答：**每段 1-3 位，所以"剩余字符数"必须在 `[剩余段数, 3×剩余段数]` 之间**——超出即可提前排除。

**追问五："分割问题的复杂度为什么是 $O(n \cdot 2^n)$？"** 答：**因为每个位置可以"切"或"不切"（$2^n$ 种分割），每种分割的代价是 $O(n)$（拼接/判断）。**

### 7.2 复杂度速查

| 题目 | 时间 | 空间 |
|------|------|------|
| LC 131 分割回文串 | $O(n \cdot 2^n)$ | $O(n)$ |
| LC 22 括号生成 | $O(C_n)$（Catalan 数） | $O(n)$ |
| LC 93 IP 恢复 | $O(3^4)$ 级别 | $O(1)$ |
| LC 139 单词拆分 | $O(n^2)$（记忆化） | $O(n)$ |
| LC 140 单词拆分 II | 输出敏感 | $O(n)$ |

**注意"分割问题的复杂度是输出敏感的"**——**若答案有 $k$ 条、每条长 $d$，至少要 $O(kd)$ 输出。**

### 7.3 一个值得养成的习惯

**写字符串回溯题前，先问三句**：

1. **选择是什么？** 切分、添加、还是替换；
2. **合法性如何判定？** 回文、字典、前缀合法、段范围；
3. **能否前向剪枝？** 计数约束、长度约束。

**这三句，能定下字符串回溯题的方案。**

> [!info] 字符串回溯的"三要素"
> 字符串回溯题的差异，可以归结为三要素：**选择（切/加/替换）、合法性判定、剪枝方式。** **把这三要素想清楚，字符串回溯题就成了填空。** 这与组合题"三处旋钮"、矩阵搜索"三要素"是同一思路。

### 7.4 一个总体的建议

**字符串回溯题的练习，建议"按选择方式"分类**：

- **切分**：131、93、139、140；
- **添加**：22、17；
- **替换**：784。

**"选择方式"决定了"合法性判定"与"剪枝方式"。**

## 第 8 章 字符串回溯的技巧总结与工程联系

### 8.1 前向剪枝的三种形式

**字符串回溯的"前向剪枝"，有三种常见形式**：

- **计数约束**（括号生成）：用"左括号数 < n""右括号数 < 左括号数"保证前缀合法；
- **长度约束**（IP 恢复）：用"剩余字符数在 `[剩余段数, 3×剩余段数]`"排除不可能；
- **前缀约束**（Word Search II）：用 Trie 判断"当前路径是否是某单词的前缀"。

**三种形式的共同点，是"用'当前的局部信息'提前判定'这一支无解'"**——**这正是剪枝的本质。**

### 8.2 与正则引擎的联系

**字符串回溯与"正则引擎"有直接联系**——**回溯引擎（PCRE、Java、Python 的 `re`）匹配正则时，用的就是"回溯"。**

**例如匹配 `a*ab` 时，引擎会先让 `a*` 尽可能多地匹配 `a`，若后面匹配失败，就"回溯"、让 `a*` 少匹配一个。** **这正是"做选择、探索、撤销"这一回溯模式。**

**理解了这一点，你就明白为什么"正则可能指数回溯（ReDoS）"**——**因为回溯的搜索空间可能指数级。** **而"自动机引擎（RE2）"之所以能保证线性，是因为它不回溯、而是"同时推进所有可能"。**

### 8.3 与 AC 自动机的联系

**"多模式匹配"（如敏感词过滤）用 AC 自动机**——**它是"Trie + 失配指针"，本质是"把 KMP 的思想搬到 Trie 上"。**

**AC 自动机与"Word Search II 的 Trie + DFS"是同一思路的不同应用**：

- **Word Search II**：在"矩阵"上，用 Trie 剪枝做多模式匹配；
- **AC 自动机**：在"文本"上，用 Trie + 失配指针做多模式匹配。

**它们共享"用 Trie 共享前缀、一次搜索匹配多个模式"这一思想。**

### 8.4 一个值得记住的对照

| 技术 | 场景 | 核心 |
|------|------|------|
| 计数约束 | 括号生成 | 前缀合法 |
| 长度约束 | IP 恢复 | 剩余字符范围 |
| Trie 剪枝 | Word Search II | 前缀共享 |
| AC 自动机 | 敏感词过滤 | Trie + 失配指针 |
| 回溯引擎 | 正则匹配 | 做选择-撤销 |

**这张表说明："字符串回溯"与"字符串匹配"是相通的**——**它们都在"字符串空间"里搜索，只是"剪枝方式"与"是否回溯"不同。**

> [!info] 从"回溯"到"字符串匹配"
> 字符串回溯与字符串匹配（KMP、AC 自动机、正则引擎）是相通的——**它们都在"字符串空间"里搜索。** **理解了这一联系，你就把"搜索专栏"与"字符串专栏"打通了**——**它们共享"在字符串空间里找解"这一内核。**

### 8.5 一个可复用的判断

**遇到"字符串匹配/枚举"类问题，按这个顺序问**：

1. **单模式还是多模式？** 单模式用 KMP/回溯，多模式用 Trie/AC；
2. **要枚举所有匹配还是判断存在？** 枚举用回溯，存在用 KMP；
3. **能否前向剪枝？** 计数、长度、前缀三种约束；
4. **有无重叠子问题？** 有则考虑记忆化。

**这四问，能定下字符串匹配/枚举题的方案。**

## 第 9 章 从字符串回溯到解析器：一次推广

### 9.1 分割问题与"分词"

**分割问题（LC 131、93、139）本质上都是"分词"**——**把字符串切成若干"合法单元"。**

**"分词"是自然语言处理（NLP）的基础任务**——**中文分词、英文分词，都是"把一串字符切成词"。** **而"单词拆分"（LC 139）就是"用给定词典分词"的最简模型。**

**"分词"的通用方法是"动态规划 + 词典查询"**——**与 LC 139 的"记忆化搜索"完全一致。** **理解了这一点，你就把"分割问题"与"NLP 分词"联系了起来。**

### 9.2 分割问题与"语法分析"

**更一般地，分割问题是"语法分析（Parsing）"的最简形式**——**语法分析要"把 token 序列组织成语法树"，本质上也是"分割 + 递归"。**

**例如"括号匹配"是"语法分析"的简化版**——**它用栈判断"括号是否配对"**（栈与队列专栏第 01 篇）。**而"括号生成"（LC 22）是它的"生成版"**——**用回溯生成所有合法的括号串。**

**"生成"与"分析"是一对逆操作**——**一个"从结构到字符串"，一个"从字符串到结构"。** **这与字符串专栏"重建 vs 序列化"是同一对逆操作。**

### 9.3 回溯与"递归下降解析"

**编译器的"递归下降解析（Recursive Descent Parsing）"是回溯的直接应用**——**它为每个语法规则写一个函数，函数内部"尝试匹配"、失败则"回溯"。**

**例如解析表达式时，"尝试匹配一个项、失败则尝试另一个规则"**——**这正是"做选择、探索、撤销"这一回溯模式。**

**"递归下降"是最直观的解析方法**——**它的"可读性"远高于"自动机生成"，代价是"可能回溯爆炸"**（与正则的回溯引擎同理）。

### 9.4 一个值得记住的对照

| 任务 | 方法 | 与回溯的关系 |
|------|------|-------------|
| 单词拆分 | DP / 记忆化 | 分割 + 缓存 |
| 括号生成 | 回溯 | 生成 + 前向剪枝 |
| 括号匹配 | 栈 | 分析（非回溯） |
| 递归下降解析 | 回溯 | 直接应用 |
| 正则匹配 | 回溯引擎 | 直接应用 |

**这张表说明："字符串回溯"是"解析"这一大类问题的核心**——**从分词到语法分析，从正则到编译器，都用到"分割 + 递归 + 撤销"。**

> [!info] 从"字符串回溯"到"解析"
> 字符串回溯不是孤立的算法——**它是"解析（Parsing）"这一大类问题的核心**，从 NLP 分词到编译器语法分析，都用到它。**理解了这一点，你就把"字符串回溯"上升成了"解析"这一通用能力。** 这是本专栏"从具体到抽象"的又一次体现。

### 9.5 一个可复用的判断

**遇到"字符串解析/分割"类问题，按这个顺序问**：

1. **是"生成"还是"分析"？** 生成用回溯，分析可能用栈/自动机；
2. **单元的合法性如何判定？** 回文、词典、括号配对；
3. **能否前向剪枝？** 计数、长度、前缀；
4. **有无重叠子问题？** 有则用记忆化。

**这四问，能定下字符串解析/分割题的方案。**

## 第 10 章 字符串回溯的工程应用

### 10.1 模板引擎

**模板引擎（如 Jinja2、Mustache）的"解析"用到字符串回溯**——**它要"识别模板语法（`{{ }}`、`{% %}`），并把它与普通文本分开"。**

**这本质上是"分割问题"**——**把模板字符串切成"文本段"与"表达式段"。** **而"递归处理嵌套结构（如 `{% if %}` 的嵌套）"，则用到回溯。**

### 10.2 配置展开

**"配置展开"用到字符串回溯**——**如"环境变量替换"（`${VAR}`）、"通配符展开"（`*.txt`）。**

**"通配符展开"本质上是"字符串匹配"**——**它用"回溯"或"DP"匹配 `*`、`?`（字符串专栏第 05 篇）。** **而"变量替换"则要"识别 `${...}` 并替换"，是分割问题的变体。**

### 10.3 SQL 与表达式解析

**SQL 解析、表达式求值，用到"分割 + 递归"**——**它们要"把 SQL 语句切成 token，再组织成语法树"。**

**"表达式求值"（LC 224、227）用"栈"处理优先级**（栈与队列专栏第 07 篇）——**但"更一般的表达式解析"（含函数调用、嵌套括号）则需要"递归下降"（回溯）。**

### 10.4 一个值得记住的对照

| 应用 | 与字符串回溯的关系 |
|------|-------------------|
| 模板引擎 | 分割（文本段 vs 表达式段） |
| 环境变量替换 | 分割（识别 `${...}`） |
| 通配符展开 | 字符串匹配（回溯/DP） |
| SQL 解析 | 分割 + 递归 |
| 表达式求值 | 栈 / 递归下降 |

**这张表说明："字符串回溯"是"文本处理"的通用工具**——**从模板到 SQL，都用到它。**

## 第 12 章 一句话总结

**如果只能从本篇带走一句话，那就是：**"字符串回溯的差异，在'选择列表'与'合法性判定'——骨架不变，变的是'切什么'与'什么算合法'。"

**而"前向剪枝"是字符串回溯的核心优化**——**它在生成时就保证合法，把搜索空间直接缩小到合法解的数量。**

> **"选择（切/加/替换）+ 合法性判定 + 前向剪枝。"** 记住这一句，你面对任何字符串回溯题，都能快速定下方案。**而"前向剪枝"比"生成后过滤"更强——它在生成时就保证合法。**

## 小结

本篇用三道题讲清了字符串型回溯：**分割问题的"起点指针"模型（131、93）** 与 **"前向剪枝"（22）**。三题的骨架一致，差异只在"选择列表"与"合法性判定"。

贯穿全篇的核心认知有两条。其一，**分割问题的通用形态是"起点指针 + 枚举终点"**——它把"切分字符串"转化为"从某位置切一段、递归剩余"。其二，**"前向剪枝"比"生成后过滤"更强**——它在生成时就保证合法，把搜索空间直接缩小到合法解的数量。**把这两条握住，你面对任何分割/生成类字符串题，都有了实现的起点。**

**最后补充一点落点。** 字符串回溯是"解析（Parsing）"这一大类问题的核心——**从 NLP 分词到编译器语法分析，都用到"分割 + 递归 + 撤销"。** 而"前向剪枝"则是它的灵魂——**它在生成时就保证合法，把搜索空间直接缩小到合法解的数量。** 理解了这两点，你不仅会解字符串回溯题，也能理解"解析器"这一工程组件的思路。

**再补充一点。** 字符串回溯的"选择"很灵活——**切分、添加、替换，都是"选择"的形态。** 但无论选择是什么，骨架都是"做选择、递归、撤销"。**理解了这一点，你就不会被"选择的花样"迷惑——抓住骨架，题目就成了填空。**

**再补充最后一点。** 字符串回溯的"起点指针"模型（分割问题）与组合题的"`start`"参数，本质是同一件事——**都是"规定一个起点，避免重复枚举"。** 区别只在"起点是'字符位置'还是'数组下标'"。**理解了这一点，你就把"分割"与"组合"统一了起来。** 而"合法性判定"则是它们的分野——**组合只要求"不重复"，分割还要求"每段合法"。** **这一分野，正是字符串回溯比组合题"多一层"的地方。**
