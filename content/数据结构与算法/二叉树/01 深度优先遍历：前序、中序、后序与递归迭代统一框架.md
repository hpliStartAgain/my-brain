# 深度优先遍历：前序、中序、后序与递归迭代统一框架

**摘要：**

二叉树专题真正的起点，不是"会背三种遍历顺序"，而是理解一件更本质的事：**递归进入一个节点时，天然存在三个可以处理它的时机**——进入左子树之前、左子树处理完但右子树未开始、左右子树都处理完之后。前序、中序、后序，不过是"在这三个时机中选择一个"的结果。想清楚这一点，三种遍历就不再是需要记忆的规则，而是同一段骨架的三种填法。本文从这一视角出发，用 Go 语言完整实现 LeetCode 144、94、145 的递归与迭代两种写法，并解释迭代写法为什么容易乱、如何用"系统栈的显式化"这一视角理顺它；随后给出一套"函数该定义什么"的通用框架，并补充 $O(1)$ 空间的 Morris 遍历。这套框架会一路迁移到后面的二叉搜索树、树形 DP 与路径问题。

---

## 第 1 章 为什么遍历顺序不是死记硬背

### 1.1 一个节点天然有三个处理时机

对任意节点 `root`，递归函数的骨架天然长这样：

```go
func dfs(node *TreeNode) {
    if node == nil {
        return
    }
    // 时机 A：进入左子树之前
    dfs(node.Left)
    // 时机 B：左子树处理完、右子树开始前
    dfs(node.Right)
    // 时机 C：左右子树都处理完之后
}
```

这三个时机，正好对应三种遍历：

| 遍历 | 处理当前节点的时机 | 典型用途 |
|------|-------------------|----------|
| 前序 | 进入左子树之前（时机 A） | 复制树、序列化、记录根到节点的路径 |
| 中序 | 左子树后、右子树前（时机 B） | 二叉搜索树的有序遍历 |
| 后序 | 左右子树都结束后（时机 C） | 汇总左右子树信息、树形 DP、删除树 |

**所以遍历顺序的本质不是"三个词"，而是"节点在哪个时机被处理"。** 只要这个语义想清楚，后面绝大多数树题都不再需要记模板——你只需问自己"我需要在这三个时机中的哪一个处理当前节点"。

### 1.2 为什么树题天然适合递归

因为**树本身就是递归定义的**：一棵树由根节点、左子树、右子树组成。你在根节点看到的结构，和你在左子树、右子树里看到的结构是同构的——**同一个函数既能解决整棵树，也能解决任意一棵子树。**

> [!info] 递归的关键不是"自己调自己"
> 很多人把递归理解成"函数调用自身"，于是写起来患得患失。**真正关键的，是函数的输入与输出在子问题上保持同样的语义**——只要"`dfs(node)` 能正确处理以 `node` 为根的子树"这一承诺成立，递归就成立。至于函数体内部怎么实现，是它自己的事。**这种"先相信子问题已被解决、再处理当前层"的思维方式，是写对递归的唯一诀窍。**

## 第 2 章 三种递归遍历

先把节点定义写出来（LeetCode 的标准定义，后文不再重复）：

```go
type TreeNode struct {
    Val   int
    Left  *TreeNode
    Right *TreeNode
}
```

### 2.1 LeetCode 144：前序遍历（根 → 左 → 右）

```go
func preorderTraversal(root *TreeNode) []int {
    var res []int
    var dfs func(node *TreeNode)
    dfs = func(node *TreeNode) {
        if node == nil {
            return
        }
        res = append(res, node.Val) // 时机 A：先处理自己
        dfs(node.Left)
        dfs(node.Right)
    }
    dfs(root)
    return res
}
```

前序适合"先处理当前节点，再把状态带给子节点"的场景：记录根到当前节点的路径前缀、构造序列化字符串、复制节点并继续复制左右子树。

### 2.2 LeetCode 94：中序遍历（左 → 根 → 右）

```go
func inorderTraversal(root *TreeNode) []int {
    var res []int
    var dfs func(node *TreeNode)
    dfs = func(node *TreeNode) {
        if node == nil {
            return
        }
        dfs(node.Left)
        res = append(res, node.Val) // 时机 B：左子树之后
        dfs(node.Right)
    }
    dfs(root)
    return res
}
```

**中序最重要的价值在于：对二叉搜索树（BST）而言，中序遍历会产生一个严格递增的序列。** 后面的 Validate BST、Recover BST，以及大量搜索树题，全都依赖这一性质——**它是把"树"降维成"有序序列"的那把钥匙。**

### 2.3 LeetCode 145：后序遍历（左 → 右 → 根）

```go
func postorderTraversal(root *TreeNode) []int {
    var res []int
    var dfs func(node *TreeNode)
    dfs = func(node *TreeNode) {
        if node == nil {
            return
        }
        dfs(node.Left)
        dfs(node.Right)
        res = append(res, node.Val) // 时机 C：左右都处理完
    }
    dfs(root)
    return res
}
```

后序适合"当前节点的答案依赖左右子树答案"的场景：平衡二叉树的高度计算、二叉树中的最大路径和、树的删除与释放。**凡是"要先知道左右子树的结果、才能决定当前节点怎么处理"的问题，后序都是首选。**

## 第 3 章 迭代写法为什么容易乱

### 3.1 递归的本质是系统栈

递归并不神秘，它只是把"下一步去左子树还是右子树、回来之后该做什么"这些**控制流信息**交给了系统调用栈保存。**改写成迭代，本质上就是你自己维护这个栈**——所以迭代写法的难点，从来不是"用栈"，而是"把递归里隐式的控制流，显式地表达出来"。

**想通这一点，迭代写法就不再是"另一套需要背的代码"，而是"把递归翻译一遍"。** 翻译的过程中，哪一步该压栈、哪一步该弹栈，都会变得有迹可循。

### 3.2 前序遍历的迭代写法

前序的逻辑最自然：弹出节点就访问，然后把右孩子、左孩子依次压栈。**之所以先压右、再压左，是因为栈后进先出——左孩子后压，所以先被处理**，从而满足"根 → 左 → 右"的顺序。

```go
func preorderTraversalIter(root *TreeNode) []int {
    var res []int
    if root == nil {
        return res
    }
    stack := []*TreeNode{root}
    for len(stack) > 0 {
        node := stack[len(stack)-1]
        stack = stack[:len(stack)-1]
        res = append(res, node.Val)
        if node.Right != nil { // 先压右
            stack = append(stack, node.Right)
        }
        if node.Left != nil { // 后压左，故左先出
            stack = append(stack, node.Left)
        }
    }
    return res
}
```

### 3.3 中序遍历的迭代写法

中序的难点是：**节点不能在第一次遇到时立刻访问**，必须一路向左下钻，直到左子树为空，再开始回退。

```go
func inorderTraversalIter(root *TreeNode) []int {
    var res []int
    stack := []*TreeNode{}
    current := root

    for current != nil || len(stack) > 0 {
        // 一路向左，把沿途节点压栈（它们尚未访问）
        for current != nil {
            stack = append(stack, current)
            current = current.Left
        }
        // 左边到底了，弹出并访问，再转向右子树
        current = stack[len(stack)-1]
        stack = stack[:len(stack)-1]
        res = append(res, current.Val)
        current = current.Right
    }
    return res
}
```

**这里的核心不是代码，而是两个变量的状态语义**：`current` 负责"持续向左推进"，`stack` 保存"还没访问、但左边已处理完、需要回来访问的节点"。**把这两个语义说清楚，中序迭代就不再"绕"。**

### 3.4 后序遍历的迭代写法

后序最难，因为节点必须在左右子树**都**处理完之后才能访问。常见写法有两种：**双栈法**（一个栈做遍历、一个栈反转输出）与**单栈 + `prev` 指针**（判断右子树是否访问过）。面试中推荐先讲双栈法，逻辑更直白。

```go
func postorderTraversalIter(root *TreeNode) []int {
    var res []int
    if root == nil {
        return res
    }
    stack1 := []*TreeNode{root}
    var stack2 []*TreeNode

    for len(stack1) > 0 {
        node := stack1[len(stack1)-1]
        stack1 = stack1[:len(stack1)-1]
        stack2 = append(stack2, node) // 记录访问顺序
        if node.Left != nil {
            stack1 = append(stack1, node.Left)
        }
        if node.Right != nil {
            stack1 = append(stack1, node.Right)
        }
    }
    // stack2 里是"根-右-左"的顺序，反转即得"左-右-根"
    for i := len(stack2) - 1; i >= 0; i-- {
        res = append(res, stack2[i].Val)
    }
    return res
}
```

**为什么可行？** 因为第一个栈产生的访问顺序是"根 → 右 → 左"（先压左、后压右，右先出），而把它整体反转，正好就是"左 → 右 → 根"——正是后序。**"正序的逆序等于逆序的正序"，这个对称性是双栈法的全部依据。**

## 第 4 章 一个统一视角：递归函数到底该定义什么

很多人学树题越学越乱，是因为把"遍历顺序"和"函数返回值"混为一谈。更稳的做法，是先问两个问题：

1. **这道题要求我在遍历过程中收集什么？**（决定是否用全局变量/闭包累积）
2. **当前函数要不要给父节点返回信息？**（决定返回值的类型与语义）

- 若只是"遍历收集序列"，返回值可以是"无"（用闭包累积即可）；
- 若父节点需要子树高度、子树是否合法、对子树的最大贡献值，那**返回值就必须承载这些信息**。

> [!note] 遍历顺序只决定"什么时候处理当前节点"
> **函数返回值决定"你要把什么带回给父节点"。** 这是所有树题最重要的一层抽象——很多人写不对树题，正是因为把这两件事搅在了一起：既想用遍历顺序解决问题，又想让返回值自动带出答案。**把它们分开，问题立刻清晰。**

**用一个具体例子说明**：求"二叉树的最大深度"。遍历顺序上，它天然是后序（要先知道左右子树深度）；返回值上，它需要"以当前节点为根的子树深度"这一信息返回给父节点。**两个问题分开答，代码骨架就定了**：

```go
func maxDepth(root *TreeNode) int {
    if root == nil {
        return 0
    }
    left := maxDepth(root.Left)
    right := maxDepth(root.Right)
    return max(left, right) + 1 // 后序 + 返回值承载"子树深度"
}
```

**这道题正是"后序 + 返回值汇总"的最小模型**——本专栏后面的平衡树、最大路径和、路径求和，全都是它的放大版。

## 第 5 章 延伸：Morris 遍历（$O(1)$ 空间的中序）

三种迭代写法都需要 $O(n)$ 的栈空间。有没有可能把空间压到 $O(1)$？答案是 **Morris 遍历**——它利用树中大量空闲的右指针（叶节点的 `Right` 为 `nil`），把它们临时"借"来指向中序后继，从而在遍历中"记住回去的路"，无需任何栈。

**Morris 中序的核心思路**：对当前节点 `cur`，若它有左子树，就找到左子树中序下的"最右节点"（前驱），把它的 `Right` 临时指向 `cur`（建立"线索"）；处理完左子树后，再靠这条线索回到 `cur`、断开线索、转向右子树。若 `cur` 没有左子树，直接访问它并转向右子树。

```go
func inorderMorris(root *TreeNode) []int {
    var res []int
    cur := root
    for cur != nil {
        if cur.Left == nil {
            res = append(res, cur.Val) // 无左子树，直接访问
            cur = cur.Right
        } else {
            // 找左子树的最右节点（中序前驱）
            prev := cur.Left
            for prev.Right != nil && prev.Right != cur {
                prev = prev.Right
            }
            if prev.Right == nil {
                prev.Right = cur // 建立线索，指向中序后继
                cur = cur.Left
            } else {
                prev.Right = nil            // 断开线索，恢复原结构
                res = append(res, cur.Val) // 左子树已处理完，访问 cur
                cur = cur.Right
            }
        }
    }
    return res
}
```

**Morris 遍历的时间是 $O(n)$、空间 $O(1)$**（线索的建立与断开各一次，均摊到每个节点是常数）。它的价值在于展示一个重要的思想：**当"递归/栈"需要额外空间时，有时可以把"回去的路"藏进数据结构本身**——这与线性表专栏第 07 篇"用第一行第一列当标记"的就地技巧是同一种精神：**用数据自身承载元数据，从而省掉辅助结构。**

> [!info] Morris 要不要掌握
> Morris 遍历在面试中出现的频率不高，但**"能否把中序遍历的空间压到 $O(1)$"是一个常见的追问**。理解它的思想（借右指针当线索）比背下代码更重要——它提醒你：**"需要栈"这件事，有时是问题结构决定的，有时只是"常规实现"的惯性。**

## 第 6 章 延伸：遍历的三大应用

三种遍历不只是"输出顺序"，它们是三类实际问题的引擎。本章用三道题展示遍历在真实题目里的用法。

### 6.1 序列化与反序列化（LeetCode 297）

**题目**：设计一个算法，将二叉树序列化为一个字符串，并能将字符串反序列化回原树。

**前序遍历 + 空标记**是最简洁的方案：前序负责"记录结构"，用 `#`（或 `null`）标记空节点，从而让序列唯一可还原。

```go
type Codec struct{}

func (Codec) serialize(root *TreeNode) string {
    var sb []string
    var dfs func(node *TreeNode)
    dfs = func(node *TreeNode) {
        if node == nil {
            sb = append(sb, "#") // 空节点也要记录，否则结构丢失
            return
        }
        sb = append(sb, strconv.Itoa(node.Val))
        dfs(node.Left)
        dfs(node.Right)
    }
    dfs(root)
    return strings.Join(sb, ",")
}

func (Codec) deserialize(data string) *TreeNode {
    parts := strings.Split(data, ",")
    i := 0
    var build func() *TreeNode
    build = func() *TreeNode {
        if parts[i] == "#" {
            i++
            return nil
        }
        val, _ := strconv.Atoi(parts[i])
        i++
        node := &TreeNode{Val: val}
        node.Left = build()
        node.Right = build()
        return node
    }
    return build()
}
```

**为什么空节点也必须记录？** 因为若只记录非空节点，`[1,2]` 与 `[1,null,2]` 会得到相同的序列（都是 `1,2`），无法区分。**加上 `#` 标记，序列才能唯一地编码结构。** 这又一次印证了第 03 篇的那句话：**在树结构问题里，`nil` 本身就是一种信息。**

### 6.2 二叉树的垂序遍历（LeetCode 987）

**题目**：按列（列号从左到右）返回节点的值；同一列内按行（从上到下）排序，同行按值排序。

**这道题的关键是"给每个节点一个坐标"**：以根为 `(row=0, col=0)`，左孩子 `col-1`、右孩子 `col+1`。用一次 DFS 收集 `(col, row, val)`，再排序输出即可：

```go
func verticalTraversal(root *TreeNode) [][]int {
    type item struct{ col, row, val int }
    var items []item
    var dfs func(node *TreeNode, row, col int)
    dfs = func(node *TreeNode, row, col int) {
        if node == nil {
            return
        }
        items = append(items, item{col, row, node.Val})
        dfs(node.Left, row+1, col-1)
        dfs(node.Right, row+1, col+1)
    }
    dfs(root, 0, 0)
    // 排序：先列、再行、再值
    sort.Slice(items, func(i, j int) bool {
        if items[i].col != items[j].col {
            return items[i].col < items[j].col
        }
        if items[i].row != items[j].row {
            return items[i].row < items[j].row
        }
        return items[i].val < items[j].val
    })
    // 按列分组
    var res [][]int
    for i := 0; i < len(items); {
        j := i
        for j < len(items) && items[j].col == items[i].col {
            j++
        }
        col := make([]int, 0, j-i)
        for k := i; k < j; k++ {
            col = append(col, items[k].val)
        }
        res = append(res, col)
        i = j
    }
    return res
}
```

**这道题的启示是"给节点附上坐标，把树问题转成排序问题"**——一旦每个节点有了 `(row, col)`，垂序遍历就退化成"按坐标排序"。**这与第 07 篇矩阵专题"用 `i+j` 等坐标不变量处理对角线"是同一思路：给元素附上合适的坐标，几何/结构关系就变成了数值关系。**

### 6.3 统计好节点的数目（LeetCode 1448）

**题目**：根到某节点的路径上，若没有节点的值比它大，则它是"好节点"。求好节点的数目。

**这是"前序携带状态"的典型**——沿途维护"路径上的最大值"，每到一个节点就判断它是否不小于该最大值：

```go
func goodNodes(root *TreeNode) int {
    var dfs func(node *TreeNode, maxSoFar int) int
    dfs = func(node *TreeNode, maxSoFar int) int {
        if node == nil {
            return 0
        }
        count := 0
        if node.Val >= maxSoFar { // 不小于路径上最大值，是好节点
            count = 1
            maxSoFar = node.Val // 更新最大值
        }
        return count + dfs(node.Left, maxSoFar) + dfs(node.Right, maxSoFar)
    }
    return dfs(root, math.MinInt32)
}
```

**注意这里用的是"前序携带状态"**：进入节点时判断、并把更新后的状态传给子节点。**它与第 10 篇的路径总和是同一模式**——都是"沿路径向下携带一个状态，在节点处结算"。**区别只在状态是什么（最大值 vs 剩余和）。**

### 6.4 三道延伸题的共性

三道题分别展示了遍历的三种用法：**序列化**用前序 + 空标记编码结构，**垂序遍历**用 DFS 附坐标再排序，**好节点计数**用前序携带路径状态。**它们共同说明：三种遍历不只是"输出顺序"，而是"在特定时机做特定事"的引擎。** 选哪种遍历，取决于"你要在哪个时机做事"——这正是第 1 章那三个"处理时机"的实际价值。

## 第 7 章 常见误区与自测方法

### 7.1 四个高频误区

**误区一：把遍历顺序当成"三套独立的模板"去背。** 它们本是同一段骨架的三个时机，理解"时机"就不会记混。

**误区二：中序迭代的两个变量语义不清。** `current` 是"向左推进的游标"，`stack` 是"待回来访问的节点"——混用就会写出死循环。

**误区三：前序迭代压栈顺序反了。** 必须先压右、后压左，才能让左先出栈。

**误区四：后序迭代忘了"反转"。** 双栈法产生的顺序是"根-右-左"，必须反转才是后序。

### 7.2 一套自测用例

| 用例 | 检验什么 |
|------|---------|
| `nil`（空树） | 空指针边界 |
| 单节点 `[1]` | 最简情形 |
| 只有左链 `[1,2,null,3]` | 单边深链 |
| 只有右链 `[1,null,2,null,3]` | 单边深链（另一侧） |
| 完全二叉树 `[1,2,3,4,5,6,7]` | 常规情形 |

**其中"单边深链"最值得测**——它把递归/迭代在"一条路走到黑"时的行为压到极致，是检验"栈是否会被压空/压满"的最好用例。**凡是遍历题，先用一条左链和一条右链各测一遍，能拦下大量边界 bug。**

## 第 8 章 遍历的性能与工程考量

遍历题看起来"简单"，但一旦进入工程语境，"递归还是迭代""要不要 Morris"这些问题就会变得具体。本章把几种写法的**性能与适用边界**讲清楚。

### 8.1 递归与迭代：常数因子与调用栈

递归写法代码短、语义清晰，但它有一个常被忽视的代价——**函数调用的开销**。每次递归调用都要保存返回地址、局部变量、寄存器现场，这些开销在"访问每个节点"这种高频操作上会累积起来。迭代写法把这部分开销显式化成了"对栈的 push/pop"，通常常数更小。

但更重要的是**调用栈的深度**。递归的空间复杂度是 $O(h)$（$h$ 为树高），而这个 $h$ **在最坏情况下等于节点数 $n$**（树退化成链时）。这意味着：**对一棵退化成链的树（例如按有序顺序插入 BST 得到的树），递归遍历会占用 $O(n)$ 的栈空间，可能触发栈溢出。** 而迭代写法用的是堆上的显式栈，容量受限于可用内存，通常更安全。

**所以，工程上选择递归还是迭代，往往取决于"输入是否可能很深"**：深度可控（如平衡树）时递归足够优雅；深度不可控（如用户输入构造的树）时，迭代更稳妥。**这与栈与队列专栏第 07 篇"递归还是显式栈"的取舍是同一条判断。**

### 8.2 尾递归：一种"看起来能省栈"的优化

中序遍历有一种"尾递归"式的写法（把待处理节点作为参数传递），理论上编译器可以优化掉栈帧。**但 Go 编译器并不做尾递归优化**，所以写出来仍是 $O(h)$ 空间。**这一点值得注意：不要想当然地认为"尾递归能省栈"——它取决于语言与编译器的支持。** Java、Go 都不做通用尾调用优化；只有部分函数式语言（如 Scheme）会保证。

### 8.3 Morris 的适用边界

Morris 遍历用 $O(1)$ 空间换来了"临时修改树结构"这一代价——它会在遍历过程中**把叶节点的右指针临时指向中序后继**，遍历完再恢复。**这带来两条边界**：

- **多线程不安全**：若遍历过程中有别的线程在读这棵树，它会看到"被临时修改过"的结构；
- **不适合"只读"语义**：如果调用方期望"遍历不改变树"，Morris 就违反了这一约定。

**所以 Morris 是一种"用可变性换空间"的技巧，它适合"独占访问 + 空间敏感"的场景，不适合"共享只读"的场景。** 理解这一点，你就明白为什么它虽优雅，却很少出现在工程代码里——**工程系统往往宁可多花 $O(h)$ 的栈空间，也不愿承担"临时改结构"带来的并发风险。**

### 8.4 三种写法的选择

把三种写法的取舍汇总成一张表：

| 写法 | 空间 | 是否改结构 | 适用场景 |
|------|------|-----------|---------|
| 递归 | $O(h)$（栈） | 否 | 深度可控、追求可读性 |
| 迭代（显式栈） | $O(h)$（堆） | 否 | 深度不可控、追求稳健 |
| Morris | $O(1)$ | **是**（临时） | 空间敏感 + 独占访问 |

**这张表的落点，仍是那句反复出现的话：没有最优写法，只有最匹配约束的写法。** 面试中若被追问"能否 $O(1)$ 空间"，Morris 是加分项；但若能主动说出"Morris 会临时改结构、并发下不安全"，则更能体现工程素养。

> [!info] 从"会写"到"会选"
> 学遍历的初期，目标是"三种遍历都能写对"；进阶的目标，则是"**知道在什么场景该选哪种写法**"。**前者考的是记忆与熟练，后者考的是判断与权衡。** 本篇花了大量篇幅讲迭代的"为什么容易乱"、Morris 的"适用边界"，正是为了帮你从"会写"跨到"会选"——**而这，恰恰是面试里区分"熟练"与"优秀"的地方。**

## 第 9 章 从二叉树推广：N 叉树的遍历

二叉树遍历的三种"处理时机"，可以无损地推广到 N 叉树——**这恰好验证了"遍历的本质是处理时机，而非固定的左右结构"这一论断。**

对 N 叉树节点 `{Val, Children []*NNode}`，前序与后序的写法是：

```go
// N 叉树前序：先处理自己，再依次处理每个孩子
func preorderN(root *NNode) []int {
    var res []int
    var dfs func(node *NNode)
    dfs = func(node *NNode) {
        if node == nil {
            return
        }
        res = append(res, node.Val) // 时机 A
        for _, c := range node.Children {
            dfs(c)
        }
    }
    dfs(root)
    return res
}

// N 叉树后序：先依次处理每个孩子，再处理自己
func postorderN(root *NNode) []int {
    var res []int
    var dfs func(node *NNode)
    dfs = func(node *NNode) {
        if node == nil {
            return
        }
        for _, c := range node.Children {
            dfs(c)
        }
        res = append(res, node.Val) // 时机 C
    }
    dfs(root)
    return res
}
```

**注意 N 叉树没有"中序"**——因为"中序"依赖"左、根、右"这一三段结构，而 N 叉树的"根"没有唯一的"中间位置"。**这从反面印证了第 1 章的论断：三种遍历不是"三个固定的词"，而是"三个处理时机"；当结构变化（孩子从一个变多个）时，"时机"仍在，但"中序"这一特定填法失去了意义。**

**更一般地，N 叉树的遍历骨架与二叉树完全同构**——"处理当前节点"与"递归处理孩子"两个动作，只是"孩子的数量"从 2 变成了 `len(Children)`。**这解释了为什么学会了二叉树遍历，就能立刻写出 N 叉树、乃至一般图（用 visited 标记）的遍历——因为它们共享同一个"访问 + 递归"的骨架。**

> [!note] 一个可迁移的视角
> "遍历 = 在某个时机处理节点 + 递归处理孩子"——这个视角可以一路推广：N 叉树（孩子变多）、图（加 visited 防环）、状态空间搜索（加状态去重）。**它们都不是"新算法"，而是同一个骨架在不同结构上的实例。** 本专栏后面（搜索专栏）会把这个骨架推广到图与状态空间；理解了它，你就抓住了"遍历类算法"的统一形态。

## 第 10 章 遍历题的面试表达与追问

### 10.1 表达套路

被要求手写某种遍历时，建议这样组织：

1. **先声明"处理时机"**："中序是'左子树之后、右子树之前'处理当前节点。"
2. **给递归骨架**："`dfs(node)` 里先递归左、再处理、再递归右。"
3. **给迭代骨架**："迭代版用栈模拟系统栈，中序要'一路向左、再回退'。"
4. **说清复杂度**："时间 $O(n)$，空间 $O(h)$。"
5. **主动提边界**："空树返回空列表；单节点直接返回。"

**第 1 步是关键**——它表明你不是在背"左根右"这三个字，而是理解了"时机"这一抽象。

### 10.2 常见追问

**追问一："迭代版为什么容易乱？"** 答：因为递归把"控制流"交给了系统栈，迭代要自己维护它——难的不是"用栈"，而是"把隐式的控制流显式化"。

**追问二："后序迭代为什么用双栈？"** 答：后序要求"左右都处理完才访问当前"，直接用单栈难以判断"右子树是否处理过"；双栈法先产生"根-右-左"，再反转即得"左-右-根"。

**追问三："中序迭代的 `current` 和 `stack` 各是什么？"** 答：`current` 是"向左推进的游标"，`stack` 是"待回来访问的节点"。

**追问四："能不能 $O(1)$ 空间？"** 答：能，用 Morris 遍历（借叶节点右指针当线索），但它会临时改结构。

**追问五："三种遍历能互相推导吗？"** 答：能。前序是"根-左-右"，把它的左右递归顺序互换（根-右-左）再反转，即得后序；中序则依赖"左-根-右"的三段结构，无法由前序/后序直接推得。

### 10.3 落点

遍历题的"简单"，是它只考"顺序"；遍历题的"不简单"，是它把"顺序"背后的**控制流、递归语义、空间优化**都藏在了短短几行里。**能把 144/94/145 讲出层次（时机、迭代、Morris、适用边界），就说明你对 DFS 的理解已经扎实**——而这份扎实，会一路支撑后面所有树题。

## 小结

本篇从"递归进入节点有三个处理时机"这一视角出发，把前序、中序、后序三种遍历统一成同一段骨架的三种填法。递归写法只是"在某个时机处理当前节点"；迭代写法则是"把系统栈显式化"，其中中序靠"一路向左 + 回退"、后序靠"双栈反转"来还原控制流。Morris 遍历进一步展示了"把回去的路藏进数据结构本身"这一省空间的思想。而贯穿全篇最重要的一层抽象是：**遍历顺序决定"何时处理当前节点"，函数返回值决定"把什么带回父节点"——把这两件事分开，树题就会豁然开朗。**

这篇的模板，会一路迁移到后面的二叉搜索树（中序有序）、树形 DP（后序汇总）、路径问题（前序携带状态）。**144/94/145 看似基础，实则是整个二叉树专栏的模板库**——把这三个"时机"刻进肌肉记忆，后面的题都只是它们的组合与变形。

下一篇 [[02 广度优先遍历：层序、倒序层序与锯齿层序]] 会把视角从"沿深度向下钻"切换到"按层横向扫描"。你会看到，队列在树题里真正保存的，不是节点本身，而是"当前层边界尚未处理完的工作集"。
