# 二叉树结构判定：相同树、对称树与平衡二叉树

**摘要：**

二叉树里的判定题，往往比遍历题更能暴露思维漏洞。LeetCode 100、101、110 分别代表三类典型任务：判断两棵树是否完全一致、判断一棵树是否镜像对称、判断一棵树是否高度平衡。它们都能用递归解决，但**递归函数的定义各不相同**——Same Tree 返回布尔值就够了，Symmetric Tree 需要"镜像比较"，Balanced Binary Tree 则必须让函数同时携带"是否合法"与"高度"两类信息。本文用 Go 语言完整实现这三道题，并借此讲清一件树题里最关键、也最容易被忽视的事：**先定义函数语义，再写代码**。文中还会追问：为什么对称不是"相同"、为什么"先算高度再判平衡"会慢到 $O(n^2)$、以及"失败哨兵值"这一技巧如何把两类信息塞进一次递归。这三道题是树形 DP 的前奏，理解了它们，后面的最大路径和就只是"把返回值与全局状态变复杂"。

---

## 第 1 章 判定题为什么更难

遍历题的目标是"把节点按某种顺序收集起来"，判定题的目标却是"回答一个是非问题"。**后者的难点不在遍历，而在"如何把大问题拆成可判定的小问题"。**

以"两棵树是否相同"为例：它不是"遍历一遍比较"这么简单，而是要先想清楚——**相同意味着什么？** 是"每个对应位置的节点值相等"吗？不够，因为 `[1,2]` 与 `[1,null,2]` 的值可能部分重合，但结构不同。**"相同"必须同时涵盖"结构一致"与"值一致"两重含义。** 想清楚这一点，递归函数才写得对。

**这揭示了一条通用经验：判定题的难度，藏在"判定条件的精确定义"里，而不在遍历本身。** 下文三道题，恰好对应三种不同的"判定条件定义方式"。

## 第 2 章 LeetCode 100：Same Tree

### 2.1 题目

**LeetCode 100 - Same Tree**（简单）

给你两棵二叉树的根节点 `p` 和 `q`，编写一个函数来检验它们是否相同。相同要求：结构一致，且对应位置的节点值相等。

```text
输入: p = [1,2,3], q = [1,2,3]  →  输出: true
输入: p = [1,2],   q = [1,null,2] →  输出: false
```

### 2.2 递归语义：给我两棵树，返回它们是否相同

```go
func isSameTree(p, q *TreeNode) bool {
    if p == nil && q == nil {
        return true // 都为空，相同
    }
    if p == nil || q == nil {
        return false // 一空一非空，结构不同
    }
    if p.Val != q.Val {
        return false // 值不同
    }
    return isSameTree(p.Left, q.Left) && isSameTree(p.Right, q.Right)
}
```

**这个函数的语义非常直接：给我两棵树，我返回它们是否相同。** 三个判断分支依次处理"都空""一空""值不等"，最后递归比较左右子树——**注意比较的是"平行位置"（`p.Left` 对 `q.Left`、`p.Right` 对 `q.Right`）。**

**复杂度**：时间 $O(n)$（每个节点比较一次），空间 $O(h)$（递归栈深度，$h$ 为树高）。

## 第 3 章 LeetCode 101：Symmetric Tree

### 3.1 题目

**LeetCode 101 - Symmetric Tree**（简单）

给你一个二叉树的根节点 `root`，检查它是否轴对称。

```text
输入: root = [1,2,2,3,4,4,3]  →  输出: true
输入: root = [1,2,2,null,3,null,3]  →  输出: false
```

### 3.2 为什么不能直接比较左右子树

很多人第一反应是：判断 `root.Left` 和 `root.Right` 是否相同（复用 Same Tree）。**但对称不是"相同"，而是"互为镜像"：**

- 左子树的**左**孩子，对应右子树的**右**孩子；
- 左子树的**右**孩子，对应右子树的**左**孩子。

**这意味着比较关系发生了"交叉"。** 若照搬 Same Tree 的平行比较，就会把"镜像"错当成"相同"，得到错误答案。**这就是"判定条件定义不同"带来的第一个分叉。**

### 3.3 递归语义：镜像比较

```go
func isSymmetric(root *TreeNode) bool {
    if root == nil {
        return true
    }
    return isMirror(root.Left, root.Right)
}

// isMirror：判断两棵子树是否互为镜像
func isMirror(left, right *TreeNode) bool {
    if left == nil && right == nil {
        return true
    }
    if left == nil || right == nil {
        return false
    }
    if left.Val != right.Val {
        return false
    }
    // 关键：交叉比较
    return isMirror(left.Left, right.Right) && isMirror(left.Right, right.Left)
}
```

**Same Tree 比较的是"平行位置"，Symmetric Tree 比较的是"镜像位置"——这就是两道题最大的区别。** 只差最后一行递归参数的顺序，语义却完全不同。

### 3.4 迭代写法：成对入队

对称性也可以用迭代判断——**用队列成对放入"应当互为镜像的两个节点"**，每次取出两个比较，再按镜像顺序把它们的四个孩子成对入队：

```go
func isSymmetricIter(root *TreeNode) bool {
    if root == nil {
        return true
    }
    queue := []*TreeNode{root.Left, root.Right}
    for len(queue) > 0 {
        left, right := queue[0], queue[1]
        queue = queue[2:]
        if left == nil && right == nil {
            continue
        }
        if left == nil || right == nil || left.Val != right.Val {
            return false
        }
        // 按镜像顺序成对入队
        queue = append(queue, left.Left, right.Right)
        queue = append(queue, left.Right, right.Left)
    }
    return true
}
```

**这类"成对比较"的迭代题，本质上是在显式模拟递归的参数对**——队列里存的不是一个节点，而是一对"应当互为镜像"的节点。**理解了这一点，你就明白为什么迭代版也能保持同样的语义。**

## 第 4 章 LeetCode 110：Balanced Binary Tree

### 4.1 题目

**LeetCode 110 - Balanced Binary Tree**（简单）

给定一个二叉树，判断它是否是高度平衡的。高度平衡的定义：每个节点的左右两个子树的高度差的绝对值不超过 1。

```text
输入: root = [3,9,20,null,null,15,7]  →  输出: true
输入: root = [1,2,2,3,3,null,null,4,4] →  输出: false
```

### 4.2 为什么"先算高度再判平衡"会慢

最直观的思路是：

1. 对每个节点分别求左子树高度、右子树高度；
2. 比较高度差是否超过 1；
3. 再递归判断左右子树是否平衡。

**这个写法是正确的，但会重复计算高度**——每个节点都被反复求高度，最坏情况下复杂度退化到 $O(n^2)$。**对一棵退化成链的树，几乎每个节点都要重扫一遍它的子树。**

### 4.3 正确思路：后序遍历，一次返回高度

**"当前节点是否平衡"依赖左右子树的高度，而高度必须先由子树给出——所以这是一个标准后序问题。** 我们让函数**返回子树高度**，但如果发现某棵子树已经不平衡，就返回一个"失败哨兵值"（如 `-1`），从而把"判断平衡"与"返回高度"合并到一次递归里。

```go
func isBalanced(root *TreeNode) bool {
    return height(root) != -1
}

// height：返回子树高度；若子树已不平衡，返回 -1
func height(node *TreeNode) int {
    if node == nil {
        return 0
    }
    leftHeight := height(node.Left)
    if leftHeight == -1 {
        return -1 // 左子树已不平衡，提前失败
    }
    rightHeight := height(node.Right)
    if rightHeight == -1 {
        return -1 // 右子树已不平衡
    }
    if abs(leftHeight-rightHeight) > 1 {
        return -1 // 当前节点不平衡
    }
    return max(leftHeight, rightHeight) + 1 // 返回真实高度
}

func abs(x int) int { if x < 0 { return -x }; return x }
func max(a, b int) int { if a > b { return a }; return b }
```

**这里 `-1` 不是高度，而是一个"失败哨兵值"**，表示"这棵子树已经不平衡"。**用一个特殊值同时承载"失败"与"高度"两重信息，是树题里极常用的技巧**——它避免了"要么返回布尔值、要么返回高度"的二选一困境。

**复杂度**：时间 $O(n)$（每个节点只访问一次），空间 $O(h)$。

### 4.4 为什么这道题是树形 DP 的前奏

因为它已经体现了树题里最典型的模式：

- 左子树先算出结果；
- 右子树再算出结果；
- 当前节点拿到左右结果后**完成汇总**；
- 汇总结果**继续返回给父节点**。

**这就是树形 DP 的基本骨架。** 后面的"二叉树中的最大路径和"（第 11 篇），只是把这个骨架里的"返回值"和"全局状态"变复杂了——**理解了平衡树这道题，你就理解了树形 DP 的"最小可用模型"。**

## 第 5 章 三道题的递归语义对比

把三道题的递归函数设计并排看，会看到一条清晰的"难度阶梯"：

| 题目 | 函数输入 | 函数返回值 | 本质 |
|------|----------|------------|------|
| Same Tree | 两棵树 | 是否相同 | 平行比较 |
| Symmetric Tree | 两棵镜像位置子树 | 是否镜像 | 交叉比较 |
| Balanced Binary Tree | 一棵树 | 高度或失败哨兵 | 后序汇总 |

**从这张表可以看出，树题真正决定难度的不是遍历方式，而是递归函数的语义设计。** 遍历方式（前中后序）只是"何时处理当前节点"；而**函数语义决定"输入是什么、返回什么"**——后者才是难度的来源。

> [!info] 先定义函数，再写代码
> 面试里，如果你能**先把函数语义说清楚**（"这个函数接收两棵子树，返回它们是否镜像"），代码几乎会自然长出来；如果一上来就写 `if node == nil`，通常意味着思路还没抽象稳定。**"先定义函数、再写代码"是树题乃至所有递归题的第一条纪律。**

## 第 6 章 延伸：判定题的更多面孔

### 6.1 另一棵树的子树（LeetCode 572）

**题目**：给你两棵二叉树 `root` 和 `subRoot`，判断 `subRoot` 是否是 `root` 的子树（结构相同且值相同）。

**思路**：先复用 Same Tree 写一个"判断两棵树是否相同"的函数，再遍历 `root` 的每个节点，对每个节点调用它：

```go
func isSubtree(root, subRoot *TreeNode) bool {
    if root == nil {
        return false
    }
    // 当前节点为根的子树是否与 subRoot 相同，或答案在左右子树中
    return isSameTree(root, subRoot) || isSubtree(root.Left, subRoot) || isSubtree(root.Right, subRoot)
}
```

**这道题展示了"判定题可以组合"**——把一个判定（Same Tree）当作零件，嵌进另一个判定（子树）里。**复杂度是 $O(m \times n)$**（对 `root` 的每个节点都做一次 Same Tree），在数据规模不大时足够；若追求更优，可用"树的哈希/序列化"做预处理。

### 6.2 翻转二叉树（LeetCode 226）

**题目**：翻转一棵二叉树（交换每个节点的左右子树）。

```go
func invertTree(root *TreeNode) *TreeNode {
    if root == nil {
        return nil
    }
    root.Left, root.Right = root.Right, root.Left // 交换左右
    invertTree(root.Left)                          // 递归处理（此时原右子树）
    invertTree(root.Right)
    return root
}
```

**这道题与 Symmetric Tree 是一对**：Symmetric 判断"是否镜像"，Invert 制造"镜像"。**它们的递归结构相似，目标却相反**——一个是"验证"，一个是"构造"。**把这两道题对照着看，能帮你更清楚地理解"镜像"这一关系。**

### 6.3 三道延伸题的共性

572、226 加上主线的 100、101，构成了一组"结构关系"题：相同（100）、镜像（101）、子树（572）、制造镜像（226）。**它们的共性是：判定/操作的对象不是"单个节点的值"，而是"子树之间的结构关系"。** 处理这类题，**递归函数往往要接收"两个子树"而非"一个节点"**——这是它们区别于遍历题的关键特征。

## 第 7 章 递归返回值的设计模式库

三道判定题（加上延伸）展示了递归返回值的几种典型设计。把它们归纳成一个"模式库"，你在写陌生树题时就能"对号入座"。

### 7.1 模式一：返回布尔值（判定类）

**适用**：问题是"是否满足某条件"（Same Tree、Symmetric Tree）。
**写法**：递归返回 `bool`，用"与/或"组合子结果。
**要点**：先处理"基准情况"（`nil` 的对称性），再组合。

```go
func isSame(p, q *TreeNode) bool {
    if p == nil && q == nil { return true }
    if p == nil || q == nil { return false }
    return p.Val == q.Val && isSame(p.Left, q.Left) && isSame(p.Right, q.Right)
}
```

**判定类是最简单的一类**——因为它"不需要向父节点传递额外信息"，只需回答一个是非。

### 7.2 模式二：返回单值（汇总类）

**适用**：问题是"求某个量"（最大深度、子树大小、节点和）。
**写法**：递归返回该量，父节点用子结果算出自己的量。
**要点**：想清"这个量的定义"，让"父节点的量"能由"子节点的量"算出。

```go
func depth(node *TreeNode) int {
    if node == nil { return 0 }
    return max(depth(node.Left), depth(node.Right)) + 1
}
```

### 7.3 模式三：返回哨兵值（"两类信息合一"类）

**适用**：需要同时传递"一个数值"与"一个是否合法的标记"（平衡树）。
**写法**：用一个"非法值"（如 `-1`）作为哨兵，同时承载"失败"与"数值"两重含义。
**要点**：哨兵值必须是一个"正常结果不可能取到"的值。

```go
func height(node *TreeNode) int {
    if node == nil { return 0 }
    l := height(node.Left)
    if l == -1 { return -1 }
    r := height(node.Right)
    if r == -1 { return -1 }
    if abs(l-r) > 1 { return -1 }
    return max(l, r) + 1
}
```

**哨兵模式的精妙在于"合并两次传递为一次"**——若不用哨兵，就得返回一个结构体（`{高度, 是否平衡}`）。**哨兵更轻，但要求"非法值不与正常值冲突"。**

### 7.4 模式四：返回值 + 全局变量（"最值类"）

**适用**：答案是"任意节点/路径的全局最优"（直径、最大路径和）。
**写法**：函数返回"给父节点用的贡献值"，同时用外部变量记录"全局答案"。
**要点**：**严格区分"返回值"与"全局答案"**——前者供传递，后者供结算。

```go
ans := 0
var dfs func(node *TreeNode) int
dfs = func(node *TreeNode) int {
    if node == nil { return 0 }
    l, r := dfs(node.Left), dfs(node.Right)
    ans = max(ans, l+r)        // 全局答案：以当前节点为拐点
    return max(l, r) + 1       // 返回值：只能选一边
}
```

**模式四是四类里最容易出错的**——因为它要求"同一个函数同时做两件事"。**把这两件事分开想，是它的唯一诀窍**（详见第 11 篇）。

### 7.5 四类模式的选择

| 模式 | 返回值 | 适用问题 | 代表 |
|------|--------|---------|------|
| 布尔判定 | `bool` | 是否满足条件 | 100、101 |
| 单值汇总 | 数值 | 求某个量 | 104 |
| 哨兵合并 | 数值（含非法值） | 数值 + 合法性 | 110 |
| 返回值 + 全局 | 数值 + 外部变量 | 全局最优 | 543、124 |

**拿到一道树题，先判断它属于哪一类，返回值的设计就有了方向。** 这张表，是本专栏"递归语义设计"这一主线的一个凝练版本——**它把"该返回什么"从一个需要灵感的动作，变成了一次可以查表的判断。**

> [!info] 从"设计返回值"到"查表"
> 初学者写树题，常常卡在"这个函数该返回什么"。**但返回值的类型其实很有限——布尔、单值、哨兵、返回值+全局，也就这四类。** 把它们做成一张表，你就不再需要每次从零设计。**这正是"把经验结构化"的价值：它不是让你更聪明，而是让你更少犯错。**

## 第 8 章 常见误区与自测方法

### 7.1 四个高频误区

**误区一：把 Symmetric Tree 写成 Same Tree。** 这是最常见的错误，原因不是"不会递归"，而是没有真正看到"镜像"这个关系变化——比较关系应当是**交叉**的。

**误区二：在 Balanced Binary Tree 里重复算高度。** 只要一个节点每次都重新调用求高度函数，就说明没有把"高度"作为子树返回值复用起来，复杂度会退化到 $O(n^2)$。

**误区三：只关注值，不关注 `nil` 结构。** 树题很多 bug 不是"值比较错了"，而是"`nil` 分支没对齐"。**在树结构问题里，`nil` 本身就是一种信息**——它代表"这里没有子树"。

**误区四：混淆"失败哨兵值"与"真实高度"。** `-1` 是哨兵，不能参与高度计算；一旦混用，就会把"失败"当成"高度为 -1"，得出荒谬结果。

### 7.2 一套自测用例

| 用例 | 检验什么 |
|------|---------|
| 两棵都为空 | Same Tree 的 `nil` 边界 |
| `[1,2]` vs `[1,null,2]` | 结构不同但值部分重合 |
| `[1,2,2,null,3,null,3]` | 对称树的反例（镜像位置值不同） |
| 退化成链的树 | 平衡树的 $O(n^2)$ 陷阱 |
| 单节点树 | 最简情形 |

**其中"`[1,2]` vs `[1,null,2]`"最值得测**——它专门检验"结构不同"这一判定，是"只比值不比结构"这类错误的照妖镜。**凡是结构判定题，都要用一个"值相同但结构不同"的用例来验证。**

## 第 9 章 判定题的边界、反例与面试表达

### 9.1 判定题的"边界三件套"

所有树形判定题，都要过三关：

**第一关，空树。** `nil` 是最容易被忽略的输入。对"相同""对称"这类题，两个 `nil` 应当判为"相同/对称"（都空）；对一个 `nil`、一个非空，应判为"不同/不对称"。**这两条基准规则必须写对，否则整棵树的判定都会偏。**

**第二关，单节点。** 单节点树是最简的非空情形。它检验"递归是否能正确终止"以及"返回值是否正确"。

**第三关，单孩子。** 这是树题最"阴险"的边界——很多 bug（如第 09 篇最小深度的陷阱、第 10 篇的叶子判定）都藏在"某节点只有一个孩子"的情形里。**凡是树题，都要专门测一个"单孩子"的输入。**

**这三关，覆盖了树形判定题 90% 以上的边界 bug。**

### 9.2 三个典型反例

**反例一：值相同但结构不同。** `[1,2]` 与 `[1,null,2]`——它专治"只比值不比结构"。**判定"相同"必须同时比结构与值。**

**反例二：镜像位置值不同。** `[1,2,2,null,3,null,3]`——它专治"把对称当成相同"（平行比较而非交叉比较）。

**反例三：高度差恰为 2。** 构造一棵"某节点左右子树高度差恰好是 2"的树——它检验"平衡判定"的阈值（是 `> 1` 还是 `> 2`）。**阈值差一位，结果就全错。**

**这三个反例，分别对应"结构判定""镜像判定""平衡判定"三类题，值得在面试前各准备一个。**

### 9.3 面试表达：先讲语义，再讲代码

树形判定题的面试表达，建议按这个顺序：

1. **先定义函数语义**："这个函数接收两棵子树，返回它们是否镜像。"**——把语义讲清，代码几乎会自然长出。**
2. **再讲基准情况**："两个都空返回 true，一空一非空返回 false。"
3. **然后讲递归关系**："镜像比较是交叉的——左的左对右的右。"
4. **最后讲复杂度**："时间 $O(n)$，空间 $O(h)$。"

**第 1 步是关键**——很多人一上来就写 `if root == nil`，说明思路还没抽象稳定。**先讲清"函数是什么"，比急着写代码重要得多。**

> [!info] 判定题考的是"定义能力"
> 遍历题考的是"按顺序做事"，判定题考的是"**精确地定义什么是'满足条件'**"。Same Tree 要定义"相同"、Symmetric 要定义"对称"、Balanced 要定义"平衡"——**定义错了，代码再漂亮也是错的。** 这也是为什么本篇反复强调"先定义语义"——**判定题的难度，从不在遍历，而在定义。**

### 9.4 一个可以迁移的习惯

**"先定义、再实现"这个习惯，不止适用于树题。** 面对任何问题——无论是写一个函数、设计一个系统、还是分析一道算法题——**先问"我要解决的确切是什么"，往往比急着动手更能避免返工。** 树形判定题只是这个习惯的一个小切口：**它把"定义不清"的代价，压缩到了一道题的范围里，让你能快速体会到"先定义"的价值。**

## 第 10 章 递归的调试与验证

### 10.1 递归 bug 的三种形态

树题的递归 bug，往往不是"逻辑错"，而是"边界漏"。三种典型：

**形态一，基准情况写错。** 如 Same Tree 里只判断了"都为空"，忘了"一空一非空"。**表现是"某些输入返回了错误结果"。**

**形态二，递归关系写错。** 如 Symmetric 写成了平行比较（`left.Left` 对 `right.Left`），而非交叉（`left.Left` 对 `right.Right`）。**表现是"简单输入能过、镜像输入出错"。**

**形态三，返回值语义混乱。** 如平衡树里"哨兵 `-1`"与"真实高度"混用。**表现是"结果忽对忽错，取决于输入"。**

**三种形态的共同点是"边界"，而非"主逻辑"**——**递归的主逻辑往往是对的，错的是那些"只在特殊输入下才走到"的分支。**

### 10.2 调试递归的方法

**方法一，从最小输入开始。** 先用"空树、单节点、两节点"逐步验证，再放大规模。**因为递归的 bug 通常在小输入下就已暴露。**

**方法二，打印中间返回值。** 在递归函数里打印"参数"与"返回值"，观察"每一层的输入输出是否符合预期"。**递归 bug 最有效的手段，是"看每一层的返回值"。**

**方法三，用"函数语义"反查。** 写完后，重新读一遍函数，问："**它是否真的实现了我在注释里写的那个语义？**" 例如 Symmetric 的语义是"判断是否镜像"，若代码做的是"判断是否相同"，语义就对不上。

**这三种方法，从"输入规模""中间值""语义一致性"三个角度切入**，覆盖了递归调试的主要场景。

### 10.3 一个值得养成的习惯

**写递归时，先写"函数语义"的注释，再写代码。** 例如：

```go
// isMirror 判断两棵子树是否互为镜像
func isMirror(left, right *TreeNode) bool { ... }
```

**这个习惯的价值，是"把'意图'固化下来"**——写完代码后，你可以对照注释检查"实现是否与意图一致"。**很多递归 bug，正是因为"写的时候想的是一个语义、写出来的是另一个语义"。** 把语义先写下来，就能在"实现"与"意图"之间做一次对照——**这是递归调试最省力的手段。**

> [!note] 递归的"信任"与"验证"
> 写递归时，我们总是"先相信子问题已被解决"（第 01 篇的"信任子问题"）。**但"信任"不等于"不验证"**——验证的对象是"函数语义"与"实现是否一致"，而非"子问题的每一步"。**把"信任"（对子问题）与"验证"（对语义）结合起来，是写对递归的完整心法。**

### 10.4 落点

判定题的调试，本质是"**确认'判定条件'是否被正确实现**"。**而判定条件的精确表述（第 1 章、第 9 章反复强调），正是避免这类 bug 的根本办法**——**如果一开始就把"相同""对称""平衡"定义清楚，很多 bug 根本不会出现。** 所以，调试的最高境界，是"通过精确的定义，从源头避免 bug"。

## 第 11 章 判定题的自查清单与落点

### 11.1 一份自查清单

| 检查项 | 对应问题 |
|--------|---------|
| 基准情况是否处理了"一空一非空" | Same Tree 漏判 |
| 对称是否用"交叉比较" | 写成平行比较 |
| 平衡是否复用高度 | $O(n^2)$ 退化 |
| 哨兵 `-1` 是否与真实高度混用 | 语义混乱 |
| 是否只比值不比结构 | `[1,2]` vs `[1,null,2]` |
| 空树、单节点是否返回正确 | 基准情况 |

### 11.2 落点

**判定专题的落点，是"递归函数的语义设计"**——Same Tree 返回"是否相同"、Symmetric 返回"是否镜像"、Balanced 返回"高度或哨兵"。**三者的遍历方式相似，难度却层层递进，差别全在"函数接收什么、返回什么"。**

**而更深一层的收获，是"先定义、再实现"这一习惯**——**判定题的难度从不在遍历，而在"精确地定义什么是'满足条件'"。** 定义错了，代码再漂亮也是错的。**这个习惯不止适用于树题，也适用于一切"需要精确描述目标"的工作。**

> [!info] 一句话带走
> 如果只能带走一句话，那就是：**"树题的难度不在遍历，而在递归函数的语义设计。"** 遍历顺序只决定"何时处理当前节点"；真正决定难度的，是"函数接收什么、返回什么"。**先把语义讲清楚，代码几乎会自然长出来。**

### 11.3 从"判定"到"设计"

**判定题训练的能力——"精确地定义条件"——在工程里对应的是"写清楚需求"。** 一个模糊的需求（如"系统要快"），就像一道没定义清楚的判定题，无论怎么实现都可能"不对"。**而"把需求拆成可判定的条件"（如"P99 延迟 < 100ms"），正是工程师的核心能力之一。** 树形判定题虽小，却把这个能力演示得清清楚楚——**它让你在最小的规模上，体会到"定义清楚"的价值。**

---

### 11.4 一个值得记住的边界

**"空树是否合法"是判定题的第一个分歧点。** Same Tree 里"两棵都空"算相同；Symmetric 里"空树"算对称；Balanced 里"空树"算平衡。**但到了别的题，"空"未必合法**（如"求最小值"时空集无解）。**所以每道题都要先确认"空输入是否算合法答案"**——这是最容易漏、也最容易错的一处。

---

## 小结

本篇用三道判定题，讲清了树题里最关键的一层抽象——**递归函数的语义设计**。Same Tree 做"平行比较"、返回布尔值；Symmetric Tree 做"交叉比较"、处理镜像关系；Balanced Binary Tree 做"后序汇总"、用失败哨兵把两类信息塞进一次递归。三者的遍历方式相似，难度却层层递进，差别全在"函数接收什么、返回什么"。

贯穿全篇的核心认知有两条。其一，**判定题的难度藏在"判定条件的精确定义"里**——"相同"要涵盖结构与值，"对称"是交叉而非平行，"平衡"要复用高度而非重算。其二，**"先定义函数语义，再写代码"是递归题的第一条纪律**——函数接收什么、返回什么，一旦想清，代码自会长出。**把这两条握住，你面对任何陌生的树形判定题，都能先定语义、再落笔。**
