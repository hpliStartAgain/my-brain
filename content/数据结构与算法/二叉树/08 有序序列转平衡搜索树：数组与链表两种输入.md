# 有序序列转平衡搜索树：数组与链表两种输入

**摘要：**

"把有序序列转成一棵平衡 BST"，是一道看似简单、却藏着两个不同难度的题：LeetCode 108（有序数组）与 109（有序链表）。**数组版**的关键，是理解"为什么取中点作根就能保证平衡"——这背后是一条可以证明的性质；**链表版**的难点，则在于链表**不支持随机访问**，无法照抄数组的"取 `mid`"操作，必须换一套思路。本文用 Go 语言完整实现这两道题，并给出链表版的两种解法：**快慢指针找中点**（$O(n \log n)$）与**模拟中序构造**（$O(n)$）。全文会逐层追问：取中点为什么平衡、快慢指针为什么慢、以及"用中序构造"这一技巧如何把链表版也压到线性时间。掌握这两道题，你会对"分治 + 平衡"这一组合有更深的体会。

---

## 第 1 章 为什么"取中点作根"能保证平衡

### 1.1 平衡的定义与目标

BST 的"平衡"通常指"任意节点的左右子树高度差不超过 1"（即高度平衡）。我们要构造的，是一棵**高度平衡**的 BST——这样的树高度为 $O(\log n)$，查找、插入都是 $O(\log n)$。

### 1.2 中点作根的证明

**为什么取中点作根就能保证平衡？** 直觉是：**取中点作根，左右两侧的元素数量最多相差 1**（`mid = left + (right-left)/2` 使左半与右半长度差不超过 1）。而"左右元素数量最多差 1"，递归下去，每一层的两棵子树规模都近乎相等——**规模相等 ⇒ 高度相等（或差 1）⇒ 平衡。**

**严格地说，这是一条归纳性质**：若对任意区间"取中点作根"都能得到高度平衡的 BST，那么对它的左右子区间同样成立；而"左右规模差不超过 1"保证了归纳的"高度差不超过 1"这一结论。**这与"二分查找把区间均匀切开"是同一种"均分"思想。**

### 1.3 一个自然的类比

**取中点作根构造平衡 BST，本质上就是"把二分查找的判定树显式地造出来"。** 二分查找的每一步"取中点"，恰好对应 BST 的每一个"根节点"。**理解了这一点，108 题就不再需要"证明平衡"——因为二分查找的判定树天然是平衡的。**

## 第 2 章 LeetCode 108：有序数组转 BST

### 2.1 题目

**LeetCode 108 - Convert Sorted Array to Binary Search Tree**（简单）

给你一个整数数组 `nums`，其中元素已经按升序排列，请你将其转换为一棵高度平衡的二叉搜索树。

```text
输入: nums = [-10,-3,0,5,9]
输出: [0,-3,9,-10,null,5]（或其它合法答案）
```

### 2.2 Go 实现

```go
func sortedArrayToBST(nums []int) *TreeNode {
    var build func(left, right int) *TreeNode
    build = func(left, right int) *TreeNode {
        if left > right {
            return nil
        }
        mid := left + (right-left)/2 // 取中点，保证左右规模差 ≤ 1
        node := &TreeNode{Val: nums[mid]}
        node.Left = build(left, mid-1)
        node.Right = build(mid+1, right)
        return node
    }
    return build(0, len(nums)-1)
}
```

**复杂度**：时间 $O(n)$（每个元素构造一次），空间 $O(\log n)$（递归栈深度，因为平衡）。

**注意 `mid = left + (right-left)/2` 这一写法**——它与二分查找的"防溢出中点"完全一致。**这道题与二分查找共享同一套"均分"逻辑**，这也是为什么它如此"眼熟"。

### 2.3 为什么数组版如此简单

因为数组**支持 $O(1)$ 随机访问**——"取中点"是 $O(1)$ 的，于是整个构造是 $O(n)$。**难点在链表版——链表取中点不是 $O(1)$。**

## 第 3 章 LeetCode 109：有序链表转 BST

### 3.1 题目

**LeetCode 109 - Convert Sorted List to Binary Search Tree**（中等）

给定一个单链表的头节点 `head`，其中元素已经按升序排列，将其转换为一棵高度平衡的二叉搜索树。

```text
输入: head = [-10,-3,0,5,9]
输出: [0,-3,9,-10,null,5]（或其它合法答案）
```

### 3.2 难点：链表取中点不是 $O(1)$

数组版的核心操作是"取 `nums[mid]`"，这是 $O(1)$ 的。**但链表没有下标，要找到中点，只能从头遍历——这是 $O(k)$（$k$ 为当前链表长度）。**

### 3.3 解法一：快慢指针找中点（$O(n \log n)$）

最直接的思路：**用快慢指针找当前链表的中点**，以它为根，再递归处理左右两半。

```go
func sortedListToBST(head *ListNode) *TreeNode {
    var build func(left, right *ListNode) *TreeNode // 区间 [left, right)
    build = func(left, right *ListNode) *TreeNode {
        if left == right {
            return nil
        }
        // 快慢指针找中点
        slow, fast := left, left
        for fast != right && fast.Next != right {
            slow = slow.Next
            fast = fast.Next.Next
        }
        node := &TreeNode{Val: slow.Val}
        node.Left = build(left, slow)       // [left, slow)
        node.Right = build(slow.Next, right) // (slow, right)
        return node
    }
    return build(head, nil)
}
```

**为什么用"区间 `[left, right)`"而不是"直接传链表"？** 因为快慢指针需要知道"到哪里停"——`right` 就是区间的右界（不含）。**传区间边界而非切片，与第 05 篇重建题的"传下标而非切数组"是同一思路。**

**复杂度是 $O(n \log n)$**：每一层递归要找中点（$O(\text{当前长度})$），而递归深度是 $O(\log n)$，总代价 $O(n \log n)$。**这份"慢"，正来自"每次找中点都要重新遍历"。**

### 3.4 解法二：模拟中序构造（$O(n)$）

有没有办法做到 $O(n)$？有——**利用一个关键事实：中序遍历一棵 BST，恰好得到有序序列。** 于是我们可以"**按中序的顺序**"来构造：先递归构造左子树、再"取链表当前节点作根"、再构造右子树。

**难点在于"确定子树规模"**——但如果我们**先遍历一遍链表求出总长度**，就可以用"区间长度"来驱动递归，而"取链表当前节点"只需一个从头到尾的指针：

```go
func sortedListToBSTFast(head *ListNode) *TreeNode {
    // 第一步：求链表长度
    length := 0
    for node := head; node != nil; node = node.Next {
        length++
    }

    curr := head // 全局游标：按中序顺序依次取用
    var build func(size int) *TreeNode
    build = func(size int) *TreeNode {
        if size <= 0 {
            return nil
        }
        leftSize := size / 2
        // 先构造左子树（它会消费掉 leftSize 个节点）
        left := build(leftSize)
        // 此时 curr 恰好指向"本层的根"
        root := &TreeNode{Val: curr.Val}
        curr = curr.Next
        // 再构造右子树
        root.Left = left
        root.Right = build(size - 1 - leftSize)
        return root
    }
    return build(length)
}
```

**这个解法的时间是 $O(n)$**——因为每个节点只被"取用"一次。**它的精妙之处，在于"按中序顺序取节点"这一洞察**：既然中序 = 有序序列，那么"递归构造左子树 → 取当前节点 → 构造右子树"的访问顺序，恰好与链表的自然顺序一致，于是 `curr` 只需单调前进。

> [!info] 从 $O(n \log n)$ 到 $O(n)$：换个视角看问题
> 快慢指针解法把"找中点"当成一个必须反复做的操作，于是每次都要 $O(k)$；而模拟中序解法**换了一个视角**——它不问"中点是哪个节点"，而问"**构造的顺序恰好是什么**"。一旦发现"构造顺序 = 中序 = 链表顺序"，找中点这件事就被彻底绕开了。**很多优化的本质，不是"把某个操作做得更快"，而是"换一个视角，让那个操作不再需要"。** 这与线性表专栏第 06 篇"用阶乘数系绕开生成全部排列"是同一种思路。

## 第 4 章 两道题的对照

| 维度 | LC 108 数组 | LC 109 链表（快慢指针） | LC 109 链表（模拟中序） |
|------|------------|----------------------|----------------------|
| 取中点 | $O(1)$ 随机访问 | $O(k)$ 遍历 | 不需要 |

## 第 5 章 平衡的层级：从"高度平衡"到"完全平衡"

"平衡"这个词，其实有多个层级。搞清楚它们的差别，能帮你在面试里答得更准确。

### 5.1 三种"平衡"

- **高度平衡**：任意节点的左右子树高度差不超过 1。这是 LeetCode 108/109 与第 03 篇 110 题采用的定义。
- **完全平衡（perfectly balanced）**：所有叶子在同一层，即"完美二叉树"。它比高度平衡更强。
- **完全二叉树（complete binary tree）**：除最后一层外每层都满，且最后一层的节点集中在左侧。**它是"用数组存树"时最省空间的结构**（见第 5.3 节）。

**取中点构造得到的，是"高度平衡"，但不一定是"完全平衡"。** 例如 `[1,2,3,4]`，取中点 `2`（或 `3`）作根，得到的树高度差不超过 1，但叶子不在同一层——它高度平衡，却不是完全平衡。**理解这个差别，你就不会把"平衡"当成一个笼统的词。**

### 5.2 如何构造"完全平衡"的 BST

若要求"所有叶子在同一层"（即完美二叉树），节点数必须恰好是 $2^k - 1$。此时"取中点"恰好能得到完美二叉树——**因为对 $2^k - 1$ 个元素，中点把区间分成两个各含 $2^{k-1} - 1$ 个元素的子区间，递归下去每层都满。**

**若节点数不是 $2^k - 1$，就无法构造完美二叉树**——这从"数量"上就排除了。**所以在实际题目里，通常只要求"高度平衡"**（108/109 都是如此），而不要求"完全平衡"。

### 5.3 为什么"完全二叉树"对工程很重要

**完全二叉树可以用数组表示**：把节点按层序编号，第 `i` 个节点的左孩子在 `2i`、右孩子在 `2i+1`。**这样无需任何指针，就能在 $O(1)$ 内定位父子关系。**

**这正是"二叉堆"（优先队列的底层）的存储方式**——堆是一棵完全二叉树，用数组存储，于是"父子定位"和"数组随机访问"兼得。**理解了这一点，你就明白为什么堆用数组而不是指针实现**：完全二叉树的"结构规整"，让"下标即位置"成为可能。

**回到 108/109**：它们构造的是"高度平衡"BST，用于高效查找；而"完全二叉树"更多用于"堆"这类需要数组存储的场景。**同样是"平衡"，用途不同，对结构的要求也不同。**

> [!info] 一个反复出现的主题：结构规整带来便利
> 从第 04 篇"完美二叉树让 116 能 $O(1)$ 空间"、到本章"完全二叉树让堆能用数组存"，再到第 02 篇"完美二叉树的层序最规整"——**"结构越规整，能利用的性质越多"这一主题贯穿了整个专栏。** 它提醒我们：**遇到问题时，先看看"输入有没有额外的结构约束"——那些约束往往就是解题的钥匙。**

## 第 6 章 常见误区与自测方法

### 5.1 四个高频误区

**误区一：链表版直接照抄数组版的"取 `mid`"。** 链表没有下标，无法随机访问，会写不出代码或写出 $O(n^2)$。

**误区二：快慢指针的终止条件写错。** 区间是 `[left, right)`，快指针的停止条件要用 `right`（`fast != right && fast.Next != right`），否则会越界或找错中点。

**误区三：模拟中序构造忘了先求长度。** 没有总长度，就无法确定左右子树的规模，递归无从驱动。

**误区四：把"平衡"当成"必须是唯一的那棵树"。** 题目只要求"一棵"高度平衡的 BST，答案不唯一（取左中点或右中点都可）。

### 5.2 一套自测用例

| 用例 | 检验什么 |
|------|---------|
| 空数组/空链表 | 空边界 |
| 单元素 `[1]` | 最简 |
| 两元素 `[1,2]` | 中点选择（左右均可） |
| 五元素 `[1,2,3,4,5]` | 常规平衡构造 |
| 链表含偶数个节点 | 快慢指针的中点位置 |

**其中"偶数个节点"最值得测**——它让"中点"有两个候选（左中或右中），最能暴露"区间边界"与"快慢指针终止条件"的 bug。**凡是取中点的题，都要用偶数长度的输入验证。**

## 第 7 章 构造题的验证与面试表达

### 7.1 如何验证构造结果

108/109 的答案不唯一，所以不能"对答案"。但可以用三条性质来验证：

**性质一，是合法 BST。** 跑一次 Validate BST（第 06 篇），确认"左小右大"成立。**这一步能抓住"取中点取错、左右挂反"这类错误。**

**性质二，是高度平衡的。** 跑一次平衡判定（第 03 篇），确认"每个节点左右高度差不超过 1"。**这一步能抓住"中点计算错误"导致的失衡。**

**性质三，包含了所有元素。** 对结果做一次中序遍历，应当得到原序列（有序数组或链表的值）。**这一步能抓住"漏掉某些元素"这类错误。**

**三条性质合起来，足以验证构造的正确性**——它们分别对应"顺序对""结构对""内容全"。

### 7.2 一个容易忽视的验证点

**"高度平衡"的验证尤其重要**——因为它是 108/109 的核心要求，却容易被"看起来对"的构造骗过。**取中点的方式稍有偏差（如 `mid = (left+right)/2` 与 `mid = left + (right-left)/2` 在负数下不同），就可能构造出"失衡"的树。** 而失衡的树在小规模输入下往往"看不出问题"，只有跑一次平衡判定才能确认。

**所以，"构造 + 验证"应当成对进行**——构造题不能只看"结果长得像不像"，而要用性质来验证。

### 7.3 面试表达

构造题的面试表达，建议按这个顺序：

1. **点出核心洞察**："取中点作根，能保证左右规模差不超过 1，从而保证平衡。"
2. **讲清递归**："递归地对左右子区间做同样的事。"
3. **讲复杂度**："时间 $O(n)$，空间 $O(\log n)$。"
4. **主动补充**："答案不唯一——取左中点或右中点都可以。"

**第 4 步尤其值得主动说**——它表明你理解"题目只要求一棵平衡 BST"，而非"唯一解"。**很多人在面试里纠结"我的答案和标准答案不一样"，其实题目根本没要求唯一。**

> [!info] 构造题与验证题是一对
> 第 06 篇的 Validate 是"验证"，本篇的构造是"生成"——**它们互为逆操作**：Validate 检查"是否满足 BST 性质"，构造则"生成满足性质的树"。**把它们成对理解，你就能用"验证"来检查"构造"的结果**（正如 7.1 节所做）。**这种"用逆操作验证正操作"的思路，是工程上常用的自检手段**——写编码器时用解码器验证、写序列化时用反序列化验证。

### 7.4 从"平衡"到"工程"

最后回到"平衡"这件事的工程意义。**平衡的 BST，高度是 $O(\log n)$，查找、插入、删除都是 $O(\log n)$**——这正是"有序集合"（如 Redis 的 Sorted Set、Java 的 `TreeMap`）能用 BST 类结构实现高效查询的原因。

**而"构造一棵平衡 BST"，对应到工程里，就是"把一批有序数据建成索引"**——数据库建索引时，正是要把有序数据组织成平衡的树（B+ 树），以便高效查询。**108/109 虽然是"简单题"，但它背后的"平衡构造"，正是数据库索引的地基。** 理解了这一点，你就明白为什么"取中点保证平衡"值得单独成题——**它是一整套索引技术的起点。**

## 第 8 章 有序结构的三种用法与面试追问

### 8.1 有序数组的三种用法

给定一个有序数组，我们至少有三种"利用它"的方式：

- **二分查找**：在 $O(\log n)$ 内定位一个值（第 03 篇）；
- **双指针夹逼**：在 $O(n)$ 内找一对满足条件的元素（第 05 篇）；
- **构造平衡 BST**：把它组织成一棵树，支持"动态插入/删除"（本篇）。

**三者的共同前提都是"有序"**——但用途不同：二分用于"静态查找"，双指针用于"找配对"，建树用于"支持动态操作"。**同一个"有序"，在不同需求下催生了不同的算法。**

**这解释了"为什么有序性如此重要"**——它不是某一种算法的专属，而是"一大类算法的共同前提"。**面试中看到"已排序"三个字，就该条件反射地意识到：二分、双指针、建树都可能用得上。**

### 8.2 数组与链表的"有序操作"差异

| 操作 | 有序数组 | 有序链表 |
|------|---------|---------|
| 随机访问中点 | $O(1)$ | $O(k)$ |
| 二分查找 | $O(\log n)$ | 不适用（无随机访问） |
| 构造平衡 BST | $O(n)$ | $O(n \log n)$（快慢指针）或 $O(n)$（模拟中序） |
| 动态插入 | $O(n)$（需移位） | $O(1)$（已知位置） |

**这张表的核心是"随机访问"**——数组有它，所以二分与"取中点"都很快；链表没有它，所以一切"按下标定位"的操作都要退化成遍历。**108 与 109 的难度差异，根源就在这一行。**

**但请注意最后一行**：链表在"动态插入"上反而更优（$O(1)$）。**这正是"没有哪种结构绝对更优"的又一例证**——数组擅长"静态、随机访问"，链表擅长"动态、局部修改"。**选哪种，取决于"你的数据是静态还是动态"。**

### 8.3 面试追问

**追问一："为什么取中点能保证平衡？"** 答：取中点使左右规模差不超过 1；递归下去，每层两棵子树规模都近乎相等，于是高度差不超过 1。

**追问二："链表版为什么不能照抄数组版？"** 答：链表不支持随机访问，"取 `mid`"这个操作无法 $O(1)$ 完成。

**追问三："链表版有没有 $O(n)$ 的解法？"** 答：有——用"模拟中序构造"，按中序顺序依次取用节点，避免反复找中点。

**追问四："答案唯一吗？"** 答：不唯一。取左中点或右中点都可，题目只要求"一棵"高度平衡的 BST。

**追问五："如果要求'完全平衡'（完美二叉树）呢？"** 答：只有节点数恰好为 $2^k - 1$ 时才可能；否则无法构造完美二叉树，只能保证高度平衡。

### 8.4 一个值得记住的"结构选择"视角

108/109 这对题，最终教给我们的其实是一个"**结构选择**"的视角：**同一件事（构造平衡 BST），在数组上 $O(n)$、在链表上要动脑筋**——因为**数据结构的"能力差异"，直接决定了算法的难度。**

**这与本专栏开篇（第 01 篇）讲的"数组与链表是两种契约"首尾呼应**：数组用"连续内存"换来"随机访问"，链表用"分散存储"换来"局部修改"。**108 与 109 的差异，正是这两种契约在"构造平衡树"这一具体任务上的投影。** 理解了这一点，你就把"数据结构的选择"与"算法的设计"这两件事，联系到了一起——**而这，正是整个算法学习的核心命题。**

> [!note] 结构决定难度
> 很多人以为"算法题考的是算法"，其实**很多题考的首先是"你对数据结构的理解"**。108 与 109 的算法思路完全一样（都是"取中点递归"），难度差异却全来自"取中点"这一操作在两种结构上的代价。**遇到"思路一样、难度不同"的题，先问一句"是不是数据结构的能力不同"——这往往就是答案。**

## 第 9 章 构造题的调试与落点

### 9.1 调试构造题的方法

**构造题的结果不唯一，所以"对答案"没用——必须用"性质"来验证。** 调试时按下面的顺序：

1. **先验"是合法 BST"**（跑 Validate）——排除"左右挂反""根值选错"；
2. **再验"是平衡的"**（跑平衡判定）——排除"中点计算错误"；
3. **最后验"元素齐全"**（跑中序）——排除"漏掉元素"。

**"先验合法、再验平衡、最后验齐全"**——这个顺序由"最基础的错误"到"最细节的错误"，能最快定位问题。

### 9.2 两个容易踩的坑

**坑一，中点计算。** `mid = (left + right) / 2` 与 `mid = left + (right-left)/2` 在**非负下标**下等价，但后者能防溢出。**建议统一用后者。**

**坑二，链表版的中点定位。** 快慢指针的终止条件要结合"区间右界 `right`"，写错就会找错中点或越界。**建议先用"3 节点链表"手走一遍。**

### 9.3 落点

**构造专题的落点，是"取中点保证平衡"这一性质，以及"模拟中序"这一优化视角**：

- **"取中点保证平衡"** 揭示了"均分 ⇒ 规模相近 ⇒ 高度平衡"这一链条，它是二分判定树的显式化；
- **"模拟中序"** 展示了"换个视角，让某个操作不再需要"这一优化思路——**它绕开了"找中点"，而非把"找中点"做得更快。**

**后者尤其有价值**——它提醒我们：**优化的最高境界，不是"把慢操作变快"，而是"让慢操作不再需要"。** 这与线性表专栏第 06 篇（用阶乘数系绕开生成全部排列）是同一种思路。

> [!info] 两种优化思路
> 优化有两条路：**其一，把某个操作做得更快**（如用哈希表把查找降到 $O(1)$）；**其二，换一个视角，让那个操作不再需要**（如用模拟中序绕开找中点）。**后者往往更彻底、更优雅**，但需要更深的洞察。**本专栏里两种都有**（哈希表加速是前者，模拟中序是后者）——**能区分它们，并优先寻找"让操作消失"的机会，是进阶的标志。**

### 9.4 一个可以迁移的检查清单

| 检查项 | 对应问题 |
|--------|---------|
| 中点用防溢出写法 | 溢出 |
| 结果是合法 BST | 挂反、选错根 |
| 结果是平衡的 | 中点偏差 |
| 元素齐全 | 漏元素 |
| 链表版快慢指针终止条件 | 越界、找错中点 |

**这份清单，是构造题"自查"的固定套路。** 它把"该检查什么"从"凭经验"变成了"照清单"。

### 9.5 一个跨领域的落点

**"把有序数据建成平衡树"这件事，在工程里就是"建索引"。** 数据库的 B+ 树索引、Redis 的跳表、乃至搜索引擎的倒排索引，**本质都是"把数据组织成支持高效查询的结构"**。**108/109 是这件大事的最小模型**——它让你从"取中点"这一行代码里，看到"索引"这一整套技术的起点。**理解了这一点，你就明白为什么"简单题"也值得认真对待——它们往往是复杂系统的一块基石。**

---

### 9.6 一个值得记住的边界

**"答案不唯一"是构造题的一个特点。** 108/109 都只要求"一棵"高度平衡的 BST——取左中点或右中点都可以。**面试中若你的答案与"标准答案"不同，不必怀疑自己**——**只要满足"是 BST + 高度平衡"，就是正确解。** 主动说出"答案不唯一"，反而能体现你对题意的准确把握。

**最后补充一点**：链表版的递归解法空间是 $O(\log n)$（栈），若要严格 $O(1)$，需把递归改成迭代——**但"找中点"这一操作，无论如何都需要遍历，这是链表结构的固有限制。**

**再补充一点**：数组版若要处理"含重复元素的有序数组"，构造仍然成立（BST 允许相等），但需先明确"相等值放左还是放右"的约定——**否则会构造出不符合预期的 BST。** 若约定"相等放右"，则取中点后需保证"左侧全小于、右侧不小于"——**这个约定必须与后续的查找逻辑保持一致。** 同理，BST 是否"严格"（允许不允许相等），也要与查找时的 `<` / `<=` 对齐——**构造与查找，必须遵守同一份"有序性约定"。**

## 小结

本篇用两道题，把"分治 + 平衡"这一组合讲透。数组版（108）的关键是理解"取中点作根保证平衡"——它本质上是"把二分查找的判定树显式造出来"；链表版（109）的难点在于"链表不支持随机访问"，于是有了两种解法：**快慢指针找中点**（$O(n \log n)$）与**模拟中序构造**（$O(n)$）。后者尤其有价值——它展示了"换个视角，让某个操作不再需要"这一优化思路。

贯穿全篇的核心认知有两条。其一，**"取中点"是构造平衡结构的通用手法**——它的依据是"均分保证规模相近、进而保证高度平衡"。其二，**当某个操作反复昂贵时，不妨问一句"它是不是根本不需要做"**——模拟中序解法正是绕开了"找中点"，而非把"找中点"做得更快。**把这两条握住，你面对任何"构造平衡结构"或"优化重复操作"的题，都有了新的切入点。**

下一篇 [[09 二叉树深度问题：最小深度、最大深度与 BFS-DFS 取舍]] 会回到更基础的深度问题。最小深度与最大深度常被一起问，但解题逻辑并不对称——最大深度天然适合 DFS，最小深度则要格外警惕"空子树不能直接取 min"这个经典陷阱。
