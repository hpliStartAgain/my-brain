# 二叉搜索树判定与修复：Validate BST 与 Recover BST

**摘要：**

二叉搜索树（BST）是二叉树专题里最重要的特殊结构，因为它提供了一个极强的约束：**中序遍历结果必须严格递增**。LeetCode 98（Validate BST）与 99（Recover BST）看似一个是"合法性判断"、一个是"错误修复"，底层依赖却完全相同。本文要讲清三件事：其一，为什么"只比较父子大小"是错误的局部视角（并用一个反例说明 BST 约束是"整棵子树"而非"父子之间"）；其二，为什么 Validate BST 需要"全局上下界"或"中序前驱"这两种等价的正确写法；其三，为什么 Recover BST 可以通过中序序列里的"逆序对"精确定位被交换的两个节点。随后补充 BST 有序性在"第 k 小元素""迭代器"等问题上的威力。全文用 Go 语言实现，并逐层追问：上下界法与中序法为什么等价、逆序对为什么能定位错误、以及"第二个节点为什么要持续更新"。

## 第 1 章 LeetCode 98：为什么局部判断不够

### 1.1 题目

**LeetCode 98 - Validate Binary Search Tree**（中等）

给你一个二叉树的根节点 `root`，判断它是否是一个有效的二叉搜索树。BST 的定义：节点的左子树只包含小于当前节点的数，右子树只包含大于当前节点的数。

```text
输入: root = [2,1,3]     →  输出: true
输入: root = [5,1,4,null,null,3,6]  →  输出: false
```

### 1.2 常见错误思路：只比较父子

很多人会写：

```go
root.Left.Val < root.Val && root.Val < root.Right.Val
```

然后递归检查左右子树。**这是不够的**——因为 BST 约束不是"父子之间"，而是"**整个左子树都小于根，整个右子树都大于根**"。

反例：

```text
    5
   / \
  1   6
     / \
    3   7
```

节点 `3 < 6` 没问题，但它位于根 `5` 的**右子树**里，因此必须大于 `5`——`3 < 5`，所以这棵树其实非法。**只看父子关系，就会漏掉这种"跨越多个层级"的违规。**

### 1.3 正确思路一：上下界递归

**解法是：给每个节点传递一个"允许的取值区间" `(lower, upper)`，节点值必须严格落在这个开区间内。** 这个区间由所有祖先共同约束而来：

```go
func isValidBST(root *TreeNode) bool {
    // 用指针表示"无界"，避免用极值哨兵带来的溢出风险
    var validate func(node *TreeNode, lower, upper *int) bool
    validate = func(node *TreeNode, lower, upper *int) bool {
        if node == nil {
            return true
        }
        if lower != nil && node.Val <= *lower {
            return false
        }
        if upper != nil && node.Val >= *upper {
            return false
        }
        // 进入左子树：上界收紧为当前值；进入右子树：下界收紧为当前值
        return validate(node.Left, lower, &node.Val) &&
            validate(node.Right, &node.Val, upper)
    }
    return validate(root, nil, nil)
}
```

**注意这里传的不是"父节点的值"，而是"当前节点允许落入的区间"。** 进入左子树时上界收紧为当前值、进入右子树时下界收紧为当前值——**区间随着下钻不断收窄，这正是"整棵子树"约束的精确表达。**

> [!warning] 生产避坑：别用极值哨兵做上下界
> 有人用 `math.MinInt64` / `math.MaxInt64` 作为初始上下界。**若节点值本身可能就是这些极值，判断就会出错。** 更稳的做法是用**指针**表示"无界"（`nil` 代表没有约束），彻底规避溢出与极值冲突。**"用 `nil` 表示无界"这一技巧，是把"哨兵值可能与真实值冲突"这一问题从根上消除。**

### 1.4 正确思路二：中序递增检查

**因为 BST 的中序严格递增，所以也可以在中序遍历中，检查"前一个节点值是否始终小于当前节点值"。**

```go
func isValidBSTInorder(root *TreeNode) bool {
    var prev *TreeNode
    var inorder func(node *TreeNode) bool
    inorder = func(node *TreeNode) bool {
        if node == nil {
            return true
        }
        if !inorder(node.Left) {
            return false
        }
        if prev != nil && prev.Val >= node.Val {
            return false // 不严格递增，非法
        }
        prev = node
        return inorder(node.Right)
    }
    return inorder(root)
}
```

**这两种方法本质一致**：上下界法**显式**传递"合法区间"，中序法**隐式**利用了"中序的全局顺序"。**它们是从两个角度看同一件事——一个从"约束"出发，一个从"顺序"出发。**

## 第 2 章 LeetCode 99：Recover BST

### 2.1 题目

**LeetCode 99 - Recover Binary Search Tree**（中等）

给你一棵二叉搜索树的根节点 `root`，**树中有且只有两个节点的值被错误地交换**。请在不改变树结构的情况下，恢复这棵树。

### 2.2 题目本质：中序序列里的逆序对

**把 BST 做中序遍历，本应得到一个严格递增序列。** 两个节点被交换后，这个递增序列会出现"逆序"。

假设原序列是 `1, 2, 3, 4, 5`：

- 若交换**相邻**的 `2` 和 `3`，得到 `1, 3, 2, 4, 5`——**只出现一次逆序**（`3 > 2`）；
- 若交换**不相邻**的 `2` 和 `5`，得到 `1, 5, 3, 4, 2`——**出现两次逆序**（`5 > 3` 和 `4 > 2`）。

**由此得到定位规则**：

- 第一次看到 `prev.Val > curr.Val` 时，记录 `first = prev`；
- 每次看到逆序时，都更新 `second = curr`。

最后交换 `first` 与 `second` 的值即可。

### 2.3 Go 实现

```go
func recoverTree(root *TreeNode) {
    var first, second, prev *TreeNode
    var inorder func(node *TreeNode)
    inorder = func(node *TreeNode) {
        if node == nil {
            return
        }
        inorder(node.Left)
        if prev != nil && prev.Val > node.Val {
            if first == nil {
                first = prev // 第一次逆序：记录较大的那个
            }
            second = node // 每次都更新：记录较小的那个
        }
        prev = node
        inorder(node.Right)
    }
    inorder(root)
    first.Val, second.Val = second.Val, first.Val // 交换值（不改结构）
}
```

**复杂度**：时间 $O(n)$，空间 $O(h)$（递归栈）。

### 2.4 为什么"第二个节点要持续更新"

这是本题最精妙、也最容易写错的一点。因为**非相邻交换时会出现两次逆序**：

- 第一次逆序里的**较大值**，才是真正错位的"前一个节点"（`first`）；
- 第二次逆序里的**较小值**，才是真正错位的"后一个节点"（`second`）。

**所以 `first` 只在第一次逆序时设定，而 `second` 需要在每次逆序时都更新**——这样，相邻交换（一次逆序）与非相邻交换（两次逆序）都能被正确处理。

> [!info] 逆序对：一个可以复用的"定位工具"
> "在一个本应有序的序列里，用逆序对定位被交换的元素"——这是一个通用的技巧。**它把"找出哪两个元素错位"这一结构问题，转化成了"扫描序列找逆序"这一线性问题。** 理解了它，你不仅会解 Recover BST，也能处理"数组中两个元素被交换，找出它们"这类变体。

## 第 3 章 中序有序性质到底强在哪里

### 3.1 把结构题降成序列题

中序有序的价值，在于它**把树问题降成了序列问题**：

- Validate BST → "序列是否严格递增"；
- Recover BST → "递增序列中找被交换的两个元素"。

**这意味着搜索树题很多时候不需要硬想树形结构，而是先问一句：能不能把它投影成一个有序序列问题？**

### 3.2 更多依赖中序有序的题

| 题目 | 中序有序如何被用 |
|------|-----------------|
| LC 98 Validate BST | 检查递增 |
| LC 99 Recover BST | 找逆序对 |
| LC 230 第 k 小的元素 | 中序第 k 个 |
| LC 173 BST 迭代器 | 用栈模拟中序，惰性取下一个 |
| LC 108 有序数组转 BST | 反向利用"中序即有序数组" |

**这张表说明：一旦你意识到"BST 的中序 = 有序数组"，一大批题都会立刻变得熟悉**——它们不过是"有序数组上的操作"换了件树的外衣。

### 3.3 第 k 小的元素（LeetCode 230）

**题目**：给定 BST 的根节点与整数 `k`，返回第 `k` 小的元素。

**解法**：中序遍历，第 `k` 个访问到的节点即为答案——**因为它就是有序序列里的第 `k` 个。**

```go
func kthSmallest(root *TreeNode, k int) int {
    stack := []*TreeNode{}
    curr := root
    for curr != nil || len(stack) > 0 {
        for curr != nil { // 一路向左
            stack = append(stack, curr)
            curr = curr.Left
        }
        curr = stack[len(stack)-1]
        stack = stack[:len(stack)-1]
        k--
        if k == 0 {
            return curr.Val // 第 k 个中序节点
        }
        curr = curr.Right
    }
    return -1
}
```

**这道题是"中序即有序数组"最直白的体现**——"第 k 小"在有序数组里就是"下标 k-1"，在这里就是"中序的第 k 个"。**把 BST 看成"一个用树形组织的有序数组"，这道题就毫无难度。**

## 第 4 章 两道主线题的对照

| 维度 | LC 98 Validate | LC 99 Recover |
|------|---------------|---------------|
| 目标 | 判断是否合法 | 定位并修复错误 |
| 中序的作用 | 检查是否递增 | 找逆序对 |

| 输出 | 布尔值 | 修改树（交换值） |

## 第 4 章 延伸：BST 中序有序的更多应用

"BST 的中序 = 有序数组"这一映射，还能解锁一大批题。本章再给三道，进一步巩固这一视角。

### 4.1 BST 迭代器（LeetCode 173）

**题目**：实现一个 BST 迭代器，`Next()` 返回下一个最小的元素，`HasNext()` 判断是否还有元素。要求 `Next()` 的均摊复杂度是 $O(1)$。

**思路**：**用栈模拟中序遍历，但"惰性"地前进**——不一次性把整棵树中序展开，而是"每次 `Next()` 才走一步"。这正好是第 01 篇中序迭代写法的"分步版"：

```go
type BSTIterator struct {
    stack []*TreeNode
}

func Constructor(root *TreeNode) BSTIterator {
    it := BSTIterator{}
    it.pushLeft(root) // 先把最左路径压栈
    return it
}

func (it *BSTIterator) pushLeft(node *TreeNode) {
    for node != nil {
        it.stack = append(it.stack, node)
        node = node.Left
    }
}

func (it *BSTIterator) Next() int {
    node := it.stack[len(it.stack)-1]
    it.stack = it.stack[:len(it.stack)-1]
    it.pushLeft(node.Right) // 转向右子树，继续压最左路径
    return node.Val
}

func (it *BSTIterator) HasNext() bool {
    return len(it.stack) > 0
}
```

**为什么均摊 $O(1)$？** 因为每个节点至多被压栈一次、弹栈一次——**与第 01 篇中序迭代的摊还分析完全一致。** 这道题是"中序迭代"从"一次性遍历"到"可暂停/可续的迭代器"的升级。

### 4.2 BST 中序遍历中的最小绝对差（LeetCode 530）

**题目**：给你一棵 BST 的根节点，返回树中任意两不同节点值之间的最小差值。

**思路**：**最小差一定出现在"中序序列的相邻两个元素"之间**——因为在有序序列里，差值最小的两个数必然相邻。

```go
func getMinimumDifference(root *TreeNode) int {
    ans := math.MaxInt32
    var prev *TreeNode
    var inorder func(node *TreeNode)
    inorder = func(node *TreeNode) {
        if node == nil {
            return
        }
        inorder(node.Left)
        if prev != nil && node.Val-prev.Val < ans {
            ans = node.Val - prev.Val // 只比相邻
        }
        prev = node
        inorder(node.Right)
    }
    inorder(root)
    return ans
}
```

**这道题的洞察是"有序序列里最小差必相邻"**——它把"比较所有节点对"（$O(n^2)$）降成了"比较相邻"（$O(n)$）。**这又一次说明：一旦把 BST 投影成有序序列，很多"看似要两两比较"的问题，都变成了"相邻比较"。**

### 4.3 二叉搜索树中的搜索（LeetCode 700）

**题目**：给定 BST 的根节点和一个值，在 BST 中找到该节点并返回。

```go
func searchBST(root *TreeNode, val int) *TreeNode {
    if root == nil || root.Val == val {
        return root
    }
    if val < root.Val {
        return searchBST(root.Left, val) // 比根小，去左边
    }
    return searchBST(root.Right, val)    // 比根大，去右边
}
```

**这道题展示了 BST 的"查找"本质**——每一步都能排除一半，时间 $O(\log n)$（平衡时）。**它是"BST 为什么快"的最直接体现**：因为"左小右大"，每次比较都能决定"往哪边走"，从而像二分一样排除一半。

### 4.4 三道延伸题的共性

173、530、700 三道题，都在用"BST 的中序有序"或"左小右大"这两条性质：**173 用中序的"顺序"，530 用中序的"相邻性"，700 用左小右大的"可判定性"。** 它们共同说明：**BST 的一切优势，都源于"它把顺序编码进了结构"**——理解这一点，你面对任何 BST 题，都会先问一句"它能不能用有序性简化"。

## 第 5 章 常见误区与自测方法

### 5.1 四个高频误区

**误区一：Validate BST 只比较父子。** 会漏掉"跨层级"的违规（如第 1.2 节的反例）。

**误区二：用极值哨兵做上下界。** 若节点值恰好是极值，判断出错。用 `nil` 表示无界更稳。

**误区三：Recover BST 的 `second` 只记录一次。** 非相邻交换有两次逆序，`second` 必须每次更新。

**误区四：Recover BST 去"改结构"。** 题目要求不改变树结构，只需交换两个节点的**值**即可。

### 5.2 一套自测用例

| 用例 | 检验什么 |
|------|---------|
| `[2,1,3]` | 合法 BST |
| `[5,1,4,null,null,3,6]` | 跨层级违规 |
| `[1,1]`（含相等） | 严格递增（相等也非法） |
| 相邻交换 `[1,3,2]` | 一次逆序 |
| 非相邻交换 `[1,5,3,4,2]` | 两次逆序 |

**其中"跨层级违规"与"非相邻交换"最值得测**——前者专治"只比父子"，后者专治"`second` 只记一次"。**凡是 BST 判定/修复题，都要用这两个用例来验证。**

## 第 6 章 BST 的工程意义与面试表达

### 6.1 BST 在工程中的影子

**普通 BST 在工程里其实很少单独使用**——因为它在"有序插入"时会退化成链（高度变 $n$，查找退化到 $O(n)$）。**工程上用的是"自平衡的 BST"**：AVL 树、红黑树、B 树/B+ 树。

**但它们的内核都是 BST 的"左小右大"**——自平衡只是加上了"插入/删除后重新调整、保持高度 $O(\log n)$"的机制。理解了普通 BST，你就理解了这些自平衡树的"地基"：

- **红黑树**：`std::map`、Java 的 `TreeMap`、Linux 内核的调度器都用它；
- **B+ 树**：数据库索引的主力，它是"多路搜索树"，本质是 BST 的"多叉推广"（一次比较排除更多分支）；
- **跳表**：Redis 的有序集合用它，是"用概率方法模拟平衡树"的替代方案。

**它们存在的理由，都指向 BST 的那个软肋——"有序插入会退化"**。**自平衡机制，正是为了消除这个软肋。** 所以"为什么要自平衡"，答案就是"因为普通 BST 会退化"。

### 6.2 为什么 B+ 树一次能排除更多

**BST 是二叉的——每个节点只有两个孩子，一次比较只能排除一半。** 而 B+ 树是多叉的（一个节点有几百个孩子），**一次比较能排除更多分支，于是树高更低、磁盘 I/O 更少。** 这正是"数据库索引用 B+ 树而非红黑树"的原因——**磁盘 I/O 是数据库的瓶颈，降低树高能显著减少 I/O 次数。**

**从 BST 到 B+ 树的推广，本质是"把二叉变成多叉"**——这与本篇"从二叉树推广到 N 叉树"（第 01 篇第 9 章）是同一种推广思路。**理解了 BST，你就理解了 B+ 树的"内核"；理解了"二叉到多叉"，你就理解了"为什么数据库用 B+ 树"。**

### 6.3 面试表达：先讲性质，再讲技巧

BST 题的面试表达，建议按这个顺序：

1. **先点出核心性质**："BST 的中序遍历是严格递增的，这是解这类题的关键。"
2. **再讲具体技巧**："Validate 我用上下界递归，Recover 我用中序找逆序对。"
3. **然后讲为什么**："Recover 之所以能用逆序对定位，是因为交换两个节点会让有序序列出现 1 或 2 个逆序。"
4. **最后讲边界**："Validate 要注意'整棵子树'的约束，不能只比父子。"

**第 1 步是关键**——它表明你不是在背题，而是抓住了 BST 的本质。**面试官听到"中序有序"这四个字，就知道你理解了这个结构的核心。**

> [!info] 一个结构的"核心性质"，往往就是它的"解题钥匙"
> BST 的核心性质是"中序有序"；栈的核心性质是"后进先出"；队列的核心性质是"先进先出"；哈希表的核心性质是"$O(1)$ 按值查找"。**每学一个结构，都应该问一句"它最核心的性质是什么"——因为那道性质，往往就是解这类题的钥匙。** 本专栏反复出现的"先找性质、再想技巧"，正是这个习惯的体现。

### 6.4 从"验证"到"修复"：一个值得体会的对照

**Validate（验证）与 Recover（修复）是一对**：一个问"是否合法"，一个问"如何修正"。**它们在现实系统中也成对出现**——数据校验与数据修复、配置检查与配置纠正、健康检查与故障自愈。**"先能发现错误，再能修正错误"是工程系统的基本能力**，而 Recover BST 正是这个能力在数据结构上的最小演练：**它用"中序逆序对"这一不变量，同时完成了"发现"与"修正"。**

## 第 7 章 BST 题的解法选择与面试追问

### 7.1 中序遍历的三种实现，以及该选哪一种

本篇的两道题都依赖"中序遍历"，而第 01 篇给过中序的三种实现：递归、显式栈、Morris。**BST 题该选哪一种？**

- **递归**：代码最短，但空间 $O(h)$。**Validate/Recover 的"上下界法/逆序对法"用递归最自然。**
- **显式栈**：空间同为 $O(h)$，但可"分步"（适合迭代器，如 173 题）。
- **Morris**：空间 $O(1)$，但会临时改结构。**若题目要求"$O(1)$ 空间"，Morris 是唯一选择。**

**面试中的建议**：先用递归给出解法（清晰、易讲），若面试官追问"能否 $O(1)$ 空间"，再提 Morris。**而 Recover BST 恰恰有一道"要求 $O(1)$ 空间"的进阶版**——那正是 Morris 的用武之地。

### 7.2 Recover BST 的 $O(1)$ 空间版本

**题目进阶**：若要求 Recover BST 用 $O(1)$ 空间，该怎么办？

**答案是 Morris 中序遍历**——在 Morris 的"访问节点"时机，做与递归版相同的"逆序对检测"。**Morris 把"中序的访问顺序"暴露成了一次显式的循环，于是"检测逆序对"这一步可以原样嵌入**：

```go
// Morris 版 Recover BST（示意，省略树结构恢复的细节）
func recoverTreeMorris(root *TreeNode) {
    var first, second, prev *TreeNode
    cur := root
    for cur != nil {
        if cur.Left == nil {
            // 访问 cur：检测逆序
            if prev != nil && prev.Val > cur.Val {
                if first == nil {
                    first = prev
                }
                second = cur
            }
            prev = cur
            cur = cur.Right
        } else {
            // 找前驱，建立/断开线索
            p := cur.Left
            for p.Right != nil && p.Right != cur {
                p = p.Right
            }
            if p.Right == nil {
                p.Right = cur
                cur = cur.Left
            } else {
                p.Right = nil
                // 访问 cur：检测逆序
                if prev != nil && prev.Val > cur.Val {
                    if first == nil {
                        first = prev
                    }
                    second = cur
                }
                prev = cur
                cur = cur.Right
            }
        }
    }
    first.Val, second.Val = second.Val, first.Val
}
```

**注意"访问 cur"的逻辑出现了两次**（左孩子为空时、断开线索时）——**这是因为 Morris 遍历里，"访问节点"的时机有两个入口。** 把这段逻辑抽成一个函数，就能避免重复。

**这道进阶题的价值，在于它展示了"把递归逻辑嵌入 Morris 循环"的一般方法**——**只要递归版里"在访问时机做的事"能抽出来，就能原样放进 Morris 的访问时机。** 理解了这一点，你就能把任何"中序 + 处理"的算法改成 $O(1)$ 空间版。

### 7.3 面试追问

**追问一："Validate BST 为什么不能只比父子？"** 答：BST 约束是"整棵子树"的，跨层级的违规（如右子树里有个小于根的值）会被漏掉。

**追问二："上下界法与中序法为什么等价？"** 答：上下界显式传递"合法区间"，中序隐式利用"全局顺序"——它们是从"约束"与"顺序"两个角度看同一件事。

**追问三："Recover BST 的 `second` 为什么要每次更新？"** 答：非相邻交换会产生两次逆序，`first` 取第一次的较大值，`second` 取最后一次的较小值。

**追问四："为什么用 `nil` 而不是极值做上下界？"** 答：极值可能与真实节点值冲突（当节点值恰好是 `MinInt64` 时），用 `nil` 表示"无界"能彻底规避。

**追问五："中序法能用于任意二叉树吗？"** 答：能"跑"，但只有 BST 的中序才有"递增"意义——对普通二叉树，中序只是一个顺序，不具备"有序性"。

### 7.4 一个统一的理解

**BST 题的一切，都可以归结为"中序有序"这一个性质。** Validate 用它检查递增、Recover 用它找逆序、第 k 小用它定位、迭代器用它分步、最小绝对差用它比相邻……**它们是同一性质的不同应用。**

**所以学 BST，真正要记住的不是"这些题的解法"，而是"中序有序"这四个字。** 遇到任何 BST 题，先问一句"这题怎么用中序有序"——**答案往往就浮现了。** 这与本专栏反复强调的"先找性质、再想技巧"完全一致。

> [!info] 一个性质，解锁一族题
> "中序有序"这一性质，解锁了 Validate、Recover、第 k 小、迭代器、最小绝对差等一整族题。**这就是"抓住核心性质"的价值**——它不是让你"多会几道题"，而是让你"看到这类题就知道往哪想"。**每个数据结构都有这样一个"核心性质"，找到它，比记住十道题更有用。**

## 第 8 章 BST 题的验证、调试与落点

### 8.1 验证 BST 题的三类用例

**用例一，跨层级违规。** `[5,1,4,null,null,3,6]`——它专治"只比父子"。**正确答案是 `false`（`3 < 5` 却在右子树）。**

**用例二，含相等值。** `[1,1]`——BST 要求"严格递增"，相等也非法。**它检验"是否用了 `<` 而非 `<=`"。**

**用例三，相邻与非相邻交换。** 对 Recover，用 `[1,3,2]`（相邻，一次逆序）与 `[1,5,3,4,2]`（非相邻，两次逆序）各测一次。**它们检验"`first` 只记一次、`second` 每次更新"是否正确。**

**这三类用例，覆盖了 BST 题最常见的 bug。**

### 8.2 调试 BST 题的方法

**方法一，先求中序序列。** 对任何 BST 题，**先手算它的中序序列**——很多问题在中序序列上会变得直观（如"是否递增""逆序对在哪"）。

**方法二，用"上下界"复核。** 对 Validate，除了写"上下界法"，还可以**手算每个节点的合法区间**，对照代码的区间传递是否正确。

**方法三，检查"哨兵/初始值"。** 对 Recover，检查 `first`/`second` 的初始值（`nil`）；对 Validate，检查上下界是否用 `nil`（而非极值）。

**"先求中序"是 BST 题调试的第一手段**——它把树的问题，立刻转成了序列的问题，而序列问题更容易验证。

### 8.3 落点

**BST 题的落点，是"中序有序"这一性质，以及"局部 vs 全局"这一认知**：

- Validate 教我们"**局部的大小关系不等于全局合法**"——BST 约束是"整棵子树"的；
- Recover 教我们"**用不变量（中序递增）定位错误**"——逆序对就是那个不变量被破坏的证据。

**这两条认知，超越了 BST 本身**：前者提醒我们"判定条件要考虑全局约束"，后者提醒我们"错误往往表现为不变量的破坏"。**理解了它们，你在面对任何"判定"与"修复"类问题时，都会先问一句"全局约束是什么、不变量是什么"。**

> [!info] 从 BST 到"不变量思维"
> Recover BST 用"中序递增"这一不变量定位错误——**这是"不变量思维"的一个漂亮范例**。**在系统设计里，我们同样依赖不变量**（如"账户余额 = 所有交易之和""缓存与数据库最终一致"），一旦不变量被破坏，就说明出了问题。**Recover BST 虽小，却把"用不变量发现并修复错误"这一工程思路，演示得淋漓尽致。**

### 8.4 一个可以迁移的检查清单

写任何 BST 题后，用这份清单自查：

| 检查项 | 对应问题 |
|--------|---------|
| 是否用 `nil` 而非极值做上下界 | 溢出与极值冲突 |
| 是否处理了"含相等值" | 严格递增的边界 |
| 是否用中序（而非父子比较） | 跨层级违规 |
| 是否用中序（而非全局扫描） | 效率 |
| `first`/`second` 更新规则是否正确 | 相邻/非相邻交换 |

**这份清单，是 BST 题"自查"的固定套路。** 它把"该检查什么"从"凭经验"变成了"照清单"——**这正是把经验结构化的价值。**

---

### 8.5 一个值得记住的对照：BST 与堆

**BST 与堆都是二叉树，但"有序"的程度不同**：BST 要求"左小右大"（**全局有序**），堆只要求"父节点与孩子的大小关系"（**部分有序**）。**这个差别，决定了它们的用途**：

- BST 支持"$O(\log n)$ 查找任意值"（因为全局有序，可二分）；
- 堆只支持"$O(1)$ 取最值"（因为只有父子有序，无法查找任意值）。

**"有序程度决定能力"**——这是一条值得记住的规律。**理解了它，你就明白为什么"求最值"用堆（$O(1)$）、"查找任意值"用 BST（$O(\log n)$）**——**它们各自利用了"自己那份有序性"。**

**最后补充一点**：Recover BST 若要求"交换节点而非交换值"（当节点携带额外数据时），代码需要改为"在结构上交换两个节点的位置"，或调整数据归属。**面试中主动提这一点，能体现你对"值语义 vs 节点语义"的敏感**——这正是"改值"与"改结构"这两类操作的分野。

**再补充一点**：Validate 的上下界法用 `nil` 表示"无界"，是 Go 里规避"极值冲突"的惯用写法；若用整数哨兵（如 `math.MinInt64`），需先确认节点值不会取到它。**"用 `nil` 而非极值表示无界"，是把"哨兵可能与真实值冲突"这一问题从根上消除。** 同理，中序法用"前驱节点"比较，也不需要任何哨兵——**两种写法都天然规避了"极值冲突"。**

## 小结

本篇用两道题，把 BST 最重要的性质——**中序有序**——用到了极致。Validate BST 要理解"BST 约束是整棵子树而非父子之间"，于是需要"全局上下界"或"中序前驱"这两种等价写法；Recover BST 则把"定位被交换的两个节点"转化为"扫描中序序列找逆序对"，其中"`first` 只记一次、`second` 每次更新"这一细节，是处理相邻/非相邻交换两种情形的关键。

贯穿全篇的核心认知有两条。其一，**BST 的中序 = 有序数组**——一旦建立这个映射，Validate、Recover、第 k 小、迭代器等一大批题，都不过是"有序数组上的操作"换了件外衣。其二，**"约束降维"是 BST 题的通用思路**——用"左小右大"这一强约束，把结构问题降成序列问题。**把这两条握住，你面对任何 BST 题，都能先问一句"它能不能投影成有序序列"。**
