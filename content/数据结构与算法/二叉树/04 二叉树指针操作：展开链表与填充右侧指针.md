# 二叉树指针操作：展开链表与填充右侧指针

**摘要：**

前面几篇的树题都在"读树"——遍历、判断、汇总。本篇开始"改树"：在**原地修改指针**的前提下，把二叉树重构成另一种结构。这类题的难度会陡然上升，因为一旦开始动指针，**递归的副作用（修改是否会影响尚未处理的子树）**与**控制边界（什么时候能安全地改写某个指针）**都会变得微妙。本文用两道题把"改树"的两类技巧讲透：LeetCode 114（展开为链表）是在**深度方向**上重连指针——把每个节点变成一条只有右指针的链；LeetCode 116/117（填充右侧指针）则是在**横向（层）方向**上建立连接——让每层节点串成一条链。两者恰好对应"纵向重连"与"横向连接"两类指针操作。本文用 Go 语言完整实现，并逐层追问：为什么展开要"先存右子树"、为什么 116 能省掉队列而 117 不能、以及原地修改时"顺序"为什么如此致命。

---

## 第 1 章 从"读树"到"改树"：难度的跃升

### 1.1 读树与改树的根本区别

- **读树**：函数是"纯"的——它只读取节点信息、返回结果，不改变树的结构。你可以放心地递归，因为子问题之间互不干扰。
- **改树**：函数有"副作用"——它会修改指针。此时**递归的顺序、修改的时机**都会影响结果，因为你可能在"还没处理完某个子树"时就改动了它。

**这就是"改树"题的难点来源：不是算法更复杂，而是"副作用"引入了新的约束。** 你必须时刻问自己一句：**"我这一步修改，会不会破坏我接下来还要用的结构？"**

### 1.2 两类指针操作

本篇两道题，恰好代表两类不同的指针重连：

| 题目 | 重连方向 | 目标结构 |
|------|---------|---------|
| LC 114 展开为链表 | **纵向**（深度方向） | 每个节点只有右指针，形成一条链 |
| LC 116/117 填充右侧指针 | **横向**（层方向） | 每层节点串成一条链 |

**把这两类方向分开看，思路会清晰很多**：一个是在"树变链"的纵向压缩，一个是在"层变链"的横向连接。

## 第 2 章 LeetCode 114：二叉树展开为链表

### 2.1 题目

**LeetCode 114 - Flatten Binary Tree to Linked List**（中等）

给你二叉树的根节点 `root`，将它展开为一个单链表：展开后的单链表应该同样使用 `TreeNode`，其中 `Right` 子指针指向链表中下一个节点，而 `Left` 子指针始终为 `nil`。展开后的顺序应与二叉树**前序遍历**的顺序一致。

```text
输入: root = [1,2,5,3,4,null,6]
输出: [1,null,2,null,3,null,4,null,5,null,6]
```

### 2.2 核心观察：把左子树"插"到右子树之前

**前序顺序是"根 → 左 → 右"**，所以展开后的链应当是：根，然后是（展开后的）左子树，然后是（展开后的）右子树。

于是，对每个节点，我们只需做一件事：**把"展开后的左子树"整体接到"根与右子树之间"**。具体地：找到左子树展开后的**尾节点**，让它的 `Right` 指向原右子树；再让根的 `Right` 指向原左子树，并把根的 `Left` 置空。

### 2.3 递归写法：后序返回"尾节点"

```go
func flatten(root *TreeNode) {
    var dfs func(node *TreeNode) *TreeNode // 返回展开后的尾节点
    dfs = func(node *TreeNode) *TreeNode {
        if node == nil {
            return nil
        }
        leftTail := dfs(node.Left)
        rightTail := dfs(node.Right)

        if node.Left != nil {
            // 把展开后的左子树接到根与原右子树之间
            leftTail.Right = node.Right
            node.Right = node.Left
            node.Left = nil
        }
        // 返回当前子树展开后的尾节点
        if rightTail != nil {
            return rightTail
        }
        if leftTail != nil {
            return leftTail
        }
        return node
    }
    dfs(root)
}
```

**为什么用后序（先处理左右子树、再处理当前节点）？** 因为"把左子树接到右子树之前"这一步，需要先知道"左子树展开后的尾节点在哪里"——而这个尾节点只有**先把左子树处理完**才能得到。**这是典型的"后序返回信息"模式：返回值承载"尾节点"，供父节点使用。**

### 2.4 另一种思路：前序 + 暂存右子树

也可以用前序的思路，但必须**先暂存右子树**：

```go
func flattenPreorder(root *TreeNode) {
    curr := root
    for curr != nil {
        if curr.Left != nil {
            // 找到左子树的最右节点（前序下左子树的尾）
            prev := curr.Left
            for prev.Right != nil {
                prev = prev.Right
            }
            // 把原右子树接到左子树尾部
            prev.Right = curr.Right
            // 左子树整体移到右边
            curr.Right = curr.Left
            curr.Left = nil
        }
        curr = curr.Right // 沿右指针前进
    }
}
```

**这个写法是"原地迭代"**：每次把当前节点的左子树"折叠"到右边，然后沿右指针前进。**它没有递归、没有额外空间（除了找尾节点的循环）**，是这道题最优雅的解法之一。

> [!warning] 生产避坑：改写指针前，先保存要用的东西
> 展开题的致命之处在于"顺序"：如果你先写 `node.Right = node.Left`，就**丢失了原来的右子树**——它再也找不回来了。**必须先把"要保留的"存下来（如先让左子树尾节点接住原右子树），再改写指针。** 这与第 12 篇（链表反转）"先存 `next` 再改 `curr.Next`"是同一条铁律：**改指针之前，先保存被覆盖的内容。**

## 第 3 章 LeetCode 116：填充每个节点的下一个右侧节点指针（完美二叉树）

### 3.1 题目

**LeetCode 116 - Populating Next Right Pointers in Each Node**（中等）

给定一个**完美二叉树**（所有叶子在同一层，每个父节点都有两个子节点），填充它的每个 `Next` 指针，让其指向同一层的下一个右侧节点；若没有下一个右侧节点，则 `Next` 置为 `NULL`。

```go
type Node struct {
    Val   int
    Left  *Node
    Right *Node
    Next  *Node
}
```

### 3.2 最直观的解法：层序遍历 + 连接

用第 02 篇的层序模板，把每层节点串起来即可：

```go
func connectBFS(root *Node) *Node {
    if root == nil {
        return nil
    }
    queue := []*Node{root}
    for len(queue) > 0 {
        size := len(queue)
        for i := 0; i < size; i++ {
            node := queue[0]
            queue = queue[1:]
            if i < size-1 {
                node.Next = queue[0] // 指向本层下一个
            }
            if node.Left != nil {
                queue = append(queue, node.Left)
            }
            if node.Right != nil {
                queue = append(queue, node.Right)
            }
        }
    }
    return root
}
```

**这个写法直观、通用，但用了 $O(n)$ 的队列空间。** 题目其实可以做到 $O(1)$ 额外空间——因为 `Next` 指针本身就是"层内的一条链"，可以拿它来遍历下一层。

### 3.3 $O(1)$ 空间解法：借 `Next` 指针遍历下一层

**核心洞察**：当第 $i$ 层已经被 `Next` 串成链时，我们可以**沿第 $i$ 层的 `Next` 链**去给第 $i+1$ 层建立 `Next`，而无需队列。对完美二叉树，规律很整齐：

- `node.Left.Next = node.Right`（同一父节点的两个孩子相连）；
- `node.Right.Next = node.Next.Left`（跨父节点相连，若 `node.Next` 存在）。

```go
func connect(root *Node) *Node {
    if root == nil {
        return nil
    }
    // leftMost 是每一层的最左节点，沿 Left 指针下降
    for leftMost := root; leftMost.Left != nil; leftMost = leftMost.Left {
        // 沿本层的 Next 链遍历，为下一层建立 Next
        for node := leftMost; node != nil; node = node.Next {
            node.Left.Next = node.Right // 同父相连
            if node.Next != nil {
                node.Right.Next = node.Next.Left // 跨父相连
            }
        }
    }
    return root
}
```

**为什么 116 能做到 $O(1)$ 空间？** 因为"完美二叉树"这一前提保证了**结构规整**——每个节点都有左右孩子，跨父连接的目标（`node.Next.Left`）一定存在。**正是这份"完美"，让 `Next` 指针能兼任"下一层的遍历通道"。**

## 第 4 章 LeetCode 117：填充右侧指针 II（普通二叉树）

### 4.1 题目

**LeetCode 117 - Populating Next Right Pointers in Each Node II**（中等）

与 116 相同，但给定的二叉树**不再是完美二叉树**（可能是任意二叉树）。

```text
输入: root = [1,2,3,4,5,null,7]
输出: [1,#,2,3,#,4,5,7,#]
```

### 4.2 为什么 116 的技巧不再适用

116 的 $O(1)$ 解法依赖两条前提：`node.Left` 与 `node.Right` 都存在；跨父连接的目标 `node.Next.Left` 存在。**在普通二叉树里，这两条都可能不成立**——某个节点可能只有右孩子、没有左孩子，`node.Next.Left` 也可能是 `nil`。

**所以必须换一套更通用的思路。** 一种干净的做法是：**为每一层维护一个"哑节点" `dummy`，用 `tail` 指针把下一层的节点依次串起来**（跳过空孩子）。

```go
func connectII(root *Node) *Node {
    if root == nil {
        return nil
    }
    cur := root // 当前层的起点
    for cur != nil {
        dummy := &Node{} // 下一层的哑头
        tail := dummy    // 下一层待连接的尾
        // 遍历当前层（沿 Next 链），把下一层的非空孩子串起来
        for node := cur; node != nil; node = node.Next {
            if node.Left != nil {
                tail.Next = node.Left
                tail = tail.Next
            }
            if node.Right != nil {
                tail.Next = node.Right
                tail = tail.Next
            }
        }
        cur = dummy.Next // 下一层的起点（哑节点的后继）
    }
    return root
}
```

**这段代码的精妙之处，全在那个 `dummy` 哑节点**：它让"下一层还没有任何节点"这一情形无需特判——`tail` 始终指向一个真实存在的位置，第一个孩子到来时直接接上即可。**这与线性表专栏里链表题的哑节点是同一思想：用一个"永远存在的前驱"，把边界特例抹平成通例。** 而且这个解法**空间是 $O(1)$**（只用了两个指针），且对任意二叉树都成立。

### 4.3 116 与 117 的对照

| 维度 | LC 116（完美二叉树） | LC 117（普通二叉树） |
|------|---------------------|---------------------|
| 前提 | 结构规整 | 结构任意 |
| $O(1)$ 解法 | 借 `Next` 遍历下一层 | 借哑节点串联下一层 |
| 关键技巧 | `node.Left.Next = node.Right` | `dummy` + `tail` 串联 |

**这两道题的对照，恰好展示了"约束越强、解法越简单"这一规律**：116 的"完美"前提让连接规则变得整齐，117 去掉前提后，就必须引入哑节点来兜住各种空缺。**理解这一点，你就能明白为什么很多题会先给一个"加强版前提"、再出"去掉前提"的变体——它考的是"你的解法究竟依赖了哪个前提"。**

## 第 5 章 指针操作的通用纪律

把两道题的经验归拢，可以得到一套"改树"的通用纪律：

**纪律一，改指针前先保存。** 展开题里必须先让左子树尾节点接住原右子树，才能改写 `node.Right`；否则原右子树丢失。**这是所有指针操作的铁律。**

**纪律二，想清楚"副作用会不会破坏后续"。** 改树题的递归顺序不是随意的——用后序（先处理子树、再改当前节点）通常更安全，因为"当前节点的修改"不会影响"已经处理完的子树"。

**纪律三，能借现成结构就别开新空间。** 116 借 `Next` 当遍历通道、117 借哑节点兜边界，都是"用数据自身承载控制信息"——这与线性表专栏第 07 篇"就地借用标记"、第 01 篇 Morris 遍历是同一精神。

**纪律四，边界用哨兵抹平。** 哑节点、失败哨兵、哨兵值——这类"用特殊节点消除特判"的手法，在指针题里出现的频率极高。

> [!info] "改树"是工程感的开端
> 读树题考的是"你能不能看出一棵树的结构"；改树题考的是"你能不能在改动结构的同时，不把结构弄坏"。**后者更接近真实工程——因为真实系统里，数据结构往往是"活的"：它被不断增删改，而每一次改动都必须保证不破坏其他部分。** 把改树题练扎实，你对"数据结构的可变性"这一工程命题会有更深的体会。

## 第 6 章 延伸：指针改造的更多面孔

### 6.1 BST 转双向链表（LeetCode 426 / 剑指 Offer 36）

**题目**：把一棵二叉搜索树原地转换成一个排序的循环双向链表，要求不能创建任何新节点，只能调整指针。

**思路**：**中序遍历 BST 得到的正是有序序列**——所以用中序，在"访问当前节点"的时机，把它接到"上一个访问的节点"之后：

```go
func treeToDoublyList(root *TreeNode) *TreeNode {
    var first, prev *TreeNode
    var inorder func(node *TreeNode)
    inorder = func(node *TreeNode) {
        if node == nil {
            return
        }
        inorder(node.Left)
        if prev == nil {
            first = node // 最左节点，即链表头
        } else {
            prev.Right = node // 前驱的右指针指向当前
            node.Left = prev  // 当前的左指针指向前驱
        }
        prev = node
        inorder(node.Right)
    }
    inorder(root)
    if first != nil {
        first.Left = prev // 首尾相连，构成循环
        prev.Right = first
    }
    return first
}
```

**这道题把"中序有序"与"指针改造"结合起来**——中序保证顺序，指针改造把"树形"变成"线性"。**它是"改树"与"BST 中序"两个主题的交汇点**，很能体现本专栏"技巧可以组合"的特点。

### 6.2 递增顺序搜索树（LeetCode 897）

**题目**：把一棵 BST 转换为只有右孩子的"递增顺序搜索树"，使最左边的节点成为新的根。

**思路**：同样是中序遍历，用哑节点串起一条只有右指针的链：

```go
func increasingBST(root *TreeNode) *TreeNode {
    dummy := &TreeNode{}
    tail := dummy
    var inorder func(node *TreeNode)
    inorder = func(node *TreeNode) {
        if node == nil {
            return
        }
        inorder(node.Left)
        // 把当前节点接到链尾，并断开左指针
        tail.Right = node
        node.Left = nil
        tail = node
        inorder(node.Right)
    }
    inorder(root)
    return dummy.Next() // 这里示意：返回 dummy.Right
}
```

**注意这里的 `dummy` 又出现了**——它让"链表还没有节点"这一情形无需特判，第一个节点直接接上即可。**与第 114 题展开链表相比，897 的规则更简单**（只需把中序序列串成右链），但它同样依赖"改指针前先处理好左右子树的递归"。

### 6.3 两道延伸题的共性

426 与 897 的共同点是：**它们都用"中序遍历 + 指针改造"把 BST 变成一条链**。区别只在"链的形态"：426 是双向循环链表、897 是单向右链。**它们进一步印证了本篇的核心——"改树"的难点不在算法，而在"改指针的顺序与时机"。** 只要把"中序保证顺序""哑节点兜边界""改指针前先处理好递归"这几点守住，这两道题都不难。

## 第 7 章 常见误区与自测方法

### 6.1 四个高频误区

**误区一：展开题里先改 `node.Right` 再保存原右子树。** 会永久丢失原右子树。

**误区二：展开题返回错"尾节点"。** 若当前节点有右子树，尾节点是右子树展开后的尾；否则是左子树的尾；都没有才是当前节点本身——顺序不能错。

**误区三：117 题照搬 116 的解法。** 普通二叉树里 `node.Left`/`node.Next.Left` 可能为空，会空指针异常。

**误区四：117 题忘记哑节点。** 若直接用一个可能为空的 `tail`，就要为"下一层第一个节点"写特判，代码反而更乱。

### 6.2 一套自测用例

| 用例 | 检验什么 |
|------|---------|
| 只有左链 `[1,2,null,3]` | 展开题的左子树折叠 |
| 只有右链 `[1,null,2,null,3]` | 展开题的无左子树情形 |
| 完美二叉树 `[1,2,3,4,5,6,7]` | 116 的规整连接 |
| 只有右孩子的树 `[1,null,2]` | 117 的空缺处理 |
| 单节点 | 最简情形 |

**其中"只有左链"最值得测**——它让每个节点都只有左孩子，展开时每一步都要折叠，最能暴露"尾节点返回顺序"与"指针保存"的 bug。

## 第 8 章 改树题的验证与调试

指针改造题"写对很难、验证更难"——因为一旦改错，树的结构就被破坏了，后续的检查往往也失效。本章给出一套"改树题的验证方法"。

### 8.1 为什么改树题难验证

读树题（遍历、判定）如果写错，结果通常"少个值"或"判断反了"，容易发现。**而改树题一旦改错，可能把树改成了环、或丢了一整棵子树**——此时任何基于"遍历结果"的检查都会失败或死循环，你很难判断"是哪一步改坏的"。

**所以改树题的验证，必须"在改动过程中"进行，而不是"改完再看"。**

### 8.2 三个验证手段

**手段一，画图逐步走。** 在纸上画出初始结构，然后**每执行一次指针修改，就重画一次**。对展开题，重点看"左子树尾节点有没有接住原右子树""根的 Left 有没有置空"。**改树题的 bug 几乎全在"某一步的指针指向了哪里"，画图是暴露它的唯一办法。**

**手段二，先在一个"三节点小树"上验证。** 三节点树（根 + 左右孩子）足够覆盖大多数分支（有左、有右、有左右）。**先在它上面走通，再推广到更大规模。**

**手段三，检查"不变式"。** 对展开题，展开后应当满足"每个节点 Left 为 nil、且前序顺序与原树一致"——**这是可以用一次遍历验证的不变式**。对 117 题的 Next 指针，不变式是"每层节点串成链、且链尾 Next 为 nil"。

### 8.3 一个通用的调试策略

**改树题最有效的调试策略，是"把'改动'和'检查'分离"**：

- 先在**副本**上做改动（不破坏原树）；
- 改动完成后，用一个**独立的检查函数**（如"是否为合法链"）验证副本；
- 若通过，再在真树上做同样的改动。

**这需要额外空间，但能让你"改错了还能重来"。** 在面试的纸上推导里，这对应的就是"先想清楚每一步，再落笔"——**改树题惩罚的从来不是'想得慢'，而是'改得急'。**

> [!warning] 生产避坑：改树前先备份关键指针
> 在真实代码里改树，建议**先把要改动的指针的旧值记下来**（哪怕是临时的），以便出错时恢复。**这与线性表专栏第 12 篇"反转链表前先存 `next`"是同一条纪律**——**改指针之前，先保存被覆盖的内容。** 它既是正确性的保证，也是调试的退路。

### 8.4 从"改树"到"改状态"

**"改树"其实是一类更广泛问题的缩影——"在原地修改共享状态"。** 链表反转（改 `Next`）、并查集（改父指针）、原地数组操作（改元素）、乃至数据库事务（改数据），都属于这一类。**它们的共同纪律是三条：改前保存、顺序正确、改后可验证。** 理解了这三条，你面对任何"原地修改"的场景，都有了安全的操作准则——**这也解释了为什么本专栏把"改树"单独成篇：它是一个可以被反复迁移的通用技能。**

## 第 9 章 指针改造题的面试追问与落点

### 9.1 表达套路

1. **先点出方向**："展开是'纵向重连'（树变链），填充 Next 是'横向连接'（层变链）。"
2. **讲清安全纪律**："改指针前先保存——展开时要先让左子树尾接住原右子树。"
3. **给核心技巧**："116 借 Next 遍历下一层，117 用哑节点兜边界。"
4. **说复杂度**："时间 $O(n)$，空间 $O(1)$（117 的哑节点法）。"
5. **主动提边界**："单节点、单孩子、末节点的 Next 都要检查。"

### 9.2 常见追问

**追问一："展开为什么用后序？"** 答：因为"把左子树接到右子树之前"需要先知道"左子树展开后的尾节点"——只有先把左子树处理完才能得到。

**追问二："116 为什么能 $O(1)$ 空间？"** 答：因为"完美二叉树"结构规整，可以用 `Next` 指针当"下一层的遍历通道"。

**追问三："117 为什么不能照抄 116？"** 答：普通二叉树里 `node.Left`/`node.Next.Left` 可能为空，116 的连接规则不再成立。

**追问四："117 的哑节点解决了什么？"** 答：它让"下一层还没有节点"这一情形无需特判——`tail` 始终指向真实位置。

**追问五："展开题如果要求'保留原树'怎么办？"** 答：那就不能原地改，只能新建一条链（此时空间变成 $O(n)$）。

### 9.3 落点

**指针改造题的核心，是"改指针的安全纪律"**——改前保存、顺序正确、改后可验证。**这三条纪律，不止用于树，也用于链表反转、并查集、乃至任何"原地修改共享状态"的场景。** 理解了它们，你就掌握了"安全地改结构"这一通用能力——**而这，正是"改树"这一主题真正的价值所在：它不是为了多会几道题，而是为了练出"改结构时不出错"的手感。**

> [!info] 为什么"改树"值得单独成篇
> 读树题考"看懂结构"，改树题考"改对结构"。**后者更接近真实工程——因为真实系统里的数据结构是"活的"，被不断修改，而每次修改都不能破坏其他部分。** 把改树题练扎实，你对"数据结构的可变性"这一工程命题会有更深的体会。**这也是本专栏把 04 篇单独列出的原因——它训练的是另一种能力。**

### 9.4 从"改树"到"改任何结构"

**"改树"的纪律，可以推广到一切"原地修改"的场景**：

| 场景 | 改前保存 | 顺序正确 | 改后验证 |
|------|---------|---------|---------|
| 展开链表 | 存原右子树 | 先接左尾再接根 | 检查 Left 全空 |
| 链表反转 | 存 next | 先改指向再前进 | 检查无环 |
| 并查集路径压缩 | 存父指针 | 先找根再改父 | 检查根一致 |
| 原地数组去重 | 存覆盖值 | 先读后写 | 检查前缀 |

**这张表说明：三条纪律是通用的。** 无论改的是树、链表、数组还是集合，**"保存、顺序、验证"都是必须遵守的准则。** 理解了这一点，你就把"改树"这一具体技能，上升成了"原地修改"这一通用能力。

## 第 10 章 指针改造题的自查清单与落点

### 10.1 一份自查清单

| 检查项 | 对应问题 |
|--------|---------|
| 改指针前是否保存了被覆盖的内容 | 丢失子树 |
| 展开题的尾节点返回顺序（右、左、自己） | 返回错尾节点 |
| 展开题是否把 `Left` 置空 | 残留左指针 |
| 116 是否借用了 `Next` 遍历 | 多余队列空间 |
| 117 是否用了哑节点 | 边界特判 |
| 末节点的 `Next` 是否置空 | 成环 |

### 10.2 落点

**指针改造专题的落点，是"改结构的安全纪律"**——改前保存、顺序正确、改后可验证。**这三条纪律，是"原地修改"这类操作的通则**（详见第 9 章的表）。

**而更深一层的收获，是"用哨兵抹平边界"这一通用手法**——哑节点、失败哨兵、哨兵值，它们把需要分类讨论的边界，统一成了无需讨论的通例。**从第 02 篇最小栈的哑节点，到本篇 117 题的哑节点，再到第 05 篇的哨兵下标——"哨兵"贯穿了整个算法体系。**

> [!info] 一句话带走
> 如果只能带走一句话，那就是：**"改指针之前，先保存被覆盖的内容。"** 展开题要先让左子树尾接住原右子树、链表反转要先存 `next`、并查集要先存父指针——**所有"原地修改"的 bug，几乎都源于"改得太急、忘了保存"。** 记住这句话，你改任何结构都会更安全。

### 10.3 从"改树"到"可变性"

**"改树"训练的，是"在保持结构不坏的前提下修改结构"这一能力。** 这在工程里对应的是"**可变数据结构的操作**"——链表的增删、树的旋转、图的加边、数据库的更新。**它们都要求"修改一处、不破坏其余"。**

**而"不可变数据结构"（函数式编程里常见）正是为了消除这类风险**——它不允许原地修改，每次"修改"都返回一个新结构。**代价是空间，收益是"永不担心改坏"。** 理解了这一取舍，你就明白"可变 vs 不可变"这一工程命题的核心——**它本质上是"空间"与"安全性"之间的权衡。** 树形指针改造题，正是这个命题的最小演练。

---

### 10.4 一个值得记住的对照

**展开题（114）与链表反转（线性表专栏第 12 篇）是一对**：两者都在"重连指针"，都遵守"改前保存"的铁律。**区别只在"方向"**——反转是"把后继改成前驱"，展开是"把左子树接到右边"。**理解了它们同源，你就把"树"与"链表"的指针操作统一了起来。**

## 小结

本篇把树题从"读"推进到"改"，用两道题覆盖了指针操作的两个方向：LeetCode 114 在**纵向**把树压成链，核心是"后序返回尾节点 + 改指针前先保存"；LeetCode 116/117 在**横向**把层串成链，核心是"借 `Next` 遍历下一层"与"借哑节点兜住空缺"。116 与 117 的对照尤其有价值——它展示了"去掉一个前提，解法就必须升级"这一规律。

贯穿全篇的核心认知有两条。其一，**"改树"的难点来自副作用**——一旦动指针，递归顺序与修改时机都会影响结果，必须时刻问"这一步修改会不会破坏我接下来要用的结构"。其二，**"用哨兵抹平边界"是指针题的通用武器**——哑节点、失败哨兵、哨兵值，它们把需要分类讨论的边界，统一成了无需讨论的通例。**把这两条握住，你在面对任何"原地改造结构"的题时，都有了安全的操作纪律。**

下一篇 [[05 二叉树重建：前序+中序、后序+中序的构造逻辑]] 会进入"从遍历序列反推树"的构造问题。它表面像记公式，实际考察的是你能否从序列中精确恢复"根、左子树区间、右子树区间"三者的边界关系。
