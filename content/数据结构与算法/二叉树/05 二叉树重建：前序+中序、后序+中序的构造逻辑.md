# 二叉树重建：前序+中序、后序+中序的构造逻辑

**摘要：**

二叉树重建题，是遍历专题之后最自然、也最容易"看着会、写着错"的进阶。LeetCode 105、106 表面只是"输入两组遍历数组、输出一棵树"，真正考察的却是**你是否理解根节点在不同遍历中的位置决定了"谁先确定根"，而中序遍历决定了"左右子树的边界在哪里"**。本文先回答一个根本问题——为什么没有中序就很难唯一重建（并用"前序 + 后序"的反例说明）；随后把 105、106 抽象成同一个"区间映射"框架，讲清"根值 → 中序切分点 → 左子树大小 → 另一数组对应区间"这条链条；再补充"为什么不要直接切数组"这一工程细节，以及"前序 + 后序"在什么前提下才能重建。全文用 Go 语言实现，并逐层追问：为什么用哈希表能把复杂度压到 $O(n)$、区间下标为什么比切片数组更稳。

---

## 第 1 章 为什么重建必须依赖中序

### 1.1 三种遍历各自告诉了我们什么

先把三种遍历"能提供的信息"摆清楚：

- **前序**（根、左、右）：第一个元素一定是根；
- **后序**（左、右、根）：最后一个元素一定是根；
- **中序**（左、根、右）：根节点**左边**全属于左子树，**右边**全属于右子树。

**归纳成一句话**：**前序或后序负责"找到根"，中序负责"切分左右子树范围"。** 前序/后序告诉你"谁在根的位置"，但它们无法告诉你"左子树有多大"——而这恰恰是重建的关键。

### 1.2 为什么"前序 + 后序"通常不能唯一确定

用一个最简单的反例说明：给定

```text
前序: [1, 2]
后序: [2, 1]
```

这既可能是：

```text
  1
 /
2
```

也可能是：

```text
1
 \
  2
```

**两种结构的根与孩子都能对上，但结构不唯一。** 这说明：前序 + 后序虽然能确定"根是谁"，却无法确定"孩子挂在左边还是右边"——**缺了中序提供的"左右边界"信息，重建就失去了唯一性。**

> [!info] 重建题的核心：区间映射，而非遍历顺序
> 一旦你能把这条链条说完整——"**当前根值 → 在中序中的切分点 → 左子树大小 → 另一个数组中的对应区间**"——代码基本不会写错。**很多人写错重建题，不是因为不懂遍历，而是因为没把"两个数组的区间如何对应"想清楚。**

## 第 2 章 LeetCode 105：前序 + 中序构造

### 2.1 题目

**LeetCode 105 - Construct Binary Tree from Preorder and Inorder Traversal**（中等）

给定两个整数数组 `preorder` 和 `inorder`，其中 `preorder` 是二叉树的先序遍历，`inorder` 是同一棵树的中序遍历，请构造这棵二叉树并返回其根节点。假设树中没有重复元素。

```text
输入: preorder = [3,9,20,15,7], inorder = [9,3,15,20,7]
输出: [3,9,20,null,null,15,7]
```

### 2.2 递归切分逻辑

前序第一个元素一定是根。设 `preorder[preLeft]` 是当前根值，在中序里找到它的位置 `idx` 后：

- `inLeft .. idx-1` 是左子树的中序区间；
- `idx+1 .. inRight` 是右子树的中序区间。

**左子树的节点数是 `leftSize = idx - inLeft`**。有了它，前序区间也能对应切开：

- 左子树前序区间：`preLeft+1 .. preLeft+leftSize`；
- 右子树前序区间：`preLeft+leftSize+1 .. preRight`。

### 2.3 Go 实现（区间下标 + 哈希表）

```go
func buildTree(preorder, inorder []int) *TreeNode {
    // 用哈希表把"中序中查根位置"从 O(n) 降到 O(1)
    indexMap := make(map[int]int, len(inorder))
    for i, v := range inorder {
        indexMap[v] = i
    }

    var build func(preLeft, preRight, inLeft, inRight int) *TreeNode
    build = func(preLeft, preRight, inLeft, inRight int) *TreeNode {
        if preLeft > preRight {
            return nil
        }
        rootVal := preorder[preLeft] // 前序头部即根
        root := &TreeNode{Val: rootVal}
        idx := indexMap[rootVal]
        leftSize := idx - inLeft

        root.Left = build(preLeft+1, preLeft+leftSize, inLeft, idx-1)
        root.Right = build(preLeft+leftSize+1, preRight, idx+1, inRight)
        return root
    }
    return build(0, len(preorder)-1, 0, len(inorder)-1)
}
```

**复杂度**：时间 $O(n)$（每个节点构造一次，查根位置 $O(1)$），空间 $O(n)$（哈希表 + 递归栈）。

### 2.4 为什么不要直接切数组

很多人会写成 `copyOfRange` 来切子数组，逻辑看起来直观。**但每层递归都复制数组，时间与空间都会恶化到 $O(n \log n)$ 甚至 $O(n^2)$。** 对构造题而言，**传区间边界（下标）而不是传切片数组，是更稳的工程写法**——它把"切分"变成了一次纯下标计算，不产生任何数据复制。

> [!note] 从"切数组"到"传下标"：一次典型的空间优化
> "切数组"与"传下标"在结果上完全等价，区别只在"是否复制数据"。**前者把区间信息实体化成了新数组，后者把它抽象成了两个整数。** 这是算法优化里极常见的一类思路——**当你能用"坐标"表达一段区间时，就不必真的把那段区间"搬"出来。** 第 01 篇的"传区间而非切片"、第 07 篇的"逐行降维"，都是这一思路的变体。

## 第 3 章 LeetCode 106：中序 + 后序构造

### 3.1 与 105 的差异只在根的位置

后序的**最后一个**元素才是根，所以当前根值是 `postorder[postRight]`。拿到中序里的位置 `idx` 后，左子树大小仍是 `leftSize = idx - inLeft`。于是后序区间这样切：

- 左子树后序区间：`postLeft .. postLeft+leftSize-1`；
- 右子树后序区间：`postLeft+leftSize .. postRight-1`。

**注意右子树的尾部是 `postRight-1`**（因为 `postRight` 被根占用了）——这是最容易写错的一位。

```go
func buildTreePost(inorder, postorder []int) *TreeNode {
    indexMap := make(map[int]int, len(inorder))
    for i, v := range inorder {
        indexMap[v] = i
    }

    var build func(inLeft, inRight, postLeft, postRight int) *TreeNode
    build = func(inLeft, inRight, postLeft, postRight int) *TreeNode {
        if inLeft > inRight {
            return nil
        }
        rootVal := postorder[postRight] // 后序尾部即根
        root := &TreeNode{Val: rootVal}
        idx := indexMap[rootVal]
        leftSize := idx - inLeft

        root.Left = build(inLeft, idx-1, postLeft, postLeft+leftSize-1)
        root.Right = build(idx+1, inRight, postLeft+leftSize, postRight-1)
        return root
    }
    return build(0, len(inorder)-1, 0, len(postorder)-1)
}
```

**复杂度**：时间 $O(n)$，空间 $O(n)$。

### 3.2 三个容易写错的地方

- **左子树区间长度算错一位**：`leftSize` 是 `idx - inLeft`，不是 `idx - inLeft + 1`；
- **后序右子树尾部仍写成 `postRight`**：应为 `postRight-1`（根占了一位）；
- **递归终止条件写成 `==` 而非 `>`**：空区间有多种形态，统一用 `left > right` 更稳。

**这类题最稳的方式不是背公式，而是每次都明确"当前根占掉一个位置，左子树大小是多少"。** 把这句话在纸上写一遍，区间就不会错。

## 第 4 章 两道题的统一抽象

把 105、106 并排看，会发现它们的骨架完全一致：

| 题目 | 根节点位置 | 中序作用 | 关键公式 |
|------|-----------|----------|----------|
| LC 105 | 前序**头部** | 划分左右区间 | `leftSize = idx - inLeft` |
| LC 106 | 后序**尾部** | 划分左右区间 | `leftSize = idx - inLeft` |

**真正没变的是"中序的边界作用"，变的只是"根从哪里拿"。** 理解了这一点，你就能用同一个框架套住这两道题，甚至推导出"前序 + 后序"的构造（在特定前提下）。

> [!info] 重建题的"三问"框架
> 拿到任何重建题，先问三个问题：
> 1. **根在哪里？**（前序看头部、后序看尾部、BST 看值域）
> 2. **左子树有多大？**（从中序切分点算出）
> 3. **两个数组的区间如何对应？**（用左子树大小对齐）
>
> 这三问答完，代码就定了。**重建题考的从来不是遍历顺序的记忆，而是这套区间映射的推导能力。**

## 第 5 章 延伸：更多构造题

### 5.1 前序 + 后序构造（LeetCode 889）

**题目**：给定前序与后序，构造二叉树（若答案不唯一，返回任意一个）。

**这道题的难点，正是第 1 章说的"不唯一"**——因为前序 + 后序无法确定"单个孩子挂在左还是右"。工程上的处理是：**遇到"只有一个孩子"的情形时，统一挂到左边（或右边），返回其中一个合法答案即可。**

```go
func constructFromPrePost(preorder, postorder []int) *TreeNode {
    if len(preorder) == 0 {
        return nil
    }
    root := &TreeNode{Val: preorder[0]}
    if len(preorder) == 1 {
        return root
    }
    // 前序第二个是左子树的根，在后序里找到它，即可切分
    leftRoot := preorder[1]
    idx := 0
    for postorder[idx] != leftRoot {
        idx++
    }
    leftSize := idx + 1 // 左子树节点数
    root.Left = constructFromPrePost(preorder[1:1+leftSize], postorder[:leftSize])
    root.Right = constructFromPrePost(preorder[1+leftSize:], postorder[leftSize:len(postorder)-1])
    return root
}
```

**注意这里用了切片（`preorder[1:1+leftSize]`）而非下标**——因为它用哈希表优化查位置的空间换时间在这里不划算（后序里找 `leftRoot` 本身就是线性）。**"用下标还是用切片"，取决于"是否需要频繁查位置"**：需要就建表、传下标；不需要就直接切片，代码更短。

### 5.2 根据前序遍历构造 BST（LeetCode 1008）

**题目**：给定一个 BST 的前序遍历，构造这棵 BST。

**这道题的特殊之处在于"BST"这一额外约束**——有了它，前序单独就能重建。因为对 BST 而言，"哪些元素属于左子树"由值的大小决定（小于根的在左、大于根的在右），无需中序。

```go
func bstFromPreorder(preorder []int) *TreeNode {
    i := 0
    var build func(upper int) *TreeNode // upper：当前子树的取值上界
    build = func(upper int) *TreeNode {
        if i == len(preorder) || preorder[i] > upper {
            return nil // 超出上界，说明不属于这棵子树
        }
        root := &TreeNode{Val: preorder[i]}
        i++
        root.Left = build(root.Val)  // 左子树的上界是 root.Val
        root.Right = build(upper)    // 右子树沿用当前上界
        return root
    }
    return build(math.MaxInt32)
}
```

**这道题的价值，在于它展示了"约束能替代信息"**：普通二叉树重建需要两组遍历（因为缺少"左右边界"信息），而 BST 的"左小右大"约束恰好补上了这份信息——**于是前序单独就够。** 这与第 06 篇"BST 的中序有序把结构题降成序列题"是同一种"约束降维"的思路。

### 5.3 三道构造题的共性

105、106、889、1008 四道题，可以归拢成一张"信息 vs 约束"的表：

| 题目 | 提供的遍历 | 提供的约束 | 能否唯一重建 |
|------|-----------|-----------|-------------|
| LC 105 | 前序 + 中序 | 无重复元素 | 能 |
| LC 106 | 中序 + 后序 | 无重复元素 | 能 |
| LC 889 | 前序 + 后序 | 无重复元素 | 不唯一（返回其一） |
| LC 1008 | 前序 | BST 约束 | 能 |

**这张表说明：重建的"唯一性"取决于"信息 + 约束"是否足够。** 中序提供了"左右边界"这一关键信息；BST 约束则用"值的大小关系"替代了它。**理解了这一点，你就明白为什么"重建必须依赖中序"这句话，有一个重要的例外——当有更强的约束时。**

## 第 6 章 递归构造的通用模式与复杂度

### 6.1 递归构造的三要素

105、106、889、1008 四道题，共享同一个"递归构造"的骨架，可以抽象成三要素：

**要素一，基准情况（何时停止）。** 当区间为空（`left > right`）时返回 `nil`。**这是递归的出口，必须精确。**

**要素二，切分点（如何确定根与左右子树的范围）。** 这是每道题真正的差异所在：
- 105：根在前序头部；
- 106：根在后序尾部；
- 889：根在前序头部，左子树根在前序第二个；
- 1008：根在前序头部，用"上界"划分。

**要素三，递归构造左右子树。** 一旦切分点定了，左右子树的区间也随之确定，递归即可。

**把这三要素想清楚，任何"从序列构造结构"的题都能拆解。** 它的通用形态是：**"确定根 → 切出左右区间 → 递归构造"**——这与第 07 篇"选根 → 左右独立 → 递归"是同一个骨架，只是那里在"计数/生成"，这里在"还原"。

### 6.2 复杂度：哈希表的作用

以 105 为例，若**不用哈希表**，"在中序里找根的位置"需要线性扫描：

- 每一层递归都要扫描一次中序区间，代价 $O(k)$（$k$ 为区间长度）；
- 递归树有 $O(n)$ 个节点，但每个节点的扫描长度不同，总代价最坏 $O(n^2)$（当树退化成链时，每层扫描长度递减，总和约 $n^2/2$）。

**用了哈希表**之后，"找根的位置"变成 $O(1)$：

- 建表 $O(n)$；
- 每个节点构造一次、查表一次，总代价 $O(n)$。

**所以哈希表把复杂度从 $O(n^2)$ 降到了 $O(n)$。** 这是一次典型的"用 $O(n)$ 空间换一个 $\log$ 甚至 $n$ 级别的时间提升"——**建表的一次性投入，换来了每次查根的常数化。**

> [!info] 预处理：把"反复查找"变成"一次建表"
> "建哈希表把查找降到 $O(1)$"，是算法优化里极常见的一招。**它的本质是：当某个查找被反复执行时，与其每次都现算，不如先花一次性代价把结果存下来。** 第 01 篇 Morris 遍历的"借指针当线索"、第 04 篇 116 题的"借 Next 遍历下一层"，都是"预处理/预存"思想的变体。**凡是"反复做同一件事"的地方，都值得问一句：能不能先把它存下来？**

### 6.3 为什么"传下标"比"传切片"更优

第 2.4 节提到过这一点，这里从复杂度角度再确认一遍：

- **传切片**：每层递归复制子数组，一次复制 $O(k)$，总和可能 $O(n \log n)$ 甚至 $O(n^2)$；
- **传下标**：每层只是传递几个整数，$O(1)$，不产生任何数据复制。

**所以"传下标"不只是"更优雅"，它直接改善了复杂度。** 这与线性表专栏"原地操作省空间"、第 01 篇"Morris 省栈"是同一类"用坐标代替实体"的思路——**能用一个坐标表示一段区间时，就不要把那段区间搬出来。**

### 6.4 一个值得记住的对照

| 写法 | 找根 | 切分 | 总时间 |
|------|------|------|--------|
| 传切片 + 线性查 | $O(k)$ | $O(k)$ 复制 | $O(n^2)$ |
| 传下标 + 线性查 | $O(k)$ | $O(1)$ | $O(n^2)$ |
| 传下标 + 哈希表 | $O(1)$ | $O(1)$ | $O(n)$ |

**这张表清晰地展示了"两个独立优化"的叠加**：传下标解决了"切分开销"，哈希表解决了"查找开销"。**把两者合起来，才得到 $O(n)$。** 理解这种"分别优化、叠加收益"的分析方式，比记住"用哈希表就快"更有价值。

## 第 7 章 常见误区与自测方法

### 6.1 四个高频误区

**误区一：用切片数组而非下标。** 每层递归复制数组，复杂度恶化。

**误区二：区间长度算错一位。** `leftSize = idx - inLeft`，别多加 1。

**误区三：后序右子树尾部写成 `postRight`。** 应为 `postRight-1`。

**误区四：递归终止条件写 `==`。** 空区间形态多样，统一用 `left > right`。

### 6.2 一套自测用例

| 用例 | 检验什么 |
|------|---------|
| 单节点 `[1],[1]` | 最简情形 |
| 只有左链 `[1,2],[2,1]` | 左子树切分 |
| 只有右链 `[1,2],[1,2]` | 右子树切分 |
| 完全二叉树 `[1,2,4,5,3,6,7],[4,2,5,1,6,3,7]` | 常规情形 |
| 含重复元素的输入（题目保证没有） | 边界提醒 |

**其中"只有左链"与"只有右链"最值得测**——它们让左右子树之一为空，最能暴露"区间切分"与"空区间判断"的 bug。**凡是重建题，先用这两条链各测一遍。**

## 第 8 章 重建与序列化：一对互逆的操作

"重建"是"序列 → 树"，"序列化"是"树 → 序列"。**它们是一对互逆的操作**，理解了它们的对应关系，你对"结构如何被编码"会有更完整的认识。

### 8.1 什么样的序列能唯一编码一棵树

第 1 章说过："前序 + 中序"能唯一重建，而"前序 + 后序"通常不能。**那么，一个序列要"唯一编码一棵树"，需要满足什么条件？**

**答案是：它必须同时包含"根的信息"与"左右边界的信息"。**

- 前序/后序提供"根是谁"；
- 中序提供"左右子树的边界"；
- 单独的前序 + 空标记（`#`）也能唯一编码（如第 01 篇 6.1 节的序列化）——因为空标记补上了"边界"信息。

**换句话说，"能唯一编码"的本质，是"序列里包含了重建所需的所有信息"。** 缺了边界信息（如前序 + 后序），就重建不出唯一的树。

### 8.2 序列化的三种常见方案

| 方案 | 序列内容 | 能否唯一还原 | 特点 |
|------|---------|-------------|------|
| 前序 + 空标记 | 根、左、右、`#` | 能 | 紧凑、递归还原 |
| 层序 + 空标记 | 逐层、`#` | 能 | 直观、但空节点多 |
| 前序 + 中序 | 两组遍历 | 能（无重复值） | 不依赖空标记，但需两串 |

**三种方案各有取舍**：前序 + 空标记最紧凑（第 01 篇），层序 + 空标记最直观（第 02 篇），前序 + 中序最"数学"（本篇）。**选哪一种，取决于"是否允许改序列格式"以及"树的稀疏程度"。**

### 8.3 一个深刻的观察

**"重建"与"序列化"这对互逆操作，揭示了一个普遍现象：一个数据结构能否被"无损地编码成序列"，取决于"序列是否携带了足够的结构信息"。**

- 数组 → 序列：天然无损（顺序就是结构）；
- 链表 → 序列：天然无损（顺序就是结构）；
- 树 → 序列：**需要额外的边界信息**（因为树有分叉）；
- 图 → 序列：**需要额外的边信息**（因为图更复杂）。

**结构的复杂度越高，编码它所需的"额外信息"就越多。** 这正是为什么"树需要两组遍历或空标记""图需要邻接表"——**它们的分叉/环路结构，无法仅靠"元素顺序"表达。**

> [!note] 编码与结构的复杂度
> 从数组到链表到树到图，"结构复杂度"递增，"编码所需的信息量"也随之递增。**这条规律在计算机科学的许多领域反复出现**——从数据序列化（JSON 比 CSV 能表达更复杂的结构）、到数据库范式（结构越复杂越需要拆表）、再到网络协议（越复杂的语义越需要越多的字段）。**理解了"结构复杂度决定编码复杂度"，你就能从更高的视角看待"序列化"这类问题。**

### 8.4 与第 01 篇的呼应

本篇的"重建"与第 01 篇的"序列化"（LeetCode 297），是同一枚硬币的两面：**一个把序列还原成树，一个把树编码成序列。** 把它们对照着看，你会对"树的结构如何被表达"有更深的体会——**而这，正是理解"树是什么"的一个绕不开的角度。**

## 第 9 章 重建题的面试追问与落点

### 9.1 表达套路

1. **先讲信息分工**："前序/后序负责'找根'，中序负责'切分左右边界'。"
2. **给三问框架**："根在哪、左子树多大、两数组区间如何对应。"
3. **讲优化**："用哈希表把'查中序位置'降到 $O(1)$；用下标而非切片。"
4. **说复杂度**："时间 $O(n)$，空间 $O(n)$。"
5. **主动补充**："若无重复元素才能唯一重建。"

### 9.2 常见追问

**追问一："为什么没有中序就重建不了？"** 答：前序/后序只能确定"根是谁"，无法确定"左子树有多大"；中序提供的"左右边界"信息是不可替代的。

**追问二："前序 + 后序为什么通常不唯一？"** 答：因为当某节点只有一个孩子时，前序 + 后序无法区分"这个孩子挂在左还是右"。

**追问三："为什么用哈希表？"** 答：把"在中序里查根位置"从 $O(n)$ 降到 $O(1)$，整体从 $O(n^2)$ 降到 $O(n)$。

**追问四："为什么传下标而非切片？"** 答：切片每层复制是 $O(k)$，传下标是 $O(1)$，不产生数据复制。

**追问五："BST 为什么只给前序就能重建？"** 答：因为 BST 的"左小右大"约束替代了中序的"边界"信息。

**追问六："若树中含重复元素怎么办？"** 答：105/106 无法唯一重建（因为无法用值定位根），需要额外信息（如"每个值的位置列表"或"节点编号"）。

### 9.3 落点

**重建题的落点，是"区间映射"这一抽象**——**它把"两个序列如何对应"这件事，提炼成了"根值 → 切分点 → 左子树大小 → 对应区间"的一条链。** 一旦掌握这条链，105、106、889、1008 都只是它的变体。

**更重要的是，"区间映射"这一思路可以迁移**——任何"从一组信息还原一个结构"的问题（如从 JSON 还原对象、从 AST 还原源码），本质上都是"确定根/边界、递归还原"。**理解了重建题，你就理解了"结构还原"这类问题的通用形态。**

> [!info] 从"一道题"到"一类问题"
> 重建题看起来是"二叉树专属"，但它的内核——"**用有限的信息，确定一个递归结构的根与边界，再递归还原**"——是通用的。**序列化/反序列化、语法分析、配置解析，都属于这一类。** 这就是为什么本专栏反复强调"看穿共性"——**题目是有限的，而"共性"是可迁移的。**

### 9.4 一个跨领域的对照

**"从遍历序列重建树"与"从 JSON 重建对象"、"从 SQL 重建结果集"，本质上是同一类问题**：**给定一串有结构的线性数据，还原出它背后的层次结构。** 它们都面临同样的核心问题——"如何从线性序列里，识别出'层次'与'边界'"。

**树的重建，是这类问题的"最小模型"**——它把"如何从序列识别层次"这件事，压缩到了最简单的结构上。**理解了它，你就理解了"解析"这一大类问题的核心。** 这也是为什么"重建"值得在二叉树专栏里占一整篇——**它不是一道题，而是一类问题的缩影。**

## 第 10 章 重建题的自查清单与落点

### 10.1 一份自查清单

| 检查项 | 对应问题 |
|--------|---------|
| 终止条件用 `left > right` 而非 `==` | 空区间形态多样 |
| `leftSize = idx - inLeft`（不多加 1） | 区间长度 |
| 后序右子树尾部是 `postRight-1` | 根占一位 |
| 用哈希表而非线性查 | $O(n^2)$ |
| 用下标而非切片 | 复制开销 |
| 无重复元素的前提 | 唯一性 |

### 10.2 落点

**重建专题的落点，是"区间映射"与"三问框架"**——**根在哪、左子树多大、两数组区间如何对应**。答完这三问，代码就定了。

**而更深一层的收获，是"结构还原"这一抽象**——**"用有限的信息，确定一个递归结构的根与边界，再递归还原"**，这正是"解析"这一大类问题的核心（序列化/反序列化、语法分析、配置解析）。**理解了重建题，你就理解了"从线性数据还原层次结构"的通用形态。**

> [!info] 一句话带走
> 如果只能带走一句话，那就是：**"重建的本质，是从序列中恢复'根'与'边界'这两类信息。"** 前序/后序给"根"，中序（或空标记、或 BST 约束）给"边界"——**缺了任何一类，都无法唯一重建。** 记住这句话，你面对任何"重建/还原"的题，都会先问一句"根在哪、边界从哪来"。

### 10.3 从"重建"到"编码"

**重建与序列化是一对互逆操作**（第 8 章），它们的共同主题是"**结构如何被编码成线性序列、又如何从序列还原**"。**这个主题在计算机科学里极为基础**：

- 数据序列化（JSON、Protobuf）——结构 ↔ 字节流；
- 编译器（AST ↔ 源码）——结构 ↔ 文本；
- 数据库（表 ↔ 磁盘页）——结构 ↔ 存储；
- 网络协议（对象 ↔ 报文）——结构 ↔ 字节。

**它们的核心问题都是"如何用线性数据表达层次结构"，而树的重建，正是这个问题的最小模型。** 理解了它，你就理解了"编码/解码"这一大类问题的起点——**这也是为什么"重建"值得在二叉树专栏里占一整篇。**

---

### 10.4 一个值得记住的边界

**"无重复元素"是重建题的一个隐含前提。** 若树中有重复值，"在中序里找根位置"就不再唯一，重建也就失去了唯一性。**面试中若题目没说"无重复"，最好主动确认一句**——这既是严谨，也可能引出面试官的追问（"有重复怎么办"），从而展示你的思考深度。

**最后补充一点**：重建题的"无重复元素"前提，在实际面试里最好主动确认——它既是严谨，也可能引出"有重复怎么办"的追问，从而展示你的思考深度。

## 小结

本篇把二叉树重建从"记公式"还原成了它的本质——**区间映射**。前序/后序负责"找根"，中序负责"切分左右边界"；105、106 的差别只在"根从前拿还是从后拿"，骨架完全一致。用哈希表把"查中序位置"降到 $O(1)$、用下标而非切片，是把复杂度压到 $O(n)$ 的两个关键工程细节。延伸的 889、1008 进一步说明：**重建的唯一性取决于"信息 + 约束"是否足够**——缺了中序，就需要别的约束（如 BST 的"左小右大"）来补。

贯穿全篇的核心认知有两条。其一，**重建题的"三问框架"——根在哪、左子树多大、区间如何对应**——答完这三问，代码就定了。其二，**"用坐标表达区间"比"把区间搬出来"更优**，这是空间优化的一条通用思路。**把这两条握住，你面对任何"从序列反推结构"的题，都有了推导的起点。**

下一篇 [[06 二叉搜索树判定与修复：Validate BST 与 Recover BST]] 会切入二叉搜索树专题。你会看到，"中序有序"这一性质，足以同时解决"是否合法"与"如何修复"两类问题——它把树的结构题，降维成了序列题。
