# 根到叶路径专题：Path Sum、Path Sum II 与数字累积

**摘要：**

从 LeetCode 112（Path Sum）到 113（Path Sum II），再到 129（Sum Root to Leaf Numbers），三道题的题意看似各不相同——一个判"是否存在"、一个求"所有路径"、一个算"数字之和"——**本质却完全一致：沿"根到叶"路径向下携带状态，在叶子处结算。** 本篇要讲清的核心是"**路径状态如何设计**"：状态可以是"剩余目标值"（112）、"已走过的路径"（113）、或"累积成的数字"（129）。一旦状态设计对了，三道题的骨架就是同一段代码。文中还会重点讲清两个易错点：**为什么"在叶子处结算"必须排除"单孩子节点"、以及"复制路径"与"回溯撤销"为什么必须成对出现**。全文用 Go 语言实现，并补充 LC437（路径总和 III）这一"不限定根到叶"的进阶形态。

---

## 第 1 章 路径问题的统一框架

### 1.1 三道题共享的骨架

三道题都能写成同一段骨架：

```text
dfs(node, state):
    1. 更新状态（把当前节点纳入路径）
    2. 若 node 是叶子 → 在叶子处结算
    3. 递归左右子树
    4. 撤销状态（回溯）
```

**它们唯一的区别，在"state 是什么"与"结算时做什么"**：

| 题目 | state 是什么 | 叶子处做什么 |
|------|-------------|-------------|
| LC 112 Path Sum | 剩余目标值 | 判断是否恰好为 0 |
| LC 113 Path Sum II | 已走过的路径 | 把路径加入结果 |
| LC 129 数字之和 | 累积成的数字 | 把数字累加到总和 |

**"状态设计对了，骨架就定了"——这是路径类问题的第一原则。**

### 1.2 为什么路径问题用 DFS（前序携带状态）

**路径问题的中间状态是"从根到当前节点经过的那条路"**——这正是 DFS 的中间状态（回顾第 02 篇的判据："中间状态是层还是路径"）。**所以路径问题天然用 DFS，且通常用"前序"：进入节点时携带状态、离开时撤销状态。**

**这与第 02 篇的层序问题形成鲜明对照**：层序的中间状态是"当前层边界"（用 BFS），路径的中间状态是"当前路径"（用 DFS）。**同一个判据，再次定下了遍历方式。**

## 第 2 章 LeetCode 112：路径总和（是否存在）

### 2.1 题目

**LeetCode 112 - Path Sum**（简单）

给你二叉树的根节点 `root` 和一个表示目标和的整数 `targetSum`，判断该树中是否存在"根节点到叶子节点"的路径，使路径上所有节点值相加等于目标和。

```text
输入: root = [5,4,8,11,null,13,4,7,2,null,null,null,1], targetSum = 22
输出: true（路径 5→4→11→2 之和为 22）
```

### 2.2 状态设计：剩余目标值

**最简洁的状态设计是"剩余目标值"**——从 `targetSum` 出发，每经过一个节点就减去它的值，到叶子时判断"剩余是否为 0"。

```go
func hasPathSum(root *TreeNode, targetSum int) bool {
    if root == nil {
        return false
    }
    // 叶子节点：判断剩余目标是否为 0
    if root.Left == nil && root.Right == nil {
        return root.Val == targetSum
    }
    remain := targetSum - root.Val
    return hasPathSum(root.Left, remain) || hasPathSum(root.Right, remain)
}
```

**注意这里用了"剩余目标值"而非"累计和"**——两者等价，但"剩余"更省一个参数（因为目标值本身不需要一直带着）。**状态设计的取舍，常常就是"哪个量算起来更省"的问题。**

### 2.3 为什么必须"到叶子"才算

题目要求"根节点到**叶子**节点"的路径。**这带来一个易错点**：若某个节点只有一个孩子，它本身不是叶子——**即使它的值恰好等于剩余目标，也不能算数。**

```text
    1
   /
  2
targetSum = 1
```

这里根 `1` 的值等于目标，但它不是叶子（有左孩子 `2`），所以 `hasPathSum` 应返回 `false`（真正到叶子的路径 1→2 之和是 3）。**代码里 `root.Left == nil && root.Right == nil` 这一判断，正是为了排除"单孩子节点"。**

> [!warning] 生产避坑：叶子判定必须"两个孩子都为空"
> 很多人会写成"左孩子为空"或"右孩子为空"就当作叶子——**这会错把单孩子节点当叶子**。**"叶子"的准确定义是"左右孩子都为空"。** 这与第 09 篇最小深度的陷阱同源：都是"没有正确处理单孩子情形"。

## 第 3 章 LeetCode 113：路径总和 II（求所有路径）

### 3.1 题目

**LeetCode 113 - Path Sum II**（中等）

给你二叉树的根节点 `root` 和目标整数 `targetSum`，找出所有"从根节点到叶子节点"的路径，使路径上所有节点值相加等于目标和。

### 3.2 状态设计：已走过的路径 + 回溯

**这道题的状态从"剩余目标值"升级成了"已走过的路径"**——因为最终要输出的是路径本身，而不是一个布尔值。

```go
func pathSum(root *TreeNode, targetSum int) [][]int {
    var res [][]int
    var path []int

    var dfs func(node *TreeNode, remain int)
    dfs = func(node *TreeNode, remain int) {
        if node == nil {
            return
        }
        path = append(path, node.Val) // 进入：把当前节点纳入路径
        remain -= node.Val

        // 到叶子且剩余为 0：记录一条完整路径
        if node.Left == nil && node.Right == nil && remain == 0 {
            tmp := make([]int, len(path))
            copy(tmp, path) // 必须复制，否则后续回溯会改坏它
            res = append(res, tmp)
        }

        dfs(node.Left, remain)
        dfs(node.Right, remain)
        path = path[:len(path)-1] // 离开：撤销（回溯）
    }
    dfs(root, targetSum)
    return res
}
```

### 3.3 两个必须讲清的细节

**细节一：记录路径时必须"复制"。** `path` 是一个会被后续回溯不断修改的切片。若直接 `res = append(res, path)`，那么**当 `path` 后续被修改时，已记录的那条路径也会被改坏**——最终结果全乱。**必须复制一份（`copy`）再存入结果。**

**细节二："纳入"与"撤销"必须成对。** `path = append(path, node.Val)` 与 `path = path[:len(path)-1]` 必须严格配对——**进入节点时纳入、离开节点时撤销**。这就是"回溯"的本质：**函数返回前，把状态恢复到进入前的样子，以免影响兄弟分支。**

> [!info] 回溯：让"共享的状态"在分支间互不干扰
> 路径类问题用一个共享的 `path` 来累积状态，效率高（无需每层复制）。**但共享就意味着"一个分支的修改会污染另一个分支"——而回溯正是消除这种污染的手段**：分支返回前，把状态恢复原样。**"共享 + 回溯"是 DFS 处理路径/组合问题的标准模式**，第 06 篇（搜索专栏）的组合回溯也会反复用到它。

## 第 4 章 LeetCode 129：求根节点到叶节点数字之和

### 4.1 题目

**LeetCode 129 - Sum Root to Leaf Numbers**（中等）

给你一个二叉树的根节点 `root`，树中每个节点都存放有一个 `0` 到 `9` 之间的数字。每条从根节点到叶节点的路径都代表一个数字（如路径 `1→2→3` 代表 `123`）。计算从根节点到叶节点生成的**所有数字之和**。

```text
输入: root = [1,2,3]  →  输出: 25（12 + 13 = 25）
```

### 4.2 状态设计：累积数字

**这道题的状态是"当前路径累积成的数字"**——每深入一层，就把累积值乘 10 再加当前节点的值。

```go
func sumNumbers(root *TreeNode) int {
    var dfs func(node *TreeNode, cur int) int
    dfs = func(node *TreeNode, cur int) int {
        if node == nil {
            return 0
        }
        cur = cur*10 + node.Val // 累积：相当于"在末尾追加一位数字"
        // 到叶子：这条路径的数字就是 cur
        if node.Left == nil && node.Right == nil {
            return cur
        }
        return dfs(node.Left, cur) + dfs(node.Right, cur)
    }
    return dfs(root, 0)
}
```

**`cur = cur*10 + node.Val` 这一行是本题的精髓**——它把"路径上依次经过的数字"拼成了一个整数，**无需显式保存整条路径**。**这展示了状态设计的一种优化：当"结算"只需要路径的某个函数值时，就只携带那个函数值，而不必携带整条路径。** 与 113 题"必须携带整条路径"形成对照。

### 4.3 与 112、113 的对照

| 题目 | 状态 | 为什么是这种状态 |
|------|------|-----------------|
| 112 | 剩余目标值 | 结算只需"是否为 0"，无需路径本身 |
| 113 | 整条路径 | 结算需要输出路径本身 |
| 129 | 累积数字 | 结算只需"数字之和"，可边算边累积 |

**这张表说明：状态设计的粒度，取决于"结算时需要什么"**——需要布尔值就带剩余量，需要路径就带整条路，需要函数值就带那个值。**"按结算需求反推状态"，是路径类问题最实用的设计方法。**

## 第 5 章 延伸：路径总和 III（LeetCode 437）

### 5.1 题目

**LeetCode 437 - Path Sum III**（中等）

给定一个二叉树的根节点 `root` 和一个整数 `targetSum`，求该二叉树里节点值之和等于 `targetSum` 的**路径**的数目。**路径不需要从根节点开始，也不需要在叶子节点结束**，但路径方向必须是向下的（只能从父节点到子节点）。

### 5.2 思路：前缀和 + 哈希表

**这道题的约束被放宽了**——路径不必从根开始、也不必到叶结束。**这带来一个关键困难：路径的起点可以是任意节点。**

**解法是"前缀和 + 哈希表"**：维护"从根到当前节点路径上的所有前缀和"，对当前节点，统计"有多少个前缀和等于 `当前路径和 - targetSum`"——那些位置就是合法的起点。

```go
func pathSumIII(root *TreeNode, targetSum int) int {
    prefixCount := map[int]int{0: 1} // 前缀和 → 出现次数；初始 {0:1} 表示"从根开始"
    count := 0

    var dfs func(node *TreeNode, cur int)
    dfs = func(node *TreeNode, cur int) {
        if node == nil {
            return
        }
        cur += node.Val
        // 有多少个前缀和 = cur - targetSum，就有多少条合法路径以当前节点为终点
        count += prefixCount[cur-targetSum]
        prefixCount[cur]++
        dfs(node.Left, cur)
        dfs(node.Right, cur)
        prefixCount[cur]-- // 回溯：撤销本节点的前缀和
    }
    dfs(root, 0)
    return count
}
```

**这道题与 112/113 的关键区别，是"路径不限定起点"**——于是不能只用一个"剩余目标值"，而必须用"前缀和 + 哈希表"来**枚举所有可能的起点**。**它把"路径和"问题，转化成了"前缀和之差"问题**——这与线性表专栏第 04 篇"子数组和为 K"的哈希解法是同一种思路。**理解了它，你就明白"前缀和"这一工具可以同时用于数组与树。**

## 第 6 章 延伸：路径问题与组合回溯的统一

### 6.1 二叉树的所有路径（LeetCode 257）

**题目**：给你一个二叉树的根节点，按任意顺序返回所有从根节点到叶子节点的路径（字符串形式 `1->2->5`）。

**思路**：与 113 完全同构——**共享一个 `path`、进入时纳入、离开时撤销、到叶子时记录**：

```go
func binaryTreePaths(root *TreeNode) []string {
    var res []string
    var path []string
    var dfs func(node *TreeNode)
    dfs = func(node *TreeNode) {
        if node == nil {
            return
        }
        path = append(path, strconv.Itoa(node.Val))
        if node.Left == nil && node.Right == nil {
            res = append(res, strings.Join(path, "->")) // 到叶子，记录
        }
        dfs(node.Left)
        dfs(node.Right)
        path = path[:len(path)-1] // 撤销
    }
    dfs(root)
    return res
}
```

**这道题与 113 的唯一区别，是"记录时拼接成字符串"而非"复制成数组"**——但骨架一字不差。**它再次印证了路径问题的统一性：状态是"路径"，结算在"叶子"，离开时"撤销"。**

### 6.2 路径问题与组合回溯的同构

把二叉树路径问题与"组合回溯"（如求 `[1,2,3]` 的所有子集）并排看，会发现它们是同一个模式：

| 维度 | 二叉树路径 | 组合回溯 |
|------|-----------|---------|
| 共享状态 | `path`（当前路径） | `path`（当前组合） |
| 进入 | `path = append(path, node.Val)` | `path = append(path, nums[i])` |
| 结算 | 到叶子时记录 | 到决策边界时记录 |
| 离开 | `path = path[:len(path)-1]` | `path = path[:len(path)-1]` |

**两者的骨架完全一致——都是"共享状态 + 进入时纳入 + 离开时撤销 + 在边界处结算"。** 区别只在"什么是边界"：二叉树里是"叶子"，组合问题里是"选够了个数"或"到了数组末尾"。**理解了这一同构，你就把"路径问题"与"组合回溯"统一成了一种模式**——而搜索专栏（第 06 篇组合型回溯）会把这套模式进一步展开。

### 6.3 一个值得注意的复杂度问题

**路径问题的时间复杂度，往往被低估。** 以 113 为例：递归本身是 $O(n)$，但**"记录路径"时要复制一份 `path`（长度可能是 $O(n)$）**，于是最坏情况下（树退化成链、且每条路径都被记录）总时间是 $O(n^2)$。**这不是算法的错，而是"输出规模"决定的**——若答案是 $O(n)$ 条路径、每条 $O(n)$ 长，那么仅"写出答案"就要 $O(n^2)$。

**这提醒我们：分析复杂度时，别忘了把"输出规模"算进去。** 凡是"返回所有解"的题（路径、组合、排列），其复杂度下界往往由"解的个数 × 每个解的规模"决定。**第 07 篇的 95 题（生成所有 BST）也有同样的现象。**

> [!info] 输出敏感：一类容易被忽视的复杂度
> "输出敏感（output-sensitive）"是算法分析里一个重要视角：**当问题的答案本身很大时，任何算法都至少要把答案写出来，因此复杂度下界就是"输出规模"。** 路径问题、组合枚举、排列生成，都属于这一类。**面试中若能主动指出"这里的时间主要花在写出答案上"，会显得你对复杂度有更深的理解。**

## 第 7 章 常见误区与自测方法

### 6.1 四个高频误区

**误区一：叶子判定写成"单孩子为空"。** 会错把单孩子节点当叶子。

**误区二：113 题记录路径时不复制。** `path` 后续会被回溯修改，导致已记录的路径被改坏。

**误区三："纳入"与"撤销"不成对。** 会导致 `path` 在分支间残留，污染结果。

**误区四：129 题显式保存整条路径。** 其实只需累积数字，显式保存是浪费。

### 6.2 一套自测用例

| 用例 | 检验什么 |
|------|---------|
| `[1,2], target=1` | 单孩子非叶子（陷阱） |
| `[1,2,3]`, target=3 | 单孩子 + 叶子 |
| `[5,4,8,11,null,13,4,7,2]`, target=22 | 113 的多路径 |
| `[1,2,3]` | 129 的数字拼接 |
| `[0,1,1]` | 前缀和的初始 `{0:1}` |

**其中 `[1,2], target=1` 最值得测**——根的值等于目标，但它不是叶子，正确答案应为 `false`。**它专治"单孩子节点被误当叶子"这一陷阱。**

## 第 8 章 路径题的验证与面试表达

### 8.1 三个必测的边界

路径题的 bug，集中在三处边界：

**边界一，单孩子节点。** `[1,2], target=1`——根的值等于目标，但它不是叶子，答案应为 `false`。**这检验"叶子判定"是否写成了"左右都空"。**

**边界二，路径的复制。** 对 113 题，测一个"有多条路径"的输入，检查记录下来的路径**是否各自独立**（没有被后续回溯改坏）。**若结果里的路径"全都一样"或"尾部缺失"，就是忘了复制。**

**边界三，负数与零。** 路径和问题里，节点值可能为负或零。测一个"含负数"的输入，检验"提前剪枝"（如"和已经超过目标就返回"）是否会漏解。**很多人在路径题里加"剪枝"，却忘了负数会让"和"非单调——这会漏解。**

**这三处边界，覆盖了路径题 90% 以上的 bug。**

### 8.2 一个关于"剪枝"的提醒

**路径和问题里，不要随便加剪枝。** 有人会写"若当前和已经大于目标，就提前返回"——**这在节点值全为正时成立，但一旦有负数，就错了**（因为加上负数后，和可能又变小到目标）。

**"剪枝依赖单调性"**——这是本专栏反复出现的主题（回顾线性表专栏第 02 篇、栈与队列专栏第 04 篇）。**路径和问题里，节点值不保证为正，所以"和"不单调，剪枝就不成立。** 除非题目明确"所有节点值为正"，否则不要剪枝。

### 8.3 面试表达

路径题的面试表达，建议按这个顺序：

1. **先讲状态设计**："我沿路径携带'剩余目标值'（或'累积数字'）。"
2. **再讲结算时机**："到叶子时结算——注意叶子是'左右都空'。"
3. **然后讲回溯**："记录路径时要复制，离开节点时要撤销。"
4. **主动补充**："若要输出所有路径，复杂度还包含'复制路径'的开销。"

**第 1 步是关键**——它表明你理解了"状态由结算需求决定"这一原则。

> [!info] 状态设计：路径题的第一原则
> 路径题（乃至所有 DFS 携带状态的问题）的核心，是"**状态设计**"——带剩余量、带路径、带累积值、带极值对……**状态设计对了，骨架就定了；状态设计错了，怎么调都别扭。** 而设计状态的依据，永远是"结算时需要什么"。**记住这一原则，你面对任何"沿路径携带状态"的问题，都能先定状态、再写代码。**

### 8.4 路径问题的普遍性

**"路径"是树、图、乃至一切"有向结构"里的基本概念**：文件系统的路径、依赖图的调用链、状态机的转换序列、神经网络的反向传播路径……**它们都涉及"沿一条链路携带信息、在终点结算"。**

**二叉树路径问题，是这类问题的"最小模型"**——它把"路径携带状态 + 回溯撤销"这套机制，压缩到了最简单的结构上。**理解了它，你就理解了"沿路径累积"这一模式的全部要素**（携带什么、何时结算、如何撤销）。**而这套模式，会一路迁移到回溯、动态规划、乃至图算法中。**

## 第 9 章 路径状态的形态图谱与跨领域联系

### 9.1 路径状态的可能形态

回顾本专栏出现过的所有"路径携带状态"，可以整理出一张图谱：

| 状态形态 | 结算方式 | 代表题 |
|---------|---------|--------|
| 剩余目标值 | 判断是否为 0 | 112 |
| 整条路径 | 复制路径 | 113、257 |
| 累积数字 | 累加 | 129、1022 |
| 路径极值对 | 算差值 | 1026 |
| 路径最大值 | 比较 | 1448 |
| 累积和 + 前缀表 | 查表计数 | 437 |
| 方向对 | 取对应方向 | 1372 |

**这张图谱说明：路径状态的设计空间很大，但都遵循同一原则——"按结算需求反推状态"。** 需要判断就带剩余量、需要输出就带整条路、需要数值就带累积值、需要计数就带前缀表。**理解了这条原则，你就能为任何路径题设计出合适的状态。**

### 9.2 路径问题的跨领域联系

**"沿路径携带状态"这一模式，在计算机科学里无处不在**：

- **文件系统的路径解析**：沿目录链累积"当前绝对路径"；
- **依赖解析**：沿依赖链累积"已访问的包集合"，检测循环依赖；
- **状态机/正则匹配**：沿状态转移路径累积"当前状态"；
- **编译器的作用域分析**：沿语法树路径累积"当前作用域"；
- **神经网络的链式法则**：沿计算图反向传播"梯度"，正是"沿路径累积"的数学形式。

**它们共享同一个结构：进入时更新状态、在某个节点结算、离开时恢复。** 二叉树路径问题，正是这个结构在"树"上的最小实例。**理解了它，你就能把"沿路径携带状态"这套机制，迁移到任何"层次结构"上。**

### 9.3 一个值得体会的对照：路径 vs 组合

**路径问题（DFS 携带路径）与组合问题（回溯枚举组合），骨架完全一致**（第 6.2 节）。这个对照很有启发性：

- **路径问题**：路径由"树的结构"唯一决定——从根到叶只有一条路；
- **组合问题**：组合由"选择"决定——每一步都有多个分支可选。

**所以"路径"是"组合"的一个特例**——当每一步的选择只有一个（只能往下走）时，组合就退化成路径。**理解了这一点，你会发现"路径"与"组合"用的是同一套回溯框架，只是"分支数"不同。** 而搜索专栏（第 06 篇组合型回溯）会把"分支数更多"的那一侧展开。

> [!info] 从"一条路"到"所有组合"
> 路径问题是"**只有一条路**"的 DFS，组合问题是"**每条路都要试**"的 DFS。**它们的差别，只在"每层有多少分支"**——路径每层只往下走，组合每层要枚举。**理解了这一点，你就把"路径"与"组合"统一成了同一个框架的两个极端。** 这也是为什么本专栏的路径专题，能作为搜索专栏的前置——**它们本就是同一件事。**

### 9.4 落点

**路径专题的落点，是"状态设计"这一能力**——它要求你在动手前先想清"结算需要什么、该携带什么"。**而这项能力，贯穿了整个树形 DP、回溯、乃至动态规划。** 理解了"按需求设计状态"，你就掌握了处理"带状态的递归"这类问题的通用钥匙。

**最后留一个问题**：本专栏的三道主线题（112、113、129）状态各不相同，但骨架一致。**如果题目要求"输出所有路径及其和"，状态该怎么设计？** 答案是"同时携带路径与累积和"——**这正是"按结算需求设计状态"的又一次应用：结算需要路径与和，就两者都带。**

## 第 10 章 路径题的自查清单与落点

### 10.1 一份自查清单

| 检查项 | 对应问题 |
|--------|---------|
| 叶子判定是"左右都空" | 单孩子误判 |
| 记录路径时复制 | 回溯改坏结果 |
| 纳入与撤销成对 | 状态残留 |
| 含负数时不剪枝 | 剪枝依赖单调性 |
| 状态按"结算需求"设计 | 状态选错 |
| 437 用前缀和 + 哈希 | 起点不固定 |

### 10.2 落点

**路径专题的落点，是"状态设计"这一能力**——**按结算需求反推状态**：要判断就带剩余量、要输出就带整条路、要数值就带累积值、要计数就带前缀表。

**而更深一层的收获，是"共享状态 + 回溯撤销"这一模式**——它与组合回溯完全同构（第 6.2 节），是 DFS 处理"路径/组合"类问题的标准框架。**理解了这一点，你就把"路径问题"与"搜索专栏的组合回溯"统一了起来。**

> [!info] 一句话带走
> 如果只能带走一句话，那就是：**"路径问题的核心，是'沿路径携带状态、在叶子结算、离开时撤销'。"** 携带什么由结算需求决定；结算必须在叶子（左右都空）；撤销必须与纳入成对。**这三条守住，任何路径题都不难。**

### 10.3 从"路径"到"状态机"

**路径问题本质上是一个"状态机"的运行**——**每经过一个节点，状态就按某个规则更新；到达叶子时，读出一个结果。** 从这个角度看：

- 112 的状态机：`剩余目标 → 剩余目标 - 当前值`；
- 129 的状态机：`累积数字 → 累积数字 × 10 + 当前值`；
- 437 的状态机：`前缀表 → 前缀表 + 当前前缀和`。

**"状态如何更新"就是"转移函数"，"何时结算"就是"终止条件"。** 一旦这样理解，路径问题就成了"在树上跑一个状态机"——**而这套视角，可以迁移到任何"沿结构传播状态"的场景**（如编译器的类型推导、数据流的分析）。**树形路径问题，是这个视角的最小演练。**

---

### 10.4 一个值得记住的边界

**"路径是否必须从根开始、到叶结束"是路径题的第一个分歧点。** 112/113/129 都要求"根到叶"；而 437 允许"任意节点到任意节点（向下）"。**这个约束的松紧，直接决定了状态设计**——"根到叶"可以用"剩余量"，"任意起点"则必须用"前缀和 + 哈希表"。**所以拿到路径题，先确认"路径的起止约束"，再设计状态。**

**最后补充一点**：路径题若要求 $O(1)$ 额外空间，则不能"复制整条路径"——只能改用"回溯 + 全局路径栈"，或把递归改成迭代。**但大多数面试题不卡这个空间，所以"复制路径"是更清晰的写法。**

---

## 小结

本篇用三道题，把"根到叶路径"这一主题讲透。它们的骨架完全一致——**沿路径向下携带状态、在叶子处结算、离开时回溯**——差异只在"状态是什么"与"结算时做什么"：112 带"剩余目标值"、113 带"整条路径"、129 带"累积数字"。两道延伸题进一步拓展了视野：437 用"前缀和 + 哈希表"处理"不限定起点"的路径，展示了前缀和工具的通用性。

贯穿全篇的核心认知有两条。其一，**状态设计的粒度，取决于"结算时需要什么"**——按结算需求反推状态，是路径类问题最实用的方法。其二，**"共享状态 + 回溯撤销"是 DFS 处理路径/组合问题的标准模式**，而"记录时必须复制"与"纳入撤销必须成对"是两个必须守住的细节。**把这两条握住，你面对任何路径类或组合类问题，都有了拆解与自查的起点。**

下一篇 [[11 树形 DP 进阶：二叉树中的最大路径和]] 是本专栏的收束。它训练的是最关键的能力：区分"对父节点可贡献的值"与"当前节点作为路径拐点时的最优值"。只要把这两类值混在一起，代码就一定错。
