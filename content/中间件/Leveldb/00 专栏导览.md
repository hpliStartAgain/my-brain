# LevelDB 与 RocksDB 深度解析专栏导览

## 这一列怎么读

LevelDB 是 LSM 家族最干净的一个实现，RocksDB 是它在生产里的那个版本（TiKV 的引擎、MyRocks、CockroachDB 的 Pebble 都从这里来）。这一列不写源码剖析——那在 `深入浅出存储引擎/09`（13,659 字）里已经做透了。

这一列写**调优与选型**：三笔放大账怎么算、写停是怎么发生的、读放大怎么被压下去、compaction 策略怎么选、`rocksdb.stats` 怎么读。每一篇都落到"这个参数调大调小各付什么代价"和"这个现象该看哪个指标"。

**技术版本**：RocksDB 8.x/9.x。LevelDB 的发布停在 1.23（已核 tags），所以生产里默认指的是 RocksDB；两者的差异在篇内标注。

**与 `深入浅出存储引擎` 的分工**：那一列写"存储引擎这一层有什么派系、LSM 与 B+ 树各自的原理、BoltDB 与 LevelDB 的源码"；这一列写"用 LSM 引擎时怎么算账、怎么调、坏了怎么查"。

## 一条调优路径

这一列的五篇是可以按顺序读的：先算账（01 知道自己该优化哪一笔）→ 再调写（02 写缓冲与写停）→ 再调读（03 缓存与 bloom）→ 再选策略（04 compaction）→ 最后用观测验证（05）。

反过来排查时顺序不同：

| 现象 | 先去哪篇 | 看什么 |
| :--- | :--- | :--- |
| 写入阻塞、P99 长尾 | 02 / 05 | `rocksdb.is-write-stopped`、`num-files-at-level0`、`estimate-pending-compaction-bytes` |
| 点查变慢 | 03 | block cache 命中率、bloom 是否生效、`prefix_extractor` 是否配了 |
| 磁盘占用异常增长 | 01 / 04 | 空间放大、`max_size_amplification_percent`、墓碑是否清不掉 |
| 写放大拖垮 SSD 寿命 | 04 | `rocksdb.stats` 的 `W-Amp` 列、compaction 策略是否该换 |
| SSD 寿命与写带宽吃紧 | 01 | 三笔账的取舍，是否该从 LSM 换成 B+ 树 |
