# 05 Doris 实时数据导入——Stream Load、Routine Load 与 Flink Connector

**摘要：**

数据导入是数据链路里"最容易被低估"的一环——它看起来只是"把数据发过去存起来"，但在分布式环境下要同时满足三个要求：**原子性**（要么全可见、要么全不可见）、**幂等性**（重试不产生重复）、以及**可运维性**（能监控、能暂停、能恢复）。本文先讲清导入为什么需要两阶段提交、以及一次导入会牵动多少个节点；再梳理 Doris 的五类导入方式（Stream Load、Broker Load、Routine Load、Flink Connector、SQL 写入）各自的定位与共同底层机制；然后逐一拆解三种主流方式：Stream Load 的同步 HTTP 推送与 Label 幂等、Routine Load 的"FE 管调度、BE 做消费"分工与 Offset 提交时机、Flink Connector 如何把 Flink Checkpoint 与 Doris 事务绑定成端到端 Exactly-Once。之后讲导入的一致性与幂等性、导入调优与排障、以及导入对查询的影响。全文回答两个问题：五种导入方式分别在什么条件下最优，以及为什么"导入频率"是这套系统最需要被管理的变量。

---

## 第 1 章 导入为什么需要事务

### 1.1 一次导入牵动多少节点

先建立一个量级感。假设导入一批数据到一张"32 个分桶、3 副本"的表：这批数据会被分发到 32 个 Tablet，每个 Tablet 有 3 个副本分布在不同 BE 上，因此**一次导入在存储侧涉及近百个写入目标**（32 个 Tablet 乘以副本数，且副本之间还需要同步）。

在这个规模下，"中途某个节点失败"不是异常而是常态——网络抖动、磁盘瞬时压力、BE 进程重启都可能让某一路写入失败。如果系统不提供原子性，就会留下"部分 Tablet 写入了新数据、部分没写入"的状态，而这种状态对使用者是不可理解的：**同一个查询可能返回一半新数据一半旧数据。**

### 1.2 原子性的承诺

因此 Doris 对所有导入方式给出的承诺是同一个：**一次导入要么整体可见，要么完全不可见。**

这个承诺的表述看似简单，但它排除了很多"看起来能用"的实现方式。例如"逐个 Tablet 写入并逐个生效"就不满足这个承诺——它在中途失败时会留下部分生效的状态。"先写入再统一标记生效"则满足，代价是需要一个额外的提交阶段。

### 1.3 两阶段提交

Doris 采用的正是后者的思路，即**两阶段提交（2PC）**。

**第一阶段（Prepare）**：FE 为本次导入生成全局事务标识，把数据分发到各目标 BE，每个 BE 把数据写成**未提交状态**的 Rowset——数据已经落盘，但查询看不见。各 BE 完成后向 FE 报告。

**第二阶段（Commit 或 Abort）**：如果全部 BE 都报告成功，FE 通知它们把 Rowset 标记为已提交（查询可见）；如果任意一路失败，FE 通知所有 BE 删除未提交的 Rowset，不留痕迹。

这个机制的价值在于"**未提交的中间状态对使用者完全不可见**"。它同时带来一个副作用：**导入的提交延迟取决于最慢的那一路**。如果某个 BE 恰好负载很高，整批导入的完成时间就被它拖住——这也是"导入性能受集群负载影响"的根本原因。

> [!info] 核心概念
> 两阶段提交在这里解决的不是"跨库分布式事务"（那是另一类问题），而是"**单次批量写入的原子性**"。它的成本结构很清晰：**写入阶段是并行的**（各 BE 同时写），**提交阶段是同步的**（等最慢的一路）。因此优化的重点通常不在"写得多快"，而在"如何避免某一路特别慢"——这又回到了集群负载均衡与 Tablet 分布的话题。

---

### 1.4 导入与元数据事务

两阶段提交的"事务标识"由 FE 生成与维护，这意味着**每一次导入都会在 FE 上产生一笔元数据事务**。

这笔事务的内容包括：事务标识与状态、涉及的目标 Tablet 与版本号、以及提交或回滚的结果。它在 FE 内存中占用空间，直到事务终结（提交或回滚）并被清理。

由此得到两条实用结论。**其一，导入频率直接影响 FE 的元数据负载**——不是"数据量"影响它，而是"导入次数"影响它。**其二，失败的事务需要被清理**——如果大量导入失败后未被正确回滚，这些悬空事务会持续占用 FE 内存，表现为"元数据对象数量异常增长"。

这也解释了为什么"导入频率"这个变量在本专栏反复出现：**它同时作用于存储侧（Rowset 与 Compaction）与元数据侧（事务与 FE 内存）**，是两个不同层面的压力来源。**降低导入频率、增大单批数据量，是唯一能同时缓解这两处压力的动作。**

### 1.5 提交阶段的同步代价

前文提到"提交延迟取决于最慢的一路"，这一点值得再展开，因为它解释了导入性能中很多看似反常的现象。

提交阶段要等所有目标 BE 都完成写入。因此导入的耗时分布不是"平均耗时"，而是"**所有并行分支中最大者**"——这是一个极值统计，而不是平均值统计。极值统计有两个特性：**它随并行分支数的增加而增大**（分支越多，出现一个慢分支的概率越高），**且它对个别慢节点极其敏感**。

由此可以解释三个常见现象。

**现象一：同样的数据量，分桶数多的表导入更慢。** 因为分桶数决定了并行分支数，分支越多，"最慢一路"的期望值越大。

**现象二：集群里有少数慢节点时，导入普遍变慢。** 因为每次导入都有相当概率命中这些慢节点，从而被拖住。

**现象三：扩容后导入没有变快。** 如果扩容引入了性能较差的节点（如磁盘型号不同），"最慢一路"的期望值可能不降反升。

**这三条现象的共同对策是"消除慢节点"**，而不是"增加并行度"。这与分布式查询里"长尾由最慢分片决定"是同一个道理——**在极值统计主导的系统里，消除最差的那一部分比提升平均水平更有效。**

## 第 2 章 导入方式的谱系

### 2.1 五类导入方式

Doris 提供的导入方式可以按"数据来源"与"是否常驻"两个维度排列。

| 方式 | 数据来源 | 触发方式 | 典型延迟 |
|---|---|---|---|
| Stream Load | 应用直接推送（HTTP） | 同步调用 | 秒级 |
| Broker Load | 外部存储（对象存储、HDFS） | 异步任务 | 分钟级 |
| Routine Load | 消息队列（Kafka） | 常驻任务 | 秒级 |
| Flink Connector | Flink 作业输出 | 随 Checkpoint | 秒级到毫秒级 |
| SQL 写入（INSERT） | SQL 查询结果或常量 | 同步执行 | 视数据量 |

这五种方式不是竞争关系，而是**覆盖不同场景**：数据在外部存储里用 Broker Load；数据在消息队列里用 Routine Load；需要复杂转换或 CDC 同步用 Flink Connector；应用直接产生数据用 Stream Load；表间加工用 SQL 写入。

### 2.2 选型的两个判断维度

选择导入方式时，真正需要判断的是两个维度。

**维度一：数据的来源形态。** 数据是"已经在文件里"、"在消息队列里"、还是"由应用实时产生"？这直接决定了候选集合——文件对应 Broker Load，消息队列对应 Routine Load，实时产生对应 Stream Load。

**维度二：对延迟与转换复杂度的要求。** 如果只需要简单映射（字段重命名、简单过滤），Routine Load 的内置转换能力够用；如果需要复杂转换（关联维表、窗口聚合、处理删除语义），就必须引入 Flink。

**一个常见的选型错误是"用复杂度换取想象中的低延迟"。** 例如为了"更快"而引入 Flink，但实际的延迟瓶颈在数据源侧或 Checkpoint 间隔上，引入 Flink 只是增加了运维对象而没有改善延迟。**延迟的决定因素往往不是导入方式，而是批处理窗口与 Checkpoint 周期。**

### 2.3 共同依赖的底层机制

无论哪种方式，最终都落到同一套底层机制上：**事务标识（Label 或事务 ID）、两阶段提交、以及 Rowset 的版本管理。**

这个共性带来两个实用推论。**其一，所有导入方式在"攒批"这条纪律上是相同的**——无论用哪种方式，导入频率过高都会造成 Rowset 与元数据事务压力。**其二，排障思路是相通的**——无论哪种方式，导入慢都可以沿"数据分发、写入、提交"三段定位。

---

### 2.4 SQL 写入与表间加工

除了面向外部数据源的四种方式，Doris 还支持用 SQL 直接写入数据——包括插入常量行、以及把查询结果写入另一张表。

**`INSERT INTO ... VALUES`** 适合小批量数据（如维度表的少量行），它的开销与一次普通查询相当，不适合大批量。

**`INSERT INTO ... SELECT`** 是"表间加工"的主力：从一张表（或外部表）读取、转换、写入另一张表。它适合数仓的分层加工（明细层到汇总层），也适合从外部数据源（如通过连接器读取的对象存储、外部数据库）导入。

它有一个容易被忽略的代价：**`INSERT INTO ... SELECT` 本身是一条查询，因此它消耗的资源包括"读"与"写"两部分**——既要扫描源表，又要走完整的导入事务。因此在大批量加工时，它同时给查询资源与导入资源带来压力。**这也是为什么"大批量加工"通常建议用外部计算引擎（如 Spark）产出文件后再导入，而不是直接用 SQL 在库内加工。**

### 2.5 导入链路的整体视角

把导入放进整条数据链路看，它的位置决定了它的重要性容易被低估。

**上游是数据产生方**（业务系统、日志采集、CDC），**下游是查询消费方**（报表、看板、下游加工）。导入是这两者之间的"关口"：上游的频率由业务决定，下游的性能由存储状态决定，而导入是唯一能在这两端之间做调节的环节。

这个位置带来一个责任：**导入层必须承担"削峰填谷"的职责。** 如果上游是"随时产生、零散到达"的形态（如业务系统的实时事件），导入层应当用缓冲（消息队列）把零散数据攒成批次；如果上游是"周期性大批量"的形态（如每日快照），导入层应当控制并发与限速，避免与查询争抢。

**把"调节"这件事交给导入层，而不是要求上游改变产生节奏或下游忍受性能波动，是更现实的工程选择。** 因为上游的节奏由业务决定（难以改变），下游的性能要求是刚性的（不能妥协），只有中间的导入层有调整空间。

## 第 3 章 Stream Load

### 3.1 定位与接口

**Stream Load** 是最基础的导入方式：通过 HTTP 请求把数据推送给 Doris，同步等待导入结果。

```bash
curl -u user:passwd \
  -H "label: batch-20260101-001" \
  -H "column_separator: ," \
  -H "columns: event_date, region, amount" \
  -T /data/orders_20260101.csv \
  "http://fe_host:8030/api/my_db/orders/_stream_load"
```

它的响应里包含关键的执行信息：事务标识、状态、总行数、成功导入行数、导入字节数、耗时。**这些字段是排查导入问题的第一手材料**——特别是"总行数与成功行数的差值"，它直接反映了有多少行因为格式问题被过滤。

### 3.2 Label：幂等的来源

Stream Load 的每个请求必须携带一个 **Label**——用户定义的唯一标识。

Label 的作用是提供**幂等性**：如果一次导入因为网络超时而不确定是否成功，可以用同一个 Label 重试；Doris 保证相同 Label 的导入只被执行一次，重复请求会返回"Label 已存在"而不是重复导入数据。

这个机制解决的是一个非常现实的问题：**HTTP 请求超时不等于导入失败。** 请求可能在服务端已经成功执行、只是响应没回来；此时如果客户端直接重试（用新 Label），就会造成数据重复。因此正确做法是"**用同一 Label 重试，并根据返回结果判断是否已成功**"。

### 3.3 内部流程

Stream Load 的执行路径可以拆成五步：FE 生成事务并选择目标 Tablet 与 BE；FE 把数据流式代理到各目标 BE；每个 BE 接收、解析、排序并写成未提交 Rowset；FE 收到全部成功报告后执行提交；最后返回 HTTP 响应。

**整个流程是同步的**——HTTP 连接保持到导入完成。这个性质决定了它的适用边界：连接期间占用一个 HTTP 连接与对应资源，因此不适合"单次超大批量"（一次几十 GB）；也不适合"每秒一次"的高频调用（每次都是一次完整的 2PC）。

### 3.4 适用与限制

**适用**：批量文件的定期同步（如每十分钟一次的 ETL）、应用侧的批量推送、以及数据量适中的导入（通常建议单次在百 MB 到 GB 量级）。

**限制**：同步阻塞（不适合超大批量）；不内置消息队列集成（调用时机与打包由应用负责）；高频调用会推高元数据事务压力。

### 3.5 攒批纪律在 Stream Load 上的体现

把第 2 篇的"攒批纪律"落到 Stream Load 上，可以得到三条具体建议。

**建议一：单批数据量不宜过小。** 每批只有几千行时，产生的 Rowset 极小，Compaction 的收益低而开销相对高。通常建议单批在几十 MB 以上。

**建议二：调用间隔不宜过短。** 如果导入耗时 30 秒、间隔也是 30 秒，Compaction 几乎没有喘息时间。合理间隔应当让系统有时间消化上一批数据。

**建议三：优先用更高层的封装来管理批次。** 例如用消息队列做缓冲、由消费端按批次触发导入（这正是 Routine Load 做的事），而不是由应用直接高频调用 Stream Load。**把"批次管理"这个职责交给专门的组件，比在应用里手工控制更可靠。**

---

### 3.6 并发与限速

Stream Load 的并发能力与限制手段都值得说明，因为它们决定了"导入能有多快"。

**并发来源有两层**：应用侧可以并发发起多个 Stream Load 请求（不同批次），而每个请求内部又会在多个 BE 上并行写入。因此"导入吞吐"是"应用并发度 × 单请求内并行度"的乘积。这解释了为什么"提高导入吞吐"可以从两端入手。

**限速手段同样有两层**：应用侧控制并发请求数（避免把 BE 打满），以及限制单个请求的数据量（避免某一路写入耗时过长而拖慢整体提交）。**后者常被忽略——一个超大单批虽然"看起来效率高"，但它的提交阶段要等所有 BE 完成，任何一路慢都会拖累整批。**

实践中还有一个与并发相关的现象：**并发导入同一张表时，不同批次的提交可能互相影响**。因为多个批次都要在相同的 Tablet 上生成新的 Rowset，元数据版本的管理会让它们产生一定的串行化。**因此"并发导入"不是线性提速的**——在达到某个并发度之后，继续提高只会增加冲突而没有吞吐收益。

这一现象有一个实用的推论：**如果导入吞吐上不去，先确认瓶颈是不是"同一张表的并发冲突"，而不是急着加并发。** 判断方法是看"不同表并发导入"与"同一张表并发导入"的吞吐差异——如果前者明显更高，说明瓶颈在表级别的版本管理上，而非集群整体能力。此时可行的方向包括：把不同批次按分区分开（减少同一 Tablet 上的冲突）、或改用更少的更大批次。

## 第 4 章 Broker Load：外部存储的批量导入

### 4.1 定位

**Broker Load** 面向"数据已经在外部存储里"的场景：通过 Doris 的 Broker 组件读取对象存储或 HDFS 上的文件，批量导入到表中。

它的关键特征是**异步**：提交一个导入任务后立即返回，任务在后台执行，通过查询任务状态获知进度。这与 Stream Load 的同步语义形成对照——**异步让它可以承接更大的数据量**（因为不受 HTTP 连接时长限制），代价是需要额外的任务状态管理。

### 4.2 并行读取与资源隔离

Broker Load 的执行方式是由多个 BE 并行读取外部文件的不同部分，各自处理后再走两阶段提交。因此它的吞吐上限取决于"并行读取的并发度"与"外部存储的读取带宽"。

这里有一处值得注意的设计考虑：**导入任务会占用 BE 的资源，从而与查询争抢。** 因此大批量导入通常需要限速或安排在低峰期执行。这与 Compaction 的资源竞争是同一类问题——**在同一个 BE 上，所有任务共享同一批 CPU、内存与 IO。**

### 4.3 适用场景

Broker Load 适合三类场景：**历史数据的一次性回填**、**定期的大批量文件同步**（如每天从对象存储导入全量快照）、以及**数据量超出 Stream Load 合理范围的导入**。

它的一个隐性优势是**与数据湖生态的衔接**：如果数据已经以文件形式存在对象存储上（Parquet、ORC 等列式格式），Broker Load 可以直接读取，不需要额外的转换步骤。**这种"直接读文件"的能力，让 Doris 可以扮演"数据湖的加速层"**——数据留在对象存储（低成本），需要高性能分析时导入 Doris。

---

### 4.4 任务管理与失败重试

Broker Load 的异步语义带来了一类特有的运维问题：**任务可能长时间处于"进行中"状态，也可能失败后需要重试。**

三个管理要点如下。

**要点一：任务状态需要主动查询。** 因为它不在调用链上阻塞，所以"提交成功"只代表任务已创建，不代表数据已导入。任务的状态（进行中、成功、失败、取消）需要显式查询与监控。

**要点二：失败任务需要清理。** 失败的任务可能留下未提交的 Rowset 或临时状态，需要显式取消以释放资源。**长期积累的失败任务会占用 FE 的元数据空间**，这是异步导入方式特有的运维负担。

**要点三：重试要用同一标签。** 与 Stream Load 一致，Broker Load 同样通过标签提供幂等性。**用新标签重试已部分成功的任务会导致数据重复**，这一点在"任务失败"与"任务超时"两种情形下都需要注意。

这三点的共同背景是"**异步把复杂性从调用方转移到了管理方**"：同步调用时，调用方通过返回值就知道结果；异步任务则要求有配套的状态管理机制。**选择异步导入方式时，必须同时准备这套管理机制，否则会出现"任务失败了没人知道"的情况。**

## 第 5 章 Routine Load：内置的消息队列消费

### 5.1 定位

**Routine Load** 是 Doris 内置的消息队列消费框架：由 Doris 自己管理消费任务，BE 作为消费者从消息队列持续拉取数据并写入表中，**不需要外部 ETL 工具**。

```sql
CREATE ROUTINE LOAD my_db.events_load ON events
    COLUMNS TERMINATED BY ",",
    COLUMNS(event_date, region, amount),
    WHERE amount > 0
PROPERTIES (
    "desired_concurrent_number" = "4",
    "max_batch_interval" = "10",
    "max_batch_rows" = "100000",
    "max_batch_size" = "104857600"
)
FROM KAFKA (
    "kafka_broker_list" = "kafka-1:9092,kafka-2:9092",
    "kafka_topic" = "events_topic",
    "property.group.id" = "doris-events-consumer"
);
```

它的核心价值是**把"批次管理"这件事从应用侧拿掉**：应用只需把数据写进消息队列，Doris 按配置的批量条件（行数、字节数、时间间隔）自动攒批并导入。**这正是第 3.5 节建议的"把批次管理交给专门组件"的具体实现。**

### 5.2 FE 与 BE 的分工

Routine Load 的架构分工值得单独说明，因为它决定了它的可用性与扩展性。

**FE 负责调度**：维护任务状态、把消息队列的分区分配给各消费子任务、管理 Offset 的提交时机、以及任务的暂停与恢复。

**BE 负责消费**：每个子任务在 BE 上作为独立线程运行，直接从消息队列拉取数据，按批量条件攒批后触发一次内部导入。

这个分工带来两个性质。**其一，消费能力可以通过增加子任务数扩展**（受消息队列分区数约束——每个分区只能被一个子任务消费）。**其二，FE 是任务管理的单点**——任务的元数据与调度都在 FE 上，因此大量 Routine Load 任务会给 FE 带来管理压力。

### 5.3 Exactly-Once 的实现

Routine Load 的 Exactly-Once 保证来自"**导入事务提交与 Offset 提交的绑定**"。

正确的顺序是：先让 Doris 的导入事务提交成功，再向消息队列提交 Offset。这样：

- 如果 Doris 事务提交失败 → Offset 不提交 → 重启后从上次提交的位置重新消费（不丢数据）；
- 如果 Doris 事务提交成功但 Offset 提交失败 → 重启后会重复消费这批数据 → 但**导入侧的 Label 幂等机制会识别出"这批已经导入过"**，从而避免重复。

两个机制的组合覆盖了"恰好一次"的语义：**前者防丢，后者防重。** 这也解释了为什么 Label 幂等在 Routine Load 里不是可选项，而是正确性的一部分。

### 5.4 延迟与批量参数

Routine Load 的延迟由批量参数决定：**数据攒够行数或字节数就提交，或者等待时间到期就提交。**

因此"降低延迟"意味着"调小批量参数"，代价是**导入频率上升**——每批更小、次数更多，元数据事务与 Rowset 的压力同步上升。这正是本专栏反复强调的权衡：**延迟与写入压力在导入环节是直接对立的两个目标。**

实践中需要注意的一点是：**延迟的下限由"消息队列自身的延迟 + 攒批窗口"共同决定**，单纯调小攒批窗口并不能让延迟无限降低。如果业务要求亚秒级延迟，那么正确的选择是改用流式写入方式（Flink Connector），而不是把攒批窗口调到极限。

### 5.5 运维与故障恢复

Routine Load 作为常驻任务，它的运维要点与一次性导入不同。

**要点一：消费延迟必须被监控。** 消费延迟（当前消费位置与队列最新位置的距离）是判断"消费是否跟得上"的核心指标。**如果它持续增长，说明消费能力不足**——可能是子任务数不够、也可能是目标表的写入能力（Compaction）成了瓶颈。

**要点二：任务需要能暂停与恢复。** 在目标表需要维护（如 Schema 变更）时，应当先暂停任务，避免导入失败累积。

**要点三：失败要有明确的可见性。** Routine Load 任务可能因为数据格式问题、目标表问题或队列问题而进入异常状态。这些状态必须被监控并告警，否则会出现"数据静默停止流入"的情况——**而这类问题比"导入失败"更危险，因为它不报错、只是没有数据。**

---

### 5.6 内置转换能力的边界

Routine Load 支持在导入过程中做简单转换：列映射、列表达式（如从某个字段计算出另一个字段）、以及 WHERE 过滤。理解这个能力的边界很重要，因为它决定了"什么时候必须引入 Flink"。

**它能做的**：字段重命名与顺序调整、简单的表达式计算（字符串截取、类型转换）、行级过滤、以及指定列的部分更新。

**它不能做的**：多表关联（无法在导入时查另一张表）、窗口聚合（无法做跨行计算）、以及**表达删除语义**（它只能追加或覆盖，无法"删除某一行"）。

**最后一条是最关键的分界。** 从业务数据库同步时，源端的 DELETE 必须被正确表达为目标端的删除；而 Routine Load 的机制里没有"删除"这个动作。因此**任何需要处理删除的同步场景，都必须使用具备删除能力的写入方式**（通常是 Flink Connector 配合唯一键模型）。

判断标准可以简化为一句：**如果源端会产生删除，或者需要跨行/跨表的加工，就应当用 Flink；否则 Routine Load 的运维成本更低。**

### 5.7 分区分配与并发度

Routine Load 的并发度不是任意设定的，它受消息队列分区数约束——**每个分区只能被一个消费子任务消费**，因此"子任务数超过分区数"是无效的。

这个约束带来两条实践建议。**其一，设定并发度时要先看主题的分区数**：如果主题只有 4 个分区，那么把子任务数设为 8 不会带来额外吞吐。**其二，需要更高并发时应当先扩分区**（如果队列支持），而不是只调 Doris 侧参数。

还有一处细节值得留意：**分区数不均会导致消费不均衡。** 如果某个分区的数据量远大于其他分区（例如上游按某个键分区而该键分布不均），那么消费该分区的子任务会成为瓶颈，整体消费延迟由它决定。**这与分布式查询里的"数据倾斜"是同一类问题**——瓶颈集中在少数分片上，增加整体并发并不能缓解。

## 第 6 章 Flink Connector：与流处理框架绑定

### 6.1 为什么需要它

Routine Load 覆盖了"简单 ETL + 消息队列"的场景，但有三类需求它无法承接。

**需求一：复杂数据转换。** 字段计算、关联维表、窗口聚合——这些需要完整的流处理能力，而 Routine Load 的内置转换能力有限。

**需求二：处理删除语义。** 从业务数据库同步时，源端会有 DELETE 操作；Routine Load 的转换能力无法表达"删除"（它只能追加或覆盖），因此需要 Flink 把删除事件转换成 Doris 能理解的语义。

**需求三：多源合并。** 把多个数据源合并后写入同一张表，需要在流处理层完成。

### 6.2 两阶段提交的绑定

Flink Connector 的核心机制是**把 Flink 的 Checkpoint 与 Doris 的事务绑定**。

执行流程是：Flink 的 Checkpoint 触发时，连接器调用 Doris 的导入接口完成"准备"阶段（数据写成未提交 Rowset），并把 Doris 的事务标识记录到 Flink 的 Checkpoint 状态里；当 Flink 的 Checkpoint 整体完成时，连接器才调用 Doris 的提交接口让数据可见；如果 Checkpoint 失败，则调用回滚接口。

这个设计的价值在于**两个系统的"成功点"被对齐了**：Flink 认为 Checkpoint 成功的时刻，正是 Doris 数据可见的时刻。因此从 Flink 恢复时，"已提交的数据已可见、未提交的数据已回滚"，不会出现"Flink 认为写成功但 Doris 里没有"这类不一致。

### 6.3 CDC 全链路架构

把上述能力用在数据库同步上，就得到了最主流的实时同步架构。

```mermaid
%%{init: {'theme': 'dracula'}}%%

    DB["业务数据库<br/>（MySQL 等）"] -- "Binlog" --> CDC["CDC Source<br/>（读取变更日志）"]
    CDC --> TR["Flink Transform<br/>（字段映射 / 过滤 / 聚合）"]
    TR --> SINK["Flink Doris Sink<br/>（两阶段提交）"]
    SINK -- "事务绑定" --> DORIS["Doris<br/>（唯一键模型）"]

```

这条链路的每一段都有明确的职责：**CDC 负责把行级变更解析为事件流**（INSERT/UPDATE/DELETE）；**Transform 负责业务语义的加工**；**Sink 负责把流写入 Doris 并保证一致性**；**Doris 侧用唯一键模型承接覆盖语义**。端到端延迟由"CDC 采集延迟 + Flink 处理延迟 + Checkpoint 间隔"共同决定。

### 6.4 与 Routine Load 的分工

两者的分工可以用一句话概括：**Routine Load 适合"数据格式简单、不需要复杂转换"的队列消费；Flink Connector 适合"需要流处理能力或处理删除语义"的场景。**

判断标准有三条：**是否需要关联维表或窗口聚合**（需要则用 Flink）；**是否需要处理删除**（需要则用 Flink）；**是否希望减少一个常驻组件**（希望则用 Routine Load）。三条都指向 Routine Load 时，它的运维成本更低；任意一条指向 Flink 时，就应当接受 Flink 的额外运维对象——**因为用 Routine Load 硬扛复杂转换，最终会在数据正确性上付出代价。**

---

### 6.5 延迟的决定因素与调优

Flink Connector 的端到端延迟由三段构成，调优时必须分别看待。

**第一段是数据源侧的采集延迟**（如 CDC 读取变更日志的速度）。这一段通常不受 Doris 控制，但它是延迟的组成部分——**如果源端采集就慢，优化下游没有意义。**

**第二段是 Flink 的处理延迟**（算子链的吞吐与背压情况）。如果出现背压，说明下游写入能力不足或算子本身成为瓶颈。

**第三段是 Checkpoint 间隔带来的"提交延迟"**。这一段的性质比较特殊：数据可能已经"准备好了"，但要等到 Checkpoint 完成才可见。因此**Checkpoint 间隔直接决定了可见延迟的下限**——间隔 1 分钟，就意味着最坏情况下数据要等近 1 分钟才可见。

由此得到两条调优结论。**其一，降低延迟最直接的手段是缩短 Checkpoint 间隔**，但代价是更频繁的提交（元数据事务压力上升）与更多的检查点开销。**其二，Checkpoint 间隔不能小于"单次 Checkpoint 的耗时"**，否则会出现检查点持续堆积——这是流处理系统里常见的失效模式。

**这条权衡与 Routine Load 的"攒批窗口"是同一件事的两种形态**：两者都在"延迟"与"写入压力"之间取平衡点。区别只在于 Routine Load 由 Doris 侧控制窗口，Flink Connector 由流处理框架侧控制周期。

### 6.6 写入模式与目标表模型的配合

Flink Connector 写入时可以选择不同的语义模式，它与目标表的数据模型必须匹配。

**追加模式**（只插入新行）适合明细模型——写入的每一行都被保留。

**UPSERT 模式**（按主键覆盖）适合唯一键模型——写入的行会覆盖同主键的旧行。

**带删除的 UPSERT 模式**适合"需要处理源端删除"的唯一键模型——它把删除事件转换为对目标行的删除标记。

**模式与模型不匹配是常见的错误来源。** 例如用追加模式写入唯一键表，会导致"更新"表现为"多出一行"（虽然唯一键表最终会去重，但期间可能出现重复）；用 UPSERT 模式写入明细表，则无法表达"更新"（明细表不按主键去重，因此每次写入都追加一行）。

**因此选写入模式时，必须先确认目标表的模型。** 这个顺序不能反——先定模型（第 4 篇的内容），再定写入模式，最后才是参数调优。

## 第 7 章 一致性与幂等性

### 7.1 标签、事务与去重

把前几章的机制汇总起来，Doris 的导入一致性与幂等性由三个要素共同保证。

**要素一：事务（Transaction）** 保证原子性——一次导入要么全可见、要么全不可见。

**要素二：标签（Label）** 提供幂等性——相同标签的导入只生效一次，重复请求被识别。

**要素三：版本（Version）** 提供读取一致性——查询在开始时确定版本，执行期间不受新导入影响。

三者的分工可以这样理解：**事务管"这批数据是否生效"，标签管"这批数据是否重复"，版本管"这次查询看到哪些数据"。** 三个问题互相独立，缺任何一个都会留下具体的漏洞。

### 7.2 重放场景的正确做法

"数据重放"是导入运维里最容易出错的场景，值得单独说明。

假设上游发现某天的数据有错误，需要重新推送。此时正确的做法取决于表的**数据模型**（这一点与第 4 篇直接相关）。

**对明细模型**：重放会追加新的行，因此**必须先删除该范围的数据再重放**，否则会出现"同一份数据存在两份"。

**对聚合模型**：重放会让 SUM 类指标翻倍，因此**同样必须先删除再重放**。

**对唯一键模型**：重放会按主键覆盖，因此**在数据内容完全一致的前提下可以直接重放**（结果幂等）；但如果重放的数据与已导入的不同（例如修正了某些字段），则结果取决于序列列的配置。

**这条规则的统一表述是："重放前先确认模型的写入语义。"** 而它的实践难点在于：删除操作本身也需要谨慎（按分区删除比按条件删除更高效也更安全）。

### 7.3 导入失败的分类与处置

导入失败按性质分两类，处置方式完全不同。

**系统性失败**（网络、磁盘、进程重启）：特征是"全部数据都没进去"。处置是排除环境问题后用**相同标签**重试。

**数据质量失败**（格式不符、字段数量不匹配）：特征是"部分行被过滤"。处置取决于策略配置——可以配置为整批拒绝（保证不静默丢数据），也可以配置为过滤错误行（保证链路不中断）。

对后者的实用折中是"**开启错误行过滤，同时对错误行比例设置告警**"——既不让个别坏行阻塞链路，又能在坏行比例异常时被及时发现。**数据质量的治理原则是"允许个别异常，但必须可观测"。**

---

### 7.4 导入的可观测性

导入的可观测性有三个层次，缺一层就会出现盲区。

**第一层：单次导入的结果。** 每次导入返回的状态、总行数、成功行数、过滤行数、耗时。这一层回答"这一批是否正常"。

**第二层：导入任务的健康度。** 对常驻任务（Routine Load）与异步任务（Broker Load）而言，需要监控任务状态与消费/处理延迟。这一层回答"任务是否在正常工作"。

**第三层：导入对系统的影响。** 导入频率、产生的 Rowset 数量、对 Compaction 的压力、以及导入期间的查询延迟。这一层回答"导入是否在损害系统"。

**第三层是最容易被忽略的，也是最重要的。** 因为前两层关注的是"导入本身是否成功"，而导入的真正风险往往在"它对系统的长期影响"上——**一个每批都成功、每批都很快的导入链路，可能正在稳定地积累 Rowset 债务。** 只有把导入指标与存储引擎指标放在一起看，才能发现这类问题。

## 第 8 章 导入的调优与排障

### 8.1 导入慢：三段定位

导入慢的定位可以沿"分发、写入、提交"三段展开。

**分发段**：数据从来源到 BE 的传输是否成为瓶颈。看网络带宽与来源侧（消息队列、对象存储）的读取速率。

**写入段**：BE 把数据解析、排序、落盘的过程。看 BE 的 CPU 与磁盘 IO——**如果磁盘接近饱和，写入段就是瓶颈**。

**提交段**：等待所有 BE 完成并提交。**如果各 BE 的完成时间差异很大，提交段就会被最慢的那一路拖住**——此时问题不在"导入本身"，而在"集群负载不均衡"。

这条三段划分的价值在于：**它把"导入慢"从一个笼统现象拆成了三个可分别验证的假设。**

### 8.2 常见错误与对策

| 现象 | 常见原因 | 对策 |
|---|---|---|
| 导入超时 | 单批数据过大、BE 负载高 | 减小单批数据量、错峰导入 |
| 部分行被过滤 | 数据格式与列定义不符 | 检查分隔符与列映射，配置错误行告警 |
| 重复导入报错 | 标签重复（正常行为） | 用新标签或确认前次是否已成功 |
| 导入频率高导致查询变慢 | Rowset 与 Compaction 积压 | 降低导入频率、增大单批数据量 |
| 消息队列消费延迟持续增长 | 消费能力不足或目标表写入受限 | 增加子任务数、检查 Compaction 状态 |

最后一行值得展开：**消费延迟增长的根因可能在"目标表的写入能力"上，而不在消费侧。** 如果表上的 Compaction 已经积压，那么每次导入的提交都会变慢，进而拖慢消费。此时增加消费子任务只会让积压更严重。**这也是为什么导入与存储引擎的监控必须一起看。**

### 8.3 导入对查询的影响

导入与查询共享同一批 BE 资源，因此导入会以三种方式影响查询。

**其一是资源争抢**：导入的 CPU 与磁盘 IO 占用会挤占查询资源，表现为查询延迟上升。

**其二是 Rowset 增长**：导入产生的 Rowset 会增加查询时的合并开销，**这是一个"滞后生效"的影响**——导入本身很快，但它留下的 Rowset 会让之后的查询变慢。

**其三是元数据事务压力**：高频导入会推高 FE 的事务负载，表现为导入提交变慢，并可能间接影响查询的计划生成。

**这三条影响里，第二条最容易被忽略**：团队看到"导入很快"就认为没有问题，直到某天查询集体变慢才发现是 Rowset 积压。**因此"导入健康度"的指标不能只看导入耗时，还要看它留下的 Rowset 数量。**

---

### 8.4 导入压测与容量规划

导入能力需要被测量，否则容量规划只能凭经验。

**压测要回答三个问题**：单批导入的耗时随数据量如何变化（线性还是有拐点）、并发导入的吞吐上限在哪里（从哪个并发度开始收益递减）、以及导入对查询的影响有多大（同样的查询在导入期间慢多少）。

**容量规划要回答一个问题**：这张表的写入频率上限是多少？这个上限由"集群的 Compaction 能力"决定，而不是由"导入接口的吞吐"决定——**因为导入接口通常比 Compaction 更快，所以真正的约束在后者。** 规划方法可以是：先测出集群在稳态下的 Compaction 吞吐（单位时间能合并多少数据），再据此反推"单位时间可以导入多少数据"，最后折算成"每批多大数据、间隔多久"。

这条规划路径的价值在于**把"导入频率"从经验值变成推导值**。实践中大量导入引发的性能问题，根源都是"导入频率是按业务需要定的，而不是按集群能力定的"——而这两个数字往往相差数倍。

### 8.5 限速：让导入"让路"给查询

当导入与查询争抢资源时，"限速"是最直接的调节手段。可用的维度有三个。

**维度一：限制导入的并发度。** 减少同时进行的导入任务数，从而降低它对 BE 资源的瞬时占用。

**维度二：限制单批数据量。** 减小单批规模可以缩短单次导入的持续时间，让资源占用更"平滑"。

**维度三：限制导入的 IO 速率。** 部分导入方式支持速率限制，直接约束它对磁盘的占用。

三个维度的适用场景不同：**如果问题是"导入高峰期查询变慢"，用维度一（降并发）；如果问题是"单次导入持续时间过长影响其他任务"，用维度二（减批量）；如果问题是"磁盘 IO 被导入打满"，用维度三（限速率）。**

一条通用原则是：**限速的目标不是"让导入变慢"，而是"让导入的负面影响变得可预测"。** 一个被限速的导入仍然是"确定的慢"，而一个不限速的导入会让整个集群的表现变得不可预测——**在共享资源的系统里，"可预测"往往比"快"更重要。**

## 第 9 章 边界与反例

### 9.1 反例一：把导入当成"不占资源的操作"

导入要消耗 CPU（解析与排序）、磁盘 IO（落盘）、网络（分发）与元数据事务（提交），并且会留下需要后续合并的 Rowset。把它当作"轻量操作"会导致资源规划失准。**导入的成本不只体现在它自己的耗时上，还体现在它给系统留下的后续工作。**

### 9.2 反例二：用新标签重试超时的导入

HTTP 超时不代表导入失败。用新标签重试会导致数据重复，而重复数据在明细模型上表现为"多出来的行"、在聚合模型上表现为"指标翻倍"。**正确做法是用同一标签重试。**

### 9.3 反例三：为追求低延迟把批量窗口调到极限

把攒批窗口调到极小会让导入频率极高，从而推高元数据事务与 Compaction 压力。**延迟与写入压力在导入环节直接对立**，调参时必须同时看两边的指标。

### 9.4 反例四：用 Routine Load 硬扛复杂转换

Routine Load 的转换能力有限，尤其无法表达删除语义。用它承接 CDC 同步会导致"源端的删除在目标端表现为不删除"，而这类错误往往在很久之后才被发现。**需要删除语义时应当使用支持两阶段提交与删除处理的写入方式。**

### 9.5 反例五：忽略消费延迟的监控

Routine Load 任务可能因为各种原因进入异常状态而停止消费。如果只监控"任务是否存在"而不监控"消费延迟"，就会出现"数据静默停止流入"——**这类故障比导入失败更危险，因为它不产生错误、只产生缺失。**

### 9.6 反例六：在业务高峰期执行大批量导入

大批量导入会长时间占用 BE 资源，与查询争抢。把它安排在高峰期执行，会让"查询变慢"与"导入变慢"同时发生，且难以归因。**导入应当与查询错峰，或显式限速。**

### 9.7 反例七：把"导入成功"等同于"数据可用"

导入成功只意味着"数据已提交、对查询可见"，不意味着"数据是正确的"（可能被过滤掉部分行）、也不意味着"查询会快"（可能留下大量 Rowset）。**导入的验收标准应当包含"行数核对"与"Rowset 健康度"两项，而不是只看返回状态。**

---

### 9.8 反例八：把导入频率按业务需要定，而不按集群能力定

这是最普遍的根因。业务方希望"数据越快可见越好"，于是把导入频率定得很高；而集群的 Compaction 能力是固定的。两者的差距会以"查询逐渐变慢"的形式暴露出来，而届时已经很难让业务方降频。**正确的做法是在容量规划阶段就把这个约束显式地告知业务方，并把它写进数据接入规范。**

### 9.9 反例九：只测导入吞吐，不测导入对查询的影响

导入压测通常只关注"导入能多快"，但导入的真实成本还包括"它对查询的影响"。如果压测只测前者，就会得出"导入能力充足"的错误结论——而生产环境里真正的投诉往往来自"查询变慢了"。**导入压测必须包含查询侧的观测，因为导入与查询共享的是同一批资源，而资源竞争的成本只会体现在查询侧。**

## 第 10 章 落点

回到开头：导入这一环要同时满足原子性、幂等性与可运维性。三种主流方式各自用不同的机制达成这三项要求——Stream Load 靠同步调用与 Label 幂等，Routine Load 靠事务与 Offset 的提交顺序绑定，Flink Connector 靠 Checkpoint 与事务的绑定。

但这三种机制背后是同一个判断：**导入的可靠性来自"把成功点对齐"**。Stream Load 把"响应返回"与"数据可见"对齐；Routine Load 把"事务提交"与"Offset 提交"对齐；Flink Connector 把"Checkpoint 完成"与"事务提交"对齐。**凡是能明确回答"在哪个时刻可以认为这批数据已安全"的方案，就能做到端到端一致；凡是模糊这个时刻的方案，就会在故障时产生难以定位的不一致。**

而这一切都受制于同一条纪律：**导入频率必须与集群的合并能力匹配。** 因为每次导入都在系统里留下一笔"待合并"的债务，而债务的偿还能力由集群规模决定。理解了这一点，就能理解为什么"导入频率"是本专栏反复出现的核心变量——**它不是导入方式的属性，而是整个存储模型对写入方的要求。**

把五篇的内容串起来看，Doris 的导入设计其实回答了一个更大的问题：**一个"写入代价高、读取代价低"的存储引擎，如何让写入方以可接受的成本把数据送进来。** 答案分成三层：接口层提供多种方式以适配不同的数据来源；机制层用两阶段提交与标签保证原子性与幂等；约束层则要求写入方遵守"攒批"的纪律。这三层里，接口层最容易被替换（换一种导入方式即可），机制层最不容易出错（由系统保证），只有约束层需要长期协作。

**三层里最容易出问题的是第三层**——因为前两层由系统保证，第三层依赖写入方的配合。而"要求写入方改变行为"在实践中是最难的，这也是为什么导入相关的性能问题往往不是技术问题，而是协作问题：**需要把"集群的合并能力"这个技术约束，翻译成业务方能理解并接受的"数据接入规范"。** 下一篇将转向运维，看分区、分桶、慢查询诊断与集群变更这些长期工作如何把这套约束落到实处——因为导入的纪律只有在运维层面被持续检查，才可能真正被执行。反过来，如果运维只关注"服务是否可用"而不关注"写入节奏是否合理"，那么导入侧积累的债务最终仍会以查询变慢的形式暴露出来。
