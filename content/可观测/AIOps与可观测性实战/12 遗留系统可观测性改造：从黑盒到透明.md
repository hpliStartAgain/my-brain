## 摘要

2023 年，某国有银行的核心交易系统出现了一次持续 47 分钟的性能降级：交易响应时间从正常的 200ms 逐渐升高到 8 秒，期间没有任何告警触发，直到客服热线开始接到大量用户投诉，运维团队才意识到问题的存在。这套运行了 14 年的 Java 单体系统，没有 Metrics 暴露端点，没有结构化日志，只有每 5 分钟轮询一次可用性的"黑盒监控"（Ping-check）。故障已经发生了 47 分钟，系统仍然显示"绿色"。

这不是个例。金融、电信、制造等传统行业中，大量核心业务系统都是"黑盒"：从外部只能看到它是否可达，无法看到内部的处理状态、资源使用情况和性能瓶颈。本文探讨如何在不大规模重写遗留系统的前提下，渐进式地为其建立可观测性能力。

---

## 第 1 章 遗留系统的可观测性困境

### 1.1 为什么遗留系统难以改造

遗留系统（Legacy System）通常具有以下特征，使得可观测性改造面临特殊挑战：

**代码层面**：没有 Metrics 暴露能力、日志是非结构化文本（甚至是固定格式的报文，非人类可读的日志）、没有链路追踪的 Trace Context 传播、核心业务逻辑耦合了大量基础设施细节。

**知识层面**：原始开发者已经离职，没有完整的系统文档，没有人真正理解系统内部的工作原理（"运转就好，不要动"的心态）。

**组织层面**：遗留系统的修改风险极高（触一发而动全身，没有自动化测试，修改可能引入不可预见的副作用），变更审批流程复杂，导致技术债务持续积累，无人愿意深入重构。

**技术层面**：遗留系统可能运行在不再维护的语言版本或框架上（如 Java 6、PHP 5.6、Python 2.7），现代的可观测性库无法直接在这些版本上运行。

### 1.2 三阶段改造框架

面对遗留系统的可观测性改造，不存在"一步到位"的解决方案，必须采用渐进式方法，分三个阶段逐步提升系统的可见性：

**第一阶段 - 黑盒监控（外部视角）**：在不修改系统内部代码的前提下，从系统外部建立监控。这包括：HTTP/TCP 可达性探测（Blackbox Exporter）、日志文件的关键词匹配告警、端口可用性检查、外部事务模拟（合成监控，定期执行模拟用户操作的脚本）。第一阶段能够发现"系统宕机"或"功能完全失效"，但无法发现性能降级和局部故障。

**第二阶段 - Sidecar 代理监控（进出口视角）**：通过在遗留系统的前面部署反向代理（如 Nginx 或 Envoy），收集所有进出遗留系统的 HTTP/TCP 流量的 Metrics（请求速率、错误率、延迟），以及在网络层注入链路追踪（Trace ID）。第二阶段能够实现服务级别的 RED Metrics 和基本的调用链路可见性，无需修改遗留系统任何代码。

**第三阶段 - 应用内 SDK 集成（进程内视角）**：最终在遗留系统内部集成 Prometheus Client、OpenTelemetry SDK 或 APM Agent（如 Elastic APM、SkyWalking），获得进程内的细粒度 Metrics（JVM 内存、GC 时间、线程池状态、数据库连接池使用情况）和方法级别的链路追踪。第三阶段提供最完整的可观测性，但需要修改（或至少重启并注入 Agent）遗留系统。

## 第 2 章 第一阶段：黑盒监控的技术实现

### 2.1 Prometheus Blackbox Exporter

[[Prometheus Blackbox Exporter]] 是 Prometheus 官方提供的黑盒探测工具，支持 HTTP/HTTPS、TCP、ICMP、DNS 探测，可以验证：目标 URL 的响应码是否符合预期（如是否返回 200）、响应体中是否包含特定关键词（如"交易成功"）、TLS 证书的有效期、DNS 解析的正确性。

通过 Blackbox Exporter，可以实现"用户视角的可用性监控"：从外部模拟用户访问，测量端到端的响应时间和成功率，作为 SLO 的基准指标。这是遗留系统可观测性改造的最低成本起点——只需要在运维基础设施上部署 Blackbox Exporter，不需要触碰遗留系统本身。

### 2.2 合成监控（Synthetic Monitoring）

可达性探测（Ping-check）只能检测系统是否"活着"，无法验证核心业务功能是否正常。**合成监控**（Synthetic Monitoring）通过定期执行模拟真实用户操作的脚本，检测业务功能的完整性：

模拟用户登录流程（GET /login 页面 → POST /login 提交凭证 → 验证跳转到主页）、模拟完整的下单流程（搜索商品 → 加购物车 → 结算 → 提交订单）、模拟 API 调用链（外部系统调用遗留系统的 API，验证返回值的正确性）。

合成监控是发现"功能性降级"的关键手段：系统虽然可达（Ping-check 成功），但登录功能因为数据库连接超时而响应很慢，只有合成监控的登录脚本才能发现这个问题。

### 2.3 日志文件的关键词监控

遗留系统通常有大量的日志输出（即使是非结构化的），这些日志中往往包含有价值的信息：ERROR/EXCEPTION 关键词（业务逻辑异常）、连接超时/Connection Refused 信息（依赖故障）、内存不足/Out of Memory 告警。

通过在遗留系统所在服务器上部署 `Filebeat` 或 `Fluentd` 采集日志文件，将日志发送到 Elasticsearch/Loki，然后对关键词（ERROR、EXCEPTION、OOM、TIMEOUT）进行实时监控和告警，可以在不修改遗留系统的前提下，提前发现潜在问题。

## 第 3 章 第二阶段：Sidecar 代理与网络层可观测性

### 3.1 Nginx 的详细访问日志

将遗留系统放置在 Nginx 反向代理后面，通过配置 Nginx 的详细访问日志（记录每个请求的响应时间、响应状态码、响应体大小、上游响应时间），并通过 `nginx-prometheus-exporter` 将 Nginx Metrics 暴露给 Prometheus，可以获得：每个 API 端点的请求速率、错误率和 P99 延迟（RED Metrics），以及 Nginx 层面的连接数、活跃连接数等网络状态指标。

这种方式的优点是完全不需要修改遗留系统——Nginx 是在遗留系统前面新增的一层，遗留系统对此完全无感知。所有的 Metrics 采集都在 Nginx 层完成。

### 3.2 Envoy 代理与 Trace Context 注入

[[Envoy]] 是 Istio 服务网格的数据平面组件，也可以作为独立的 Sidecar 代理部署在遗留系统旁边。Envoy 相比 Nginx 提供了更丰富的可观测性特性：

**自动 Trace Context 注入**：Envoy 可以为每个经过代理的 HTTP 请求自动注入 `x-request-id`、`x-b3-traceid`（Zipkin B3 格式）或 `traceparent`（W3C TraceContext 格式）Header，即使遗留系统本身不理解这些 Header，下游的新系统可以读取这些 Header，在调用链路中关联来自遗留系统的请求，提供部分的端到端链路可见性。

**细粒度的 Metrics**：Envoy 提供 Prometheus 格式的 Metrics，包括：L7 层的每个路由的请求量、错误率、延迟百分位；连接池状态（等待连接数、活跃连接数）；熔断器状态（是否触发熔断）；以及上游集群（遗留系统）的健康状态。

## 第 4 章 第三阶段：应用内 SDK 集成

### 4.1 Java Agent 的无侵入 APM

对于 Java 遗留系统（这是最常见的遗留系统类型），Java Agent 技术提供了一种"无需修改代码、只需修改启动命令"的 APM 集成方式：

通过在 Java 进程的启动命令中添加 `-javaagent:/path/to/elastic-apm-agent.jar`（或 OpenTelemetry Java Agent），APM Agent 在 JVM 启动时通过字节码增强（Bytecode Instrumentation）自动为应用代码注入 Trace 采集逻辑，拦截：HTTP 请求的进入和响应（自动创建 Span，记录 URL、Method、Status Code、延迟）、JDBC 的数据库查询（自动创建 DB Span，记录 SQL 语句和查询延迟）、Redis/Memcache 的缓存操作、JVM 自身的 Metrics（堆内存、GC 时间、线程数）。

这种方式的优势是：无需修改遗留系统任何代码，只需要修改启动脚本，添加一行 javaagent 参数，即可获得应用级别的全面可观测性。唯一的要求是遗留系统能够被重启（在计划维护窗口内）。

对于无法重启的遗留系统（如 7×24 小时运行、无维护窗口的关键系统），可以使用 DCEVM（Dynamic Code Evolution Virtual Machine）或 Arthas（阿里巴巴开源的 Java 诊断工具）的 Attach 功能，在不重启的情况下动态注入监控逻辑。

### 4.2 非 Java 遗留系统的改造路径

**Python 遗留系统**：Python 3.6+ 支持 OpenTelemetry 的自动仪表化（`opentelemetry-instrument` 命令），类似于 Java Agent，可以在不修改代码的情况下自动采集 Flask/Django 的请求 Metrics 和 Traces。对于更老的 Python 版本，可能需要手动集成 Prometheus Python Client 库（需要修改代码）。

**PHP 遗留系统**：PHP 支持通过 `APCu`、`php_uopz` 等扩展实现部分的 APM 功能。也可以通过 Nginx + PHP-FPM 的详细状态端点获取 PHP-FPM 的进程状态 Metrics（活跃进程数、等待进程数、队列深度）。

**.NET 遗留系统**：.NET Core 和 .NET 5+ 支持 OpenTelemetry .NET SDK；.NET Framework 4.x 遗留系统可以使用 Elastic APM .NET Agent（通过 NuGet 包安装，支持 .NET Framework 4.6+）。

## 第 5 章 Strangler Fig 模式与渐进式重构

### 5.1 什么是 Strangler Fig 模式

[[Strangler Fig]]（勒死榕模式）是 Martin Fowler 提出的遗留系统渐进式替换模式，其名称来自一种热带植物——勒死榕树的种子落在宿主树上，慢慢生长，逐渐包围并最终替代宿主树。

在软件架构中，Strangler Fig 的含义是：不试图"一次性重写"整个遗留系统（"大爆炸"重写失败率极高），而是在遗留系统旁边逐步建立新系统，将遗留系统的功能一个一个地迁移到新系统，直到遗留系统的功能被完全替代，可以安全下线。

这个模式与可观测性改造的关系是：在新旧系统并行运行期间，对遗留系统的可观测性数据（从第一、二阶段已经建立的监控）进行持续对比，验证新系统是否达到了遗留系统的功能和性能基准，是迁移进度决策的重要数据依据。

### 5.2 流量切分与灰度验证

在 Strangler Fig 模式下，流量从遗留系统逐渐迁移到新系统，通常经历以下阶段：

**影子模式（Shadow Mode）**：所有流量仍然发送到遗留系统，同时将相同的流量镜像发送到新系统。新系统的响应被丢弃（不影响真实用户），但其行为（响应时间、错误率、响应内容的差异）被记录和分析。这个阶段用于验证新系统与遗留系统的行为一致性，而不冒任何用户影响风险。

**金丝雀阶段**：将 1%-5% 的真实流量切换到新系统，通过可观测性数据（SLO 指标对比、错误率对比）验证新系统在真实流量下的表现，发现遗留系统测试无法覆盖的真实用户行为导致的问题。

**渐进切换**：确认金丝雀阶段没有问题后，逐步提高新系统的流量比例（10% → 25% → 50% → 100%），每个阶段都通过可观测性数据验证新旧系统的 SLO 表现对比，确保迁移不会导致用户体验降级。

## 第 6 章 ROI 分析：向管理层证明改造价值

### 6.1 量化改造的成本与收益

遗留系统可观测性改造需要投入资源（人力成本），管理层会要求清晰的 ROI（投资回报率）分析。以下框架有助于量化改造的收益：

**改造前的成本**：每次故障的平均检测时间（MTTD）× 故障成本率（每分钟宕机损失，通常按业务损失或 SLA 罚款计算）× 年故障次数。例如：MTTD = 45 分钟，每分钟业务损失 3000 元，年故障 8 次 → 故障检测延迟成本 = 45 × 3000 × 8 = 108 万元/年。

**改造后的预期改善**：根据行业数据，从"黑盒监控"到"白盒监控"，MTTD 通常能够缩短 70-80%（从 45 分钟降低到 10 分钟）。改造后故障检测延迟成本 = 10 × 3000 × 8 = 24 万元/年。年节省 = 108 - 24 = 84 万元。

**改造成本**：假设改造需要 2 名工程师投入 3 个月（第一、二阶段），人力成本约 30 万元；工具和基础设施成本约 5 万元/年。

**ROI 计算**：第一年 ROI = (84 - 30 - 5) / (30 + 5) × 100% = 140%。即第一年就能收回成本，并有 140% 的净收益。第二年起，净年收益 = 84 - 5 = 79 万元/年（没有初始开发成本）。

## 第 7 章 真实案例：某股份制银行核心系统改造

### 7.1 背景与挑战

某股份制银行运营着一套运行了 16 年的核心交易处理系统（Java 6 + Spring 2.5 + IBM WebSphere AS），处理每日数百万笔的国内转账、境外汇款和外汇兑换业务。

该系统面临的可观测性困境：无任何 Metrics 暴露端点、日志以专有格式写入 IBM WebSphere 的内部日志系统（无法用标准工具采集）、运维监控仅有 Nagios 的 TCP 可用性检查（每 5 分钟一次）、系统的性能状态完全不可见（"是否有性能瓶颈？在哪里？"无法回答）。

系统的变更风险极高：任何代码修改都需要经过 3 周的测试周期和多层审批，且必须在每月一次的维护窗口（凌晨 2:00-6:00）部署。

### 7.2 改造实施过程

**阶段一（第 1-3 个月）：外部黑盒监控**

在不对遗留系统做任何修改的前提下，部署：Prometheus Blackbox Exporter（每 30 秒检查 HTTP 端点的响应时间和响应码）、合成监控脚本（每 2 分钟模拟完整的转账流程，包括查询余额、发起转账、验证回执）、WebSphere 系统 Metrics 采集（通过 WebSphere 的 PMI 接口采集 JVM 和线程池状态，不需要修改应用代码）。

这一阶段首次建立了基于业务功能的告警（合成监控告警：转账模拟失败率 > 5%），而不只是基础设施告警（TCP 端口可达性）。在实施的第 3 周，通过合成监控发现了一个之前未被察觉的问题：每天 14:00-15:00，境外汇款功能的响应时间从正常的 1.5 秒升高到 8-12 秒，恰好对应外汇市场开盘时段的业务高峰，但从未触发过 Nagios 的告警（因为系统仍然可达）。这个发现直接推动了对应时段的线程池优化工作。

**阶段二（第 4-6 个月）：F5 负载均衡 Metrics 集成**

银行网络架构使用 F5 负载均衡器前置于核心系统，通过 F5 的 iControl API 接口，编写自定义 Exporter 采集 F5 的连接状态 Metrics（虚拟服务器的连接数、活跃连接数、连接队列深度、响应时间分布），并将这些 Metrics 接入 Prometheus，在 Grafana 中创建展示核心系统流量状态的 Dashboard。

这一阶段实现了更精细的流量可见性，同时完全不需要修改遗留系统。

**阶段三（第 7-12 个月）：Java Agent 集成**

利用一次计划内的系统升级机会（WebSphere 从 8.5 升级到 9.0），在升级过程中将 OpenTelemetry Java Agent（适配 Java 6/7 的旧版本）注入到 WebSphere 的 JVM 启动参数中。

这一步需要最细心的准备：在测试环境全面验证 Agent 不影响系统功能（运行 3 周的完整业务测试用例）、确认 Agent 的性能开销在可接受范围内（测试显示约 3-5% 的 CPU 开销增加，在业务可接受范围内）、准备详细的回滚方案（如果 Agent 导致问题，可以在 5 分钟内移除并重启 JVM）。

Java Agent 集成后，首次获得了进程内的细粒度 Metrics：JVM 堆内存使用率和 GC 频率（发现 Minor GC 在业务高峰期每 30 秒发生一次，影响响应时间）、线程池状态（发现境外汇款线程池在高峰期长期满载，确认了之前合成监控发现的性能问题的根因）、JDBC 数据库查询延迟（发现 3 条高频 SQL 查询缺乏合适的数据库索引，平均查询时间 > 200ms）。

### 7.3 改造成果与量化收益

经过 12 个月的三阶段改造：

**可观测性覆盖率**：从近乎零（只有 TCP Ping 检查）提升到覆盖系统的所有核心功能（业务 SLO Dashboard + 进程内细粒度 Metrics）。

**MTTD（平均检测时间）**：从 47 分钟（等到用户投诉）降低到 4 分钟（合成监控 + Burn Rate 告警）。

**发现的潜在问题**：12 个月内，通过新建立的可观测性能力，主动发现了 5 个此前未知的性能瓶颈，其中 3 个（JDBC 索引缺失、线程池配置不当、GC 频率过高）经过优化后，系统整体 P99 延迟从 8 秒降低到 1.2 秒。

**量化业务价值**：MTTD 降低 91%，按前述 ROI 模型计算，第一年净节省约 280 万元（含性能优化带来的硬件成本节省）。

## 第 8 章 变更管理：让保守的组织接受可观测性改造

### 8.1 改造阻力的来源分析

在传统行业（金融、政府、电信）的遗留系统改造项目中，技术难度往往不是最大的挑战，组织变更阻力才是。理解阻力的来源，是制定有效推进策略的前提：

**"稳定性优先"心态**：核心业务系统的 7×24 小时稳定运行是压倒一切的目标，任何"不必要"的改动都被视为风险。可观测性被视为"锦上添花"而非"雪中送炭"，在没有发生大故障之前，很难获得改造资源。

**责任规避心理**：如果"改造后系统出了问题"，推动改造的人会被追责。即使改造本身没有引入问题，而是别的原因导致系统异常，推动改造的人仍然可能成为替罪羊。这种责任规避心理导致工程师宁可维持"看起来没问题"的黑盒状态。

**短期成本 vs 长期收益**：改造需要当期投入（人力、测试时间、审批流程），而收益（更快的故障发现、更低的运维成本）是长期的。在预算和资源有限的情况下，当期成本优先于长期收益是常见的决策偏向。

### 8.2 推进改造的策略

**从"痛点"切入，而非从"技术蓝图"切入**：不要向管理层展示一个宏大的"可观测性平台改造计划"，而是从一个具体的、让人印象深刻的痛点出发：上次故障花了多久才发现？历史上有哪次故障是因为缺乏监控而导致排查时间过长？将改造的价值与具体的、已经发生的业务损失挂钩，比抽象的技术愿景更有说服力。

**从最低风险的第一阶段开始**：第一阶段（黑盒监控）完全不修改遗留系统，变更风险为零，审批难度最低。先完成第一阶段，建立可观测性的初步价值（提前发现一两个未知问题），以此作为推进第二、三阶段的内部成功案例。"已经发现了一个之前不知道的问题"，比任何 PPT 都更有说服力。

**建立回滚预案，降低决策风险**：对于每一步改造，都要准备详细的、经过演练的回滚方案。管理层决策时，清晰的回滚预案（"如果出现问题，5 分钟内可以恢复到改造前状态"）能够显著降低批准改造的心理门槛。

## 第 9 章 遗留数据库的可观测性改造

### 9.1 Oracle/DB2 遗留数据库的 Metrics 采集

遗留系统通常连接着年份更久的关系型数据库（Oracle 11g、IBM DB2、SQL Server 2008），这些数据库往往是整个系统链路中最难被替换的组件，也是最重要的可观测性改造目标（数据库通常是性能瓶颈的首要来源）。

[[Prometheus Database Exporter]]（多种语言实现）通过数据库的系统视图或管理 API，采集数据库的关键 Metrics：活跃连接数和等待连接数（连接池使用情况）、正在执行中的慢 SQL 数量（执行时间 > N 秒的查询数量）、表的读写 IOPS 和响应延迟（存储层的 I/O 状态）、缓冲池命中率（Buffer Cache Hit Ratio，衡量内存是否充足）、锁等待事件（锁争用是数据库性能问题的常见根因）。

这些 Metrics 都是通过查询数据库自身的性能视图（Oracle 的 v$session、v$sql、v$wait_stat 等；DB2 的 mon_get_activity 等）获取的，不需要修改应用或数据库本身，属于"非侵入式"采集。

### 9.2 慢 SQL 日志的结构化分析

几乎所有主流数据库都支持慢 SQL 日志（Slow Query Log），记录执行时间超过阈值的 SQL 语句。将慢 SQL 日志接入 Loki/Elasticsearch 进行分析，可以回答：哪些 SQL 语句消耗时间最多（TopK 分析）？慢 SQL 的出现频率和时间分布（是否有规律，如业务高峰期才出现）？哪些表和索引是性能瓶颈的核心（SQL 执行计划分析）？

在遗留系统中，慢 SQL 分析往往是改造中性价比最高的工作：不需要修改任何代码，只需要开启数据库的慢查询日志，就能发现系统中最大的性能瓶颈，通过加索引或优化 SQL（有时候只需要数小时工作）即可获得数倍的性能提升。

## 第 10 章 容器化遗留系统的可观测性机遇

### 10.1 容器化是可观测性改造的黄金机会

许多遗留系统改造的第一步是"容器化"（将遗留系统打包为 Docker 镜像，部署到 Kubernetes）。容器化过程是可观测性改造的天然窗口期——必须重写启动脚本和部署配置，可以趁机注入 Java Agent、修改日志配置（改为结构化日志）、添加健康检查端点。

容器化后，遗留系统立即获得 K8s 生态的可观测性红利：kube-state-metrics 自动采集 Pod 的状态（重启次数、资源使用率）、Prometheus Operator 的 Service Monitor 自动发现新部署的服务（如果遗留系统有 /metrics 端点）、K8s 的存活探针（livenessProbe）和就绪探针（readinessProbe）提供基本的健康检查能力。

### 10.2 OpenTelemetry Operator 的自动仪表化

在 Kubernetes 中，[[OpenTelemetry Operator]] 提供了"自动仪表化"功能：通过在 Namespace 或 Deployment 上添加特定的 Annotation，Operator 会自动将 OpenTelemetry Java/Python/.NET Agent 注入到对应的 Pod 中，无需修改 Deployment 的镜像或容器配置。

这是遗留系统容器化后获得链路追踪能力的最便捷路径：不需要修改遗留系统的代码，不需要重新构建镜像，只需要在 K8s 中添加一个 Annotation，OpenTelemetry Operator 就会自动完成 Agent 注入。

## 第 11 章 遗留系统改造的质量保证体系

### 11.1 改造过程中的回归测试

在遗留系统中进行任何修改（即使是只添加 Agent 注入），都必须有充分的回归测试保证不引入新问题。但遗留系统通常缺乏完善的自动化测试。

**流量录制与回放**是遗留系统回归测试的有效替代方案：在改造前，使用 [[GoReplay]] 或 [[Tcpreplay]] 等工具录制真实的生产流量（HTTP 请求/响应对），建立基准。在改造后，使用同样的录制流量在测试环境回放，对比改造前后的响应内容和响应时间，验证功能和性能没有发生变化。

这种方式不需要编写任何测试代码，利用真实的生产流量作为测试数据，测试覆盖率远高于手写测试用例，是遗留系统改造中最实用的质量保证手段。

### 11.2 改造前后的性能基准对比

在每次改造步骤执行后，通过可观测性数据（改造后新建立的 Metrics Dashboard）与改造前的基准数据对比，验证改造没有引入性能回退：

CPU 和内存使用率对比（Agent 的开销是否在预期范围内）、P99 延迟对比（改造后的延迟是否与改造前一致）、错误率对比（改造后是否出现新的错误类型）。

这个对比过程本身就是可观测性改造的价值体现——正因为有了 Metrics，才能做改造前后的量化对比，才能客观评估改造的影响，而不是依赖人工测试的主观判断。

## 第 12 章 遗留系统可观测性改造的长期路线图

### 12.1 从改造到现代化的演进路径

遗留系统的可观测性改造不是终点，而是系统现代化的起点。通过建立可观测性能力，团队获得了对系统内部状态的清晰认知，这是进行更深度改造（性能优化、架构重构、微服务拆分）的数据基础。

改造路径的推荐顺序：

1. 建立可观测性（本文所述的三阶段方法）
2. 基于可观测性数据，识别和修复最严重的性能瓶颈（通常 20% 的问题导致 80% 的性能损失）
3. 建立自动化测试（利用流量录制与回放，逐步为系统建立回归测试套件）
4. 渐进式重构（在有了测试保护和可观测性监控的双重保障下，对系统进行有针对性的局部重构）
5. Strangler Fig 迁移（将重构好的模块逐步提取为独立服务，用现代架构替代遗留模块）

### 12.2 可观测性是技术债务的"债务表"

遗留系统通常积累了大量技术债务（过时的设计、未解决的缺陷、次优的实现），但这些债务是不可见的——没有人知道系统的真实状况，只知道"能用就行"。

可观测性改造的一个重要副作用是：让技术债务变得可见。当你能看到 JVM 的 GC 频率（过高），能看到数据库连接池的等待时间（过长），能看到特定 API 的错误率（偏高），这些问题从"可能存在"变成了"明确存在且有量化数据"。

可见的问题才能被优先级排序和解决。可观测性改造将遗留系统的技术债务从"隐性债务"转变为"显性债务"，是启动系统现代化计划的第一步，也是最重要的一步。

## 附录 A：遗留系统改造检查清单

### A.1 改造前的准备工作

在启动遗留系统可观测性改造之前，需要完成以下准备工作：

**系统基础信息梳理**：确认系统的技术栈（语言、版本、框架）、部署方式（物理机/虚机/容器）、依赖的外部系统（数据库、消息队列、第三方 API）、当前的监控覆盖情况（是否有任何告警？告警的触发方式是什么？）。

**业务影响评估**：确认系统的业务重要性（P0/P1/P2 级）、可允许的改造维护窗口（是否有计划维护时间窗口？多长时间？频率？）、业务关键功能清单（哪些功能必须通过合成监控覆盖？）。

**风险评估与回滚方案**：针对每个改造阶段，准备详细的回滚方案，并在测试环境演练确认回滚步骤可行、回滚时间在可接受范围内。

### A.2 三阶段改造的验收标准

**第一阶段验收**：Blackbox Exporter 探测成功，所有业务 API 端点有可用性和延迟 Metrics；合成监控脚本覆盖所有核心业务功能，每 2 分钟运行一次；关键日志关键词告警已配置（ERROR、EXCEPTION、OOM 等），告警通道连接到团队的 On-call 系统。

**第二阶段验收**：反向代理（Nginx 或 Envoy）部署完成，所有业务流量经过代理；代理层 RED Metrics（Rate、Error、Duration）正确反映实际业务流量；Trace Context Header 注入正常工作（在下游系统可以追溯到从遗留系统发出的请求的 Trace ID）。

**第三阶段验收**：进程内 Metrics（JVM/运行时 Metrics）正确采集并在 Grafana 展示；数据库连接池状态、线程池状态等核心内部 Metrics 可见；方法级别的 Trace 数据正确采集，在 Jaeger/Tempo 中可以查看完整的请求处理链路。

## 附录 C：遗留系统改造的常见坑与避坑指南

**坑 1：Agent 注入导致的 ClassLoader 冲突**

Java Agent 通过字节码增强工作，某些遗留系统使用了自定义 ClassLoader，可能与 Agent 的类加载机制冲突，导致 ClassNotFoundException 或 ClassCastException。

避坑方法：在测试环境全面运行系统的完整测试套件，并特别关注 ClassLoader 相关的配置（如 WebSphere 的类加载策略配置）；如果遇到冲突，可以尝试在 Agent 配置中排除冲突的类。

**坑 2：Sidecar 代理引入的额外延迟**

Nginx 或 Envoy 作为反向代理，会为每个请求增加一点延迟（通常 0.1-1ms）。对于延迟极其敏感的高频交易系统，这个额外延迟可能不可接受。

避坑方法：在引入代理前，在负载测试环境精确测量代理引入的延迟；对于 P99 延迟 SLO 非常严格的系统，考虑使用 eBPF 方案代替代理层，eBPF 的延迟开销低一到两个数量级。

**坑 3：日志量爆炸导致存储成本超预算**

许多遗留系统在开启详细日志后，每天产生数百 GB 的日志，存储成本超过预算。

避坑方法：在采集管道中配置明确的日志过滤和采样规则，在数据到达存储层之前就过滤掉无价值的日志（DEBUG 级别、高频重复的心跳日志）；设置日志存储的生命周期策略（7 天热存储、30 天温存储、归档冷存储），避免无限制累积。

---

> [!warning] 遗留系统改造的核心原则
> 遗留系统的可观测性改造，最重要的原则是"首先不伤害"（First, Do No Harm）：每一步改造的首要目标是不影响系统的正常业务运行，可观测性的增益是次要目标。宁可在第一阶段停留更长时间，也不冒过大风险仓促推进第二、三阶段。记住：遗留系统之所以遗留，是因为它们还在支撑着关键业务，改造它们的可观测性，是为了让这些业务运行得更好，而不是用不必要的风险来证明技术能力。

> [!info] 最后的思考
> 可观测性的终极目标，是让每一个工程师都能在任何时刻清晰地回答："我的系统现在怎样？为什么？"当这个问题有了清晰的答案，工程师从守护黑盒的焦虑中解放出来，才能将更多的精力投入到真正有价值的工作：构建更好的产品，服务更多的用户。遗留系统的改造之路漫长，但每一步都值得。

## 第 14 章 电信行业遗留系统改造的特殊挑战

### 14.1 电信网元设备的可观测性困境

电信行业的遗留系统面临独特的可观测性挑战，与互联网行业有本质区别：核心网元（如 HLR 归属位置寄存器、MSC 移动交换中心）通常运行在专有硬件上，采用专有操作系统和专有协议（SS7、Diameter、SIP），完全无法使用标准的 Prometheus Exporter 或 Java Agent 进行改造。

这些设备的可观测性数据，通常只能通过设备厂商提供的网管接口（SNMP、NetConf/YANG、私有 Restful API）获取，并且有严格的数据格式和访问权限限制。

针对这类设备的可观测性改造思路：优先使用 SNMP Exporter（Prometheus 官方）采集设备提供的 SNMP Metrics（CPU 使用率、内存使用率、板卡状态、端口流量），建立设备健康状态的基础监控；同时分析设备产生的 CDR（呼叫详细记录）和 Syslog，从外部数据推断网元的业务处理状态（成功呼叫率、呼叫建立延迟）；在有条件时，与设备厂商协商获得更丰富的管理接口（如 NETCONF/YANG 接口），实现更细粒度的状态数据采集。

### 14.2 批处理遗留系统的可观测性特殊设计

与在线交易系统不同，批处理遗留系统（如夜间结算批次、月末报表生成批次）具有不同的可观测性需求：

批处理系统的关键指标不是"每秒请求数"（批处理通常是单进程顺序处理），而是：批次处理进度（已处理记录数 / 总记录数，实现"进度条"式监控）、批次处理速率（每分钟处理记录数，用于预测完成时间）、错误记录率（处理失败记录数占比）、预计完成时间 vs SLA 时限（是否有超时风险）。

实现批次进度监控的最简单方式：在批处理程序中，每处理一定数量的记录（如每 1000 条），将当前进度写入一个"进度文件"或数据库表，然后用 Prometheus 的 Textfile Collector 采集进度文件，在 Grafana 中展示实时进度。这种方式只需要在批处理程序中添加几行写文件的代码，是遗留批处理系统最低成本的可观测性改造方案。

## 第 15 章 可观测性改造的技术债务管理

### 15.1 可观测性也会产生技术债务

可观测性改造本身也可能产生技术债务：过时的 Dashboard（展示已不存在的服务的 Metrics）、僵尸告警规则（永远不会触发或已失去意义的告警，但没有人清理）、不一致的 Metrics 命名（不同团队、不同时期添加的 Metrics 使用不同的命名风格，导致跨服务对比分析困难）、过期的 Runbook（系统架构已经变化，但 Runbook 仍然描述已废弃的处理步骤）。

这些"可观测性技术债务"会随着时间积累，降低团队对可观测性工具的信任（"这个 Dashboard 的数据还对吗？"），最终导致可观测性工具被弃用。

### 15.2 可观测性资产的治理实践

**季度清理**：每季度对 Grafana Dashboard、Prometheus AlertRule、Runbook 进行一次审查，删除或归档已不活跃服务（下线 30 天以上）的对应可观测性资产，更新与系统现状不符的 Dashboard 和 Runbook。

**所有权制度**：每个可观测性资产（Dashboard、AlertRule）必须有明确的"Owner"（负责团队），Owner 负责维护资产的准确性。没有 Owner 的资产在一段时间后（如 90 天）自动标记为"待清理"并通知相关团队认领或删除。

**Metrics 命名规范的强制执行**：在 CI/CD 中加入 Metrics 命名规范检查（扫描代码中的 Prometheus Client 调用，验证指标名称符合平台规范），从源头防止不一致的命名进入生产环境。新引入的可观测性资产，必须通过命名规范检查才能合并到主干，类似于代码风格检查对代码质量的作用。

## 行业视角：不同行业遗留系统改造的典型路径

### 金融行业改造路径

金融行业（银行、保险、证券）的遗留系统改造有其独特的监管约束：所有生产系统变更必须经过风险委员会审批，标准审批周期 2-4 周；生产变更必须在规定的"变更窗口"（通常是工作日夜间或周末）进行；核心业务系统必须满足 RPO（恢复点目标）和 RTO（恢复时间目标）的监管要求，改造过程不得影响灾备能力。

针对这些约束，金融行业改造的最佳路径是：优先实施零变更的第一阶段（黑盒监控），通过快速展示价值（发现未知问题）为后续阶段的审批建立信任；将第二阶段（代理层）的审批材料提前准备（包括详细的技术方案、安全评估、回滚预案），利用等待审批的时间在测试环境充分验证；第三阶段（SDK/Agent 集成）通常与系统的计划升级或迁移项目合并进行，避免单独发起改造申请。

### 制造行业 OT 系统（操作技术）的改造

制造行业的工业控制系统（SCADA、PLC、DCS）与 IT 系统完全不同：运行在专有实时操作系统上、使用工业协议（OPC-UA、Modbus、PROFINET），对延迟和稳定性要求极高（任何中断都可能导致生产线停止），通常与外部网络物理隔离（气隙安全，Air Gap）。

这类系统的可观测性改造通常采用"被动监听"方式：在工业网络中部署流量镜像（TAP），捕获 OT 设备之间的工业协议流量，通过专业的 OT 网络流量分析工具（如 Claroty、Nozomi Networks 的 IDS 产品）解析工业协议数据，提取设备状态 Metrics，绝不主动向 OT 设备发送任何探测请求（避免影响工业控制系统的实时性）。

## 工具实践：Prometheus Blackbox Exporter 配置示例（纯文字说明）

为了帮助读者理解黑盒监控的实际配置逻辑，以下用中文描述 Blackbox Exporter 的典型配置场景（无代码，仅概念描述）：

**HTTP 探针配置要点**：配置目标 URL 和检查间隔（推荐 30-60 秒）；设置期望的 HTTP 状态码范围（如 200-399 为成功）；配置超时时间（推荐不超过探测间隔的 80%，如 30 秒间隔则设置 24 秒超时）；可选：配置期望的响应体关键词（正则匹配），验证响应内容而非只检查状态码；可选：配置 TLS 证书有效期告警（提前 30 天告警证书即将过期）。

**TCP 探针配置要点**：配置目标主机和端口（适用于非 HTTP 协议的服务，如数据库监听端口、消息队列端口）；设置连接超时（TCP 三次握手完成的最长时间）；适合监控只需验证"端口是否可达"的遗留服务（不需要 HTTP 层的可见性）。

**告警规则的最佳实践**：黑盒探测的告警规则必须有足够的持续时间（如"连续 3 次探测失败才告警"），避免单次网络抖动导致的误报；同时设置"告警时间到实际下线时间"的合理上限，避免遗留系统长时间故障却没有升级告警。

> [!warning] 一个重要警告
> 在进行任何遗留系统的可观测性改造时，永远不要在没有完整备份和回滚方案的情况下修改生产系统。遗留系统的脆弱性往往超出预期——一次看似简单的配置修改，可能触发隐藏了多年的依赖问题。备份、回滚预案和分步部署（每次只改一个变量，验证后再推进下一步），是遗留系统改造的铁律。

## 遗留系统可观测性改造：工程师的心理准备与团队建设

### 成为"第一个推动改造的人"所需要的勇气

改造遗留系统的可观测性，需要有人愿意第一个站出来承担改造的风险和审批压力。这种改变往往很难，特别是在高度风险规避的组织文化中。

成为"改造推动者"需要准备：清晰的问题陈述（"上次故障因为缺乏监控，导致用户受影响了 47 分钟而我们不知道"）、小而具体的第一步行动（"我只需要在系统外部部署一个探针，不修改任何代码，明天就可以完成"）、成功案例的快速积累（第一个月内必须让改造产生一个可以讲述的"发现了之前不知道的问题"故事）。

改造推动者最大的陷阱是"一次做太多"——试图一步到位地完成所有三个阶段，结果复杂度超出控制，出现问题时无法快速定位，最终引发对整个改造计划的质疑。从最小可行的第一步开始，用成功积累信任，是遗留系统改造最有效的推进方式。

### 团队能力建设：可观测性技能的培训路径

可观测性改造需要团队掌握新的技能，包括：Prometheus 查询语言（PromQL）的基本用法（用于编写告警规则和 Grafana Panel 查询）、Grafana Dashboard 的基本操作（创建面板、设置变量、配置告警）、Linux 系统的基础 Metrics 解读（CPU、内存、磁盘 I/O、网络的 Metrics 含义和正常范围）、OpenTelemetry 的基本概念（Span、Trace、Attribute 的含义和关系）。

这些技能的培训不需要专门的课程——最有效的学习方式是"做中学"：将一个真实的遗留系统改造作为培训项目，团队成员在完成真实改造任务的过程中，自然掌握了所需的技能，同时产出了实际的业务价值，是双赢的学习方式。

遗留系统可观测性改造的成功，最终取决于三个因素的结合：正确的技术方法（三阶段渐进式改造）、有效的组织推进策略（从小处入手、建立信任）、以及持续坚持的团队文化（可观测性不是一个项目，而是一种持续实践）。三者缺一不可，缺少任何一个，改造都难以持续产生价值。
