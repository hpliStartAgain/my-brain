# 可观测性三大支柱深度解析：Metrics、Logs 与 Traces

## 摘要

在可观测性领域，有一个几乎所有工程师都听说过的说法：可观测性由 Metrics（指标）、Logs（日志）和 Traces（链路追踪）三大支柱构成。但这个说法被重复得太多，反而失去了它的核心价值——它没有告诉你**为什么是这三种，而不是其他**，也没有告诉你**当你只有其中一种或两种时，你究竟在哪些维度是盲的**。

本文将回答这些问题。我们从每种信号类型的本质出发，剖析它们各自解决的认知问题、各自的工程设计哲学，以及三者如何联动构成一个完整的可观测性认知系统。

## 第 1 章 为什么是"三个支柱"：监控认知层次的演进

### 1.1 一次故障复盘引出的问题

想象这样一个场景：你们公司的订单服务在凌晨两点收到了 on-call 告警——错误率超过 5%。你打开 Prometheus Dashboard，看到错误率曲线从 0.1% 突然跳到了 6%，持续了 8 分钟后自行恢复。

Metrics 告诉了你什么？它告诉你**有问题发生了，问题的规模和时间窗口**。这是非常宝贵的信息，但还远远不够：你不知道具体是什么错误，不知道哪类请求出错，不知道错误发生在哪段代码里。

于是你去看日志。你找到了那 8 分钟内的错误日志，看到满屏的 `Connection refused: MySQL:3306`。这下你知道了**具体发生了什么**——数据库连接失败。但新的问题来了：这些日志是所有用户请求产生的，你不知道**一次用户请求从入口到出口的完整路径上，到底哪里最先出问题**，也不知道失败的那些请求在进入数据库之前经历了什么。

这时候你需要 Traces。如果系统有完整的分布式追踪，你可以找到一条失败的 Trace，看到：用户的请求进入 API 网关，转发到订单服务，订单服务调用了库存服务（成功，200ms），然后调用了 MySQL（失败，报错 `Connection refused`），整个请求在 230ms 时终止并返回 500 错误。

至此，三种信号各司其职，完成了一次完整的故障定位：**Metrics 告诉你哪里出问题了（订单服务错误率高），Logs 告诉你发生了什么（数据库连接拒绝），Traces 告诉你这个问题在哪里发生（订单服务→MySQL 这一跳）**。

这个三层认知结构，就是"三大支柱"这个说法的本质所在。

### 1.2 早期监控为什么失败：只有 Metrics 的世界

在分布式追踪和结构化日志普及之前，大多数系统的可观测性只有第一层——Metrics。那个时代的监控工具（Nagios、Zabbix）的核心逻辑是：定义一组阈值，当某个指标超过阈值时发告警。

这个模型在架构相对简单的时代尚能接受，但当系统演进为微服务架构时，它的局限性彻底暴露：

**告警泛滥**：一次上游服务的故障，会级联触发所有依赖它的下游服务的告警。如果订单服务、支付服务、物流服务都依赖同一个用户服务，用户服务挂了会同时触发三个告警。值班工程师面对这三个告警，并不知道它们来自同一个根因，往往会分别去排查三个服务，浪费大量时间。

**定位困难**：Metrics 的本质是聚合数值——把成千上万条请求压缩成一个错误率数字。这种压缩不可逆：你无法从"错误率 6%"这个数字反推出"是哪 6% 的请求出了什么错"。

**无上下文**：Metrics 没有时间窗口内的因果关系信息。你看到 CPU 使用率在 14:23 突然升高，但你不知道那一刻发生了什么——是某个批处理任务启动了？是某个慢查询执行了？是一次 GC 风暴？

> [!info] 核心概念
> **Metrics 的本质是聚合统计**：它将无数的离散事件（每一次 HTTP 请求、每一次 SQL 查询）压缩成时间序列上的数值，这个压缩过程丢失了"哪个请求""在哪里""为什么"等关键上下文。Metrics 擅长回答"什么程度"的问题，而不擅长回答"为什么"的问题。

### 1.3 日志的天然局限：有上下文，缺全局视角

结构化日志的出现解决了"为什么"的问题，但引入了新的困境——**规模噪音问题**。

在一个每秒处理一万个请求的系统中，即使只记录 ERROR 级别日志，也可能每小时产生几十万条日志。当错误率升高时，你面对的是一个浩如烟海的日志文件，里面每条错误日志都是独立的、没有关联关系的。

你能看到 `用户 A 的订单请求失败`、`用户 B 的订单请求失败`、`用户 C 的订单请求失败`……但这些日志都是孤立的岛屿。你不知道用户 A 的这次失败请求，在调用订单服务之前，是否已经在 API 网关经历了重试；不知道用户 A 和用户 B 的失败请求是否命中了同一台问题实例；不知道整条调用链路上，哪一步是最先失败的，哪一步是级联失败的。

这是日志的结构性局限：**日志记录的是孤立的事件，而分布式系统中的故障是跨越多个服务、多条线程的因果链**。

### 1.4 Traces 的出现：因果链的显式表达

分布式追踪的核心思想，是为每一次用户请求分配一个全局唯一的追踪 ID（[[TraceID]]），并在这次请求流经的所有服务中传播这个 ID。每个服务处理请求时，创建一个对应的 Span，记录开始时间、结束时间、状态和相关属性，并把这个 Span 与父 Span（调用方的 Span）关联起来。最终，一次用户请求生成的所有 Span，汇聚成一棵以 TraceID 为根的树，完整还原了这次请求的时间因果链。

Traces 解决了日志不能解决的问题，但它也引入了独特的挑战：

**采样压力**：如果每次请求都记录完整的 Trace，存储成本会非常高。一个每秒十万请求的系统，如果每个请求产生 10 个 Span，每天就是 860 亿个 Span。这迫使工程师必须做采样——但采样意味着可能恰好丢弃了那条出问题的请求的 Trace。

**延迟分析的盲区**：Traces 擅长分析单次请求的延迟细节，但对于**宏观趋势分析**能力较弱。你很难从 Trace 数据中回答"过去一周，P99 延迟的趋势是怎样的？"——这类趋势问题更适合 Metrics。

这就是为什么三个支柱必须共存：它们各自擅长不同的认知场景，相互补充，缺一不可。

## 第 2 章 Metrics 的工程深度：数字背后的设计哲学

### 2.1 时间序列数据的本质

Metrics 的核心数据模型是**时间序列（Time Series）**：一组按时间排列的数值样本，每个样本是一个 `(时间戳, 数值)` 对。

听起来很简单，但 [[Prometheus]] 在这个基础上做的一个设计决策，彻底改变了监控系统的表达能力：**用标签（Labels）区分不同维度的时间序列**。

这个设计意味着什么？在没有标签的监控系统中，"HTTP 请求错误率"只是一个数值，你无法区分是哪个服务的请求、哪类错误代码、哪个接口出问题了。在 Prometheus 的标签体系中，同一个指标可以同时存在数以百计的时间序列：

```
http_request_total{service="order", method="POST", status="500"}  → 一条时间序列
http_request_total{service="order", method="GET",  status="200"}  → 另一条时间序列
http_request_total{service="payment", method="POST", status="200"} → 又一条时间序列
```

你可以用 PromQL 精确筛选、聚合这些维度：只看订单服务的 5xx 错误率、按服务维度横向对比错误率、统计所有服务的总请求量。这个多维度的标签模型，赋予了 Metrics 极强的切片分析能力。

### 2.2 四种 Metric 类型的设计哲学

Prometheus 定义了四种基本 Metric 类型，每种类型的设计都反映了一种不同的数据语义：

**Counter（计数器）**

Counter 是一个单调递增的累计计数器，只能增加，不能减少（除非进程重启导致归零）。最典型的例子是 HTTP 请求总数、发送的字节数、错误总数。

Counter 的核心价值在于：通过计算一段时间内的增量，可以得到"速率"。Prometheus 的 `rate()` 函数就是做这件事的。`rate(http_request_total[5m])` 意味着：计算过去 5 分钟内 Counter 的增量，除以 300 秒，得到每秒的请求速率。

为什么不直接记录"当前请求速率"而是记录"累计请求数"？因为累计计数器对于采集时的抖动（采集延迟、短暂失联）更加健壮：即使偶尔漏采了一个数据点，通过首尾两个点的差值仍然能计算出合理的速率；而直接记录速率的 Gauge，一旦采集失败就丢失了那个时间点的信息。

> [!note] 设计哲学
> Counter 单调递增的设计是"累积语义"的体现：**宁可记录原始事件的累积，也不要记录计算结果**。原始数据保留了所有的信息，计算结果可以在查询时按需生成，反之则不行。

**Gauge（仪表盘）**

Gauge 记录的是某个时刻的瞬时值，可以任意增减：当前 CPU 使用率、内存占用、在线用户数、当前连接数。

Gauge 直观易懂，但有一个工程上的微妙点：由于 Gauge 记录的是瞬时值，如果采集间隔是 15 秒，那么你看到的是 15 秒快照的连接，而不是 15 秒内的平均连接数。两次采集之间的连接数变化被"淹没"了。对于变化非常快的指标（如某些消息队列的积压量），15 秒的采集间隔可能会错过重要的峰值。

**Histogram（直方图）**

Histogram 是三种类型中工程设计最复杂的。它用于记录一个可观测量（通常是延迟或请求大小）的**分布情况**，而不是单一的数值。一个 Histogram 实际上由三组时间序列构成：若干个桶（bucket），分别记录"落在这个延迟范围内的请求数量"；一个样本总数（_count）；一个样本总和（_sum）。

Histogram 的价值在于可以计算**百分位数（Percentile）**，这是 SLO 体系中最重要的度量方式。P99 延迟意味着"99% 的请求在这个时间内完成"，这比平均延迟更能反映用户实际体验——平均延迟可能被大量快速请求拉低，掩盖了少数极慢请求的存在。

Histogram 有一个不可回避的工程权衡：桶的边界需要提前定义。如果你定义了 `[0.1, 0.5, 1.0, 5.0]` 秒的桶，那么你只能准确计算这些范围内的分位数；如果实际延迟大多集中在 50ms 以下，这些桶就太粗糙了，P99 的精度会很差。桶的设计需要对业务的延迟分布有先验知识。

**Summary（摘要）**

Summary 和 Histogram 都用于延迟分布，但设计哲学不同。Histogram 在服务端采集原始数据，在 Prometheus 查询时计算百分位数；Summary 则在客户端（应用程序内部）就计算好百分位数，直接暴露出 P50、P95、P99 等数值。

Summary 的优点是不需要定义桶，百分位数计算精确；缺点是**不能跨实例聚合**。如果你有 10 个 pod 各自暴露了 P99 延迟，你无法把它们加起来得到整个服务的 P99 延迟（因为 P99 不是线性可加的统计量）。Histogram 可以通过 Prometheus 的 `histogram_quantile()` 函数，在查询时对多个实例的桶数据进行聚合后再计算百分位数。

在大多数现代可观测性实践中，**Histogram 是比 Summary 更推荐的选择**，因为多实例聚合是分布式系统中的基本需求。

### 2.3 高基数问题：一个可以摧毁监控系统的设计错误

理解了 Prometheus 的标签体系，就必须理解**高基数（High Cardinality）问题**——这是 Metrics 系统中最常见、也最致命的工程错误之一。

**基数（Cardinality）** 指的是一个标签可能取到的不同值的数量。一个 `service` 标签，如果系统有 50 个微服务，那么它的基数是 50；一个 `status_code` 标签，HTTP 状态码有限，基数在 20 以内。这些都是低基数标签，没有问题。

问题出在把**高基数的信息作为 Metric 标签**。最典型的反例是把用户 ID 作为标签：

```
http_request_total{service="order", user_id="12345678"}
http_request_total{service="order", user_id="12345679"}
http_request_total{service="order", user_id="12345680"}
...
```

如果系统有一千万个用户，这个 Metric 就会产生一千万条时间序列。每条时间序列都需要在内存中维护状态、在磁盘上持久化、在网络上传输。一千万条时间序列会直接压垮 Prometheus。

更隐蔽的高基数陷阱：
- **把请求 ID（Request ID）作为标签**：每次请求唯一，基数无上界
- **把错误消息（Error Message）作为标签**：错误消息包含动态内容（如 SQL 语句），基数极高
- **把版本号作为标签，但版本迭代频繁**：每次发布产生新的时间序列，旧的时间序列永久占据存储

> [!warning] 生产避坑
> 判断一个 Metric 标签是否安全的黄金准则：**这个标签的取值集合是否有明确的上界，且这个上界在可接受范围内（通常 < 10000）？**
> 
> 如果答案是"否"，就不应该作为 Metric 标签。对于高基数的分析需求（如"某个用户的请求延迟分布"），应该用 Logs 或 Traces 而不是 Metrics。

### 2.4 PromQL 的查询哲学：rate 的滑动窗口与查询精度

PromQL 的 `rate()` 函数有一个选择：窗口应该设多大？`rate(http_request_total[1m])` 和 `rate(http_request_total[5m])` 计算的是同一个指标，但含义不同。

**窗口越小，对瞬时变化越敏感，但曲线越"毛糙"（噪声更多）**。1 分钟窗口能快速反映突发的错误率上升，但曲线会有大量短暂的锯齿。

**窗口越大，曲线越平滑，但对变化的感知越滞后**。5 分钟窗口会把一次持续 30 秒的错误峰值"稀释"到一个较低的错误率数值，可能导致告警响应时间变长。

这个权衡没有通用答案，需要根据业务 SLO 的要求来决定：如果 SLO 是"连续 5 分钟错误率不超过 1%"，那么使用 5 分钟窗口是合适的；如果 SLO 是对用户体验更敏感的短窗口，就需要更小的窗口。

## 第 3 章 Logs 的结构化之路：从 printf 到可查询的事件流

### 3.1 非结构化日志的原罪

软件工程师记录日志的历史几乎和编程本身一样久——最早的日志就是 `printf("error: %d\n", errno)` 这样的语句。这种日志记录方式沿用了几十年，直到现代分布式系统的复杂性彻底暴露了它的局限。

非结构化日志的根本问题是：**它是为人类阅读而设计的，而不是为机器解析而设计的**。

当你有三台服务器、日志量每天几十万行时，人工翻日志是可行的。但当你有三百个微服务实例、日志量每天几十亿行时，你唯一的希望是用机器来解析、搜索和聚合日志。而机器解析非结构化日志，需要依赖正则表达式——这是一条充满脆弱性的路。

以这条非结构化日志为例：
```
2024-01-15 14:23:45 [ERROR] Failed to process order 12345 for user john.doe@example.com, payment declined with code 4031
```

要从中提取"订单 ID""用户邮箱""错误代码"，你需要写一个脆弱的正则表达式。一旦开发者改变了日志消息的措辞（比如把"Failed to process"改成"Unable to process"），正则表达式就失效了。更糟糕的是，这个正则表达式的更改几乎无法被测试——直到它在生产环境中悄悄开始丢失数据，你才会发现。

### 3.2 结构化日志的本质：字段是一等公民

结构化日志的核心思想是：**把日志中的每个关键信息都作为独立的字段存储，而不是嵌入到一段文本中**。

同样的信息，用结构化的 JSON 日志表达：

```json
{
  "timestamp": "2024-01-15T14:23:45.123Z",
  "level": "ERROR",
  "service": "order-service",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "user_email": "john.doe@example.com",
  "order_id": "12345",
  "event": "payment_declined",
  "payment_error_code": 4031,
  "message": "Payment declined during order processing"
}
```

这条日志可以被任何 JSON 解析器准确解析，每个字段可以直接用于查询和聚合：`查找所有 payment_error_code = 4031 的日志`、`统计过去一小时内 user_email 字段中各域名的错误率`。没有正则表达式，没有脆弱的依赖。

> [!info] 核心概念
> 结构化日志的本质转变：**日志从"人类可读的文本中偶尔包含字段"，变成了"机器可解析的字段集合中偶尔包含可读文本"**。字段从附属品变成了一等公民。

### 3.3 日志级别的工程含义：不是随便选的

工程师写代码时面对一个常见困惑：这行日志应该用 INFO 还是 WARN？这个疑问背后，是对日志级别本质含义的不清晰。

日志级别的本质，是**告诉运维人员（或自动化工具）这条日志需要多少关注度**。以下是一种有工程价值的定义：

**DEBUG**：对开发者调试有价值的详细信息，在生产环境通常默认关闭。包括函数入参、中间计算结果、缓存命中/未命中等。DEBUG 日志如果在生产全量打开，通常会让日志量增加 10-100 倍，因此常用的做法是支持动态开关——只在需要排查问题时，针对特定服务动态调高日志级别。

**INFO**：正常业务流程的关键里程碑。"用户 A 完成了订单支付"、"批处理任务启动，共处理 1000 条记录"、"外部 API 调用成功，响应时间 230ms"。INFO 日志应该能让你看到系统在做什么，但不应该多到让人应接不暇。一个健康系统的 INFO 日志，应该能让新工程师读懂系统的业务流程。

**WARN**：**值得关注但不需要立即处理**的异常情况。"重试第 2 次"、"数据库连接池使用率达到 80%"、"某个配置项使用了废弃的格式"。WARN 的关键语义是：**如果一直是 WARN，系统还能运行；但如果 WARN 持续累积或频率升高，就需要关注了**。

**ERROR**：**影响了单次请求但不影响整体服务存活**的错误。"这笔订单处理失败了"、"这次 API 调用返回了 500"。ERROR 的语义是：**有一件本该成功的事情失败了，但服务整体还活着**。

**FATAL / CRITICAL**：**服务即将崩溃或已经处于不可恢复状态**。在许多框架中，FATAL 日志之后程序会直接退出。

理解了这个语义体系，就能理解一个常见的工程反模式：**把本质上是 ERROR 的事件记录为 WARN，是为了避免告警触发**。这是一种自欺欺人的掩耳盗铃——它用日志级别的降级来规避技术债，让问题在更长的时间里积累，直到某天它突然演变成不可控的故障。

### 3.4 上下文传播：没有 trace_id 的日志，是孤岛

单体应用时代，一条请求的所有日志都来自同一个进程，你可以用请求的发起时间、用户 ID 来关联同一请求的所有日志。但在微服务架构中，一次用户请求会流经 5 个、10 个、甚至更多的服务进程，每个进程都产生各自的日志，这些日志分散在不同的文件、不同的服务器上。

**没有统一的上下文 ID，这些日志就是一堆孤岛——你永远无法把一次用户请求的完整故事拼凑起来**。

[[W3C TraceContext]] 标准定义了如何在 HTTP 请求中传递追踪上下文，核心是两个 HTTP 头：`traceparent` 携带 TraceID 和 SpanID，`tracestate` 携带厂商特定的追踪信息。任何遵循 [[OpenTelemetry]] 规范的库，在处理 HTTP 请求时都会自动读取这两个头，把 TraceID 注入到当前的上下文中，日志库可以从这个上下文中自动读取 TraceID 并加入每一条日志。

这意味着，当你查看一条日志时，如果它有 `trace_id` 字段，你可以直接跳转到对应的 Trace，看到这条请求的完整调用链；反过来，当你在 Trace 视图中发现一个可疑的 Span，你可以用它的 SpanID 过滤日志，找到在这个 Span 执行期间产生的所有日志。

这种双向跳转，就是"可观测性三支柱联动"的第一个实例。

### 3.5 日志采样：写多写少都是成本

日志并不是越多越好。日志的成本主要体现在三个维度：**存储成本**（日志本身的磁盘空间）、**计算成本**（日志格式化、序列化的 CPU 开销）、**带宽成本**（日志从应用发送到日志系统的网络开销）。

对于高流量的接口，如果不做任何采样控制，全量 INFO 日志可能会让日志成本比业务本身更高。一个每秒处理十万请求的服务，如果每个请求产生 2KB 的日志，每天就是 17TB 的日志量，这在存储和索引成本上是不可接受的。

常见的日志采样策略：

**按级别采样**：DEBUG 日志在生产环境全量关闭，INFO 日志按 1% 或 10% 采样，ERROR 日志始终全量保留。这是最简单的采样策略，但过于粗暴——重要的 INFO 日志（如支付完成）和不重要的 INFO 日志（如健康检查）被同等对待。

**按请求结果采样**：成功的请求日志以低比例采样（1-10%），失败的请求日志全量保留。这个策略在"不出问题时省成本，出问题时有足够数据"的目标上表现最好，是实践中最推荐的策略。

**动态采样**：正常情况下以低比例采样，当错误率升高时自动提升采样率。这是最智能的策略，但实现复杂度较高，通常需要配合 Tail-Based Sampling（尾部采样）的追踪系统一起使用。

> [!warning] 生产避坑
> 日志采样有一个容易被忽视的陷阱：采样需要在**产生日志时**就决定是否保留，而不是在日志写入后再过滤。如果在写入后过滤，格式化和序列化的 CPU 成本已经发生了，采样只能节省存储和传输成本，无法节省计算成本。
>
> 在 OpenTelemetry 中，可以通过在 OTel Collector 配置 `probabilistic_sampler` 在采集侧做概率采样，在应用日志库配置采样规则在源头做采样——两者各有适用场景。

## 第 4 章 Traces 的深层逻辑：因果关系的显式编码

### 4.1 分布式追踪为什么在微服务时代才变得必需

Traces 的概念并不是微服务时代的发明。早在 2000 年代初，Google 内部就有类似的系统，后来被总结为 Dapper 论文（2010 年）。但分布式追踪真正成为主流工程实践，是 2015 年以后——也就是微服务架构开始大规模普及之后。

这不是巧合。在单体应用时代，一次请求的完整执行路径就在同一个进程内，函数调用栈（Stack Trace）本身就提供了因果链信息：你可以用调试器跟踪每一步调用，可以在任何位置打断点检查状态。

微服务架构彻底打破了这个假设。一次用户请求进入 API 网关，触发了 5 个微服务的调用，其中有 2 个是并行调用，3 个是串行调用，每个服务运行在不同的进程、不同的机器上。**调用栈的概念在这里完全失效了**：没有一个统一的进程可以追踪整条执行路径，也没有一个调试器可以同时附加到 5 个不同的进程上。

分布式追踪的本质，是**用软件手段显式地重建了这种天然存在于单体应用中、但在微服务中隐式丢失的因果链**。TraceID 的传播，扮演的角色类似于"虚拟进程上下文"：它把分散在不同机器、不同进程的所有操作，逻辑上串联成一个整体。

### 4.2 Span 模型的本质：时间与因果的双重编码

一个 [[Span]] 是追踪的最小单位，它编码了两层信息：**时间信息**（开始时间戳、持续时长）和**因果信息**（父 SpanID）。

时间信息让你可以做延迟分析：这次数据库查询花了多长时间？整个请求的总时长中，各个子操作各占多少比例？哪一步是性能瓶颈？

因果信息让你可以还原调用链：这个 Span 是由哪个 Span 触发的？这次数据库查询是在处理哪个 HTTP 请求时发生的？当前 Span 的并行兄弟 Span 是哪些？

这两层信息组合在一起，形成了一个**时间因果图**（Temporal Causal Graph）：你可以看到整个请求的执行顺序，也可以看到并行操作的时间重叠情况，还可以识别出关键路径（Critical Path）——也就是那些串行依赖关系中，耗时最长的那条链。

从架构优化的角度，关键路径分析非常有价值：如果你有 3 个并行操作分别耗时 100ms、150ms、80ms，总耗时是 150ms（由最慢的那个决定），你的优化目标应该是那个 150ms 的操作，而不是去优化 80ms 的那个。Trace 的可视化界面（如 Jaeger 的 Waterfall 视图）可以直观地展示这种关键路径。

### 4.3 采样策略的深层权衡：谁决定这条请求值得保留

采样是 Traces 系统中工程复杂度最集中的地方。你不可能保留所有 Trace——在高流量系统中，这意味着PB 级的存储需求。你必须决定：哪些请求的 Trace 值得永久保留？

**Head-Based Sampling（头部采样）**：在请求的入口处（第一个 Span 创建时）随机决定是否采样。如果决定采样，这个决定通过上下文传播到整条追踪链；如果决定不采样，这条请求的所有 Span 都不会被发送到后端存储。

头部采样的优点是**确定性强、开销低**：在请求开始时就做决定，所有下游服务不需要额外的协商。缺点是**无法识别重要性**：你在请求开始时并不知道这条请求会不会出错、会不会特别慢。一条随机采样率 1% 的策略，意味着 99% 的出错请求也会被丢弃。

**Tail-Based Sampling（尾部采样）**：等到整条 Trace 完成后，根据结果（是否出错、是否超过延迟阈值）再决定是否保留。对于出错的 Trace 或慢 Trace，始终保留；对于成功且快速的 Trace，以低比例采样。

尾部采样的优点是**采样质量高**：确保了所有异常请求都有完整的 Trace 记录。缺点是**实现复杂**：需要一个中间层（如 [[OpenTelemetry Collector]] 的 Tail Sampling Processor）暂时缓存所有 Span，等待整条 Trace 完成。这个中间层本身就是一个有状态的服务，需要考虑高可用、内存压力、Tail Latency 等问题。

> [!info] 核心概念
> **采样策略的本质权衡**：Head Sampling 是"随机剪枝"，Tail Sampling 是"按价值剪枝"。在存储成本和采样质量之间，Tail Sampling 是更优的方案，但需要更复杂的基础设施支撑。对于大多数团队，**推荐的路径是先用 Head Sampling 起步（简单、够用），当 Trace 存储成本成为问题或需要保证错误请求的覆盖率时，再迁移到 Tail Sampling**。

### 4.4 上下文传播的脆弱性：哪些地方会断链

分布式追踪最令人沮丧的问题是：明明已经部署了，但 Trace 经常在某些地方断掉——某些 Span 孤立存在，找不到父 Span；或者整条调用链中间缺了一段。

断链的常见原因：

**消息队列的异步解耦**：同步 HTTP 调用的 Trace 传播相对简单，因为请求和响应在同一个连接上。但当 A 服务发送消息到 Kafka，B 服务从 Kafka 消费时，A 的执行时间和 B 的执行时间可能差了几十分钟。这里的 Trace 上下文传播需要在消息头（Message Header）中显式携带 TraceID，且消费方需要从消息头中提取并恢复上下文——这不是默认行为，需要主动配置。

**DNS/反向代理的透传失败**：一些老旧的反向代理或负载均衡器不会透传未知的 HTTP 头，而 `traceparent` 对它们来说就是一个未知的头部。这会导致 Trace 上下文在请求经过代理时被静默丢弃，从而断链。

**第三方 SDK 的缺失支持**：如果你调用了一个内部私有协议（不是标准 HTTP/gRPC）的服务，或者使用了某个不支持 OpenTelemetry 的内部 SDK，那么跨越这个调用的 Trace 就会断链。

**线程切换和异步代码**：在 Java 的线程池模型中，如果你把任务提交到线程池，并且没有正确地传递当前的上下文，新线程上的操作就会在不同的 Span 上下文中执行。现代 OTel SDK 通常通过 `ContextPropagator` 自动处理这个问题，但如果代码用了非标准的线程切换方式，仍然可能出现问题。

这些断链场景不是 OpenTelemetry 的缺陷，而是分布式系统中**边界条件的天然复杂性**。理解它们，才能在 Trace 数据出现异常时快速定位原因。

## 第 5 章 三支柱的联动：从孤立信号到完整认知

### 5.1 Exemplar：Metrics 与 Traces 的桥梁

三支柱各自独立时，你需要在不同系统之间手动关联信息：看到 Metrics 异常，打开 Jaeger，手动输入时间范围搜索 Trace，猜测是哪条 Trace 代表了那个异常请求。这个过程既费时又不可靠。

[[Exemplar]] 是 Prometheus 和 OpenMetrics 标准引入的一个机制，在这两个系统之间建立了直接的桥梁。

Exemplar 的工作方式：当 Prometheus 记录一个 Histogram 观测值时，它可以附带一个"样本引用"，里面包含对应请求的 TraceID。例如，当一个 P99 延迟（假设 4.2 秒）的请求被记录到 Histogram 桶中时，这条样本会同时附带这次请求的 TraceID `4bf92f3577b34da6a3ce929d0e0e4736`。

在 Grafana 中，当你查看 Histogram 图表时，这些带有 TraceID 的样本点会被显示为特殊的点标记。点击这个点，就可以直接跳转到 Tempo（Trace 存储）中查看对应的完整追踪链——从 Metrics 异常点，一键定位到代表这次异常的具体 Trace，而不需要手动搜索。

Exemplar 的设计哲学是**跨系统的"证据链"**：每一个 Metrics 数据点都可以携带一个"举证"，证明某条具体的请求代表了这个数值。这把 Metrics 的统计宏观视角，和 Traces 的单次请求微观视角连接了起来。

### 5.2 Derived Fields：Logs 与 Traces 的双向跳转

[[Grafana Loki]] 的 Derived Fields 功能，实现了日志与 Trace 之间的双向关联。

**从日志跳到 Trace**：你在 Loki 中查看日志，某条 ERROR 日志里包含了 `trace_id=4bf92f3577b34da6a3ce929d0e0e4736`。配置了 Derived Fields 之后，这个 trace_id 值会自动被渲染为一个可点击的链接，点击后直接打开 Tempo 中对应的 Trace 详情。

**从 Trace 跳到日志**：在 Jaeger 或 Tempo 的 Trace 视图中，你看到某个 Span 的执行时间是 3 秒，远超正常值。你可以用这个 Span 的时间范围和服务名，直接跳转到 Loki，筛选出该服务在这个时间窗口内产生的所有日志——查看这 3 秒内究竟发生了什么。

这种双向跳转能力，把日志系统和追踪系统从两个独立的工具，变成了一个互相印证的整体。

### 5.3 三支柱的信息密度与成本矩阵

理解三支柱的本质，还需要理解它们各自的**信息密度与成本结构**，这决定了在系统资源有限时，如何做取舍：

**Metrics 的信息密度最低，成本最低**。一个 Histogram 指标把几万条请求压缩成几十个桶的计数，是极高的数据压缩率。查询速度快，存储成本低，但无法反映单次请求的细节。Prometheus 的存储效率非常高，通常每个时间序列每秒一个样本，仅需要 1-2 字节的存储。

**Logs 的信息密度中等，成本中等**。每条日志记录了一个独立事件的完整上下文，信息量远多于一个 Metrics 样本。对于高流量系统，日志量可能非常大（每天 TB 级），存储和索引成本显著。但日志比 Traces 更容易理解，且对现有系统的改造成本较低（通常只需要调整日志输出格式）。

**Traces 的信息密度最高，成本最高**。每条 Trace 记录了整条请求链路的所有 Span，包含每一步的时间、状态、属性。这是最详细的可观测性数据，也是成本最高的。在不采样的情况下，Trace 数据量通常比日志数据量还要大。

这个成本矩阵给出了一个实践建议：**Metrics 应该全量采集（成本低，价值高）；Logs 可以按级别和采样率控制（ERROR 全量，INFO 采样）；Traces 必须做采样（全量成本不可承受，尾部采样是首选策略）**。

### 5.4 MELT 框架：第四个维度

随着 AI Native 系统和 eBPF 监控的普及，可观测性从"三支柱"扩展到了 MELT 框架，加入了第四个维度：**Events（事件）**。

Events 是一类特殊的数据，它既不是持续采集的 Metrics，也不是请求级的 Trace，而是系统中**离散发生的重要事件**：服务部署、配置变更、数据库扩容、节点宕机。这些事件本质上是时间线上的"标记点"，与 Metrics 曲线叠加显示时，能够直观地展示"变更"与"指标变化"之间的时间关联。

例如，在 Grafana 中把 Kubernetes 部署事件（Annotation）叠加到延迟 Metrics 图上，一眼就能看出"这次延迟升高，与 14:23 的 order-service v2.3.1 发布有直接的时间关联"。没有 Events 层，这种关联需要人工翻日志来推断；有了 Events 层，因果关系一目了然。

> [!note] 设计哲学
> MELT 框架的每一个字母，代表的是一个不同的**认知维度**：
> - **Metrics（M）**：系统的"体温计"——持续监测整体健康状态
> - **Events（E）**：系统的"日志本"——记录重要变更和里程碑
> - **Logs（L）**：系统的"诊断报告"——记录单次操作的详细上下文
> - **Traces（T）**：系统的"手术记录"——重建单次请求的完整执行路径
>
> 没有任何一个维度可以替代其他三个。

## 第 6 章 三支柱在现代可观测性工具中的实现：LGTM 栈

### 6.1 Loki-Grafana-Tempo-Mimir 的设计统一性

现代开源可观测性生态中，有一套正在成为事实标准的工具组合：**LGTM 栈**（Loki + Grafana + Tempo + Mimir/Prometheus）。这套工具的核心优势不仅在于它们分别是各自领域的优秀工具，更在于它们共享了一套统一的设计哲学。

这套哲学可以用一句话概括：**用对象存储做持久化，用内存做高效查询，把成本效益和简单运维放在第一位**。

[[Loki]]（日志存储）的设计思想类比于"日志的 Prometheus"：它不索引日志的内容，只索引标签（类似于 Prometheus 的 Labels）。这意味着 Loki 的存储成本极低（比 Elasticsearch 低 10 倍以上），但代价是查询速度较慢——全文搜索需要扫描所有原始日志，而不是查询索引。Loki 的理念是：**90% 的日志查询场景，通过标签过滤缩小范围后，再做全文搜索是完全够用的**。对于需要高速全文搜索的场景，Elasticsearch 仍然是更好的选择。

[[Tempo]]（Trace 存储）的设计哲学更激进：它把 Trace 数据直接以 Parquet 格式存储在 S3/GCS 这类对象存储中，几乎不做索引，查询时通过 TraceID 直接定位。这意味着按 TraceID 查询非常快（O(1) 复杂度），但按服务名、标签做聚合分析非常慢（需要扫描大量数据）。Tempo 的哲学是：**Trace 的主要使用场景是"我已经知道哪条 Trace，我要看它的详情"，而不是"我要在所有 Trace 上做分析"**。后者应该由 Metrics（预聚合）来承担，而不是对 Trace 做全量分析。

这两个工具的设计决策，都体现了一个重要的工程取舍：**用查询速度换取存储成本，用专用化的查询模式换取通用性**。理解这种取舍，才能在工具选型时做出正确的判断——Loki 不是 Elasticsearch 的替代品，Tempo 也不是支持 OLAP 查询的 Trace 数据仓库，它们有各自明确的适用场景边界。

### 6.2 技术选型对比

三支柱的每个信号类型，在开源生态中都有多种实现方案可选：

**Metrics 存储**：

| 工具 | 适用规模 | 核心优势 | 局限性 |
|------|---------|---------|--------|
| Prometheus | 单集群，< 1000 万时间序列 | 简单、可靠、生态成熟 | 不支持水平扩展，无长期存储 |
| Mimir/Thanos | 大规模、多集群 | 水平扩展、长期存储 | 运维复杂度高 |
| VictoriaMetrics | 中大规模 | 高压缩率、低资源占用 | 社区规模较 Prometheus 小 |

**日志存储**：

| 工具 | 适用场景 | 核心优势 | 局限性 |
|------|---------|---------|--------|
| Loki | 主要按标签过滤，不需要全文搜索 | 低成本、与 Prometheus 体系协同 | 全文搜索性能差 |
| Elasticsearch | 需要高速全文搜索、复杂聚合 | 查询功能强大、生态完善 | 存储成本高、运维复杂 |

**Trace 存储**：

| 工具 | 适用场景 | 核心优势 | 局限性 |
|------|---------|---------|--------|
| Tempo | 按 TraceID 查询为主 | 极低存储成本（对象存储） | 不支持复杂聚合查询 |
| Jaeger | 需要按服务、操作名搜索 Trace | 功能丰富、界面友好 | 存储成本较高 |

## 第 7 章 边界与反例：三支柱不能解决的问题

### 7.1 可观测性的覆盖盲区

即使三支柱部署完整，仍然有一些关键问题它们无法直接回答：

**客户端的真实体验**：Metrics、Logs、Traces 都是**服务端的视角**。你知道你的 API 在服务端返回了 200ms 的响应，但不知道用户的浏览器实际上花了多少时间渲染页面——因为页面渲染发生在客户端，不在你的观测范围内。这就是前端可观测性（RUM，Real User Monitoring）的价值所在，它填补了服务端可观测性无法覆盖的"最后一公里"。

**长时间运行任务的中间状态**：如果你有一个批处理任务需要运行 6 小时，Traces 只能记录它的开始和结束，无法观测中间状态。Metrics 可以每隔一段时间记录进度，但缺乏上下文。这类任务的可观测性通常需要额外的进度报告机制（Progress Reporting）。

**多次请求的用户旅程**：Traces 记录的是单次请求的链路，但用户体验往往由**一系列请求组成的旅程**决定：用户搜索商品（请求 1），浏览详情（请求 2），加入购物车（请求 3），提交支付（请求 4）。如果想分析"哪些用户在哪一步放弃了"，需要额外的用户行为分析（User Analytics），而不是 Traces。

### 7.2 指标是结果，不是根因

最后，有一个认知上的陷阱需要警惕：**Metrics 告诉你发生了什么（What），但它通常无法告诉你为什么（Why）**。

看到 CPU 使用率 90%，你不知道是业务量增长、某个低效算法、还是内存压力导致的 GC 风暴。看到错误率 6%，你不知道是代码 Bug、数据库故障、还是下游服务降级。

Metrics 是故障的**症状**，不是故障的**根因**。把两者混淆，是工程实践中非常常见的错误。告警应该基于症状（SLI/SLO 违反）触发，但定位根因需要深入 Logs 和 Traces，甚至需要检查系统外部的变化（如最近的代码发布、配置变更、基础设施变更）。

## 小结

本文的核心论点可以浓缩成三句话：

**为什么是三个支柱**：因为每种信号解决了不同维度的认知问题——Metrics 回答"什么程度"，Logs 回答"发生了什么"，Traces 回答"在哪里发生"。三者缺一，就在某个认知维度上是盲的。

**每个支柱的核心工程权衡**：Metrics 的基数问题（标签设计直接影响系统稳定性），Logs 的采样策略（写多写少都是成本），Traces 的采样哲学（Head vs Tail，各有取舍）。

**三支柱联动是可观测性的终局**：Exemplar（Metrics→Traces）、Derived Fields（Logs↔Traces）、Events（变更关联 Metrics）——单独看三支柱是工具，联动起来才是认知系统。

## 附录：Continuous Profiling 与可观测性第四维

### 为什么 Profiling 是可观测性体系的重要补充

在 Metrics、Logs、Traces 之外，有一种信号在近年来开始受到越来越多的重视：**持续性能分析（Continuous Profiling）**。

传统的性能分析（Profiling）是一种侵入性的、按需的操作：你怀疑某个接口有性能问题，就临时开启 Profiler，让它采样 CPU 调用栈或内存分配，分析完之后关掉。这种方式的问题是：它是事后的，需要你在知道问题存在之后才去分析；而很多生产性能问题的根因，在你意识到问题时已经消失了（比如 GC 风暴只持续了 30 秒，你开启 Profiler 时已经结束了）。

Continuous Profiling 的核心思想是：**以极低的开销持续采集 Profiling 数据，并存储一段历史**。典型实现（如 [[Phlare]] 或 Pyroscope）的 CPU 采集开销约为 1-2%，这个开销在生产环境是完全可接受的。

Continuous Profiling 与三支柱的关系是**正交的**：

- Metrics 告诉你 CPU 使用率 80%（现象）
- Profiling 告诉你这 80% 的 CPU 被哪些函数消耗了（根因）
- Traces 告诉你哪条请求最慢（路径）
- Profiling 告诉你这条请求慢在哪个代码路径上（代码级根因）

四者结合，构成了从宏观系统层到微观代码层的完整可观测性栈。

### Profiling 数据的核心呈现：火焰图

Profiling 数据通常以**火焰图（Flame Graph）**的形式可视化。火焰图的横轴代表 CPU 时间（越宽代表占用 CPU 时间越长），纵轴代表调用栈深度（上层函数调用下层函数）。从火焰图上，你可以直观地看到：哪个函数是 CPU 热点、哪条调用路径是耗时主体、哪次内存分配是最大开销来源。

一个资深工程师能从火焰图中一眼识别出常见的性能反模式：一个宽而矮的平台（说明某个函数本身占用了大量 CPU）、一条细长的垂直线（说明存在很深的递归调用栈）、频繁出现的 `java/lang/StringBuilder.append`（说明存在 String 拼接的性能问题）。

Continuous Profiling 尤其在两个场景下有不可替代的价值：

**场景 1：解释 Metrics 指标，而非仅仅告警**。当错误预算消耗率异常时，Metrics 只能告诉你"消耗速度加快了"，Profiling 可以告诉你"是 HTTP 请求处理线程中的 JSON 序列化开销突然增加了 3 倍"——这是 Metrics 无法提供的信息粒度。

**场景 2：验证优化效果**。当你完成了一次性能优化（比如把某个 N+1 查询改为批量查询），Profiling 数据的前后对比是最直接的"效果证明"：可以清晰看到那个函数在火焰图中从一个宽平台缩小到一条细线。


### 从工具视角到认知视角的转变

本文花了大量篇幅讲解三支柱的工程细节（Histogram 的桶设计、Loki 的索引策略、Tail Sampling 的实现复杂度），但这些细节背后有一个统一的更高层次视角：**可观测性不是关于工具，而是关于你能以多快的速度、用多少认知成本，理解系统的当前状态并定位问题根因**。

工具是认知能力的放大器，但放大器的效果取决于你有多清楚自己想问的问题。在生产环境中，最有价值的不是部署了多少可观测性工具，而是工程师能否在面对一个告警时，清晰地回答：我接下来要去哪个系统看什么数据、我在寻找什么样的证据、当我找到了什么样的证据时我可以得出结论？

这种能力，一半来自对工具的熟练，另一半来自对"三支柱各自解决什么认知问题"的深刻理解——而后者，才是本文想传递的核心。


三支柱的联动不是"装了三个工具就完事了"，而是需要在工程设计层面做以下投资：

**统一标签体系**：Metrics 的标签（`service="order-service"`）、Logs 的标签（`service: order-service`）、Traces 的资源属性（`service.name: order-service`）必须保持一致，这样才能在不同系统间做关联查询。

**统一时间同步**：所有服务的时钟偏差应小于 1 秒（通过 NTP 保证），否则跨服务的 Span 时间关联会出现错乱，Trace Waterfall 视图会显示"子 Span 的开始时间早于父 Span"的荒谬情况。

**统一采集标准**：OTel 的核心价值之一，就是把这三种信号的采集规范统一为一套 API，让开发者不需要同时学习三套不同的 SDK，运维人员不需要同时维护三套不同的采集管道。

这就是下一篇文章的主题：OpenTelemetry 如何成为可观测性标准化的终局。
