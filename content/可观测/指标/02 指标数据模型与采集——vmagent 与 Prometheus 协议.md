# 02 指标数据模型与采集——vmagent 与 Prometheus 协议

**摘要：**

上一篇讲清了"为什么需要指标"，这一篇要回答"指标是怎么被采集进来的"。采集是整条指标链路的入口——入口处的每一个设计选择，都会沿链路放大：采集频率决定了精度与成本，服务发现决定了能否适配动态基础设施，relabel 决定了进入存储的基数，而采集端本身的性能上限，则决定了单机能管理多大的集群。本文从一次"目标抓不到"的故障切入，先完整回顾时间序列的数据模型与暴露协议（含 OpenMetrics），再拆解 Prometheus 的两大采集决策——Pull 模型与服务发现，并说明 relabel 为什么是采集链路里性价比最高的治理点。随后本文重点展开 **vmagent**：VictoriaMetrics 为什么要在 Prometheus 之外重写一个采集端，它在磁盘缓冲、流式聚合与 relabel 性能上做了哪些取舍，以及它与 OpenTelemetry Collector 的分工。最后落到采集环节的边界与反例——抓取超时、标签爆炸、采集频率误用。读完之后，你应当能为自己的集群设计一条既不丢数据、又不炸基数的采集链路。

---

## 第 1 章 一次"抓不到"的故障

### 1.1 现象：指标图出现空洞

值班工程师发现，某天下午三点之后，订单服务的 QPS 曲线开始出现规律性的"空洞"——每隔几分钟就断一小段，而业务本身没有任何异常。他先怀疑是存储问题，查了写入速率，正常；又怀疑是查询问题，换了个时间范围，空洞依旧。

真正的原因，藏在采集端。那段时间集群里新增了一批短生命周期的任务（每分钟启动一次的对账作业），每个任务启动时都会向采集端注册一个新的采集目标。采集端的目标数在短时间内翻了三倍，而每个目标的抓取超时时间没有调整——结果是采集端的并发抓取队列被占满，一部分正常目标被"饿死"，抓取间隔被拉长，落到存储里就表现为曲线上的空洞。

这个故障点出了一个常被忽视的事实：**采集端不是透明的管道，它有自己的容量上限与调度策略**。当你只关心"指标有没有存下来"时，往往会在采集这一层埋下隐患。

### 1.2 采集链路的三段

一条完整的指标采集链路，可以拆成三段：

```mermaid
%%{init: {'theme': 'dracula'}}%%
graph LR
    T["目标 (Target)</br>/metrics 端点"]
    D["发现 (Discovery)</br>目标从哪来"]
    S["抓取 (Scrape)</br>按间隔拉取"]
    P["处理 (Relabel)</br>整形与过滤"]
    W["写入 (Write)</br>本地存储或远程写入"]

    T --> D --> S --> P --> W

    classDef a fill:#44475a,stroke:#8be9fd,color:#f8f8f2
    classDef b fill:#44475a,stroke:#ffb86c,color:#f8f8f2
    classDef c fill:#44475a,stroke:#50fa7b,color:#f8f8f2
    class T,D a
    class S,P b
    class W c
```

- **发现**：采集端怎么知道"该抓谁"——静态配置、服务发现、还是主动注册。
- **抓取**：按什么间隔、什么超时、多少并发去拉取数据。
- **处理**：拉回来的原始数据要不要过滤、改名、丢标签。

这三段里，**发现的动态性**决定了能否适配容器环境，**处理的能力**决定了基数能否在入口被压住。本文按这三段展开。

## 第 2 章 数据模型与暴露协议

### 2.1 度量名与标签

时间序列的身份由**度量名（metric name）**与**标签集（label set）**共同确定。上一篇已给出定义，这里补充几个工程上必须理解的细节。

度量名在 Prometheus 内部是一个特殊标签 `__name__`，这意味着它在概念上与普通标签同权——你甚至可以在查询里用 `{__name__=~"http_.*"}` 做正则匹配。这个设计让"按名字模式批量选择指标"成为可能，也是录制规则（recording rule）批量生成的基础。

标签的取值是**字符串**，但存在两条隐含约束。其一，标签名必须匹配 `[a-zA-Z_][a-zA-Z0-9_]*`，且以 `__` 开头的是保留名（如 `__name__`、`__address__`、`__meta_*`），供内部使用。其二，**标签集的顺序无关**——`{a="1", b="2"}` 与 `{b="2", a="1"}` 是同一条序列，存储层会对其排序后去重。这一点在理解"为什么标签顺序不影响基数"时很重要。

### 2.2 样本与暴露格式

一个**样本（sample）**由"序列 + 时间戳 + 值"构成。值的类型是 64 位浮点数，时间戳是毫秒整数。采集端从目标拉回来的，是一段符合**暴露格式（exposition format）**的文本：

```text
# HELP node_cpu_seconds_total Seconds the CPUs spent in each mode.
# TYPE node_cpu_seconds_total counter
node_cpu_seconds_total{cpu="0",mode="idle"} 1.234e+05
node_cpu_seconds_total{cpu="0",mode="user"} 8.9e+03
```

三行结构分别承载了元信息、类型声明与样本。`# TYPE` 让采集端知道该序列是 counter 还是 gauge，从而在存储时可以做类型校验；`# HELP` 是可读的描述，最终会作为元数据进入存储，在 Grafana 的指标浏览器里显示。

暴露格式的"人类可读"特性是一把双刃剑。好处是任何语言只需几十行代码就能实现一个 exporter；坏处是文本解析的开销在目标规模大时不可忽略——这正是后来 OpenMetrics 与 protobuf 编码出现的原因之一。

### 2.3 OpenMetrics 与语义约定

**OpenMetrics** 把上述事实标准写成了规范，主要补充了三点：更严格的语法校验、Exemplar 的原生表达、以及直方图的标准化编码。它的出现让"兼容 OpenMetrics"有了可测试的判定依据，而不再只是"看起来像 Prometheus 格式"。

比格式更重要的，是 **语义约定（Semantic Conventions）**。OpenTelemetry 规定了一套跨信号的属性命名规范：服务名统一叫 `service.name`（映射到 Prometheus 标签时转成 `service_name`），主机名统一叫 `host.name`。这套约定的价值不在格式，而在**互操作**——它让指标、日志、追踪三者在"同一个对象的同一个属性叫什么名字"这件事上达成一致，从而使跨数据源跳转成为可能。

### 2.4 数据模型的四条约束

把数据模型摊开，可以得到四条工程约束，它们决定了指标能做什么、不能做什么：

| 约束 | 含义 | 后果 |
|---|---|---|
| 序列由标签集唯一确定 | 标签变则序列变 | 标签漂移会制造新序列 |
| 时间戳单调递增 | 同序列不接受乱序 | 乱序写入需要特殊支持 |
| 值是浮点数 | 不支持文本与结构 | 非数值信息不属于指标 |
| 无 schema | 无需预定义表结构 | 灵活，但基数失控无预警 |

这四条约束共同解释了上一篇提到的"高基数是生命线"——它不是某个实现的选择，而是数据模型本身的必然结果。

---

### 2.5 指标为什么不能"结构化"

一个常被提出的问题是：既然日志可以结构化（JSON 里放任意字段），为什么指标不行？答案藏在存储模型里。结构化意味着"每条记录可以有不同的字段集合"，而指标的存储引擎建立在"序列的标签集是稳定的、取值组合是有限枚举"这个假设之上。一旦允许任意字段，索引就从"标签值 → 序列"的倒排表退化成"每行都要读一遍"的全扫描，成本结构完全改变。

所以，**指标的"不能结构化"不是实现偷懒，而是它为极致压缩与极速聚合付出的代价**。想表达结构化信息，正确的信号是日志（Loki 的 JSON 日志、Elasticsearch 的文档），而不是硬塞进标签里。这也是为什么"用指标存审计信息"是一种从模型层面就注定失败的设计。

---

### 2.6 指标的时间语义：即时向量与范围向量

采集把样本写进存储，查询再把样本取出来，这两端对"时间"的理解并不完全一致。Prometheus 的查询语言把时间序列分成两种形态：**即时向量（instant vector）**表示"某一时刻各序列的值"，**范围向量（range vector）**表示"某段时间窗口内各序列的样本集合"。绝大多数查询函数（`rate`、`increase`、`avg_over_time`）都要求范围向量作为输入，因为它们需要"一段时间内的变化"才能计算。

这里藏着一个初学者最容易困惑的问题：**为什么 `rate()` 必须带时间窗口，而直接引用指标名却不行？** 因为直接引用指标名得到的是即时向量——它只取了每个序列在查询时刻附近的一个样本，一个点无法计算速率。`rate(x[5m])` 的语义是"在最近 5 分钟的窗口内，取该序列的首尾样本做差分，再除以窗口时长"。理解了这一点，就能理解为什么"窗口太短会导致速率抖动、窗口太长会导致速率迟钝"——这是同一个插值精度与平滑度之间的权衡。

与之配套的是**回溯窗口（lookback delta）**。当你写 `http_requests_total` 而不带窗口时，查询引擎并不会真的只取"查询时刻那一刻"的样本——因为样本是离散的，那一刻未必有数据点。它会向前回溯一个默认 5 分钟的窗口，取窗口内最新的样本作为"当前值"。如果回溯窗口内一个样本都没有，该序列就被判定为"无数据"，从结果里消失。这个机制解释了两种看似矛盾的现象：目标刚下线时，指标不会立刻消失（还在回溯窗口内）；而目标下线超过回溯窗口后，指标会突然"集体消失"，让基于它的聚合结果骤降。**理解回溯窗口，是理解"指标为什么会在某个时刻突然变少"的钥匙。**

## 第 3 章 采集模型：Pull 与 Push

### 3.1 为什么 Prometheus 选择 Pull

2012 年 Prometheus 诞生时，业界主流的监控采集方式是 Push（Nagios 被动检查、StatsD 主动上报）。Prometheus 反其道而行，选择了 Pull，理由有三条，且至今仍然成立。

第一，**目标的真实状态由采集端判定**。在 Pull 模型里，"抓取失败"本身就是一个明确的信号——采集端知道目标应该在某个时刻响应，如果没响应，就写入 `up=0`。而在 Push 模型里，"没收到数据"与"目标正常但网络丢包"难以区分，容易出现"监控静默"这种最危险的故障。

第二，**配置集中在采集端**。要采集哪些目标、什么间隔、怎么整形，全部写在采集端的配置里。这避免了"应用侧需要知道监控系统地址"的耦合，也让治理动作（改间隔、丢标签）可以集中下发。

第三，**天然适配服务发现**。在容器环境里，目标列表是动态的；Pull 模型让采集端作为"主动方"去发现目标，比让每个容器主动上报更符合运维直觉。

### 3.2 Pull 的代价

Pull 并非没有代价，两类场景会让它难受：

- **短生命周期任务**：一个只运行 3 秒的批处理作业，可能正好落在两次抓取之间，永远抓不到。解决办法是引入 **Pushgateway**——任务结束前把结果推送到网关，由网关作为一个长期目标被采集。但 Pushgateway 有已知的坑：它不会自动清理过期数据，如果任务不再运行，旧值会一直挂着，造成"僵尸指标"。
- **网络拓扑限制**：采集端必须能访问目标。在跨 NAT、跨安全域的场景里，反向连接可能不被允许，此时只能用 Push 或代理。

所以现实中的选择从来不是"Pull 还是 Push"，而是"**哪些用 Pull、哪些用 Push、边界划在哪**"。一条经验是：**长期服务用 Pull，批处理与边缘节点用 Push**，并确保 Push 进来的数据有明确的过期机制。

### 3.3 Remote Write：采集与存储解耦

当采集端与存储端分离时，需要一个"把样本送出去"的协议，这就是 **Remote Write**。采集端（Prometheus、vmagent）把样本按 Remote Write 协议发给远端存储（VictoriaMetrics、Thanos、Mimir）。

Remote Write 的设计目标是**高效的批量流式传输**：样本按序列组织、经 protobuf 编码、压缩后发送，接收端确认后采集端才推进消费位点。这条链路的关键工程问题是**背压**——如果接收端写入变慢，采集端必须有缓冲，否则只能丢数据。这正是 vmagent 引入磁盘缓冲（见第 6 章）的动机。

---

### 3.4 抓取不是采样

"采样（sampling）"这个词在可观测性里被用得很混，这里必须把两个概念分开。**抓取（scrape）是周期性的全量拉取**——每一次抓取都会把目标当前暴露的**所有**序列完整取回，不是随机挑几条。**采样（sampling）是概率性地只保留一部分数据**，这是链路追踪的常规做法（只留 1%~10% 的 Trace），指标不用。

这个区分很重要，因为它解释了为什么"调大采集间隔"与"对追踪做采样"不是一回事。追踪采样丢的是"部分请求的完整链路"，保留的那部分仍然精确；指标调间隔丢的是"两次抓取之间的所有变化"，保留的每个点仍然是精确的瞬时值，但**瞬时尖峰可能整段消失**。前者是"少看几个样本"，后者是"可能完全没看见"。

由此可以推出一条告警设计原则：**对可能瞬时越界、越界即故障的指标（如内存突增），采集间隔要足够短以捕捉它；对缓慢变化的指标（如磁盘使用率），间隔可以放宽**。一刀切地设置统一间隔，要么浪费存储，要么漏掉故障。

---

### 3.5 Push 的三种实现与选型

Push 并不是一种单一模式，它至少有三种实现路径，代价与适用场景各不相同。

第一种是**推送网关（Pushgateway）**：任务把结果推给网关，网关作为长期目标被采集。它最大的优点是简单，兼容一切支持 HTTP 的环境；最大的缺点是数据没有生命周期管理，且**聚合语义容易出错**——多个实例推同一个 job，最后写入的是"每个实例最后一次推送的值"，`rate()` 在这种数据上会得出无意义的结果。因此 Pushgateway 只适合"单实例、周期性、只关心最后一次结果"的场景，绝不能用来上报需要聚合的计数器。

第二种是**应用直接 Remote Write**：应用或边车进程按 Remote Write 协议把样本发给存储。它绕过了 Pushgateway 的聚合陷阱，因为样本的时间戳与序列身份由发送方完整提供。代价是应用侧要引入 SDK 与网络依赖，且要自己处理重试与缓冲。

第三种是**代理汇聚（如 OTel Collector 的 gateway 模式）**：边缘节点把数据发给就近的 Collector，Collector 再统一转发。它适合跨网络边界的场景——边缘只与 Collector 通信，不必知道最终存储地址。Collector 的处理器链还能在汇聚点做过滤与转换，把治理动作从"分散在边缘"收敛到"集中在汇聚层"。

选型的判断线索是**数据是否需要跨实例聚合**：需要聚合的用 Remote Write 或 Collector，不需要聚合的才用 Pushgateway。把这条线索记牢，能避开 Push 模型里最常见的一类错误。

## 第 4 章 服务发现与 Relabel

### 4.1 静态配置的困境

最早的 Prometheus 用静态配置列出目标：

```yaml
scrape_configs:
  - job_name: 'node'
    static_configs:
      - targets: ['10.0.0.1:9100', '10.0.0.2:9100']
```

在容器环境里，这套配置几乎无法维护——Pod 的 IP 每次重建都会变，实例数在几分钟内可能翻倍。静态配置的失效，催生了服务发现。

### 4.2 服务发现：让目标列表自己长出来

服务发现（Service Discovery，SD）把"目标列表"从手工维护变成自动获取。常见的 SD 类型包括：

| 类型 | 目标来源 | 适用场景 |
|---|---|---|
| `kubernetes_sd` | K8s API（Pod/Service/Endpoints/Ingress） | 容器平台 |
| `consul_sd` / `etcd_sd` | 注册中心 | 微服务注册 |
| `file_sd` | 本地 JSON/YAML 文件 | 混合环境、由外部程序刷新 |
| `dns_sd` | DNS SRV 记录 | 简单场景 |
| `static_configs` | 静态列表 | 少量固定目标 |

`kubernetes_sd` 是最常用也最复杂的一种，它有多种"角色"（role）：按 `pod` 发现会拿到所有 Pod，按 `endpoints` 发现会拿到 Service 背后的就绪端点，按 `service` 发现拿到 Service 本身。选错角色会导致采集到不该采集的目标——比如用 `pod` 角色会把没有暴露指标的 Pod 也纳入采集范围，白白消耗采集端资源。

### 4.3 Relabel：采集链路的整形手术

服务发现给出的原始目标，带有一堆 `__meta_*` 元标签（如 `__meta_kubernetes_pod_name`）。这些元标签不能直接作为最终标签进入存储，需要经过 **relabel** 整形。relabel 是采集链路里最强大、也最容易被低估的机制，它用一组"源标签 → 正则 → 目标标签"的规则，完成四类操作：

- **改名**：把 `__meta_kubernetes_pod_label_app` 映射为 `service`。
- **过滤**：用 `keep`/`drop` 决定保留还是丢弃目标，或保留还是丢弃指标。
- **丢弃标签**：用 `labeldrop` 把易漂移的高基数标签（如 `pod`、`container_id`）在入口处删掉。
- **重写**：用 `replace` 把 URL 路径收敛成路由模板，避免 `path` 标签爆炸。

> [!info] 为什么 relabel 是性价比最高的治理点
> 所有降基数的动作里，relabel 是唯一发生在"数据进入存储之前"的。在入口丢掉一个高基数标签，等于同时省下采集端内存、传输带宽、存储空间与查询开销。相比之下，事后清理需要先发现、再删除，成本高得多。**指标治理的第一现场，永远是采集配置。**

### 4.4 metric_relabel_configs 与 label_limit

relabel 分两个层面：`relabel_configs` 作用于**目标**（决定抓不抓这个目标），`metric_relabel_configs` 作用于**样本**（决定抓回来的样本留不留）。后者是丢弃无用指标的主力，例如：

```yaml
metric_relabel_configs:
  # 丢弃采集耗时极高但无人查看的指标
  - source_labels: [__name__]
    regex: 'go_gc_duration_seconds.*'
    action: drop
  # 收敛 URL 路径，避免高基数
  - source_labels: [path]
    regex: '/orders/[0-9]+'
    target_label: path
    replacement: '/orders/:id'
```

此外，采集端普遍支持**标签数量与长度上限**（如 Prometheus 的 `label_limit`、`label_name_length_limit`、`label_value_length_limit`），超限的样本会被拒绝并计数。这些"护栏"不会阻止基数增长，但能防止单个异常目标拖垮整个采集端。

---

### 4.5 服务发现的失效模式

服务发现把"目标列表"交给了外部系统，也就把一部分可靠性依赖转移了出去。它有几类典型的失效模式，值得在部署前就想清楚：

- **发现延迟**：K8s 的 Endpoints 更新与采集端的同步之间存在时间差。一个新 Pod 可能在被采集之前就已经处理了请求，这段"指标空白"是结构性的，无法完全消除，只能缩短。
- **发现抖动**：短时间内大量目标反复出现与消失（如 CrashLoopBackOff 的 Pod），会让采集端的目标池频繁变动，消耗同步开销。对这类目标应当用 relabel 排除，而不是让它反复被采集。
- **权限与限流**：`kubernetes_sd` 需要访问 K8s API。当集群规模大时，API 请求本身可能成为负担，甚至触发 API Server 的限流。大规模场景下，采集端的服务发现应当使用 watch 机制而非轮询，并考虑用集中式的发现代理来分摊 API 压力。
- **元标签泄漏**：服务发现注入的 `__meta_*` 标签如果忘记清理，会直接进入存储，成为高基数来源。这类标签的数量往往远超预期——一个 K8s Pod 的元标签可以有几十个。

这四类失效模式的共同点是：**它们都发生在"数据进入采集端之前"，且都不会立刻报错**。等到曲线出现异常时，往往已经积累了一段时间。

---

### 4.6 file_sd 与配置的治理边界

在纯容器环境里，`kubernetes_sd` 能解决绝大部分发现需求；但在混合环境（既有容器又有物理机、既有 K8s 又有裸机中间件）里，`file_sd` 往往是最实用的折中。它的机制很简单：采集端周期性读取一个本地 JSON/YAML 文件，文件内容就是目标列表；外部程序（如 CMDB 同步脚本、Ansible、自研控制器）负责刷新这个文件。

`file_sd` 的价值在于**把"目标从哪来"这件事与采集端解耦**。采集端只认文件格式，不关心上游是 CMDB、是配置管理数据库、还是一个手写的脚本。这带来两个好处：其一，接入新类型的对象只需改上游同步程序，不必动采集端配置；其二，目标的来源可以被审计——文件本身就是一份"当前该采集谁"的清单。

它的代价是**多了一跳同步延迟**，以及**文件刷新本身的可靠性**（脚本挂了、写文件写坏了，都会导致目标列表异常）。因此在生产里，`file_sd` 的刷新程序必须被纳入监控，且应当以"原子替换"的方式更新文件，避免采集端读到半截内容。

无论用哪种服务发现，有一条治理边界需要提前划定：**发现是"目标的来源"，不是"目标的授权"**。服务发现会把所有符合条件的目标都交给你，但"要不要采集它"是另一回事——这需要在 relabel 里显式表达（`keep` 或 `drop`）。把发现与授权混在一起，是许多"意外采集到大量无关目标"事故的根源。

## 第 5 章 一次 Scrape 的完整流程

### 5.1 生命周期

把一次抓取拆开，可以看到采集端的内部时序：

```
1. 调度器从目标池中取出一个到期目标
2. 发起 HTTP GET /metrics，带上 Accept 头（声明支持的格式）
3. 读取响应体，逐行解析（或按 protobuf 解析）
4. 对每个样本应用 metric_relabel_configs
5. 校验：标签数量/长度、时间戳合法性、样本数上限
6. 追加到内存中的时序缓冲区（Head）
7. 写入 WAL（若启用本地存储）
8. 记录抓取元数据：up、scrape_duration_seconds、scrape_samples_scraped

```

其中第 8 步产出的**自监控指标**极其重要。`up` 告诉你目标是否可达，`scrape_duration_seconds` 告诉你抓取有多慢，`scrape_samples_scraped` 告诉你目标暴露了多少样本。采集端自身的健康，必须靠它自己暴露的指标来观测——这是"用指标监控指标系统"的自举。

### 5.2 抓取失败与 up 指标

`up` 是最朴素也最有效的健康指标：`up == 0` 表示这次抓取失败。但要注意，**抓取失败不等于服务不可用**。可能的原因包括：目标过载无法及时响应、网络抖动、`/metrics` 端点本身有 bug、采集端并发不足。

因此，把 `up == 0` 直接当成"服务挂了"来告警，会产生大量误报。更稳妥的做法是把 `up` 与业务指标结合判断：`up == 0` 且该服务的业务 QPS 也掉零，才是真正的服务故障。

### 5.3 陈旧标记与数据缺失

当目标从服务发现里消失（Pod 被删除）时，采集端会为它的所有序列写入**陈旧标记（staleness marker）**。这个标记让查询引擎知道"此后无数据"，从而在聚合时正确地把失效实例排除。

如果不理解这个机制，会踩两类坑。其一，告警规则里用 `absent()` 检测"指标消失"时，必须意识到"目标下线"与"指标未暴露"是两回事。其二，某些聚合函数在遇到陈旧标记时的行为与"值为 0"不同——`rate()` 会把陈旧点当作序列结束，而不是当作 0，这恰恰是我们想要的语义。

---

### 5.4 抓取并发、分片与限流

第 1 章那个"抓取饥饿"的故障，根子在采集端的调度模型。采集端通常维护一个"抓取池（scrape pool）"，池内的目标按间隔轮转抓取，池之间有并发上限。当目标数增加时，如果并发上限不变，单个目标的实际抓取间隔就会被拉长——**配置里写的间隔是"期望值"，实际间隔由调度决定**。

处理这个问题的标准手段有三层：

- **分组（分池）**：把抓取间隔与超时需求相近的目标放进同一个池。短周期目标与长周期目标混在一个池里，会让调度变得低效。
- **分片（sharding）**：当单实例采集端扛不住时，用一致性哈希把目标分散到多个采集端。vmagent 支持这种水平分片，每片只负责一部分目标，再统一远程写入。分片的关键是"目标分配要稳定"——否则目标在分片间漂移会造成重复或遗漏。
- **限流与背压**：对单次抓取的样本数设上限（`sample_limit`），对并发抓取数设上限，对目标响应体大小设上限。这些护栏的作用是"让一个异常目标不能拖垮整池"。

一条经验判断是：**如果你的采集端 CPU 长期高于 50%，或者 `scrape_duration_seconds` 的 P99 逼近超时值，就该考虑分片了**，而不是等到出现空洞。

---

### 5.5 采集自监控：该盯哪几个指标

采集链路必须被监控，而最合适的数据源就是采集端自己暴露的元指标。把它们整理成一份清单，可以直接作为"采集健康看板"的骨架：

| 元指标 | 含义 | 异常含义 |
|---|---|---|
| `up` | 目标是否抓取成功 | 为 0 需区分目标故障与抓取饥饿 |
| `scrape_duration_seconds` | 单次抓取耗时 | P99 逼近超时值说明目标变慢或并发不足 |
| `scrape_samples_scraped` | 单次抓到的样本数 | 突增是基数风险的早期信号 |
| `scrape_series_added` | 新增序列数 | 持续为正说明存在标签漂移 |
| `prometheus_target_scrape_pool_sync_total` | 服务发现同步次数 | 频繁变动说明目标池不稳定 |
| `prometheus_tsdb_head_series` | 头部序列总数 | 长期上升说明基数在缓慢泄漏 |

这份清单的价值在于**把"采集健康"从"看不见"变成"可量化"**。其中 `scrape_series_added` 尤其值得关注——它衡量的是"每次抓取新增了多少条序列"，如果这个数长期为正，就说明标签在持续漂移，序列数只增不减。这是发现标签漂移最灵敏的探针，比事后去存储里翻基数报告要早得多。

---

### 5.6 协议协商与传输开销

抓取不是一个"下载文本文件"的简单动作，采集端与目标之间会做一轮协议协商。采集端在 `Accept` 头里声明自己支持的格式（文本、protobuf、OpenMetrics 变体），目标选择其中一个返回。这个协商过程决定了三件事：**解析成本**（文本解析比 protobuf 慢）、**传输体积**（文本未压缩，protobuf 更紧凑）、以及**功能可用性**（原生直方图、Exemplar 只在特定格式下支持）。

在大规模集群里，这轮协商的开销不可忽视。以 5000 个目标、每目标 500 条样本为例，单轮全量抓取要传输 250 万行文本；如果启用压缩（`Accept-Encoding: gzip`）与 protobuf 编码，传输体积可以下降数倍，解析的 CPU 开销也能明显降低。这正是采集端普遍支持多种格式、并优先协商压缩的原因。

值得注意的是，**压缩与解析是"采集端 CPU"与"网络带宽"之间的另一组权衡**。压缩能省带宽，但要花 CPU 解压；不压缩省 CPU，但要多传数据。在带宽充裕、CPU 紧张的边缘节点上，关掉压缩反而可能更快。这类"看起来是优化、实际要按环境判断"的选择，在采集链路里比比皆是——它们共同说明了一件事：**采集配置没有放之四海皆准的最优解，只有针对当前瓶颈的最优解**。

## 第 6 章 vmagent：重写采集端的动机

### 6.1 Prometheus 采集端的瓶颈

Prometheus 的采集与存储是耦合的——采集端抓到的样本直接进入本地 TSDB。这种耦合在中小规模下很方便，但在大规模下会暴露两个问题。

其一是**资源争抢**。采集（网络 I/O + 解析）、存储（压缩 + 合并）、查询（扫描）三者跑在同一个进程里，互相抢 CPU 与内存。当集群规模变大时，你很难在不影响查询的前提下扩容采集能力。

其二是**可靠性**。如果本地 TSDB 出问题（磁盘满、合并卡住），采集端会跟着受影响；反过来，如果采集端要迁移，本地数据也不好带走。采集与存储耦合，让"水平扩展采集"这件事变得别扭。

### 6.2 vmagent 的定位

**vmagent** 是 VictoriaMetrics 提供的独立采集端，它的核心定位是"**把采集从存储里拆出来**"。它做的事情与 Prometheus 的采集部分相同——服务发现、抓取、relabel——但把数据统一通过 Remote Write 发往远端存储（可以是 VictoriaMetrics，也可以是任何兼容的接收端）。

这个拆分带来三个直接好处：

- **可独立扩展**：采集能力与存储能力解耦，各自按需扩容。
- **可做前置聚合**：vmagent 支持 `-streamAggr` 等流式聚合，在数据出采集端之前就做降采样或预聚合，减少远端存储压力。
- **可多路复用**：一份采集数据可以同时发往多个接收端（如生产存储 + 灾备存储），实现写入侧的高可用。

### 6.3 磁盘缓冲：不丢数据的代价

采集链路最怕的故障是"接收端短暂不可用导致数据丢失"。Prometheus 的本地存储天然有缓冲（数据先落本地 WAL），而一旦采集与存储分离，"采集端到接收端"这段网络就成了新的丢数据风险点。

vmagent 的解法是**磁盘缓冲（persistent queue）**：抓到的样本先写入本地磁盘队列，成功发送到接收端后才推进消费位点。这样即使接收端宕机数小时，采集端也能在磁盘上攒住数据，等接收端恢复后补齐。代价是本地需要一块可观的磁盘空间——缓冲队列的大小与"最长可容忍的接收端故障时长 × 采集速率"成正比。

这个取舍体现了一条更普遍的原则：**可靠性与成本永远成对出现**。要"不丢数据"，就得付出磁盘与复杂度的代价；要"简单便宜"，就得接受"接收端故障时丢一部分"。vmagent 把选择权交给了配置。

### 6.4 relabel 性能与流式聚合

在大规模集群里，relabel 规则本身会成为 CPU 热点——每抓一次、每条样本都要过一遍正则。vmagent 在这方面做了针对性优化，把常见的 relabel 操作做成更高效的实现路径。

更有意思的是**流式聚合**。传统做法是"先全量写入存储，再在查询时聚合"；vmagent 允许在采集端做一部分预聚合，例如把每秒的原始样本聚合成每分钟的摘要再发出。这能显著降低存储与查询成本，但代价是**丢失了细粒度下钻能力**——聚合之后，你再也无法按原始标签做切片。因此流式聚合只适用于那些"确定不需要细粒度"的指标，且应当谨慎评估。

### 6.5 vmagent、Prometheus 与 OTel Collector 的分工

三个采集端经常被放在一起比较，但它们的设计目标不同：

| 采集端 | 核心定位 | 适合场景 | 关键差异 |
|---|---|---|---|
| Prometheus | 采集 + 存储 + 查询一体 | 中小规模、单机自足 | 简单，但难独立扩展采集 |
| vmagent | 纯采集 + 远程写入 | 大规模、采集存储分离 | 磁盘缓冲、流式聚合、多路复用 |
| OTel Collector | 多信号统一管道 | 需要同时处理指标/日志/追踪 | 协议丰富、可插拔处理器 |

一个务实的组合是：**用 OTel Collector 统一接入应用侧的多信号数据，用 vmagent 承担指标的高吞吐采集与远程写入**。两者并不冲突——Collector 擅长"协议转换与多信号编排"，vmagent 擅长"高吞吐指标采集"。选择的关键在于你的瓶颈在哪一端。

---

### 6.6 选型判断：什么时候该换采集端

换采集端是有成本的——新的组件、新的配置语法、新的运维习惯。判断"是否值得换"，可以看三个信号：

- **采集与存储互相拖累**：Prometheus 的查询变慢会连带影响采集，或者采集的尖峰会让查询抖动。这说明耦合已经成为瓶颈。
- **需要写入侧高可用**：业务要求"采集数据同时进生产与灾备存储"，而这在单体 Prometheus 上需要额外组件。
- **需要跨网络边界的汇聚**：边缘节点只能 Push，需要采集端具备磁盘缓冲与断点续传能力。

如果以上三条都不成立——单集群、中等规模、采集与查询互不干扰——那么继续用 Prometheus 内置采集端反而更简单。**架构升级的理由应当是"当前的耦合真的成了瓶颈"，而不是"vmagent 听起来更先进"**。这与本专栏一贯的立场一致：没有银弹，只有权衡。

---

### 6.7 部署形态与容量估算

vmagent 的部署形态决定了它的容量边界。常见有三种：**单实例**（适合中小规模，配置简单）、**多实例分片**（每个实例负责一部分目标，用一致性哈希分配）、**多实例冗余**（多个实例抓同样的目标，互为备份，用于对"不丢数据"要求极高的场景）。分片解决"抓不过来"，冗余解决"抓挂了怎么办"，两者可以叠加，但叠加会成倍增加采集开销。

容量估算的关键是三个数：**目标数、每目标样本数、采集间隔**。三者相乘再除以间隔，就是采集端的样本处理速率。以"5000 个目标、每目标 500 条样本、间隔 15 秒"为例，单次抓取要处理 250 万个样本，每秒要处理约 16.7 万个样本——这已经接近单实例 Prometheus 的舒适区上限。此时应当考虑分片，或把采集端换成对高吞吐更友好的实现。

一个常被忽略的容量因素，是**relabel 的复杂度**。每条样本都要过一遍 relabel 规则，规则的条数与正则的复杂度会直接乘到处理速率上。在大规模场景里，"精简 relabel 规则"本身就是一项性能优化。

## 第 7 章 Exporter 生态与自建指标

### 7.1 Exporter 模式

绝大多数系统本身并不暴露 Prometheus 格式的指标，于是需要 **exporter** 作为适配器：它以独立进程（或 sidecar）运行，从目标系统拉取原始状态（通过其自身 API、命令行、日志等），转换成暴露格式供采集端抓取。

这个模式的价值在于**解耦**：被监控的系统不需要为了可观测性而改造自己，exporter 承担了所有适配成本。常见的 exporter 有 Node Exporter（主机）、MySQL/Redis Exporter（数据库）、Kafka Exporter（消息队列）等。

Exporter 模式的代价是**额外的进程与一次额外的数据搬运**。每个 exporter 都是一个新的部署单元、一个新的故障点、一份新的资源开销。在 K8s 里，这通常通过 DaemonSet（如 Node Exporter）或 sidecar 来落地。

### 7.2 四种客户端库

对于自己开发的应用，直接在代码里埋点比外挂 exporter 更精确。主流语言的客户端库都提供四种指标类型（对应上一篇讲的 Counter/Gauge/Histogram/Summary）：

- **Counter**：`requests_total.inc()`，单调递增。
- **Gauge**：`inflight.set(42)`，可增可减。
- **Histogram**：`duration.observe(0.23)`，自动分桶累计。
- **Summary**：`duration.observe(0.23)`，客户端算分位数。

埋点的一个基本原则是**在正确的位置埋**：延迟应当埋在"请求入口到出口"的完整跨度上，而不是埋在某个内部函数上；错误计数应当埋在"决定成败的那一处"，而不是散落在多个 catch 块里。埋点位置错了，指标再准也回答不了业务问题。

### 7.3 自建指标的命名与口径

自建指标最容易出的问题不是技术，而是**口径**。同一个"成功率"，不同团队可能按不同标准统计。避免口径混乱的办法是把命名规范与口径一起固化：

- 名字带单位：`_seconds`、`_bytes`、`_total`。
- Counter 用 `_total` 且语义是"累计成功/失败次数"。
- 在 `# HELP` 里写清口径："success rate excludes 4xx client errors"。
- 业务指标与资源指标分开命名，避免混用。

口径是业务决策，必须在埋点之前与业务方对齐——这是上一篇"口径不一致导致 SLO 失真"那节在采集侧的延伸。

---

### 7.4 Exporter 的常见坑

Exporter 看似简单，实际部署中有几类反复出现的问题：

- **采集超时**：许多 exporter 在每次被抓取时才去查询后端（如 MySQL 的 `SHOW STATUS`），如果后端慢，exporter 就会超时。解决办法是在 exporter 内部做缓存（`--collector` 级别），把"慢查询"与"抓取"解耦。
- **自身成为瓶颈**：一个 exporter 被配置成采集大量指标（如把所有表都纳入），单次抓取可能耗时数秒，拖垮采集端。应当按需裁剪 collector。
- **多实例语义错位**：exporter 抓的是"它连接的那个后端"的状态，而不是"它自己所在主机"的状态。如果一个 exporter 实例连接多个后端，指标会混在一起，导致 `instance` 标签失真。正确的做法是"一个 exporter 实例只对应一个被监控对象"。
- **无谓的高基数**：某些 exporter 默认暴露带 `table`、`query` 等维度的指标，在数据库表多、查询杂的场景里会制造大量序列。这类指标应当通过 `metric_relabel_configs` 在采集端丢弃。

这些坑的共同特征是：**它们都发生在"适配层"而不是"被监控系统"里**，因此往往不被当作"被监控系统的问题"来处理，长期积累。

---

### 7.5 埋点的三个层次

一个服务的指标埋点，应当覆盖三个层次，缺一层就会在排障时出现"断层"：

- **服务层（RED）**：QPS、错误率、延迟分布。这是最外层，回答"用户感受如何"。它通常由框架或网关自动埋点，成本最低。
- **依赖层**：对下游的调用量、调用延迟、失败率；数据库连接池占用、慢查询数；缓存命中率。这一层回答"瓶颈在哪一跳"。它是排障时最有价值的一层，因为大多数故障的根因都在依赖上，而不是在本服务内部。
- **资源层（USE）**：CPU、内存、GC、线程池、文件描述符。这一层回答"为什么这一跳会慢"。它通常由运行时或 exporter 提供。

三层齐备的好处是**排障时可以沿着"用户感受 → 哪一跳 → 为什么"逐级下钻**，每一级都有对应的指标。如果只有服务层，你会发现"错误率涨了但不知道为什么"；如果只有资源层，你会发现"CPU 很高但不知道是否影响用户"。埋点设计的本质，就是为排障路径的每一步预先准备好证据。

---

### 7.6 Exporter 与 SDK 的边界

最后划清一条边界：**exporter 与 SDK 不是竞争关系，而是覆盖不同对象的手段**。SDK 用于"你自己的代码"——你能改它，所以可以在关键路径上精确埋点，拿到最贴合业务的指标；exporter 用于"你改不了的系统"——数据库、消息队列、操作系统，你只能从外部观察它们暴露的状态。

判断用哪个，看一个问题：**这个对象内部有没有"业务语义"？** 如果你需要知道"这个服务处理了多少订单、失败了多少笔"，这只能靠 SDK，因为外部观察不到业务语义；如果你只需要知道"这个进程占了多少内存、打开了多少连接"，exporter 就够了，因为这些都是进程对外可见的状态。

一个常见的错误是"用 exporter 硬凑业务指标"——比如从数据库的慢查询日志里统计"业务成功率"。这种做法既脆弱（日志格式一变就失效），又失真（日志里的成功率与用户感受到的成功率是两回事）。**业务语义只能从业务代码里来**，这是 exporter 模式无法逾越的边界。

## 第 8 章 边界与反例

### 8.1 采集频率的误用

把采集频率当成"越高越好"是常见误解。频率提高的收益是"捕捉更短的尖峰"，但收益是递减的：从 60 秒到 15 秒，你能多看到 4 倍的细节；从 15 秒到 1 秒，你多看到的细节对绝大多数告警与容量分析没有价值，成本却涨了 15 倍。

更重要的是，**采集频率高不等于数据可信**。如果目标本身的指标是"每分钟更新一次"（如某些云厂商 API），那么把抓取间隔调到 5 秒，只会抓到 12 次重复的旧值，徒增存储。

### 8.2 标签爆炸的三个入口

采集侧的基数爆炸，通常从三个入口进入：**服务发现带来的元标签**（`__meta_*` 未清理）、**目标自身的标签**（应用把请求 ID 写进了指标）、**relabel 规则写错**（正则过于宽松，把不该保留的标签保留了下来）。三者的共同点都是"入口没有做减法"。前面反复强调 relabel 的价值，正是因为它是这三个入口唯一统一的把关点。

### 8.3 抓取超时与并发

回到第 1 章那个故障：目标数暴增导致抓取饥饿。它的根因是**采集端的并发与超时没有随目标数调整**。工程上的处理办法包括：合理设置 `scrape_timeout`（通常不超过间隔的一半）、限制单次抓取的样本数上限、对慢目标单独分组、以及用 vmagent 这类可水平扩展的采集端。

一条容易被忽视的规则是：**`scrape_timeout` 必须小于 `scrape_interval`**。如果超时等于间隔，那么一个卡住的目标会挤占下一个抓取周期，形成雪崩。把超时设为间隔的一半，是留出"重试与恢复"余地的常见做法。

### 8.4 一个正例：用 up 与 scrape 元数据做自监控

采集链路本身也必须被监控，而最好的监控数据恰恰来自采集端自己暴露的元指标：

- `up == 0`：目标不可达，需要区分"目标真挂了"与"抓取被饿死"。
- `scrape_duration_seconds` 持续上升：目标响应变慢，可能需要调大超时或排查目标。
- `scrape_samples_scraped` 突增：某个目标开始暴露大量新指标，是基数风险的早期信号。
- `prometheus_target_scrape_pool_sync_total`：服务发现同步频率，异常时说明发现机制出了问题。

把这几个元指标做成一块"采集健康"看板，能在基数事故与抓取饥饿演变成故障之前就发出预警。这是"自举监控"最直接的收益。

### 8.5 反例：Pushgateway 的僵尸指标

Pushgateway 的坑值得单独讲，因为它的表现极具迷惑性。当一个批处理任务把结果推送到 Pushgateway 后停止运行，Pushgateway **不会**自动删除这条数据——它不知道任务是否还会再跑。于是这条"最后一次推送的值"会一直挂在那里，被采集端持续抓取。

后果是什么？如果这个指标是"上次任务成功数"，那么告警规则 `task_success_total < 1` 永远不会触发，因为值一直停在最后一次的成功结果上。监控看起来"一直正常"，而任务实际上已经几周没跑了。这类"僵尸指标"是监控系统里最危险的一类假象——**它不是缺数据，而是有错误的数据**。

避免办法有两条：一是在指标里带上 `push_time_seconds` 这类时间戳，告警规则同时判断"值"与"新鲜度"；二是对不再运行的任务，用 Pushgateway 的删除接口显式清理，并把这个清理动作纳入任务的生命周期管理。

### 8.6 反例：把 exporter 的失败当成服务失败

有一类误报特别常见，值得单独拎出来讲：**exporter 抓取失败被当成被监控服务故障**。exporter 是一个独立进程，它会因为自身的原因失败——配置写错、依赖的后端凭据过期、进程被 OOM、端口被占用。这些失败与"被监控的服务是否健康"毫无关系，但如果告警规则只看 `up == 0`，就会把 exporter 的故障误报成业务故障。

更麻烦的是，某些 exporter 在失败时**仍然返回 200**，只是指标值为 0 或缺失。此时 `up` 是 1，看起来一切正常，而实际数据已经不可信。这类"沉默的失败"比抓取失败更危险。

应对这类问题的原则是**给 exporter 自身的健康单独建一条观测线**：为每个 exporter 暴露一个"最近一次成功采集的时间戳"指标，告警规则同时判断"业务指标是否异常"与"数据是否新鲜"。把"数据缺失"与"数据正常"严格区分开，是任何监控体系的基本功——这也是上一篇"忘记区分零与无数据"那条反例在采集侧的具体表现。

### 8.7 一条贯穿全篇的原则

从抓取饥饿、标签泄漏到僵尸指标，本文列举的故障有一个共同结构：**入口处的设计缺陷，会在下游以完全不同的面貌暴露**。抓取饥饿表现为曲线空洞，标签泄漏表现为查询变慢，僵尸指标表现为监控静默——但它们的根都在采集配置里。

这也是为什么本文把大半篇幅花在 relabel、服务发现与抓取调度上：**在指标链路里，入口治理的杠杆最大、成本最低**。把入口管住，后面的存储与查询才有从容优化的余地。

### 8.8 反例：采集配置的"复制粘贴"债务

最后一个反例不在技术上，而在协作上。采集配置往往由不同团队各自维护，新服务上线时最常见的方式是"把上一个服务的抓取配置复制过来改改"。这种复制会持续累积债务：relabel 规则里残留着上一个服务的过滤条件，采集间隔沿用了上一个服务的历史选择，标签命名带上了上一个团队的偏好。

这些债务单看都不致命，但它们的总和会让"采集配置"从一份可读的声明，退化成一堆无人敢动的历史沉积。当需要做一次全局的基数治理时，你会发现自己无法回答"这个规则到底是为谁写的"。

对抗这种债务的办法是把配置**当成代码来管理**：统一放在版本控制里、通过模板生成而非手工复制、对每一段非默认配置写明"为什么"。采集配置是整条指标链路的入口，它的可读性直接决定了后续治理的可行性。

---

## 小结

采集是指标链路的入口，也是治理杠杆最大的一环。本文从一次抓取饥饿的故障出发，走完了发现、抓取、处理三段：发现决定了能否适配动态基础设施，抓取决定了精度与成本的平衡，而处理（relabel）决定了进入存储的基数。

vmagent 的出现，本质上是把"采集"从"存储"里拆出来，让两者可以独立扩展——它用磁盘缓冲换取了不丢数据，用流式聚合换取了更低的存储压力，代价是复杂度的上升与本地磁盘的占用。这些取舍没有标准答案，只有与你的规模、可靠性与成本目标是否匹配。

最后回到一条贯穿全篇的判断：**指标治理的最佳位置是采集入口**。等到数据已经进入存储，再去发现与清理高基数，成本要高一个数量级。把 relabel 规则、标签上限、抓取超时这些"入口护栏"配置好，比事后任何补救都更划算。
