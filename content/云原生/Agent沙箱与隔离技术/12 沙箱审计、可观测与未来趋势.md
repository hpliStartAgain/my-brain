# 12 沙箱审计、可观测与未来趋势

> [!abstract] 摘要
> 这是 Agent 沙箱与隔离技术专栏的收官篇。前 11 篇覆盖了"如何隔离"（namespace/cgroups/seccomp/gVisor/Kata/Firecracker）、"如何防外泄"（Egress 过滤）、"如何防逃逸和防诱导"（沙箱逃逸与 Agent 特有风险）。本文讨论最后两个维度——"如何知道发生了什么"（审计可观测）和"未来向何处去"（演进趋势）。审计可观测部分深入三大 eBPF 监控工具——Tetragon（内核态安全策略执行）、Falco（syscall 级运行时安全监控）、AgentSight（AI Agent 专用 eBPF 监控）——以及四层审计粒度（syscall 级/进程级/网络级/文件级）和审计与性能开销的平衡。未来趋势部分讨论三个前沿方向——Confidential Containers（基于 AMD SEV-SNP/Intel TDX 硬件 TEE 的加密 VM）、WebAssembly Agent 沙箱（Pyodide/agent-sandbox，<13ms 冷启动）、GKE Agent Substrate（超大规模 Agent 编排）——以及标准化方向。最后回顾全专栏 12 篇的核心认知，构建从"chroot 到 Confidential Containers"的完整知识图谱。核心认知：Agent 沙箱技术正在从"容器隔离"向"硬件加密隔离"演进——未来的 Agent 沙箱不仅防止代码逃逸到宿主机，还防止"即使宿主机管理员也无法读取 Agent 的内存内容"。

## 第 1 章 审计可观测——知道沙箱内发生了什么

### 1.1 为什么审计可观测至关重要

前 11 篇讨论的隔离、过滤、防御都是"预防性"措施——试图阻止攻击发生。但没有任何预防措施是 100% 可靠的——攻击可能绕过防御。当攻击发生时（或怀疑发生时），你需要"知道发生了什么"——这就是审计可观测的职责。

Agent 沙箱的审计可观测有三个核心目标：
1. **实时检测**——攻击正在发生时立即发现（如 Agent 突然开始大量外传数据）
2. **事后取证**——攻击发生后回溯"什么时候、通过什么路径、泄露了什么"
3. **合规审计**——满足法规要求的操作记录（如"谁在什么时候访问了什么数据"）

### 1.2 eBPF——审计可观测的技术基础

eBPF（Extended Berkeley Packet Filter）是现代 Linux 审计可观测的技术基础——它允许在内核中运行沙箱化的程序，在内核的各个挂载点（系统调用入口、网络栈、文件操作等）采集事件。

**eBPF 相比传统审计的优势**：
- **内核态执行**——eBPF 程序在内核中运行，不需要每次事件都切换到用户态——性能开销极低
- **可编程**——可以用 C/Rust 编写自定义的审计逻辑，而非依赖预定义的审计规则
- **安全**——eBPF 程序经过验证器（verifier）检查，确保不会崩溃内核或无限循环
- **无需修改内核**——eBPF 程序可以动态加载和卸载，不需要重新编译内核或重启系统

### 1.3 Tetragon——内核态安全策略执行

Tetragon 是 CNCF/Cilium 项目的 eBPF 安全可观测和运行时执行工具——它不仅"观测"，还能"执行"安全策略。

**核心特性**：
- **内核态策略评估**——安全策略在内核中评估，不需要用户态介入——从事件发生到策略评估的延迟在微秒级
- **实时 enforcement**——不仅能检测违规，还能实时阻止（如杀死违规进程、阻止网络连接）
- **多粒度监控**——进程执行、系统调用、I/O 活动、网络连接

**Agent 沙箱中的 Tetragon 应用**：
- 检测"沙箱内进程尝试执行 `/bin/sh`"——可能是逃逸尝试
- 检测"沙箱内进程尝试连接非白名单 IP"——可能是数据外泄
- 检测"沙箱内进程尝试读取 `/proc/1/root`"——可能是通过 /proc 访问宿主机文件系统
- 实时阻止上述违规——而非只记录日志

### 1.4 Falco——syscall 级运行时安全

Falco 是 CNCF 的运行时安全工具——专注于 syscall 级监控。

**与 Tetragon 的区别**：Falco 更侧重"检测和告警"——它用规则文件定义"什么行为是可疑的"，当 syscall 匹配规则时触发告警。Tetragon 更侧重"检测和阻止"——策略在内核中评估并可以实时阻止。两者互补——Falco 适合"告警驱动的安全运营"，Tetragon 适合"实时防护"。

**Falco 的规则示例**：
```
# 检测容器内执行 shell
- rule: Shell Spawned in Container
  condition: evt.type=execve and container.id != host and proc.name in (bash, sh, zsh)
  output: Shell spawned in container (container=%container.id proc=%proc.name)
```

### 1.5 AgentSight——AI Agent 专用 eBPF 监控

AgentSight 是 2024 年发布的 AI Agent 专用 eBPF 监控工具——专门为 Agent 场景设计的审计可观测。

**Agent 专用的监控维度**：
- **Agent 操作追踪**——追踪 Agent 的每个工具调用（bash 命令、文件读写、网络请求）
- **Agent 间通信监控**——在多 Agent 系统中追踪 Agent 之间的消息传递
- **异常 Agent 行为检测**——基于 Agent 的正常行为基线检测异常（如突然的数据外传、异常的命令模式）

**与传统安全监控的区别**：传统安全监控（Tetragon/Falco）关注"系统级行为"——进程、文件、网络。AgentSight 关注"Agent 级行为"——工具调用、决策路径、上下文使用。这种"Agent 级"的监控维度让安全团队可以检测到"系统级行为正常但 Agent 级行为异常"的情况——如 Agent 执行了合法的 `curl` 命令（系统级正常），但目标是非预期的域名（Agent 级异常）。

### 1.6 四层审计粒度

Agent 沙箱的审计可以在四个粒度层面进行：

| 粒度 | 监控对象 | 工具 | 开销 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| **Syscall 级** | 每个系统调用 | Falco | 中 | 最详细的审计——但也产生最多数据 |
| **进程级** | 进程创建/销毁/执行 | Tetragon | 低 | 检测异常进程行为 |
| **网络级** | 网络连接/流量 | Tetragon/Cilium | 低 | 检测异常网络行为 |
| **文件级** | 文件读写 | Tetragon | 低 | 检测敏感文件访问 |

**审计与性能开销的平衡**：审计不是"免费的"——每个被审计的事件都需要内核处理和存储。syscall 级审计的开销最高（因为 syscall 频率极高），进程/网络/文件级审计的开销较低（因为事件频率相对低）。在生产环境中，通常不做"全量 syscall 审计"——而是审计"可疑的 syscall 子集"（如只审计 `open`/`connect`/`execve` 等安全相关的调用），在覆盖率和性能之间取得平衡。

> [!info] 核心概念：审计是"事后的眼睛"
> 审计不能"阻止攻击"——它只能"记录攻击发生了"。但审计的价值在于——当攻击发生时，你不会"什么都不知道"。一个没有审计的沙箱被攻破后，你不知道"什么时候被攻破的、通过什么路径、泄露了什么数据"——你甚至可能不知道"被攻破了"。一个有审计的沙箱被攻破后，你可以回溯完整攻击链——从"哪个 Prompt Injection 触发了攻击"到"哪些文件被读取"到"数据发送到了哪里"。这种"可追溯性"是安全事件的应急响应和取证调查的基础——没有审计，安全事件就是"黑箱"。

### 1.7 审计数据的存储与检索

审计产生的数据量可能极大——一个高频活动的 Agent 沙箱每秒可能产生数百个审计事件（每个 syscall、每个文件操作、每个网络连接）。如何存储和检索这些数据是审计系统的工程关键。

**存储策略**：
- **热数据**（最近 24-72 小时）——存储在内存或 SSD 中，支持实时查询和告警
- **温数据**（最近 7-30 天）——存储在对象存储中，支持按需查询
- **冷数据**（30 天以上）——压缩归档到冷存储，仅在安全取证时检索

**检索能力**：审计系统需要支持以下查询模式：
- **时间范围查询**——"昨天 14:00-16:00 之间沙箱 X 发生了什么"
- **事件类型过滤**——"沙箱 X 中所有被阻止的网络连接尝试"
- **进程追踪**——"沙箱 X 中 PID 42 的完整执行历史"
- **跨沙箱关联**——"同一时间段内哪些沙箱尝试连接了同一个外部 IP"

**与 Kubernetes 的集成**：在 K8s 环境中，审计数据通常通过 Prometheus + Grafana 做指标监控，通过 ELK/Loki 做日志存储和检索。Tetragon 和 Falco 都可以输出 Prometheus 指标和结构化日志——与 K8s 的监控生态无缝集成。GKE Agent Sandbox 的 PSI 指标也通过 kubelet 的 Summary API 暴露——可以在 Grafana 中可视化每个沙箱的资源压力趋势。

### 1.8 审计的隐私考量

审计可能记录敏感信息——如 Agent 处理的用户数据内容、API Key 值（如果出现在命令行参数中）、文件内容摘要。审计系统需要考虑隐私：

- **数据脱敏**——在审计日志中脱敏 API Key、密码等敏感字段
- **访问控制**——审计日志的访问需要严格的 RBAC——不是所有人都能查看
- **数据保留策略**——审计数据不应无限期保留——在满足合规要求的前提下定期清理

## 第 2 章 未来趋势

### 2.1 Confidential Containers——硬件加密隔离

**什么是 Confidential Containers**：Confidential Containers（CoCo）是一个 CNCF 项目——利用硬件 TEE（Trusted Execution Environment）加密 VM 的内存内容。即使宿主机管理员（或有物理访问权限的攻击者）也无法读取 Guest VM 的内存——因为内存被硬件加密。

**支持的硬件 TEE**：
- **AMD SEV-SNP**（Secure Encrypted Virtualization-Secure Nested Paging）——AMD 的 VM 内存加密技术
- **Intel TDX**（Trust Domain Extensions）——Intel 的 VM 内存加密技术
- **IBM Secure Execution**——IBM 的 VM 保护技术

**基于 Kata Containers**：CoCo 基于 Kata Containers 构建——Kata 的 VM 隔离加上 TEE 的内存加密，提供"即使基础设施提供商也不可信"的极端安全隔离。

**Agent 沙箱的价值**：对于"Agent 处理高度敏感数据"的场景（如金融分析 Agent、医疗数据 Agent），Confidential Containers 提供了"即使云提供商也被排除在信任边界之外"的隔离——云提供商无法读取 Agent 沙箱的内存，即使他们有物理访问权限。

**当前状态**：Azure AKS 2025 年提供了 Confidential Containers 的 public preview（基于 AMD SEV-SNP）。CoCo v0.15.0（2025-07）基于 Kata Containers 3.19.1。技术仍在早期阶段——硬件依赖（需要特定 CPU）、性能开销、生态成熟度都是限制因素。

**CoCo 的 Attestation 机制**：CoCo 不仅仅加密 VM 内存——它还提供"远程证明"（Remote Attestation）能力——让 Agent 沙箱的用户可以验证"我的沙箱确实运行在受保护的 TEE 中，且没有被篡改"。Attestation 通过 Trustee 组件提供——Trustee 生成一个密码学证据，证明 VM 的初始状态（如内核镜像的哈希、初始内存内容的哈希），用户可以验证这个证据以确保"沙箱的环境是我预期的，不是被云提供商篡改过的"。这种"可验证的隔离"对于"需要证明数据不会被基础设施提供商窥探"的合规场景（如 GDPR 数据跨境处理）有重要价值。

**CoCo 对 Agent 沙箱的独特价值**：在多租户 Agent 平台场景中，平台运营者可能需要"证明自己无法窥探用户的 Agent 数据"——传统的 VM 隔离做不到这一点（平台运营者有宿主机 root 权限，可以读取任何 VM 的内存）。CoCo 通过硬件加密让"即使有 root 权限也无法读取 VM 内存"——平台运营者可以据此向用户保证"我们技术上无法窥探你的 Agent 数据"。这种"技术保证"比"政策保证"（如"我们承诺不查看你的数据"）更有说服力——因为即使平台运营者想窥探，硬件 TEE 也会阻止。

### 2.2 WebAssembly Agent 沙箱

**WebAssembly 作为沙箱**：WebAssembly（Wasm）最初是为浏览器设计的"安全二进制指令格式"——它的设计自带沙箱特性：线性内存隔离、无系统调用（所有 I/O 通过宿主提供的 capabilities）、< 13ms 冷启动（AOT 预编译）。

**Agent 沙箱中的 Wasm 应用**：
- **Pyodide**——CPython 3.11 编译到 Wasm——在 Wasm 沙箱中运行 Python 代码
- **agent-sandbox**——80+ 内置 CLI 工具 + 完整 shell 解释器，< 13ms 冷启动
- **vital-agentbox**——Chromium + Pyodide 双层隔离

**Wasm vs 传统沙箱的优势**：
- **启动极快**——< 13ms 冷启动 vs Firecracker ~125ms vs 传统容器毫秒级但隔离弱
- **内存极低**——Wasm 运行时的内存开销远低于 VM
- **安全模型简洁**——Wasm 没有"系统调用"概念——所有 I/O 通过宿主提供的 capabilities，宿主可以精确控制"Wasm 代码能做什么"

**局限**：
- **兼容性**——Python 生态在 Wasm 中仍有限制（不是所有 C 扩展都能编译到 Wasm）
- **性能**——Wasm 的执行性能通常低于原生代码（虽然有 JIT，但不如 V8 那样成熟）
- **生态**——Wasm Agent 沙箱生态仍在建设初期——不如 E2B/Daytona/GKE 等成熟

**Wasm 与传统沙箱的哲学差异**：传统沙箱（容器/gVisor/MicroVM）的隔离思路是"给进程一个系统环境，然后限制它能做什么"——先给能力再限制。Wasm 的隔离思路是"给代码一个无系统调用的环境，然后按需提供能力"——先无能力再授予。这种"默认无能力"的模型与[[10 Egress 网络过滤——防止 Agent 泄漏的出站控制|第 10 篇]]讨论的"Default-Deny"哲学一致——Wasm 天然遵循"最小权限"原则，因为它的 I/O 完全依赖宿主提供的 capabilities。如果宿主不提供"网络访问"capability，Wasm 代码根本无法做网络请求——不需要 Egress 过滤，因为 Wasm 没有做网络请求的能力。

**NVIDIA 的 Wasm Agent 沙箱实践**：NVIDIA 在 2025 年发布了关于"用 Wasm 沙箱化 Agentic AI 工作流"的技术博客——探讨了用 Wasm 作为 Agent 代码执行沙箱的可行性。NVIDIA 的关注点在于"Agent 执行的 GPU 计算任务的安全隔离"——Wasm 的 capability 模型可以精确控制 Agent 代码能访问哪些 GPU 资源，而非像传统容器那样"要么全给要么全不给"。这种"细粒度 GPU capability 控制"是 Wasm 在 Agent 沙箱领域的独特优势——传统沙箱很难做"只允许 Agent 使用 GPU 的特定显存区域"，但 Wasm 的 capability 模型天然支持这种细粒度控制。

### 2.3 GKE Agent Substrate——超大规模编排

[[09 OpenHands Runtime 与通用执行平台|第 9 篇]]已经介绍了 GKE Agent Substrate 的基本概念——本文补充其未来方向的深度。

**Agent Substrate 解决什么问题**：当 Agent 数量从"数百"增长到"数万"甚至"数十万"时，传统的"每个 Agent 一个 Pod/VM"模型遇到了密度瓶颈——即使每个沙箱只占 5MB 内存，10 万个沙箱也需要 500GB——单台服务器无法容纳。Agent Substrate 通过"实时移入/移出计算容量"的编排模式——让 Agent 在"需要执行时"获得计算资源，在"空闲时"释放资源——同一基础设施上可以运行远超传统模型数量的 Agent。

**与 Serverless 的关系**：Agent Substrate 的"按需分配 + 即时释放"模式与 Serverless 计算的理念一致——但 Agent Substrate 是"Agent 级别的 Serverless"，而非"函数级别"。每个 Agent 是一个"长生命周期但有空闲期"的工作负载——Substrate 在 Agent 的活跃期分配资源，空闲期释放资源——在"Agent 体验"（不中断工作）和"资源效率"（不浪费空闲资源）之间取得平衡。

### 2.4 标准化方向

Agent 沙箱领域当前最大的"缺失"是标准化——每个平台定义自己的 API、SDK 和隔离后端。未来的标准化可能沿以下路径发展：

**路径一：Kubernetes agent-sandbox 标准**——`kubernetes-sigs/agent-sandbox` 控制器正在建立 K8s 原生的 Agent 沙箱标准。GKE Agent Sandbox 已基于此标准。如果 E2B/Daytona 等独立平台也提供兼容适配层，这个标准可能成为跨平台兼容的基础。

**路径二：OpenAI Agents SDK 沙箱接口成为事实标准**——Daytona 已原生支持 OpenAI Agents SDK 的沙箱接口。如果更多平台提供适配层，OpenAI 的接口可能成为"Agent 框架层面的沙箱标准"。

**路径三：OCI 式的开放沙箱规范**——社区可能发起一个类似 OCI（Open Container Initiative）的"开放沙箱接口"规范——定义沙箱创建、执行、销毁、快照的标准 API。但这需要多方达成共识，可能需要更长时间。

### 2.5 ActPlane——eBPF 信息流执行引擎

除了 Tetragon/Falco/AgentSight，eBPF 在 Agent 安全领域还有一个前沿应用——ActPlane，一个基于 eBPF 的信息流执行引擎。它的核心思想是"追踪数据在系统中的流动路径"——如"文件 A 的内容被读取→通过管道传递给进程 B→进程 B 把它发送到网络 C"。这种"信息流追踪"让安全团队可以回答"这个敏感数据是怎么从文件到达外部网络的"——而不仅仅是"有网络连接到了外部"。

**对 Agent 沙箱的价值**：在 Prompt Injection 攻击场景中，攻击链通常是"读取敏感文件→通过网络外传"。传统审计可能只看到"有文件读取"和"有网络连接"两个独立事件——难以关联。ActPlane 的信息流追踪可以把这两个事件关联为"文件 → 进程 → 网络"的完整流——明确展示数据外泄的完整路径。这种"端到端信息流追踪"是 Agent 沙箱审计的未来方向——从"孤立事件检测"到"完整攻击链重构"。

### 2.6 演进趋势的综合判断

综合以上前沿方向，Agent 沙箱技术的演进呈现以下趋势：

**趋势一：隔离边界从"软件"向"硬件"演进**。从 namespace（纯软件）→ gVisor（用户空间软件）→ Kata/Firecracker（硬件虚拟化）→ Confidential Containers（硬件加密虚拟化）——信任边界越来越"硬"，从"依赖软件正确性"到"依赖硬件物理特性"。

**趋势二：启动速度从"秒级"向"毫秒级"演进**。从传统 VM（秒级）→ Firecracker（~125ms）→ Wasm（< 13ms）——启动速度越来越快，让"每次请求创建新沙箱"的交互式场景越来越可行。

**趋势三：审计从"系统级"向"Agent 级"演进**。从 Falco/Tetragon（syscall/进程/网络级）→ AgentSight（Agent 工具调用级）→ ActPlane（信息流级）——审计粒度越来越贴近 Agent 的行为模式，从"检测系统异常"到"检测 Agent 异常"。

**趋势四：编排从"单沙箱"向"超大规模"演进**。从单个容器→ Kubernetes Pod→ GKE Agent Sandbox（warm/cold pool）→ Agent Substrate（实时移入移出计算容量）——编排能力支持越来越多的并发 Agent。

**趋势五：标准化从"碎片化"向"统一接口"演进**。从每个平台自定义 API→ Kubernetes agent-sandbox 标准→ 可能的 OpenAI Agents SDK 沙箱接口事实标准——Agent 沙箱接口正在走向统一。

### 3.2 核心认知总结

贯穿 12 篇文章的核心认知：

1. **传统容器对 AI 生成的不可信代码不安全**——共享宿主内核是根本问题，runc CVE 持续涌现证明了这一点。2025 年 11 月 runc 三连击（CVE-2025-31133/52565/52881）再次验证——容器逃逸不是历史问题，是持续威胁。

2. **三条更强隔离路线各有取舍**——gVisor（高密度/中等隔离/82% 兼容）、Kata（K8s 原生/强隔离/完整兼容）、Firecracker（极致轻量/强隔离/功能最少）。没有"最好的"——只有"最匹配约束的"。

3. **Agent 专用沙箱降低了采用门槛**——E2B/Daytona 把底层复杂性隐藏在 `Sandbox.create()` 之下。GKE Agent Sandbox 在 K8s 原生路线上实现了 16 倍增长和 75% 成本降低——证明"集成解决方案"的价值。

4. **Egress 过滤是 Agent 沙箱的必需**——Agent 的"正常网络能力"可能被恶意导向，Default-Deny + 白名单是唯一正确策略。Egress 过滤是 Prompt Injection 攻击的"最后防线"——即使 Agent 被诱导，数据也无法外泄到非白名单目标。

5. **Agent 特有风险不依赖内核漏洞**——Prompt Injection 利用的是"Agent 被诱导"而非"系统被攻破"。INJECAGENT 基准测试的 24% 攻击成功率说明这是一个现实威胁，不是理论可能。LLMSmith 研究的 20 个框架漏洞（19 个 RCE）说明即使沙箱隔离完善，框架自身的漏洞也可能被利用。

6. **纵深防御是唯一可靠策略**——五层不完美的隔离叠加（隔离边界 + 权限控制 + 网络过滤 + 行为监控 + 人在环路），每层捕获不同层面的攻击，单层被突破不等于全部失守。

7. **审计可观测是"事后的眼睛"**——Tetragon/Falco/AgentSight 的 eBPF 监控让安全事件可追溯——从"黑箱"到"完整攻击链重构"。没有审计，安全事件就是"不知道发生了什么"。

8. **未来从"容器隔离"向"硬件加密隔离"演进**——Confidential Containers 让"即使基础设施提供商也不可信"成为可能。Wasm 沙箱的 < 13ms 启动和"默认无能力"模型提供了另一种隔离思路。Agent Substrate 让超大规模 Agent 编排成为可能。

9. **标准化是下一个关键里程碑**——Agent 沙箱领域当前碎片化（E2B/Daytona/GKE 各有 API），未来需要类似 OCI 的开放标准让 Agent 代码与沙箱平台解耦。

10. **安全是"工程实践"而非"理论完美"**——没有完美的隔离方案，只有"多层不完美叠加接近足够安全"的工程实践。Agent 沙箱安全的本质不是"找到一个万能方案"，而是"在约束条件下选择最合适的组合，并持续迭代"。

## 思考题

1. **Confidential Containers 利用硬件 TEE 加密 VM 内存——即使宿主机管理员也无法读取。但对于 Agent 沙箱场景，威胁模型通常是"Agent 代码可能被 Prompt Injection 攻击"，而非"基础设施提供商不可信"。Confidential Containers 对 Agent 场景是否"过度设计"？什么场景下它真正必要？** 提示：考虑"数据敏感性"——如果 Agent 处理的是公开数据，CoCo 确实过度。但如果 Agent 处理金融交易、医疗记录等高度敏感数据，且运行在不可信的云基础设施上，CoCo 提供了"即使云提供商也无法窥探 Agent 数据"的保证——这在合规要求严格的行业（如金融、医疗）可能是必需的。

2. **WebAssembly 沙箱的 < 13ms 冷启动远快于 Firecracker 的 ~125ms。但 Wasm 的兼容性有限——不是所有 Python 包都能在 Wasm 中运行。这种"极速启动 vs 兼容性受限"的取舍对 Agent 场景意味着什么？什么类型的 Agent 适合 Wasm 沙箱？** 提示：考虑 Agent 的代码执行模式——如果 Agent 只执行简单的 Python 代码（标准库 + 少量纯 Python 包），Wasm 沙箱的极速启动是巨大优势。如果 Agent 需要使用大量 C 扩展包（如 numpy/pandas/torch），Wasm 的兼容性限制可能阻碍使用。

3. **本专栏 12 篇文章贯穿了一个核心认知——"没有完美的隔离方案，只有多层不完美隔离的叠加"。请回顾全文，选出你认为在 Agent 沙箱部署中"最不能省略"的三层防御，并解释为什么。** 提示：考虑"如果省略这一层，什么攻击会成功"——隔离边界（省略→内核漏洞逃逸）、Egress 过滤（省略→数据外泄）、权限控制（省略→危险系统调用）。行为监控和人在环路虽然重要，但在资源有限时可能被暂时省略——而前三层是"不可省略"的安全底线。
