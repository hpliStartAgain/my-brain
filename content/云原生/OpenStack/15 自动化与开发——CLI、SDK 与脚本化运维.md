# 15 自动化与开发——CLI、SDK 与脚本化运维

**摘要：**

当平台规模超过"一个人能记住所有实例名字"的程度，手工运维就到了极限——批量操作靠人肉点选必然出错，资源核对靠肉眼必然遗漏，故障响应靠记忆必然失灵。本文是本专栏的最后一篇，从运维开发的视角梳理 OpenStack 自动化的四个层次：CLI 的精要用法（输出格式化与 jq 配合）、OpenStackSDK 的 Python 开发（认证、资源操作、批量任务）、Ansible 与 Terraform 的基础设施即代码实践、以及 API 直调的排障技巧。每个层次都配真实场景的完整代码。最后讨论自动化的边界——什么不该自动化，以及为什么"能自动化的先自动化"不总是正确答案。

## 第 1 章 运维开发的定位——手工运维的极限在哪里

### 1.1 三个信号

手工运维的极限不是按实例数计算的，而是按三个信号判断的：

**信号一：同样的操作做了第三次。** 第一次是学习，第二次是确认，第三次就该写脚本了。譬如每月给新入职同事开测试机，第一次手工点选可以理解流程，第三次还在点选就是在浪费生命——而且第三次时你已经不会仔细看了，出错概率反而更高。

**信号二：核对类工作开始出现遗漏。** "所有实例都打标签了吗""每台主机的镜像版本一致吗"——这类全量核对工作，人眼的可靠性随清单长度急剧下降。十个实例能核对清楚，一百个实例必然遗漏。

**信号三：故障响应依赖特定的人。** 如果某些操作只有老张会做、只有老张知道在哪台机器上做，这个平台就与单点故障绑定了。自动化的另一个名字是"知识的产品化"——把脑子里的操作步骤变成任何人都能执行的脚本。

信号三的解药还有一个更轻量的形态：**操作文档化**。在自动化之前，先把操作步骤写成 runbook——runbook 让"只有老张会"变成"照着文档谁都能做"，它比脚本的开发成本低，且是脚本的前置材料（写 runbook 的过程就是梳理脚本逻辑的过程）。

三个信号的共同点是**重复与依赖**——重复产生自动化的需求，依赖产生自动化的紧迫性。判断一个操作值不值得自动化，可以用一个简单的算式：自动化成本（开发+维护）vs 手工成本（单次耗时 × 频次 × 出错概率 × 故障代价）。算下来划算就做，算不划算就先手工——不是所有操作都值得自动化，这个判断本身就是运维成熟度的体现。

还有一个反向信号值得警惕：**为自动化而自动化**。把一个每周一次、五分钟完成的手工操作自动化，开发两小时、维护成本每月半小时——这笔账怎么算都不划算。自动化的优先级排序应该按"节省的总时间"与"减少的出错概率"加权，而不是按"这个操作能不能自动化"。



### 1.2 运维开发与纯开发的区别

运维开发写的是脚本与工具，但它与业务开发有一个本质区别：**运维代码的执行频率低、容错要求高**。一个每天跑一次的巡检脚本，写两小时、跑一分钟，它的质量要求是"绝对不能误报、绝不能误操作"，而不是"性能最优"。这个区别决定了运维代码的设计取向：宁可啰嗦一点（显式的确认、详细的日志、保守的超时），也不要炫技。

运维代码的另一个特点是**生命周期长**。业务代码迭代快、废弃快，运维脚本一用就是三五年——三年后接手的同事要能看懂并安全修改它。所以运维代码的可读性优先级高于 cleverness：直白的循环好过炫技的推导式，显式的参数好过隐式的默认值，注释里写清楚"为什么这么做"比"做了什么"更重要。

还有一个容易忽略的维度：**运维代码也是攻击面**。脚本里硬编码的凭据、过宽的权限、不安全的临时文件，都会成为入侵路径。运维代码的安全要求（凭据管理、最小权限、日志脱敏）不比业务代码低——这一点在 02 篇的 conductor 案例里已经反复强调过。

运维代码的第三个特点是**与环境的耦合深**。业务代码的依赖是显式的（import 的库），运维代码的依赖是隐式的（CLI 的版本、API 的微版本、权限的配置）——环境一变，脚本就可能悄悄失效。所以运维脚本要有"环境自检"：启动时先验证依赖的命令存在、API 可达、权限够用，把环境问题在脚本开头就暴露出来。

### 1.3 本专栏知识在自动化中的位置

自动化脚本不是孤立的——它建立在专栏前面所有篇章的知识之上：写批量创建脚本要知道 flavor 与调度（04 篇），写网络核对要知道 Neutron 的对象模型（06 篇），写存储报表要知道 Cinder 的后端概念（08 篇），设计告警要知道指标分层（13 篇）。**自动化脚本的每一行，都是某篇原理知识的应用**。反过来说，写自动化脚本时遇到的"看不懂的报错"，往往暴露的是对应篇章的知识缺口——回去补原理，脚本自然就顺了。

本篇的组织也遵循这个逻辑：按"运维开发的四个层次"展开，每个层次给出工具、模式与真实场景，而不是 API 手册式的罗列——API 细节查官方文档即可，模式与取舍才是本篇的价值。

### 1.4 自动化的技术选型原则

本篇会覆盖四类工具（CLI、SDK、Ansible、API 直调），选型的判断标准只有两条：**任务的形态**与**团队的技能**。单次任务用 CLI，重复任务用脚本（SDK），资源集合管理用 IaC（Ansible/Terraform），排障用直调。团队会 Python 就用 SDK，会 Ansible 就用 collection——工具服务于人，而不是人迁就工具。

## 第 2 章 CLI 精要——openstack client 的正确打开方式

### 2.1 命令体系与帮助

openstack client 是统一的命令行入口，所有服务的命令都在 `openstack` 命名空间下。在它出现之前，每个服务有自己的客户端（nova、neutron、glance 命令），命令风格与认证方式各自为政——python-openstackclient（OSC）项目把这些统一成一个 `openstack` 命令，这个统一本身就是 OpenStack"松耦合服务"理念在客户端侧的补课。

OSC 的统一还体现在**插件机制**上：第三方服务（譬如某些存储或网络厂商的扩展）可以把自己的命令注册进 openstack 命令空间，用户的学习成本不增加。这个机制让 OSC 成了整个生态的统一门面——也是它取代各服务独立客户端的根本原因。

它的自省能力很强，两条命令解决大部分"怎么用"的问题：

OSC 的命令命名有一套稳定的语法：`openstack <资源> <动作>`——`server list`、`volume create`、`network show`。掌握这个语法后，没用过的命令也能猜出个大概：资源名词从服务来（server 是 Nova、volume 是 Cinder），动作从需求来（list/show/create/delete/set）。这种可预测性让"查文档"的频率大幅下降。



```bash
# 看某个命令的完整帮助（比搜索引擎快）
openstack server create --help

# 列出某个资源的所有子命令
openstack server --help | grep list
```

### 2.2 输出格式化——脚本化的第一要务

CLI 的默认输出是人读的表格，脚本化时必须切换到机器可读格式：

```bash
# 输出 JSON（脚本的标配）
openstack server list --format json

# 配合 jq 提取字段：列出所有实例的名字与状态
openstack server list --all-projects --format json | \
  jq -r '.[] | "\(.Name) \(.Status)"'

# 统计各状态的实例数
openstack server list --all-projects --format json | \
  jq 'group_by(.Status) | map({status: .[0].Status, count: length})'
```

`--format json` 加 `jq` 的组合是 OpenStack 自动化的瑞士军刀——大部分"批量核对""资源报表"的需求，一行管道就能解决。`-r` 参数（raw output）去掉 JSON 的引号，方便直接拼进 shell 变量。

CLI 还有一个常被忽略的参数组合：`--all-projects` 与 `--tag`。前者是 admin 视角的全量查询（巡检与报表的必备），后者按标签过滤（配合实例打标签的管理约定）。这两个参数的熟练使用，能把很多"要写脚本"的需求变成"一行命令"。



再补几个高频的 jq 管道：

```bash
# 找出所有 vCPU 超过 16 的规格
openstack flavor list --format json |   jq '[.[] | select(.VCPUs > 16) | .Name]'

# 统计各宿主机的实例数（调度倾斜检查）
openstack server list --all-projects --long --format json |   jq 'group_by(."OS-EXT-SRV-ATTR:host") | map({host: .[0]."OS-EXT-SRV-ATTR:host", count: length}) | sort_by(-.count)'

# 提取所有端点的 URL（健康检查的输入）
openstack endpoint list --format json |   jq -r '.[] | select(.Service Type == "compute") | .URL'
```

jq 的学习曲线大约半天，回报是终身受用——它不只服务于 OpenStack，所有输出 JSON 的工具（云厂商 CLI、Kubernetes 的 kubectl -o json）都适用。

jq 的另一个高频用法是**数据重组**——把 CLI 的输出转成另一种结构：

```bash
# 把实例列表转成 "名字: IP" 的映射（供其他脚本消费）
openstack server list --format json |   jq 'map({(.Name): .Networks}) | add'
```

数据重组类需求在工具链集成时特别常见——巡检脚本的输出要喂给告警系统、报表脚本的数据要进 Excel，中间的格式转换都是 jq 的主场。



### 2.3 --debug：排障的透视镜

`--debug` 参数会让 CLI 打印完整的 HTTP 请求与响应——包括 token 获取、API 调用的 URL、请求体、响应码。这个模式是排障的透视镜：CLI 报错"找不到资源"时，加上 `--debug` 重跑，能看到实际的请求 URL 与服务端的原始响应，是 404 还是 403 一目了然。

`--debug` 的另一个用途是**学习 API**：想用 SDK 或 curl 直调 API 时，先跑一遍 CLI 的 `--debug`，把请求抄下来改一改，比读 API 文档快得多。

**习惯二：对比法。** 同一个操作，CLI 成功而脚本失败时，用 CLI 的 `--debug` 抓下完整请求，与脚本的请求逐字段对比——差异点就是根因。90% 的差异是缺 header、少参数或微版本不对。



`--debug` 的输出里最有价值的三段：token 获取请求（看认证参数怎么传）、资源请求的 URL 与 query 参数（看分页与过滤怎么拼）、响应体（看返回的完整结构）。这三段抄下来，就是一份现成的 API 调用样例——比文档更贴近你的实际环境（版本、配置、端点都是你自己的）。

### 2.3 等待与轮询

CLI 的很多操作是异步的——创建实例返回 202 后要等状态变 ACTIVE。CLI 提供了 `--wait` 参数把异步变同步：

```bash
# 创建并等待完成（脚本里常用）
openstack server create --wait   --image ubuntu-22.04 --flavor m1.small   --network test-net demo-vm

# CLI 2.x 时代的 wait 子命令（老版本）
openstack server create ... && openstack server wait demo-vm
```

`--wait` 的轮询逻辑内置了超时与状态判断，比脚本里手写 while 循环可靠。但要注意它的超时时间——超大镜像的实例创建可能超过默认超时，脚本里要显式调大。

### 2.4 dry-run 与试运行

部分命令支持 `--dry-run`（或通过 `--preview`），不实际执行只显示将要做的动作。批量操作前先 dry-run 一遍，是"先看后做"纪律在 CLI 层的落地。没有 dry-run 支持的命令，可以用 `--debug` 模拟——看请求而不发请求。

dry-run 的价值在批量操作前尤其突出：批量删除 100 台实例前先 dry-run，确认筛选条件没有写错（多删或少删都在这一步暴露）。把 dry-run 纳入批量脚本的标准流程（先 dry-run 输出清单、人工过目、再真执行），是高危操作防呆的最低成本方案。



### 2.5 环境管理：openrc 与多集群

CLI 的认证靠环境变量（openrc 文件 source 进来），多集群环境的常见做法是为每个集群准备一份 openrc，用别名切换：

```bash
alias prod='source ~/openrc/prod.sh'
alias staging='source ~/openrc/staging.sh'
```

切换后先跑 `openstack catalog list` 确认连的是哪个集群——**在错误的集群上执行删除操作**是运维事故的经典来源，一个 2 秒的确认动作能避免一场灾难。

多集群环境还有一个进阶实践：**PS1 提示符染色**。把集群名注入 shell 提示符（prod 红色、staging 绿色），让"当前在哪个集群"始终可见——视觉的持续提醒比记忆可靠得多。这个技巧成本五分钟，防住的事故价值连城。

### 2.6 场景：批量核对

CLI 加 jq 的组合能覆盖大部分核对需求，几个常用的管道：

```bash
# 找出没有打特定标签的实例（漏打标的漏网之鱼）
openstack server list --all-projects --format json |   jq '[.[] | select(.Tags | length == 0)] | length'

# 找出分配在指定主机上的实例（维护前的影响面确认）
openstack server list --all-projects --format json |   jq '[.[] | select(."OS-EXT-SRV-ATTR:host" == "compute-03")] | length'

# 找出超过 90 天未更新的镜像
openstack image list --format json |   jq '[.[] | select(.UpdatedAt < "2026-06-01")] | length'
```

核对场景的要点是**把"人眼扫描"变成"jq 过滤"**——过滤条件一旦写成命令，就变成了可重复执行的巡检项。12 篇的巡检清单里有一半的项，都可以用 CLI 管道实现。

### 2.7 场景：安全组与配额管理

安全组的批量管理是另一个高频场景——新租户开通时的标准安全组模板下发：

```bash
# 创建安全组与规则（模板化）
openstack security group create web-sg --description "Web 前端标准组"
openstack security group rule create web-sg --proto tcp --dst-port 443 --remote-ip 0.0.0.0/0
openstack security group rule create web-sg --proto tcp --dst-port 22 --remote-ip 10.0.0.0/8
```

安全组模板化管理的价值在于**一致性**——手工建的安全组规则五花八门，模板化的安全组让"哪些端口对谁开放"有据可查。配额管理同理：`openstack quota set` 的批量下发配合模板，避免每个租户的配额五花八门。

模板化管理的进阶形态是**配置即代码**：安全组与配额的定义放在 YAML 文件里，变更走 review、执行走流水线——与 5 章的 IaC 理念一脉相承。模板化是 IaC 的雏形，两者之间没有鸿沟，只有成熟度的差异。



安全组与配额的模板化管理还有一个进阶形态：**自助服务门户**——把模板化的操作包装成表单，让业务方自助申请、自动下发。这是自动化向平台化演进的中间形态（本篇末尾会展开），它的技术基础就是本节讨论的 CLI 与脚本。



### 2.8 场景：日志与审计的 CLI 用法

OpenStack 的操作审计（谁在什么时候做了什么）可以通过 API 查询（各服务的 events 接口），CLI 层面最常用的是 `openstack server show --diagnostics`（实例的诊断信息）与各服务的日志。审计类需求的 CLI 用法要点是 `--long` 与时间过滤——`openstack server list --long` 带出宿主机与镜像信息，配合时间过滤能回答"最近谁改了什么"类的问题。

审计数据的留存策略要与合规要求对齐——安全事件回溯时，"操作记录只保留了 7 天"是很多团队的痛。

## 第 3 章 OpenStackSDK——Python 世界的正规军

### 3.1 连接与认证

OpenStackSDK（`openstacksdk` 包）是官方推荐的 Python 库，它把认证、服务发现、API 调用封装成统一的连接对象：

```python
import openstack

# 方式一：使用环境变量（source openrc 后）
conn = openstack.connect()

# 方式二：显式传参（适合脚本内嵌凭据的场景）
conn = openstack.connect(
    auth_url="https://cloud.example.com:5000/v3",
    project_name="prod",
    username="ops-bot",
    password="***",
    user_domain_name="Default",
    project_domain_name="Default",
)

# 验证连接
print(conn.compute.servers())
```

认证细节上最容易踩的坑是**域（domain）**：用户与项目各有一个 domain，只配一个会报 401。另一个坑是**区域（region）**：多 region 部署时，`conn` 对象默认连 region_one，其他 region 的资源要用 `conn.region_name` 切换。

SDK 的连接对象是线程安全的（多线程可以共享同一个 conn），这为批量操作的并发化提供了基础——3.3 节的并发批量操作就依赖这个特性。

SDK 的版本兼容性也要留意：openstacksdk 的版本决定了它支持的 OpenStack 服务版本范围，升级 OpenStack 后要同步检查 SDK 的支持矩阵——监控脚本因为 SDK 不支持新 API 而静默失败，是升级后监控失明的常见原因（与 13 篇的 exporter 版本管理呼应）。

认证方式的选择也有讲究：交互式脚本用 openrc 环境变量（凭据不进代码），定时任务用应用凭据（application credential，独立于人员账号、可单独吊销），CI 流水线用受限角色的专用账号。三种方式的共同原则是**凭据与用途匹配**——巡检脚本不该拿着 admin 全权限的账号跑，这是最小权限原则在自动化场景的落地。

### 3.2 资源操作的统一模式

SDK 的资源操作遵循统一模式：`conn.<服务>.<动作>`，配合迭代器与生成器：

```python
# 列出所有运行中的实例（自动分页）
for server in conn.compute.servers(all_projects=True):
    if server.status == "ACTIVE":
        print(server.name, server.compute_host)

# 创建实例（最小参数集）
server = conn.compute.create_server(
    name="demo-vm",
    image_id=" <image-uuid>",
    flavor_id="<flavor-uuid>",
    networks=[{"uuid": "<network-uuid>"}],
)

# 等待实例就绪（SDK 内置轮询）
server = conn.compute.wait_for_server(server, timeout=600)
```

`wait_for_server` 这类内置等待方法值得专门一提——它们封装了轮询与状态判断，比自己写 while 循环可靠得多。自己写轮询的常见错误是轮询间隔太短（打爆 API）或超时处理缺失（脚本挂死）。

SDK 的资源对象还有一个特性：**懒加载与属性访问**。`server.compute_host` 这类属性在列表接口里可能没有（列表接口返回的是摘要），SDK 会在访问时自动补一次详情查询——方便但隐藏了 N+1 查询的风险。批量处理时用 `list` 接口的 `detail` 变体一次拿全，比逐个访问属性快一个数量级。

SDK 的资源对象还有 `to_dict()` 方法，把对象转成纯字典——调试时打印对象状态、把数据写入 JSON 报表，都用得上。调试 SDK 脚本的另一个技巧是开启 SDK 的日志（`openstack.enable_logging(debug=True)`），能看到底层的 HTTP 交互——与 CLI 的 --debug 异曲同工。

### 3.3 批量操作与并发

SDK 的操作默认串行，批量任务可以用线程池并发（注意 API 的限流——并发 10 以上容易触发 429）。并发度的经验值：读操作 10-20 并发，写操作 3-5 并发。并发写操作还要考虑服务端的顺序依赖——譬如批量创建实例时，同一网络的端口创建可能有竞态，并发度要保守。

并发还有一个隐藏收益：**它逼你把错误处理写对**。串行脚本的错误处理可以偷懒（失败就退出），并发脚本的错误必须逐个收集——这个"被迫"往往能让脚本的健壮性上一个台阶。

并发脚本的错误处理也要升级：串行脚本一个失败可以继续下一个，并发脚本要用线程安全的收集器（或队列）汇总结果，避免多个线程写同一个列表导致丢结果。Python 的 `concurrent.futures` 配合 `as_completed` 是标准写法——每个 future 的结果与异常都要收集，不能只取成功的。

### 3.2 异常处理与重试

SDK 的异常体系值得了解：`openstack.exceptions.ResourceNotFound`（资源不存在）、`Conflict`（状态冲突，譬如重复创建）、`Forbidden`（权限不足）。批量脚本的标准异常处理模式：

```python
import openstack
from openstack import exceptions

conn = openstack.connect()
results = {"ok": [], "skip": [], "fail": []}

for name in target_names:
    try:
        if conn.compute.find_server(name):
            results["skip"].append(name)
            continue
        conn.compute.create_server(name=name, ...)
        results["ok"].append(name)
    except exceptions.ConflictException:
        results["skip"].append(name)   # 并发冲突，视为已存在
    except exceptions.ForbiddenException as e:
        results["fail"].append((name, "权限不足，跳过后续"))
        break   # 权限问题不会自愈，停止批量
    except Exception as e:
        results["fail"].append((name, str(e)))
```

异常分类的要点是**区分"可重试"与"不可重试"**：网络超时可以重试，权限不足重试一百次也是 403。批量脚本遇到不可重试的异常应当立即停止或跳过同类操作，而不是把失败重复 N 遍。

### 3.3 分页与全量遍历

SDK 的列表方法默认自动分页（`servers()` 方法内部处理 marker），但要注意 `all_projects=True` 的权限要求——没有 admin 权限时只能看到自己项目的资源。全量遍历大集群（数千实例）时，SDK 的分页是惰性的（按需取下一页），内存占用可控；但如果在遍历中逐个实例再查详情，就是 N+1 查询问题——详情字段尽量在列表接口一次拿全。

### 3.4 镜像与卷的 SDK 操作

镜像与卷的操作模式与实例一致，几个高频片段：

```python
# 上传镜像（从本地文件）
image = conn.image.upload_image(
    name="ubuntu-22.04-custom",
    filename="/tmp/ubuntu.qcow2",
    disk_format="qcow2",
)

# 给镜像打属性（调度依赖这些属性）
conn.image.update_image(image.id, **{
    "hw_qemu_guest_agent": "yes",
    "os_distro": "ubuntu",
})

# 创建卷（从镜像）
volume = conn.block_volume.create(
    name="data-vol-01",
    size=100,
    volume_type="ceph-cephfs",   # 卷类型决定后端
)

# 卷挂载到实例
conn.compute.create_volume_attachment(server.id, volume_id=volume.id)
```

SDK 方法名的规律值得掌握：`find_*`（按名或 ID 查找，找不到抛异常或返回 None）、`get_*`（精确获取）、`create_/update_/delete_`（增删改）。掌握了规律，没查过文档的方法也能猜个八九不离十——SDK 的 API 设计是自洽的。

SDK 还有一个调试利器：`conn.compute.get_server_by_id()` 这类方法失败时的异常信息里带有完整的请求 URL 与响应——与 CLI 的 --debug 异曲同工。遇到 SDK 的行为不符合预期时，先看异常详情，再决定是查文档还是抓包。



### 3.5 脚本的凭据管理

SDK 脚本的凭据管理有三条纪律：**凭据不进代码库**（用环境变量或独立的凭据文件，.gitignore 掉）、**凭据最小权限**（巡检脚本用只读账号，批量操作账号按需授权）、**凭据定期轮换**（与 14 篇的证书案例呼应——轮换要全量下发并验证）。脚本凭据的泄露后果比个人凭据更严重，因为它通常权限更大、生命周期更长。

凭据管理的工程化方案是**应用凭据（application credential）**：为每个脚本创建独立的应用凭据，权限按需分配、可单独吊销、不依赖人员账号。脚本与人员凭据分离后，人员离职、换岗都不影响自动化脚本的运行——这也是 02 篇 Keystone 篇里应用凭据机制的落地场景。

## 第 4 章 脚本化运维实战

### 4.1 场景一：批量创建测试机

新项目要 20 台测试机，手工点选 20 遍不可接受。脚本要点：参数化（名字、规格、网络从配置读）、幂等（已存在的跳过）、汇总输出。先看配置文件的设计——把资源描述从代码里分离出来，改需求时不用改代码：

```yaml
# test-vms.yaml
vms:
  - name: test-vm-01
    image: ubuntu-22.04
    flavor: m1.small
    network: test-net
  - name: test-vm-02
    image: ubuntu-22.04
    flavor: m1.small
    network: test-net
```

```python
import openstack, yaml

conn = openstack.connect()
config = yaml.safe_load(open("test-vms.yaml"))

created, skipped = [], []
for spec in config["vms"]:
    name = spec["name"]
    if conn.compute.find_server(name):
        skipped.append(name)   # 幂等：已存在就跳过
        continue
    server = conn.compute.create_server(
        name=name,
        image_id=conn.image.find_image(spec["image"]).id,
        flavor_id=conn.compute.find_flavor(spec["flavor"]).id,
        networks=[{"uuid": spec["network"]}],
    )
    created.append(name)

print(f"创建 {len(created)} 台: {created}")
print(f"跳过 {len(skipped)} 台: {skipped}")
```

幂等设计是批量脚本的核心——脚本可以安全地重跑，重跑不会产生重复资源。这个特性在脚本中途失败需要重跑时尤其重要。

幂等的实现手段有三种：按名字查存在性（本例的 `find_server`）、用固定 UUID（自己生成 UUID 而不是让系统生成）、用外部记账（把已创建的资源记在本地清单）。三种手段的取舍按场景定：名字唯一性有保障时用查存在性，跨系统对账时用外部记账。

批量创建还有一个容易忽略的依赖处理：实例的网络、镜像、规格的 UUID 要先解析好（`find_image`/`find_flavor`/`find_network`），解析失败的项要在创建前就剔除并报告——让 20 台实例因为一个错误的镜像名整体失败，是脚本设计的问题，不是用户的问题。



批量创建还有一个工程细节：**创建后的等待**。20 台实例的创建请求发出后，它们是并行 build 的，脚本要在"全部就绪"后才能通知用户。SDK 的 `wait_for_server` 是逐台等待，20 台串行等待会拉长总时长——更好的做法是先全部发起创建，再统一轮询状态：

```python
servers = [conn.compute.create_server(**spec) for spec in specs]
# 全部发起后再统一等待（SDK 的 wait 支持并发轮询）
for s in servers:
    conn.compute.wait_for_server(s, timeout=900)
```

发起与等待分离的模式，把总时长从"20 × 单台时长"压缩到接近"单台时长"——批量操作的并行化是自动化最直接的收益。

批量创建还要考虑**失败的部分回滚**：20 台里 5 台创建失败，成功的 15 台要保留还是全部回滚？答案取决于业务语义——测试机场景保留即可，计费场景可能要全退。脚本要有明确的回滚策略参数，而不是让业务方在故障现场决定。

每月的资源使用报表（各租户的实例数、vCPU、内存、卷容量）是容量规划与计费分摊的输入。这个场景的工程要点是**数据口径的确定性**：报表要说明"统计的是 ACTIVE 状态还是包含 SHUTOFF""时间点还是时间段"——口径不清的报表，业务方与运维各说各话。

报表脚本还有一个进阶方向：**与配额数据交叉**——使用量与配额的比值（使用率）比绝对值更有管理价值。配额数据从 `openstack quota show` 类接口拿，与使用量做除法，产出"租户资源使用率"报表——它是容量规划与配额调整的决策输入。



报表的生成频率也有讲究：月度报表用"月末快照"口径（当月最后一天的状态），趋势分析用"每日快照"口径——两种口径的数字会不同（月中创建又删除的实例只在每日口径里出现），报表要标注口径避免误读。



报表脚本的另一个工程要点是**输出的稳定性**：列名、顺序、格式固定，下游（Excel 透视表、计费系统）才能稳定消费。报表格式的随意变更，是报表类脚本最常见的"软故障"——脚本没坏，但下游解析坏了。

import openstack
from collections import defaultdict

conn = openstack.connect()
usage = defaultdict(lambda: {"vms": 0, "vcpu": 0, "mem": 0})

for server in conn.compute.servers(all_projects=True):

```python
flavors = {f.id: f for f in conn.compute.flavors()}   # 一次拉全
for server in conn.compute.servers(all_projects=True):
    flavor = flavors.get(server.flavor.id)   # 本地查表，零 API 调用
```

### 4.3 场景三：巡检脚本

巡检脚本的模式在 13 篇已经给出骨架，这里补充与 SDK 的结合：巡检项用 SDK 实现（比 CLI 调用更快、错误处理更细），结果统一进结构化输出。巡检脚本与批量操作脚本的工程要求一致：幂等、可重跑、异常不中断整体。

巡检脚本的一个设计原则是**检查项与处置分离**：脚本只负责"发现与报告"，处置动作（重启服务、清理资源）由人确认后执行或由独立的处置脚本执行。检查与处置混在一个脚本里，脚本 bug 就会直接作用于生产资源——13 篇的"巡检与监控互补"说的也是这个分工。



巡检脚本与批量操作脚本的工程要求一致：幂等、可重跑、异常不中断整体。巡检脚本的特殊要求是**输出结构化**——每项检查的结果（名称、是否异常、详情）进统一的结构，日报生成与告警推送都从结构化结果派生。巡检项的增删是常态，好的结构让增删变成加一行检查函数。

巡检脚本与 13 篇的监控告警的分工再强调一次：巡检发现的是"账实关系"（孤儿资源、配置漂移），监控发现的是"实时状态"（延迟、水位）。两者有少量重叠，但各自的独有领域都不可替代——巡检的账实核对，监控永远做不了。



三个场景的共同工程纪律：**凭据与代码分离**（连接参数从环境变量或配置文件读，不硬编码）、**日志完整**（每个动作有记录，出问题能回溯）、**失败可感知**（脚本失败要有通知，静默失败比失败更糟）。

### 4.4 场景四：批量配置变更

给 50 台实例统一加一个 metadata、给一批安全组补一条规则——批量配置变更的脚本模式与批量创建一致，但多一个**变更前快照**：把变更前的配置导出存档，变更后对比验证。配置变更的回滚依赖快照，没有快照的回滚是凭记忆的回滚。

```python
# 变更前快照
before = {s.id: dict(s.metadata) for s in conn.compute.servers(all_projects=True)}
json.dump(before, open(f"metadata-snapshot-{date}.json", "w"))

# 批量变更（带确认）
for s in targets:
    conn.compute.set_server_metadata(s, **{"backup-policy": "weekly"})
```

批量配置变更的另一个纪律是**分批执行**：50 台分 5 批，每批之间抽查验证——批量脚本的 bug 影响面与批量大小成正比，分批是把"50 台全错"变成"10 台错"的保险丝。

批量变更的脚本还要处理**部分失败的中断语义**：第 3 台失败后，第 4-50 台还继续吗？答案取决于变更的原子性需求——如果 50 台是一个整体（譬如同一套服务的集群），部分失败就该停止并回滚；如果相互独立（譬如给不同租户的实例打标签），继续执行并汇总失败项更好。脚本要把这个语义做成参数，而不是写死。

### 4.5 场景五：与监控联动的自动化

13 篇的巡检脚本发现异常后，可以联动自动化脚本做初步处置——譬如发现某主机实例全失联，自动收集该主机的诊断信息（virsh list、日志尾部、dmesg）并附在告警里。这种"发现即取证"的联动，能把故障响应的取证时间从分钟级压到秒级。

联动的实现要点是**处置与取证分离**：取证是只读的、安全的，可以全自动；处置是写操作，必须过人工确认。混在一起的联动脚本，会在半夜自动重启你不想重启的服务。

批量变更还有一个纪律：**变更前通知受影响的业务方**。metadata 变更通常无感，但某些属性（譬如挂载卷的设备名约定）的变更会影响业务脚本。通知的内容要具体（哪些实例、什么变更、什么时间），泛泛的"今晚要变更"等于没通知。

## 第 5 章 Ansible 与基础设施即代码

### 5.1 openstack.cloud collection

Ansible 与 Terraform 是基础设施即代码（IaC）的两条主流路线，它们与前面章节的 CLI/SDK 脚本不是竞争关系，而是抽象层次的递进：脚本解决"单个任务的自动化"，IaC 解决"资源集合的声明式管理"。

IaC 的核心承诺是**环境的可重现**——测试环境与生产环境的差异收敛到变量文件，环境的重建从"三天的人工配置"变成"一次 playbook 执行"。这个承诺的兑现前提是"所有变更走代码"——只要有一个手工变更溜进去，可重现性就破了。



Ansible 的 `openstack.cloud` collection 提供了声明式的资源管理模块——用 YAML 描述期望状态，由 Ansible 负责达成。先看一个最小例子：

```yaml
- name: 确保测试机存在
  hosts: localhost
  tasks:
    - name: 创建实例
      openstack.cloud.server:
        name: "demo-{{ item }}"
        image: "ubuntu-22.04"
        flavor: "m1.small"
        network: "test-net"
        state: present
      loop: "{{ range(1, 21) | list }}"
```

声明式的价值在**幂等与漂移检测**：同一份 playbook 跑一百遍，结果都是"期望状态"，重复执行不会产生重复资源。这与手写脚本的幂等设计目标一致，但 Ansible 把幂等的实现细节（检查存在性、比较差异）内置了。

声明式的另一个优势是**可审查性**：YAML 文件里的资源清单可以被人工审阅、被 diff 比较、被合规工具扫描——"这个环境到底有哪些资源"的问题，答案就在代码库里，而不是散落在界面的各个角落。

Ansible 的模块覆盖了 OpenStack 的主要资源（server、volume、network、security group、keypair），模块的参数与 API 参数一一对应——会 API 就会写 playbook。Ansible 相比手写脚本的优势还有**变量与模板**：不同环境（测试/生产）的差异收敛到变量文件，playbook 本身环境无关。

Ansible 的幂等性由模块实现——`openstack.cloud.server` 模块会先查目标实例是否存在、配置是否一致，只在有差异时才动手。这个"检查-差异-执行"的三段式是所有声明式工具的内核，理解了它，就能理解为什么声明式工具天然适合"配置管理"场景（要的是终态），而命令式脚本适合"动作编排"场景（要的是过程）。



Ansible 的 OpenStack 模块底层用的就是 openstacksdk——所以 SDK 的认证方式（openrc 或显式参数）在 Ansible 里同样适用，两套工具可以共享同一份凭据管理方案。这个细节让"脚本与 IaC 混用"的团队至少在凭据管理上是统一的。

### 5.2 与 Terraform 的取舍

Terraform 的 openstack provider 也能做同样的事，两者的取舍在于状态管理：Ansible 无状态（每次执行现查现比），Terraform 有状态文件（记录"我管理了什么"）。资源少、变更简单时 Ansible 足够；资源多、依赖复杂（VPC、子网、实例、卷的依赖图）时 Terraform 的依赖图与漂移检测更可靠。笔者的建议是：**团队里谁熟悉用哪个，两者混用是大忌**——同一批资源被两套工具管理，状态必然打架。

Terraform 的 state 文件管理是它特有的运维点：state 记录了"Terraform 认为自己管理着什么"，state 丢失或损坏的恢复成本很高（要从头 import）。state 的备份与加锁（防止并发 apply）是 Terraform 团队的必修课——这些运维成本在选型时就要算进去。

IaC 的实践还有一条纪律值得强调：**代码库即真相源**。资源的手工变更（有人在界面上点了个配置）会造成"代码与现实的漂移"，漂移的发现靠定期 plan（Terraform）或 check 模式（Ansible 的 --check），漂移的处置要么回滚手工变更、要么把变更写回代码——总之代码库要重新成为唯一真相。漂移不治理，IaC 就退化成"一份过时的文档"。

### 5.3 自动化代码的工程化

无论是 Ansible playbook 还是 Python 脚本，自动化代码都应当进版本库、走 review、有测试。测试的形式可以很轻：`--check` 模式的干跑、测试环境的全流程执行、关键脚本的单元测试（对纯函数部分）。自动化代码的 bug 的后果是"批量地错误操作生产资源"——它的测试要求不比业务代码低。

测试的形式按脚本类型选：纯函数逻辑（数据处理、格式转换）用单元测试；涉及真实 API 的部分用测试环境的全流程执行；Ansible playbook 用 --check 干跑。三种测试的投入产出比依次降低，按脚本的风险等级选——操作生产资源的脚本，测试环境的全流程执行不可省。

自动化代码的工程化还有一个实践：**变更的灰度**。与 12 篇的配置变更灰度同理，IaC 的变更先在一个测试 project 上执行，验证后再推全量——"全量直推"的 IaC 变更，等价于把所有资源同时暴露给同一个 bug。

### 5.4 从脚本到平台的演进

运维自动化的终点是自服务平台：用户自己填表单开机器、自己调配额、自己看成本——运维从"操作员"变成"平台开发者"。这个演进的技术栈就是本篇内容的组合：SDK 做后端、表单做前端、配额与审批做控制点。但平台化是自动化成熟后的自然演进，不是一步到位的起点——先有可靠的脚本，才有可靠的平台。

## 第 6 章 API 直调与排障

### 6.1 三步拿到 token

SDK 与 CLI 封装了认证，但排障时经常需要直调 API（譬如复现一个 SDK 报错的原始请求、调用 SDK 尚未封装的新接口、或者只是想看清楚"CLI 到底做了什么"）。直调的第一步是拿 token：

```bash
# 从 openrc 环境获取 token
unset OS_AUTH_TOKEN
TOKEN=$(openstack token issue -f value -c id)

# 用 token 调 API
curl -s -H "X-Auth-Token: $TOKEN" \
  https://cloud.example.com:8774/v2.1/servers?limit=1 | python3 -m json.tool
```

`python3 -m json.tool` 是 curl 的黄金搭档——把压缩的 JSON 响应格式化缩进，人眼可读。这个组合在 API 排障时的出场率极高：看响应结构、确认字段名、检查错误信息，全靠它。



### 6.2 API 排障的三个习惯

token 拿到后先验证有效性（`openstack token show` 能看到过期时间与角色），排障时"token 过期"与"权限不足"的表现都是 401/403，先排除 token 问题能省一轮排查。

token 的传递方式也有讲究：环境变量优于命令行参数（不进 history），临时文件优于环境变量（多脚本共享）。无论哪种方式，脚本结束时清理凭据是好习惯——凭据的暴露面每少一寸，安全的边界就多一寸。

Fernet token 的默认有效期是 1 小时（02 篇讲过 token 风暴与有效期权衡），长脚本要注意 token 的中途刷新——SDK 会自动刷新，手写 curl 的脚本要自己处理。脚本跑一半 token 过期的症状是"前半成功后半 401"，看到这个模式直接查 token 有效期。



**习惯一：先看服务目录。** 不确定某资源的 API 路径时，`openstack catalog list` 列出所有服务的 endpoint，路径规律一目了然（compute 在 8774、volume 在 8776、network 在 9696）。

服务目录还能回答"这个集群部署了哪些服务"——没有部署的服务不会有 endpoint。新接手一个 OpenStack 环境时，`openstack catalog list` 是了解"这个环境有什么"的第一条命令，比翻配置文件快得多。

**习惯二：对比法。** 同一个操作，CLI 成功而脚本失败时，用 CLI 的 `--debug` 抓下完整请求，与脚本的请求逐字段对比——差异点就是根因。90% 的差异是缺 header、少参数或微版本不对。

API 排障还有一个进阶技巧：**用 OpenStack 的 API 校验端点**。各服务的 `/v2.1`（或对应版本路径）根路径会返回 API 的版本与能力信息，不带 token 也能访问——它是"服务活着且版本正确"的最轻量探针，13 篇的黑盒探活用的就是它。



**习惯三：错误信息要读全。** OpenStack 的 API 错误响应通常带 `message` 字段，里面的信息比 HTTP 状态码丰富得多——403 的 message 会告诉你具体缺哪个角色的哪个权限。

API 排障还有一个利器：**对比成功与失败的请求**。同样的操作，CLI 成功而 curl 失败时，把两者的请求头与请求体逐字段对比——差异点就是根因。这个方法笨但有效，因为它不依赖任何假设，只依赖事实。

---

直调 API 还有一个高频场景：**验证服务目录与端点健康**。13 篇的监控探针、12 篇的巡检脚本，本质上都是 API 直调——`curl` 各服务的 endpoint 并校验返回。这类探针的写法要点是超时控制（`curl -m 5`，不给探针无限等待）与返回码校验（只看 HTTP 200 不够，还要解析响应体确认服务逻辑正常）。

API 直调的进阶用法是**微版本控制**：请求头带 `X-OpenStack-Nova-API-Version: 2.X` 可以精确控制行为（04 篇讲过微版本的兼容机制）。脚本固定微版本号是跨版本兼容的最佳实践。

### 6.3 直调 API 的安全注意

直调 API 的脚本要特别注意 token 的处理：token 不进日志（日志里的 token 要脱敏）、不进命令历史（用环境变量传递而不是命令行参数——命令行参数会进 shell history）。token 泄露的后果与密码泄露等同，而它的有效期短反而容易让人放松警惕。

直调 API 的脚本还要处理**分页**：OpenStack 的列表 API 默认返回 1000 条（limit 参数可调），超过部分要用 marker 参数翻页。SDK 的列表方法自动处理分页，手写 curl 的脚本要自己处理——漏掉分页的脚本会"看起来正常但数据不全"，这类 bug 比报错的更危险。

---

举一个 API 直调排障的实例：SDK 报 `Conflict` 但信息不详。用 CLI 的 `--debug` 复现同样的操作，看到完整响应体：

```json
{"error": {"code": 409, "message": "Virtual Machine port ... can not be directly attached ..."}}
```

完整的 message 说明是"端口已被其他实例占用"——SDK 的异常类只给了 Conflict，响应体给出了具体原因。这个对比说明：**SDK 的异常是给人看的摘要，API 响应是给机器看的全文**，排障时永远要看全文。

## 第 7 章 自动化的边界——什么不该自动化

### 7.1 三类不该自动化的操作

自动化的边界讨论，本质是"机器擅长什么、人擅长什么"的分工问题。机器擅长重复、精确、不知疲倦；人擅长判断、权衡、处理意外。自动化的边界就画在这条线上——机器做的事要"规则明确、结果可验证"，超出这个范围的操作，自动化的风险会超过收益。



自动化是方向，但不是所有操作都该自动化。三类操作建议保留人工：

**不可逆的破坏性操作**：删除卷、清理数据库、强制下电。自动化可以做"预检查与审批流"，但最终扳机留在人手里——13 篇讨论过的 safe-to-destroy 流程就是这个思路。

破坏性操作的自动化还有一个折中形态：**"自动化预检 + 人工确认"的两段式**。脚本负责收集信息（这个卷被谁用着、删除会影响什么）、生成命令、等待确认；人负责看一眼确认信息、按回车。两段式把"收集信息"的重复劳动自动化了，把"按下扳机"的判断留给了人。



**涉及计费与配额的操作**：给租户调配额、开通特权资源——这些操作的影响是商业性的而非技术性的，自动化可以做流程（工单流转、审批记录），但决策要留给人。

破坏性操作的自动化有一个折中形态：**"自动化预检 + 人工确认"的两段式**。脚本负责收集信息（这个卷被谁用着、删除会影响什么）、生成命令、等待确认；人负责看一眼确认信息、按回车。两段式把"收集信息"的重复劳动自动化了，把"按下扳机"的判断留给了人——14 篇的 safe-to-destroy 流程就是这个模式的实例。

**低频且高变的操作**：一年做一次、每次步骤都不同的操作，自动化的开发成本高于执行成本，而且脚本因为没有重复使用而得不到验证，反而成为隐患。

**需要业务判断的操作**：扩容多少、给谁扩、什么时候扩——这些决策依赖业务上下文，自动化可以准备数据（容量报告），但决策本身不该交给脚本。

三类之外的灰色地带也值得讨论：**低频但关键的容灾切换**。主备切换的自动化（Masakari 类方案）能显著缩短故障恢复时间，但自动切换的误触发（譬如网络抖动被误判为主机宕机）会造成脑裂。笔者的建议是：切换的"检测"自动化、"执行"半自动——系统自动准备好切换动作，人按确认键。这个"半自动"模式在 05 篇的 evacuate 讨论中也出现过：自动化负责快，人负责对。

### 7.2 自动化的成熟度模型

### 7.2 自动化的成熟度模型

运维自动化的演进可以分四步：**手工操作**（一切靠人）→ **脚本化**（单点操作自动化）→ **编排化**（多步骤任务一键执行）→ **自愈化**（异常自动处置）。每一步都要踩实——跳过脚本化直接做编排的团队，编排里的每个步骤都是没验证过的黑盒。本篇的 CLI、SDK、Ansible 分别对应前三步的工具，自愈化则建立在前面三步全部可靠的前提上。

成熟度模型还有一个常被忽略的维度：**自动化的可观测性**。自动化脚本自己也是"系统的一部分"——它什么时候跑了、做了什么、成功了没有，这些信息要进监控与日志（13 篇的巡检心跳就是例子）。没有可观测性的自动化，故障时是"看不见的变量"，会让排障复杂度翻倍。

成熟度模型还有一个隐含的次序：**先自动化"读"，再自动化"写"**。读操作（巡检、报表、核对）失败的成本低，适合先行；写操作（创建、修改、删除）失败的成本高，要在读操作积累了足够的信任后再逐步放开。13 篇的监控（读）先于 12 篇的 SOP（写），也是同一个次序。

成熟度模型的每一步都有对应的失败形态：脚本化的失败是"脚本腐烂"（没人维护、跑不通），编排化的失败是"编排黑盒"（没人知道编排里做了什么），自愈化的失败是"自愈变自杀"（错误的自动处置放大故障）。每一步的失败形态都提示了该阶段的建设重点：脚本化要配文档，编排化要配测试，自愈化要配熔断。

自愈化的准入条件可以参考 13 篇的告警分级：P2 级的趋势问题适合自动处置（譬如自动清理孤儿资源），P0 级的故障保留人工决策——自愈的边界，就是"误处置的代价"与"响应速度收益"的权衡线。



### 7.3 自动化的文档化

自动化代码的最后一公里是文档：脚本的用途、参数、依赖、执行频率、失败时的处置——这些信息不写下来，三个月后连作者自己都要重新读代码。文档的最好形态是"代码旁边的一屏说明"：用途一句话、参数表、执行示例、失败处置。文档与代码同库同 review，才能不腐烂。

自动化文档的最后一个建议是**失败案例也要记**：脚本曾经怎么失败过、当时怎么修的——失败案例的价值不亚于成功案例，它们是"已知的坑"清单，能防止后人重蹈覆辙。



自动化文档的最小模板：一句话用途、参数说明、执行示例、失败处置、负责人。五项俱全的文档，配合版本库的变更历史，就是自动化代码的完整档案。文档的更新时机绑定在代码变更的同一个 commit 里——代码与文档不同步的根因，多数是"更新文档要单独提交一次"的摩擦。

## 第 8 章 小结


本专栏从全景走到运维开发，最后一篇落在自动化，是有意的安排：自动化是前面所有知识的"变现"——CLI、SDK、Ansible 的每一行代码，背后都是 04 篇的调度原理、06 篇的网络路径、08 篇的卷状态机。不理解原理的自动化是危险的（脚本会以你意想不到的方式操作资源），理解了原理的手工是低效的（同样的知识每次都要人肉执行）。

运维开发的终局不是"把所有操作都写成脚本"，而是**把重复劳动交给脚本，把判断与决策留给人**——脚本负责快与准，人负责权衡与兜底。这个分工，与整个专栏反复出现的"权衡取舍"是同一件事。

回顾本篇的四类工具，它们的选型逻辑可以收拢成一句话：**一次性用 CLI，重复用 SDK，集合用 IaC，排障用直调**。四类工具不是互斥的选项，而是同一个运维体系里的不同层次——成熟的团队四者并用，各司其职。



到这里，本专栏的 15 篇走完了一个完整的循环：从全景与地基（01-03），到核心服务（04-07），到存储与镜像（08-10），再到部署与运维开发（11-15）。如果这些文字能让你在接手 OpenStack 运维的第一天少一点慌乱、在第一次故障排查时多一点方向，专栏的目的就达到了。运维的学问最终要在生产环境里长成——专栏给你的是地图，路要你自己走。

如果要用一句话收束整个专栏，那就是 01 篇的那句话的回响：架构不是设计出来的，是演进出来的。运维能力也一样——从手工到脚本，从脚本到编排，从编排到自愈，每一步都建立在上一步的可靠之上。愿这份地图，陪你走好每一步。
