# 14 故障案例库——从告警到根因

**摘要：**

故障案例是运维知识沉淀的最高形态——原理文章告诉你系统"应该怎样工作"，案例库告诉你系统"实际怎样坏掉"。本文按"现象→诊断命令链→根因分析→处置→预防"的五段结构，复盘六类高频故障：OSD 式的实例启动失败、热迁移卡住、网络不通、卷挂载失败、MQ 积压与数据库连接耗尽、控制面证书过期。每个案例的命令链都可以照着敲，案例之间的共性（先保护后修复、沿调用链找断点、变更记录是第一线索）汇入方法论章节。本篇与 12 篇的 SOP 互为表里：SOP 是操作手册，案例库是推理过程。

## 第 1 章 故障排查方法论

### 1.1 通用路径：从告警到根因的四步

凌晨三点的告警不会给你时间重读架构文档，所以排查路径必须提前内化——内化的方式不是背文档，而是把每个案例的推理过程消化成自己的直觉。笔者的方法论是四步：

**第一步：定级与止血。** 先判断影响面（多少实例、多少租户、数据面还是控制面），如果故障正在扩大，第一动作是止血——把故障节点摘出调度池、冻结变更、必要时 set noout 式的保护（OpenStack 里对应 `nova service-disable`）。止血不是修复，它买的是思考时间。

止血动作的清单也值得预置：摘出调度池（nova service-disable）、暂停巡检与自动化任务（防止它们在故障期间做出错误决策）、通知业务方（哪怕还没有结论，"已知悉、正在处理"的通报也比沉默好）。这些动作应该印在值班手册的第一页——故障时刻没有时间回忆清单，清单必须提前存在。

定级的三个速问：影响多少租户（一个还是全部）？数据面受影响吗（实例运行是否正常）？故障在扩大还是稳定（对比 10 分钟前的状态）？三个问题的答案组合，基本能定下处置的节奏——全部租户加数据面受损是 P0，单个租户加控制面异常是 P1。定级的价值不只是排优先级，更是给后续动作定授权边界：P0 可以重启服务，P1 就未必可以。

**第二步：沿链路定位断点。** OpenStack 的每个用户操作都是一条跨服务链路（04 篇的时序图），故障必然表现为链路某一环的断点。从用户报错出发，逐跳核对：API 收到了吗？下游依赖响应了吗？状态机卡在哪一步？每跳都有日志与状态可查。

沿链路排查的前提是**心里有链路图**。这也是为什么本专栏把架构篇放在运维篇之前——不知道创建实例要经过哪几个服务，就不可能"沿链路"排查。链路图的颗粒度要到"组件+交互方式"（谁调用谁的 API、谁走 MQ、谁直接连数据库），因为不同交互方式的故障表现完全不同：API 调用失败有明确的报错，MQ 消息丢失则悄无声息。

**第三步：验证假设。** 有了根因假设后，先做一个最小验证（譬如"怀疑 MQ 积压"就先看队列深度），再动手修复。跳过验证直接修复的代价是：修错了方向，故障还在，还引入了新的变更变量。

**第四步：恢复与复盘。** 恢复要按依赖顺序（先地基后上层），复盘要产出三样东西：根因描述、runbook 更新、预防措施。没有复盘的故障，大概率会以另一个面目重演。

四步之中，最容易被跳过的是第三步——验证假设。故障排查时的心理压力会让人倾向于"赶紧做点什么"，而"做点什么"如果没有验证支撑，本质上是在赌博。笔者见过的最贵的一次排障失误，就是值班同事在未验证的情况下重启了整个 MQ 集群——根因其实是数据库锁等待，重启 MQ 不仅没解决问题，还让所有服务经历了一次连接风暴，故障面扩大了三倍。

### 1.2 两条铁律

**铁律一：先保护后修复。** 故障进行中不是做实验的时候——所有修复动作都应当可回滚，所有破坏性操作（重启服务、清理数据）都要先确认影响面。凌晨三点最危险的不是故障本身，而是疲劳状态下手滑的"修复"。

"保护"的具体动作有一份清单：把故障节点摘出调度池（防止新实例落上去）、冻结变更窗口（防止变更与故障互相干扰）、对高危命令加双人复核（清理数据类的操作）。这些动作的共同点是**可逆**——摘出调度池可以恢复，冻结可以解除，而删除不可逆。故障处置的每一步都优先选可逆的动作，这是把"处置失误"与"原始故障"解耦的关键。

**铁律二：变更记录是第一线索。** 90% 的"莫名其妙"故障，根因是最近 24 小时内的某次变更——配置修改、版本升级、网络调整。排查开始前先看变更记录，可能五分钟就结束战斗；不看变更记录，可能排查两小时后才发现"哦，下午有人改过交换机"。

变更记录要可用的前提是"变更被记录"——这听起来像废话，但很多团队的变更管理只覆盖"正式变更"，临时操作（值班同事顺手改了个参数、开发同学登机修了个配置）往往不记录。故障排查时这些"暗变更"恰恰是最难发现的根因。把"所有生产变更必须留痕"变成团队纪律，是故障排查效率的地基投资。

### 1.3 排障工具箱

四步方法论落地时，下面这些命令是最高频的"手术刀"，按排查阶段归类：

**定位阶段**：

- `openstack server show <id>`：实例状态与 fault 字段
- `openstack compute service list`：服务存活与心跳
- `openstack network agent list`：网络 agent 状态
- `openstack volume show <id>`：卷状态机

**深入阶段**：

- `virsh list / dominfo / dumpxml`：libvirt 层的实例状态
- `ovs-vsctl show`：OVS 端口与桥的拓扑
- `rabbitmqctl list_queues`：MQ 队列与消费者
- `mysql -e "show processlist"`：数据库连接与锁

**取证阶段**：

- `tcpdump -i <iface>`：分段抓包
- `virsh dumpxml`：生成的域配置
- 各服务日志的 request-id 串联检索

工具箱不必一次备齐，但每用一次新工具就往 runbook 里加一条——工具箱是长出来的，不是一次画出来的。

## 第 2 章 案例：实例启动失败

### 2.1 现象

某租户反馈：批量创建 10 台实例，3 台成功、7 台一直卡在 BUILD，20 分钟后转为 ERROR。`nova show` 显示 fault 字段为 `No valid host was found`。

这个现象里藏着两条关键线索：其一，"3 台成功"说明调度器与计算节点的基本功能是好的——如果是全局性故障（MQ 断了、数据库挂了），10 台应该全失败；其二，"7 台失败"发生在同一批请求里，说明这批请求有共同的约束——同一个 flavor、同一个镜像、同一个可用区。两条线索合起来，排查范围可以缩小到"这批请求的约束与集群资源的匹配问题"。

还有一个时间线索：这批创建发生在昨天晚上的一次批量删除之后（业务方先删旧实例再建新实例）。时间上的先后关系不一定是因果关系，但它提供了第一个假设——删除与创建之间可能有资源状态的残留问题。好的排查习惯是：把时间线画出来（什么时候做了什么、什么时候开始坏），假设从时间线的交点里长出来。

### 2.2 诊断命令链

先说一个排查习惯：`No valid host` 的报错信息本身几乎没有信息量——它只告诉你"所有主机都不行"，不告诉你"为什么不行"。所以诊断的第一步不是盯着报错，而是打开调度器的 DEBUG 日志，让每个 filter 把淘汰理由说出来。

```bash
# 1. 确认调度失败的原始报错（scheduler 日志）
grep "No valid host" /var/log/kolla/nova/nova-scheduler.log | tail

# 2. 临时开启 DEBUG 级别重试一次创建，观察每个 filter 的淘汰记录
#    （Kolla 部署下用 docker exec 进容器改 log level，或用 openstack --debug 看请求细节）
openstack --debug server create ...

# 3. 查看各主机的资源水位——账面承诺与实际使用分开看
openstack hypervisor list
openstack hypervisor show <id>   # free_ram_mb 是关键列

# 4. 查 Placement 账本是否与实际一致（本案例的关键一步）
openstack resource provider list
openstack resource provider show <uuid> --resource-class VCPU
```

诊断过程中的一个关键转折值得强调：`openstack hypervisor list` 显示多台主机 free_ram_mb 富余充足，但调度器依然报 RamFilter 淘汰——**账面与直觉矛盾时，先怀疑账本**。Nova 数据库的实例表与 Placement 的 allocation 表是两本账，前者记录"活的实例"，后者记录"承诺出去的资源"，两本账对不上时，调度器信的是 Placement。

这个"两本账"的结构还有一层含义：修复时要明确以哪本账为准。本案例中实例确实已删除，所以以 Nova 数据库为准、清理 Placement 的多余 allocation。但反过来（实例在跑而 allocation 丢失）的修复方向就完全相反——先辨明哪本账是对的，再动手清理，这是所有对账操作的第一原则。

### 2.3 根因分析

日志显示所有主机都被 RamFilter 淘汰，但 hypervisor list 显示多台主机内存富余充足——账面与直觉矛盾。进一步查 Placement 的 allocation 记录，发现大量孤儿 allocation：上周一次批量删除实例的操作中，某台 nova-compute 进程崩溃，回收逻辑没有执行，几十台已删除实例的 allocation 全部残留。

**根因**：删除流程中断导致 Placement 账本虚高，调度器看到的"可用内存"远小于实际。

深挖一层：为什么删除流程会中断？回溯那台 nova-compute 的日志，发现批量删除进行到一半时，宿主机发生了 OOM，nova-compute 进程被内核杀掉——删除流程中的"通知 Placement 释放 allocation"这一步没有执行。进程被 systemd 拉起后，它不会自动补做"上次没做完的回收"（Nova 没有这种补偿机制），孤儿 allocation 就此沉淀。

这个案例的教训有两层：表层是"要定期对账"，深层是**分布式系统里的删除操作天然不是原子的**——跨了数据库、消息队列、Placement 三个系统，任何一环断掉都会留下残渣。对账不是权宜之计，是这类系统的必备卫生机制。

还有一个衍生问题值得思考：为什么 Nova 没有内建的补偿机制？答案是补偿的前提是"能判断哪些操作没完成"，而这需要跨系统的分布式事务支持——引入的复杂度比"定期对账"高得多。OpenStack 选择了最终一致加人工对账的路线，这是一个务实的权衡：对账的成本是每周几分钟的脚本运行，分布式事务的成本是每个写操作的额外延迟与实现复杂度。理解了这个权衡，就不会抱怨"为什么 Nova 不自动清理"了。

对账的具体做法也值得展开：对比的基准是"Placement 的每条 allocation 是否能在 Nova 数据库的 instances 表里找到对应的活实例"。技术实现上，两边各导出一份 ID 清单，差集就是嫌疑名单。嫌疑名单要人工复核——因为有些 allocation 属于构建中的实例或特殊状态，不能见着对不上就删。自动化对账脚本的产出应当是"嫌疑清单"而不是"自动删除"，删除的扳机留在人手里。

### 2.4 处置

```bash
# 1. 找出孤儿 allocation（对比 nova 数据库的实例列表与 Placement 的 allocation）
# 2. 逐条确认实例确实已删除后，清理孤儿 allocation
openstack resource provider allocation set --resource <uuid> <provider> --delete
# 3. 重新触发创建
```

处置的顺序有讲究：先清理孤儿 allocation（释放账面资源），再让租户重试创建——顺序反了的话，重试依然失败，租户的体验是"你们说要修，修了还是不行"，信任损失比故障本身更大。另外清理 allocation 前的"确认实例确实已删除"不能省——万一实例还活着（只是状态同步异常），删掉它的 allocation 会导致资源超卖。

### 2.5 预防

- Placement 对账纳入每日巡检（13 篇的巡检清单），孤儿 allocation 的清理要走"确认实例已删除"的人工复核，脚本自动清理要留白名单
- nova-compute 的 OOM 保护（systemd OOMScoreAdjust 调低被杀概率），同时把宿主机的内存水位纳入告警——compute 进程被 OOM 杀掉的前兆是宿主机内存贴顶
- 批量删除操作安排在低峰期，删除后立即核对 allocation 回收情况
- 把"孤儿 allocation 数量"做成趋势指标：数量稳定说明是偶发，持续上涨说明删除流程有系统性问题

这个指标还有一个衍生用法：孤儿 allocation 的产生速率是"删除流程健康度"的代理指标——它突然抬头，往往对应着某次变更引入的删除流程回归。把代理指标纳入监控，等于给删除流程装了一台烟雾报警器。

## 第 3 章 案例：热迁移卡住

### 3.1 现象

运维做主机维护，对一台实例执行 live-migration，状态卡在 `migrating` 超过 30 分钟，源与目标主机的 virsh 都能看到域，但迁移进度条不动。

"卡住"的判断要先量化：热迁移的耗时与实例内存大小、脏页增速、迁移带宽三个变量相关，一台 64GB 内存的高负载实例迁移十几分钟并不算异常。判断"卡住"的标准是**进度停滞**——`virsh domjobinfo` 的 Data remaining 连续几分钟不下降，才是真正的卡住。没有这个量化，"卡住"与"慢"会被混为一谈，而两者的处置完全不同：慢可以等，卡必须干预。

### 3.2 诊断命令链

```bash
# 1. 看迁移任务状态
openstack server show <id>   # 关注 OS-EXT-STS:vm_state 与 task_state

# 2. 在源主机看迁移进度（QEMU 层）——本案例的关键命令
virsh domjobinfo <instance-uuid>
# 关注 Data remaining（剩余内存量）是否在下降

# 3. 检查迁移网络带宽（cluster 网络是否被挤占）
iftop -i <cluster-iface>

# 4. 看目标主机的 libvirt 日志
grep -i migrate /var/log/libvirt/qemu/<instance-uuid>.log
```

四条命令各管一层：第一条看 OpenStack 视角的任务状态，第二条看 QEMU 视角的迁移进度（最关键），第三条看网络带宽的实际占用，第四条看目标侧的错误。迁移问题的排查要在源与目标两台主机之间来回切换，两边的日志时间戳要对齐（NTP 不同步会让日志对不上，徒增混乱）。

### 3.3 根因分析

`domjobinfo` 显示 Data remaining 长期不降——内存脏页产生的速度超过了网络拷贝的速度。这台实例跑的是内存密集型业务（Redis），写内存的速率极高，pre-copy 迁移陷入了"追不上"的死循环：拷贝一轮内存，业务又把同样的页改脏了。

理解这个死循环要先理解 pre-copy 的原理：热迁移把源主机的内存页逐轮拷贝到目标主机，第一轮拷全量，后续轮次只拷"上一轮期间被改脏的页"，当剩余脏页足够少时，短暂停机完成最后一轮拷贝与切换。这个算法的收敛前提是**脏页增速 < 拷贝带宽**——一旦业务写内存的速率超过迁移链路的带宽，脏页永远追不完，迁移就永远停不下来。

**根因**：内存写速率 > 迁移带宽，pre-copy 算法收敛不了。这不是 OpenStack 的 bug，而是 pre-copy 算法的数学边界——任何基于预拷贝的迁移方案都受此约束。

量化一下这个边界：该实例 64GB 内存，业务写速率约 2GB/s，迁移网络的有效带宽约 1.5GB/s——写比拷贝快 33%，无论拷多少轮，脏页都在净增长。这个算术一旦摆出来，"继续等"就不是选项了，剩下的只有三个变量可调：降写入、加带宽、换算法（post-copy 或停机迁移）。故障排查到了算术层面，决策反而变得简单。

### 3.4 处置

三个选项按侵入性排序：其一，降低业务写入压力（与业务方协调，譬如暂停 Redis 的持久化重写）；其二，提高迁移带宽（`live_migration_bandwidth` 参数或专用迁移网络）；其三，取消迁移改用维护窗口停机迁移（`openstack server migrate` 冷迁移）。本例选择了方案一加方案二组合，迁移在 8 分钟内完成。

处置过程中还有一个细节值得记录：取消热迁移（`openstack server migrate --abort` 或旧版本的删除迁移任务）是安全的——pre-copy 的设计保证了源主机的实例始终在跑，取消只是丢弃已拷贝的数据，业务无感知。这个"可随时反悔"的特性是 pre-copy 相对于 post-copy 的最大优势：post-copy 先切换后拷贝，切换之后就没有回头路了，目标主机一旦异常，实例直接挂。

迁移完成后还有一个容易忽略的收尾：**验证目标主机上的实例状态**。迁移成功不等于万事大吉——实例在目标主机上的性能可能与源主机不同（NUMA 拓扑差异、CPU 特性差异、网络路径变化），业务方的体感才是最终验收标准。把"迁移后业务确认"写进维护预案，是很多团队交过学费后才学到的步骤。

### 3.5 预防

- 热迁移前检查实例的内存写速率（高写速率实例是迁移困难户，提前标记）——Redis、Kafka 这类内存写密集型业务要在 CMDB 里打标
- 部署专用迁移网络（与业务网络、存储网络隔离），带宽按"最大实例内存 / 期望迁移时长"倒推
- 把"热迁移成功率"纳入维护预案的演练项，每次演练记录耗时与失败原因，积累成迁移难度画像
- 对确实迁不动的实例，提前与业务方约定停机窗口——预案比临场决策从容得多

补充一个技术细节：热迁移的带宽参数（`live_migration_bandwidth`）与迁移网络的规划要匹配——参数设得再大，物理链路给不出带宽也是空谈。迁移网络的带宽规划公式可以简化为：最大实例内存 × 2 ÷ 期望迁移时长。譬如 64GB 内存的实例要在 2 分钟内迁完，需要约 1GB/s 的有效带宽——这对迁移网络的要求是万兆起步。

## 第 4 章 案例：实例网络不通

### 4.1 现象

某租户反馈：一台实例突然 ping 不通浮动 IP，但同子网的其他实例正常。实例本身在运行，控制台登录后 `ip addr` 显示网卡正常、IP 正确。

这个现象的组合信息已经很有价值：实例活着（能从控制台登录）、网卡配置正确（IP 与路由都在）、同子网其他实例正常（子网级故障排除）、只有浮动 IP 不通（南北向链路问题，而非东西向）。带着这四条信息进入排查，范围已经缩小到"该实例的南北向链路"——可能是安全组、可能是浮动 IP 绑定、可能是该实例所在宿主机的数据面。

补充一个时间线索：这台实例上周经历过一次热迁移（同为主机维护的一部分）。时间线索与现象线索叠加，"迁移后遗留问题"的假设权重就该上调——不是说要带着偏见排查，而是把高概率假设排在前面验证，是效率的正确用法。

### 4.2 诊断命令链

```bash
# 1. 从内向外逐段检查
# 1.1 实例内：网卡与默认路由
ip addr && ip route

# 1.2 宿主机：tap 设备与 OVS 端口
tap=$(grep tap /etc/nova/nova.conf 2>/dev/null; virsh dumpxml <id> | grep -o 'tap[0-9a-f-]*' | head -1)
ovs-vsctl show | grep -A2 $tap

# 1.3 安全组：iptables 是否放行 ICMP
iptables -L -n | grep icmp

# 1.4 网络节点：路由与浮动 IP
ip netns list   # 找到 qrouter 命名空间
ip netns exec qrouter-<uuid> ip addr | grep <floating-ip>

# 1.5 抓包定位断点（在 tap 与 br-int 之间分段抓）
tcpdump -i tap<id> icmp
tcpdump -i br-int icmp
```

### 4.3 根因分析

分段抓包发现：tap 设备上有 ICMP 出包，br-int 上没有——断点在 tap 到 OVS 的桥接段。

抓包的具体操作值得记录，因为位置选错会浪费大量时间：

```bash
# 第一段：实例的 tap 设备（确认包有没有从实例出来）
tcpdump -i tap<id> icmp -n

# 第二段：qbr 桥（Linux bridge 不能直接抓，抓它的端口）
tcpdump -i <qbr-port> icmp -n

# 第三段：br-int（OVS 桥要抓它的 internal 端口或用 mirror）
tcpdump -i br-int icmp -n
```

包在第一段有、第二段没有，断点就在 tap 到 qbr 之间——本案例正是如此。分段抓包的本质是二分法：每抓一次排除一半的链路，三四次抓包就能把断点定位到具体设备。这个分段方法值得展开：实例的包要经过 tap（实例侧网卡）→ qbr（Linux bridge，安全组过滤）→ br-int（OVS 集成桥）→ br-tun（隧道封装）→ 物理网络，任何一段断了，表现都是"ping 不通"。tcpdump 在每段各抓一次，包在哪一段消失，断点就在哪一段——这是网络排障里最朴素也最有效的二分法。

检查发现 qbr 桥上的 tap 端口处于异常状态（该实例经历过一次热迁移，迁移后 tap 与 OVS 端口的绑定没有正确重建）。

**根因**：热迁移后的网络设备重连不完整，tap 设备游离在 OVS 桥之外。

这里展开解释一下 tap 与 qbr 的关系（详见 06 篇）：实例的网卡在宿主机上表现为 tap 设备，因为安全组用 iptables 实现，而 OVS 的流表与 iptables 不兼容，中间垫了一层 Linux bridge（qbr）。包的路径是 tap → qbr → br-int。tap 游离在 qbr 之外，等于实例的网线没插进交换机——实例自己看一切正常，包就是出不去。

### 4.4 处置

处置方案的取舍要先与业务方对齐：硬重启会中断业务（这台实例跑的是什么业务决定了对中断的容忍度），手工桥接不中断但有操作风险。笔者的建议是：非核心业务直接硬重启（快、干净、可复制），核心业务先尝试手工桥接（在维护窗口内、双人复核），两条路都走不通再考虑迁移实例重建网络。

```bash
# 重挂端口（或最简单：软重启实例让 Nova 重建网络设备）
openstack server reboot --hard <id>
```

硬重启后设备重建，网络恢复。但硬重启会中断业务——如果业务不允许，可以手工把 tap 端口重新桥接到 qbr（`ovs-vsctl add-port`），这是更精细但风险更高的操作。手工桥接的每一步都要先在测试环境演练过：OVS 的端口操作是即时生效的，敲错命令可能把正常实例的网络也断掉。精细操作的价值是避免业务中断，前提是操作者对数据面的理解足够扎实——否则"最简单的硬重启"才是正确选择。

处置之后的信息同步也值得强调：网络类故障的用户感知往往早于监控（用户发现 SSH 连不上比指标异常更快），处置过程中要主动向业务方通报进展——"已定位到断点，正在处置，预计 10 分钟恢复"与沉默的十分钟，给业务方的感受天差地别。故障沟通的模板（现象、影响面、当前动作、预计恢复时间）应当提前备好，故障时填空即可。

还有一个技术备选方案值得记录：如果硬重启与手工桥接都不可接受，第三条路是把实例迁移到别的宿主机（冷迁移会重建全部网络设备）——迁移绕过了"修复损坏的设备"，用重建代替修复。三条路径的取舍（快但中断、精细但高风险、绕行但耗时）就是运维日常的权衡缩影。

### 4.5 预防

- 热迁移后抽查实例网络连通性（迁移不是结束，验证才是）——迁移完成的验收清单里应当有"网络连通性探测"一项
- 把"tap 与 OVS 端口一致性"纳入巡检脚本：对比 libvirt XML 里的 tap 设备与 `ovs-vsctl show` 的端口列表，游离设备一目了然
- 网络类故障的排查，tcpdump 分段抓包是最快定位断点的手段——把抓包位置图（tap/qbr/br-int/br-ex 四个点）贴在 runbook 里，新同事照着抓就行
- 对热迁移频繁的环境，评估升级到修复了此类问题的 OpenStack 版本（该类缺陷在多个版本有过修复记录，升级前查 release notes）

## 第 5 章 案例：卷挂载失败

### 5.1 现象

用户给实例挂载一块数据卷，Cinder 界面显示 attaching 后转为 error，实例内没有出现新磁盘。补充两个观察：这台实例所在宿主机上的其他实例挂卷正常（排除全局性故障），这块卷之前挂在另一台实例上、刚刚被卸载（卷是有"历史"的）。第二个观察很重要——跨实例迁移挂载的卷，涉及旧连接的清理与新连接的建立，出问题的概率比全新卷的首次挂载高得多。

### 5.2 诊断命令链

```bash
# 1. 看卷的状态机——status 与 attachment 字段是第一现场
openstack volume show <volume-id>   # status 与 attachment 字段

# 2. 看 cinder-volume 日志中该卷的操作记录（控制面视角）
grep <volume-id> /var/log/kolla/cinder/cinder-volume.log | tail -20

# 3. 看 nova-compute 侧的 attach 日志（数据面视角——本案例的关键）
grep -i "attach" /var/log/kolla/nova/nova-compute.log | tail

# 4. Ceph 侧确认卷的 RBD 对象存在（RBD 后端）
rbd -p cinder-volumes info volume-<uuid>

# 5. 在计算节点上验证 Ceph 连通性（本案例的破案一步）
rbd -p cinder-volumes ls --id cinder   # 用 cinder 的 keyring 测试认证
```

诊断的顺序也值得说明：为什么先查 cinder-volume 再查 nova-compute？因为 attach 流程的发起方是 cinder-volume（它先与 Ceph 交互建立连接配置），如果 cinder-volume 侧就报错，问题在控制面；cinder-volume 正常而 nova-compute 失败，问题才在数据面。先确认"上游是否正常"再查"下游为什么失败"，能避免在错误的组件里空转。

### 5.3 根因分析

cinder-volume 日志显示 attach 请求正常下发，但 nova-compute 侧报 `Failed to connect to volume`。这个报错的位置很有信息量：cinder-volume（控制面）认为一切正常——卷的状态、后端的响应都没问题；失败发生在 nova-compute（数据面）——真正去连 Ceph 集群的是计算节点。**控制面成功、数据面失败**，这个组合提示要去看计算节点的本地状态。

"控制面成功、数据面失败"是分布式存储接入场景的经典故障形态，同类问题还有：Glance 上传成功但计算节点下载镜像失败、Neutron 创建端口成功但实例内 DHCP 拿不到地址。它们的共同点是：控制面的"成功"只代表控制面视角的流程走完，数据面的实际动作（下载、连接、认证）是否成功，只有数据面自己知道。遇到这类组合，排查方向立即转向数据面节点的本地状态。

进一步查发现该实例所在计算节点与 Ceph 集群的连接异常——cinder 的 Ceph 凭据在该节点上失效（此前轮换过 Ceph keyring，该节点的配置没有同步更新）。

**根因**：Ceph 凭据轮换时漏更新了一台计算节点，该节点上的所有卷操作都会失败。验证方法也很直接：在该节点上用 cinder 的 keyring 手动执行 `rbd -p cinder-volumes ls`，认证失败即坐实。

### 5.4 处置与预防

更新该节点的 Ceph keyring 后重启 nova-compute，卷挂载成功。处置时还有一个收尾动作不能省：检查该节点上在此期间失败过的其他卷操作——不只是这一台实例的这一次挂载，凡是该节点在凭据失效窗口内发起的卷操作都可能留下了中间状态（卡在 attaching 的卷、半初始化的连接），要逐一核对清理。

预防措施：凭据轮换必须用 Ansible 等工具全量下发并校验，禁止手工单台修改；把"计算节点到 Ceph 的连接健康"纳入巡检（用 rbd 命令做只读探测）；凭据轮换的变更单要附"全节点下发核对清单"，逐台打勾确认——漏掉一台的代价是这台节点上的所有卷操作持续失败，直到有人报障。

凭据轮换这类"全量下发"的变更，还有一个验证技巧：下发完成后，从每个节点抽样执行一次真实操作（读一个 RBD 对象），而不是只检查配置文件的内容——配置文件对了不代表凭据能用的所有前提（网络、权限、时间同步）都满足。端到端验证比配置核对更接近真相。

凭据轮换的顺序也有讲究：先加新的、验证通过、再删旧的（双凭据过渡期），比"先删后加"的窗口期安全得多。Ceph 的 cephx 支持多 keyring 共存，利用好这个特性可以把轮换的故障窗口压到零。

这个案例还有一个值得复盘的角度：**为什么凭据轮换会漏掉一台节点？** 回溯发现，那台节点当时正在硬件维护（下电换内存），轮换脚本跳过了不可达的主机，维护完成后没有人补发。变更脚本"跳过不可达目标"的设计本意是容错，但它把失败静默化了——正确的做法是"跳过但记录，维护完成后强制补发"。容错设计与变更闭环的结合点，往往就是故障的出生地。

## 第 6 章 案例：MQ 积压与 API 变慢

### 6.1 现象

平台整体 API 响应变慢（从 200ms 恶化到 8s），创建实例成功率下降，RabbitMQ 管理界面显示多个队列深度上万。

"整体变慢"与"单个操作失败"是两类不同的故障：前者指向共享依赖（数据库、MQ、Keystone），后者指向特定链路。整体变慢的排查起点是共享依赖——三个嫌疑人按历史故障率排序：数据库锁等待、MQ 积压、Keystone 风暴。RabbitMQ 管理界面上"多个队列深度上万"直接把嫌疑锁定在 MQ——但积压是根因还是结果（下游服务挂了导致没人消费），还要看消费者状态。

还有一个时间维度的信息：变更是两小时前开始的，而 API 变慢是一小时前开始的——时间差说明 MQ 维护本身不是直接根因（如果是，变慢应该与维护同步开始），维护触发的某个延迟效应（譬如消费者断连后的消息堆积逐渐恶化）才是。时间线的对齐，是区分"相关"与"因果"的关键证据。

值班时的第一反应是重启服务——但重启哪个？API 慢的原因还没定位，盲目重启只会让 MQ 里的消息风暴来得更猛。先诊断，后动手。

### 6.2 诊断命令链

```bash
# 1. 看哪些队列在积压（messages 是深度，consumers 是消费者数）
rabbitmqctl list_queues name messages consumers

# 2. 重点看 consumers=0 的队列——积压且无消费者的队列是重灾区
rabbitmqctl list_queues name consumers   # consumers=0 的队列是重灾区

# 3. 看控制面服务状态（是否有服务假死——进程在但消费者断连）
openstack compute service list

# 4. 看数据库连接数（积压消化时会冲击数据库，提前评估）
mysql -e "show processlist" | wc -l
```

这四条命令的顺序有讲究：先看队列深度确认"有没有积压"，再看消费者确认"是生产过多还是消费不足"（本案例是后者），然后核对服务状态确认"消费者为什么失联"，最后评估数据库——因为恢复消费的瞬间，积压消息会转化为数据库写入，要确认数据库扛得住。诊断链的顺序，本质是因果链的顺序。

补充一个工具细节：`rabbitmqctl list_queues` 在队列很多时输出会刷屏，配合 `name` 过滤（只看 nova 相关队列）能快很多。管理界面（rabbitmqctl 的 Web UI）更适合人看，命令行更适合脚本——两者配合，人看趋势、脚本看细节。



诊断中还有一个容易误判的地方：队列积压与 API 变慢的因果关系。积压是"结果"还是"原因"？本案例中两者互为因果——消费者失联导致积压，积压的消息里包含大量待处理的 API 请求，API 变慢又让用户重试，重试进一步加剧积压。这种正反馈回路是分布式故障的常见形态，处置时要么切断回路（暂停重试、限流），要么快速消化积压打破循环——只修根因不破回路，恢复会很慢。

### 6.3 根因分析

积压集中在 Nova 的调度相关队列，且对应队列的消费者数量为 0——nova-scheduler 的消费者连接断开且没有恢复。这个现象的诡异之处在于：nova-scheduler 的进程明明活着（service list 显示 up），API 也还在受理请求——**进程活着不等于消费者活着**，消息消费的连接是独立于进程存活状态的。

回溯变更记录发现：两小时前 MQ 集群做了一次维护（滚动重启），nova-scheduler 的连接没有自动恢复（该版本的 kombu 重连逻辑有缺陷），调度消息全部堆积。

**根因**：MQ 维护触发了服务重连缺陷，消费者静默失联。"静默"是这个案例最危险的属性——进程活着、服务显示 up、监控的服务存活指标全绿，唯一的异常信号是队列深度，而当时队列深度还没有纳入告警。

"静默故障"（silent failure）是分布式运维最头疼的类别——它不触发任何异常日志，所有进程健康检查都通过，唯一的症状是"功能没有发生"。对付静默故障只有一招：**监控"效果"而不是"进程"**——消费者进程活着不算数，消息被消费才算数；API 进程活着不算数，请求成功返回才算数。效果监控的每一个指标，都是对一类静默故障的免疫。

### 6.4 处置与预防

重启 nova-scheduler 恢复消费者，队列迅速消化，API 延迟回落。重启的顺序也有讲究：先重启消费者（让积压开始消化），观察消化速率，确认数据库扛得住——如果积压的消息里有大量写操作，消化过程就是一次突发的写入风暴。必要时分批恢复消费者，给数据库留出缓冲。处置时有个细节要注意：积压的消息消化初期会有一个"补偿风暴"——积压的调度消息被集中处理，可能瞬间产生大量实例创建请求，把刚恢复的系统再次打垮。如果积压量大，可以考虑清掉过期的调度消息（调度消息有时效性，过期消息执行反而有害）再恢复消费者——这个决策要按消息的业务语义来定，不能一刀切。

预防措施：MQ 维护窗口后必须执行"消费者健康检查"（所有队列 consumers > 0）；升级 kombu 与 OpenStack 的 MQ 客户端到修复了重连缺陷的版本；MQ 队列深度纳入告警（13 篇的 P1 规则）。

这个案例还有一个组织层面的教训：MQ 维护的变更单里没有"维护后验证"这一项——维护的同学重启完 MQ 确认 MQ 自身健康就收工了，而受影响的其实是消费者侧。**变更单的验证清单要覆盖"受影响的下游"**，这是变更管理的通用原则：你动的不只是你动的东西，还有所有连着它的东西。

变更验证清单的模板化也值得做：每类变更（MQ 维护、数据库升级、证书轮换）配一张固定的验证清单模板，变更执行人按模板逐项打勾。模板的价值在于把"经验"变成"清单"——老运维脑子里的检查项，新值班同事看不到，写进模板才能传承。

MQ 维护的验证清单至少包含四项：集群状态健康（三个节点全部在线）、关键队列的消费者数量恢复（逐队列核对）、抽样消息的端到端验证（发一条测试消息确认能被消费）、观察期（维护后 30 分钟内盯住队列深度曲线）。四项全绿才算收工——这套清单同样适用于其他中间件的维护。

## 第 7 章 案例：控制面证书过期

### 7.1 现象

所有 API 突然返回 SSL 握手失败，Horizon 无法登录，但已有实例运行正常（数据面无感知）。监控显示各服务进程全部存活。

这个故障的"现象组合"本身就是重要的诊断信息：控制面 API 全部不可用（SSL 层失败）、数据面完全正常（实例照常跑）、进程全部存活（不是服务崩溃）。三个信息拼在一起，指向一个结论：问题出在 API 的"门"上——TLS 层——而不是服务本体。这类"门坏了"的故障，排查方向与"屋里着火"完全不同。

这类故障还有一个特征：影响面是"所有走 HTTPS 的客户端"，但走内网 HTTP 的监控探针可能完全正常——监控探针的协议与路径决定了它能看见什么。这也是黑盒探活要覆盖"用户真实路径"（HTTPS 走公网）的原因：探针走的路与用户不同，看见的世界就不同。

### 7.2 诊断与根因

```bash
# 检查 API 端点证书
echo | openssl s_client -connect <api-endpoint>:443 2>/dev/null | openssl x509 -noout -dates
# 输出显示 notAfter 就是今天

# 顺带检查所有端点的证书（一个脚本扫全部 API VIP）
for ep in $(openstack endpoint list -f value -c URL | grep -oP 'https://[^/]+'); do
  echo -n "$ep : "
  echo | openssl s_client -connect ${ep#https://}:443 2>/dev/null | openssl x509 -noout -enddate
done
```

**根因**：API 网关的 TLS 证书过期，未配置自动续期。这是典型的"低级但高频"故障——证书过期不痛不痒地潜伏一年，然后在某个凌晨集中爆发。诊断本身只需要一分钟，难的是"记得往证书方向想"——进程全活的故障，人的直觉是去查服务日志，而日志里什么都没有。

"进程全活但功能不可用"的故障，有一个通用的快速分诊口诀：先看入口（负载均衡/证书/DNS），再看依赖（数据库/MQ/缓存），最后看服务本体。入口层的检查成本最低（一条 openssl/curl 命令），把它排在前面，能避免在服务日志里空转。

### 7.3 处置与预防

更换证书后恢复。恢复的过程有个细节：换证书要重启 API 网关（haproxy 或各服务的 WSGI），重启的顺序与间隔要控制——全部同时重启会让 Keystone 短暂不可用，把"证书过期故障"升级成"控制面中断故障"。正确的顺序是先换非关键服务（Horizon），观察，再逐个换核心服务。

预防措施：证书有效期纳入监控（13 篇的 P2 规则：30 天内过期即告警）；证书续期自动化（acme 或内部 CA 流程）；所有长期有效的凭据（证书、keyring、密码）建立台账并统一监控有效期。证书过期的故障在业界的发生频率高得惊人——它没有任何技术难度，纯粹是生命周期管理问题，而生命周期管理恰恰是自动化最擅长的事。

同类风险的一次性排查也值得做：证书只是"长期有效凭据"家族的一员，keyring 的有效期、数据库账号的密码策略、API 用户的 token 生命周期，都属于同一类风险。用一次故障推动一次全量排查，是故障复盘的最高回报形式——修一个证书是救火，建一套凭据生命周期管理是防火。

## 第 8 章 故障复盘方法论

### 8.1 从案例到预案

复盘的产出要落入三个去处，缺一处就是浪费：runbook 承载处置动作，巡检脚本承载检查盲区，告警规则承载早期信号。三个去处对应三个问题——"下次怎么修得快"、"下次怎么提前发现"、"下次怎么不发生"。

每个故障复盘的产出应当反哺三个地方：runbook（告警通知里挂的处置文档）、巡检脚本（本次故障暴露的检查盲区）、告警规则（本次故障是否有更早的信号可抓）。复盘的产出不进 runbook，等于故障只修了一半——代码修好了，能力没有沉淀。

runbook 的写法有一个实用标准：**按时间轴写，而不是按知识写**。"先看 A，再看 B，如果 C 则做 D"——值班同事要的是决策树，不是原理阐述。原理留在专栏文章里，runbook 只留动作。两者的分工是：文章培养理解，runbook 承载执行，混在一起会两头不讨好。

runbook 的颗粒度也有讲究：太粗（"检查网络"）等于没写，太细（每条命令的每个参数都解释一遍）会淹没重点。好的颗粒度是"每个动作一行、关键命令带参数、判断分支写清楚"——值班同事照着走不需要查资料，遇到分支能自己判断走哪条。



预案的另一个组成部分是**升级路径**：runbook 的每一步都要写"如果这步不奏效，升级给谁、提供什么信息"。升级路径的断点是真实故障中最浪费时间的地方——值班同事试完了 runbook 的所有步骤，然后呢？不知道。升级路径要具体到人（或值班角色）与信息清单（日志片段、时间线、已尝试的步骤），让接手的人不用从零开始。

### 8.2 告警-预案映射表

把案例库与告警体系连接起来的是一张映射表：每条 P0/P1 告警对应一个 runbook，runbook 里引用本篇的案例作为推理参考。这张表的维护成本很低（故障复盘时顺手更新），价值却很高——它让"告警→诊断→处置"的链路在故障发生前就铺好。

| 告警 | 对应案例 | runbook 要点 | 升级路径 |
| :--- | :--- | :--- | :--- |
| No valid host 频发 | 第 2 章 | 查 filter 日志→对账 Placement | 资源不足则启动扩容 |
| 热迁移超时 | 第 3 章 | domjobinfo 看进度→评估带宽 | 业务方协调降写入 |
| 实例网络不通 | 第 4 章 | 分段抓包定位断点 | 网络组介入 |
| 卷挂载失败 | 第 5 章 | 控制面/数据面日志分离查 | 存储组介入 |
| MQ 队列积压 | 第 6 章 | 查消费者→评估消化冲击 | MQ 管理员 |
| API SSL 失败 | 第 7 章 | 查证书有效期 | 换证书流程 |

这张表的最大受益者是新接值班的同事：告警触发时，他不需要"回忆起某个案例"，只需要按表索引——从告警名到 runbook 的映射是机械的，判断与决策留给人。

映射表的形态建议直接用表格维护在知识库里（本篇的表格就是起点），每行一条告警。表格的列可以随团队需要扩展——臂加上"平均处置时长"与"最近一次触发时间"，前者帮新同事建立预期，后者帮团队识别"从未触发的告警"（要么平台太稳，要么规则失效）。

映射表的另一个用法是**演练选题**：每季度演练时，从映射表里挑一条"最近没触发过"的告警做桌面推演——久未触发的告警，其预案的时效性最可疑。

映射表的维护有一个纪律：**每条告警规则上线时，映射表必须同步更新**——没有对应预案的告警不允许上线（13 篇的"有处置动作才准入"原则在案例库侧的延伸）。这条纪律把案例库、告警体系、runbook 三者锁成了一个闭环：告警引用预案，预案引用案例，案例反哺告警。

### 8.3 案例库的运营

案例库本身也需要运营，否则会退化成"写完就没人看的文档"。三条运营纪律：**新故障必入库**——每个 P0/P1 故障复盘后，按五段结构写成案例入库（哪怕简短）；**案例定期回顾**——每季度过一遍案例库，把过时的命令与版本信息更新掉；**案例与告警联动**——新案例的"最早信号"要检查是否已被监控覆盖，没覆盖的补告警。

案例库的读者是两类人：故障发生时的值班同事（要快、要准、要能照着做），与学习中的新同事（要理解推理过程）。五段结构同时服务两者——值班看"诊断命令链"直接干活，新人读"根因分析"学习推理。

案例的选题也有标准：不是每个故障都值得写案例。值得写的三类是"根因意外的"（排查走了弯路，结论反直觉）、"复现过的"（出现两次以上的问题会再出现第三次）、"涉及跨服务协作的"（单服务的故障看日志就能解决，跨服务的才有沉淀价值）。符合任一条即可入库，三条都不占的故障，写进 CHANGELOG 就够了。

### 8.4 小结

六个案例的根因分布值得回味：孤儿资源（删除流程缺陷）、迁移不收敛（业务特征与容量规划）、设备重连缺陷（热迁移边界）、凭据不一致（变更管理）、消费者失联（MQ 维护）、证书过期（生命周期管理）——**没有一个是 OpenStack 内核的 bug**。分布式系统的故障大头永远在配置、变更与依赖管理上，这也是运维工作的价值所在：系统的可靠性，一半是架构给的，一半是运维挣的。

再横向看六个案例的"最早可发现信号"：孤儿资源可由对账巡检发现、迁移不收敛可由 domjobinfo 监控发现、设备重连缺陷可由端口一致性巡检发现、凭据不一致可由只读探测发现、消费者失联可由队列深度告警发现、证书过期可由有效期监控发现——**每个故障都有比用户报障更早的信号**。把这张"信号-指标"表落地成监控与巡检项，就是案例库从"事后复盘"走向"事前预防"的路径。

> [!note] 思考题
> 1. 第 2 章的孤儿 allocation 案例，如果发生在"批量删除进行中"而非"删除完成后"，清理孤儿 allocation 时如何避免误删正在创建中的实例的 allocation？由此设计一个安全的对账流程。
> 2. 第 3 章的热迁移死循环，pre-copy 无法收敛。post-copy 模式（先切换后拷贝）能解决这个问题吗？它引入了什么新风险？什么业务适合 post-copy？
> 3. 六个案例中，哪些故障可以在"用户报障之前"被监控发现？把每个案例的最早信号整理成一张"信号-指标"表，对照 13 篇的告警清单查漏补缺。

本案例的完整时间线也值得复盘：热迁移发生在三天前，网络不通发生在今天——故障的"因"与"果"隔了三天。这种延迟显性的故障，排查时最容易漏掉"三天前的那个动作"，因为所有人的注意力都在"今天改了什么"上。时间线的复盘范围要覆盖到"最近一次可能相关的操作"，而不是最近的几小时。

维护预案的最后一个要素是**放弃条件**：什么情况下放弃热迁移改用停机迁移？没有放弃条件的预案，会让运维在"再试一次"的循环里耗掉整个维护窗口。放弃条件要量化（譬如迁移进度 30 分钟无进展、重试两次失败），并且要在维护窗口开始前就与业务方约定好。
