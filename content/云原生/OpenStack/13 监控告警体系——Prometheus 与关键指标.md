# 13 监控告警体系——Prometheus 与关键指标

**摘要：**

OpenStack 的监控难点不在工具而在指标——几十个服务、上百个进程、三层故障域（控制面/数据面/基础设施），哪些指标值得告警、哪些只是噪音，需要一套方法论而不是一堆 dashboard。本文从 OpenStack 监控的架构讲起，剖析 openstack-exporter 的工作原理与先天局限，然后逐层拆解核心指标——服务健康、容量水位、API 性能、MQ 与数据库地基，每一层都给出"看什么、怎么判、何时告"的完整答案；在此基础上给出三级告警的设计模板、可直接套用的 PromQL 示例与去噪三板斧，最后落到与 VictoriaMetrics 生态的衔接、Grafana 面板的组织方式及巡检自动化的思路。读完你应当能搭起一套"告警少而准、指标全而深"的 OpenStack 监控体系。

---

## 第 1 章 监控架构——exporter 的原理与局限

### 1.1 openstack-exporter 的工作方式

OpenStack 没有内建的 Prometheus 指标端点，这一点与 Ceph 的做法很不一样——Ceph 的 ceph-mgr 自带 prometheus 插件，集群自己就能吐指标；而 OpenStack 的各服务只提供 API 与日志，指标需要额外的翻译官。社区的标准方案是 **openstack-exporter**：一个独立的 Python 进程，定期用 OpenStack API 轮询各服务的状态与统计信息，把结果翻译成 Prometheus 格式的指标，暴露在自己的 `/metrics` 端口上，等待 Prometheus 或 vmagent 来抓取。

这个"翻译官"架构决定了它的三个特性，运维必须心里有数。

**特性一：指标是拉取时刻的快照。** 两次抓取之间的瞬时异常会被漏掉——譬如某次 API 超时只持续了 20 秒，而抓取间隔是 60 秒，这次异常在指标里根本不存在，事后翻历史曲线也找不到。所以抓取间隔不宜过长（建议 60 秒以内），关键路径还要用黑盒探测补充——黑盒探测的频率可以更高，且它模拟的是真实用户视角。

快照式监控还有一个推论：**指标的历史曲线是"事后取证"的重要材料**。故障复盘时"当时到底发生了什么"的问题，答案往往在指标曲线里——API 延迟何时开始抬头、哪个指标率先异动、恢复点在哪。这也是为什么指标要尽早建：没有历史数据，复盘就只能靠日志与记忆。

**特性二：监控自身依赖被监控对象。** exporter 用 OpenStack API 查询数据，Keystone 挂了、API 慢了，exporter 的指标就会断流或延迟——**监控自身会失明**。这与"用体温计量自己体温"的困境同构：体温计坏了的时候，你并不知道体温计坏了。解法是分层监控：exporter 进程本身由基础设施层的存活探测守护，监控管道的断流本身要成为一条告警——"指标断流"与"指标异常"是两类不同性质的告警，前者往往比后者更紧急。

**特性三：exporter 需要一个专属身份。** 它要用一个服务账号调用各服务的 API，这个账号应当是只读的、独立于任何真实用户的——既保证权限最小化，也避免人员账号变更导致监控失效。实践中见过用管理员个人账号跑 exporter 的案例，人一离职监控全灭，这种事故完全可以靠一个专用服务账号避免。

部署形态上，exporter 建议与被监控对象适度分离——把监控探针与被监控服务放在同一台机器上，机器故障时两者一起消失，监控在最需要的时候失明。多控制节点的环境有两种选择：每个控制节点跑一个 exporter 实例（分别抓取本机服务的本地端点），或者集中部署一个实例抓取 VIP。前者能区分"节点级故障"与"服务级故障"，后者部署简单。笔者的建议是：小规模集中部署，大规模按节点部署。

exporter 的版本管理也有讲究：它与 OpenStack 服务的 API 版本有兼容矩阵，升级 OpenStack 后要同步检查 exporter 的版本支持情况——监控的升级节奏要跟着平台走，而不是反过来。把 exporter 的版本纳入 OpenStack 升级清单，是避免"升级后监控失明"的关键一步。

### 1.2 指标的四个层次

OpenStack 的指标可以按层次组织，每层回答不同的问题：

| 层次 | 回答的问题 | 代表指标 | 告警紧迫度 |
| :--- | :--- | :--- | :--- |
| 服务健康层 | 服务活着吗 | openstack_service_up、API 黑盒探活 | 秒级到分钟级 |
| 容量层 | 资源还够吗 | 实例数/vCPU/内存/卷容量水位 | 天到周 |
| 性能层 | 快不快 | API 延迟、实例启动时长、镜像下载时长 | 分钟级 |
| 业务层 | 用户顺不顺 | 创建失败率、配额使用率、租户活跃度 | 趋势观察 |

这张表的排列顺序是有讲究的：健康层最紧急但信息量最小（只有活着/死了两个状态），业务层最不紧急但信息量最大（它决定了你与业务方的信任关系）。监控体系的设计顺序应当与这张表相反：**先定义"什么状态该叫人"，再倒推需要哪些指标**——而不是先把指标堆满 dashboard，再发愁怎么配告警。指标堆砌的结局必然是告警疲劳，而告警疲劳的结局是 P0 被淹没在噪音里。

## 第 2 章 核心指标详解

### 2.1 服务健康层：up 不等于正常

openstack-exporter 暴露的 `openstack_service_up`（按服务与 endpoint 细分）是最基础的存活指标，每个服务的每个二进制进程都对应一条时间序列。但只看它有两个坑，每个坑都值得单独展开。

**坑一：exporter 查的是 admin endpoint，公网 endpoint 的故障它看不到。** API 网关到公网段的链路故障、负载均衡配置错误、证书过期——这些只影响外部用户的故障，内部指标一片祥和。你可能在监控大屏上看到全绿的指标，同时业务方已经在群里炸锅。解法是黑盒探活：从用户视角（办公网、公网）定期 curl 各服务的公开 endpoint 并校验返回码，与内部指标互为补充。黑盒探活的价值在于它测的是"用户实际经历的可用性"，这是任何内部指标都替代不了的。

**坑二：服务 up 不等于功能正常。** nova-api 进程活着但数据库连不上时，up 指标依然是 1，只是每个请求都报 500。进程存活与功能可用之间隔着一整条依赖链——数据库、MQ、Keystone，任何一环断了，进程再健康也是僵尸。所以健康层必须叠加**功能探针**：定期执行轻量的真实操作（`openstack server list`、`openstack image list`）并记录成功率与耗时。功能探针是"用户视角的可用性"，它比进程存活更接近真相。

功能探针的设计要点是"轻而全"：每个核心服务挑一个最轻量的读操作（list 一个资源、查一个 token），覆盖所有关键服务，单次探针的总耗时控制在秒级。探针失败的告警要区分"单个服务失败"（该服务问题）与"全部失败"（探针自身或网络问题）——这个区分逻辑与 exporter 断流的判断是同一套思路。

### 2.2 容量层：价值密度最高的一层

容量问题的演进是缓慢而确定的——从 80% 涨到 95% 需要时间，这给了运维充足的预告窗口。容量指标是 OpenStack 监控里价值密度最高的一层，因为每一条容量告警都可以提前数天甚至数周发出，而提前预告正是运维与业务方建立信任的最有效方式。

**计算容量**：各 hypervisor 的 vCPU/内存分配率与实际使用率。这里要区分两个口径：分配率（账面承诺了多少资源给实例）与使用率（实例实际消耗了多少）。分配率贴顶意味着新实例调度不出去——这是调度器的问题；使用率贴顶意味着性能风险——这是超分比的问题。两者背离时（分配率低、使用率高）说明超分比过激，需要校准——譬如分配率只有 60% 但物理内存已经吃紧，说明部分实例的实际用量远超其配额，邻居效应正在发生。

计算容量的监控还有一个进阶视角：**按业务属性分组看水位**。全局平均水位 60% 可能掩盖了"CPU 型节点 90%、通用节点 40%"的结构性失衡——这种失衡靠加机器解决不了，要靠调度策略与 flavor 规划调整。把容量指标按 aggregate/availability zone 分组聚合，结构性问题才会现形。

**存储容量**：Cinder 各后端的容量水位、Glance 存储池的水位。这里有个容易混淆的点：Ceph 后端的容量归 Ceph 集群管（见 Ceph 监控篇），Cinder 侧只是周期性上报——两边对不上时优先信 Ceph 侧的数字，因为它是数据面真正写入的地方。Glance 的存储池如果与 Cinder 共用一套 Ceph，还要叠加考虑两者的容量竞争。

**配额水位**：大租户的配额使用率是容易被忽略的金矿指标。配额打满会引发业务方的"故障"——创建实例突然失败，而业务方往往把它当成平台故障来投诉。给配额使用率超过 80% 的大租户发预告，是运维与业务方建立信任的低成本方式：一条"您的配额两周内将耗尽"的预告，比十条"创建失败"的事故报告更能体现运维的专业性。

容量监控的终极形态是**容量预测**——基于历史增速外推"还能撑多久"。PromQL 的 `predict_linear` 能做线性外推，更精细的做法是把月度巡检的容量数据导出来做趋势分析（业务的增长往往有季节性，线性外推在业务高峰期会失准）。容量预测的产出应当进入月度容量报告，作为扩容决策的数据支撑——"按当前增速，计算资源将在 11 月中旬耗尽"这句话，比"资源有点紧张"有力得多。

### 2.3 性能层：API 延迟是控制面的体温计

性能指标里最实用的是 **API 延迟**。openstack-exporter 从较新版本起提供了 API 请求时延指标（按服务与方法细分），老版本可以用黑盒探针补齐——定期执行轻量 API 调用并计时，记录分位数（P50/P95/P99）。

API 延迟之所以是"体温计"，是因为它处在所有控制面故障的下游——数据库慢了它先变慢，MQ 卡了它先变慢，Keystone 风暴它先变慢。把 API 延迟作为第一层告警，等于给整个控制面装了一个综合探测器：它不告诉你根因在哪，但它能最快告诉你"出事了"。

API 延迟是控制面健康的综合体温计：数据库慢查询、MQ 积压、Keystone token 风暴、Galera 流控，最终都会体现在 API 延迟曲线上。它的价值不在于单点读数，而在于**趋势与关联**——延迟曲线抬头的时间点，与变更记录、流量高峰对齐，根因往往就藏在交点里。笔者见过太多"API 变慢"的排查，最后在变更记录里找到答案：某次批量任务把数据库打慢了，而 API 延迟曲线忠实地记录了这一切。

实例启动时长是另一个金指标：从 `BUILD` 到 `ACTIVE` 的耗时分布。它的恶化往往先于用户投诉，且能定位到具体环节——镜像下载慢看 Glance 与网络，调度慢看 filter 日志，网络注入慢看 Neutron。把启动时长的 P50 与 P95 分开看，P95 的恶化比 P50 更早暴露长尾问题：P50 稳定而 P95 飙升，说明多数实例正常但少数走了慢路径（譬如命中了冷缓存的主机），这种结构性问题只有分位数能暴露。

性能监控还有一个容易忽略的维度：**性能的基线管理**。同样的 API 延迟，在业务高峰期是正常的，在凌晨三点就是异常——静态阈值无法区分这两种场景。解法是建立"时间感知"的基线：按小时/星期维度记录历史分位数，用当前值与同时段基线的偏离度做判断。基线数据的积累需要时间（至少四周），这也是性能告警往往要上线数月后才能调准的原因——急不得。

### 2.4 消息队列与数据库：地基的监控

MQ 与数据库是控制面的地基（02 篇已详述），监控上要单独对待——它们不来自 openstack-exporter，而来自 RabbitMQ 与 MariaDB 自己的 exporter。

**RabbitMQ 侧**的四个关键指标：队列深度（积压的第一信号，正常情况下消息队列的深度应该在个位数到几十之间波动，持续增长意味着消费者跟不上）；消费者数量（消费者掉线会导致消息堆积，而 OpenStack 服务的消费者掉线往往意味着该服务出问题了）；连接数（连接风暴的前兆，服务重启潮会表现为连接数剧烈波动）；未确认消息数（消费者收到但没处理完的消息，持续增长说明消费者处理能力不足）。

**MariaDB/Galera 侧**的四个关键指标：集群节点数（必须为奇数且全员在线，少一个节点就进入降级状态）；流控暂停次数（Flow Control 是 Galera 过载的直接表现，频繁流控说明写入压力超过集群消化能力）；慢查询计数（OpenStack 的数据库 schema 复杂，慢查询是 API 延迟恶化的常见根因）；连接数水位（每个 OpenStack 服务都维护连接池，连接数耗尽的故障表现为大面积 API 报错）。

笔者的经验是：**OpenStack 监控体系的一半其实在基础设施层**。MQ 与数据库的故障占控制面故障的大头，而它们的监控指标与 OpenStack 服务无关——这个认知能避免"监控都配了还是漏报"的困惑。监控的覆盖范围应当按故障分布来设计，而不是按服务边界来设计。

基础设施层监控还有一个特殊性：**它的告警要"抢跑"**。MQ 队列从积压到服务超时之间有缓冲时间，Galera 从流控到集群不可用之间也有过程——这些"过程指标"是抢跑告警的依据。等"MQ 不可用"的告警触发时，故障已经发生；而"队列深度持续增长"的告警，能在故障发生前 20 分钟给出干预窗口。抢跑告警的价值换算成故障恢复时间，是任何精细面板都替代不了的。

MQ 与数据库的告警阈值也要单独调校：RabbitMQ 的队列深度告警不能一刀切——控制面的队列（譬如 nova 的调度队列）深度超过 100 就该警觉，而遥测类队列（Ceilometer 的样本队列）天然吞吐大，阈值要放宽一个数量级。给不同业务语义的队列配不同的阈值，需要先搞清楚每条队列的"正常形态"——这没有捷径，只能靠观察与记录。

### 2.5 实例状态与调度健康：从状态分布看问题

实例的状态分布是一个容易被低估的指标。`openstack server list --all-projects` 按 vm_state 统计，正常集群的分布应当是绝大多数 ACTIVE、极少数 SHUTOFF、ERROR 接近于零。这个分布的**形状变化**比绝对数值更有信息量：ERROR 实例数突然抬头，说明某个环节出了问题——可能是某台计算节点的存储满了，可能是镜像服务异常，也可能是某次变更引入的回归。把 ERROR 实例按宿主机分组统计，还能进一步定位到"是不是某台主机的问题"。

调度健康是另一个值得单独监控的维度：调度成功率（成功调度的请求数 / 总调度请求数）与调度耗时。调度成功率下降的常见根因是资源碎片化——集群总容量够，但没有任何单台主机能放下请求的规格。这种问题靠容量指标发现不了（总量充足），靠调度失败告警才能暴露。

与 04 篇的 Nova 链路呼应：监控的指标设计应当沿着调用链布置——API 层看延迟与错误率，调度层看成功率与耗时，compute 层看 build 失败率。每条链路环节有自己的指标，故障发生时才能快速定位断点，而不是在几百个指标里大海捞针。

### 2.6 指标命名与标签的设计约定

监控体系要长期运营，指标命名与标签的规范性决定了后续分析的成本。三条约定：

**约定一：标签的基数纪律。** 每个标签的取值数量（基数）要可控——`service` 标签只有几十个取值，安全；`instance_uuid` 有上万个取值，危险。给实例级别的指标打 uuid 标签之前，先问自己：这个粒度的数据有人看吗？告警用得到吗？

**约定二：指标名带服务前缀。** openstack-exporter 的指标已经带了前缀（openstack_nova_*、openstack_neutron_*），自建指标也应当遵循同样的命名空间——混入基础设施指标（node_*、mysql_*）时能一眼区分层次。

**约定三：单位进指标名。** 字节、毫秒、百分比在指标名里显式声明（`_bytes`、`_ms`、`_ratio`），避免面板上出现"这个数字是 MB 还是 GB"的灵魂拷问。

命名约定之外，还有一条团队约定值得建立：**指标的 owner 制度**。每条告警规则、每个核心指标都要有明确的负责人——负责人不一定亲自处理所有问题，但他要能回答"这个指标为什么存在、阈值为什么是这个值"。没有 owner 的指标，半年后就没人敢动，也不敢删，最后变成谁也看不懂的祖传配置。

### 2.7 各服务的专属指标

除了通用的服务健康指标，每个核心服务都有值得单独监控的专属指标。这里按服务过一遍，每一条都来自真实的运维痛点。

**Nova 侧**：实例状态分布（前文已述）、调度失败计数（`No valid host` 的次数趋势，突然抬头说明资源碎片化或规格配置问题）、build 耗时分布（镜像缓存命中的试金石）、服务心跳（与 04 篇的 service_down_time 呼应）。Nova 的指标价值在于**实例是平台的最终产品**——用户感知到的所有问题，最终都会落到实例状态上。

**Neutron 侧**：端口数量与状态分布（DOWN 端口的堆积说明清理逻辑有问题）、L3 agent 的 router 分布（集中式路由下 network node 的 router 数量是容量指标）、DHCP agent 的健康。Neutron 的故障往往表现为"部分实例网络不通"而不是"服务 down"，所以端口级的指标比服务级的更有排障价值。

**Cinder 侧**：各后端的容量与卷数量、卷状态分布（卡在 attaching/detaching 的卷是故障前兆）、backup 任务的成功率。Cinder 的状态机复杂，卡状态的卷需要专门的巡检兜底（监控指标发现不了"卡住"，只能发现"消失"）。

**Glance 侧**：镜像数量与大小分布、上传/下载的成功率与耗时。镜像服务的故障影响面是"所有新创建的实例"，它的监控优先级往往被低估——直到某天镜像上传全部失败，才发现 Glance 的 store 后端早就满了。

**Keystone 侧**：token 签发速率（token 风暴的前兆）、认证失败率（突增可能是密码扫描攻击）、Fernet key 的轮换状态。Keystone 是所有 API 的前置依赖，它的性能指标要单独建面板。

这五个服务的专属指标加起来大约三四十条，全部接入并不费力，但它们覆盖了 80% 的日常排障场景。监控体系的建设顺序建议是：先通用健康层（一天搭完），再容量层（一周），最后逐服务补专属指标（持续迭代）——不要试图一次建全。

### 2.8 日志监控——指标之外的第三只眼

指标擅长回答"状态好不好"，但有些问题只藏在日志里——异常堆栈、认证失败、被拒绝的请求。日志监控的思路是把关键日志模式转成计数指标：Filebeat/Loki 采集日志后，按模式匹配计数（Traceback 出现次数、`No valid host` 出现次数、认证失败次数），再对这些计数告警。

日志监控的性价比取决于模式库的质量。起步阶段只需要五六个模式：各服务的 Traceback、`No valid host`、数据库连接失败、认证失败、MQ 连接失败。模式库随故障复盘持续扩充——每次故障的"标志性日志"都值得变成一条监控模式，这是把排障经验自动化成监控的最短路径。

### 2.9 监控指标的分级清单（速查）

把前文的核心指标收拢成一张速查清单，按优先级排列，新环境搭建监控时按序落地：

**第一批（第一天，健康层）**：

- 各服务 `openstack_service_up`（按 endpoint 细分）
- API 黑盒探活（从用户视角）
- exporter 自身的存活与抓取成功率
- MQ 集群节点数与队列深度
- Galera 集群节点数与流控状态

**第二批（第一周，容量层）**：

- 各 hypervisor 的 vCPU/内存分配率与使用率
- Cinder 各后端容量水位
- Glance 存储池水位
- 大租户配额使用率 TOP10
- 镜像存储占用

**第三批（第一个月，性能与业务层）**：

- API 延迟分位数（按服务与方法）
- 实例启动时长分布（P50/P95）
- 调度成功率与失败原因分布
- ERROR 实例增量趋势
- token 签发速率与认证失败率

**第四批（持续迭代，专属指标）**：

- 各服务专属指标（见 2.7 节）
- 日志模式计数（见 2.8 节）
- 跨服务链路指标（按故障复盘补充）

这份清单的价值不在全而在序——按批次落地，每一步都有独立的告警价值，不会陷入"要建就建全"的完美主义陷阱。

---

日志监控与指标监控的分工可以这样划：指标回答"多严重"，日志回答"为什么"。值班同事被告警叫醒后，第一跳是看指标定级（P0 还是 P1），第二跳就是看日志定因（哪个组件、什么错误）。日志监控把"第二跳"的部分工作前置——日志里的异常模式直接变成告警，等于把排障的第一步自动化了。

### 2.8 指标覆盖的差距审计

监控体系建成之后，定期做一次"覆盖差距审计"很有必要——方法是拿最近的故障复盘记录，逐条检查：这次故障，哪些指标提前给出了信号？哪些指标在故障期间是缺失的？审计的产出是一份"指标缺口清单"，指导下一阶段的补建。

审计时常见的三类缺口：**跨服务链路缺口**（每个服务都监控了，但"API 到数据库的整条链路耗时"没人算）；**业务视角缺口**（技术指标齐全，但"租户创建成功率"这种业务指标没有）；**基础设施缺口**（OpenStack 层监控完善，但 MQ/数据库的地基指标缺失）。三类缺口的补建优先级，按历史故障的分布定——故障最多的缺口先补。

## 第 3 章 告警设计——分级与去噪

### 3.1 分级模板

告警的价值密度取决于分级是否克制。一个设计良好的告警体系，P0 应当是稀缺的——它的稀缺性正是它权威性的来源。笔者的模板是三级：

在设计分级之前，先想清楚一个问题：告警是给谁看的？答案不是"运维"这么笼统——告警的读者是"此刻值班的那个人"，他的状态是刚睡醒、手边只有笔记本、对故障的上下文一无所知。分级、通知渠道、runbook，全都要围绕这个具体的人来设计。

| 级别 | 定义 | 响应要求 | 示例 |
| :--- | :--- | :--- | :--- |
| P0 | 数据面受损或控制面不可用 | 立即响应，电话叫醒 | API 全部不可用、MQ 集群故障、存储池写满 |
| P1 | 冗余降级或容量告急 | 工作时间处理 | 单控制节点 down、容量过 85%、单 MQ 节点离线 |
| P2 | 趋势与卫生 | 周会过一遍 | 配额使用率爬升、API 延迟缓慢上涨、证书 30 天内过期 |

分级的核心纪律是：**P0 的数量要少**。如果一周有三个 P0，要么是阈值太敏感，要么是平台真的不行——前者调阈值，后者做工程，总之不能让 P0 变成日常。P1 是"冗余还在但变薄了"的信号，它给的是工作时间内的修复窗口；P2 是给周会准备的议题，它的价值在趋势而非即时性——把 P2 当 P1 处理，是对运维精力的浪费；把 P1 当 P2 处理，是对故障的赌博。

分级的另一个维度是**时间敏感性**：P0 的通知必须穿透免打扰（电话/短信），P1 用即时消息，P2 用邮件。渠道的选择不是技术问题，而是组织约定——值班同事的手机必须能被 P0 叫醒，这条纪律要在团队里反复强调并演练。见过太多团队把所有告警都发到一个群里，结果 P0 与"某人忘了贴周报"在同一个信息流里竞争注意力，这是监控体系最隐蔽的失败形态。

### 3.2 PromQL 示例

几条实用的告警规则骨架（指标名以 openstack-exporter 实际暴露为准，不同版本有差异，落地时以 `curl /metrics` 的实际输出为准）：

```yaml
# P0：计算服务全下（所有 compute agent 都不可用）
- alert: NovaComputeAllDown
  expr: sum(openstack_nova_agent_state{service="compute", admin_state="up"}) == 0
  for: 3m

# P1：单计算节点失联（心跳丢失，给维护窗口留余量）
- alert: NovaComputeSingleDown
  expr: openstack_nova_agent_state{service="compute"} == 0
  for: 10m

# P1：磁盘容量预测（按当前增速 8 天内写满）
- alert: CinderBackendFillingUp
  expr: >
    predict_linear(cinder_volume_usage{type="used"}[6h], 8*24*3600)
    > scalar(cinder_volume_usage{type="total"})

# P2：证书 30 天内过期
- alert: KeystoneCertExpiring
  expr: openstack_keystone_cert_expiry_days < 30
```

`predict_linear` 是容量告警的利器——它不看静态水位，而看趋势斜率，"增速快的 80%"比"增速慢的 90%"更危险，静态阈值表达不了这个判断。这四条规则的共同点是：**每条都对应一个明确的处置动作**。NovaComputeAllDown 对应"查控制面"，NovaComputeSingleDown 对应"查那台节点"，CinderBackendFillingUp 对应"启动扩容流程"，KeystoneCertExpiring 对应"换证书"。没有处置动作的告警，无论指标多漂亮，都不该存在。

这四条规则之外，还有一类特殊的告警值得单独设计：**"没有数据"的告警**。指标断流（exporter 挂了、抓取失败）在 Prometheus 里表现为"时间序列消失"，普通的阈值告警不会触发——需要用 `absent()` 或 `count_up` 类函数显式检测。监控自身的健康是所有告警的前提，这类"元告警"应当第一批上线。

写 PromQL 时有几个实用的技巧值得记下：其一，`for` 的取值要与指标的自然波动周期匹配——容量类指标分钟级不会突变，`for: 30m` 也不迟；其二，聚合要先用 `by` 缩小范围再判断，避免全局聚合掩盖局部故障；其三，阈值判断尽量用比例而不是绝对值——"错误率超过 5%"比"错误数超过 100"在流量波动时稳定得多。这三条能解决大部分"告警一上线就狂响"的问题。

### 3.3 去噪三板斧

告警疲劳是监控体系的头号杀手——值班同事对告警群麻木的那一天，就是 P0 被漏掉的那一天。去噪有三板斧。

**第一板斧：`for` 持续时长。** 瞬时抖动不告警——`for: 3m` 意味着条件持续 3 分钟才触发，能滤掉绝大部分毛刺。P0 的 for 要短（3 分钟），P2 的 for 可以长到小时级。for 的取值本质上是"误报成本"与"漏报成本"的权衡：P0 漏报成本高，for 就短；P2 误报成本高（打扰周会），for 就长。

for 的另一个作用是给"自动恢复"留时间：很多瞬时故障会被 OpenStack 的自愈机制消化（服务自动重连、实例自动重调度），for 的窗口就是给自愈机制留的缓冲。判断一个告警该不该加 for，可以问一句：这个条件如果 5 分钟后自己恢复了，我还需不需要被叫醒？答案是否，就加 for。

**第二板斧：分组聚合。** 同一故障域的十条告警合并成一条——譬如网络抖动会导致十台 compute 同时掉线，十条"节点失联"告警应该聚合成一条"网络疑似故障"。Prometheus 的 `group_by` 与 Alertmanager 的 group 机制都是为此而生。聚合的粒度是门手艺：按故障域聚合（同一机架、同一网段），而不是简单地按告警名聚合。

聚合的落地依赖标签设计——如果 compute 节点的指标没有"机架"标签，按故障域聚合就无从谈起。这又回到了 CMDB 与标签规范：监控的聚合能力，上限是标签体系的完备度。标签体系的投入在监控建设之前，回报在每一次故障定位之中。

**第三板斧：抑制规则。** P0 触发时抑制其衍生的 P1/P2——MQ 集群故障会连带几十个服务异常，根因告警触发后，衍生告警全部静默。没有抑制规则的告警体系，在真正的 P0 面前会变成噪音海啸，而噪音海啸会淹没真正的根因线索。

### 3.4 通知渠道的设计

告警触发后走什么渠道，与分级强相关。P0 走电话或即时消息的强提醒（值班手机必须能被叫醒）；P1 走即时消息的普通通知（工作时间内可见即可）；P2 走邮件或周会（根本不需要实时性）。渠道设计的常见错误是"所有告警进一个群"——群消息的洪水会让 P0 与 P2 在同一个列表里滚动，P0 被看到时已经过去两小时。

另一个实践细节是**值班轮转与告警路由**：告警应当发给"当前值班的人"而不是"所有人"。Alertmanager 的 route 配置支持按标签路由到不同的接收组，P0 走电话组、P1 走值班群、P2 走邮件列表。值班交接时的路由切换要自动化（与排班表联动），靠人肉改配置的值班路由，迟早会在交接日漏掉告警。

通知内容的信息密度也有讲究：一条好的告警通知应当包含"是什么、在哪、多严重、第一步做什么、runbook 链接"五要素。Alertmanager 的模板支持把标签值注入通知文本，把 `{{ $labels.service }}` 与 `{{ $labels.host }}` 拼进通知，值班同事不用打开 Grafana 就知道该往哪看。通知模板的一次投入，换来的是每次告警的效率提升——这是监控体系里回报率最高的十分钟投入。

### 3.5 告警的验收与演练

告警规则上线不等于告警体系建成——**没有触发过的告警等于没有告警**。每条新告警规则都应当经过一次人工触发验证：在测试环境制造对应故障（停掉一个服务、填满一个磁盘），确认告警能触发、通知能送达、runbook 链接能打开。这个验收步骤能过滤掉大半的"纸面告警"——表达式写错、标签不匹配、通知渠道配错，都是验收才能发现的问题。

演练则更进一步：每季度做一次"告警-预案"对练，随机抽一条历史告警，按 runbook 走一遍处置流程。演练暴露的问题（runbook 过时、命令失效、依赖的人不在）在真实故障前修掉，才是演练的意义。告警体系与消防系统一样，平时不演练，战时必掉链子。

### 3.7 起步告警规则清单（速查）

新环境搭建告警时，按此清单从上到下落地，每条都标注了分级与建议阈值：

**P0 级（立即响应）**：

- 所有 compute agent 不可用（for: 3m）
- Keystone API 探活失败（for: 3m）
- MQ 集群不可用（quorum 丢失，for: 1m）
- Galera 集群节点数 < 3（for: 1m）
- Cinder 后端容量 100%（for: 5m）

**P1 级（工作时间处理）**：

- 单 compute agent 失联（for: 10m）
- 单 MQ 节点离线（for: 10m）
- Galera 流控频繁触发（for: 15m）
- 容量预测 8 天内写满（趋势告警）
- API P95 延迟超过基线 3 倍（for: 15m）
- ERROR 实例 1 小时内新增超过 10 台

**P2 级（周会过一遍）**：

- 容量水位超过 80%（趋势）
- 配额使用率超过 80% 的大租户
- 证书 30 天内过期
- API 延迟基线偏离持续一周
- 孤儿资源数量环比上升

**元告警（监控自身）**：

- exporter 抓取失败（for: 10m）
- 指标断流（absent 检测，for: 10m）
- 告警通道自身探活失败

这份清单是起点而非终点——每条规则的阈值都要按自己平台的基线校准，清单之外的新规则按"有处置动作才准入"的原则增补。

演练的形式可以很轻：月度值班例会上抽 10 分钟，随机挑一条本周告警，让值班同事口述"如果这条告警半夜触发，你会怎么做"。口述暴露的知识缺口，比真实故障暴露的成本低得多。这种轻量演练没有排期负担，却能把 runbook 的更新频率提高一个数量级。

### 3.6 变更与告警的联动

告警体系最大的噪音源不是阈值，而是**变更**——每次升级、扩容、迁移都会触发一批"预期内"的告警，如果不做处理，值班同事要么被轰炸，要么学会无视告警（后者更危险）。

解法是**维护窗口的静默机制**：变更前，把受影响范围的告警静默（Alertmanager 的 silence 机制，按标签匹配），变更结束后解除。静默的粒度要精确——升级 compute-03 时只静默 compute-03 相关的告警，而不是把整个集群静默。静默期间出其他故障怎么办？静默只屏蔽"预期内的告警"，预期外的告警（譬如静默期间另一台节点挂了）必须照常触发——这要求静默规则按主机标签精确匹配，而不是一刀切。

变更与告警的联动还有一个反向价值：**变更后的告警数据是变更质量的验收单**。升级后 24 小时内，如果相关告警清零且 API 延迟平稳，变更才算真正成功；如果告警清零但延迟曲线抬头了，说明升级引入了性能回退——这种回退靠功能验证发现不了，只有监控能抓住。

## 第 4 章 与 VictoriaMetrics 生态的衔接

VictoriaMetrics 兼容 Prometheus 的抓取与查询协议，OpenStack 的指标可以直接用 vmagent 抓取 openstack-exporter 并 remote-write 到 VM 集群。对于已经在用 VictoriaMetrics 的团队（譬如大数据平台的监控体系），OpenStack 的指标接入几乎是零成本的——加一个 scrape 配置即可。衔接时有三个实践要点。

**指标基数控制**：openstack-exporter 的部分指标按租户/实例打标签，实例数上万时时间序列基数会膨胀，VM 的内存与磁盘压力随之上升。用 `metric_relabel_configs` 裁剪低价值标签（譬如不需要按实例细分的指标就丢掉实例标签），基数能降一个数量级。基数管理的原则是：**按需保留**——告警与面板用到的标签才保留，"以后可能有用"的标签一律裁掉，真需要时再改配置重抓。

基数膨胀的征兆要会识别：vmagent 或 VM 的内存缓慢上涨、磁盘写入速率持续增加、查询变慢——这些都可能是新指标或高基数标签引入的。定期（每月）用 VM 的 `top-series` 接口查看基数最大的时间序列，是时序库运维的基本功。

**长期趋势与实时告警分库**：实时告警走短保留周期的高性能实例（15 天保留足够），长期趋势走降采样存储（一年以上），查询体验与存储成本兼得。容量趋势分析用长保留库——容量预测需要至少半年的历史数据才能看出季节性规律；值班告警用短保留库——查询快、定位准。两条管道互不干扰。

**Grafana 面板**：社区有现成的 OpenStack dashboard（按服务健康/容量/性能分层组织），自建面板时按"先容量后性能再健康"的顺序排布，与值班的心智模型一致。面板的第一屏应当是"一图看全平台"——四个层次各取一两个代表指标，30 秒内判断平台是否健康，细节下钻留给第二层。面板设计的最大误区是把所有指标都塞进第一屏，结果谁也不看。

vmagent 抓取 openstack-exporter 的配置要点清单：

- scrape_interval：60s（与 exporter 的轮询周期错开，避免叠加压力）
- 抓取超时：要大于 exporter 完成一轮全量 API 查询的耗时（可先实测）
- relabel：裁剪高基数标签（instance_uuid 等）
- remote_write：队列与重试参数按 VM 集群的容量调
- external_labels：打上集群/环境标签（多套 OpenStack 环境共用 VM 时必需）

这五项配置的顺序就是排障顺序：抓不到先看 scrape 配置，数据异常再看 relabel，存储压力再看 remote_write。

第一屏的推荐布局可以具体化：左上放服务健康总览（各服务 up 状态的着色矩阵，一格一个服务，绿/红一目了然）；右上放容量水位条（计算/存储/配额三个横向进度条，85% 以上变黄）；左下放 API 延迟趋势（最近 6 小时的 P95 曲线）；右下放 MQ 与数据库的迷你图。这一屏不追求信息完整，只追求"异常能被看见"——看到异常后，值班同事再按服务跳转到细节面板。

### 4.2 与既有监控体系的关系

大数据中心的监控体系往往是多套并存——基础设施层有 Zabbix 或 Prometheus，应用层有各自的 APM，OpenStack 的指标接入时要回答"放哪里、怎么融合"。笔者的建议是：**指标统一入湖（VM/Prometheus），告警统一通道，面板按受众分**。OpenStack 的指标与 Ceph、Kubernetes 的指标进同一个时序库，跨系统的关联分析才有可能——譬如"实例 IO 慢"的排查需要同时看 Nova、Cinder 与 Ceph 的指标，三套割裂的监控体系会让关联分析变成人工搬运数据。

统一入湖的落地顺序也有讲究：先把 exporter 的指标接进来（成本最低），再把基础设施层（MQ/DB）的指标接入（价值最高），最后考虑跨系统的标签打通（譬如给 OpenStack 指标打上"该实例对应的 Ceph 卷"标签，实现存储链路的关联查询）。标签打通是关联分析的基础，但它的前提是各系统的命名规范能对上——这又回到了 CMDB 与命名规范的老话题。

## 第 5 章 巡检自动化

监控解决"异常发现"，巡检解决"慢性病筛查"——两者互补而非替代。监控看的是实时指标，巡检查的是指标覆盖不到的账实关系与卫生状况：Placement 的账实对账、孤儿端口的清理、证书的有效期、备份的可恢复性——这些都不是时间序列指标，而是需要主动查询核对的离散事实。

OpenStack 的巡检天然适合脚本化：所有巡检项都是 API 调用或 CLI 查询，输出 JSON 后用规则判断即可。巡检清单的分层：

| 频率 | 巡检项 | 产出 |
| :--- | :--- | :--- |
| 每日 | 服务状态、ERROR 实例增量、MQ 队列深度、容量水位 | 巡检日报 |
| 每周 | 配额使用率 TOP10、孤儿资源对账（allocation/端口）、证书有效期 | 周报 + 整改单 |
| 每月 | 容量趋势预测、性能基线对比、备份恢复演练 | 月度容量报告 |

这张表值得逐项展开。**每日巡检**的核心是"增量思维"——绝对值意义不大，与昨天比的变化才有意义：ERROR 实例从 2 涨到 3 没什么，从 2 涨到 30 就是事故前兆。**每周巡检**的核心是"账实核对"——Placement 的 allocation 与真实实例对账、Neutron 的端口与实例对账，孤儿资源是容量虚高的隐形推手。**每月巡检**的核心是"演练"——备份不演练等于没有备份，恢复演练暴露的问题（备份过期、恢复脚本失效、依赖缺失）只有在演练中才会现形。

把巡检脚本接入告警通道（发现异常时推送而非等人看日报），巡检就从"例行公事"变成了"第二道监控网"。巡检脚本本身也要被监控——脚本静默失败一周而无人知晓，是巡检体系最尴尬的死法。最简单的兜底是"心跳巡检"：脚本每次成功运行后写一个时间戳，监控侧检查时间戳的新鲜度，超过 25 小时没更新就告警。

每日巡检的清单再细化一层：服务状态看的是"enabled 且 up"的组合（disabled 的服务不参与调度，是维护中的正常态，不算异常）；ERROR 实例增量要与变更记录对照（变更日的 ERROR 增量有解释，无变更日的突增才是问题）；容量水位要看三个后端（计算/块存储/镜像）加三个水位（85/90/95），任何一条过线都要在日报里点名。



巡检清单的维护有一条经验：**每个巡检项都要有"发现过问题"的记录**。连续半年没有发现过任何问题的巡检项，要么是平台真的稳定，要么是检查方式错了——前者可以降频，后者应该修检查逻辑。巡检清单不是越全越好，每一项都要能回答"它上次发现问题是什么时候"，回答不了的项就该被优化或移除。

巡检与监控的分工可以用一个例子说明：监控发现"某计算节点内存使用率 90%"（指标异常），巡检发现"该节点上 20 台实例里有 15 台是僵尸实例"（账实关系）——前者是实时状态，后者是长期积累的数据卫生问题，两者需要不同的工具。监控负责"现在好不好"，巡检负责"底子干不干净"，缺了哪一个，另一个都会被拖垮。

两者的边界用一张表划清：

| 维度 | 监控告警 | 巡检脚本 |
| :--- | :--- | :--- |
| 时效 | 实时（分钟级） | 周期（小时到天） |
| 数据形态 | 时间序列 | 离散事实 |
| 典型问题 | 服务挂了吗、延迟高吗 | 账实相符吗、证书快过期吗 |
| 实现方式 | exporter + 告警规则 | API 脚本 + 规则判断 |
| 失败模式 | 漏报瞬时异常 | 静默失败 |

划清边界的意义在于避免重复建设：能用告警规则表达的就不要写巡检脚本，需要账实核对的就不要硬塞进告警规则。

### 5.2 一个巡检脚本的骨架

巡检脚本不需要复杂框架，一个 Python 文件加 cron 就够。骨架思路：

```python
#!/usr/bin/env python3
# 每日巡检骨架：每项检查返回 (名称, 是否异常, 详情)
checks = []
def check(name, ok, detail=""):
    checks.append((name, ok, detail))

# 1. 服务状态
out = run("openstack compute service list --format json")
down = [s for s in json.loads(out) if s["Status"] != "enabled"]
check("compute服务状态", len(down) == 0, f"异常: {down}")

# 2. ERROR 实例增量（与昨日对比）
# 3. MQ 队列深度（rabbitmqctl）
# 4. 容量水位（placement/cinder）

# 汇总推送：异常项进告警通道，全部正常写日报
bad = [c for c in checks if not c[1]]
if bad:
    push_alert(f"巡检异常 {len(bad)} 项: {bad}")
else:
    push_daily("巡检全部正常")
```

骨架的价值在于**结构而非代码**：每项检查独立、结果结构化、异常与正常分流。巡检项会随着运维经验的积累不断增删，好的骨架让增删变成加一行函数调用，而不是改一坨 if-else。

骨架的价值在于**结构而非代码**：每项检查独立、结果结构化、异常与正常分流。巡检项会随着运维经验的积累不断增删，好的骨架让增删变成加一行函数调用，而不是改一坨 if-else。

巡检项的起步清单（与监控指标互补，侧重"账实核对"）：

- 服务状态核对：`openstack compute service list` 中 enabled 且 up 的服务数
- ERROR 实例清单：与昨日对比增量，列出 fault 信息
- Placement 对账：allocation 数与实例数核对，列出孤儿 allocation
- 端口对账：无实例归属的 DOWN 端口清单
- 卷状态核对：卡在 attaching/detaching/detaching 超过 10 分钟的卷
- 证书有效期：所有 HTTPS endpoint 证书的剩余天数
- 备份新鲜度：最近一次成功备份的时间与大小
- 容量三水位：计算/块存储/镜像的 85/90/95 水位核对

巡检脚本的工程化还有三点实践：其一，凭据与告警通道配置放独立配置文件，脚本进版本库、配置不进（与 .env 的分离同理）；其二，每次巡检的完整输出存档（哪怕没人看），故障复盘时"当时的巡检数据"是宝贵的第一现场；其三，巡检脚本的变更也要走 review——一个写错的巡检脚本比没有巡检更危险，因为它会给出错误的"一切正常"。

### 5.3 巡检结果的运营

巡检产出如果不被消费，巡检就会退化成形式主义。运营巡检结果有三个层次：**日报自动生成**（异常项高亮、正常项折叠，值班同事 30 秒扫完）；**整改单闭环**（周报里的异常项必须有人认领、有时限、有回执，否则巡检发现的永远是同一批问题）；**趋势入库**（巡检数据写入时序库，与监控指标同屏展示——巡检发现的"账实偏差"趋势，往往比单次偏差值更有预警价值）。

### 6.1 告警的 runbook 化

每条 P0/P1 告警都应当挂一个 runbook 链接——告警通知里直接可点的那种。runbook 的最小内容：这个告警说明什么、第一步做什么、需要哪些权限、升级给谁。没有 runbook 的告警，等于让每个值班同事在凌晨三点从零开始推理——同样的故障，第一个人排查两小时，第十个人还要排查两小时，这就是没有沉淀的代价。

runbook 的维护是持续工作：每次真实故障复盘后，把新的排查路径回填到对应告警的 runbook 里。判断 runbook 是否健康的标准很简单：新值班同事拿着它能不能独立处置？如果答案是否，说明 runbook 写的是"作者的记忆"而不是"读者的地图"。

runbook 与监控的衔接可以做成硬约束：Alertmanager 的告警通知模板里强制带上 runbook 链接字段，没有 runbook 的告警规则不允许合入——用流程的刚性弥补自觉性的弹性。runbook 本身建议放在知识库里（譬如本仓库）而非文档工具里，让链接长期有效。

## 附：常见问题速答

**问：openstack-exporter 和 Ceilometer 什么关系？选哪个？**

答：定位不同。exporter 面向运维监控（拉取状态、暴露指标），Ceilometer 面向计量计费（采集事件与样本）。运维监控选 exporter，计量审计用 Ceilometer，两者可以共存。

**问：指标抓取间隔设多少合适？**

答：60 秒以内。exporter 每次抓取要调用几十个 API，间隔过短会给控制面压力，过长会漏掉瞬时异常。60 秒是平衡点。

**问：告警发到哪个群？**

答：按分级路由——P0 电话叫醒，P1 值班群，P2 邮件。所有告警进一个群是告警疲劳的头号来源。

**问：监控指标断流了怎么排查？**

答：先查 exporter 进程与抓取任务（监控自身的健康），再查 Keystone（exporter 的认证依赖），最后查网络路径。断流本身要有告警，否则你不会知道监控已经失明。

## 第 6 章 小结## 第 6 章 小结

OpenStack 监控体系的设计要点可以收拢成三句话：**指标按四层组织，告警按三级克制，巡检与监控互补**。工具层面，openstack-exporter 加 VictoriaMetrics 是当前社区的主流组合，但工具永远是最容易的部分——难的是定义"什么状态该叫人"，而这需要对你平台上业务形态的理解。

监控体系的成熟度，最终体现在值班同事的睡眠质量上。告警少而准、趋势有预告、预案有演练——做到这三点，OpenStack 的运维就从救火队变成了工程学科。监控不是一次性的建设项目，而是持续运营的治理过程：每季度回顾一次告警质量、每半年校准一次容量模型，让体系跟着平台一起长大。

衡量这套体系是否成功，可以设三个检验点：第一，过去一个月的 P0 是否都在 5 分钟内被发现（发现能力）；第二，每条 P1 是否都有 runbook 且能照着走（处置能力）；第三，容量决策是否有数据支撑而非拍脑袋（预测能力）。三个检验点都过关，监控体系才算从"建成了"走到"用起来了"。

建设节奏上，笔者的建议是分三步走：第一步（一周）搭健康层与基础告警，让"服务挂了"能被叫醒；第二步（一个月）补容量层与性能层，让"快出事"能被预告；第三步（持续）建业务层与巡检自动化，让运维从被动响应转向主动治理。三步之间不要跳级——没有健康层打底的性能告警，只会让值班同事在噪音里怀疑人生。

监控体系还有一个常被忽视的产出：**它是最诚实的架构文档**。指标的组织方式暴露了系统的真实依赖关系，面板的布局反映了运维的心智模型，告警的分级体现了风险偏好。新接手一个平台的运维，从监控体系的现状就能读出前任的运维哲学——这也是为什么监控体系要持续治理：它不仅是工具，更是团队运维能力的镜子。

最后回答一个常见问题：OpenStack 的监控要不要用 Ceilometer/Aodh/Gnocchi 这套原生遥测栈？笔者的看法是：它们的设计目标是计量计费与资源审计（Ceilometer 采集事件与样本、Gnocchi 存时序、Aodh 做告警），与运维监控的场景有重叠但侧重不同。如果团队已经用 Prometheus 生态，openstack-exporter 的方案更轻、更成熟；Ceilometer 更适合作为事件源补充（譬如审计实例生命周期事件）。两者不互斥，但不要为了"用原生组件"而把运维监控架在为计费设计的栈上——工具的取舍，永远看场景而不是看出身。

> [!note] 思考题
> 1. openstack-exporter 抓取一次全量指标需要调用几十个 API，如果 Keystone 响应变慢，监控指标会出现什么形态的异常？如何区分"平台真的慢"与"监控自身失明"？
> 2. 容量告警线设 85% 的依据是"给扩容留执行时间"。如果你的扩容是自动化的一键加节点（10 分钟完成），告警线应该怎么调？由此推演：告警阈值与运维自动化程度之间的普遍规律是什么？
> 3. 设计一个"告警质量"的度量方案：如何量化过去一个月的告警中，多少比例是有效告警、多少是噪音？用什么指标驱动告警规则的持续优化？

这张表还有一个隐藏用法：**它定义了监控建设的优先级**。健康层一天就能搭完（几个探针加 exporter），容量层需要一周（要理清各服务的容量口径），性能层需要持续迭代（分位数与基线要积累数据），业务层则需要与业务方共同定义。按这个顺序建，每一层的投入都有前一层作为地基，不会出现"面板华丽但连服务挂了都不知道"的倒挂。

黑盒探活的实现很轻：一个定时任务从用户视角的网络位置发起请求（list 一个最小的资源集合），记录返回码与耗时，失败即告警。探活的频率是成本与灵敏度的权衡——每分钟一次足以捕捉持续故障，也几乎不构成 API 压力。要注意的是探活凭据的管理：探针用的 token 过期会表现为"全部探活失败"，与真实故障难以区分，所以探针账号要用长期有效的凭据并单独监控。

巡检数据入库还有一个衍生价值：**它是自动化决策的输入**。譬如"孤儿资源对账"的数据积累到一定程度，就能回答"孤儿资源的产生速率是否在上升"——如果上升，说明删除流程有回归，需要排查；如果稳定，说明是常态损耗，按周期清理即可。数据不积累，判断就只能靠感觉。
