# Kubernetes 架构原则与对象设计专栏导览

## 这个专栏回答什么问题

学 Kubernetes 的人常常卡在同一个地方：命令会用，YAML 会抄，但一旦遇到"为什么这个字段不能改""为什么删了 Deployment 之后 Pod 还在转圈""为什么改了 ConfigMap 容器没反应"，就只能靠搜索和试错。这类问题的答案不在任何一个组件内部，而在 K8s 对外暴露的那层**接口契约**上。

本专栏不讲组件怎么实现，讲的是这套接口**为什么被设计成这样**。用一句话概括它的主线：

> Kubernetes 把"运行在集群上的应用"抽象成一组**可声明、可关联、可持久化、可扩展**的 API 对象；理解了这四件事，就理解了 K8s 的全部对外行为。

四个关键词对应四条主线，也是六篇文章的骨架：

| 主线 | 回答的问题 | 承载文章 |
| --- | --- | --- |
| **可声明** | 用户凭什么只写"想要什么"，系统就能自己做到 | 01、02 |
| **可关联** | 对象之间不写死名字，靠什么建立关系 | 03、04 |
| **可持久化** | 这些对象存在哪里、版本语义如何保证 | 06 |
| **可扩展** | 不改进程、不重新编译，怎么长出新的对象类型 | 03 |

## 叙事弧：一条从"经验"到"契约"的路径

本专栏的六篇文章不是六个并列的知识点，而是一条单向推进的论证链：

1. **先有经验，后有原则**（01）。Google 用 Borg 和 Omega 在内部试错了十年，K8s 是这套经验面向外部世界的重新表达。声明式、控制器模式、面向终态、Level-triggered、松耦合这五条原则，每一条都能在 Borg 的某个具体设计或某次失败里找到出处。
2. **原则必须落到边界上**（02）。原则是抽象的，架构是具体的——控制平面与数据平面之间、组件与组件之间画的那几条线，就是原则的物理形态。这一篇只关心"线画在哪、为什么画在这"，组件内部机制留给兄弟专栏。
3. **边界之内是对象模型**（03）。所有跨越这些边界的通信，传的都是同一种东西：`TypeMeta + ObjectMeta + Spec + Status` 的四段式对象。统一结构换来了通用工具链，代价是每个对象都必须接受同一套元数据约束。
4. **对象之间靠标签说话**（04）。K8s 拒绝外键式的硬引用，改用"贴标签 + 按标签筛选"。这不是风格偏好，而是为了让副本可以被随意替换——替换的前提是"关系不依赖于身份"。
5. **对象最终要表达工作负载的语义**（05）。Pod、Deployment、StatefulSet、DaemonSet、Job 不是五种配置模板，而是五组**不同的不变量承诺**。选型的本质是问自己"我的应用需要系统替我保证哪一条"。
6. **所有承诺都要落到磁盘上**（06）。对象的每一次变更都要经过 etcd 的 Raft 复制与 MVCC 版本管理，`resourceVersion`、Watch、List-Watch、Lease 这些机制全部是 etcd 语义在 K8s 侧的回声。
