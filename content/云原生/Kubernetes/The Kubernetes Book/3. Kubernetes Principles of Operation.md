## Kubernetes 40,000 英尺高空俯瞰

Kubernetes 具有以下双重身份：

- 一个[[集群]]
- 一个[[编排器]]

### Kubernetes：集群

Kubernetes 集群是一个或多个提供 CPU、内存和其他资源供应用程序使用的[[节点]]。

Kubernetes 支持两种节点类型：

- [[控制平面节点]]
- [[工作节点]]

> [!INFO] 节点类型说明
> 两种类型都可以是物理服务器、虚拟机或云实例，并且都可以运行在 ARM 和 AMD64/x86-64 架构上。控制平面节点必须是 Linux，但工作节点可以是 Linux 或 Windows。

[[控制平面节点]]实现 Kubernetes 的智能，每个集群至少需要一个。然而，为了高可用性（HA），您应该运行三个或五个。

每个控制平面节点都运行每个控制平面服务。这些服务包括 [[API 服务器]]、调度器，以及实现云原生特性（如自愈、自动扩展和版本发布）的控制器。

[[工作节点]]是运行您业务应用程序的地方。

> [!TIP] 图示说明
> 图 2.1 展示了一个包含三个控制平面节点和三个工作节点的集群。
> 
> ```mermaid
> flowchart LR
>     subgraph CP["控制平面节点 (3个)"]
>         CP1["控制平面 1"]
>         CP2["控制平面 2"]
>         CP3["控制平面 3"]
>     end
>     subgraph W["工作节点 (3个)"]
>         W1["工作节点 1"]
>         W2["工作节点 2"]
>         W3["工作节点 3"]
>     end
> ```

在开发和测试环境中，在控制平面节点上运行用户应用程序是很常见的。但是，许多生产环境会将用户应用程序限制在工作节点上，以便控制平面节点可以集中资源处理集群操作。这样做可以让控制平面节点专注于管理集群。

### Kubernetes：编排器

编排器是用于部署和管理应用程序的系统的行业术语。

Kubernetes 是行业标准的编排器，可以智能地将应用程序部署到跨节点和故障区域，以获得最佳性能和可用性。它还可以在出现问题时修复，在需求变化时扩展，并管理版本发布和回滚。

这就是大局观。让我们更深入地了解一下。

## 控制平面和工作节点

我们已经说过，Kubernetes 集群由一个或多个控制平面节点和工作节点组成。

> [!IMPORTANT] 操作系统要求
> 控制平面节点必须是 Linux，但工作节点可以是 Linux 或 Windows。

几乎所有云原生应用程序都是 Linux 应用程序，需要 Linux 工作节点。但是，如果您有云原生 Windows 应用程序，您将需要一个或多个 Windows 工作节点。

幸运的是，单个 Kubernetes 集群可以混合使用 Linux 和 Windows 工作节点，Kubernetes 足够智能，可以将应用程序调度到正确的节点。

### 控制平面

[[控制平面]]是一组系统服务，实现了 Kubernetes 的核心功能。它公开 API、调度应用程序、实现自愈、管理扩展操作等。

最简单的集群运行单个控制平面节点，最适合实验室和测试环境。对于生产集群，您应该运行三个或五个控制平面节点，并将它们分布在多个可用区中以实现高可用性。

> [!TIP] 高可用性最佳实践
> 如前所述，在工作节点上运行所有用户应用程序通常是生产最佳实践，允许控制平面节点将其资源分配给集群相关的操作。
> 
> 大多数集群在每个控制平面节点上运行每个控制平面服务以实现 HA。

让我们更详细地了解主要的控制平面服务。

#### API 服务器

[[API 服务器]]是 Kubernetes 的前端，所有命令和请求都通过它。甚至内部控制平面服务也通过 API 服务器相互通信。

它通过 HTTPS 公开 RESTful API，所有请求都经过身份验证和授权。例如，部署或更新应用程序遵循以下过程：

1. 在 YAML 配置文件中描述应用程序
2. 将配置文件发布到 API 服务器
3. 请求将被身份验证和授权
4. 应用程序定义将被持久化到集群存储中
5. 应用程序的容器将被调度到集群中的节点

#### 集群存储

[[集群存储]]保存所有应用程序和集群组件的期望状态，它是控制平面中唯一的有状态部分。

它基于 etcd 分布式数据库，大多数 Kubernetes 集群为实现 HA 在每个控制平面节点上运行一个 etcd 副本。但是，对于经历高变更率的大型集群，可能会运行一个单独的 etcd 集群以获得更好的性能。

> [!WARNING] 备份与恢复
> 请注意，高可用性集群存储不能替代备份和恢复。当出现问题时，您仍然需要适当的方法来恢复集群存储。

关于可用性，etcd 倾向于使用奇数个副本以帮助避免脑裂情况。这是因为副本遇到通信问题，无法确定自己是否拥有多数票（仲裁）。

> [!TIP] 图示说明
> 图 2.3 展示了两组 etcd 配置遇到网络分区错误的情况。左侧的集群 A 有四个节点，正在经历脑裂，每侧两个节点，均无多数票。右侧的集群 B 只有三个节点，但没有经历脑裂，因为节点 A 知道自己没有多数票，而节点 B 和节点 C 知道自己有。
> 
> ```mermaid
> flowchart LR
>     subgraph ClusterA["集群 A (脑裂状态)"]
>         A1["节点 1"] <-->|网络分区| A2["节点 2"]
>         A3["节点 3"] <-->|网络分区| A4["节点 4"]
>         noteA["❌ 无多数票"]
>     end
>     subgraph ClusterB["集群 B (正常)"]
>         B1["节点 A"] -->|正常通信| B2["节点 B"]
>         B2 --> B3["节点 C"]
>         noteB["✅ 有多数票"]
>     end
> ```

如果发生脑裂，etcd 进入只读模式，防止对集群进行更新。用户应用程序将继续工作，但 Kubernetes 将无法扩展或更新它们。

与所有分布式数据库一样，写入一致性至关重要。例如，来自不同源的多个写入操作写入同一位置可能导致损坏。etcd 使用 RAFT 共识算法来防止这种情况发生。

#### 控制器和控制器管理器

Kubernetes 使用[[控制器]]来实现大量集群智能。每个控制器都作为控制平面上运行的进程，一些更常见的包括：

- [[Deployment 控制器]]
- [[StatefulSet 控制器]]
- [[ReplicaSet 控制器]]

还有很多其他的，我们稍后会在书中介绍。但是，它们都作为后台监控循环运行，将观察到的状态与期望状态进行协调。

这是很多术语，我们将在本章后面详细讨论。但现在，这意味着控制器确保集群运行您要求它运行的内容。例如，如果您请求三个应用副本，控制器将确保您有三个健康的副本，并在没有时采取适当的操作。

Kubernetes 还运行一个控制器管理器，负责生成和管理各个控制器。

> [!TIP] 控制器管理器架构
> 图 2.4 提供了控制器管理器和控制器的概要视图。
> 
> ```mermaid
> flowchart TD
>     CM["控制器管理器"]
>     CM --> DC["Deployment 控制器"]
>     CM --> SC["StatefulSet 控制器"]
>     CM --> RC["ReplicaSet 控制器"]
>     CM --> OC["其他控制器..."]
> ```

#### 调度器

[[调度器]]监控 API 服务器的新任务，并将它们分配给健康的工作节点。

它实现以下过程：

1. 监控 API 服务器的新任务
2. 识别能够执行任务的节点
3. 将任务分配给节点

识别能够执行任务的节点涉及谓词检查、过滤和排名算法。它检查污点、亲和性和反亲和性规则、网络端口可用性以及可用的 CPU 和内存。它忽略无法运行任务的节点，并根据因素对剩余节点进行排名，例如是否已有所需的镜像、可用的 CPU 和内存数量，以及它当前正在运行的任务数量。每个因素都有分值，选择得分最高的节点来运行任务。

如果找不到合适的节点，调度器会将任务标记为待处理。

如果集群配置了节点自动扩展，待处理任务会触发集群自动扩展事件，向集群添加新节点，调度器将任务分配给新节点。

#### 云控制器管理器

如果您的集群在公共云上（如 AWS、Azure、GCP 或 Civo Cloud），它将运行一个[[云控制器管理器]]，将集群与云服务集成，如实例、负载均衡器和存储。例如，如果您在云上并且应用程序请求负载均衡器，云控制器管理器会配置一个云负载均衡器并将其连接到您的应用程序。

### 控制平面总结

[[控制平面]]实现了 Kubernetes 的核心功能，包括 API 服务器、调度器和集群存储。它还实现了控制器，确保集群运行您要求它运行的内容。

>

> 
> API 服务器是 Kubernetes 前端，所有通信都通过它。

## 工作节点

[[工作节点]]运行您的业务应用程序。

> [!INFO] 工作节点架构
> 图 2.6 展示了工作节点的主要组件。
> 
> ```mermaid
> flowchart TD
>     subgraph WN["工作节点"]

>         KProxy["Kube-proxy"]
>     end
>     Kubelet --> Runtime
>     Runtime --> KProxy
> ```

让我们看看主要的工作节点组件。

### Kubelet

[[Kubelet]] 是主要的 Kubernetes 代理，处理与集群的所有通信。

它执行以下关键任务：

- 监控 API 服务器的新任务
- 指示适当的运行时执行任务
- 向 API 服务器报告任务状态

如果任务无法运行，Kubelet 会向 API 服务器报告问题，并让控制平面决定采取什么行动。

### 运行时

每个工作节点都有一个或多个用于执行任务的[[运行时]]。

大多数新的 Kubernetes 集群预装了 containerd 运行时，并使用它来执行任务。这些任务包括：

- 拉取容器镜像
- 管理生命周期操作，如启动和停止容器

> [!INFO] 运行时选择
> 较旧的集群使用 Docker 运行时，但现在已不再支持。红帽 OpenShift 集群使用 CRI-O 运行时。还有许多其他运行时，各有优缺点。
> 
> 我们将在 Wasm 章节中使用一些不同的运行时。

### Kube-proxy

每个工作节点都运行一个 [[Kube-proxy]] 服务，实现集群网络并将流量负载均衡到节点上运行的任务。

## 为 Kubernetes 打包应用程序

Kubernetes 运行容器、VM、Wasm 应用程序等。但是，所有这些都需要包装在 [[Pod]] 中才能在 Kubernetes 上运行。

我们稍后会介绍 Pod，但现在可以将它们视为一个薄包装层，抽象不同类型的任务以便它们可以在 Kubernetes 上运行。下面的快递类比可能有助于理解。

快递员允许您运送书籍、衣服、食物、电器等，只要您使用他们批准的包装和标签。一旦您包装并标记了您的货物，您将它们交给快递员进行递送。快递员然后处理复杂的物流，包括使用哪些飞机和卡车、安全移交到本地递送枢纽，以及最终递送到客户手中。他们还提供跟踪包裹、更改递送详情和证明成功递送的服务。您要做的只是包装和标记货物。

在 Kubernetes 上运行应用程序类似。Kubernetes 可以运行容器、VM、Wasm 应用程序等，只要您将它们包装在 Pod 中。一旦包装在 Pod 中，您将 Pod 交给 Kubernetes，Kubernetes 就会运行它。这包括选择适当节点的复杂物流、加入网络、附加卷等。Kubernetes 甚至允许您查询应用程序并进行更改。

考虑一下一个简单的例子。

您用您喜欢的语言编写一个应用程序，将其容器化，推送到仓库，并包装在 Pod 中。此时，您可以将其交给 Kubernetes，Kubernetes 就会运行它。

但是，您几乎总是通过更高级别的控制器来部署和管理 Pod。例如，您可以将 Pod 包装在 [[Deployment]] 中以实现扩展、自愈和版本发布。

> [!TIP] 关键要点
> 现在您只需要知道两件事：
> 
> 1. 应用程序需要包装在 Pod 中才能在 Kubernetes 上运行
> 2. Pod 被包装在更高级别的控制器中以获得高级功能

让我们快速回到快递类比来帮助解释控制器的角色。

大多数快递员提供额外的服务，如货物保险、冷藏递送、签名和摄影递送证明、特快递送服务等。

同样，Kubernetes 也类似。它实现控制器来增加价值，如确保应用程序的健康、在需求增加时自动扩展等。

> [!INFO] 对象嵌套关系
> 图 2.7 展示了一个包装在 Pod 中的容器，而 Pod 又被包装在 Deployment 中。
> 
> ```mermaid
> flowchart TD
>     subgraph Deploy["Deployment"]
>         subgraph Pod["Pod"]
>             Container["容器"]
>         end
>     end
> ```
> 
> 不要担心 YAML 配置的细节，它只是为了种下这个想法的种子。

重要的是要理解，每一层包装都添加了一些东西：

- **容器**包装应用程序并提供依赖项
- **Pod**包装容器，以便它可以在 Kubernetes 上运行
- **Deployment**包装 Pod 并添加自愈、扩展等功能

您将 Deployment（YAML 文件）发布到 API 服务器作为应用程序的期望状态，Kubernetes 就会实现它。

## 声明式模型和期望状态

[[声明式模型]]和[[期望状态]]是 Kubernetes 运作的核心。它们基于三个基本原则：

- **期望状态** - 您想要的
- **观察状态** - 您拥有的
- **协调** - 使观察状态与期望状态保持同步的过程

> [!INFO] 术语说明
> 我们使用术语"实际状态"、"当前状态"和"观察状态"来表示同一件事——集群的最新视图。

在 Kubernetes 中，声明式模型的工作方式如下：

1. 您在 YAML 清单文件中描述应用程序的期望状态
2. 您将 YAML 文件发布到 API 服务器
3. Kubernetes 将其记录在集群存储中作为意图记录
4. 控制器注意到集群的观察状态与新的期望状态不匹配
5. 控制器进行必要的更改来协调差异
6. 控制器继续在后台运行，确保观察状态始终与期望状态匹配

让我们仔细看看。

您编写 YAML 清单文件，告诉 Kubernetes 您希望应用程序是什么样子。我们称之为**期望状态**，包括使用哪些镜像、多少副本、哪些网络端口等。

创建清单后，您将其发布到 API 服务器，在那里经过身份验证和授权。将 YAML 文件发布到 Kubernetes 最常见的方式是使用 kubectl 命令行工具。

一旦通过身份验证和授权，Kubernetes 将配置持久化到集群存储中作为意图记录。

此时，集群的观察状态与您新的期望状态不匹配。控制器会注意到这一点，并开始协调过程。这将涉及进行 YAML 文件中描述的所有更改，可能包括调度新的 Pod、拉取镜像、启动容器、将它们附加到网络以及启动应用程序进程。

一旦协调完成，观察状态将与期望状态匹配，一切都会正常。但是，控制器继续在后台运行，准备协调任何未来的差异。

> [!IMPORTANT] 声明式 vs 命令式
> 重要的是要理解，我们所描述的与传统的命令式模型有很大不同：
> 
> **命令式模型**需要复杂的平台特定命令脚本来达到最终状态
> 
> **声明式模型**是一种简单的平台无关的方式来描述最终状态
> 
> Kubernetes 两者都支持，但更喜欢声明式模型。这是因为声明式模型与版本控制系统集成，并支持自愈、自动扩展和滚动更新。

让我们看几个简单的声明式例子。

假设您从请求十个副本的 YAML 文件部署了一个应用程序。如果运行其中两个副本的节点发生故障，观察状态将下降到 8 个副本，不再与 10 个的期望状态匹配。没关系，控制器会看到差异并调度 2 个新副本，使总数恢复到 10。

同样的情况也会发生在应用程序更新时。例如，如果您更新 YAML，告诉应用程序使用更新版本的镜像，并将更改发布到 Kubernetes，相关的控制器会注意到差异，并用运行新版本的新副本替换运行旧版本的副本。

如果您尝试用命令式方式执行这样的更新，您需要编写复杂的脚本来管理、监控和健康检查整个更新过程。而用声明式方式，您只需要更改一行 YAML，Kubernetes 就会完成其他所有工作。

尽管很简单，但这非常强大，它是 Kubernetes 工作方式的基础。

## Pod

在 VMware 中，调度的原子单位是虚拟机（VM）。在 Kubernetes 中，它是 [[Pod]]。

是的，Kubernetes 运行容器、VM、Wasm 应用程序等。但它们都需要包装在 Pod 中。

### Pod 和容器

最简单的配置是每个 Pod 运行一个容器，这就是为什么我们有时可以互换使用 Pod 和容器这两个术语。但是，多容器 Pod 有一些强大的用例，包括：

- 服务网格
- 初始化环境的辅助服务
- 具有紧密耦合辅助功能（如日志抓取器）的应用程序

> [!INFO] 多容器 Pod 示例
> 图 2.8 展示了一个多容器 Pod，包含一个主应用程序容器和一个服务网格 sidecar。Sidecar 是指与主应用程序容器运行在同一 Pod 中的辅助容器，提供额外服务。在图 2.8 中，服务网格 sidecar 加密网络流量并提供遥测数据。
> 
> ```mermaid
> flowchart TD
>     subgraph Pod["Pod"]
>         Main["主应用程序容器"]
>         Sidecar["服务网格 Sidecar"]
>     end
>     Main <-->|加密/遥测| Sidecar
> ```

多容器 Pod 也有助于我们实现单一职责原则，其中每个容器执行一个任务。在图 2.8 中，主应用程序容器可能正在服务消息队列或其他核心应用程序功能。我们不将加密和遥测逻辑添加到主应用程序中，而是保持应用程序简单，并在同一 Pod 中的服务网格容器中实现额外服务。

### Pod 构造

每个 [[Pod]] 都是一个共享的执行环境，供一个或多个容器使用。执行环境包括网络栈、卷、共享内存等。

单容器 Pod 中的容器拥有自己的执行环境，而多容器 Pod 中的容器共享它。

例如，下图展示了一个多容器 Pod，两个容器共享 Pod 的 IP 地址。主应用程序容器可以通过 `10.0.10.15:8080` 从 Pod 外部访问，sidecar 通过 `10.0.10.15:5005` 访问。如果它们需要相互通信（Pod 内的容器间通信），可以使用 Pod 的 localhost 接口。

> [!TIP] 网络共享
> ```mermaid
> flowchart LR
>     subgraph Pod["Pod (10.0.10.15)"]
>         Main["主容器 :8080"]
>         Side["Sidecar :5005"]
>     end
>     Main <-->|localhost| Side
>     External["外部客户端"] -->|10.0.10.15:8080| Main
> ```

> [!INFO] 何时使用多容器 Pod
> 当您的应用程序有紧密耦合的组件需要共享资源（如内存或存储）时，您应该选择多容器 Pod。在大多数其他情况下，您应该使用单容器 Pod 并通过松散耦合通过网络连接它们。

### Pod 调度

Kubernetes 始终将同一 Pod 中的容器调度到单个节点。这是因为 Kubernetes 调度 Pod，而不是单独的容器。但这也是因为 Pod 是一个共享执行环境，您不能轻易跨不同节点共享内存、网络和卷。

启动 Pod 也是一个原子操作。这意味着 Kubernetes 仅在所有容器运行时才将 Pod 标记为就绪。例如，如果一个 Pod 有两个容器且只有一个启动，Pod 就没有就绪。

### Pod 作为扩展单位

[[Pod]] 是 Kubernetes 中调度的最小单位。因此，将应用程序扩展会增加更多 Pod，缩小会删除 Pod。您不是通过向现有 Pod 添加更多容器来扩展的。

### Pod 生命周期

[[Pod]] 是有生命周期的——它们被创建、存活，然后死亡。每次有一个死亡，Kubernetes 都会用一个新的替换它。即使新 Pod 看起来、闻起来和感觉都与旧 Pod 相同，它始终是一个全新的 Pod，具有新的 ID 和新的 IP。

> [!CAUTION] 应用程序设计要求
> 这迫使您设计应用程序时要松散耦合，以便它们能够免受单个 Pod 故障的影响。

### Pod 不可变性

[[Pod]] 是不可变的。这意味着您一旦运行它们就永远不会更改它们。

例如，如果您需要更改或更新 Pod，您总是用运行更新的新 Pod 替换它。您绝不应该登录 Pod 并更改它。这意味着我们谈论"更新 Pod"时，始终意味着删除旧的并用新的替换。这对某些人来说可能是一个巨大的心态转变，但它非常适合现代工具和 GitOps 风格的工作流程。

## Deployment

即使 Kubernetes 与 [[Pod]] 一起工作，您几乎总是通过更高级别的控制器（如 [[Deployment]]、StatefulSet 和 DaemonSet）来部署它们。这些都是作为后台监控循环运行的控制平面服务，将观察状态与期望状态进行协调。

[[Deployment]] 为无状态应用程序添加了自愈、扩展、滚动更新和版本回滚功能。

## Service 对象和稳定网络

本章前面，我们说过 Pod 是有生命周期的，可能会死亡。但是，如果失败的 Pod 由控制器管理，它会被一个新的具有新 ID 和新 IP 地址的 Pod 替换。相同的逻辑也适用于版本发布和扩展操作：

- **版本发布**用具有新 IP 的新 Pod 替换旧的 Pod
- **扩展**添加具有新 IP 的新 Pod
- **缩减**删除现有的 Pod

像这样的事件会产生 IP 变动，使 Pod 变得不可靠。例如，客户端无法对单个 Pod 建立可靠的连接，因为 Kubernetes 不能保证它们会存在。

这就是 [[Service]] 的用武之地，它为 Pod 组提供可靠的网络。

> [!INFO] Service 网络架构
> 图 2.11 展示了内部和外部客户端如何通过 Kubernetes Service 连接到一组 Pod。Service（首字母大写，因为它是 Kubernetes API 资源）提供可靠的名称和 IP，并将请求负载均衡到其背后的 Pod。
> 
> ```mermaid
> flowchart LR
>     subgraph Svc["Service"]
>         DNS["稳定 DNS 名称"]
>         IP["稳定 IP"]
>         Port["端口"]
>     end
>     External["外部客户端"] --> Svc
>     Internal["内部客户端"] --> Svc
>     Svc --> P1["Pod 1"]
>     Svc --> P2["Pod 2"]
>     Svc --> P3["Pod 3"]
> ```

> [!TIP] Service 前端和后端
> 您应该将 Service 视为具有前端和后端。前端具有稳定的 DNS 名称、IP 地址和网络端口。后端使用标签将流量负载均衡到一个动态的 Pod 集合。

Service 维护一个健康 Pod 列表，因为扩展事件、版本发布和故障会导致 Pod 来来去去。这意味着它们始终会将流量引导到活动健康的 Pod。Service 还保证前端的名称、IP 和端口永远不会改变。

## 章节总结

本章向您介绍了一些主要的 Kubernetes 特性。

### [[控制平面节点]]

- 托管实现 Kubernetes 智能的控制平面服务
- 可以是物理服务器、VM、云实例等
- 生产集群通常运行三个或五个控制平面节点以实现高可用性
- 控制平面服务包括 [[API 服务器]]、[[调度器]]、[[集群存储]]和各种[[控制器]]

### [[工作节点]]

- 运行您的业务应用程序
- 也可以是物理服务器、VM、云实例等
- 每个工作节点都运行 [[Kubelet]] 服务，监控 API 服务器的新工作任务并报告任务状态

> [!TIP] 关键概念回顾
> 
> - Kubernetes 是集群和编排器
> - 控制平面实现核心功能，工作节点运行应用程序
> - 应用程序需要包装在 Pod 中，Pod 由 Deployment 管理
> - 声明式模型使用期望状态和协调来管理集群
> - Service 为动态 Pod 组提供稳定网络
