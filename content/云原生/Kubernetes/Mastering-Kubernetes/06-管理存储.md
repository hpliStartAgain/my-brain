# 管理存储

在本章中，我们将探讨 Kubernetes 如何管理存储。存储与计算非常不同，但从高层次来看，它们都属于资源。作为一个通用平台，Kubernetes 采用的方法是将存储抽象为编程模型和一组供存储提供商使用的插件。首先，我们将详细了解概念性的存储模型以及存储如何在集群中对容器可用。然后，我们将介绍常见的云平台存储提供商，例如 Amazon Web Services (AWS)、Google Compute Engine (GCE) 和 Azure。接着，我们将介绍一个著名的开源存储提供商——来自 Red Hat 的 GlusterFS，它提供了一个分布式文件系统。我们还将研究另一种解决方案——Ceph——它使用 Rook 操作器将数据作为 Kubernetes 集群的一部分在容器中进行管理。我们将了解 Kubernetes 如何支持集成现有的企业存储解决方案。最后，我们将探索容器存储接口 (CSI) 及其带来的所有高级能力。

本章将涵盖以下主要主题：

-   持久卷详解
-   端到端演示持久卷存储
-   公有云存储卷类型——GCE、AWS 和 Azure
-   Kubernetes 中的 GlusterFS 和 Ceph 卷
-   将企业存储集成到 Kubernetes 中
-   容器存储接口

在本章结束时，您将对存储如何在 Kubernetes 中表示、各种部署环境（本地测试、公有云和企业）中的各种存储选项，以及如何为您的用例选择最佳方案有扎实的理解。

建议您在 minikube 或其他支持存储的集群上尝试本章中的代码示例。KinD 集群在与节点标签相关的一些问题上存在缺陷，而标签对于某些存储解决方案来说是必需的。

## 持久卷详解

在本节中，我们将理解 Kubernetes 存储概念模型，并了解如何将持久存储映射到容器中，以便它们能够读写。让我们从理解存储问题开始。

容器和 Pod 是瞬态的。容器写入其自身文件系统的任何内容都会在容器死亡时被清除。容器也可以从其宿主机挂载目录并进行读写。这些内容在容器重启后仍然存在，但节点本身并非不朽。此外，如果 Pod 本身被驱逐并调度到不同的节点，Pod 的容器将无法访问旧宿主的文件系统。

还有其他问题，例如当容器死亡时挂载的宿主目录的所有权问题。想象一下，一堆容器将重要数据写入宿主上的各种数据目录，然后消失，所有数据散落在各个节点上，却无法直接判断哪个容器写了哪些数据。你可以尝试记录这些信息，但应该记录在哪里呢？很明显，对于一个大规模系统，你需要可从任何节点访问的持久存储来可靠地管理数据。

### 理解卷

Kubernetes 的基本存储抽象是卷。容器挂载绑定到其 Pod 的卷，并像访问本地文件系统一样访问存储（无论存储位于何处）。这并非什么新鲜事，而且它很棒，因为作为编写需要访问数据的应用程序的开发人员，您无需担心数据的存储位置和方式。Kubernetes 支持多种类型的卷，每种卷都有其独特的功能。让我们回顾一些主要的卷类型。

### 使用 emptyDir 实现 Pod 内通信

使用共享卷在同一 Pod 中的容器之间共享数据非常简单。容器 1 和容器 2 只需挂载同一个卷，即可通过读写这个共享空间进行通信。最基本的卷是 emptyDir。emptyDir 卷是宿主机上的一个空目录。请注意，它不是持久的，因为当 Pod 被驱逐或删除时，其内容将被清除。如果容器只是崩溃，Pod 会保留，重启后的容器可以访问卷中的数据。另一个非常有趣的选择是使用 RAM 磁盘，只需将 medium 指定为 Memory。现在，您的容器通过共享内存进行通信，速度更快，但显然也更易丢失。如果节点重启，emptyDir 卷的内容将丢失。

以下是一个 Pod 配置文件，其中包含两个容器，它们挂载同一个名为 `shared-volume` 的卷。容器将其挂载在不同的路径上，但当 `hue-global-listener` 容器向 `/notifications` 写入文件时，`hue-job-scheduler` 容器将在 `/incoming` 下看到该文件：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: hue-scheduler
spec:
  containers:
  - image: g1g1/hue-global-listener:1.0
    name: hue-global-listener
    volumeMounts:
    - mountPath: /notifications
      name: shared-volume
  - image: g1g1/hue-job-scheduler:1.0
    name: hue-job-scheduler
    volumeMounts:
    - mountPath: /incoming
      name: shared-volume
  volumes:
  - name: shared-volume
    emptyDir: {}
```

要使用共享内存选项，我们只需在 emptyDir 部分添加 `medium: Memory`：

```yaml
volumes:
- name: shared-volume
  emptyDir:
    medium: Memory
```

请注意，基于内存的 emptyDir 会计入容器的内存限制。

为了验证它是否工作，让我们创建 Pod，然后使用一个容器写入文件，并使用另一个容器读取它：

```bash
$ k create -f hue-scheduler.yaml
pod/hue-scheduler created
```

请注意，该 Pod 有两个容器：

```bash
$ k get pod hue-scheduler -o json | jq .spec.containers
[
  {
    "image": "g1g1/hue-global-listener:1.0",
    "name": "hue-global-listener",
    "volumeMounts": [
      {
        "mountPath": "/notifications",
        "name": "shared-volume"
      },
      ...
    ]
    ...
  },
  {
    "image": "g1g1/hue-job-scheduler:1.0",
    "name": "hue-job-scheduler",
    "volumeMounts": [
      {
        "mountPath": "/incoming",
        "name": "shared-volume"
      },
      ...
    ]
    ...
  }
]
```

现在，我们可以在 `hue-global-listener` 容器的 `/notifications` 目录下创建一个文件，并在 `hue-job-scheduler` 容器的 `/incoming` 目录下列出它：

```bash
$ kubectl exec -it hue-scheduler -c hue-global-listener -- touch /notifications/1.txt
$ kubectl exec -it hue-scheduler -c hue-job-scheduler -- ls /incoming
1.txt
```

如您所见，我们能够在另一个容器的文件系统中看到在一个容器中创建的文件；因此，容器可以通过共享文件系统进行通信。

### 使用 HostPath 实现节点内通信

有时，您希望 Pod 能够访问某些宿主信息（例如 Docker 守护进程），或者希望同一节点上的 Pod 能够相互通信。这在 Pod 知道它们在同一个宿主机上时很有用。由于 Kubernetes 根据可用资源调度 Pod，Pod 通常不知道它们与哪些其他 Pod 共享节点。在以下几种情况下，Pod 可以依赖其他 Pod 与其调度在同一节点上：

-   在单节点集群中，所有 Pod 显然共享同一个节点
-   DaemonSet Pod 始终与任何匹配其选择器的其他 Pod 共享一个节点
-   具有必需 Pod 亲和性的 Pod 始终被调度在一起

例如，在第 5 章《在实践中使用 Kubernetes 资源》中，我们讨论了一个作为聚合代理用于其他 Pod 的 DaemonSet Pod。实现此行为的另一种方式是让 Pod 简单地将数据写入挂载到宿主目录的卷中，然后 DaemonSet Pod 可以直接读取并对其进行操作。

HostPath 卷是挂载到 Pod 中的宿主机文件或目录。在决定使用 HostPath 卷之前，请确保您了解其后果：

-   这是一个安全风险，因为访问宿主文件系统可能会暴露敏感数据（例如 kubelet 密钥）
-   如果 Pod 的行为由数据驱动且其宿主机上的文件不同，则配置相同的 Pod 的行为可能不同
-   它可能违反基于资源的调度，因为 Kubernetes 无法监控 HostPath 资源
-   访问宿主目录的容器必须具有将 `privileged` 设置为 `true` 的安全上下文，或者在宿主机端更改权限以允许写入
-   很难协调同一节点上多个 Pod 之间的磁盘使用情况
-   您很容易耗尽磁盘空间

以下是一个配置文件，它将 `/coupons` 目录挂载到 `hue-coupon-hunter` 容器中，该目录映射到宿主机的 `/etc/hue/data/coupons` 目录：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: hue-coupon-hunter
spec:
  containers:
  - image: the_g1g1/hue-coupon-hunter
    name: hue-coupon-hunter
    volumeMounts:
    - mountPath: /coupons
      name: coupons-volume
  volumes:
  - name: coupons-volume
    host-path:
      path: /etc/hue/data/coupons
```

由于 Pod 没有特权安全上下文，它将无法写入宿主目录。让我们修改容器规范，通过添加安全上下文来启用写入：

```yaml
- image: the_g1g1/hue-coupon-hunter
  name: hue-coupon-hunter
  volumeMounts:
  - mountPath: /coupons
    name: coupons-volume
  securityContext:
    privileged: true
```

在下图中，您可以看到每个容器都有自己的本地存储区域，其他容器或 Pod 无法访问，而宿主机的 `/data` 目录作为卷同时挂载到容器 1 和容器 2 中：

### 使用本地卷实现持久的节点存储

本地卷类似于 HostPath，但它们在 Pod 重启和节点重启后仍然存在。从这个意义上说，它们被认为是持久卷。它们是在 Kubernetes 1.7 中添加的。从 Kubernetes 1.14 开始，它们被认为是稳定的。本地卷的目的是支持有状态集 (StatefulSet)，其中特定的 Pod 需要被调度到包含特定存储卷的节点上。本地卷具有节点亲和性注解，简化了 Pod 与所需存储的绑定。

我们需要定义一个存储类来使用本地卷。我们将在本章后面深入介绍存储类。简单来说，存储类使用制备器 (provisioner) 为 Pod 分配存储。让我们在一个名为 `local-storage-class.yaml` 的文件中定义存储类并创建它：

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: local-storage
provisioner: kubernetes.io/no-provisioner
volumeBindingMode: WaitForFirstConsumer
```

```bash
$ k create -f local-storage-class.yaml
storageclass.storage.k8s.io/local-storage created
```

现在，我们可以使用该存储类创建一个持久卷，该卷即使在使用它的 Pod 终止后也会持续存在：

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: local-pv
  labels:
    release: stable
  capacity: 10Gi
spec:
  capacity:
    storage: 10Gi
  volumeMode: Filesystem
  accessModes:
  - ReadWriteOnce
  persistentVolumeReclaimPolicy: Delete
  storageClassName: local-storage
  local:
    path: /mnt/disks/disk-1
  nodeAffinity:
    required:
      nodeSelectorTerms:
      - matchExpressions:
        - key: kubernetes.io/hostname
          operator: In
          values:
          - k3d-k3s-default-agent-1
```

## 制备持久卷

虽然 emptyDir 卷可以被容器挂载和使用，但它们不是持久的，并且不需要任何特殊的制备，因为它们使用节点上的现有存储。HostPath 卷在原始节点上持久存在，但如果 Pod 在另一个节点上重启，则无法访问其先前节点的 HostPath 卷。本地卷是真正的持久卷，它们使用管理员预先制备的存储或通过存储类进行动态制备的存储。它们在节点上持久存在，可以承受 Pod 重启和重新调度，甚至节点重启。一些持久卷使用管理员预先制备的外部存储（而非物理连接到节点的磁盘）。在云环境中，制备可能非常简化，但仍然需要，作为 Kubernetes 集群管理员，您至少必须确保存储配额充足，并勤勉地监控使用情况与配额的关系。

请记住，持久卷是 Kubernetes 集群使用的资源，类似于节点。因此，它们不由 Kubernetes API 服务器管理。

您可以静态或动态地制备资源。

### 静态制备持久卷

静态制备很直接。集群管理员预先创建由某些存储介质支持的持久卷，这些持久卷可以被容器声明 (claim)。

### 动态制备持久卷

当持久卷声明 (PVC) 与任何静态制备的持久卷都不匹配时，可能会发生动态制备。如果声明指定了一个存储类，并且管理员将该类配置为动态制备，那么持久卷可能会被即时制备。当我们稍后讨论持久卷声明和存储类时，将看到相关示例。

### 外部制备持久卷

Kubernetes 最初在核心代码库中包含大量存储制备的"树内 (in-tree)"代码。随着 CSI 的引入，存储制备器开始从 Kubernetes 核心迁移到卷插件（也称为"树外 (out-of-tree)"）。外部制备器的工作方式与树内动态制备器类似，但可以独立部署和更新。大多数树内存储制备器已迁移到树外。请查看此项目以获取编写外部存储制备器的库和指南：[https://github.com/kubernetes-sigs/sig-storage-lib-external-provisioner](https://github.com/kubernetes-sigs/sig-storage-lib-external-provisioner)。

### 创建持久卷

以下是一个 NFS 持久卷的配置文件：

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-777
spec:
  capacity:
    storage: 10Gi
  volumeMode: Filesystem
  accessModes:
  - ReadWriteMany
  - ReadOnlyMany
  persistentVolumeReclaimPolicy: Recycle
  storageClassName: slow
  mountOptions:
  - hard
  - nfsvers=4.2
  nfs:
    path: /tmp
    server: nfs-server.default.svc.cluster.local
```

一个持久卷具有 spec 和 metadata，可能包含存储类名称。让我们专注于这里的 spec。有六个部分：容量 (capacity)、卷模式 (volume mode)、访问模式 (access modes)、回收策略 (reclaim policy)、存储类 (storage class) 和卷类型 (volume type)（在示例中是 nfs）。

#### 容量

每个卷都有指定数量的存储空间。存储声明可以被至少具有该存储量的持久卷满足。在示例中，持久卷的容量为 10 gibibytes（1 gibibyte 等于 2 的 30 次方字节）。

```yaml
capacity:
  storage: 10Gi
```

在分配静态持久卷时，理解存储请求模式非常重要。例如，如果您制备了 20 个容量为 100 GiB 的持久卷，而某个容器声明了一个需要 150 GiB 的持久卷，那么即使集群中有足够的总容量，此声明也不会被满足。

#### 卷模式

可选的卷模式是在 Kubernetes 1.9 中作为 Alpha 功能添加的（在 Kubernetes 1.13 中迁移到 Beta），用于静态制备。它允许您指定是需要文件系统 (Filesystem) 还是原始存储 (Block)。如果您不指定卷模式，则默认为 Filesystem，就像 1.9 之前一样。

#### 访问模式

有三种访问模式：

-   **ReadOnlyMany**：可以被多个节点以只读方式挂载
-   **ReadWriteOnce**：可以被单个节点以读写方式挂载
-   **ReadWriteMany**：可以被多个节点以读写方式挂载

存储被挂载到节点，所以即使使用 ReadWriteOnce，同一节点上的多个容器也可以挂载该卷并进行写入。如果这导致问题，您需要通过其他机制来处理（例如，仅在与您知道每个节点只有一个 Pod 的 DaemonSet 中声明该卷）。

不同的存储提供商支持这些模式的某个子集。当您制备一个持久卷时，可以指定它将支持哪些模式。例如，NFS 支持所有模式，但在示例中，只启用了这些模式：

```yaml
accessModes:
- ReadWriteMany
- ReadOnlyMany
```

#### 回收策略

回收策略决定了当持久卷声明被删除时会发生什么。有三种不同的策略：

-   **Retain**（保留）——卷需要手动回收
-   **Delete**（删除）——内容、卷和后端存储都被删除
-   **Recycle**（回收）——仅删除内容（`rm -rf /volume/*`）

Retain 和 Delete 策略意味着该持久卷不再可用于未来的声明。Recycle 策略允许该卷再次被声明。

目前，NFS 和 HostPath 支持 recycle 策略，而 AWS EBS、GCE PD、Azure Disk 和 Cinder 卷支持 delete 策略。请注意，动态制备的卷总是被删除。

#### 存储类

您可以使用 spec 中的可选字段 `storageClassName` 来指定存储类。如果这样做，那么只有指定了相同存储类的持久卷声明才能绑定到该持久卷。如果您不指定存储类，那么只有未指定存储类的持久卷声明才能绑定到它。

```yaml
storageClassName: slow
```

#### 卷类型

卷类型在 spec 中通过名称指定。spec 中没有 `volumeType` 小节。在前面的示例中，`nfs` 是卷类型：

```yaml
nfs:
  path: /tmp
  server: 172.17.0.8
```

每种卷类型可能有自己的一组参数。在这里，它们是路径 (path) 和服务器 (server)。

稍后我们将介绍各种卷类型。

#### 挂载选项

某些持久卷类型具有您可以指定的额外挂载选项。挂载选项不会经过验证。如果您提供了无效的挂载选项，卷制备将会失败。例如，NFS 支持额外的挂载选项：

```yaml
mountOptions:
- hard
- nfsvers=4.1
```

现在我们已经了解了如何制备单个持久卷，让我们来看看投射卷 (projected volumes)，它们增加了更多的灵活性和存储抽象。

## 投射卷

投射卷允许您将多个持久卷挂载到同一个目录中。当然，您需要注意命名冲突。

以下卷类型支持投射卷：

-   ConfigMap
-   Secret
-   DownwardAPI
-   ServiceAccountToken

下面的代码片段将一个 ConfigMap 和一个 Secret 投射到同一个目录中：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: projected-volumes-demo
spec:
  containers:
  - name: projected-volumes-demo
    image: busybox:1.28
    volumeMounts:
    - name: projected-volumes-demo
      mountPath: "/projected-volume"
      readOnly: true
  volumes:
  - name: projected-volumes-demo
    projected:
      sources:
      - secret:
          name: the-user
          items:
          - key: username
            path: the-group/the-user
      - configMap:
          name: the-config-map
          items:
          - key: config
            path: the-group/the-config-map
```

投射卷的参数与普通卷非常相似。例外情况是：

-   为了与 ConfigMap 命名保持一致，secret 的 `secretName` 字段已更新为 `name`。
-   `defaultMode` 只能在投射级别设置，不能为每个卷源单独指定（但您可以为每个投射显式指定模式）。

让我们来看一种特殊的投射卷——serviceAccountToken。

### serviceAccountToken 投射卷

Kubernetes Pod 可以使用与 Pod 关联的服务帐户的权限来访问 Kubernetes API 服务器。serviceAccountToken 投射卷从安全角度为您提供了更细粒度和更多的控制。令牌可以有过期时间和特定的受众。

更多详情请参见：[https://kubernetes.io/docs/concepts/storage/projected-volumes/#serviceaccounttoken](https://kubernetes.io/docs/concepts/storage/projected-volumes/#serviceaccounttoken)

## 创建本地卷

本地卷是在特定节点上分配的静态持久磁盘。它们类似于 HostPath 卷，但 Kubernetes 知道每个本地卷属于哪个节点，并将绑定到该本地卷的 Pod 始终调度到该节点上。这意味着 Pod 不会被驱逐并调度到数据不可用的另一个节点上。

让我们创建一个本地卷。首先，我们需要创建一个后端目录。对于 KinD 和 k3d 集群，您可以通过 Docker 访问节点：

```bash
$ docker exec -it k3d-k3s-default-agent-1 mkdir -p /mnt/disks/disk-1
$ docker exec -it k3d-k3s-default-agent-1 ls -la /mnt/disks
total 12
drwxr-xr-x 3 0 0 4096 Jun 29 21:40 .
drwxr-xr-x 3 0 0 4096 Jun 29 21:40 ..
drwxr-xr-x 2 0 0 4096 Jun 29 21:40 disk-1
```

对于 minikube，您需要使用 `minikube ssh`。

现在，我们可以创建一个由 `/mnt/disks/disk-1` 目录支持的本地卷：

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: local-pv
  labels:
    release: stable
  capacity: 10Gi
spec:
  capacity:
    storage: 10Gi
  volumeMode: Filesystem
  accessModes:
  - ReadWriteOnce
  persistentVolumeReclaimPolicy: Delete
  storageClassName: local-storage
  local:
    path: /mnt/disks/disk-1
  nodeAffinity:
    required:
      nodeSelectorTerms:
      - matchExpressions:
        - key: kubernetes.io/hostname
          operator: In
          values:
          - k3d-k3s-default-agent-1
```

以下是创建命令：

```bash
$ k create -f local-volume.yaml
persistentvolume/local-pv created
$ k get pv
NAME      CAPACITY   ACCESS MODES   STORAGECLASS    RECLAIM POLICY   STATUS   CLAIM                           AGE
local-pv  10Gi       RWO            local-storage   Delete           Bound    default/local-storage-         6m44s
```

## 发起持久卷声明

当容器需要访问某些持久存储时，它们会发起一个声明（更确切地说，开发人员和集群管理员协调所需的存储资源来进行声明）。以下是一个示例声明，它与上一节"创建本地卷"中的持久卷匹配：

```yaml
kind: PersistentVolumeClaim
apiVersion: v1
metadata:
  name: local-storage-claim
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 8Gi
  storageClassName: local-storage
  selector:
    matchLabels:
      release: "stable"
    matchExpressions:
    - {key: capacity, operator: In, values: [8Gi, 10Gi]}
```

让我们创建该声明，然后解释各个部分的作用：

```bash
$ k create -f local-persistent-volume-claim.yaml
persistentvolumeclaim/local-storage-claim created
$ k get pvc
NAME                  STATUS               VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS      AGE
local-storage-claim   WaitForFirstConsumer local-pv  10Gi       RWO            local-storage     21m
```

名称 `local-storage-claim` 稍后将在将声明挂载到容器中时变得重要。

spec 中的访问模式是 `ReadWriteOnce`，这意味着如果该声明被满足，则没有其他具有 `ReadWriteOnce` 访问模式的声明可以再被满足，但 `ReadOnlyMany` 的声明仍然可以被满足。

resources 部分请求 8 GiB。这可以被我们的容量为 10 Gi 的持久卷满足。但这有点浪费，因为按定义会有 2 Gi 不会被使用。

存储类名称是 `local-storage`。如前所述，它必须与持久卷的类名称匹配。然而，对于 PVC，空的类名称 (`""`) 和根本没有类名称之间存在差异。前者（空的类名称）匹配没有存储类名称的持久卷。后者（没有类名称）只有在 `DefaultStorageClass` 准入插件已打开并且默认存储类被使用时，才能绑定到持久卷。

selector 部分允许您进一步过滤可用的卷。例如，这里卷必须匹配标签 `release:stable`，并且具有标签为 `capacity:8Gi` 或 `capacity:10Gi` 的卷。

想象一下，我们还有其他几个容量为 20 Gi 和 50 Gi 的已制备卷。当我们只需要 8 Gi 时，我们不想声明一个 50 Gi 的卷。

> Kubernetes 总是尝试匹配能满足声明的最小卷，但如果没有 8 Gi 或 10 Gi 的卷，那么标签将阻止分配 20 Gi 或 50 Gi 的卷，并使用动态制备。

> 重要的是要认识到声明不会按名称提及卷。您不能声明特定的卷。匹配由 Kubernetes 根据存储类、容量和标签完成。

最后，持久卷声明属于一个命名空间。将持久卷绑定到声明是排他性的。这意味着一个持久卷将绑定到一个命名空间。即使访问模式是 `ReadOnlyMany` 或 `ReadWriteMany`，所有挂载该持久卷声明的 Pod 都必须来自该声明的命名空间。

## 将声明挂载为卷

好的。我们已经制备了一个卷并发起了声明。是时候在容器中使用已声明的存储了。事实证明这非常简单。首先，持久卷声明必须作为卷在 Pod 中使用，然后 Pod 中的容器可以像任何其他卷一样挂载它。以下是一个 Pod 清单，它指定了我们之前创建的持久卷声明（绑定到我们制备的本地持久卷）：

```yaml
kind: Pod
apiVersion: v1
metadata:
  name: the-pod
spec:
  containers:
  - name: the-container
    image: g1g1/py-kube:0.3
    volumeMounts:
    - mountPath: "/mnt/data"
      name: persistent-volume
  volumes:
  - name: persistent-volume
    persistentVolumeClaim:
      claimName: local-storage-claim
```

关键在于 `volumes` 下的 `persistentVolumeClaim` 部分。声明名称（这里是 `local-storage-claim`）在当前命名空间内唯一标识特定的声明，并使其作为卷（名为 `persistent-volume`）可用。然后，容器可以通过其名称引用它，并将其挂载到 `"/mnt/data"`。

在创建 Pod 之前，需要注意持久卷声明实际上还没有声明任何存储，也没有绑定到我们的本地卷。直到某个容器实际尝试通过此声明挂载卷时，声明才会处于待处理状态：

```bash
$ k get pvc
NAME                  STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS    AGE
local-storage-claim   Pending                                                    6m14s
```

现在，该声明将在创建 Pod 时被绑定：

```bash
$ k create -f pod-with-local-claim.yaml
pod/the-pod created
$ k get pvc
NAME                  STATUS   VOLUME     CAPACITY   ACCESS MODES   STORAGECLASS    AGE
local-storage-claim   Bound    local-pv   100Gi      RWO            local-storage   20m
```

## 原始块卷

Kubernetes 1.9 将此功能作为 Alpha 功能添加。Kubernetes 1.13 将其迁移到 Beta。从 Kubernetes 1.18 开始，它是 GA（正式发布）。

原始块卷提供对底层存储的直接访问，而无需通过文件系统抽象进行中介。这对于需要高性能存储的应用程序（如数据库）或需要一致 I/O 性能和低延迟的场景非常有用。以下存储提供商支持原始块卷：

-   AWSElasticBlockStore
-   AzureDisk
-   FC（光纤通道）
-   GCE Persistent Disk
-   iSCSI
-   本地卷
-   OpenStack Cinder
-   RBD（Ceph 块设备）
-   VsphereVolume

此外，许多 CSI 存储提供商也提供原始块卷。完整列表请查看：[https://kubernetes-csi.github.io/docs/drivers.html](https://kubernetes-csi.github.io/docs/drivers.html)

以下是使用光纤通道 (FC) 提供商定义原始块卷的方法：

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: block-pv
spec:
  capacity:
    storage: 10Gi
  accessModes:
  - ReadWriteOnce
  volumeMode: Block
  persistentVolumeReclaimPolicy: Retain
  fc:
    targetWWNs: ["50060e801049cfd1"]
    lun: 0
    readOnly: false
```

匹配的持久卷声明 (PVC) **必须**也指定 `volumeMode: Block`。如下所示：

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: block-pvc
spec:
  accessModes:
  - ReadWriteOnce
  volumeMode: Block
  resources:
    requests:
      storage: 10Gi
```

Pod 将原始块卷作为 `/dev` 下的设备来使用，而**不是**作为挂载的文件系统。然后容器可以访问这些设备并进行读写。实际上，这意味着对块存储的 I/O 请求直接发送到底层块存储，不会经过文件系统驱动程序。这在理论上更快，但如果您的应用程序受益于文件系统缓冲，实际上反而可能降低性能。

以下是一个 Pod，其中的容器将 `block-pvc` 与原始块存储绑定为一个名为 `/dev/xdva` 的设备：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod-with-block-volume
spec:
  containers:
  - name: fc-container
    image: fedora:26
    command: ["/bin/sh", "-c"]
    args: ["tail -f /dev/null"]
    volumeDevices:
    - name: data
      devicePath: /dev/xvda
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: block-pvc
```

## CSI 临时卷

我们将在本章后面的"容器存储接口"部分详细介绍 CSI。CSI 临时卷由节点上的本地存储支持。这些卷的生命周期与 Pod 的生命周期绑定。此外，它们只能由该 Pod 的容器挂载，这对于将密钥和证书直接注入 Pod 而无需通过 Kubernetes Secret 对象非常有用。

以下是一个使用 CSI 临时卷的 Pod 示例：

```yaml
kind: Pod
apiVersion: v1
metadata:
  name: the-pod
spec:
  containers:
  - name: the-container
    image: g1g1/py-kube:0.3
    volumeMounts:
    - mountPath: "/data"
      name: the-volume
    command: [ "sleep", "1000000" ]
  volumes:
  - name: the-volume
    csi:
      driver: inline.storage.kubernetes.io
      volumeAttributes:
        key: value
```

CSI 临时卷自 Kubernetes 1.25 起已 GA。但并非所有 CSI 驱动程序都支持它们。像往常一样，请查看列表：[https://kubernetes-csi.github.io/docs/drivers.html](https://kubernetes-csi.github.io/docs/drivers.html)

## 通用临时卷

通用临时卷是另一种与 Pod 生命周期绑定的卷类型。当 Pod 消失时，通用临时卷也会消失。

此卷类型实际上会创建一个功能完备的持久卷声明。这提供了几种能力：

-   卷的存储可以是本地的，也可以是网络附加的
-   卷可以选择使用固定大小进行制备
-   根据驱动程序和指定的参数，卷可能包含初始数据
-   如果驱动程序支持，可以对卷执行典型操作，例如快照、克隆、调整大小和存储容量跟踪

以下是一个使用通用临时卷的 Pod 示例：

```yaml
kind: Pod
apiVersion: v1
metadata:
  name: the-pod
spec:
  containers:
  - name: the-container
    image: g1g1/py-kube:0.3
    volumeMounts:
    - mountPath: "/data"
      name: the-volume
    command: [ "sleep", "1000000" ]
  volumes:
  - name: the-volume
    ephemeral:
      volumeClaimTemplate:
        metadata:
          labels:
            type: generic-ephemeral-volume
        spec:
          accessModes: [ "ReadWriteOnce" ]
          storageClassName: generic-storage
          resources:
            requests:
              storage: 1Gi
```

请注意，从安全角度来看，具有创建 Pod 权限但没有创建 PVC 权限的用户现在可以通过通用临时卷创建 PVC。为防止这种情况，可以使用准入控制。

## 存储类

我们已经接触过存储类。它们到底是什么？存储类允许管理员使用自定义持久存储来配置集群（只要有合适的插件支持它）。存储类在 metadata 中有一个名称（必须在声明的 `storageClassName` 字段中指定），一个制备器，一个回收策略和参数。

我们之前为本地存储声明了一个存储类。以下是一个使用 AWS EBS 作为制备器的示例存储类（因此，它只在 AWS 上工作）：

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: standard
provisioner: kubernetes.io/aws-ebs
parameters:
  type: gp2
reclaimPolicy: Retain
allowVolumeExpansion: true
mountOptions:
- debug
volumeBindingMode: Immediate
```

您可以为同一个制备器创建多个具有不同参数的存储类。每个制备器都有自己的参数。

目前支持的制备器包括：

-   AWSElasticBlockStore
-   AzureFile
-   AzureDisk
-   CephFS
-   Cinder
-   FC
-   FlexVolume
-   Flocker
-   GCE Persistent Disk
-   GlusterFS
-   iSCSI
-   Quobyte
-   NFS
-   RBD
-   VsphereVolume
-   PortworxVolume
-   ScaleIO
-   StorageOS
-   Local

此列表不包含其他卷类型的制备器，例如 configMap 或 secret，它们不由典型的网络存储支持。这些卷类型不需要存储类。智能地利用卷类型是架构设计和管理集群的重要组成部分。

### 默认存储类

集群管理员也可以分配一个默认存储类。当分配了默认存储类并且 `DefaultStorageClass` 准入插件已打开时，没有存储类的声明将使用默认存储类进行动态制备。如果未定义默认存储类或未打开准入插件，则没有存储类的声明只能匹配没有存储类的卷。

我们涵盖了很多内容以及大量以不同方式制备和使用存储的选项。让我们将所有内容整合起来，展示从开始到结束的整个过程。

## 端到端演示持久卷存储

为了说明所有概念，让我们做一个小型演示，其中我们创建一个 HostPath 卷，声明它，挂载它，并让容器写入它。我们将使用 k3d 进行此部分。

首先，让我们使用 `dir` 存储类创建一个 HostPath 卷。将以下内容保存到 `dir-persistent-volume.yaml`：

```yaml
kind: PersistentVolume
apiVersion: v1
metadata:
  name: dir-pv
spec:
  storageClassName: dir
  capacity:
    storage: 1Gi
  accessModes:
  - ReadWriteMany
  hostPath:
    path: "/tmp/data"
```

```bash

dir-pv  1Gi        RWX            dir             Retain           Available          22s
```

容量是请求的 1 GiB。回收策略是 Retain，因为 HostPath 卷被保留（不会被销毁）。状态是 Available，因为该卷尚未被声明。访问模式指定为 RWX，表示 ReadWriteMany。所有访问模式都有简写版本：

-   RWO – ReadWriteOnce
-   ROX – ReadOnlyMany
-   RWX – ReadWriteMany

我们有一个持久卷。让我们创建一个声明。将以下内容保存到 `dir-persistent-volume-claim.yaml`：

```yaml

apiVersion: v1

  name: dir-pvc

  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
```

然后，运行以下命令：


让我们检查声明和卷：

```bash

dir-pv  1Gi        RWX            dir             Retain           Bound    default/dir-pvc  4m25s
```

如您所见，声明和卷相互绑定并相互引用。绑定之所以有效，是因为卷和声明使用了相同的存储类。但是，如果它们不匹配会怎样？让我们从持久卷声明中移除存储类，看看会发生什么。将以下持久卷声明保存到 `some-persistent-volume-claim.yaml`：


## 公有云存储卷类型——GCE、AWS 和 Azure

在本节中，我们将了解主要公有云平台上一些常见的卷类型。大规模管理存储是一项困难的任务，最终涉及物理资源，类似于节点。如果您选择在公有云平台上运行 Kubernetes 集群，可以让云提供商处理所有这些挑战，并专注于您的系统。但了解每种卷类型的各种选项、约束和限制很重要。

> 我们将介绍的许多卷类型过去由树内插件（核心 Kubernetes 的一部分）处理，但现在已迁移到树外 CSI 插件。
> CSI 迁移功能允许具有对应树外 CSI 插件的树内插件将操作定向到树外插件，作为过渡措施。
> 我们稍后将在"容器存储接口"部分介绍 CSI 本身。

### AWS Elastic Block Store (EBS)

AWS 提供 Elastic Block Store (EBS) 作为 EC2 实例的持久存储。AWS Kubernetes 集群可以使用 AWS EBS 作为持久存储，但有以下限制：

-   Pod 必须在作为节点的 AWS EC2 实例上运行
-   Pod 只能访问在其可用区中制备的 EBS 卷
-   一个 EBS 卷只能挂载到单个 EC2 实例上

这些是严重的限制。单一可用区的限制虽然有利于性能，但消除了大规模共享存储或在跨地理分布式系统中共享存储的能力（无需自定义复制和同步）。单个 EBS 卷只能挂载到单个 EC2 实例的限制意味着即使在同一个可用区内，除非确保 Pod 运行在同一个节点上，否则它们也无法共享存储（即使是只读）。

这是一个树内插件的例子，它也有 CSI 驱动程序并支持 CSIMigration。这意味着如果安装了 AWS EBS 的 CSI 驱动程序 (`ebs.csi.aws.com`)，树内插件会将所有插件操作重定向到树外插件。

也可以通过将 `InTreePluginAWSUnregister` 特性门控设置为 `true`（默认值为 `false`）来禁用加载树内 `awsElasticBlockStore` 存储插件。查看所有特性门控：[https://kubernetes.io/docs/reference/command-line-tools-reference/feature-gates/](https://kubernetes.io/docs/reference/command-line-tools-reference/feature-gates/)

让我们看看如何定义一个 AWS EBS 持久卷（静态制备）：

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: test-pv
spec:
  accessModes:
  - ReadWriteOnce
  capacity:
    storage: 5Gi
  csi:
    driver: ebs.csi.aws.com
    volumeHandle: {EBS volume ID}
  nodeAffinity:
    required:
      nodeSelectorTerms:
      - matchExpressions:
        - key: topology.ebs.csi.aws.com/zone
          operator: In
          values:
          - {availability zone}
```

然后你需要定义一个 PVC：

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: ebs-claim
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi
```

最后，Pod 可以挂载 PVC：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: some-pod
spec:
  containers:
  - image: some-container
    name: some-container
    volumeMounts:
    - name: persistent-storage
      mountPath: /data
  volumes:
  - name: persistent-storage
    persistentVolumeClaim:
      claimName: ebs-claim
```

### AWS Elastic File System (EFS)

AWS 有一个名为 Elastic File System (EFS) 的服务。这实际上是一个托管 NFS 服务。它使用 NFS 4.1 协议，相比 EBS 有许多优势：

-   多个 EC2 实例可以跨多个可用区访问相同的文件（但在同一区域内）
-   容量根据实际使用情况自动扩展和缩减
-   只需按使用量付费
-   可以通过 VPN 将本地服务器连接到 EFS
-   EFS 运行在 SSD 驱动器上，这些驱动器在可用区之间自动复制

也就是说，即使考虑到自动跨可用区复制，EFS 也比 EBS 更昂贵（假设您充分利用了 EBS 卷）。推荐通过其专用 CSI 驱动程序使用 EFS：[https://github.com/kubernetes-sigs/aws-efs-csi-driver](https://github.com/kubernetes-sigs/aws-efs-csi-driver)

以下是静态制备的示例。首先，定义持久卷：

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: efs-pv
spec:
  capacity:
    storage: 1Gi
  volumeMode: Filesystem
  accessModes:
  - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  csi:
    driver: efs.csi.aws.com
    volumeHandle: <Filesystem Id>
```

您可以使用 AWS CLI 查找 Filesystem Id：

```bash
aws efs describe-file-systems --query "FileSystems[*].FileSystemId"
```

然后定义一个 PVC：

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: efs-claim
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: ""
  resources:
    requests:
      storage: 1Gi
```

以下是消费它的 Pod：

```yaml
piVersion: v1
kind: Pod
metadata:
  name: efs-app
spec:
  containers:
  - name: app
    image: centos
    command: ["/bin/sh"]
    args: ["-c", "while true; do echo $(date -u) >> /data/out.txt; sleep 5; done"]
    volumeMounts:
    - name: persistent-storage
      mountPath: /data
  volumes:
  - name: persistent-storage
    persistentVolumeClaim:
      claimName: efs-claim
```

您也可以通过定义合适的存储类（而不是创建静态卷）来使用动态制备：

```yaml
kind: StorageClass
apiVersion: storage.k8s.io/v1
metadata:
  name: efs-sc
provisioner: efs.csi.aws.com
parameters:
  provisioningMode: efs-ap
  fileSystemId: <Filesystem Id>
  directoryPerms: "700"
  gidRangeStart: "1000"   # 可选
  gidRangeEnd: "2000"     # 可选
  basePath: "/dynamic_provisioning" # 可选
```

PVC 类似，但现在使用存储类名称：

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: efs-claim
spec:
  accessModes:
  - ReadWriteMany
  storageClassName: efs-sc
  resources:
    requests:
      storage: 5Gi
```

Pod 像之前一样消费 PVC：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: efs-app
spec:
  containers:
  - name: app
    image: centos
    command: ["/bin/sh"]
    args: ["-c", "while true; do echo $(date -u) >> /data/out; sleep 5; done"]
    volumeMounts:
    - name: persistent-storage
      mountPath: /data
  volumes:
  - name: persistent-storage
    persistentVolumeClaim:
      claimName: efs-claim
```

### GCE 持久磁盘

`gcePersistentDisk` 卷类型与 `awsElasticBlockStore` 非常相似。您必须提前制备磁盘。它只能由同一项目和区域中的 GCE 实例使用。但同一个卷可以在多个实例上以只读方式使用。这意味着它支持 `ReadWriteOnce` 和 `ReadOnlyMany`。您可以使用 GCE 持久磁盘在同一区域内的多个 Pod 之间以只读方式共享数据。

它也有一个 CSI 驱动程序，名为 `pd.csi.storage.gke.io`，并支持 CSIMigration。

如果使用 `ReadWriteOnce` 模式的持久磁盘的 Pod 由复制控制器、副本集或 Deployment 控制，则副本数必须为 0 或 1。尝试扩展到超过 1 会失败，原因显而易见。

以下是使用 CSI 驱动程序的 GCE 持久磁盘存储类：

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: csi-gce-pd
provisioner: pd.csi.storage.gke.io
parameters:
  labels: key1=value1,key2=value2
volumeBindingMode: WaitForFirstConsumer
```

以下是 PVC：

```yaml
kind: PersistentVolumeClaim
apiVersion: v1
metadata:
  name: gce-pd-pvc
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: csi-gce-pd
  resources:
    requests:
      storage: 200Gi
```

Pod 可以消费它进行动态制备：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: some-pod
spec:
  containers:
  - image: some-image
    name: some-container
    volumeMounts:
    - mountPath: /pd
      name: some-volume
  volumes:
  - name: some-volume
    persistentVolumeClaim:
      claimName: gce-pd-pvc
      readOnly: false
```

GCE 持久磁盘自 Kubernetes 1.10（Beta）起支持区域磁盘选项。区域持久磁盘自动在两个区域之间同步。以下是区域持久磁盘的存储类定义：

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: csi-gce-pd
provisioner: pd.csi.storage.gke.io
parameters:
  type: pd-standard
  replication-type: regional-pd
volumeBindingMode: WaitForFirstConsumer
```

### Google Cloud Filestore

Google Cloud Filestore 是 GCP 的托管 NFS 文件服务。Kubernetes 没有它的树内插件，也没有通用的受支持 CSI 驱动程序。

但是，GKE 上使用了一个 CSI 驱动程序，如果您喜欢冒险，可能在 GCP 上自行安装 Kubernetes 并希望使用 Google Cloud Storage 作为存储选项时，您可能想要尝试它。参见：[https://github.com/kubernetes-sigs/gcp-filestore-csi-driver](https://github.com/kubernetes-sigs/gcp-filestore-csi-driver)

### Azure 数据磁盘

Azure 数据磁盘是存储在 Azure 存储中的虚拟硬盘。其能力类似于 AWS EBS 或 GCE 持久磁盘。

它也有一个 CSI 驱动程序，名为 `disk.csi.azure.com`，并支持 CSIMigration。参见：[https://github.com/kubernetes-sigs/azuredisk-csi-driver](https://github.com/kubernetes-sigs/azuredisk-csi-driver)

以下是定义 Azure 磁盘持久卷的示例：

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-azuredisk
spec:
  capacity:
    storage: 10Gi
  accessModes:
  - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: managed-csi
  csi:
    driver: disk.csi.azure.com
    readOnly: false
    volumeHandle: /subscriptions/{sub-id}/resourcegroups/{group-name}/providers/microsoft.compute/disks/{disk-id}
    volumeAttributes:
      fsType: ext4
```

除了必需的 `diskName` 和 `diskURI` 参数外，它还有几个可选参数：

-   **kind**：磁盘存储配置的可用选项包括 Shared（每个存储帐户允许多个磁盘）、Dedicated（每个存储帐户提供单个 Blob 磁盘）或 Managed（提供 Azure 托管数据磁盘）。默认为 Shared。
-   **cachingMode**：磁盘缓存模式。必须是 `None`、`ReadOnly` 或 `ReadWrite` 之一。默认为 `None`。
-   **fsType**：要挂载的文件系统类型。默认为 `ext4`。
-   **readOnly**：文件系统是否以只读方式使用。默认为 `false`。

Azure 数据磁盘限制为 32 GiB。每个 Azure VM 最多可以有 32 个数据磁盘。更大的 VM 大小可以挂载更多的磁盘。您可以将 Azure 数据磁盘挂载到单个 Azure VM。

像往常一样，您应该创建一个 PVC 并在 Pod（或 Pod 控制器）中消费它。

### Azure 文件

除了数据磁盘，Azure 还有一个类似于 AWS EFS 的共享文件系统。但 Azure 文件存储使用 SMB/CIFS 协议（支持 SMB 2.1 和 SMB 3.0）。它基于 Azure 存储平台，与 Azure Blob、Table 或 Queue 存储具有相同的可用性、持久性、可扩展性和地理冗余能力。

要使用 Azure 文件存储，您需要在每个客户端 VM 上安装 `cifs-utils` 包。您还需要创建一个密钥，这是一个必需的参数：

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: azure-file-secret
type: Opaque
data:
  azurestorageaccountname: <base64 encoded account name>
  azurestorageaccountkey: <base64 encoded account key>
```

以下是一个使用 Azure 文件存储的 Pod：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: some-pod
spec:
  containers:
  - image: some-container
    name: some-container
    volumeMounts:
    - name: some-volume
      mountPath: /azure
  volumes:
  - name: some-volume
    azureFile:
      secretName: azure-file-secret
      shareName: azure-share
      readOnly: false
```

Azure 文件存储支持同一区域内的共享，也支持连接本地客户端。

这涵盖了公有云存储卷类型。让我们看看一些可以在集群中自行安装的分布式存储卷。

## Kubernetes 中的 GlusterFS 和 Ceph 卷

GlusterFS 和 Ceph 是两个分布式持久存储系统。GlusterFS 核心是一个网络文件系统。Ceph 核心是一个对象存储。两者都暴露块、对象和文件系统接口。两者都在底层使用 xfs 文件系统来存储数据，并将元数据作为 xattr 属性存储。您可能希望在 Kubernetes 集群中使用 GlusterFS 或 Ceph 作为持久卷的原因有几个：

-   您在本地运行，云存储不可用
-   您可能有很多数据以及访问 GlusterFS 或 Ceph 中数据的应用程序
-   您拥有管理 GlusterFS 或 Ceph 的运维专长
-   您在云中运行，但云平台持久存储的限制不可接受

让我们更详细地看看 GlusterFS。

### 使用 GlusterFS

GlusterFS 有意保持简单，按原样暴露底层目录，并将高可用性、复制和分发的处理留给客户端（或中间件）。GlusterFS 将数据组织成逻辑卷，这些卷包含多个节点（机器），节点包含砖块 (brick)，砖块存储文件。文件根据 DHT（分布式哈希表）分配到砖块。如果文件被重命名，或者 GlusterFS 集群被扩展或重新平衡，文件可能会在砖块之间移动。下图展示了 GlusterFS 的构建块：

![图 6.2: GlusterFS 构建块](ch06-fig02.png)

要使用 GlusterFS 集群作为 Kubernetes 的持久存储（假设您有一个正在运行的 GlusterFS 集群），您需要遵循几个步骤。具体来说，GlusterFS 节点由插件作为 Kubernetes 服务进行管理。

#### 创建端点

以下是一个端点资源的示例，您可以使用 `kubectl create` 将其作为普通 Kubernetes 资源创建：

```yaml
kind: Endpoints
apiVersion: v1
metadata:
  name: glusterfs-cluster
subsets:
- addresses:
  - ip: 10.240.106.152
    ports:
    - port: 1
  - addresses:
    - ip: 10.240.79.157
    ports:
    - port: 1
```

#### 添加 GlusterFS Kubernetes 服务

为了使端点持久化，您使用一个没有选择器的 Kubernetes 服务来指示端点是手动管理的：

```yaml
kind: Service
apiVersion: v1
metadata:
  name: glusterfs-cluster
spec:
  ports:
  - port: 1
```

#### 创建 Pod

最后，在 Pod 规范的 `volumes` 部分，提供以下信息：

```yaml
volumes:
- name: glusterfsvol
  glusterfs:
    endpoints: glusterfs-cluster
    path: kube_vol
    readOnly: true
```

然后容器可以按名称挂载 `glusterfsvol`。

端点告诉 GlusterFS 卷插件如何找到 GlusterFS 集群的存储节点。

曾经有创建 GlusterFS CSI 驱动程序的工作，但已被放弃：[https://github.com/gluster/gluster-csi-driver](https://github.com/gluster/gluster-csi-driver)

在介绍完 GlusterFS 之后，让我们看看 CephFS。

### 使用 Ceph

Ceph 的对象存储可以通过多个接口访问。与 GlusterFS 不同，Ceph 自动完成大量工作。它自行完成分发、复制和自我修复。下图展示了底层对象存储 RADOS 如何以多种方式被访问。

![图 6.3: 访问 RADOS](ch06-fig03.png)

Kubernetes 通过 Rados 块设备 (RBD) 接口支持 Ceph。

#### 使用 RBD 连接到 Ceph

您必须在 Kubernetes 集群的每个节点上安装 `ceph-common`。一旦您的 Ceph 集群启动并运行，您需要在 Pod 配置文件中提供 Ceph RBD 卷插件所需的一些信息：

-   **monitors**：Ceph 监视器。
-   **pool**：RADOS 池的名称。如果未提供，则使用默认的 RBD 池。
-   **image**：RBD 已创建的镜像名称。
-   **user**：RADOS 用户名。如果未提供，则使用默认的 admin。
-   **keyring**：密钥环文件的路径。如果未提供，则使用默认的 `/etc/ceph/keyring`。
-   **secretName**：认证密钥的名称。如果提供，secretName 会覆盖 keyring。注意：请参阅下一段关于如何创建密钥的内容。
-   **fsType**：在设备上格式化的文件系统类型（ext4、xfs 等）。
-   **readOnly**：文件系统是否以只读方式使用。

如果使用了 Ceph 认证密钥，您需要创建一个 Secret 对象：

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: ceph-secret
type: "kubernetes.io/rbd"
data:
  key: QVFCMTZWMVZvRjVtRXhBQTVrQ1FzN2JCajhWVUxSdzI2Qzg0SEE9PQ==
```

密钥类型是 `kubernetes.io/rbd`。

以下是一个使用树内提供商通过 RBD 结合密钥使用 Ceph 的示例 Pod：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: rbd2
spec:
  containers:
  - image: kubernetes/pause
    name: rbd-rw
    volumeMounts:
    - name: rbdpd
      mountPath: /mnt/rbd
  volumes:
  - name: rbdpd
    rbd:
      monitors:
      - '10.16.154.78:6789'
      - '10.16.154.82:6789'
      - '10.16.154.83:6789'
      pool: kube
      image: foo
      fsType: ext4
      readOnly: true
      user: admin
      secretRef:
        name: ceph-secret
```

Ceph RBD 支持 `ReadWriteOnce` 和 `ReadOnlyMany` 访问模式。但现在，最好通过 Rook 来使用 Ceph。

### Rook

Rook 是一个开源的云原生存储编排器。它目前是一个已毕业的 CNCF 项目。它最初在多种存储解决方案（如 Ceph、edgeFS、Cassandra、Minio、NFS、CockroachDB 和 YugabyteDB）之上提供一致的体验。但最终，它专注于仅支持 Ceph。以下是 Rook 提供的功能：

-   自动化部署
-   启动引导
-   配置
-   制备
-   扩展
-   升级
-   迁移
-   调度
-   生命周期管理
-   资源管理
-   监控
-   灾难恢复

Rook 利用了现代 Kubernetes 的最佳实践，如 CRD 和 Operator。

## 将企业存储集成到 Kubernetes

如果您有通过 iSCSI 接口暴露的现有存储区域网络 (SAN)，Kubernetes 有适合您的卷插件。它遵循与我们之前看到的其他共享持久存储插件相同的模型。它支持以下功能：

-   连接到一个门户 (portal)
-   直接或通过 multipathd 挂载设备
-   格式化并分区任何新设备
-   通过 CHAP 进行身份验证

您必须配置 iSCSI 发起程序，但不需要提供任何发起程序信息。您需要提供的只是：

-   iSCSI 目标的 IP 地址和端口（如果不是默认的 3260）
-   目标的 IQN（iSCSI 限定名称）——通常是反向域名
-   LUN（逻辑单元号）
-   文件系统类型
-   只读布尔标志

iSCSI 插件支持 `ReadWriteOnce` 和 `ReadonlyMany`。请注意，目前您不能对设备进行分区。以下是一个带有 iSCSI 卷规范的 Pod 示例：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: iscsipd
spec:
  containers:
  - name: iscsipd-rw
    image: kubernetes/pause
    volumeMounts:
    - mountPath: "/mnt/iscsipd"
      name: iscsipd-rw
  volumes:
  - name: iscsipd-rw
    iscsi:
      targetPortal: 10.0.2.15:3260
      portals: ['10.0.2.16:3260', '10.0.2.17:3260']
      iqn: iqn.2001-04.com.example:storage.kube.sys1.xyz
      lun: 0
      fsType: ext4
      readOnly: true
```

### 其他存储提供商

Kubernetes 存储领域不断创新。许多公司将其产品适配到 Kubernetes，一些公司和组织构建了专用于 Kubernetes 的存储解决方案。以下是一些更流行和成熟的解决方案：

-   OpenEBS
-   Longhorn
-   Portworx

## 容器存储接口

容器存储接口 (CSI) 是容器编排器和存储提供商之间交互的标准接口。它由 Kubernetes、Docker、Mesos 和 Cloud Foundry 共同开发。其理念是存储提供商只需实现一个 CSI 驱动程序，所有容器编排器只需支持 CSI 即可。它相当于存储领域的 CNI。

CSI 卷插件在 Kubernetes 1.9 中作为 Alpha 功能添加，自 Kubernetes 1.13 起已正式发布 (GA)。较旧的 FlexVolume 方法（您可能遇到过）现已弃用。

### 高级存储功能

这些功能仅适用于 CSI 驱动程序。它们代表统一存储模型的好处，允许通过统一接口在所有存储提供商上添加可选的高级功能。

#### 卷快照

卷快照自 Kubernetes 1.20 起已正式发布 (GA)。它们就像听起来那样——卷在某个时间点的快照。您可以创建快照，然后从快照恢复卷。有趣的是，与快照关联的 API 对象是 CRD，而不是核心 Kubernetes API 的一部分。这些对象是：

-   VolumeSnapshotClass
-   VolumeSnapshotContents
-   VolumeSnapshot

卷快照使用 Kubernetes 团队开发的外部快照 sidecar 容器 (external-snapshotter) 工作。它监视快照 CRD 的创建，并与快照控制器交互，快照控制器可以调用实现了快照支持的 CSI 驱动程序的 `CreateSnapshot` 和 `DeleteSnapshot` 操作。

以下是声��卷快照的方法：

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: new-snapshot-test
spec:
  volumeSnapshotClassName: csi-hostpath-snapclass
  source:
    persistentVolumeClaimName: pvc-test
```

您也可以从快照制备卷。

以下是一个绑定到快照的持久卷声明：

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: restore-pvc
spec:
  storageClassName: csi-hostpath-sc
  dataSource:
    name: new-snapshot-test
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
```

详情请参见 [https://github.com/kubernetes-csi/external-snapshotter#design](https://github.com/kubernetes-csi/external-snapshotter#design)。

#### CSI 卷克隆

卷克隆自 Kubernetes 1.18 起已 GA。卷克隆是用现有卷的内容填充的新卷。一旦卷克隆完成，原始卷和克隆之间就没有关系了。它们的内容会随时间推移而分叉。您可以通过创建快照然后从快照创建新卷来手动执行克隆。但卷克隆更加简化和高效。

它仅适用于动态制备，并且克隆也使用源卷的存储类。您通过将现有的持久卷声明指定为新持久卷声明的数据源来发起卷克隆。这会触发新卷的动态制备，该卷克隆源声明的卷：

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: clone-of-pvc-1
  namespace: myns
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: cloning
  resources:
    requests:
      storage: 5Gi
  dataSource:
    kind: PersistentVolumeClaim
    name: pvc-1
```

详情请参见 [https://kubernetes.io/docs/concepts/storage/volume-pvc-datasource/](https://kubernetes.io/docs/concepts/storage/volume-pvc-datasource/)。

#### 存储容量跟踪

存储容量跟踪（自 Kubernetes 1.24 起 GA）允许调度器更好地将需要存储的 Pod 调度到能够提供该存储的节点上。这需要支持存储容量跟踪的 CSI 驱动程序。

CSI 驱动程序会为每个存储类创建一个 `CSIStorageCapacity` 对象，并确定哪些节点可以访问此存储。此外，`CSIDriverSpec` 的 `StorageCapacity` 字段必须设置为 `true`。

当 Pod 在 `WaitForFirstConsumer` 模式下指定了存储类名称，并且 CSI 驱动程序的 `StorageCapacity` 设置为 `true` 时，Kubernetes 调度器会考虑与该存储类关联的 `CSIStorageCapacity` 对象，并仅将 Pod 调度到具有充足存储的节点上。

详情请参见 [https://kubernetes.io/docs/concepts/storage/storage-capacity](https://kubernetes.io/docs/concepts/storage/storage-capacity)。

#### 卷健康监控

卷健康监控是存储 API 的最新补充。自 Kubernetes 1.21 起一直处于 Alpha 阶段。它涉及两个组件：

-   外部健康监控器 (external health monitor)
-   kubelet

支持卷健康监控的 CSI 驱动程序会使用相关存储卷的异常状况事件更新 PVC。外部健康监控器还会监视节点的故障，并将事件报告给绑定到这些节点的 PVC。

如果 CSI 驱动程序从节点端启用了卷健康监控，则检测到的任何异常状况都会导致为每个使用有相应问题的 PVC 的 Pod 报告一个事件。

还有一个与卷健康相关的新指标：`kubelet_volume_stats_health_status_abnormal`。它有两个标签：`namespace` 和 `persistentvolumeclaim`。值为 0 或 1。

更多详情请参见 [https://kubernetes.io/docs/concepts/storage/volume-health-monitoring/](https://kubernetes.io/docs/concepts/storage/volume-health-monitoring/)。

CSI 是一个激动人心的举措，它通过外部化存储驱动程序简化了 Kubernetes 代码库本身。它简化了存储解决方案（可以开发树外驱动程序）的工作，并为 Kubernetes 的存储能力增加了许多高级功能。

## 总结

在本章中，我们深入探讨了 Kubernetes 中的存储。我们研究了基于卷、声明和存储类的通用概念模型，以及卷插件的实现。Kubernetes 最终将所有存储系统映射到容器中的挂载文件系统或原始块存储设备。这种直截了当的模型允许管理员配置和接入任何存储系统——从本地宿主目录，到基于云的共享存储，一直到企业存储系统。存储制备器从树内向基于 CSI 的树外驱动程序的转变对存储生态系统来说是一个好兆头。您现在应该清楚地理解存储如何在 Kubernetes 中建模和实现，并能够就如何在 Kubernetes 集群中实现存储做出明智的选择。

在第 7 章《在 Kubernetes 上运行有状态应用程序》中，我们将看到 Kubernetes 如何提高抽象层次，并在存储之上帮助使用有状态集 (StatefulSet) 等概念来开发、部署和运维有状态应用程序。
