# 在生产环境中运行Kubernetes

在上一章中，我们讨论了治理和策略引擎。这是管理大规模基于 Kubernetes 的生产系统的重要组成部分。然而，它只是其中的一部分。在本章中，我们将把注意力转向 Kubernetes 在生产环境中的整体管理。重点将放在在云中运行多个托管 Kubernetes 集群上。

我们将涵盖的主题包括：

- 理解云中的托管 Kubernetes
- 管理多集群
- 为大规模 Kubernetes 部署构建有效的流程
- 大规模处理基础设施
- 管理集群和节点池
- 升级 Kubernetes
- 故障排除
- 成本管理

## 理解云中的托管 Kubernetes

托管 Kubernetes 是由云服务提供商（如 Amazon Web Services（AWS）、Google Cloud Platform（GCP）和 Microsoft Azure）提供的服务，它简化了容器化应用程序在云中的部署、管理和扩展。通过托管 Kubernetes，组织可以专注于开发和部署应用程序，而无需过多担心底层基础设施。

托管 Kubernetes 提供了一个预配置和优化的环境来部署容器，消除了手动设置和维护 Kubernetes 集群的需要。这使得组织能够快速部署和扩展其应用程序，缩短上市时间，并释放宝贵资源。

此外，托管 Kubernetes 与云提供商的其他服务集成，如数据库、网络、存储解决方案、安全、身份和可观测性功能，使管理和保护整个应用栈变得更加容易。这也使组织能够利用云提供商在管理大规模基础设施、确保高可用性和减少停机时间方面的专业知识。

总体而言，托管 Kubernetes 提供了一种简化和高效的方式来在云中部署和管理容器化应用程序，减少了运营开销并改善了上市时间。这使得它成为各种规模的组织想要利用容器和云优势的一个有吸引力的选择。

### 深度集成

云提供商利用 Kubernetes 的可扩展性，通过 CNI、CSI 以及认证/授权插件，将其托管 Kubernetes 解决方案与其云服务进行深度集成。云提供商还实现了云控制器接口（CCI），以允许其计算基础设施作为 Kubernetes 节点提供服务。

然而，集成更加深入。云提供商通常配置 kubelet，控制在每个节点上运行的容器运行时，并在每个节点上部署各种 DaemonSet。

例如，AKS 利用了许多 Azure 服务：

- **Azure Compute**：AKS 利用 Azure 计算资源（如虚拟机（VM）、可用集和规模集）来提供托管的 Kubernetes 体验。
- **Azure Virtual Network**：AKS 与 Azure Virtual Network 集成，允许用户创建和管理自己的虚拟网络和子网。这为用户提供了对其网络布局的控制以及严格控制网络流量的能力。
- **Azure Blob Storage**：AKS 与 Azure Blob Storage 集成，允许用户在云中存储和管理其应用程序数据。这为用户提供了可扩展、安全且高可用的应用程序存储。
- **Azure Key Vault**：AKS 与 Azure Key Vault 集成，允许用户安全管理密码、密钥和证书等机密。这为用户提供了安全的应用程序机密存储。
- **Azure Monitor**：AKS 与 Azure Monitor 集成，允许用户从其应用程序收集和分析指标、日志和追踪。这为用户提供了监控和故障排除其工作负载的能力。
- **Azure Active Directory（AAD）**：AKS 与 AAD 集成，为运行 Kubernetes 集群提供安全、可靠和高可用的平台。AAD 提供了高效和安全的方式来认证和授权用户和应用程序访问集群。AAD 还可以与 Kubernetes RBAC（基于角色的访问控制）集成，以提供对集群资源的细粒度访问控制。

现在让我们来讨论在云中成功管理生产级基于 Kubernetes 的系统的关键要素之一。

### 配额和限制

云基础设施彻底改变了组织存储和管理数据以及运行工作负载的方式。然而，一个需要关注的主要问题是云服务提供商使用的配额和限制。这些配额和限制虽然对于确保云基础设施的稳定性和安全性是必要的，但可能成为用户沮丧甚至宕机的主要来源。

配额和限制是对用户可以消耗的资源数量的限制。例如，可能限制了在每个区域环境中可以创建的特定类型虚拟机的数量，或者可以使用的存储空间配额。设置这些配额和限制是为了防止单个用户消耗过多资源，从而可能破坏云基础设施的整体性能。它还保护用户不会意外预配大量他们实际上不需要但必须付费的资源。

理论上，云是无限可扩展和弹性的。在实践中，这仅在配额和限制范围内成立。

现在我们了解了配额和限制是什么，让我们讨论容量规划。

#### 容量规划

在过去，容量规划意味着考虑数据中心需要多少台服务器、磁盘应该有多大以及网络的带宽。这是基于工作负载的使用情况以及为冗余和增长保持健康的余量来确定的。然后，你还需要考虑升级以及如何淘汰过时的硬件。在云中，你不需要担心硬件。但是，你确实需要围绕配额和限制进行规划。这意味着你需要监控配额和限制，每当接近当前配额时，请求增加配额。对于诸如特定 VM 系列的 VM 实例数量之类的配额，我建议尽可能保持在 50%-60% 以下。这将为灾难恢复和增长以及蓝绿部署（在新旧版本并行运行一段时间）留出充足的空间。

#### 何时不应该使用托管 Kubernetes？

托管 Kubernetes 很棒，但它不是万能药。在某些情况下，你可能更愿意自己管理 Kubernetes，例如：

- 最明显的用例是你在本地运行 Kubernetes，而托管解决方案根本不可用。但是，你可以通过 GKE Anthos、AWS Outposts 和 Azure Arc 等平台运行类似于云托管 Kubernetes 的部署栈。
- 你需要对控制平面、节点组件以及在每个节点上运行的 DaemonSet 进行极端控制。
- 你已经拥有自行运行 Kubernetes 的内部专业知识，而使用托管 Kubernetes 可能需要陡峭的学习曲线，并且可能成本更高。
- 你管理高度敏感的信息，必须完全控制且不能信任云提供商。
- 你在多个云提供商和/或混合环境中运行 Kubernetes，并且希望在所有环境中使用统一的方式来管理 Kubernetes。
- 你希望确保自己不被锁定在特定的云提供商上。

简而言之，存在各种情况你可能需要自行管理 Kubernetes。让我们看看在不同环境中部署和管理多个 Kubernetes 集群的各种方式。

## 管理多集群

单个 Kubernetes 集群功能强大，可以管理大量工作负载（数千个节点和数十万个 Pod）。作为初创公司，你可能会依靠一个集群走得很远。然而，在企业规模上，你将需要多个集群。让我们考虑一些用例。

### 地理分布式集群

地理分布式集群是在不同位置运行的集群。使用地理分布式集群有三个主要原因：

- 使数据和负载靠近其消费者。
- 合规和数据隐私法律要求数据必须保留在其原产国。
- 高可用性和灾难恢复，以应对区域性故障。

### 多云

如果你在多个云上运行，那么自然每个云提供商至少需要一个集群。在多云上运行可能很复杂，但在企业规模上，这可能是不可避免的，有时也是可取的。例如，你的公司可能在云 X 上运行 Kubernetes，并收购了一家在云 Y 上运行 Kubernetes 的公司。从 Y 迁移到 X 可能风险太大且成本太高。在多云上运行的另一个合理原因是为了在与云提供商谈判时拥有筹码，以获得更好的折扣并确保你不会完全被锁定。最后，它可能使你能够容忍某个云提供商的完全宕机（这并不容易实现）。

### 混合云

混合 Kubernetes 意味着一些 Kubernetes 集群在云中运行（使用单个或多个云提供商）和某些 Kubernetes 集群在本地运行。

这种情况可能像以前一样由于收购而产生，或者即使你正处于从本地 Kubernetes 迁移到云的过程中。大型系统可能需要数年才能完成迁移，在迁移期间，你将不得不同时运行混合环境中的 Kubernetes 集群。

你还可能采用诸如"突发到云"之类的模式，即你的大多数 Kubernetes 集群在本地运行，但你可以灵活地将工作负载部署到云中的 Kubernetes 集群，以便在遇到意外负载或本地基础设施出现问题时快速扩展。

### 边缘 Kubernetes

大多数企业数据（约 90%）是在云和私有数据中心生成的；然而，根据 Gartner 的数据，到 2025 年，这一数字将下降到仅 25%。这令人震惊。边缘计算（AKS IoT）将负责这一巨大转变。

分布在各处的大量设备将产生持续的数据流。其中一些数据将被发送回后端进行处理、聚合和存储。然而，在数据附近执行各种形式的数据处理比直接发送原始数据更有意义。在某些情况下，你甚至可以在靠近数据的本地运行工作负载，并完全在边缘为用户提供服务。

这就是边缘计算的承诺。在边缘运行 Kubernetes 允许组织将数据处理靠近数据生成源，从而减少将数据发送到集中式数据中心或云的延迟和带宽需求。这带来了更快的响应时间和实时数据处理，使其成为工业 IoT、自动驾驶车辆和其他实时数据处理应用等场景的理想解决方案。

然而，在边缘运行 Kubernetes 也有其自身的挑战。边缘设备通常资源受限，因此有必要针对边缘环境优化 Kubernetes 的部署。组织还必须考虑边缘设备的网络连接和可靠性，以及在边缘部署 Kubernetes 集群的安全和隐私影响。

像 CNCF KubeEdge（https://kubeedge.io）这样的项目可以帮助你入门。

不过，在本章的其余部分，我们将专注于云中的大规模基于 Kubernetes 的系统。

## 为大规模 Kubernetes 部署构建有效的流程

要在生产环境中运行多集群 Kubernetes 系统，你必须制定一套涵盖操作各个方面的有效流程和最佳实践。以下是一些关键领域。

### 开发生命周期

多集群基于 Kubernetes 的系统在生产环境中的开发生命周期可能是一个复杂的过程，但通过正确的方法可以简化它。

你**绝对**应该实施 CI/CD 流水线，自动构建、测试和部署代码变更。该流水线应与 Git 等版本控制系统集成，并且还应包括自动化测试以确保代码质量。

管理代码库不同领域的所有权和审批流程非常重要。Kubernetes 命名空间可以提供一种便捷的方式来组织工作负载和相应的软件资产，并将其与团队和利益相关者关联起来。

你应该拥有变更、正在进行的构建和部署的完整追踪，以及冻结活动和回滚每个工作负载变更的能力。

控制工作负载在不同集群和区域的逐步部署也很重要，以避免错误变更同时部署到所有地方并导致整个系统宕机的情况。

### 环境

代码审查和谨慎的增量部署同时监控结果，对于拥有多个 Kubernetes 集群的大型企业系统来说是必要的，但还不够。某些变更可能只有在运行一段时间后或在特定条件下才会显示出负面影响，这将逃过我们之前提到的控制机制。最佳实践是拥有多个运行时环境，例如生产、预发布（staging）和开发（development）。环境的具体划分可能有所不同，但通常你至少需要一个生产环境（管理所有数据且用户与之交互的实际系统）和一个预发布环境（模拟生产系统，可以在其中测试变更和新版本，而不会影响用户或冒导致生产环境宕机的风险）。

让我们考虑一下使用多个环境的一些方面。

#### 隔离的环境

预发布环境不能意外污染和影响生产环境，这一点至关重要。例如，如果你在预发布环境中运行压力测试，并且预发布环境中的某些工作负载配置错误并访问了生产端点，那么你将陷入非常麻烦的困境。

严格的网络隔离是良好第一步，使预发布环境无法访问生产环境。你仍然需要注意预发布和生产环境通过公共端点的交互。预发布工作负载不应拥有允许访问生产环境的密钥和身份。

#### 预发布环境的保真度

预发布环境的主要动机是在将变更部署到生产环境之前测试变更以及与其他子系统的交互。这意味着预发布环境应尽可能模拟生产环境。然而，运行生产环境的精确副本成本过高。

预发布环境应使用相同自动化的 CI/CD 流水线进行配置和设置，该流水线能够部署预发布和生产环境。

预发布基础设施和资源也应使用与生产相同的工具来配置，尽管通常分配给预发布的资源会更少。

你可能希望能够临时缩减甚至完全关闭预发布环境的某些部分，并仅在必要时将其恢复以在预发布中运行大规模测试。

#### 资源配额

预发布和生产环境中的资源配额可以确保配置错误甚至攻击不会导致过度的资源使用。

#### 升级流程

一旦变更在预发布环境中经过充分测试，应该有明确的升级流程将其部署到生产环境。不同组件的流程可能不同，取决于变更的范围和影响。升级可以完全自动化，CI/CD 流水线检测到预发布测试成功完成后直接进行生产部署，也可能涉及额外步骤，可能需要另一次针对生产的显式部署。

### 权限和访问控制

当你管理运行在云基础设施上的一组 Kubernetes 集群时，需要非常关注权限模型和访问控制。这建立在前面关于开发生命周期和环境的最佳实践之上。

#### 最小权限原则

最小权限原则来自安全领域，但在安全之外，它对可靠性、性能和成本也非常有用。参与者——无论是人还是工作负载——不应拥有超出完成其任务所必需的权限。通过将访问权限降到最低，你可以确保不会发生意外或恶意的资源操作。

此外，在调查事件时，它会自动将可能的嫌疑人缩小到那些有权对错误配置资源进行操作或执行无效操作的人。

如果你遵循 GitOps 模型，可以创建一个工作流程，其中对集群和基础设施的每次更改都由 CI/CD 和专用工具完成。人类工程师只有只读访问权限。可以设置一些特殊的例外（参见本章的"紧急破例"部分）。

#### 将权限分配给组

强烈建议将权限分配给组或团队，而不是个人。即使当前只有一个人在执行需要特定权限集的任务，你也应该定义一个组，让这个人成为唯一成员。这样可以更方便地在以后添加其他人或替换人员。

#### 微调权限模型

然而，有时过于严格的权限模型可能适得其反。你将需要维护一组非常细粒度的权限，用于大量资源。每当发生最微小的变化（例如需要对某个资源执行另一个操作）时，你都需要修改权限。

要找到一条黄金路径——既不是给每个人超级管理员权限，也不是为每个资源费尽心思地创建成百上千个角色。

特别是，考虑在开发环境（可能还有预发布环境）中放宽权限模型。这些环境是进行大量实验的地方，你可以发现需要执行哪些操作以及实际上需要哪些权限，然后在部署到生产环境之前调整权限模型。

#### 紧急破例

有时，你的 CI/CD 流水线本身可能崩溃，或者由于覆盖不全，某些资源可能是手动配置的。在这些情况下，人类工程师必须干预，可以说"打破常规"，直接对 Kubernetes 或云基础设施采取行动。

建议制定一个正式的流程来获取紧急破例访问权限：谁有权获得、持续多长时间、并记录谁拥有过这种权限。

这引出了下一节关于可观测性的内容。

### 可观测性

一个全面的可观测性栈是绝对必要的。由多个 Kubernetes 集群组成的复杂系统可以从理论上进行推理和理解。你必须拥有来自云提供商、Kubernetes 本身和工作负载的完整事件记录。你的 CI/CD 流水线和其他工具也必须是完全可观测的。

让我们看看多集群可观测性的一些要素。

#### 一站式可观测性

云提供商和 Kubernetes 本身以日志和指标的形式提供了大量开箱即用的可观测性。然而，这些通常是在集群级别组织的。如果你正在处理跨多个集群的广泛问题，那么进入每个单独的集群、提取可观测性数据并试图理解它将非常困难，在一定的规模下甚至不可能。你必须将所有可观测性数据发送到一个集中式系统，在那里可以进行聚合、汇总，并准备好进行多集群分析和响应。

#### 可观测性栈的故障排除

你的可观测性栈是系统不可或缺的组成部分。如果它宕机或降级，你可能盲目飞行，无法有效响应问题。此外，跨集群问题可能会影响你的可观测性栈，就像它影响整个系统一样。请非常仔细地考虑这种场景，并确保如果主要可观测性栈暂时无法胜任工作时，你有足够的冗余和可观测性替代方案。例如，如果你的集中式可观测性栈受损，你可以依赖集群内的可观测性解决方案。如果你想要完全冗余，可以在两个云提供商上运行并行的可观测性栈。

考虑测试 CI/CD 流水线和可观测性栈宕机这些严峻的场景，看看你如何运作。

接下来，让我们更具体地研究不同类型的基础设施以及如何大规模处理它们。

## 大规模处理基础设施

在云中运行大规模多集群 Kubernetes 时，最具挑战性的任务之一是处理云基础设施。在某些方面，这比负责底层计算、网络和存储基础设施要好得多。但是，你失去了很多控制权，而且故障排除问题也很有挑战性。

在深入讨论每个基础设施类别之前，让我们先看看一些通用的云级别考虑因素。

### 云级别的考虑因素

在云中，你将资源组织在实体中，例如 AWS 账户、GCP 项目和 Azure 订阅。一个组织可能有多个这样的组，每个组都有自己的限制和配额。为简洁起见，我们统称为"账户"。企业组织的基础设施需求将超过单个账户的容量。决定如何将基础设施分解到不同的账户至关重要。一个好的启发式方法是将环境——生产、预发布和开发——分离到不同的账户中。账户级别的隔离对这些环境非常有益。但是，这可能还不够，在单个环境内，你可能需要比单个账户能容纳的更多资源。

拥有一个坚实的账户管理策略是关键。账户也可以成为访问控制的边界，因为即使是账户管理员也无法访问其他账户。

请与你的安全团队讨论基于安全动机的账户划分。

另一个重要方面是区域的划分。如果你跨多个区域管理基础设施，并且这些区域中的工作负载相互通信，那么这将对延迟和成本产生严重影响。特别是，跨区域出站流量通常不是免费的。

让我们看看每个基础设施类别。

### 计算

托管 Kubernetes 的计算基础设施包括 Kubernetes 集群本身及其工作节点。工作节点通常分组为节点池，这不是 Kubernetes 的概念。你将系统如何分解为 Kubernetes 集群，以及每个集群中存在哪些类型的节点池，将极大地影响你大规模管理系统的能力。

理想情况下，你可以像对待牲畜一样对待集群，配置相同的集群，并轻松地在不同位置添加或删除集群。每个集群将具有相同的节点池。

这种统一一致的集群组织并不总是可能的。有时有理由为特定目的使用不同的集群。你仍然应该追求少量可以轻松复制的集群类型。

#### 设计集群分解

云中的集群通常从位于一个区域的虚拟网络中为节点和 Pod 分配私有 IP 地址。是的，可以拥有跨区域的广泛集群，但这是例外而非规则。强烈建议尽可能像对待牲畜一样管理集群，并自动在所有运营区域配置集群。

#### 设计节点池分解

节点池是具有相同实例类型的节点的组。它们通常可以在集群自动扩缩器的帮助下自动扩展以满足集群的需求。如何选择在集群中配置哪些节点池是一个基础性决策，会影响性能、成本和操作复杂性。

我们将在本章后面深入讨论这个问题。

### 网络

网络是基础设施中一个非常动态的领域。有很多自由度。延迟和带宽之间相互影响，存在细微差别。工作负载不能请求一定量的带宽或保证的延迟。此外，有很多外部因素会影响网络的连接性、可达性和性能。让我们看看我们必须考虑和规划的一些重要主题。

#### IP 地址空间管理

当你运行一个多集群基于 Kubernetes 的系统时，集群中的每个 Pod 都会获得一个唯一的私有 IP 地址。但是，如果你想连接多个集群，并让一个集群中的工作负载通过其私有 IP 地址访问其他集群中的工作负载，那么必须满足两个条件：

1. 不同集群的网络必须对等连接。
2. Pod 的私有 IP 地址在所有集群中必须是唯一的。

这需要对私有 IP 地址空间进行集中管理，并仔细为不同的集群分配 IP 范围。

云提供商在为集群分配 IP 地址范围的方法上略有不同。AKS 要求每个集群属于一个具有自己 IP 地址范围的 VNet，然后为节点和 Pod 分配来自 VNet IP 地址范围的子网。GKE 带有一个默认网络，没有自己的 IP 地址范围。集群通过具有自己 IP 地址范围的子网进行配置。

此外，服务也需要自己的 IP 地址，以及其他一些组件可能需要。

整个私有 IPv4 地址空间由几个块组成：

- `10.0.0.0/8`（A 类）
- `172.16.0.0/12`（B 类）
- `192.168.0.0/8`（C 类）

在大规模环境中，最重要的是 `10.0.0.0/8`，它包含 2^24 个 IP 地址，超过 1600 万个地址。这是大量的 IP 地址，但如果你不仔细规划，可能会导致碎片化，即使有大量未使用的 IP 地址，也可能耗尽大块地址段。

以下是一些管理 IP 地址空间的最佳实践：

- 为 Pod、节点和服务分配 CIDR 块，使其足够用且不会浪费太多空间。
- 注意 Kubernetes 和云提供商在支持的节点和 Pod 数量方面的限制。
- 考虑跨集群的网络对等连接和服务网格。
- 确保对连接的集群使用不重叠的 CIDR 块。
- 使用适当的工具来管理地址空间。
- 考虑 Pod 密度对 IP 地址空间的影响（例如，在 AKS 上，IP 地址会预先分配到节点上最大 Pod 数量，即使未使用）。
- 注意限制，例如一个区域中可用的最大 IP 地址数量。

#### 网络拓扑

所有云提供商都提供虚拟网络或 VPC 概念。所有云提供商也都有区域的概念，区域是云提供商托管资源的地理区域。具体来说，虚拟网络始终局限于单个区域。由于云中的 Kubernetes 集群与虚拟网络相关联，因此单个 Kubernetes 集群不能跨越多个区域。这对可用性和可靠性有影响。如果你想在区域故障中幸存下来，你需要跨不同区域的多个集群运行每个关键工作负载。此外，所有这些集群通常需要相互连接。我们将在下面的"跨集群通信"部分更多地讨论这个问题。但是，就网络拓扑而言，同一区域中的多个集群共享相同的虚拟网络可能更好。

#### 网络分段

网络分段是将网络划分为更小的子网。在 Kubernetes 的上下文中，最重要的子网是节点、Pod 和服务的子网。在某些情况下，节点和 Pod 共享同一个子网，在其他情况下，节点和 Pod 有独立的子网。无论哪种情况，你都需要规划并了解集群可以容纳多少节点和 Pod，并相应调整集群子网的大小。

#### 跨集群通信

当运行多个 Kubernetes 集群时，将集群组视为单一概念集群通常是有益的。这意味着任何集群中的 Pod 都可以直接通过其私有 IP 地址到达其他集群中的 Pod。这种扁平 IP 地址模型是将单个集群内的标准 Kubernetes 网络模型扩展到多个集群。这需要我们在前面讨论的两个要素：

1. 所有连接的集群中 Pod 的非冲突 IP 地址范围。
2. 集群之间的网络对等连接。

网络对等连接需求可能很繁琐，因为集群会不断创建和销毁。拥有一个单一的区域虚拟网络可以减少开销，并且只需要对区域虚拟网络进行对等连接。但是，如果你在同一区域中运行大量共享相同虚拟网络的集群，可能会遇到云提供商限制，从而阻碍你的增长。例如，在 Azure 上，一个 VNet 最多可以有 64K 个唯一 IP 地址。

#### 跨云通信

如果你的系统跨越多个云提供商，你需要考虑如何跨云提供商连接你的 Kubernetes 集群。有几种方法，各有利弊。

首先，你可以决定避免不同云提供商上的集群之间直接通信。如果部署在不同云上的 Kubernetes 集群需要相互通信，它们可以通过公共 API 进行。这种方法很简单，但消除了统一概念集群（其中 Pod 可以直接相互通信，无论它们在哪里）的想法。

站点到站点 VPN 是一种通信方法，不同云提供商可以通过 BGP 连接系统，并通过位于虚拟网络前面的 VPN 网关建立到另一个云提供商管理的网络的 VPN 连接。这建立了一个安全通道；但是，VPN 网关设置并不简单，并且会带来显著的开销。

专线连接（也称为直接对等连接）是另一种选项，需要在云提供商的接入点安装路由器。此方法允许将运行在私有数据中心中的 Kubernetes 集群连接到云中的集群。此外，性能要好得多，因为中间没有 VPN 网关。缺点是设置相当复杂，并且你可能需要遵守各种要求。对于具有深厚底层网络专业知识的组织来说，这是一个不错的选择。

运营商或合作伙伴对等连接类似于专线连接；但是，你利用了已建立的第三方（专门提供此服务，已与云提供商建立关系并通过认证）的专业知识。当然，你需要为此服务付费。

#### 跨集群服务网格

正如我们在第 14 章"使用服务网格"中所讨论的，服务网格为 Kubernetes 带来了巨大价值。当在生产环境中运行多个 Kubernetes 集群时，通过服务网格连接所有集群可以说更加重要。服务网格的高级功能和策略可以应用于跨所有集群的连接和路由管理。

有两种方法需要考虑：

1. 单个完全连接的服务网格。
2. 将集群划分为多个网格。

单个完全连接的网格在概念上符合单一概念 Kubernetes 集群的方法。一切都简单明了。新集群只需加入网格，网格配置为允许每个 Pod 与每个其他 Pod 通信（只要路由策略允许）。

但是，你最终可能会遇到可扩展性障碍，因为单个网格意味着网格控制平面需要处理所有集群中所有工作负载的策略，并且为所有 Pod 更新 sidecar 可能会给你的集群带来很大负担。

另一种方法是拥有多个独立的网格。属于特定网格的集群中的 Pod 可以直接与同一服务网格中所有其他集群中的 Pod 通信，但必须通过公共端点才能访问其他服务网格中的集群。

多网格方法更具可扩展性，但复杂得多。你需要考虑如何将系统划分为不同的服务网格，以及新集群加入或离开系统时如何影响你的整体架构。

在多服务网格的情况下，私有 IP 地址空间管理可能更加微妙，不同的服务网格可以拥有冲突的 IP 地址。这意味着你可以为每个网格单独管理 IP 地址空间。

服务网格还提供了另一种有趣的跨集群连接解决方案，即东西向网关。使用东西向网关方法，不同集群中的工作负载通过每个集群中的专用网关间接通信。这意味着每个集群的私有 IP 地址是未知的，并且每次跨集群通信都有一个额外的跳数。

#### 大规模管理出口流量

某些系统需要频繁访问外部系统。也许你经常从外部系统获取数据，或者你的系统的目的是通过 API 管理一些外部系统。出口流量可能存在需要特别关注的独特问题。一些第三方组织甚至国家可能具有阻止或限制来自某些地理区域或特定 IP CIDR 块的流量的策略。例如，中国及其防火长城以阻止和审查大量公司（如 Google 和 Facebook）而闻名。如果你在 GCP 上运行并需要访问中国，这可能是一个严重的问题。

除了完全封锁外，如果你大规模尝试访问某些第三方 API，可能存在限制和限流。

如果你坚持访问这些第三方 API，甚至可能被举报，你的云提供商可能会施加各种制裁。

让我们考虑一些解决这些现实问题的方案。

如果你的当前云提供商不允许访问你的目标目的地，那么你必须在云提供商之外建立出口存在。这可以在另一个云提供商上，或通过一个信誉良好的中间组织进行。这种代理方法可以有多种形式，超出了本节的范围。

如果你正在被限流，那么问题可能是你从同一个源 IP 地址发送了太多请求。一个好的解决方案是创建一个具有不同公共 IP 地址的出口节点池，并通过多个不同的 IP 地址分发你的请求。定期轮换你的公共 IP 地址也会有帮助，这在云中很容易实现，只需重新创建实例即可获得新的公共 IP 地址。

相反的问题是，如果你与某个第三方公司有协议，他们通过白名单你提供的一些 IP 地址来专门允许来自你的组织的流量。在这种情况下，你需要管理不会变化的静态公共 IP 地址，并确保对该第三方组织的所有请求都通过白名单 IP 地址发出。

最后，为了解决被云提供商举报和标记的风险，你可能需要将你的出口访问隔离到单独的账户中。大多数云提供商的制裁是账户级别的。如果你的出口账户被云提供商禁用，至少它不会拖垮整个企业。

#### 在集群级别管理 DNS

具有大量 Pod 和服务的大规模集群可能会给 CoreDNS（Kubernetes 的内部 DNS 服务器）带来高负载。确保足够的 DNS 容量非常重要，因为集群中工作负载之间的大多数内部通信使用 DNS 名称进行寻址，而不是直接使用 IP 地址。

建议使用 DNS 自动扩缩，这通常默认未启用。更多详情请参见 https://kubernetes.io/docs/tasks/administer-cluster/dns-horizontal-autoscaling/。

### 存储

存储可以说是基础设施中最关键的要素。这里存放着你的持久数据，是组织的长期记忆。

#### 选择正确的存储解决方案

云中有许多可用于 Kubernetes 集群的存储解决方案，例如云原生 Blob 存储、托管存储服务、托管数据库和托管文件系统。你应该深入了解每种存储解决方案的性能、持久性和成本，并将其与你的存储用例进行匹配。

你的基线始终应该是云原生 Blob 存储（也称为"桶"），如 AWS S3、GCP Google Cloud Storage 或 Azure Blob Storage。很难想象一个大规模托管 Kubernetes 企业不使用桶。

然后，考虑更结构化或更高层次的存储解决方案。如果你的目标是保持云无关，你可以忽略基于云的托管存储解决方案，并部署自己的解决方案，正如我们在第 6 章"管理存储"中所看到的。

在企业规模上，考虑不同重要性级别的数据使用不同的访问速度和成本可能是值得的。

#### 数据备份和恢复

规划数据备份和恢复。你的数据是有价值的。数据备份和恢复对于生产环境至关重要。考虑实施可靠且可扩展的数据备份和恢复流程，并确保定期测试和更新。

你还应该考虑数据保留策略，而不是自动假设所有数据必须永久保留。

当然，为了遵守 GDPR 等数据隐私法律和法规，你还需要构建选择性删除数据的能力。

#### 存储监控

建立存储监控。句号。监控存储性能、使用情况和容量对于在问题影响应用程序可用性或性能之前识别和解决问题至关重要。设置存储利用率、延迟和吞吐量的监控和告警。这对于托管存储很重要，对于节点存储也很重要，因为日志很容易积累并使节点无法运行。

#### 数据安全

实施数据安全措施。保护敏感数据并确保符合数据保护法规对于生产环境至关重要。实施访问控制、加密和数据安全策略以保护你的数据。

#### 优化存储使用

云中的 Kubernetes 集群可能很昂贵，存储成本可能很快累积起来。通过删除未使用的数据、使用数据压缩或去重以及设置存储分层来优化存储使用。

#### 测试和验证存储性能

在将应用程序部署到生产环境之前，测试和验证存储解决方案的性能，以确保其满足工作负载的性能要求。

通过考虑这些因素并实施在云中为 Kubernetes 集群管理生产存储的最佳实践，你可以确保应用程序获得可靠且可扩展的存储性能。

既然我们已经涵盖了大规模管理云基础设施的许多指南和最佳实践，让我们聚焦于集群和节点池的管理，这是管理生产级多集群 Kubernetes 的核心。

## 管理集群和节点池

管理集群和节点池是大型基于 Kubernetes 的企业最高级别的基础设施管理活动。在本节中，我们将研究几个关键方面，包括配置、装箱和利用率、升级、故障排除和成本管理。

### 配置托管集群和节点池

有不同的方法来配置集群和节点池。你应该明智地选择最适合你的用例的方法，因为这里的失败可能导致灾难性的宕机。让我们回顾一些选项。所有云提供商都通过 API、CLI 和 UI 提供集群和节点池配置。

我强烈建议避免直接使用这些方法中的任何一种，而是使用基于 GitOps 的声明式方法。以下是一些可靠的选项供考虑。

#### Cluster API

Cluster API 是来自 Cluster Lifecycle SIG 的一个开源项目。其目标是使配置、升级和操作多个 Kubernetes 集群更加容易。它专注于集群和节点池的生命周期。然而，它最初主要是作为使用 kubeadm 配置集群的一种方式。后来增加了对不同云提供商的托管集群支持，并且它仍然年轻。特别是，不支持 GKE（尽管你可以在 GCP 上配置 Kubernetes 集群作为基础设施层）。支持 AKS 和 EKS。

Cluster API 有很大的发展势头，如果你不运行 GKE，绝对应该考虑它。

#### Terraform/Pulumi

Terraform 和 Pulumi 在其方法上类似。它们可以在所有云提供商上配置集群和节点池。然而，这些工具本身无法响应带外更改，并且在配置后不监控基础设施的状态。它们的内部状态可能与现实世界产生偏差，这可能导致难以恢复的情况，需要仔细的"外科手术"。特别是，节点池经常需要配置或更新，而 Terraform 或 Pulumi 可能无法胜任这项任务。如果你对这些工具有丰富的经验，并且了解它们的怪癖和特殊要求，它们可能仍然是一个不错的选择。

#### Kubernetes Operator

另一种替代方案是使用 Kubernetes Operator，它将集群和节点池规范的 CRD 与云提供商进行协调。在底层，Operator 将调用云提供商的托管 Kubernetes API。这需要编写 Kubernetes Operator 方面的重要工作和专业知识，但能给你最终的控制权。

你可以尝试使用 Crossplane 而不是编写自己的 Operator；但是，Crossplane 目前的支持似乎还比较基础和不足。扩展范围的一种方法是使用 Upjet 项目（https://github.com/upbound/upjet）从 Terraform 提供程序生成 Crossplane 控制器。

#### 利用托管节点

你还可以尝试使用托管节点，这样永远不需要直接处理节点池和节点的配置。所有云提供商都提供某种形式的托管节点，例如 GKE AutoPilot、EKS + Fargate 和 AKS + ACI。对于企业用例，我认为你将需要比完全托管的节点池提供的更多控制。对于你的工作负载子集来说，这可能是一个不错的选择。然而，在大规模环境中，你会希望优化资源使用和性能，而托管节点池的限制可能过于严格。

一旦你确定了如何配置和管理集群和节点池，你应该把注意力转向有效使用你配置的资源。

### 装箱和利用率

云资源很昂贵。在 Kubernetes 上高效使用资源有两个部分：基于资源请求将 Pod 高效调度到节点，以及 Pod 实际使用它们请求的资源。

装箱意味着确保资源请求的总和尽可能接近目标节点上的可分配资源。一旦工作负载被调度到节点，在正常情况下即使节点利用率很低，它也不会被驱逐，但集群自动扩缩器等组件可以提供帮助。

资源利用率衡量请求的资源实际使用的百分比。资源利用率通常不是固定的，因为工作负载的资源使用量在其生命周期中可能会有很大变化。

装箱、资源利用率以及它们之间的相互作用有许多细微差别。例如，有不同的资源，如 CPU、内存、磁盘和网络。一个节点可能有 100% 的 CPU 装箱，但只有 20% 的内存装箱。节点上的网络和非临时磁盘是共享资源，Pod 可以请求以确保它们始终拥有一定数量的资源。这使操作和可靠性变得复杂。让我们讨论一些可以帮助驾驭这个复杂主题的原则和概念。

#### 理解工作负载形状

工作负载形状是工作负载 CPU 请求与其内存请求之间的比率。在云中，标准比率是 1 CPU 对应 4 GiB 内存。因此，你可以选择的大多数 VM 类型都提供具有此比率的资源容量。一些工作负载需要比此比率更多的内存或更多的 CPU。所有云提供商也提供比率为 1 CPU 对应 8 GiB 内存的高内存 VM 类型，以及比率为 1 CPU 对应 2 GiB 内存的高 CPU VM 类型。

了解工作负载的资源形状对于选择优化资源使用的 VM 类型至关重要。

例如，如果一个工作负载需要 1 CPU 和 8 GiB 内存，并且你将其调度到比率为 1:4 的 VM 类型上，你将需要在具有 2 CPU 和 8 GiB 内存的节点上运行它。没有其他 Pod 可以运行在这个节点上，因为原始工作负载使用了所有 8 GiB 内存。但是，2 个 CPU 中有 1 个根本没有被使用。将工作负载调度到比率为 1:8 的 VM 类型节点上会好得多，这确保了最佳的装箱效果。

#### 设置请求和限制

为工作负载设置请求和限制是正确利用资源的关键。回想一下，当你为 Pod 的容器设置请求时，它将被调度到一个节点，该节点具有至少等于所有容器请求总和的可分配资源。请求的资源分配给每个容器独占使用，只要 Pod 在节点上运行。如果可用，容器可以使用比请求更多的资源。如果你指定了 CPU 限制，并且容器尝试使用超过限制的 CPU，那么 Pod 可能会被节流（throttled）。如果你指定了内存限制，并且容器尝试使用超过限制的内存，那么容器将被 OOMKilled 并重新启动。

最佳实践是为 CPU、内存甚至临时存储（如果容器使用任何）设置资源请求。你怎么知道该请求多少？你可以从一个粗略的估计开始，随着时间的推移监控实际资源使用情况，并在之后进行微调。

但即使是这种直接的方法也有一些微妙之处。假设一个工作负载使用 2 到 4 个 CPU，平均使用 3 个 CPU。你应该请求 4 个 CPU 并确保工作负载永远不会被节流吗？但是，由于平均使用量只有 3 个 CPU，你浪费了整整一个 CPU。如果你请求 3 个 CPU，那么每当工作负载需要超过 3 个 CPU 时，你都会被节流吗？这取决于 Pod 调度到的节点上的可用 CPU。如果节点上的整体 CPU 由于所有 Pod 都需要大量 CPU 而饱和，那么这是可能的。

在普通请求之上，你还可以为工作负载分配优先级，这允许你控制高优先级工作负载的命运，并确保它们优先于非优先级或低优先级的工作负载。

是的，调度远非易事。如果你需要复习，请查看第 15 章"扩展 Kubernetes"中的"理解 Kubernetes 调度器的设计"部分。

现在让我们把注意力转向限制。一个简单的方法是将限制设置为等于请求。这通常确保容器不会使用超过其请求的资源，这使得装箱变得容易。然而，在现实世界中，工作负载的资源使用情况会变化。通常更经济的方法是请求少于最大用量，有时甚至少于平均用量。在这种情况下，你可以选择完全不设置限制，或者将限制设置为高于请求。例如，如果一个工作负载使用 1 到 4 个 CPU，那么你可能会决定请求 2 个 CPU 并将限制设置为 4 个 CPU。只请求 2 个 CPU 将允许将更多 Pod 打包到同一个节点上，或者将 Pod 调度到更小的节点上。那么，为什么还要设置限制呢？嗯，设置一些限制可以确保 Pod 不会失控，占满所有 CPU，并使其他可能设置了较低请求但实际需要额外 CPU 的 Pod 饥饿。

设置较高的内存限制更加重要，特别是对于更敏感且不应经常重新启动的工作负载，因为任何尝试使用超过限制分配内存的行为都将导致容器重新启动。

#### 利用 Init 容器

一些工作负载在刚启动时需要做大量工作，然后其资源需求就会降低。例如，一个工作负载需要 10 GiB 内存和 4 个 CPU 来获取一些数据并在内存中处理，然后才能处理请求。但是，一旦运行，它不需要超过 1 个 CPU 和 4 GiB 内存。如果 Pod 是长时间运行的，请求 4 个 CPU 和 10 GiB 内存将非常浪费。这就是 init 容器非常有用的时候。你可以将工作负载拆分为两个容器。所有需要 4 个 CPU 和 10 GiB 内存的初始化工作可以由一个 init 容器完成，然后主容器只需请求 1 个 CPU 和 4 GiB 内存。

#### 共享节点与专用节点

在设计节点池时，你需要做出两个基本选择。共享节点池有多个不同的工作负载被调度到同一个节点上并排运行。专用节点池让单个工作负载独占一个节点（可能是同一工作负载的多个实例）。

共享节点池很简单。极端情况下，你只有一个节点池，所有 Pod 都从这个节点池调度到节点上。如果你有多个共享节点池（例如，一个使用常规节点，一个使用竞价实例），那么你需要将污点（taint）分配给节点池，将容忍度（toleration）分配给工作负载，以及处理节点和 Pod 的亲和性。

由于你不确切知道哪些 Pod 组合最终会在哪个节点上，装箱可能存在效率低下的问题。但是，只要整体平均工作负载形状与节点的资源比率相匹配，大规模装箱应接近最优。

工作负载可以请求它们需要的 CPU、内存和临时存储。但是，节点上存在一些共享资源，如网络和磁盘 I/O，当同一节点上的其他工作负载可能尝试使用相同资源时，你无法轻松地为你的工作负载划分这些资源。

这就是专用节点池发挥作用的地方。关键工作负载（如数据库或事件队列）需要可预测的网络和磁盘 I/O。将此类工作负载调度到专用节点上可确保工作负载无需担心其他工作负载占用共享资源。

在这种情况下，让工作负载请求超过标准资源（如 CPU 或内存）的 50% 是有意义的，以确保关键工作负载的单个 Pod 在节点上调度。

请记住，系统守护进程也将在节点上运行并具有更高优先级。如果你的专用工作负载请求过多资源，它可能变得不可调度。

我曾在升级后遇到过这个问题，节点上的 DaemonSet 需要更多资源，导致专用工作负载在减少其资源请求之前变得不可调度。

#### 大节点与小节点

在云中，节点有多种尺寸，从 1 核到数十甚至数百核。你应该拥有许多小节点还是更少的大节点？

首先也是最重要的，你必须拥有适合最大工作负载的节点。例如，如果一个工作负载请求 8 个 CPU，那么你必须有至少具有 8 个 CPU 的节点可用。

但是更大的节点呢？较大节点在效率方面有优势。在云中，当你配置（例如）一个具有 1 个 CPU 核心和 4 GiB 内存的节点时，你实际上并不能得到所有这些资源。首先，操作系统、容器运行时和 kube-proxy 会占用它们的资源，然后是云提供商决定在每个节点上运行的额外进程，然后是各种系统 DaemonSet 和你自己的 DaemonSet。最后，剩下的是可供你的工作负载使用的资源。所有这些始终在每个节点上运行的进程和工作负载需要大量资源。但是，它们所需的资源与节点的大小不成比例。这意味着在小节点上，你付费的资源中可用于 Pod 的比例要小得多。让我们看一个例子。

在资源配置效率和为工作负载提供更多可用资源方面，大节点无疑取得了胜利。

然而，还需要考虑其他细微差别和考量。让我们考虑小型和短生命周期的工作负载。

##### 小型和短生命周期的工作负载

假设我们使用大节点，并且我们的集群装箱非常高效。某部署需要扩展并创建一个新 Pod。如果任何现有节点上没有空间容纳新 Pod，则必须配置一个新节点。然而，如果新 Pod 很小，那么我们实际上在一个大节点上只运行一个小 Pod 会浪费大量资源。在大规模环境中，当大量 Pod 快速创建和销毁时，这可能不是问题。但是，考虑以下场景——我们的集群通常在 100 个大节点上运行。在活动临时高峰期间，我们的集群扩展到 200 个大节点，然后活动恢复正常。我们的资源利用率现在是 50%（集群在 200 个节点中需要 100 个节点）。在理想情况下，集群自动扩缩器最终会将空节点缩减，直到我们有 100 个装箱良好的节点。但是，在现实世界中，特别是在存在小型短生命周期 Pod 的情况下，新 Pod 可能会被任意调度到所有 200 个节点，而自动扩缩器可能难以缩减。我们将在后面的"自定义调度"部分看到一些选项。

短生命周期工作负载的另一个问题是，即使它们可以在现有节点上找到空间，如果它们需要一段时间才能就绪，仍然会浪费资源。考虑一个需要 1 分钟就绪、平均运行 1 分钟的 Pod。这个 Pod 即使最佳利用其资源，也只能达到 50% 的利用率，因为在其被调度后，它会在节点上保留资源 2 分钟，但实际只工作 1 分钟。如果 Pod 需要拉取镜像，那么可能需要几分钟才能就绪。

Kubernetes 调度器非常复杂，也可以被扩展，正如我们在第 15 章"扩展 Kubernetes"中所介绍的。我们提到的不同用例中 Pod 调度效率低下的问题，可能通过选择不同的评分策略来解决。默认评分策略 `RequestedToCapacityRatio` 旨在将工作负载均匀分布到所有节点上。这对于紧密装箱并不理想。`MostAllocated` 评分策略可能更可取。更多详情请参见 https://kubernetes.io/docs/concepts/scheduling-eviction/resource-bin-packing。

##### Pod 密度

Pod 密度是每个节点的最大 Pod 数（Kubernetes 默认值为 110）。如前所述，一些资源（如私有 IP 地址或系统守护进程的 CPU 和内存）可能与 Pod 密度相关。如果 Pod 密度太高，那么你可能会浪费预先分配以支持每个节点上许多 Pod 的资源。但是，如果将 Pod 密度设置得太低，那么你可能无法调度足够的 Pod 在节点上运行。让我们考虑一个具有 64 个 CPU 核心和 256 GiB 内存的大节点。如果 Pod 密度为 100，那么最多可以在该节点上运行 100 个 Pod。假设我们有很多只使用 10 mCPU 和 100 MiB 内存的小 Pod。100 个 Pod 总共只需 10 个 CPU 核心和 10 GiB 内存。如果 100 个这样的 Pod 被调度到一个大节点上，该节点将严重未充分利用。54 个 CPU 核心和 246 GiB 内存将被浪费。

如果你采用共享节点池模型，那么具有不同工作负载形状和资源需求的 Pod 的任意组合可以被调度到节点上。

#### 备用节点池

云提供商偶尔会遇到临时容量问题，因此无法配置新节点。此外，如果对常规节点的需求很大，竞价实例可能随时消失。好消息是，这些故障通常是区域性的，并且通常仅限于特定的实例类型或 VM 系列。

解决这个问题的一个好策略是使用备用节点池。

备用节点池是一个禁用了自动扩缩的空节点池，具有与另一个活动节点池相同的标签和污点，但使用不同的 VM 系列或不同的节点类型（例如，常规与竞价）。如果活动节点池无法配置更多节点并且存在 Pending 的 Pod，那么备用节点池可以被调整大小和/或启用自动扩缩。这将允许 Pending 的 Pod 被调度到备用节点池，直到本源节点池的情况得到解决。

如果你选择这条路，你需要制定一个合适的程序来激活备用节点池，包括检测活动节点池中的问题、手动或自动激活备用节点池的流程，以及在活动节点池恢复正常时缩回的流程。

确保备用节点池在需要时有足够的配额来取代其活动节点池，这一点非常重要。

这已经是对装箱和资源利用率的非常彻底的处理了。让我们把注意力转向升级。

## 升级 Kubernetes

升级 Kubernetes 可能是一个非常紧张的操作。仓促的升级可能会移除对某些资源版本的支持，如果你有不受支持的资源已部署，你将遇到灾难性故障。使用托管 Kubernetes 有其优缺点。在升级方面，在任何时候都有一个受支持版本的范围。

你可以升级到更新的受支持版本。但是，如果你延迟并忽视升级，一旦你落后于受支持版本的最新前沿，云提供商将自动升级你的集群和节点池。让我们看看你必须掌握升级 Kubernetes 的各种要素。

### 了解云提供商的生命周期

云提供商不能支持任何存在的 Kubernetes 版本。了解集群和节点池的当前版本何时将被废弃是至关重要的。所有云提供商都有系统化的流程并广泛共享信息。以下是三大云提供商各自的位置：

- AWS EKS：https://docs.aws.amazon.com/eks/latest/userguide/kubernetes-versions.html
- Azure AKS：https://learn.microsoft.com/en-us/azure/aks/supported-kubernetes-versions
- Google GKE：https://cloud.google.com/kubernetes-engine/docs/release-schedule

例如，在撰写本文时，AKS 支持版本 1.23 到 1.26。此外，每个版本都有官方的生命周期结束日期。例如，1.23 的生命周期结束日期是 2023 年 4 月。如果你的集群仍然运行在 1.23 上，那么 AKS 可能会自动将你的集群升级到版本 1.24。云提供商升级的过程是渐进的，按区域进行，可能需要几周时间。

所有云提供商都提供 API 和 CLI 来检查每个区域中版本的完整列表（包括补丁版本）。

例如，目前，Central US 区域 AKS 支持的版本如下：

```shell
$ az aks get-versions --location centralus --output table

```

如你所见，对于每个次要版本，有几个补丁版本。它甚至友好地提到你可以自行升级到哪些版本。由于安全问题，云提供商可能随时放弃对补丁版本的支持。

接下来让我们谈谈控制平面的升级过程。

### 升级集群

当使用云中的托管 Kubernetes 时，你不负责控制平面的操作，但仍然需要管理升级过程。你有两个选择：

- **自动升级**：在自动升级中，云提供商将按照其计划更新你的集群，但你仍然必须确保集群中资源的版本与新版本兼容。
- **手动升级**：手动升级要求你自己进行升级，但可以更灵活地控制时机。例如，你可以选择更早更新以受益于某些新功能。

请记住，手动升级并不意味着你可以永远停留在同一个 Kubernetes 版本上。如果你落后于最低支持版本，云提供商将强制升级你。

Kubernetes 大约每 3 个月发布一个新版本。云提供商大约支持 4 个版本。这意味着如果你刚刚升级到最新的支持版本，你可以推迟大约一年再进行升级，但届时你将处于最低支持版本，这意味着你以后将每 3 个月需要升级一次。

请注意，你应该每次将控制平面升级一个次要版本。如果你在版本 1.24 上，想升级到 1.26，你必须先升级到 1.25，然后从 1.25 升级到 1.26。

底线是，升级 Kubernetes 控制平面是一个每年要进行多次的标准操作。你应该有一个简化的流程。

让我们看看涉及哪些内容。

#### 规划升级

你应该规划升级并与集群用户协调。控制平面升级通常需要 20-45 分钟。这对你的工作负载来说是一个无中断的操作。你的工作负载将继续运行，新 Pod 将被调度到现有节点。但是，在控制平面升级期间，节点池操作可能会被阻塞。

如果你运行具有冗余方案的多个集群，最好逐步执行升级，从非关键集群（例如，开发或预发布环境）开始。

我建议为每个命名空间指定所有者（工程师或团队）。通知所有所有者即将进行的升级，以便他们预留时间来转换不兼容的资源。

#### 检测不兼容的资源

升级的主要担忧是，系统的功能将受到影响或完全损坏，因为它使用的资源不再受支持。大多数情况下，特定版本的资源将被移除，而更新版本将可用。

但是，你不必等到最后一刻才匆忙替换已移除的资源或版本。Kubernetes 有一个弃用策略，资源在被完全移除之前将弃用几个版本。我建议在每次升级之前确保所有已弃用的资源已更新或替换。这将确保升级过程不会令人紧张，因为即使你没有设法更新所有资源，已弃用的资源在新版本中仍然受支持，你将有额外的时间在它们被完全移除之前进行更新。

Kubernetes 发布了一个迁移指南，详细说明了每个版本中已弃用和已移除的 API。参见 https://kubernetes.io/docs/reference/using-api/deprecation-guide。

例如，Kubernetes 1.25 停止提供 API 版本为 `batch/v1beta1` 的 CronJob 资源。而 `batch/v1` 的 CronJob 资源自 Kubernetes 1.21 以来一直可用。理想情况下，在升级到 Kubernetes 1.21 后，你已将所有的 CronJob 资源更新为使用 `batch/v1`，这样到升级到 Kubernetes 1.25 时，`batch/v1beta1` 被移除这个事实就不是问题了，因为你已经在使用受支持的版本。

有几种方法可以确保你检测到当前使用的所有已弃用和/或已移除的资源。你可以使用手动方法阅读弃用指南并扫描代码检测不兼容的资源。大多数版本没有很多弃用或移除。然而，某些版本可能有多达十个不同的资源被弃用或移除。例如，Kubernetes 1.25 停止提供七种不同的资源版本。

更系统的方法是使用像 kube-no-trouble（https://github.com/doitintl/kube-no-trouble）这样的工具，它可以扫描你的集群并输出已弃用资源的列表。

#### 处理已移除的功能

还有另一种情况需要处理，即功能被完全移除而没有升级路径。Kubernetes 1.25 完全移除了对 Pod 安全策略（PSP）的支持。PSP 在 Pod 上的应用已经让许多尝试使用它们的用户感到困惑。有关更多详情，请查看此链接：https://kubernetes.io/blog/2021/04/06/podsecuritypolicy-deprecation-past-present-and-future/。

如果你使用了 PSP，那么当升级到 Kubernetes 1.25 时，你的 PSP 将不再起作用。Kubernetes 开发者并非在没有替代方案的情况下直接移除了该功能。PSP 有两种替代方案：

- Pod 安全准入（Pod Security Admission）
- 第三方准入控制器

Pod 安全准入是一个简化的解决方案，可能不一定能完全替代 PSP。Kubernetes 开发者发布了一份详细的迁移指南。请查看：https://kubernetes.io/docs/tasks/configure-pod-container/migrate-from-psp/。

如果你选择第三方（例如 Kyverno），那么你应该查看其文档。Kyverno 附带了许多用于 Pod 安全的示例策略，过渡相对简单。

### 升级节点池

升级多个集群的节点池可能是一项重大工程。如果你有数十到数百个集群，每个集群中有多个节点池（5-20 个并不罕见），那么准备好迎接一次严峻的冒险。控制平面升级（一旦你确保工作负载与新版本兼容）相当快速且无痛。节点池升级非常困难。实际上，在一个具有数十到数百个节点池、数千个节点的大型基于 Kubernetes 的系统中，升级所有节点池可能需要数周时间。

#### 与控制平面升级同步

Kubernetes 对控制平面和工作节点的版本施加了约束。Kubernetes 节点组件可以比控制平面低两个次要版本。如果控制平面在版本 N，那么节点池可以在版本 N-2。由于节点池升级比控制平面升级更具破坏性和劳动密集型，我建议只在每个其他 Kubernetes 版本上升级节点池。例如，假设我们从控制平面和节点都在版本 1.24 的 Kubernetes 集群开始。当升级到版本 1.25 时，我们只将控制平面升级到 1.25，并将节点池保持在 1.24，这是兼容的。然后，当需要升级到 1.26 时，我们先将控制平面从 1.25 升级到 1.26，然后开始将所有节点池从 1.24 直接升级到 1.26。让我们看看如何进行节点池升级。

#### 如何执行节点池升级

节点池升级需要一个新的节点池。无法升级节点池内的节点。甚至无法向现有节点池添加具有新版本的节点。节点版本是节点池的基本属性之一。这意味着实际上你并不是升级现有的节点池，而是替换节点池。首先，创建一个新的节点池，扩展它，然后开始从旧节点池排空节点，直到所有 Pod 都在新节点池上运行，然后你可以删除旧（现在为空）的节点池。

如果你的原始节点池是一个自动扩缩的节点池，那么在开始升级过程之前，你必须关闭自动扩缩；否则，从旧节点池节点中驱逐的 Pod 可能会被直接调度回旧节点池。让我们列出升级节点池所需的确切步骤：

- 创建一个与现有节点池具有完全相同的规格（实例类型、标签、容忍度）但使用新版本的新节点池。
- 你可以预先在新区池中分配一些实例，以便它们准备好接收来自旧节点池的 Pod。
- 关闭旧节点池中的自动扩缩。
- 封锁旧节点池中的所有节点，以防止新 Pod 被调度到旧节点池。
- 排空旧节点池的节点。
- 观察并处理问题。
- 等待集群自动扩缩器删除空的旧节点池节点，或自行删除以加快进程。

让我们看一些可能延迟甚至阻碍升级过程的问题。

##### 并发排空

如果你需要升级许多节点池，每个池中有大量节点，你可能会决定一次性或以大批量方式配置新节点池并开始排空所有节点池。这可能导致超出配额或遇到云提供商容量问题。

你应该注意配额，并确保无论升级如何，你都有足够的配额。如果你接近配额上限，我建议在进行像节点池升级这样复杂的操作之前增加配额。你最不希望的事情就是在升级过程中，由于业务需求需要扩展容量时，发现配额已用尽。

处理容量问题和加快速度（云提供商为新节点配置实例的速度）的一个好策略是预先分配这些实例。同样，这要求你同时拥有旧节点池和新节点池的足够配额。

让我们了解如果你不在新节点池中预先分配节点会发生什么。当你从旧节点池排空一个节点时，所有 Pod 都会从该节点被驱逐并变为 Pending 状态。Kubernetes 将尝试将这些 Pod 调度到现有节点（如果有可用的）。旧节点池已被封锁，因此要么 Kubernetes 可以在其他现有节点池上找到合适的节点（这是一件好事，改进了装箱），要么集群自动扩缩器需要配置一个新节点。这需要几分钟。如果你同时排空多个节点，那么所有这些节点上的 Pod 将在几分钟内处于 Pending 状态，直到新节点可以配置，你的系统容量将下降。此外，如果云提供商有容量问题，可能无法配置新节点，你的 Pod 将保持 Pending 状态直到那时。

预先分配节点意味着新节点池将有随时可用的节点。一旦 Pod 从旧节点池被驱逐，它将立即被调度到新节点池中的可用节点上。

##### 处理没有 PDB 的工作负载

当排空一个节点时，Kubernetes 会注意 Pod 中断预算（PDB）。如果某部署有一个 PDB 规定只能有一个 Pod 不可用，并且被排空节点上有该部署的两个 Pod，那么 Kubernetes 将只驱逐一个 Pod，并等待它被成功调度后再驱逐另一个 Pod。但是，如果你有工作负载没有 PDB，那就意味着 Kubernetes 允许同时驱逐这些工作负载的所有 Pod。对于大多数工作负载来说，这是不可接受的。你应该识别这些工作负载并与它们的所有者合作添加 PDB。请注意，在一次性排空所有节点的场景中，即使没有 PDB 的工作负载在不同节点上运行许多 Pod，它们也很脆弱。

##### 处理 PDB 为零的工作负载

然而，相反的问题——不可驱逐的 Pod——是节点池升级的祸根。如果一个节点包含一个不可驱逐的 Pod，那么它无法被排空，Kubernetes 将永远等待（或直到 Pod 被手动删除）才能完全排空该节点。这可能会无限期地停止升级过程，通常需要与工作负载所有者协调来解决。

如果一个工作负载的 PDB 设置 `minUnavailable: 0`，这意味着无论工作负载有多少副本，Kubernetes 都不允许驱逐该工作负载的任何 Pod。

一些工作负载（通常是有状态的）比其他工作负载更敏感，并且更希望完全不被打扰。当然，这是一个不切实际的期望，因为节点本身可能出故障，或者底层 VM 可能因云提供商问题而消失，然后在它上面调度的 Pod 将不得不被驱逐。最好是和工作负载所有者合作，提出一个最小化中断但仍然允许升级进行的解决方案。这必须在升级过程开始之前解决。你不希望出现单个工作负载劫持节点池升级过程的情况，而你必须乞求工作负载所有者允许你驱逐一个 Pod。

但是，除了严格的 PDB 为零的工作负载之外，你可能还会遇到实际上 PDB 为零的情况。考虑一个 PDB 为 `minUnavailable: 1` 的工作负载。这很常见，意味着该工作负载允许一次有一个 Pod 不可用。在排空此工作负载的 Pod 时，只要所有其他 Pod 都在运行，Kubernetes 就允许驱逐一个 Pod。但是，如果此工作负载的 Pod 中有一个由于任何原因处于 Pending 或无法就绪，那么实际上该工作负载已经有一个 Pod 不可用了，升级过程将再次停止。

这里的最佳实践是在升级过程开始之前识别这些工作负载，并确保所有工作负载健康，可以参与节点池升级过程。

然而，即使你事先做了所有准备工作，一些工作负载可能在升级过程中（记住我们说的是一个可能持续数周的过程）进入不健康状态。我建议对升级过程的进展进行强有力的监控，检测卡住的 Pod，并与所有者合作解决问题。对于调度到旧节点池上且无法就绪的 Pod，一个简单的解决方案就是删除 Pod，让它被调度到新节点池，并让工作负载所有者解决新节点池上的问题。

其他情况可能需要更有创意的解决方案。

让我们把注意力转向集群中可能出现的各种问题以及如何处理它们，特别是在大规模环境中。

## 故障排除

在本节中，我们将介绍生产集群中的故障排除过程以及采取操作的逻辑顺序。Pod 生命周期涉及多个阶段，每个阶段都可能发生故障。此外，Pod 容器经历自己的小型生命周期，其中 init 容器运行完成，然后主容器开始运行。让我们看看在此过程中可能出错的地方以及如何处理。

### 处理 Pending Pod

当创建新 Pod 时，Kubernetes 过去将其置于 Pending 状态并尝试找到一个节点来调度它。然而，从 Kubernetes 1.26 开始，还有一个更早的状态，Pod 无法被调度。

让我们创建一个名为 "trouble" 的新 1.26 kind 集群，并启用 Pod 调度就绪特性。以下是配置文件（`cluster-config.yaml`）：

```yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: trouble
nodes:
- role: control-plane
  featureGates:
    "PodSchedulingReadiness": true
```

以下是创建 kind 集群的方法：

```shell
$ kind create cluster -n trouble --config cluster-config.yaml --image kindest/node:v1.26.0
Creating cluster "trouble" ...
 ✓ Ensuring node image (kindest/node:v1.26.0)
 ✓ Preparing nodes
 ✓ Writing configuration
 ✓ Starting control-plane
 ✓ Installing CNI
 ✓ Installing StorageClass
Set kubectl context to "kind-trouble"
You can now use your cluster with:
kubectl cluster-info --context kind-trouble
```

接下来，我们将创建一个名为 `trouble` 的新命名空间并在此基础上继续。

```shell
$ k create ns trouble
namespace/trouble created
```

让我们创建一个具有名为 `no-scheduling-yet` 的调度门的 Pod：

```shell
$ cat <<EOF | k apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: some-pod
  namespace: trouble
  labels:
    app: the-app
spec:
  schedulingGates:
  - name: no-schedule-yet
  containers:
  - name: pause
    image: registry.k8s.io/pause:3.8
EOF
pod/some-pod created
$ k get po -n trouble
NAME       READY   STATUS            RESTARTS   AGE
some-pod   0/1     SchedulingGated   0          10s
```

如你所见，Pod 的状态为 `SchedulingGated`。

调度门的好处是，如果 Pod 由于配额等问题暂时无法调度（需要外部解决），那么处于此状态的 Pod 不会给 Kubernetes 调度器带来大量波动，调度器将忽略它。在外部问题解决后，你（或更可能是某个 Operator）可以移除特性门，Pod 将变为 Pending 状态，准备进行调度。

现在，让我们把注意力转向 Pending Pod。Pod 处于 Pending 状态是可以的；但是，如果 Pod 处于 Pending 状态超过几分钟，那就是出了问题，我们需要调查。我建议设置告警，当 Pod 保持 Pending 状态超过 X 分钟时触发（X 的合理值可以在 10 到 60 分钟之间）。

有两种类型的 Pending Pod：临时 Pending 和永久 Pending。临时 Pending Pod 可能可以调度到现有节点池之一；但是，目前所有节点上都没有空间。如果节点池启用了自动扩缩，集群自动扩缩器将尝试配置一个新节点。如果节点池禁用了自动扩缩，那么 Pod 将保持 Pending 状态，直到其他 Pod 完成或被从节点上驱逐以腾出空间。另一类临时不可调度的 Pod 是目标命名空间的资源配额当前已用尽。以下是一个例子，命名空间的资源配额为 1 个 CPU，创建了一个具有 3 个副本的部署，每个 Pod 请求 0.5 个 CPU。只有 2 个 Pod 能适配命名空间配额。第三个 Pod 将处于 Pending 状态：

```shell
cat <<EOF | k apply -f -
apiVersion: v1
kind: ResourceQuota
metadata:
  name: cpu-requests
  namespace: trouble
spec:
  hard:
    requests.cpu: "1"
EOF
resourcequota/cpu-requests created
```

现在，让我们创建 Deployment 并查看会发生什么：

```shell
cat <<EOF | k apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: some-deployment
  namespace: trouble
  labels:
    app: the-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: the-app
  template:
    metadata:
      namespace: trouble
      labels:
        app: the-app
    spec:
      containers:
      - name: pause
        image: registry.k8s.io/pause:3.8
        resources:
          requests:
            cpu: "0.5"
EOF
deployment.apps/some-deployment created
```

我们最终如预期只有两个运行中的 Pod：

```shell
$ k get deploy -n trouble
NAME              READY   UP-TO-DATE   AVAILABLE   AGE
some-deployment   2/3     2            2           5m3s

$ k get po -n trouble
NAME                               READY   STATUS    RESTARTS   AGE
some-deployment-7f876df998-fc7kq   1/1     Running   0          4m34s
some-deployment-7f876df998-htdsn   1/1     Running   0          4m34s
```

注意，在这种情况下没有第三个 Pending Pod。Kubernetes 足够智能，在这种情况下只创建了两个 Pod。

原因是命名空间配额：

```shell
$ k get deploy some-deployment -o yaml -n trouble | grep forbidden -A 2
message: 'pods "some-deployment-7f876df998-84z9s" is forbidden: exceeded quota:
  cpu-requests, requested: requests.cpu=500m, used: requests.cpu=1, limited:
  requests.cpu=1'
reason: FailedCreate
```

永久 Pending Pod 是无法在任何可用节点池上调度的 Pod，因此配置新节点也无济于事。有几类这样的永久不可调度的 Pod：

- 所有节点池都有污点（taint），而 Pod 没有适当的容忍度（toleration）。
- Pod 请求的资源超过任何节点池可用的资源。
- Pod 正在等待持久卷。
- Pod 具有不正确的 `nodeSelector` 或 `nodeAffinity`。

让我们删除之前的 Deployment 和资源配额，并看一个请求过多资源（666 个 CPU 核心）的 Pod 示例：

```shell
$ k delete resourcequota cpu-requests -n trouble
resourcequota "cpu-requests" deleted
$ k delete deploy some-deployment -n trouble
deployment.apps "some-deployment" deleted
$ cat <<EOF | k apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: some-deployment
  namespace: trouble
  labels:
    app: the-app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: the-app
  template:
    metadata:
      labels:
        app: the-app
    spec:
      containers:
      - name: pause
        image: registry.k8s.io/pause:3.8
        resources:
          requests:
            cpu: "666"
            memory: 1Gi
EOF
deployment.apps/some-deployment created
```

如果我们查看现在创建的 Pod，可以看到它确实处于 Pending 状态：

```shell
$ k get po -n trouble
NAME                               READY   STATUS    RESTARTS   AGE
some-deployment-bbf88d559-pdf8p   0/1     Pending   0          2m37s
```

要理解为什么它是 Pending 的，我们可以查看 Pod 的状态：

```shell
$ k get po some-deployment-bbf88d559-pdf8p -o yaml -n trouble | yq .status
conditions:
- lastProbeTime: null
  lastTransitionTime: "2023-03-26T05:35:30Z"
  message: '0/1 nodes are available: 1 Insufficient cpu. preemption: 0/1 nodes are
    available: 1 No preemption victims found for incoming pod..'
  reason: Unschedulable
  status: "False"
  type: PodScheduled

```

消息非常清楚，解释了 0/1 个节点可用于调度。它甚至说有 1 个节点 CPU 不足。如果集群中还有其他节点有不同原因，它也会列出。

Pending Pod 不使用资源，也不占用节点空间；但是，它们会给 API 服务器带来一些压力，而且意味着某些工作负载无法执行其工作，等待被调度到节点上，这在生产环境中可能非常严重。注意你的 Pending Pod，并确保快速解决任何问题。

下一类问题是已调度到节点但无法运行的 Pod。

### 处理已调度但未运行的 Pod

已调度的 Pod 无法运行可能有几个原因。最常见的原因之一是拉取 Pod 中某个容器所需的镜像失败。kubelet 将继续尝试，Pod 的状态将显示为 `ErrImagePull`：

```shell
cat <<EOF | k apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: no-such-image
  namespace: trouble
  labels:
    app: no-such-image
spec:
  replicas: 1
  selector:
    matchLabels:
      app: no-such-image
  template:
    metadata:
      labels:
        app: no-such-image
    spec:
      containers:
      - name: no-such-image
        image: no-such-image:6.6.6
EOF
deployment.apps/no-such-image created
```

让我们检查 Pod：

```shell
$ k get po -l app=no-such-image -n trouble
NAME                             READY   STATUS         RESTARTS   AGE
no-such-image-77585fd5b4-tqpv2  0/1     ErrImagePull   0          27s
```

要查看更多详细信息，我们可以检查状态中的 `containerStatuses` 字段：

```shell
$ k get po no-such-image-77585fd5b4-tqpv2 -n trouble -o yaml | yq '.status.containerStatuses[0].state'
waiting:
  message: Back-off pulling image "no-such-image:6.6.6"
  reason: ImagePullBackOff
```

镜像拉取错误可能与镜像配置错误有关。镜像名称或镜像标签可能错误。但是，镜像可能是正确的，但可能意外地从仓库中删除了。如果你尝试从私有仓库拉取，那么可能是你没有正确的权限。最后，镜像仓库可能不可用。例如，Docker Hub 经常有速率限制。

你可能更希望从一个你可以控制的单一源拉取所有镜像，你可以在那里扫描和审查镜像，确保镜像不会从你这里消失。如果你在云中，那么每个云提供商都提供自己的镜像仓库。在大多数情况下，这应该是首选选项。你可能通过使用私有仓库节省一些费用，或者在混合云场景中你可能更喜欢不同的解决方案。

Pod 无法开始运行的另一个原因是 init 容器未完成：

```shell
cat <<EOF | k apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: infinite-init
  namespace: trouble
  labels:
    app: infinite-init
spec:
  replicas: 1
  selector:
    matchLabels:
      app: infinite-init
  template:
    metadata:
      name: infinite-init
      labels:
        app: infinite-init
    spec:
      initContainers:
      - name: init-pause
        image: registry.k8s.io/pause:3.8
      containers:
      - name: main-pause
        image: registry.k8s.io/pause:3.8
EOF
deployment.apps/infinite-init created
```

检查 Pod 状态，我们可以看到它卡在了 init 阶段，因为我们的 init 容器是 pause 容器，它永远不会完成：

```shell
$ k get po -l app=infinite-init -n trouble
NAME                              READY   STATUS     RESTARTS   AGE
infinite-init-d555945fb-dccbk     0/1     Init:0/1   0          46s
```

有时 Pod 开始运行，但容器不断失败。在这种情况下，你需要检查 Pod 的日志或 Dockerfile 以查找原因。以下是一个不断崩溃的 Pod，因为其 Dockerfile 命令只以退出码 1 退出：

```shell
cat <<EOF | k apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: run-container-error
  namespace: trouble
spec:
  containers:
  - name: run-container-error
    image: bash
    command:
    - exit
    - "1"
EOF
pod/run-container-error created
```

结果是 Pod 的状态将变为 `RunContainerError`。Kubernetes 将持续重启 Pod（假设默认的重启策略为 Always）：

```shell
$ k get po run-container-error -n trouble
NAME                 READY   STATUS             RESTARTS      AGE
run-container-error  0/1     RunContainerError  4 (8s ago)    100s
```

让 Pod 和容器进入运行状态是一个好的开始，但这还不够。为了让 Kubernetes 将请求发送到你的 Pod，所有容器必须就绪。让我们看看可能遇到的问题。

### 处理运行中但未就绪的 Pod

如果你所有的 init 容器都已完成，所有主容器都在运行且没有错误，那么探针就开始发挥作用了。如果没有定义探针，或者所有容器的所有探针都成功，Kubernetes 才会认为运行中容器的 Pod 已就绪可供接收请求。启动探针（startup probe）最初被检查，直到成功。如果失败，Pod 不被认为就绪。如果你的容器有一个挂起的启动探针，它将永远无法就绪。

Kubernetes 最终会杀死并重启你的容器，启动探针将再次有机会。

以下是一个部署，其中主容器有一个将永远失败的启动探针（pause 容器甚至不在 80 端口上监听）。Pod 将永远无法达到就绪状态。在启动探针定义的一些重试和延迟之后，Kubernetes 将重启容器，周期将重复：

```shell
cat <<EOF | k apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: bad-startup-probe
  namespace: trouble
  labels:
    app: bad-startup-probe
spec:
  replicas: 1
  selector:
    matchLabels:
      app: bad-startup-probe
  template:
    metadata:
      name: bad-startup-probe
      labels:
        app: bad-startup-probe
    spec:
      containers:
      - name: pause
        image: registry.k8s.io/pause:3.8
        startupProbe:
          httpGet:
            path: /
            port: 80
          failureThreshold: 3
          periodSeconds: 10
          initialDelaySeconds: 5
          timeoutSeconds: 2
EOF
deployment/bad-startup-probe created
```

检查 Pod 显示 Pod 处于 `CrashLoopBackOff` 状态，Kubernetes 持续重启容器：

```shell
$ k get po -l app=bad-startup-probe -n trouble
NAME                                  READY   STATUS             RESTARTS        AGE
bad-startup-probe-66fb7cf4fd-qw8kp   0/1     CrashLoopBackOff   160 (3m56s ago) 8h
```

请注意，重启之间的延迟呈指数增长，以避免容器给 API 服务器和 kubelet 带来太大压力，使它们不需要频繁重启。

如果没有启动探针或者它成功了，那么障碍就是就绪探针（readiness probe）。它的工作方式与启动探针非常相似，只是 Kubernetes 不会重启容器。它将不断检查就绪探针。当就绪探针失败时，Pod 将从匹配其标签的任何服务的端点列表中移除，因此它不会处理任何请求。但是，Pod 保持存活并在节点上消耗资源。

让我们看看它的实际效果：

```shell
cat <<EOF | k apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: bad-readiness-probe
  namespace: trouble
  labels:
    app: bad-readiness-probe
spec:
  replicas: 1
  selector:
    matchLabels:
      app: bad-readiness-probe
  template:
    metadata:
      name: bad-readiness-probe
      labels:
        app: bad-readiness-probe
    spec:
      containers:
      - name: pause
        image: registry.k8s.io/pause:3.8
        readinessProbe:
          httpGet:
            path: /
            port: 80
          failureThreshold: 3
          periodSeconds: 10
          initialDelaySeconds: 5
          timeoutSeconds: 2
EOF
deployment.apps/bad-readiness-probe created
```

如你所见，Pod 运行了一个小时，从未就绪，也没有被重启：

```shell
$ k get po -l app=bad-readiness-probe -n trouble
NAME                                    READY   STATUS    RESTARTS   AGE
bad-readiness-probe-7458b65d98-5jrjq   0/1     Running   0          60m
```

最后一种类型的探针是存活探针（liveness probe）。它的工作方式与启动探针类似（容器将被重启，Pod 将进入 `CrashLoopBackOff`），除了它会被定期检查，即使它成功了（而启动探针是一次性的，一旦成功就不再检查）。

之所以需要启动探针和存活探针两者，是因为某些容器需要更长的启动时间，但一旦初始化完成，定期的存活检查应该更短。

这涵盖了 Pod 生命周期的故障排除。当 Pod 被调度但未运行或未就绪时，会产生成本影响。让我们继续考虑成本管理。

## 成本管理

当在云中大规模运行 Kubernetes 时，主要关注点之一是基础设施的成本。云提供商为你的 Kubernetes 集群提供了各种基础设施选项和服务。这些都价格不菲。要控制成本，请确保遵循诸如以下的最佳实践：

- 具有成本意识
- 成本可观测性
- 明智地选择资源
- 高效使用资源
- 折扣、预留实例和竞价实例
- 投资本地环境

让我们逐一回顾。

### 成本意识

工程师经常忽视成本或将其放在优先级列表的底部。我通常按此顺序思考：使其工作，使其快速，使其持久，使其安全，然后才使其便宜。这不一定是坏事，特别是对于初创公司或新项目。增长和速度通常是首要任务。毕竟，如果你没有好的产品，没有客户，即使你的成本为零，业务也会失败。

此外，当系统很小时，即使存在大量浪费，绝对成本也可能相对较小。再加上云提供商通过慷慨的信用额度吸引公司进入的事实。

然而，如果你是大型企业的一部分，或者你的初创公司成功并成长起来，在某个时候，成本将成为一个重要的关注点。此时，你需要转变思维，将成本作为你所做一切的主要关注点。成本可能与其他举措一致，也可能不一致。例如，每个人都喜欢帕累托改进。如果你设法使用比原来少 20% 的虚拟机来完成相同的任务，那么你将自动节省大量资金，而不会对其他方面产生负面影响。

但是，这些轻松取胜和低挂的果实最终会枯竭。然后，你会遇到更艰难的决定。例如，在内存中缓存最近一周的数据将提供出色的响应时间，但成本高昂。如果你只缓存一天呢？

可用性和冗余也常常与成本相矛盾。你真的需要一个全面的、跨多个可用区、区域和云提供商的零宕机双活设置吗？还是可以在灾难性故障时接受一些停机时间和从备份恢复？

你最终可能会选择更昂贵的选项，但你应该明确了解你为此支付了多少，并确保你获得的价值更大。

这将我们带到下一个主题：成本可观测性。

### 成本可观测性

为了管理 Kubernetes 和云上的基础设施成本，你必须拥有强大的面向成本的可观测性。让我们看看实现这一点的一些方法。

#### 标记

标记是将每个资源与一组标签或标记关联起来。从成本角度来看，标记应使你能够将任何基础设施资源的成本归因于相关的利益相关者。例如，你可能会有一个团队标签或所有者标签。如果某个特定团队配置的资源突然快速增长，你可以更快地缩小问题范围。具体的标记取决于你。常见的标记可能包括环境（生产、预发布和开发）、发布版本和 git sha。云中的许多资源都带有云提供商的标签，你可以利用这些标签。

#### 策略和预算

策略和预算可以让你遏制基础设施上的过度支出。有些策略是隐性的，例如命名空间资源配额，它会阻止超额资源的配置。然而，其他策略可能更针对成本，并且由成本追踪提供信息。预算允许你设置不同范围内的硬性支出限制。所有云提供商都将其预算作为成本管理解决方案的一部分：

1. 教程：创建和管理 Azure 预算：https://learn.microsoft.com/en-us/azure/cost-management-billing/costs/tutorial-acm-create-budgets
2. 使用 AWS Budgets 管理成本：https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html
3. 在 GCP 中创建、编辑或删除预算和预算提醒：https://cloud.google.com/billing/docs/how-to/budgets

策略和预算很好，但有时它们还不够，或者你没有时间指定和更新它们。这就是告警发挥作用的地方。

#### 告警

预算通常是防止恶意基础设施配置或意外失控配置的最后手段。例如，你可以为几个总体类别设置广泛的预算，比如计算支出不超过 500,000 美元。当然，这些预算需要与业务增长保持一致，并确保如果你临时需要配置更多基础设施来处理暂时的需求高峰，不会导致事故。预算通常只有高层管理人员批准才能设置或修改。

细粒度和日常的成本管理告警更加灵活和实用。如果你超过或接近某个成本限制，你可以设置告警来通知你，并在必要时升级。告警依赖于正确的标记，以便你拥有有意义的信息来评估成本增加的原因和负责方。

如你所见，管理成本是一项动态且复杂的活动。你需要好的工具来帮助你。

#### 工具

所有云提供商都有强大的成本管理工具。请查看：

1. AWS Cost Explorer：https://aws.amazon.com/aws-cost-management/aws-cost-explorer/
2. Azure Cost Analyzer：https://www.serverless360.com/azure-cost-analysis
3. GCP Cost Management：https://cloud.google.com/cost-management/

此外，你可以选择使用多云开源工具，如 kubecost（https://www.kubecost.com）或付费产品，如 cast.ai（https://cast.ai）。当然，你也可以自己做一切，将来自云提供商的成本指标导入 Prometheus，并在其上构建你的 Grafana 仪表板和告警。

请记住，选择正确的工具集可以很快收回成本。

### 明智地选择资源

云提供了大量的选择和组合，用于资源（如虚拟机、网络和磁盘）。我们在本章前面的"装箱和利用率"部分已经涵盖了所有考量。但是，从成本的角度来看，你应该确保了解你可以用更便宜的替代方案完成工作，从而显著降低成本。熟悉资源清单，并保持最新，因为云提供商会更新其产品并可能调整价格。

### 高效使用资源

当你削减成本时，任何未使用的资源都是一个危险信号。你等于在把钱留在桌上。通常有必要建立灵活性。例如，行业平均 CPU 利用率在 40%-60% 的范围内。这看起来可能很低，但在一个非常动态的环境中，在诸如高可用性、快速恢复和快速扩展能力等约束下，要改进并不容易。

### 折扣、预留实例和竞价实例

降低最佳的方式之一就是直接为相同的资源向云提供商支付更少的钱。实现这一目标的常见方式是折扣、预留实例和竞价实例。

#### 折扣和信用额度

折扣是最好的。它们只有好处。你只需支付低于标价的价格。就这样。嗯，没那么容易。你需要进行谈判以获得最佳价格，并通常展示增长前景和对平台的长期承诺。

信用额度是抵消初始云支出的另一种好方法。所有主要的云提供商都提供各种信用计划，你也可以谈判获得更多信用额度。

AWS 有 Activate 计划，主要针对初创公司，你可以获得高达 100,000 美元的 AWS 信用额度。参见 https://aws.amazon.com/activate/。

Azure 有 Microsoft for Startups 计划，提供高达 150,000 美元的 Azure 信用额度。参见 https://www.microsoft.com/en-us/startups。

GCP 有 Google for Startups 云计划，提供（像 AWS 一样）高达 100,000 美元的 GCP 信用额度。参见 https://cloud.google.com/startup。

这些计划旨在促进没有大量收入的年轻初创公司。让我们转向仍然希望减少云支出的成熟企业组织的选项。

#### 预留实例

预留实例是一种非常好的降低成本的方式。它们要求你批量购买容量并承诺较长的期限（一年或三年）。期限越长，折扣越大。总体而言，折扣很大，与按需价格相比，可以从 30% 到 75% 不等。

除了价格，预留实例还可以确保容量，而按需实例在特定可用区中特定实例类型可能会暂时不可用。

预留实例的缺点是你通常需要预付款，并且承诺通常与特定的实例类型和区域绑定。你可能可以交换等效的预留实例，但你需要检查云提供商的条款和条件。此外，如果你无法使用所有预留容量，你仍然需要为其付费（尽管价格非常优惠）。

如果你考虑预留实例（RI），你可以选择有限容量的预留实例（你知道你总是可以利用的），然后使用按需和竞价实例来处理峰值并利用云的弹性。如果你后来发现按需支出过多，你可以随时预留更多实例，并采用三年预留实例、一年预留实例、按需和竞价实例的组合。这很好地引出了列表中的下一个项目：竞价实例。

#### 竞价实例

云提供商喜欢预留实例。他们销售它们，配置它们，赚取利润，然后可以忘记它们（除了确保它们正常运行）。按需方面则大不相同。云提供商必须确保在客户需要时能够合理地配置更多容量。特别是，云提供商应该大致有足够的容量来处理每个客户的配额，即使客户显著未充分利用其配额。这意味着，在实践中，在正常情况下，云提供商有大量闲置或未充分利用的容量。

这就是竞价实例发挥作用的地方。云提供商可以出售这种超额容量，理论上这些容量是为按需使用分配的。如果需要，云提供商只需收回竞价实例，并将其提供给按需客户。

为什么要使用竞价实例？嗯，因为它们便宜得多。由于它们潜在的临时性，它们带有高达 90% 的显著折扣。请记住，从云提供商的角度来看，这基本上是免费的钱。这些实例已经通过使用中的按需实例的加价和每个客户的配额比列被考虑和支付了。

在实践中，竞价实例不会很快从你这里消失。Kubernetes 的方式倡导工作负载不应该太关心特定节点。如果你在竞价实例上运行，而它消失了，你所有的 Pod 将被驱逐并调度到其他节点。如果你有敏感的工作负载不能很好地处理从其节点被驱逐，那么这些工作负载本来就不是良好的 Kubernetes 公民。无论如何，节点都会时不时变得不健康，你的工作负载应该能够处理驱逐。

然而，有一种情况需要解决，特别是如果你在竞价实例上运行关键工作负载。如果特定实例类型发生区域性故障，云提供商可能会回收许多竞价实例。我建议具有使用相同或相似实例类型以及相同标签和污点的空按需备用节点池。如果使用竞价实例的节点池突然失去大量节点并且无法扩展（因为竞价实例不可用），那么你可以扩展你的空按需节点池，你的 Pod 将调度到那里，直到竞价实例再次可用。

确保你有足够的配额让备用节点池在等效竞价实例不可用时填补缺口。

接下来，让我们谈谈本地环境以及它们如何帮助我们节省资金。

### 投资本地环境

组织实践不同的开发和测试协议。一些组织在云中的预发布和开发环境中进行大量测试。有时，工程师为各种实验和测试配置基础设施。这样的开发和测试环境可能难以有效管理，因为基础设施通常是临时配置的。有一些解决方案，如一次性 Kubernetes 集群和虚拟集群。另一个方向是投资于本地开发环境，工程师可以在自己的本地机器上运行。这些环境的优点是它们通常非常快速设置和销毁，并且不会产生任何昂贵的云成本。缺点是这些环境可能不能完全代表预发布或生产环境。我建议研究本地环境，找到可以在不损害系统其他关键方面的情况下节省云成本的方法。
