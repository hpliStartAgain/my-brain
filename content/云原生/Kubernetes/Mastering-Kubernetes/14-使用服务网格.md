# 使用服务网格

在上一章中，我们探讨了监控和可观测性。实现全面监控的一个障碍是它需要对代码进行大量与业务逻辑正交的更改。

在本章中，我们将学习服务网格如何让你将这些横切关注点从应用程序代码中外部化。服务网格在设计、演进和操作Kubernetes上的分布式系统方面是一个真正的范式转变。我喜欢将其视为云原生分布式系统的面向切面编程。我们还将更深入地了解Istio服务网格。我们将涵盖的主题包括：

-   什么是服务网格？
-   选择服务网格
-   理解Istio架构
-   将Istio集成到你的Kubernetes集群中
-   使用Istio

让我们直接开始。

## 什么是服务网格？

服务网格是一种面向由众多微服务组成的大规模云原生应用程序的架构模式。当你的应用程序被构建为微服务集合时，在Kubernetes集群内部的微服务边界上会发生很多事情。这与传统单体应用程序（其中大部分工作由单个操作系统进程完成）不同。

以下是每个微服务或微服务之间交互相关的一些关注点：

-   高级负载均衡
-   服务发现
-   支持金丝雀部署
-   缓存
-   跨多个微服务追踪请求
-   服务间认证
-   限制一个服务在给定时间内处理的请求数
-   自动重试失败的请求
-   当一个组件持续失败时，故障转移到替代组件
-   收集指标

所有这些关注点完全与服务的领域逻辑正交，但它们都非常重要。一种天真的方法是简单地将所有这些关注点直接编码到每个微服务中。这显然不可扩展。因此，典型的做法是将所有这些功能打包到一个大型库或一组库中，并在每个服务中使用这些库。

![典型的基于库的架构](images/ch14-fig01.png)

**图14.1：典型的基于库的架构**

大型库方法存在几个问题：

-   你需要在所有使用的编程语言中实现该库，并确保它们兼容
-   如果你想更新库，必须升级所有服务的版本
-   如果新版本的库不向后兼容，则很难增量升级服务

相比之下，服务网格不接触你的应用程序。它将一个Sidecar代理容器注入到每个Pod中，并使用一个服务网格控制器。代理拦截Pod之间的所有通信，并与网格控制器协作，处理所有横切关注点。

![Sidecar服务网格架构](ch14-fig02.png)

**图14.2：Sidecar服务网格架构**

以下是代理注入方法的一些属性：

-   应用程序对服务网格无感知
-   你可以按Pod开启或关闭网格，并独立更新网格
-   无需在每个节点上部署代理
-   同一节点上的不同Pod可以拥有不同的Sidecar（或版本）
-   每个Pod有自己的代理副本

在Kubernetes上，它看起来是这样的：

![Kubernetes中的服务网格架构](images/ch14-fig03.png)

**图14.3：Kubernetes中的服务网格架构**

还有一种将服务网格代理实现为节点代理的方式，它不会被注入到每个Pod中。这种方法不太常见，但在某些情况下（尤其是在非Kubernetes环境中），它很有用。它可以节省运行大量小Pod的节点上的资源，因为所有Sidecar容器的开销会累积。

![节点代理服务网格架构](images/ch14-fig04.png)

**图14.4：节点代理服务网格架构**

在服务网格世界中，有一个控制平面，通常是Kubernetes上的一组控制器，和一个数据平面，由连接网格中所有服务的代理组成。数据平面由所有拦截网格中服务之间通信的Sidecar容器（或节点代理）组成。控制平面负责管理代理，并配置当服务之间的流量或服务与外界的流量被拦截时实际发生的情况。

现在，我们对服务网格是什么、如何工作以及为什么如此有用有了很好的理解，让我们回顾一下当前的一些服务网格。

## 选择服务网格

服务网格的概念相对较新，但已经有很多选择。我们稍后将在本章中使用Istio。但是，你可能会根据你的用例选择不同的服务网格。以下是当前服务网格的简要回顾。

### Envoy

Envoy（https://www.envoyproxy.io）是另一个CNCF毕业项目。它是一个非常通用且高性能的L7代理。它提供了许多服务网格功能；然而，它被认为是相当底层的，配置起来很困难。它也不是Kubernetes专用的。一些Kubernetes服务网格使用Envoy作为底层数据平面，并提供Kubernetes原生的控制平面来配置和与之交互。如果你想在Kubernetes上直接使用Envoy，那么建议使用其他开源项目，如Ambassador和Gloo作为Ingress控制器和/或API网关。

### Linkerd 2

Linkerd 2（https://linkerd.io）是一个Kubernetes专用的服务网格，也是一个CNCF孵化项目。它由Buoyant（https://buoyant.io）开发。Buoyant创造了"服务网格"这个术语，并在几年前将其介绍给世界。他们从一个基于Scala的多平台（包括Kubernetes）服务网格开始，名为Linkerd。但他们决定开发一个更好、性能更高、仅针对Kubernetes的服务网格。这就是Linkerd 2的由来，它是Kubernetes专用的。他们用Rust实现了数据平面（代理层），用Go实现了控制平面。

### Kuma

Kuma（https://kuma.io/）是一个基于Envoy的开源服务网格。它最初由Kong开发，后者在Kuma之上提供名为Kong Mesh的企业产品。它可以在Kubernetes以及其他环境中工作。它的出名之处在于超级易于配置，并且允许在单个网格中混合使用Kubernetes和基于VM的系统。

### AWS App Mesh

当然，AWS有自己的专有服务网格——AWS App Mesh（https://aws.amazon.com/app-mesh）。App Mesh也使用Envoy作为其数据平面。它可以在EC2、Fargate、ECS和EKS以及普通Kubernetes上运行。App Mesh在服务网格领域来得稍晚，因此不如其他一些服务网格成熟，但它正在迎头赶上。它基于可靠的Envoy，并且由于与AWS服务的紧密集成，可能是最佳选择。

### Mæsh

Mæsh（https://mae.sh）由Træfik（https://containo.us/traefik）的开发者开发。它很有意思，因为它使用节点代理方法而不是Sidecar容器。它严重依赖Traefik中间件来实现服务网格功能。你可以通过在服务上使用注解来配置它。如果你在集群边缘使用Traefik，这可能是一个尝试服务网格的有趣且轻量级的方法。

### Istio

Istio（https://istio.io/）是Kubernetes上最知名的服务网格。它构建在Envoy之上，并允许你通过YAML清单以Kubernetes原生方式进行配置。Istio由Google、IBM和Lyft（Envoy的开发者）发起。它可以在Google GKE上一键安装，并且在Kubernetes社区中广泛应用于任何环境。它也是Knative的默认Ingress/API网关解决方案，这进一步促进了它的采用。

### OSM（开放服务网格）

OSM（https://openservicemesh.io）是另一个基于Envoy的服务网格。它可以通过SMI（服务网格接口）进行配置，SMI是一个规范，旨在提供一套与提供商无关的API来配置服务网格。更多详情请参见 https://smi-spec.io。OSM和SMI都是CNCF沙箱项目。OSM由Microsoft开发并贡献给CNCF。

### Cilium Service Mesh

Cilium Service Mesh（https://isovalent.com/blog/post/cilium-service-mesh）是服务网格领域的新来者。它由Isovalent（https://isovalent.com）开发。它因尝试将eBPF的优势引入服务网格并采用无Sidecar的方法而引人注目。它还处于早期阶段，Cilium Service Mesh不像其他服务网格那样成熟。然而，它有一个有趣的概念，允许你自带控制平面。它可以与Istio集成，也可以与Sidecar互操作。值得关注。

在讨论了各种服务网格选择之后，让我们试用一下Istio。我们选择Istio的原因是它是最成熟的服务网格之一，拥有庞大的社区、大量的用户以及行业领导者的支持。

## 理解Istio架构

在本节中，我们将更好地了解Istio。

首先，让我们认识Istio的主要组件，理解它们的作用以及它们之间的关系。

Istio是一个大型框架，提供了许多功能，它有多个部分相互交互，并与Kubernetes组件交互（主要是间接且不引人注目的）。它分为控制平面和数据平面。数据平面是一组代理（每个Pod一个）。它们的控制平面是一组负责配置代理和收集遥测数据的组件。

下图说明了Istio的不同部分、它们之间的关系以及它们之间交换的信息。

![Istio架构](images/ch14-fig05.png)

**图14.5：Istio架构**

如你所见，有两个主要组件：Envoy代理，它是附加到每个服务实例（每个Pod）的Sidecar容器；以及istiod，它负责发现、配置和证书。Istiod是一个单一的二进制文件，实际上包含多个组件：Pilot、Citadel和Galley。这些组件以前作为独立的二进制文件运行。在Istio 1.5中，它们被合并到一个二进制文件中，以简化安装、运行和升级Istio的体验。

让我们深入了解每个组件，从Envoy代理开始。

### Envoy

我们在回顾Kubernetes的服务网格时简要讨论了Envoy。在这里，它作为Istio的数据平面。Envoy用C++实现，是一个高性能代理。对于服务网格中的每个Pod，Istio注入（自动或通过istioctl CLI）一个Envoy Sidecar容器来完成繁重的工作。

以下是Envoy执行的一些任务：

-   代理Pod之间的HTTP、HTTP/2和gRPC流量
-   复杂的负载均衡
-   mTLS终止
-   HTTP/2和gRPC代理
-   提供服务健康检查
-   对不健康服务的熔断
-   基于百分比的流量整形
-   用于测试的故障注入
-   详细的指标

Envoy代理控制其Pod的所有入站和出站通信。它无疑是Istio最重要的组件。Envoy的配置并非易事，这是Istio控制平面处理的大部分工作。

下一个组件是Pilot。

### Pilot

Pilot负责与平台无关的服务发现、动态负载均衡和路由。它将高级路由规则转换为Envoy配置。这个抽象层允许Istio在多个编排平台上运行。Pilot获取所有平台特定的信息，将其转换为Envoy数据平面配置格式，并通过Envoy数据平面API传播给每个Envoy代理。Pilot是无状态的；在Kubernetes中，所有配置都作为自定义资源定义（CRD）存储在etcd中。

下一个组件是Citadel。

### Citadel

Citadel负责证书和密钥管理。它是Istio安全性的关键部分。Citadel与各种平台集成，并与它们的身份机制保持一致。例如，在Kubernetes中，它使用服务账户；在AWS上，它使用AWS IAM；在Azure上，它使用AAD；在GCP/GKE上，它可以使用GCP IAM。Istio PKI基于Citadel。它使用SPIFFE格式的X.509证书作为服务身份的载体。

以下是Kubernetes中Envoy代理强身份的工作流程：

1.  Citadel为现有服务账户创建证书和密钥对。
2.  Citadel监视Kubernetes API服务器，为新的服务账户配置证书和密钥对。
3.  Citadel将证书和密钥存储为Kubernetes Secret。
4.  Kubernetes将Secret挂载到与该服务账户关联的每个新Pod中（这是标准的Kubernetes实践）。
5.  Citadel在证书过期时自动轮换Kubernetes Secret。
6.  Pilot生成安全的命名信息，将服务账户与Istio服务关联起来。Pilot然后将安全的命名信息传递给Envoy代理。

我们将介绍的最后一个主要组件是Galley。

### Galley

Galley负责抽象不同平台上的用户配置。它将处理后的配置提供给Pilot。这是一个相当简单的组件。

现在我们已经将Istio分解为它的主要组件，让我们动手实践Istio，并将其集成到Kubernetes集群中。

## 将Istio集成到你的Kubernetes集群中

在本节中，我们将在新集群中安装Istio，并探索它提供的所有服务网格功能。

### 为Istio准备minikube集群

我们将使用minikube集群来体验Istio。在安装Istio之前，我们应该确保我们的集群有足够的容量来处理Istio及其演示应用程序BookInfo。我们将启动具有16GB内存和四个CPU的minikube，这应该是足够的。确保你使用的Docker VM（例如Rancher Desktop）具有足够的CPU和内存：

```shell
$ minikube start --memory=16384 --cpus=4
```

Minikube可以为Istio提供负载均衡器。让我们在单独的终端中运行此命令，因为它会阻塞（在完成之前不要停止隧道）：

```shell
$ minikube tunnel
Tunnel successfully started
NOTE: Please do not close this terminal as this process must stay alive for the tunnel to be accessible ...
```

Minikube有时不会清理隧道网络，因此建议在停止集群后运行以下命令：

```shell
minikube tunnel --cleanup
```

### 安装Istio

在minikube启动并运行后，我们可以安装Istio本身。有几种方法可以安装Istio：

-   使用istioctl（Istio CLI）进行自定义安装
-   使用Helm通过Istio operator进行自定义安装（支持，但不鼓励）
-   多集群安装
-   外部控制平面
-   虚拟机安装

我们将采用推荐的istioctl选项。Istio版本可能高于1.15：

```shell
$ curl -L https://istio.io/downloadIstio | sh -
```

istioctl工具位于 `istio-1.15.2/bin` 目录中（下载时的版本可能不同）。确保它在你的PATH中。Kubernetes安装清单位于 `istio-1.15.2/install/kubernetes`，示例位于 `istio-1.15.2/samples`。

### 安装BookInfo

BookInfo是一个简单的基于微服务的应用程序，顾名思义，它展示一本书的信息，如名称、描述、ISBN，甚至评论。BookInfo的开发者真正接受了多语言风格，每个微服务用不同的编程语言实现：

-   ProductPage服务：Python
-   Reviews服务：Java
-   Details服务：Ruby
-   Ratings服务：JavaScript（Node.js）

下图描述了BookInfo服务之间的关系和信息流：

![BookInfo服务之间的信息流](ch14-fig06.png)

好的，应用程序部署成功，包括每个服务的单独服务账户。如你所见，部署了三个版本的reviews服务。这在我们后面进行升级和高级路由与部署模式时将会派上用场。

在继续之前，我们还需要等待所有Pod初始化，然后Istio将注入其Sidecar代理容器。当一切稳定后，你应该会看到类似这样的内容：

```shell
$ k get po -n bookinfo
```

注意，在READY列下，每个Pod显示2/2，这意味着每个Pod有2个容器。一个是应用程序容器，另一个是注入的代理。

由于我们将在bookinfo命名空间中操作，让我们定义一个别名来简化操作：

```shell
$ alias kb='kubectl -n bookinfo'
```

现在，使用我们的小kb别名，我们可以验证可以从ratings服务获取产品页面：

```shell
$ kb exec -it $(kb get pod -l app=ratings -o jsonpath='{.items[0].metadata.name}') -c ratings -- curl productpage:9080/productpage | grep -o "<title>.*</title>"
<title>Simple Bookstore App</title>
```

但该应用程序还不能从外部访问。这就是Istio网关的作用。让我们部署它：

```shell
$ kb apply -f https://raw.githubusercontent.com/istio/istio/release-1.15/samples/bookinfo/networking/bookinfo-gateway.yaml
gateway.networking.istio.io/bookinfo-gateway created
virtualservice.networking.istio.io/bookinfo created
```

让我们获取从外部访问应用程序的URL：

```shell
$ export INGRESS_HOST=$(kubectl -n istio-system get service istio-ingressgateway -o jsonpath='{.status.loadBalancer.ingress[0].ip}')
$ export INGRESS_PORT=$(kubectl -n istio-system get service istio-ingressgateway -o jsonpath='{.spec.ports[?(@.name=="http2")].port}')
$ export SECURE_INGRESS_PORT=$(kubectl -n istio-system get service istio-ingressgateway -o jsonpath='{.spec.ports[?(@.name=="https")].port}')
$ export GATEWAY_URL=${INGRESS_HOST}:${INGRESS_PORT}
```

现在我们可以从外部尝试：

```shell
$ http http://${GATEWAY_URL}/productpage | grep -o "<title>.*</title>"
```

### 流量管理

Istio流量管理是根据你定义的目标规则将流量路由到你的服务。Istio为你的所有服务及其端点维护一个服务注册表。基本的流量管理允许每对服务之间的流量，并在每个服务实例之间进行简单的轮询负载均衡。但Istio可以做得更多。Istio的流量管理API包括五个资源：

-   虚拟服务（Virtual services）
-   目标规则（Destination rules）
-   网关（Gateways）
-   服务条目（Service entries）
-   Sidecar（Sidecars）

### 安全性

安全性是Istio的核心功能。它提供身份管理、认证和授权、安全策略以及加密。安全支持跨越多个层次，使用多种行业标准协议和最佳实践安全原则，如纵深防御、默认安全和零信任。

以下是Istio安全架构的全景图：

![Istio安全架构](ch14-fig09.png)

**图14.9：Istio安全架构**

Istio通过以下能力实现强大的安全态势：

-   Sidecar和外围代理实现客户端和服务器之间的认证和授权通信
-   控制平面管理密钥和证书
-   控制平面向代理分发安全策略和安全的命名信息
-   控制平面管理审计

让我们逐部分剖析。

#### Istio身份

Istio利用安全命名，其中由服务发现机制（例如DNS）定义的服务名称映射到基于证书的服务器身份。客户端验证服务器身份。服务器可以配置为验证客户端的身份。所有安全策略都适用于给定的身份。服务器根据客户端的身份决定客户端具有什么访问权限。

Istio身份模型可以利用其运行平台上的现有身份基础设施。在Kubernetes上，它当然使用Kubernetes服务账户。

Istio通过与Envoy代理一起运行的代理，为每个工作负载安全地分配一个x.509证书。该代理与istiod协作，自动配置和轮换证书和私钥。

#### Istio证书管理

以下是配置证书和密钥的工作流程：

1.  istiod暴露一个gRPC服务，监听证书签名请求（CSR）。
2.  该过程从Istio代理开始，它在启动时生成一个私钥和一个CSR。然后它将CSR及其自身凭据一起传输到istiod的CSR服务。
3.  此时，istiod证书颁发机构（CA）检查CSR中包含的代理凭据。如果认为有效，istiod CA会签署CSR，从而创建证书。
4.  当工作负载启动时，位于同一容器中的Envoy代理使用Envoy SDS（Secret Discovery Service）API向Istio代理请求证书和相应的密钥。
5.  Istio代理主动监控工作负载证书的过期时间，启动定期刷新证书和密钥的流程，以确保它们保持最新。

#### Istio认证

安全身份模型是Istio认证框架的基础。Istio支持两种认证模式：对等认证和请求认证。

##### 对等认证

对等认证用于服务到服务的认证。它的酷炫之处在于Istio无需任何代码更改即可提供此功能。它确保服务到服务的通信只在配置了认证策略的服务之间进行。

以下是reviews服务的认证策略，它需要双向TLS：

```yaml
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: "example-peer-policy"
  namespace: "foo"
spec:
  selector:
    matchLabels:
      app: reviews
  mtls:
    mode: STRICT
```

##### 请求认证

请求认证用于终端用户认证。Istio将验证发出请求的终端用户是否被允许发出该请求。这种请求级别的认证利用JWT（JSON Web Token），并支持许多OpenID Connect后端。

一旦调用者的身份被建立，认证框架会将其与其他声明一起传递给链条中的下一个环节——授权框架。

#### Istio授权

Istio可以在多个级别授权请求：

-   整个服务网格
-   整个命名空间
-   工作负载级别

以下是Istio的授权架构：

![Istio授权架构](ch14-fig10.png)

**图14.10：Istio授权架构**

授权基于授权策略。每个策略都有一个选择器（它适用于哪些工作负载）和规则（谁被允许访问资源以及在什么条件下）。

如果工作负载上没有定义策略，则允许所有请求。但是，如果为工作负载定义了策略，则只允许策略中规则允许的请求。你也可以定义排除规则。

以下是一个授权策略，它允许两个来源（服务账户 `cluster.local/ns/default/sa/sleep` 和命名空间 `dev`）访问命名空间 `foo` 中具有标签 `app: httpbin` 和 `version: v1` 的工作负载，前提是请求使用有效的JWT令牌发送：

```yaml
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: httpbin
  namespace: foo
spec:
  selector:
    matchLabels:
      app: httpbin
      version: v1
  action: ALLOW
  rules:
  - from:
    - source:
        principals: ["cluster.local/ns/default/sa/sleep"]
    - source:
        namespaces: ["dev"]
    to:
    - operation:
        methods: ["GET"]
    when:
    - key: request.auth.claims[iss]
      values: ["https://accounts.google.com"]
```

粒度不必限于工作负载级别。我们也可以限制对特定端点和方法的访问。除了精确匹配外，我们还可以使用前缀匹配、后缀匹配或存在匹配来指定操作。例如，以下策略允许访问所有以 `/test/` 开头的路径和所有以 `/info` 结尾的路径。允许的方法只有GET和HEAD：

```yaml
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: tester
  namespace: default
spec:
  selector:
    matchLabels:
      app: products
  rules:
  - to:
    - operation:
        paths: ["/test/*", "*/info"]
        methods: ["GET", "HEAD"]
```

如果我们想更进一步，可以指定条件。例如，我们可以只允许带有特定标头的请求。以下是一个策略，要求版本标头的值为v1或v2：

```yaml
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: httpbin
  namespace: foo
spec:
  selector:
    matchLabels:
      app: httpbin
      version: v1
  rules:
  - from:
    - source:
        principals: ["cluster.local/ns/default/sa/sleep"]
    to:
    - operation:
        methods: ["GET"]
    when:
    - key: request.headers[version]
      values: ["v1", "v2"]
```

对于TCP服务，操作的路径和方法字段不适用。Istio会直接忽略它们。但是，我们可以为特定端口指定策略：

```yaml
apiVersion: "security.istio.io/v1beta1"
kind: AuthorizationPolicy
metadata:
  name: mongodb-policy
  namespace: default
spec:
  selector:
    matchLabels:
      app: mongodb
  rules:
  - from:
    - source:
        principals: ["cluster.local/ns/default/sa/bookinfo-ratings-v2"]
    to:
    - operation:
        ports: ["27017"]
```

让我们看看Istio提供巨大价值的领域之一——遥测。

### 监控与可观测性

为你的应用程序进行遥测检测是一件吃力不讨好的工作。覆盖范围非常庞大。你需要记录日志、收集指标、为追踪创建Span。全面的可观测性对于故障排除和缓解事件至关重要，但绝非易事：

-   首先，它需要时间和精力来实现
-   需要更多时间和精力来确保它在集群中所有服务之间保持一致
-   你很容易错过一个重要的检测点或配置错误
-   如果你想更改日志提供商或分布式追踪解决方案，可能需要修改所有服务
-   它用大量内容充斥着你的代码，掩盖了业务逻辑
-   你可能需要显式地将其关闭以进行测试

如果所有这些都自动处理好了，永远不需要任何代码更改，那会怎样？这就是服务网格遥测的承诺。当然，你可能需要在应用程序/服务级别做一些工作，特别是如果你想捕获自定义指标或进行一些特定的日志记录。如果你的系统按照真正代表你的领域和工作流的边界划分为内聚的微服务，那么Istio可以帮助你开箱即用地获得不错的检测能力。其理念是Istio可以跟踪服务之间接缝处发生的事情。

### 使用Kiali可视化服务网格

Kiali是一个开源项目，它整合了Prometheus、Grafana和Jaeger，为你的Istio服务网格提供可观测性控制台。它可以回答以下问题：

-   哪些微服务参与了Istio服务网格？
-   这些微服务之间是如何连接的？
-   这些微服务的性能如何？

它有各种视图，真正允许你通过放大和缩小、过滤以及选择要显示的各种属性来对服务网格进行切片和切块。它有几种视图，你可以在它们之间切换。

## 总结

在本章中，我们非常全面地研究了Kubernetes上的服务网格。服务网格将会长期存在。它们只是运维复杂分布式系统的正确方式。将所有运维关注点与代理分离，并让服务网格控制它们，这是一个范式转变。Kubernetes当然主要是为复杂的分布式系统设计的，因此服务网格的价值立刻就显现出来。也很高兴看到Kubernetes上有许多服务网格选项。虽然大多数服务网格并非Kubernetes专用，但它是其中最重要的部署平台之一。此外，我们全面回顾了Istio——可以说是势头最猛的服务网格——并对其进行了实际测试。我们演示了服务网格的许多好处，以及它们如何与各种其他系统集成。你应该能够评估服务网格对你的系统的有用程度，以及你是否应该部署一个并开始享受其好处。

在下一章中，我们将探讨扩展Kubernetes的众多方式，并利用其模块化和灵活的设计。这是Kubernetes的标志之一，也是它被如此多社区迅速采用的原因。
