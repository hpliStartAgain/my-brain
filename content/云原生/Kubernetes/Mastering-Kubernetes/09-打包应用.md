# 打包应用

在本章中，我们将探讨Helm，这个流行的Kubernetes包管理器。每个成功且不平凡的平台都必须有一个良好的打包系统。Helm由Deis开发（2017年4月被微软收购），后来直接贡献给了Kubernetes项目。它于2018年成为CNCF项目。我们将从理解Helm的动机、架构和组件开始。然后，我们将动手实践，看看如何在Kubernetes中使用Helm及其Chart。这包括查找、安装、定制、删除和管理Chart。最后但同样重要的是，我们将涵盖如何创建自己的Chart，以及处理版本控制、依赖关系和模板化。

我们将涵盖的主题如下：

- 理解Helm
- 使用Helm
- 创建你自己的Chart
- Helm替代方案

## 理解Helm

Kubernetes提供了多种在运行时组织和编排容器的方式，但它缺少将镜像分组在一起的更高级别的组织方式。这就是Helm发挥作用的地方。在本节中，我们将介绍Helm的动机、架构和组件。我们将讨论Helm 3。你可能仍然会在生产环境中遇到Helm 2，但它的生命周期已于2020年底结束。

你可能还记得，Kubernetes在希腊语中的意思是舵手或领航员。Helm项目非常认真地对待了航海主题，正如项目名称所暗示的那样。Helm的主要概念是Chart（图表）。就像航海图详细描述海洋或沿海地区一样，Helm Chart详细描述了应用程序的所有部分。

Helm旨在执行以下操作：

- 从头构建Chart
- 将Chart打包成归档文件（.tgz）
- 与包含Chart的仓库交互
- 在现有Kubernetes集群中部署和删除Chart
- 处理已安装Chart的生命周期

### Helm的动机

Helm为几个重要的用例提供支持：

- **管理复杂性**：Chart甚至可以定义最复杂的应用程序，提供一致的应用程序安装，并充当中央权威源。
- **轻松升级**：原地升级和自定义hook允许轻松更新。
- **简单共享**：可以轻松共享可版本控制并托管在公共或私有服务器上的Chart。
- **安全回滚**：当你需要回滚最近的升级时，Helm提供了一个单一命令来回滚对基础设施的一组连贯变更。

### Helm 3架构

Helm 3架构完全依赖于客户端工具，并将其状态存储为Kubernetes Secret。Helm 3有几个组件：Release Secret、客户端和库。

![Helm 3架构](ch09-fig01.png)

客户端是命令行界面，通常使用CI/CD流水线来打包和安装应用程序。客户端利用Helm库执行请求的操作，每个已部署应用程序的状态存储在Release Secret中。

让我们回顾一下各个组件。

### Helm Release Secret

Helm将其Release作为Kubernetes Secret存储在目标命名空间中。这意味着只要存储在不同的命名空间中，你就可以拥有多个同名的Release。以下是Release Secret的样子：

```bash
$ kubectl describe secret sh.helm.release.v1.prometheus.v1 -n monitoring
Name:         sh.helm.release.v1.prometheus.v1
Namespace:    monitoring
Labels:       modifiedAt=1659855458
              name=prometheus
              owner=helm
              status=deployed
              version=1
Annotations:  <none>
Type:         helm.sh/release.v1
Data
====
release:  51716 bytes
```

数据经过两次Base64编码，然后进行GZIP压缩。

### Helm客户端

你在机器上安装Helm客户端。Helm执行以下任务：

- 促进本地Chart开发
- 管理仓库
- 监督Release
- 与Helm库交互以执行：
  - 部署新Release
  - 升级现有Release
  - 删除现有Release

### Helm库

Helm库是Helm的核心组件，负责执行所有繁重的工作。Helm库与Kubernetes API Server通信，并提供以下能力：

- 结合Helm Chart、模板和values文件来构建Release
- 将Release安装到Kubernetes中
- 创建Release对象
- 升级和卸载Chart

### Helm 2 vs Helm 3

Helm 2非常出色，在Kubernetes生态系统中扮演了非常重要的角色。但是，关于其服务端组件Tiller有很多批评。Helm 2是在RBAC成为官方访问控制方法之前设计和实现的。为了可用性，Tiller默认以非常开放的权限集安装。为生产使用锁定它并不容易。在多租户集群中这尤其具有挑战性。

Helm团队听取了批评意见，并提出了Helm 3的设计。Helm 3不再使用集群内组件Tiller，而是利用Kubernetes API Server本身通过CRD来管理Release的状态。结果是，Helm 3是一个纯客户端程序。它仍然可以管理Release并执行与Helm 2相同的任务，但无需安装服务端组件。

这种方法更加Kubernetes原生，更简单，安全性问题也不复存在。Helm用户只能通过Helm执行其kube config允许的操作。

## 使用Helm

Helm是一个丰富的包管理系统，允许你执行管理集群上安装的应用程序所需的所有必要步骤。让我们卷起袖子开始吧。我们将介绍如何安装Helm 2和Helm 3，但在所有动手实验和演示中，我们将使用Helm 3。

### 安装Helm

安装Helm涉及安装客户端和服务端。Helm用Go实现。Helm 2的可执行文件既可以作为客户端也可以作为服务端。如前所述，Helm 3是一个纯客户端程序。

### 安装Helm客户端

你必须正确配置Kubectl以与Kubernetes集群通信，因为Helm客户端使用Kubectl配置来与Kubernetes API Server通信。

Helm在此处提供所有平台的二进制版本：https://github.com/helm/helm/releases。

对于Windows，Chocolatey（https://chocolatey.org）包管理器是最佳选择（通常保持最新）：

```
choco install kubernetes-helm
```

对于macOS和Linux，你可以通过脚本安装客户端：

```bash
$ curl -fsSL -o get_helm.sh https://raw.githubusercontent.com/helm/helm/master/scripts/get-helm-3
$ chmod 700 get_helm.sh
$ ./get_helm.sh
```

在macOS上，你还可以使用Homebrew（https://brew.sh）：

```bash
$ brew install helm
$ helm version
version.BuildInfo{Version:"v3.9.2",
GitCommit:"1addefbfe665c350f4daf868a9adc5600cc064fd", GitTreeState:"clean",
GoVersion:"go1.18.4"}
```

### 查找Chart

要使用Helm安装有用的应用程序和软件，首先需要找到它们的Chart。Helm设计为可与多个Chart仓库一起使用。Helm 2默认配置为搜索稳定仓库，但你可以添加其他仓库。Helm 3没有默认仓库，但你可以搜索Helm Hub（https://artifacthub.io）或特定仓库。Helm Hub于2018年12月推出，旨在让发现托管在稳定或孵化器仓库之外的Chart和仓库变得更容易。

这就是 `helm search` 命令的用武之地。Helm可以搜索Helm Hub或特定仓库。

### 添加仓库

默认情况下，Helm 3没有设置任何仓库，因此你只能搜索Hub。过去，CNCF托管的稳定仓库是一个查找Chart的好选择。但是，CNCF不想再为托管付费，所以现在它只包含许多已弃用的Chart。

相反，你可以从Hub安装Chart，或者做一些研究并添加单个仓库。例如，对于Prometheus，有 `prometheus-community` Helm仓库。让我们添加它：

### 安装包

好的。你已经找到了你梦寐以求的包。现在，你可能想在Kubernetes集群上安装它。当你安装一个包时，Helm会创建一个Release，你可以用它来跟踪安装进度。我们使用 `helm install` 命令在 `monitoring` 命名空间中安装Prometheus，并指示Helm为我们创建命名空间：

```bash
$ helm install prometheus prometheus-community/prometheus -n monitoring --create-namespace
```

让我们看一下输出。输出的第一部分列出了我们提供的Release名称 `prometheus`、部署时间、命名空间和修订版本：

```
NAME: prometheus
LAST DEPLOYED: Sat Aug  6 23:54:50 2022
NAMESPACE: monitoring
STATUS: deployed
REVISION: 1
TEST SUITE: None
```

下一部分是自定义注释，可能相当冗长。这里有很多关于如何连接到Prometheus Server、Alert Manager和Pushgateway的有用信息。

### 检查安装状态

Helm不会等待安装完成，因为这可能需要一段时间。`helm status` 命令以与初始 `helm install` 命令输出相同的格式显示Release的最新信息。

如果你只关心状态而不需要所有额外信息，可以直接grep `STATUS` 行：

```bash
$ helm status -n monitoring prometheus | grep STATUS
STATUS: deployed
```

让我们列出 `monitoring` 命名空间中的所有Helm Release，并验证 `prometheus` 是否在其中：

```bash
$ helm list -n monitoring
NAME        NAMESPACE   REVISION  UPDATED                   STATUS    CHART                   APP VERSION
prometheus  monitoring  1         2022-08-06 ...            deployed  prometheus-15.12.0      2.36.2
```

正如你所记得的，Helm将Release信息存储在Secret中：

```bash
$ kubectl describe secret sh.helm.release.v1.prometheus.v1 -n monitoring
Name:         sh.helm.release.v1.prometheus.v1
Namespace:    monitoring
Labels:       modifiedAt=1659855458
              name=prometheus
              owner=helm
              status=deployed
              version=1
Type:         helm.sh/release.v1
Data
====
release:  51716 bytes
```

如果你想查找所有命名空间中的所有Helm Release，请使用：

```bash
$ helm list -A
```

如果你想深入底层，可以列出所有具有 `owner=helm` 标签的Secret：

```bash
$ kubectl get secret -A -l owner=helm
```

要从Secret中实际提取Release数据，你需要经过一些步骤，因为它经过了两次Base64编码（为什么？）和GZIP压缩。最终结果是JSON：

```bash
$ kubectl get secret sh.helm.release.v1.prometheus.v1 -n monitoring -o jsonpath='{.data.release}' | base64 --decode | base64 --decode | gunzip > prometheus.v1.json
```

你可能还感兴趣的是仅提取清单（manifest）：

```bash
$ kubectl get secret sh.helm.release.v1.prometheus.v1 -n monitoring -o jsonpath='{.data.release}' | base64 --decode | base64 --decode | gunzip | jq .manifest -r
```

### 定制Chart

作为用户，你经常想要定制或配置你安装的Chart。Helm完全支持通过配置文件进行定制。要了解可能的定制选项，你可以再次使用 `helm show` 命令，但这次关注values。对于像Prometheus这样复杂的项目，values文件可能相当大：

```bash
$ helm show values prometheus-community/prometheus | wc -l
1901
```

以下是部分输出：

```bash
$ helm show values prometheus-community/prometheus | head -n 20
rbac:
  create: true
podSecurityPolicy:
  enabled: false
imagePullSecrets:
  # - name: "image-pull-secret"
...
```

被注释掉的行通常包含默认值，如 `imagePullSecrets` 的名称。

如果你想定制Prometheus安装的任何部分，请将values保存到文件中，进行任何你想要的修改，然后使用自定义的values文件安装Prometheus：

```bash
$ helm install prometheus prometheus-community/prometheus --create-namespace -n monitoring -f custom-values.yaml
```

你也可以使用 `--set` 在命令行上设置单个值。如果 `-f` 和 `--set` 尝试设置相同的值，则 `--set` 优先。你可以使用逗号分隔的列表指定多个值：`--set a=1,b=2`。嵌套值可以设置为 `--set outer.inner=value`。

### 其他安装选项

`helm install` 命令可以处理各种来源：

- Chart仓库（如上所示）
- 本地Chart归档（`helm install foo-0.1.1.tgz`）
- 解压后的Chart目录（`helm install path/to/foo`）
- 完整URL（`helm install https://example.com/charts/foo-1.2.3.tgz`）

### 升级和回滚Release

你可能希望将已安装的包升级到最新和最好的版本。Helm提供了 `upgrade` 命令，它智能地操作，仅更新已更改的内容。例如，让我们检查Prometheus安装的当前值：

```bash
$ helm get values prometheus -n monitoring
USER-SUPPLIED VALUES:
null
```

到目前为止，我们还没有提供任何用户值。作为默认安装的一部分，Prometheus安装了一个Alert Manager组件：

```bash
$ k get deploy prometheus-alertmanager -n monitoring
NAME                        READY   UP-TO-DATE   AVAILABLE   AGE
prometheus-alertmanager     1/1     1            1           19h
```

让我们通过升级并传递新值来禁用Alert Manager：

```bash
$ helm upgrade --set alertmanager.enabled=false \
  prometheus prometheus-community/prometheus \
  -n monitoring
Release "prometheus" has been upgraded. Happy Helming!
NAME: prometheus
LAST DEPLOYED: Sun Aug  7 19:55:52 2022
NAMESPACE: monitoring
STATUS: deployed
REVISION: 2
TEST SUITE: None
NOTES:
...
```

升级成功完成。我们可以看到输出不再提及如何获取Alert Manager的URL。让我们验证Alert Manager的Deployment已被移除：

```bash
$ k get deployment -n monitoring
NAME                            READY   UP-TO-DATE   AVAILABLE   AGE
prometheus-kube-state-metrics   1/1     1            1           20h
prometheus-pushgateway          1/1     1            1           20h
prometheus-server               1/1     1            1           20h
```

现在，如果我们检查自定义值，可以看到我们的修改：

```bash
$ helm get values prometheus -n monitoring
USER-SUPPLIED VALUES:
alertmanager:
  enabled: false
```

假设我们决定告警还是重要的，实际上我们希望拥有Prometheus Alert Manager。没问题，我们可以回滚到最初的安装。`helm history` 命令显示所有可以回滚到的可用修订版本：

```bash
$ helm history prometheus -n monitoring
REVISION  UPDATED                   STATUS      CHART                   APP VERSION  DESCRIPTION
1         Sat Aug  6 23:57:34 2022  superseded  prometheus-15.12.0      2.36.2       Install complete
2         Sun Aug  7 19:55:52 2022  deployed    prometheus-15.12.0      2.36.2       Upgrade complete
```

让我们回滚到修订版本1：

```bash
$ helm rollback prometheus 1 -n monitoring
Rollback was a success! Happy Helming!
$ helm history prometheus -n monitoring
REVISION  UPDATED                   STATUS      CHART                   APP VERSION  DESCRIPTION
1         Sat Aug  6 23:57:34 2022  superseded  prometheus-15.12.0      2.36.2       Install complete
2         Sun Aug  7 19:55:52 2022  superseded  prometheus-15.12.0      2.36.2       Upgrade complete
3         Sun Aug  7 20:02:30 2022  deployed    prometheus-15.12.0      2.36.2       Rollback to 1
```

如你所见，回滚实际上创建了一个新的修订版本号3。修订版本2仍然存在，以防我们想回到它。

让我们验证我们的更改已被回滚：

```bash
$ k get deployment -n monitoring
NAME                            READY   UP-TO-DATE   AVAILABLE   AGE
prometheus-alertmanager         1/1     1            1           152m
prometheus-kube-state-metrics   1/1     1            1           22h
prometheus-pushgateway          1/1     1            1           22h
prometheus-server               1/1     1            1           22h
```

是的。Alert Manager回来了。

### 删除Release

当然，你也可以使用 `helm uninstall` 命令卸载Release。

首先，让我们检查Release列表。我们只在 `monitoring` 命名空间中有一个 `prometheus` Release：

```bash
$ helm list -n monitoring
NAME        NAMESPACE   REVISION  UPDATED                   STATUS    CHART                   APP VERSION
prometheus  monitoring  3         2022-08-07 ...            deployed  prometheus-15.12.0      2.36.2
```

现在，让我们卸载它。你可以使用以下任一等效命令：

- uninstall
- un
- delete
- del

这里我们使用 `uninstall` 命令：

```bash
$ helm uninstall prometheus -n monitoring
release "prometheus" uninstalled
```

这样，就没有Release了：

```bash
$ helm list -n monitoring
NAME    NAMESPACE   REVISION  UPDATED  STATUS  CHART  APP VERSION
```

Helm也可以跟踪已卸载的Release。如果你在卸载时提供 `--keep-history`，那么你可以通过向 `helm list` 添加 `--all` 或 `--uninstalled` 标志来查看已卸载的Release。请注意，尽管 `monitoring` 命名空间是由Helm在安装Prometheus时创建的，但它仍然存在，不过现在是空的：

```bash
$ k get all -n monitoring
No resources found in monitoring namespace.
```

### 使用仓库

Helm将Chart存储在作为简单HTTP服务器的仓库中。任何标准HTTP服务器都可以托管Helm仓库。在云端，Helm团队已验证AWS S3和Google Cloud Storage都可以在启用Web模式下作为Helm仓库。你甚至可以在GitHub Pages上存储Helm仓库。

需要注意的是，Helm不提供将Chart上传到远程仓库的工具，因为这将要求远程服务器理解Helm，知道将Chart放在哪里，以及如何更新 `index.yaml` 文件。

请注意，Helm最近添加了对在OCI注册表中存储Helm Chart的实验性支持。更多详情请参见 https://helm.sh/docs/topics/registries/。

在客户端，`helm repo` 命令允许你列出、添加、删除、索引和更新：

```bash
$ helm repo
This command consists of multiple subcommands to interact with chart repositories.
It can be used to add, remove, list, and index chart repositories.
Usage:
  helm repo [command]
Available Commands:
  add       add a chart repository
  index     generate an index file given a directory containing packaged charts
  list      list chart repositories
  remove    remove one or more chart repositories
  update    update information of available charts locally from chart repositories
```

我们之前已经使用了 `helm repo add` 和 `helm repo list` 命令。让我们看看如何创建我们自己的Chart并管理它们。

### 使用Helm管理Chart

Helm提供了几个命令来管理Chart。

它为你创建一个新的Chart：

```bash
$ helm create cool-chart
Creating cool-chart
```

Helm将在 `cool-chart` 下创建以下文件和目录：

```
cool-chart
├── Chart.yaml
├── charts
├── templates
│   ├── _helpers.tpl
│   ├── deployment.yaml
│   ├── hpa.yaml
│   ├── ingress.yaml
│   ├── NOTES.txt
│   ├── service.yaml
│   ├── serviceaccount.yaml
│   └── tests
│       └── test-connection.yaml
```

![Helm Chart目录结构](ch09-fig02.png)

编辑完Chart后，你可以将其打包成tar.gz归档文件：

```bash
$ helm package cool-chart
Successfully packaged chart and saved it to: cool-chart-0.1.0.tgz
```

Helm将创建一个名为 `cool-chart-0.1.0.tgz` 的归档文件，并将其存储在本地目录中。

你也可以使用 `helm lint` 来帮助你发现Chart格式或信息方面的问题：

```bash
$ helm lint cool-chart
==> Linting cool-chart
[INFO] Chart.yaml: icon is recommended
1 chart(s) linted, 0 chart(s) failed
```

### 利用starter包

`helm create` 命令提供了一个可选的 `--starter` 标志，允许你指定一个starter Chart。Starter是位于 `$XDG_DATA_HOME/helm/starters` 中的常规Chart。作为Chart开发者，你可以创建明确旨在作为创建新Chart的starter模板的Chart。在开发此类Chart时，请记住以下注意事项：

- Starter Chart中的YAML内容将被生成器覆盖。
- 用户通常会修改starter Chart的内容，因此提供清晰的文档说明用户如何进行修改至关重要。

目前，没有用于安装starter Chart的内置机制。将Chart添加到 `$XDG_DATA_HOME/helm/starters` 的唯一方法是通过手动复制。如果你创建starter pack Chart，请确保Chart的文档明确提及此要求。

## 创建你自己的Chart

Chart代表一组定义了一组连贯Kubernetes资源的文件。它可以范围从简单的Memcached Pod部署到完整Web应用栈（包括HTTP服务器、数据库、缓存、队列等）的复杂配置。

为了组织Chart，其文件被结构化为特定的目录树。这些文件随后可以打包成版本化的归档文件，便于部署和管理。关键文件是 `Chart.yaml`。

### Chart.yaml文件

`Chart.yaml` 文件是Helm Chart的主要文件。它需要 `name` 和 `version` 字段：

- **apiVersion**：Chart的API版本。
- **name**：Chart的名称，应与目录名匹配。
- **version**：Chart的版本，使用SemVer 2格式。

此外，`Chart.yaml` 文件中可以包含几个可选字段：

- **kubeVersion**：以SemVer格式指定的兼容Kubernetes版本范围。
- **description**：对项目的简短一句话描述。
- **keywords**：与项目关联的关键字列表。
- **home**：项目主页的URL。
- **sources**：项目源代码的URL列表。
- **dependencies**：Chart的依赖项列表，包括name、version、repository、condition、tags和alias。
- **maintainers**：Chart的维护者列表，包括name、email和URL。
- **icon**：可用作图标的SVG或PNG图像的URL。
- **appVersion**：Chart中包含的应用程序版本。不必遵循SemVer。
- **deprecated**：指示Chart是否已弃用的布尔值。
- **annotations**：提供额外信息的附加键值对。

### Chart版本控制

`Chart.yaml` 文件中的 `version` 字段对各种Helm工具起着关键作用。`helm package` 命令在创建包时使用它，因为它根据 `Chart.yaml` 中指定的版本构造包名。确保包名中的版本号与 `Chart.yaml` 文件中的版本号匹配非常重要。偏离此预期可能会导致错误，因为系统假定这些版本号的一致性。因此，保持 `Chart.yaml` 文件中的 `version` 字段与生成的包名之间的一致性至关重要，以避免任何问题。

### appVersion字段

可选的 `appVersion` 字段与 `version` 字段无关。Helm不使用它，它仅作为元数据或文档，供希望了解部署内容的用户使用。Helm忽略它。

### 弃用Chart

偶尔，你可能想要弃用一个Chart。你可以通过将 `Chart.yaml` 中的可选 `deprecated` 字段设置为 `true` 来将Chart标记为已弃用。只需弃用Chart的最新版本就足够了。你以后可以重用Chart名称并发布一个未弃用的新版本。弃用Chart的工作流通常包括以下步骤：

1. **更新Chart.yaml文件**：修改Chart的 `Chart.yaml` 文件以指示已弃用。这可以通过添加 `deprecated` 字段并将其设置为 `true` 来完成。此外，通常的做法是增加Chart的版本，以表明已发布包含弃用信息的新版本。

2. **发布新版本**：将包含弃用信息的更新后Chart打包并发布到Chart仓库。这确保用户在尝试安装或升级Chart时知晓弃用情况。

3. **传达弃用信息**：向用户传达弃用信息，并提供替代选项或推荐迁移路径的说明。这可以通过文档、发布说明或其他渠道完成，以确保用户知晓弃用情况并能相应地进行规划。

4. **从源代码仓库中删除Chart**：一旦发布了弃用的Chart并告知了用户，建议从源代码仓库（如Git仓库）中删除该Chart，以避免混淆，并确保用户被指向Chart仓库中的最新版本。

通过遵循这些步骤，你可以有效地弃用Chart，并为用户过渡到新版本或替代解决方案提供清晰的流程。

### Chart元数据文件

Chart可以包含几个元数据文件，如 `README.md`、`LICENSE` 和 `NOTES.txt`，这些文件提供了关于Chart的重要信息。`README.md` 文件（格式为markdown）特别重要，应包含以下详细信息：

- **应用程序或服务描述**：提供Chart所代表的应用程序或服务的清晰简洁的描述。此描述应帮助用户理解Chart的目的和功能。
- **前提条件和要求**：指定使用Chart之前需要满足的任何先决条件或要求。这可能包括特定版本的Kubernetes、必需的依赖项或其他必须满足的条件。
- **YAML选项和默认值**：记录用户可以在Chart的YAML文件中配置的可用选项。描述每个选项、其用途、接受的值或格式以及默认值。这些信息使用户能够根据需要定制Chart。
- **安装和配置说明**：提供如何安装和配置Chart的清晰说明。这可能包括指定部署Chart的命令行选项或Helm命令，以及在配置过程中的任何额外步骤或注意事项。
- **附加信息**：包含任何可能帮助用户在安装或配置Chart期间的其他相关信息。这可能涉及最佳实践、故障排除提示或已知限制。

通过在 `README.md` 文件中包含这些详细信息，Chart用户可以轻松理解Chart的目的、要求以及如何为其特定用例有效地安装和配置它。

如果Chart包含模板或 `NOTES.txt` 文件，则该文件将在安装后以及查看Release状态或升级时显示并打印出来。注释应该简洁以避免杂乱，并指向 `README.md` 文件以获取详细解释。通常将使用说明和后续步骤放在 `NOTES.txt` 中。请记住，该文件作为模板进行评估。注释在运行 `helm install` 以及 `helm status` 时打印在屏幕上。

### 管理Chart依赖项

在Helm中，一个Chart可能依赖于其他Chart。这些依赖项通过在 `Chart.yaml` 文件的 `dependencies` 字段中显式列出，或直接复制到 `charts/` 子目录中来明确表达。这提供了一种很好的方式来受益于和重用他人的知识和劳动。在Helm中，依赖项可以采取Chart归档（例如 `foo-1.2.3.tgz`）或解压后的Chart目录的形式。

然而，重要的是要注意，依赖项的名称不应以下划线（`_`）或句点（`.`）开头，因为Chart加载器会忽略这些文件。因此，建议避免以这些字符开头依赖项名称，以确保它们能被Helm正确识别和加载。

让我们将 `kube-state-metrics`（来自 `prometheus-community` 仓库）作为依赖项添加到我们的 `cool-chart` 的 `Chart.yaml` 文件中：

```yaml
dependencies:
- name: kube-state-metrics
  version: "4.13.*"
  repository: https://prometheus-community.github.io/helm-charts
  condition: kubeStateMetrics.enabled
```

`name` 字段表示你想要安装的Chart的期望名称。它应与仓库中定义的Chart名称匹配。

`version` 字段指定你想要安装的Chart的特定版本。它有助于确保你获得所需版本的Chart。

`repository` 字段包含将从其中获取Chart的Chart仓库的完整URL。它指向存储和访问Chart及其版本的位置。

`condition` 字段将在后续部分讨论。

如果仓库尚未添加，请使用 `helm repo` 在本地添加它。

一旦定义了依赖项，你可以运行 `helm dependency update` 命令。Helm将为你在 `charts` 子目录中下载所有指定的Chart：

```bash
$ helm dep up cool-chart
Hang tight while we grab the latest from your chart repositories...
...Successfully got an update from the "prometheus-community" chart repository
Update Complete. Happy Helming!
Saving 1 charts
Downloading kube-state-metrics from repo https://prometheus-community.github.io/helm-charts
Deleting outdated charts
```

Helm将依赖项Chart作为归档文件存储在 `charts/` 目录中：

```bash
$ ls cool-chart/charts
kube-state-metrics-4.13.0.tgz
```

在 `Chart.yaml` 的 `dependencies` 字段中管理Chart及其依赖项（而不是仅仅将Chart复制到 `charts/` 子目录）是一种最佳实践。它显式记录了依赖关系，促进了团队间的共享，并支持自动化流水线。

### 利用依赖项字段的附加子字段

`Chart.yaml` 中每个依赖项条目可能包含可选字段，如 `tags` 和 `condition`。

这些字段可用于动态控制Chart的加载（如果未指定，则将加载所有Chart）。如果存在 `tags` 或 `condition` 字段，Helm将评估它们并确定是否应加载目标Chart。

- **condition字段**：Chart依赖项中的 `condition` 字段包含一个或多个逗号分隔的YAML路径。这些路径引用顶级父Chart的values文件中的值。如果某个路径存在且评估为布尔值，则决定Chart是启用还是禁用。如果提供了多个路径，则仅评估第一个有效的路径。如果没有路径存在，则condition无效，Chart将无条件加载。

- **tags字段**：`tags` 字段允许你为Chart关联标签。它是一个YAML列表，你可以在其中指定一个或多个标签。在顶级父Chart的values文件中，你可以通过指定标签和相应的布尔值来启用或禁用所有具有特定标签的Chart。这提供了一种根据关联标签来管理和控制Chart的便捷方式。

以下是一个 `dependencies` 字段和充分利用了conditions和tags的 `values.yaml` 示例，用于启用和禁用依赖项的安装。`dependencies` 字段根据 `global.enabled` 字段的值和特定子Chart的 `enabled` 字段的值定义了安装依赖项的两个条件：

```yaml
dependencies:
  - name: subchart1
    repository: http://localhost:10191
    version: 0.1.0
    condition: subchart1.enabled, global.subchart1.enabled
    tags:
      - front-end
      - subchart1
  - name: subchart2
    repository: http://localhost:10191
    version: 0.1.0
    condition: subchart2.enabled, global.subchart2.enabled
    tags:
      - back-end
      - subchart2
```

`values.yaml` 文件为一些condition变量赋值。`subchart2` 标签没有获得值，因此它自动启用：

```yaml
# parentchart/values.yaml
subchart1:
  enabled: true
tags:
  front-end: false
  back-end: true
```

你可以在安装Chart时从命令行设置tags和condition值，并且它们将优先于 `values.yaml` 文件：

```bash
$ helm install --set subchart2.enabled=false
```

tags和conditions的解析规则如下：

- 在values中设置的条件会覆盖tags。每个Chart找到的第一个存在的条件路径生效，其他条件被忽略。
- 如果与Chart关联的任何标签在顶级父Chart的values中设置为 `true`，则Chart被视为启用。
- tags和condition值必须在values文件的顶层设置。
- 当前不支持嵌套的tags表或全局配置中的tags。这意味着tags应直接在顶级父Chart的values下，而不是嵌套在其他结构中。

### 使用模板和值

任何非平凡的应用程序都需要针对特定用例进行配置和适配。Helm Chart是使用Go模板语言填充占位符的模板。Helm支持来自Sprig库的额外函数，该库包含许多有用的辅助函数以及几个其他专门的函数。模板文件存储在Chart的 `templates/` 子目录中。Helm将使用模板引擎渲染此目录中的所有文件，并应用提供的values文件。

### 编写模板文件

模板文件只是遵循Go模板语言规则的文本文件。它们可以生成Kubernetes配置文件以及任何其他文件。以下是来自 `prometheus-community` 仓库的Prometheus Server的 `service.yaml` 模板文件：

```yaml
{{- if and .Values.server.enabled .Values.server.service.enabled -}}
apiVersion: v1
kind: Service
metadata:
{{- if .Values.server.service.annotations }}
  annotations:
{{ toYaml .Values.server.service.annotations | indent 4 }}
{{- end }}
  labels:
{{ include "prometheus.server.labels" . | nindent 4 }}
{{- if .Values.server.service.labels }}
{{ toYaml .Values.server.service.labels | indent 4 }}
{{- end }}
  name: {{ template "prometheus.server.fullname" . }}
{{ include "prometheus.namespace" . | indent 2 }}
spec:
{{- if .Values.server.service.clusterIP }}
  clusterIP: {{ .Values.server.service.clusterIP }}
{{- end }}
...
  type: "{{ .Values.server.service.type }}"
{{- end -}}
```

该文件可在此处获取：https://github.com/prometheus-community/helm-charts/blob/main/charts/prometheus/templates/service.yaml。

如果它看起来令人困惑，不用担心。基本思想是你有一个简单的文本文件，其中包含稍后可以以各种方式填充的值的占位符，以及条件、一些函数和可以应用于这些值的流水线。

### 使用流水线和函数

Helm通过内置的Go模板函数、Sprig函数和流水线，允许在模板文件中使用丰富和复杂的语法。以下是一个利用这些功能的模板示例。它使用 `repeat`、`quote` 和 `upper` 函数处理 `food` 和 `drink` 键，并使用流水线将多个函数链接在一起：

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: {{ .Release.Name }}-configmap
data:
  greeting: "Hello World"
  drink: {{ .Values.favorite.drink | repeat 3 | quote }}
  food: {{ .Values.favorite.food | upper }}
```

让我们添加一个 `values.yaml` 文件：

```yaml
favorite:
  drink: coffee
  food: pizza
```

### 嵌入内置对象

Helm提供了一些你可以在模板中使用的内置对象。在上面的Prometheus Chart模板中，`Release.Name`、`Release.Service`、`Chart.Name` 和 `Chart.Version` 是Helm预定义值的例子。其他对象包括：

- `Values`
- `Chart`
- `Template`
- `Files`
- `Capabilities`

`Values` 对象包含在values文件或命令行上定义的所有值。`Chart` 对象是 `Chart.yaml` 的内容。`Template` 对象包含有关当前模板的信息。`Files` 和 `Capabilities` 是类似映射的对象，允许通过各种函数访问非专门化文件以及关于Kubernetes集群的一般信息。

请注意，`Chart.yaml` 中的未知字段会被模板引擎忽略，不能用于向模板传递任意的结构化数据。

### 从文件提供值

以下是Prometheus Server的默认values文件的一部分。此文件中的值用于填充多个模板。这些值代表默认值，你可以通过复制文件并根据需要修改来覆盖它们。注意那些解释每个值的目的和各种选项的有用注释：

```yaml
server:
  ## Prometheus server容器名称
  ##
  enabled: true

  name: server

```

## Helm替代方案

Helm经过实战检验，在Kubernetes世界中非常常见，但它也有缺点和批评，特别是当你开发自己的Chart时。很多批评是针对Helm 2及其服务端组件Tiller的。然而，Helm 3也不是万能的。在规模化情况下，当你开发自己的Chart并编写包含大量条件逻辑和庞大values文件的复杂模板时，管理起来可能变得非常具有挑战性。

如果你感受到了这种痛苦，你可能想研究一些替代方案。请注意，这些项目大多侧重于部署方面。Helm的依赖管理仍然是其优势。让我们看看你可能想考虑的一些有趣的项目。

### Kustomize

Kustomize是YAML模板化的一种替代方案，它通过在原始YAML文件之上使用overlay的概念来实现。它在Kubernetes 1.14中被添加到kubectl中。

参见 https://github.com/kubernetes-sigs/kustomize。

### Cue

Cue是一个非常有趣的项目。其数据验证语言和推理深受逻辑编程的启发。它不是一种通用编程语言。它专注于数据验证、数据模板化、配置、查询和代码生成，但也具有一些脚本能力。Cue的主要概念是类型和数据的统一。这赋予了Cue很大的表达能力，并消除了对枚举和泛型等结构的需求。

参见 https://cuelang.org。

关于用Cue替代Helm的具体讨论，请参见：https://github.com/cue-lang/cue/discussions/1159。

### kapp-controller

kapp-controller为Kubernetes提供持续交付和包管理能力。其声明式API和分层方法允许你有效地构建、部署和管理你的应用程序。使用kapp-controller，你可以将软件打包成可分发的包，并让用户无缝地在Kubernetes集群上发现、配置和安装这些包。

参见 https://carvel.dev/kapp-controller/。

至此，我们对Helm替代方案的快速回顾到此结束。

## 总结

在本章中，我们了解了Helm，一个流行的Kubernetes包管理器。Helm赋予Kubernetes管理由许多具有相互依赖关系的Kubernetes资源组成的复杂软件的能力。它服务于与操作系统包管理器相同的目的。它组织包，让你可以搜索Chart、安装和升级Chart，以及与协作者共享Chart。你可以开发自己的Chart并将其存储在仓库中。Helm 3是一个纯客户端解决方案，使用Kubernetes Secret来管理集群中Release的状态。我们还看了一些Helm的替代方案。

至此，你应该理解Helm在Kubernetes生态系统和社区中扮演的重要角色。你应该能够高效地使用它，甚至可以开发和共享你自己的Chart。
