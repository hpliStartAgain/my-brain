在不断演进的数据存储和处理领域中，选择正确的数据格式是一个关键决策，它会显著影响性能、效率和进行分析的便利性。本章深入探讨三种主要的表文件格式——ORC（Optimized Row Columnar）、Parquet 和 Avro——每种格式都旨在解决大数据领域中特定的挑战。

### 理解文件格式

文件格式是一种标准化框架，规定数据如何在文件中结构化和存储。它建立了编码信息的规则，并指定了数据的表示、排列和解释方式。这种标准化结构对于跨不同计算机系统、应用程序和平台的数据交换、存储和处理至关重要。

文件格式中的规范管理数据结构，涵盖记录组织、字符编码和元数据表示等细节。不同的文件格式是为特定目的而设计的，影响着数据压缩、存储效率和可解释性等因素。

在 Hadoop 生态系统的上下文中，文件格式定义了数据在分布式计算框架中如何组织、存储和处理。Hadoop 生态系统包含一系列为处理海量数据集而设计的工具和组件，文件格式的选择会显著影响数据存储、检索和处理效率。Hadoop 中的文件格式旨在满足特定需求，考虑数据压缩、Schema 演进以及与各种处理引擎的兼容性等因素。ORC、Parquet 和 Avro 已成为流行的选择，每种格式都基于其设计原则提供独特的优势。

所选择的文件格式会影响数据序列化、压缩和存储组织，影响查询性能、存储效率以及与不同数据处理框架的集成等要素。因此，理解和选择适当的文件格式在优化 Hadoop 生态系统中的数据工作流和分析方面发挥着关键作用。

各种文件格式之间的一个显著区别在于它们存储和组织数据的方式。有些格式采用**行式存储**（将单行的数据组合在一起），而另一些使用**列式存储**（将单列的数据组合在一起）。这种选择显著影响特定查询和分析的效率。

此外，表文件格式通常集成了压缩算法等特性以减少存储需求，以及序列化机制以便于系统间的数据交换。随着数据量的持续增长，对高效存储和处理机制的需求变得越来越关键，使得选择合适的表格式成为数据系统设计和优化中的关键决策。

### Optimized Row Columnar（ORC）表格式

![[Pasted image 20260517220924.png]]

**图 6.2: Apache ORC**

Optimized Row Columnar（ORC）是一种列式存储格式，专为在大数据处理框架中最大化分析查询的效率而设计。ORC 源于 Apache Hive 项目，策略性地结合了基于行和基于列存储的优势，使其成为使用 Apache Hive、Apache Spark 和其他兼容平台的数据生态系统的首选。

#### 动机

多年来，Hive 的 RCFile 一直是 Hadoop 中表格数据存储的主要格式。然而，它存在局限性，因为它将每列仅仅视为没有内在含义的二进制 blob。在 Hive 0.11 中，引入了一种名为 Optimized Row Columnar（ORC）的新文件格式来解决这个问题。与 RCFile 不同，ORC 保留了表定义中的类型信息，从而实现更高效的数据存储和检索。

ORC 使用类型特定的读取器和写入器，实现轻量级压缩技术，如字典编码、位填充、增量编码和行程编码。与 RCFile 相比，这大大减小了文件大小。此外，除了轻量级压缩方法外，ORC 还支持使用 Zlib 或 Snappy 进行通用压缩，进一步减小文件大小。

除了存储效率之外，ORC 还引入了诸如**投影（Projection）** 等特性，允许查询只读取必要的列，从而最小化数据访问。此外，ORC 文件包含轻量级索引，包含每 10,000 行集合和整个文件中每列的最小值和最大值。利用来自 Hive 的谓词下推（Pushdown Filter），文件读取器可以高效跳过不相关的行集，提升查询性能。

#### 关键特性

以下是 ORC 表格式的一些关键特性：

**列式存储（Columnar Storage）：** ORC 的基本原则在于其列式存储模型，数据按列而不是按行组织和存储。这种方法通过将相似的数据类型和值组合在一起来实现更好的压缩比，减少冗余并优化存储。

**压缩技术（Compression Techniques）：** ORC 的一个突出特性是支持多种压缩算法，包括 Zlib、Snappy 和 LZ4。这种灵活性使用户能够根据其特定需求定制压缩策略，在存储空间和查询性能之间找到合适的平衡。

**谓词下推（Predicate Pushdown）：** ORC 引入了谓词下推，这是一种将过滤操作下推到存储层的技术。通过在存储层过滤数据，查询执行期间跳过不必要的信息，从而带来显著的性能提升，因为只处理相关部分。

**轻量级索引（Lightweight Indexing）：** 为提升数据检索速度，ORC 集成了轻量级索引机制，如布隆过滤器（Bloom Filters）和最小-最大统计信息。这些特性有助于在查询执行期间跳过不相关的数据块，为分析工作负载的整体效率做出贡献。

**Schema 演进（Schema Evolution）：** ORC 支持 Schema 演进，这是一个关键特性，允许添加或修改列而无需完全重写整个数据集。这种适应性在数据 Schema 随时间变化的场景中特别有益。

#### 用例

ORC 在分析查询占主导的场景中找到了最佳定位，使其成为涉及数据仓库、商业智能和大规模分析的应用的理想选择。

### Parquet 表格式

![[Pasted image 20260517220935.png]]

**图 6.3: Apache Parquet**

Parquet 是一种列式存储格式，已发展成为在大数据环境中广泛采用的高效数据存储和处理解决方案。其设计专注于优化性能、实现跨不同数据处理框架的兼容性，以及提供有效的压缩机制。本节深入探讨定义 Parquet 表格式的关键特性和规范。

#### 动机

Parquet 的开发旨在将压缩、高效的列式数据表示的优势扩展到 Hadoop 生态系统中的每个项目。

Parquet 专注于复杂的嵌套数据结构，整合了 Dremel 论文中描述的记录拆分和组装算法。这种方法被认为优于简单的嵌套命名空间扁平化。

Parquet 旨在促进高效的压缩和编码方案。各种项目已经展示了将适当的压缩和编码方案应用于数据对性能的影响。Parquet 支持按列指定压缩方案，并且旨在支持在开发和实现更多编码时添加它们。

Parquet 面向 Hadoop 生态系统中的广泛用户基础。考虑到 Hadoop 中数据处理框架的多样性，其重点是提供一个高效、实现良好的列式存储基础，对所有框架都有价值，而无需在设置过程中承担大量和困难的依赖。

#### 关键特性

以下是 Parquet 表格式的关键特性：

**列式存储模型（Columnar Storage Model）：** Parquet 以列式格式组织和存储数据，这与传统的行式存储不同。这种设计选择将相似的数据组合在一起，实现更好的压缩、更好的查询性能以及分析工作负载的高效数据检索。

**Schema 演进（Schema Evolution）：** Parquet 的一个显著特性是其对 Schema 演进的强大支持。这允许数据 Schema 随时间演进，适应诸如添加新列或修改现有列等变化，而无需完全重写数据集。这种灵活性在动态数据环境中特别有价值。

**压缩技术（Compression Techniques）：** Parquet 支持一系列压缩算法，包括 Snappy、Gzip 和 LZ4。这种灵活性使用户能够根据其特定的存储和处理需求定制压缩策略，在存储空间和查询性能之间取得平衡。

**谓词下推（Predicate Pushdown）：** 与 ORC 类似，Parquet 支持谓词下推。过滤操作被下推到存储层，最小化查询执行期间需要处理的数据量。这个特性通过跳过不相关的数据来提升查询性能。

**跨平台兼容性（Cross-Platform Compatibility）：** Parquet 的设计强调跨平台兼容性，使其成为不同大数据处理框架之间互操作的理想选择。其开放标准允许用户在系统之间无缝移动和共享数据，促进灵活性并避免供应商锁定。

**高级嵌套数据支持（Advanced Nested Data Support）：** Parquet 在处理复杂嵌套数据结构方面表现出色，使其非常适合涉及嵌套数组和映射的场景。这种能力对于以结构化且高效的方式表示多样化和层次化的数据至关重要。

#### 用例

Parquet 在分析查询、数据仓库和大规模分析盛行的场景中得到广泛使用。它高效处理列式存储、支持 Schema 演进以及提供跨平台兼容性的能力，使其成为满足多样化数据处理需求的可靠选择。

### Avro 表格式

![[Pasted image 20260517220944.png]]

**图 6.4: Apache AVRO**

Avro 是一种紧凑的二进制序列化格式，作为数据交换和存储的灵活高效选择而广受欢迎。Avro 开发于 Apache Hadoop 项目，强调简单性、可扩展性和对各种数据类型的支持。在本节中，我们将探讨定义 Avro 表格式的关键特性和优势。

#### 动机

Avro 是一个面向行的框架，用于远程过程调用和数据序列化，起源于 Apache 的 Hadoop 项目。它利用 JSON 定义数据类型和协议，同时采用紧凑的二进制格式进行数据序列化。Avro 的主要应用在 Apache Hadoop 中，既作为持久数据的序列化格式，也作为 Hadoop 节点之间以及从客户端程序到 Hadoop 服务的通信有线格式。为了组织编码数据，Avro 使用 Schema，提供两种不同的形式：一种适合人工编辑（Avro IDL），另一种基于 JSON，更适合机器阅读。

它类似于 Thrift 和 Protocol Buffers，但在 Schema 更改时不需要运行代码生成程序（除非对于静态类型语言需要）。

#### 关键特性

Avro 表格式的关键特性包括：

**二进制序列化（Binary Serialization）：** Avro 采用二进制序列化格式，实现紧凑且高效的数据表示。这种设计选择提高了数据传输速度并减少存储需求，使 Avro 适合带宽或存储资源有限的场景。

**Schema 定义（Schema Definition）：** Avro 的一个显著特点是依赖 Schema 定义。Avro 数据始终伴随着描述数据结构的 Schema。这个 Schema 以 JSON 格式定义，允许数据结构以自描述和人类可读的方式表示。

**动态类型（Dynamic Typing）：** Avro 支持动态类型，使用户能够演进其数据 Schema 而无需更改已存储的数据。这种灵活性在数据结构可能随时间变化的动态环境中很有益。

**跨语言兼容性（Compatibility Across Languages）：** Avro 的设计促进了跨语言兼容性，允许使用 Avro 序列化的数据在用不同编程语言编写的应用程序之间轻松交换。这种互操作性在异构计算环境中至关重要。

**Schema 演进（Schema Evolution）：** 与 Parquet 类似，Avro 支持 Schema 演进。这使得可以在不要求完全重写现有数据的情况下添加或修改 Schema 中的字段。Avro 的 Schema 演进能力有助于其在变化的数据场景中的适应性。

#### 用例

Avro 非常适合紧凑数据表示、Schema 灵活性和跨语言兼容性至关重要的场景。其轻量级和自描述的特性使其成为不同系统和语言之间数据交换的首选。

### 为你的用例选择合适的格式

选择适当的数据存储格式是一个关键决策，会显著影响数据处理工作流的效率和性能。三种讨论的格式——Parquet、ORC 和 Avro——各有其优势和特性，使它们适合特定的用例。

**Parquet**

- **用例：** 适合分析查询、数据仓库以及高效压缩和列式存储至关重要的场景。
- **优势：** 在读密集型分析工作负载中表现出色，支持 Schema 演进，并在不同数据处理框架之间具有广泛的兼容性。

**ORC**

- **用例：** 非常适合分析、数据仓库以及需要高效压缩和谓词下推能力的应用。
- **优势：** 结合了行式和列式存储的优化，高级压缩技术，支持谓词下推，提升查询性能。

**Avro**

- **用例：** 最适合数据交换、紧凑序列化以及需要轻量级、跨语言兼容格式的应用。
- **优势：** 紧凑的二进制序列化、动态类型、跨语言兼容性以及内置的 Schema 演进支持。

**根据工作负载选择正确的格式：**

- **分析工作负载：** 对于读密集型分析工作负载，高效压缩和列式存储至关重要，Parquet 通常是首选，因为它具有出色的性能特征。
- **数据仓库：** Parquet 和 ORC 都适合数据仓库，Parquet 在兼容性方面表现优异，而 ORC 则提供高级压缩和谓词下推能力。
- **数据交换和紧凑序列化：** 当数据交换和紧凑序列化是主要关注点时，Avro 是首选格式，因为它具有紧凑的二进制序列化和跨语言兼容性。
- **Schema 不断演进的动态环境：** 如果您的数据环境涉及频繁的 Schema 更改，Parquet 和 Avro 都支持 Schema 演进，为适应动态数据结构提供了灵活性。

总之，Parquet、ORC 和 Avro 之间的选择取决于您用例的具体需求。在做出决策时，请考虑查询模式、存储效率、Schema 演进需求以及与现有数据处理框架的兼容性等因素。通常，对每种格式在您数据工作流上下文中的独特特性进行性能测试和分析，以确保获得最佳结果。

### 文件格式在 Hadoop 技术栈中的定位

Hadoop 生态系统中的文件格式在定义数据的存储、处理和交换方式方面起着至关重要的作用。它们在 Hadoop 技术栈中的位置根据其特性和用例而有所不同，但共同考虑因素包括：

- **存储效率：** 所有三种文件格式（ORC、Parquet 和 Avro）都以其存储效率著称，提供压缩机制以减少存储需求并提高数据处理速度。
- **Schema 演进：** Parquet 和 Avro 都设计为支持 Schema 演进，允许数据随时间修改结构而无需完全重写数据集。

理解文件格式在 Hadoop 技术栈中的位置使组织能够在设计数据处理工作流时做出明智的决策。选择正确的文件格式可以显著影响存储效率、查询性能和大数据计划的整体成功，因此它与存储层密切相关。因此，我们可以将分布式存储和文件格式进一步归入 Hadoop 技术栈的存储层。

## 第二部分：表格式——赋能数据湖和湖仓一体

在本节中，我们将全面探讨各种表格式，考察它们的结构、功能和应用。

### 理解表格式

在深入探讨具体格式之前，让我们首先定义表格式在大数据领域中的含义。

### 定义表格式

表格式概述了数据在位于数据湖或湖仓一体架构（也称为存储层）中的表内如何构成和组织的独特方式。它建立了列和行的组织、数据的分区和版本控制以及事务的处理方式。选择适当的表格式可以深刻影响大数据管道和分析工作流的性能、可靠性和可管理性。

**表格式的关键方面：**

- **结构（Structure）：** 定义列和行的排列，包括数据类型、空值处理和约束。
- **分区（Partitioning）：** 根据特定条件将数据分割为较小的段，使查询更快、存储管理更高效。
- **版本控制（Versioning）：** 跟踪数据随时间进行的修改，允许回滚和审计追踪。
- **事务（Transactions）：** 通过在写操作期间强制执行 ACID 属性（原子性、一致性、隔离性、持久性）来保证数据一致性。
- **查询（Querying）：** 不同的格式可能以不同的方式优化查询性能，取决于数据访问模式和大小。
- **存储效率（Storage Efficiency）：** 一些格式使用压缩技术或高效的文件格式来优化存储利用率。

### 表格式与文件格式

表格式和文件格式完美协作。文件格式通过高效存储和编码单个文件中的数据奠定基础。表格式然后在此基础上构建，将这些文件编排为一个有凝聚力的单元，实现对大数据的高效查询、分析和管理。

选择正确的表格式和文件格式组合对于优化大数据管道和释放数据的全部潜力至关重要。理解它们各自的角色和交互使您能够自信且高效地驾驭大数据的复杂世界。

下表总结了表格式和文件格式之间的主要区别：

| 维度 | 文件格式 | 表格式 |
|------|---------|--------|
| **关注点** | 单个文件中的数据编码和存储 | 跨多个文件的表级数据组织和管理 |
| **范围** | 文件级别 | 表/数据集级别 |
| **事务支持** | 通常不提供 | 提供 ACID 事务支持 |
| **Schema 管理** | 文件头部包含 Schema | 集中式元数据管理，Schema 演进 |
| **版本控制** | 通常不追踪版本 | 通过快照（Snapshot）提供版本控制和历史记录 |
| **分区** | 不涉及分区管理 | 管理分区策略和演进 |
| **时间旅行** | 不支持 | 支持（查询历史数据版本）|
| **示例** | ORC、Parquet、Avro | Apache Iceberg、Delta Lake、Apache Hudi、Hive ACID |

### 大数据常用表格式

传统数据仓库具有严格的 Schema 和 ACID 事务，但往往难以跟上当今世界不断增长的数据量和速度。这就是现代表格式（如 Apache Hive ACID、Iceberg、Delta Lake 和 Hudi）发挥作用的地方。这些格式弥合了传统数据仓库与数据湖灵活性之间的差距，实现了对大型不断演进数据集的高效管理和查询。

大数据中流行的表格式：

- **Hive ACID：** 在熟悉的 Hive 生态系统中提供 ACID 事务，为数据湖中的大型数据集提供高效的查询性能和数据管理。
- **Delta Lake：** 结合了数据湖的灵活性与数据仓库的特性，如 ACID 事务和 Schema 演进，提供在分布式文件系统/云存储上摄取、管理和查询大型分析数据集的能力，并支持增量更新和删除。
- **Apache Hudi：** 专为增量数据处理而设计，支持高效的 Upsert 和 Delete 操作，减少全量重处理的开销。

#### Delta Lake

Delta Lake 是一个开源存储层，为数据湖带来可靠性。它由 Databricks 开发，通过提供 ACID（原子性、一致性、隔离性、持久性）事务来扩展 Apache Spark 和 Apache Hadoop 的能力，即使在并发数据写入和读取的情况下也能确保数据完整性和一致性。

**Delta Lake 的关键特性：**

- **ACID 事务：** Delta Lake 支持 ACID 事务，使得执行可靠且一致的数据操作（如插入、更新和删除）成为可能。这确保了即使在并发操作的情况下也能维护数据完整性。
- **Schema 强制和执行与演进：** Delta Lake 允许 Schema 强制执行和 Schema 演进。Schema 强制执行确保数据符合定义的结构，而 Schema 演进允许 Schema 随时间变化而不会中断正在进行的操作。
- **时间旅行（Time Travel）：** Delta Lake 提供时间旅行能力，使用户能够查询数据的先前版本。这对于审计、调试和重现实验特别有用。
- **高效数据管理：** Delta Lake 通过使用数据压缩和分区等技术来优化存储。这降低了存储成本并提高了查询性能。
- **可扩展性：** 设计用于处理 PB 级数据，Delta Lake 可以水平扩展以适应不断增长的数据量。

#### Apache Hudi

Apache Hudi（Hadoop Upsert, Delete, and Incremental）是一个开源数据管理框架，用于简化增量数据处理和改进数据湖管理。它最初由 Uber 开发，并已贡献给 Apache 软件基金会。

**Apache Hudi 的关键特性：**

- **增量数据处理：** Hudi 专为增量数据处理而设计，允许高效的 Upsert 和 Delete 操作。这减少了与全量重处理大型数据集相关的开销。
- **索引机制：** Hudi 提供内置索引机制，实现快速的 Upsert、Delete 和记录查找。这对于维护数据新鲜度和确保快速访问更新记录至关重要。
- **数据版本控制：** 与 Delta Lake 一样，Hudi 支持数据版本控制，使用户能够访问数据的历史版本。这有助于数据审计和回滚能力。
- **可扩展和分布式：** Hudi 构建为与分布式文件系统和云存储解决方案无缝协作，使其能够为大型数据集提供可扩展性。
- **实时数据处理：** Hudi 支持实时数据摄取，并提供处理流数据的机制，使其适用于需要实时摄取和处理数据的场景。
- **优化的查询性能：** Hudi 与 Apache Hive、Apache Spark 和 Presto 等查询引擎集成，通过数据聚类和压缩等技术优化查询性能。

Delta Lake 和 Apache Hudi 都是管理数据湖中大型不断演进数据集的强大工具。它们通过提供强大的事务支持、高效的数据管理以及确保数据可靠性和一致性的特性，增强了传统数据湖的能力。

虽然 Delta Lake 和 Apache Hudi 提供了强大的特性（如 ACID 事务和增量数据处理），但 Apache Iceberg 对 Schema 演进、高效查询性能和灵活元数据管理的重视使其对在数据湖环境中处理大型不断演进数据集的组织特别有吸引力。其设计原则迎合了现代数据管理和分析的复杂性，使其在许多场景中成为首选。

#### 导航 Iceberg 版图：基本术语

进入 Apache Iceberg 的领域需要熟悉其独特的语言。以下是为数据管理之旅做准备的关键术语词汇表：

**基础知识：**

- **表（Table）：** Iceberg 中的数据组织基本单元，类似于传统表但具有高级特性。
- **快照（Snapshot）：** 数据在特定时间点的冻结版本，捕获所有行、列和 Schema 定义。
- **清单（Manifest）：** 包含属于一个快照的文件的详细信息（包括大小、位置和分区数据）的文件。
- **数据文件（Data File）：** 存储在快照中的实际数据的独立单元，通常采用 Parquet 或 ORC 等压缩格式。
- **分区（Partition）：** 基于特定条件（如日期、区域）对数据进行逻辑细分，允许高效查询和组织。

**高级特性：**

- **ACID 事务：** 即使在并发写入和更新的情况下也能确保数据一致性，保证数据操作准确可靠。
- **时间旅行（Time Travel）：** 能够访问历史快照，使您能够分析数据的过去版本并回滚意外更改。
- **Schema 演进（Schema Evolution）：** 无需中断现有查询即可修改表结构（添加/删除列），确保灵活性和适应性。
- **隐式分区（Hidden Partitioning）：** 在查询期间跳过不相关的分区，显著提高大型数据集的性能。
- **聚类（Clustering）：** 优化特定查询模式的数据布局，进一步加速数据访问。

**其他概念：**

- **目录（Catalog）：** 定义 Iceberg 存储元数据的位置（如定义表、快照）以及如何访问它。
- **Refs 表：** 跟踪链接到 Iceberg 表的外部数据源，如 Avro 或 ORC 文件。
- **Merge Into：** 高效地将新数据或更新集成到现有 Iceberg 表中。
- **写审计（Write Audit）：** 通过将较小的文件合并为更大、更高效的文件来优化数据存储。

通过掌握这些核心 Iceberg 术语，您将解锁这个强大数据管理平台的全部潜力。请记住，持续学习和探索在数据分析旅程中至关重要。

#### Apache Iceberg 的关键特性

让我们讨论 Apache Iceberg 的关键特性：

**Schema 演进与灵活性：**
Apache Iceberg 允许用户无缝演进来表 Schema。这种灵活性在数据结构随时间演进的场景中至关重要，消除了复杂且资源密集型的 Schema 迁移过程。

**快照隔离（Snapshot Isolation）：**
快照隔离的概念确保查询在特定时间点的表的一致且隔离的视图上运行。这个特性对于维护数据一致性至关重要的分析和报告任务来说是基础性的。

**事务支持（Transaction Support）：**
对事务的原生支持使得对表的更新可以原子化且隔离。这保证了写操作期间的数据完整性，并提供了管理并发修改的强大机制。

**时间旅行能力（Time-Travel Capabilities）：**
时间旅行功能允许用户查询表的历史版本。这个特性对于审计、调试和分析趋势非常宝贵，通过提供对不同时间点数据状态的洞察。

**元数据管理（Metadata Management）：**
Apache Iceberg 在元数据管理方面表现出色，细致地跟踪表结构的更改。这不仅增强了数据治理，还简化了系统内数据演进的理解和控制。

**引擎无关的自由（Engine Agnostic Freedom）：**
Iceberg 与 Spark、Trino、Presto 和 Hive 等流行引擎无缝集成，在数据处理生态系统中提供灵活性和自由。

#### 实际用例

**大规模分析：**
Apache Iceberg 在涉及大规模分析的场景中表现出色，提供高效的表管理、Schema 演进和事务支持。这些能力对于维护数据完整性和确保最佳查询性能至关重要。

**数据仓库：**
快照隔离和时间旅行特性使 Apache Iceberg 成为数据仓库应用的绝佳选择。它提供一致和历史的数据视图，增强分析和报告能力。

**云原生环境：**
凭借对云存储系统的原生支持，Apache Iceberg 无缝集成到云原生环境中。利用云存储解决方案的可扩展性和成本效益，Iceberg 被证明是组织在云中运营的通用选择。

### Apache Iceberg 在 Hadoop 技术栈中的定位

![[Pasted image 20260517221014.png]]

**图 6.7: Apache Iceberg 在 Hadoop 技术栈中的定位**

Apache Iceberg 作为数据管理层，构成数据湖的骨干。它位于存储和集群资源管理层之上，以及数据处理和数据访问层之下，原因如下：

- **基础存储：** Iceberg 通常位于分布式文件系统（如 HDFS）或基于云的对象存储（S3、ADLS 等）之上，为存储数据文件提供基础层。

随着组织应对管理大型数据集的复杂性，Apache Iceberg 作为一种变革性解决方案脱颖而出。它致力于解决 Schema 演进、一致性和可扩展性的挑战，使 Iceberg 成为大数据技术演进中的基石。随着采用率的不断增长，Apache Iceberg 始终站在前沿，塑造着大数据世界中表管理的未来。

### 在 Spark 中使用 ORC、Parquet 和 Avro 格式创建表

- **识别当前版本：** 查看当前用于查询的快照并访问其元数据。
- **列出可用版本：** 浏览所有历史快照并访问其详细信息。

![[Pasted image 20260517221650.png]]

Manifests 表存储有关每个快照组成文件的详细信息。这包括文件路径、大小、数据统计信息和分区信息。Manifests 表允许您：

- **优化查询：** Iceberg 使用清单高效定位查询的相关数据文件，显著提高性能。
- **验证数据完整性：** 验证数据文件没有被损坏或篡改。
- **理解数据分布：** 分析数据如何在每个快照的文件之间进行分区和分布。

Partitions 表列出 Iceberg 表的所有定义分区。它包括分区名称、值以及每个分区内数据的统计信息。此表允许您：

- **按分区分割分析数据：** 基于特定分区值进行过滤和聚合数据。
- **监控数据增长：** 跟踪每个分区中随时间存储的数据量。
- **优化数据布局：** 利用分区信息高效管理和组织数据。

Refs 表存储 Iceberg 表使用的外部数据源的引用。这可以包括导入到 Iceberg 表中的 Avro 或 ORC 文件等内容。Refs 表允许您：

- **追踪外部来源：** 识别 Iceberg 表所依赖的外部数据源。
- **管理数据依赖：** 了解 Iceberg 表如何与其他数据源交互。
- **维护数据血缘：** 将数据的起源追溯到其原始来源。

通过理解和利用这些元数据表，您可以有效管理 Iceberg 表，确保数据完整性，深入了解数据历史，并优化查询以获得最佳性能。

### 分支与标签

在 Iceberg 中，分支（Branch）和标签（Tag）在管理表快照和数据版本控制方面起着关键作用。分支和标签可用于处理 GDPR 需求以及保留重要的历史快照以供审计。

#### 分支

**定义：** Iceberg 中的分支是指向表快照的命名指针。每个分支代表表快照的传承，使用户能够创建隔离和版本化的数据视图。

**用例：**

- **数据实验：** 开发者和数据科学家可以创建分支来实验数据转换、分析或测试，而不影响主表。
- **回滚与恢复：** 在出现错误或不希望更改的情况下，分支允许通过将指针切换到较早的快照来轻松回滚。
- **并行开发：** 多个团队可以同时在不同的分支上工作，实现并行开发和测试工作流。

#### 标签

**定义：** Iceberg 中的标签是指向特定表快照的不可变标记。与分支不同，标签不创建更改的传承，而是提供对特定时间点的稳定引用。

**用例：**

- **数据发布：** 标签通过指向精确的快照来确保报告、分析或合规目的的引用数据一致。
- **版本追踪：** 标签有助于追踪和管理数据的特定版本，这对审计和历史分析至关重要。

### 时间旅行与 Apache Iceberg

Apache Iceberg 最令人着迷的功能之一是其穿越时间的能力，允许您访问数据的历史快照，仿佛它们就是现在一样。这使您能够：

- **审计数据修改：** 调查对数据所做的任何修改，精确定位谁在何时更改了什么。
- **回滚意外更改：** 通过回滚到先前的快照来撤销意外的修改。
- **分析历史趋势：** 深入了解数据如何随时间演变，揭示有价值的模式和洞察。

**它是如何工作的？** Iceberg 精心跟踪对数据的每一次更新，在特定时间点创建快照。这些快照捕获该时刻的数据状态，包括所有行、列和 Schema 定义。要开始您的时间旅行旅程，只需在查询中指定所需的快照名称。

**示例：**

假设您有一个名为 `sales_data` 的 Iceberg 表，包含每日销售数据。周五的一个关键更新意外删除了几条记录。想要在不丢失数据的情况下分析周四的销售数据？使用以下查询：

```sql
SELECT * FROM sales_data AS OF SNAPSHOT '2024-01-12';
```

此查询指示 Iceberg 访问名为 `2024-01-12` 的快照，有效地将时间倒回到周四删除之前。您的分析现在将反映当天准确的销售数据。

Iceberg 中的时间旅行不仅是理论上的；它是一种实用工具，使您能够自信地管理数据，穿越修订版本，并获得更深层的历史洞察。因此，深入研究过去，探索数据的不同版本，用 Apache Iceberg 重写您自己的数据分析历史！

### Apache Iceberg 中的 Schema 演进

在动态的数据世界中，适应能力至关重要。Apache Iceberg 使您能够无缝演进数据模型，而不会中断现有查询或需要全表重写——这一特性被称为 Schema 演进。

**关键概念：**

- **Schema 不是强制的：** Iceberg 不对数据文件执行严格的 Schema。它在查询执行期间动态读取 Schema 信息，允许灵活性。
- **元数据追踪：** Schema 更改在 Iceberg 的元数据中进行跟踪，确保跨不同快照和查询会话的一致性。
- **向后兼容性：** 针对旧 Schema 编写的查询即使在 Schema 修改后也能继续正确工作，保持连续性。

**支持的操作：**

- **添加列（Adding Columns）：** 在不影响现有数据或查询的情况下向表添加新列。
- **移除列（Removing Columns）：** 删除未使用的列以简化数据模型。
- **重命名列（Renaming Columns）：** 更新列名称以提高清晰度或一致性。
- **更改数据类型（Changing Data Types）：** 调整数据类型以适应不断演进的数据需求。
- **修改结构体（Struct Modifications）：** 修改列内的嵌套结构以获得更大的灵活性。

Apache Iceberg 中有更多的功能，新功能正在积极开发中。因此，关注开源 Apache Iceberg 社区以了解 Iceberg 的最新发展是一个非常好的实践。

## 要点

**文件格式对决：**

- **ORC：** 高效的列式格式，提供良好的压缩和谓词下推功能，用于高效过滤。非常适合频繁查询的大型数据集。
- **Parquet：** 灵活的格式，支持嵌套数据结构和 Schema 演进。非常适合复杂数据分析和与各种工具的互操作。
- **Avro：** 类似 JSON 的格式，提供 Schema 灵活性和语言中立性。适合数据交换和与多样化生态系统的集成。

**压缩魔法：**

- **Snappy：** 快速且轻量级的压缩，适合较小的数据集和实时处理。
- **Gzip：** 强大的压缩但速度较慢，最大化存储节省。适合归档或离线分析。
- **zstd：** 高压缩比且速度快，在压缩率和速度之间提供良好平衡。

**表格式：从混沌到有序：**

- 使用像 Iceberg 这样的表格式将数据组织为逻辑单元。
- 实现超越单个文件的高效查询、分区和数据管理。

**Iceberg 强力玩法：**

- **ACID 事务：** 即使在并发写入和更新的情况下也能确保数据一致性，对可靠分析至关重要。
- **时间旅行：** 重新访问数据的过去版本，分析历史趋势，回滚错误。
- **Schema 演进：** 无缝适应数据模型，不中断现有查询。
