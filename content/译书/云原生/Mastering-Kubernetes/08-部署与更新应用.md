# 部署与更新应用

在本章中，我们将探讨Kubernetes提供的自动Pod伸缩能力，它如何影响滚动更新，以及如何与配额交互。我们将触及配置管理这个重要话题，以及如何选择和管理集群规模。最后，我们将探讨CI/CD流水线和基础设施配置。以下是我们将涵盖的主要内容：

- 实时集群更新
- 水平Pod自动伸缩
- 在自动伸缩下执行滚动更新
- 使用配额和限制处理稀缺资源
- 持续集成与部署
- 使用Terraform、Pulumi、自定义Operator和Crossplane配置基础设施

通过本章的学习，你将能够规划大规模集群，经济高效地进行配置，并在性能、成本和可用性之间做出明智的权衡。你还将了解如何设置水平Pod自动伸缩，以及如何智能地使用资源配额，让Kubernetes自动处理间歇性的负载波动，并安全地将软件部署到你的集群中。

## 实时集群更新

运行Kubernetes集群最复杂和风险最高的任务之一就是实时升级。当系统中部分组件使用不同版本时，各部分之间的交互往往难以预测，但在许多情况下又必不可少。拥有大量用户的大型集群无法承受因维护而离线。应对复杂性的最佳方式是分而治之。微服务架构在这方面帮助很大。你永远不会一次性升级整个系统。你只需持续升级几组相关的微服务，如果API发生了变化，也要同时升级它们的客户端。一个设计良好的升级过程会保持向后兼容性，至少等到所有客户端都升级完毕，然后在几个版本之后弃用旧API。

### 滚动更新

滚动更新是指你将组件从当前版本逐步更新到下一个版本。这意味着你的集群将同时运行当前版本和新版本的组件。这里有两种情况需要考虑：

- 新组件向后兼容
- 新组件不向后兼容

如果新组件是向后兼容的，那么升级应该非常容易。在早期版本的Kubernetes中，你必须使用标签非常小心地管理滚动更新，并逐步更改旧版本和新版本的副本数量（尽管 `kubectl rolling-update` 为ReplicationController提供了一个便捷的快捷方式）。但是，Kubernetes 1.2 中引入的Deployment资源使这变得更容易，并支持ReplicaSet。它具有以下内置功能：

- 在服务端运行（如果你的机器断开连接，它仍会继续）
- 版本控制
- 多个并发推出
- 更新部署
- 聚合所有Pod的状态
- 回滚
- 金丝雀部署
- 多种升级策略（滚动升级是默认策略）

以下是一个部署三个Nginx Pod的Deployment清单示例：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
  labels:
    app: nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.7.9
        ports:
        - containerPort: 80
```

资源类型为 `Deployment`，名称为 `nginx-deployment`，你可以用此名称引用此Deployment（例如，用于更新或回滚）。当然，最重要的部分是 `spec`，它包含一个Pod模板。`replicas` 决定了集群中将有多少个Pod，而模板规约包含了每个容器的配置。在这个例子中，只有一个容器。

要启动滚动更新，创建Deployment资源并检查它是否成功推出：

```bash
$ k create -f nginx-deployment.yaml
deployment.apps/nginx-deployment created
$ k rollout status deployment/nginx-deployment
deployment "nginx-deployment" successfully rolled out
```

Deployment具有更新策略，默认为 `rollingUpdate`：

```bash
$ k get deployment nginx-deployment -o yaml | grep strategy -A 4
strategy:
  rollingUpdate:
    maxSurge: 25%
    maxUnavailable: 25%
  type: RollingUpdate
```

### 复杂部署

当你只想升级一个Pod时，Deployment资源非常棒，但你经常需要升级多个Pod，而这些Pod有时存在版本间的相互依赖关系。在这些情况下，你有时必须放弃滚动更新，或者引入一个临时的兼容层。

例如，假设服务A依赖于服务B。服务B现在有了一个破坏性变更。服务A的v1 Pod无法与服务B的v2 Pod互操作。从可靠性和变更管理的角度来看，让服务B的v2 Pod同时支持旧API和新API也是不可取的。在这种情况下，解决方案可能是引入一个适配器服务，该服务实现B服务的v1 API。这个服务将位于A和B之间，并在不同版本之间翻译请求和响应。

这增加了部署过程的复杂性，需要多个步骤，但好处是A和B服务本身保持简单。你可以在不兼容的版本之间执行滚动更新，一旦所有人都升级到v2（所有A Pod和所有B Pod），所有间接层就可以消失了。

但是，滚动更新并不总是答案。

### 蓝绿部署

滚动更新对于可用性很好，但有时管理适当的滚动更新所涉及的复杂性被认为过高，或者它会增加大量的工作量，从而推迟更重要的项目。在这些情况下，蓝绿升级提供了一个很好的替代方案。使用蓝绿发布，你准备一个完整的新版本生产环境副本。现在你有两个副本：旧的（蓝色）和新的（绿色）。哪个是蓝色、哪个是绿色并不重要。重要的是你有两个完全独立的生产环境。当前蓝色处于活跃状态，服务所有请求。你可以在绿色上运行所有测试。一旦你满意了，就切换开关，绿色变为活跃。如果出现问题，回滚也同样简单；只需从绿色切换回蓝色。

![蓝绿部署](ch08-fig02.png)

我之前完全忽略了存储和内存状态。这种即时切换假设蓝色和绿色仅由无状态组件组成，并共享一个共同的持久化层。

如果存在存储变更或对外部客户端可访问的API的破坏性变更，则需要采取额外的步骤。例如，如果蓝色和绿色有自己的存储，那么所有传入的请求可能需要同时发送到蓝色和绿色，而绿色在切换之前可能需要从蓝色摄取历史数据以保持同步。

### 金丝雀部署

蓝绿部署很棒。然而，有时需要更精细的方法。假设你负责一个拥有许多用户的大型分布式系统。开发人员计划部署一个新版本的服务。他们在测试和预发布环境中测试了新版本的服务。但是，生产环境太复杂，无法为测试目的进行一对一的复制。这意味着服务在生产环境中可能出现问题的风险。这就是金丝雀部署的用武之地。

基本思想是在生产环境中以有限的能力测试服务。这样，如果新版本有问题，只有一小部分用户或一小部分请求会受到影响。在Kubernetes中，这可以在Pod级别非常容易地实现。如果一个服务由10个Pod支持，而你向一个Pod部署新版本，那么只有10%的请求会由服务负载均衡器路由到金丝雀Pod，而90%的请求仍然由当前版本提供服务。

![金丝雀部署](ch08-fig03.png)

还有更复杂的方式可以使用服务网格将流量路由到金丝雀部署。我们将在第14章"利用服务网格"中探讨这一点。

我们已经讨论了执行实时集群更新的不同方式。现在让我们来解决管理数据契约变更这个难题。

### 管理数据契约变更

数据契约描述了数据的组织方式。它是结构元数据的一个统称。最常见的例子是关系数据库模式。其他例子包括网络负载、文件格式，甚至字符串参数或响应的内容。如果你有一个配置文件，那么这个配置文件既有文件格式（JSON、YAML、TOML、XML、INI或自定义格式），也有一些内部结构，描述了什么样的层级、键、值和数据类型是有效的。有时数据契约是显式的，有时是隐式的。无论哪种方式，你都需要小心管理，否则当读取、解析或验证的代码遇到不熟悉结构的数据时，你将得到运行时错误。

### 数据迁移

数据迁移是一件大事。如今，许多系统管理着以TB、PB甚至更多计量的惊人数据量。在可预见的未来，收集和管理的数据量将继续增长。数据收集的速度超过了硬件创新的速度。要点是，如果你有大量数据并需要迁移它，这可能需要一段时间。在我之前的一家公司，我负责监督一个项目，将接近100TB的数据从一个遗留系统的Cassandra集群迁移到另一个Cassandra集群。

第二个Cassandra集群有不同的模式，并且被一个Kubernetes集群全天候访问。这个项目非常复杂，因此当紧急问题出现时，它不断被推迟。在原始估计之后很久，遗留系统仍然与下一代系统并存。

有很多机制来分割数据并将其发送到两个集群，但后来我们遇到了新系统的可伸缩性问题，在继续之前我们必须解决这些问题。历史数据很重要，但不需要以与近期热数据相同的服务水平来访问。因此，我们开始了另一个项目，将历史数据发送到更便宜的存储。当然，这意味着客户端库或前端服务必须知道如何查询两个存储并合并结果。当你处理大量数据时，你不能对任何事情想当然。你会遇到工具、基础设施、第三方依赖和流程方面的可伸缩性问题。大规模不仅是量的变化，通常也是质的变化。不要指望它会顺利进行。这远不止是将一些文件从A复制到B。

### 弃用API

API弃用有两种形式：内部和外部。内部API是由你和你的团队或组织完全控制的组件使用的API。你可以确保所有API用户将在短时间内升级到新API。外部API由你直接影响范围之外的用户或服务使用。

在一些灰色地带的情况下，你在一个庞大的组织（比如Google）中工作，即使是内部API也可能需要当作外部API来对待。如果你幸运的话，你所有的外部API都由自更新应用程序或通过你控制的Web界面使用。在这些情况下，API实际上是隐藏的，你甚至不需要发布它。

如果你有很多用户（或几个非常重要的用户）使用你的API，你应该非常谨慎地考虑弃用。弃用一个API意味着你迫使你的用户更改他们的应用程序以与你配合，或者停留在早期版本上。

有几种方法可以减轻这种痛苦：

- **不要弃用**。扩展现有API或保持前一个API活跃。虽然这增加了测试负担，但有时非常简单。
- **为目标受众提供所有相关编程语言的客户端库**。这始终是良好的实践。它允许你对底层API进行许多更改而不会干扰用户（只要你保持编程语言接口的稳定）。
- **如果你必须弃用**，请解释原因，允许用户有充足的时间升级，并提供尽可能多的支持（例如，带示例的升级指南）。你的用户会感激的。

我们涵盖了部署和升级工作负载的不同方式，并讨论了如何管理数据迁移和弃用API。现在让我们来看看Kubernetes的另一个重要功能——水平Pod自动伸缩——它允许我们的工作负载高效地处理不同量的请求，并动态调整用于处理这些请求的Pod数量。

## 水平Pod自动伸缩

Kubernetes可以监控你的Pod，并在CPU利用率、内存或其他指标超过阈值时进行伸缩。自动伸缩资源指定了详细信息（CPU百分比和检查频率），对应的自动伸缩控制器在需要时调整副本数量。

下图展示了不同的参与者及其关系：

![水平Pod自动伸缩](ch08-fig04.png)

如你所见，水平Pod自动伸缩器不直接创建或销毁Pod。它调整Deployment或StatefulSet资源中的副本数量，其对应的控制器负责实际创建和销毁Pod。这非常智能，因为你不需要处理自动伸缩与这些控制器正常操作冲突的情况——这些控制器对自动伸缩器的操作毫不知情。

自动伸缩器自动完成了我们之前必须手动做的事情。没有自动伸缩器，如果我们有一个副本数设置为3的Deployment，但我们根据平均CPU利用率确定实际上需要4个，那么我们必须将Deployment从3更新到4，并在所有Pod中手动持续监控CPU利用率。而现在，自动伸缩器会为我们做这些。

### 创建水平Pod自动伸缩器

要声明一个水平Pod自动伸缩器，我们需要一个工作负载资源（Deployment或StatefulSet）和一个 `HorizontalPodAutoscaler` 资源。以下是一个配置了维护3个Nginx Pod的简单Deployment：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      run: nginx
  template:
    metadata:
      labels:
        run: nginx
    spec:
      containers:
      - name: nginx
        image: nginx
        resources:
          requests:
            cpu: 400m
        ports:
        - containerPort: 80
```

```bash
$ k apply -f nginx-deployment.yaml
deployment.apps/nginx created
```

注意，为了参与自动伸缩，容器必须请求特定数量的CPU。

水平Pod自动伸缩器在 `scaleTargetRef` 中引用Nginx Deployment：

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: nginx
spec:
  maxReplicas: 4
  minReplicas: 2
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: nginx
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 90
```

```bash
$ k apply -f nginx-hpa.yaml
horizontalpodautoscaler.autoscaling/nginx created
```

`minReplicas` 和 `maxReplicas` 指定了伸缩的范围。这是为了避免由于某些问题可能导致的失控情况。想象一下，由于某个Bug，无论实际负载如何，每个Pod立即使用了100%的CPU。如果没有 `maxReplicas` 限制，Kubernetes将不断创建越来越多的Pod，直到所有集群资源耗尽。如果我们在具有VM自动伸缩的云环境中运行，将会产生巨大的成本。这个问题的另一方面是，如果没有 `minReplicas` 并且活动出现间歇，那么所有Pod都可能被终止，当新请求到来时，必须创建和调度新的Pod，如果还需要配置新节点，并且Pod需要一些时间才能就绪，这可能需要几分钟时间。如果存在"开-关"的活动模式，这个循环可能会重复多次。保持最小数量的副本运行可以平滑这一现象。在上面的例子中，`minReplicas` 设置为2，`maxReplicas` 设置为4。Kubernetes将确保始终有2到4个Nginx实例在运行。

目标CPU利用率百分比（TCUP）是一个需要理解的重要概念。你指定一个像80%这样的数字，但Kubernetes不会在阈值被跨越时立即开始伸缩。如果平均负载在TCUP附近徘徊，这可能导致持续的抖动。Kubernetes会在添加更多副本和移除副本之间频繁切换。这通常不是期望的行为。为了解决这个问题，你可以指定伸缩的延迟时间。

`kube-controller-manager` 有两个标志来支持这一点：

- `--horizontal-pod-autoscaler-downscale-delay`: 此选项需要一个持续时间值，确定自动伸缩器在当前缩减操作完成后、发起下一次缩减操作之前的等待时间。默认持续时间为5分钟（5m0s）。
- `--horizontal-pod-autoscaler-upscale-delay`: 此选项需要一个持续时间值，确定自动伸缩器在当前扩容操作完成后、发起下一次扩容操作之前的等待时间。默认持续时间为3分钟（3m0s）。

### 自定义指标

CPU利用率是衡量是否应该扩容承受过多请求的Pod、或缩减大多数空闲Pod的重要指标。但CPU并不是唯一——有时甚至不是最好的——需要跟踪的指标。内存可能是限制因素，甚至是更专业的指标，如并发线程数、Pod内部磁盘队列深度、请求的平均延迟或平均服务超时次数。

水平Pod自定义指标在1.2版本中作为alpha扩展添加。在1.6版本中升级为beta状态，在1.23版本中成为稳定版。你现在可以基于多个自定义指标对Pod进行自动伸缩。

自动伸缩器将评估所有指标，并基于所需的最大副本数进行自动伸缩，从而尊重所有指标的要求。

使用自定义指标的HPA在启动集群时需要一些配置。首先，你需要启用API聚合层。然后，你需要注册资源指标API和自定义指标API。这并不简单。这时候就要用到Keda了。

### Keda

Keda 代表 Kubernetes Event-Driven Autoscaling（Kubernetes事件驱动自动伸缩）。这是一个令人印象深刻的项目，它将实现水平Pod自动伸缩自定义指标所需的一切打包在一起。通常，你想要伸缩Deployment、StatefulSet或Job，但Keda也可以伸缩CRD，只要它们具有 `/scale` 子资源。Keda作为operator部署，它监视几个自定义资源：

- scaledobjects.keda.sh
- scaledjobs.keda.sh
- triggerauthentications.keda.sh
- clustertriggerauthentications.keda.sh

Keda还有一个metrics server，它支持大量的事件源和缩放器（scaler），并且可以从所有这些源收集指标来为伸缩过程提供信息。事件源包括所有流行的数据库、消息队列、云数据存储和各种监控API。例如，如果你依赖Prometheus获取指标，你可以使用Keda根据你推送到Prometheus的任何指标或指标组合来伸缩你的工作负载。

### 使用kubectl进行自动伸缩

kubectl可以使用标准的 `create` 命令接受配置文件来创建自动伸缩资源。但kubectl还有一个特殊的 `autoscale` 命令，让你可以在一条命令中轻松设置自动伸缩器，而无需特殊的配置文件。

首先，让我们启动一个Deployment，确保有三个简单Pod的副本，并且只运行一个无限bash循环：

```yaml
apiVersion: apps/v1

metadata:
  name: bash-loop
spec:
  replicas: 3
  selector:
    matchLabels:
      name: bash-loop
  template:
    metadata:
      labels:
        name: bash-loop
    spec:
      containers:
      - name: bash-loop
        image: g1g1/py-kube:0.3
        resources:
          requests:
            cpu: 100m
        command: ["/bin/bash", "-c", "while true; do sleep 10; done"]
```

```bash

```

```bash

bash-loop-8496f889f8-hcd2d     1/1     Running   0          105s
```


最初，Deployment设置为有三个副本，但自动伸缩器的最小值为四个Pod。这对Deployment有什么影响？现在期望的副本数是4。如果平均CPU利用率超过50%，它将增加到5甚至6，但永远不会低于4：



```bash
$ k get deploy bash-loop -o jsonpath='{.spec.replicas}'

```

## 在自动伸缩下执行滚动更新

滚动更新是管理大型集群中工作负载的基石。当你在由HPA控制的Deployment上执行滚动更新时，Deployment将使用新镜像创建一个新的ReplicaSet，并开始增加其副本数，同时减少旧ReplicaSet的副本数。同时，HPA可能会更改Deployment的总副本数。这不是问题。所有内容最终都会协调一致。

## 使用限制和配额处理稀缺资源

随着HPA动态创建Pod，我们需要考虑管理我们的资源。调度很容易失控，资源使用效率低下是一个真正的问题。有几个因素可能以微妙的方式相互影响：

- 整体集群容量
- 每节点的资源粒度
- 每个命名空间的工作负载划分
- DaemonSet
- StatefulSet
- 亲和性、反亲和性、污点和容忍度

首先，让我们理解核心问题。Kubernetes调度器在调度Pod时必须考虑所有这些因素。如果存在冲突或大量重叠的需求，那么Kubernetes可能难以找到空间来调度新的Pod。例如，一个非常极端但又简单的场景是：DaemonSet在每个节点上运行一个Pod，占用可用内存的50%。现在，Kubernetes无法调度任何需要超过50%内存的其他Pod，因为DaemonSet的Pod获得了优先级。即使你配置新节点，DaemonSet也会立即占用一半的内存。

StatefulSet与DaemonSet类似，它们需要新节点来扩展。触发向StatefulSet添加新成员的是数据增长，但其影响是从可用于Kubernetes调度其他工作负载的资源池中获取资源。在多租户情况下，吵闹的邻居问题可能在配置或资源分配的背景下显现。你可能会在你的命名空间中精确地规划不同Pod之间的配额及其资源需求，但你和来自其他命名空间的邻居共享实际节点，而这些邻居你可能甚至没有可见性。

大多数这些问题可以通过明智地使用命名空间资源配额以及在多种资源类型（如CPU、内存和存储）上仔细管理集群容量来缓解。此外，如果你控制节点配置，你可以通过给节点打污点来为你的工作负载划分专用节点。

但是，在大多数情况下，更健壮和动态的方法是利用集群自动伸缩器（Cluster Autoscaler），它可以在需要时（直到配额耗尽）为集群增加容量。

### 启用资源配额

大多数Kubernetes发行版默认支持ResourceQuota。API Server的 `--admission-control` 标志必须将 `ResourceQuota` 作为其参数之一。你还必须创建一个 `ResourceQuota` 对象来强制执行它。请注意，每个命名空间最多只能有一个 `ResourceQuota` 对象，以防止潜在的冲突。这是由Kubernetes强制执行的。

### 资源配额类型

我们可以管理和控制不同类型的配额。类别包括计算资源、存储资源和对象资源。

### 计算资源配额

计算资源是CPU和内存。对于每种资源，你可以指定一个限制或请求一定数量。以下是与计算相关的字段列表。注意，`requests.cpu` 可以简写为 `cpu`，`requests.memory` 可以简写为 `memory`：

- `limits.cpu`：所有非终止状态的Pod的CPU限制总和不能超过此值。
- `limits.memory`：所有非终止状态的Pod的内存限制总和不能超过此值。
- `requests.cpu`：所有非终止状态的Pod的CPU请求总和不能超过此值。
- `requests.memory`：所有非终止状态的Pod的内存请求总和不能超过此值。
- `hugepages-<size>`：指定大小的HugePage请求的最大允许数量，所有非终止状态的Pod不得超过此值。

自Kubernetes 1.10起，你还可以指定扩展资源（如GPU资源）的配额。例如：
```yaml
requests.nvidia.com/gpu: 10
```

### 存储资源配额

存储资源配额类型稍微复杂一些。每个命名空间可以限制两个实体：存储总量和PersistentVolumeClaim的数量。然而，除了全局设置总存储或PVC总数的配额外，你还可以按存储类进行限制。存储类资源配额的表示法稍微冗长，但能完成任务：

- `requests.storage`：所有PersistentVolumeClaim的请求存储总量
- `persistentvolumeclaims`：命名空间中允许的PersistentVolumeClaim的最大数量
- `<storage-class-name>.storageclass.storage.k8s.io/requests.storage`：与指定存储类关联的所有PersistentVolumeClaim的请求存储总量
- `<storage-class-name>.storageclass.storage.k8s.io/persistentvolumeclaims`：命名空间中允许的与指定存储类关联的PersistentVolumeClaim的最大数量

Kubernetes 1.8还添加了对临时存储配额的alpha支持：

- `requests.ephemeral-storage`：命名空间中所有Pod的临时存储请求总量
- `limits.ephemeral-storage`：命名空间中所有Pod的临时存储限制总量

配置存储的一个问题是，磁盘容量不是唯一的因素。磁盘I/O也是一个重要资源。例如，考虑一个不断更新同一个小文件的Pod。它不会使用大量容量，但会执行大量I/O操作。

### 对象数量配额

Kubernetes有另一类资源配额，即API对象。我的猜测是，目标是为了保护Kubernetes API Server免于管理太多对象。记住，Kubernetes在底层做了很多工作。它通常需要查询多个对象来认证、授权和确保操作不违反任何可能存在的策略。

一个简单的例子是基于ReplicationController的Pod调度。想象一下，你有一百万个ReplicaSet对象。可能你只有三个Pod，而大多数ReplicaSet有零个副本。尽管如此，Kubernetes将花费所有时间来验证确实那一百万个ReplicaSet没有其Pod模板的副本，并且它们不需要杀死任何Pod。这是一个极端的例子，但这个概念是适用的。拥有太多API对象意味着Kubernetes需要做大量工作。

此外，客户端（如kubectl本身）使用发现缓存也是一个问题。参见这个issue：https://github.com/kubernetes/kubectl/issues/1126。

自Kubernetes 1.9起，你可以限制任何命名空间资源的数量（在此之前，可以限制的对象覆盖范围有些不完整）。语法很有趣：`count/<resource type>.<group>`。通常在YAML文件和kubectl中，你先按组标识对象，如 `<group>/<resource type>`。

以下是一些你可能想要限制的对象（注意，Deployment可以在两个不同的API组中被限制）：

- count/configmaps
- count/deployments.apps
- count/deployments.extensions
- count/persistentvolumeclaims
- count/replicasets.apps
- count/replicationcontrollers
- count/secrets
- count/services
- count/statefulsets.apps
- count/jobs.batch
- count/cronjobs.batch

自Kubernetes 1.5起，你也可以限制自定义资源的数量。注意，虽然自定义资源定义是集群范围的，但这允许你在每个命名空间中限制实际的自定义资源数量。例如：

- count/awesome.custom.resource

最明显的遗漏是命名空间本身。命名空间的数量没有限制。由于所有限制都是按命名空间进行的，你可以通过创建太多命名空间来轻易压垮Kubernetes，即使每个命名空间只有少量API对象。但是，创建命名空间的能力应该只保留给集群管理员，他们不需要资源配额来约束自己。

### 配额作用域

某些资源（如Pod）可能处于不同状态，为这些不同状态设置不同的配额是很有用的。例如，如果有很多正在终止的Pod（这在滚动更新期间经常发生），那么即使总数超过配额，创建更多Pod也可以。这可以通过仅将Pod对象计数配额应用于非终止Pod来实现。以下是现有的作用域：

- **Terminating**：选择 `activeDeadlineSeconds` 的值大于或等于0的Pod。
- **NotTerminating**：选择未指定 `activeDeadlineSeconds`（nil）的Pod。
- **BestEffort**：选择具有尽力而为服务质量的Pod，即未指定资源请求和限制的Pod。
- **NotBestEffort**：选择不具有尽力而为服务质量的Pod，即指定了资源请求和限制的Pod。
- **PriorityClass**：选择定义了优先级类的Pod。
- **CrossNamespacePodAffinity**：选择具有跨命名空间亲和性或反亲和性条件的Pod进行调度。

虽然 `BestEffort` 作用域仅适用于Pod，但 `Terminating`、`NotTerminating` 和 `NotBestEffort` 作用域也适用于CPU和内存。这很有趣，因为资源配额限制可能会阻止Pod终止。以下是支持的对象：

- CPU
- Memory
- limits.cpu
- limits.memory
- requests.cpu
- requests.memory
- Pods

### 资源配额和优先级类

Kubernetes 1.9 引入了优先级类，作为在资源稀缺时优先调度Pod的一种方式。在Kubernetes 1.14中，优先级类成为稳定功能。然而，自Kubernetes 1.12起，资源配额支持每个优先级类的独立资源配额（beta 状态）。这意味着使用优先级类，你可以在非常精细的粒度上塑造你的资源配额，甚至在一个命名空间内也是如此。

更多详情请参见 https://kubernetes.io/docs/concepts/policy/resourcequotas/#resource-quota-per-priorityclass。

### 请求和限制

在资源配额的上下文中，请求和限制的含义是要求容器显式指定目标属性。这样，Kubernetes可以管理总配额，因为它确切地知道分配给每个容器的资源范围。

```bash
OldReplicaSets:  <none>
NewReplicaSet:   nginx-64f97b4d86 (0/3 replicas created)
Events:
  Type    Reason             Age   From                   Message
  ----    ------             ----  ----                   -------
  Normal  ScalingReplicaSet  65s   deployment-controller  Scaled up replica set nginx-64f97b4d86 to 3
```

在 `Conditions` 部分——`ReplicaFailure` 状态为 `True`，原因是 `FailedCreate`。你可以看到Deployment创建了一个名为 `nginx-64f97b4d86` 的新ReplicaSet，但它无法创建它应该创建的Pod。我们仍然不知道原因。

让我们检查ReplicaSet。我使用JSON输出格式（`-o json`）并通过管道传给 `jq`，以获得比kubectl原生支持的 `jsonpath` 输出格式更好的布局：

```bash
$ k get rs nginx-64f97b4d86 -o json | jq .status.conditions
[
  {
    "lastTransitionTime": "2022-07-31T20:49:24Z",
    "message": "pods \"nginx-64f97b4d86-ks7d6\" is forbidden: failed quota: compute-quota: must specify limits.cpu,limits.memory,requests.memory",
    "reason": "FailedCreate",
    "status": "True",
    "type": "ReplicaFailure"
  }
]
```

消息非常清晰。由于命名空间中存在计算配额，每个容器必须指定其CPU、内存请求和限制。配额控制器必须核算每个容器的计算资源使用情况，以确保整个命名空间的配额得到遵守。

好的。我们理解了问题，但如何解决呢？我们可以为要使用的每种Pod类型创建一个专用的Deployment对象，并仔细设置CPU和内存请求及限制。

例如，我们可以定义带资源声明的Nginx Deployment。由于资源配额指定了2个Pod的硬限制，让我们也将副本数从3减少到2：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx
spec:
  replicas: 2
  selector:
    matchLabels:
      run: nginx
  template:
    metadata:
      labels:
        run: nginx
    spec:
      containers:
      - name: nginx
        image: nginx
        resources:
          requests:
            cpu: 400m
            memory: 60Mi
          limits:
            cpu: 400m
            memory: 60Mi
        ports:
        - containerPort: 80
```

让我们创建它并检查Pod：

```bash
$ k apply -f nginx-deployment-with-resources.yaml
deployment.apps/nginx created
$ k get po
NAME                    READY   STATUS    RESTARTS   AGE
nginx-5d68f45c5f-6h9w9  1/1     Running   0          21s
nginx-5d68f45c5f-b8htm  1/1     Running   0          21s
```

是的，成功了！然而，为每种Pod类型指定限制和资源可能会很繁琐。有没有更简单或更好的方法？

### 使用LimitRange设置默认计算配额

更好的方法是指定默认计算限制。这就引入了LimitRange。以下是一个为容器设置一些默认值的配置文件：

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: limits
spec:
  limits:
  - default:
      cpu: 400m
      memory: 50Mi
    defaultRequest:
      cpu: 400m
      memory: 50Mi
    type: Container
```

让我们创建它并观察默认限制：

```bash
$ k apply -f limits.yaml
limitrange/limits created
$ k describe limits
Name:       limits
Namespace:  ns
Type        Resource  Min  Max  Default Request  Default Limit  Max Limit/Request
----        --------  ---  ---  ---------------  -------------  -----------------
Container   cpu       -    -    400m             400m           -
Container   memory    -    -    50Mi             50Mi           -
```

为了测试它，让我们删除当前带显式限制的Nginx Deployment，并重新部署原始的Nginx：

```bash
$ k delete deployment nginx
deployment.apps "nginx" deleted
$ k apply -f nginx-deployment.yaml
deployment.apps/nginx created
$ k get deployment
NAME    READY   UP-TO-DATE   AVAILABLE   AGE
nginx   2/3     2            2           16s
```

如你所见，只有3个Pod中的2个就绪了。发生了什么？默认限制生效了，但如果你还记得，计算配额对命名空间有2个Pod的硬限制。无法用 `LimitRange` 对象来覆盖它，所以Deployment只能创建两个Nginx Pod。根据当前配置，这正是期望的结果。如果Deployment确实需要3个Pod，那么应该更新命名空间的计算配额以允许3个Pod。

至此，我们关于使用请求、限制和配额进行资源管理的讨论到此结束。下一节探讨如何在Kubernetes上大规模自动化部署和配置多个工作负载。

## 持续集成与部署

Kubernetes是运行基于微服务的应用的优秀平台。但归根结底，它是一个实现细节。用户，通常也包括大多数开发人员，可能不知道系统部署在Kubernetes上。但Kubernetes可以改变游戏规则，使以前过于困难的事情成为可能。

在本节中，我们将探讨CI/CD流水线以及Kubernetes带来的优势。在本节结束时，你将能够设计利用Kubernetes特性（如易于伸缩和开发-生产一致性）的CI/CD流水线，以提高日常开发和部署的生产力和健壮性。

### 什么是CI/CD流水线？

CI/CD流水线是一组工具和步骤的集合，它获取开发人员或运维人员对系统代码、数据或配置的修改，进行测试，然后将其部署到生产环境（以及可能其他环境）。有些流水线是完全自动化的，有些是半自动化的，包含人工检查环节。在大型组织中，将变更自动部署到测试和预发布环境是常见的做法。发布到生产环境需要人工干预和审批。下图描绘了一个遵循这种实践的典型CI/CD流水线：

![CI/CD流水线](ch08-fig06.png)

值得一提的是，开发人员可以与生产基础设施完全隔离。他们的接口只是一个Git工作流，一个很好的例子是Deis Workflow（Kubernetes上的PaaS，类似于Heroku）。

### 为Kubernetes设计CI/CD流水线

当你的部署目标是Kubernetes集群时，你应该重新思考一些传统实践。首先，打包方式不同。你需要为容器构建镜像。通过使用智能标签，回滚代码变更变得超级容易和即时。这给了你很大的信心，即使一个不好的变更以某种方式通过了测试网络，你也能立即恢复到之前的版本。但你需要小心。模式更改和数据迁移在没有协调的情况下无法自动回滚。

Kubernetes的另一个独特能力是开发人员可以在本地运行整个集群。这在你设计集群时需要一些工作，但由于组成系统的微服务运行在容器中，而这些容器通过API进行交互，因此这是可能且可行的。一如既往，如果你的系统非常数据驱动，你需要适应这一点，并提供开发人员可以使用的数据快照和合成数据。此外，如果你的服务访问外部系统或云提供商服务，那么完全的本地集群可能不是理想的选择。

你的CI/CD流水线应该允许集群管理员快速调整配额和限制，以适应扩展和业务增长。此外，你应该能够轻松地将大部分工作负载部署到不同的环境中。例如，如果你的预发布环境与生产环境存在差异，就会降低对在预发布环境中运行良好的变更不会损害生产环境的信心。通过确保所有环境变更都通过CI/CD进行，可以使不同环境保持同步。

有许多商业CI/CD解决方案支持Kubernetes，但也有几个Kubernetes原生的解决方案，如Tekton、Argo CD、Flux CD和Jenkins X。

Kubernetes原生的CI/CD解决方案运行在你的集群内部，使用Kubernetes CRD进行定义，并使用容器来执行步骤。通过使用Kubernetes原生的CI/CD解决方案，你可以获得Kubernetes管理和轻松扩展CI/CD流水线的好处，而这通常是一个不小的任务。

## 为你的应用程序配置基础设施

CI/CD流水线用于在Kubernetes上部署工作负载。然而，这些服务通常需要你针对云资源、数据库甚至Kubernetes集群本身等基础设施进行操作。有不同的方式来配置这些基础设施。让我们回顾一些常见的解决方案。

### 云提供商API和工具

如果你完全致力于单一云提供商，并且没有计划使用多个云提供商或混合云集群与本地集群，你可能更倾向于使用云提供商的API工具（例如AWS CloudFormation）。这种方法有几个好处：

- 与你的云提供商基础设施深度集成
- 来自云提供商的最佳支持
- 无间接层

然而，这意味着你对系统的视图将被分割。一些信息将通过Kubernetes获得并存储在etcd中。其他信息将通过你的云提供商存储和访问。

缺乏Kubernetes原生的基础设施视图意味着可能难以运行本地集群，而集成其他云提供商或本地部署肯定需要大量工作。

### Terraform

HashiCorp的Terraform（https://terraform.io）是一种用于IaC（基础设施即代码）的工具。它是当前的市场领导者。你使用Terraform的HCL语言定义基础设施，并可以使用模块来结构化你的基础设施配置。它最初专注于AWS，但随着时间的推移，它成为了一种通用工具，用于在任何云上配置基础设施，以及通过提供商插件配置其他类型的基础设施。

查看Terraform注册中心中的所有可用提供商：https://registry.terraform.io/browse/providers。

由于Terraform声明式地定义基础设施，它自然支持GitOps生命周期，其中对基础设施的变更必须检入代码控制并可审查，并且历史被记录下来。

你通常通过其CLI与Terraform交互。你可以运行 `terraform plan` 命令查看Terraform将做出哪些更改，如果对结果满意，则通过 `terraform apply` 应用这些更改。

![Terraform工作流](images/ch08-fig07.png)

我曾在AWS、GCP和Azure上广泛使用Terraform来配置大规模系统的基础设施。它确实可以完成任务，但存在几个问题：

- 其管理状态可能与现实世界不同步
- 其设计和语言使其难以大规模使用
- 它无法自动检测和协调基础设施的外部变更

### Pulumi

Pulumi是一个更现代的IaC工具。从概念上讲，它与Terraform类似，但你可以使用多种编程语言来定义基础设施，而不是使用自定义DSL。这为你提供了像TypeScript、Python或Go这样的语言的完整生态系统，包括测试和打包来管理你的基础设施。

Pulumi还宣称拥有动态提供商，这些提供商在同一天更新以支持云提供商资源。它还可以封装Terraform提供商，以实现对基础设施需求的全面覆盖。

Pulumi编程模型基于堆栈、资源和输入/输出的概念：

![Pulumi编程模型](images/ch08-fig08.png)

以下是一个使用Pulumi在Python中配置EC2实例的简单示例：

```python
import pulumi
import pulumi_aws as aws

group = aws.ec2.SecurityGroup('web-sg',
    description='Enable HTTP access',
    ingress=[
        { 'protocol': 'tcp', 'from_port': 80, 'to_port': 80, 'cidr_blocks': ['0.0.0.0/0'] }
    ])

server = aws.ec2.Instance('web-server',
    ami='ami-6869aa05',
    instance_type='t2.micro',
    vpc_security_group_ids=[group.name]  # 引用上面的安全组资源
)

pulumi.export('public_ip', server.public_ip)
pulumi.export('public_dns', server.public_dns)
```

### 自定义Operator

Terraform和Pulumi都支持Kubernetes并且可以配置集群，但它们不是云原生的。它们也不允许动态协调，这违背了Kubernetes模型的理念。这意味着如果有人删除或修改了由Terraform或Pulumi配置的基础设施，直到你下次运行Terraform/Pulumi时才会被检测到。

编写自定义Kubernetes Operator可以给你完全的控制权。你可以暴露目标基础设施的任意多配置面，并可以强制实施规则和默认配置。

例如，在我目前所在的公司，我们曾经通过Terraform管理大量Cloudflare DNS域名。这导致了显著的性能问题，因为Terraform试图通过对任何基础设施变更（即使与Cloudflare无关）向Cloudflare发起API调用来刷新所有这些域名。我们决定编写一个自定义Kubernetes Operator来管理这些域名。该Operator定义了多个CRD来表示区域、域和记录，并通过Cloudflare的API与之交互。

除了完全控制权和性能优势之外，该Operator还自动协调任何外部变更，以避免意外的手动更改。

### 使用Crossplane

自定义Operator非常强大，但编写和维护一个Operator需要大量工作。Crossplane（https://crossplane.io）将自身定位为你的基础设施的控制平面。实际上，这意味着你通过CRD配置所有内容（提供商、证书、资源和复合资源）。像数据库连接信息这样的基础设施凭证被写入Kubernetes Secret，稍后可以由工作负载消费。Crossplane Operator监控所有定义基础设施的自定义资源，并与基础设施提供商进行协调。

以下是一个定义AWS RDS PostgreSQL实例的示例：

```yaml
apiVersion: database.example.org/v1alpha1
kind: PostgreSQLInstance
metadata:
  name: the-db
  namespace: data
spec:
  parameters:
    storageGB: 20
  compositionSelector:
    matchLabels:
      provider: aws
      vpc: default
  writeConnectionSecretToRef:
    name: db-conn
```

Crossplane使用自己的CLI扩展了kubectl，以提供构建、推送和安装包的支持。
