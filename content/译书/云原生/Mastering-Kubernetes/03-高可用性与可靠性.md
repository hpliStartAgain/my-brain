# 高可用性与可靠性

在第二章《创建 Kubernetes 集群》中，我们学习了如何在不同环境中创建 Kubernetes 集群，尝试了不同的工具，并创建了几个集群。创建 Kubernetes 集群仅仅是故事的开始。一旦集群启动并运行，你需要确保它保持可运行状态。

在本章中，我们将深入探讨高可用集群的主题。这是一个复杂的主题。Kubernetes 项目和社区尚未就实现高可用极致的唯一正确方式达成共识。高可用 Kubernetes 集群涉及许多方面，例如确保控制平面在面临故障时仍能持续运行、保护 etcd 中的集群状态、保护系统数据，以及快速恢复容量和/或性能。不同的系统会有不同的可靠性和可用性要求。如何设计和实现高可用 Kubernetes 集群将取决于这些要求。

本章将探讨以下主要主题：

- 高可用性概念
- 高可用性最佳实践
- 高可用性、可扩展性和容量规划
- 大规模集群性能、成本和设计权衡
- 选择和管理集群容量
- 突破 Kubernetes 的极限
- 大规模测试 Kubernetes

在本章结束时，你将理解与高可用性相关的各种概念，熟悉 Kubernetes 的高可用性最佳实践以及何时使用它们。你将能够使用不同的策略和技术升级在线集群，并能够根据性能、成本和可用性之间的权衡选择多种可能的解决方案。

## 高可用性概念

在本节中，我们将通过探索可靠和高可用系统的概念和构建块来开启高可用性之旅。核心问题是：我们如何用不可靠的组件构建可靠且高可用的系统？组件会失效，这一点你可以确信。硬件会故障，网络会故障，配置会出错，软件会有 bug，人会犯错误。接受这一点后，我们需要设计一个即使在组件故障时也能保持可靠和高可用的系统。思路是：从冗余开始，检测组件故障，并快速替换故障组件。

### 冗余

冗余是在硬件和软件层面上构建可靠和高可用系统的基础。如果一个关键组件发生故障，而你希望系统继续运行，那么你必须准备好另一个相同的组件。Kubernetes 本身通过 replication controller 和 replica set 来管理无状态 Pod。但是，你的 etcd 中的集群状态以及控制平面组件本身需要冗余，才能在部分组件故障时正常运作。在实践中，这意味着要在 3 个或更多节点上运行 etcd 和 API 服务器。

此外，如果你的有状态组件尚未由冗余持久化存储（例如在云平台上）备份，那么你需要添加冗余以防止数据丢失。

### 热插拔

热插拔是指在系统不停机的情况下即时替换故障组件的概念，对用户造成的中断最小化（理想情况下为零）。如果组件是无状态的（或其状态存储在独立的冗余存储中），那么热插拔一个新组件来替换它是很容易的，只需将所有客户端重定向到新组件即可。但是，如果它存储了本地状态，包括内存中的状态，那么热插拔就不简单了。主要有两种选择：

- 放弃正在进行的处理中的事务（客户端将重试）
- 保持一个热副本同步（主动-主动模式）

第一种解决方案要简单得多。大多数系统足够有弹性来应对故障。客户端可以重试失败的请求，热插拔后的组件将为它们服务。

第二种解决方案更加复杂和脆弱，并且会带来性能开销，因为每次交互都必须复制到两个副本（并确认）。对于系统的某些关键部分，这可能是必要的。

### 领导者选举

领导者选举是分布式系统中的一种常见模式。你通常有多个相同的组件协作并分担负载，但其中一个组件被选举为领导者，某些操作通过领导者串行化。你可以将具有领导者选举的分布式系统视为冗余和热插拔的组合。所有组件都是冗余的，当当前领导者发生故障或不可用时，新的领导者被选举出来并进行热插拔。

### 智能负载均衡

负载均衡是关于将工作负载分布到处理传入请求的多个副本上。这对于通过调整副本数量来应对高负载的扩缩容非常有用。当某些副本发生故障时，负载均衡器将停止向故障或不可达的组件发送请求。Kubernetes 将配置新的副本，恢复容量，并更新负载均衡器。Kubernetes 通过服务、端点、replica set、标签和 ingress controller 提供了出色的支持来实现这一点。

### 幂等性

许多类型的故障可能是暂时的。这在网络问题或过于严格的超时时最常见。如果某个组件对健康检查没有响应，它将被视为不可达，另一个组件将取代它。原本计划给被认为故障的组件的工作可能会被发送给另一个组件。但原始组件可能仍在工作并完成了相同的工作。最终结果是同一份工作可能被执行两次。避免这种情况非常困难。为了支持精确一次（exactly-once）语义，你需要在开销、性能、延迟和复杂性方面付出沉重的代价。因此，大多数系统选择支持至少一次（at-least-once）语义，这意味着同一份工作可以被执行多次而不会违反系统的数据完整性。这种属性称为幂等性。幂等系统即使在某个操作被执行多次时也能保持其状态不变。

### 自愈

当动态系统中发生组件故障时，你通常希望系统能够自我修复。Kubernetes replica set 是自愈系统的绝佳例子。但故障远不止于 Pod。自愈始于问题的自动检测，然后是自动解决。配额和限制有助于建立制衡机制，确保自动化的自愈不会由于 bug 或 DDoS 攻击等情况而失控。自愈系统通过重试失败的操作来处理瞬时故障，并且只有在确定没有其他选择时才将故障升级。一些自愈系统有后备路径，包括在无法获得最新内容时提供缓存内容。自愈系统试图优雅地降级并继续工作，直到核心问题得到修复。

在本节中，我们考虑了创建可靠和高可用系统所涉及的各种概念。在下一节中，我们将应用这些概念并展示部署在 Kubernetes 集群上的系统的最佳实践。

## 高可用性最佳实践

构建可靠且高可用的分布式系统并非易事。在本节中，我们将介绍一些最佳实践，这些实践使基于 Kubernetes 的系统能够可靠运行并在面对各种故障类别时保持可用。我们还将深入探讨如何构建自己的高可用集群。然而，由于影响高可用集群的复杂性和大量因素，我们只提供指导。我们不会在此提供构建高可用集群的逐步说明。

请注意，只有非常特殊的情况下，你才应该自行构建高可用 Kubernetes 集群。有多种强大的工具（通常构建在 kubeadm 之上）提供了经过实战检验的方法来在控制平面层面创建高可用 Kubernetes 集群。你应该充分利用投入这些工具的所有工作和努力。特别是，云提供商提供了高可用的托管 Kubernetes 集群。

### 创建高可用集群

要创建高可用 Kubernetes 集群，控制平面组件必须是冗余的。这意味着 etcd 必须部署为集群（通常在三个或五个节点上），并且 Kubernetes API 服务器必须是冗余的。辅助集群管理服务（例如可观测性栈存储）也应该冗余部署。下图描绘了一个典型的可靠且高可用的 Kubernetes 集群，采用堆叠 etcd 拓扑。有多个负载均衡的控制平面节点，每个节点包含所有控制平面组件以及一个 etcd 组件：

自托管 Kubernetes 集群——其中控制平面组件作为 Pod 和 StatefulSet 部署在集群中——是通过将 Kubernetes 应用于 Kubernetes 本身来简化控制平面组件的鲁棒性、灾难恢复和自愈的绝佳方法。这意味着管理 Kubernetes 的某些组件本身也由 Kubernetes 管理。例如，如果一个 Kubernetes API 服务器节点宕机，其他 API 服务器 Pod 将检测到并配置一个新的 API 服务器。

### 使你的节点可靠

节点会故障，或者某些组件会故障，但许多故障是暂时的。基本保证是确保运行时引擎（Docker daemon、Containerd 或任何 CRI 实现）和 kubelet 在发生故障时自动重启。

如果你运行 CoreOS、现代的基于 Debian 的操作系统（包括 Ubuntu >= 16.04）或任何其他使用 systemd 作为 init 机制的操作系统，那么很容易将 Docker 和 kubelet 部署为自启动守护进程：

```bash
systemctl enable docker
systemctl enable kubelet
```

对于其他操作系统，Kubernetes 项目在其高可用性示例中选择了 monit 进程监视器，但你也可以使用任何你喜欢的进程监视器。主要要求是确保这两个关键组件在发生故障时能够无需外部干预地重启。

参见：https://monit-docs.web.cern.ch/base/kubernetes/

### 保护集群状态

Kubernetes 集群状态通常存储在 etcd 中（某些 Kubernetes 实现如 k3s 使用像 SQLite 这样的替代存储引擎）。etcd 集群被设计为超可靠且分布在多个节点上。通过确保在其中一个副本丢失且不可达时拥有集群状态的多个副本，利用这些能力来构建可靠且高可用的 Kubernetes 集群非常重要。

### 将 etcd 集群化

你的 etcd 集群应该至少有三个节点。如果你需要更高的可靠性和冗余性，可以有五个、七个或任何其他奇数个节点。节点数必须是奇数，以便在网络分区时获得明确的多数。

为了创建一个集群，etcd 节点需要能够发现彼此。有几种方法可以实现这一点，例如：

- 静态方式
- etcd 发现
- DNS 发现

CoreOS 的 etcd-operator 项目曾经是部署 etcd 集群的首选解决方案。不幸的是，该项目已被归档且不再积极开发。Kubeadm 使用静态方法来为 Kubernetes 配置 etcd 集群，所以如果你使用任何基于 kubeadm 的工具，那就没问题了。如果你想部署一个高可用 etcd 集群，我建议遵循官方文档：

https://github.com/etcd-io/etcd/blob/release-3.4/Documentation/op-guide/clustering.md

### 保护你的数据

保护集群状态和配置固然很好，但更重要的是保护你自己的数据。如果集群状态以某种方式损坏，你总是可以从头重建集群（尽管在重建期间集群将不可用）。但如果你的自有数据损坏或丢失，你就会陷入大麻烦。同样的规则适用；冗余为王。但 Kubernetes 集群状态非常动态，而你的许多数据可能不那么动态。例如，大量历史数据通常很重要，可以备份和恢复。实时数据可能会丢失，但整个系统可以恢复到较早的快照，仅遭受临时性损害。

你应该考虑使用 Velero 作为备份整个集群（包括你自己数据）的解决方案。Heptio（现为 VMware 的一部分）开发了 Velero，它是开源的，对于关键系统来说可能是救星。

在此查看：https://velero.io/

### 运行冗余的 API 服务器

API 服务器是无状态的，所有必要数据都从 etcd 集群即时获取。这意味着你可以轻松运行多个 API 服务器，而无需在它们之间进行协调。一旦你运行了多个 API 服务器，你可以在它们前面放置一个负载均衡器，使其对客户端透明。

### 在 Kubernetes 中运行领导者选举

某些控制平面组件，如调度器和 controller manager，不能同时运行多个活跃实例。这将变成混乱，因为多个调度器试图将同一个 Pod 调度到多个节点，或多次调度到同一个节点。可以运行多个配置为管理不同 Pod 的调度器。拥有高度可扩展的 Kubernetes 集群的正确方式是让这些组件以领导者选举模式运行。这意味着多个实例在运行，但一次只有一个处于活跃状态，如果它发生故障，另一个被选举为领导者并取代其位置。

Kubernetes 通过 `--leader-elect` 标志（默认为 True）支持这种模式。调度器和 controller manager 可以通过将各自的清单复制到 `/etc/kubernetes/manifests` 来作为 Pod 部署。

这是一个调度器清单的片段，展示了该标志的使用：

```yaml
command:
- /bin/sh
- -c
- /usr/local/bin/kube-scheduler --master=127.0.0.1:8080 --v=2 --leader-elect=true
1>>/var/log/kube-scheduler.log
2>&1
```

这是一个 controller manager 清单的片段，展示了该标志的使用：

```yaml
- command:
- /bin/sh
- -c
- /usr/local/bin/kube-controller-manager --master=127.0.0.1:8080 --clustername=e2e-test-bburns
--cluster-cidr=10.245.0.0/16 --allocate-node-cidrs=true --cloud-provider=gce
--service-account-private-key-file=/srv/kubernetes/server.key
--v=2 --leader-elect=true 1>>/var/log/kube-controller-manager.log 2>&1
image: gcr.io/google_containers/kube-controller-manager:fda24638d51a48baa13c353
37fcd4793
```

还有其他几个标志用于控制领导者选举。它们都有合理的默认值：

```
--leader-elect-lease-duration duration

默认值: 15s

--leader-elect-renew-deadline duration

默认值: 10s

--leader-elect-resource-lock endpoints

默认值: "endpoints" ("configmaps" 是另一个选项)

--leader-elect-retry-period duration

默认值: 2s
```

请注意，不可能像其他 Pod 那样让这些组件由 Kubernetes 自动重启，因为这些正是负责重启失败 Pod 的 Kubernetes 组件，所以如果它们自身失败，就无法重启自己。必须有一个已经准备好的替换组件在运行。

### 使你的预发布环境高可用

高可用性不是容易设置的。如果你费心设置高可用性，这意味着有一个业务案例需要一个高可用的系统。因此，你希望在部署到生产环境之前测试你的可靠且高可用的集群（除非你是 Netflix，你在生产环境中测试）。此外，对集群的任何更改理论上都可能在破坏高可用性的同时不影响其他集群功能。关键点是，就像其他任何东西一样，如果你不测试它，就假设它不工作。

我们已经确定你需要测试可靠性和高可用性。最好的方法是创建一个尽可能接近地复制生产环境的预发布环境。这可能会很昂贵。有几种方法可以管理成本：

- **临时高可用预发布环境**：仅为高可用测试期间创建一个大型高可用集群。
- **压缩时间**：提前创建有趣的事件流和场景，提供输入，并快速连续地模拟各种情况。
- **将高可用测试与性能和压力测试结合**：在性能和压力测试结束时，使系统过载，观察可靠性和高可用性配置如何处理负载。

实践混沌工程并有意在不同层面引发故障来验证系统能否处理这些故障模式，这也很重要。

### 测试高可用性

测试高可用性需要规划和深入理解你的系统。每个测试的目标是揭示系统设计和/或实现中的缺陷，并提供足够好的覆盖率，使得如果测试通过，你将确信系统行为符合预期。

在可靠性、自愈和高可用性领域，这意味着你需要找出破坏系统并观察其自我修复的方法。

这需要以下几个要素：

- 全面的可能故障列表（包括合理的组合）
- 对于每种可能的故障，应该清楚系统应如何响应
- 一种引发故障的方式
- 一种观察系统如何反应的方式

这些要素中没有一个是简单的。根据我的经验，最好的方法是增量地进行，并尝试提出相对少量的通用故障类别和通用响应，而不是一份详尽且不断变化的大量底层故障列表。

例如，一个通用的故障类别是节点无响应。通用的响应可能是重启节点，引发故障的方式可以是停止节点的虚拟机（如果是虚拟机），而观察应该是：当节点宕机时，系统仍然基于标准的验收测试正常运行；节点最终恢复，系统恢复正常。你可能还想测试许多其他事情，例如问题是否被记录、相关告警是否发送给了正确的人、以及各种统计数据和报告是否已更新。

但是，要警惕过度泛化。在通用无响应节点故障模式的情况下，一个关键组件是检测节点无响应。如果你的检测方法有问题，那么你的系统将无法正确反应。使用健康检查和就绪检查等最佳实践。

请注意，有时一个故障无法通过单个响应来解决。例如，在我们的无响应节点案例中，如果是硬件故障，那么重启将无济于事。在这种情况下，第二级响应开始发挥作用，可能会配置一个新节点来替换故障节点。在这种情况下，你不能太泛化，你可能需要为节点上的特定类型的 Pod/角色（etcd、master、worker、数据库和监控）创建测试。

如果你有高质量要求，请准备好花费比生产环境多得多的时间来设置适当的测试环境和测试。

最后一点至关重要：尽量做到非侵入性。这意味着，理想情况下，你的生产系统不会有允许关闭其部分功能的功能，或者被配置为以降低容量运行以进行测试。原因是这会增加系统的攻击面，并且可能由于配置错误而被意外触发。理想情况下，你可以在不修改将要部署到生产环境的代码或配置的情况下控制你的测试环境。使用 Kubernetes，通常很容易注入具有自定义测试功能的 Pod 和容器，这些 Pod 和容器可以在预发布环境中与系统组件交互，但永远不会部署到生产环境。

混沌工程 CNCF 孵化项目 Chaos Mesh 是一个很好的起点：https://chaos-mesh.org

在本节中，我们了解了实际拥有一个可靠且高可用的集群需要什么，包括 etcd、API 服务器、调度器和 controller manager。我们考虑了保护集群本身以及你的数据的最佳实践，并特别关注意了有关预发布环境和测试的问题。

## 高可用性、可扩展性和容量规划

高可用系统也必须是可扩展的。大多数复杂分布式系统的负载可能因一天中的时间、工作日与周末、季节性效应、营销活动和许多其他因素而剧烈变化。成功的系统会随着时间推移拥有更多用户并积累越来越多数据。这意味着集群的物理资源——主要是节点和存储——也必须随着时间推移而增长。如果你的集群配置不足，它将无法满足所有需求，并且由于请求超时或排队而无法快速处理，因此将不可用。

这就是容量规划的领域。一种简单的方法是过度配置你的集群。预测需求并确保你有足够的缓冲来应对活动高峰。但是，这种方法存在几个缺陷：

- 对于高度动态和复杂的分布式系统，即使近似预测需求也很困难。
- 过度配置成本高昂。你在很少或从未使用的资源上花费了大量金钱。
- 你必须定期重复整个过程，因为系统的平均负载和峰值负载会随时间变化。
- 你必须为多个使用特定资源的工作负载组执行整个过程（例如，使用高内存节点的工作负载和需要 GPU 的工作负载）。

更好的方法是使用基于意图的容量规划，其中使用高级抽象，系统相应地自我调整。在 Kubernetes 的背景下，有 Horizontal Pod Autoscaler（HPA），它可以根据需要增加或减少处理特定工作负载请求所需的 Pod 数量。但这仅适用于改变分配给不同工作负载的资源比例。当整个集群（或节点池）接近饱和时，你只需要更多资源。这时集群自动缩放器（Cluster Autoscaler）就发挥作用了。这是一个 Kubernetes 项目，从 Kubernetes 1.8 开始可用。它在云环境中特别有效，因为可以通过编程 API 配置额外的资源。

当集群自动缩放器（CAS）确定 Pod 无法被调度（处于待处理状态）时，它会为集群配置一个新节点。它也可以从集群中移除节点（缩容），如果它确定集群拥有处理负载所需的节点数过多。CAS 默认每 30 秒检查一次待处理的 Pod。它只在低使用率持续 10 分钟后才会移除节点，以避免抖动。

CAS 根据 CPU 和内存使用率做出缩容决策。如果节点上运行的所有 Pod 的 CPU 和内存请求总和小于节点可分配资源的 50%（默认值，可配置），则该节点将被考虑移除。所有 Pod（除 DaemonSet Pod 外）必须可移动（某些 Pod 由于调度约束或本地存储等因素无法移动），且该节点不能禁用缩容。

以下是一些需要考虑的问题：

- 即使总 CPU 或内存利用率较低，由于亲和性、反亲和性、污点、容忍、Pod 优先级、每节点最大 Pod 数、每节点最大持久卷数和 Pod 中断预算等控制机制，集群可能仍需要更多节点。
- 除了触发节点扩缩容的内置延迟外，从云提供商配置新节点还有额外的几分钟延迟。
- 某些节点（例如具有本地存储的节点）默认情况下无法移除（需要特殊注解）。
- HPA 和 CAS 之间的交互可能很微妙。

HPA 和 CAS 的组合提供了一个真正弹性的集群，其中 HPA 确保服务使用适当数量的 Pod 来处理每个服务的负载，而 CAS 确保节点数量与集群上的整体负载相匹配。

### 考虑垂直 Pod 自动缩放器

垂直 Pod 自动缩放器是另一种作用于 Pod 的自动缩放器。它的工作是基于实际使用情况调整 Pod 的 CPU 和内存请求与限制。它通过每个工作负载的 CRD 进行配置，并包含三个组件：

- **Recommender（推荐器）** - 监视 CPU 和内存使用情况，并为 CPU 和内存请求提供新的推荐值
- **Updater（更新器）** - 杀死那些 CPU 和内存请求与推荐器提出的建议不匹配的受管 Pod
- **Admission control webhook（准入控制 webhook）** - 根据推荐为新创建或重新创建的 Pod 设置 CPU 和内存请求

VPA 可以仅运行在推荐模式下，或主动调整 Pod 大小。当 VPA 决定调整 Pod 大小时，它会驱逐该 Pod。当 Pod 被重新调度时，它会根据最新推荐修改请求和限制。

以下是一个在推荐模式下为名为 awesome-deployment 的 Deployment 定义 VPA 自定义资源的示例：

```yaml
apiVersion: autoscaling.k8s.io/v1beta2
kind: VerticalPodAutoscaler
metadata:
  name: awesome-deployment
spec:
  targetRef:
    apiVersion: "apps/v1"
    kind: Deployment
    name: awesome-deployment
  updatePolicy:
    updateMode: "Off"
```

以下是使用 VPA 的一些主要要求和限制：

- 需要 metrics server
- 无法将内存设置为小于 250Mi
- 无法更新正在运行的 Pod（因此 updater 会杀死 Pod 以使用正确的请求重新启动它们）
- 无法驱逐不受 controller 管理的 Pod
- 不推荐将 VPA 与 HPA 一起运行

### 基于自定义指标自动缩放

HPA 默认基于 CPU 和内存指标运行。但可以配置为基于任意自定义指标运行，例如队列深度（如 AWS SQS 队列）或线程数，这些可能成为由于并发性导致的瓶颈，即使 CPU 和内存仍然可用。Keda 项目（https://keda.sh/）为自定义指标提供了一个强大的解决方案，而不是从头开始。他们使用基于事件的自动缩放概念作为泛化。

## 大型集群的性能、成本和设计权衡

在上一节中，我们研究了配置和规划容量以及自动缩放集群和工作负载的各种方法。在本节中，我们将考虑大型集群的各种选项和配置，以及它们不同的可靠性和高可用性属性。在设计集群时，你需要了解你的选项并根据组织的需求明智地选择。

我们将涵盖的主题包括各种可用性要求，从尽力而为一直到零宕机的终极目标。最后，我们将确定在实用的站点可靠性工程方法上。对于每个可用性类别，我们将从性能和成本的角度考虑其含义。

### 可用性要求

不同的系统对可靠性和可用性有截然不同的要求。此外，不同的子系统也有截然不同的要求。例如，计费系统始终是高优先级的，因为如果计费系统宕机，你就无法赚钱。但是，即使是在计费系统中，如果争议费用功能有时不可用，从业务角度来看可能是可以接受的。

### 尽力而为

尽力而为意味着，反直觉的是，没有任何保证。如果它工作，很好！如果它不工作——那也没办法，你能怎么办呢？这种级别的可靠性和可用性可能适用于经常更改的内部组件，而使其鲁棒所需的精力不值得。只要调用不可靠服务的服务或客户端能够处理偶尔的错误或宕机，那么一切都没问题。它也适用于以 beta 版本发布的对外服务。

尽力而为对开发者来说很好。开发者可以快速行动并破坏事物。他们不必担心后果，也不必经过一系列严格的测试和审批。尽力而为服务的性能可能比更鲁棒的服务更好，因为尽力而为服务通常可以跳过昂贵的步骤，例如验证请求、持久化中间结果和复制数据。但另一方面，更鲁棒的服务通常经过高度优化，其支持性硬件针对其工作负载进行了微调。尽力而为服务的成本通常较低，因为它们不需要采用冗余，除非运维人员忽略了基本的容量规划而只是不必要地过度配置。

在 Kubernetes 的背景下，大问题是集群提供的所有服务是否都是尽力而为的。如果是这样，那么集群本身不必是高可用的。你可能只需要一个带有单个 etcd 实例的单个主节点，甚至可能不需要部署监控解决方案。这通常只适用于本地开发集群。即使是多个开发者使用的共享开发集群，也应该具有相当水平的可靠性和鲁棒性，否则每当集群意外宕机时，所有开发者都将无所事事。

### 维护窗口

在具有维护窗口的系统中，会安排专门的时间来执行各种维护活动，例如应用安全补丁、升级软件、清理日志文件和数据库清理。在维护窗口期间，系统（或子系统）变得不可用。这通常安排在非工作时间，并且通常会通知用户。维护窗口的好处是你不必担心你的维护操作会如何与进入系统的实时请求交互。它可以极大地简化运维。系统管理员和运维人员喜爱维护窗口，就像开发者喜爱尽力而为系统一样。

当然，缺点是系统在维护期间宕机。这可能只适用于用户活动限制在特定时间（例如美国办公时间或仅工作日）的系统。

使用 Kubernetes，你可以通过负载均衡器将所有传入请求重定向到一个通知用户维护窗口的网页（或 JSON 响应）来实现维护窗口。

但在大多数情况下，Kubernetes 的灵活性应该允许你进行在线维护。在极端情况下，例如升级 Kubernetes 版本，或从 etcd v2 切换到 etcd v3，你可能希望采用维护窗口。蓝绿部署是另一种替代方案。但是集群越大，蓝绿部署的开销也越大，因为你必须复制整个生产集群，这既昂贵又可能导致配额不足等问题。

### 快速恢复

快速恢复是高可用集群的另一个重要方面。某些事情迟早会出问题。你的不可用时间开始计时。你需要多久才能恢复正常？平均恢复时间（MTTR）是一个重要的衡量指标，需要跟踪并确保你的系统能够充分应对灾难。

有时这并不取决于你。例如，如果你的云提供商出现宕机（并且你没有实现联邦集群，我们将在后面的第十一章《在多个集群上运行 Kubernetes》中讨论），那么你只能坐着等待他们解决问题。但最可能的罪魁祸首是最近部署的问题。当然，还有与时间相关的问题，甚至与日历相关的问题。你还记得 2012 年 2 月 29 日那次导致 Microsoft Azure 宕机的闰年 bug 吗？

快速恢复的典范当然是蓝绿部署——如果你在发现问题时保持之前的版本运行。但通常这适用于在部署期间或部署后不久发现的问题。如果一个隐蔽的 bug 潜伏下来，直到部署后数小时才被发现，那么你可能已经拆除了你的蓝色部署，无法再回退。

另一方面，滚动更新意味着如果问题被发现得早，那么你的大多数 Pod 仍在运行之前的版本。

与数据相关的问题可能需要很长时间才能逆向恢复，即使你的备份是最新的并且恢复过程确实有效（一定要定期测试这一点）。

像 Velero 这样的工具可以在某些场景下提供帮助，它创建集群的快照备份，你可以在出现问题时直接恢复，而不必知道如何修复。

### 零宕机

最后，我们来到了零宕机系统。实际上并不存在真正零宕机的系统。所有系统都会故障，所有软件系统肯定会故障。系统的可靠性通常用"几个九"来衡量。参见：https://en.wikipedia.org/wiki/High_availability#%22Nines%22

有时故障严重到系统或其部分服务会宕机。将零宕机视为一种尽力而为的分布式系统设计。你为零宕机而设计，意味着你提供了大量冗余和机制来应对预期中的故障而不使系统宕机。一如既往地记住，即使有零宕机的业务案例，也不意味着每个组件都必须零宕机。可靠的（合理范围内的）系统可以由高度不可靠的组件构建而成。

零宕机的计划如下：

- **每个级别的冗余**：这是必要条件。你的设计中不能有单点故障，因为当它故障时，你的系统就宕机了。
- **故障组件的自动热插拔**：冗余只有在其冗余组件能够在原始组件故障后立即投入行动时才有价值。某些组件可以分担负载（例如，无状态 Web 服务器），因此不需要显式操作。在其他情况下，例如 Kubernetes 调度器和 controller manager，你需要建立领导者选举机制来确集群持续顺畅运行。
- **大量指标、监控和告警以尽早发现问题**：即使经过仔细设计，你也可能遗漏某些东西，或者某些隐含假设可能使你的设计失效。通常，这些微妙的问题会逐渐出现，通过足够的关注，你可以在它们发展成全面系统故障之前发现它们。例如，假设有一个机制可以在磁盘空间超过 90% 时清理旧日志文件，但由于某种原因它不工作了。如果你设置了磁盘空间超过 95% 时的告警，那么你就能捕获这个问题并防止系统故障。
- **部署到生产环境前的顽强测试**：全面的测试已被证明是提高质量的可靠方法。为像大型 Kubernetes 集群运行大规模分布式系统这样复杂的事物编写全面测试是项艰苦的工作，但你需要它。你应该测试什么？一切。没错。对于零宕机，你需要同时测试应用程序和基础设施。你的 100% 通过的单元测试是一个好的开始，但它们并不能给你太多信心，当你将应用程序部署到生产 Kubernetes 集群上时，它仍然能按预期运行。当然，最好的测试是在蓝绿部署或相同集群后的生产集群上进行。如果没有完全相同的集群，考虑尽可能忠实地模拟生产环境的预发布环境。以下是你应该运行的测试列表。每个测试都应该是全面的，因为如果你留下任何未测试的内容，它可能就出问题：

  - 单元测试
  - 验收测试
  - 性能测试
  - 压力测试
  - 回滚测试
  - 数据恢复测试
  - 渗透测试

- **保留原始数据**：对于许多系统来说，数据是最关键的资产。如果你保留原始数据，你可以从任何后来发生的数据损坏和处理后数据丢失中恢复。这对零宕机并不能真正起到帮助作用，因为重新处理原始数据可能需要时间，但它有助于实现零数据丢失，这通常更为重要。这种方法的缺点是原始数据通常比处理后数据大得多。一个好的选择可能是将原始数据存储在比处理后数据更便宜的存储中。
- **将感知在线时间作为最后手段**：好吧。系统的某部分宕机了。你可能仍然能够维持某种级别的服务。在许多情况下，你可能可以访问略微过时的数据版本，或者让用户访问系统的其他部分。这不是一个很好的用户体验，但从技术上讲，系统仍然可用。

这听起来疯狂吗？很好。零宕机的大规模系统很难（实际上是不可能的）。微软、谷歌、亚马逊、Facebook 和其他大公司有数万名软件工程师（合计）只是致力于基础设施、运维和确保一切正常运行，这是有原因的。

### 站点可靠性工程

SRE 是运维可靠分布式系统的现实方法。SRE 拥抱故障，并与服务级指标（SLI）、服务级目标（SLO）和服务级协议（SLA）一起工作。每个服务都有目标，例如 95% 的请求延迟低于 50 毫秒。如果某个服务违反了其目标，那么团队在回去开发新功能和能力之前会专注于修复问题。

SRE 的美妙之处在于你可以调整成本和性能的旋钮。如果你想在可靠性上投入更多，那么就要做好准备在资源和开发时间上付出代价。

### 性能与数据一致性

当你开发或运维分布式系统时，CAP 定理应该始终记在脑海中。CAP 代表一致性（Consistency）、可用性（Availability）和分区容错性（Partition Tolerance）：

- **一致性**意味着每次读取都能收到最新的写入或返回错误
- **可用性**意味着每个请求都会收到一个非错误的响应（但响应可能是过时的）
- **分区容错性**意味着即使网络中节点之间的任意数量的消息被丢弃或延迟，系统也能继续运行

该定理指出你最多只能同时拥有三者中的两个。由于任何分布式系统都可能遭受网络分区，在实践中你可以在 CP 或 AP 之间选择。CP 意味着为了保持一致性，系统在网络分区时将不可用。AP 意味着系统将始终可用但可能不一致。例如，来自不同分区的读取可能返回不同的结果，因为其中一个分区没有收到写入。

在本节中，我们专注于高可用系统，这意味着 AP。为了实现高可用性，我们必须牺牲一致性。但这并不意味着我们的系统会有损坏或任意数据。关键概念是最终一致性。我们的系统可能稍微落后一些，并提供对略微过时数据的访问，但最终你会得到你所期望的。

当你开始以最终一致性的方式思考时，它为潜在的重大性能改进打开了大门。例如，如果某个重要值被频繁更新（假设每秒更新一次），但你每分钟只发送一次它的值，那么你的网络流量减少了 60 倍，而平均仅落后实时更新 30 秒。这非常显著。这是巨大的。你刚刚使你的系统能够使用相同资源处理 60 倍的用户或请求。

正如我们之前讨论的，冗余是高可用系统的关键。然而，冗余和成本之间存在紧张关系。在下一节中，我们将讨论选择和管理集群容量。

## 选择和管理集群容量

借助 Kubernetes 的水平 Pod 自动缩放、DaemonSet、StatefulSet 和配额，我们可以缩放和控制 Pod、存储和其他对象。然而，最终我们受到 Kubernetes 集群可用物理（虚拟）资源的限制。如果你所有的节点都在 100% 容量下运行，你需要向集群添加更多节点。这是绕不过去的。Kubernetes 将无法扩展。另一方面，如果你有非常动态的工作负载，那么 Kubernetes 可以缩容你的 Pod，但如果你不相应缩容节点，你仍然需要为超额容量付费。在云环境中，你可以按需启停实例。将其与集群自动缩放器结合，可以自动解决计算容量问题。这是理论。在实践中，总有细微差别。

### 选择节点类型

最简单的解决方案是选择一种具有已知 CPU、内存和本地存储数量的单一节点类型。但这通常不是最高效且成本最优的解决方案。它使容量规划变得简单，因为唯一的问题是需要多少个节点。每当你添加一个节点，你向集群中添加了已知数量的 CPU 和内存，但大多数 Kubernetes 集群和集群内的组件处理的是不同的工作负载。我们可能有一个流处理管道，其中许多 Pod 接收一些数据并在一个地方处理它。

这种工作负载是 CPU 密集型的，可能不一定需要大量内存。某些组件，例如分布式内存缓存，需要大量内存但 CPU 需求很小。其他组件，例如 Cassandra 集群，需要每个节点附加多个 SSD 磁盘。机器学习工作负载可以从 GPU 中受益。此外，云提供商提供竞价实例——这些节点更便宜，但如果其他客户愿意支付常规价格，它们可能会被从你手中夺走。

在规模下，成本开始累积，你应该努力使工作负载与它们运行的节点配置对齐，这意味着使用具有不同节点（实例）类型的多个节点池。

对于每种节点类型，你应该分配适当的标签，并确保 Kubernetes 将设计在该节点类型上运行的 Pod 调度到该类节点上。

### 选择存储解决方案

存储是扩展集群的一个巨大因素。有三类可扩展存储解决方案：

- **自行构建**：你在 Kubernetes 集群中安装某种类型的存储解决方案。好处是灵活性和完全控制，但你必须自己管理和扩展它。
- **使用云平台存储解决方案**：你获得很多开箱即用的功能，但失去控制，通常支付更多费用，并且根据服务不同，你可能会被锁定在该提供商。
- **使用集群外解决方案**：数据传输的性能和成本可能会高得多。如果你需要与现有系统集成，通常使用此选项。

当然，大型集群可能有来自所有类别的多个数据存储。这是你必须做出的最关键决策之一，而且你的存储需求可能会随时间变化和演进。

### 权衡成本与响应时间

如果钱不是问题，你可以直接过度配置你的集群。每个节点都将具有可用的最佳硬件配置，你将拥有远远超出处理工作负载所需的节点数量，并且你将拥有大量的可用存储。但猜猜看？钱始终是个问题！

当你刚开始且集群没有处理大量流量时，过度配置也许可行。你可能只运行五个节点，即使大部分时间两个节点就足够了。然而，将所有东西乘以 1,000，如果你有数千台闲置机器和 PB 级的空存储，财务部门的人就会来找你问问题。

好吧。那么你仔细衡量和优化，实现了每个资源 99.99999% 的利用率。恭喜你，你刚刚创建了一个不能承受一丝额外负载或单个节点故障的系统——要么丢弃请求，要么延迟响应。

你需要找到中间立场。了解工作负载的典型波动，并考虑超额容量的成本/收益比，与降低响应时间或处理能力之间的权衡。

有时，如果你有严格的可用性和可靠性要求，你可以将冗余构建到系统中，然后有意地过度配置。例如，你希望能够热插拔故障组件而不产生宕机或明显的影响。也许你甚至连一笔交易都不能丢失。在这种情况下，你将拥有所有关键组件的在线备份，而且这些额外容量可以用来缓解临时波动而无需任何特殊操作。

### 有效地使用多种节点配置

有效的容量规划要求你了解系统的使用模式以及每个组件可以处理的负载。这可能涉及系统内部生成的大量数据流。当你通过指标对典型工作负载有了扎实的理解后，你可以查看工作流以及哪些组件处理哪些部分负载。然后你可以计算 Pod 的数量及其资源需求。根据我的经验，有些工作负载相对固定，有些工作负载可以预测地变化（例如办公时间与非办公时间），然后你还有那些完全疯狂、行为不稳定的工作负载。你必须为每种工作负载相应地进行规划，并且你可以设计几类节点配置，用于调度匹配特定工作负载的 Pod。

### 受益于弹性云资源

大多数云提供商允许你自动缩放实例，这是对 Kubernetes 水平 Pod 自动缩放的完美补充。如果你使用云存储，它也会神奇地增长，你无需做任何事。然而，有一些陷阱你需要注意。

#### 自动缩放实例

所有大型云提供商都有实例自动缩放功能。有一些差异，但基于 CPU 利用率的扩缩容始终可用，有时自定义指标也可用。有时还提供负载均衡。如你所见，这里与 Kubernetes 有一些重叠。

如果你的云提供商没有适当的自动缩放功能和适当的控制，并且不受集群自动缩放器支持，那么自行构建相对容易——你可以监控集群资源使用情况并调用云 API 来添加或移除实例。你可以从 Kubernetes 提取指标。下图展示了如何基于 CPU 负载监控添加两个新实例：

#### 注意云配额

使用云提供商时，最烦人的事情之一是配额。我曾与四家不同的云提供商（AWS、GCP、Azure 和阿里云）合作过，并总是在某个时候被配额所困扰。配额的存在是为了让云提供商能做他们自己的容量规划（也是为了保护你不会无意中启动 1,000,000 个实例而无法支付），但从你的角度来看，这又多了一个可能绊倒你的东西。想象一下，你设置了一个像魔法一样工作的漂亮自动缩放系统，突然系统在你达到 100 个节点时不再扩展。你很快发现你被限制在 100 个节点，于是你提交支持请求来增加配额。然而，配额请求必须由人审批，这可能需要一两天时间。在此期间，你的系统无法处理负载。

#### 谨慎管理区域

云平台按区域和可用区组织。在 GCP 和 Azure 等云提供商上，不同区域之间的成本差异可能高达 20%。在 AWS 上，可能更加极端（30%-70%）。某些服务和机器配置只在某些区域可用。

云配额也是按区域管理的。区域内数据传输的性能和成本远低于（通常是免费的）跨区域传输。在规划集群时，你应该仔细考虑你的地理分布策略。如果你需要跨多个区域运行工作负载，你可能在冗余、可用性、性能和成本方面需要做出一些艰难的决定。

### 考虑容器原生解决方案

容器原生解决方案是指你的云提供商提供一种方式，将容器直接部署到其基础设施中。你不需要配置实例，然后安装容器运行时（如 Docker daemon），然后才部署容器。相反，你只需提供容器，平台负责找机器来运行你的容器。你完全与实际运行容器的机器分离。

所有主要云提供商现在都提供了完全抽象实例的解决方案：

- AWS Fargate
- Azure Container Instances
- Google Cloud Run

这些解决方案不是 Kubernetes 特有的，但它们可以与 Kubernetes 很好地配合使用。云提供商已经提供了托管的 Kubernetes 控制平面，包括 Google 的 Google Kubernetes Engine（GKE）、Microsoft 的 Azure Kubernetes Service（AKS）和 Amazon Web Services 的 Elastic Kubernetes Service（EKS）。但管理数据平面（节点）留给了集群管理员。容器原生解决方案允许云提供商代表你完成这项工作。带有 GKE 的 Google Cloud Run、带有 ACI 的 AKS 以及带有 Fargate 的 AWS EKS 可以同时管理控制平面和数据平面。

例如，在 AKS 中，你可以配置虚拟节点。虚拟节点不由实际 VM 支持。相反，它在必要时利用 ACI 来部署容器。你只在集群需要扩展到超出常规节点容量时才为此付费。它比使用集群自动缩放器（需要配置实际的 VM 支持的节点）扩展得更快。

## 突破 Kubernetes 的极限

在本节中，我们将看到 Kubernetes 团队如何将 Kubernetes 推向其极限。这些数字非常说明问题，但有些工具和技术（如 Kubemark）非常巧妙，你甚至可以用它们来测试你的集群。Kubernetes 被设计为支持具有以下属性的集群：

- 每节点最多 110 个 Pod
- 最多 5,000 个节点
- 最多 150,000 个 Pod
- 最多 300,000 个总容器数

这些数字只是指导方针，并非硬性限制。托管具有特殊的部署和运行时模式（涉及 Pod 的创建和终止）的专业工作负载的集群可能支持截然不同的数字。

在 CERN，OpenStack 团队实现了每秒 200 万次请求：http://superuser.openstack.org/articles/scaling-magnum-and-kubernetes-2-million-requests-per-second

Mirantis 在其扩展实验室中进行了一项性能和扩展测试，他们在 500 台物理服务器上部署了 5,000 个 Kubernetes 节点（在虚拟机中）。

OpenAI 在 Azure 上将其机器学习 Kubernetes 集群扩展到 2,500 个节点，并学到了一些宝贵的经验，例如注意日志代理的查询负载以及将事件存储在单独的 etcd 集群中：https://openai.com/research/scaling-kubernetes-to-2500-nodes

这里有更多有趣的用例：https://www.cncf.io/projects/case-studies

到本节结束时，你将体会到投入到大规模改进 Kubernetes 中的努力和创造力，你将知道单个 Kubernetes 集群能推到什么程度以及预期性能如何，并且你将深入了解一些可以帮助你评估自己 Kubernetes 集群性能的工具和技术。

### 改进 Kubernetes 的性能和可扩展性

Kubernetes 团队在 Kubernetes 1.6 中重点关注了性能和可扩展性。当 Kubernetes 1.2 发布时，它支持在 Kubernetes 服务级目标范围内最多 1,000 个节点的集群。Kubernetes 1.3 将这个数字翻倍到 2,000 个节点，而 Kubernetes 1.6 将其提升到惊人的每个集群 5,000 个节点。5,000 个节点可以带你走很远，特别是如果你使用大型节点。但是，当你运行大型节点时，你也需要注意每节点 Pod 数的指导方针。请注意，云提供商仍建议每个集群最多 1,000 个节点。

我们稍后将深入探讨这些数字，但首先，让我们看看底层，了解 Kubernetes 是如何实现这些令人印象深刻的改进的。

### API 服务器中的缓存读取

Kubernetes 将系统状态保存在 etcd 中，etcd 非常可靠，但速度不是超级快（尽管 etcd 3 带来了巨大改进，专门为支持更大的 Kubernetes 集群）。各种 Kubernetes 组件基于该状态的快照运行，而不依赖实时更新。这一事实允许用一些延迟换取吞吐量。以前，所有快照都是通过 etcd watch 更新的。现在，API 服务器有一个用于更新状态快照的内存读缓存。内存读缓存由 etcd watch 更新。这些方案显著减少了对 etcd 的负载，并提高了 API 服务器的整体吞吐量。

### Pod 生命周期事件生成器

增加集群中的节点数量是水平可扩展性的关键，但 Pod 密度也至关重要。Pod 密度是 kubelet 在一个节点上可以有效管理的 Pod 数量。如果 Pod 密度低，那么你在一个节点上无法运行太多 Pod。这意味着你可能无法从更强大的节点（每个节点更多 CPU 和内存）中受益，因为 kubelet 无法管理更多 Pod。另一种选择是迫使开发者妥协他们的设计，创建每个 Pod 做更多工作的粗粒度 Pod。理想情况下，Kubernetes 不应在 Pod 粒度上强迫你的设计。Kubernetes 团队非常理解这一点，并在提高 Pod 密度方面投入了大量工作。

在 Kubernetes 1.1 中，官方（经过测试和宣传）数字是每节点 30 个 Pod。我实际上在 Kubernetes 1.1 上每节点运行了 40 个 Pod，但我为此付出了代价，因为过多的 kubelet 开销从工作 Pod 中窃取了 CPU。在 Kubernetes 1.2 中，这个数字跃升至每节点 100 个 Pod。Kubelet 过去常常在自己的 goroutine 中不断轮询容器运行时以获取每个 Pod 的信息。这对容器运行时造成了很大压力，在性能峰值期间会导致可靠性问题，特别是 CPU 利用率。解决方案是 Pod 生命周期事件生成器（PLEG）。PLEG 的工作原理是列出所有 Pod 和容器的状态，并将其与先前状态进行比较。这是对所有 Pod 和容器一次性完成的。然后，通过将状态与先前状态进行比较，PLEG 知道哪些 Pod 需要再次同步，并且只调用那些 Pod。这一变化导致 kubelet 和容器运行时的 CPU 使用率显著降低四倍。它还缩短了轮询周期，从而提高了响应性。

### 使用 Protocol Buffers 序列化 API 对象

API 服务器有一个 REST API。REST API 通常使用 JSON 作为其序列化格式，Kubernetes API 服务器也不例外。然而，JSON 序列化意味着需要将 JSON 编组和解析为原生数据结构。这是一项昂贵的操作。在大规模 Kubernetes 集群中，许多组件需要频繁查询或更新 API 服务器。所有这些 JSON 解析和组合的成本迅速增加。在 Kubernetes 1.3 中，Kubernetes 团队添加了高效的 Protocol Buffers 序列化格式。JSON 格式仍然存在，但 Kubernetes 组件之间的所有内部通信都使用 Protocol Buffers 序列化格式。

### etcd3

Kubernetes 在 1.6 版本中从 etcd2 切换到 etcd3。这是一件大事。由于 etcd2 的限制，特别是与 watch 实现相关的限制，不可能将 Kubernetes 扩展到 5,000 个节点。Kubernetes 的可扩展性需求推动了 etcd3 的许多改进，因为 CoreOS 将 Kubernetes 作为衡量标准。这里讨论一些重要的改进项。

#### gRPC 替代 REST

etcd2 有 REST API，而 etcd3 有 gRPC API（以及通过 gRPC 网关提供的 REST API）。gRPC 底层的 HTTP/2 协议可以使用单个 TCP 连接来处理多个请求和响应流。

#### 租约替代 TTL

etcd2 使用每个键的生存时间（TTL）作为键过期的机制，而 etcd3 使用带 TTL 的租约，其中多个键可以共享同一个租约。这显著降低了保活流量。

#### Watch 实现

etcd3 的 watch 实现利用 gRPC 的双向流，维护一个单一的 TCP 连接来发送多个事件，这使内存占用至少减少了一个数量级。

#### 状态存储

使用 etcd3，Kubernetes 开始将所有状态存储为 Protocol Buffers，这消除了大量浪费的 JSON 序列化开销。

### 其他优化

Kubernetes 团队还做了许多其他优化，例如：

- 优化调度器（导致调度吞吐量提高了 5-10 倍）
- 将所有 controller 切换到使用共享 informer 的新推荐设计，减少了 controller-manager 的资源消耗
- 优化 API 服务器中的单个操作（转换、深拷贝和补丁）
- 减少 API 服务器中的内存分配（这显著影响 API 调用的延迟）

### 衡量 Kubernetes 的性能和可扩展性

为了改进性能和可扩展性，你需要清楚你想要改进什么以及如何衡量改进。你还必须确保在追求改进性能和可扩展性时，不违反基本属性和保证。我喜欢性能改进的一点是，它们通常免费带来可扩展性的提升。例如，如果一个 Pod 需要节点 50% 的 CPU 来完成其工作，而你通过性能改进使 Pod 可以使用 33% 的 CPU 来完成相同工作，那么你突然可以在该节点上运行 3 个 Pod 而不是 2 个，你的集群整体可扩展性提高了 50%（或者成本降低了 33%）。

#### Kubernetes SLO

Kubernetes 有服务级目标（SLO）。在尝试改进性能和可扩展性时，必须遵守这些保证。Kubernetes 的 API 调用响应时间为 1 秒（99 百分位）。那是 1,000 毫秒。实际上，它在大多数时候实现了快一个数量级的响应时间。

#### 衡量 API 响应能力

API 有许多不同的端点。没有一个简单的 API 响应能力数字。每个调用都必须单独衡量。此外，由于系统的复杂性和分布式特性，更不用说网络问题，结果可能会有很大波动。一个可靠的方法是将 API 测量分解到各个端点，然后随着时间的推移运行大量测试并查看百分位数（这是标准做法）。

使用足够的硬件来管理大量对象也很重要。Kubernetes 团队在此测试中为 master 使用了 32 核 VM，搭配 120GB 内存。

#### 衡量端到端 Pod 启动时间

大型动态集群最重要的性能特征之一是端到端 Pod 启动时间。Kubernetes 一直在创建、销毁和移动 Pod。可以说 Kubernetes 的主要功能是调度 Pod。在下图中，你可以看到 Pod 启动时间比 API 调用更稳定。这是有道理的，因为有很多工作要做，比如启动运行时的新实例，这不依赖于集群大小。在 Kubernetes 1.2 的 1,000 节点集群上，启动 Pod 的 99 百分位端到端时间小于 3 秒。在 Kubernetes 1.3 的 2,000 节点集群上，启动 Pod 的 99 百分位端到端时间稍高于 2.5 秒。

## 大规模测试 Kubernetes

拥有数千个节点的集群是昂贵的。即使像 Kubernetes 这样享有谷歌及其他行业巨头支持的项目，仍然需要想出合理的方式来测试，同时不破费。

Kubernetes 团队在每个版本中至少会在真实集群上运行一次全面测试，以收集真实的性能和可扩展性数据。然而，还需要一种轻量级且更便宜的方式来试验潜在的改进和检测回归。于是 Kubemark 应运而生。

### 介绍 Kubemark 工具

Kubemark 是一个运行称为 hollow node（空心节点）的模拟节点的 Kubernetes 集群，用于对大规模（空心）集群运行轻量级基准测试。真实节点上的某些 Kubernetes 组件（如 kubelet）被替换为空心 kubelet。空心 kubelet 模拟真实 kubelet 的大部分功能。空心 kubelet 实际上不会启动任何容器，也不会挂载任何卷。但从 Kubernetes 的角度——存储在 etcd 中的状态——所有这些对象都存在，你可以查询 API 服务器。空心 kubelet 实际上是真实的 kubelet，只是注入了一个什么都不做的模拟 Docker 客户端。

另一个重要的空心组件是 hollow proxy，它模拟 kube-proxy 组件。它同样使用了真实的 kube-proxy 代码，但使用一个什么都不做的模拟 proxier 接口，避免操作 iptables。

### 设置 Kubemark 集群

Kubemark 集群利用了 Kubernetes 的能力。要设置 Kubemark 集群，请执行以下步骤：

1. 创建一个常规的 Kubernetes 集群，我们可以在其中运行 N 个空心节点。
2. 创建一个专用 VM 来启动 Kubemark 集群的所有 master 组件。
3. 在基础 Kubernetes 集群上调度 N 个空心节点 Pod。这些空心节点被配置为与在专用 VM 上运行的 Kubemark API 服务器通信。
4. 通过将附加 Pod 调度到基础集群上并将其配置为与 Kubemark API 服务器通信来创建附加 Pod。

完整的指南在此：
https://github.com/kubernetes/community/blob/master/contributors/devel/sig-scalability/kubemark-guide.md

### 比较 Kubemark 集群与真实集群

Kubemark 集群的性能与真实集群的性能大多相似。对于 Pod 启动端到端延迟，差异可以忽略不计。对于 API 响应能力，差异更大一些，但通常小于两倍。然而，趋势完全相同：真实集群上的改进/回归在 Kubemark 上表现为指标类似百分比的下降/上升。

## 总结

在本章中，我们研究了可靠且高可用的大规模 Kubernetes 集群。这可以说是 Kubernetes 的最佳应用场景。虽然能够编排运行少量容器的小型集群也很有用，但这并非必需；但在规模下，你必须有一个你可以信任的编排解决方案，能够随系统一起扩展，并提供工具和最佳实践来实现这一点。

你现在对分布式系统中可靠性和高可用性的概念有了扎实的理解。你深入研究了运行可靠且高可用的 Kubernetes 集群的最佳实践。你探索了围绕扩展 Kubernetes 集群和衡量其性能的复杂问题。你现在可以就在可靠性和可用性的级别，以及其性能和成本之间做出明智的设计选择。
