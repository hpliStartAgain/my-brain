# 10 混沌工程

## 引言

其核心而言，**混沌工程**（Chaos Engineering）是一种主动发现系统潜在弱点的方法，以防止它们造成重大损害。混沌工程源于 Netflix 和 Amazon 等公司在复杂大规模系统中的实践，涉及有意向系统引入故障以测试其健壮性和韧性。通过引发受控的中断，工程师可以监控系统的反应、发现其薄弱环节，并提高其对未来故障的抵御能力。

混沌工程与其名称所暗示的混乱相反，它是有序和组织化的。它的目标不是制造无法阻止的混乱，而是提供一种严格的方法来处理当前系统架构的复杂性。在停机可能给企业带来重大收入损失和声誉损害的世界中，理解系统在压力下的行为至关重要。

在[[站点可靠性工程]]（SRE）中——其主要目标是维护和提升服务的正常运行时间和可靠性——混沌工程扮演着至关重要的角色。通过将 SRE 的目标与混沌工程的原理相结合，组织可以构建更可靠的系统，能够处理已知和意外事件。

本章将讨论混沌工程的原理、方法和最佳实践，以及它在 SRE 中的重要作用。我们还将探讨如何在组织中使用混沌工程，以及所使用的工具和技术，以及行业领先者的案例研究。

## 混沌工程的原理

混沌工程的原理由 Netflix 的工程师正式确定，是理解和实施混沌工程的基石。这些原则提出了一种有纪律的、科学的方法，通过引入受控中断、观察系统响应并逐步增加这些中断的复杂性来发现系统中的弱点。

### 建立假设

混沌工程的第一步是对系统的行为建立**假设**（Hypothesis）。假设通常始于对系统稳态的断言，即系统在正常操作条件下的行为。假设基于对系统架构、组件、依赖关系和操作知识的理解而构建。它应概述混沌实验的预期结果以及对系统稳态的潜在影响。

### 引入真实世界事件

形成假设后，下一步是将**真实世界事件**（Real-world Events）引入系统。这可以通过故障注入来实现，可能简单如关闭一个服务、引入网络延迟或模拟系统上的重负载。目标是模拟可能在实际生产环境中发生的事件，无论是硬件故障、意外的流量高峰还是软件 Bug。

### 观察系统

下一个关键阶段是在事件期间和之后**观察系统**（Observing the System）。监控和可观测性工具在此阶段至关重要，用于收集系统行为、性能指标以及偏离稳态的任何数据。这包括检查系统是否按预期行为运行，或者是否因中断而出现新的、不可预见的问题。

### 验证假设

观察系统并收集数据后，下一步是验证初始假设。如果系统行为符合预期且假设得到确认，则提供了对系统韧性的信心。如果假设不正确，观察到的结果将为系统的弱点或潜在改进领域提供宝贵的见解。

### 渐进式复杂度

混沌工程不是一次性事件，而是一个迭代过程，其中实验的复杂性会逐步增加。每个新实验都应建立在前一个实验收集的见解之上。随着系统的演进和成熟，混沌实验也应变得更加复杂，模拟更具挑战性的事件并包含更多系统部分。这种渐进式方法有助于管理风险，因为它允许逐步理解和改善系统的韧性。

## 混沌工程在 SRE 中的作用

如前所述，混沌工程是一门通过有意向系统引入故障来帮助 SRE 确保系统可靠性的学科。这使 SRE 能够观察系统在过载下的行为，并识别需要改进的领域。混沌工程可以增加系统韧性、发现系统弱点、增强系统可扩展性、改善事件响应时间以及验证系统假设。

让我们逐一了解相关收益：

- **提升系统韧性**：混沌工程可以帮助 SRE 发现和缓解系统弱点，从而提高系统韧性。通过有意向系统引入故障，SRE 可以看到系统的反应并识别需要改进的领域。这有助于防止未来的宕机和其他中断。例如，SRE 可能向数据库引入故障，以观察其恢复速度。如果数据库恢复时间过长，SRE 可以更改数据库的配置或架构以提高其韧性。
- **发现系统弱点**：混沌工程还可以帮助 SRE 发现在正常操作条件下可能不明显的系统弱点。通过引入受控故障，SRE 可以看到系统的响应并识别不够有韧性的领域。这些信息随后可用于改进系统设计和架构，使其更加健壮和可靠。例如，SRE 可能向负载均衡器引入故障，以观察其对后端系统可用性的影响。如果负载均衡器故障，SRE 可以更改其配置或架构以提高可靠性。
- **增强系统可扩展性**：混沌工程还可用于测试系统的可扩展性。通过引入故障和增加负载，SRE 可以观察系统在压力下的表现。这些信息随后可用于识别瓶颈并改进系统架构。例如，SRE 可能向 Web 服务器引入故障，以观察其对网站性能的影响。如果网站开始变慢，SRE 可以更改 Web 服务器的配置或架构以提高其可扩展性。
- **改善事件响应时间**：混沌工程还可以帮助改善事件响应时间。通过模拟真实世界的事件，SRE 可以培训其团队快速有效地响应。这有助于减少解决事件所需的时间，最小化对用户的影响。例如，SRE 可能模拟停电以观察团队恢复服务的速度。如果团队恢复时间过长，SRE 可以更改其事件响应计划以提高效率。
- **验证系统假设**：混沌工程还可用于验证系统假设。通过有意引入故障，SRE 可以测试其对系统行为的假设。这有助于发现和纠正任何不正确的假设，确保系统按预期设计和运行。例如，SRE 可能假设特定组件始终可用。通过向该组件引入故障，SRE 可以测试其假设并在必要时更改系统。

## 混沌工程中的关键概念

混沌工程是通过有意实验来主动发现和修复系统漏洞的方法。它涉及以下关键概念：

### 爆炸半径

**爆炸半径**（Blast Radius）在混沌工程中指的是故障对系统的影响范围。概念是从小爆炸半径开始实验（只影响系统的一小部分或最小数量的用户），然后随着对系统信心的增长逐渐增加规模。这有助于限制对用户的潜在负面影响，同时允许深入了解系统在压力下的行为。

### 故障注入

**故障注入**（Failure Injection）是一种有意向系统注入故障以观察其反应的方法。这可能涉及关闭服务器、切断网络连接或模拟高负载条件。目的是测试系统的韧性和冗余性，验证故障转移和恢复过程是否按预期工作，并识别需要改进的任何薄弱点。

### 稳态

**稳态**（Steady State）是系统的正常操作条件。它是系统在没有经历任何故障或压力时的行为方式。通过了解系统的稳态，可以更容易地识别系统何时行为异常。混沌工程涉及使系统偏离其稳态并观察实验结束后它是否能恢复到该状态。

### 可观测性与监控

**可观测性**（Observability）和**监控**（Monitoring）是混沌工程的基本组成部分。可观测性意味着对系统内部状态有足够的洞察，可以根据系统的外部输出来推断其行为或识别问题。这可能包括日志、指标和追踪数据。监控指的是对系统状态的持续检查。如果没有强大的可观测性和监控，就不可能理解混沌实验的效果或知道何时出了问题。

### 混沌实验

**混沌实验**（Chaos Experiments）是对系统进行受控的故障应用，以了解其在压力下的行为。设计良好的混沌实验始于关于系统将如何反应的假设，应用故障场景，然后观察结果以确认或否定假设。这些实验通常是自动化的并定期运行，以捕获回归或系统行为的变化。

### 游戏日

**游戏日**（Game Days）是计划好的活动，团队在受控环境中模拟事件以实践事件响应协议。它们是混沌工程的一种宝贵形式，因为它们不仅测试系统的技术方面，还测试人为因素：沟通、决策以及文档和行动手册的有效性。游戏日帮助团队为真实事件做好准备，并学习如何在事件发生时更有效地响应。

## 准备混沌工程

为混沌工程做准备首先要彻底分析基础设施，以确定最关键的系统。这些系统是那些故障会对运营产生重大影响的系统。一旦确定了这些系统，就要建立正常系统行为的基线。这通常包括期望的延迟、吞吐量和错误率等指标。有了基线，就可以设计实验了。

这些实验旨在中断正常的系统操作，可能涉及向系统引入延迟、故意使服务失败或模拟其他潜在的系统中断来源。这些实验的目的是观察系统如何响应以及弱点在哪里，从而使你能够改善系统韧性。

### 设定目标和指标

为混沌测试设定目标需要确定与组织的韧性和可靠性目标相一致的、具体的、可衡量的目标。

设定正确混沌测试目标的一些步骤：

1. **识别关键指标**：首先，确定衡量系统健康状态的关键绩效指标（KPI）。这些包括正常运行时间、响应时间、错误率和系统吞吐量。
2. **定义基线**：建立这些 KPI 的正常行为。这涉及收集和分析数据以设定操作基线。
3. **识别故障或缺陷**：决定要模拟的故障或缺陷类型。范围可以从基础设施故障（如服务器崩溃或网络中断）到软件故障（如代码错误）。
4. **建立预期结果**：对于每种类型的故障或缺陷，确定预期的系统响应。这构成了每个实验的假设。例如，如果服务器故障，备用服务器可能会自动接管，对响应时间的影响很小。
5. **设定改进目标**：定义希望通过这些实验实现的改进。这可能涉及减少停机时间、改进系统冗余或识别和修复系统中的薄弱点。

每个实验的结果应根据定义的目标进行衡量，这将提供清晰的指示，表明系统是否按预期运行以及哪些地方需要改进。

### 构建可观测性基础设施

构建可观测性基础设施是执行混沌测试的关键部分，因为它允许跟踪实验的影响并理解系统行为。以下是逐步指南：

1. **确定关键指标**：确定需要观察的关键指标以理解系统行为。这些包括错误率、系统延迟、吞吐量和其他性能指标。
2. **仪表化**：对服务进行仪表化以收集这些指标。可以使用各种监控工具和专为可观测性设计的软件库来完成，这些工具可以实时跟踪系统性能和状态。
3. **日志和追踪**：实施健壮的日志记录和追踪能力。日志提供已发生事件的详细记录，追踪提供请求生命周期的详细视图。它们共同帮助理解复杂的系统交互。
4. **告警**：基于已识别的关键指标设置告警。这些告警可以在系统行为出现重大偏差时通知团队。
5. **仪表板**：创建综合仪表板，可视化系统数据。这些仪表板应提供系统健康和性能的一目了然的视图，并能够快速识别任何问题。
6. **分析和改进**：分析混沌实验期间收集的数据，以了解系统在不同故障条件下的行为。此分析可以帮助发现系统中的薄弱点并进行必要的改进。

请记住，可观测性的目标不仅仅是收集数据，而是获得可操作的见解，以改善系统的韧性和可靠性。从有效可观测性基础设施中获得的见解对于理解混沌测试实验的影响至关重要。

### 建立强大的事件响应策略

在混沌测试期间建立强大的事件响应策略涉及定义用于识别、响应和学习系统中断的程序。

建立强大事件响应策略的最佳方法如下：

- **事件识别**：设置能够快速识别事件的监控和告警系统。这些可以基于偏离正常行为的 KPI。
- **事件分类**：根据严重程度对事件进行分类，范围从小问题到重大故障。这有助于优先安排响应工作和资源。
- **沟通计划**：制定清晰的计划，明确谁应该被告知事件、如何告知以及他们需要知道哪些信息。这可能包括团队成员、利益相关者，甚至客户（如果事件影响他们）。
- **事件响应**：建立清晰的事件处理流程。这通常意味着找出问题原因、阻止问题、修复它并使系统恢复正常。如果存在备用系统，也可能意味着启动故障转移过程。
- **事后审查**：问题解决后，进行事后分析以找出原因、评估响应的有效性以及可以采取哪些措施防止类似问题再次发生。
- **持续改进**：使用事后审查中学到的经验来不断改进事件响应计划。这可能意味着更改系统架构以提高韧性、调整告警阈值或改进人员沟通方式。

## 实施混沌工程

实施混沌工程涉及一系列步骤，每个步骤都旨在加深对系统韧性和可靠性的理解。以下流程概述了如何实施混沌工程：

1. **基线定义**：建立对系统正常行为的扎实理解。收集响应时间、错误率和吞吐量等指标，以创建可用于比较实验结果的基线。
2. **假设制定**：对于每个实验，制定预测系统行为的假设。该假设将基于对系统架构和功能的理解。例如，可能预测如果特定服务宕机，备用服务将无缝接管。
3. **设计和实施实验**：设计将以受控方式中断系统的混沌实验。这可能涉及注入延迟、关闭服务或模拟高流量负载。目标是模拟潜在的故障来源并观察系统的反应。
4. **观察和监控**：实验期间，使用可观测性基础设施密切监控系统行为。这将提供系统如何响应中断的实时洞察。
5. **分析结果并完善假设**：实验完成后，分析结果并与原始假设进行比较。这可能确认对系统的理解，也可能揭示需要解决的意外行为。
6. **实施改进**：使用从实验中获得的见解来改善系统韧性。这可能涉及对代码、基础设施甚至事件响应程序的更改。
7. **重复该过程**：混沌工程是一个迭代过程。持续重复此过程有助于确保系统在随时间演进时保持韧性。

为混沌测试模拟生产负载对于评估系统韧性至关重要。首先要了解生产环境的负载模式，并使用 JMeter 或 Locust 等工具生成真实的负载配置文件。分布负载生成以模拟真实场景，并实施性能指标监控。逐步增加负载同时引入混沌场景，如网络故障或资源耗尽。分析结果以识别弱点，并迭代改善系统韧性，考虑在 CI/CD 管道中自动化持续测试。

## 混沌工程的工具和技术

从故障注入到监控和分析，混沌工程可以借助多种工具和技术来实施。以下是一些示例：

### Chaos Toolkit

**Chaos Toolkit** 是一个开源、社区驱动的项目，旨在提供一种直接简单的方式来实施混沌工程。它提供命令行界面，帮助定义、运行和回滚系统中的混沌实验。该工具包支持多个扩展，能够与各种平台和服务集成。在实验期间，还可以将其与 Prometheus 或 Grafana 结合使用以实现有效的可观测性。

### Gremlin

**Gremlin** 是一个完全托管的混沌工程平台，有时被称为"故障即服务"（failure-as-a-service）。它允许在系统中安全可靠地执行混沌实验。Gremlin 开箱即用提供多种攻击类型，包括资源攻击（如 CPU、内存或磁盘）、网络攻击和状态攻击（如关机或时间旅行）。它支持基于云和本地环境，并提供用户友好的界面来规划、安排和回滚混沌实验。

### Chaos Monkey

**Chaos Monkey** 是由 Netflix 开发的韧性工具，帮助应用容忍随机的实例故障。它遵循"经常失败，快速失败"（fail often, fail fast）的原则。Chaos Monkey 随机终止生产环境中运行的虚拟机实例和容器。这种不可预测的中断性质迫使开发人员从一开始就构建有韧性的服务，从而确保高可用性和健壮性。

其他混沌工具包括：

- **LitmusChaos**：一个专为 Kubernetes 设计的开源混沌工程工具。它提供多种预定义的混沌实验，如 Pod 故障或网络延迟，并允许开发人员创建自己的实验。
- **PowerfulSeal**：另一个用于 Kubernetes 的开源工具，向集群注入故障，允许识别和修复系统韧性中的弱点。
- **ToxiProxy**：由 Shopify 开发，ToxiProxy 是一个 TCP 代理，用于创建和测试网络条件，如慢速连接、超时等。可用于测试应用程序如何处理各种网络问题。
- **Pumba**：一个开源的混沌测试工具，用于中断 Docker 容器中的 TCP、网络和进程。它轻量且可移植，是基于容器的应用程序的绝佳选择。

## 混沌工程案例研究

通过正确实施混沌工程，公司达到了新的高度。它涉及多次实验的多次迭代。让我们考察以下案例研究。

### Netflix

Netflix 是使用混沌工程改善系统韧性的先驱。该公司使用一套名为 **Simian Army**（猿军）的工具，以受控和安全的方式向生产环境注入故障。这使得 Netflix 能够在故障导致宕机或其他问题之前发现并修复系统中的弱点。

Simian Army 中最著名的工具之一是 Chaos Monkey。Chaos Monkey 随机终止生产环境中的虚拟机实例。这模拟了物理服务器的故障，可能对其他系统产生级联影响。通过更频繁地让工程师接触这些故障，Chaos Monkey 帮助他们构建更有韧性的应用。

Simian Army 中的另一个工具是 **Latency Monkey**（延迟猴）。Latency Monkey 向 RESTful 客户端-服务器通信引入人为延迟。这模拟了网络延迟或其他性能问题的影响。通过使用 Latency Monkey，Netflix 可以测试其应用对不同延迟水平的响应。

Netflix 还使用了 Simian Army 中的其他几种工具，包括：

- **Error Monkey**（错误猴）：向应用代码引入错误。
- **Kill Disk Monkey**（磁盘杀手猴）：随机卸载虚拟机的磁盘。
- **Zombie Load Monkey**（僵尸负载猴）：向应用引入人为负载。
- **Change Monkey**（变更猴）：随机更改配置设置。

这些工具使 Netflix 能够以多种方式测试其系统的韧性。通过以受控和安全的方式让系统暴露于故障，Netflix 可以在问题出现之前发现并修复弱点。这有助于 Netflix 即使在意外故障的情况下也能保持其服务的正常运行。

Netflix 工程师估计，Chaos Monkey 已经防止了 100 多次宕机。该公司还声称，Latency Monkey 帮助减少了 50% 的客户关于性能问题的投诉。

### Amazon

Amazon 是另一家使用混沌工程改善系统韧性的公司。该公司使用各种工具，包括 **AWS Fault Injection Simulator**（AWS FIS）、**Chaos Toolkit** 和 **Litmus Chaos**。

AWS FIS 是一个完全托管的服务，允许 Amazon 客户以受控和安全的方式向其 AWS 环境注入故障。这可用于测试应用、服务和基础设施对意外故障的韧性。

Amazon 使用这些工具运行了许多混沌实验，包括：

- 向 Amazon EC2 实例注入延迟
- 删除 Amazon RDS 实例
- 断开 Amazon ELB 实例与 Amazon EC2 实例的连接

这些实验帮助 Amazon 发现并修复了系统中的弱点。例如，一个实验发现 Amazon 的 ELB 服务对单个 EC2 实例的丢失不具有韧性。通过添加一种机制来修复，该机制会在故障时自动将流量路由到健康的 EC2 实例。

Amazon 使用混沌工程显著提高了其系统的韧性。该公司多年来没有发生过重大宕机。

### Google

Google 多年来一直使用混沌工程来改善其系统的韧性。该公司使用各种工具，包括：

- **Chaos Mesh**：一个 Kubernetes 原生的混沌工程框架，允许工程师以受控和安全的方式向其 Kubernetes 环境注入故障。
- **Fault Injection Framework**（FIF）：允许工程师向其 Google Cloud Platform（GCP）环境注入故障。
- **Chaos Monkey**：随机终止生产环境中虚拟机实例的工具。
- **Latency Monkey**：向 RESTful 客户端-服务器通信引入人为延迟的工具。

这些工具帮助 Google 在故障导致宕机或其他问题之前发现并修复系统中的弱点。例如，使用 Chaos Mesh 的一个实验发现 Google 的 Kubernetes 调度器对单个节点的丢失不具有韧性。通过向调度器添加一种机制来修复，该机制会在故障时自动将 Pod 重新调度到健康节点。

Google 还使用混沌工程改善其基础设施的韧性。例如，使用 FIF 的一个实验发现 Google 的网络对单个链路的丢失不具有韧性。通过向网络添加冗余来修复。

除了上述工具，Google 还使用其他技术来改善系统韧性，如：

- **金丝雀部署**（Canary Deployments）：在向所有用户部署新版本软件之前，先向一小部分用户部署，以在故障导致宕机之前发现并修复问题。
- **A/B 测试**：比较两个版本软件以查看哪个表现更好，可在故障导致宕机之前发现并修复问题。
- **监控**：收集和分析系统性能数据，可用于在问题导致宕机之前发现它们。

## 混沌工程的未来

混沌工程的未来是光明的。随着越来越多的公司采用混沌工程，这一实践将变得更加复杂和有效。以下是一些可能塑造混沌工程未来的趋势：

- **在云原生环境中越来越多地使用混沌工程**：随着越来越多的应用部署在云中，混沌工程将变得越来越重要，以确保这些系统的韧性。
- **更自动化混沌工程工具的开发**：这将使工程师更容易运行混沌实验，而无需手动干预。
- **越来越多地使用混沌工程改善系统安全性**：混沌工程可用于发现和修复攻击者可能利用的安全漏洞。
- **越来越多地使用混沌工程改善系统性能**：通过了解系统在压力下的行为，工程师可以识别瓶颈和其他性能问题。
