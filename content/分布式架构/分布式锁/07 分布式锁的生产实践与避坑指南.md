# 07 分布式锁的生产实践与避坑指南

**摘要：**

前六篇文章系统讲解了分布式锁的理论原理与各方案的实现机制。本篇回到工程现场，聚焦那些理论文章不会告诉你、但在生产环境中真实发生过的问题。内容分为四个维度：**锁粒度设计**（粒度过粗和过细各有什么代价、如何找到合适的粒度）、**加锁失败的降级策略**（快速失败还是排队等待，如何设计合理的降级链路）、**监控与告警**（分布式锁应该暴露哪些指标、异常告警阈值如何设定）、以及**典型生产故障复盘**（死锁、锁泄漏、锁风暴、误解锁的根因与修复方案），最后给出分布式锁的测试方法。读完本文，你应当能回答两个问题：锁粒度为什么是最容易被忽视的架构决策，以及生产故障背后的共性根因是什么。

## 第 1 章 锁粒度设计：最容易被忽视的架构决策

### 1.1 什么是锁粒度

**锁粒度（Lock Granularity）** 是指分布式锁所保护的资源范围大小。粒度越粗，一把锁保护的资源越多；粒度越细，一把锁保护的资源越少。

用一个具体的例子来说明。假设一个电商系统需要保护库存扣减操作，锁粒度可以是：

```
粒度 1（最粗）：全局库存锁
  lock_key = "inventory_lock"
  → 所有商品的库存扣减都竞争同一把锁
  → 串行化程度最高，吞吐量最低

粒度 2：商品级锁
  lock_key = "inventory_lock:product:{productId}"
  → 不同商品的库存扣减互不影响
  → 同一商品的并发请求串行化

粒度 3：商品+仓库级锁
  lock_key = "inventory_lock:product:{productId}:warehouse:{warehouseId}"
  → 不同仓库的同一商品可以并发扣减
  → 粒度最细，并发度最高

粒度 4（最细）：订单级锁
  lock_key = "inventory_lock:order:{orderId}"
  → 每个订单独享一把锁
  → 但无法防止同一商品被多个订单同时超卖
```

### 1.2 锁粒度过粗的代价

**核心问题是并发度被人为压低**。粒度过粗的锁会把大量本不需要互斥的操作强制串行化。考虑上例中"全局库存锁"方案：商品 A 和商品 B 的库存扣减操作完全独立，没有任何共享资源需要保护，但全局锁强迫它们排队执行。

**量化影响**：假设单次库存扣减操作耗时 10ms，使用全局锁的系统 QPS 上限等于 1000ms / 10ms 等于 100 QPS。而使用商品级锁，如果有 1000 种商品，理论上可以支持 100,000 QPS（1000 商品 × 100 QPS）。

**真实案例**：某电商平台在大促活动中，把所有商品的秒杀库存扣减都用一把全局 Redis 锁保护，压测中发现 QPS 极低（仅 200 左右），原因就是全局锁把所有商品的扣减操作完全串行化。修改为商品级锁（`lock_key = "seckill:product:{productId}"`）后，QPS 提升了 200 倍。

这个案例的教训是：**锁粒度的选择，直接决定了系统的并发上限**。而且这个上限是"乘法级"的——从全局锁到商品级锁，并发上限从 1 倍变成 N 倍（N 为商品数）。**因此，锁粒度不是"优化项"，而是"架构决策"**，它应当在设计阶段就被认真考虑，而不是等压测出问题再回头改。

### 1.3 锁粒度过细的代价

**核心问题是数据一致性边界被打破**。粒度过细的锁可能无法保护真正需要保护的一致性约束。以上例中"订单级锁"为例：每个订单都有自己的锁，但订单之间是可以并发执行的。如果两个订单同时对同一商品进行库存扣减，它们各自持有不同的订单锁，互不阻塞，最终可能导致超卖。

粒度过细的另一个问题是**锁数量爆炸**。如果系统中有百万级商品，"商品+用户级锁"会产生海量不同的 lock_key，虽然每把锁的竞争度都很低，但这些锁记录会占用大量内存（Redis）或 ZNode（ZooKeeper），同时增加了锁管理的复杂度。

**量化参考（Redis）**：一个 Redis String key 约占 50 到 100 字节（含 key 名、value、元数据）。百万级 lock_key 约 50 到 100MB 内存占用，通常可以接受；但亿级 lock_key 就是 5 到 10GB，可能影响 Redis 的内存和扫描性能。

**"过细"与"过粗"的代价是对称的**：过粗损失并发，过细损失正确性。因此，粒度的设计目标不是"越细越好"，而是"恰好覆盖需要互斥的范围"。

### 1.4 锁粒度的设计原则

**原则一，以"最小化互斥范围"为目标**。锁的范围应该恰好覆盖"需要原子执行的操作集合"，不多也不少。如果两个操作之间完全没有共享资源（不存在数据竞争），就不应该让它们互斥。

**原则二，先识别"竞争维度"，再设计 key 结构**。竞争维度是指哪个维度的并发操作可能产生冲突。常见的竞争维度包括：

- **用户维度**：同一用户的并发请求（防止重复下单），`lock_key = "order:user:{userId}"`
- **资源维度**：竞争同一资源（防止超卖），`lock_key = "inventory:{productId}"`
- **时间维度**：同一时间段内只允许一次执行（防止重复任务），`lock_key = "task:{taskId}:{date}"`

**原则三，使用层次化的 key 结构，方便监控和故障排查**：

```
推荐的 key 命名规范：
{业务模块}:{操作类型}:{竞争维度1}:{竞争维度2}...

示例：
  order:create:user:123456             # 用户 123456 的创建订单锁
  inventory:deduct:product:P001        # 商品 P001 的库存扣减锁
  task:daily_report:2024-01-01         # 日报任务的执行锁
  payment:process:order:O789012        # 订单 O789012 的支付处理锁
```

清晰的命名规范使得通过 Redis `SCAN` 命令或监控系统快速定位锁的归属成为可能。

> [!info] 锁粒度是"业务建模"问题，不是"技术配置"问题
> 值得强调的是，锁粒度的选择本质上是一个**业务建模**问题。要回答"锁该多细"，必须先回答"哪些操作之间存在真正的数据竞争"——而这个问题只有理解业务的人才能回答。技术手段（如分片锁）只能缓解竞争，不能替代"想清楚竞争边界"。
>
> 因此，锁粒度设计应当由"理解业务的工程师"主导，而不是交给"配置锁参数的人"。**把锁粒度当成一个纯技术配置来对待，是很多系统并发上不去的根源**。

### 1.5 热点锁问题与分片

即使设计了合适的锁粒度，某些"热点资源"仍然会成为锁竞争的瓶颈。典型场景是爆款商品（某款限量球鞋）的库存，可能在秒杀活动中有数万个并发请求同时竞争同一把锁。

**热点锁的特征**是：同一个 lock_key 上有大量并发等待者；锁等待时间 P99 远高于正常值；对应 key 的访问频率远高于其他 key。

**分片锁（Lock Sharding）** 的思路是：把一把热点锁拆分为 N 把子锁，每个请求根据某个键（如 orderId）哈希选择一把子锁：

```java
// 分片锁实现思路
public class ShardedDistributedLock {
    private static final int SHARD_COUNT = 8;  // 拆分为 8 个分片

    public RLock getShard(String lockKey, String shardingKey) {
        int shardIndex = Math.abs(shardingKey.hashCode()) % SHARD_COUNT;
        String shardedKey = lockKey + ":" + shardIndex;
        return redissonClient.getLock(shardedKey);
    }
}

// 使用：每个订单根据 orderId 选择不同的库存锁分片
RLock lock = shardedLock.getShard("inventory:product:P001", orderId);
lock.lock();
try {
    deductInventory(productId, quantity);
} finally {
    lock.unlock();
}
```

**注意**：分片锁无法保证全局互斥（不同分片的请求可以并发执行），因此需要配合业务层的原子操作（如 `UPDATE inventory SET stock = stock - 1 WHERE stock > 0`）来保证最终一致性。分片锁的作用是**减少竞争，降低锁等待时间**，而不是替代业务层的数据一致性保证。

这一点非常关键：**分片锁把"互斥"降级成了"减少冲突"，因此它必须与"服务端校验"配套使用**。这与本专栏反复强调的立场一致——**当锁不再提供绝对互斥时，正确性必须由服务端的原子操作兜底**。

### 1.6 锁粒度与"数据分片"的呼应

分片锁的思路，与数据库领域的"分库分表"、库存领域的"库存分桶"其实是同一个思想：**把"单点热点"拆成"多个次热点"**。

这个思想的适用性很广。库存扣减的热点，可以拆成"10 个库存桶"；数据库写入的热点，可以拆成"多个分库"；锁的热点，可以拆成"多个分片"。它们的共同逻辑是：**当一个点的并发压力超过它能承受的上限时，把它拆成 N 个点，让压力分摊到 N 个点上**。

但拆解也带来新的问题，而且这些问题也是共通的。**其一，全局一致性**：拆开之后，"总共还剩多少"这类全局问题需要额外的聚合，而聚合本身又可能成为新的热点。**其二，拆分的粒度**：拆得太少缓解不够，拆得太多管理复杂——这与锁粒度的取舍完全同构。**其三，拆分的均衡性**：如果流量集中在少数几个分片上（如某个爆款商品），拆分的效果就会大打折扣。

因此，**分片不是一个"银弹"，而是一个"用复杂度换并发度"的手段**。采用它之前，应当先问："热点是均匀分布的，还是集中在少数几个点上？"如果是后者，分片可能治标不治本——真正的问题可能是"这个爆款商品的库存只有 1 件，无论如何都无法避免争抢"。**认清热点的性质，才能选对解法**。

### 1.7 一个锁粒度演进的反例

锁粒度的调整，往往不是"一次设计到位"，而是"随问题演进"——而每次调整都可能引入新的问题。看一个演进的反例。

**第一阶段，用全局锁**。某系统最初用一把全局锁保护库存扣减，简单可靠。但随着业务增长，全局锁成了瓶颈——所有商品串行，QPS 上不去。

**第二阶段，改为"商品级锁"**。团队把 key 改成 `inventory:{productId}`，并发度大幅提升，问题解决了。但新的问题出现了：业务还有一个"活动总库存"的限制（如"全场限量 1000 件"），需要跨商品汇总。商品级锁只能保护单个商品的扣减，无法保护"总量不超过 1000"这个跨商品的约束——于是活动期间出现了"总量超发"。

**第三阶段，引入"活动级锁加商品级锁"**。团队为活动总量加了第二把锁，扣减时先锁活动、再锁商品。这解决了超发，但引入了新问题：**两把锁的加锁顺序必须一致，否则死锁**；且活动级锁又成了新的热点。

这个演进反例的教训有三点。**其一，粒度调整不是"越细越好"，而是"要恰好覆盖所有需要保护的约束"**——商品级锁覆盖了单商品约束，却漏了跨商品的总量约束。**其二，多层锁会引入死锁风险**，必须统一加锁顺序（这与 05 篇 `SELECT FOR UPDATE` 的死锁问题是同一类）。**其三，每次粒度调整都可能"把热点从一个地方挪到另一个地方"**——全局锁的热点被挪走了，活动级锁又成了新热点。

**因此，锁粒度的设计应当"自上而下地识别所有约束"，而不是"自下而上地逐层拆解"**。先把"需要保护的约束"列全（单商品不超卖、活动总量不超发、单用户不重复），再据此设计锁的层次与 key 结构——**这样才不会在"解决一个问题"的同时"漏掉另一个问题"**。

## 第 2 章 加锁失败的降级策略

### 2.1 加锁失败的两种语义

加锁失败（`tryLock` 返回 false）有两种不同的语义，对应不同的处理策略。

**语义一，竞争失败（Lock Contended）**。锁被其他客户端持有，当前请求无法立即获取锁。此时有两种选择：**等待重试**（在 `waitTime` 内循环尝试，等到锁释放）或**快速失败**（立即放弃，返回错误给用户）。

**语义二，系统故障（System Error）**。Redis 或 ZooKeeper 服务不可用，或网络超时，导致加锁操作本身失败。此时应该触发降级流程，而不是无限重试（重试也不会成功）。

**区分这两种语义很重要**：竞争失败是"正常的忙"，系统故障是"异常"。对前者应当"快速失败或有限等待"，对后者应当"熔断降级"。把它们混为一谈，会导致"把故障当忙等，白等很久"或"把忙当故障，过早降级"。

### 2.2 快速失败策略

**适用场景**：用户发起的请求（如下单、支付），需要快速响应，不能让用户等待。

```java
@PostMapping("/orders")
public ResponseEntity<OrderResponse> createOrder(@RequestBody CreateOrderRequest request) {
    String lockKey = "order:create:user:" + request.getUserId();
    String lockValue = UUID.randomUUID().toString();

    // 尝试立即加锁（waitTime = 0，不等待）
    boolean acquired = distributedLock.tryLock(lockKey, lockValue, 0, 30000);

    if (!acquired) {
        // 快速失败：返回友好提示，引导用户稍后重试
        return ResponseEntity.status(429)
            .body(OrderResponse.error("操作太频繁，请稍后再试"));
    }

    try {
        Order order = orderService.createOrder(request);
        return ResponseEntity.ok(OrderResponse.success(order));
    } finally {
        distributedLock.release(lockKey, lockValue);
    }
}
```

快速失败策略需要配合前端友好提示：用户收到"稍后重试"提示后，知道可以在几秒后重新尝试，而不是以为系统故障。**"快速失败加友好提示"比"长时间等待后超时"对用户体验更好**——前者是"明确地告诉你稍后再来"，后者是"让你等很久最后还失败"。

### 2.3 有界等待策略

**适用场景**：批处理任务、异步任务，可以接受等待但需要有上限。

```java
public void processBatchTask(String taskId) {
    String lockKey = "task:batch:" + taskId;

    // 有界等待：等待最多 5 秒
    boolean acquired = lock.tryLock(5, TimeUnit.SECONDS);
    if (!acquired) {
        // 记录日志，放入重试队列（而不是直接报错）
        log.warn("任务 {} 获取锁超时，加入重试队列", taskId);
        retryQueue.offer(new RetryTask(taskId, System.currentTimeMillis() + 60000));
        return;
    }

    try {
        executeBatchTask(taskId);
    } finally {
        lock.unlock();
    }
}
```

**重试队列的设计要点**：设置最大重试次数，防止无限重试；使用指数退避延迟，避免重试风暴；记录每次重试的原因，便于监控。

### 2.4 熔断降级：锁服务不可用时的兜底

当 Redis 或 ZooKeeper 本身不可用时，继续尝试加锁只会增加系统压力。应该结合熔断器（Circuit Breaker）进行降级：

```java
@Service
public class DistributedLockService {

    private final CircuitBreaker circuitBreaker;  // Resilience4j 熔断器

    public boolean tryLock(String lockKey, String lockValue, long ttlMs) {
        // 通过熔断器保护加锁操作
        try {
            return circuitBreaker.executeSupplier(() ->
                redissonClient.getLock(lockKey).tryLock(0, ttlMs, TimeUnit.MILLISECONDS)
            );
        } catch (CallNotPermittedException e) {
            // 熔断器 OPEN 状态：Redis 可能不可用，走降级逻辑
            log.warn("分布式锁服务熔断，使用本地 JVM 锁降级处理");
            return localFallback(lockKey);  // 单节点降级方案
        }
    }

    private boolean localFallback(String lockKey) {
        // 降级方案：使用本地 ConcurrentHashMap + ReentrantLock
        // 注意：本地锁只在单节点有效，无法保证跨节点的互斥
        // 但在 Redis 不可用的紧急情况下，至少能保证单节点安全
        return localLockManager.tryLock(lockKey);
    }
}
```

**熔断降级的注意事项**：本地 JVM 锁降级只能保证单节点内的互斥，无法跨节点。在 Redis 不可用期间，如果多个节点同时降级为本地锁，仍然存在跨节点并发的问题。因此，降级方案需要结合业务的幂等性设计（数据库唯一约束等）来共同保证数据安全。

> [!warning] 降级不是"降级到更弱的锁"，而是"降级到更可靠的兜底"
> 这里有一个容易误解的点：**把分布式锁降级为本地锁，看起来是"降级"，实际上是把互斥范围从"跨节点"缩小到了"单节点"——它降低的不是"性能"，而是"正确性"**。因此，这种降级只有在"业务有服务端校验兜底"时才是安全的。
>
> 更稳妥的降级思路是：**当锁服务不可用时，直接走"不依赖锁的路径"**——例如，对于库存扣减，降级为"直接执行带条件的原子 SQL"（`WHERE stock > 0`），让数据库来保证不超卖；对于防重复提交，降级为"依赖数据库唯一约束"。**与其降级到一个更弱的锁，不如降级到一个不需要锁的方案**——这与本专栏"能不用锁就不用锁"的立场一致。

### 2.5 降级链路的设计原则

把三种策略串起来，可以得到一个完整的降级链路设计：**正常路径用分布式锁；锁竞争时快速失败或有限等待；锁服务故障时熔断并切换到"不依赖锁的兜底路径"**。

这条链路的每一级都对应一种"越来越弱但越来越可靠"的保障：分布式锁提供"跨节点互斥"，服务端校验提供"数据层面的正确性"。**当强保障不可用时，退回到弱保障，而不是退回到"没有保障"**——这是降级设计的核心思想。

### 2.6 一个降级的反例

降级策略设计不当，可能比"不降级"更危险。看一个反例。

某系统为了应对 Redis 不可用，实现了"降级到本地 JVM 锁"的方案：当 Redis 连接失败时，改用本节点的 `ReentrantLock` 加锁。团队的想法是"至少单节点内还是安全的"。

问题出在跨节点场景。Redis 不可用时，**所有节点都降级到了各自的本地锁**。于是，节点 A 和节点 B 各自用"自己的本地锁"保护同一个资源——**它们之间毫无互斥可言**。原本被分布式锁挡住的并发写入，在降级期间全部放行，直接冲击数据库。而数据库又没有"原子条件更新"这类兜底，于是产生了重复扣减。

这个反例的教训是：**"降级到本地锁"这种看似合理的方案，实际上是把"跨节点互斥"降级成了"单节点互斥"，它降低的是正确性，而不是性能**。如果没有服务端校验兜底，这种降级就是"在故障时主动放弃保护"。

正确的降级方向应当是：**锁服务不可用时，切换到"不依赖锁的路径"**——例如，库存扣减改为"直接执行带条件的原子 SQL"，让数据库来保证不超卖；防重复提交改为"依赖数据库唯一约束"。**这类降级不依赖"锁"这个抽象，因此不会因为"锁服务故障"而失效**。**降级的智慧，不在于"找一个更弱的锁"，而在于"找一个不需要锁的等价方案"**。

### 2.7 一个降级链路的完整示例

把前面几节的策略串起来，给出一个"库存扣减"场景的完整降级链路，作为设计参考。

```
第一级：分布式锁加原子 SQL（最强保障）
  - 用 Redis 锁保护扣减
  - 扣减 SQL 带条件：UPDATE ... WHERE stock >= n
  - 双重保障：锁减少冲突，SQL 保证不超卖

第二级：锁竞争时的有界等待
  - tryLock(waitTime=100ms)
  - 等待超时则快速失败，返回"系统繁忙"

第三级：锁服务故障时的熔断降级
  - 熔断器检测到 Redis 不可用，切换路径
  - 跳过锁，直接执行带条件的原子 SQL
  - 数据库行锁保证同一行的扣减串行化
  - 此时"减少冲突"的能力丧失，但"不超卖"仍有保障

第四级：数据库也过载时的兜底
  - 若数据库响应超时，返回"系统繁忙"
  - 不重试、不降级到"无校验路径"
  - 宁可拒绝服务，也不破坏数据
```

这条链路的每一级都在回答同一个问题：**"当上一层保障不可用时，下一层能否仍然守住'不超卖'这条底线？"** 答案是能——因为它把"正确性"锚定在了数据库的原子 SQL 上，而锁只是"减少冲突"的优化层。**这正是本专栏反复强调的架构原则：把正确性锚在最可靠的一层，让其他层只负责优化**。

## 第 3 章 监控与告警：让锁的状态可观测

### 3.1 分布式锁应该暴露哪些指标

分布式锁是系统的关键基础设施，其运行状态应该纳入监控体系。以下是最重要的监控指标。

**指标一，锁等待时间（P50/P95/P99）**：

```
lock_wait_duration_seconds{lock_key="inventory:product:*", quantile="0.99"}
```

等待时间的 P99 突然升高，通常预示着锁竞争加剧（可能是热点锁或锁持有时间过长）。

**指标二，加锁成功率**：

```
lock_acquire_success_rate = lock_acquired_total / lock_attempt_total
```

加锁成功率持续低于 95%，说明系统存在严重的锁竞争或锁服务问题。

**指标三，锁持有时间（P50/P95/P99）**：

```
lock_hold_duration_seconds{lock_key="payment:process:*", quantile="0.99"}
```

锁持有时间的 P99 突然升高，可能是临界区操作变慢（如数据库查询变慢、外部 API 超时），也可能是锁泄漏（持锁后未释放）。

**指标四，加锁失败计数（按失败原因分类）**：

```
lock_acquire_failed_total{reason="timeout"}    # 等待超时
lock_acquire_failed_total{reason="error"}      # 锁服务异常
```

**指标五，Watch 触发频率（ZooKeeper 方案特有）**。Watch 事件频率可以反映锁竞争的激烈程度。频率过高说明锁争用严重，可能需要优化锁粒度。

这五个指标覆盖了分布式锁的"等待、获取、持有、失败、竞争"五个环节，与本专栏 01、02 篇提出的"活性度量"和"持锁与释放度量"互补，构成完整的可观测性。

### 3.2 用 Micrometer 暴露 Redisson 锁指标

```java
@Aspect
@Component
public class DistributedLockMetricsAspect {

    private final MeterRegistry meterRegistry;

    @Around("@annotation(DistributedLock)")
    public Object recordLockMetrics(ProceedingJoinPoint pjp,
                                    DistributedLock distributedLock) throws Throwable {
        String lockKey = resolveLockKey(pjp, distributedLock);

        // 记录等待时间
        long waitStart = System.currentTimeMillis();
        boolean acquired = false;

        try {
            acquired = acquireLock(lockKey, distributedLock.waitTime());
            long waitDuration = System.currentTimeMillis() - waitStart;

            meterRegistry.timer("distributed_lock.wait_duration",
                    "lock_key", maskLockKey(lockKey),  // 对动态部分做掩码，避免 cardinality 爆炸
                    "acquired", String.valueOf(acquired))
                .record(waitDuration, TimeUnit.MILLISECONDS);

            if (!acquired) {
                meterRegistry.counter("distributed_lock.acquire_failed",
                        "lock_key", maskLockKey(lockKey),
                        "reason", "timeout")
                    .increment();
                throw new LockAcquireException("获取分布式锁超时: " + lockKey);
            }

            // 记录持有时间
            long holdStart = System.currentTimeMillis();
            try {
                return pjp.proceed();
            } finally {
                long holdDuration = System.currentTimeMillis() - holdStart;
                meterRegistry.timer("distributed_lock.hold_duration",
                        "lock_key", maskLockKey(lockKey))
                    .record(holdDuration, TimeUnit.MILLISECONDS);
            }
        } finally {
            if (acquired) {
                releaseLock(lockKey);
            }
        }
    }

    /**
     * 对锁 key 中的动态部分做掩码，防止 Prometheus label cardinality 爆炸
     * 例：inventory:product:P001 → inventory:product:{id}
     */
    private String maskLockKey(String lockKey) {
        return lockKey.replaceAll(":[0-9a-zA-Z-]{8,}", ":{id}");
    }
}
```

> [!warning] Prometheus 的 Cardinality 陷阱
> 监控系统（如 Prometheus）中，每个唯一的 label 组合都会产生一个时序（Time Series）。如果把动态的 lock_key（如包含 userId、orderId）直接作为 label，会产生海量不同的时序，导致 Prometheus 的内存暴涨（Cardinality 爆炸）。
>
> 解决方案是对 lock_key 做掩码，把动态部分替换为占位符（`{id}`），只保留 key 的结构信息，而不是具体值。例如：`inventory:product:P001` 变成 `inventory:product:{id}`。
>
> 这个陷阱之所以普遍，是因为**"给每个具体的锁打标签"看起来更精细，实际却会压垮监控系统**。监控的粒度应当匹配"你想观察的维度"（如按业务模块、按锁类型），而不是"每一个具体对象"。

### 3.3 告警阈值参考

| 指标 | 告警阈值（参考）| 告警级别 | 可能的根因 |
| :--- | :--- | :--- | :--- |
| 锁等待时间 P99 > 500ms | > 500ms（持续 2 分钟）| WARNING | 锁竞争加剧、锁持有时间过长 |
| 锁等待时间 P99 > 2s | > 2s（持续 1 分钟）| CRITICAL | 热点锁、死锁或锁泄漏 |
| 加锁成功率 < 95% | < 95%（持续 5 分钟）| WARNING | 高并发锁竞争 |
| 加锁成功率 < 80% | < 80%（持续 2 分钟）| CRITICAL | 锁服务异常或系统过载 |
| 锁持有时间 P99 > 10s | > 10s（持续 2 分钟）| WARNING | 临界区操作变慢或锁泄漏 |
| Redis 连接错误率 > 1% | > 1%（持续 1 分钟）| CRITICAL | Redis 实例故障 |

这些阈值是"参考值"，实际应当结合业务的正常水位来设定。**阈值设定的原则是"基于历史基线，而非拍脑袋"**——先观察一段时间的正常值，再在正常值的若干倍处设阈值。

### 3.4 监控的一个实践：锁的健康看板

把上述指标组织成一块"锁健康看板"，能让"沉默的故障"变得可见。建议包含四个面板。

**面板一，等待时间趋势**。按锁类型（如 `inventory:*`、`order:*`）分组，展示 P50/P95/P99 的时间趋势。**趋势比绝对值更重要**——等待时间"从 5ms 涨到 50ms"这个变化，比"当前是 50ms"更能说明问题。

**面板二，成功率与失败原因**。展示加锁成功率，并按失败原因（超时、错误）细分。失败原因的变化，能区分"竞争加剧"与"服务故障"。

**面板三，持有时长分布**。展示锁持有时间的分布。**持有时长 P99 逼近 TTL，是双持风险最直接的预警**。

**面板四，异常锁计数**。包括"TTL 为 -1 的锁数量""长期处于中间态的锁数量"等。这些是锁泄漏与悬挂的直接指标。

这四个面板的共同作用是：**把"锁是否健康"从一种需要事后排查的疑问，变成一种可以实时观察的状态**。**当锁的问题能在看板上"提前看到"时，就不必等到业务出故障才去排查**——这正是可观测性的核心价值。**一个没有锁看板的系统，等于在黑暗中开锁，只能等撞上问题才知道它坏了**。

### 3.5 一个与降级配套的演练机制

降级路径有一个残酷的特点：**它平时从不被使用，只在故障时才生效**。因此，如果不主动演练，就无法知道它是否真的能工作。

一个常见的窘境是：某次 Redis 真的挂了，熔断器触发，系统切到降级路径——结果发现降级路径里有 bug（如依赖了一个在 Redis 不可用时同样不可用的组件），导致故障从"锁不可用"扩大成了"服务完全不可用"。**降级路径从未被验证过，等于不存在**。

因此，建议把"降级演练"纳入常态化的混沌工程：**定期在测试环境（甚至生产环境的低峰期）主动触发熔断，验证降级路径的正确性**。演练的内容包括：熔断是否正确触发、降级路径是否被正确调用、降级路径是否守住了数据底线、熔断恢复后是否正常回切。

这个机制的价值在于：**它把"降级策略"从一份"文档里的预案"，变成了一个"被验证过的能力"**。**在分布式系统里，任何"只在故障时生效"的机制，都必须经过演练才能被信任**——这与备份恢复、故障转移是同一类要求：**没有演练过的预案，都只是纸上的预案**。

## 第 4 章 典型生产故障复盘

### 4.1 故障案例一：Redis 主从切换导致双写（超卖事故）

**故障背景**：某大促活动期间，秒杀系统使用 Redis 主从架构的分布式锁保护库存扣减。活动期间，Redis Master 因内存压力 OOM，被系统 Kill，Sentinel 自动把 Slave 提升为新 Master。

**故障过程**：

```
T1: 客户端 A 向 Master 加锁成功（SET lock:product:P001 "client_A" NX PX 30000）
T2: 扣减操作写入 DB：UPDATE inventory SET stock = stock - 1 WHERE product_id = 'P001'
T3: [在数据复制到 Slave 之前] Master 因 OOM 宕机
T4: Sentinel 将 Slave 提升为新 Master（Slave 上无 lock:product:P001 记录）
T5: 客户端 B 向新 Master 加锁：SET lock:product:P001 "client_B" NX PX 30000 → 成功
T6: 客户端 B 也执行扣减：UPDATE inventory SET stock = stock - 1 WHERE product_id = 'P001'
T7: 最终 stock 被扣减 2 次，但实际上应该只有 1 件商品
→ 超卖。
```

**根本原因**：Redis 主从异步复制在 Master 宕机时存在数据丢失窗口，使得新 Master 上锁记录缺失，其他客户端可以重新加锁。**这正是 03 篇讨论的"主从复制异步性"在生产中的具体表现**。

**修复方案**：

方案 A（短期）：在数据库层面增加最终防线，通过原子 SQL 防止超卖：

```sql
-- 乐观锁兜底：只有 stock > 0 时才更新，且原子检查
UPDATE inventory
SET stock = stock - 1
WHERE product_id = 'P001' AND stock > 0;

-- 检查影响行数，如果为 0 说明库存不足
-- rows_affected = 0 → 返回"库存不足"，不写订单
```

方案 B（中期）：迁移到 ZooKeeper 分布式锁，利用 ZAB 强一致性消除主从切换的数据丢失问题。

方案 C（长期）：接受 Redis 锁的概率性失效，把数据库层的原子操作作为强一致性保障，Redis 锁作为"减少数据库压力"的优化手段，而非"唯一的互斥保障"。

**教训**：**不要把分布式锁作为数据一致性的唯一保障**。数据库层面的约束（唯一索引、乐观锁 CAS）应该作为最后一道防线，即使分布式锁偶尔失效，数据也不会损坏。这与 03 篇"正确性的最终防线应在服务端"完全一致。

### 4.2 故障案例二：看门狗续期失效导致并发执行

**故障背景**：某支付系统使用 Redisson 的可重入锁，默认看门狗 TTL 30 秒。某天凌晨进行大批量对账操作，Full GC 频繁发生。

**故障过程**：

```
T0: 对账线程 Thread-1 加锁成功，看门狗启动（每 10 秒续期一次）
T10: Thread-1 正常执行，看门狗续期成功（TTL 重置为 30 秒）
T20: Thread-1 正常执行，看门狗续期成功
T25: JVM 发生 Full GC，所有线程暂停（包括看门狗线程）
T50: [锁 TTL 在 T40 时过期，此时 Full GC 已持续 25 秒，超过剩余 TTL 10 秒]
T52: Thread-2 加锁成功（Thread-1 的锁已过期）
T55: Full GC 结束，Thread-1 恢复执行
T55~T60: Thread-1 和 Thread-2 同时对同一批账单执行对账，产生重复对账记录
```

**根本原因**：Full GC 停顿时间（25 秒）超过了看门狗剩余的 TTL（10 秒），看门狗线程被 GC 暂停期间无法续期，锁自动过期。**这正是 01 篇与 02 篇反复讨论的"GC 停顿破坏锁有效性"的实例**。

**修复方案**：

方案 A（短期）：增大看门狗 TTL（从 30 秒增加到 120 秒），给 GC 停顿留出更大的安全余量：

```java
Config config = new Config();
config.setLockWatchdogTimeout(120000);  // 120 秒，看门狗每 40 秒续期
```

即使 GC 停顿 40 秒，锁仍有 80 秒的剩余 TTL，续期可以在 GC 结束后恢复。

方案 B（中期）：升级 JVM GC 算法为 ZGC，把 GC 停顿时间控制在 10ms 以内，从根本上消除 GC 停顿超过 TTL 的可能性。

方案 C（长期）：在对账操作层面实现幂等性（对账记录中添加唯一约束），即使偶发的并发执行也不会产生重复记录：

```sql
CREATE UNIQUE INDEX uk_reconciliation ON reconciliation_records (batch_id, account_id);
-- INSERT IGNORE INTO reconciliation_records 即使重复也不会抛出错误
```

**教训**：**看门狗不是银弹，GC 停顿是它的死穴**。在 Full GC 频繁的系统中，必须配合低延迟 GC 算法或业务层幂等性来共同保证安全。**三个方案的优先级很清晰：短期缓解（调 TTL）、中期根治（换 GC）、长期兜底（幂等）**——其中"幂等"是最根本的一层，因为它不依赖任何锁的假设。

### 4.3 故障案例三：锁泄漏（Lock Leak）

**故障背景**：某订单系统在某次发版后，发现系统 QPS 持续下降，订单创建接口响应时间从 100ms 升高到 5 秒以上，甚至超时。

**故障排查**：

```bash
# 通过 Redis CLI 扫描持续存在的锁 key
redis-cli SCAN 0 MATCH "order:create:*" COUNT 1000

# 发现大量 order:create:user:* 的 key，且 TTL 均为 -1（永不过期）
redis-cli TTL order:create:user:123456
# 返回：-1（表示没有设置 TTL）
```

所有正常的 Redisson 锁都应该有 TTL（由看门狗维护），TTL 为 -1 是异常状态，说明这些锁被手动 SET 写入，绕过了 Redisson 的 TTL 机制。

**根因定位**：某个同学在代码 review 中发现了一处"优化"代码：

```java
// 错误代码（某次"优化"引入）
// 开发者误以为直接 SETNX 更简单，但忘记了 Redisson 锁是 Hash 结构
redisTemplate.opsForValue().setIfAbsent("order:create:user:" + userId, "locked");
// 没有设置 TTL，锁永远不会过期。
```

这段代码使用了 Spring 的 `redisTemplate` 直接写入 String 类型的 key，没有设置 TTL。后续的 Redisson 加锁操作使用 `exists()` 检查 key 是否存在，发现 key 已存在（虽然是 String 类型而不是 Hash 类型），直接返回加锁失败，导致所有后续的加锁请求永远失败。

**修复方案**：

其一，立即清理所有 TTL 为 -1 的异常锁 key：

```bash
# 扫描并删除 TTL = -1 的 order:create:* key（谨慎执行，先确认影响范围）
redis-cli --scan --pattern "order:create:*" | while read key; do
    ttl=$(redis-cli TTL "$key")
    if [ "$ttl" = "-1" ]; then
        redis-cli DEL "$key"
        echo "Deleted: $key"
    fi
done
```

其二，代码规范：统一使用 Redisson 接口操作分布式锁，禁止通过 `redisTemplate` 直接操作锁 key。

其三，监控加固：增加告警规则，当 `order:create:*` 的 key 出现 TTL 为 -1 时立即告警。

**教训**：**分布式锁的操作必须通过统一的封装层进行，禁止绕过锁框架直接操作 Redis 或 ZooKeeper**。可以通过 Code Review 规范和静态代码分析工具强制执行。

这个案例还有一个更深层的教训：**"锁的 key"应当被视为框架的私有数据结构，而不是普通的 Redis key**。Redisson 用 Hash 存锁、ZK 用特定路径存锁，这些结构都有约定；一旦有人用"更简单的写法"绕过它，就会制造出框架无法理解的"畸形锁"。**把框架的内部结构当普通数据操作，是很多"锁莫名失效"的根源**。

### 4.4 故障案例四：ZooKeeper 羊群效应导致 ZK 集群雪崩

**故障背景**：某平台使用朴素的 ZooKeeper 锁（监听单一锁节点，所有等待者同时竞争），某次高峰期出现 ZooKeeper 集群响应时间飙升，最终 Leader 失联，触发 Leader 选举，服务中断约 30 秒。

**故障过程**：

```
正常状态：约 500 个并发请求在等待同一把 ZK 锁
锁释放时：500 个客户端同时收到 Watch 通知
         → 500 个并发 EPHEMERAL 节点创建请求涌向 ZK Leader
         → ZK Leader 处理队列瞬间爆满（正常处理能力约 1000 TPS）
         → ZK 处理延迟飙升
         → 客户端 heartbeat 超时（因为 ZK 处理线程忙于处理锁请求，无法及时处理 heartbeat）
         → 大量 Session 超时，临时节点被删除
         → 又触发新一轮 Watch 通知
         → 雪崩。
```

**根本原因**：使用了朴素的"所有等待者监听同一节点"的 ZK 锁实现，锁释放时产生羊群效应，500 个并发唤醒请求瞬间压垮 ZK Leader。**这正是 04 篇讨论的"羊群效应"在生产中的放大版**——它不仅拖慢锁操作，还会通过"心跳超时导致 Session 过期"引发雪崩。

**修复方案**：迁移到临时顺序节点加监听前驱节点的公平锁实现（使用 Apache Curator `InterProcessMutex`），彻底消除羊群效应。迁移后，即使有 500 个等待者，每次锁释放只唤醒 1 个客户端，ZK Leader 的负载平稳正常。

**教训**：**不要自己实现 ZooKeeper 分布式锁，直接使用 Apache Curator**。Curator 的实现已经处理了羊群效应、Watch 窗口期等所有边界情况，手工实现极易引入这类隐藏 Bug。

### 4.5 四个故障的共性根因

把四个故障放在一起看，会发现它们共享几条共性根因。

**根因一，把锁当成了"绝对可靠"的东西**。四个故障都源于"以为锁一定能保证互斥"——而实际上锁会在主从切换、GC 停顿、人为绕过、惊群等情况下失效。

**根因二，缺少服务端的最终防线**。四个故障中，如果业务有"服务端校验"（原子 SQL、唯一约束、幂等），后果都会从"数据错乱"降级为"重复执行被拦截"。**服务端校验的缺失，把小概率的锁失效放大成了实际的数据事故**。

**根因三，可观测性不足**。锁泄漏故障是靠"扫描 Redis 发现 TTL 为 -1"才定位的；如果早有"锁 TTL 异常"的监控，本可以提前发现。**故障的"沉默"特性，让可观测性成了必需品**。

这三条共性根因，恰好对应本专栏反复强调的三条原则：**锁不是银弹、正确性靠服务端、可观测性是必需**。**故障复盘的价值，不在于记住"某个案例怎么修"，而在于看清"为什么同类问题会反复发生"**。

### 4.6 故障案例五：误解锁导致的双持

前面四个故障都涉及"锁本身失效"，还有一个故障源自"解锁操作不当"——误解锁，它同样会造成双持。

**故障背景**：某系统用 Redis 锁保护定时任务的执行，代码里解锁时直接用了 `DEL lock_key`，没有校验 value 归属。

**故障过程**：

```
T1: 客户端 A 加锁成功，value = "client_A:token_001"，TTL = 30 秒
T2: 客户端 A 执行任务，因一次外部调用阻塞，耗时 35 秒
T3: [T1 后 30 秒] 锁 TTL 到期，被 Redis 自动删除
T4: 客户端 B 加锁成功，value = "client_B:token_002"
T5: 客户端 B 开始执行同一任务
T6: [T1 后 35 秒] 客户端 A 的任务终于执行完，调用 DEL lock_key 解锁
T7: 客户端 A 删除了客户端 B 的锁。
T8: 客户端 C 随即加锁成功，也开始执行同一任务
→ 三个客户端在很短的时间内都执行了同一任务
```

**根本原因**：解锁时没有校验 value 归属，导致"过期的客户端"删掉了"当前持有者"的锁。**这正是 01 篇与 02 篇反复强调的"幽灵重复"场景**。

**修复方案**：把解锁改为 Lua 脚本，先校验 value 再删除（即 02 篇的标准解锁脚本）：

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

同时，把任务的执行改为幂等（用任务 ID 加执行日期做唯一键），即使误解锁导致重复执行，也不会产生重复的业务效果。

**教训**：**解锁必须校验归属**。这个要求在 02 篇就讲过，但它之所以在生产中反复出现，是因为"直接 DEL"看起来更简单、也"通常没问题"——只有在锁恰好过期、且恰好被他人重新获取的时序下才会出事。**这类"小概率但后果严重"的错误，恰恰是最需要在代码规范层面强制禁止的**。这也是为什么应当统一使用框架（Redisson 的 `unlock()` 已内置校验），而不是自己手写 `DEL`。

### 4.7 故障案例六：锁风暴

最后一个案例与前面几个不同，它不来自"锁失效"，而来自"重试放大"——锁风暴。

**故障背景**：某系统在高峰期出现"Redis 响应变慢"的连锁反应。排查发现，Redis 的命令队列在某一刻堆积了大量 `SET ... NX` 命令，而这些命令几乎全部来自同一个业务模块。

**故障过程**：

```
T0: 某热点锁（如爆款商品库存）被一个客户端持有
T1: 大量等待者（约 5000 个）开始轮询重试
T2: 这些等待者采用固定间隔（如 50ms）重试，且间隔完全一致
T3: 每 50ms，约 5000 个 SET NX 命令同时到达 Redis
T4: Redis 的处理队列被这些无效请求占满，正常请求也开始排队
T5: 业务整体延迟上升，更多请求超时并重试
T6: 重试进一步放大 Redis 压力 → 恶性循环
```

**根本原因**：等待者采用**固定间隔、无随机化**的轮询重试，导致所有等待者的重试"同步化"，形成周期性的请求尖峰。**这正是 06 篇讨论的"惊群效应"在生产中的放大版**。

**修复方案**：

其一，**随机化重试间隔**（Jitter）：把固定 50ms 改为"10 到 150ms 随机"，打散重试的同步性。

其二，**改用事件通知而非轮询**：Redisson 的 Pub/Sub 等待机制，在锁释放时才唤醒等待者，避免了无意义的轮询。

其三，**对等待者做限流或排队**：如果热点锁的等待者必然很多，可以在业务层前置一个队列，让请求有序进入，而不是全部涌向锁服务。

**教训**：**锁的等待策略，与锁的获取策略同样重要**。一个设计良好的锁，不仅要"能正确加锁"，还要"在竞争激烈时不拖垮锁服务"。**固定间隔轮询是锁风暴的经典成因，随机退避与事件通知是它的标准解药**——这与 06 篇的结论完全一致。

## 第 5 章 分布式锁的测试方法

### 5.1 单元测试：验证基本语义

```java
@Test
public void testMutualExclusion() throws InterruptedException {
    String lockKey = "test:mutex:lock";
    AtomicInteger concurrentCount = new AtomicInteger(0);
    AtomicBoolean mutexViolated = new AtomicBoolean(false);
    int threadCount = 10;
    CountDownLatch latch = new CountDownLatch(threadCount);

    for (int i = 0; i < threadCount; i++) {
        new Thread(() -> {
            RLock lock = redissonClient.getLock(lockKey);
            try {
                lock.lock();
                try {
                    // 进入临界区，验证同时只有一个线程
                    int current = concurrentCount.incrementAndGet();
                    if (current > 1) {
                        mutexViolated.set(true);  // 互斥性被破坏。
                    }
                    Thread.sleep(50);  // 模拟业务操作
                    concurrentCount.decrementAndGet();
                } finally {
                    lock.unlock();
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            } finally {
                latch.countDown();
            }
        }).start();
    }

    latch.await(30, TimeUnit.SECONDS);
    assertFalse("互斥性被破坏，", mutexViolated.get());
}
```

### 5.2 混沌工程测试

在测试环境中模拟各种故障场景，验证系统的容错能力：

1. **Redis 主从切换**：在持锁期间强制杀掉 Redis Master，验证系统行为
2. **网络分区**：使用 `tc` 命令注入网络延迟，验证锁操作的超时处理
3. **GC 压力注入**：使用 `-XX:+UseSerialGC` 强制使用串行 GC，制造 Full GC 场景，验证看门狗续期
4. **进程 Kill**：在持锁期间 `kill -9` 持锁进程，验证 TTL 过期后锁能被正确释放

### 5.3 测试的三个层次

分布式锁的测试应当覆盖三个层次，缺一不可。

**第一层，功能测试**。验证"互斥、可重入、公平、超时"等基本语义正确。这是 5.1 节的内容。

**第二层，故障注入测试**。验证"锁失效时业务会怎样"。这是 5.2 节的内容——**它的重点不是"验证锁还正确"，而是"验证业务的兜底机制生效"**。

**第三层，容量与竞争测试**。验证在高并发、热点竞争下，锁的等待时间与成功率是否在可接受范围。**这一层测试常常被忽视，但它是发现"锁粒度不合理"的最直接手段**。

这三个层次的共同点是：**它们测试的不是"锁能不能用"，而是"锁在压力与故障下表现如何"**。**分布式锁的正确性，只有在前两层都通过、第三层也达标时，才算真正被验证过**。

### 5.4 上线前的灰度策略

即使测试通过，分布式锁的上线也应当灰度推进，因为它的很多问题"只在真实流量下才暴露"。

**第一步，小流量接入**。先在一个低风险的业务场景接入，观察锁的等待时间、成功率、持有时长是否在预期范围。

**第二步，逐步扩量**。按流量比例逐步扩大接入范围，每一步都观察指标是否有异常变化。**扩量的过程，也是验证"锁粒度是否合适"的过程**——如果扩量后等待时间急剧上升，说明粒度可能过粗。

**第三步，故障演练**。在灰度期间，主动注入故障（如杀掉 Redis 主节点），验证降级链路是否按预期工作。**这一步最容易被省略，却最有价值**——因为"降级策略能不能生效"，只有在真实故障时才见分晓。

**第四步，全量与复盘**。全量接入后，复盘各项指标，确认是否符合预期，并把观察到的正常水位固化为告警基线。

这个灰度策略的核心思想是：**锁是一个"出问题就影响数据"的组件，因此它的引入必须"可控、可观测、可回退"**。**把"上线一把锁"当作一次生产变更来管理**，而不是"改完代码就发布"——这是把前六篇的理论，真正落到工程纪律上的一步。

### 5.5 一个测试清单

把测试应当覆盖的项目汇总成清单，便于逐项确认。

**语义测试**：互斥性（多线程临界区不重叠）、可重入性（嵌套加锁不死锁）、公平性（如启用）、超时行为（等待超时与持有超时）。

**边界测试**：锁过期后他人能否加锁、误解锁是否被拒绝（value 校验）、重复解锁是否幂等、空回滚与悬挂（如适用）。

**故障测试**：锁服务主从切换、网络分区、GC 停顿注入、持锁进程被 Kill、锁服务重启。

**竞争测试**：热点锁的等待时间分布、加锁成功率、锁风暴（大量等待者同时重试）的表现。

**降级测试**：熔断触发后是否切换到正确路径、降级路径是否仍然守住数据底线、熔断恢复后是否正常回切。

这五类测试的覆盖顺序应当是：**先保证语义正确，再验证边界，然后注入故障，最后压竞争与降级**。**其中"故障测试"与"降级测试"最容易被省略，却最能反映"锁失效时系统是否安全"**——而这恰恰是分布式锁最需要被验证的部分。**一个只测了"正常情况"的锁，等于没测**。

### 5.6 一个上线检查清单

把本篇的内容汇总为上线前的检查清单，逐项确认后再发布。

**必要性**：这把锁真的必要吗？能否用数据库原子操作、幂等或队列替代？

**粒度**：锁的 key 覆盖了所有需要保护的约束吗（单商品、总量、单用户）？有没有漏掉的约束？

**超时**：`waitTime` 与接口超时预算对齐了吗？业务时间不确定时启用看门狗了吗？有没有"图省事"设的过短 `leaseTime`？

**兜底**：如果这把锁失效，业务会怎样？有服务端校验（唯一约束、原子 SQL）兜底吗？

**监控**：等待时间、成功率、持有时长、失败原因、TTL 异常，这些指标都采集并配置告警了吗？

**降级**：锁服务故障时切换到什么路径？这条路径演练过吗？它守住了数据底线吗？

**释放**：解锁在 `finally` 中吗？有绕过框架直接操作锁 key 的代码吗？

**演练**：做过故障注入（主从切换、GC 停顿、进程 Kill）测试吗？

这八项覆盖了"选锁、配锁、用锁、验锁"的全过程。**其中最容易遗漏的是"兜底"与"演练"两项**——前者决定了"锁失效时业务是否安全"，后者决定了"降级路径是否真的能工作"。**把这份清单固化为团队的发布门禁，是把前七篇的理论转化为工程纪律的最后一环**。

## 第 6 章 小结：生产实践的三个关键词

把本篇的内容收敛，可以得到三个关键词。

**粒度**。锁粒度决定了并发上限，它是最容易被忽视的架构决策。**设计锁的第一步，不是"选哪种锁"，而是"想清楚锁该多细"**。

**兜底**。任何锁都可能失效，因此必须有一层"服务端校验"作为最终防线。**降级的目标不是"降级到更弱的锁"，而是"降级到不需要锁的方案"**。

**可观测**。锁的失效是沉默的，因此监控不是可选项。**等待时间、成功率、持有时长、失败原因、TTL 异常**——这些指标是发现问题的前提。

这三个关键词，把前六篇的理论落到了生产现场。**它们共同指向一个结论：分布式锁的可靠性，不只取决于"锁本身"，更取决于"围绕锁的整套工程设计"**——粒度、兜底、监控，缺一不可。

### 6.1 一个"锁治理"的组织建议

分布式锁的很多问题，最终是"协作问题"而非"技术问题"——而协作问题需要靠规范与流程来解决。

**建议一，建立锁的登记与审查机制**。把系统里所有的分布式锁登记在一处（如一份文档或一个配置中心），记录它的 key、用途、负责人、引入时间。定期（如每季度）审查：这把锁还有必要吗？粒度还合适吗？**登记的价值在于让"锁"从"散落在各处的代码"变成"可被集中审视的资产"**。

**建议二，统一锁的接入方式**。提供统一的锁封装（如一个 `@DistributedLock` 注解加配套的切面），禁止各团队自行用 `redisTemplate` 或原生 ZK 客户端操作锁。**统一接入的价值在于把"正确使用"从"个人经验"变成"框架保障"**——07 篇的锁泄漏故障，根源正是"有人绕过了框架"。

**建议三，把上线检查清单变成发布门禁**。把 5.6 节的检查清单纳入发布流程，作为"涉及锁的变更"必须通过的检查项。**门禁的价值在于让"关键检查"不再依赖个人的自觉**。

**建议四，把降级演练纳入常态化**。定期演练锁服务故障的降级路径，验证它真的能工作。

这四条建议的共同逻辑是：**分布式锁的正确性，需要"技术加组织"共同保证**。技术手段（框架、监控）能减少个人犯错的空间，组织手段（登记、审查、门禁）能保证"关键动作被执行"。**一个只有技术手段、没有组织手段的锁体系，会随着团队扩张与人员流动而逐渐失控**——而"失控的锁体系"，正是本专栏反复强调的那些故障的温床。

### 7.4 一个延伸：锁的"容量规划"

锁的容量规划，常被忽视——但"锁"本身也消耗资源，需要规划。

**资源一，"锁 key 的数量"**。**每一把不同的锁对应一个 key**——**如果 key 设计得"太细"（如"每用户每商品一把"），key 数量可能爆炸**。**因此，key 的粒度要"恰好覆盖竞争维度"，不能过细**。

**资源二，"Redis 的内存"**。**锁 key 占用 Redis 内存**——**虽然单个 key 很小，但如果"锁数量巨大"（如百万级），内存占用就不可忽视**。**因此，锁 key 应当"尽量少、尽量短"**。

**资源三，"Redis 的连接与 QPS"**。**加锁、解锁、续期都是 Redis 命令**——**高并发下，"锁的 QPS"可能成为 Redis 的负担**。**因此，要"监控锁相关的 QPS"，并考虑"锁是否必要"**。

**资源四，"等待队列的深度"**。**等待锁的客户端会占用"线程/连接"**——**如果等待者过多，可能耗尽资源**。**因此，要有"等待超时"与"快速失败"**。

**这四项资源的共同点是"它们都容易被忽视，因为'锁'看起来'不占资源'"**——**但"百万个锁 key""每秒十万次加锁"，都会实实在在消耗资源**。

**这条延伸的启示是**：**"任何机制都有资源成本"，包括"看起来轻量"的锁**。**因此，容量规划要"把所有组件都算进去"**——**而不是"只算业务数据"**。**这也是"可观测性"的价值：只有监控了，才知道"锁消耗了多少资源"**。
