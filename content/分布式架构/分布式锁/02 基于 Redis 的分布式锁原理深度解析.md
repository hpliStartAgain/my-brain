# 02 基于 Redis 的分布式锁原理深度解析

**摘要：**

Redis 分布式锁是工业界最广泛使用的分布式锁实现，其演进历程本身就是一部分布式系统工程实践的教科书——从最朴素的 `SETNX + EXPIRE` 两步操作，到 `SET NX PX` 的单命令原子化，再到 Lua 脚本保证解锁原子性，最后到 Redisson 框架的看门狗续期与可重入支持，每一步演进都是为了修补上一步方案的安全漏洞。本文按照这条演进脉络，逐层深入分析每个阶段的设计动机、实现细节与残余缺陷；剖析 Redis 单线程模型在分布式锁中的作用；完整解析 Redisson 的看门狗机制与可重入锁实现；最后梳理单节点 Redis 锁仍无法覆盖的失效场景，为 Redlock 与 ZooKeeper 方案的引入做铺垫。读完本文，你应当能回答两个问题：为什么"两步操作"注定不可靠，以及看门狗到底解决了什么、又没能解决什么。

---

## 第 1 章 Redis 为什么适合做分布式锁

在深入研究 Redis 分布式锁的具体实现之前，有必要先思考一个基础问题：Redis 具备哪些特性，使得它成为分布式锁的主流选择？这不是一个显而易见的问题——很多存储系统（MySQL、MongoDB、Memcached）也可以用来实现分布式锁，Redis 的优势究竟在哪里？

### 1.1 Redis 的单线程命令处理模型

Redis 在 6.0 版本之前，命令的执行是严格单线程的：所有客户端发来的命令被放入一个队列，由单个主线程串行处理。6.0 版本之后，Redis 引入了多线程用于网络 I/O，但命令的**执行**仍然是单线程的。

这个"单线程执行"特性对于分布式锁来说非常重要，因为它提供了一个关键保证：**任意两条 Redis 命令的执行是串行的，不会相互交错**。这意味着，只要我们能将"检查锁是否存在加设置锁"封装成一条原子命令（或一个 Lua 脚本），就能保证这个组合操作的原子性。

对比 MySQL：MySQL 的并发处理依赖多线程加锁机制，虽然事务提供了原子性，但实现分布式锁需要依赖 `SELECT ... FOR UPDATE` 或唯一索引约束，这些操作涉及磁盘 I/O，性能远不及 Redis 的内存操作。

### 1.2 Redis 的高性能内存操作

Redis 的所有数据存储在内存中，读写操作的延迟在微秒级（通常 0.1 到 1ms）。对于分布式锁这种高频操作（加锁与解锁伴随着每次临界区操作），存储系统的延迟直接影响整体系统吞吐量。

如果用 MySQL 实现分布式锁，每次加锁与解锁涉及磁盘写入，延迟可能在 1 到 10ms，对于 QPS 高达万级的接口，锁操作本身就会成为明显的性能瓶颈。

### 1.3 原生的 TTL 支持

Redis 对每个 Key 原生支持过期时间（TTL），存储层面直接处理过期逻辑——过期后 Redis 内部会自动清除该 Key，不需要应用层实现定时清理任务。

这一特性天然契合分布式锁的"无死锁"要求：持锁客户端崩溃后，锁的 TTL 到期，Redis 自动释放，其他客户端可以重新竞争。相比之下，用 MySQL 实现无死锁需要在锁记录中存储 `expire_time` 字段，并在加锁时由应用代码检查是否超期，逻辑更复杂，也更容易出错。

### 1.4 Lua 脚本的原子执行

Redis 支持 Lua 脚本，且保证同一个 Lua 脚本在 Redis 侧的执行是原子的（不会被其他命令插入执行）。这为实现"组合操作原子化"提供了强大的工具——任何需要"先检查后执行"的逻辑都可以通过 Lua 脚本实现原子性，而不需要在应用层做额外的事务处理。

### 1.5 四个特性的共同作用

把这四个特性放在一起看，会发现它们恰好对应了分布式锁的核心需求：**单线程执行**提供了"组合操作可原子化"的基础，**内存高性能**提供了高并发下的低延迟，**原生 TTL**提供了无死锁的自动释放，**Lua 脚本**提供了自定义原子逻辑的能力。

不过，这四项能力都有一个共同的边界：**它们都只保证"单个 Redis 实例内"的正确性**。一旦涉及主从复制、集群、故障切换，这些保证就会打折扣——这正是后文"正确性边界"一节要讨论的，也是 Redlock 与 ZooKeeper 方案出现的动机。**理解了"单实例内很强、跨实例很弱"这个特点，就理解了 Redis 锁的全部优势与全部风险**。

## 第 2 章 SETNX 方案的演进：从两步操作到单命令原子化

### 2.1 第一代方案：SETNX 加 EXPIRE

分布式锁最早的 Redis 实现，使用两条命令组合：

```redis
SETNX lock_key "client_value"   # 如果 key 不存在则设置，返回 1（成功）或 0（已存在）
EXPIRE lock_key 30              # 设置 30 秒过期
```

`SETNX`（SET if Not eXists）是 Redis 提供的原子性条件写入命令：只有当 `lock_key` **不存在**时，才执行写入并返回 1；如果已存在，直接返回 0。这个原子性保证了"检查加写入"在 Redis 层面不会被并发请求打断。

**SETNX 返回 1**：说明在这个瞬间，没有其他客户端持有锁，当前客户端成功获取锁。

**SETNX 返回 0**：说明锁已被其他客户端持有，当前客户端获取锁失败，需要等待或重试。

这个方案看似合理，但存在一个**致命缺陷**：`SETNX` 和 `EXPIRE` 是两条独立的命令，它们之间没有原子性保证。考虑以下故障场景：

```
时间线：
T1: 客户端 A 执行 SETNX lock_key "client_A"，返回 1（加锁成功）
T2: 客户端 A 所在服务器宕机，进程崩溃
T3: EXPIRE 命令永远不会被执行
T4: lock_key 永久存在，没有 TTL
T5: 其他所有客户端尝试 SETNX，永远返回 0
T6: [系统进入死锁状态]
```

一行服务崩溃在 `SETNX` 成功之后、`EXPIRE` 执行之前，就足以让整个分布式锁系统陷入永久死锁。在生产环境中，这种"代码执行到一半崩溃"的场景并不罕见：进程 OOM 被系统 Kill、服务发版重启、物理机断电，任何一种情况都可能触发这个 Bug。

**一个历史性的"聪明"补丁**：

在 `SET NX PX` 命令出现之前，有人提出了一个"巧妙"的修复方案——把过期时间戳作为 value 存储，在 SETNX 失败时读取 value，判断锁是否已经过期，如果过期则用 `GETSET` 命令强制替换：

```python
def acquire_lock_with_timeout(lock_key, acquire_timeout, lock_expire):
    value = time.time() + lock_expire  # 锁的过期时间戳

    if redis.setnx(lock_key, value):
        return value  # 加锁成功

    # 加锁失败，检查当前锁是否已超期
    current_value = redis.get(lock_key)
    if current_value and float(current_value) < time.time():
        # 锁已超期，用 GETSET 替换
        old_value = redis.getset(lock_key, value)
        if old_value == current_value:
            return value  # 替换成功，加锁成功

    return None  # 加锁失败
```

这个方案虽然解决了死锁问题，但引入了新的问题：

1. **时钟依赖**：不同机器的时钟可能不同步，时间戳比较不可靠
2. **竞争窗口**：两个客户端可能同时检测到锁超期，都执行 GETSET，最终第二个 GETSET 的客户端会覆盖第一个，导致第一个客户端误认为加锁成功
3. **代码复杂**：理解和维护成本高，容易出 Bug

这个"聪明"方案的存在，恰好说明了为什么需要一个真正原子的加锁命令。**它的失败也提供了一个通用教训：用多条命令去"拼凑"原子性，几乎总会在某个时序下露出破绽**——因为"检查"与"执行"之间的窗口无法被应用层消除，只能被下推到存储层。

### 2.2 第二代方案：SET NX PX

Redis 2.6.12 版本引入了对 `SET` 命令的扩展参数，允许在一条命令中同时完成"条件设置加过期时间设置"：

```redis
SET lock_key "client_A:token_uuid" NX PX 30000
```

参数说明：

- `NX`：Only set the key if it does **N**ot e**X**ist（与 SETNX 语义相同）
- `PX 30000`：设置 30000 毫秒（30 秒）后过期（也可用 `EX 30` 设置秒级过期）

这是一条原子命令——Redis 在单次命令处理中同时完成了"检查 key 是否存在加写入 key 加设置 TTL"，不存在中间被打断的可能。从此，第一代方案中 SETNX 和 EXPIRE 之间的"原子性窗口"彻底消失。

**关于 value 的设计**：

注意，value 不能是一个固定字符串（如 `"locked"`），而应该是一个能唯一标识当前持锁客户端的值。原因在于解锁的正确性——解锁时需要确认"当前锁是否确实由自己持有"，如果 value 固定，就无法区分"是我加的锁"和"别人加的锁"。

value 的推荐生成方式：

```python
import uuid
# 方式 1：纯随机 UUID（适合大多数场景）
lock_value = str(uuid.uuid4())

# 方式 2：客户端 ID + 线程 ID + 时间戳（可追溯，适合调试）
lock_value = f"{socket.gethostname()}:{os.getpid()}:{threading.current_thread().ident}:{time.time()}"
```

用 UUID 作为 value，每次加锁生成一个全局唯一的令牌，解锁时只删除 value 与当前令牌匹配的 key——这样即使锁因 TTL 超期被自动删除，再被其他客户端重新获取后，老客户端尝试用旧令牌解锁也不会成功（value 不匹配，解锁失败），从而避免了"解错他人的锁"的问题。

### 2.3 加锁命令正确了，但解锁还有问题

`SET NX PX` 解决了加锁的原子性问题，但解锁操作仍然存在隐患。

最朴素的解锁方式是直接 `DEL lock_key`：

```python
redis.delete(lock_key)
```

但这是不安全的，原因在 01 篇已经分析过：如果持锁客户端的 TTL 到期后锁被自动释放，另一个客户端重新获取了锁，此时第一个客户端执行 `DEL` 会删掉第二个客户端的锁，造成互斥性破坏。

正确的解锁逻辑是：**先验证 value 是否匹配（确认是自己的锁），再删除**：

```python
current_value = redis.get(lock_key)
if current_value == my_lock_value:
    redis.delete(lock_key)
```

但这里有一个新的原子性问题：`GET` 和 `DEL` 是两条命令，两条命令之间有窗口期：

```
时间线（并发场景）：
T1: 客户端 A 执行 GET lock_key，返回 "client_A:token_001"
T2: [客户端 A 的 TTL 刚好在此时到期，锁被 Redis 自动删除]
T3: 客户端 B 执行 SET NX PX，加锁成功，value = "client_B:token_002"
T4: 客户端 A 执行 DEL lock_key（因为 T1 时 GET 返回的是自己的 value，判断通过了）
T5: 客户端 A 删除了客户端 B 的锁。
```

这个窗口期虽然概率极低，但在生产系统中这种"极低概率"事件终究会发生，特别是在高并发场景下。解决这个问题，需要把"GET 校验加 DEL 删除"变成一个原子操作——这正是 Lua 脚本的用武之地。

> [!warning] "检查加操作"的窗口是分布式锁的通用陷阱
> 从 SETNX 加 EXPIRE 的窗口，到 GET 加 DEL 的窗口，本质上是同一个问题：**应用层的"检查"与"操作"之间总有一个无法消除的时间差**。只要这个时间差存在，其他客户端就可能在这个窗口里改变状态，让检查的结论失效。解法只有两条：要么把检查与操作合并为存储层的单条原子命令，要么用存储层的脚本把多条命令打包成原子块。记住这个模式，后面遇到的每一个"原子性修复"，几乎都是它的应用。

### 2.4 从 SETNX 到 SET：一条命令的演进说明了什么

`SETNX` 到 `SET NX PX` 的演进，看起来只是一条命令的参数扩展，但它揭示了一个更深的设计规律：**当多个独立操作必须原子地完成时，正确的做法是把它们"合并成一个原语"，而不是在应用层"想办法串起来"**。

第一代方案试图用"两条命令加判断"来模拟原子性，结果处处是窗口；第二代方案直接把"条件判断加写入加过期"做成一条命令的参数，窗口自然消失。这与数据库领域的发展如出一辙：早期用"读加比较加写"实现乐观锁（有窗口），后来有了 `INSERT ... ON DUPLICATE KEY UPDATE` 这类"带条件的原子写"（无窗口）。**把常见的原子组合下沉为原语，是存储系统提升可靠性的通用手段**。

理解了这条规律，也就理解了为什么 Lua 脚本如此重要——它是这条规律的"通用版"：当存储系统没有预置你需要的原子原语时，Lua 脚本让你自己定义一个。**从"依赖预置原语"到"自定义原子单元"，是使用 Redis 做并发控制的一次关键能力跃升**。

## 第 3 章 Lua 脚本：原子化解锁的标准方案

### 3.1 Redis Lua 脚本的原子性保证

Redis 执行 Lua 脚本时，整个脚本被视为一个原子操作——脚本执行期间，Redis 不会处理其他客户端的命令。这和 Redis 单条命令的原子性一样，都来源于 Redis 的单线程命令处理模型：脚本开始执行后，会一直运行到结束，期间没有其他命令能"插队"。

这意味着：**在 Lua 脚本中执行多条 Redis 命令，等价于在单个原子操作中执行这些命令**。"GET 校验加 DEL 删除"放进 Lua 脚本，就实现了原子性的解锁。

### 3.2 标准解锁 Lua 脚本

这是 Redis 分布式锁解锁操作的工业标准实现：

```lua
-- 解锁 Lua 脚本（Redis 官方推荐方案）
-- KEYS[1]: 锁的 key
-- ARGV[1]: 当前客户端的唯一 token（加锁时使用的 value）

if redis.call("GET", KEYS[1]) == ARGV[1] then
    -- value 匹配，确认是自己持有的锁，执行删除
    return redis.call("DEL", KEYS[1])
else
    -- value 不匹配，说明锁已被其他客户端持有（或锁已过期被删除）
    -- 不做任何操作，返回 0 表示解锁失败
    return 0
end
```

在 Java 中通过 Jedis 执行：

```java
private static final String UNLOCK_SCRIPT =
    "if redis.call('GET', KEYS[1]) == ARGV[1] then " +
    "    return redis.call('DEL', KEYS[1]) " +
    "else " +
    "    return 0 " +
    "end";

public boolean releaseLock(String lockKey, String lockValue) {
    // evalsha 或 eval 执行 Lua 脚本
    // KEYS 列表：[lockKey]
    // ARGV 列表：[lockValue]
    Object result = jedis.eval(
        UNLOCK_SCRIPT,
        Collections.singletonList(lockKey),      // KEYS
        Collections.singletonList(lockValue)      // ARGV
    );
    return Long.valueOf(1L).equals(result);
}
```

### 3.3 Lua 脚本的注意事项

**其一，脚本超时问题**。Redis 对 Lua 脚本的执行有超时限制（默认 5 秒，`lua-time-limit` 配置项）。如果脚本执行超过这个时间，Redis 不会强制终止脚本（因为终止会破坏原子性），而是进入特殊的"脚本超时"模式：

- 此时 Redis 只接受 `SCRIPT KILL` 和 `SHUTDOWN NOSAVE` 命令
- `SCRIPT KILL` 会终止当前脚本，并向脚本发送错误；但如果脚本已经执行了写操作，`SCRIPT KILL` 无法终止（防止数据不一致），只能用 `SHUTDOWN NOSAVE` 终止 Redis 进程

对于分布式锁的解锁脚本，逻辑极简（只有一次 GET 和一次 DEL），正常情况下执行时间在微秒级，完全不会触发脚本超时。但这个机制值得了解，以便在排查 Redis "不响应"问题时有正确的方向。

**其二，KEYS 参数的传递规范**。Redis Lua 脚本中，访问的 key 应该通过 `KEYS[n]` 参数显式传入，而不是在脚本中硬编码字符串。这是因为 Redis Cluster 模式下，不同的 key 可能存储在不同的集群节点上，Redis Cluster 通过 key 来路由请求。如果脚本中涉及多个 key 且它们在不同节点上，脚本执行会失败。通过 `KEYS` 传入，Redis Cluster 可以提前分析 key 的分布，并（在同一节点的情况下）正确路由。

> [!info] Lua 脚本为何成为"标准解法"
> 从这一章可以看出，Lua 脚本的价值不在于它"快"，而在于它提供了一个**在存储层执行自定义原子逻辑**的通用能力。有了它，"检查加操作"这类组合逻辑不必再依赖存储层预置的命令（如 SETNX、GETSET），而是可以自由组合。**这是从"用现成命令拼凑"到"自定义原子单元"的一次能力跃升**，也是后续所有 Redis 锁进阶实现（看门狗续期、可重入计数）的基础。

### 3.4 Lua 脚本的工程细节：版本管理与调试

Lua 脚本在生产中并非"写完就完"，有两个工程细节值得单独说明。

**其一，用 EVALSHA 替代 EVAL，避免重复传输脚本体**。每次 `EVAL` 都会把整个脚本内容发给 Redis，在网络往返里传输脚本体是浪费。正确做法是先用 `SCRIPT LOAD` 把脚本加载进 Redis，拿到一个 SHA1 摘要，之后用 `EVALSHA` 加摘要来调用。客户端库（如 Redisson）通常会缓存摘要，并在遇到"脚本不存在"错误时自动回退到 `EVAL` 重新加载——**这个"缓存加回退"的模式，是分布式环境下调用远程脚本的标准做法**，因为 Redis 可能重启、可能发生主从切换，脚本缓存随时可能丢失。

**其二，脚本的调试与验证**。Lua 脚本的一个隐患是：它跑在 Redis 内部，出问题时的可观测性很差。实践中应做到两点：一是在测试环境用 `redis-cli --eval` 充分覆盖各种时序（尤其是 value 不匹配、key 不存在等边界），二是给脚本加上明确的返回值约定（如成功返回 1、失败返回 0、无权操作返回 nil），便于应用层区分不同的失败原因，而不是笼统地当成"解锁失败"。

这两个细节看似琐碎，却是把"能跑的脚本"变成"能维护的脚本"的分水岭。**在分布式锁这种"出错就影响数据"的场景里，脚本的可靠性验证与失败原因区分，其重要性不低于脚本本身的逻辑正确性**。

### 3.5 一个反例：脚本里访问了未声明的 key

Lua 脚本有一个容易被忽视的约束，会在 Redis Cluster 下突然暴露。

前面提到，脚本中访问的 key 应当通过 `KEYS[n]` 显式传入，而不是硬编码。有人会觉得这只是"规范问题"——在单节点 Redis 上，硬编码 key 的脚本照样能跑。但一旦迁移到 Redis Cluster，这个"规范问题"就变成了"功能故障"。

原因在于 Redis Cluster 的 key 路由机制：客户端（或代理）需要先根据 key 计算哈希槽，才能把命令发到正确的节点。对于普通命令，key 是命令参数，容易识别；对于 Lua 脚本，Redis 只能通过 `KEYS` 数组来识别脚本会访问哪些 key，从而判断这些 key 是否落在同一个节点上。如果脚本硬编码了 key，Redis 就无法提前判断，脚本执行时可能因为"访问了不属于当前节点的 key"而报错。

这个反例的教训是：**在单节点环境下"能跑"，不代表在多节点环境下"能跑"**。许多为单节点 Redis 编写的锁实现，在迁移到集群时才发现脚本的 key 声明不规范。**这也是分布式系统里一个反复出现的陷阱：一个在"单一环境"下被掩盖的问题，会在"分布式环境"下暴露**——因为分布式环境放大了所有对"局部性"的依赖。

## 第 4 章 看门狗机制：解决 TTL 与业务执行时间的矛盾

### 4.1 TTL 设置困境

`SET NX PX` 加 Lua 解锁方案在正确性上已经相当可靠，但在实际工程中还面临一个难以回避的问题：**锁的 TTL 应该设置多长？**

这个问题的本质是：我们无法提前准确预知临界区业务逻辑的执行时间。

- 如果 TTL 设置为 5 秒，但数据库查询偶尔慢到 8 秒，锁就会提前过期
- 如果 TTL 设置为 30 秒，但客户端崩溃后其他等待者需要等 30 秒，系统可用性受损
- 如果业务涉及外部 API 调用，响应时间可能从 100ms 到 30 秒不等，TTL 根本无法覆盖所有情况

**一个常见的错误做法**：把 TTL 设置得足够大（比如 5 分钟），期望业务逻辑绝对在 5 分钟内完成。这虽然降低了锁提前过期的概率，但客户端崩溃后的恢复时间也变成了 5 分钟，严重影响可用性，而且在高并发场景下 5 分钟的锁持有时间会大幅降低系统吞吐量。

### 4.2 看门狗：持续续期的守护线程

看门狗（Watchdog）机制的核心思想：**不是在加锁时预设一个"足够大"的 TTL，而是设置一个较短的初始 TTL（比如 30 秒），同时启动一个后台线程，定期检查业务是否还在执行，如果是则自动续期（延长 TTL）**。

```
看门狗工作原理：

[加锁成功] → 启动看门狗线程
    看门狗线程每隔 TTL/3（如 10 秒）检查一次：
    - 如果业务线程仍在临界区（持锁标记有效）：执行 PEXPIRE lock_key 30000（续期 30 秒）
    - 如果业务线程已离开临界区（已解锁）：看门狗线程结束
    - 如果业务线程崩溃（JVM 进程退出）：看门狗线程也随之消亡，TTL 自然到期，锁自动释放

[正常解锁] → 业务线程执行解锁 Lua 脚本，看门狗线程检测到锁不存在，停止续期
[异常崩溃] → 看门狗线程消亡，TTL 30 秒后到期，锁自动释放
```

这个设计优雅地解决了 TTL 与业务执行时间的矛盾：

- 初始 TTL 较短（30 秒），崩溃后恢复时间可控
- 正常执行时看门狗持续续期，无论业务多慢都不会锁提前过期
- 看门狗与业务进程同生共死，进程崩溃时看门狗自然停止，TTL 自然到期

> [!warning] 看门狗的边界条件：GC 停顿
> 看门狗线程虽然解决了大多数 TTL 问题，但无法完全规避 01 篇提到的 GC 停顿场景：如果 JVM 发生长时间 Full GC（假设 60 秒），看门狗线程同样被暂停，无法续期，30 秒 TTL 到期后锁被释放，其他客户端获取锁，GC 结束后可能出现两个客户端同时在临界区的情况。
> 缓解措施：使用低延迟 GC（ZGC/Shenandoah）把 GC 停顿控制在 50ms 以内，远低于 TTL 初始值（30 秒），使得这个场景的概率极低。

### 4.3 Redisson 的看门狗实现

Redisson 是 Java 生态中最完善的 Redis 客户端框架，提供了生产级的分布式锁实现。Redisson 的看门狗机制是业界标准实现，值得深入分析。

**Redisson 加锁的核心 Lua 脚本**：

```lua
-- Redisson 加锁脚本（支持可重入）
-- KEYS[1]: 锁的 key
-- ARGV[1]: 锁超时时间（毫秒），默认 30000
-- ARGV[2]: 锁的唯一标识，格式：UUID:threadId（如 "a1b2c3d4:1"）

if (redis.call('exists', KEYS[1]) == 0) then
    -- 锁不存在，直接加锁
    redis.call('hincrby', KEYS[1], ARGV[2], 1);  -- Hash 结构，存储持锁线程 + 重入次数
    redis.call('pexpire', KEYS[1], ARGV[1]);       -- 设置 TTL
    return nil;  -- 返回 nil 表示加锁成功
end;

if (redis.call('hexists', KEYS[1], ARGV[2]) == 1) then
    -- 锁存在，且是当前线程持有的（可重入）
    redis.call('hincrby', KEYS[1], ARGV[2], 1);  -- 重入次数 +1
    redis.call('pexpire', KEYS[1], ARGV[1]);       -- 续期
    return nil;  -- 返回 nil 表示加锁成功（可重入）
end;

-- 锁存在，且不是当前线程持有，返回锁的剩余 TTL（单位毫秒）
return redis.call('pttl', KEYS[1]);
```

注意 Redisson 使用 Redis 的 **Hash（哈希）数据结构**来存储锁，而不是简单的 String。Hash 的 field 是"UUID:threadId"，value 是重入次数。这个设计同时支持了**唯一性标识**（UUID 标识客户端实例，threadId 标识线程）和**可重入计数**（重入次数）。

**看门狗的实现原理（源码层面分析）**：

Redisson 在加锁成功后，通过 Netty 的时间轮（HashedWheelTimer）调度一个延迟任务来实现看门狗：

```java
// Redisson 源码的看门狗续期逻辑（简化）
private void renewExpiration() {
    // 调度在 lockWatchdogTimeout / 3 后执行续期任务
    // 默认 lockWatchdogTimeout = 30 秒，所以每 10 秒续期一次
    Timeout task = commandExecutor.getConnectionManager().newTimeout(
        new TimerTask() {
            @Override
            public void run(Timeout timeout) {
                // 执行续期 Lua 脚本：将 TTL 重置为 lockWatchdogTimeout
                // 续期成功后，再次调度下一次续期任务（形成递归调度）
                RFuture<Boolean> future = renewExpirationAsync(threadId);
                future.onComplete((res, e) -> {
                    if (e != null) {
                        // 续期失败（Redis 连接断开等），停止看门狗
                        return;
                    }
                    if (res) {
                        // 续期成功，递归调度下一次续期
                        renewExpiration();
                    }
                    // res = false 说明锁已不存在（正常解锁后），停止看门狗
                });
            }
        },
        lockWatchdogTimeout / 3,  // 延迟执行时间（10 秒）
        TimeUnit.MILLISECONDS
    );

    // 将任务句柄存储起来，解锁时可以取消
    expirationRenewalMap.put(getEntryName(), new ExpirationEntry(threadId, task));
}
```

续期使用的 Lua 脚本：

```lua
-- Redisson 续期脚本
-- KEYS[1]: 锁的 key
-- ARGV[1]: 新的 TTL（毫秒）
-- ARGV[2]: 持锁线程标识（UUID:threadId）

if (redis.call('hexists', KEYS[1], ARGV[2]) == 1) then
    redis.call('pexpire', KEYS[1], ARGV[1]);  -- 重置 TTL
    return 1;
end;
return 0;  -- 锁已不存在（或不是当前线程的锁），续期失败
```

**看门狗的生命周期管理**：

- **加锁成功**时：调用 `renewExpiration()` 启动看门狗
- **解锁时**：从 `expirationRenewalMap` 中取出任务句柄，调用 `cancel()` 取消看门狗任务
- **指定了 leaseTime（自定义 TTL）时**：Redisson 不启动看门狗，TTL 固定为传入的值，到期后锁自动释放

> [!note] 为什么续期间隔是 TTL 的三分之一
> 把续期间隔设为 TTL 的 1/3，是一个典型的"容错余量"设计。它意味着**在 TTL 到期前，看门狗有三次续期机会**。只要三次里成功一次，锁就不会过期。这个比例给了网络抖动、单次续期失败等偶发问题足够的缓冲，同时也不至于让续期过于频繁。这种"留出冗余次数"的设计思路，在心跳、租约、健康检查等机制里都很常见——**凡是"定期做某事"的机制，都应允许若干次失败而不立即失效**。

### 4.4 看门狗与租约：两个相似却不同的概念

看门狗常被与"租约（Lease）"混为一谈，但它们其实是两个不同的机制，混淆它们会导致错误的设计判断。

**看门狗是"客户端主动续期"**：锁的持有者定期向存储服务延长锁的生存期。它的主动权在客户端，存储服务只是被动接受续期请求。Redisson 的看门狗就是这种形态。

**租约是"服务端授予一段确定期限的所有权"**：存储服务（或协调者）在授予锁的同时，承诺"在一段确定的时间内，这把锁只属于你"。它的主动权在服务端，客户端只是被动接受。etcd 的租约（Lease）机制就是这种形态——客户端拿到一个带 TTL 的租约，需要定期续租，但租约的语义由 etcd 保证。

两者的差别在故障时表现得最清楚。**看门狗模式下，如果客户端停顿（如 GC），续期停止，锁过期——而客户端并不知道自己已经失去锁**，醒来后可能继续操作，造成双持。**租约模式下，客户端在续租失败时会明确得知自己失去了所有权**（因为它持有的是一个"带期限的凭证"），从而可以主动放弃操作。

这个差别指向一个更本质的区分：**"我持有锁"这件事，是一个客户端自认为的状态，还是一个由服务端授予、可被客户端查询的事实**。前者在客户端停顿时会失准，后者不会。这也正是 Kleppmann 主张"栅栏令牌"的深层理由——**把"所有权"从客户端的主观判断，变成服务端可验证的客观凭证**。理解了看门狗与租约的这一层差别，就理解了 03 篇 Redlock 争议的核心分歧所在。

### 4.5 看门狗的代价与误用

看门狗解决了"TTL 太短导致锁提前过期"的问题，但它并非没有代价，而且它引入了一个反直觉的新风险。

**第一处代价是持续的续期开销**。看门狗是一个永不停止的定时任务，只要业务在跑，它就会按固定间隔向 Redis 发送续期命令。对于长事务、长任务，这会持续产生网络流量与 Redis 负载。虽然单次续期的成本很低，但当大量锁同时存在时，这些续期请求会累积成可观的压力。

**第二处代价，也是更危险的：看门狗可能把锁"续"成永久锁**。这个风险的反直觉之处在于——**看门狗解决了"锁太早释放"，却可能制造"锁永远不释放"**。设想某个业务线程在临界区里陷入了死循环，或者调用了一个挂起的远程接口：只要这个线程还活着，看门狗就会一直为它续期，锁永远不会过期，其他所有等待者永远拿不到锁。**原本用于解决死锁的 TTL 机制，被看门狗"抵消"了，锁服务重新退化成了"有死锁"的状态**。

缓解这个风险的办法有两条。其一，**在临界区内设置业务级的超时**：给关键操作（尤其是外部调用）设置明确的超时，避免线程无限期挂起。其二，**限制续期的上限**：为看门狗设置一个"最长续期次数"或"最长持锁时间"，超过之后停止续期，让锁自然过期并告警——这相当于给锁加了一道"硬上限"。

这个案例再次印证了一条分布式系统的通用规律：**任何机制都是在转移问题，而不是消除问题**。看门狗把"锁过早释放"转移成了"锁可能过久持有"；TTL 把"崩溃后死锁"转移成了"过期后可能双持"。工程上能做的是理解每一次转移，并针对转移后的新问题设计对策——而不是以为某个机制"一劳永逸"。

## 第 5 章 可重入锁：同一线程多次加同一把锁

### 5.1 什么是可重入，为什么需要它

**可重入锁（Reentrant Lock）** 是指：同一个线程或客户端可以多次加同一把锁而不发生死锁。加锁次数记录在锁的状态中，每次加锁计数加一，每次解锁计数减一，只有计数归零时锁才真正被释放。

Java 的 `ReentrantLock` 和 `synchronized` 都是可重入的——同一个线程进入 `synchronized(lock)` 方法后，可以再次调用同样锁定在 `lock` 上的方法，不会死锁。

**为什么分布式场景也需要可重入锁？** 考虑以下代码结构：

```java
@GlobalLocked(key = "order_lock")
public void processOrder(String orderId) {
    // 持有 order_lock 的情况下，调用了另一个也需要 order_lock 的方法
    validateOrder(orderId);
    ...
}

@GlobalLocked(key = "order_lock")
public void validateOrder(String orderId) {
    // 此方法也尝试获取 order_lock
    // 如果分布式锁不支持可重入，这里会死锁
    ...
}
```

如果分布式锁不支持可重入，`processOrder` 已经持有 `order_lock`，调用 `validateOrder` 时再次尝试加 `order_lock` 会永远等待（因为锁已被同一个请求持有），造成死锁。

### 5.2 Redisson 可重入锁的实现原理

如第 4.3 节的 Lua 脚本所示，Redisson 使用 Redis Hash 来存储锁信息：

```
Hash 结构：
Key: "order_lock"
Field: "a1b2c3d4-xxxx:1"  (UUID:threadId)
Value: 2  (重入次数)
TTL: 30000ms
```

**加锁逻辑**：

1. 检查 `order_lock` 是否存在：不存在则直接加锁，`hincrby field 1` 写入重入次数 = 1
2. 存在且 field 匹配当前线程：`hincrby field 1`，重入次数加一（此次加锁成功，不会阻塞）
3. 存在但 field 不匹配：锁被其他线程持有，返回剩余 TTL，客户端等待

**解锁逻辑**（同样是 Lua 脚本保证原子性）：

```lua
-- Redisson 解锁脚本
-- KEYS[1]: 锁的 key
-- KEYS[2]: 解锁成功时发布通知的 channel（用于唤醒等待者）
-- ARGV[1]: 解锁通知消息
-- ARGV[2]: 锁的 TTL（毫秒）
-- ARGV[3]: 持锁线程标识（UUID:threadId）

if (redis.call('hexists', KEYS[1], ARGV[3]) == 0) then
    return nil;  -- 不是当前线程的锁，无权解锁
end;

-- 重入计数 -1
local counter = redis.call('hincrby', KEYS[1], ARGV[3], -1);

if (counter > 0) then
    -- 还有重入层级，不真正释放锁，仅续期
    redis.call('pexpire', KEYS[1], ARGV[2]);
    return 0;
else
    -- 重入计数归零，真正释放锁
    redis.call('del', KEYS[1]);
    -- 发布解锁通知，唤醒正在等待的客户端（通过 Redis Pub/Sub）
    redis.call('publish', KEYS[2], ARGV[1]);
    return 1;
end;

return nil;
```

> [!warning] 可重入的代价：锁的"持有者"变成了"线程"
> 可重入把锁的持有者粒度从"客户端"细化为"客户端加线程"。这带来一个副作用：**同一个客户端的另一个线程无法再获取这把锁**（因为它不是持有它的那个线程），这在某些场景下反而是限制。更微妙的是，如果可重入计数因为异常路径没有正确减一，锁会被"泄漏"在一个非零的重入计数上，直到 TTL 到期。因此，使用可重入锁时，解锁必须放在 `finally` 中，且加锁与解锁的次数必须严格配对。

### 5.3 等待加锁：Pub/Sub 替代轮询

在客户端加锁失败后，有两种等待策略。

**方式一：轮询（Spin Lock）**

```python
while True:
    result = redis.set(lock_key, value, nx=True, px=30000)
    if result:
        break  # 加锁成功
    time.sleep(0.1)  # 等待 100ms 后重试
```

这种方式简单，但存在两个问题：**CPU 空转**（大量轮询请求对 Redis 形成无效负载）、**延迟不可控**（等待时间取决于轮询间隔，无法精确响应锁释放事件）。

**方式二：Pub/Sub 订阅（Redisson 使用此方式）**

Redisson 利用 Redis 的发布与订阅（Pub/Sub）机制来实现"锁释放时精确唤醒等待者"：

```
等待流程：
1. 客户端 B 尝试加锁，失败
2. 客户端 B 订阅 Channel "redisson_lock_channel:{lock_key}"
3. 客户端 B 阻塞等待（通过 Java Semaphore 阻塞当前线程，不占用 CPU）
4. 客户端 A 解锁时，解锁 Lua 脚本 PUBLISH "redisson_lock_channel:{lock_key}" "0"
5. 客户端 B 收到消息，唤醒，再次尝试加锁
6. 如果此时锁已被其他等待者抢走，客户端 B 重新订阅等待
```

这种方式相比轮询，减少了无效的 Redis 请求，且响应锁释放的延迟极低（Pub/Sub 的消息投递延迟通常在 1ms 以内）。不过需要留意：Pub/Sub 的消息是"即发即弃"的，如果客户端在收到通知前恰好断线重连，可能错过这次唤醒——因此实现上必须配合超时兜底，避免无限等待。**事件通知提升效率，超时兜底保证活性，两者缺一不可**。

### 5.4 可重入锁的适用边界

可重入不是"越多越好"的能力，它有明确的适用边界。

**适合可重入的场景**：业务代码里存在"持锁方法调用另一个也需要同一把锁的方法"的结构。这种结构在分层清晰的代码里并不罕见——外层是业务编排方法，内层是校验或辅助方法，两者都标注了同一把锁。此时可重入避免了自锁死。

**不需要可重入的场景**：锁的持有范围是"单一方法，无嵌套调用"。此时用最简单的 `SET NX PX` 加 Lua 解锁即可，引入可重入只会增加复杂度。

**需要警惕可重入的场景**：跨进程或跨服务的嵌套。可重入的语义建立在"同一个线程"之上，而一次 RPC 调用已经换了线程（甚至换了进程），此时"可重入"无法跨越 RPC 边界生效——你需要在调用链上显式传递锁的持有凭证，才能实现跨服务的可重入，而这已经超出了普通锁的范畴。**因此，可重入锁解决的是"进程内嵌套"，而不是"跨服务嵌套"**，把这两者混为一谈，会导致"以为可重入能防住跨服务自锁"的错误预期。

一句话概括：**可重入是一把"按需启用"的钥匙，不是"默认开启"的功能**。只有确认代码里存在进程内的嵌套加锁，才值得引入它；否则，简单的不可重入锁更清晰、更少出错。

## 第 6 章 完整的 Redis 分布式锁实现

### 6.1 手写一个生产可用的 Redis 锁（无框架依赖）

对于不使用 Redisson 的场景（如 Python、Go 项目），需要手工实现一个可靠的 Redis 锁：

```python
import redis
import uuid
import time

class RedisDistributedLock:
    """
    生产可用的 Redis 分布式锁实现
    支持：原子加锁、Lua 原子解锁、超时控制
    不支持（需额外实现）：看门狗续期、可重入
    """

    # 解锁 Lua 脚本（原子性 GET + DEL）
    UNLOCK_SCRIPT = """
        if redis.call('GET', KEYS[1]) == ARGV[1] then
            return redis.call('DEL', KEYS[1])
        else
            return 0
        end
    """

    def __init__(self, redis_client: redis.Redis, lock_key: str, ttl_ms: int = 30000):
        self.redis = redis_client
        self.lock_key = lock_key
        self.ttl_ms = ttl_ms
        self.lock_value = None

    def acquire(self, timeout_ms: int = 5000) -> bool:
        """
        尝试在 timeout_ms 内获取锁
        返回 True 表示加锁成功，False 表示超时失败
        """
        self.lock_value = str(uuid.uuid4())  # 生成唯一 token
        deadline = time.time() + timeout_ms / 1000

        while time.time() < deadline:
            # SET NX PX 原子加锁
            result = self.redis.set(
                self.lock_key,
                self.lock_value,
                nx=True,           # 仅在 key 不存在时设置
                px=self.ttl_ms     # 毫秒级 TTL
            )
            if result:
                return True  # 加锁成功

            # 加锁失败，短暂等待后重试（简单轮询，生产可替换为 Pub/Sub）
            time.sleep(0.05)  # 50ms 轮询间隔

        return False  # 超时

    def release(self) -> bool:
        """
        释放锁（Lua 脚本保证原子性）
        """
        if self.lock_value is None:
            return False

        result = self.redis.eval(
            self.UNLOCK_SCRIPT,
            1,                 # key 的数量
            self.lock_key,     # KEYS[1]
            self.lock_value    # ARGV[1]
        )
        return result == 1

    def __enter__(self):
        if not self.acquire():
            raise TimeoutError(f"无法在超时时间内获取锁: {self.lock_key}")
        return self

    def __exit__(self, exc_type, exc_val, exc_tb):
        self.release()
        return False  # 不吞掉异常


# 使用示例
r = redis.Redis(host='localhost', port=6379)

with RedisDistributedLock(r, "order_process_lock", ttl_ms=30000) as lock:
    # 临界区：安全地执行业务逻辑
    process_order(order_id)
```

### 6.2 使用 Redisson 的最佳实践（Java）

对于 Java 项目，推荐直接使用 Redisson，它处理了所有边界情况：

```java
@Service
public class OrderService {

    @Autowired
    private RedissonClient redissonClient;

    public void processOrder(String orderId) throws InterruptedException {
        // 获取锁对象（此时尚未加锁）
        RLock lock = redissonClient.getLock("order_process_lock:" + orderId);

        // 方式 1：不设置 leaseTime，启用看门狗自动续期
        lock.lock();
        try {
            doProcessOrder(orderId);
        } finally {
            lock.unlock();  // 必须在 finally 中解锁，防止异常导致锁泄漏
        }

        // 方式 2：设置 leaseTime，不启用看门狗（业务执行时间可预知的场景）
        lock.lock(10, TimeUnit.SECONDS);  // 最多持锁 10 秒
        try {
            doProcessOrder(orderId);
        } finally {
            lock.unlock();
        }

        // 方式 3：尝试加锁，带超时（推荐用于大多数业务场景）
        boolean acquired = lock.tryLock(
            5, TimeUnit.SECONDS,   // 等待获取锁的最长时间
            30, TimeUnit.SECONDS   // 锁的持有时间（leaseTime，不启用看门狗）
        );
        if (!acquired) {
            throw new BusinessException("系统繁忙，请稍后重试");
        }
        try {
            doProcessOrder(orderId);
        } finally {
            lock.unlock();
        }
    }
}
```

> [!warning] 最常见的 Redisson 使用错误
> 在 `tryLock` 时指定了 `leaseTime`，导致看门狗不启动，但业务逻辑执行时间超过了 `leaseTime`：
> ```java
> // 错误：leaseTime=5s，但业务可能需要 10s
> lock.tryLock(1, 5, TimeUnit.SECONDS);
> // 结果：5s 后锁自动过期，其他线程进入临界区，数据不一致
> ```
> 建议：如果业务执行时间不确定，使用 `lock.lock()` 不指定 `leaseTime`，让看门狗自动续期。**这个坑之所以常见，是因为 `tryLock` 的三个参数看起来"更完整、更保险"，但实际上指定了 `leaseTime` 等于主动关掉了看门狗**——API 的"看起来更严谨"与实际更安全，往往是两回事。

### 6.3 手写与框架的边界

对比 6.1 与 6.2 两段代码，可以看出框架替你做了什么。手写版本覆盖了"原子加锁、原子解锁、超时控制"这三件事，但**没有覆盖看门狗与可重入**——而这两件事恰恰是最容易出错的：看门狗涉及定时调度与生命周期管理，可重入涉及计数与线程标识的配合。

因此，选择手写还是用框架，本质上是判断"你的场景是否需要看门狗与可重入"。如果临界区执行时间可预知（不需要看门狗）、且不存在嵌套加锁（不需要可重入），手写一个精简版本是完全合理的；只要涉及这两者中的任何一个，使用 Redisson 这类成熟框架就更划算——**因为这两个机制的边界情况远比看起来多**。

### 6.4 一个监控清单：Redis 锁必须观测的指标

Redis 锁的失效往往是"沉默"的，因此监控不是可选项。以下指标建议纳入观测。

**锁等待时长与超时率**。统计每次加锁的等待时长，以及因等待超时而失败的请求比例。等待时长持续上升，说明锁的持有时长变长或竞争加剧；超时率上升，说明系统已经接近瓶颈。

**持锁时长分布**。统计每次临界区的实际执行时长。如果 P99 持锁时长接近或超过 TTL，说明看门狗配置可能不够安全，或者业务里有耗时的意外操作。**持锁时长逼近 TTL，是双持风险最直接的预警信号**。

**续期失败次数**。看门狗续期失败意味着与 Redis 的连接出现了问题，或锁已被他人获取。续期失败的次数与分布，是判断锁服务健康度的关键。

**锁 key 的数量与分布**。监控有多少把不同的锁在被使用。数量异常增长可能意味着锁粒度过细或存在锁泄漏（锁未被正确释放）。

**未正常释放的锁计数**。统计"因超时自动过期而非主动解锁"的锁数量。这个数字上升，说明有业务路径没有在 `finally` 中正确解锁，或者有客户端崩溃。

这几个指标合起来，能覆盖 Redis 锁最主要的失效前兆。它们与 01 篇提出的"活性度量"是互补的——01 篇关注"等待机制是否健康"，这里关注"持锁与释放是否健康"。**两者结合，构成对 Redis 锁的完整可观测性**。

### 6.5 一个反例：解锁忘了放在 finally

在众多 Redisson 使用错误里，最简单也最普遍的一个是：**解锁没有放在 `finally` 中**。

```java
// 错误：解锁不在 finally 中
lock.lock();
doBusiness();      // 如果这里抛异常，下面的 unlock 不会执行
lock.unlock();
```

这段代码的问题在于：`doBusiness()` 一旦抛出异常，`unlock()` 就被跳过了，锁不会被主动释放。此时有两种结局：如果启用了看门狗，看门狗会一直为这把锁续期（因为进程还活着、锁还在），锁被无限持有，其他等待者全部阻塞——这正是 4.5 节讨论的"看门狗把锁续成永久锁"；如果没启用看门狗，锁会在 TTL 后过期，但要等整个 TTL 时长，期间其他请求全部失败。

正确写法是把 `unlock()` 放进 `finally`：

```java
lock.lock();
try {
    doBusiness();
} finally {
    lock.unlock();
}
```

这个反例的教训很朴素，却值得反复强调：**分布式锁的"释放"与"获取"必须严格配对，而 `finally` 是保证配对的语言级手段**。它与单机锁必须用 `try-finally` 释放是同一个道理——**锁的正确性不仅取决于锁服务，也取决于使用者是否遵守了基本的编程约定**。这也再次说明，为什么本专栏反复强调"锁是工具，不是银弹"：再可靠的锁服务，也挡不住"忘记解锁"这类使用层面的错误。

### 6.6 一个协作细节：锁 key 的命名与治理

锁的 key 是跨团队共享的资源，它的命名规范属于"协作层面"的工程细节，却直接影响锁的可维护性。

一个推荐的命名格式是 `业务域:资源类型:资源标识`，例如 `order:process:12345`、`inventory:deduct:P001`。这样命名的好处有三：其一，**从 key 就能看出锁保护的是什么资源**，排查问题时一目了然；其二，**不同业务域的锁天然隔离**，避免了"两个团队恰好用了同一个 key 名"造成的意外互斥；其三，**便于按前缀统计与清理**，比如可以统计"order 域的锁有多少把、平均持有时长是多少"。

反面的做法是使用"裸名"，如直接叫 `lock`、`mutex`。这类命名在单团队小系统里或许可行，一旦系统变大、团队变多，就会变成一场灾难——因为不同模块的 `lock` 可能指向完全不同的资源，而它们却会互相阻塞。

这个细节的价值在于它提醒我们：**分布式锁不只是一段代码，还是一个跨团队共享的基础设施**。它的命名、监控、清理、容量规划，都需要像对待其他基础设施一样认真治理。**一个没有被治理的锁体系，会随着团队扩张而逐渐变成一团互相阻塞的乱麻**——这往往不是技术问题，而是协作问题。

## 第 7 章 Redis 分布式锁的正确性边界

### 7.1 单节点 Redis 锁的失效场景梳理

经过上述所有优化，单节点 Redis 分布式锁在以下场景仍然可能失效：

| 场景 | 失效原因 | 发生概率 | 影响 |
| :--- | :--- | :--- | :--- |
| Redis 主从切换 | 锁数据在 Slave 提升时可能未同步 | 极低（主宕机才触发）| 短暂双写 |
| 长时间 GC 停顿 | 看门狗被暂停，TTL 可能到期 | 极低（ZGC 下几乎不发生）| 短暂双写 |
| 时钟漂移 | TTL 计算偏差 | 极低（NTP 正常工作时可忽略）| TTL 略微不准 |
| 客户端与 Redis 网络分区 | 加锁超时但 Redis 侧可能已成功 | 低 | 幻象失败（可用性损失，非安全问题）|

对于绝大多数互联网业务场景，这些失效概率可以接受，配合业务层的幂等性设计可以做到最终正确。

### 7.2 何时需要更强的保证：Redlock 或 ZooKeeper

如果业务对分布式锁的正确性有极高要求（金融结算、库存精确控制），且无法接受上述任何一种失效场景，则需要考虑：

- **Redlock 算法**：通过多数派加锁降低单节点故障的影响（但 Redlock 自身也有争议，详见 03 篇）
- **ZooKeeper 分布式锁**：基于 ZAB 强一致性协议，主从切换不会丢失数据（详见 04 篇）

### 7.3 一个务实的判断：锁 + 幂等

把第 7.1 节的失效场景与第 7.2 节的需求对照，可以得到一个务实的原则：**单节点 Redis 锁的可靠性，应当由业务层的幂等来补足**。

具体地说，使用 Redis 锁时应当同时问一句："如果这把锁偶发失效导致重复执行，我的业务会发生什么？"如果答案是"数据错乱且无法修复"，那么 Redis 锁就不够，需要上更强的方案；如果答案是"最多重复执行一次，而我的操作是幂等的"，那么 Redis 锁配合幂等就足够了。

这个判断把"选多强的锁"这个问题，转化成了"业务能容忍多弱的锁"。**它反映的是一种普遍适用的思路：与其追求锁的绝对可靠，不如让业务对锁的偶发失效具备免疫力**——这正是 08 篇"边界与替代方案"要展开的核心观点。

### 7.4 从单节点到多节点：Redis 锁的能力边界

把本文的分析收敛到一句话：**单节点 Redis 锁在"单实例内"是可靠的，但它的可靠性会在"跨实例"时打折**。

本文讨论的所有机制——SET NX PX、Lua 原子解锁、看门狗续期、可重入计数——都建立在"命令在同一个 Redis 实例上原子执行"这个前提之上。只要这个前提成立，它们就是可靠的。而一旦涉及主从切换、集群分片、故障转移，前提就被打破了：锁数据可能丢失、脚本可能落到不同节点、续期可能打到错误的分片。

这就给出了一个清晰的能力边界判断：

**场景一，业务能容忍极低概率的双持，且有幂等兜底**。此时单节点或主从 Redis 锁足够——它性能最高、实现最简单，偶发的双持被幂等吸收，不会造成实际损失。这是绝大多数互联网业务的现实选择。

**场景二，业务不能容忍双持，且没有幂等兜底**。此时单节点 Redis 锁不够，需要升级到 Redlock（多实例多数派加锁）或 ZooKeeper（基于共识的强一致）。Redlock 试图在 Redis 生态内提供更强的保证，但它自身存在争议；ZooKeeper 通过共识协议提供了更彻底的强一致，代价是性能与运维复杂度。

**场景三，业务既不能容忍双持，又对性能敏感**。这是一个两难，现实的解法通常是"用 Redis 锁加栅栏令牌"——把互斥交给 Redis（高性能），把"防止过期后误写"交给服务端校验的栅栏令牌。这样，即使锁偶发失效，服务端的版本校验也能挡住过期令牌的写入。这条路线正是 Kleppmann 所推荐的，也将在 03 篇详细展开。

由此可见，从单节点 Redis 锁出发，往前走有两条路：一条是"提升锁本身的一致性"（Redlock、ZooKeeper），另一条是"承认锁不够可靠，用服务端校验兜底"（栅栏令牌）。这两条路的取舍，构成了后续几篇的主线。

### 7.5 从用途到方案：一张决策流程

把本文的边界分析整理成一个判断流程，可以在面对具体场景时快速定位该用哪种方案。

**第一问：这把锁是"效率优化"还是"正确性保证"？** 如果只是为了避免重复做一件代价高但无害的事（重复发邮件、重复触发计算），用单节点 Redis 锁即可，不必追求更强的一致性。

**第二问（若为正确性保证）：能否在存储层加一层服务端校验？** 如果目标资源是一张有主键或唯一约束的表，加一层"唯一约束或版本号校验"就能兜住锁的偶发失效——此时单节点 Redis 锁加服务端校验就够了，不必上 Redlock 或 ZooKeeper。

**第三问（若无法加服务端校验）：能否接受"锁失效时停摆"？** 如果能接受（宁可拒绝服务也不出错），且需要更强的锁本身，则选 ZooKeeper 这类基于共识的方案；如果不能接受停摆，则问题不在锁，而在于业务缺少一层服务端校验——应当补上它。

这三问的逻辑主线是：**先定用途，再定"兜底放在哪"，最后才考虑"锁本身要多强"**。它把"该用多强的锁"这个容易纠结的问题，转化为"兜底机制放在哪一层"这个更清晰的问题。**很多时候，加一层服务端校验比换一个更强的锁更简单、更有效**——这正是 03 篇 Redlock 争议最终指向的结论。

### 9.4 一个延伸：Redis 锁的"TTL 选择"

Redis 锁的 TTL（`leaseTime`）是一个"没有标准答案"的参数——它的选择值得展开。

**TTL 太短的后果是"锁提前过期"**：业务还没执行完，锁就过期了，其他客户端可能拿到锁——**这是"互斥性失效"的常见原因**。

**TTL 太长的后果是"故障恢复慢"**：如果持锁者崩溃，锁要等 TTL 到期才能释放——**这期间其他客户端都在等待**。

**因此，TTL 的选择是"安全性"与"可用性"的取舍**：**短 TTL 偏向"可用"（恢复快）但"不安全"（易提前过期）；长 TTL 偏向"安全"但"恢复慢"**。

**正确的做法是"用看门狗自动续期"**：**设置一个"足够短以快速恢复、又足够长以避免频繁续期"的 TTL（如 30 秒），然后由看门狗在业务执行期间自动续期**——**这样既保证了"业务完成前锁不过期"，又保证了"崩溃后 30 秒内锁自动释放"**。

**这条延伸的启示是**：**"参数选择"的困难，往往可以通过"机制设计"来化解**——**TTL 的"两难"，被"看门狗"化解了**。**因此，遇到"参数两难"时，不妨先想想"能不能用一个机制来同时满足两端"**——**这正是 Redisson 看门狗的价值所在**。
