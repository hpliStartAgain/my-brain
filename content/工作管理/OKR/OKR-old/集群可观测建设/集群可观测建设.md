## 背景和目标

**痛点：**

- **监控数据孤岛与维度缺失**：Zabbix 基于 Host 模型，无法聚合 Queue/Tenant 维度；指标与日志分离，排查问题需在 Grafana 和 SSH 终端间反复切换。
    
- **日志“黑洞”与存储成本失控**：核心组件（NameNode/RM/HS2）日志散落在物理机，排查效率低；海量 DEBUG/INFO 垃圾日志占用大量磁盘，高价值 Error 被淹没。
    
- **采集瓶颈与维护 Toil**：JMX 高负载下易超时；Zabbix 告警规则配置繁琐，缺乏代码化管理能力。
    

**目标：**

- **构建云原生指标体系**：基于 Exporter + Prometheus 架构，替代 Zabbix JMX，实现指标标准化采集。
    
- **构建统一日志中心**：部署 Loki + Alloy，集中采集核心组件日志，实现上下文关联查询。
    
- **存储成本降低50%**：通过 Pipeline 清洗策略，丢弃无用日志，提升存储效率。
    
- **告警规则代码化**：利用 LLM Agent 将 Zabbix 告警转化为 PromQL/LogQL，实现 GitOps 管理。
    
- **为 RCA 奠基**：统一 Metrics 与 Logs 的 Label 体系，为 AI 根因分析提供数据底座。
    

**技术亮点：**

- **Metric-Log 深度联动**：Grafana Split View 实现“点击指标异常点即展示对应日志”。
    
- **LLM 驱动迁移**：利用 LLM Agent 自动将 Zabbix 阈值转换为 PromQL，降低迁移门槛。
    
- **Pipeline 日志降噪**：在采集端进行 Multiline 聚合（堆栈还原）与 Filter 过滤。
    
- **无侵入 Sidecar**：采集组件与业务进程解耦，保障核心服务稳定性。

## 建设手段

**1. 架构升级：Exporter + Loki 替代 JMX + SSH**

- **目标**：部署 Hadoop/Hive Exporter 及 Alloy Sidecar，实现数据采集的标准化与集中化。
    
- **策略**：采用 DaemonSet 或 Sidecar 模式部署，确保 Label（Cluster, Host, Component）与指标体系完全对齐。
    

**2. 日志治理：Pipeline 清洗与降噪**

- **目标**：解决日志“脏、乱、大”的问题，仅存储高价值数据。
    
- **策略**：
    
    - **Drop**：直接丢弃无用的 DEBUG 及频繁的鉴权 INFO 日志。
        
    - **Multiline**：将 Java Exception 堆栈聚合为单条日志，便于 AI 读取。
        
    - **Label**：提取关键字段（如 User, JobID）作为索引标签。
        

**3. 智能化迁移：LLM Agent 规则转换**

- **目标**：低成本完成 Zabbix 到 Foxeye (Prometheus) 的迁移。
    
- **策略**：利用 Go-eino 开发 Migration Agent，读取 Zabbix XML 配置，通过 LLM 生成对应的 PromQL 和 AlertManager 规则文件。
