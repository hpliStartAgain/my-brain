# 1 背景/现状

Foxeye 可观测平台是团队基于开源夜莺（Nightingale）搭建的统一可观测性平台，承担公司内部指标监控、告警管理等核心职能。平台当前现状如下：

- **平台基础**：基于开源夜莺搭建，开源夜莺功能丰富但页面组织分散，用户使用成本较高，不同角色（开发、运维）的功能未做差异化设计，可观测配置链路不清晰
- **时序存储**：使用 VictoriaMetrics（VM）集群，目前为大中央独立集群，现已按指标规模拆分为两个独立集群，但缺乏按业务隔离的写入和查询路由控制
- **可观测能力**：当前仅具备指标（Metrics）可观测能力，日志（Logs）和链路追踪（Traces）能力缺失。Loki（日志存储）和 Tempo（Trace 存储）数据服务已部署，但平台侧尚未接入
- **告警通知**：支持 3 条告警通知链路（直接触达、webhook 分发、事件聚合处理），链路依赖组件多，缺乏自身监控保障机制

# 2 问题分析

基于平台现状，当前存在以下核心问题：

**1.平台自身监控保障缺失**

**2.VM 集群业务隔离与路由问题**

- 现有两个 VM 集群按指标规模拆分，但未按业务维度做隔离，不同业务的指标混存在同一集群中，互相影响查询性能
- 缺乏统一的写入路由控制（vmagent-forward），指标写入路径不清晰，无法按业务灵活路由到不同集群
- 缺乏统一的查询路由控制（vmauth），查询请求无法按业务自动路由到对应集群，跨集群全局查询能力不足

**3.平台功能分散，配置链路不清晰**

- **服务监控场景**（K8s 部署）：K8s 内置指标采集器，用户只需配置采集端口及路径，然后查询指标、配置告警即可，但平台未提供清晰的配置引导链路
- **主机/资源监控场景**：用户需先在目标资源安装采集器，再配置采集项，涉及采集器、主机、采集配置、指标、告警规则等多个环节，流程复杂且缺乏统一管理视角
- 两种场景的配置链路差异较大，但平台未做区分引导，用户难以找到清晰的配置切入点，监控资源之间缺乏关联和组织

**4.日志/Trace可观测能力缺失**

- Foxeye 平台未提供日志收集配置和日志查询能力
- 用户查看日志需要使用独立工具（如 Grafana），无法在统一平台上关联trae和日志
- 日志收集链路缺乏平台化管理，容器和非容器场景的日志采集配置分散

# 3 方案/目标

**Objective**：通过完善自身监控保障、优化 VM 集群架构、重塑平台功能体验、接入日志能力，将 Foxeye 打造为稳定可靠、易用高效、能力完整的一站式可观测平台。

- **KR1**：通过建立服务自身白盒监控，利用端到端探测方法，完善可观测自身监控保障机制。**预计 3 月底**，建立 Foxeye 自身及相关报警链路关键指标大盘，以及 3 条报警通知链路的端到端验证异常报警机制
- **KR2**：VM 集群架构调整，按业务隔离集群，引入 vmagent-forward 和 vmauth 统一路由控制，提高集群稳定性和查询性能。**预计 3 月中旬**，VM 完成业务隔离集群架构升级，日常高频指标查询 P99 时延降低至 5s 以内
- **KR3**：Foxeye 平台产品功能性优化，简化不同场景下的配置链路，降低平台学习成本。**预计 4 月底**，平台针对服务监控和主机/资源监控两种场景，提供用户 step by step 的最佳实践配置指引，并实现以业务组为中心的监控资源关联管理视角
- **KR4**：Loki 配置链路平台化，Foxeye 平台支持日志收集、日志查询能力。**预计 5 月底**，Loki 日志收集链路上线 Foxeye 平台，覆盖容器 & 非容器场景

## 3.1 自身监控保障方案（KR1）

建立 Foxeye 平台自身的白盒监控体系，利用端到端探测方法验证告警通知链路的可用性。

**核心设计思路**：

- **白盒监控大盘**：采集 Foxeye 及相关组件的关键运行指标（告警规则评估延迟、事件推送成功率、组件健康状态等），建立统一监控大盘
- **端到端探测**：针对 3 条告警通知链路，分别构建探测告警规则，模拟真实告警从产生到触达的完整路径，验证链路可用性
- **异常报警**：当端到端探测发现链路异常时，通过独立渠道（避免依赖被监控链路自身）发送告警通知

[可观测自身服务&报警通知链路监控方案](https://bd-docs.panther.sohurdc.com/pages/viewpage.action?pageId=103707895)

## 3.2 VM 集群业务隔离方案（KR2）

对 VictoriaMetrics 集群进行按业务隔离的架构升级，新建独立集群并引入 vmagent-forward 和 vmauth 统一控制写入和查询流量路由。

![[Pasted image 20260313183832.png]]

**核心设计思路**：

- **按业务隔离存储**：在旧集群（共享，存储其他部门指标）基础上，新建基础运营组独享集群和 DomeOS 独享集群，实现业务级别的存储隔离，避免互相影响
- **写入路由（vmagent-forward）**：通过 vmagent-forward 作为写指标统一入口，根据指标标签将数据路由到对应的业务集群（基础运营组指标 -> 基础指标集群，DomeOS 指标 -> DomeOS 集群，其他 -> 旧集群）
- **查询路由（vmauth）**：通过 vmauth 作为查指标统一入口，根据业务维度将查询请求路由到对应的 vm-select 组件（支持基础运营组查询、其他部门查询、DomeOS 查询及大数据中心全局查询）
- **全局查询**：vm-select-global 支持跨所有集群的联合查询，满足大数据中心等需要全局视角的查询场景

**性能目标**：日常高频指标查询 P99 时延降低至 5s 以内。

## 3.3 平台功能优化方案（KR3）

简化用户配置链路，针对不同监控场景提供清晰的配置指引，并为用户提供有切入点、有组织、有关联的监控资源管理能力。

**核心设计思路**：

- **场景化配置引导**：区分服务监控和主机/资源监控两种场景，分别提供 step by step 的配置指引链路
    - **服务监控**（K8s 场景）：引导用户完成"配置采集端口/路径 -> 查询指标 -> 配置告警规则 -> 搭建大盘"的完整流程，无需关注采集器部署
    - **主机/资源监控**：引导用户完成"安装采集器 -> 配置采集项 -> 查询指标 -> 配置告警规则 -> 搭建大盘"的完整流程，关注采集器与主机的绑定管理
- **监控资源统一管理**：建立以业务组为中心的监控资源管理视角，将采集器、采集配置、指标、告警规则、大盘等资源进行关联组织，用户进入业务组后能清晰看到所有相关资源及其关联关系
- **配置链路串联**：将分散的功能模块通过配置链路串联起来，用户从一个清晰的切入点出发，按步骤完成全部配置，减少在不同页面间跳转

## 3.4 日志能力接入方案（KR4）

将 Loki 日志收集链路平台化，在 Foxeye 上支持日志收集配置和日志查询能力。

**核心设计思路**：

- **日志收集配置**：平台化管理日志采集配置，支持容器场景（通过 DaemonSet 方式采集容器标准输出/日志文件）和非容器场景（通过 Agent 方式采集主机日志文件）
- **日志查询**：在 Foxeye 平台集成 Loki 日志查询能力，支持 LogQL 查询语法，提供日志搜索、过滤、上下文查看等功能
- **指标-日志关联**：支持从指标告警快速跳转到相关日志，提升故障排查效率
