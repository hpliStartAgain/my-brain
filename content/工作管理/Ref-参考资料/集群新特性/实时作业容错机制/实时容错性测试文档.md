| 原理分析         | 核心逻辑是：**NM 进程死了，但 Container 进程作为孤儿进程由 OS 接管；NM 重启后，通过本地账本（LevelDB）找到这些孤儿。**<br><br>---<br><br>### 1. 恢复的核心机制：状态存储 (State Store)<br><br>在 Container 运行期间，NodeManager (NM) 会维持一个 **NMStateStore**。这是恢复的基石。<br><br>- **实时记录**：每当一个 Container 启动、资源变更或完成时，NM 都会将其元数据（如 `ContainerId`、`Resource`、`Tokens`、`LogDir`、`WorkDir`）同步写入本地的 LevelDB 数据库中。<br>    <br>- **PID 记录**：NM 会记录下 Container 对应的操作系统进程 ID (PID)。<br>    <br><br>---<br><br>### 2. 恢复的具体步骤<br><br>当 NM 重新启动且 `yarn.nodemanager.recovery.supervised` 为 `true` 时，它会执行以下“寻亲”过程：<br><br>#### A. 加载本地状态<br><br>NM 启动后，首先读取 `yarn.nodemanager.recovery.dir` 指定路径下的 LevelDB 文件。它会重建内存中的 Container 列表，此时这些 Container 的状态被标记为 `RECOVERING`。<br><br>#### B. 进程探测 (Liveness Check)<br><br>NM 不会盲目相信数据库。它会通过操作系统指令（如 `kill -0 <PID>`）检查之前记录的 PID 是否还在运行：<br><br>- **如果进程还在**：NM 重新与之建立监控关系。<br>    <br>- **如果进程不在**：NM 将该 Container 标记为已失败，并通知 ResourceManager (RM)。<br>    <br><br>#### C. 重连 Shuffle Handler 与辅助服务<br><br>对于 MapReduce 等任务，NM 会重新初始化辅助服务（Auxiliary Services），确保正在运行的任务依然能通过原来的端口拉取 Shuffle 数据。<br><br>#### D. 与 ResourceManager (RM) 同步<br><br>NM 向 RM 发送心跳，报告自己“复活”了，并告知 RM 它手里目前正带着哪些 Container。RM 会根据全局状态确认这些 Container 是否还应该继续运行（防止在 NM 挂掉期间，作业已经被用户 Kill 掉了）。<br><br>---<br><br>### 3. Supervised 模式的特殊角色<br><br>为什么叫 **Supervised（受监控的）**？这个配置项主要改变了 NM 处理“退出信号”的行为：<br><br>1. **非 Supervised 模式**：NM 正常关闭时（如执行 `stop-yarn.sh`），会认为这是一次彻底的停机，通常会尝试清理（Kill）掉所有正在运行的 Container。<br>    <br>2. **Supervised 模式**：NM 假定自己运行在 `systemd`、`supervisord` 或 `keepalived` 等监控工具下。当它收到退出信号时，它**故意不清理** Container。它认为自己很快就会被监控工具拉起来，所以选择“保留现场”。<br>    <br><br>> **关键点**：`supervised` 确保了 NM 在“生死循环”中，Container 的进程树不会被级联破坏。<br><br>### 4. 注意事项<br><br>- **资源预留**：在 NM 重启期间，RM 不会向该节点分配新任务，直到恢复流程完成。<br>    <br>- **超时机制**：如果 NM 挂掉的时间过长（超过 RM 设定的过期时间），RM 会要求 NM 杀掉所有已恢复的 Container，因为作业可能已经超时失败了。 |     |
