| 计算治理             | Spark 向量化引擎自适应优化系统建设 | **痛点分析：**<br><br>- **盲目启用导致的稳定性下降：** 目前 Gluten 的开启依赖人工判断或粗暴的白名单，导致部分含不支持算子（如复杂 UDF、特定 Window 函数）的作业因频繁的 `Row-to-Columnar` 数据转换而出现 OOM 或性能回退。<br>    <br>- **内存模型不匹配：** Vanilla Spark 依赖 On-Heap 内存，而 Gluten 强依赖 Off-Heap。用户原有的参数配置（如大 Heap）直接应用到 Gluten 会导致堆外内存不足，手动调整参数门槛高且易错。<br>    <br>- **算力浪费：** 大量 CPU 密集型作业（Scan/Agg/Join）仍运行在低效的 Vanilla JVM 引擎上，集群 CPU 利用率存在显著的“虚高”现象，导致额外的扩容成本。<br>    <br>- **缺乏反馈闭环：** 作业开启 Gluten 后是快了还是慢了，缺乏自动化的对比评估， 无法量化收益。<br>    <br><br>**目标：**<br><br>- **构建 GSS (Gluten Suitability Score) 评分模型：** 基于历史 EventLog 画像，量化评估作业对向量化执行的契合度，实现“良币驱逐劣币”。<br>    <br>- **实现自动化内存重配 (Auto-Rebalance)：** 在注入 Gluten 配置时，自动拦截并重写内存参数（将 On-Heap 转移至 Off-Heap），消除因内存模型差异导致的 OOM。<br>    <br>- **降本增效：** 覆盖集群 30% 以上的核心 SQL/ETL 作业，平均 CPU 消耗降低 20% 以上，执行时长缩短 15%。<br>    <br>- **零人工介入：** 实现“画像分析 -> 决策 -> 参数注入 -> 效果验证 -> 黑名单回滚”的全链路自动化。<br>    <br><br>**技术亮点：**<br><br>- **执行计划指纹 (Execution Plan Fingerprint)：** 深度解析 Spark Physical Plan，精准识别“三明治”结构（Columnar -> Row -> Columnar）等高危回退模式。<br>    <br>- **智能内存投影 (Memory Projection)：** 建立数学模型，根据作业历史 Peak Memory 使用情况，动态计算 Gluten 模式下的最佳 Off-Heap/On-Heap 比例。<br>    <br>- **无感灰度 (Canary Launch)：** 利用 Hash 算法对高分作业进行小流量灰度，结合自动化回滚机制，确保生产环境稳定性。                                                                                                                                          |
