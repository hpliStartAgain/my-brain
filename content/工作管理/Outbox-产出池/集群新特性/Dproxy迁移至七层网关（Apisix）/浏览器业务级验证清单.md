### A05 / H 组二次深挖结论（2026-05-09 晚）

> [!WARNING] 当前可以明确：`A05 / H01 / H02 / H03` **仍未通过**，且根因已从“业务 URL 访问错误”收敛到“Tez deep-link 静态资源链路在 SCLB 侧未稳定生效”。

#### 已确认事实

1. `http://10.18.102.127/tez-ui/app/<application_id>` 与 `http://10.18.102.127/knox/gateway/venus/tez/app/<application_id>` 才是本轮用于浏览器终验的正确 deep-link 形态；此前 `#/app/...` 不是最终验证口径。
2. 旧链路中 Tez UI 依赖的不只是 `timeline host`；deep-link 页面本身还依赖 `assets/vendor.js`、`assets/tez-ui.js`、`config/configs.js` 这三类静态资源正确落到同一前缀下。
3. 浏览器白屏时，Network 中只有文档与静态资源，没有后续 `application_*` / `tez_application_*` XHR，请求链路在**前端启动阶段**就已经中断。
4. 直接抓包确认：当浏览器访问 `/tez-ui/app/...` 或 `/knox/gateway/venus/tez/app/...` 时，页面 HTML 里的静态资源仍会落到 `/app/assets/*`、`/app/config/*` 这类 deep-link 子路径；这些子路径一旦返回 HTML 而不是 JS/CSS，前端就会在 `vendor.js` 阶段白屏。

#### 已完成但仍未彻底收敛的修复尝试

1. 已将 `tez-ui.js` 中的 `hosts.timeline` 与 `hosts.rm` 从 `localhost` / 内网地址改写为公网可达地址。
2. 已新增两条 SCLB 路由草案并执行启用：
   - `r-tez-ui-deeplink-assets`：专门承接 `/app/assets/*`、`/app/config/*`
   - `r-tez-ui-deeplink-pages`：专门承接 `/app/*`、`/dag/*`
3. 已尝试将 `r-tez-ui-static` 从自定义 `plg-knox-strip-ingress-prefix` 切换到内置 `serverless-pre-function`，希望直接在已发布路由中完成 deep-link URI 重写。

#### 当前阻塞点

1. `r-tez-ui-deeplink-assets` 与 `r-tez-ui-deeplink-pages` 在 SCLB 控制面上长期停留在**发布中**，浏览器实际流量并未稳定命中新路由。
2. `r-tez-ui-static` 上的 `serverless-pre-function` 配置虽可保存成功，但 `/app/assets/*`、`/app/config/*` 实际返回仍然是 HTML，说明该内置 rewrite 方案尚未在运行面生效。
3. 因此，当前已能确认的结论不是“Tez 前端本身损坏”，而是 **SCLB 平台对 Tez deep-link 静态资源的路由/发布链路存在平台级生效异常**。

> [!NOTE] 以上记录分为两种口径：`已收敛` = HTTP/正文级行为已确认一致；`HTTP/资源已收敛，浏览器待终验` = 结构性问题已修掉，但仍建议再用浏览器对 `A05/H01/C04/F02/F03` 补一次肉眼验收（重点看 DAG 图渲染、样式加载与 Network 中 Timeline 请求）。
