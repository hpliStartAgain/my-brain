> **研究背景**：集群硬件故障（风扇坏、内存坏）需要重启机器换备件，目标是做到用户作业无感知或影响最小化。
> 版本：Spark 3.2.3 / Flink 1.13 & 1.17，YARN on Ambari，Kerberos 认证。

---

## 一、最重要的场景区分

> **这是整篇研究的核心前提**，两个场景处理方式完全不同。

| 场景 | 触发条件 | Container 进程状态 | supervised 有效？ | 恢复机制 |
|------|---------|-------------------|-----------------|--------|
| **NM 服务重启** | `systemctl restart nodemanager` | OS 接管，进程存活 | ✅ 有效（< 10min） | NM 重连孤儿进程 |
| **整机重启** | 机器断电/reboot | 全部被 OS 杀死 | ❌ 无效 | 应用级 checkpoint 恢复 |

**换风扇/换内存 = 整机重启 = supervised 无效 = 必须走 Decommission + Checkpoint 恢复路径**

---

## 二、NM supervised 机制原理（仅适用于 NM 服务重启）

### 核心逻辑

```
NM 进程死了 → Container 进程作为孤儿由 OS 接管
NM 重启后 → 通过本地 LevelDB 账本找到这些孤儿进程重新接管
```

### 恢复步骤

1. **加载状态**：NM 读取 `yarn.nodemanager.recovery.dir` 中的 LevelDB，重建 Container 列表（状态标记为 `RECOVERING`）
2. **进程探测**：`kill -0 <PID>` 检查原 PID 是否存活
   - 进程存活 → NM 重新建立监控关系
   - 进程已死 → 标记失败，通知 RM
3. **重连辅助服务**：Shuffle Handler 等重新初始化（Spark shuffle 数据不中断）
4. **与 RM 同步**：NM 向 RM 报告"复活"，RM 确认这些 Container 是否还应继续运行

### Supervised 模式的作用

- **非 Supervised**：NM 停止时会 **级联杀死所有 Container**（清理现场）
- **Supervised**：NM 假定自己由 systemd 管理，**故意不杀 Container**，等待被拉起后重连

### 关键限制

- NM 挂掉时间 **不能超过 `yarn.resourcemanager.nm.liveness-monitor.expiry-interval-ms`**（默认 10min）
- 超时后 RM 判定 NM 死亡，会要求 NM 杀掉所有恢复的 Container → 作业失败

### 已验证配置

```xml
<property>
  <name>yarn.nodemanager.recovery.enabled</name>
  <value>true</value>
</property>
<property>
  <name>yarn.nodemanager.recovery.supervised</name>
  <value>true</value>
</property>
```

**实测结论（来自测试文档）**：
- Flink 1.17：NM 停止 3min 后重启 → 作业正常，无失败
- Flink 1.17：NM 停止 10min → 作业失败
- Spark 3.2.3：NM 重启（< 10min）→ 作业运行正常

## 三、整机重启的容错路径

### 3.1 Flink 1.17 容错链路

#### TM 节点整机重启

```
TM 节点重启 → 容器进程全死
→ NM 向 RM 报告 Container 异常退出
→ RM 通知 JM（通过 AM 心跳）
→ JM 检测到 TM 心跳超时（秒级感知）
→ 触发 restart-strategy
→ 向 RM 重新申请 TM Container（在其他节点）
→ 新 TM 启动，向 JM 注册
→ JM 协调所有 TM 从最新 checkpoint 恢复
→ 继续消费 Kafka，重放 [last_checkpoint, failure) 区间数据
```

**恢复时间**：
- Container 申请 < 30s
- TM 启动 < 30s
- Checkpoint 加载：取决于状态大小（通常 10s-2min）
- **总计：通常 1-3min**

#### JM 节点整机重启（需要 HA）

```
JM 节点重启 → AM Container 死
→ RM 检测 AM 超时（yarn.am.max-attempts 控制重试）
→ RM 在其他节点重新启动新 AM Container
→ 新 JM 启动，从 ZooKeeper 竞选为 Active
→ 新 JM 从 HDFS 加载最新 checkpoint
→ 通知所有 TM 重新连接
→ 作业恢复运行
```

**要求**：必须开启 `high-availability.type=zookeeper`，HDFS 存储 checkpoint

#### Flink 关键配置

```yaml
# Checkpoint
execution.checkpointing.enabled: true
execution.checkpointing.interval: 60000        # 60s，平衡性能与恢复粒度
execution.checkpointing.mode: EXACTLY_ONCE
execution.checkpointing.timeout: 600000        # 10min，大状态作业需要
state.backend: rocksdb                         # 大状态推荐
state.backend.rocksdb.checkpoint.incremental: true  # 增量 checkpoint，减少 IO
state.checkpoints.dir: hdfs://router/user/bdwh/flink_checkpoints/<job-name>
state.checkpoints.num-retained: 3             # 保留 3 个，方便回滚

# 重启策略（节点换件场景推荐指数退避）
restart-strategy: exponential-backoff
restart-strategy.exponential-backoff.initial-backoff: 1 s
restart-strategy.exponential-backoff.max-backoff: 1 min
restart-strategy.exponential-backoff.backoff-multiplier: 2.0
restart-strategy.exponential-backoff.reset-backoff-after: 10 min

# YARN HA（JM 节点换件必须）
high-availability: zookeeper
high-availability.zookeeper.quorum: zk1:2181,zk2:2181,zk3:2181
high-availability.storageDir: hdfs://router/user/flink/ha
```

### 3.2 Spark Structured Streaming 3.2.3 容错链路

#### Executor 节点整机重启

```
Executor 节点重启 → Executor 容器进程全死
→ NM 向 RM 报告 Container 异常
→ RM 通知 Driver（心跳，秒级）
→ Driver 将该 Executor 加入黑名单（spark.blacklist.enabled=true）
→ 当前微批未完成的 Task 重试（spark.task.maxFailures=4）
→ 重试 Task 分配到其他 Executor（黑名单节点排除）
→ Driver 向 RM 重新申请 Executor（其他节点）
→ 新 Executor 启动，继续处理后续微批
→ 整体：微批延迟增加，数据不丢失
```

#### Driver（Cluster Mode）节点整机重启

```
Driver 所在节点重启 → AM Container 死
→ RM 检测 AM 失败（spark.yarn.maxAppAttempts 控制重试，默认 2）
→ RM 在其他节点重新启动 AM Container
→ 新 Driver 启动，读取 HDFS 上的 checkpoint 目录
→ 从最近成功微批的 offset 继续消费 Kafka
→ 重放 [last_checkpoint_offset, failure_offset) 数据
→ 作业恢复，用户感知：约 60-120s 的服务中断
```

**注意**：Client Mode 下 Driver 在本地机器，没有 HA，Driver 所在机器重启 = 作业丢失。**生产必须用 Cluster Mode**。

#### Structured Streaming 三层恢复机制

```
Checkpoint 目录结构（HDFS）：
  /checkpoints/<app-name>/
    ├── metadata/       → 应用元数据
    ├── offsets/        → WAL：每个微批消费的 Kafka offset
    ├── commits/        → 已提交（成功处理）的微批 ID
    └── state/          → 有状态操作的状态快照（aggregation, join 等）
```

**恢复语义**：
- `offsets/N` 存在 but `commits/N` 不存在 → 微批 N 未完成 → 重新处理（Exactly-Once 语义要求 sink 幂等）
- `commits/N` 存在 → 微批 N 已完成 → 跳过，继续 N+1

#### Spark 关键配置

```properties
# YARN 相关
spark.submit.deployMode=cluster              # 生产必须 cluster
spark.yarn.maxAppAttempts=2                  # Driver 最大重试次数

# Task 容错
spark.task.maxFailures=4                     # 单个 Task 的最大失败次数
spark.blacklist.enabled=true
spark.blacklist.timeout.conf=600000          # 与 YARN NM 超时对齐（10min）

# Checkpoint（必须指向 HDFS）
spark.sql.streaming.checkpointLocation=hdfs://router/user/bdwh/spark_checkpoints/<app-name>
spark.sql.streaming.schemaInference=false    # 生产必须 false，防止 schema 漂移

# 动态分配（可选，节点重启后 Executor 自动迁移）
spark.dynamicAllocation.enabled=true
spark.dynamicAllocation.minExecutors=1
```

## 四、Decommission：换件时的推荐 SOP

### 适用场景
- 整机重启（换风扇、换内存、换磁盘）
- 希望在重启前先让作业迁走，减少 checkpoint 恢复时间

### Decommission 对各框架的行为差异

| 框架 | Decommission 期间行为 | 新 Container 申请 | 迁移主动性 |
|------|----------------------|-----------------|---------|
| **Flink** | TM **不主动迁移**，等待自然完成 | 停止在该节点申请 | 被动（NM down 后才重试） |
| **Spark** | 新 Task 自动转移；动态分配释放 Executor | 停止在该节点申请 | 主动（黑名单机制） |
| **MR** | map task 自动迁移 | 停止 | 主动 |

**Flink 的特殊注意**：长时间运行的 Flink 作业（如 Kafka → HDFS 管道），TM 不会主动迁走，Decommission 可能等很久（几小时）。可以选择：
1. **等待**：自然等 Flink 微批完成（推荐，对用户完全无感）
2. **主动触发 SavePoint**：`flink savepoint <job-id> <savepoint-dir>`，停止作业，重启后从 savepoint 恢复（有秒级中断）

### 操作 SOP

```bash
# === Step 1: 预检查（5min）===
yarn node -list -all | grep <node>
yarn application -list | grep RUNNING
# 记录当前运行的 Flink/Spark 作业列表

# === Step 2: 启动 Decommission ===
yarn node -decommission <node-hostname>

# === Step 3: 等待 Container 清空 ===
# Spark 通常 < 30min；Flink 可能较长
watch -n 30 'yarn node -list -states decommissioning'
watch -n 30 'yarn node -status <node> | grep "Running Containers"'

# 等待 Running Containers 降为 0

# === Step 4: 重启机器 ===
ssh <node> 'sudo shutdown -r 0'

# === Step 5: 硬件维护 ===
# 更换风扇/内存/磁盘

# === Step 6: 重新上线 ===
# 等 NM 服务启动后
yarn node -recommission <node-hostname>
yarn node -status <node> | grep "Node-Health-Status"
# 期望输出：Node-Health-Status: HEALTHY

# === Step 7: 验证 ===
yarn node -list -all | grep <node>
# 检查 Flink/Spark 是否开始在该节点申请新 Container
```

## 五、关键超时参数汇总

| 参数 | 默认值 | 含义 | 建议值 |
|------|--------|------|--------|
| `yarn.resourcemanager.nm.liveness-monitor.expiry-interval-ms` | 600000 (10min) | RM 认定 NM 死亡的超时 | 保持 600000（对应 NM 重启窗口） |
| `yarn.nodemanager.recovery.supervised` | false | NM 重启时是否保留 Container | **true** |
| `yarn.am.max-attempts` | 2 | AM（Driver/JM）最大重试次数 | 2-3 |
| `execution.checkpointing.interval` | 无 | Flink checkpoint 间隔 | 30000-60000 ms |
| `execution.checkpointing.timeout` | 600000 | Flink checkpoint 超时 | 600000（大状态）|
| `spark.task.maxFailures` | 4 | Spark Task 最大失败次数 | 4（默认够用）|
| `spark.yarn.maxAppAttempts` | 2 | Spark Driver 重试次数 | 2 |
| `spark.blacklist.timeout.conf` | 3600000 (1h) | Spark Executor 黑名单 TTL | **600000 (10min)** |

## 六、结论汇总

### 场景一：换 NM 内部故障（服务级）
**结论**：`supervised=true` + NM 重启 < 10min → **Flink 和 Spark 作业均无感知**

### 场景二：整机重启（换风扇/内存）
**推荐路径**：Decommission → 等 Container 清空 → 重启 → Recommission
**保障**：Flink checkpoint + Spark checkpoint → 恢复时间 1-5min，数据不丢失

### 场景三：JM/Driver 节点需要换件
- Flink：需要开启 YARN HA（ZooKeeper + HDFS），JM 所在节点 decommission 后，Standby JM 接管
- Spark：Cluster Mode + `spark.yarn.maxAppAttempts >= 2`，Driver AM 自动在其他节点重启

### 最小化影响的核心前提
1. **Flink**：`state.checkpoints.dir` 必须在 HDFS，checkpoint 正常在跑
2. **Spark**：`checkpointLocation` 必须在 HDFS，`deployMode=cluster`
3. **YARN**：`yarn.nodemanager.recovery.supervised=true`（服务重启保障）
4. **维护**：优先走 Decommission，让作业自然迁移，而非直接重启
