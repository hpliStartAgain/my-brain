## 摘要

这篇文章记录了我这段时间系统性地把大模型融入日常工作的一些真实体会，涵盖名词扫盲、工具配置、Vibe Coding、AI辅助排障、AI任务管理、以及用 Go+Eino 开发 Agent 几个方向。不追求大而全，只写自己真正用起来的那部分。

---

## 第 1 章 为什么开始认真用 AI

说实话，最开始我对大模型的态度是半信半疑的。偶尔用 ChatGPT 查个语法、解释个报错，跟用搜索引擎差不多。真正让我改变态度是两件事：

第一件事是用 AI 排查了一个折腾我好几天的 NameNode GC 问题。一个 Scan RS 从 4ms 爆炸到 41000ms 的故障，传统排查流程绕了一大圈，最后靠一个有 JVM 经验的同事才点破——Swap 把 JVM 的老年代换出去了，导致缺页中断。后来我把同样的症状贴给 AI，它三分钟之内直接给出了 Swap+NUMA 的三角关系分析，还顺手生成了诊断脚本。

第二件事是看到团队里有人用 Claude Code 把几百行的告警迁移系统需求转化成了完整的架构设计文档和 API 定义，比我自己写快了不止一个数量级。

这两件事让我意识到：AI 不是玩具，是真的能进工作流的工具。关键是要搞清楚它能做什么、怎么用对。

## 第 2 章 先扫盲：搞清楚那些绕来绕去的名词

大模型领域的名词增长速度很夸张。Prompt、RAG、Agent、MCP、Function Calling……每篇文章都用这些词，但含义经常微妙地不同，有时同一个词在不同厂商的文档里指不同的东西。先把这张地图理清楚，后面所有内容才好说。

### 2.1 Token：模型看到的不是"字"

模型处理文本的最小单位是 Token，不是字符，不是词。用 BPE 分词算法切分后，英文单词平均约 1.3 个 Token，中文汉字约 1.5-2 个 Token。这带来两个实际影响：

1. **成本估算要用 Token 而不是字数**。同样的信息量，中文比英文消耗更多 Token。
2. **"128K 上下文"不等于"128K 个汉字"**，实际能放的汉字量要打折。

不同模型的分词器不一样，Token 计数不能跨模型直接比较。

### 2.2 Prompt 的三个角色

跟模型对话，输入内容分三种角色：

**System Prompt（系统提示词）**：定义模型的角色、行为规则、输出格式约束。这部分在整个对话中持续生效，适合放那些每次都要遵守的规则。它不是万能的——精心构造的 User Prompt 可以在某些情况下覆盖 System Prompt 的指令（这叫 Prompt Injection），所以安全边界不能全靠它。

**User Prompt（用户消息）**：每次请求的具体内容，这是你最熟悉的部分。质量直接影响输出，但没有持久性，每次重新构造。

**Assistant Prompt（预填充）**：这个用得少，但挺有用——在发送请求时，把"助手已开始回复"的内容带上，强制模型从这个位置继续生成，能有效控制输出格式（比如强制输出 JSON）。Claude API 支持这个用法。

### 2.3 上下文窗口：模型的"工作内存"

上下文窗口是模型单次推理能"看到"的最大 Token 数，包含 System Prompt + 对话历史 + 当前输入 + 注入的文档。

有个反直觉的结论：窗口大不代表能有效利用里面的全部内容。实验表明模型对上下文**开头和结尾**的关注度高，中间容易被忽略（"Lost in the Middle"效应）。所以组织信息的原则是：最重要的内容放首尾，用 XML 风格标签划定信息块边界。

当前主流模型的窗口大小对比：

| 模型                      | 上下文窗口                            |
| ----------------------- | -------------------------------- |
| GPT-4o                  | 128K                             |
| Claude（内网代理版）           | 200K（claude-sonnet/opus），1M beta |
| Gemini 3 Pro            | 1M                               |
| panther-v3/r1（deepseek） | 128K                             |

### 2.4 RAG：开卷考试

RAG（Retrieval-Augmented Generation，检索增强生成）解决的是模型"不知道私有/最新信息"的问题。核心流程是：把文档提前切块、向量化存库，查询时先检索相关文档块，再把检索结果和问题一起喂给模型，让它基于文档回答。

类比：闭卷考试是靠预训练知识回答，RAG 是开卷考试——答题时可以翻资料。

RAG 的局限不能忽视：
- **检索噪声**：召回的文档块不一定都相关，错误的上下文会让模型给出"看似合理的错误答案"，比直接说"不知道"更危险
- **多跳推理**：需要跨多个文档关联推理的问题，单次检索覆盖不了
- **Chunking 策略**：块切太小缺乏上下文，切太大引入噪声，没有通用最优解

### 2.5 Function Calling / Tool Use：模型的"手"

Function Calling 让模型能声明"我需要调用某个函数，参数是这些"，然后由外部程序真正执行。模型不执行，只决策——这是关键。

执行流程：用户提问 → 模型输出 `tool_call` 意图（含函数名和参数）→ 外部程序执行函数 → 把结果返回给模型 → 模型生成最终回答。这个过程模型推理了两次。

这比"让模型直接输出 JSON 再 parse"可靠得多，因为 Function Calling 的参数生成是按 JSON Schema 约束的，结构稳定，不会出现各种奇怪的格式。

### 2.6 MCP：工具连接的 USB 标准

MCP（Model Context Protocol）是 Anthropic 2024 年发布的工具连接协议。在没有 MCP 之前，每个 AI 应用接每个外部工具都要自己写集成代码，N 个应用 × M 个工具 = N×M 套集成，维护成本很高。

有了 MCP，工具开发者实现一次 MCP Server，任何支持 MCP 的应用都可以直接接。相当于 USB 统一接口，不用再为每个设备配专属线。

MCP 里有三个概念：
- **Tools**：模型可以调用的函数（等同于 Function Calling）
- **Resources**：MCP Server 暴露的可读数据（类似 GET 接口）
- **Prompts**：预定义的 Prompt 模板

目前生态已经比较丰富，Filesystem、Git、PostgreSQL、Brave Search、GitHub 等常用工具都有官方 MCP Server。

### 2.7 AI Agent：能自主完成任务的程序

Agent 的本质是一个循环：感知 → 推理 → 行动 → 再感知 → ……直到任务完成。最常见的推理框架是 ReAct（Reasoning + Acting）：模型先"想"（Thought），再"做"（Action），观察结果后继续想。

很重要的一点：**不是所有任务都适合用 Agent**。步骤固定的任务用 Workflow 比 Agent 更可靠、更易调试。只有当"下一步做什么"需要根据中间结果动态决定时，才真的需要 Agent。

Agent vs Workflow 的判断标准：任务的执行路径在开始前能不能完全确定？能确定 → Workflow；不能确定 → Agent。

### 2.8 Skills：Claude Code 里的可复用行为

Skills 是 [[Claude Code]] 体系里的概念，本质是一个 Markdown 文件，描述一类特定任务的执行流程和输出规范，放在 `.claude/skills/` 目录下。触发对应 Skill 时，Claude Code 会加载这个文件，按照里面的指令执行任务。

与 Tool/Function 的区别：Tool 是让外部程序执行确定性操作，Skill 是让模型本身按照预定义的行为模式处理判断性任务。

### 2.9 Extended Thinking：模型的草稿纸

Extended Thinking（DeepSeek 叫 R1，OpenAI 叫 o 系列）是让模型在给出最终答案前，先在内部进行大量推理（这些推理过程通常对用户半可见）。本质是**用更多 Token 换更高推理质量**。

适合用 Thinking 的场景：复杂逻辑推理、数学证明、需要多角度分析的决策。
不适合的场景：简单问答、内容生成——纯浪费钱。

### 3.2 Claude Code（CC）：我最常用的 AI 工具

Claude Code 是 Anthropic 官方的命令行 AI 助手，在终端里跑，能感知当前目录、读写文件、执行命令。跟普通聊天 AI 的最大区别是它有**工作区感知**——它知道你在哪个目录，会主动读 CLAUDE.md 里的上下文约定，理解你的项目结构。

**接入内网代理**（加到 `~/.bashrc`）：

```bash
export ANTHROPIC_BASE_URL="https://aix.panther.sohurdc.com"
export ANTHROPIC_API_KEY="your-proxy-key"
export ANTHROPIC_DEFAULT_SONNET_MODEL="claude-sonnet-4-6"
export ANTHROPIC_DEFAULT_OPUS_MODEL="claude-opus-4-6"
export ANTHROPIC_DEFAULT_HAIKU_MODEL="claude-haiku-4-5"
export ANTHROPIC_MODEL="claude-sonnet-4-6"
```

或者写到 `~/.claude/settings.json` 的 `env` 字段里，效果一样。

推荐同时安装 **cc-switch**（[https://github.com/farion1231/cc-switch](https://github.com/farion1231/cc-switch)），可以快速在不同配置 Profile 之间切换，比如"日常模式"（sonnet）和"深度推理模式"（opus 或 r1）。

### 3.3 Cline（VS Code 插件）

如果习惯在 VS Code 里工作，Cline 是比较好的选择，功能上跟 CC 类似但集成在编辑器里。配置方法：

左侧 Cline 图标 → 右上角齿轮 → API Provider 选 `Anthropic` → Base URL 填 `https://aix.panther.sohurdc.com` → 填入代理 Key → 选模型。

## 第 4 章 Vibe Coding：用 AI 写代码的正确姿势

"Vibe Coding"这个词有点玄，实际上就是一种编程状态：你描述意图，AI 实现细节，你负责把关方向和质量。这不是"让 AI 替代你写代码"，而是把你从重复性的实现工作中解放出来，专注在更有价值的部分。

### 4.1 Vibe Coding 的核心原则

**描述意图，不是指令**。与其说"帮我写一个 for 循环遍历这个列表"，不如说"我需要统计每个用户过去 7 天的登录次数，数据在这个结构里"。前者是在教 AI 怎么写，后者是在告诉 AI 你要什么。

**提供上下文，不要让 AI 猜**。在工作目录里维护好 `CLAUDE.md`，写清楚项目背景、技术栈约定、目录结构。AI 读到这些后给出的方案会更贴合实际，不会推荐一堆用不了的东西。

**小步迭代，及时纠偏**。不要一次让 AI 写几百行然后希望全对。每次聚焦一个功能点，看输出，确认方向对，再继续。出了偏差越早说越好，上下文越短纠正成本越低。

**Review 是必须的**。AI 生成的代码逻辑上不一定完全正确，安全性不一定考虑周全。你需要读懂它写了什么，而不是盲目执行。"生成了就用"是最危险的姿势，也是从 AI 工具中学不到东西的捷径。

### 4.2 什么任务适合 Vibe Coding

高度适合：
- **有明确规范的任务**：写符合某个协议/API 格式的代码（REST API、Prometheus Exporter、MCP Server）
- **重复性实现**：CRUD、序列化/反序列化、测试用例生成
- **已知模式的实现**：对某种设计模式有清晰理解，让 AI 快速填充
- **脚本工具**：诊断脚本、数据处理脚本，生成后人工 Review 再执行

不太适合：
- **需要深度理解业务语义的核心逻辑**：AI 不知道你的业务，容易写出"能跑但不对"的代码
- **性能敏感的底层代码**：生成的代码需要 Benchmark 验证，不能凭感觉
- **安全敏感的代码**：认证、加密、权限控制，AI 生成的方案需要专项安全审查

### 4.3 几个实用的提问技巧

**贴入相关代码**，让 AI 在你的上下文里工作，而不是从零设计：

```
以下是我们已有的 Exporter 基础结构，请参照这个风格，
为 HiveServer2 的 JVM 指标新增一个 Collector 实现，
需要暴露 heap_used、gc_count、gc_time 三个指标：

[粘贴已有代码]
```

**明确约束条件**，避免 AI 过度设计：

```
请不要引入新的依赖，只用标准库实现。
函数保持在 30 行以内，不需要错误重试逻辑，调用方负责处理错误。
```

**让 AI 解释它写的东西**：看不懂但觉得可能对，直接问"这段代码的 XXX 是什么意思"，这比对着文档自己研究快多了，而且顺便可以确认 AI 的理解是否和你的预期一致。

### 4.4 Claude Code 的特殊能力

CC 跟普通聊天 AI 最大的不同是它有**文件系统操作能力**：可以直接读写文件，执行 shell 命令，在多个文件之间做修改，甚至提交 git。这让它能处理跨文件的重构任务，而不只是在对话框里粘代码。

几个我常用的工作流：

- **生成完整功能**：在 CC 里说"在 `pkg/exporter/` 下新建一个 Kafka JMX Collector，参照 `hdfs_collector.go` 的结构"，它会直接创建文件。
- **代码审查**：`/review` 或直接描述"帮我看看这段代码有什么问题"，它会给出具体的改进意见。
- **调试辅助**：把报错信息和相关代码一起粘进去，通常能很快定位问题方向。

## 第 5 章 AI 辅助排障：以大数据集群为例

排查生产故障是我工作中最高强度的场景之一。信息分散（指标在 Grafana、日志在 Loki、配置在 Ambari）、经验孤岛（老工程师的诊断直觉很难文档化）、告警噪声（一次批量作业失败触发几十条告警）——这三个问题 AI 都能不同程度地帮上忙。

### 5.1 我们的可观测武器库

AI 排障的前提是先有信息来源。我们集群的可观测体系大致如下：

- **指标层**：自研 Exporter（HDFS/YARN/HBase）+ Prometheus 抓取 + VictoriaMetrics 长期存储 + Grafana 可视化
- **日志层**：Aloy 采集各节点组件日志 → Loki 聚合 → Grafana LogQL 查询（进行中）
- **告警层**：Foxeye（基于夜莺 Nightingale 二次开发）+ PromQL/MetricsQL 告警规则
- **集群管理**：Ambari，配置变更历史追踪很有用
- **作业层**：YARN ResourceManager UI + Spark History Server + Flink Web UI

排障时，这些工具提供的原始信息（日志片段、指标截图、配置 diff）是喂给 AI 的原材料。

### 5.2 黄金三问法

我总结出的 AI 排障对话框架，分三轮进行：

**第一轮：描述现象**

把故障的第一手观察结构化出来：发生时间、发现来源（告警/用户反馈）、受影响范围、初步观察到的异常。尽量精确，"高了一些"没用，"从 70% 升至 92%，14:23 开始"才有用。

**第二轮：提供数据**

AI 会给出 2-5 个可能方向，针对每个方向去采集对应数据，把数据回馈给 AI。这一步的关键是数据质量而不是数据量：100 行有代表性的日志比 10 万行原始日志更有效。

**第三轮：验证假设**

AI 给出假设后，工程师执行验证命令，把结果反馈，AI 确认或否定假设，继续下一轮。通常 2-4 轮能收敛到根因。

### 5.3 三个真实案例

**案例一：NameNode 长 GC**

G1 GC 的 Scan RS 耗时从正常的 4.4ms 爆炸到 41,111ms（放大 10,000 倍），HDFS 读写严重延迟。

传统排查：大约 67 分钟，最后靠网上别人分享的issue点破根因——Linux Swap 把 JVM 老年代 Region 换出物理内存，G1 扫描 Remembered Set 时触发缺页中断，磁盘随机 I/O 的寻道时间和 DRAM 访问差了 6 个数量级。

AI 辅助排查：把 GC 日志片段 + `free -h` + `vmstat` 输出贴给 AI，约 18 分钟拿到根因分析，AI 直接指向 Swap+NUMA 的三角关系，并给出了"确认 Swap 使用量→执行 swapoff→加 JVM 参数"的修复 SOP 和可复用的诊断脚本。

**案例二：HiveServer2 文件描述符泄漏**

进程 FD 数量接近上限（65535），重启即愈但 3-4 天后复发。

传统排查：横跨 3 次故障周期、约 2 周才定位到是业务 UDF 里的 Jedis 连接在异常路径下没有关闭。

AI 辅助排查：把 `lsof` 的统计摘要（按 FD 类型分组计数）贴给 AI，AI 发现 IPv4 socket 数量异常，建议按远端 IP 聚合统计。一执行，25000+ 条连接全指向同一个 Redis 集群，AI 立即聚焦到 UDF 内的 Jedis 泄漏——约 2 小时定位，比 2 周快了 200 倍。

**案例三：Flink Savepoint 磁盘打满**

HDFS 路径从 200GB 膨胀到 1.8TB，触发容量告警。

AI 辅助：把 `hdfs dfs -ls -R` 输出粘给 AI，它直接生成了保留最近 N 个 Savepoint、清理其余的脚本，同时指出根因（Flink 不会自动清理 Savepoint）并给出了完整的配置建议（区分 Savepoint 和 Checkpoint 的清理策略）。从贴信息到拿到可用脚本，约 5 分钟。

### 5.4 给 AI 设定角色

System Prompt 的质量直接影响排障对话质量。我用的基础角色设定：

```
你是一名拥有 10 年经验的大数据平台 SRE，精通 Hadoop/Flink/Spark/Hive/HBase 运维。
你熟悉 JVM 调优（G1/ZGC）、Linux 内核参数（swap、NUMA、THP）、网络诊断。
排障风格：先系统层（OS/JVM），再组件层，最后业务层。
提出假设时，同时给出验证该假设需要收集的具体数据和命令。
生成脚本时，标注脚本用途和风险提示，高风险操作先检查前置条件。
```

这比每次空白对话能得到更精准的分析。

### 5.5 AI 排障的边界

**适合 AI 的**：解析报错堆栈、分析日志模式、生成诊断脚本、翻译 Zabbix 规则到 PromQL、撰写故障复盘初稿。

**不适合 AI 的**：实际执行高风险命令（swapoff、GC dump）、判断业务语义是否正确、物理层排查（硬件/网络抖动）、最终决策（上线/回滚）。

这个边界的本质：AI 是"知识顾问"，工程师是"执行者"。

## 第 6 章 AI 任务管理：让繁琐的事情不再繁琐

这块是我花时间最多、也最有成就感的地方——把自己的工作流搭成了一套 AI 可以参与的系统。

### 6.1 工作系统的底层设计

我的工作管理体系基于 Obsidian 构建，核心思路是**结构化优先**：让每个任务都有机器可读的元数据，这样 AI 才能理解你的工作状态，而不是只能看到一堆纯文本。

**三层看板**，按任务属性分开管：
- `架构演进与交付.md`：周期 >1 周、需要设计文档的中大型任务
- `日常运维与琐事.md`：配置变更、定期检查等重复性运维
- `技术攻坚与前瞻研究.md`：预研、调研、可行性分析

![[Pasted image 20260317142116.png]]

看板里不直接写内容，每个条目是指向 `Inbox-Task池/` 下独立任务文件的 Wiki 链接。这样任务详情、进度、附件都在一个地方，看板只做状态展示。

**任务文件的 Frontmatter**（Dataview 插件依赖这些字段）：

```yaml
---
type: task
status: todo | doing | done
priority: P0 | P1 | P2
deadline: YYYY-MM-DD
domain: 集群新特性 | 集群可观测建设 | 集群智能运维 | 集群日常运维 | 计算治理
lifecycle: research | engineering | review
progress: "0"
completed_date:
started_date:
---
```

**日记系统**：每天的日记分晨间 Init（Dataview 查询进行中任务 + 当日碎片记录）和晚间 Checkpoint（Dataview 查询当日完成任务 + 文字复盘）。晨间看当天要做什么，晚间确认做了什么。

这套体系本身不复杂，复杂的是持续维护它。而 AI 的价值就在这里——它能帮你减少"维护工作流"本身的摩擦。

### 6.2 Claude Code Skills：可复用的工作流自动化

我在 `.claude/skills/` 目录下存了三个常用 Skill，触发对应指令时 CC 会按照 Skill 里的指令执行：

**daily-report**：读取当天日记和进行中任务的 Frontmatter，生成"今日完成/进行中/明日计划"的摘要表格，追加到日记末尾。以前每天晚上手动写复盘，现在 CC 帮我生成初稿，我只需要改几行。

**weekly-init**：每周一跑，扫描当前 OKR 任务，补全缺少验收标准的任务，检查是否有需要新建 Inbox 任务的 OKR 条目，更新看板状态。

**write-OKR**：读取 OKR-old 目录和 Inbox-Task池 的任务文件，生成完整的半年度 OKR 文档，包含 Mermaid 架构图和 Gantt 时间轴。以前写 OKR 要半天，现在 CC 跑一遍生成初稿，我负责校对和补充细节。

### 6.3 CLAUDE.md：让 AI 理解你的工作环境

每个项目目录放一个 `CLAUDE.md`，写清楚：
- 这个目录是干什么的
- 目录结构和各文件夹的职责
- 核心约定（Frontmatter 规范、命名规则、工具栈）
- 不要写什么：当前任务状态、临时上下文（这些会过期）

这是 AI 理解你工作环境的"说明书"，投入写好这个文件的时间，会在后续所有 AI 交互中持续回报。

### 6.4 一个实用原则

AI 最适合做的任务管理工作是：**有固定格式要求、需要聚合信息、但本身不需要你做判断**的部分。比如"把这周完成的任务整理成周报格式"、"根据这些任务文件生成 OKR 的进展摘要"。

需要你拍板的决策（这个任务优先级怎么定、这件事要不要做）、需要你评估的判断（这个方案是否可行），AI 是帮不了的，它只能提供信息，决策权在你。

## 第 7 章 AI 开发 Agent：用 Eino 入门

我们团队在做 Oncall Copilot 项目，技术选型是 Go + Eino 框架。这里分享一些入门级的经验，适合想用 Go 开发 LLM 应用的同学。

### 7.1 为什么用 Eino 而不是 LangChain

核心原因很简单：我们的工程语言是 Go，而 LangChain 是 Python 生态的。在 Go 生产环境里套 Python 服务，运维成本太高。

Eino 是字节跳动开源的 Go LLM 框架（CloudWeGo/eino），核心优势：
- 类型安全，编译期发现问题
- 基于有向图（Graph）的组件编排，逻辑清晰
- 原生支持流式输出
- 内置 Callback 机制，方便对接可观测体系

### 7.2 最基础的用法：对话 Agent

接入内网模型，用 OpenAI Compatible 接口：

```go
package main

import (
    "context"
    "fmt"
    "os"

    "github.com/cloudwego/eino-ext/components/model/openai"
    "github.com/cloudwego/eino/schema"
)

func main() {
    ctx := context.Background()

    // 初始化 ChatModel，接入内网代理
    // 使用 OpenAI Compatible 接口，baseURL 指向内网代理
    model, err := openai.NewChatModel(ctx, &openai.ChatModelConfig{
        BaseURL: "https://aix.panther.sohurdc.com/v1",
        APIKey:  os.Getenv("ANTHROPIC_API_KEY"),
        Model:   "panther-v3", // 或 "claude-sonnet-4-6"
    })
    if err != nil {
        panic(err)
    }

    // 构造对话消息
    messages := []*schema.Message{
        schema.SystemMessage("你是一名大数据集群 SRE，擅长排查 Hadoop/Flink/Spark 故障。"),
        schema.HumanMessage("NameNode GC Scan RS 耗时突然从 5ms 升至 40000ms，可能是什么原因？"),
    }

    // 发起对话
    resp, err := model.Generate(ctx, messages)
    if err != nil {
        panic(err)
    }

    fmt.Println(resp.Content)
}
```

### 7.3 带工具调用的 Agent（ReAct 模式）

工具调用的核心是定义工具函数，让模型决定何时调用：

```go
package main

import (
    "context"
    "fmt"
    "os"

    "github.com/cloudwego/eino-ext/components/model/openai"
    "github.com/cloudwego/eino/components/tool"
    "github.com/cloudwego/eino/compose"
    "github.com/cloudwego/eino/schema"
)

// 定义诊断工具：查询集群指标
type ClusterMetricsTool struct{}

func (t *ClusterMetricsTool) Info(ctx context.Context) (*schema.ToolInfo, error) {
    return &schema.ToolInfo{
        Name: "get_cluster_metrics",
        Desc: "查询大数据集群的关键指标，如 NameNode Heap 使用率、GC 停顿时间等",
        ParamsOneOf: schema.NewParamsOneOfByParams(map[string]*schema.ParameterInfo{
            "component": {
                Type: schema.String,
                Desc: "组件名称，如 namenode、resourcemanager、hiveserver2",
            },
            "metric": {
                Type: schema.String,
                Desc: "指标名称，如 heap_used_ratio、gc_pause_ms",
            },
        }),
    }, nil
}

func (t *ClusterMetricsTool) InvokableRun(ctx context.Context, args string, opts ...tool.Option) (string, error) {
    // 实际实现中这里调用 VictoriaMetrics API
    // 这里用模拟数据演示
    return `{"component":"namenode","metric":"gc_pause_ms","value":41111,"unit":"ms","timestamp":"2026-03-10T14:28:15+08:00"}`, nil
}

func main() {
    ctx := context.Background()

    // 初始化带工具的 ChatModel
    model, err := openai.NewChatModel(ctx, &openai.ChatModelConfig{
        BaseURL: "https://aix.panther.sohurdc.com/v1",
        APIKey:  os.Getenv("ANTHROPIC_API_KEY"),
        Model:   "claude-sonnet-4-6",
    })
    if err != nil {
        panic(err)
    }

    // 注册工具
    clusterTool := &ClusterMetricsTool{}
    toolsNode, err := compose.NewToolNode(ctx, &compose.ToolsNodeConfig{
        Tools: []tool.BaseTool{clusterTool},
    })
    if err != nil {
        panic(err)
    }

    // 构建 ReAct 循环的 Graph
    // Graph 的结构：ChatModel → 判断是否需要调用工具 → ToolsNode → 回到 ChatModel
    graph := compose.NewGraph[*schema.Message, *schema.Message]()

    graph.AddChatModelNode("llm", model)
    graph.AddToolsNode("tools", toolsNode)
    graph.AddEdge(compose.START, "llm")

    // 条件边：如果模型决定调用工具，走 tools 节点；否则结束
    graph.AddConditionalEdges("llm", compose.ToolsNodePregelCondition, map[string]string{
        compose.ToolsNodePregelResultHasToolCall: "tools",
        compose.ToolsNodePregelResultNoToolCall:  compose.END,
    })
    graph.AddEdge("tools", "llm") // 工具执行完后回到 LLM

    chain, err := graph.Compile(ctx)
    if err != nil {
        panic(err)
    }

    // 发起带工具调用的对话
    resp, err := chain.Invoke(ctx, schema.HumanMessage(
        "帮我查一下 NameNode 的 GC 停顿时间",
    ))
    if err != nil {
        panic(err)
    }

    fmt.Println(resp.Content)
}
```

### 7.4 我们的实践：告警迁移系统

团队第一个落地的 Eino 项目是告警迁移系统——把 Zabbix 存量告警规则迁移到 Foxeye（PromQL 格式）。核心流程：

1. 读取 Zabbix 告警规则（自定义触发器表达式）
2. 通过 LLM 翻译成等价的 PromQL
3. 对比新旧规则在历史数据上的触发情况（双跑验证）
4. 输出差异报告，人工确认后上线

这个项目验证了 Eino 在生产场景的可用性，也让我们对"LLM 能做什么、不能做什么"有了更清晰的认识——翻译工作 LLM 完成得很好，但语义等价性验证仍然需要工程师参与。

### 7.5 进阶：Oncall Copilot 的多 Agent 架构

我们正在规划的 Oncall Copilot 是一个 Master-Sub 多智能体系统：

- **Master Agent**（对话中枢）：基于 ReAct 范式，接收用户指令或告警事件，分解任务，分发给专化的 Sub-Agent
- **Alert Agent**（告警聚合）：解决告警风暴，同一故障的多条告警自动聚合
- **Diag Agent**（故障诊断）：L1 通用联动（自动关联同主机日志+指标）+ L2 专家 SOP（按预设排查流程执行）
- **Inspect Agent**（主动巡检）：定期检查集群健康状态，提前发现隐患

知识库用 Milvus 做 RAG，把历史故障案例向量化存储，新故障触发时检索相似历史案例作为参考。

这个方向目前还在规划阶段，但已有的 Eino 经验（告警迁移系统）为后续落地打下了基础。

## 第 8 章 一些实践感悟

**AI 是降低启动阻力的工具，不是替代思考的工具。**

最大的价值是把"有价值但麻烦"的事情变得可以开始。比如写 OKR 文档，不是不会写，是面对空白文档不知道从哪里开始。让 AI 生成一个框架和初稿，你再补充和修改，比从零写快了不止一倍，而且质量往往更高因为你把精力放在了真正重要的部分。

**越懂 AI 的工作原理，用得越好。**

理解 Token 和上下文窗口，才会知道为什么要精简 Prompt、为什么不能粘贴 10 万行日志。理解 RAG，才会知道知识库的质量比数量重要。理解 Agent 和 Workflow 的区别，才不会为简单任务过度设计。

**把 AI 当成"永不嫌烦的初级同事"。**

那种"问一个问题怕显得不懂"的心理负担消失了，可以反复追问、要求解释、让它改 5 遍输出格式，它不会不耐烦。这让学新东西的成本大幅降低——碰到不熟悉的领域，先让 AI 给个鸟瞰图，再自己深入细节，比纯自学快很多。

**人机协作的效果取决于人的部分做得好不好。**

AI 输出的质量上限，受限于你提供的输入质量。模糊的需求得到模糊的输出，结构化的、有充足上下文的输入得到精准的输出。这意味着"会用 AI"本质上是"会把自己的思路结构化表达出来"——这个能力本身就很有价值，跟 AI 无关。
