### P2
帅哥，蕾姐，大家好，我是基础架构组的李浩鹏。
在试用期的六个月里，作为集群 SRE，我的工作始终围绕两个核心目标：**集群稳定性**与**计算效能**。屏幕上是这半年的工作全景，可以概括为四个方向。
第一，**架构高可用**。针对核心服务链路的单点隐患，我主导落地了 ATS V1.5 的高可用架构。通过引入状态机调和机制，将原本依赖人工介入的小时级恢复，升级为自动故障处置，RTO 收敛到 60 秒以内。
第二，**计算资源治理**。在降本增效背景下，业务无感知地接入新技术本身就是工程难点。我开发了 Spark 动态参数注入系统，以此为基础平滑推进了 RSS 和 Spark 向量化引擎的落地。向量化引擎在基准测试中最高取得了 64.6% 的性能提升。
第三，**全链路可观测**。我重构了集群监控的采集链路，补齐了 Hadoop、Hive 等核心组件的 Exporter，支撑百万级指标的秒级采集，并完成了存量告警规则从 Zabbix 到 Foxeye 的迁移。
第四，**深度排障与 AIOps**。运维侧，我深入 JVM 与 OS 内核机制，定位了 NameNode 长 GC 和 Hive UDF 句柄泄漏的根因。工程侧，我基于 Eino 框架开发了多智能体系统，将 142 条 Zabbix 告警规则以 100% 准确率自动迁移到 Foxeye，节省了约 5 个工作日的人工投入。
接下来，我选取其中几个技术深度较高的方向做重点汇报，先从 ATS 高可用架构开始。
### P3
ATS 是记录集群全量历史任务的核心组件，但其原生版本存在单点故障风险，一旦宕机，作业历史数据链路即告中断。
项目启动时，我调研了业界通行的 Pacemaker 方案——通过 Corosync 同步、VIP 漂移实现主备切换。但在深入分析后发现这条路有一个结构性问题：ATS 的底层存储是 LevelDB，而 LevelDB 严格限制单进程独占读写。如果仅靠外部工具触发进程拉起，在网络抖动时容易出现双活窗口，导致多个进程并发写同一份 LevelDB 文件，数据损坏无法恢复。
因此，我放弃了工具拼凑的思路，参考 Kubernetes 的 Controller 模式，自主设计了屏幕上这套 HA 架构。核心在两个层面：
**第一层：防脑裂**。我没有单纯依赖 Keepalived 的边缘触发（Edge-Triggered），而是增加了一个常驻守护进程做水平触发（Level-Triggered）的状态持续校准。即使短暂的网络抖动导致信号丢失，系统也能在下一个检测周期内自我纠正。一旦探测到 VIP 漂移，系统会执行 STONITH 机制，通过 kill -9 强制终止原节点的残留进程，从操作系统层面消除双活的可能。
**第二层：数据一致性**。拉起备节点服务前，必须先完成双节点的数据对齐。我分析了 LevelDB 的底层存储结构，设计了分阶段 Rsync 策略：优先同步体积大且不可变的 SSTable，再同步元数据 MANIFEST，最后同步正在活跃写入的 WAL 日志。这个同步顺序能在增量窗口内规避脏读，确保备节点接管时数据状态完整。
这套方案目前已完成架构联调，将故障恢复时间从人工干预的小时级压缩到了分钟级以内。
### P4
讲完架构层的高可用，我们向上一层，看计算资源的治理问题。
在推进 RSS 或 Spark 向量化落地时，有一个绕不开的工程阻力：如何让存量的几百上千个作业切换到新配置？如果依赖业务团队逐一修改提交参数，不仅推进周期长，跨部门沟通成本高，还会引入操作风险。
为了解决这个问题，我设计并开发了这套 **Spark 动态参数注入系统**，核心思路是在平台层完成配置管控，对业务侧保持透明。
大家看右侧的架构流转。我在客户端层埋入了一个轻量级的 Hook 拦截器。业务侧正常发起 spark-submit，Hook 在提交流程中拦截请求，提取 job_name 等标识信息，联查后端的作业画像与白名单数据库，在作业真正提交给 YARN 之前，由 Config Merger 模块将调优参数静默合并进去。整个过程对业务侧完全无感知。
这套机制带来的实际价值是：平台侧对所有提交作业具备了统一的配置管控能力，基础设施层的迭代与业务代码完全解耦。现在我们可以基于作业画像做分批灰度切换，不再需要跨部门协调来推进底层配置变更。
这套系统也是后面 RSS 和 Spark 向量化能够平滑落地的基础设施前提，接下来我来汇报这两项技术的落地情况。
### P5
基于动态注入系统提供的配置管控能力，我主导推进了两项计算层面的技术落地。
**第一项是 RSS（远程 Shuffle 服务）**。随着单体离线作业规模增长，传统本地 Shuffle 对 NodeManager 磁盘的压力越来越大，也制约了计算与存储的弹性扩展。我主导了 Apache Uniffle v0.11 的集群部署与容量压测，验证了 RSS 在大 Shuffle 场景下的稳定性，并完成了配套的动态配置参数调优，实现了计算节点与 Shuffle 存储的分离。
**第二项是 Spark 向量化引擎**。我们引入了 Gluten + Velox 架构，将 Spark SQL 的物理算子卸载到 Velox 原生 C++ 引擎执行，利用列式批处理和 SIMD 指令加速计算密集型操作，同时减少 JVM GC 压力。经过深度参数调优，基准测试中平均执行时间缩短约 20%，部分算子（如 HashAggregate、列式 Join）最高加速达 64.6%。
但向量化并非对所有作业都有收益——包含大量 Hive UDF、行式数据源或频繁行列转换的作业可能产生性能回退。因此，我同步开发了一套作业画像分析工具，通过解析 Spark EventLog，基于算子组成、数据格式、CPU 密集度等维度对每个作业计算向量化适配评分，筛选出高收益作业作为灰度白名单，再通过 Hook 机制静默注入。
这套体系全面落地后，预计可降低集群约 10% 的整体算力消耗。

### P6
计算层的工作讲完了，接下来是可观测体系的重构。
Zabbix 在集群监控中一直承担着核心角色，其 JMX 采集精度高，告警响应也足够及时。但随着整体运维平台升级，我们面临两个现实问题：一是监控数据分散，大数据集群的指标没有统一收敛到公司级的 Foxeye 平台，排障时需要横跨多个系统；二是 Zabbix 在高基数指标场景下的存储与查询能力有明显瓶颈，难以支撑我们后续精细化运营的需求。
为此，我主导了集群监控体系的迁移与重构，具体分三个层次。
**采集层**：针对 Hadoop、Hive、ATS 等大数据组件，原有 JMX 接口暴露的是非结构化的内部状态。我通过自研和深度定制各组件的 Exporter，将这些内部指标标准化为 Prometheus Metrics 格式，补齐了原先缺失的覆盖范围。
**存储与计算层**：引入 VictoriaMetrics 替代单点存储，支撑百万级指标的高并发写入；补充 Loki 完成日志链路的接入。
**告警层**：基于新的指标体系，我梳理并在 Foxeye 平台上补齐了约 400 条集群侧告警规则。
这套架构落地后，我们的监控覆盖度在原有 Zabbix 基础上进一步完善，并统一收敛到了 Foxeye 平台，具备了支撑更大规模指标的能力。
但新体系建立的同时，还有一个历史问题需要处理：Zabbix 上已有的存量告警规则如何迁移，这就是下一页要讲的内容。
### P7
Zabbix 的触发器语法包含大量复杂的阈值函数和时间窗口表达式，如果逐条人工翻译成 Foxeye 的 JSON 配置格式，需要数天时间，且容易因为理解偏差导致迁移后的规则语义发生漂移，出现漏报或误报。
这类问题的本质是：有明确的规则语义转换逻辑，但工作量机械且重复。我引入大模型能力，开发了这套基于多智能体架构的自动化迁移系统。
系统的核心设计思路是多角色职责分离，而不是单一模型做端到端翻译。
**Master Agent** 负责任务编排，基于 DeepSeek-V3，通过 ReACT 框架解析迁移意图，动态规划每条规则的处理路径。
**Converter Agent** 负责语义转换，接入 DeepSeek-R1 推理模型，利用其链式推理（CoT）能力分析 Zabbix 表达式的语义，再生成符合 Foxeye 规范的配置。选用推理模型而非通用模型，是因为 Zabbix 的函数表达式存在大量隐式的上下文依赖，需要逐步推导而不是直接映射。
**Matcher Agent** 负责质量验证，对转换前后的规则进行语义打分，确保生成结果不发生语义漂移，构成完整的闭环。
最终，这套工具完成了 142 条告警规则的自动迁移，语义转换准确率 100%，节省了约 5 个工作日的人工投入。更重要的是，它形成了一个可复用的 Multi-Agent 工程样板，为后续集群日志分析和故障处置场景的 AIOps 探索提供了工程基础。

### P8
最后，我向各位汇报试用期内让我印象最深的一次排障。
事故触发点是一台配置了 200G 内存的 NameNode 发生了 ZKFC 脑裂切换。排查监控时，我发现一个异常现象：物理内存非常充裕，但 JVM 的 Mixed GC 停顿时间达到了 62 秒，其中单 Scan RS（扫描记忆集）阶段就耗费了 41 秒。这个数字在 G1 GC 体系里是很不正常的。
这说明问题不在 JVM 的对象分配或内存分代比例，而是在 GC 的内存访问路径上。我将排查视角从 JVM 延伸到了 OS 内核层。
原因如下：Linux 内核的 LRU 页面淘汰机制，会将长期未被访问的"冷页"换出到 Swap 分区。对于 200G 的 NameNode 堆，老年代中有大量对象长期驻留但访问频率低，这部分页面会被内核静默换出。
问题在于，G1 的 Mixed GC 在 Scan RS 阶段需要随机遍历堆内所有 Region 的引用关系。一旦访问到已换出的冷页，会触发硬缺页中断（Major Page Fault），迫使 CPU 等待磁盘 I/O 完成换入。原本纳秒级的内存访问退化为毫秒级的磁盘读取，延迟放大了四到五个数量级。Scan RS 阶段本身访问模式随机、访问量大，触发的缺页中断数量足以把 GC 停顿推到几十秒。
定位到根因后，调优方向明确：通过 `vm.swappiness=1` 大幅降低内核换出倾向，同时调整 G1 的并发标记参数，避免过早进入 Mixed GC 周期，减少 Scan RS 的触发频率和单次工作量。
这次排障让我意识到：大堆 JVM 服务的 GC 行为与 OS 内存管理之间存在深度耦合，定位这类问题需要同时具备 JVM 和内核两个视角，分开来看都会误判。

### P9
最后，借这次述职机会，做一个阶段性复盘，并汇报接下来的规划。
回顾这六个月，我在两个方向上投入最多：一是复杂故障的深度排查，习惯追溯到 JVM、OS 内核或源码层面找根因，并将排障过程整理为可复用的 SOP；二是基础设施的系统性建设，包括 ATS 高可用、监控体系迁移、动态注入系统，这些都是为后续更大范围的集群演进打基础。
面向 2026 年上半年，我的重点方向有两个：
**第一，计算治理的落地闭环**。动态注入系统和作业画像工具已经具备，接下来的工作是在生产环境中基于精准的画像结果，分批扩大 Spark 向量化和 RSS 的覆盖范围，把基准测试中观测到的性能收益真正转化为集群层面可量化的资源节省。
**第二，AIOps 场景的拓展**。告警迁移系统验证了多智能体框架在运维场景中的可行性。下一步，我计划在此基础上探索集群故障根因分析 Copilot 的落地，结合现有的监控指标和日志体系，辅助工程师在故障时快速缩小排查范围，以及探索存量告警的智能降噪机制，降低告警风暴对值班工程师的干扰。
总的来说，这半年在基础架构组的工作让我对大规模集群运维有了更系统的认知。接下来希望能在稳定性保障和效能建设两个方向上继续深入。
