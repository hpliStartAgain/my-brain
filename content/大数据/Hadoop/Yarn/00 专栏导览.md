# YARN 深度解析专栏导览

## 这一列怎么读

YARN 的文档和文章都不少，但多数停在"RM 管资源、NM 管节点、AM 管应用"这三句话上。真正会踩坑的地方在别处：为什么应用卡在 ACCEPTED、为什么 vcores 是个谎言、为什么容器莫名退出码 137、为什么队列有配额却拿不到资源。

九个位置按"一次应用提交会依次碰到什么"排列：先讲它为什么被造出来（01），再走完整的申请链路（02），然后是链路上每一站的内部机制——RM 怎么记账（03）、容器怎么起来（04）、队列怎么分（05）、AM 怎么活（06）、资源怎么隔离（07）、坏了怎么恢复（08）。最后 09 收口到容量规划与迁移判据。

每一篇都落三类东西：配置项与它调大调小的代价、观测点（REST 端点或日志关键行）、故障形态与判据。

**技术版本**：Hadoop 3.3.x。Capacity Scheduler 的 `capacity` 支持百分比与绝对值两种写法、Auto-Creation 叶子队列、cgroups v2 支持从 3.4 起完善——这类版本敏感项在篇内标注。

## 一条故障的排查顺序

这一列的判据是可以串起来用的。应用提交后不出结果，按这个顺序走：

| 现象 | 先去哪篇 | 看什么 |
| :--- | :--- | :--- |
| 卡在 `ACCEPTED` | 05 | 队列 `capacity`/`maximum-capacity`、用户限制、`maximum-am-resource-percent` 是否占满 |
| 容器起来了又立刻消失 | 03 / 04 | `ContainerAllocationExpirer` 是否回收、本地化是否失败 |
| 退出码 137 | 04 / 07 | 是 OOM 被杀、还是抢占/主动 kill/分配过期 |
| 容器里 CPU 抢不到 | 07 | vcores 默认无隔离，要看 cgroups 的 `cpu.cfs_quota_us` 是否配了 |
| 应用反复重启 | 06 / 08 | `maxAppAttempts` 是总数还是重试数、Spark 重启是否等于全量重算 |
| 节点变 `UNHEALTHY` | 09 | 磁盘满、`local-dirs` 不可写、cgroup 挂载失败 |
