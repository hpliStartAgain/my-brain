# Hive 深度解析专栏导览

## 这一列写什么

Hive 的处境很特殊：它几乎是最老的 SQL-on-Hadoop 引擎，却又是今天绝大多数数据仓库的元数据中枢——哪怕计算已经迁到 Spark 或 Trino，表定义仍在 Hive Metastore 里。所以理解 Hive 有两层价值：头一层是还能不能直接用它跑批，第二层是看懂那套元数据与分区约定，因为所有下游引擎都在按它的规矩读数据。

本列按一条查询的旅程组织：连接进 HiveServer2（01）→ 查 Metastore 拿元数据（02）→ 编译成 Operator 树（03）→ 选执行引擎（04）→ 优化器介入（05）→ 决定 Join 策略（06）→ 依赖分区与分桶的物理组织（07）→ 落到 ORC/Parquet 的文件格式（08）→ 用 UDF 扩展（09）→ Tez 上调优（10）→ 生产运维（11）→ 故障排查（12）。

每一篇都写"机制是什么、判据在哪、配错了看见什么"，不写安装步骤与 SQL 语法教程。

## 与知识库里其他内容的边界

- **`大数据/Hadoop/Yarn`**（9 篇）：YARN 的资源调度机制。本列 04/10 只讲 Hive 怎么用 Tez，Tez 自身的 DAG 机制一句话带过。
- **`SRE/故障排查与复盘`**：里面有四份真实的 Hive 事故报告（Kerberos 认证故障、Redis UDF 文件描述符泄漏、Tez 作业 `AbstractMethodError`、Beeline EXPLAIN 常量折叠）。本列 09/11/12 引用它们的**形态**并双链过去，不复制细节。
- **`大数据/Spark`**：本列 03/05 与 Spark 的 Catalyst 有对照，但 Spark 的优化器细节在 `Spark-SQL深度解析与性能调优` 里，此处只做对照。

## 版本口径

Hive 4.x（以 4.0.1 / 4.1.0 的 `HiveConf.java` 与 `ql` 源码核实）。几个跨版本会翻转行为的点必须注意：`hive.optimize.index.filter` 在 3.1 默认 false、4.0 默认 true（升级即翻转）；`hive.cbo.enable` 从 1.2 起就是 true；Hive 4.0 移除了 Hive-on-Spark 与 `hive.optimize.cp`/`hive.optimize.pruner` 这些老开关。核实不了的写「以对应版本文档为准」。
