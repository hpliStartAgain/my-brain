本章是一个系统性能案例研究：一个真实性能问题的完整故事，从最初的报告到最终的解决。这个特定的问题发生在一个生产环境的云计算场景中；我选择它作为系统性能分析的一个典型范例。

我在本章的意图不是介绍新的技术内容，而是通过故事讲述展示工具和方法论如何在实际工作环境中应用。这对于尚未处理过真实世界系统性能问题的初学者来说尤其有用，它提供了一个“跟班”视角，观察专家如何处理问题，以及专家在分析过程中可能在想什么、为什么要这么想。这并不一定记录了可能的最佳方法，而是解释了为什么采取了某种特定的方法。

## 16.1 一个无法解释的性能红利 (An Unexplained Win)

Netflix 的一个微服务在新的基于容器的平台上进行了测试，发现请求延迟降低了三到四倍。虽然容器平台有很多优点，但如此巨大的增益是出乎意料的！这听起来好得令人难以置信，我受命调查并解释这是如何发生的。

为了进行分析，我使用了各种工具，包括基于计数器、静态配置、PMC、软件事件和追踪的工具。所有这些工具类型都发挥了作用，并提供了拼凑在一起的线索。由于这构成了一次广泛的系统性能分析之旅，我将其作为我 USENIX LISA 2019 关于系统性能演讲 [Gregg 19h] 的开场故事，并将其作为案例研究包含在此。

### 16.1.1 问题陈述 (Problem Statement)

通过与服务团队交流，我了解了该微服务的细节：它是一个用于计算客户推荐的 Java 应用程序，目前运行在 AWS EC2 云中的虚拟机实例上。该微服务由两个组件组成，其中一个正在名为 Titus 的新 Netflix 容器平台上进行测试，该平台也运行在 AWS EC2 上。这个组件在 VM 实例上的请求延迟为三到四秒，而在容器上变成了一秒：快了三到四倍！

问题在于解释这种性能差异。如果这仅仅是由于迁移到容器带来的，那么微服务可以通过迁移获得永久的 3-4 倍收益。如果是由于其他因素造成的，那么了解这个因素是什么以及它是否会持久存在将非常有价值。也许它还可以被应用到其他地方，并发挥更大的作用。

我立刻想到的是运行工作负载中单个组件带来的隔离优势：它将能够使用整个 CPU 缓存，而不会受到另一个组件的竞争，从而提高缓存命中率并提升性能。另一个猜想是容器平台上的资源爆发（bursting），即容器可以使用来自其他容器的空闲 CPU 资源。

### 16.1.2 分析策略 (Analysis Strategy)

由于流量由负载均衡器（AWS ELB）处理，因此可以将流量分配到 VM 和容器之间，这样我就可以同时登录两者。这是对比分析的理想情况：我可以在一天的同一时间（相同的流量构成和负载）在两者上运行相同的分析命令，并立即对比输出。

在这种情况下，我可以访问容器宿主机，而不仅仅是容器本身，这允许我使用任何分析工具，并提供了这些工具进行任何系统调用的权限。如果我只能访问容器，分析将由于观测源和内核权限受限而更加耗时，需要从有限的指标中进行更多的推论，而不是直接测量。目前，仅从容器内部分析某些性能问题是不切实际的（见第 11 章 [[11 云计算|云计算]]）。

在方法论方面，我计划从“60 秒检查清单”（第 1 章 [[01 绪论#1.10.1 Linux 60 秒分析清单|绪论]]）和 USE 方法（第 2 章 [[02 方法论#2.5.9 USE 方法|方法论]]）开始，并根据它们的线索进行钻取分析（Section 2.5.12）和其他方法。

在接下来的章节中，我包含了运行的命令及其输出，VM 实例使用 `serverA#` 提示符，容器宿主机使用 `serverB#` 提示符。

### 16.1.3 统计信息 (Statistics)

我首先运行 `uptime(1)` 来检查平均负载统计信息。在两个系统上：

```bash
serverA# uptime
 22:07:23 up 15 days,  5:01,  1 user,  load average: 85.09, 89.25, 91.26

serverB# uptime
 22:06:24 up 91 days, 23:52,  1 user,  load average: 17.94, 16.92, 16.62
```

这显示负载大致稳定，VM 实例上的负载稍微减轻了一些（85.09 对比 91.26），而容器上的负载稍微加重了一些（17.94 对比 16.62）。我检查了趋势，以确定问题是在增加、减少还是稳定：这在可以自动将负载从不健康实例移走的云环境中尤为重要。我不止一次登录到一个有问题的实例，却发现活动很少，一分钟平均负载接近于零。

平均负载还显示 VM 的负载远高于容器宿主机（85.09 对 17.94），尽管我需要其他工具的统计信息来理解这意味着什么。高平均负载通常指向 CPU 需求，但也可能与 I/O 相关（见第 6 章 [[06 CPU#6.6.1 uptime|CPU]]）。

`mpstat(1)` 在第一行打印 CPU 数量。输出显示虚拟机有 48 个 CPU，而容器宿主机有 64 个。这帮助我进一步解读平均负载：如果它们是基于 CPU 的，则显示 VM 实例运行在严重的 CPU 饱和状态，因为平均负载大约是 CPU 数量的两倍，而容器宿主机则处于低负载状态。`mpstat(1)` 的指标支持了这一假设：VM 的空闲时间约为 2%，而容器宿主机约为 78%。

通过检查其他 `mpstat(1)` 统计信息，我发现了其他线索：

- **CPU 利用率** (`%usr + %sys + ...`) 显示 VM 为 98%，而容器为 22%。这些处理器每个 CPU 核心有两个超线程，因此超过 50% 的利用率通常意味着超线程核心竞争，从而降低性能。VM 已完全进入这一领域，而容器宿主机可能仍受益于每个核心只有一个繁忙的超线程。
- **系统时间** (`%sys`) 在 VM 上要高得多：约为 8% 对 0.38%。如果 VM 运行在 CPU 饱和状态，这些额外的 `%sys` 时间可能包括内核上下文切换的代码路径。内核追踪或剖析可以确认这一点。

我继续运行 60 秒检查清单上的其他命令。`vmstat(8)` 显示运行队列长度与平均负载相似，确认了平均负载是基于 CPU 的。`iostat(1)` 显示磁盘 I/O 很少，`sar(1)` 显示网络 I/O 很少（这些输出未包含在此处）。这证实了 VM 运行在 CPU 饱和状态，导致可运行线程排队等待，而容器宿主机则没有。容器宿主机上的 `top(1)` 还显示只运行了一个容器。

这些命令为 USE 方法提供了统计数据，同样识别出了 CPU 负载问题。

我已经解决问题了吗？我发现 VM 在 48 CPU 系统上的平均负载为 85，且该负载是基于 CPU 的。这意味着线程大约有 77% 的时间在排队等待 (85/48 - 1)，消除这部分等待时间将产生约 4 倍的加速 (1 / (1 - 0.77))。虽然这个量级与问题吻合，但我还无法解释为什么平均负载更高：需要进行更多分析。

### 16.1.5 PMC

性能监控计数器（PMC）可以解释 CPU 周期性能，在 AWS EC2 的某些实例上可以使用。我发布了一个用于云端 PMC 分析的工具包 [Gregg 20e]，其中包括 `pmcarch(8)`（Section 6.6.11 [[06 CPU#6.6.11 pmcarch|pmcarch]]）。`pmcarch(8)` 显示 Intel 的“架构集（architectural set）” PMC，这是最通用的基础集合。

这显示 VM 的每周期指令数（IPC）约为 0.57，而容器约为 1.52：差异达 2.6 倍。

IPC 较低的一个原因可能是超线程竞争，因为 VM 宿主机的 CPU 利用率超过 50%。最后一列显示了另一个原因：VM 的末级缓存（LLC）命中率仅为 30%，而容器约为 90%。这将导致 VM 上的指令频繁阻塞在主内存访问上，从而拉低 IPC 和指令吞吐量（性能）。

VM 上较低的 LLC 命中率可能由至少三个因素引起：
- 较小的 LLC 大小（33 对比 45 Mbytes）。
- 运行完整的工作负载，而不是单个子组件（如问题陈述中所述）；子组件可能具有更好的缓存效果：更少的指令和数据。
- CPU 饱和导致更多的上下文切换，以及在代码路径之间（包括用户态和内核态）频繁切换，增加了缓存压力。

最后一个因素可以使用追踪工具进行调查。

### 16.1.6 软件事件 (Software Events)

为了调查上下文切换，我首先使用 `perf(1)` 命令来统计系统范围的上下文切换率。这使用的是软件事件，类似于硬件事件（PMC），但是通过软件实现的（见第 4 章 [[04 观测工具#图 4.5 内核追踪与性能事件层级|观测工具]] 和第 13 章 [[13 perf#13.5 软件事件|perf]]）。


现在应用程序通常在 CPU 上停留 2 到 4 毫秒。其他工具显示它受非自愿上下文切换的影响不大。

VM 上的非自愿上下文切换以及随后看到的高上下文切换率导致了性能问题。导致应用程序在通常不到 10 微秒后就离开 CPU，也使得 CPU 缓存没有足够的时间为当前代码路径预热。

### 16.1.8 结论 (Conclusion)

我得出结论，性能提升的原因如下：

- **无容器邻居**：容器宿主机除了这一个容器外处于闲置状态。这使得容器可以独占整个 CPU 缓存，并运行在没有 CPU 竞争的环境中。虽然这在测试期间产生了对容器有利的结果，但在邻居容器将成为常态的长期生产使用中，这并非预期情况。当其他租户搬入时，该微服务可能会发现 3-4 倍的性能红利消失。
- **LLC 大小和工作负载差异**：VM 的 IPC 低了 2.6 倍，这可以解释 2.6 倍的减速。原因之一可能是超线程竞争，因为 VM 宿主机的利用率超过 50%（且每个核心有两个超线程）。然而，主要原因可能是较低的 LLC 命中率：VM 为 30%，容器为 90%。这种低 LLC 命中率有三个可能的原因：
    - VM 的 LLC 大小较小：33 Mbytes 对 45 Mbytes。
    - VM 上的工作负载更复杂：完整应用需要更多的指令代码和数据，而容器上只运行单个组件。
    - VM 上的上下文切换率很高：每秒约 200 万次。这阻碍了线程长时间在 CPU 上运行，干扰了缓存预热。VM 上的在 CPU 持续时间通常小于 10 μs，而容器宿主机上为 2-4 ms。
- **CPU 负载差异**：更高的负载被导向 VM，导致 CPU 饱和：在 48 CPU 系统上，基于 CPU 的平均负载为 85。这导致了每秒约 200 万次上下文切换，以及线程排队等待时的运行队列延迟。平均负载暗示的运行队列延迟表明 VM 运行速度慢了约 4 倍。

这些问题解释了观察到的性能差异。
