# 12 基准测试方法论：JMH 与系统级 benchmark 的陷阱

> [!abstract] 摘要
> 本文是专栏第五部分"实践与边界"的第一篇，聚焦性能工程中最容易"自欺欺人"的环节——基准测试。文章从"为什么基准测试如此容易出错"这一根本问题出发，讲透微基准测试的三大陷阱（JIT 过度优化、Dead Code Elimination、测量失真），然后深入 JMH（Java Microbenchmark Harness）的设计哲学与核心注解，剖析预热机制、Blackhole 消费、Fork 隔离、状态管理等关键概念。之后转向系统级压测，讨论工作负载模型、负载场景设计、自上而下与自下而上的双重视角。最后给出基准测试的"伦理"——什么时候该做基准测试，什么时候不该做，以及如何判断基准测试结果的可信度。核心认知：基准测试不是"跑个数字"，而是一项需要严格方法论支撑的实验科学；错误的基准测试比不做基准测试更危险，因为它会用"数据"支撑错误的决策。

## 第 1 章 基准测试的本质与困境

### 1.1 什么是基准测试

基准测试（Benchmark）是通过运行标准化的工作负载，测量系统性能指标的方法。它的核心目的是**回答"这个系统/组件有多快"或"A 和 B 谁更快"的问题**。

基准测试可以分为三个层次：

| 层次 | 测量对象 | 典型工具 | 价值 |
|------|---------|---------|------|
| **微基准（Microbenchmark）** | 单个方法/代码片段 | JMH | 算法/数据结构选型 |
| **组件基准（Component Benchmark）** | 单个组件/服务 | wrk, ab | 组件性能上限 |
| **系统级压测（System Benchmark）** | 端到端系统 | JMeter, Gatling | 容量规划、SLO 验证 |

```mermaid
graph LR
    Micro["微基准<br/>JMH<br/>单个方法"] --> Component["组件基准<br/>wrk/ab<br/>单个服务"]
    Component --> System["系统级压测<br/>JMeter/Gatling<br/>端到端"]

    classDef micro fill:#50fa7b,stroke:#282a36,color:#282a36
    classDef component fill:#f1fa8c,stroke:#282a36,color:#282a36
    classDef system fill:#ffb86c,stroke:#282a36,color:#282a36
    class Micro micro
    class Component component
    class System system
```

三个层次的测量对象、干扰源和可信度完全不同：微基准的敌人是 JIT（第 2 章），组件基准的敌人是"组件外依赖的噪声"（网络、下游服务），系统级压测的敌人是"环境不可控"（第 13 篇的云噪声）。**层次越高，测量越接近真实，但归因越难**——端到端慢了，可能是任何一层的问题；微基准快了，不代表端到端快。三个层次是互补的测量工具，不是互相替代的。

> [!info] 核心概念：基准测试是实验科学，不是"跑个数字"
> 基准测试的本质是受控实验——需要控制变量、消除干扰、确保可重复性。很多人把基准测试理解为"写个循环跑一万次看耗时"，这忽略了 JIT 优化、GC 干扰、OS 调度、缓存预热等大量干扰因素。一个没有方法论支撑的基准测试，其结果可能完全不可信——不是因为数字"不准"，而是因为数字"测的不是你以为的东西"。

### 1.2 为什么基准测试如此容易出错

Java 基准测试的困难根源在于 **JIT 编译器的自适应优化**。JIT 不是一个"忠实的翻译官"，它是一个"激进的优化器"——会根据运行时 profile 做出各种假设和变换。这些优化在正常应用中是好事，但在基准测试中会扭曲测量结果。

三大典型陷阱：

**陷阱 1：Dead Code Elimination（死代码消除）**

```java
// 错误的微基准
@Benchmark
public void test() {
    int result = 0;
    for (int i = 0; i < 1000; i++) {
        result += compute(i);
    }
    // result 没有被使用，JIT 认为整个循环是死代码，直接消除
}
```

JIT 发现 `result` 计算后没有被任何代码使用，整个循环没有副作用，于是将循环消除。基准测试"跑"了，但实际什么都没执行——测到的时间是零。

**陷阱 2：常量折叠（Constant Folding）**

```java
@Benchmark
public int test() {
    int a = 1;
    int b = 2;
    return a + b;  // JIT 在编译时直接算出 3，运行时无计算
}
```

JIT 在编译时发现 `a` 和 `b` 是常量，直接将 `a + b` 折叠为 `3`。基准测试测的不是"加法有多快"，而是"返回常量有多快"。

**陷阱 3：循环不变量外提（Loop-Invariant Code Motion）**

```java
@Benchmark
public int test(int[] data) {
    int sum = 0;
    for (int i = 0; i < data.length; i++) {
        sum += data[i] * Math.PI;  // Math.PI 是循环不变量
    }
    return sum;
}
// JIT 将 Math.PI 的加载移到循环外，循环内只剩乘加
```

JIT 将循环不变的计算移到循环外，使得循环内的实际工作量比"看起来"的少。

这三个陷阱的共同根源值得点破：**JIT 优化的是"程序语义"，而基准测试想测的是"程序工作量"——两者不等价**。JIT 的合法优化（消除无副作用代码、折叠常量、外提不变量）在真实应用中是纯收益，但在基准测试中把"工作量"偷换了。JMH 的所有机制（Blackhole、@State、Fork）本质上都是在"向 JIT 隐瞒测量意图"，让它无法把被测代码当作可优化对象。理解了这个根源，就能理解为什么"手写基准"几乎必败——你在与一个比你更了解代码执行路径的优化器博弈。

> [!warning] 生产避坑：不要手写微基准
> 任何手写的 `for (int i = 0; i < N; i++) { ... }` 式微基准都几乎必然被 JIT 优化扭曲。Java 微基准测试必须使用 JMH——它是专门为对抗 JIT 优化而设计的工具。JMH 的核心价值不是"提供方便的 API"，而是"确保测量结果可信"。

### 1.3 基准测试的"伦理"：预注册假设

基准测试的"伦理"指的不是道德说教，而是一套防止"自我欺骗"的纪律。基准测试的最大风险不是"测不准"，而是"测出了你想要的结果"——确认偏误（第 14 篇的思维陷阱之一）在基准测试中的表现极其隐蔽：你会不自觉地给"期望更快"的实现更优的输入、更充分的预热、更宽松的判定标准。

工程上的防御机制是**预注册假设**：在跑基准之前，把"预期结果、判定标准、实验配置"写下来（哪怕只是写在 PR 描述里），跑完后再对照。预注册的价值在于防"事后解释"——如果结果与预期不符，你会诚实地报告"假设不成立"，而不是回头改实验配置直到"结论正确"。这个纪律来自科学实验的预注册（preregistration）传统，在性能工程中同样有效。

> [!note] 设计哲学：什么时候不该做基准测试
> 基准测试不是万能的。以下场景做基准测试是浪费时间或有害：
> - **没有明确的假设**：如果你不知道要验证什么，基准测试只会产生一堆没有解释力的数字
> - **微基准结果用于推断系统性能**：一个方法的微基准结果不能推断端到端系统性能——系统瓶颈通常在 I/O、锁、网络，而非单个方法
> - **在非生产环境做容量规划**：测试环境的硬件、网络、负载模式与生产不同，系统级压测结果不能直接用于生产容量规划
> - **A/B 比较时没有控制变量**：如果 A 和 B 的运行环境、JVM 参数、输入数据不同，比较结果没有意义
>
> 基准测试的正确动机是"验证一个明确的性能假设"——例如"HashMap.get() 在 1000 个元素时比 TreeMap.get() 快多少倍"。有明确假设，才能设计正确的实验。

## 第 2 章 JMH 的设计哲学

### 2.1 JMH 是什么

JMH（Java Microbenchmark Harness）是 OpenJDK 团队开发的微基准测试框架，由 Aleksey Shipilev 维护。它不是"方便写基准测试的工具"，而是"确保基准测试结果可信的工具"。

JMH 的核心设计目标：

1. **对抗 JIT 优化**：通过 Blackhole、Fork 隔离等机制防止 DCE、常量折叠等优化扭曲结果
2. **控制测量精度**：通过预热迭代、多次测量、统计显著性分析确保结果可信
3. **管理 JVM 状态**：通过 Fork 隔离确保每次测量在独立的 JVM 进程中进行，避免跨测量的状态污染

理解 JMH 定位的一个方式是看它"不做"什么：它不提供 HTTP 压测（那是 wrk/JMeter 的领域）、不做端到端延迟测量（需要系统级工具）、不做资源监控（配合外部工具）。JMH 只做一件事——**在 JVM 的各种"自动优化"干扰下，尽可能可信地测量一小段代码的性能**。这个窄定位恰恰是它的价值：微基准的测量难度（对抗 JIT）远高于表面看起来，专门工具是必需品而非奢侈品。

```xml
<!-- Maven 依赖 -->
<dependency>
    <groupId>org.openjdk.jmh</groupId>
    <artifactId>jmh-core</artifactId>
    <version>1.37</version>
</dependency>
<dependency>
    <groupId>org.openjdk.jmh</groupId>
    <artifactId>jmh-generator-annprocess</artifactId>
    <version>1.37</version>
    <scope>provided</scope>
</dependency>
```

### 2.2 第一个 JMH 基准测试

```java
import org.openjdk.jmh.annotations.*;
import org.openjdk.jmh.infra.Blackhole;
import java.util.concurrent.TimeUnit;

@BenchmarkMode(Mode.Throughput)
@OutputTimeUnit(TimeUnit.SECONDS)
@Warmup(iterations = 5, time = 1)
@Measurement(iterations = 5, time = 1)
@Fork(2)
@State(Scope.Thread)
public class MyBenchmark {

    @Benchmark
    public void testMethod(Blackhole bh) {
        int result = 0;
        for (int i = 0; i < 1000; i++) {
            result += i;
        }
        bh.consume(result);  // 防止 DCE
    }
}
```

关键元素解析：

- `@BenchmarkMode(Mode.Throughput)`：测量吞吐量（每秒操作数）
- `@Warmup(iterations = 5, time = 1)`：5 次预热迭代，每次 1 秒
- `@Measurement(iterations = 5, time = 1)`：5 次测量迭代，每次 1 秒
- `@Fork(2)`：2 个独立的 JVM 进程，每个进程执行完整的预热+测量
- `@State(Scope.Thread)`：每个线程有独立的状态实例
- `Blackhole.consume(result)`：消费计算结果，防止 JIT 消除死代码

这个"最小模板"的每个注解都对应一个测量威胁：Warmup 对抗 JIT 预热、Fork 对抗状态污染、Blackhole 对抗 DCE、@State 对抗共享竞争——**JMH 的注解不是"配置项"，而是"对抗测量失真的武器清单"**。理解每个注解防御的是什么，才能在"结果可疑"时知道调哪个旋钮。后续 3 章会逐一展开这些机制的原理。

> [!info] 核心概念：为什么需要 Fork
> Fork 是 JMH 最重要也最容易被忽略的特性。每次 Fork 启动一个全新的 JVM 进程，确保：
> - JIT 编译器的 profile 不会跨测量污染
> - GC 堆状态不会跨测量影响
> - 类加载器的状态不会跨测量累积
>
> 如果不做 Fork（`@Fork(0)`），所有测量在同一个 JVM 中进行，第一次测量的 JIT 优化、GC 行为会影响后续测量。Fork 确保每次测量是"干净的"——这是 JMH 结果可信的基石。

### 2.3 JMH 的测量模式

| 模式 | 含义 | 适用场景 |
|------|------|---------|
| `Throughput` | 每秒操作数（ops/s） | 评估整体吞吐能力 |
| `AverageTime` | 平均单次操作耗时 | 评估单次操作延迟 |
| `SampleTime` | 采样延迟分布（P50/P90/P99） | 评估延迟尾部 |
| `SingleShotTime` | 单次冷启动耗时 | 评估启动性能或冷操作 |

> [!note] 设计哲学：Throughput vs AverageTime 的关系
> Throughput 和 AverageTime 互为倒数——如果吞吐是 1000 ops/s，平均延迟就是 1/1000 = 1ms。那为什么需要两个模式？因为它们的统计特性不同：Throughput 测量的是"固定时间内完成了多少操作"，AverageTime 测量的是"完成固定操作需要多少时间"。在高吞吐场景下，Throughput 的统计更稳定；在低延迟场景下，AverageTime 更直观。选择哪个取决于你更关心"总量"还是"单次"。

四个模式的选择还有一个与第 01 篇呼应的原则：**SampleTime 是默认推荐**。Throughput/AverageTime 只给"平均值"，掩盖长尾——而延迟敏感系统的决策依据是 P99（第 01 篇 2.5 节）。SampleTime 输出完整的百分位分布，让"长尾是否存在、有多长"可见。一个实用的组合：`Mode.AverageTime` + `@OutputTimeUnit(NANOSECONDS)` 看均值，配合 `-prof gc` 看分配——如果分配速率高，均值波动大，长尾风险高，此时应切换 SampleTime 看分布。

## 第 3 章 JMH 核心机制深度解析

### 3.1 预热机制

预热（Warmup）是 JMH 对抗 JIT 预热效应的核心机制。在正式测量前，JMH 先运行若干轮预热迭代，让 JIT 编译器识别热点、完成编译优化。

```mermaid
graph LR
    JVM["JVM 启动"] --> Warm["预热迭代<br/>5轮 x 1秒"]
    Warm --> JIT["JIT 编译热点<br/>C1/C2 优化"]
    JIT --> Measure["测量迭代<br/>5轮 x 1秒"]
    Measure --> Result["稳态性能数据"]

    classDef warmup fill:#ffb86c,stroke:#282a36,color:#282a36
    classDef jit fill:#bd93f9,stroke:#282a36,color:#282a36
    classDef measure fill:#50fa7b,stroke:#282a36,color:#282a36
    classDef result fill:#f1fa8c,stroke:#282a36,color:#282a36
    class Warm warmup
    class JIT jit
    class Measure measure
    class Result result
```

预热迭代的关键参数：

```java
@Warmup(iterations = 5, time = 1, batchSize = 1)
```

- `iterations`：预热轮数（默认 5）
- `time`：每轮时长（默认 1 秒）
- `batchSize`：每批次调用次数（默认 1）

预热参数的设定依据是第 09 篇的"稳态判定"：**预热要持续到编译速率下降到稳态**——5 轮 × 1 秒对简单方法足够，对"启动时涌入大量新类"的复杂基准（动态代理、反射密集）远远不够。判断预热是否充分的观测方法：`-prof comp` 分析器显示编译事件——如果测量迭代中仍有大量编译事件，预热不足。**预热不足的测量结果"偏低且方差大"**——它测的是"还在爬坡的性能"，既不代表冷启动也不代表稳态，是最没有解释力的数字。

> [!warning] 生产避坑：预热轮数不够导致测量失真
> 如果预热轮数太少，JIT 可能还没完成 C2 编译，测量的是"半优化"状态的性能。对于复杂的基准测试，建议预热至少 10 轮。可以通过 JMH 的 `-prof gc` 分析器观察预热期间 GC 行为是否稳定——如果 GC 频率在预热后期趋于稳定，说明 JIT 已基本完成。

### 3.2 Blackhole：对抗 Dead Code Elimination

Blackhole 是 JMH 对抗 DCE 的核心武器。它的作用是"消费"计算结果，让 JIT 认为该结果被使用了，从而不会消除产生该结果的代码。

```java
@Benchmark
public void test(Blackhole bh) {
    bh.consume(computeA());
    bh.consume(computeB());
    bh.consume(computeC());
}
```

Blackhole 的工作原理：

1. **volatile 写入**：Blackhole 内部使用 volatile 字段存储消费的值，防止 JIT 将消费操作优化掉
2. **类型特化**：对 int/long/Object 等不同类型有特化的 consume 方法，避免装箱开销
3. **编译器屏障**：Blackhole 的实现经过精心设计，确保 JIT 无法"看穿"它

Blackhole 的使用有一个性能细节：**consume 本身有开销（几纳秒），且会阻止跨调用的优化**。对纳秒级的被测操作，一次 consume 的开销可能占测量的 10%+。缓解方法：批量操作 + `@OperationsPerInvocation`（把 consume 摊到 N 次操作上）——3.4 节的模式。另一个细节：多个 consume 调用会阻止 JIT 把多个计算合并优化——如果被测逻辑天然是"一次计算多个结果"，用 `bh.consume(new Result(a, b, c))` 打包消费比逐个消费更保真。

> [!info] 核心概念：Blackhole 不是"打印结果"
> Blackhole 的目的不是"使用"结果，而是"让 JIT 认为结果被使用了"。它不检查结果的正确性，也不会输出任何东西。它的存在纯粹是为了对抗 JIT 的 DCE 优化。理解这一点很重要——如果你把 Blackhole 换成 `System.out.println(result)`，虽然也能防止 DCE，但 println 的 I/O 开销会严重扭曲测量结果。

### 3.3 @State：状态生命周期管理

`@State` 注解管理基准测试中的状态对象生命周期。它的核心是 `Scope`（作用域）：

| Scope | 含义 | 适用场景 |
|-------|------|---------|
| `Scope.Thread` | 每个线程独立实例 | 线程本地状态（如线程本地缓存） |
| `Scope.Group` | 同一线程组共享实例 | 多线程协作场景 |
| `Scope.Benchmark` | 所有线程共享实例 | 全局共享状态（如只读数据） |

Scope 的选择直接影响测量的并发语义，这个选择错误是"多线程基准结果异常"的头号原因。**Scope.Thread 测的是"单线程性能 × N"**（无共享竞争），**Scope.Benchmark 测的是"真实共享竞争下的性能"**——两者可能差一个数量级（第 11 篇的锁竞争）。测什么取决于你要回答什么问题：评估数据结构的多线程扩展性用 Benchmark scope，评估单线程操作成本用 Thread scope。**用 Thread scope 测"并发性能"是最常见的基准测试错误**——它测出来的是理想化的线性扩展，生产中不存在。

```java
@State(Scope.Thread)
public class MyState {
    int[] data;

    @Setup(Level.Trial)
    public void setup() {
        data = new int[1000];
        // 初始化数据
    }

    @TearDown(Level.Trial)
    public void tearDown() {
        data = null;
    }
}
```

`@Setup` 和 `@TearDown` 的 Level：

- `Level.Trial`：每次完整的 Trial（一次 Fork 的全部迭代）执行一次
- `Level.Iteration`：每次迭代执行一次
- `Level.Invocation`：每次方法调用执行一次（**慎用**，开销可能扭曲测量）

> [!warning] 生产避坑：Level.Invocation 的陷阱
> `@Setup(Level.Invocation)` 在每次 `@Benchmark` 方法调用前后执行。对于纳秒级的方法，Setup 的开销可能比被测方法还大，严重扭曲测量。JMH 官方建议：除非方法执行时间在微秒级以上，否则不要使用 `Level.Invocation`。替代方案是使用 `@OperationsPerInvocation` 告知 JMH 每次调用包含多少操作，然后在方法内部循环执行多次。

### 3.4 @OperationsPerInvocation：批量操作

`@OperationsPerInvocation` 告知 JMH 每次基准方法调用包含多少个"操作"。这用于在方法内部循环执行多次操作，减少方法调用的固定开销：

```java
@Benchmark
@OperationsPerInvocation(1000)
public void test(Blackhole bh) {
    int[] data = this.data;
    for (int i = 0; i < 1000; i++) {
        bh.consume(data[i]);
    }
}
```

JMH 会将测量的吞吐量除以 1000，得到"每操作"的吞吐量。这避免了每次方法调用的开销（如 JMH 的控制逻辑）淹没实际操作的开销。

批量模式的适用判断：**被测操作本身在纳秒级时，必须批量**——JMH 每次调用的固定开销（状态检查、计时、Blackhole）约 5-20ns，对 100ns 的操作占比 5-20%，对 1ns 的操作占比 500-2000%（测量完全失真）。批量 1000 次后，固定开销摊薄到可忽略。但批量也有代价：**循环内的连续操作会被 JIT/硬件"协同优化"**（循环展开、预取、分支预测学习）——批量测的结果偏向"理想流水线"，单次测的结果偏向"冷调用"。两个数字都有价值：批量值是"稳态吞吐上限"，单次值是"最坏情况延迟"——生产表现介于两者之间，取决于调用模式（第 4.4 节的跨调用优化）。

### 3.6 Fork 的代价与权衡

Fork 保证了测量的"干净"，但它不是免费的。每个 Fork 启动一个全新 JVM——JVM 启动 + 类加载 + JIT 预热都要重来一遍。一个 2 Fork × 5 Warmup × 5 Measurement × 1s 的基准测试，实际运行时间是 (5+5) × 2 = 20 秒的测量期 + 2 次 JVM 启动预热（各 5-15 秒）≈ 30-50 秒。参数化基准（@Param 多值）会成倍放大这个成本——10 个参数值 × 2 Fork = 20 次 JVM 启动。

工程上的权衡策略：

| 场景 | Fork 策略 | 理由 |
|------|----------|------|
| 正式结论（发布前验证） | `@Fork(3)` + 完整预热 | 统计可信度优先 |
| 日常开发快速迭代 | `@Fork(1)` + `-Xprof` | 速度优先，结论只做参考 |
| 参数化扫描（@Param 多值） | `@Fork(2)` + 缩短迭代时长 | 平衡总时长与可信度 |
| CI 回归基准 | `@Fork(1)` + 固定基线对比 | 相对变化比绝对值重要 |

还有一个容易被忽视的细节：**Fork 的 JVM 参数隔离**。JMH 默认用与宿主相同的 JVM 参数启动子进程，但基准测试常常需要特定参数（譬如固定堆大小、关闭 TieredCompilation 对比）。`@Fork(jvmArgs = {...})` 显式指定——**不显式指定参数的基准测试，结果受宿主环境影响，不可复现**。第 6.2 节的环境隔离准则在这里落地。

### 3.7 JMH 性能分析器

JMH 内置了多种性能分析器（Profiler），通过 `-prof` 参数启用：

| 分析器 | 作用 | 命令 |
|--------|------|------|
| `gc` | GC 统计 | `-prof gc` |
| `comp` | JIT 编译统计 | `-prof comp` |
| `stack` | 栈采样 | `-prof stack` |
| `perf` | Linux perf 集成 | `-prof perf` |
| `perfasm` | 汇编级分析 | `-prof perfasm` |
| `async` | async-profiler 集成 | `-prof async` |

```bash
# 运行基准测试并启用 GC 和编译分析器
java -jar benchmarks.jar -prof gc,comp

# 启用 perfasm 分析 JIT 生成的汇编代码
java -jar benchmarks.jar -prof perfasm
```

分析器的选型逻辑与第 02 篇的观测三层模型一致：`gc`/`comp` 是 Counters 层（低开销，回答"GC/编译是否干扰测量"），`stack`/`perf`/`async` 是 Profiling 层（回答"时间花在哪"），`perfasm` 是终极下钻（回答"生成的机器码长什么样"）。日常基准测试的推荐组合是 `-prof gc,comp`——开销低、信息量大，能回答"结果可信吗"（GC 干扰、预热充分性）这两个前置问题；深度剖析只在"结果异常"时启用。

> [!info] 核心概念：perfasm 是终极武器
> `perfasm` 分析器将 JMH 与 Linux `perf` 和 HotSpot `hsdis`（反汇编器）结合，可以显示 JIT 编译器为基准方法生成的实际汇编代码。这是验证"JIT 是否真的做了你期望的优化"的终极手段。例如，你可以通过 perfasm 确认 JIT 是否内联了某个方法、是否向量化了某个循环（第 09 篇 2.3 节的向量化）。perfasm 的使用门槛较高，但对于追求极致性能的微基准测试，它是不可或缺的工具。

## 第 4 章 微基准测试的典型陷阱

### 4.1 陷阱清单

| 陷阱 | 症状 | 解决方案 |
|------|------|---------|
| Dead Code Elimination | 测量结果异常快（接近零） | 使用 Blackhole.consume() |
| 常量折叠 | 测量结果与输入无关 | 使用 @State 提供运行时输入 |
| 循环展开过度 | 测量结果异常快 | 使用 @OperationsPerInvocation |
| 未预热 | 测量结果不稳定 | 设置足够的 @Warmup |
| 共享状态污染 | 多线程结果异常 | 正确使用 @State Scope |
| GC 干扰 | 测量结果有周期性波动 | 使用 -prof gc 监控 |
| 类加载开销 | 首次迭代异常慢 | 确保预热覆盖类加载 |
| 测量粒度太细 | 单次操作 < 纳秒 | 批量操作 + @OperationsPerInvocation |
| 输入分布失真 | 结果比生产乐观数倍 | 用生产分布的数据（4.3 节） |
| Scope 选错 | 并发结果虚高 | 并发语义用 Benchmark scope（3.3 节） |

这张清单的用法是"症状反查"：测量结果"好得不真实"时，从上往下核对——异常快对应 DCE/常量折叠/循环展开，结果"稳得不真实"（方差极小）可能是输入太规整。**基准测试结果的第一反应应该是怀疑，而不是欣喜**——"比预期快 5 倍"大概率是测量问题，不是代码奇迹。

### 4.2 陷阱实例：常量折叠

```java
// 错误：常量折叠
@Benchmark
public int test() {
    int x = 10;
    int y = 20;
    return x + y;  // JIT 编译时直接算出 30
}

// 正确：从状态中读取
@State(Scope.Thread)
public class MyState {
    @Param({"10", "20", "30"})
    int x;
    int y;
}

@Benchmark
public int test(MyState state) {
    return state.x + state.y;  // JIT 无法在编译时确定值
}
```

`@Param` 注解让 JMH 在运行时注入不同的参数值，防止 JIT 在编译时折叠常量。JMH 会为每个 `@Param` 值运行一次完整的基准测试，生成对比结果。

### 4.3 陷阱实例：常量折叠与输入的真实性

常量折叠的修复（用 @State 提供运行时输入）背后有一个更深层的问题——**输入的真实性**。即使消除了常量折叠，如果输入数据"太规整"，测到的性能仍然失真：

```java
// 输入规整：JIT/硬件可以"作弊"
@Setup
public void setup() {
    data = new int[1000];
    for (int i = 0; i < 1000; i++) data[i] = i;   // 顺序数据
}

// 输入真实：模拟生产分布
@Setup
public void setup() {
    data = new int[1000];
    Random r = new Random(42);   // 固定种子保证可复现
    for (int i = 0; i < 1000; i++) data[i] = r.nextInt();
}
```

规整输入的失真机制有三层：**分支预测器**学会"永远走同一个分支"（真实数据不会这么配合）；**缓存**里全是热数据（真实数据集更大更冷）；**JIT** 可能基于"数组内容有序"的 profile 做激进优化。三层叠加，微基准结果可能比生产表现乐观 2-10 倍。

修复的原则是**输入分布要贴近生产**：从生产采样真实数据（脱敏后）、或按生产的 key 分布生成（Zipf 分布模拟热点 key）。固定随机种子（可复现）+ 真实分布（不失真）是微基准输入构造的两个基本要求。第 5 章的系统级压测同样适用——"压测数据与生产数据分布不一致"是压测结果与生产表现脱节的最常见原因。

### 4.4 陷阱实例：内联导致的测量失真

```java
// 错误：小方法被内联，测量的是内联后的代码
@Benchmark
public int test() {
    return helper(42);  // helper() 可能被内联
}

private int helper(int x) {
    return x * 2;
}

// 正确：使用 @State 隔离或 -XX:MaxInlineLevel 控制
// 或在 JMH 中使用 -prof comp 确认是否内联
```

JIT 的方法内联是基准测试的隐形陷阱——如果被测方法调用了小方法，JIT 可能将小方法内联，使得测量的不是"方法调用 + 执行"而是"内联后的直接执行"。这不是"错误"（内联是 JIT 的正常优化），但如果你要测量"方法调用的开销"，需要通过 `-XX:MaxInlineLevel=0` 禁用内联（注意这会扭曲整体性能）。

内联陷阱的更隐蔽形态是**"跨调用优化"**：JIT 基于前几次调用的行为优化后续调用（分支预测学习、profile 驱动的投机优化）——基准测试的"重复调用同一操作"恰好是 JIT 最擅长优化的模式，生产中"每次输入不同"的调用模式不会被这样优化。这是 4.3 节"输入真实性"重要性的又一佐证：**JIT 的优化深度取决于它看到的调用模式，基准测试的调用模式越"规整"，测到的优化收益越虚高**。

> [!note] 设计哲学：微基准测试测的是"什么"
> 微基准测试的核心争议是"测的是真实应用中的性能，还是隔离环境中的性能"。答案是后者——微基准测试测的是"在 JMH 控制的隔离环境中，特定代码片段的性能"。这个性能可能与真实应用中的性能不同，因为真实应用有 JIT 交互、GC 压力、缓存竞争等微基准无法模拟的因素。微基准测试的价值在于"相对比较"——A 比 B 快多少倍——而非"绝对预测"——A 在生产中有多快。

## 第 5 章 系统级压测方法论

### 5.1 工作负载模型

系统级压测的核心是**工作负载模型**——模拟真实用户行为的负载模式。工作负载模型的关键要素：

1. **工作单元（Unit of Work, UoW）**：单个用户请求、批量请求或系统预期执行的任何任务
2. **负载强度**：并发用户数、请求速率（QPS/RPS）
3. **负载模式**：恒定负载、阶梯负载、脉冲负载、峰值负载
4. **混合比例**：不同类型请求的比例（如 80% 读 + 20% 写）

四个要素中，**混合比例是最容易被忽视也最容易失真的**。生产流量极少是"纯读"或"纯写"——读写混合比例直接决定缓存行为（读命中）、锁竞争（写冲突）、GC 压力（分配速率）——80/20 与 50/50 的压测结果可能差数倍。获取真实混合比例的方法：从生产 access log 统计接口调用占比、从 APM 提取事务类型分布。**负载模型的保真度决定了压测结论的适用范围**——用"理想化负载"压出的容量数字，在生产混合负载下不可信。

### 5.2 关键指标

系统级压测需要监控的指标层次：

| 层次 | 指标 | 工具 |
|------|------|------|
| **用户体验** | 响应时间（P50/P90/P99/P999） | 压测工具 |
| **系统吞吐** | QPS/RPS、TPS | 压测工具 |
| **资源利用率** | CPU、内存、磁盘 I/O、网络 | sar, dstat, iostat |
| **JVM 运行时** | 堆使用、GC 频率/停顿、线程状态 | JFR, GC 日志 |
| **应用内部** | 缓存命中率、连接池、队列深度 | 应用监控 |

这张指标层次表的用法是"分层归因"：压测发现 P99 恶化时，按层次从上往下排查——用户体验层确认"恶化了多少"，资源层看"哪个资源饱和"，JVM 层看"GC/编译是否异常"，应用层看"哪个内部组件排队"。这个分层与第 14 篇的全栈排查闭环完全同构——**压测就是"受控的故障注入"，压测期间的排查就是一次完整的性能排查演练**。压测的价值因此有二：验证容量上限 + 排查性能瓶颈的"预演"。只看 QPS 数字、不做分层观测的压测，浪费了第二重价值。

> [!info] 核心概念：响应时间分布比平均值更重要
> 系统级压测中，平均响应时间几乎没有意义——它掩盖了尾部延迟。一个系统可能平均响应时间 10ms，但 P99 是 500ms——对于延迟敏感型应用，P99 才是用户体验的真实写照。始终关注 P90/P99/P999 分布，而非平均值。这也是为什么 JMH 提供了 `SampleTime` 模式——它采样延迟分布而非计算平均值。

### 5.3 负载场景设计

三种核心负载场景：

**标准运营负载**：模拟日常流量，用于验证系统在正常条件下的性能基线。

**峰值需求**：模拟流量高峰（如促销活动），用于验证系统在极端条件下的表现。关键问题不是"系统能扛多少"，而是"系统在什么负载下开始退化，退化模式是什么"。

**扩展因子评估**：通过逐步增加负载，找到系统的性能拐点。性能拐点是"吞吐量不再随负载增加而增加"的点——超过拐点后，增加负载只会增加延迟，不增加吞吐。

三种场景的递进关系值得明确：**标准负载建立基线，峰值负载暴露退化模式，阶梯加压找到拐点**。退化模式（degradation mode）是峰值测试最有价值的产出——系统过载时是"优雅降级"（延迟线性上升、错误率可控）还是"雪崩"（延迟指数上升、级联失败）？两种模式的生产应对完全不同：前者可以靠限流保护，后者需要熔断和隔离。**压测的目的不是证明"能扛"，而是刻画"怎么倒下"**——知道退化模式，才能设计正确的过载保护。

> [!warning] 生产避坑：找到拐点比找到"最大承受"更重要
> 很多压测的目标是"系统能扛多少 QPS"，但更有价值的信息是"系统在什么 QPS 下开始退化"。拐点之前的负载是"安全负载"，拐点之后是"危险负载"。容量规划应该基于拐点而非最大承受——因为在拐点附近，系统的延迟已经开始恶化，用户体验已经下降。经验法则：安全负载约为拐点负载的 70-80%。

### 5.5 压测工具的选择与陷阱

系统级压测工具的选择本身就是一个容易踩坑的决策点。主流工具的能力与陷阱：

| 工具 | 定位 | 优势 | 关键陷阱 |
|------|------|------|---------|
| wrk / wrk2 | HTTP 吞吐与延迟 | 高性能、Lua 脚本扩展 | wrk 的固定速率模式有协调遗漏（第 01 篇 2.5 节），要用 wrk2 的恒定速率模式 |
| JMeter | 全协议压测 | GUI、断言、分布式 | 单机吞吐上限低，高并发时工具本身成为瓶颈 |
| Gatling | HTTP 高性能压测 | Scala DSL、报告精美 | 学习曲线陡 |
| 自研 RPC 压测 | 内部协议 | 贴合业务语义 | 常见协调遗漏 + 无预热纪律 |

工具选择的决策依据是"协议匹配度 + 工具开销 + 结果可信度"三者的权衡。一个常被忽视的原则：**压测工具的负载模型要与被测系统的真实协议匹配**——用 HTTP 压测工具压 gRPC 服务（需要额外网关转换），转换层本身就是瓶颈和失真源。内部 RPC 协议（Dubbo、Thrift、gRPC 直连）的压测，自研工具虽然要承担"协调遗漏"的修复成本，但协议直连的保真度是通用工具无法替代的。

其中**协调遗漏（Coordinated Omission）**值得再次强调，因为它是自研压测工具的头号陷阱。第 01 篇讲过机制：压测客户端被服务端卡顿阻塞后，"本应发出"的请求没有发出，慢请求从样本中消失——P99 被系统性低估，可能低估 10 倍以上。自研工具几乎默认踩这个坑（同步等待响应再发下一个），wrk 的固定速率模式也踩。修正方法：按"预定发送时刻"计算延迟（HdrHistogram 的思路），或用恒定速率发送器（wrk2、Gatling 的 open workload 模式要慎用）。

压测工具的第二个陷阱是**工具自身成为瓶颈**。一个 4 核压测机跑 JMeter 压 10 万 QPS，JMeter 自己的线程调度、序列化开销可能占掉 2 个核——压出来的"服务端延迟"里混着"压测客户端的排队延迟"。判断方法：观察压测机的 CPU（超过 70% 就可疑）、对比不同压测机数量的结果（结果不随压测机数量变化才是可信的）。**压测机的资源监控与被测系统同等重要**。

### 5.4 自上而下与自下而上

性能分析有两种视角：

**自上而下（Top-Down）**：从系统目标出发，逐层下钻到细节。聚焦"已知已知"（已观测到的问题）和"已知未知"（知道哪里有问题但不知道根因）。

```
系统目标（SLO） → 响应时间异常 → 哪个请求慢？ → 哪个组件慢？ → 哪个方法慢？ → 为什么慢？
```

**自下而上（Bottom-Up）**：从硬件出发，逐层上溯到应用。精准测量全栈性能。

```
硬件（CPU/内存/IO） → OS 内核 → JVM 运行时 → 应用代码 → 用户请求
```

两种视角互补：自上而下适合"有明确症状的问题排查"，自下而上适合"无明确症状的性能挖掘"。在基准测试语境下，两者的分工是：**压测（自上而下）发现"系统在 8000 QPS 时 P99 恶化"，微基准 + perf（自下而上）回答"为什么是这里先饱和"**——压测定位"哪里有问题"，微基准和剖析定位"为什么"。两种视角的协同在第 14 篇的全栈排查闭环中完整展开。

### 6.2 环境隔离准则

| 准则 | 原因 | 实践 |
|------|------|------|
| 独占硬件 | 避免"嘈杂邻居"干扰 | 物理机或独占云主机 |
| 关闭节能模式 | CPU 频率波动影响测量 | BIOS 关闭 DVFS（第 05 篇 1.5 节） |
| 固定 CPU 亲和性 | 避免线程跨核迁移 | `taskset` 或 `numactl` |
| 关闭后台服务 | 减少 OS 噪声 | 停止 cron、监控 agent |
| 固定 JVM 参数 | 确保可重复性 | 记录所有 `-XX` 参数 |
| 相同输入数据 | 确保可比性 | 使用固定种子或预生成数据 |
| 禁用透明大页自动整理 | THP compaction 引入停顿 | `madvise` 模式或关闭（第 06 篇） |

这六条准则的共同目标是**消除"测量环境"这个混杂变量**。值得强调的是它们的"不对称重要性"：前两条（独占硬件 + 固定频率）影响最大——一台被邻居挤占的虚拟机、一个频率波动的 CPU，能让同一代码的测量结果波动 2-5 倍，任何统计手段都救不回来。后四条影响较小但决定"可复现性"——结果可以复现，对比才有意义。**环境准备占基准测试工作量的 70%，测量本身只占 30%**——这个比例是 JMH 作者 Shipilev 反复强调的。

> [!warning] 生产避坑：云环境中的基准测试不可信
> 在共享云环境（如 EC2 共享实例）中做基准测试，结果几乎不可信——CPU steal time、网络抖动、存储 I/O 波动都是不可控的干扰。如果必须在云环境中做基准测试，至少使用独占型实例（如 EC2 Dedicated Host、GCP Sole-Tenant Node）。对于需要高可信度的基准测试，物理机仍然是首选。

### 6.3 统计显著性

JMH 默认输出每次测量的分数和误差范围。误差范围基于测量迭代的统计分布计算：

```
Result "testMethod":
  1000.123 ± 5.678 ops/s  (95.0% confidence interval)
```

`± 5.678` 是 95% 置信区间。如果两个基准测试的置信区间重叠，说明差异不显著——不能断言"A 比 B 快"。

统计显著性的完整判断流程：

```text
1. 检查误差范围：± 值相对 Score 的比例（> 5% 说明测量噪声大，先解决环境问题）
2. 对比置信区间：A 的区间 [994, 1006]，B 的区间 [998, 1012]
   → 重叠 [998, 1006] → 无法区分，增加迭代或 Fork 数
3. 区间不重叠时计算差异幅度：差异 < 5% 的"优化"在生产噪声面前无意义
4. 多次独立运行验证：同一基准跑两次，结果差异大说明环境不稳定
```

第三条值得展开：**统计显著 ≠ 工程显著**。A 比 B 快 2% 且置信区间不重叠——统计上成立，但生产环境的噪声（GC 时机、调度波动、流量波动）远大于 2%，这个"优化"在生产中不可观测。工程上的经验阈值：**差异 < 10% 的微基准结论不作为优化决策依据**，除非这个操作在极热路径上（每秒百万次调用，2% 累积可观）。把"统计显著性"和"工程显著性"分开判断，是基准测试解读的最后一步，也是最容易被忽略的一步。

> [!info] 核心概念：置信区间重叠意味着"无法区分"
> 基准测试比较中，如果 A 的置信区间是 [994, 1006]，B 的置信区间是 [998, 1012]，两者重叠 [998, 1006]，说明在 95% 置信度下无法区分 A 和 B 的性能差异。此时不能说"A 比 B 快"或"B 比 A 快"——只能说"在本测试条件下，A 和 B 的性能差异不显著"。增加测量迭代次数可以缩小置信区间，但前提是差异确实存在。

## 第 7 章 基准测试的反模式

### 7.1 常见反模式

**反模式 1：用微基准结果推断系统性能**

```java
// 微基准：HashMap.get() 1000 万次/秒
// 推断：系统每秒能处理 1000 万个请求
// 实际：系统每秒只能处理 1 万个请求（瓶颈在网络和数据库）
```

微基准测的是"隔离环境中单个方法的性能"，系统性能受 I/O、锁、网络、GC 等多重因素影响，微基准结果不能直接外推。

**反模式 2：在开发机上做基准测试**

开发机运行着 IDE、浏览器、聊天工具，CPU 和内存被大量占用。在这种环境下的基准测试结果不可信。

**反模式 3：只看平均值不看分布**

```
平均响应时间：10ms
P50：5ms
P90：15ms
P99：200ms
P999：2000ms
```

平均值 10ms 看起来很好，但 P99 是 200ms——1% 的用户体验很差。只看平均值会掩盖尾部延迟问题。

**反模式 4：一次测量下结论**

单次基准测试的结果可能有偶然性（如恰好遇到 GC、OS 调度中断）。至少需要多次测量并检查置信区间。

**反模式 5：比较不同环境下的结果**

"A 在我的笔记本上测，B 在 CI 服务器上测，B 快 20%"——这个结论无效。**基准测试的对比必须在同一环境、同一时间窗口内完成**——环境差异（频率、缓存、NUMA、邻居）远大于多数被测差异。CI 上的回归基准之所以可行，是因为它每次都在同一环境跑基线与候选——"同环境对比"是基准测试的铁律。

### 7.2 基准测试的"诚实"原则

> [!note] 设计哲学：基准测试的伦理
> 基准测试的伦理是"诚实"——不为了得到期望的结果而调整方法。常见的"不诚实"行为：
> - **挑选有利的测量轮次**：只报告最好的那次结果
> - **调整参数直到结果"好看"**：反复调参直到 A 比 B 快
> - **忽略不利的指标**：只报告吞吐量，不报告延迟
> - **在非可比环境下比较**：A 在物理机上测，B 在虚拟机上测
>
> 基准测试的目的不是"证明你的代码快"，而是"理解代码的真实性能"。如果结果与预期不符，应该调查原因而非调整方法。一个"不好看但真实"的基准测试结果比一个"好看但虚假"的结果有价值得多。

"诚实"原则的工程落地是**结果的可复现性声明**：一份可信的基准测试报告必须包含——完整的环境描述（硬件、JVM 版本、所有参数）、原始数据（不只给平均值，给全部迭代数据）、实验配置（代码仓库 + 可复现的运行命令）。缺了这三样，报告的结论无法被他人验证，也就无法被信任。**基准测试的价值不在于"数字多大"，而在于"数字可被验证"**——这与第 14 篇"文档化是闭环的闭环"一脉相承。

## 第 8 章 JMH 进阶用法

### 8.1 @Param：参数化基准测试

`@Param` 让 JMH 对不同参数值运行同一基准测试，生成对比结果：

```java
@State(Scope.Thread)
public class ParamBenchmark {
    @Param({"100", "1000", "10000", "100000"})
    int size;

    int[] data;

    @Setup
    public void setup() {
        data = new int[size];
        // 初始化
    }

    @Benchmark
    public int test() {
        int sum = 0;
        for (int i = 0; i < size; i++) {
            sum += data[i];
        }
        return sum;
    }
}
```

JMH 会为每个 `size` 值运行完整的基准测试，输出对比表格：

```
Benchmark          (size)   Mode  Cnt     Score     Error  Units
testBenchmark        100  thrpt    10  1000.123 ±  5.678  ops/s
testBenchmark       1000  thrpt    10   100.456 ±  1.234  ops/s
testBenchmark      10000  thrpt    10    10.078 ±  0.123  ops/s
testBenchmark     100000  thrpt    10     1.012 ±  0.012  ops/s
```

@Param 的工程价值在于**找到"性能拐点"**：上面的输出显示吞吐随 size 线性下降（O(n) 操作的预期），但如果某个数据结构在 size 超过某阈值后性能"跳水"（譬如 HashMap 扩容、缓存超过 LLC 容量），@Param 扫描能精确定位这个阈值——**阈值知识比平均性能更有工程价值**，它直接对应容量规划的约束（第 01 篇的拐点思维在微基准维度的应用）。注意 @Param 的组合爆炸：两个 @Param（各 5 个值）= 25 次完整基准，每次含 Fork 启动——参数扫描的时间成本要提前规划（3.6 节的 Fork 代价）。

### 8.2 @CompilerControl：控制 JIT 编译

`@CompilerControl` 可以针对特定方法控制 JIT 编译行为：

```java
@CompilerControl(CompilerControl.Mode.DONT_INLINE)
private int helper(int x) {
    return x * 2;
}
// 强制 JIT 不内联 helper()，测量"方法调用 + 执行"的真实开销
```

@CompilerControl 还有两个常用模式：`Mode.INLINE`（强制内联——验证"如果内联了会多快"，量化内联收益）、`Mode.EXCLUDE`（禁止编译——让方法永远解释执行，量化 JIT 的贡献）。这两个模式组合出一个实用的分析方法：**同一逻辑测三次（正常 / 强制内联 / 禁止编译），三个数字的差值就是"JIT 各阶段贡献"的分解**——这比猜测"JIT 帮了多少忙"精确得多。

### 8.3 异步基准测试与返回值消费

JMH 对异步代码的基准测试通过返回值消费实现：

```java
@Benchmark
public CompletableFuture<Integer> testAsync() {
    return CompletableFuture.supplyAsync(() -> compute());
}
// JMH 会等待 CompletableFuture 完成后再计时
```

异步基准的陷阱是**"提交"与"完成"的混淆**：返回 `CompletableFuture` 的基准，JMH 等待的是"Future 完成"——如果被测代码把工作提交到另一个线程池就返回，测到的是"提交开销"而非"完成时间"。测异步操作的正确姿势：**Future.get() 显式等待**（把异步变同步再测），或者用 `@BenchmarkMode(Mode.SingleShotTime)` + 自行同步。异步基准的另一个陷阱是线程池的预热——被测代码内部如果懒初始化线程池，前几次测量的"池创建开销"会污染结果——@Setup(Level.Iteration) 里预热连接池/线程池是标准做法。

异步基准还有一个与第 11 篇呼应的陷阱：**异步框架内部的锁竞争**。CompletableFuture 默认用 ForkJoinPool.commonPool——多个基准线程共享它时，测到的"异步性能"里混着 commonPool 的竞争。控制方法：@State 里创建专用线程池（隔离竞争源），或在结论中明确声明"测量包含共享池竞争"。

### 8.4 JMH 与 JFR 集成

在 JMH 基准测试中启用 JFR，可以同时获得微基准结果和 JVM 运行时事件：

```bash
java -jar benchmarks.jar \
  -jvmArgs "-XX:StartFlightRecording=duration=60s,filename=bench.jfr" \
  -prof gc
```

JFR 与 JMH 的组合价值在于**解释"为什么快/慢"**：基准测试给出"快了多少"，JFR 给出"快在哪里"——GC 事件、编译事件、分配采样与基准结果按时间对齐，可以确认"性能差异确实来自假设的原因"（第 01 篇的因果验证原则）。譬如对比两个集合实现，A 比 B 快 30%——用 JFR 确认 A 的优势来自"更少的分配"（GC 事件少）而不是"碰巧没有触发 Full GC"，结论才可迁移到生产。

## 第 9 章 案例复盘：一次"缓存选型"基准测试的完整推演

用一个常见场景串联本章方法论：团队要为热点数据选缓存实现，候选是 ConcurrentHashMap（直接当缓存用）与 Caffeine。这个案例演示"从假设到结论"的完整基准测试流程。

**第一步：明确假设。** "Caffeine 的读性能与 ConcurrentHashMap 相当（都在 100ns 级），但内存占用更高（记录访问顺序的元数据）；Caffeine 的价值在淘汰策略而非读速度。"——这是一个可证伪的明确假设。

**第二步：设计实验。** 微基准（JMH）对比三种读操作：直接 get、带过期检查的 get、带统计计数的 get。@Param 扫描缓存大小（100/10K/1M 条目），@Fork(2)，预热 5 轮。输入用 Zipf 分布的 key（模拟生产热点）——第 4.3 节的输入真实性原则。

**第三轮：解读结果。** 微基准显示：纯 get 三者相当（都在 20-30ns）；Caffeine 的过期检查增加约 15ns；1M 条目时两者都出现 LLC miss 上升（第 05 篇的缓存层级）。**结论：读路径上 Caffeine 没有惩罚，选型由功能决定（需要过期/淘汰就用 Caffeine）**——微基准的价值是"排除性能顾虑"，而不是"证明谁快"。

**第四步：系统级验证。** 微基准的结论要过业务压测这一关：真实服务的缓存命中率、序列化开销、网络延迟都会稀释微基准的差异。用生产级负载模型（5.1 节）压测后确认：缓存实现的差异在端到端延迟中不可观测（< 1%），真正影响 P99 的是命中率（由容量和淘汰策略决定）。**最终决策依据从"哪个 get 更快"转向"哪个淘汰策略让命中率更高"——微基准回答了错误的问题，业务压测纠正了它**。

> [!note] 设计哲学：基准测试的"假设链"
> 这个案例展示了一个完整的假设链：**微基准验证组件级假设（读操作成本）→ 业务压测验证系统级假设（端到端收益）→ 生产灰度验证真实负载下的表现**。每一环都有明确的假设、实验和验证标准。跳过任何一环都会引入风险：只有微基准（可能系统级不成立）、只有业务压测（不知道差异来自哪个组件）。基准测试不是"一个测试"，而是"一条从组件到系统的假设验证链"——每一环的结论都依赖上一环的成立。这也是本章标题里"方法论"三个字的分量：工具（JMH/wrk）只是执行器，假设链才是灵魂。

## 第 10 章 总结

基准测试方法论的核心知识可以归纳为以下主线：

1. **基准测试是实验科学**：不是"跑个数字"，而是需要控制变量、消除干扰、确保可重复性的受控实验。错误的基准测试比不做基准测试更危险。

2. **JIT 是基准测试的最大敌人**：DCE、常量折叠、循环不变量外提等 JIT 优化会扭曲测量结果。JMH 的核心价值是对抗这些优化。

3. **JMH 的三大武器**：Blackhole（对抗 DCE）、Fork（隔离 JVM 状态）、预热（让 JIT 达到稳态）。理解这三个机制是正确使用 JMH 的前提。

4. **微基准测的是"相对比较"**：微基准结果不能推断系统性能，但可以用于"A 比 B 快多少倍"的相对比较。绝对预测需要系统级压测。

5. **系统级压测的核心是工作负载模型**：UoW 定义、负载强度、负载模式、混合比例。关注响应时间分布（P90/P99）而非平均值。

6. **找到拐点比找到"最大承受"更重要**：容量规划应基于性能拐点（约拐点负载的 70-80%），而非最大承受负载。

7. **环境隔离是可信度的前提**：独占硬件、关闭节能、固定亲和性、相同 JVM 参数。云环境中的基准测试需要独占型实例。

8. **统计显著性是结论的门槛**：置信区间重叠意味着"无法区分"。单次测量不可信，至少需要多次测量并检查置信区间。

9. **统计显著 ≠ 工程显著**：差异 < 10% 的结论不作为优化决策依据，除非在极热路径上。

10. **压测工具自身可能是瓶颈与偏差源**：协调遗漏让 P99 系统性低估；压测机 CPU 超过 70% 时结果可疑。

11. **输入分布要贴近生产**：规整输入让分支预测/缓存/JIT"作弊"，微基准结果乐观 2-10 倍。

12. **基准测试是假设验证链**：微基准 → 业务压测 → 生产灰度，每一环验证不同层级的假设，缺一环就有一环的风险。
