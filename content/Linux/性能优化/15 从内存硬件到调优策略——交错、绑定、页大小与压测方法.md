## 第 1 章 为什么真正有效的内存调优，必须从硬件矛盾出发

### 1.1 “参数清单式调优”为何经常无效

很多团队的所谓调优手册是这样的：

1. 开 THP 或关 THP。
2. 用 `numactl --membind`。
3. 绑核。
4. 看 `perf stat`。
5. 再跑一次压测。

问题是，这个流程没有解释：

- 为什么是这个动作。
- 它试图修什么。
- 对应的硬件瓶颈到底是什么。

结果就是两个极端：

要么所有机器都套同一套模板。

要么每个人凭经验拍脑袋。

真正稳定的调优，必须先回到硬件矛盾本身。

参数清单式调优为何经常无效还有一个与"模板套用"相关的危害——"参数清单式调优"让所有机器套同一模板——但不同机器硬件不同（通道数、NUMA 拓扑、DIMM 配置），同一模板在不同机器效果不同。所以"模板套用"忽视硬件差异——效果不可预测。**"模板套用"忽视硬件差异效果不可预测**——这是参数清单的"模板危害"，忽视差异。

参数清单式调优为何经常无效还有一个与"经验拍脑袋"相关的另一极端——"经验拍脑袋"是另一极端——凭经验调，无量化验证。经验可能过时（旧硬件经验不适用新硬件）或片面（只见过部分场景）。所以"经验拍脑袋"不可靠——要量化验证。**"经验拍脑袋"不可靠要量化验证**——这是参数清单的"经验极端"，要量化。

### 1.2 常见内存问题，其实来自四类不同矛盾

把问题抽象一下，内存相关性能问题大致可以归到四类：

1. **供给不够宽**：Channel / 节点带宽不够，流量跑不满业务需要。
2. **数据离计算太远**：线程跑在一个节点，内存却分配在另一个节点。
3. **地址翻译成本太高**：TLB 覆盖不足、页表遍历压力大。
4. **访问路径本身不友好**：Row Buffer 命中差、随机性强、长尾高。

你会发现，这四类问题对应的动作并不一样。

交错更偏向第一类。

绑定更偏向第二类。

页大小更偏向第三类。

压测方法则是为了确认你面对的到底是哪一类。

常见内存问题来自四类不同矛盾还有一个与"四类正交"相关的认知——四类矛盾"正交"——一个问题可能同时有"供给不够宽 + 访问不友好"（譬如带宽型 + 随机访问）。要分别诊断每类的贡献——不能混。所以"四类正交"——分别诊断每类贡献。**"四类正交"分别诊断每类贡献**——这是四类矛盾的"正交认知"，分别诊断。

常见内存问题来自四类不同矛盾还有一个与"主次排序"相关的实践——四类矛盾要"主次排序"——先解决主矛盾，再解决次矛盾。譬如主矛盾是"远端访问"（NUMA），次矛盾是"TLB 压力"——先绑 NUMA 再开大页。所以"主次排序"是调优实践——先主后次。**"主次排序"是调优实践先主后次**——这是四类矛盾的"排序实践"，先主后次。

### 1.3 为什么“知道根因”比“知道命令”更重要

举个简单例子。

如果你的问题是远端 NUMA 访问，盲目开大页通常帮不上忙。

如果你的问题是 TLB Miss 很重，单纯 `membind` 也不解决页表压力。

如果你的问题是单节点带宽打满，再怎么把线程绑得更紧，也只是让局部更拥塞。

所以调优顺序一定是：

**根因先行，动作后置。**

知道根因比知道命令更重要还有一个与"根因 → 动作映射"相关的框架——"根因先行"的框架：先诊断根因（四类矛盾哪类），再选动作（交错/绑定/页大小对应）。根因 → 动作是一一映射——不诊断根因就选动作是"盲调"。所以"根因 → 动作映射"是框架——先诊断后选动作。**"根因 → 动作映射"是框架先诊断后选动作**——这是根因先行的"映射框架"，一一映射。

知道根因比知道命令更重要还有一个与"误用命令"相关的避免——不诊断根因就选命令——可能"误用命令"：譬如根因是 TLB 压力却用 `membind`（绑内存不解决 TLB）——误用。所以"根因先行"避免"误用命令"——对症下药。**"根因先行"避免"误用命令"对症下药**——这是根因先行的"避免误用"，对症下药。

### 1.4 本文的行动地图

为了让策略和硬件一一对应，本文围绕四个动作展开：

1. 交错：什么时候应该把流量分散到更多节点或通道。
2. 绑定：什么时候应该强行把计算和内存收拢在一起。
3. 页大小：什么时候该换取更大的 TLB 覆盖，什么时候不该。
4. 压测：如何构造能验证这些动作是否真的改善了硬件瓶颈的实验。

## 第 2 章 交错（Interleaving）：它解决的是“供给太窄”，不是“延迟太高”

### 2.1 为什么交错的第一性原理是“并行利用更多内存资源”

内存系统的供给能力来自：

- 更多 Channel；
- 更多 NUMA 节点；
- 更好的 Rank / Bank 并发利用；
- 更高的 MT/s。

当 workload 是典型的流式带宽型任务时，如果所有分配都集中在单一节点，就等于只让一部分内存控制器和通道工作。

这时交错策略的价值就非常直接：

**把页分散到多个节点，让更多控制器和通道同时供给数据。**

交错的第一性原理是并行利用更多内存资源还有一个与"交错 ≠ 拆分单次访问"相关的澄清——`--interleave` 不是"把单次访问拆到多节点并行"——单次 load 仍只落一个节点。交错是"页级轮转分散"——让工作集分布到多节点——提高总供给。所以"交错 ≠ 拆分单次访问"——是页级分散非访问拆分。**"交错 ≠ 拆分单次访问"是页级分散**——这是交错原理的"澄清认知"，页级非访问级。

交错的第一性原理是并行利用更多内存资源还有一个与"总供给 vs 单次延迟"相关的权衡——交错提高"总供给"（多节点并行供给）但可能降低"单次延迟"（更多远端访问）。所以交错是"总供给 vs 单次延迟"的权衡——带宽型受益，延迟型受损。**交错是"总供给 vs 单次延迟"权衡**——这是交错原理的"权衡认知"，带宽受益延迟损。

### 2.2 Linux 世界里的交错通常指哪几层

工程上提“交错”，至少可能指三层不同东西：

1. 平台 / BIOS 级内存交错。
2. NUMA 策略层的页交错，如 `numactl --interleave=all`。
3. 应用 / 数据分片层的人为均摊。

本文主要聚焦第二层，也就是 Linux 层能直接控制的页分配策略。

因为这是最常见、也最容易和业务结合的交错动作。

Linux 世界里的交错通常指哪几层还有一个与"BIOS 级交错"相关的底层——BIOS 级交错是"硬件交错"——BIOS 配置内存控制器把物理地址跨 Channel/Rank 交错——对 OS 透明。Linux 看不到 BIOS 交错——但能受益（地址天然分散到多 Channel）。所以"BIOS 级交错"是硬件层——OS 透明但受益。**"BIOS 级交错"是硬件层 OS 透明但受益**——这是交错三层的"BIOS 底层"，OS 透明。

Linux 世界里的交错通常指哪几层还有一个与"应用分片"相关的上层——应用层交错是"数据分片"——譬如数据库按 hash 分片到多节点——每片在不同节点。这是"应用层交错"——比 `numactl --interleave` 更上层。所以"应用分片"是应用层交错——比 numactl 更上层。**"应用分片"是应用层交错比 numactl 更上层**——这是交错三层的"应用上层"，数据分片。

### 2.3 `numactl --interleave` 真正做了什么

它不是把一条指令的单次内存访问“拆分到多个节点并行完成”。

这是很多人最容易误解的地方。

`--interleave` 做的是：

**后续页面分配按页轮转分散到指定节点集合。**

因此，它改善的是整体工作集在多个节点上的分布，从而提高总供给能力。

但对任意单次 load 来说，它仍然只会落在某一个物理地址、某一个目标节点上。

numactl --interleave 真正做了什么还有一个与"页轮转粒度"相关的细节——`--interleave` 的轮转粒度是"页"（默认 4KB）——第 1 页在 node0，第 2 页在 node1，第 3 页在 node0...所以"页轮转粒度"是 4KB——按页轮转分散。**"页轮转粒度"是 4KB 按页轮转分散**——这是 interleave 的"粒度细节"，4KB 轮转。

numactl --interleave 真正做了什么还有一个与"interleave=all vs interleave=0,1"相关的范围——`--interleave=all` 分散到所有节点；`--interleave=0,1` 只分散到 node0 和 node1。可以指定节点子集——不一定要 all。所以"interleave 范围可指定"——不一定要 all，可子集。**"interleave 范围可指定"不一定要 all 可子集**——这是 interleave 的"范围细节"，可指定子集。

### 2.4 什么场景最适合交错

典型适用场景包括：

1. 大规模顺序扫描。
2. 分析型查询。
3. 批处理或向量化处理。
4. 明显吃带宽，而不是吃首字节延迟的任务。
5. 单节点内存容量不足，必须跨节点分配的大工作集。

这些场景的共同点是：

- 更在乎总吞吐；
- 可接受一定比例的远端访问；
- 线程通常够多，可以并行消费多个节点的供给。

什么场景最适合交错还有一个与"Spark / Flink"相关的典型——Spark/Flink 大数据处理是交错典型——大工作集（TB 级）、多线程、带宽型、吞吐优先。这些场景 `--interleave=all` 能显著提带宽。所以"Spark/Flink"是交错典型——大数据处理受益。**"Spark/Flink"是交错典型大数据处理受益**——这是交错场景的"典型代表"，大数据受益。

什么场景最适合交错还有一个与"单节点容量不足"相关的另一动机——交错不只为带宽——也为"单节点容量不足"。如果工作集 > 单节点内存——必须跨节点分配——`--interleave` 让分配均匀分散——避免单节点 OOM。所以"单节点容量不足"也是交错动机——不只带宽。**"单节点容量不足"也是交错动机不只带宽**——这是交错场景的"容量动机"，跨节点避 OOM。

### 2.5 什么场景不适合交错

如果 workload 更像下面这些：

- 单线程或少线程 KV；
- 延迟敏感 RPC；
- 强本地性缓存；
- 高频随机读；
- 对 P99 极其敏感的在线服务；

那么交错常常得不偿失。

原因很简单。

你虽然把总带宽池做大了。

但也让更多访问有概率落到远端节点。

对这些业务来说，远端访问增加的单次延迟，往往比多出来的总带宽更致命。

什么场景不适合交错还有一个与"Redis 单实例"相关的典型——Redis 单实例是交错不适合的典型——延迟敏感（P99 要求高）、单线程或少线程、强本地性。`--interleave` 让 Redis 访问跨节点——P99 恶化。所以"Redis 单实例"是交错不适合——延迟敏感受损。**"Redis 单实例"是交错不适合延迟敏感受损**——这是不适合交错的"典型代表"，Redis 受损。

什么场景不适合交错还有一个与"高频交易"相关的极端——高频交易对延迟极端敏感（微秒级）——任何远端访问都不可接受。`--interleave` 增加远端概率——高频交易绝对不用。所以"高频交易"是交错不适合的极端——绝对不用。**"高频交易"是交错不适合的极端绝对不用**——这是不适合交错的"极端代表"，绝对不用。

### 2.6 交错最容易被误用成“带宽万金油”

有人看到带宽基准分数更高，就以为线上所有任务都该 `--interleave=all`。

这其实把“系统吞吐最优”和“请求延迟最优”混成了一件事。

它们常常不是同一个最优点。

这件事必须记住。

> [!warning] 生产避坑
> 交错能扩大总体供给，但通常会稀释局部性。凡是对单次远端延迟敏感的业务，都不能把 `interleave` 当默认配置。

### 2.7 一个非常实用的判断标准

如果一个 workload 满足下面三个条件中的两个以上，才值得优先考虑交错：

1. `STREAM` / 带宽基准与业务都显示明显 bandwidth bound。
2. 线程数较多，且并行性足以消费更多节点供给。
3. 延迟目标更宽松，吞吐优先于单次请求响应。

如果不是，就先不要急着交错。

一个非常实用的判断标准还有一个与"先测再决定"相关的纪律——判断标准要"先测再决定"：先跑 STREAM 看是否 bandwidth bound，先跑 pointer chasing 看是否 latency bound，先看 P99 看是否延迟敏感。测完再决定是否交错——不盲调。所以"先测再决定"是判断标准的纪律——不盲调。**"先测再决定"是判断标准纪律不盲调**——这是判断标准的"测后决定"，先测再调。

一个非常实用的判断标准还有一个与"三条件权重"相关的灵活——三条件不是"全部满足才交错"——是"满足两个以上才考虑"。灵活权重——譬如带宽 bound + 多线程（满足两个）→ 考虑交错，即使延迟敏感也考虑（因为带宽 bound 主导）。所以"三条件权重灵活"——满足两个以上即考虑。**"三条件权重灵活"满足两个以上即考虑**——这是判断标准的"权重灵活"，两条件即考虑。

### 2.8 交错与 Row Buffer 问题的边界

交错可以增加节点级并行度。

但它并不会直接修复 [[12 Row Buffer 命中与 Bank 冲突——内存延迟抖动的硬件根因|Row Conflict]]。

更准确地说：

它可能通过把工作集摊薄到更多控制器与 Bank 集合上，间接降低局部拥挤。

但如果单线程随机访问模式本身没变，那么行冲突的结构性问题仍然存在。

所以不要把交错误当成“Row Buffer 优化开关”。

交错与 Row Buffer 问题的边界还有一个与"间接降低 Bank 拥挤"相关的连带——交错把工作集摊到更多控制器和 Bank 集合——间接降低"局部 Bank 拥挤"（更多 Bank 可用）。但这不修复"单线程随机访问的 Row Conflict"——只降低"多线程 Bank 拥挤"。所以交错"间接降低 Bank 拥挤"但不修复"单线程 Row Conflict"——边界明确。**交错"间接降 Bank 拥挤"不修复"单线程 Row Conflict"**——这是交错 Row Buffer 边界的"连带认知"，间接降拥挤。

交错与 Row Buffer 问题的边界还有一个与"Row Buffer 优化靠数据布局"相关的方向——Row Buffer 优化的正确方向是"数据布局"——让相关数据落同行（提 Row Hit），而非"交错"（摊到多节点）。所以 Row Buffer 优化靠"数据布局"非"交错"——方向不同。**Row Buffer 优化靠"数据布局"非"交错"**——这是交错 Row Buffer 边界的"优化方向"，数据布局非交错。

## 第 3 章 绑定（Binding）：它解决的是“数据离计算太远”

### 3.1 为什么绑定的核心不是控制欲，而是缩短路径

`cpunodebind`、`membind`、`preferred`、`localalloc` 看起来都像在“人为限制调度自由”。

很多人因此天然排斥绑定，觉得这是在和内核对着干。

其实绑定的本质不是控制欲。

它是在回答一个极其朴素的问题：

**既然数据在某个节点，为什么线程要跑到另一个节点去取。**

绑定的核心不是控制欲而是缩短路径还有一个与"远端访问代价"相关的动机——远端访问比本地访问慢 1.5-2 倍（典型 NUMA distance 20 vs 10）——绑定缩短路径，避免远端代价。所以绑定的动机是"远端访问代价"——缩短路径避远端。**绑定的动机是"远端访问代价"缩短路径避远端**——这是绑定核心的"动机认知"，远端慢 1.5-2 倍。

绑定的核心不是控制欲而是缩短路径还有一个与"控制欲误解"相关的澄清——很多人以为绑定是"控制欲"（人为限制调度自由）——其实是"缩短路径"（让数据离计算近）。理解本质后——绑定不是和内核对着干，而是优化数据局部性。所以"控制欲"是误解——本质是"缩短路径"。**"控制欲"是误解本质是"缩短路径"**——这是绑定核心的"误解澄清"，本质非控制欲。

### 3.2 绑定通常有哪几种力度

Linux 里常见的绑定策略可以按力度大致理解为：

1. `--preferred`：优先在某节点分配，不够时允许退让。
2. `--localalloc`：尽量从当前节点分配，保持一定动态性。
3. `--membind`：强制从指定节点分配，不够时失败。
4. `--cpunodebind` / `--physcpubind`：把线程执行位置也收紧。

它们从宽松到严格，分别适合不同场景。

绑定通常有哪几种力度还有一个与"preferred vs membind"相关的区别——`--preferred` 优先在某节点分配，不够时退让到其他节点（柔性）；`--membind` 强制从指定节点分配，不够时失败（刚性）。延迟敏感服务用 `--preferred`（避免失败），独占节点用 `--membind`（确保本地）。所以"preferred 柔性 membind 刚性"——按场景选力度。**"preferred 柔性 membind 刚性"按场景选力度**——这是绑定力度的"柔刚区别"，按场景选。

绑定通常有哪几种力度还有一个与"cpunodebind + membind 成对"相关的纪律——`--cpunodebind` 和 `--membind` 要成对用——只绑 CPU 不绑内存（或反之）只做对一半。成对绑才让"线程 + 数据"同节点。所以"cpunodebind + membind 成对"是纪律——成对绑。**"cpunodebind + membind 成对"是纪律成对绑**——这是绑定力度的"成对纪律"，成对用。

### 3.3 为什么只绑 CPU 不绑内存，经常只做对一半

如果你把线程限制在 Node 0 上，但历史分配的堆、大页、共享内存仍然大多在 Node 1，那么结果是什么。

结果就是：

- 调度看起来更整齐；
- 但 load 仍然要跨节点；
- 延迟不一定改善；
- 某些情况下甚至更糟，因为你失去了线程在远端节点本地执行的自由。

这就是为什么 NUMA 调优里常说：

计算和内存要成对考虑。

只绑 CPU 不绑内存经常只做对一半还有一个与"历史分配"相关的难点——"历史分配"是难点：进程已运行的堆/大页可能在绑 CPU 前就分配在远端——绑 CPU 后仍跨节点访问。要解决——需"重启绑定"（numactl 启动时同时绑 CPU + 内存）或"迁移页面"（migrate_pages）。所以"历史分配"是绑定的难点——要重启或迁移。**"历史分配"是绑定难点要重启或迁移**——这是只绑 CPU 的"历史难点"，重启或迁移。

只绑 CPU 不绑内存经常只做对一半还有一个与"migrate_pages"相关的工具——`migrate_pages` 系统调用（或 `numactl --migrate`）能把已分配页面迁移到目标节点——解决"历史分配"问题。但迁移有开销（拷贝数据）——不适合频繁迁移。所以 `migrate_pages` 解决"历史分配"——但有开销不频繁。**`migrate_pages` 解决"历史分配"但有开销不频繁**——这是只绑 CPU 的"迁移工具"，解决历史分配。

### 3.4 为什么只绑内存不绑 CPU，也可能收效有限

反过来也是一样。

如果你强制 `--membind=0`，但线程仍然在所有节点到处跑，那么：

- 在 Node 0 运行的线程会受益；
- 在其他节点运行的线程会持续远端访问 Node 0；
- 负载分布反而可能更加失衡。

所以绑定的真正目标不是“把所有东西都绑死”。

而是：

**让线程最常访问的数据，尽量位于它最常运行的那个节点。**

只绑内存不绑 CPU 也可能收效有限还有一个与"调度自由 vs 本地性"相关的矛盾——不绑 CPU 时内核可自由调度线程到任何节点——如果线程跑到远端节点访问绑定的内存——仍跨节点。绑内存限制"数据位置"但不限制"线程位置"——线程可能远离数据。所以"只绑内存"的矛盾是"调度自由 vs 本地性"——线程可能远离数据。**"只绑内存"的矛盾是"调度自由 vs 本地性"线程可能远离**——这是只绑内存的"矛盾认知"，线程远离数据。

只绑内存不绑 CPU 也可能收效有限还有一个与"自动 NUMA 平衡"相关的补偿——Linux"自动 NUMA 平衡"（numad）会自动迁移页面到访问 CPU 所在节点——部分补偿"只绑内存"的问题。但自动平衡有延迟（不是立即迁移）——延迟敏感场景仍需手动绑 CPU。所以"自动 NUMA 平衡"部分补偿——但延迟敏感仍需手动绑。**"自动 NUMA 平衡"部分补偿延迟敏感仍需手动绑**——这是只绑内存的"自动补偿"，部分补偿。

### 3.5 什么场景最适合绑定

下面这些场景通常更适合绑定策略：

1. 延迟敏感服务。
2. 单实例较大、但仍能装进单节点内存的服务。
3. 网络或存储设备已经有明显 NUMA 归属，需要和 CPU / 内存一起收口。
4. 进程线程模型比较稳定，长期驻留在固定 CPU 集合上。

例如：

- Redis 单实例；
- 低延迟撮合或网关服务；
- 需要控制尾延迟的缓存服务；
- 某些独占节点的 Java 进程。

什么场景最适合绑定还有一个与"网卡 NUMA"相关的扩展——网卡也有 NUMA 归属——譬如某些 NIC 的队列绑在 node0。如果网络密集型服务的 CPU/内存绑在 node1 但网卡在 node0——网络数据包处理跨节点。所以绑定要"CPU + 内存 + 网卡"一起考虑——不只是 CPU 和内存。**绑定要"CPU + 内存 + 网卡"一起考虑**——这是绑定场景的"网卡扩展"，一起考虑。

什么场景最适合绑定还有一个与"DPDK / SPDK"相关的极端——DPDK（数据面网络包处理）/ SPDK（存储）对延迟极端敏感——通常独占 CPU + 绑定 NUMA + 绑定网卡队列。这些场景绑定是"必须"——不绑无法达到微秒级延迟。所以"DPDK/SPDK"是绑定极端——必须绑。**"DPDK/SPDK"是绑定极端必须绑**——这是绑定场景的"DPDK 极端"，必须绑。

### 3.6 什么场景过度绑定反而有害

如果你的工作集根本放不进单节点，或者线程会动态扩缩、负载极不均衡，那么过度 `membind` 可能导致：

1. 单节点内存先耗尽。
2. 分配失败或频繁 fallback。
3. 某一侧 CPU 忙死，另一侧闲着。
4. 自动 NUMA 平衡与手动策略互相打架。

这说明绑定不是越硬越好。

它本质上是在“本地性”和“资源弹性”之间做取舍。

什么场景过度绑定反而有害还有一个与"弹性扩缩"相关的冲突——过度绑定与"弹性扩缩"冲突——绑死在固定 CPU/内存后，无法弹性扩缩到其他节点。云原生场景（K8s 动态调度）与过度绑定冲突——pod 可能调度到任何节点，绑定假设固定节点。所以"过度绑定 vs 弹性扩缩"冲突——云原生慎用绑定。**"过度绑定 vs 弹性扩缩"冲突云原生慎用**——这是过度绑定的"弹性冲突"，云原生慎用。

什么场景过度绑定反而有害还有一个与"自动 NUMA 平衡打架"相关的另一问题——手动绑定可能与"自动 NUMA 平衡"（numad）打架——numad 想迁移页面，手动绑定禁止迁移。两者冲突——要么关 numad 要么不用手动绑定。所以"手动绑定 vs numad 打架"——二选一。**"手动绑定 vs numad 打架"二选一**——这是过度绑定的"numad 冲突"，二选一。

### 3.7 一个常被忽略的问题：绑定也会改变压测结果的解释

你用 `taskset`、`numactl` 绑了 CPU 和内存以后，压测分数当然可能变。

但你必须知道自己改变了什么：

- 是减少了远端访问。
- 还是减少了调度波动。
- 还是只是在缩小可用资源池后，让平均值看起来更稳定。

这就是为什么绑定实验必须配合：

- `numastat -p`；
- `perf stat`；
- 请求级延迟分布。

一起看，不能只看 QPS。

绑定也会改变压测结果的解释还有一个与"QPS 假象"相关的陷阱——绑定后 QPS 可能升——但升的原因不一定是"本地性改善"——可能是"调度波动减少"（线程不迁移，cache 稳定）或"资源池缩小"（少节点少争用）。只看 QPS 无法区分——要配合 numastat/perf 看原因。所以"QPS 假象"是绑定的陷阱——要配合观测看原因。**"QPS 假象"是绑定陷阱要配合观测看原因**——这是绑定压测的"QPS 陷阱"，配合观测。

绑定也会改变压测结果的解释还有一个与"P99 vs 平均"相关的重点——绑定对"P99"的影响常比"平均"更显著——绑定减少远端访问，P99（最慢请求）改善明显，平均（多数请求）改善少。所以绑定压测要看"P99"——不只平均。**绑定压测要看"P99"不只平均**——这是绑定压测的"P99 重点"，P99 更显著。

### 3.8 绑定与交错，为什么常常是对立策略

交错想要把页摊开。

绑定想要把页收拢。

前者优先总供给。

后者优先本地性。

它们不是谁更高级，而是在解决不同问题。

如果你不知道自己更缺哪一个，就不该同时把两者都开到最大。

绑定与交错为什么常常是对立策略还有一个与"不可能同时最优"相关的本质——"总供给最优"（交错）和"单次延迟最优"（绑定）常常不可能同时最优——交错摊开增加远端，绑定收拢减少总供给。这是"带宽 vs 延迟"的根本权衡——不可能同时最优。所以"不可能同时最优"是绑定 vs 交错的本质——权衡。**"不可能同时最优"是绑定 vs 交错本质权衡**——这是绑定交错的"本质权衡"，不可能同时。

绑定与交错为什么常常是对立策略还有一个与"混合策略"相关的折中——某些场景用"混合策略"——譬如"按分片绑定 + 分片间交错"：每个分片绑在固定节点（分片内本地性），分片间交错分布到多节点（整体供给）。这是"绑定 + 交错"的折中——分片粒度上同时实现。所以"混合策略"是绑定 vs 交错的折中——分片粒度。**"混合策略"是绑定 vs 交错折中分片粒度**——这是绑定交错的"混合折中"，分片粒度。

## 第 4 章 页大小（Page Size）：它解决的是翻译成本，不是 DRAM 神奇提速

### 4.1 为什么页大小调优经常被神化

大页很容易被包装成一种“开启就能让内存更快”的万能技巧。

这话最危险的地方在于，它把真正的收益来源说错了。

页大小最核心的作用在于：

1. 扩大单个 TLB 表项覆盖的地址范围。
2. 降低页表层级遍历压力。
3. 某些情况下改善物理内存管理与映射开销。

它不是直接把 DRAM 频率调高，也不是直接提升 Row Buffer 命中率。

页大小调优经常被神化还有一个与"神化来源"相关的误解——大页"神化"的来源：早期 JVM/数据库用大页后性能显著提升——被传成"大页万能"。但那些场景是"TLB 压力主导"——大页对症。非 TLB 主导场景大页收益小——神化不成立。所以"神化来源"是早期 TLB 主导场景——非 TLB 主导不神化。**"神化来源"是早期 TLB 主导场景非 TLB 主导不神化**——这是大页神化的"来源误解"，早期场景。

页大小调优经常被神化还有一个与"大页副作用"相关的代价——大页有副作用：① 碎片化（大页需连续物理内存，碎片化难分配）；② 内存浪费（内部碎片，大页未填满浪费）；③ THP compaction 抖动（后台整理内存引发延迟）。所以大页有"副作用"——不是无代价。**大页有"副作用"不是无代价**——这是大页神化的"副作用代价"，碎片浪费抖动。

### 4.2 4KB、2MB、1GB 分别意味着什么

从工程视角可以这样理解：

- 4KB：默认页，灵活、碎片代价低、TLB 覆盖最小。
- 2MB：常见 HugePage，TLB 覆盖大幅提升，碎片与回收成本更高。
- 1GB：超大页，极端覆盖率，适用边界极窄，对连续物理内存要求高。

因此，页大小从来不只是“越大越先进”。

它伴随的是更强的分配约束和内存管理副作用。

4KB 2MB 1GB 分别意味着什么还有一个与"TLB 覆盖对比"相关的量化——TLB 覆盖对比：4KB 页 × 64 表项 = 256KB 覆盖；2MB 页 × 64 表项 = 128MB 覆盖；1GB 页 × 64 表项 = 64GB 覆盖。大页覆盖呈数量级提升——但 1GB 适用边界极窄（需 1GB 连续物理内存）。所以"TLB 覆盖对比"呈数量级提升——1GB 边界窄。**"TLB 覆盖对比"数量级提升 1GB 边界窄**——这是页大小的"覆盖量化"，数量级提升。

4KB 2MB 1GB 分别意味着什么还有一个与"1GB 页适用场景"相关的极窄——1GB 页适用场景极窄——譬如大内存数据库（HANA）、HPC 大数组。这些场景工作集几十 GB 且连续——1GB 页显著降 TLB 压力。普通业务用 1GB 页不现实（分配约束太强）。所以"1GB 页适用极窄"——大内存数据库/HPC。**"1GB 页适用极窄"大内存数据库/HPC**——这是页大小的"1GB 场景"，极窄适用。

### 4.3 什么场景最适合大页

大页通常更适合：

1. 大内存、长生命周期、访问范围广的进程。
2. 需要减少 TLB Miss 的数据库、JVM、大型缓存。
3. 页表开销明显、工作集远大于默认页粒度的场景。

如果 `perf stat`、`TLB-load-misses`、应用特征都指向地址翻译成本较重，那么页大小调整就更有意义。

什么场景最适合大页还有一个与"JVM 大页"相关的典型——JVM 是大页典型——堆大（GB 级）、对象多、TLB 压力大。JVM 用大页（`-XX:+UseLargePages`）显著降 TLB miss。所以"JVM 大页"是典型——堆大 TLB 压力大受益。**"JVM 大页"是典型堆大 TLB 压力大受益**——这是大页场景的"JVM 典型"，堆大受益。

什么场景最适合大页还有一个与"数据库大页"相关的另一典型——数据库（Oracle/PostgreSQL）也是大页典型——共享缓冲池大（GB 级）、访问范围广。数据库用大页降 TLB miss——显著改善。所以"数据库大页"是另一典型——缓冲池大受益。**"数据库大页"是另一典型缓冲池大受益**——这是大页场景的"数据库典型"，缓冲池大。

### 4.4 什么场景不该急着用大页

下面这些情况就要谨慎：

1. 工作集其实很小，大多数数据都在 cache 内。
2. 进程生命周期短、分配释放剧烈、内存碎片敏感。
3. 你真正的问题是远端 NUMA 或带宽不足。
4. 系统内存压力本来就大，THP compaction 可能引入抖动。

如果根因不在 TLB，强上大页往往只会制造新的副作用。

什么场景不该急着用大页还有一个与"小工作集"相关的无感——工作集 < LLC 时——数据在 cache——不落 DRAM——TLB miss 少（访问少）。大页对小工作集无感——TLB 压力本来就不大。所以"小工作集"大页无感——TLB 压力本不大。**"小工作集"大页无感 TLB 压力本不大**——这是不该用大页的"小工作集"，无感。

什么场景不该急着用大页还有一个与"短生命周期"相关的浪费——短生命周期进程（譬如 cron 任务、临时脚本）——分配释放剧烈——大页分配开销大（找连续物理内存）且无法重用（释放后碎片）。所以"短生命周期"大页浪费——分配开销大无法重用。**"短生命周期"大页浪费分配开销大无法重用**——这是不该用大页的"短生命周期"，浪费。

### 4.5 THP 与显式 HugePage 的取舍为什么必须分场景

[[THP]] 的优点是自动化。

缺点也正是自动化。

因为它意味着：

- 内核可能在后台做合并和整理；
- 某些时刻会发生 compaction；
- 延迟敏感业务可能因此出现抖动。

显式 HugePage（如 `hugetlbfs`）更可控。

但代价是：

- 预留麻烦；
- 失败更刚性；
- 运维复杂度更高。

所以对在线延迟服务和离线吞吐任务，选择往往不同。

THP 与显式 HugePage 的取舍为什么必须分场景还有一个与"THP compaction 抖动"相关的风险——THP 的 compaction（内存整理）可能引发"抖动"——内核后台整理内存时短暂停顿业务——延迟敏感业务 P99 恶化。所以"THP compaction 抖动"是 THP 的风险——延迟敏感慎用 THP。**"THP compaction 抖动"是 THP 风险延迟敏感慎用**——这是 THP vs HugePage 的"抖动风险"，延迟敏感慎用。

THP 与显式 HugePage 的取舍为什么必须分场景还有一个与"显式 HugePage 预留"相关的运维——显式 HugePage 要"预留"（`sysctl vm.nr_hugepages`）——预留的内存不能给普通页用——运维复杂。但预留后稳定（无 compaction 抖动）。所以"显式 HugePage 预留"是运维代价——预留稳定但复杂。**"显式 HugePage 预留"是运维代价预留稳定但复杂**——这是 THP vs HugePage 的"预留运维"，稳定但复杂。

### 4.6 页大小与物理连续性的关系，为什么既重要又不能神化

大页通常意味着更大块的物理连续区域。

这可能间接影响地址映射与预取表现。

但不要过度推导成：

“用了大页，Row Buffer 命中率就一定更高。”

那是把两个不同层级的问题混在了一起。

更稳妥的表述是：

大页主要改善地址翻译层，可能对物理布局和整体访存行为产生次级影响，但并不直接等价于 DRAM 行局部性优化。

页大小与物理连续性的关系为什么既重要又不能神化还有一个与"次级影响"相关的间接——大页的"次级影响"：物理连续 → 预取更有效（连续地址预取器工作好）→ 可能间接改善 prefetch 命中。但这是"次级"——非主要收益。主要收益是 TLB。所以大页"次级影响"是预取——非主要收益。**大页"次级影响"是预取非主要收益**——这是页大小连续性的"次级认知"，预取间接。

页大小与物理连续性的关系为什么既重要又不能神化还有一个与"Row Hit 不直接"相关的边界——大页不直接提 Row Hit——Row Hit 取决于"访问是否落同行"，与页大小无直接关系。大页让物理地址连续——但访问模式（随机 vs 顺序）决定 Row Hit，不是页大小。所以"Row Hit 不直接"是大页的边界——访问模式决定非页大小。**"Row Hit 不直接"是大页边界访问模式决定**——这是页大小连续性的"Row Hit 边界"，访问模式决定。

### 4.7 一个实用的判断框架

如果你怀疑该不该动页大小，先问三件事：

1. `perf` 是否显示明显 TLB 压力。
2. 工作集是否足够大且生命周期足够长。
3. 业务对碎片、回收、分配失败的容忍度如何。

三件事都偏正向，再考虑大页。

否则先别急。

一个实用的判断框架还有一个与"perf TLB 事件"相关的诊断——判断"TLB 压力"的诊断命令：`perf stat -e dTLB-load-misses,iTLB-load-misses ./program`——看 TLB miss 率。如果 dTLB-load-misses 高（譬如 > 10% of loads）→ TLB 压力大 → 大页有意义。所以"perf TLB 事件"是诊断 TLB 压力的命令——看 miss 率。**"perf TLB 事件"诊断 TLB 压力看 miss 率**——这是判断框架的"诊断命令"，看 miss 率。

一个实用的判断框架还有一个与"三问顺序"相关的纪律——三问要按顺序：先问"TLB 压力"（perf）→ 再问"工作集大小"（> LLC 才有意义）→ 再问"业务容忍度"（碎片/回收/失败容忍）。按顺序——前一个不满足就不看后一个。所以"三问顺序"是纪律——按序判断。**"三问顺序"是纪律按序判断**——这是判断框架的"顺序纪律"，按序判断。

## 第 5 章 压测方法：为什么没有正确实验设计，所有调优都不可信

### 5.1 为什么压测不是“跑个 benchmark 看分数”

内存调优最容易出现的假阳性有三类：

1. 改动了 CPU 亲和性，但以为自己优化了内存。
2. 改动了页大小，但工作集没出 LLC，结果测不出差异。
3. 改动了交错策略，但 benchmark 本身不吃带宽。

这些问题本质上都是实验设计不正确。

所以压测必须回答的不只是“变快了吗”。

还要回答：

- 快的是哪一类指标；
- 快的原因和你的假设是否一致；
- 在生产 workload 下能不能复现。

为什么压测不是跑个 benchmark 看分数还有一个与"假阳性"相关的风险——"假阳性"是压测最大风险——以为调优有效实则无效。三类假阳性：① 改 CPU 亲和性以为是内存优化；② 改页大小但工作集没出 LLC 测不出差异；③ 改交错但 benchmark 不吃带宽。所以"假阳性"是压测风险——要避免。**"假阳性"是压测风险要避免**——这是压测不是看分数的"假阳性风险"，三类假阳性。

为什么压测不是跑个 benchmark 看分数还有一个与"假阴性"相关的另一风险——"假阴性"是另一风险——以为调优无效实则有效。譬如工作集设太小（< LLC）→ 测不出大页收益 → 以为大页无效（假阴性）。所以"假阴性"也是压测风险——工作集设计不当。**"假阴性"也是压测风险工作集设计不当**——这是压测不是看分数的"假阴性风险"，工作集不当。

### 5.2 压测首先要选对问题类型

内存相关压测至少可以分成三类：

1. **延迟型微基准**：看单次随机访问代价。
2. **带宽型微基准**：看持续流量供给。
3. **业务型压测**：看真实请求路径在特定策略下的体感变化。

这三类测试谁都不能替代谁。

如果你只跑带宽测试，就得不到随机读延迟结论。

如果你只跑 pointer chasing，也得不到节点级总吞吐结论。

压测首先要选对问题类型还有一个与"三类互补"相关的纪律——三类测试"互补"——延迟型看单次代价，带宽型看总供给，业务型看真实体感。任何一类都不能替代其他两类——要三类都跑。所以"三类互补"是压测纪律——三类都跑。**"三类互补"是压测纪律三类都跑**——这是选对问题类型的"互补纪律"，三类都跑。

压测首先要选对问题类型还有一个与"先微基准后业务"相关的顺序——压测顺序：先微基准（延迟型 + 带宽型）验证硬件假设——再业务压测验证收益穿透。不要先业务——业务结果复杂无法定位是哪类改善。所以"先微基准后业务"是压测顺序——先验证假设后验证穿透。**"先微基准后业务"是压测顺序先验证假设后验证穿透**——这是选对问题类型的"压测顺序"，先微后业务。

### 5.3 延迟型测试应该如何设计

若目标是验证本地性、Row Buffer 友好度、随机访问代价，延迟型测试需要注意：

1. 工作集必须明显大于 LLC。
2. 访问模式要尽量形成真实依赖，避免被乱序和预取过度隐藏。
3. 线程数要和业务模型一致，单线程与多线程结果意义不同。
4. 必须控制 CPU 绑定与内存绑定，明确本地 / 远端条件。

这类测试更适合观察：

- 平均 load latency；
- P95 / P99；
- IPC；
- backend memory bound。

延迟型测试应该如何设计还有一个与"pointer chasing"相关的工具——"pointer chasing"是延迟型典型工具——链表节点随机分布，每个节点存下一节点指针——访问模式随机（无法预取）——测真实 load latency。lmbench 的 `lat_mem_rd` 是经典实现。所以"pointer chasing"是延迟型典型——测真实 load latency。**"pointer chasing"是延迟型典型测真实 load latency**——这是延迟型测试的"pointer chasing"，测真实延迟。

延迟型测试应该如何设计还有一个与"避免预取"相关的注意——延迟型测试要"避免预取"——如果访问模式可预取（顺序），硬件预取器提前取数据——测不到真实延迟（预取隐藏延迟）。pointer chasing 用随机链表避免预取——测真实延迟。所以"避免预取"是延迟型测试的注意——随机访问避免预取。**"避免预取"是延迟型测试注意随机访问避免预取**——这是延迟型测试的"预取注意"，随机避免。

### 5.4 带宽型测试应该如何设计

如果目标是验证交错或通道利用率，就应该使用更偏流式的测试：

- `STREAM`；
- 大数组 copy / triad；
- 向量化扫描。

它们的设计要点是：

1. 数据足够大，能持续出 LLC。
2. 线程数足够多，能把带宽压起来。
3. 分别测试单节点、本地绑定、全局交错等策略。
4. 用 `perf` 或平台工具辅助确认 IMC 活动。

带宽型测试应该如何设计还有一个与"STREAM Triad"相关的经典——STREAM Triad 是带宽型经典——`a[i] = b[i] + scalar * c[i]`——连续访问 + 计算——测持续带宽。Triad 比 Copy/Add/Scale 更接近真实业务（读 + 写 + 计算）。所以"STREAM Triad"是带宽型经典——测持续带宽。**"STREAM Triad"是带宽型经典测持续带宽**——这是带宽型测试的"STREAM Triad"，经典持续带宽。

带宽型测试应该如何设计还有一个与"IMC 流量确认"相关的验证——带宽型测试要用 `perf` 确认 IMC 流量——`perf stat -e uncore_imc/cas_count.read/,uncore_imc/cas_count.write/`——看 IMC 实际流量。确认带宽是否真打到 IMC（而非 cache 命中）。所以"IMC 流量确认"是带宽型测试的验证——确认打到 IMC。**"IMC 流量确认"是带宽型验证确认打到 IMC**——这是带宽型测试的"IMC 确认"，确认打到 IMC。

### 5.5 业务型压测为什么必须保留

微基准再漂亮，也不等于业务一定改善。

因为真实业务还包含：

- 锁；
- GC；
- I/O；
- 网络；
- 数据结构和对象模型；
- 热点分布变化。

所以最稳妥的做法是：

先用微基准验证硬件假设。

再用业务压测验证收益能否穿透到最终指标。

业务型压测为什么必须保留还有一个与"收益穿透"相关的核心——"收益穿透"是业务压测的核心——微基准显示改善（譬如带宽 +20%）——但业务指标（QPS/延迟）是否改善？如果微基准改善但业务不改善——收益未穿透——调优对业务无感。所以"收益穿透"是业务压测核心——验证穿透。**"收益穿透"是业务压测核心验证穿透**——这是业务压测的"穿透核心"，验证穿透。

业务型压测为什么必须保留还有一个与"锁/GC/IO 干扰"相关的复杂——业务压测有"锁/GC/IO 干扰"——这些因素可能掩盖内存调优收益。譬如内存调优改善 10% 但锁瓶颈占 50%——业务整体只改善 5%（锁瓶颈掩盖）。所以"锁/GC/IO 干扰"是业务压测的复杂——可能掩盖收益。**"锁/GC/IO 干扰"是业务压测复杂可能掩盖收益**——这是业务压测的"干扰复杂"，可能掩盖。

### 5.6 一个完整实验矩阵应该包含哪些维度

如果你要验证“绑定、交错、页大小”三类动作，最小可用实验矩阵至少应包含：

1. CPU 绑定：不绑 / 本地绑 / 跨节点。
2. 内存策略：默认 / preferred / membind / interleave。
3. 页大小：4KB / THP / 显式 HugePage。
4. 并发度：单线程 / 中等并发 / 高并发。
5. 工作集：小于 LLC / 大于 LLC 但小于单节点 / 跨节点大工作集。

没有这类矩阵，你很容易只在一个角落看到局部最优，然后把它错当全局最优。

一个完整实验矩阵应该包含哪些维度还有一个与"矩阵爆炸"相关的挑战——完整矩阵维度多（5 维）→ 组合爆炸（譬如 3×4×3×3×3=324 组合）。实际不可能跑全部——要"降维"：固定不重要的维度（譬如页大小固定 4KB），只变重要维度。所以"矩阵爆炸"是挑战——要降维选重要维度。**"矩阵爆炸"是挑战要降维选重要维度**——这是实验矩阵的"爆炸挑战"，降维选重要。

一个完整实验矩阵应该包含哪些维度还有一个与"基线对照"相关的必须——每类实验要有"基线对照"——默认配置（不绑/默认页/默认策略）作为基线——其他配置和基线对比。没有基线无法判断"改善多少"。所以"基线对照"是实验矩阵的必须——每类有基线。**"基线对照"是实验矩阵必须每类有基线**——这是实验矩阵的"基线必须"，每类有基线。

### 5.7 为什么要同时记录系统指标和业务指标

只记录 QPS 或耗时是不够的。

你还至少要同步记录：

- `perf stat` 核心事件；
- `numastat -p`；
- CPU 亲和性；
- 内存节点分布；
- p50 / p95 / p99；

收益到底来自哪里。

## 第 6 章 把策略映射回具体 workload：不要让所有系统吃同一副药

### 6.1 在线低延迟服务：优先本地性，谨慎交错

对在线服务而言，通常更应优先：

1. 让线程与内存位于同一节点。
2. 避免无谓远端访问。
3. 观察 P99，而不是只看平均吞吐。
4. 慎用会制造后台抖动的自动内存整理动作。

所以这类服务更常见的策略是：

- 绑定优先；
- 交错保守；
- 大页按 TLB 证据决定；
- 压测重点看长尾。

在线低延迟服务优先本地性谨慎交错还有一个与"THP 慎用"相关的注意——在线低延迟服务对 THP 要慎用——THP compaction 可能引发 P99 抖动。如果要用大页——用显式 HugePage（无 compaction）非 THP。所以"THP 慎用"是在线服务的注意——用显式 HugePage 非 THP。**"THP 慎用"是在线服务注意用显式 HugePage 非 THP**——这是在线服务的"THP 注意"，用显式非 THP。

在线低延迟服务优先本地性谨慎交错还有一个与"网卡 NUMA 一起绑"相关的扩展——在线网络密集型服务要"CPU + 内存 + 网卡"一起绑——避免网络包处理跨节点。譬如 `ethtool -L` 绑网卡队列到 node0，numactl 绑 CPU/内存到 node0。所以"网卡 NUMA 一起绑"是在线服务的扩展——三绑一起。**"网卡 NUMA 一起绑"是在线服务扩展三绑一起**——这是在线服务的"网卡扩展"，三绑一起。

### 6.2 分析型 / 批处理任务：优先总供给，允许适度远端

对大扫描、大 Join、大向量处理而言，更重要的是：

- 总带宽；
- 节点并行供给；
- 大工作集吞吐。

所以这类任务更可能受益于：

- 交错；
- 多线程铺满多个节点；
- 大页降低 TLB 压力；
- 延迟局部变差但吞吐整体提高。

分析型批处理任务优先总供给允许适度远端还有一个与"Spark/YARN"相关的典型——Spark/YARN 大数据处理是分析型典型——大工作集（TB 级）、多线程、带宽型。这些场景 `--interleave=all` + 大页 + 多线程铺满多节点——显著提吞吐。所以"Spark/YARN"是分析型典型——交错 + 大页受益。**"Spark/YARN"是分析型典型交错 + 大页受益**——这是分析型任务的"Spark 典型"，交错大页受益。

分析型批处理任务优先总供给允许适度远端还有一个与"THP 适合"相关的对比——分析型任务对 THP 适合——批处理对 compaction 抖动不敏感（吞吐优先非延迟优先）——THP 的自动化方便。所以"THP 适合分析型"——批处理不敏感抖动。**"THP 适合分析型"批处理不敏感抖动**——这是分析型任务的"THP 适合"，不敏感抖动。

### 6.3 大型 JVM 服务：绑定、页大小、GC 观测要一起看

JVM 场景里很少有单一杠杆能解决所有问题。

因为你同时面对：

- 堆分配；
- GC 扫描；
- TLAB / 对象布局；
- 本地 / 远端内存分配；
- 可能的 THP / HugePage 影响。

因此 JVM 调优更适合：

1. 先确认 NUMA 分布。
2. 再评估大页对 TLB 和 GC 的影响。
3. 最后通过应用尾延迟与 `perf` 一起验证。

大型 JVM 服务绑定页大小 GC 观测要一起看还有一个与"JVM NUMA"相关的特性——JVM 有"NUMA 感知"——`-XX:+UseNUMA` 让 JVM 自动按 NUMA 节点分配堆——类似自动绑定。但 JVM NUMA 不如手动 numactl 精细——复杂场景仍需手动绑。所以"JVM NUMA"是自动绑定——不如手动精细。**"JVM NUMA"是自动绑定不如手动精细**——这是 JVM 服务的"NUMA 特性"，自动不如手动。

大型 JVM 服务绑定页大小 GC 观测要一起看还有一个与"GC 扫描带宽"相关的瓶颈——GC 扫描堆时是"带宽型"——扫描大堆需高带宽。如果堆跨节点（交错）——GC 扫描带宽高（多节点供给）——GC 快。所以"GC 扫描带宽"是 JVM 交错的一个收益——GC 快。**"GC 扫描带宽"是 JVM 交错收益 GC 快**——这是 JVM 服务的"GC 带宽"，交错 GC 快。

### 6.4 Redis / 缓存类服务：容量够不够和本地性一样重要

这类服务经常面临一个两难：

- 单节点本地性最好；
- 但数据集一旦超出单节点容量，就必须跨节点。

所以它们往往需要在：

- 分片；
- 实例拆分；
- 单实例绑定；
- 节点级部署规划。

之间做架构取舍，而不是只靠 `numactl` 一条命令解决。

Redis 缓存类服务容量够不够和本地性一样重要还有一个与"分片部署"相关的架构——Redis 超单节点容量时——用"分片部署"——每个分片一个 Redis 实例绑一个节点——分片内本地性 + 分片间扩容。这是"架构级 NUMA 优化"——比 numactl 更上层。所以"分片部署"是 Redis 容量超单节点的架构——架构级优化。**"分片部署"是 Redis 容量超单节点架构架构级优化**——这是 Redis 服务的"分片架构"，架构级优化。

Redis 缓存类服务容量够不够和本地性一样重要还有一个与"单实例绑核"相关的实践——Redis 单实例绑核是常见实践——`numactl --cpunodebind=0 --membind=0 redis-server`——绑在 node0——本地性最优。但要注意"绑核不要太细"——绑到单核可能瓶颈（Redis 单线程）——绑到 node0 的多核更稳。所以"单实例绑核"是 Redis 实践——绑节点非单核。**"单实例绑核"是 Redis 实践绑节点非单核**——这是 Redis 服务的"绑核实践"，绑节点非单核。

### 6.5 一个非常现实的结论

内存调优不是“找到一条最强命令”。

它更像是：

针对不同 workload，在本地性、总供给、页表成本、资源弹性之间做权衡。

这就是为什么策略必须和业务形态绑在一起看。

一个非常现实的结论还有一个与"权衡而非最优"相关的认知——内存调优是"权衡而非最优"——每个动作有收益有代价——交错提带宽降延迟，绑定提本地性降弹性，大页降 TLB 增碎片。没有"无代价最优"——只有"权衡后合适"。所以"权衡而非最优"是内存调优的认知——无无代价最优。**"权衡而非最优"是内存调优认知无无代价最优**——这是现实结论的"权衡认知"，无无代价最优。

一个非常现实的结论还有一个与"业务形态绑定"相关的纪律——策略必须和"业务形态绑定"——在线低延迟（绑定优先）、分析型批处理（交错优先）、JVM（绑定+大页+GC 一起）、Redis（分片+绑核）。不同形态不同策略——不套同一模板。所以"业务形态绑定"是调优纪律——不同形态不同策略。**"业务形态绑定"是调优纪律不同形态不同策略**——这是现实结论的"形态纪律"，不同形态不同策略。

## 第 7 章 边界、反例与真正成熟的调优心态

### 7.1 不要把所有收益都归功于你想证明的那个动作

比如你做了 `membind`，QPS 提升了。

这不自动说明“本地内存访问改善”就是唯一原因。

还可能同时发生了：

- CPU 亲和性更稳定；
- 调度迁移更少；
- 某些线程碰巧避开了争用；
- 页面重新分配改变了热度分布。

所以调优验证一定要看辅助观测。

不要把所有收益都归功于你想证明的那个动作还有一个与"确认偏差"相关的心理——"确认偏差"是调优心理陷阱——你想证明"membind 有效"→ QPS 升后归功于 membind → 忽略其他原因（调度/争用/热度）。要克服确认偏差——看辅助观测找真实原因。所以"确认偏差"是调优心理陷阱——看辅助观测克服。**"确认偏差"是调优心理陷阱看辅助观测克服**——这是收益归功的"确认偏差"，心理陷阱。

不要把所有收益都归功于你想证明的那个动作还有一个与"多因素分离"相关的方法——"多因素分离"是验证方法——逐个变因素（譬如只变 membind 不变 CPU 绑定）→ 看每个因素的独立贡献。多因素同时变无法归因——要分离。所以"多因素分离"是验证方法——逐个变因素看独立贡献。**"多因素分离"是验证方法逐个变因素看独立贡献**——这是收益归功的"分离方法"，逐个变因素。

### 7.2 不要用单一 benchmark 决定长期生产策略

单一 benchmark 往往只覆盖一个角度。

你看到它变快了，只能说明那个角度的假设成立。

生产策略要看更完整的工作集、峰值负载、故障恢复、内存压力、运维复杂度。

不要用单一 benchmark 决定长期生产策略还有一个与"峰值 vs 平均"相关的维度——单一 benchmark 常测"平均负载"——但生产要考虑"峰值负载"——峰值时内存压力、NUMA 拥挤可能不同。调优在平均下好——峰值下可能差（譬如 membind 在峰值时单节点 OOM）。所以"峰值 vs 平均"是生产策略的维度——要测峰值。**"峰值 vs 平均"是生产策略维度要测峰值**——这是单一 benchmark 的"峰值维度"，要测峰值。

不要用单一 benchmark 决定长期生产策略还有一个与"故障恢复"相关的另一维度——生产策略要考虑"故障恢复"——譬如某节点故障时，membind 到该节点的服务能否迁移？membind 刚性可能阻碍故障恢复。所以"故障恢复"是生产策略的维度——刚性绑定可能阻碍恢复。**"故障恢复"是生产策略维度刚性绑定可能阻碍恢复**——这是单一 benchmark 的"故障维度"，刚性阻碍恢复。

### 7.3 不要把 THP 的开与关当成宗教

THP 既不是永远该开，也不是永远该关。

它是否合适，取决于：

- 工作集；
- 碎片程度；
- 延迟容忍度；
- 是否有显式 HugePage 替代；
- 业务生命周期。

任何绝对化答案都不可靠。

不要把 THP 的开与关当成宗教还有一个与"折中方案"相关的实践——THP 的"折中方案"：`madvise` 模式——只对显式标记的内存区域用 THP（`madvise(MADV_HUGEPAGE)`），其他区域不用。这样关键区域（譬如 JVM 堆）用 THP，其他区域不用——折中。所以"madvise 折中"是 THP 的实践——选择性用 THP。**"madvise 折中"是 THP 实践选择性用 THP**——这是 THP 宗教的"折中方案"，选择性用。

不要把 THP 的开与关当成宗教还有一个与"监控 compaction"相关的运维——开 THP 后要"监控 compaction 事件"——`/proc/vmstat` 的 `compact_stall` 计数——如果 compact_stall 上升——说明 compaction 在引发停顿——考虑关 THP 或用 madvise。所以"监控 compaction"是 THP 运维——看 compact_stall。**"监控 compaction"是 THP 运维看 compact_stall**——这是 THP 宗教的"监控运维"，看 compact_stall。

### 7.4 不要忽略容量与稳定性约束

某些策略在实验里很好看，但上线后不现实。

例如：

- 过于严格的 `membind` 导致单节点 OOM 风险上升；
- 超大页预留影响其他业务；
- 极致绑定让弹性扩缩容困难；
- 激进交错让在线长尾不可接受。

真正成熟的调优，不是只追求峰值分数。

而是追求在约束内的最优可运营状态。

不要忽略容量与稳定性约束还有一个与"可运营"相关的目标——调优的最终目标是"可运营"——不只峰值分数——要稳定、可运维、可故障恢复。实验里好看的策略如果不可运营（譬如 membind 刚性阻碍故障恢复）——不采用。所以"可运营"是调优最终目标——不只峰值。**"可运营"是调优最终目标不只峰值**——这是容量稳定性的"可运营目标"，不只峰值。

不要忽略容量与稳定性约束还有一个与"灰度上线"相关的实践——调优策略要"灰度上线"——先小流量验证——观察 P99/稳定性/故障恢复——再全量。不要全量直接上——避免意外。所以"灰度上线"是调优实践——先小流量后全量。**"灰度上线"是调优实践先小流量后全量**——这是容量稳定性的"灰度实践"，先小后全。

### 7.5 一个应该长期带着的判断句

> [!note] 设计哲学
> 交错解决供给，绑定解决路径，页大小解决翻译，压测负责验证。凡是一个动作号称“同时解决所有内存问题”，基本都不值得相信。

一个应该长期带着的判断句还有一个与"四动作各司其职"相关的核心——判断句的核心是"四动作各司其职"——交错（供给）、绑定（路径）、页大小（翻译）、压测（验证）——每个动作解决不同问题——不混。所以"四动作各司其职"是判断句核心——不混。**"四动作各司其职"是判断句核心不混**——这是判断句的"各司其职核心"，不混。

一个应该长期带着的判断句还有一个与"万能动作警惕"相关的纪律——判断句的纪律是"万能动作警惕"——凡号称"同时解决所有内存问题"的动作——基本不可信。内存问题分四类——一个动作不可能同时解决四类——警惕万能。所以"万能动作警惕"是判断句纪律——警惕万能。**"万能动作警惕"是判断句纪律警惕万能**——这是判断句的"万能警惕"，警惕万能动作。

### 8.2 四条最后必须带走的结论

1. 当问题是带宽供给不足时，优先考虑交错与节点级并行供给。
