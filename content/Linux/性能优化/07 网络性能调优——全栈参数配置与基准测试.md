# 07 网络性能调优——全栈参数配置与基准测试

**摘要：**
网络协议栈专栏已经从内核角度深入剖析了 TCP/IP 实现、拥塞控制、缓冲区机制、epoll、零拷贝和容器网络。本篇是**横向整合**：将那些散落在各篇的调优参数汇聚为一份**生产可用的 sysctl 调优清单**，并给出每个参数的"为什么调"而不仅仅是"调成什么"。同时，介绍如何用 `iperf3` 和 `netperf` 科学地进行网络基准测试——测试不是为了拿到一个漂亮的数字，而是为了**量化调优前后的对比**，验证每一步调整的实际效果。最后给出三个典型场景（高吞吐量数据传输、低延迟 RPC、高并发连接）的完整调优配置，以及如何用 `ss`、`ethtool`、`netstat` 验证调优是否真正生效。

## 第 1 章 网络调优的分层模型与认知框架

### 1.1 从哪里下手：网络栈的四个调优层次

网络性能问题根据所在层次不同，调优手段截然不同。一个完整的网络调优要覆盖从网卡硬件到应用协议的四个层次——任何一层的瓶颈都会让其他层的优化白费。这是网络调优的"木桶效应"——最短的那块板决定整体性能。

```
Layer 4：应用协议层
  → 连接池复用（减少 TIME_WAIT）
  → 请求批量合并（减少小包 RTT 代价）
  → 协议选择（HTTP/1.1 vs HTTP/2 vs gRPC）

Layer 3：Socket / TCP 层
  → 缓冲区大小（tcp_rmem / tcp_wmem）
  → 拥塞控制算法（cubic → bbr）
  → 连接队列（somaxconn / tcp_max_syn_backlog）
  → TIME_WAIT 回收（tcp_tw_reuse）

Layer 2：内核网络栈层
  → 软中断（netdev_budget）
  → 接收路径（GRO / RSS / RPS / RFS）
  → 发送路径（GSO / TSO / GSO size）

Layer 1：NIC / 驱动层
  → Ring Buffer 大小（ethtool -G）
  → 队列数量（ethtool -L）
  → 中断合并（ethtool -C）
  → 网卡特性（TSO/LRO/checksum offload）
```

调优应**从 Layer 1 开始往上**：NIC 层的丢包会让上层所有调优都白费（如果 Ring Buffer 溢出，数据包在驱动层就丢弃了，TCP 再怎么调也没用）。这个"从底向上"的顺序有一个与"问题定位"相关的逻辑——底层的丢包是"硬丢包"（无重传，数据直接消失），上层的"重传"是"软重传"（TCP 层有重传机制）。硬丢包的影响比软重传大——硬丢包让应用看到"无响应"或"超时"，软重传让应用看到"延迟增加"。所以调优要先消除硬丢包（Layer 1），再优化软重传（Layer 3）。**"从底向上"调优是"先消除硬丢包，再优化软重传"**——这是网络调优的"层次优先级"原则。

从底向上调优还有一个与"成本"相关的考量——底层的调优"成本最低收益最大"。譬如 Ring Buffer 调大（一个 `ethtool -G` 命令）能消除硬丢包，让上层所有优化有意义——成本几秒，收益巨大。而上层调优（譬如 TCP 缓冲区、拥塞控制）要计算 BDP、选算法、测差分——成本高，收益不确定（如果底层丢包没解决，上层调优白费）。所以"从底向上"不只是"优先级"，还是"成本收益比"——底层先做，成本低收益大；上层后做，成本高收益精细。**"从底向上"调优是"成本收益比最优"的顺序**——这是网络调优的"经济学"考量。

从底向上调优还有一个与"诊断顺序"相关的实践——遇到网络性能问题，诊断也要"从底向上"。先用 `ethtool -S` 看 NIC 层丢包，再看 `/proc/net/softnet_stat` 看软中断，再看 `ss -ti` 看 TCP 状态，最后看应用。如果一上来就看应用（Layer 4），可能浪费大量时间——而问题在 Layer 1（Ring Buffer 丢包）。所以"从底向上"不只是调优顺序，也是诊断顺序——先排除底层，再查上层。**"从底向上"也是"诊断顺序"**——这是网络问题排查的"层次化诊断"方法，避免"在非瓶颈层浪费时间"。

### 1.2 网络调优的认知框架

网络调优的认知框架可以总结为一个核心命题——**"网络性能是多层复合函数"**。同一块 10Gbps 网卡，经过 Ring Buffer（Layer 1）、软中断（Layer 2）、TCP 缓冲区（Layer 3）、应用协议（Layer 4）的层层处理，最终性能可能只有 5Gbps——每一层都有"折损"。调优的本质是"减少每层的折损"——Ring Buffer 不丢包（Layer 1 无折损）、软中断处理跟上（Layer 2 无折损）、TCP 缓冲区够大（Layer 3 无折损）、应用协议高效（Layer 4 无折损）。**"网络性能 = 网卡带宽 × 各层折损系数"**——理解这个复合函数，才能定位"哪层折损最大"，针对性调优。

网络调优的复合函数模型还有一个与"瓶颈转移"相关的动态性——调优一层后，瓶颈可能转移到另一层。譬如调大 Ring Buffer 消除了 Layer 1 丢包，但 Layer 2 软中断处理跟不上成为新瓶颈；调大软中断预算解决了 Layer 2，但 Layer 3 TCP 缓冲区不够成为新瓶颈。所以网络调优是"逐层消除瓶颈"的迭代过程——调一层，测一次，找新瓶颈，再调。**网络调优是"逐层消除瓶颈"的迭代过程**——这是网络调优的"动态性"，不能"一次调完所有层"。

网络调优的迭代过程还有一个与"回归测试"相关的纪律——每次调优后，要"回归测试"前面的调优是否仍有效。譬如调了 Layer 3（TCP 缓冲区）后，要重测 Layer 1（Ring Buffer 丢包）是否仍无丢包——因为 Layer 3 调优可能"增加了流量"，让 Layer 1 重新出现丢包。所以调优是"螺旋上升"——每调一层，回归验证前面的层。**调优要"螺旋上升 + 回归验证"**——这是网络调优的"迭代纪律"，防止"调新层破坏旧层"。

### 1.3 基准：调优前先测量

```bash
# 在调优任何参数之前，先记录基准性能，后续调优效果对比的参考
# 使用 iperf3 测量 TCP 吞吐量（client → server，60 秒）
iperf3 -c <server_ip> -t 60 -P 4 -w 256K > baseline_throughput.txt

# 使用 netperf 测量 TCP_RR（请求-响应）延迟（代表 RPC 场景）
netperf -H <server_ip> -t TCP_RR -l 60 -- -r 100,100 > baseline_latency.txt

# 记录当前关键 sysctl 参数
sysctl net.core.somaxconn net.ipv4.tcp_rmem net.ipv4.tcp_wmem \
       net.ipv4.tcp_congestion_control net.core.netdev_budget > baseline_params.txt

# 记录网卡当前状态
ethtool -S eth0 | grep -E "rx_missed|drop|error" > baseline_nic.txt
ethtool eth0 | grep -E "Speed|Duplex" >> baseline_nic.txt
```

基准测试有一个与"科学方法"相关的原则——每次只调一个参数，测一次，对比效果。如果一次调多个参数，无法知道"哪个参数起作用"——这是"控制变量法"在网络调优的应用。基准测试的输出是"调优前后的差分"——譬如"BBR 让吞吐量从 5Gbps 提升到 8Gbps"，而非"BBR 后吞吐量 8Gbps"（不知道原来多少）。**"每次只调一个参数 + 差分对比"是网络调优的科学方法**——这是基准测试的方法论核心。

基准测试还有一个与"测试时长"相关的实践——测试时长要足够长（至少 30 秒，推荐 60 秒），让 TCP 的"慢启动"和"拥塞窗口爬升"完成。如果只测 5 秒，TCP 还在慢启动阶段，窗口没爬满，测不到"稳态吞吐量"。60 秒的测试让 TCP 充分爬升到稳态——这是"稳态测量"的正确时长。但也不能太长（譬如 1 小时）——浪费测试时间，且可能受"网络波动"干扰。**基准测试时长 30-60 秒是"稳态测量"的甜点**——这是基准测试的"时长原则"。

基准测试还有一个与"环境一致性"相关的纪律——调优前后的测试要在"相同环境"下做——相同时间（避免网络波动）、相同负载（避免其他应用干扰）、相同测试参数（`iperf3` 的 `-t`/`-P` 一致）。如果环境不一致，差分对比无意义——譬如调优前白天测（网络忙），调优后深夜测（网络闲），"提升"可能是环境差异而非调优效果。**基准测试要"环境一致"**——这是基准测试的"控制变量"纪律，确保差分反映调优效果而非环境噪声。

## 第 2 章 NIC 层调优：消除驱动层丢包

### 2.1 Ring Buffer：第一道防线

**什么是 Ring Buffer**：在 [[网络协议栈与IO/07 Linux 网络包的完整收发路径——软中断、NAPI 与 XDP]] 中详细介绍过，Ring Buffer 是网卡驱动和内核之间的 DMA 环形缓冲区。每当网卡收到数据包，DMA 将其写入 Ring Buffer；当内核软中断（NAPI）处理速度跟不上网卡收包速度时，Ring Buffer 填满，后续包被**硬件直接丢弃**（`rx_missed_errors` 计数增加）。

**为什么 Ring Buffer 满了会丢包而不是等待**：Ring Buffer 是有限的环形队列，网卡硬件写满后无法等待（等待会阻塞 DMA，影响后续硬件操作），只能丢弃新包。这是最底层的丢包，发生在 TCP 栈甚至驱动层之前，完全没有重传机制。

```bash
# 检查 Ring Buffer 是否在丢包
ethtool -S eth0 | grep -E "rx_missed|rx_fifo|drop"
# rx_missed_errors: 1234  ← ！！持续增加说明 Ring Buffer 溢出

# 查看当前 Ring Buffer 大小
ethtool -g eth0
# Ring parameters for eth0:
# Pre-set maximums:
# RX:             4096
# TX:             4096
# Current hardware settings:
# RX:             512   ← 当前只有 512，但设备最大支持 4096
# TX:             512

# 增大 Ring Buffer（立即生效，重启失效）
ethtool -G eth0 rx 4096 tx 4096

# 永久配置（通过 NetworkManager 或 /etc/network/interfaces 的 post-up）
# 对于 systemd-networkd：
cat > /etc/systemd/network/10-eth0.link << 'EOF'
[Match]
OriginalName=eth0

[Link]
RxBufferSize=4096
TxBufferSize=4096
EOF
```

> [!info] Ring Buffer 大小的权衡
> Ring Buffer 越大，越不容易因为软中断处理慢而丢包；但每个 slot 预分配了 DMA 内存（约 2KB/slot），4096 个 slot = 8MB 专用内存。对于内存紧张的场景需要权衡。通常先增大 Ring Buffer 解决丢包，再排查软中断处理瓶颈的根本原因。

Ring Buffer 的丢包有一个与"瞬时突发"相关的场景——网络流量不是均匀的，有"瞬时突发"（譬如微秒级 burst）。Ring Buffer 的作用是"吸收突发"——突发时包暂存 Ring Buffer，软中断慢慢处理。如果 Ring Buffer 太小（512），一个突发就溢出；调大（4096）能吸收更大的突发。但 Ring Buffer 调大不能"根治"丢包——如果软中断长期处理不过来，再大的 Ring Buffer 也会满。**Ring Buffer 调大是"吸收突发"，不是"根治处理瓶颈"**——这是 Ring Buffer 调优的"治标 vs 治本"区分。

Ring Buffer 的治本有一个与"软中断"相关的方向——如果软中断长期处理不过来，要"加速软中断"而非"无限调大 Ring Buffer"。加速软中断的方法：多队列网卡（多核并行处理）、RPS/RFS（软件分发到多核）、调大 `netdev_budget`（每次软中断处理更多包）。这些是"治本"——提高软中断的处理能力，而非"暂存更多包"。**"加速软中断"是 Ring Buffer 丢包的治本之道**——这是 Ring Buffer 调优的"治本方向"，要从"提高处理能力"入手。

Ring Buffer 的诊断还有一个与"rx_missed_errors vs rx_fifo_errors"相关的区分——`rx_missed_errors` 是"Ring Buffer 满丢包"（软件计数），`rx_fifo_errors` 是"网卡 FIFO 缓存满丢包"（硬件计数）。如果 `rx_missed` 增加，调大 Ring Buffer 有效；如果 `rx_fifo` 增加，调大 Ring Buffer 无效（FIFO 是网卡硬件缓存，Ring Buffer 调大不影响 FIFO）——要换更高端网卡（更大 FIFO）。所以诊断要区分"软件丢包 vs 硬件丢包"——对症下药。**`rx_missed` 调 Ring Buffer，`rx_fifo` 换网卡**——这是 Ring Buffer 诊断的"软硬件区分"。

### 2.2 中断合并（Interrupt Coalescing）

**什么是中断合并**：网卡默认每收到一个数据包就触发一次硬件中断。在 10Gbps 网卡满速收包时，每秒可能触发 100 万次中断，中断处理本身就消耗大量 CPU。中断合并（Interrupt Coalescing）让网卡在**收到 N 个包或等待 T 微秒**后才触发一次中断，大幅降低中断频率：

```bash
# 查看当前中断合并配置
ethtool -c eth0
# Coalesce parameters for eth0:
# rx-usecs: 50       ← 距离上次中断 50µs 后触发（或 rx-frames 个包）
# rx-frames: 32      ← 或累积 32 个包后触发
# tx-usecs: 50
# tx-frames: 32

# 高吞吐场景：增大合并阈值（降低中断频率，提升吞吐量，增加延迟）
ethtool -C eth0 rx-usecs 100 rx-frames 64
# 效果：中断频率降低，每次处理更多包，吞吐量提升 10-20%
# 代价：最坏情况延迟增加 100µs（一个中断周期）

# 低延迟场景：减小合并阈值（或禁用）
ethtool -C eth0 rx-usecs 1 rx-frames 1
# 效果：几乎每包一个中断，最低延迟
# 代价：中断频率高，CPU 开销大

# 自适应模式（让驱动自动选择合并策略）
ethtool -C eth0 adaptive-rx on adaptive-tx on
# 驱动根据当前流量动态调整合并参数（推荐）
```

中断合并有一个与"吞吐 vs 延迟"相关的根本权衡——合并阈值大，中断少，吞吐高，但延迟高（最坏等一个中断周期）；合并阈值小，中断多，延迟低，但吞吐低（中断开销大）。这个权衡是"吞吐延迟反比关系"在网络层的体现——高吞吐必然牺牲延迟，低延迟必然牺牲吞吐。**中断合并是"吞吐 vs 延迟"的权衡旋钮**——这是网络调优的核心权衡之一，要根据应用场景选择。

中断合并的权衡还有一个与"自适应模式"相关的解法——`adaptive-rx on` 让驱动根据流量动态调整合并参数——流量大时自动增大合并（高吞吐），流量小时自动减小合并（低延迟）。这比"固定值"更智能——固定值要么偏吞吐（延迟高），要么偏延迟（吞吐低），自适应能"两全"。所以生产环境推荐开自适应——除非有极端的"纯吞吐"或"纯延迟"需求，才用固定值。**自适应中断合并是"吞吐延迟两全"的解法**——这是中断合并调优的"自适应推荐"。

中断合并还有一个与"busy_poll"相关的进阶——`SO_BUSY_POLL` 让应用线程"主动轮询网卡"（而非等中断），进一步消除"中断延迟"。这是"用 CPU 换延迟"的极端优化——应用线程花 CPU 轮询，包一到就处理（不等中断触发）。适用于"超低延迟"场景（高频交易），但 CPU 开销大（一个核全占用）。**`SO_BUSY_POLL` 是"用 CPU 换延迟"的极端优化**——这是中断合并的"进阶"，只适合"超低延迟 + CPU 充裕"的场景。

### 2.3 网卡多队列与 IRQ 亲和性

详细内容在 [[网络协议栈与IO/08 高性能网络编程——io_uring 网络、SO_REUSEPORT 与多队列 NIC]] 中已深入讲解。这里给出快速配置命令：

```bash
# 1. 确认网卡队列数
ethtool -l eth0
# Channel parameters for eth0:
# Combined:  8  ← 当前 8 个队列（Combined = RX+TX 合并队列）

# 2. 设置队列数等于 CPU 数
ethtool -L eth0 combined $(nproc)

# 3. 设置 IRQ 亲和性（网卡 CPU 0-7 各绑定一个队列）
# 使用 set_irq_affinity 脚本（各网卡驱动通常提供）
/usr/local/sbin/set_irq_affinity local eth0
# 或手动：
for i in $(seq 0 7); do
    IRQ=$(cat /proc/interrupts | grep eth0-$i | awk '{print $1}' | tr -d ':')
    echo $((1 << i)) > /proc/irq/$IRQ/smp_affinity
done

# 4. 启用 RPS（软件 RSS，用于无多队列网卡）
echo ff > /sys/class/net/eth0/queues/rx-0/rps_cpus  # 所有 CPU 处理
```

网卡多队列有一个与"CPU 核数"相关的扩展性原理——单队列网卡的所有包由一个 CPU 处理（中断绑在一个核），这个核成为瓶颈。多队列网卡让每个队列的中断绑在不同核——N 个队列用 N 个核并行处理——"核数倍"的扩展性。所以多队列网卡是"网络处理的并行化"——与多核 CPU 的并行计算同理。**多队列网卡是"网络处理的并行化"**——这是高带宽场景（10Gbps+）必须用多队列的原因，单队列扛不住。

多队列网卡还有一个与"IRQ 亲和性"相关的调优——每个队列的中断要绑在不同 CPU 核上，否则多个队列的中断挤在一个核，并行性失效。`set_irq_affinity` 脚本能把队列 N 的中断绑在 CPU N 上——N 个队列用 N 个核。如果不绑亲和性，中断可能都挤在一个核（默认亲和性可能是 CPU 0），多队列的并行性浪费。**多队列 + IRQ 亲和性是"并行化的完整配置"**——这是多队列网卡调优的"亲和性必须"。

多队列网卡还有一个与"RPS/RFS"相关的软件补充——RPS（Receive Packet Steering）是"软件版 RSS"，把"单队列网卡"的包分发到多核——无多队列网卡时用 RPS 补充。RFS（Receive Flow Steering）是 RPS 的"流亲和"版——把"同一流"的包分到同一核（提高 cache 命中）。所以"无多队列网卡"用 RPS/RFS 软件补充，"有多队列网卡"用 RSS 硬件分发——两者是"硬件 vs 软件"的并行化方案。**RPS/RFS 是"无多队列网卡"的软件并行化补充**——这是多队列调优的"软件备选"。

### 2.4 网卡 offload：TSO、GSO、GRO、LRO

网卡 offload 是"把内核的工作卸载到网卡硬件"——网卡硬件比 CPU 更擅长这些工作（专用电路，并行处理）。

```bash
# 查看当前 offload 配置
ethtool -k eth0
# Features for eth0:
# tcp-segmentation-offload: on      ← TSO（发送方向，大包分片卸载）
# generic-segmentation-offload: on  ← GSO（发送方向，软件版 TSO）
# generic-receive-offload: on       ← GRO（接收方向，小包合并卸载）
# large-receive-offload: off        ← LRO（接收方向，硬件版 GRO，可能破坏 IP 分片）

# 通常保持默认（开启 TSO/GSO/GRO，关闭 LRO）
# LRO 在某些场景会破坏 IP 分片和 TCP 校验，建议关闭
ethtool -K eth0 lro off
```

TSO（TCP Segmentation Offload）有一个与"发送路径"相关的优化——内核把"大段数据"（譬如 64KB）作为一个大包交给网卡，网卡硬件分片为多个 MSS（譬如 1460 字节）的 TCP 包。这减少了内核的"分片 CPU 开销"——如果不 offload，内核要自己分片 64KB 为 44 个 1460 字节包，每个包都要构造 TCP/IP 头。**TSO 让"内核发大包，网卡分小包"**——这是发送方向的 offload 优化，减少 CPU 开销。

GRO（Generic Receive Offload）是接收方向的对应——网卡把多个小包合并为一个大包交给内核，减少内核的"包处理次数"。譬如网卡收到 44 个 1460 字节包，GRO 合并为一个 64KB 大包交给内核——内核只处理一次（而非 44 次）。**GRO 让"网卡收小包合并大包，内核处理一次"**——这是接收方向的 offload 优化，减少 CPU 开销。

GRO 有一个与"流区分"相关的实现细节——GRO 合并包时要区分"不同流"——只有"同一 TCP 流"的包才能合并，不同流的包合并会破坏数据。所以 GRO 要解析 TCP/IP 头，识别流（五元组），同流的包合并。这个"流识别"在网卡硬件做（硬件 GRO）或内核软件做（软件 GRO）——硬件 GRO 性能更好（网卡专用电路），但某些网卡的硬件 GRO 有 bug（错误合并不同流），所以建议用软件 GRO（内核的 `generic-receive-offload`）。**GRO 要"流区分"，软件 GRO 更可靠**——这是 GRO 调优的"可靠性"考量。

网卡 offload 还有一个与"checksum offload"相关的优化——网卡硬件做"TCP/IP 校验和"计算与验证。如果不 offload，内核要 CPU 算校验和（每个包都要算，开销大）。offload 后网卡硬件算（专用电路，零 CPU 开销）。通常默认开启（`ethtool -k eth0 | grep checksum`），生产环境保持开启——除非网卡有 bug（某些老网卡硬件 checksum 有误）。**checksum offload 是"零 CPU 校验"**——这是网卡 offload 的"默认开启"项，减少 CPU 校验开销。

### 3.1 连接队列（解决高并发连接建立）

```bash
# 场景：服务启动后瞬间大量连接建立，出现 SYN 被丢弃或连接超时

# 1. accept 队列上限（somaxconn 和 listen backlog 取最小值）
sysctl -w net.core.somaxconn=65535
# 同时修改应用层的 listen backlog：listen(fd, 65535)

# 2. SYN 队列（半连接队列）上限
sysctl -w net.ipv4.tcp_max_syn_backlog=65535

# 3. SYN Cookie（防止 SYN Flood 打满 SYN 队列）
sysctl -w net.ipv4.tcp_syncookies=1

# 验证是否有 SYN 队列溢出
netstat -s | grep -i "syn\|overflow"
# 12345 SYNs to LISTEN sockets dropped    ← SYN 队列溢出
# 6789 times the listen queue overflowed  ← accept 队列溢出
```

连接队列有一个与"瞬时连接风暴"相关的场景——服务启动或客户端重连时，可能瞬间涌入大量 SYN。如果 SYN 队列（半连接队列）小，SYN 被丢弃——客户端看到"连接超时"。`tcp_max_syn_backlog` 控制半连接队列大小，`somaxconn` 控制 accept 队列（全连接队列）大小。两个队列都要调大——任一溢出都会丢连接。**连接队列调优是"防瞬时连接风暴"**——这是高并发服务启动时的常见问题，队列太小会"启动即丢连接"。

连接队列还有一个与"应用层 listen backlog"相关的配合——`somaxconn` 是内核上限，但应用 `listen(fd, backlog)` 的 `backlog` 也要调大——实际队列大小是 `min(somaxconn, backlog)`。如果应用 `listen(fd, 128)` 而内核 `somaxconn=65535`，实际队列只有 128——内核调了白费。所以调 `somaxconn` 的同时，应用层也要调 `listen` 的 backlog——两层都要调。**连接队列要"内核 somaxconn + 应用 backlog 双调"**——这是连接队列调优的"双层配合"。

连接队列还有一个与"SYN Cookie"相关的防护——`tcp_syncookies=1` 在 SYN 队列满时启用 SYN Cookie，不分配资源就响应 SYNACK——防 SYN Flood 攻击。SYN Cookie 的代价是"丢失部分 TCP 选项"（因为 Cookie 编码在序号中，没空间传选项）——譬如 TCP Timestamps、Window Scaling 可能丢失。所以 SYN Cookie 是"应急防护"而非"常态启用"——平时靠 `tcp_max_syn_backlog` 足够，SYN Flood 时 SYN Cookie 兜底。**SYN Cookie 是"SYN Flood 应急防护"**——这是连接队列的"安全兜底"，平时靠 backlog，攻击时靠 Cookie。

### 3.2 TCP 缓冲区（解决吞吐量低）

**为什么缓冲区会限制吞吐量**：TCP 的发送速率受限于发送窗口大小（`min(cwnd, rwnd)` × MSS / RTT）。如果缓冲区过小（默认最大 4MB），在高带宽高延迟链路（例如跨数据中心：1Gbps，RTT = 20ms）上，BDP（带宽延迟积）= 1Gbps × 20ms = 2.5 MB，超过默认缓冲区上限，吞吐量被硬性限制在约 200 Mbps，远低于链路容量。

```bash
# 查看当前 TCP 缓冲区配置（三元组：最小、默认、最大，单位字节）
sysctl net.ipv4.tcp_rmem  # 接收缓冲区
# net.ipv4.tcp_rmem = 4096    131072  6291456  ← 最大 6MB

sysctl net.ipv4.tcp_wmem  # 发送缓冲区
# net.ipv4.tcp_wmem = 4096    16384   4194304  ← 最大 4MB

# 计算 BDP 并设置合适的缓冲区（以 10Gbps，RTT=1ms 为例）
# BDP = 10Gbps × 1ms = 1.25 MB → 缓冲区需要 ≥ 2 × BDP = 2.5 MB（留余量）

# 高吞吐场景（10GbE，数据中心内）
sysctl -w net.ipv4.tcp_rmem="4096 131072 33554432"  # 最大 32MB
sysctl -w net.ipv4.tcp_wmem="4096 16384 33554432"   # 最大 32MB
sysctl -w net.core.rmem_max=33554432                 # socket 级别上限
sysctl -w net.core.wmem_max=33554432

# 高吞吐场景（跨 WAN，RTT=50ms，带宽=1Gbps）
# BDP = 1Gbps × 50ms = 6.25 MB → 缓冲区需要 ≥ 12 MB
sysctl -w net.ipv4.tcp_rmem="4096 131072 134217728"  # 最大 128MB
sysctl -w net.ipv4.tcp_wmem="4096 16384 134217728"
sysctl -w net.core.rmem_max=134217728
sysctl -w net.core.wmem_max=134217728

# 确保 Autotuning 开启（内核在范围内动态调整，不设置最大值等于固定值）
sysctl -w net.ipv4.tcp_moderate_rcvbuf=1  # 默认已开启
```

TCP 缓冲区有一个与"BDP"相关的核心公式——**BDP = 带宽 × RTT**。BDP 是"链路在 RTT 时间内能传输的数据量"——TCP 要"填满管道"（充分利用带宽），窗口大小至少等于 BDP。如果窗口小于 BDP，管道填不满，带宽浪费。譬如 10Gbps × 1ms = 1.25MB，窗口至少 1.25MB 才能填满；1Gbps × 50ms = 6.25MB，窗口至少 6.25MB。跨 WAN 的 BDP 大（RTT 大），需要大缓冲区；数据中心内 BDP 小（RTT 小），小缓冲区够。**TCP 缓冲区要"按 BDP 设置"**——这是缓冲区调优的"BDP 原则"。

TCP 缓冲区还有一个与"自动调优"相关的实践——`tcp_moderate_rcvbuf=1` 让内核根据"BDP 估计"动态调整接收缓冲区大小（在 `tcp_rmem` 的 min/max 范围内）。这比"固定值"更智能——内核能根据"实际 RTT 和带宽"动态调整，适应不同链路。所以调优时主要调 `tcp_rmem` 的"最大值"（给自动调优留空间），而非"默认值"——自动调优会根据需要扩展到最大值。**`tcp_moderate_rcvbuf` 是"自动调优接收缓冲区"**——这是缓冲区调优的"自动模式"，调"最大值"而非"默认值"。

TCP 缓冲区还有一个与"发送缓冲区"相关的区别——`tcp_rmem` 是接收缓冲区（对端发给我的数据缓存），`tcp_wmem` 是发送缓冲区（我发给对端的数据缓存）。两者都要按 BDP 调——但发送缓冲区的"自动调优"不如接收缓冲区成熟（发送缓冲区主要靠应用 `setsockopt(SO_SNDBUF)` 或内核默认）。所以调优时，接收缓冲区靠 `tcp_moderate_rcvbuf` 自动调，发送缓冲区要手动调 `tcp_wmem` 最大值。**接收缓冲区自动调，发送缓冲区手动调**——这是 TCP 缓冲区调优的"收发差异"。

### 3.3 拥塞控制算法（提升长链路吞吐量）

```bash
# 查看当前拥塞控制算法
sysctl net.ipv4.tcp_congestion_control
# net.ipv4.tcp_congestion_control = cubic  ← 默认 cubic

# 查看可用的拥塞控制算法
sysctl net.ipv4.tcp_available_congestion_control
# net.ipv4.tcp_available_congestion_control = reno cubic bbr

# 切换到 BBR（高带宽高延迟链路的最佳选择）
sysctl -w net.ipv4.tcp_congestion_control=bbr

# BBR 还需要 FQ（Fair Queue）调度器配合
sysctl -w net.core.default_qdisc=fq

# BBR 适用场景：
# - 跨 WAN / 跨 IDC 的数据传输（RTT > 10ms）
# - 存在随机丢包的网络（BBR 不把丢包当拥塞信号）
# CUBIC 适用场景：
# - 数据中心内部（RTT < 1ms，CUBIC 的探测性能已经足够）
# - 对公平性要求高的场景（多条流共享带宽）
```

拥塞控制有一个与"丢包 vs 延迟"相关的算法差异——CUBIC 基于"丢包"判断拥塞（丢包 = 拥塞，降速）；BBR 基于"带宽和 RTT"判断拥塞（RTT 增加 = 拥塞，降速）。在"随机丢包"的网络（无线网络、跨 WAN），CUBIC 会误判"随机丢包 = 拥塞"，频繁降速——吞吐量低。BBR 不把丢包当拥塞，吞吐量稳定。所以 BBR 在"有随机丢包的长链路"优势明显——这是 BBR 替代 CUBIC 的核心场景。**CUBIC "丢包即拥塞"，BBR "RTT 即拥塞"**——这是两种算法的根本差异，决定了适用场景。

BBR 还有一个与"FQ 调度器"相关的配合——BBR 需要 `fq`（Fair Queue）调度器配合，因为 BBR 的" pacing rate"（ pacing 发送）需要 `fq` 的"按流排队"支持。如果不用 `fq`（譬如用默认的 `pfifo_fast`），BBR 的 pacing 失效——发送节奏被打乱，BBR 的优势消失。所以切 BBR 时要同时设 `default_qdisc=fq`——两者配套。**BBR + FQ 是"配套使用"**——这是 BBR 调优的"调度器配合"，不能只切 BBR 不设 FQ。

BBR 还有一个与"公平性"相关的局限——BBR v1 在"多流竞争"时可能不公平——BBR 的"带宽探测"可能抢占 CUBIC 流的带宽。所以 BBR v1 适合"纯 BBR 环境"（所有流都用 BBR），混用 BBR + CUBIC 时 BBR 可能"欺负" CUBIC。BBR v2/v3 改进了公平性——加入"拥塞信号"（不只看 RTT），与 CUBIC 共存更友好。所以生产环境混用时，考虑 BBR v2/v3（如果内核支持）或全 BBR v1。**BBR v1 "公平性差"，混用考虑 v2/v3**——这是 BBR 调优的"公平性"考量。

### 3.4 TIME_WAIT 优化（解决端口耗尽）

```bash
# 场景：客户端侧大量短连接，导致端口耗尽（TIME_WAIT 连接数 > 60000）

# 方法 1：TCP 时间戳 + TIME_WAIT 复用（推荐客户端配置）
sysctl -w net.ipv4.tcp_timestamps=1  # 必须开启（TIME_WAIT 复用的前提条件）
sysctl -w net.ipv4.tcp_tw_reuse=1    # 允许 TIME_WAIT 端口被新连接复用
# 效果：TIME_WAIT 连接的端口在 1 秒后即可复用，而不是等 60 秒

# 方法 2：增大本地端口范围（临时解决方案）
sysctl -w net.ipv4.ip_local_port_range="1024 65535"  # 可用端口 64511 个
# 默认：32768-60999（约 28000 个）→ 扩展到约 64000 个

# 方法 3：减少 TIME_WAIT 超时（不推荐，可能破坏 TCP 的 2MSL 保证）
# net.ipv4.tcp_fin_timeout = 30  ← 默认 60 秒，控制 FIN_WAIT2 超时
# TIME_WAIT 的 2MSL 时间由内核内部固定（Linux 为 60 秒），不可直接修改

# 查看 TIME_WAIT 连接数
ss -s | grep TIME-WAIT
# 或
ss -ant | awk '{print $1}' | sort | uniq -c | sort -rn

# ！！ 不推荐使用 tcp_tw_recycle（Linux 4.12+ 已删除）
# tcp_tw_recycle 在 NAT 环境中导致连接被错误拒绝（不同客户端的时间戳不单调）
```

TIME_WAIT 有一个与"2MSL"相关的存在原因——TCP 主动关闭方进入 TIME_WAIT 后等 2MSL（Linux 60 秒），是为了"确保最后的 ACK 到达对端"和"防止旧连接的延迟包干扰新连接"。如果不等 2MSL 立即复用端口，旧连接的延迟包可能被新连接误收——数据错乱。所以 TIME_WAIT 是"TCP 安全的代价"——60 秒的等待换"无数据错乱"。`tcp_tw_reuse` 通过"时间戳"判断"旧包 vs 新包"，允许安全复用——既保留安全性，又减少等待。**TIME_WAIT 的 60 秒是"TCP 安全代价"，`tcp_tw_reuse` 用时间戳安全缩短**——这是 TIME_WAIT 优化的原理。

TIME_WAIT 优化还有一个与"tcp_tw_recycle"相关的教训——`tcp_tw_recycle` 是"激进回收 TIME_WAIT"，看似比 `tcp_tw_reuse` 更彻底，但它在 NAT 环境会"误杀连接"——NAT 后的多个客户端用同一公网 IP，`tcp_tw_recycle` 根据"时间戳单调性"判断"旧包 vs 新包"，但 NAT 后的客户端时间戳不单调（不同机器时钟不同），导致"新连接被误判为旧包"而拒绝。所以 `tcp_tw_recycle` 在 Linux 4.12+ 被删除——这是一个"看似优化实则破坏"的教训。**`tcp_tw_recycle` 的删除是"优化破坏安全"的教训**——这是 TIME_WAIT 优化的"安全边界"，不能为优化牺牲正确性。

TIME_WAIT 优化还有一个与"tcp_max_tw_buckets"相关的上限——`tcp_max_tw_buckets` 控制"系统最多同时存在多少 TIME_WAIT"（默认 180000）。超过上限时，新关闭的连接不进 TIME_WAIT 而直接释放——这会"丢失 2MSL 安全保证"。所以 `tcp_max_tw_buckets` 是"安全阀"——超过时牺牲安全换端口。高并发场景要调大（譬如 500000），避免"正常流量就触发安全阀"。**`tcp_max_tw_buckets` 是"TIME_WAIT 安全阀"**——这是 TIME_WAIT 优化的"上限调优"，高并发要调大。

### 3.5 Keepalive 参数（检测僵尸连接）

```bash
# TCP Keepalive 用于检测长时间空闲的连接是否仍然存活
# 场景：数据库连接池保持长连接，但中间防火墙/负载均衡有空闲超时

# 开启 TCP Keepalive（全局，但应用层要设置 SO_KEEPALIVE）
sysctl -w net.ipv4.tcp_keepalive_time=600     # 空闲 600 秒后开始发送探测包（默认 7200）
sysctl -w net.ipv4.tcp_keepalive_intvl=15     # 探测包间隔 15 秒（默认 75）
sysctl -w net.ipv4.tcp_keepalive_probes=3     # 探测失败 3 次后关闭连接（默认 9）

# 在 600 秒空闲后，每 15 秒发一次探测包，3 次失败后关闭
# 总超时时间：600 + 3 × 15 = 645 秒 ≈ 11 分钟
# 这比默认的 7200 + 9 × 75 ≈ 2 小时要快得多

# 应用层同时设置 SO_KEEPALIVE（内核 Keepalive 才会生效）
int yes = 1;
setsockopt(fd, SOL_SOCKET, SO_KEEPALIVE, &yes, sizeof(yes));
```

Keepalive 有一个与"中间设备超时"相关的调优动机——防火墙、负载均衡、NAT 设备通常有"空闲连接超时"（譬如 30 分钟无数据就断开）。如果应用的长连接空闲超过这个超时，中间设备会静默断开——应用不知道，下次用连接时才发现"连接已断"（报错）。Keepalive 定期发探测包，让中间设备看到"连接活跃"，不超时断开。`tcp_keepalive_time` 要小于中间设备的超时——譬如中间设备 30 分钟超时，Keepalive 设 10 分钟（600 秒）探测一次，确保在中间设备超时前"刷活跃"。**Keepalive 的探测间隔要小于"中间设备超时"**——这是 Keepalive 调优的"超时匹配"原则。

Keepalive 还有一个与"应用层心跳"相关的对比——TCP Keepalive 是"内核级心跳"，应用层也可以实现"应用级心跳"（譬如 Redis 的 PING、MySQL 的 SELECT 1）。应用级心跳比 TCP Keepalive 更可靠——它能检测"应用层僵死"（连接活着但应用不响应，譬如死锁），TCP Keepalive 只能检测"连接层断开"（TCP 层不通）。所以生产环境推荐"应用级心跳"而非纯 TCP Keepalive——应用级心跳覆盖"连接 + 应用"两层。**应用级心跳比 TCP Keepalive 覆盖更广**——这是 Keepalive 调优的"应用层补充"。

Keepalive 还有一个与"双层心跳"相关的实践——生产环境推荐"TCP Keepalive + 应用级心跳"双层。TCP Keepalive 防"连接层断开"（譬如中间设备超时），应用级心跳防"应用层僵死"（譬如死锁）。两层覆盖不同故障——TCP Keepalive 检测"网络层"，应用级心跳检测"应用层"。双层心跳的间隔要协调——应用级心跳更频繁（譬如 30 秒），TCP Keepalive 更慢（譬如 600 秒）——应用级先发现问题，TCP Keepalive 兜底。**"TCP Keepalive + 应用级心跳"双层覆盖**——这是 Keepalive 调优的"双层实践"。

### 3.6 内核软中断调优（解决高流量下的包处理瓶颈）

```bash
# net.core.netdev_budget：每次软中断最多处理的数据包数（默认 300）
sysctl -w net.core.netdev_budget=600
# 在高流量场景（10Gbps+）增大这个值，让每次 NAPI 轮询处理更多包
# 但过大会导致单次软中断时间过长，影响延迟

# net.core.netdev_budget_usecs：每次软中断最长运行时间（µs，默认 2000）
sysctl -w net.core.netdev_budget_usecs=8000
# 配合 netdev_budget，双重限制软中断时间

# net.core.netdev_max_backlog：每个 CPU 的软中断接收队列长度（默认 1000）
sysctl -w net.core.netdev_max_backlog=10000
# 当 NAPI 来不及处理时，包暂存在此队列，避免立即丢弃

# 验证软中断是否成为瓶颈
watch -n 1 "cat /proc/net/softnet_stat"
# 每行对应一个 CPU
# 字段：total  dropped  time_squeezed  ...
# time_squeezed：因运行时间超限被打断的次数（持续增加说明需要增大 budget）
# dropped：软中断队列满丢包次数（持续增加说明需要增大 netdev_max_backlog）
```

软中断调优有一个与"预算"相关的双重限制——`netdev_budget`（包数）和 `netdev_budget_usecs`（时间）双重限制软中断的单次处理量。任一达到上限就停止——譬如处理了 600 包但用了 8ms，或处理了 300 包但用了 2ms。这个双重限制防止单次软中断"独占 CPU"——软中断是 SoftIRQ，优先级高于普通进程，如果软中断跑太久，应用进程得不到 CPU。**软中断的"双重预算"防"独占 CPU"**——这是软中断调优的"公平性"考量，不能让网络处理饿死应用。

软中断还有一个与"softnet_stat"相关的诊断——`/proc/net/softnet_stat` 的每行对应一个 CPU，字段包括 `total`（处理包总数）、`dropped`（软中断队列满丢包）、`time_squeezed`（运行时间超限被打断次数）。如果 `time_squeezed` 持续增加，说明"软中断处理不完"——要调大 `netdev_budget` 或加多队列（多核并行）。如果 `dropped` 持续增加，说明"软中断队列满"——要调大 `netdev_max_backlog`。**`softnet_stat` 是"软中断诊断的窗口"**——这是软中断调优的"诊断入口"，先看 `softnet_stat` 再调参。

软中断还有一个与"NAPI"相关的机制——NAPI（New API）是"中断 + 轮询"的混合模式。第一个包触发中断，之后内核进入"轮询模式"批量处理 Ring Buffer 的包（不再触发中断），处理完再回"中断模式"。NAPI 兼顾"低延迟"（第一个包中断响应快）和"高吞吐"（批量处理效率高）。所以 NAPI 是"中断 + 轮询"的智能切换——这是现代网卡的标准模式，无需额外配置（驱动默认启用）。**NAPI 是"中断 + 轮询"的智能切换**——这是软中断处理的"自适应机制"，驱动默认启用。

## 第 4 章 完整调优配置清单

### 4.1 高吞吐量场景（数据传输、备份、Kafka）

```bash
# /etc/sysctl.d/99-network-throughput.conf

# === TCP 缓冲区 ===
net.core.rmem_max = 134217728
net.core.wmem_max = 134217728
net.ipv4.tcp_rmem = 4096 131072 134217728
net.ipv4.tcp_wmem = 4096 16384 134217728
net.ipv4.tcp_moderate_rcvbuf = 1

# === 拥塞控制 ===
net.ipv4.tcp_congestion_control = bbr
net.core.default_qdisc = fq

# === 软中断处理 ===
net.core.netdev_budget = 600
net.core.netdev_budget_usecs = 8000
net.core.netdev_max_backlog = 10000

# === 连接管理 ===
net.core.somaxconn = 65535
net.ipv4.tcp_max_syn_backlog = 65535
net.ipv4.tcp_syncookies = 1

# === TIME_WAIT 优化 ===
net.ipv4.tcp_timestamps = 1
net.ipv4.tcp_tw_reuse = 1
net.ipv4.ip_local_port_range = 1024 65535

# 生效
sysctl -p /etc/sysctl.d/99-network-throughput.conf
```

高吞吐场景的调优有一个与"BDP"相关的核心——缓冲区要大（128MB），因为高吞吐链路的 BDP 大（譬如跨 WAN 1Gbps × 50ms = 6.25MB，缓冲区要 12MB+）。BBR 拥塞控制适合跨 WAN 的长链路（RTT 大，BBR 的带宽探测优势明显）。软中断预算调大（netdev_budget=600），因为高吞吐包多，每次软中断要多处理。**高吞吐调优的核心是"大缓冲区 + BBR + 大软中断预算"**——这是高吞吐场景的"三大件"。

高吞吐场景的配置有一个与"持久化"相关的实践——`sysctl -w` 是临时生效（重启失效），要持久化到 `/etc/sysctl.d/99-network-throughput.conf`。`sysctl -p` 加载配置文件。生产环境要用配置文件而非 `sysctl -w`——否则重启后调优丢失。**sysctl 调优要"持久化到配置文件"**——这是 sysctl 调优的"持久化"实践，`sysctl -w` 只用于测试。

高吞吐场景还有一个与"多流并行"相关的实践——iperf3 测试用 `-P 4`（4 并发流），但生产应用可能用"单流"或"多流"。单流 TCP 受"单核处理瓶颈"限制（一个流一个核），多流 TCP 用多核并行。所以高吞吐应用要"多流并行"——譬如 Kafka 的多个 partition 用多个 TCP 连接（多流），而非一个连接传所有 partition（单流）。**高吞吐应用要"多流并行"利用多核**——这是高吞吐场景的"应用层多流"实践。

### 4.2 低延迟 RPC 场景（Redis、gRPC、高频交易）

```bash
# /etc/sysctl.d/99-network-lowlatency.conf

# === TCP 缓冲区（较小，减少缓冲膨胀）===
net.core.rmem_max = 16777216
net.core.wmem_max = 16777216
net.ipv4.tcp_rmem = 4096 65536 16777216
net.ipv4.tcp_wmem = 4096 65536 16777216

# === 拥塞控制（数据中心内用 CUBIC，RTT 短）===
net.ipv4.tcp_congestion_control = cubic
net.core.default_qdisc = fq_codel  # FQ-CoDel 控制 buffer bloat

# === 禁用 Nagle（低延迟场景，配合应用层 TCP_NODELAY）===
# Nagle 在应用层禁用（TCP_NODELAY），内核侧不需要额外配置

# === 快速 ACK ===
net.ipv4.tcp_quickack = 1  # 快速 ACK（但应用层需要再次设置）

# === 连接建立优化 ===
net.ipv4.tcp_syn_retries = 3      # SYN 重试次数（默认 6），加快失败连接的发现
net.ipv4.tcp_synack_retries = 3   # SYNACK 重试次数
net.core.somaxconn = 65535
net.ipv4.tcp_max_syn_backlog = 65535

# === Keepalive 激进化 ===
net.ipv4.tcp_keepalive_time = 60  # 60 秒无数据开始探测（默认 7200 太长）
net.ipv4.tcp_keepalive_intvl = 10
net.ipv4.tcp_keepalive_probes = 3

sysctl -p /etc/sysctl.d/99-network-lowlatency.conf
```

低延迟场景的调优有一个与"缓冲膨胀"相关的核心——缓冲区要小（16MB），因为低延迟场景的 BDP 小（数据中心内 RTT < 1ms，BDP 小）。缓冲区太大会导致"缓冲膨胀"（Bufferbloat）——包在缓冲区排队，延迟增加。`fq_codel` 调度器控制缓冲膨胀——主动丢弃"排队太久"的包，防止延迟堆积。Keepalive 激进化（60 秒探测），快速发现僵尸连接——低延迟场景不能容忍"2 小时才发现连接死了"。**低延迟调优的核心是"小缓冲区 + fq_codel + 激进 Keepalive"**——这是低延迟场景的"三大件"。

低延迟场景还有一个与"TCP_NODELAY"相关的应用层配合——`TCP_NODELAY` 禁用 Nagle 算法，让小包立即发送（不攒批）。Nagle 算法会"攒小包为大包"——增加延迟（等攒批）。低延迟场景要禁用 Nagle——`setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &yes, sizeof(yes))`。但禁用 Nagle 会增加小包数量（不攒批），可能增加网络开销——所以"低延迟 + 小包多"的场景要权衡。**`TCP_NODELAY` 是低延迟的应用层配合**——这是低延迟调优的"应用层补充"，内核调优 + 应用层 `TCP_NODELAY` 配合。

低延迟场景还有一个与"中断合并"相关的 NIC 配合——低延迟要"禁用中断合并"（`ethtool -C eth0 rx-usecs 1 rx-frames 1`），让每个包立即触发中断。这与高吞吐场景"调大中断合并"相反——低延迟优先"即时响应"，高吞吐优先"批量效率"。所以低延迟调优不只是 sysctl，还要 ethtool 配合——内核 + NIC 两层调优。**低延迟要"NIC 禁用中断合并 + 内核小缓冲区"**——这是低延迟调优的"NIC + 内核双层"。

### 4.3 高并发连接场景（Nginx、API Gateway、WebSocket）

```bash
# /etc/sysctl.d/99-network-highconn.conf

# === 最大 socket 文件描述符 ===
fs.file-max = 10000000      # 系统级 fd 上限
fs.nr_open = 10000000       # 单进程 fd 上限（配合 ulimit -n）

# === 连接队列 ===
net.core.somaxconn = 65535
net.ipv4.tcp_max_syn_backlog = 65535

# === TIME_WAIT 快速回收（高并发短连接）===
net.ipv4.tcp_timestamps = 1
net.ipv4.tcp_tw_reuse = 1
net.ipv4.ip_local_port_range = 1024 65535
net.ipv4.tcp_max_tw_buckets = 500000  # 最多同时存在 50 万 TIME_WAIT（默认 180000）

# === 减少连接建立开销 ===
net.ipv4.tcp_fastopen = 3   # TCP Fast Open：客户端（1） + 服务端（2）都开启
# TFO 允许在 SYN 包中携带数据，消除初始 RTT

# === 内存压力下的 socket 回收 ===
net.ipv4.tcp_mem = 786432 1048576 26777216  # 三元组：低水位、压力线、高水位（页数）

sysctl -p /etc/sysctl.d/99-network-highconn.conf

# 同时配置系统和进程的 fd 上限
echo "* soft nofile 1000000" >> /etc/security/limits.conf
echo "* hard nofile 1000000" >> /etc/security/limits.conf
echo "root soft nofile 1000000" >> /etc/security/limits.conf
echo "root hard nofile 1000000" >> /etc/security/limits.conf
```

高并发场景的调优有一个与"fd 上限"相关的核心——每个连接占一个 fd，100 万连接要 100 万 fd。默认 fd 上限（1024 或 65536）不够——要调大 `fs.file-max`（系统级）和 `fs.nr_open`（进程级），还要调 `ulimit -n`（shell 级）。三级 fd 上限都要调——任一不够都会"too many open files"报错。**高并发调优的核心是"三级 fd 上限 + TIME_WAIT 回收 + Fast Open"**——这是高并发场景的"三大件"。

高并发场景还有一个与"TCP Fast Open"相关的优化——TFO（TCP Fast Open）允许在 SYN 包中携带数据，消除"三次握手的 RTT"——第一个包就能传数据。对于"短连接 + 小请求"的场景（譬如 HTTP API），TFO 能减少一个 RTT 的延迟。但 TFO 要客户端和服务端都支持——`tcp_fastopen=3`（客户端 1 + 服务端 2）。TFO 的安全性有考量（SYN 携带数据可能被重放）——要用 TCP Cookie 防重放。**TFO 是"消除握手 RTT"的优化**——这是高并发短连接场景的"握手优化"。

高并发场景还有一个与"连接池"相关的应用层配合——高并发的"短连接"有"握手开销"（TCP 三次握手 + TLS 握手），用"连接池"复用连接能消除握手开销。所以高并发的最佳实践是"长连接 + 连接池"而非"短连接 + TFO"——TFO 是"短连接的补救"，连接池是"更根本的解法"。Nginx 的 `keepalive` 指令、HTTP/2 的多路复用、gRPC 的连接池都是"长连接复用"的实践。**"连接池"比"TFO"更根本**——这是高并发场景的"应用层连接复用"实践。

## 第 5 章 网络基准测试方法论

### 5.1 iperf3：TCP/UDP 吞吐量测试

```bash
# 服务端启动
iperf3 -s -p 5201  # 监听 5201 端口

# 客户端：基础吞吐量测试（60 秒，单流）
iperf3 -c <server> -t 60 -p 5201
# [ ID] Interval       Transfer     Bitrate         Retr
# [  5]   0.00-60.00 sec  66.2 GBytes  9.49 Gbits/sec    0  sender

# 客户端：多并发流测试（4 个并发 TCP 流）
iperf3 -c <server> -t 60 -P 4
# 多流可以更好地利用多队列 NIC 的并行性

# 客户端：指定发送缓冲区大小（测试缓冲区调优效果）
iperf3 -c <server> -t 60 -w 4m  # -w：socket 缓冲区大小

# 双向测试（同时测试上行和下行）
iperf3 -c <server> -t 60 --bidir

# 逆向测试（服务端发送到客户端，测试下行带宽）
iperf3 -c <server> -t 60 -R

# JSON 输出（方便脚本处理和对比）
iperf3 -c <server> -t 60 -J > result.json
python3 -c "import json; d=json.load(open('result.json')); \
    print(f\"BW: {d['end']['sum_received']['bits_per_second']/1e9:.2f} Gbps\")"

# 测试特定 MTU 大小（模拟不同网络路径）
iperf3 -c <server> -t 60 --length 1400  # MTU = 1400 字节
```

iperf3 的多流测试（`-P 4`）有一个与"多队列网卡"相关的原理——单流 TCP 只用一个队列（一个核处理），多流 TCP 用多个队列（多核并行处理）。所以单流测不出"多队列的并行能力"——单流可能只有 3Gbps（单核瓶颈），多流能到 9Gbps（多核并行）。测吞吐量要用多流——这是"测多队列能力"的正确方法。**iperf3 多流测试是"测多队列并行能力"**——这是吞吐量测试的"多流原则"。

iperf3 还有一个与"UDP 测试"相关的场景——`iperf3 -u` 测 UDP 吞吐量和丢包率。UDP 无流控，发包速度由 `iperf3` 控制（`-b` 带宽）。UDP 测试能测"网络的真实丢包率"——譬如 `iperf3 -u -b 5G` 发 5Gbps UDP，看接收端丢包率。如果丢包率高，说明网络有"拥塞丢包"——TCP 的重传可能掩盖了这个问题。**iperf3 UDP 测试能"暴露真实丢包率"**——这是 UDP 测试的独特价值，TCP 测试看不到真实丢包（重传掩盖）。

iperf3 还有一个与"JSON 输出"相关的自动化——`iperf3 -J` 输出 JSON，方便脚本解析和对比。调优脚本可以"调参 → iperf3 -J → 解析 JSON → 记录吞吐"自动化。这比"人工看 iperf3 输出"高效——调优 10 个参数，人工看 10 次输出容易出错，脚本自动解析无误差。**`iperf3 -J` 是"自动化调优"的基础**——这是基准测试的"自动化"实践，用 JSON + 脚本批量调优。

### 5.2 netperf：延迟和 QPS 基准测试

`iperf3` 侧重带宽测试，`netperf` 更擅长测量**请求-响应模式**（RPC 场景）的性能：

```bash
# 服务端
netserver -p 12865

# TCP_RR（TCP Request-Response）：测量单连接 RPS 和延迟
# 模拟：一次发送 100 字节请求，接收 100 字节响应
netperf -H <server> -t TCP_RR -l 60 -- -r 100,100
# MIGRATED TCP REQUEST/RESPONSE TEST from 0.0.0.0 (0.0.0.0) port 0 to <server> port 0 : demo
# Local /Remote
# Socket Size   Request Resp.  Elapsed Trans.
# Send   Recv   Size    Size   Time    Rate
# bytes  Bytes  bytes   bytes  secs.   per sec
# 131072 131072 100     100    60.00   123456.78  ← 每秒 12.3 万次 RPC

# TCP_CRR（TCP Connect-Request-Response）：测量包含连接建立的 RPS
# 模拟：短连接场景（每次 RPC 建立新连接）
netperf -H <server> -t TCP_CRR -l 60 -- -r 100,100
# 通常比 TCP_RR 慢 5-10 倍（TCP 三次握手开销）

# TCP_STREAM：吞吐量测试（功能类似 iperf3）
netperf -H <server> -t TCP_STREAM -l 60

# UDP_RR：UDP 请求-响应（测试低延迟 UDP 场景）
netperf -H <server> -t UDP_RR -l 60 -- -r 64,64
```

netperf 的 TCP_RR vs TCP_CRR 有一个与"连接建立开销"相关的对比——TCP_RR 用长连接（一次建立，多次 RPC），TCP_CRR 用短连接（每次 RPC 都建立连接）。TCP_CRR 比 TCP_RR 慢 5-10 倍——这是"连接建立开销"的量化。如果应用的 RPC 用短连接，要参考 TCP_CRR 的数据；如果用长连接（连接池），参考 TCP_RR。**TCP_RR 测长连接 RPC，TCP_CRR 测短连接 RPC**——这是 netperf 的"连接模式区分"，要匹配应用的连接模式选测试。

netperf 还有一个与"延迟分布"相关的进阶——`netperf` 默认只报"平均 QPS"，但 RPC 场景更关心"P99 延迟"。要测 P99，用 `netperf` 的 `-D` 选项（延迟直方图）或用 `bpftrace` 追踪 `tcp_recvmsg` 的延迟分布。平均延迟可能掩盖"P99 毛刺"——譬如平均 1ms 但 P99 100ms（有毛刺）。所以 RPC 调优要看 P99 而非平均——P99 才是"用户体验"的延迟。**RPC 调优要看"P99 延迟"而非"平均"**——这是 RPC 基准测试的"分布视角"。

netperf 还有一个与"UDP_RR"相关的场景——`UDP_RR` 测 UDP 请求-响应，模拟"低延迟 UDP RPC"（譬如 DNS、QUIC）。UDP 无连接建立开销，RPC 比 TCP_RR 快——但 UDP 无可靠性保证（丢包不重传），应用要自己处理可靠性。所以 UDP_RR 适合"容忍丢包 + 极低延迟"的场景（譬如 DNS 查询），不适合"要求可靠"的场景（譬如数据库 RPC）。**UDP_RR 测"容忍丢包的极低延迟 RPC"**——这是 netperf 的"UDP RPC"场景，适合 DNS/QUIC 类应用。

### 5.3 用基准测试量化调优效果

```bash
# 调优前后对比脚本
#!/bin/bash
SERVER=10.0.0.1

echo "=== 基准测试前 ==="
# 吞吐量
iperf3 -c $SERVER -t 30 -J | python3 -c "
import json,sys; d=json.load(sys.stdin)
bw = d['end']['sum_received']['bits_per_second']/1e9
print(f'吞吐量: {bw:.2f} Gbps')"

# RPC 延迟
netperf -H $SERVER -t TCP_RR -l 30 -- -r 100,100 | tail -1 | awk '{
    printf "RPC QPS: %.0f/s\n", $NF
    printf "RPC 平均延迟: %.3f ms\n", 1000/$NF
}'

echo ""
echo "修改 sysctl 参数..."
sysctl -w net.ipv4.tcp_congestion_control=bbr
sysctl -w net.core.default_qdisc=fq

echo "=== 调优后 ==="
iperf3 -c $SERVER -t 30 -J | python3 -c "
import json,sys; d=json.load(sys.stdin)
bw = d['end']['sum_received']['bits_per_second']/1e9
print(f'吞吐量: {bw:.2f} Gbps')"

netperf -H $SERVER -t TCP_RR -l 30 -- -r 100,100 | tail -1 | awk '{
    printf "RPC QPS: %.0f/s\n", $NF
}'
```

### 5.4 验证调优效果的 ss 命令

```bash
# 调优后，用 ss -ti 确认 TCP 连接已经使用了新的参数

# 验证 BBR 是否生效
ss -ti dst <server_ip> | grep -i bbr
# cwnd:10 ssthresh:2147483647 ... bbr   ← 已使用 BBR

# 验证缓冲区是否增大（rcv_space 应接近调优后的最大值）
ss -ti dst <server_ip> | grep rcv_space
# rcv_space:65536  ← 若远低于 tcp_rmem 最大值，说明 Autotuning 未充分发挥
# rcv_space:33554432  ← 已充分扩展到最大缓冲区（33MB），带宽充分利用

# 验证拥塞窗口是否增大（cwnd 应随着连接稳定而增大）
ss -ti | grep cwnd | awk '{print $0}' | grep -v "cwnd:10 "
# 成熟连接的 cwnd 应远大于 10（初始值）
```

`ss -ti` 的验证有一个与"参数生效"相关的意义——`sysctl` 改了参数，但"参数改了"不等于"连接用了新参数"。譬如改了 `tcp_rmem` 最大值，但已有连接的缓冲区不会立即调整——只有新连接用新参数。`ss -ti` 能看到"当前连接的实际参数"——确认调优真的生效。**`ss -ti` 验证"参数真的生效"**——这是调优后的"验证闭环"，不能"改了就完"，要确认生效。

`ss -ti` 还有一个与"cwnd 观察"相关的诊断——`cwnd`（拥塞窗口）反映"TCP 当前的发送能力"。连接刚建立时 `cwnd=10`（初始值），随着"慢启动"爬升，稳态时 `cwnd` 可能到几百几千。如果 `cwnd` 长期停在 10，说明"慢启动没爬升"——可能"丢包频繁"或"接收窗口小"。所以 `ss -ti` 看 `cwnd` 能诊断"TCP 是否充分爬升"——这是"TCP 健康度"的观察窗口。**`ss -ti` 的 `cwnd` 是"TCP 健康度"的观察窗口**——这是调优验证的"深度诊断"。

`ss -ti` 还有一个与"rtt 观察"相关的诊断——`ss -ti` 显示连接的 `rtt`（平滑 RTT）和 `rttvar`（RTT 方差）。`rtt` 反映"当前链路延迟"，`rttvar` 反映"延迟抖动"。如果 `rtt` 比预期大（譬如数据中心内 rtt > 1ms），说明"链路有排队"或"路由异常"。如果 `rttvar` 大，说明"延迟抖动大"——可能影响 P99。所以 `ss -ti` 的 `rtt/rttvar` 是"链路质量"的观察窗口。**`ss -ti` 的 `rtt/rttvar` 是"链路质量"的观察窗口**——这是调优验证的"链路诊断"。

## 第 6 章 网络调优的边界与盲区

### 6.1 调优无法突破物理带宽

网络调优能"充分利用带宽"，但不能"超过带宽"。如果 10Gbps 网卡已经跑满 9.5Gbps，调优最多到 9.9Gbps——物理带宽是硬上限。要超过 10Gbps，只能换 25Gbps/100Gbps 网卡——这是硬件升级，不是调优。**调优"充分利用带宽"，硬件升级"提高带宽上限"**——这是调优与硬件升级的边界，调优到极限后要考虑硬件升级。

调优与硬件升级的边界还有一个与"成本"相关的决策——调优成本是"工程师时间"（几小时到几天），硬件升级成本是"采购费用"（几千到几万）。如果调优能把利用率从 50% 提到 90%，无需升级——调优更划算。如果调优已到 95% 仍不够，升级是唯一出路——调优无空间。所以"调优 vs 升级"的决策点是"当前利用率"——低于 90% 先调优，高于 90% 考虑升级。**"利用率 < 90% 先调优，> 90% 考虑升级"**——这是调优与升级的成本决策点。

### 6.2 调优可能引入新问题

网络调优有一个与"过度调优"相关的风险——譬如 Ring Buffer 调太大（4096），占用 8MB 内存，且增加包的"排队延迟"（包在 Ring Buffer 等处理）；缓冲区调太大（128MB），导致"缓冲膨胀"，延迟增加；中断合并调太大，延迟增加。所以调优不是"越大越好"——每个参数都有"甜点区间"，超过甜点反而变差。**调优有"甜点区间"，过度调优反而变差**——这是调优的"过犹不及"原则，要"差分测试"找甜点。

过度调优的"甜点测试"有一个与"二分法"相关的实践——譬如 Ring Buffer 从 512 调到 4096，中间有 1024/2048/4096 几档。测每档的"吞吐 + 延迟"，找"吞吐不再增加但延迟开始增加"的拐点——这就是甜点。二分法能加速找拐点——先测 2048，如果吞吐还在增加，测 4096；如果吞吐不增加延迟增加，测 1024。**"二分法找甜点"是过度调优的测试方法**——这是调优的"精细化"实践，不能"一步到位调最大"。

### 6.3 调优要匹配应用场景

网络调优有一个与"场景匹配"相关的原则——高吞吐、低延迟、高并发的调优方向不同，甚至冲突。譬如高吞吐要"大缓冲区"，低延迟要"小缓冲区"——同一参数在两个场景的值相反。所以调优不能"一套配置通用"——要按应用场景选配置。**调优要"按场景选配置"，不能"一套通用"**——这是调优的"场景化"原则，本文的三个配置清单（高吞吐、低延迟、高并发）就是场景化的体现。

场景化调优还有一个与"混合负载"相关的挑战——一个服务器可能同时跑"高吞吐服务"和"低延迟服务"，两个服务的调优方向冲突（一个要大缓冲区，一个要小缓冲区）。解法是"容器隔离"——把两个服务放不同容器/网络命名空间，各自独立调优（`sysctl` 在网络命名空间内独立）。或者"分时调度"——高吞吐服务跑在夜间（延迟不敏感），低延迟服务跑在白天。**混合负载要"容器隔离"或"分时调度"**——这是场景化调优的"混合负载"解法。

## 第 7 章 小结

网络调优是一个**多层联动**的过程，任何单层的优化都可能被其他层的瓶颈抵消：

**从底到上的调优顺序**：
1. NIC 层：Ring Buffer 丢包 → `ethtool -G` 增大；中断合并 → `ethtool -C` 调整
2. 软中断层：`netdev_budget` 和 `netdev_max_backlog` 防止软中断队列丢包
3. TCP 缓冲区层：`tcp_rmem`/`tcp_wmem` 按 BDP 设置
4. 拥塞控制：长链路 → BBR；数据中心短链路 → CUBIC
5. 连接管理：`somaxconn` + `tcp_max_syn_backlog` + `tcp_tw_reuse`

**基准测试原则**：
- 每次只调一个参数，用 `iperf3`/`netperf` 验证效果
- 记录调优前的基准数据，用差分比较而非绝对值
- 基准测试场景要匹配真实负载（带宽型 → iperf3，延迟型 → netperf TCP_RR）

网络调优的核心认知是"网络性能是多层复合函数"——同一块网卡，经过 Ring Buffer、软中断、TCP 缓冲区、应用协议的层层处理，每一层都有"折损"。调优的本质是"减少每层折损"——但要知道"哪层折损最大"，针对性调优。**"网络性能 = 网卡带宽 × 各层折损系数"**——理解这个复合函数，才能定位瓶颈层，避免"在非瓶颈层调优白费功夫"。
