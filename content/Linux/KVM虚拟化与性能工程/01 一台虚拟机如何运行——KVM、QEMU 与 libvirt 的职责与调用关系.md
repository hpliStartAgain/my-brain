# 01 一台虚拟机如何运行——KVM、QEMU 与 libvirt 的职责与调用关系

**摘要：**

一台虚机在宿主机上表现为一组进程与线程，但它背后有三个角色在协作：libvirt 提供统一接口，QEMU 负责设备与生命周期，KVM 提供内核态的硬件加速。本文不重复虚拟化技术的演进史，而是沿着一条真实调用链，把三个角色的职责边界、控制路径与数据路径的开销来源、以及宿主机侧如何观察一台运行中的虚机讲清楚。全文回答两个问题：一次「启动虚机」的调用经过了哪些层，以及虚机的性能开销分别来自哪一层。文中的命令与观察方式取自 2026 年 9 月的现场记录，涉及具体数值处标注口径；虚拟化演进与硬件机制请参见相邻专栏的对应篇目。

---

## 第 1 章 三个角色与一条调用链

在宿主机的进程列表里，一台虚机看起来只是一串名字很长的进程；但如果把它拆开，会发现至少有三种东西在同时工作：管理接口、设备模拟、硬件加速。理解它们的分工，是理解虚拟化性能的起点。

### 1.1 三个角色

**libvirt 是统一接口层**。它不实现虚拟化，而是把「创建、启动、暂停、迁移、查询」这些操作抽象成一套 API 与 XML 描述，屏蔽底层到底是 KVM、Xen 还是别的实现。运维与上层平台（如 OpenStack）通过它与虚机打交道。

**QEMU 是用户态的设备与生命周期管理者**。它创建虚机的进程与线程、模拟或半虚拟化各种设备、维护虚机的内存与状态。真正「跑起来」的虚机，是 QEMU 拉起的一个进程。

**KVM 是内核态的加速器**。它是 Linux 内核的一个模块，向用户态暴露一个字符设备接口；QEMU 通过它把 vCPU 的执行交给硬件虚拟化能力，从而避免全模拟的高昂开销。

三个角色的关系可以这样记：**libvirt 负责「说什么」，QEMU 负责「怎么做」，KVM 负责「做多快」**。

### 1.2 为什么必须分工

这个分工不是设计者的偏好，而是历史与工程约束的产物。早期虚拟化要么全靠软件模拟（慢），要么要求改造客户机（不通用）；硬件虚拟化出现后，内核需要有人把硬件能力封装成稳定接口（KVM），用户态需要有人把设备与生命周期做全（QEMU），上层需要有人把操作抽象成统一语义（libvirt）。**三者各守一段边界，才让「通用、快、可管理」这三件事同时成立**。

这也解释了为什么三层都可以单独替换：QEMU 可以被更轻的 VMM 替代（如 Firecracker），libvirt 可以被平台直接绕过（直接调用 QEMU），KVM 的接口则是稳定的。相邻专栏 [[LLM/Agent沙箱技术/隔离原语/04 KVM 与硬件虚拟化——MicroVM 隔离的硬件基石|KVM 与硬件虚拟化]] 讲的 MicroVM 路线，正是把 QEMU 换掉、保留 KVM 的例子。

### 1.4 一个类比与它的边界

一个常用的类比是：把虚机想成「在宿主机上租了一间带独立门牌的办公室」——libvirt 是物业管理系统，QEMU 是装修与家具，KVM 是水电煤的接入点。这个类比能帮助理解分工，但有两个边界需要点明。

第一，**办公室是物理隔开的，而虚机不是**。虚机与宿主机共享同一套 CPU、内存与设备，隔离靠硬件机制而非物理边界。因此「邻居效应」是真实存在的，而物理办公室不会有这个问题。第二，**水电煤的类比容易让人以为 KVM 是「基础设施」**，实际上 KVM 只在 CPU 执行这一环起作用，其余仍是用户态软件。**把 KVM 想得越重，越容易在排障时找错方向**。

类比的用途是建立直觉，边界的作用是防止直觉越界。这一点在本专栏后续各篇都会反复出现。

### 1.5 三层与云平台的对应关系

把三层映射到云平台的组件上，能帮助理解「平台上的操作」如何落到单机上。

| 平台侧 | 对应层 | 落地动作 |
| :--- | :--- | :--- |
| 计算服务 | libvirt 接口 | 生成 XML、调用域操作 |
| 镜像服务 | 启动路径 | 提供根盘内容 |
| 网络服务 | 设备与后端 | 创建虚拟网卡与后端 |
| 存储服务 | 块设备路径 | 提供卷与挂载 |
| 实例高可用 | 生命周期 | 触发重建与疏散 |

**这张表的用途是「反查」**：当平台侧某个操作失败时，可以据此判断问题可能落在哪一层，再去那一层找证据。它与 [[SRE/CVM集群可靠性工程/02 创建一台虚机——跨 Nova、Placement、Neutron、Cinder 的故障定位|02 创建一台虚机]] 的分段定位是同一个思路，只是视角从平台收到了宿主机。

### 1.6 三层模型的一个反例

三层模型有一个反例值得注意：**当 QEMU 被更轻的实现替换时，模型会塌缩成两层**。MicroVM 类实现去掉了完整设备模型与部分管理能力，只保留最小设备与生命周期，因此「设备与生命周期」这一层被压缩得很薄。

这个反例的意义在于它说明**三层划分是「职责」而非「进程」**。即使 QEMU 不存在，仍然需要有人管设备与生命周期，只是这个「人」变成了更轻的组件。**理解职责划分，比记住组件名称更重要**——组件会变，职责不会。

这也是本专栏把「职责」放在篇名里的原因：先建立职责视角，再看具体实现。

## 第 2 章 libvirt：统一接口层

libvirt 是最容易被视为「薄薄一层」的组件，但它的设计取向会影响到排障与性能观测。

### 2.1 它解决什么问题

libvirt 解决的核心问题是**语义统一**。不同虚拟化实现的 API、配置格式、状态语义都不同；libvirt 把它们抽象成一套对象模型（域、网络、存储池、接口）与一套 XML 描述。上层只需要学会一套语义，就能操作多种底层。

对运维而言，这带来两个直接好处：**操作可移植**（同一套命令换个后端仍可用）、**状态可查询**（统一的域状态与统计接口）。代价是多了一层间接，某些底层独有的能力需要通过扩展字段或直连监视器才能使用。

### 2.2 domain XML 与生命周期

libvirt 用一份 XML 描述虚机的全部配置：CPU 与拓扑、内存与大页、磁盘与网络、设备与特性。这份 XML 是「虚机的声明」，QEMU 的启动参数由它生成。

生命周期则是一组状态与转换：定义、启动、运行、暂停、保存、恢复、销毁。**理解状态机是排障的前提**——很多「虚机不见了」的问题，实际是状态停留在了某个中间态，而非真的消失。状态与迁移的细节，[[云原生/OpenStack/05 实例生命周期与迁移实战|05 实例生命周期与迁移]] 从平台侧有系统展开。

```bash
# 列出域及其状态，观察是否停在中间态
virsh list --all

# 查看域的完整 XML：配置的权威来源
virsh dumpxml <domain>

# 查看域的块设备与内存统计
virsh domstats <domain> --state --cpu-total --balloon --block
```

### 2.3 libvirtd 与连接

libvirt 以守护进程形式提供本地与远程连接，客户端通过连接串（如 `qemu:///system`）接入。这里有一个容易踩的坑：**同一个虚机在不同连接下可能表现为不同视图**（系统级与用户级、本地与远程），排查时要先确认自己连的是哪个。

连接方式还影响权限模型：系统级连接通常以特权运行，因为它需要访问宿主机的设备与内核接口。这也是为什么观测虚机的工具往往需要较高权限。

### 2.4 运维视角的定位

对运维来说，libvirt 层的定位是「**配置与状态的权威来源**」：虚机应该是什么样，看它的 XML；虚机现在是什么状态，看它的状态查询。而「虚机实际在做什么」，则要往下一层走，去看 QEMU 的进程与 KVM 的执行。**把「应该」与「实际」分开，是这一层的使用纪律**。

### 2.5 libvirt 与上层平台的分工

libvirt 与上层平台（如 OpenStack 的计算服务）在职责上有明确分界：**平台负责「应该是什么」，libvirt 负责「怎么做到」**。平台决定虚机放在哪台宿主机、用什么规格、接哪个网络；libvirt 把这些决策翻译成宿主机上的实际操作。

这个分界在实践中有一个直接后果：**同一个问题可能在两侧都留下痕迹**。例如创建失败，平台的调度器日志会记录「选中了哪台宿主机」，libvirt 的日志会记录「为什么启动失败」。排查时要两侧对照，而不是只看一侧。

分界的另一面是**能力传递**：平台能用的能力受 libvirt 暴露的接口限制。libvirt 未暴露的底层特性，平台通常也无法使用（除非直连监视器）。理解这一点，能解释为什么某些「底层能做的事」在平台上做不了。

### 2.6 一个 libvirt 视角的排查实例

设想一台虚机「状态异常」：平台显示运行中，但业务不可达。从 libvirt 视角看，域的查询显示状态正常；从进程视角看，QEMU 进程存在且占用资源。

两个视角一致，说明「虚机在跑」这件事是真的。问题因此不在生命周期上，而在虚机内部或它的设备路径上。继续往内看，若块设备统计显示 I/O 停滞、网卡统计显示无收发，则问题在设备路径；若设备统计正常，则要进 Guest 内部排查。

**这个实例演示了 libvirt 视角的定位作用：它负责排除「生命周期问题」**，从而把范围收窄到数据路径或 Guest 内部。**排除也是一种定位**，这一点在分层归因里同样重要。

### 2.7 libvirt 的统计口径

libvirt 的统计接口有几个需要留意的口径问题。**第一，CPU 时间的单位与基准**：它统计的是累计时间，需要用速率换算，且与宿主机的时间基准相关。**第二，内存使用的含义**：它可能指 Guest 视角的内存、也可能指宿主机侧的实际占用，两者在气球与页共享场景下不同。**第三，块设备与网卡的统计范围**：可能包含或不包含特定类型的 I/O（如 flush、丢弃）。

**口径不清是「数据对不上」的最常见原因**：同一次观测，平台侧与 libvirt 侧数字不同，往往不是谁错了，而是统计的对象不同。排查时要先把口径对齐，再比较数字。

这也是本篇反复强调「先问统计的是谁」的具体应用。

### 2.8 libvirt 与直连的取舍

libvirt 提供统一接口，但实践中有时会绕过它直连 QEMU 的监视器。这个取舍值得说明。

**直连的收益**是能访问 libvirt 未暴露的能力（如某些运行时调整），**代价**是绕过 libvirt 的状态管理，可能导致「libvirt 记录的状态与实际不符」。因此直连应当限于「只读诊断」，而不是「修改状态」。

**只读诊断的典型用途**是现场排查：查看设备状态、查询内存映射、观察迁移进度。这些用途不改变状态，因此不会引入不一致。

**原则可以概括为：诊断可以直连，变更必须走接口**。这条原则与 [[SRE/CVM集群可靠性工程/08 运维工程化——巡检、维护预检、SLO 与故障取证自动化|08 运维工程化]] 里「只读与写入自动化标准不同」是同一条纪律。

## 第 3 章 QEMU：用户态的设备与生命周期

QEMU 是三层里最庞大的一层，也是开销最集中的一层。

### 3.1 QEMU 的两个身份

QEMU 有两个身份。作为**模拟器**，它能在没有硬件虚拟化支持的平台上模拟整套机器，代价是慢；作为**VMM**，它借助 KVM 把 CPU 执行交给硬件，只保留设备模拟与管理职责。生产环境的虚机几乎都是后者。

理解这个双重身份的意义在于：**QEMU 的开销主要不在 CPU 执行上，而在设备与管理上**。当一台虚机「不快」时，首先要问的是它的设备路径是否高效，而不是它的 CPU 是否被模拟。

### 3.2 vCPU 线程模型

QEMU 采用「**一个 vCPU 对应一个宿主机线程**」的模型。这些线程各自循环执行「进入 Guest、被退出、处理退出、再进入」的过程。

这个模型带来几个直接推论。第一，**虚机的 CPU 能力取决于宿主机调度器如何调度这些线程**，而不是虚机内部看到的核数；超分与亲和性的影响都由此而来。第二，**vCPU 线程之间的调度延迟会表现为虚机内部的「卡顿」**，即使虚机的 CPU 使用率不高。第三，**宿主机侧的观测可以按线程粒度进行**，这为定位提供了抓手。

### 3.3 主循环与事件

QEMU 还有一个主循环线程，负责处理事件：设备 I/O、定时器、监视器命令、以及与 vCPU 线程的协作。设备 I/O 的处理方式决定了它是阻塞主循环还是交给独立线程。

**主循环是 QEMU 里最容易被忽视的瓶颈点**。当设备 I/O 处理过重时，主循环会成为串行瓶颈，表现为「虚机整体变慢」而不是某一类设备变慢。现代部署会用独立线程或内核态后端（vhost）把这类负载从主循环里挪走，这也是后面 virtio 一篇要展开的内容。

### 3.4 设备模型

设备模型是 QEMU 最复杂的部分。设备分两类：**全模拟设备**（完全由 QEMU 模拟，兼容性最好、性能最差）与**半虚拟化设备**（Guest 侧有专用驱动、宿主机侧有专用后端，性能好但需要驱动支持）。

从性能工程的角度，设备模型的选择是第一位的决策：**同一台虚机，用全模拟网卡与用半虚拟化网卡，性能可以差出一个数量级**。这也是为什么生产环境的虚机几乎全部使用半虚拟化设备。

### 3.5 QEMU 的线程家族

现代 QEMU 的线程不止 vCPU 与主循环，还有几类专职线程。理解这个家族，是读懂宿主机侧线程视图的前提。

| 线程 | 职责 | 与性能的关系 |
| :--- | :--- | :--- |
| vCPU 线程 | 执行 Guest 代码 | 决定 CPU 能力与调度延迟 |
| 主循环线程 | 事件与设备分发 | 过载时成为串行瓶颈 |
| I/O 线程 | 处理块设备 I/O | 与存储路径性能直接相关 |
| 迁移线程 | 搬内存与磁盘状态 | 影响热迁移收敛 |
| 后端线程 | virtio 后端处理 | 与网络和存储吞吐相关 |

**线程数量随配置变化**：启用多队列会创建更多后端线程，启用 I/O 线程池会创建多个 I/O 线程。因此「同一台虚机在不同配置下线程数不同」是正常的，不必惊讶。

线程家族的存在也解释了为什么「按进程看 CPU 占用」会失真：进程级的百分比把各类线程加在一起，看不出谁在消耗。

### 3.6 设备模型的选择依据

设备模型的选择依据可以归纳为三条：**性能要求、兼容性要求、可迁移性要求**。

**性能要求**决定是否使用半虚拟化设备——高吞吐场景几乎必须用。**兼容性要求**决定是否使用全模拟设备——老系统可能没有半虚拟化驱动。**可迁移性要求**决定设备的具体型号——某些设备型号在跨版本迁移时兼容性更好。

三条要求有时会冲突。例如为了极致性能选择最新设备，可能牺牲迁移兼容性；为了兼容性选择老设备，可能牺牲性能。**冲突时的取舍依据是业务优先级**：不能迁移的业务优先性能，需要频繁迁移的业务优先兼容。

### 3.7 主循环瓶颈的一个实例

设想一台虚机「整体变慢」：CPU 使用率不高、内存充足、磁盘与网络单独测试都正常，但业务响应普遍变慢。

这种「哪一项都不突出、整体却慢」的形态，值得怀疑主循环。判断方法是看主循环线程的 CPU 占用：如果它持续偏高，而 vCPU 线程占用不高，说明大量时间花在事件分发上。进一步看设备配置：如果使用了全模拟设备或大量依赖主循环处理的设备，就能解释这一现象。

处置方向是把设备负载从主循环里挪走：改用半虚拟化设备、启用独立 I/O 线程、或启用内核态后端。**主循环瓶颈的典型特征是「所有设备一起变慢」**，这与单个设备慢很容易区分。

### 3.8 QEMU 的配置与可观测性

QEMU 的配置面很大，但从性能工程的角度只需要关注几类：**设备模型**（全模拟还是半虚拟化）、**线程配置**（是否启用独立 I/O 线程与多队列）、**内存配置**（是否使用大页与共享内存）、以及**迁移相关配置**（是否启用压缩与限速）。

这四类配置对应四类性能问题：设备吞吐、主循环瓶颈、内存访问开销、迁移收敛。**把配置与问题对应起来，调参才有方向**。

QEMU 的可观测性则主要来自三个渠道：**libvirt 的统计接口**、**QEMU 自身的监视器**、以及**宿主机的进程与线程视图**。三者覆盖的粒度不同，排查时按需选用。

### 3.9 设备后端的三种形态

设备的宿主机侧后端有三种形态，它们的性能与复杂度递增：**用户态模拟**（后端在 QEMU 里，最简单、最慢）、**内核态加速**（后端在内核模块里，减少用户态切换）、以及**用户态专用进程**（后端在独立进程里，兼顾性能与隔离）。

三种形态的取舍是「性能、隔离、复杂度」的三角。用户态模拟最容易调试但性能最差；内核态加速性能最好但把逻辑放进了内核；用户态专用进程是折中，也是现代高性能虚拟化的主流选择。

**理解三种形态，能解释为什么「同一类设备」在不同部署下性能差异很大**：不是设备类型变了，而是后端形态变了。这一点在下一篇 virtio 与 vhost 里会展开到机制层。

## 第 4 章 KVM：内核态的加速器

KVM 是三层里最薄的一层，但它决定了「快」的上限。

### 4.1 三级接口

KVM 通过字符设备暴露接口，使用方式是典型的「设备 → 创建对象 → 操作对象」三级结构：打开设备得到系统级句柄，创建虚机得到虚机句柄，创建 vCPU 得到 vCPU 句柄。所有操作通过 ioctl 完成，包括配置内存、设置寄存器、启动执行。

这个结构的意义在于：**KVM 提供的是机制，不是策略**。它不知道什么是「一台完整的虚机」，只知道「有一块内存、有一个 vCPU、现在要执行」。策略（设备、生命周期、迁移）全在用户态。相邻专栏 [[LLM/Agent沙箱技术/隔离原语/04 KVM 与硬件虚拟化——MicroVM 隔离的硬件基石|KVM 与硬件虚拟化]] 对这套接口的生命周期有更细的拆解。

### 4.2 vCPU 的进入与退出

vCPU 的执行由一个「运行」调用驱动：它让 CPU 从宿主机态切到 Guest 态开始执行，直到发生某个需要宿主机介入的事件才返回。这个返回就是 VM Exit。

**性能的关键在于 Exit 的频率与处理成本**。频率高、处理贵，虚拟化开销就大；反之开销就小。硬件虚拟化的演进（EPT、posted interrupt 等）本质上都在降低这两个量。

### 4.3 Exit 的来源

Exit 的来源可以按「是否可避免」分类，这个分类对性能优化很实用。

| Exit 来源 | 是否可避免 | 说明 |
| :--- | :--- | :--- |
| 内存访问违规 | 部分 | 页表未建立或权限不足，可通过预映射减少 |
| I/O 端口与 MMIO 访问 | 可减少 | 半虚拟化设备可显著降低此类退出 |
| 特殊指令 | 部分 | 部分指令可配置为不退出 |
| 中断与定时器 | 可优化 | 中断虚拟化与定时器合并可降低频率 |
| 空闲指令 | 可优化 | Guest 空闲时的退出可被识别与优化 |

**把 Exit 按来源分类统计，是定位虚拟化开销的第一步**。如果退出集中在 I/O 类，优化方向是设备路径；如果集中在内存类，优化方向是页表与大页；如果集中在中断类，优化方向是中断虚拟化配置。

### 4.4 KVM 不做什么

KVM 不做的事同样重要：**它不模拟设备**（除了少量内核内设备）、**不管生命周期**、**不做迁移决策**。这些都在 QEMU 或上层。明确这一点，就能理解为什么「KVM 很快」不代表「虚机很快」——KVM 只是把 CPU 执行这一环做快了，其余的环仍在用户态。

### 4.5 KVM 的配置面

KVM 虽然是机制层，但它提供了不少配置面，这些配置会显著影响性能。

**内存相关的配置**包括内存区域的注册方式（是否为大页、是否可合并）、以及地址翻译的缓存策略。**中断相关的配置**包括中断控制器的实现方式（内核内还是用户态）、以及中断投递路径。**执行相关的配置**包括哪些指令允许在 Guest 内执行、哪些必须退出。

**这些配置的默认值通常已针对通用场景优化**，但在特定负载下调整仍有效。例如大页对内存密集负载的收益，中断投递方式对高吞吐网络的收益。调整的原则是「基于实测」，因为默认值的取舍针对的是平均场景，未必匹配你的负载。

### 4.6 Exit 开销的量级

Exit 的开销量级差异很大，这一点常被误解为「虚拟化一定慢」。

**便宜的退出**（如某些中断或简单指令）开销在微秒级甚至更低；**昂贵的退出**（如需要 QEMU 处理的设备 I/O）开销可能高出两三个数量级。因此「虚拟化开销」不是一个单一数字，而是**退出频率乘以平均退出成本的加权和**。

这个分解给出了优化的两条路：**降频率**（减少不必要的退出）与**降成本**（让退出处理更快）。半虚拟化设备主要降成本（把设备访问变成更高效的路径），大页与预映射主要降频率（减少内存相关的退出）。**理解自己在优化哪一条，比盲目调参有效得多**。

### 4.7 一个 Exit 分类的观察方法

Exit 的分类可以通过性能事件统计观察。宿主机的性能计数器能按退出原因给出计数，据此可以判断开销集中在哪一类。

```bash
# 按 KVM 相关事件统计，观察退出与虚拟化开销的分布
perf stat -e 'kvm:*' -a sleep 5

# 观察单个虚机进程的虚拟化相关事件
perf stat -e 'kvm:*' -p <qemu-pid> sleep 5
```

```bash
# 从 tracepoint 层面观察退出原因（需要相应 tracepoint 可用）
perf trace -e 'kvm:kvm_exit' -p <qemu-pid>
```

**观察方法的要点是「先分类、再看量级」**：只看总退出数没有意义，必须知道它们分别来自哪里。这与第 4.3 节的分类表配套使用——表给方向，命令给数据。

### 4.8 KVM 与容器运行时的关系

一个常见的疑问是：KVM 与容器运行时是什么关系？答案是**它们在不同层次上，且可以组合**。

容器运行时主要依赖内核的命名空间与资源控制做隔离，不依赖硬件虚拟化；KVM 提供的是硬件虚拟化能力。两者的组合形态是「用虚机承载容器」——在虚机里跑容器运行时，从而同时获得硬件级隔离与容器化的部署体验。

**理解这层关系，能避免把「虚拟化」与「容器化」当成互斥选项**。它们解决的是不同问题：一个解决隔离强度，一个解决交付效率。相邻专栏 [[LLM/Agent沙箱技术/00 专栏导览|Agent 沙箱技术专栏]] 讨论的隔离光谱，正是把两者放在同一个坐标系里比较。

## 第 5 章 控制路径与数据路径

三层之间流动的信息可以分成两条路径，区分它们能让排障更清晰。

### 5.1 两条路径

**控制路径**指的是管理操作：创建、启动、暂停、迁移、查询。它的特点是低频、与业务无直接关系，但一旦阻塞会让操作「卡住」。**数据路径**指的是虚机运行时的数据流动：vCPU 执行、设备 I/O、内存访问。它的特点是高频、直接决定业务性能。

两条路径的组件是重叠的（都经过 QEMU），但**它们的瓶颈来源完全不同**。控制路径的瓶颈通常是接口调用或锁竞争，数据路径的瓶颈通常是设备模型或内存映射。

### 5.2 控制路径的开销

控制路径的开销主要来自三处：**接口层的序列化**（XML 解析与校验）、**QEMU 的状态变更**（设备热插拔、内存调整）、以及**内核的配置更新**（内存槽、设备注册）。

这类开销的典型表现是「操作变慢」而不是「业务变慢」。例如批量创建时平台响应变慢，可能只是控制路径拥堵，与虚机性能无关。**把控制路径的问题当成数据路径的问题，是排障里常见的误判**。

### 5.3 数据路径的开销

数据路径的开销集中在三处：**vCPU 的退出与进入**、**设备 I/O 的转发**、**内存的地址翻译**。这三处正好对应后面三篇（vCPU 调度、virtio、内存）的主题。

它们有一个共同特征：**开销与负载相关，而不是与配置相关**。同样的配置，负载不同，开销占比可能差很多。因此数据路径的优化必须基于实测，而不能只凭配置推断。

### 5.4 排障时的意义

区分两条路径的意义在于选择排查方向。一个实用的判据是：**业务受影响还是操作受影响**。业务受影响（虚机变慢、网络抖动），查数据路径；操作受影响（创建慢、查询慢、迁移卡），查控制路径。

这个判据看似简单，却能避免大量无效排查。它与 [[SRE/CVM集群可靠性工程/01 CVM 服务地图——用户操作、控制面与数据面依赖|CVM 服务地图]] 里「控制面与数据面解耦」是同一个观察角度，只是把视角从平台收到了单机。

### 5.5 两条路径的耦合点

控制路径与数据路径并非完全独立，它们有几个耦合点，理解这些耦合点能解释一些「奇怪」的现象。

**耦合点一：内存调整**。在线调整虚机内存会同时触及控制路径（配置变更）与数据路径（内存区域重映射），因此这类操作可能引起短暂的性能抖动。**耦合点二：设备热插拔**。热插拔设备会更新 QEMU 的设备表，也可能触发中断与内存区域变化，同样会带来抖动。**耦合点三：迁移**。迁移既是控制操作，又持续搬运数据路径上的状态。

**耦合点的共同特征是「控制动作引发数据抖动」**。这类现象容易被误判为「虚机不稳定」，实际是控制路径的正常副作用。排查时如果发现抖动与某个管理操作时间吻合，就应当往耦合点上想。

### 5.6 一个路径判别的实例

设想一次批量创建「很慢」，但已经运行的虚机业务正常。

按路径判据，这是「操作受影响」，属于控制路径。排查方向因此是接口调用与状态变更，而不是设备或内存。常见原因包括：接口层序列化开销大、批量操作未并发、状态查询串行阻塞。

反过来，如果现象是「已运行虚机业务变慢」，则属于数据路径，排查方向是 vCPU、设备与内存。

**这个实例的价值在于它演示了「判据先行」**：在动手之前先用一句判据把范围砍掉一半，比漫无目的地查三个层高效得多。

### 5.7 两条路径与 SLO 的关系

两条路径最终都要服务于同一个目标：**业务的服务等级**。因此它们可以各自对应一类 SLO。

数据路径对应**性能类目标**：延迟、吞吐、可用性。控制路径对应**可操作性目标**：操作的成功率与响应时间（如「创建请求在多少秒内完成」）。

**把两类目标分开定义**，能避免一个常见错误：用性能目标去衡量控制操作，或用操作成功率去掩盖性能退化。这与 [[SRE/CVM集群可靠性工程/08 运维工程化——巡检、维护预检、SLO 与故障取证自动化|08 运维工程化]] 里「SLI 的选择要与目标匹配」是同一条原则。

## 第 6 章 启动一台虚机发生了什么

把前面几章合起来，看一次启动的完整过程。

### 6.1 从 XML 到进程

启动的第一步是把声明变成进程：解析 XML、校验参数、生成 QEMU 的启动参数、拉起进程。这一步的开销在控制路径上，与虚机运行后的性能无关。

**这一步最容易出问题的地方是参数生成**：配置里的某些组合可能生成相互冲突的参数，表现为启动失败或启动后行为异常。排查这类问题要回到 XML 与生成的命令行做对照。

### 6.2 内存与设备的准备

第二步是准备内存与设备：向内核注册内存区域、创建 vCPU、初始化设备后端、建立设备与内存的关联。这一步的开销与虚机规格相关——内存越大、设备越多，准备时间越长。

**这一步是「启动耗时」的主要来源**。大内存虚机的启动慢，通常不是因为 CPU 慢，而是因为内存注册与页表准备的时间。理解这一点，能解释为什么「加内存」会让启动时间明显上升。

### 6.3 vCPU 的开始执行

第三步是让 vCPU 开始执行：设置初始寄存器与入口地址，进入运行循环。从这一刻起，虚机开始执行固件与引导程序，进入我们熟悉的启动流程。

**这一步之后，性能的主导权交给了数据路径**。虚机启动的快慢取决于引导过程与设备初始化，而引导过程中的 I/O 又会回到设备路径上。

### 6.4 启动耗时的构成

把三段拆开，启动耗时可以这样理解：**控制路径的准备时间（与规格相关）+ 数据路径的引导时间（与 I/O 路径相关）+ 固件与内核自身的启动时间（与镜像相关）**。

三段各有优化方向：第一段靠简化配置与设备，第二段靠优化设备路径与缓存镜像，第三段靠精简镜像。**不做拆分就优化启动速度，很容易优化错方向**。

### 6.5 启动之外：热插拔与在线调整

启动只是生命周期的一个瞬间。运行中的虚机还会经历热插拔与在线调整，它们与启动共享同一套机制，但风险更高。

**热插拔设备**需要在运行中注册设备、建立后端、通知 Guest；**在线调整内存或 CPU**需要更新配置并让 Guest 感知。两者的共同点是**它们都要在不中断业务的前提下改变状态**，因此容错要求更高。

从性能工程的角度，这类操作的要点是**评估抖动窗口**：变更会不会引起短暂的延迟抬升，抬升多久，业务能否容忍。**把「变更的抖动」当成一个需要度量的量**，而不是假设它「应该没影响」，是成熟运维的标志。

### 6.6 启动失败的排查顺序

启动失败的排查应当按「声明 → 进程 → 内核」的顺序。**先看声明**：XML 是否合法、参数是否冲突。**再看进程**：QEMU 是否被拉起、日志里是否有参数错误。**最后看内核**：内存注册或设备创建是否被拒绝。

这个顺序与启动过程的顺序一致，因此每往前一步都有明确证据。**倒过来查（先看内核再看声明）会浪费大量时间**，因为大多数启动失败发生在声明与进程两段。

### 6.7 启动性能的一个实例

设想一个场景：同一批镜像，在小规格虚机上启动快，在大规格虚机上启动慢。

按启动耗时的三段拆分，差异主要来自第一段（准备时间与规格相关）——内存注册与页表准备的时间随内存增大而上升。第二、三段（引导与镜像）在两台虚机上基本相同。

因此优化方向不是「改镜像」，而是「降低准备开销」：使用大页减少页表条目、预分配内存避免启动时的分配延迟、或减少不必要的设备。

**这个实例演示了「先拆分再优化」的价值**：不拆分就会误以为是镜像问题，从而优化错方向。

## 第 7 章 宿主机侧观察一台运行中的虚机

观测能力决定了排查能力。这一章给出四个观察视角。

### 7.1 进程视角

从进程视角看，虚机是 QEMU 进程。可以观察它的内存占用、CPU 时间、以及打开的文件与设备。

```bash
# 找到虚机的 QEMU 进程
ps -eo pid,ppid,comm,args | grep qemu

# 查看其资源占用与线程
top -H -p <qemu-pid>
```

**进程视角的价值是判断「虚机整体占了多少资源」**，局限是它把 vCPU 线程、主循环、I/O 线程混在一起，看不出分工。

### 7.2 线程视角

从线程视角看，虚机的 vCPU 各自是一个线程。可以按线程观察 CPU 时间、调度延迟、以及绑核情况。

```bash
# 按线程列出，识别 vCPU 线程与 I/O 线程
ps -T -p <qemu-pid> -o tid,comm,pcpu,psr

# 观察单个 vCPU 线程的调度与迁移
perf sched record -p <qemu-pid>
```

**线程视角是定位 vCPU 性能问题的关键**：vCPU 线程是否被抢占、是否在核间迁移、是否与别的负载争抢，都在这个视角下暴露。

### 7.3 libvirt 视角

从 libvirt 视角看，虚机是一个域，可以拿到统一的统计：CPU 时间、内存使用、块设备 I/O、网卡收发。

```bash
virsh domstats <domain> --state --cpu-total --balloon --block --interface
```

**libvirt 视角的价值是「统一且稳定」**，适合做长期观测与告警；局限是粒度较粗，且依赖 libvirt 的采集实现。

### 7.4 内核视角

从内核视角看，虚机是一组被内核调度的线程与一块被映射的内存。可以观察调度延迟、内存映射、以及中断分布。

```bash
# 调度延迟与运行队列
cat /proc/schedstat
cat /proc/pressure/cpu

# 中断与软中断分布
cat /proc/interrupts
cat /proc/softirqs
```

**内核视角是定位「宿主机侧原因」的最终依据**。当 libvirt 与 QEMU 层都看不出问题时，答案往往在内核的调度、内存或中断里。

四个视角的关系是**由外向内、由粗到细**：先用进程与 libvirt 视角确认现象，再用线程与内核视角定位原因。这与 [[SRE/CVM集群可靠性工程/03 云盘为什么慢——Guest、QEMU、网络与 Ceph 的联合分析|03 云盘为什么慢]] 里的分层归因是同一种方法。

### 7.5 一个观测的最小组合

四个视角不必全用，一个最小组合通常就够了：**进程视角看整体、线程视角看 vCPU、内核视角看调度**。三者合起来能覆盖大多数「虚机慢」的问题。

| 目标 | 最小命令组合 |
| :--- | :--- |
| 整体资源 | `ps` / `top -H -p <pid>` |
| vCPU 调度 | `ps -T -p <pid>` + `perf sched` |
| 宿主机压力 | `/proc/pressure/cpu`、`/proc/schedstat` |
| 设备与内存 | `virsh domstats` |

**libvirt 视角适合长期观测而非现场排查**：它的采样周期与粒度决定了它更擅长看趋势，而不是看瞬间。把工具的定位分清，能避免在现场用错工具。

### 7.6 观测的常见陷阱

宿主机侧观测有三个常见陷阱。**第一，采样偏差**：低频采样会错过短时尖峰，而很多性能问题正是短时尖峰。**第二，观测开销**：高频采样与全量追踪会显著影响被观测对象，故障时尤其要克制。**第三，视角混淆**：把进程级数字当成线程级、把宿主机数字当成虚机数字。

三个陷阱的应对分别是：**提高关键指标的采样率**、**先粗后细、按需加深**、以及**明确每个数字的来源与口径**。

第三条最容易被忽略，也最容易导致错误结论。**看任何数字之前先问「它统计的是谁」**，是一个值得养成的习惯。

### 7.7 一个完整的现场采集清单

把四个视角的命令整理成一份现场采集清单，按顺序执行可以得到完整快照。

| 顺序 | 视角 | 命令 | 回答的问题 |
| :--- | :--- | :--- | :--- |
| 1 | libvirt | `virsh list` / `domstats` | 域状态与总体统计 |
| 2 | 进程 | `ps` / `top -H -p <pid>` | 整体资源占用 |
| 3 | 线程 | `ps -T -p <pid>` | vCPU 与 I/O 线程分布 |
| 4 | 内核 | `/proc/pressure/cpu`、`/proc/schedstat` | 宿主机调度压力 |
| 5 | 事件 | `perf stat -e 'kvm:*'` | 虚拟化开销分布 |

清单的顺序与「由外向内」一致。**它的用途是「留证」**：在处置之前先把五步采完，避免事后无从复盘。这与 [[SRE/CVM集群可靠性工程/01 CVM 服务地图——用户操作、控制面与数据面依赖|CVM 服务地图]] 里「先保存现场、再考虑处置」的纪律一致。

## 第 8 章 一次调用链的追踪实例

下面用一个实例把调用链串起来。假设某台虚机「偶尔卡顿」，但 CPU 使用率不高。

### 8.1 从现象出发

「偶尔卡顿、CPU 不高」这个组合，指向的不是计算能力不足，而是**执行被中断或延迟**。第一步应当确认卡顿是否与宿主机的调度有关。

### 8.2 逐层收敛

先看 libvirt 视角的 CPU 时间：如果虚机的 CPU 时间在卡顿时刻并未下降，说明虚机一直在「想跑」，只是没被调度到。再看线程视角：如果 vCPU 线程的调度延迟升高，说明它在等 CPU。最后看内核视角：如果运行队列变长或 CPU 压力升高，说明宿主机上有别的负载在争抢。

三层证据合起来，结论是「vCPU 被宿主机调度延迟」，而不是「虚机计算不够」或「设备慢」。**处置方向因此是调整超分、绑核或隔离干扰负载，而不是给虚机加核**。

### 8.3 这个实例的启示

这个实例的价值在于它演示了「**从外向内收敛**」的排查顺序：先用粗粒度视图定位到层，再用细粒度视图定位到因。它也说明一个反直觉的事实：**虚机卡顿的原因可能在虚机之外**，而这一点只有通过宿主机侧的多视角观察才能看到。

### 8.4 另一个方向的实例

上一节的实例是「虚机卡顿、CPU 不高」。反过来看一个「CPU 很高、但业务不慢」的实例：虚机的 CPU 使用率长期接近满值，业务却反馈正常。

排查方向应当先确认「高」的性质：是 Guest 内真的有计算负载，还是 Guest 在忙等（spin）。**忙等型的高 CPU 往往来自 Guest 内部的自旋锁或轮询驱动**，此时提高 CPU 配额没有收益，反而会加剧宿主机争抢。

确认方法是从宿主机侧看 vCPU 线程的状态：如果线程持续处于运行态且退出频率很低，说明 Guest 在纯计算；如果退出频繁，说明开销在退出处理上。**「高 CPU」本身不是结论，它需要被进一步分解**。这个实例与第一个实例正好互补：一个是「想跑跑不了」，一个是「一直在跑但没意义」。

### 8.5 两个实例的共同方法

两个实例（「想跑跑不了」与「一直在跑没意义」）的共同方法是**把现象分解成可验证的子问题**。

具体来说，分三步：**第一步，确认现象属于哪条路径**（业务慢还是操作慢）；**第二步，用由外向内的视角把范围收敛到层**（libvirt → 进程 → 线程 → 内核）；**第三步，在该层找到能解释现象的机制**（调度延迟、忙等、主循环阻塞）。

三步的共同点是**每一步都产出可验证的结论**，而不是猜测。这也是本篇与整个专栏的方法论主线：**先分层、再收敛、后解释**。

## 第 9 章 常见误区与反例

第一，**把 KVM 当成「虚拟机」**。KVM 只是加速器，不模拟设备、不管生命周期；「KVM 很快」不等于「虚机很快」。

第二，**把 libvirt 当成性能瓶颈**。它主要在控制路径上，业务性能问题很少出在它身上。

第三，**混淆控制路径与数据路径**。操作慢与业务慢是两类问题，排查方向完全不同。

第四，**只看虚机内部的指标**。虚机内部看不到宿主机调度与内存映射，很多问题必须从宿主机侧看。

第五，**认为虚拟化开销是固定的**。开销与负载、设备模型、内存配置都相关，必须实测。

第六，**用单一视角下结论**。进程视角、线程视角、libvirt 视角、内核视角各有盲区，需要交叉。

第七，**把忙等型高 CPU 当成计算不足**。提高配额没有收益，应当从 Guest 内的自旋与轮询入手。

第八，**忽略控制动作引发的抖动**。在线调整与热插拔会引起短暂性能变化，属于正常副作用，不应误判为不稳定。

第九，**把观测数字的来源搞混**。进程级、线程级、虚机级、宿主机级的口径不同，混用会得出错误结论。

第十，**把虚拟化与容器化当成互斥选项**。它们解决不同问题，组合形态（虚机承载容器）在生产中很常见。

第十一，**把 libvirt 统计与平台统计直接比较**。口径不同，数字不同是正常的；先对齐口径再比较。

## 第 10 章 边界与反例

第一，**三层模型不覆盖所有虚拟化实现**。有些实现没有独立的 libvirt 层（如容器运行时），有些没有独立的内核加速层（如全模拟）。套用模型前先确认实现形态。

第二，**观察工具本身有开销**。线程级与内核级观测在高频采样时会影响被观测对象，故障现场要谨慎使用。

第三，**配置正确不等于性能达标**。半虚拟化设备、大页、绑核都只是「有可能更快」，是否更快取决于负载特征。

第四，**性能数据必须绑定场景**。同一台虚机，不同负载下的开销占比差异很大，跨场景外推结论容易出错。

第五，**抽象层越多，定位越依赖分层能力**。三层加平台层，任何一层出问题都可能表现为「虚机慢」；定位能力本质上就是分层归因的能力。

第六，**把职责划分等同于进程划分**。组件可以被替换（如轻量 VMM 替代 QEMU），职责划分保持不变。

第七，**把单次观测当成基线**。性能判断需要基线，单次数据无法说明是否异常。

第八，**跳过「现象归类」直接查底层**。先判断是控制路径还是数据路径问题，能砍掉一半无效排查。

行文至此，把本篇落点收在两条原则上。其一，架构即权衡——三层分工换来了通用与可替换，代价是排障必须在层之间往返，这份代价要靠多视角观察来偿还。其二，复杂性不会消失只会转移——硬件虚拟化把 CPU 执行的开销降了下来，却把开销转移到了设备、内存与调度上，这正是后面几篇要逐一拆解的对象。下一篇聚焦其中最容易被忽视的一处：vCPU 在宿主机上如何被调度，以及超分到底超的是什么。相邻的组件基础可参见 [[云原生/OpenStack/03 虚拟化地基——KVM、QEMU 与 libvirt|03 虚拟化地基]]。

这张表把三层职责与四个观察视角并列，用于快速定位「该看哪一层」。使用时先按现象归类（业务慢还是操作慢），再选对应视角，避免三处平铺地查一遍。表中「局限」一列正是需要交叉验证的原因——任何单一视角都不足以给出结论。
