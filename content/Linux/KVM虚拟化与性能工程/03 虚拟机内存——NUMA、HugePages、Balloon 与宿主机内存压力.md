# 03 虚拟机内存——NUMA、HugePages、Balloon 与宿主机内存压力

**摘要：**

虚机的内存比 CPU 更容易被误解：它有三层地址、四种口径、以及三套回收机制，而虚机内部看到的永远只是最上面一层。本文沿着「虚机的一次内存访问在宿主机上发生了什么」这条线，把地址翻译、NUMA 位置、大页、气球回收、页共享与宿主机内存压力逐一拆开，给出每一层的判据、观测方法与误读陷阱。全文回答两个问题：虚机的内存访问成本由哪些因素决定，以及宿主机的内存压力如何传导进虚机。文中的命令与观察方式取自 2026 年 9 月的现场记录，涉及具体数值处标注口径；vCPU 线程模型与调用链请参见本专栏 01、02 篇。

---

## 第 1 章 虚机内存的三层地址

理解虚机内存，先要理解「地址」在虚拟化环境下有三个层次。

### 1.1 三层地址

**客户机虚拟地址（Guest Virtual Address，GVA）**是虚机内部进程看到的地址，与物理机上的进程虚拟地址性质相同。**客户机物理地址（Guest Physical Address，GPA）**是虚机看到的「物理地址」——它并不是真的物理地址，而是宿主机分配给这台虚机的一段地址空间。**宿主机物理地址（Host Physical Address，HPA）**才是真正的内存条上的地址。

三层的映射关系是：**GVA 经 Guest 页表映射到 GPA，GPA 再经虚拟化层的第二级页表映射到 HPA**。因此一次内存访问要经过两级翻译，而不是一级。

### 1.2 地址翻译的成本

两级翻译的成本体现在两处：**多一次查表**，以及**缓存失效时的代价更高**。为了缓解，硬件提供了地址翻译缓存：一级翻译的结果缓存在 Guest 可见的 TLB 里，二级翻译的结果缓存在专门的缓存里。

**这两级缓存的大小决定了地址翻译的开销**。当虚机的工作集超过缓存的覆盖范围时，每次访问都可能触发查表，表现为「内存带宽没跑满但延迟很高」。这也是大页在虚机场景下收益明显的原因——**大页让同样大小的内存只需要更少的缓存条目**。

### 1.3 为什么这个模型重要

三层地址模型解释了三个常见现象。

**第一，「虚机有多少内存」与「宿主机消耗了多少内存」是两个不同的数**。虚机声明 8 GiB，宿主机上对应的可能是 8 GiB 加一部分管理开销，也可能因为页共享而更少。**第二，虚机内部的延迟包含了二级翻译的开销**，这部分在物理机上不存在。**第三，内存超分在物理机上不存在，而在虚机上是一个必须管理的变量**——因为 GPA 空间可以承诺得比 HPA 多。

### 1.4 与物理机的差别

把差别列成一张表，便于对照。

| 维度 | 物理机 | 虚机 |
| :--- | :--- | :--- |
| 地址层次 | 两级（虚拟、物理） | 三级（GVA、GPA、HPA） |
| 翻译开销 | 一次查表 | 两级查表加两级缓存 |
| 内存超分 | 不适用 | 可以承诺多于实际 |
| 回收机制 | 页回收、swap | 页回收、swap、气球、页共享 |
| 观测视角 | 一个（操作系统内） | 两个（Guest 内、宿主机侧） |

**表的最后一行最关键**：虚机内存问题必须从两个视角看，只看一个必然片面。这与 01 篇「虚机慢的原因可能在虚机之外」是同一条纪律。

### 1.6 三层地址与超分的关系

三层地址模型是内存超分的技术前提，这一点值得展开。

**在物理机上，「承诺的内存」与「实际的内存」是同一件事**——分配 8 GiB 就是占用了 8 GiB。**在虚机上，GPA 空间可以承诺得比 HPA 多**，因为 GPA 只是一层映射，映射到多少 HPA 是可以延迟决定的。

这个解耦带来两个能力：**超分**（承诺总量大于物理总量）与**回收**（把已承诺的 HPA 收回来）。气球的本质就是「改变 GPA 到 HPA 的映射」，把一部分映射取消掉。

**理解了这一点，就能理解为什么内存超分是有代价的**：超分把「承诺」与「实际」解耦，代价是「承诺可能无法兑现」。兑现失败时，只能靠 swap 或 OOM。**超分的规模上限，就是「兑现失败时可承受的程度」**。

### 1.7 内存虚拟化的四种优化手段总览

把本篇涉及的优化手段汇总，可以看到它们各自解决什么。

| 手段 | 解决的问题 | 代价 |
| :--- | :--- | :--- |
| NUMA 绑定 | 访问落在本地节点 | 灵活性下降 |
| 大页 | 翻译缓存压力 | 不可回收、预留风险 |
| 气球 | 宿主机内存压力 | Guest 可用内存减少 |
| 页共享 | 同构负载的内存浪费 | 扫描与复制开销 |

**四种手段的共同点是「用确定性换利用率」或反之**：NUMA 绑定与大页换确定性，气球与页共享换利用率。

**理解这张表，就能理解为什么内存优化不能「全都开」**：它们方向不同，同时拉满会互相抵消。**选择依据是业务对确定性还是利用率更敏感**。

## 第 2 章 内存的分配：从声明到实际

虚机的内存从「声明」到「实际占用」，中间有几个环节。

### 2.1 内存的几种口径

虚机内存至少有四种口径，混用会导致判断错误。

**配置内存**是虚机声明的大小。**当前内存**是气球调整后的实际可用量（可能小于配置）。**使用内存**是 Guest 内部统计的已用内存。**宿主机占用**是 QEMU 进程在宿主机上的实际内存消耗。

四个口径的关系是：**配置 ≥ 当前 ≥ 使用，而宿主机占用与它们都不相等**（可能更多，因为管理开销；也可能更少，因为页共享）。

**排查内存问题时，先明确在看哪个口径**。这也是 01 篇「先问统计的是谁」在本篇的具体应用。

### 2.2 预分配与懒分配

虚机的内存可以**预分配**（启动时就占用宿主机内存）或**懒分配**（访问到时才占用）。

**预分配的优点是确定性**：内存访问不会因为「第一次触碰」而变慢，也不会因为宿主机内存紧张而被拒绝。**缺点是启动慢、占用高**。**懒分配的优点是启动快、占用省**，缺点是在宿主机内存紧张时，分配可能失败或触发回收。

**选择依据是业务对确定性的要求**。延迟敏感的业务通常选预分配，配合大页使用；弹性要求高的业务可以选懒分配。

### 2.3 内存区域注册

虚机的内存在宿主机上表现为一段被注册的内存区域。注册时确定三件事：**这段内存对应哪些 GPA、它在宿主机上的位置、以及它的属性**（是否大页、是否共享）。

**注册发生在虚机启动时，但可以在运行中调整**（如内存热插拔）。运行中调整会触发映射更新，可能带来短暂的性能抖动——这与 01 篇「控制动作引发数据抖动」是同一类现象。

### 2.4 观测方法

内存的观测要从两个视角做。

```bash
# 宿主机视角：QEMU 进程的实际内存占用
ps -o pid,rss,vsz,comm -p <qemu-pid>

# 宿主机视角：内存与 swap 使用
free -h
cat /proc/meminfo | grep -E 'MemTotal|MemAvailable|Committed'

# 虚机视角：气球与内存统计
virsh dommemstat <domain>
```

```bash
# 虚机内部：内存与 swap 使用
free -h
cat /proc/meminfo
```

**两个视角的数字对不上是正常的**，因为口径不同。关键是知道差异来自哪里：管理开销、页共享、还是大页预留。

### 2.5 一个内存口径的实例

设想一台虚机配置 16 GiB 内存，宿主机上 QEMU 进程显示占用 17.2 GiB。

差额来自哪里？常见有三处：**设备与管理开销**（虚拟设备的缓冲区、元数据）、**大页对齐的开销**（预留量按大页对齐，可能有零头）、以及**进程自身的运行时内存**。

反过来，如果 QEMU 进程占用**少于**配置内存，原因通常是**页共享**或**内存尚未被完全触碰**（懒分配）。

**这个实例说明「宿主机占用」是一个综合量**，它与配置内存之间没有固定关系。把它当成「虚机用了多少」会得出错误结论。

### 2.6 内存热插拔的代价

内存热插拔让虚机可以在运行中增加内存，但它的代价常被低估。

**第一，Guest 必须支持**：需要 Guest 内核与驱动配合，否则新内存无法被识别。**第二，映射更新有抖动**：宿主机需要更新内存区域注册，可能带来短暂性能变化。**第三，NUMA 落位不确定**：新加的内存落在哪个节点，取决于当前的内存分布，可能与原有内存不在同一节点。

**第三点最容易被忽略**：热插拔之后，虚机的内存可能横跨两个节点，导致跨节点访问增加。**因此热插拔之后应当验证 NUMA 分布**，而不是假设「加内存只有好处」。

### 2.7 一个分配策略的选择

预分配与懒分配的选择可以按三个问题来定：**业务是否对首次访问延迟敏感**、**宿主机内存是否紧张**、**是否需要确定性**。

三者都指向「预分配」时，就选预分配。例如延迟敏感的数据库虚机、宿主机内存充裕、需要确定性。反之选懒分配。

**混合策略在实践中很常见**：关键虚机预分配，一般虚机懒分配。**这也是一种按业务分级的做法**，与 02 篇「按业务等级配置策略」一致。

需要注意的是，**预分配与超分是冲突的**：预分配意味着「承诺即占用」，因此这类虚机不能被超分。**混布场景下要把两者分开规划**。

### 2.8 一个内存水位监控的要点

内存水位的监控有三个要点。

**第一，区分口径**：要分别监控「配置内存」「实际占用」「可用内存」与「swap 使用」，而不是只监控一个。**第二，按层监控**：宿主机层（可用内存、swap、压力）、虚机层（虚机内可用内存）、以及两者之间的映射（哪台虚机占用最多）。**第三，看趋势与档位**：趋势用于提前预警，档位用于决定动作。

**三个要点合起来，构成内存监控的最小集合**。只有宿主机可用内存这一个数字，既无法判断是谁的问题，也无法决定该做什么。

**这与 06 篇「容量水位要分维度分故障域」是同一纪律**，只是对象从容量换成了内存。

### 2.9 内存分配与启动性能

内存分配策略直接影响启动性能，这一点与 01 篇「启动耗时三段拆分」对应。

**预分配会让启动变慢**：它需要在启动时分配并触碰全部内存，大规格虚机的这一步可能耗时数秒甚至更长。**懒分配启动快**：它只建立映射，不触碰内存。

**因此「启动慢」与「运行稳」是一对取舍**：预分配牺牲启动速度换运行确定性。**选择依据是虚机的生命周期**——长期运行的虚机值得预分配，频繁创建销毁的虚机更适合懒分配。

**这也是「预热」思路在内存上的体现**：把耗时的准备动作提前到非关键路径。与 02 篇「镜像预热」是同一思路。

## 第 3 章 NUMA：内存的位置

内存访问的成本不仅取决于大小，还取决于「内存在哪里」。

### 3.1 NUMA 是什么

**NUMA（Non-Uniform Memory Access）指的是：CPU 访问不同内存区域的延迟不同**。多路服务器上，每个 CPU 有自己的本地内存；访问本地内存快，访问其他 CPU 挂的内存慢。

因此「内存有多少」之外，还有「内存在哪里」这个问题。**跨节点访问的延迟可能是本地访问的一倍以上**，这对内存密集型的负载影响很大。

### 3.2 虚机与 NUMA

虚机的 NUMA 问题比物理机复杂，因为多了一层映射。虚机内部可以有自己的 NUMA 拓扑（vNUMA），而它在宿主机上如何落位，取决于配置。

三种典型配置：**不感知 NUMA**（虚机内部单一节点，宿主机上随机分布）、**透传拓扑**（虚机看到与宿主机一致的拓扑）、**自定义拓扑**（按需配置）。

**大规格虚机应当使用透传或自定义拓扑**，否则虚机内部的调度决策会与实际的物理位置脱节，导致跨节点访问增多。

### 3.3 跨节点访问的代价

跨节点访问的代价体现在两处：**延迟上升**，以及**节点间的互联带宽成为瓶颈**。当多个虚机同时跨节点访问时，互联链路会拥塞，表现为整体性能下降。

**判断是否跨节点访问的方法**是看内存访问的性能计数，或直接看内存是否分配在预期的节点上。

```bash
# 查看 NUMA 拓扑与各节点的内存使用
numactl --hardware
numastat -m

# 查看 QEMU 进程内存在各节点的分布
numastat -p <qemu-pid>
```

**`numastat -p` 是虚机场景下最有用的命令之一**：它直接回答「这台虚机的内存落在哪个节点上」。如果发现大量内存在非预期节点，就找到了优化点。

### 3.4 绑定策略

NUMA 的绑定策略有三种：**不绑定**（让内核决定）、**绑定到指定节点**（把虚机内存限制在某个节点）、**与 CPU 绑定一致**（vCPU 与内存绑到同一节点）。

第三种是延迟敏感场景的标准做法。**CPU 与内存绑定一致，才能保证访问落在本地**；只绑 CPU 或只绑内存，收益都会打折——这一点在 02 篇「绑核与 NUMA 的关系」里已从 CPU 侧讲过。

```bash
# 查看与设置虚机的 NUMA 绑定
virsh numatune <domain>
```

### 3.5 观测与陷阱

NUMA 观测有两个陷阱。**第一，只看总量不看分布**：内存总量充足，但集中在某个节点上，仍会导致跨节点访问。**第二，只看配置不看实际**：配置了绑定不等于内存真的落在该节点，必须从宿主机侧验证。

**「配置正确、实际不符」在 NUMA 场景下相当常见**，原因包括配置未生效、内存被迁移、或大页预留的位置与预期不同。因此验证必须看实际分布，而不是看配置项。

### 3.6 vNUMA 的配置取舍

vNUMA（虚机内部可见的 NUMA 拓扑）的配置有三种取舍。

**不暴露拓扑**：虚机内部看到单一节点，简单但会让 Guest 内的调度决策与实际位置脱节。**暴露宿主机拓扑**：虚机看到与宿主机一致的节点结构，Guest 内的调度更合理，但要求虚机的核数与宿主机拓扑匹配。**自定义拓扑**：按业务需求配置，最灵活但需要理解业务的内存访问模式。

**取舍的依据是虚机规格与业务特征**：小规格虚机通常不需要 vNUMA；大规格（跨节点的规格）应当暴露拓扑，否则跨节点访问会明显增加。

**这也是「大虚机不等于小虚机的放大版」的一个例证**：规格越大，拓扑的影响越显著。

### 3.7 NUMA 与迁移

NUMA 与迁移之间存在约束，与 02 篇「绑核与迁移」的张力类似。

**迁移要求目标宿主机能满足 NUMA 要求**：目标机器是否有足够的空闲内存在指定节点上、拓扑是否兼容、迁移后是否需要重配绑定。

**大规格虚机的迁移尤其容易受限**：它需要跨节点的资源，而目标机器可能只有部分节点有空闲，导致迁移失败或落位不理想。

**因此在规划大规格虚机时，要同时考虑「能不能放」与「能不能迁」**。只考虑前者，会在需要迁移时才发现无处可去。这与 06 篇「疏散目标要换故障域」是同一条思路。

### 3.8 NUMA 与中断亲和性

NUMA 的优化不止内存绑定，中断的亲和性同样重要。

**设备中断如果落在错误的节点上，会导致跨节点访问**：中断处理线程在节点 A，而它访问的数据在节点 B，于是每次中断都跨节点。这在高吞吐网络场景下影响明显。

因此 NUMA 优化的完整形态是：**vCPU 绑定、内存绑定、以及中断亲和性三者一致**。三者中缺一个，收益都会打折。

**中断亲和性的观测与配置**：查看中断在各核的分布，判断是否集中在非预期节点。这与 02 篇「按核观察」的方法一致。

**实践中，中断亲和性最容易被忽略**，因为它不像 CPU 与内存绑定那样有直观的配置项。

## 第 4 章 HugePages：减少翻译成本

大页是虚机内存优化里收益最直接的一项，但它有前提条件。

### 4.1 为什么需要大页

**大页的核心作用是减少地址翻译的缓存条目需求**。普通页通常是 4 KiB，一个 2 MiB 的大页相当于 512 个普通页；因此同样大小的内存，用大页只需要 1/512 的缓存条目。

在虚机场景下，这个收益被放大：**因为要经过两级翻译，每一级都需要缓存**。大页让两级的缓存压力同时下降，因此虚机的收益通常比物理机更明显。

### 4.2 显式大页与透明大页

大页有两种实现方式。**显式大页（Static HugePages）**在系统启动时预留，之后由使用者显式分配。**透明大页（Transparent HugePages，THP）**由内核自动合并与分配，无需显式预留。

| 维度 | 显式大页 | 透明大页 |
| :--- | :--- | :--- |
| 分配方式 | 预留后显式使用 | 内核自动 |
| 确定性 | 高（预留即保证） | 中（可能分配失败） |
| 内存碎片 | 需要连续内存 | 后台合并，可能有抖动 |
| 适用场景 | 虚机内存、数据库 | 通用负载 |

**虚机场景通常选显式大页**：它保证内存一定以大页形式分配，不会在运行中因为合并失败而退化为普通页。透明大页则更适合「不需要强确定性」的通用负载。

### 4.3 虚机场景的选择

虚机内存使用大页时，有几个决策点：**用多大页**（常见 2 MiB 与 1 GiB）、**是否全部使用**（还是仅关键部分）、**如何预留**（启动时预留多少）。

**1 GiB 大页的收益更大，但对内存连续性的要求更高**，预留失败的概率也更大。因此实践中常见的是「用 2 MiB 大页覆盖主要内存，关键部分用 1 GiB」。

**「是否全部使用」取决于业务**：全部使用最简单，但会让内存不可回收（大页一旦预留就难以归还）；部分使用更灵活，但配置更复杂。

### 4.4 大页的代价与陷阱

大页有三个代价。**第一，内存不可回收**：大页预留后会从普通内存池里划走，即使虚机不用，也不会归还给其他用途——这正是 01 篇混布场景里「普通内存被悄悄削掉一块」的机制。**第二，预留失败**：内存碎片化时，大页预留可能失败，导致虚机启动失败或退化。**第三，管理复杂度**：需要规划预留量、监控使用率。

**最大的陷阱是「只预留不监控」**：预留的大页如果长期闲置，就是纯浪费；如果预留不足，虚机启动时会失败。因此大页必须有水位监控。

### 4.5 配置与观测

```bash
# 查看大页总量与使用情况
grep -i huge /proc/meminfo

# 查看透明大页的当前策略
cat /sys/kernel/mm/transparent_hugepage/enabled

# 查看虚机是否使用大页（从 XML 与宿主机侧）
virsh dumpxml <domain> | grep -i -A3 hugepages
```

**观测的要点是「预留量与使用量都要看」**：只看总量会漏掉闲置浪费，只看使用量会漏掉预留不足。

### 4.6 大页的一个算例

设想一台虚机需要 64 GiB 内存，宿主机使用 2 MiB 大页。

需要的页数是 64 GiB / 2 MiB = 32768 个页。如果用 4 KiB 普通页，则需要 64 GiB / 4 KiB ≈ 1678 万个页。

**页数的差异直接决定了翻译缓存的压力**：32768 个页的映射条目可以较容易地被缓存覆盖，而 1678 万个页几乎不可能。因此大页在「内存容量大」时收益更明显。

**但大页的代价也在同一处**：预留 32768 个大页需要 32768 个按大页粒度连续的内存块，碎片化时可能预留失败。**这就是「大页收益与预留风险同源」的含义**。

### 4.7 大页与内存回收的冲突

大页与内存回收之间存在结构性冲突。

**大页一旦预留，就难以归还**：它从普通内存池里划走，不会因为虚机空闲而自动回收。因此**使用大页的虚机无法被有效超分**——它的内存是「实打实占住的」。

这个冲突带来一个规划结论：**大页虚机与超分虚机应当分开部署**。前者追求确定性、占用真实内存；后者追求利用率、依赖回收。混在一起会让规划变得复杂，也容易在压力时出现「大页占着、普通内存不够」的局面。

**这也是 01 篇混布场景里「普通内存被悄悄削掉一块」的完整解释**：大页预留减少了可超分的普通内存，而超分策略如果没有相应调整，就会在高水位时出问题。

### 4.8 大页的一个配置取舍

大页的配置有三个取舍点，值得单独说明。

**第一个是「全部使用还是部分使用」**：全部使用最简单，但内存完全不可回收；部分使用更灵活，但要判断哪些部分该用大页。**判断依据是「内存访问的密集程度」**——密集访问的区域收益大。

**第二个是「用多大页」**：1 GiB 收益大但预留难，2 MiB 折中。**常见做法是主内存用 2 MiB，热点区域用 1 GiB**。

**第三个是「预留多少」**：预留不足会导致启动失败，预留过多会浪费。**预留量应当略高于实际使用量，并监控使用率**。

三个取舍的共同点是：**它们都在「收益」与「灵活性」之间选择**。没有统一答案，取决于业务的内存访问特征。

### 4.9 大页与迁移的关系

大页与迁移之间也有约束，与 NUMA、绑核的张力类似。

**迁移要求目标宿主机有足够的大页**：如果目标机器的大页已被占用或未预留，迁移会失败。**大页的预留状态因此成为迁移的前置条件**，必须在迁移前校验。

**大页还影响迁移的数据量**：迁移时需要传输内存内容，大页本身不减少数据量，但可能影响传输的效率（大块的传输更高效）。

**因此在大页场景下，迁移规划要额外回答两个问题**：目标是否有足够大页、迁移后是否需要重新绑定。**这两个问题与 02 篇「绑核与迁移」的问题并列**，共同构成「确定性配置对迁移的约束」。

**把这些约束集中记录在一处**，是运维工程化的一个具体做法——它让「能不能迁」成为一个可以查表回答的问题，而不是每次重新推演。

## 第 5 章 Balloon 与内存回收

气球机制是虚机内存可以「弹性」的原因，也是内存超分的技术基础。

### 5.1 气球机制

**气球机制（Balloon）在虚机内部装了一个「可充气的气球」**：充气时，气球占用虚机的内存，虚机可用内存减少，同时宿主机回收对应的物理页；放气时反过来。

它的价值在于**让宿主机在内存紧张时可以「借回」一部分虚机内存**，从而提高内存利用率。这也是内存超分能够成立的技术前提。

### 5.2 回收的代价

气球回收不是免费的。**第一，虚机可用内存减少**，Guest 内的应用可能因为内存不足而变慢或触发自己的回收。**第二，回收过程本身有开销**，Guest 需要配合归还内存。**第三，Guest 未必「配合」**：如果 Guest 内没有空闲内存可供归还，气球充气会导致 Guest 内的回收甚至 OOM。

**「气球充气导致 Guest OOM」是内存超分场景下的典型事故形态**：宿主机为了缓解自己的压力，把压力转移给了虚机。

### 5.3 与 overcommit 的关系

气球与内存超分（overcommit）是配套的：**超分承诺了更多的内存，气球是兑现承诺时的手段之一**。但两者都有前提——**Guest 内确实有空闲内存**。

如果 Guest 内没有空闲内存，气球就无处可充，超分承诺无法兑现，此时宿主机只能靠 swap 或 OOM 来解决。**这就是内存超分的红线**：超分的规模不能超过「Guest 内可回收内存的估计值」。

### 5.4 何时该用何时不该用

气球适合的场景是「虚机内存有波动、且业务能容忍内存被回收」。不适合的场景是「业务对内存敏感」或「虚机长期满载」。

**判断方法是看虚机内存的使用曲线**：如果长期在 80% 以下且有波动，气球可用；如果长期接近 100%，气球只会带来伤害。

**配置上通常的做法是按业务分级**：一般业务启用气球，关键业务禁用。这与 02 篇「按业务等级配置策略」是同一思路。

### 5.5 气球的一个实例

设想宿主机内存紧张，气球被配置为自动回收。某台虚机被充气回收了 2 GiB，之后业务反馈「变慢」。

排查发现，该虚机的实际内存使用率原本在 85%，回收 2 GiB 后变成约 98%，Guest 内部开始频繁回收，延迟上升。

**这个实例说明气球的安全前提是「Guest 内有空闲内存」**。使用率 85% 的虚机，回收 2 GiB 就把它推到了边缘。**因此气球的回收量应当与实际使用率挂钩，而不是与配置内存挂钩**。

处置方向有两个：把该虚机排除在气球回收范围外，或降低宿主机整体的超分比例。**前者是局部缓解，后者是根治**。

### 5.6 气球与 OOM 的关系

气球与 OOM 是同一条压力链上的两个环节：**气球是「温和的回收」，OOM 是「暴力的清理」**。

当宿主机内存紧张时，它会先用气球尝试回收；如果回收不足，就转向 swap；swap 也不够，就触发 OOM。**因此气球充气频繁，往往是 OOM 的前兆**。

**观测上的价值在于「提前量」**：把气球充气的频率与幅度纳入告警，可以在 OOM 之前发现内存压力的积累。**这与 06 篇「分层告警」的思路一致**——趋势告警要早于阻塞告警。

### 5.7 气球的配置要点

气球的配置有四个要点：**回收的目标**（按什么标准决定回收多少）、**回收的下限**（保留多少给虚机）、**回收的速度**（一次回收多少）、以及**是否启用**（按业务分级）。

四个要点里，**回收的下限最关键**：它决定了虚机最少能保留多少内存。设置过低会导致 Guest OOM，设置过高则回收效果有限。

**回收速度也容易被忽略**：一次回收过多会导致 Guest 内的内存分配突然失败，表现为延迟尖峰。**渐进回收比一次性回收更安全**。

**是否启用应当按业务分级**，而不是全局统一——这一点在 5.4 节已讲过，这里强调的是它应当是「明确的配置」而不是「默认开启」。

### 5.8 气球与内存热插拔的对比

气球与内存热插拔都改变虚机的可用内存，但方向与机制不同。

| 维度 | 气球 | 内存热插拔 |
| :--- | :--- | :--- |
| 方向 | 通常减少（也可增加） | 增加 |
| 触发者 | 宿主机（自动） | 运维（手动） |
| 粒度 | 细、可反复 | 粗、一次一块 |
| 前提 | Guest 有可回收内存 | Guest 支持热插拔 |
| 风险 | Guest 内存不足 | NUMA 落位变化 |

**两者的对比说明：气球是「宿主机主导的动态调整」，热插拔是「运维主导的静态调整」**。前者用于应对压力，后者用于满足增长需求。

**理解这个区别，能避免「用错工具」**：用热插拔去应对宿主机压力，或用气球去满足长期增长，都是错配。

## 第 6 章 KSM 与页共享

页共享是另一种提高内存利用率的手段，它的收益与代价都很明确。

### 6.1 KSM 原理

**页共享（Kernel Same-page Merging，KSM）让内核扫描内存页，把内容相同的页合并成一份**，多个使用者共享同一份只读页；当有人要写时，再复制一份（写时复制）。

它的收益来源是「多台虚机运行相同的内容」——例如相同的操作系统、相同的运行时、相同的只读数据。在批量部署同构虚机的场景下，收益可能很可观。

### 6.2 收益与代价

KSM 的代价有三。**第一，扫描开销**：内核需要持续扫描内存，消耗 CPU。**第二，写时复制的开销**：合并后的页在被写时需要复制，带来延迟尖峰。**第三，延迟不确定性**：复制发生在访问时刻，可能导致偶发卡顿。

**收益与代价的权衡取决于负载的相似度**：相似度高、写少读多，收益明显；相似度低或写密集，代价大于收益。

### 6.3 安全考量

KSM 还有一个安全维度：**页共享意味着不同虚机共享同一份物理内存**。理论上，共享的时机与内容可能被用于推断其他虚机的行为（侧信道）。因此在多租户环境下，KSM 是否启用需要与安全要求一起评估。

**这不是说 KSM 不能用，而是说它不能默认开**。是否启用应当是一个明确的安全决策，而不是性能优化的顺手为之。

### 6.4 KSM 的观测

KSM 的观测可以看三个数：**合并的页数**、**节省的内存**、以及**扫描的开销**。

```bash
# KSM 运行状态与收益
cat /sys/kernel/mm/ksm/pages_shared
cat /sys/kernel/mm/ksm/pages_sharing
cat /sys/kernel/mm/ksm/pages_to_scan

# 内核线程的 CPU 占用（扫描开销）
ps -o pid,comm,pcpu -C ksmd
```

**判据是「节省的内存是否值得扫描的 CPU」**：如果节省的内存很小而扫描线程的 CPU 占用明显，就应当关闭。反之则值得保留。

**观测的要点是把收益与开销放在一起看**，只看「节省了多少」会忽略成本。

### 6.5 页共享与容器

页共享在容器场景下的收益通常比虚机更明显，原因在于**容器共享同一个内核，且往往运行同构的镜像**。

不过容器的页共享主要由内核的页缓存与镜像分层机制承担，KSM 是补充手段。**两者的关系是：镜像分层解决「静态共享」，KSM 解决「运行时的相同内容」**。

对虚机而言，没有镜像分层这层机制，因此 KSM 的作用相对更重要。**理解这个差异，能解释为什么「容器很省内存」而「虚机不太省」**——它们的共享机制不同。

这条对比也提示：**在混布场景下评估内存收益时，要把两类负载的共享机制分开算**。

### 6.6 页共享与超分的配合

页共享与内存超分是两种不同的「省内存」手段，它们可以配合，也可能互相干扰。

**配合的方式**：页共享减少了实际的物理占用，从而为超分腾出空间。**干扰的方式**：如果页共享把大量页合并，而这些页随后被频繁写（触发复制），反而会增加内存压力。

**因此页共享的效果需要实测**：不能假设「开了就一定省」。判断方法是看合并页数与写时复制的频率——**合并多而复制少才是净收益**。

**这也解释了为什么页共享在「同构且读多写少」的场景下效果最好**：这正是复制频率最低的场景。

### 6.7 页共享的一个判断

页共享是否启用，可以用三个问题判断：**负载是否同构**（不同构则收益小）、**是否读多写少**（写多则复制开销大）、**是否有安全要求**（多租户敏感场景要谨慎）。

三个问题都指向「可以启用」时，才启用。**只要有一个不满足，就应当评估代价**。

**判断的产出不是「开或关」，而是「在哪些宿主机上开」**。同构负载集中的宿主机可以开，混合负载的宿主机可以关。**这又回到「按池划分」的思路**，与 02 篇的超分分级一致。

**把页共享也纳入分级管理**，而不是全局开关，是本篇反复出现的同一种成熟度标志。

## 第 7 章 宿主机内存压力如何传导进虚机

这一章把前面几章的机制合起来，回答「宿主机的内存问题如何影响虚机」。

### 7.1 三种传导路径

宿主机内存压力通过三条路径传导进虚机：**气球回收**（宿主机主动借回内存）、**swap**（宿主机把自己的页换出，或虚机内存被换出）、**OOM**（宿主机在极端压力下杀死进程，可能杀死 vCPU 线程或整个 QEMU 进程）。

三条路径的严重程度递增：气球是可管理的，swap 是性能退化，OOM 是业务中断。**因此观察宿主机内存压力的第一步是判断「到了哪一档」**。

### 7.2 swap 与回收

宿主机开始使用 swap，说明内存已经紧张。此时虚机的表现是**延迟上升**，因为内存访问变成了磁盘访问。

**判断虚机延迟是否来自宿主机 swap 的方法**：看宿主机的 swap 使用与虚机的内存访问延迟是否同步变化。如果同步，说明虚机的内存被换出了。

**需要区分两种 swap**：宿主机自身进程的 swap，与虚机内存的 swap。前者影响宿主机上的管理组件，后者直接影响虚机性能。

### 7.3 OOM

宿主机 OOM 是最严重的形态。**OOM 会杀死进程，而被杀的可能正是虚机的 vCPU 线程或整个 QEMU 进程**——后者意味着虚机直接消失。

宿主机 OOM 的判据是内核日志中的 OOM 记录，以及被杀进程的清单。**记录「谁触发的、谁被杀的」是复盘的关键**，因为两者往往不是同一个进程（01 篇已讲过这个错位现象）。

```bash
# 宿主机 OOM 现场
journalctl -k --since "2 hours ago" | grep -iE 'oom|killed process'

# 内存压力与 swap
cat /proc/pressure/memory
cat /proc/meminfo | grep -E 'SwapTotal|SwapFree|MemAvailable'
```

### 7.4 观测与判据

把宿主机内存压力的观测收成一张表。

| 档位 | 判据 | 虚机表现 | 处置方向 |
| :--- | :--- | :--- | :--- |
| 正常 | 可用内存充足、无 swap | 无异常 | — |
| 气球回收 | 气球充气、可用内存偏低 | 虚机可用内存减少 | 评估气球策略 |
| swap | swap 使用上升 | 延迟上升 | 减少超分、加内存 |
| OOM | 内核 OOM 记录 | 虚机进程被杀 | 立即减压、隔离 |

**四档的处置方向完全不同**，因此「宿主机内存紧张」这个笼统的描述不足以决策。**先定档位，再定动作**。

### 7.5 压力传导的一个实例

设想宿主机内存紧张，多台虚机同时变慢。

排查顺序是：**第一步，定档位**——看宿主机是气球、swap 还是 OOM 档。假设发现 swap 使用明显上升，处于 swap 档。

**第二步，确认因果**——看虚机延迟与宿主机 swap 的时间相关性。如果同步，说明虚机的内存被换出。

**第三步，定位具体虚机**——看哪些虚机的内存被换出最多（可以从宿主机侧的进程内存分布判断）。

**第四步，处置**——短期是把最关键的虚机迁走或给它预留内存；长期是降低超分比例或扩容。

**这个实例的价值在于它演示了「档位 → 因果 → 定位 → 处置」的四步顺序**，与本专栏其他篇目的方法一致。

### 7.6 内存压力与故障预留

宿主机内存压力与故障预留是关联的，这一点与 06 篇容量规划直接相连。

**故障时被疏散的虚机需要内存**。如果宿主机内存已经紧张（气球在回收、swap 在用），那么疏散会加剧压力，可能导致连锁失败。

因此**内存的故障预留不只是「留出空闲内存」，还要「留出不被气球回收、不被 swap 的部分」**。这一点比 CPU 的预留更微妙，因为内存的「余量」会被超分与回收机制悄悄消耗。

**判断内存预留是否充足的方法**：看「最坏情况下的可用内存」——即扣掉超分承诺与气球回收后的余量，而不是看当前的可用内存。

### 7.7 内存压力与业务等级

内存压力的处置同样应当分级。

**关键业务**：不允许被气球回收、不允许被 swap，必要时预留物理内存。**一般业务**：可以接受气球回收与短时 swap。**可中断业务**：可以接受被 OOM 回收后重启。

**分级的实现方式与 02 篇一致**：按业务等级分池，池内配置各自的策略。

**分级还有一个隐含收益：它让 OOM 的选择变得可控**。当宿主机必须 OOM 时，如果可中断业务与关键业务在同一个池里，OOM 的选择是随机的；如果分池，OOM 会优先落在可中断业务上。**这正是「按业务分级」在极端场景下的价值**。

## 第 8 章 一次内存性能定位

下面用一个实例把前面的概念串起来。

### 8.1 现象

某台虚机的业务反馈「延迟高、吞吐低」，虚机内部显示内存充足、CPU 不高。

### 8.2 分层收敛

第一步，从虚机内部排除应用层问题：内存充足、CPU 不高，说明不是资源不足。

第二步，从宿主机侧看 QEMU 进程的内存分布。如果发现内存大量落在非预期的 NUMA 节点，说明跨节点访问是嫌疑。

第三步，看虚机是否使用大页。如果没有使用，且工作集较大，地址翻译的开销可能是原因。

第四步，看宿主机的内存压力档位。如果处于 swap 档，那么延迟可能来自宿主机的 swap，而不是虚机自身。

### 8.3 结论与处置

综合四步，可能的结论有三类：**NUMA 落位错误**（处置是调整绑定）、**缺大页导致翻译开销高**（处置是启用大页）、**宿主机内存压力**（处置是减压或迁移）。

三类结论的处置方向完全不同，**而它们在第 8.2 节的四步里各有对应的证据**。这就是分层归因的价值：**同一个现象，不同的证据指向不同的原因**。

### 8.4 定位方法的可迁移部分

这次定位可以提炼成四个可迁移的动作：**先排除虚机内部、再看 NUMA 落位、然后看翻译开销、最后看宿主机压力**。

四个动作的顺序体现了「由近及远」的原则：先排除虚机自己能解释的部分，再逐层向外。**这与 01 篇「由外向内」正好相反，但目的相同**——都是为了避免在错误的方向上深挖。

**顺序的选择取决于现象的特征**：如果现象带有「与宿主机状态相关」的特征（如随宿主机负载波动），应当先向外看；如果带有「与虚机内部特征相关」的特征（如随数据量变化），应当先向内看。

### 8.5 另一条路径：内存热插拔后的验证

第 8 章走的是「定位问题」的路径。反过来的路径是「验证一次内存变更是否达到预期」，同样值得一说。

为虚机增加内存之后，验证的要点有四个：**Guest 是否识别到新内存**（虚机内 `free` 是否变化）、**宿主机占用是否相应增加**、**新内存落在哪个 NUMA 节点**、以及**业务指标是否改善**。

**第三个要点最容易被忽略**：新增内存可能落在非预期节点，导致跨节点访问增加，反而抵消了「加内存」的收益。

**第四个要点是最终判据**：加内存的目的是改善业务，如果业务指标没有改善，说明瓶颈不在内存。这与 02 篇「绑核配置正确不等于业务变快」是同一条纪律。

### 8.6 内存问题的三种典型结论

把内存性能问题的结论归纳，常见有三类。

**第一类是「位置问题」**：内存充足但落位不对（跨 NUMA 节点），表现为延迟高、带宽低。**第二类是「开销问题」**：落位正确但翻译开销高（缺大页），表现为工作集大时延迟上升。**第三类是「压力问题」**：宿主机内存紧张，虚机被回收或被 swap，表现为延迟随宿主机状态波动。

三类结论的处置分别是：**调整绑定**、**启用大页**、**减压或迁移**。

**三类问题的共同点是它们都不体现在「内存够不够」这个判断上**——内存可能是够的，问题在位置、开销或宿主机侧。**这正是本篇要建立的核心认知**。

## 第 9 章 误判与反例

第一，**把配置内存当成实际占用**。四个口径不同，混用会误判宿主机压力。

第二，**只看内存总量不看 NUMA 分布**。总量充足但分布错误，仍会导致性能下降。

第三，**配置了绑定就认为生效**。必须从宿主机侧验证实际分布。

第四，**只预留大页不监控使用**。闲置浪费与预留不足都会出问题。

第五，**认为气球是纯收益**。气球充气会把压力转移给虚机，可能导致 Guest OOM。

第六，**默认启用页共享**。页共享有扫描与复制开销，也有安全考量。

第七，**把宿主机 swap 当成虚机问题**。swap 是宿主机侧的状态，处置要在宿主机侧。

第八，**把 OOM 被杀进程当成根因**。被杀的是高占用者，触发者可能是别的进程。

第九，**把 KSM 的节省量当成纯收益**。扫描与写时复制都有开销，要看净收益。

第十，**把内存热插拔当成无感操作**。它会触发映射更新，并可能改变 NUMA 落位。

第十一，**把「加内存」当成万能解**。如果瓶颈不在内存，加内存只会增加宿主机压力。

第十二，**把四种内存优化手段全部开启**。它们方向不同，同时拉满会互相抵消。

## 第 10 章 边界与反例

第一，**三层地址模型依赖硬件支持**。没有二级页表硬件支持的实现，翻译路径不同。

第二，**大页不是越多越好**。它占用连续内存、不可回收，比例要与业务匹配。

第三，**气球与页共享都有前提**。Guest 内没有可回收空间时，两者都失效。

第四，**内存超分有硬上限**。超过「可回收内存估计值」的超分，只能靠 swap 或 OOM 兑现。

第五，**观测口径因实现而异**。跨实现比较内存数字前要确认定义。

第六，**把内存热插拔当成在线扩容的捷径**。它改变的是虚机可用内存，不是宿主机物理内存。

第七，**跨实现比较内存统计数字**。口径不同，数字不可比。

第八，**假设「开了页共享就一定省内存」**。合并多而复制少才是净收益，需要实测。

行文至此，把本篇落点收在两条原则上。其一，架构即权衡——大页、气球、页共享都在「提高利用率」与「保持确定性」之间取舍，任何一项拉满都会牺牲另一头。其二，复杂性不会消失只会转移——内存超分把成本降了下来，却把不确定性转移到了虚机的可用内存与延迟上，这份不确定性只能靠分档观测来管理。下一篇转向 I/O 路径：virtio 与 vhost 如何让虚拟磁盘与网卡接近物理性能，以及队列在其中扮演什么角色。相邻的内存机制可参见 [[Linux/内存管理/00 专栏导览|Linux 内存管理专栏]]，宿主机内存压力的完整治理见 [[SRE/CVM集群可靠性工程/01 CVM 服务地图——用户操作、控制面与数据面依赖|CVM 服务地图]]。
