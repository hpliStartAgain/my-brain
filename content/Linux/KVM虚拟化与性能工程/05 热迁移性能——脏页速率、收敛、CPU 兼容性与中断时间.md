# 05 热迁移性能——脏页速率、收敛、CPU 兼容性与中断时间

**摘要：**

热迁移是虚拟化运维里最复杂的一次操作：它要在不中断业务的前提下，把一台正在运行的虚机从一台宿主机搬到另一台。本文沿着一次迁移的四个阶段，把内存搬迁与脏页速率、收敛条件与停机窗口、磁盘与网络状态、CPU 兼容性、以及迁移带宽与业务流量的竞争逐一拆开，给出每一层的判据与观测方法。全文回答两个问题：迁移为什么可能「不收敛」，以及迁移对业务的真实影响由哪些因素决定。文中的命令与观察方式取自 2026 年 9 月的现场记录，涉及具体数值处标注口径；平台侧的生命周期与疏散流程见 [[云原生/OpenStack/05 实例生命周期与迁移实战|05 实例生命周期与迁移]]，宿主机失联的恢复决策见 [[SRE/CVM集群可靠性工程/04 宿主机失联——故障检测、Fencing、Masakari 与恢复决策|04 宿主机失联]]。

## 第 1 章 热迁移要解决的问题

先明确这件事的难度来源：它要求「服务不停」与「状态全搬」同时成立。

### 1.1 什么是热迁移

**热迁移（Live Migration）指在虚机持续运行的前提下，把它从一台宿主机迁移到另一台**。业务在迁移过程中不应感知到中断，或只感知到极短的停顿。

它与冷迁移的区别在于「是否需要停机」：冷迁移先关机再搬，简单但中断时间长；热迁移边跑边搬，复杂但中断极短。**代价的转移是明显的**：热迁移把中断时间压下去，把复杂度提上来。

### 1.2 为什么难

难在三处。**第一，状态是持续变化的**：内存内容在搬迁过程中不断被修改，搬完的那部分可能已经过期。**第二，中断窗口必须极短**：业务能容忍的停顿通常是毫秒到秒级。**第三，目标机器未必与源机器完全一致**：CPU 特性、设备、拓扑都可能不同。

三处难点分别对应本篇的三个主题：**脏页与收敛**（应对状态变化）、**停机窗口**（应对中断约束）、**CPU 兼容性**（应对机器差异）。

### 1.3 与冷迁移、疏散的区别

三者经常被混用，但目标不同。

| 操作 | 是否停机 | 主要动机 | 状态搬运范围 |
| :--- | :--- | :--- | :--- |
| 冷迁移 | 是 | 维护、均衡 | 磁盘与配置 |
| 热迁移 | 否（极短停顿） | 维护、均衡、避让 | 内存、设备、网络 |
| 疏散 | 源机已失效 | 故障恢复 | 依赖共享存储重建 |

**疏散与迁移的根本区别是「源端是否还能配合」**：迁移是源端配合地把状态交出去，疏散是源端已经不在，只能靠共享存储重建。**因此疏散不涉及脏页与收敛问题，而迁移必然涉及**。

### 1.4 一次迁移的四个阶段

把迁移拆开，可以看到四个阶段：**准备**（检查兼容性与资源）、**预拷贝**（迭代搬迁内存）、**停机切换**（暂停源端、搬剩余状态、在目标端恢复）、**收尾**（释放源端资源、确认业务正常）。

**四个阶段里，时间最长的是预拷贝，最敏感的是停机切换**。这也解释了为什么优化迁移总是围绕这两处：把预拷贝收敛得快一些，把停机切换压得短一些。

### 1.6 迁移的三个动机

热迁移不是目的，它服务于三个动机。

**第一是维护**：宿主机需要重启、升级、换硬件时，把上面的虚机迁走，避免业务中断。**第二是均衡**：某些宿主机负载过高时，把部分虚机迁到空闲机器上。**第三是避让**：某台机器出现预警信号（如内存水位上升、磁盘告警）时，提前把虚机迁走。

**三个动机对「迁移速度」的要求不同**：维护有计划的窗口，可以从容迁移；均衡与避让往往需要较快完成。**因此迁移策略应当按动机配置**，而不是全局统一。

**这也解释了为什么「迁移带宽」与「自动收敛」应当按场景设置**：为计划维护配置的策略，未必适合紧急避让。

### 1.7 迁移与业务等级的对应

迁移策略应当与业务等级对应，这一点与 02、03、04 篇的「按业务分级」一致。

**核心业务**：迁移前必须演练验证、迁移窗口要避开高峰、迁移期间要有业务侧观测。**一般业务**：可以按常规策略迁移，事后确认。**可中断业务**：可以接受较长的中断，甚至可以用冷迁移。

**分级的价值在于「把风险控制手段用在对的业务上」**。**对可中断业务做精细的热迁移规划，是过度投入；对核心业务不做演练就迁移，是风险失控**。

**这也是「工程化」在迁移场景的体现**：把策略写成按等级配置的规则，而不是每次临场判断。

### 1.8 迁移失败与迁移不收敛的区别

「迁移失败」与「迁移不收敛」是两种不同的形态，处置也不同。

**迁移失败**指迁移在开始阶段就被拒绝或很快终止，常见原因是兼容性检查不通过、资源不足、目标端不可达。**它的特征是「快」**——几秒到几分钟内就有明确结果。

**迁移不收敛**指迁移启动了但迟迟不结束，特征是「慢」——可能持续几十分钟甚至数小时。

**两者的区别决定了排查方向**：失败查前置条件（兼容性、资源、连通性），不收敛查运行期变量（脏页、带宽、并发）。**把两者混为一谈，会在错误的方向上花时间**。

**这与 02 篇「配额与排队是两件事」是同一类区分**：都是把「开始前的条件」与「开始后的过程」分开。

## 第 2 章 内存搬迁：预拷贝与脏页

内存是迁移的主体，也是收敛问题的所在。

### 2.1 预拷贝原理

**预拷贝（Pre-copy）的思路是「先整体搬一遍，再把搬的过程中被改过的部分补搬」**。第一遍是全量传输，之后每一轮只传输「上一轮之后被修改的页」。

这个思路的巧妙之处在于：**如果虚机的写入速率低于传输速率，那么每一轮要补搬的页会越来越少**，最终可以进入停机切换。**收敛就是「补搬量越来越小」这个过程**。

### 2.2 脏页速率

**脏页速率指虚机每秒修改的内存页数量**。它是决定迁移能否收敛的核心变量：**写入越快，需要补搬的越多；补搬速度跟不上写入，就永远收敛不了**。

脏页速率取决于业务类型：**读多写少的业务（如静态服务）脏页少，容易迁移**；**写密集的业务（如数据库、缓存）脏页多，迁移困难**。**因此「能不能迁移」首先是一个业务特征问题，而不是技术配置问题**。

### 2.3 收敛条件

收敛的判据可以简化表述为：**脏页速率低于迁移传输速率**。当两者接近时，补搬量下降很慢，迁移时间会被拉长；当脏页速率超过传输速率时，迁移永远无法收敛。

这个条件带来三个可操作的推论。**第一，提高带宽有助于收敛**（提升传输速率）。**第二，降低虚机的写入速率有助于收敛**（减少脏页）。**第三，两者都做不到时，只能改用其他策略**（如后拷贝或直接放弃）。

### 2.4 停机窗口

**停机窗口（Downtime）指源端暂停到目标端恢复之间的时间**。它由两部分构成：**最后一批内存与设备状态的传输时间**，以及**切换本身的开销**。

停机窗口的大小与「收敛程度」直接相关：**如果收敛得好，最后一批很小，停机窗口就短**；如果收敛得勉强，最后一批很大，停机窗口就长。**因此「缩短停机窗口」与「改善收敛」是同一件事的两个表述**。

### 2.5 后拷贝

**后拷贝（Post-copy）是另一条路**：先只搬最小必要状态并在目标端启动，其余内存按需从源端拉取（缺页时拉）。

它的优势是**总迁移时间短、几乎不受脏页速率影响**；代价是**目标端在拉取完成前高度依赖源端**——如果源端在此期间失效，虚机将无法恢复。**因此后拷贝适合「源端稳定、追求快速切换」的场景，不适合「源端可能失效」的场景**。

**这条取舍与 04 篇「零拷贝与直通」是同一类**：用可靠性或灵活性换性能。

### 2.6 脏页的一个算例

用一个简化算例说明收敛。假设虚机内存 16 GiB，迁移带宽 1 GiB/s。

**第一轮全量传输约需 16 秒**（理想情况）。在这 16 秒里，虚机以 200 MiB/s 的速率写入，产生约 3.2 GiB 脏页。**第二轮传输这 3.2 GiB 需约 3.2 秒**，期间又产生约 640 MiB 脏页。**第三轮约 0.64 秒**，期间产生约 128 MiB。**第四轮约 0.13 秒**……

**脏页量每轮按「写入速率除以传输速率」的比例递减**。在这个算例里比例是 0.2，因此几轮就收敛了。**如果写入速率是 800 MiB/s，比例接近 0.8，需要十几轮才能收敛**；如果写入速率超过带宽，**永远不收敛**。

**这个算例给出了两个可操作的结论**：写入速率与带宽的比值决定收敛速度；比值接近或超过 1 时，必须调整策略。

### 2.7 预拷贝与后拷贝的对照

| 维度 | 预拷贝 | 后拷贝 |
| :--- | :--- | :--- |
| 总时长 | 受脏页影响 | 短且稳定 |
| 停机窗口 | 取决于收敛 | 很短 |
| 源端依赖 | 完成后可释放 | 完成前必须可用 |
| 适用 | 通用 | 源端稳定、追求快速 |

**两者的对照说明「后拷贝不是更快的预拷贝，而是另一条路线」**：它把风险从「迁移时间长」换成了「迁移期间源端不能失效」。**选择依据是业务对这两类风险的容忍度**。

### 2.8 脏页的观测方法

脏页速率可以从迁移的进度信息中间接观察。

```bash
# 迁移过程中查看进度：已传数据量、剩余数据量、迭代轮数
virsh domjobinfo <domain> --completed --keep-completed

# 观察虚机的内存与气球统计（宿主机侧）
virsh domstats <domain> --balloon
```

**判读的要点是「剩余量的趋势」**：如果每轮剩余量递减，说明在收敛；如果递减很慢或不变，说明脏页速率接近或超过传输速率。

**虚机内部的写压力也可以作为旁证**：如果虚机内的磁盘写或内存写指标在迁移期间很高，说明脏页产生快。**这与 03 篇「内存压力分档」是同一种「用旁证判断」的方法**。

### 2.9 内存大小的双重影响

内存大小对迁移有双重影响，值得单独说明。

**第一重影响是传输量**：内存越大，第一轮全量传输越久，迁移总时长越长。**第二重影响是脏页产生的基数**：内存越大，同样写入比例下产生的脏页越多。

**两重影响叠加，使得大内存虚机的迁移难度显著高于小内存虚机**。**这不是线性关系，而是「传输慢加脏页多」的双重放大**。

**实践含义是：大内存虚机的迁移规划要更谨慎**，可能需要专门的带宽、更长的时间窗、甚至专用的迁移网络。**这与 03 篇「大虚机不等于小虚机的放大版」是同一结论**。

### 2.10 收敛的一个判断方法

判断一次迁移能否收敛，可以在迁移开始前做一个粗估。

**第一步，估算虚机的脏页速率**：可以从虚机的内存写压力与业务特征推断。**第二步，估算可用传输速率**：从迁移限速与网络余量推断。**第三步，比较两者**：脏页速率明显低于传输速率，收敛大概率可行；接近或超过，则要准备调整策略。

**粗估的价值在于「提前预判」**：如果粗估显示大概率不收敛，可以在迁移前先调整（提高限速、安排低谷、暂停并发迁移），而不是迁移中途才发现。

**这也是「维护预检」在迁移场景的应用**——把可预判的问题提前处理，而不是让它在中途爆发。

### 2.11 收敛与停机窗口的关系

收敛程度与停机窗口是同一件事的两个侧面，值得再明确一次。

**收敛得越彻底，剩余待传量越小，停机窗口越短**。因此「让迁移收敛得好」是缩短停机窗口最直接的手段。**反之，如果只求「尽快进入停机切换」，剩余量会很大，停机窗口反而变长**。

**这解释了一个常见的误区**：为了「快点结束」而强行提前切换，结果停机窗口变长，业务感知更差。**「快」与「短」不是一回事**——前者指总时长，后者指停机窗口。

**优化目标应当是「停机窗口短」，而不是「总时长短」**。两者的取舍在业务敏感度高时尤其重要。

## 第 3 章 磁盘与网络状态

内存之外，还有两类状态需要处理。

### 3.1 共享存储下的磁盘

**使用共享存储时，磁盘不需要搬运**：卷由两端共同访问，迁移只是把虚机对卷的访问从源端切到目标端。

这带来一个直接结论：**共享存储让迁移变得简单**，因为它消除了最大的一块状态搬运。**这也是共享存储被视为弹性平台前提的原因之一**，与 04 篇「可迁移性」的讨论一致。

### 3.2 块迁移

**没有共享存储时，磁盘也需要搬运，这称为块迁移（Block Migration）**。它的代价很大：磁盘容量通常远大于内存，传输时间可能成为主导。

**块迁移还有一致性要求**：磁盘在搬运过程中被写入，需要与内存一样做迭代同步。**因此块迁移的收敛问题比内存迁移更复杂**——它要同时收敛内存与磁盘。

**实践上的建议是：能不块迁移就不块迁移**。块迁移应当被视为「共享存储不可用时的退路」，而不是常规手段。

### 3.3 网络状态的迁移

网络状态的迁移包含几层：**虚机的虚拟网卡配置**（MAC、队列等）、**宿主机的网络后端**（虚拟交换机上的端口）、以及**连接状态**（如果有状态化的网络设备）。

**多数情况下，虚机的网络配置随虚机一起迁移，连接依赖 TCP 的重传机制在切换后恢复**。因此业务的感知通常是「短暂卡顿」而不是「连接断开」。

**需要留意的是「源端与目标端的网络拓扑是否一致」**：如果两端不在同一网段或可用域，迁移后虚机的网络可达性会变化。**这与 04 篇「后端形态与迁移的关系」是同一类约束**。

### 3.4 设备状态的迁移

除内存与网络外，还有其他设备状态：**时钟、中断控制器、virtio 队列的索引**等。这些状态量小，但**遗漏会导致迁移后行为异常**。

**这也是「迁移需要两端实现兼容」的原因之一**：设备状态的表达格式必须一致。**因此迁移不是「搬数据」，而是「在两端重建等价的状态」**——这个视角能解释很多迁移失败的形态。

### 3.5 共享存储与本地盘的迁移对照

共享存储与本地盘的迁移差异很大，值得对照。

| 维度 | 共享存储 | 本地盘 |
| :--- | :--- | :--- |
| 磁盘搬运 | 不需要 | 需要块迁移 |
| 迁移时长 | 主要由内存决定 | 内存加磁盘 |
| 收敛难度 | 中 | 高（两处同时收敛） |
| 对存储的依赖 | 高（两端都要能访问） | 低 |

**表的最后一行是一个反直觉的结论**：共享存储让迁移更简单，却让迁移更依赖存储。**如果共享存储本身有问题，迁移会连带失败**。**这与 [[SRE/CVM集群可靠性工程/05 共享故障域——网络、存储和控制面同时异常时的恢复顺序|05 共享故障域]] 是同一视角**：便利与耦合总是成对出现。

### 3.6 状态重建的一个视角

「迁移是在两端重建等价状态」这个视角值得展开，因为它能解释很多失败形态。

**如果只把迁移理解为「搬数据」，那么失败的原因只能归为「数据没搬全」**。**但如果理解为「重建状态」，失败的原因就扩展为三类**：数据没搬全、状态的表达格式不兼容、以及目标端重建条件不具备。

**三类原因对应不同的排查方向**：第一类查传输与收敛，第二类查版本与配置兼容性，第三类查目标端的资源与设备。**这个扩展让排查有了更多入口**，而不是在「数据是否传完」上打转。

**这也是「换一个框架看问题」的价值**：同一个现象，框架不同，可行动的方向数量不同。

### 3.7 设备兼容性的一个清单

- 两端的虚拟化版本是否一致或兼容。
- 设备类型是否两端都支持（如特定的半虚拟化设备）。
- 设备状态格式是否一致。
- 目标端是否有足够的设备资源（队列、直通设备）。
- 迁移后是否需要重配设备。

**五条检查项与 4.6 节的 CPU 清单并列，共同构成「能不能迁」的完整判据**。**两份清单合并，就是迁移前的预检表**——这与 08 篇「维护预检」是同一件事在迁移场景的具体化。

## 第 4 章 CPU 兼容性

CPU 兼容性是迁移能否开始的第一个门槛。

### 4.1 为什么需要兼容性

**虚机在源端看到一套 CPU 特性，迁移到目标端后必须看到等价的（或超集的）特性**。如果目标端的 CPU 缺少虚机正在使用的某个特性，迁移后虚机内的程序可能执行出错。

因此迁移前的第一件事是**确认目标端的 CPU 能满足源端虚机的要求**。这是「能不能迁」的第一道判据，与脏页速率（「能不能收敛」）是两个独立问题。

### 4.2 CPU 模型与特性

虚机看到的 CPU 由「CPU 模型」描述。三种常见做法：**透传**（把宿主机 CPU 原样暴露，性能最好、兼容性最差）、**宿主机模型**（暴露宿主机支持的特性，兼顾两者）、**自定义模型**（按需裁剪，兼容性最好、性能可能下降）。

**三者的取舍是「性能与可迁移性」**。透传性能最好，但只能在完全同构的机器间迁移；自定义模型可迁移性最好，但可能牺牲部分特性带来的性能。

### 4.3 兼容性检查

```bash
# 查看虚机的 CPU 模型配置
virsh dumpxml <domain> | grep -i -A10 '<cpu'

# 查看宿主机支持的 CPU 模型
virsh cpu-models <arch>

# 比较源端与目标端的 CPU 能力
virsh capabilities | grep -i -A20 '<cpu'
```

**检查的要点是「源端虚机实际用到的特性」而不是「宿主机支持的所有特性」**。**只比较支持列表会得出过宽的结论**——很多特性虚机根本没用到，不必要求目标端也具备。

### 4.4 兼容性与性能的取舍

兼容性与性能的取舍在集群层面表现为**「CPU 池的划分」**。

**同一池内的机器 CPU 特性一致**，因此池内可以自由迁移；**跨池迁移需要降级 CPU 模型**，可能影响性能。**这与 02 篇「按池划分」是同一思路**：把矛盾变成资源池划分。

**实践中的常见做法是「按代际划分池」**：同代机器一个池，池内透传或宿主机模型；跨代迁移时显式降级。**这样既保住了池内的性能，又保留了跨池的能力**。

### 4.5 CPU 兼容性的一个实例

设想一个集群有两种代际的机器，业务需要在这两种机器间迁移。

**如果虚机使用透传模型**：只能在同代机器间迁移，跨代直接失败。**如果使用宿主机模型**：跨代时可能需要裁剪特性，迁移可能成功但性能下降。**如果使用自定义模型**（只暴露业务实际需要的特性）：跨代迁移成功率最高，性能损失可控。

**因此「跨代迁移」的关键不是「机器是否兼容」，而是「虚机是否使用了机器差异部分的特性」**。**把虚机的 CPU 需求收敛到最小集合，是提高可迁移性的有效手段**。

**这个实例也说明 CPU 模型的选择应当由「业务需要什么」决定，而不是由「宿主机有什么」决定**。

### 4.6 CPU 兼容性的检查清单

- 虚机的 CPU 模型是什么（透传、宿主机、自定义）。
- 虚机实际使用了哪些 CPU 特性（从业务与运行时推断）。
- 目标宿主机是否具备这些特性。
- 跨代迁移是否需要降级模型。
- 降级后业务是否受影响。

**五条检查项覆盖「配置 → 需求 → 目标 → 代价」四个环节**。**第三条与第五条最容易被省略**：只看配置不看需求，会得出过严的结论；只看可行性不看代价，会在迁移后才发现性能下降。

### 4.7 CPU 池划分的一个实例

设想一个集群有三种代际的机器，业务需要在这些机器间迁移。

**划分方式是：按代际分成三个池**，池内 CPU 模型用透传（性能最好），**跨池迁移时显式降级为三代的公共特性集**。

**这样做的收益是「池内性能无损、跨池仍可行」**。**代价是「跨池迁移需要额外的配置步骤」**，且降级后部分特性不可用。

**另一个可选方案是「全集群统一使用公共特性集」**：配置简单，但所有虚机都损失了各代机器的高阶特性。**两种方案的取舍是「性能上限」与「管理复杂度」**。

**这个实例说明 CPU 兼容性不是「能不能」的问题，而是「愿意付多少代价」的问题**。

### 4.8 CPU 特性与业务的关系

CPU 特性与业务的关系，是判断兼容性代价的关键。

**大多数业务只使用 CPU 的通用指令集**（基础整数与浮点运算），对高阶特性（如向量指令扩展、加密指令）的依赖有限。**这类业务对 CPU 模型的差异不敏感**，降级后性能影响小。

**少数业务高度依赖特定特性**：如加密密集型业务依赖加密指令、AI 推理依赖向量指令。**这类业务降级后性能下降明显**，跨代迁移的代价高。

**因此判断兼容性代价的第一步是「判断业务是否依赖高阶特性」**。**判断方法可以看业务的类型，也可以实测降级前后的性能差异**。**后者更可靠**。

## 第 5 章 中断时间与业务影响

迁移对业务的影响，最终体现为中断时间与性能波动。

### 5.1 停机窗口的构成

停机窗口由四部分构成：**最后一批内存的传输**、**设备状态的保存与恢复**、**目标端的启动与自检**、以及**网络切换**。

**四部分里，第一部分通常最大**，且与收敛程度直接相关。**其余三部分相对固定**，属于「迁移本身的固有开销」。

**因此优化停机窗口的主要空间在第一部分**：让它更小。**这也是为什么「改善收敛」与「缩短停机」是同一件事**。

### 5.2 业务感知

业务对迁移的感知通常是三种：**短暂停顿**（停机窗口内）、**吞吐波动**（迁移流量与业务流量竞争）、以及**延迟尖峰**（切换瞬间）。

**三种感知里，第二种最容易被忽略**：即使停机窗口很短，迁移期间占用的带宽与 CPU 也会让业务变慢。**因此评估迁移影响时，不能只看停机窗口**。

### 5.3 如何度量

```bash
# 观察迁移进度与统计（含已传页数、剩余页数、停机时间）
virsh domjobinfo <domain>

# 观察迁移期间的宿主机资源占用
virsh domstats <domain> --cpu-total --balloon
```

**度量的要点是把「停机窗口」与「迁移总时长」分开看**：前者决定业务感知的停顿，后者决定业务受影响的总时长。**两者优化方向不同**：缩短停机靠收敛，缩短总时长靠带宽与脏页控制。

### 5.4 如何缩短

缩短中断时间的手段有三类：**改善收敛**（提高带宽、降低脏页）、**降低固有开销**（减少设备状态、优化目标端启动）、以及**调整策略**（如启用自动收敛或改用后拷贝）。

**三类手段的代价不同**：改善收敛可能需要更多带宽；降低固有开销可能需要简化配置；调整策略可能牺牲可靠性。**选择依据是「业务更在意停机还是更在意总时长」**。

### 5.5 停机窗口的一个算例

用一个算例说明停机窗口的构成。假设某次迁移的停机窗口为 200 毫秒。

**其中约 120 毫秒用于传输最后一批内存**（假设剩余 120 MiB，带宽 1 GiB/s）。**约 50 毫秒用于设备状态的保存与恢复**。**约 30 毫秒用于网络切换与目标端自检**。

**三部分里，第一部分可以通过改善收敛压缩**（如果收敛得更好，剩余量更小）；**后两部分相对固定**。

**这个算例的实践含义是：停机窗口的下限由「固有开销」决定**。**无论怎么优化收敛，都不可能低于这个下限**——这与 03 篇「延迟预算」的思路一致：任何优化都有它的物理边界。

### 5.6 业务感知的一个度量方法

业务感知难以直接测量，但可以用替代指标近似。

**替代指标有三**：**业务侧的成功率与延迟**（最直接）、**虚机内的 CPU 与 I/O 停顿**（间接）、以及**网络连接的异常计数**（针对网络业务）。

**三个指标里，第一个最可信但需要业务配合**；后两个可以从基础设施侧获得，不需要业务改造。**实践中往往是「基础设施侧持续观测加业务侧抽样验证」的组合**。

**这与 07 篇「恢复的终点是业务可用」是同一思路**：基础设施指标只是代理，业务指标才是判据。

### 5.7 迁移影响的三种时间尺度

迁移对业务的影响可以按三种时间尺度看。

**毫秒级**：停机窗口内的短暂停顿。**秒到分钟级**：迁移期间因流量竞争导致的吞吐波动与延迟上升。**分钟到小时级**：如果迁移失败或长期不收敛，业务持续处于「被迁移占用资源」的状态。

**三种尺度对应三种优化**：缩短停机窗口、控制迁移流量、以及及时放弃不收敛的迁移。**只看第一种，会漏掉后两种更大的影响**。

**这也是「业务感知」难以用一个数字表达的原因**：它是三个尺度的叠加，而不是单一事件。

## 第 6 章 迁移的网络与带宽

迁移流量与业务流量共享网络，这是性能影响的主要来源。

### 6.1 迁移流量

迁移流量的大小取决于**内存大小与迭代轮数**：内存越大、轮数越多，总流量越大。**块迁移还要加上磁盘容量**。

**迁移流量的特征是「突发且持续」**：它在迁移期间持续占用带宽，迁移结束后立刻释放。**这种形态对网络的瞬时压力大于平均值**。

### 6.2 带宽与并发

**带宽决定了收敛速度**：带宽越大，每轮传输越快，收敛越快。**但带宽是共享的**：如果同时迁移多台虚机，它们会互相争抢带宽，各自的收敛速度都下降。

**因此迁移并发需要控制**。**并发过高会让所有迁移都变慢**，甚至全部不收敛——这与 02 篇「排队延迟的非线性」是同一个机制：资源接近饱和时，边际恶化迅速。

### 6.3 限速

**迁移限速（Bandwidth Limit）限制单次迁移可用的带宽**。它的作用有两面：**保护业务流量**（不让迁移占满网络），以及**保护迁移本身**（不让多台迁移互相压垮）。

**限速的取舍是「迁移速度」与「业务影响」**。**限得太松，业务受影响；限得太紧，迁移不收敛**。**取值依据是「业务带宽需求的峰值」与「迁移的收敛要求」两者的交集**。

### 6.4 与业务流量的竞争

迁移流量与业务流量竞争网络资源，这是「迁移期间业务变慢」的直接原因。

**判断竞争是否严重的方法**：观察迁移期间的网络利用率与业务延迟。**如果网络利用率接近饱和、业务延迟同步上升，说明竞争明显**。

**缓解手段有三**：**限速**（直接控制迁移带宽）、**分时**（把迁移安排在业务低谷）、以及**分网**（把迁移流量与业务流量放到不同网络）。**第三种最彻底，但需要专门的网络规划**。

### 6.5 迁移限速的一个配置思路

迁移限速的取值可以按三步确定。

**第一步，测出业务的带宽峰值需求**：业务在高峰时占用多少带宽。**第二步，测出网络的总容量与当前余量**：还剩多少可分配给迁移。**第三步，取「余量的一部分」作为迁移限速**，而不是取全部余量。

**第三步的理由是「留出波动空间」**：业务带宽会波动，如果把余量全部给迁移，业务峰值时就会争抢。**留出余量的做法与 [[SRE/CVM集群可靠性工程/06 容量与缩容——超分、资源碎片、故障预留和恢复空间|06 容量与缩容]] 的「故障预留」是同一思路**——为不确定性留出空间。

**限速也不是越小越好**：限得太紧会导致迁移不收敛。**因此取值是「业务峰值」与「收敛要求」的交集**。

### 6.6 迁移网络的两个选择

迁移流量走哪张网，有两个选择：**与业务共用**或**独立网络**。

**共用的优点是无需额外规划**，缺点是竞争不可避免，只能用限速与分时缓解。**独立的优点是彻底消除竞争**，缺点是需要专门的网络配置与容量规划。

**选择依据是业务的敏感度与集群规模**：小集群、业务不敏感时共用即可；大集群、业务敏感时值得独立。**这与 02 篇「按池划分」是同一思路**——用隔离替代在同一份资源上做精细平衡。

### 6.7 迁移并发的一个控制思路

迁移并发需要控制，思路有三。

**第一是「总量控制」**：限制同时进行的迁移总数。**第二是「带宽配额」**：给每次迁移分配带宽，使总量不超网络容量。**第三是「队列化」**：把迁移请求排队，逐个或分批执行。

**三者可以组合**：队列化决定「谁能开始」，总量与配额决定「同时能跑多少」。**组合的效果是「迁移整体可控」**，而不是「先到先得」。

**这与 06 篇「超分与预留」是同一思路**：用配额与队列替代「自由竞争」，从而让结果可预期。

### 6.8 迁移流量的观测

迁移流量可以从两端观测。

```bash
# 源端与目标端的网络流量（迁移期间）
sar -n DEV 1 5

# 观察迁移任务的进度与统计
virsh domjobinfo <domain>
```

**观测的要点是「区分迁移流量与业务流量」**：如果两端在同一张网上，总量会混在一起。**区分方法是看流量的变化时间**——迁移开始与结束时会有明显跳变。

**另一层观测是「迁移流量的平稳性」**：如果迁移流量忽高忽低，说明限速或带宽争抢在起作用。**平稳的迁移流量意味着网络资源可控**——这与 03 篇「看趋势不看快照」是同一方法。

## 第 7 章 迁移不收敛：定位与处置

「迁移不收敛」是热迁移最常见的失败形态，值得单独一章。

### 7.1 症状

症状是**迁移长时间不停，剩余待传页数不下降或下降极慢**。业务可能仍在正常服务，但迁移迟迟不结束。

**这个症状的判别依据是「剩余页数的趋势」**：如果剩余页数持续下降，说明在收敛，只是慢；如果不降或上升，说明无法收敛。**趋势比绝对值更重要**——这与本专栏反复强调的「看趋势不看快照」一致。

### 7.2 分层定位

定位可以按三层展开。**第一层，脏页速率**：虚机的写入是否过快。**第二层，传输速率**：带宽是否被限制或争抢。**第三层，并发**：是否有其他迁移在争抢。

**三层对应三类原因**：业务写入密集、带宽不足、并发过高。**定位顺序应当是「先看自己的脏页，再看带宽，最后看并发」**——从最可控的因素开始。

### 7.3 处置手段

处置有四种：**提高带宽**（如果资源允许）、**降低脏页**（如临时减少虚机负载，但这可能影响业务）、**启用自动收敛**（在迁移期间主动限制 vCPU，从而降低写入速率）、以及**改用后拷贝**。

**四种手段的代价递增**：前两种是资源层面的调整，第三种会影响虚机性能，第四种牺牲可靠性。**按代价递增的顺序尝试**，与 04 篇「优化顺序」是同一原则。

### 7.4 何时应当放弃

**放弃也是一种正确的处置**。判断依据有三：**脏页速率长期高于传输速率**（物理上不可能收敛）、**业务对性能下降的容忍度低**（自动收敛不可用）、以及**源端稳定性不足**（后拷贝不可用）。

**三者同时成立时，应当果断放弃并改用其他方案**（如冷迁移或重建）。**持续等待一个不可能收敛的迁移，只会延长业务受影响的时间**——这与 04 篇「等待需要边界」是同一条纪律。

### 7.5 自动收敛的机制与代价

**自动收敛（Auto-converge）的思路是「在迁移期间主动限制虚机的 vCPU」**，从而降低写入速率，让迁移能够收敛。

**它的收益是「让原本不收敛的迁移收敛」**；**代价是「虚机在迁移期间变慢」**。**这是一个明确的交换**：用业务性能换迁移成功率。

**因此自动收敛是否启用，取决于业务对「迁移期间变慢」的容忍度**。**对延迟敏感的业务，自动收敛可能比「迁移失败」更糟**——它把一次明确的失败变成了持续的性能劣化。

**这个取舍与本专栏其他篇目反复出现的模式一致**：**任何「让流程更容易成功」的手段，通常都以「降低某个维度的表现」为代价**。理解代价，才能决定是否采用。

### 7.6 不收敛的一个实例

设想一次迁移在 30 分钟后仍未完成，剩余待传数据量在 2 GiB 到 3 GiB 之间波动。

**第一步看趋势**：剩余量不降反升，说明脏页速率高于传输速率。**第二步看虚机负载**：虚机内有一个写入密集的进程在持续工作。**第三步看带宽**：迁移限速设得较紧，且同时有两台虚机在迁移。

**三步合起来，原因是「写密集业务加带宽受限加并发争抢」**。**处置方向有三个**：暂停另一台迁移（缓解并发）、临时放宽限速（缓解带宽）、或接受失败并改用冷迁移。

**这个实例的价值在于它演示了「不收敛往往是三个因素叠加」**，而不是单一原因。**因此处置也应当是多管齐下，而不是只调一个参数**。

### 7.7 放弃之后的替代方案

放弃热迁移之后，还有几种替代方案。

**第一是冷迁移**：接受较长的中断，换取迁移的确定性。**第二是重建**：在目标端重建虚机（依赖共享存储或备份），中断时间取决于重建速度。**第三是推迟**：把迁移安排到业务低谷，届时脏页速率下降，可能就能收敛。

**三种方案的中断时间递增（推迟除外），确定性也递增**。**选择依据是业务对「中断时长」与「不确定性」的偏好**。

**「推迟」最容易被忽略**：很多不收敛是因为迁移窗口选得不好（业务高峰）。**把迁移挪到低谷，往往比调参数更有效**——这与 06 篇「先判断是配置还是架构问题」是同一思路：先排除最便宜的原因。

## 第 8 章 实验：如何测出迁移的收敛能力

迁移能力需要实测，而不是凭经验判断。

### 8.1 实验设计

实验的要素：**基线**（虚机在稳定负载下的脏页速率）、**变量**（负载强度与迁移带宽）、**结果**（收敛时间、停机窗口、迁移总时长）。

**关键是把「负载强度」作为变量**：同一台虚机在不同写入压力下的迁移表现差异很大，**因此「这台虚机能迁移」这个结论必须带上负载条件**。

### 8.2 度量什么

度量三件事：**收敛时间**（从开始到进入停机切换）、**停机窗口**、以及**迁移期间业务延迟的变化**。

**第三件最容易被省略，却最接近业务感知**。一次「迁移成功但业务变慢一倍」的迁移，在指标上是成功的，在体验上是失败的。

### 8.3 实验的边界

结论的边界有三条：**绑定负载特征**（写密集与读密集的结论不同）、**绑定网络条件**（带宽与并发会改变结论）、**绑定 CPU 配置**（透传与自定义模型的迁移表现不同）。

**把边界写进结论**，是本专栏实验方法的统一要求。

### 8.4 实验的一个记录模板

实验记录应当包含：**环境**（两端 CPU 型号、网络带宽、存储类型）、**基线**（虚机在稳定负载下的脏页速率）、**变量**（负载强度、迁移带宽、是否启用自动收敛）、**结果**（收敛时间、停机窗口、迁移期间业务延迟）、以及**边界**（适用的负载与网络条件）。

**「迁移期间业务延迟」这一项是这类实验的关键**：它把「迁移成功」与「业务无感」区分开。**只记录收敛时间的实验，无法回答「这次迁移业务能不能接受」**。

### 8.5 实验的一个简化流程

如果资源有限，可以用简化流程评估迁移能力：**选一台有代表性的虚机，在其正常负载下做一次迁移，记录收敛时间、停机窗口与业务延迟变化**。

**简化流程的优势是「贴近真实」**：用的是真实业务负载，结论直接可用。**劣势是「样本少」**：单次结果可能受当时条件影响（如恰好业务低谷）。

**改进办法是「重复几次并记录条件」**：同一虚机在不同时段各迁移一次，对比结果。**条件与结果的对应关系，比单次结果更有价值**——这与 02 篇「实验结论要绑定条件」是同一要求。

## 第 9 章 误判与反例

第一，**把「迁移失败」当成技术故障**。多数不收敛是业务特征（写密集）与资源条件（带宽不足）共同导致的，不是 bug。

第二，**只看停机窗口不看总时长**。业务受影响的总时长由后者决定。

第三，**用迁移前的脏页速率预测迁移表现**。负载会变，必须在迁移期间实测。

第四，**认为提高带宽总能解决收敛问题**。脏页速率高于传输速率时，提高带宽只是延长时间。

第五，**忽略迁移流量与业务流量的竞争**。迁移期间的业务变慢往往来自这里。

第六，**不控制迁移并发**。并发过高会让所有迁移都变慢。

第七，**在源端不稳定的场景使用后拷贝**。后拷贝依赖源端持续可用。

第八，**把 CPU 兼容性检查简化成「支持列表比对」**。应当比对虚机实际用到的特性。

第九，**默认启用自动收敛**。它用迁移期间的性能换成功率，是否启用应当按业务决定。

第十，**把迁移限速设成「剩余带宽全部」**。业务峰值时会争抢，应当留出波动空间。

第十一，**把不收敛归因为单一原因**。它往往是「写密集加带宽受限加并发」三者叠加，处置也要多管齐下。

第十二，**在不合适的窗口强行迁移**。业务高峰期的脏页速率最高，推迟到低谷往往比调参数更有效。

## 第 10 章 边界与反例

第一，**热迁移不适用于所有业务**。写密集业务可能根本无法收敛。

第二，**后拷贝有前提**。源端在迁移完成前失效会导致虚机无法恢复。

第三，**块迁移代价高**。它是共享存储不可用时的退路，不是常规手段。

第四，**CPU 兼容性约束跨代迁移**。跨代迁移往往需要降级 CPU 模型，牺牲部分性能。

第五，**迁移能力会随集群变化衰减**。新硬件加入、网络调整都可能改变原有结论。

第六，**把 CPU 兼容性当成二值判断**。它取决于虚机实际用到的特性，不是「兼容或不兼容」这么简单。

第七，**在跨代集群里默认使用透传模型**。它会直接阻断跨代迁移。

第八，**把迁移网络与业务网络的共用当成理所当然**。业务敏感或集群规模大时，独立网络能彻底消除竞争。

第九，**把迁移失败与不收敛混为一谈**。前者查前置条件，后者查运行期变量，方向不同。

第十，**把「迁移快」当成「业务无感」**。总时长短不代表停机窗口短，业务感知由后者决定。

行文至此，把本篇落点收在两条原则上。其一，架构即权衡——热迁移用复杂度换中断时间，而「能不能收敛」最终取决于业务写入与网络带宽的对比，这是业务特征决定的，不是配置能绕过的。其二，复杂性不会消失只会转移——共享存储消除了磁盘搬运的复杂度，却把复杂度集中到了内存收敛与 CPU 兼容性上，这正是本篇逐一拆解的对象。下一篇从「单次操作」转向「实验方法」：如何建立性能基线、如何注入干扰负载、以及如何跨 Guest 与 Host 定位问题。相邻的生命周期与疏散流程见 [[云原生/OpenStack/05 实例生命周期与迁移实战|05 实例生命周期与迁移]]，宿主机失联的恢复决策见 [[SRE/CVM集群可靠性工程/04 宿主机失联——故障检测、Fencing、Masakari 与恢复决策|04 宿主机失联]]。

这张表把热迁移的性能问题按现象归类；使用时先区分「失败」与「不收敛」——前者查前置条件，后者查运行期变量，方向完全不同。表中「关键证据」是各现象最直接的判据，若判据不成立，应当回到第 7 章的三层定位重新收敛。

还有一条通用纪律值得写在表前：**判断迁移是否正常，看的是「剩余量的趋势」而不是绝对量**。趋势下降说明在收敛，只是快慢问题；趋势不降说明无法收敛，应当及早决策。

| 现象 | 优先怀疑 | 关键证据 |
| :--- | :--- | :--- |
| 迁移长时间不结束 | 脏页速率高于传输 | `domjobinfo` 剩余页趋势 |

| 迁移期间业务变慢 | 流量竞争 | 网络利用率与业务延迟 |
| 迁移直接失败 | CPU 兼容性 | 虚机实际用到的特性 |
| 目标端启动慢 | 固有开销 | 设备状态与启动自检 |

## 口径与事实说明

- 命令与观察方式取自 2026 年 9 月的现场记录，属某时点实践，不构成唯一正确用法。
- 机制描述（预拷贝与后拷贝、脏页与收敛、停机窗口、CPU 模型、迁移带宽）属于 KVM 与 QEMU 的稳定行为。
- 迁移带宽、并发与限速的具体取值属业务决策，需与业务方共同确定。
- 迁移策略（是否启用自动收敛、是否使用后拷贝）应按业务等级确定。
- 文中涉及的内存大小与带宽数值仅为算例，不代表实际配置。
- 文中命令均为只读观测类操作，实际迁移与限速调整须走审批并回读。
- 本文与本专栏其余篇目共享同一套观察方法与口径纪律，相邻篇目已展开的机制不在此重复推导。
- 迁移能力需按集群变化定期复核，历史结论不代表当前状态。
- 本文的判据与顺序可直接用于同类虚拟化实现，具体参数需按现场调整并以实测为准，不照搬数值，并定期复核。
