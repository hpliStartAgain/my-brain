# 写后自检清单（逐项过，不达标改写后再交付）

## A. 骨架与事实
- [ ] frontmatter/摘要/章节编号/思考题等仓库骨架完整（改写稿：技术资产零丢失——图、表、代码、链接、参考资料逐项核对）
- [ ] 所有技术事实、版本号、年份准确；引用给出来源
- [ ] `[[wiki链接]]`、mermaid 主题与目标系列一致

## B. L1 语言
- [ ] 转折用「但/不过」，无「但是……所以」式冗余连词堆叠
- [ ] 举例用「譬如」；自称用「笔者」；有「我们/你/不妨」的读者对话感
- [ ] 全文零感叹号
- [ ] 长句多逗号为主流节奏；短句（≤15 字）占比 ≤5%，且只出现在强调位
- [ ] 首次术语「中文（English）」格式，此后可直接用英文
- [ ] 无「换句话说/综上所述/总而言之」式口语化复述与套话

## C. L2 结构
- [ ] 开场为三式之一（历史锚点/范围限定引矛盾/设问），未直接抛定义列清单
- [ ] 章节推进有叙事弧：为什么→是什么→代价→取舍，而非知识点平铺
- [ ] 结尾为四式之一，无口号式升华、无「希望本文对你有帮助」

## D. L3-L5 认知
- [ ] 讲技术先讲来龙去脉（起源/年份/取代了什么）
- [ ] 争议话题有正反逐项权衡，落点「因地制宜/只有选择没有高下」
- [ ] 结论段落落在 8 条核心命题中的 1-2 条上
- [ ] 每个大章节至少 1 个贴切比喻，比喻后紧跟技术限定

## E. L6 视觉
- [ ] 加粗 1-2 处/千字，加在术语/结论/对比词上
- [ ] 方案对比用表格；列表无深层嵌套
- [ ] 图表前有引导句

## F. 去 AI 味交叉检查（与 style-rules.md 冲突时以 style-rules.md 为准）
- [ ] 无「不是 A 而是 B」假靶子句式滥用
- [ ] 无「值得注意的是/总而言之/综上」堆叠
- [ ] 无每段等长的机械节奏；比喻不密集轰炸（每章 1-2 个足够）
- [ ] 术语首次出现有中文（English）对照，无中英夹杂失衡

## G. 红线
- [ ] 未搬运原书/原文章的具体观点、案例与比喻原句（复刻写法，不复刻内容）
- [ ] 未虚构年份、版本号、性能数字；不确定的事实已标注或查证

## H. 交付硬指标（delivery-standard.md）
- [ ] 篇幅达标：技术深度专栏 12000-16000 中文字 / 500+ 行（算法专栏单独标准）
- [ ] 论述五问齐全：是什么→为什么出现→不这样会怎样→如何落地→边界与反例
- [ ] 无 ASCII 表格；Mermaid 为 dracula 主题且语法可渲染
- [ ] 所有 `[[双向链接]]` 已核实目标文件真实存在
- [ ] tags 为 inline 数组且符合全局映射（Golang/Kubernetes/大小写/连字符）
- [ ] 增强类任务：原有正确内容零删减，frontmatter 结构完整
