# 六层风格规则（凤凰架构 DNA）

> 全部规则经 43.4 万字语料统计 + 深度阅读验证，正例取自已确认的 demo《03 OpenTelemetry 统一标准》。

## L1 语言 DNA

### 句子
- **长句为主，多逗号铺陈**：平均句长 90 字上下，一句常含 2-4 个逗号分句，铺垫完再收一个句号。信息密度优先，不做口语化拆解。
- **短句（≤15 字）只用于强调**，占比控制在 5% 以内。用法：一句一段下结论、转折处立论。
  - 正例：「但 OpenTracing 有两个致命缺陷。」（独立成段，引出下文）
- **禁用感叹号**（语料中几乎为零）；情绪靠措辞与节奏，不靠标点。
- 设问适度（每千字 0-1 处），用于推进论述或破除直觉，问后要么立即作答、要么明说后文回答。
  - 正例：「为什么要单独定义 API 层？……答案藏在库开发者的两难处境里」

### 标志词（高频验证）
| 用 | 不用 | 语料频率 |
|---|---|---|
| 但 / 不过 / 然而（少用）| 但是……所以 | 但 15.1/万 vs 然而 1.1/万 |
| 譬如 | 比如 / 例如 | 譬如 11.0/万 vs 比如 0.02/万 |
| 笔者（自称）| 我 | 笔者 7.1/万 |
| 我们 / 你 / 不妨（拉读者）| 各位读者 | 我们 6.0/万 |
| 由此可见 / 请注意 / 换句话说（少用）| 综上所述 / 总而言之 | — |

### 中英混用
- 首次出现：**中文（English）**，如「可观测性（Observability）」「跨度（Span）」；可附「后文直接用英文指代」。
- 此后直接用英文：Trace、Span、gRPC、Kubernetes 等缩写、协议名、产品名不翻译。

### 标点
- 括号密度高（3.9/千字）：放英文对照、词源、版本、补充说明。
- 破折号用于插入解释或转折补充；分号、省略号少用。

## L2 文章结构

### 四套结构模板
1. **历史演进类**：起源与命名(20%) → 关键阶段/人物/事件(50%) → 转折对比(20%) → 展望/过渡(10%)
2. **概念原理类**：定义与范围限定(15%) → 核心概念拆解(40%) → 原则/算法/流程(35%) → 适用与局限(10%)
3. **流程实践类**：引入(10%) → 按流程阶段展开(60%) → 工具映射(20%) → 结论建议(10%)
4. **叙事前言类**：背景故事/类比(30%) → 核心设问(30%) → 展开(40%)

### 开头三式（任选其一，禁止直接抛定义列清单）
1. **历史锚点/权威引用**：「2019 年 5 月，正当所有人以为这场标准之争还要再打十年的时候……」
2. **先定义范围再引出矛盾**：「本章所说的分布式事务特指……」（限定边界后立刻给冲突）
3. **设问/反直觉反问**：「这些问题一定要由软件系统自己来解决吗？」

### 过渡词库
然而 / 但 / 不过 / 不妨换个思路 / 由此可见 / 行文至此 / 请注意

### 结尾四式（禁止口号式升华）
1. 反问过渡式（引出下一话题）
2. 展望留有余地式：「但未来究竟如何发展，目前仍然言之尚早」
3. 结论收束式：「由此可见……因地制宜地选用合适的方案才是唯一有效的做法」
4. 自然结束式（工具链/事实收尾）

### 小标题
名词短语为主，4-6 字：「追踪与跨度」「通信的成本」「三个基本问题」；章节内编号（1.1/1.2）沿用目标系列惯例。

## L3 选题逻辑

- **切入顺序**：历史/起源先行 → 问题与定义 → 标准与实现分离评价。讲一个技术，先讲它从哪来、取代了什么、为什么长成这样。
- **三重视角交织**：历史观察者（年份/论文/人物）+ 系统设计当事人（为什么这样设计）+ 与读者对话者（你/我们/不妨设想）。
- **写什么**：概念本质、演进脉络、适用前提、利弊权衡、常见误区、与其他方案的关系。
- **不写什么**：安装命令、框架 API 手册、Hello World 教程、无观点的知识罗列。
- **争议不回避**：设「不足与争议」式小节，列观点逐一回应，落点「只有选择问题，没有高下之分」。

## L4 素材策略

- **权威序列**：博士论文/学术论文 > RFC/标准规范 > 厂商文档 > 名人名言/典故 > 个人工程经验。引用三段式：直引原文 + 中文转述 + 技术解读。
- **年份是演进锚点**：2010 Dapper、2016 OpenTracing、2019 OpenTelemetry——讲演进必给年份；版本号精确到 x.x；规模数字给量级（10PB、百万实例）。
- **贯穿性案例承载抽象概念**：一个具体场景（如「购买一本书的订单流转」）讲遍多个机制，不每节换例子。
- **比喻要求**：每个大章节至少 1 个贴切比喻，从生活或工程经验取材，比喻后紧跟技术限定，防止失真。
  - 正例：「Collector 扮演的是物流分拨中心的角色——商家只管把包裹交给最近的分拨中心……哪天换了收货地址，改的也只是分拨中心的调度单」
  - 正例：「这就好比只颁布了度量衡的标准，却没有人去铸造符合标准的钱币」
  - 反例：生硬套用不相干领域的大词（「就像区块链一样」）。

## L5 认知框架（8 条核心命题，落点取向）

1. 没有银弹，架构即权衡——「有利有弊才需要决策，有取有舍才需要权衡」
2. 架构不是发明出来的，是演进出来的
3. 出错是必然，可靠系统由「会死会重生」的部件构成
4. 实践标准取代规范标准，警惕过度规范
5. 没有放之四海皆准的方案，因地制宜
6. 演进的驱动力是「可替换/可重生」，而非单纯性能
7. 复杂性不会消失只会转移；基础设施应替应用隐藏复杂性
8. 架构者的第一职责是做决策权衡

**使用方式**：不必每篇全占，但每篇的结论段落必须落在其中 1-2 条上；全文对技术的态度是「先理解为什么，再评价好不好」，不吹不踩。

**论证套路 5 式**（按需组合）：
1. 先立定义/标准，再评实现与争议
2. 先追溯词源/历史，再对比方案
3. 正反利弊逐项权衡（CAP 拆成放弃 C/A/P 分别分析式）
4. 具体工程场景承载抽象概念
5. 比喻/故事降低抽象门槛

## L6 视觉风格（my-brain 适配版）

- **保留仓库骨架**：frontmatter（title/date/tags/aliases）、`**摘要：**` 段、`## 第 N 章` 编号、`> [!note]` callout、文末参考资料与思考题——这些是 my-brain 惯例，优先级高于原书形态。
- **加粗**：1-2 处/千字，加在术语中英并列、原则结论、分类对比词上；禁止整句加粗滥用。
- **表格**：用于方案对比（维度 × 方案）；列表适度，不层层嵌套。
- **mermaid**：沿用目标系列主题（my-brain 现行 `%%{init: {'theme': 'dracula'}}%%`）；图随文走，图前有引导句。
- **代码块**：少而精，注释解释「为什么」而非「是什么」。
- **`[[wiki链接]]`**：首次提及的站内已有概念加链接，沿用目标系列用法。

## 迁移红线（复刻写法，不复刻内容）

- 原书的具体观点、案例（Fenix's BookStore）、比喻原句不得直接搬运；比喻要为当前主题重新创作。
- 用户本次明确指令 > 目标系列骨架惯例 > L1/L6 规则 > L5 认知取向。
