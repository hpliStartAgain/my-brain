# my-brain 专栏交付标准（硬指标）

> 来源：TODO.md「专栏内容质量整改计划」「Agent 沙箱技术专栏创作」等历史任务沉淀，2026-09-04 经老板确认转为正式规范。与 style-rules.md 并列使用：本文件管"达不达标"，style-rules.md 管"像不像"。

## 1. 篇幅基准（按分组）

| 分组 | 单篇目标 | 说明 |
|---|---|---|
| 技术深度专栏 | **12000-16000 中文字 / 500+ 行** | 范文：`content/分布式架构/数据密集型系统架构实战/11 数据拆分之困.md`（JVM 专栏按此增强后篇均 13769 字/592 行） |
| 数据结构与算法 | 不追求万字 | 题解类，重点是补"为什么这样解"的说理，摆脱纯代码堆砌 |
| 专栏导览（00） | 不设下限 | 讲清主线与阅读顺序即可 |

统计口径：篇均中文字符数（CJK）、篇均行数、篇均 Mermaid 图数、篇均 Callout 数、篇均双向链接数。

## 2. 论述逻辑（扩写五问）

每篇按此主线组织，缺项即未达标：

1. **是什么**：概念定义与边界
2. **为什么出现**：解决什么问题、取代了什么
3. **不这样会怎样**：反事实论证（没有它会踩什么坑）
4. **如何落地**：机制/流程/配置，配图与代码
5. **边界与反例**：适用前提、失效场景、常见误区

## 3. 结构骨架

```markdown
---
title: "NN 标题"
date: YYYY-MM-DD
tags: [Tag1, Tag2]        # inline 数组，遵循 §5 tags 规范
aliases: []
---

# NN 标题

**摘要：**

（一段话：背景 → 本文路线 → 回答哪两个问题）

---

## 第 1 章 …（正文，章节编号沿用系列惯例）

…

---

## 参考资料

1. …

---

> [!note] 思考题
> 1. …
```

- 改写已有文章时：frontmatter、既有 mermaid/表格/代码/链接/思考题**全保留**，只重写叙述性文字。
- 新系列从 0 建时：含 `00 专栏导览.md`。

## 4. 格式硬指标

| 项 | 规则 |
|---|---|
| 表格 | 禁止 ASCII 表格，一律 Markdown 表格；用于方案对比（维度 × 方案） |
| Mermaid | 统一 `%%{init: {'theme': 'dracula'}}%%` 主题；图前有引导句；语法必须可渲染 |
| Callout | Obsidian 语法：`> [!note]` / `> [!info]` / `> [!warning]`；用于定位说明、金句、思考题 |
| 双向链接 | `[[目标]]` 写入前必须用 `find_file_by_name` 核实文件真实存在；JVM 专栏曾发现大量路径不一致死链 |
| 代码块 | 少而精，注释解释"为什么" |
| 加粗 | 1-2 处/千字，加在术语/结论/对比词（与 style-rules.md L6 一致） |

## 5. tags 规范（全局映射摘要）

- 格式：inline 数组 `tags: [A, B]`，去重、清理空格
- 大小写统一：`kubernetes→Kubernetes`、`etcd→ETCD`
- 同义词合并：`Go/Go语言→Golang`、`K8s→Kubernetes`、`java/Java语言→Java`
- 连字符统一：`LSM Tree→LSM-Tree`、`Bloom Filter→BloomFilter`、`troubleshooting→trouble-shooting`
- 完整映射字典见 TODO.md「专栏 Tags 标签规范化项目」章节

## 6. 批量执行与验证流程

1. 每批开始前先 `read` 目标文件确认现状，先修复死链
2. 并行派发 `subagent_general` 后台子代理，提示词包含：目标路径、范文路径、本文件规范全文
3. 完成后统一验证：跑篇幅统计对比前后、抽查 2-3 篇（frontmatter / Mermaid 渲染 / 链接有效性）
4. 更新 TODO.md 勾选项 + CHANGELOG.md 追加记录

## 7. 红线

- 保留原有正确内容不删减（增强是扩写，不是重写替换）
- 不破坏 frontmatter 结构（Quartz 构建依赖）
- 不虚构年份、版本号、性能数字
